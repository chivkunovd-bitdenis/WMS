# 006-picking-order — Порядок в листе подбора не совпадает с порядком ленты

## Дословно

> ### 6. Порядок в листе подбора не совпадает с порядком ленты · ТЗ пишется
>
> Слова владельца: «это надо, да».
>
> Оператор идёт по бумаге и клеит наклейки с ленты. Состав документов уже совпадает — это
> сделано двадцать первого. Порядок разный и сойтись сам не может: лента печатает по заказам,
> а лист подбора схлопывает заказы в товарные строки и сортирует по алфавиту. Человек ищет
> соответствие глазами и ошибается.
>
> Должно стать: один главный порядок для обоих документов и сквозная нумерация позиций, чтобы
> номер в листе совпадал с номером наклейки в ленте.

Раздел «Из разбора дефектов», строки 92–102 файла `night/zadachi-2026-08-21.md`.

## Что сейчас

Задействовано два документа, живущих на разных путях сортировки, и ни один не носит сквозной
номер позиции.

**Печатный лист подбора (бумага).** Формируется в браузере функцией `printPickingList`
(`frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx:1196`) из массива `pickingRows`
(там же, `:1084`). Строки собираются в `Map`, ключ — `order.product.id`, порядок — первое
появление продукта в `workspace.orders`. Явной сортировки нет. Итоговый HTML строится
`buildFbsPickingListPrintHtml` (`frontend/src/screens/v2/fbsUx.ts:68`), и первая колонка
называется «№» и содержит `index + 1` (`fbsUx.ts:77`) — то есть номер уже печатается, но
это порядковый номер группы товара, а не позиции-заказа.

Данные `workspace.orders` приходят с бэка из
`get_supply_workspace` → `build_worklist_items` (`backend/app/services/fbs_worklist_service.py:326`),
а сами заказы грузятся отношением `FbsSupply.orders` без `order_by`
(`backend/app/models/fbs_supply.py:126`) — то есть в порядке, который вернёт БД. Никакого
устойчивого «алфавита» тут нет: если бумагу перепечатать после того, как в поставку что-то
добавили, порядок может измениться.

**Диалог «Лист подбора» с чекбоксами** (модалка `FfFbsPickList`,
`frontend/src/screens/v2/FfFbsPickList.tsx`). Тянет `GET /operations/fbs-supplies/{id}/picking-list`
из `backend/app/services/fbs_supply_service.py:1574` (`get_picking_list`). Там заказы
группируются по кортежу `(article, sku_code, size, product_name)` и сортируются
`sorted(groups.items())` (`fbs_supply_service.py:1601`). То есть это тот самый «схлопывание в
товарные строки и сортировка по алфавиту» из слов владельца — но по артикулу WB, а не по
имени товара, и это отдельный от бумаги документ.

**Лента наклеек.** Печатается через `POST /operations/fbs-supplies/{id}/order-print-tape`
(`backend/app/api/fbs_supplies.py:1547`), сервис — `print_fbs_order_tape`
(`backend/app/services/fbs_order_tape_print_service.py:77`). Сервис уважает порядок
`order_ids`, который ему пришёл в теле (`_orders_in_requested_order`,
`fbs_order_tape_print_service.py:294`). Тело собирает фронт в двух местах:
`openBulkOrderMarkingPrint` (`FfFbsSupplyWorkspace.tsx:938`) передаёт
`orders.map((order) => order.id)`, а кнопка «Печать всего» (`:1776`) передаёт `packingOrders`.
`packingOrders` сортируются по `product.name.localeCompare(b.product.name, 'ru')` и затем
по `wb_order_id` (`FfFbsSupplyWorkspace.tsx:1226`).

На сам стикер номер позиции не наносится: WB отдаёт готовый PNG, а в HTML-обёртке
(`frontend/src/utils/printMarkingCodeLabel.ts`, шаблоны `buildWbOrderQrLabelHtml` и
`buildCzLabelHtml`) есть только сам QR/Data Matrix и текстовые поля бренда/КМ; никакого
«№ 27» рядом нет.

**Итого расхождение.**
- Бумажный лист: сгруппирован по товару, порядок групп — как БД вернула, номер «№» — это
  номер группы, а не позиции.
- Лента: одна наклейка на заказ, отсортирована по имени товара плюс `wb_order_id`, номера
  позиции нет вообще.
- Диалог-модалка «Лист подбора» с чекбоксами: своя третья сортировка — по артикулу.

Даже если групповой порядок бумаги случайно совпадёт с алфавитом (совпадает часто, потому
что БД возвращает заказы в порядке вставки, а вставка идёт партиями по товару), сойтись
номера всё равно не могут: одна строка бумаги — это N наклеек ленты, а «№» на бумаге
считает строки, не заказы. Владелец сформулировал ровно это: «сойтись сам не может».

WB на каждом стикере уже печатает свой человеко-читаемый номер `sticker_code` вида
«5694425 3074» (`backend/app/models/fbs_order.py:214–219`), и бумажный лист его печатает в
колонке «Стикер» (`fbsUx.ts:86`). Формально сверка возможна по этому номеру — но она и есть
то самое «искать глазами», которое ловит ошибки: цифры длинные и без общего порядка.

## Что должно быть

Один общий порядок сортировки заказов, применённый и к бумажному листу подбора, и к ленте
наклеек, плюс явный сквозной номер позиции 1..N, напечатанный в обоих документах.

Поведение:
1. Сервер определяет канонический порядок заказов внутри поставки — стабильный, детерминированный,
   не зависящий от порядка вставки в БД. Ключ сортировки живёт в одном месте
   (`fbs_supply_service.py` рядом с `get_picking_list`) и используется обоими путями:
   `get_picking_list` и `print_fbs_order_tape`.
2. Каждой позиции в этом порядке присваивается номер `1..N`.
3. Бумажный лист подбора печатает по одной строке на заказ (или, если решено сохранить
   группировку по товару, — печатает в строке товара список номеров: «№ 3, 7, 12»), и
   первая колонка — этот номер.
4. Лента наклеек печатается ровно в том же порядке, и на каждой наклейке рядом со стикером
   WB печатается тот же номер крупным шрифтом. Один номер = одна наклейка = одна строка на
   бумаге.
5. Печать «выборки заказов» (не всей поставки) наследует номера от полной канонической
   нумерации поставки — иначе повторный дозаказ ленты собьёт нумерацию.

Признак, что получилось: оператор, глядя на бумагу, читает номер позиции, находит ленту с
тем же номером, клеит — и ни разу не сверяет длинный `sticker_code`. Тестом это ловится
как «в HTML печатного листа и в HTML/PDF ленты подряд идущие номера позиций одинаковые для
одного и того же `order.id`».

## Тип

`фича`

Это правка из раздела «Из разбора дефектов», но она меняет форму двух артефактов
(добавляется номер на ленту, меняется структура/сортировка бумажного листа), требует
согласовать вид номера на стикере и решить судьбу группировки по товару на бумаге. Одним
патчем это не закрыть, поведение задевается в бэке (сервис ленты + сервис подбора) и на
фронте (сборка `pickingRows` и `packingOrders`). Ремонт багов и слоёв без макета — не про
эту карточку.

## Вопросы и допущения

**Первое ведро — меняет суть.** По этим вопросам лучше не сделать, чем сделать не то. Ответы
владельца определяют, как будет выглядеть результат.

1. **Какой ключ сортировки объявить каноническим?** Варианты, которые встретились в коде:
   а) артикул селлера (как сейчас в `get_picking_list`); б) имя товара по русской локали +
   `wb_order_id` (как сейчас в `packingOrders`); в) код ячейки хранения (логично для маршрута
   по складу); г) `deadline_at` (по срочности). Влияние: тот же оператор при одной и той же
   поставке получит разные бумаги в зависимости от выбора. Допущение на ночь: имя товара по
   русской локали, дальше `wb_order_id` — как минимум это уже стоит в ленте.
2. **Одна строка на заказ или строка на товар с колонкой «№№ позиций»?** Владелец говорит
   «номер в листе совпадал с номером наклейки в ленте» — это буквально «одна строка = одна
   наклейка». Но бумажный лист сейчас группирует, чтобы оператор видел общий объём одного
   товара в одном месте (это удобно на складе). Влияние: строк на бумаге станет столько же,
   сколько наклеек — на поставке из 150 заказов это 150 строк вместо 20–30. Допущение на
   ночь: остаёмся с группировкой по товару, но в первую колонку выводим список номеров
   позиций, а в ленте номер на стикере — с этим оператор ищет одну наклейку, а не собирает
   разброс.

**Второе ведро — частности.** Иду с допущением, помечаю явно.

3. **Как рендерить номер на стикере?** WB присылает готовый PNG, поверх него можно наложить
   номер в HTML-обёртке (`buildWbOrderQrLabelHtml` в `printMarkingCodeLabel.ts:230`) — большим
   шрифтом в углу. Второй вариант — печатать номер отдельным маленьким «предваряющим» блоком
   перед каждой наклейкой (лишний расход ленты, зато не портит поле стикера). Допущение:
   рисуем крупный номер в правом верхнем углу поверх стикера WB, шрифт как у `.cz-brand`
   (~5–6 pt на 58×40), не перекрывая штрихкод/QR.
4. **Что делать с диалогом-модалкой «Лист подбора» (`FfFbsPickList`) с чекбоксами
   Собрал/Упаковал?** Он использует свой ключ сортировки (по артикулу). Логично, чтобы и он
   пошёл в общем порядке — тогда и оператор с планшетом видит те же номера позиций.
   Допущение: перевести и модалку на канонический порядок, номера позиций показать колонкой.
5. **Печать выборки заказов из поставки (не всей).** Сейчас `openBulkOrderMarkingPrint`
   отдаёт в тело именно выбранные `orders`. Если применить локальную нумерацию 1..N —
   номера собьются между полной печатью и дозаказом. Допущение: номер позиции считается
   всегда от полного канонического списка поставки, при частичной печати наклеек будут
   пропуски (например, «5, 8, 9») — это правильно, оператор увидит, что часть уже
   отпечатана.
