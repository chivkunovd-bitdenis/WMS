## Что сейчас

Оператор сегодня получает три пересекающихся, но противоречащих друг другу картины
«готовности» задания. Разберу по шагам, откуда «зелёное» берётся и почему WB-вердикт до
строки заказа так и не доходит.

**1. Словарь вердиктов знает шесть слов из бесконечного набора WB.** Функция-переводчик
`map_wb_decision_to_meta_status` (`backend/app/services/fbs_marking_service.py:138–152`)
принимает строку `decision` из ответа `POST /api/marketplace/v3/orders/meta` и сопоставляет
её с нашим внутренним статусом. В таблице ровно восемь ключей: `accepted`, `filled`,
`rejected`, `pending`, `allowedwithoutcheck`, `allowed_without_check`, `replacementrequired`,
`replacement_required`. Всё остальное — возвращает `None`. Реальный список значений,
которые WB отдаёт в проде, в кодовой базе не задокументирован; в тестах фикстур с живыми
значениями нет. Владелец говорит «справочник не знает ни одного реального значения» —
значит на боевых ответах эта функция стабильно попадает в ветку `None`.

**2. Что происходит, когда `decision` из WB не распознан.** Дальше по цепочке —
`_apply_meta_detail_to_marking` (`fbs_marking_service.py:465–482`) кладёт в
`marking.meta_status` результат `derive_meta_status(check_status=..., decision=..., has_value=True)`
(`fbs_marking_service.py:155–177`). Если `map_wb_decision_to_meta_status` вернул `None`, а
`check_status` (числовой check из meta-ответа) тоже пуст, срабатывает последний фолбэк:
`if has_value: return META_STATUS_ASSIGNED`. То есть код есть — значит «присвоен», без
всякой оглядки на то, что маркетплейс отдал. В `order.meta_details_json` при этом
складывается сырое `{decision: <как пришло от WB>, value: ...}` — ниоткуда не читается как
человекочитаемая метка.

Дополнительно: есть мёртвая функция `_meta_details_from_wb` (`fbs_marking_service.py:256–269`),
которая честно ставит `META_STATUS_UNKNOWN`, если `decision` не распознан. Её никто не
вызывает — живой путь идёт через `_meta_details_from_markings` (см. `fbs_marking_service.py:525`).
Слово `unknown` в справочнике `FBS_META_STATUSES` есть, но в реальные данные не попадает.

**3. Где живёт «оптимистичное «можно»».** На фронте, файл
`frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx:137`:
```
const MARKING_ACCEPTED_STATUSES = ['accepted', 'assigned', 'pending', 'allowed_without_check', 'ok']
function isOrderMarkingReady(order) {
  if (order.metadata.required.length === 0) return true
  const accepted = order.metadata.states.filter((state) => MARKING_ACCEPTED_STATUSES.includes(state.status))
  return accepted.length >= order.metadata.required.length
}
```
Фронт считает заказ «маркировочно готовым», если у всех требуемых видов есть хоть какой-то
непровальный статус — включая `assigned` (мы только привязали код, WB о нём ещё не знает)
и `pending` (WB ещё думает). Это и есть та самая оптимистичная линза: строка в задании
упаковки красится в зелёный, ставится ✓, потому что `orderPrintDone = sticker.applied &&
isOrderMarkingReady(order)` (`FfFbsSupplyWorkspace.tsx:1233–1237`). Оператор видит зелёный
маркер задолго до любого подтверждения WB.

Строгое серверное правило прямо рядом: `compute_delivery_allowed`
(`fbs_marking_service.py:286–301`) считает заказ готовым к сдаче **только** при
`meta_status ∈ {accepted, allowed_without_check}`. То есть бэк и фронт разошлись:
`isOrderMarkingReady` (фронт) — набор из пяти статусов, `compute_delivery_allowed` (бэк) —
набор из двух. Это расхождение и создаёт эффект «показал зелёное, а сдать не даёт».

**4. Строка заказа на экране FBS-заказов сейчас не показывает вердикт вообще.** В
`frontend/src/screens/v2/FfFbsOrdersScreen.tsx:342–355` есть единственный признак
маркировки для строки — `metadataProblem`: возвращает красный чип «Отклонено WB», если у
какого-то `state.status ∈ {rejected, replacement_required}`, или «Не хватает честных
знаков: N» по количеству `missing`. Всё остальное (assigned, sending, pending, unknown) —
пустая ячейка, никакой подписи. То есть между «код только привязан» и «WB подтвердил» на
экране заказов нет ни одного видимого состояния. Оператор их не различает.

**5. Гейт «на сдаче» действительно строгий и работает.** Владелец это подтверждает.
Проверил в коде:
- `_build_delivery_checks` (`backend/app/services/fbs_shipment_service.py:398–517`) для
  каждого заказа зовёт `compute_delivery_allowed`; если False — добавляет чек
  `marking_not_allowed` с сообщением «Метаданные WB не допускают передачу.», `ok=False`.
- `deliver_supply` (`fbs_shipment_service.py:789+`) при попытке сдачи ловит WB-ответ
  `MetaValidationFail` и превращает его в 409 `meta_validation_fail` — WB запрещает,
  система тоже запрещает, но уже во время физической сдачи, когда всё уже упаковано и
  этикетки наклеены.

**6. Что видит владелец «на всех двадцати шести».** Как это складывается на боевом
складе:
- заказы синхронизируются с WB, у большинства `required_meta_json = ['sgtin']`;
- оператор привязывает код (сканирует или печатает из пула) — `_assign_printed_code_to_order`
  (`fbs_order_tape_print_service.py:508`) ставит `meta_status = pending`, вызывает
  `compute_delivery_allowed` → `False`, записывает `metadata_delivery_allowed = False`;
- фоновый автопулл (`fbs_autopoll_service.py:225–258`) вызывает `sync_order_marking_statuses`,
  та зовёт `POST /orders/meta` в WB, парсит ответ. В сегодняшнем боевом ответе
  `decision`-значения нашей таблице неизвестны (см. п.1) — статус остаётся `pending` или
  скатывается в `assigned`;
- фронт вокруг `isOrderMarkingReady` (п.3) видит эти статусы как «готово», строку красит
  в зелёный, ✓ ставит;
- на попытке сдачи серверный гейт всё равно отбивает `marking_not_allowed` — и это тот
  момент, о котором владелец говорит «на сдаче блокировка есть и работает».

Итого: цепочка ломается в трёх местах — (а) неполный словарь вердиктов на бэке (задача
№1 `wm-status-reading` про то, чтобы вообще правильно спрашивать; здесь — про то, чтобы
правильно разбирать ответ), (б) оптимистичный набор «готовых» статусов на фронте,
(в) полное отсутствие поля «вердикт WB» в строке заказа на экране FBS-заказов.

## Что должно быть

Оператор, глядя на строку заказа сразу после привязки кода, видит одно из трёх состояний
человеческими словами: `ждём WB` (мы отправили, ответа ещё нет), `WB принял` (verdict
подтверждён), `WB отказал: <причина>` (verdict отрицательный, оператор сразу видит
причину). Никаких «зелёная строка без ответа» больше не бывает.

Правило готовности одно на бэке и фронте: заказ считается готовым к сдаче только когда
хотя бы один вид маркировки требуется и все требуемые виды получили `accepted` или
`allowed_without_check` от WB. Промежуточные `assigned`, `pending`, `sending`, `unknown`
— это «ждём», а не «готово».

Словарь вердиктов расширен под реальные значения, которые WB присылает сегодня. Любое
непонятное значение падает в `unknown` (а не в `assigned`), оператор видит явное
«ответ WB не распознан — обратитесь в поддержку», код не считается принятым.

Признак «сдавать можно» на самой поставке (кнопка «Передать в доставку» и совокупный
прогресс) поднимается только тогда, когда все заказы поставки — с подтверждённым
вердиктом WB. Серверный гейт `_build_delivery_checks` и так строгий, менять его не надо;
надо убрать оптимизм с фронта и подтянуть его к тому же правилу.

Признак, по которому поймём, что получилось: возьми боевой день, где 26 заданий с
негативным вердиктом WB. Сейчас у всех у них строка на экране FBS-заказов пустая (или
зелёная в задании упаковки), а гейт срабатывает только в момент сдачи. После правки —
строка каждого из 26 заданий сразу после первой синхронизации с WB показывает `WB отказал:
<текст>`, оператор видит проблему в течение первого автопулла (≤ N минут), а не в конце
дня.

## Тип

`домен`. Задача не сводится к переименованию флага или починке одного эндпоинта: надо
собрать боевые значения `decision` из WB (в коде их сейчас нет), договориться о переводе
восьми-плюс статусов в короткие человеческие ярлыки, привести фронт и бэк к одному
правилу «готово», добавить в строку заказа на S-03 новую зону «вердикт WB» и решить, что
показывать, пока автопулл ещё не прошёл. Плюс это цепляется за задачу №1
`wm-status-reading` (без рабочего чтения статусов нечего и отображать), но одно другим
не заменяется: №1 — про способ спрашивать, №2 — про способ показывать.

## Вопросы и допущения

**Вопрос владельцу (частность, карточка едет дальше, помечено допущение).** Какие
конкретно значения `decision` возвращает WB на боевых ответах `POST /orders/meta`? В коде
таблица `map_wb_decision_to_meta_status` знает только `accepted / filled / rejected /
pending / allowedwithoutcheck / replacementrequired`. По словам владельца «справочник не
знает ни одного реального значения», значит на проде приходит что-то другое (варианты из
опыта WB: `waitingForAnswer`, `checking`, `declined`, `approved`, `wait`, `error`, …).
**Допущение:** до подтверждения будем расширять словарь по факту — собрать значения из
логов WB за последнюю неделю в отдельном тикете, добавить в таблицу маппинга, всё
непонятное отдаётся оператору как «ответ WB не распознан».

**Вопрос владельцу (частность, допущение).** «Прямо в строке заказа» — это ровно строка
на экране FBS-заказов (S-03), или ещё и в задании упаковки внутри workspace (`packing`
tab)? **Допущение:** делать в обоих местах. На экране FBS-заказов — в колонку `Статус`
(правее статуса заказа), в задании упаковки — на ту же строку рядом с хвостом кода
Честного знака. Одна и та же формулировка в обоих местах, чтобы оператор не путался.

**Вопрос владельцу (частность, допущение).** Что показывать в первые секунды после
привязки кода, пока автопулл ещё не сходил в WB? Технически это статус `pending` (мы
записали, отправили `PUT /orders/{id}/meta`, но `_sync_order_meta_from_wb` ещё не вернул
свежий вердикт). **Допущение:** пишем «ждём WB», без цветного маркера. Как только
автопулл принесёт `accepted` — переключаем на «WB принял» зелёным, `rejected` — на «WB
отказал» красным с причиной из `marking.reason`.

**Вопрос владельцу (частность, допущение).** Гейт `isOrderMarkingReady` на фронте
используется, чтобы красить строки упаковки зелёным и считать `printedOrdersCount`. Если
подтянуть его к серверному правилу (только `accepted`/`allowed_without_check`), эти
метрики просядут визуально: оператор перестанет видеть «упаковано столько-то» до
подтверждения WB, а увидит только после. **Допущение:** это ожидаемо и правильно —
цветовой маркер «готово» должен опираться на подтверждение WB, а не на факт печати. Если
надо визуально показать промежуточное состояние («упаковано, но WB не подтвердил») —
делаем отдельный жёлтый маркер, не смешивая с «готово».
