# 06 · Порядок в листе подбора совпадает с порядком ленты

## Дословно

> Оператор идёт по бумаге и клеит наклейки с ленты. Состав документов уже
> совпадает — это сделано двадцать первого. Порядок разный и сойтись сам не может:
> лента печатает по заказам, а лист подбора схлопывает заказы в товарные строки и
> сортирует по алфавиту. Человек ищет соответствие глазами и ошибается.
>
> Должно стать: один главный порядок для обоих документов и сквозная нумерация
> позиций, чтобы номер в листе совпадал с номером наклейки в ленте.

Источник — `night/zadachi-2026-08-21.md`, строки 92–102, раздел «Из разбора
дефектов», подзаголовок «Порядок в листе подбора не совпадает с порядком
ленты · ТЗ пишется». Слова владельца в чате: «это надо, да».

## Что сейчас

- по коду — двух главных функций (лист подбора и лента) касались последний раз

  подбора, а не молча короче` (это и есть «состав уже совпадает» из
  первоисточника — но там правился только состав, а не порядок и не нумерация);
- по веткам — ни в `etalon`, ни в `fix/picklist-size-20260819`,
  ни в `review/pick-and-binding-fixes-20260816`, ни в
  `integration/fbs-fixes-20260821`, ни на удалённых
  ветках нет ни поля-номера позиции, ни признаков общего порядка;
- по локальному дереву — `git status --porcelain` ни строкой не касается
  `fbs_supply_service.py`, `fbs_order_tape_print_service.py` или
  `FfFbsPickList.tsx`;
- по коду ищем `position`, `№`, `sequence`, `order_index` в
  `FfFbsPickList.tsx` и `get_picking_list` — пусто.

Как формируются оба документа сейчас, по коду:

**Лист подбора** — `backend/app/services/fbs_supply_service.py:1574`,
функция `get_picking_list`:

- проходит по `supply.orders`, складывает заказы в словарь по ключу
  `(article, sku_code, size, product_name)` и считает количество (`groups[key] += 1`);
- отдаёт `PickingListItem(article, sku_code, size, product_name, quantity)`,
  список отсортирован `sorted(groups.items())` — то есть по кортежу, где первым
  идёт `wb_article`, потом `sku_code`, потом `size`, потом название. Фактически
  сортировка «по WB-артикулу по алфавиту».
- ни у `PickingListItem` (`fbs_supply_service.py:129-135`), ни у
  `FbsPickingListItemOut` (`backend/app/api/fbs_supplies.py:158-163`) поля с
  номером/индексом позиции нет.
- фронт `frontend/src/screens/v2/FfFbsPickList.tsx:200-215` рисует таблицу
  «Товар — Размер — Кол-во — Собрал — Упаковал» — колонки «№» нет.
- одна строка = один товар/размер, с колонкой «Кол-во» = сколько таких заказов
  в поставке (то самое «схлопывает заказы в товарные строки»).

**Лента** — `backend/app/services/fbs_order_tape_print_service.py:294-308`,
функция `_orders_in_requested_order`:

- берёт заказы из поставки строго в том порядке, в котором фронт прислал
  `order_ids` в теле запроса;
- на каждый заказ печатает свой блок (QR стикера WB + при необходимости КЗ),
  то есть одна наклейка = один заказ, а не один товар.

Порядок `order_ids` формирует фронт в
`frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx:1223-1231` — там `packingOrders`
собирается так:

```
return [...workspace.orders].sort((a, b) => {
  const byName = a.product.name.localeCompare(b.product.name, 'ru')
  if (byName !== 0) return byName
  return a.wb_order_id - b.wb_order_id
})
```

и потом кнопка «Печать всего» (`FfFbsSupplyWorkspace.tsx:1776-1787`) отправляет
`order_ids: packingOrders.map((order) => order.id)` в
`printFbsOrderTape` (`frontend/src/screens/v2/fbsApi.ts:854`), а сервер печатает
ровно в этом порядке.

Итого расхождение из первоисточника подтверждается кодом дословно:

- **разный ключ сортировки** — лист сортирован по `wb_article` (латиница/цифры
  артикула селлера), лента — по `product.name` с русской локалью;
- **разная гранулярность** — в листе одна строка на товар+размер с колонкой
  «Кол-во», в ленте одна наклейка на заказ, и если один товар лежит в трёх
  заказах, ему в листе одна строка, а в ленте три наклейки подряд;
- **нет ни в одном из документов сквозного номера**, по которому оператор мог
  бы сопоставить наклейку и строку.

Оператор действительно вынужден искать соответствие глазами: по названию
товара и размеру. Ошибиться легко: если в поставке два похожих SKU одного
размера, лента разложит их вперемешку по `localeCompare`, а лист сгруппирует и
даст только «два товара по столько-то штук».

## Что должно быть

Один главный порядок и сквозная нумерация — так, как сформулировал владелец.

- Общий порядок описывается один раз на сервере — единая сортировка заказов
  поставки (не в двух местах, как сейчас). Ленте передаётся именно этот
  порядок, лист подбора считается по нему же.
- В листе подбора одна строка соответствует **одному заказу-наклейке**,
  а не «схлопнутой» товарной группе. У строки появляется колонка «№» —
  сквозной номер 1..N. У N-й наклейки в ленте — тот же номер N рядом с QR
  (крупно, чтобы читалось глазами), либо, если печатать номер на самой
  наклейке технически нельзя, — номер выводится хотя бы в шапке блока
  каждой наклейки в верстке ленты (`FbsOrderTapeOrder`).
- Товары одного SKU/размера идут в ленте подряд (внутри группы порядок
  стабильный — по `wb_order_id`), и в листе подбора эти строки тоже идут
  подряд, с последовательными номерами. Оператору не приходится искать
  «то же самое имя» — он читает номер с наклейки и находит строку в листе
  по номеру.
- Отметки «Собрал/Упаковал» в листе перевязать со строкой заказа, а не с
  ключом «артикул+размер» (`markKey` из `FfFbsPickList.tsx:44-46`) — иначе
  при трёх заказах одного размера один чекбокс закроет все три.

Признак, по которому увидим, что получилось: на тестовой поставке из
15–20 заказов лист подбора и лента печатаются с одинаковой нумерацией 1..N;
оператор, взяв наклейку №7, находит в листе строку №7 без прокрутки и поиска
по названию; отметка «Собрал» на строке №7 не двигает состояние строк №8 и
№9, даже если у них тот же артикул и размер.

## Тип

Ничего сегодня не «поломано»: и лист, и лента печатаются, состав их совпадает.

## Вопросы и допущения

- **Допущение (лист становится per-order).** Первоисточник напрямую этого не
  говорит, но фраза «номер в листе совпадал с номером наклейки в ленте»
  сама по себе требует 1:1 нумерации, а наклейка — на заказ. Значит и строка
  в листе тоже на заказ. Альтернативный вариант — оставить лист товарным
  и писать в нём диапазоны «№1–№3, №4–№5» — оператору читать сложнее, поэтому
  я иду в per-order. Вопрос владельцу: подтвердить, что грouping по товару
  в листе подбора убираем.
- **Вопрос владельцу.** Какой ключ считать «главным порядком»? Варианты:
  (а) по названию товара с русской локалью (сегодня так печатает лента),
  (б) по WB-артикулу селлера (сегодня так сортирует лист),
  (в) по времени приёма заказа с WB (естественный «хронологический»),
  (г) по маршруту сборки — если у товаров есть ячейки, идти по ячейкам,
  чтобы оператор проходил склад одной петлёй.
  Пока в разборе принял (а) как «наименьшее изменение поведения ленты»,
  но выбор оставляю за владельцем — он влияет на реальную скорость сборки
  на складе.
- **Вопрос владельцу.** Печатать номер позиции **на самой наклейке WB**
  можно не всегда: наклейка приходит от WB как готовый QR/PNG, дорисовать
  на ней цифру — это отдельная работа с шаблоном. Если это дорого,
  предложение — печатать номер в шапке блока над наклейкой (в
  `FbsOrderTapeOrder`) большим шрифтом. Подтвердить, что это приемлемо.
