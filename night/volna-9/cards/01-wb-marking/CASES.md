## Добавлено

В этой сессии заведены (все новые, ранее файлы S-03.md / S-14.md / S-15.md были пусты):

- **S-03-TC-001** — нормальный ход: WB принял коды → кнопка «Сдать поставку» активна.
- **S-03-TC-002** — WB вернул `rejected` → кнопка серая, `meta_status = 'rejected'` в БД.
- **S-03-TC-003** — первый тик WB-молчания: UI не меняется, в `meta_details_json` появляется `wb_orphan_candidate_at`.
- **S-03-TC-004** — второй тик WB-молчания: `reserved`-код уходит в `available`, строка маркировки переходит в `missing`, в `marking_code_events` запись `wb_orphaned`.
- **S-03-TC-005** — код `printed` при orphan: ссылка снимается, физический статус кода не меняется (консервация), событие `wb_orphaned` пишется.
- **S-03-TC-006** — ответ 429 от WB: пачка пропускается, состояние заказов не портится, лог-запись в сервере.
- **S-14-TC-001** — задание упаковки с `meta_status = 'missing'` не редактируемо.
- **S-14-TC-002** — задание упаковки с `meta_status = 'accepted'` редактируемо.
- **S-15-TC-001** — после orphan-сверки задание появляется в списке «Ожидает маркировки» без кода.

## Примечание к проверке

Карточка 01 — **бэк-only**, UI-файлы не меняются. Поэтому:

- Кейсы S-03-TC-001 и S-03-TC-002 проверяются через браузер: открыть экран, дождаться тика автополлера, обновить страницу — кнопка либо активна, либо серая.
- Кейсы S-03-TC-003…006, S-14-TC-001, S-14-TC-002, S-15-TC-001 требуют дополнительного шага: заглянуть в БД прямым запросом или через отладочный API, чтобы убедиться в точных значениях полей (`meta_status`, `marking_code_id`, `marking_code_events.event_type`). Без этого шага проверка кейса считается неполной.
- Тексты чипов и точные формулировки на кнопках в этой карточке **не меняются** — судья проверяет существующие тексты разметки, не новые (новые тексты — карточка 02).

## Ломающие кейсы

Стресс-сценарии, которые ищут, где система ломается, а не просто не работает. Ожидаемый результат — не «упадёт», а «система сделает вот это».

### S-03 (FBS workspace)

| Номер | Название | Источник риска |
|---|---|---|
| **S-03-TC-007** | Новый код привязан между первым и вторым тиком orphan — флаг candidate сбрасывается | Оператор привязывает код именно в окне между тиками; система не должна orphan-ить свежий код через остаточный флаг |
| **S-03-TC-008** | WB «вспоминает» заказ на второй тик — orphan не происходит | WB нестабилен, первый тик молчит, второй отвечает; код должен остаться в пуле |
| **S-03-TC-009** | WB возвращает успешный 200 с пустым orders[] — все строки уходят в missing на втором тике | Полный сброс клиентом своих КИЗ через внешний скрипт; система должна вернуть ВСЕ reserved-коды в пул |
| **S-03-TC-010** | Один заказ с двумя kind (sgtin + uin), WB возвращает только sgtin — orphan только по uin | Частичный ответ WB; orphan строго per-kind, не per-order |
| **S-03-TC-011** | WB отвечает 5xx несколько тиков подряд — ни одного ложного orphan | Длительный сбой WB не должен обнулять коды из пула |
| **S-03-TC-012** | WB возвращает повреждённый JSON — пачка пропускается, флаги не ставятся | Неожиданный формат ответа; система не должна ставить orphan-кандидатов |
| **S-03-TC-013** | Оператор нажимает «Сдать поставку» из устаревшей вкладки после orphan — бэк блокирует | Классический стейл-UI: бэк обязан перечитывать `metadata_delivery_allowed` из БД |
| **S-03-TC-014** | Поставка переходит в следующий статус после первого тика orphan — флаг не срабатывает бессрочно | Гонка: поставка сдана, а orphan-кандидаты зависли в JSON навсегда (бесконечная задолженность флага) |
| **S-03-TC-015** | WB возвращает decision=null — unknown-статус, кнопка серая, не orphan | WB ответил, но вердикт не дал; код не возвращается в пул, кнопка серая |
| **S-03-TC-016** | Два воркера Celery запускают autopoll для одного продавца одновременно — lock предотвращает двойную работу | Двойное начисление orphan-событий или двойной возврат кода в `available` |
