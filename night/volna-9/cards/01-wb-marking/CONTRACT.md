Карточка **бэк-only** (тип «домен»). UI-слой в этой карточке не редактируется: правки

## Контракт

### Что меняется

**1. Метод чтения меты у Wildberries.**
Все чтения меты идут одним рабочим маршрутом
`POST /api/marketplace/v3/orders/meta`, пачками до 100 идентификаторов
(`MAX_MARKETPLACE_FBS_BATCH`). Батч-возможность клиента используется и в автополлере
(`sync_marking_statuses_for_assembling_supplies`) — раньше он в цикле дёргал одиночные
запросы. Одиночный `GET /api/v3/orders/{orderId}/meta`
(`wildberries_client.py:953::fetch_marketplace_order_meta`) убирается как мёртвый и опасный
код: именно он отвечал «Not Allowed» с декабря и создавал иллюзию «зелёного» экрана.

Пользователь этих правок напрямую не видит: экран получает те же поля модели, но с
настоящими значениями от WB, а не с дефолтом `new / assigned / null`.

**2. Хранение ответа WB — per marking row.**
Для каждой строки `FbsOrderMarking` пишутся реальные значения из ответа WB:
- `check_status` — из вложенного `meta.checkStatus` для пары `(kind, value)`
  (`new / checking / ok / error / no_check`);
- `meta_status` — производный от `metaDetails.decision`
  (`missing / assigned / sending / pending / accepted / allowed_without_check /
   rejected / replacement_required / unknown`) через существующий `derive_meta_status`;
- `reason` — из `metaDetails.reason` или `metaDetails.message`;
- `meta_details_json` — сырой блок ответа по этому `kind` (для отладки, наружу не течёт).

Для каждого `FbsOrder` пересчитываются `metadata_delivery_allowed` и
`metadata_last_checked_at` — уже существующие поля, семантика та же.

**3. Правило «WB кода не знает» (orphan-сверка).**
После штатного применения `status_map` / `details_by_kind` вызывается новая приватная
функция `_reconcile_orphans_after_sync` в `fbs_marking_service.py`. Она работает **только
на успешном ответе 2xx**. На 4xx (кроме 429), 5xx, сетевой ошибке, невалидном JSON — сверка
не запускается, ни одна строка orphan-кандидатом не становится.

Двухтиковое подтверждение (защита от разовой репликационной дырки WB):
- **Тик 1.** Строка помечается флагом `meta_details_json['wb_orphan_candidate_at'] = now`.
  Пользовательский `meta_status` **не меняется**. На экране всё выглядит как было —
  пользователь этот тик не увидит.
- **Тик 2** (флаг уже стоит, прошёл хотя бы один полный цикл автополла) — перевод:
  - `meta_status = missing`, `check_status = new`, `reason = "Код отсутствует у WB"`;
  - в `meta_details_json` дописывается блок
    `{ wb_orphan_at, previous_meta_status, previous_check_status }` — для аудита;
  - если у строки был `marking_code_id`, код берётся `SELECT FOR UPDATE` и решение по нему
    принимается по его физическому статусу:
    - `reserved` → возврат в пул: `MarkingCode.status = available`,
      `FbsOrderMarking.marking_code_id = None`;
    - `printed` / `applied` → **консервация**: физический статус не трогаем (лента могла
      уйти на упаковке; вернуть в пул — гарантированная двойная наклейка и штраф ЦРПТ),
      только `FbsOrderMarking.marking_code_id = None`;
    - `introduced / shipped / transferred / void / defective / replaced` → только
      снимаем ссылку `marking_code_id = None`;
  - пишется событие `MarkingCodeEvent(event_type='wb_orphaned',
    meta_json={previous_status, previous_meta_status, wb_order_id, kind})`.
    Новое значение `EVENT_WB_ORPHANED = "wb_orphaned"` добавляется в
    `MARKING_CODE_EVENT_TYPES` в `backend/app/models/marking_code.py`
    (поле — `String(32)`, БД-CHECK нет, миграции не нужны).

После обхода — пересчёт `order.metadata_delivery_allowed` штатным путём.

**4. Устойчивость к 429 у Wildberries.**
На 429 — не более двух retry с backoff по `Retry-After`, ограниченным одной секундой
(верхняя граница — чтобы один задыхающийся селлер не растягивал тик автополла для
остальных). Правило уже реализовано в ветке `fix/wb-meta-method-20260821`.

### Что убирается

- **Мёртвый одиночный `GET .../meta`** (`wildberries_client.py:953::fetch_marketplace_order_meta`)
  и его импорты. Он не вызывается, но оставлять «второй путь через год» опаснее, чем
  удалить: в SVERKA роль зафиксировала это как решение продукта, а не пересказ ТЗ владельца.
- **Ложное «всё в порядке» на экране** при глухом WB. После правки
  `compute_delivery_allowed` перестанет давать `True` по причине «WB просто молчит»:
  через два тика WB-молчания по строке она сама переедет в `missing`, а `missing`
  не входит в `_META_DELIVERY_OK`, значит `metadata_delivery_allowed` станет `False`.
  Кнопка «Сдать поставку» на S-03 автоматически станет серой — благодаря уже
  существующей проверке в `fbs_shipment_service._build_delivery_checks`. Новых
  UI-веток блокировки здесь **не появляется** (это карточка 02).

Отдельно: **на всех трёх экранах никаких новых колонок, чипов, кнопок и alert-полос

неопасно: `missing` на строке = сдача заблокирована = ошибка обратима (кнопка серая),
никакая печать/списание не срабатывает без действия оператора.

### Состояние успеха

- В БД по каждой строке `FbsOrderMarking` заполнены `meta_status`, `check_status`,
  `reason`, `meta_details_json` из реального ответа WB (а не `new / assigned / null`).
- `FbsOrder.metadata_last_checked_at` обновляется каждый цикл автополла.
- Для той поставки на 25 заданий из ISTOCHNIK: после первого тика — все 25 строк
  помечены `wb_orphan_candidate_at`; после второго — все 25 в `missing`, 25 кодов из
  пула (те, что были `reserved`) вернулись в `available`, `marking_code_id = None`;
  `metadata_delivery_allowed = False` у каждого из 25 заказов; в `marking_code_events`
  ровно 25 записей `wb_orphaned` с контекстом. Экран без действий оператора начинает
  показывать эти заказы как «требует маркировки» — через существующие тексты S-03/S-14,
  задача 02 позже подберёт более точный текст.

### Состояние ошибки WB (пропуск тика без порчи БД)

- **429** — до 2 retry с backoff по `Retry-After` (≤1 сек). Если WB устойчиво 429 —
  пачка пропускается, лог `fbs autopoll marking batch sync skipped`, следующий тик
  попробует. Ни одна строка orphan-кандидатом не становится.
- **4xx (кроме 429) / 5xx / сетевая ошибка** — пачка пропускается целиком, лог,
  локальное состояние не меняется.
- **Невалидный JSON** — `WildberriesClientError('invalid_response')`, пачка пропускается,
  локальное состояние не меняется.
- **Нет токена продавца** — заказ пропускается с явной причиной (как сейчас).

На UI это выглядит как «данные не обновились этот цикл» — специального сообщения не
выводим (R-24: не рапортуем об успехе того, чего не делали, и симметрично — не
рапортуем об ошибке того, что попробуем через 15–30 секунд). Логи и метрики — на бэке.

### Состояние пустоты

- **Продавец без заказов в `assembling`.** Автополлер не делает ни одного HTTP-запроса —
  список пачек пуст. Никаких строк в БД не меняется, никаких событий.
- **Пачка вернула пустой `orders[]`.** Успешный 2xx с пустым массивом. Все строки этой
  пачки становятся `wb_orphan_candidate_at` на первом тике, `missing` на втором.
  Это допустимая ветка: именно так выглядит «клиент удалил свои КИЗ скриптом».

### Идемпотентность и повторы

- Все переходы идемпотентны: если тик прошёл, но транзакция откатилась, следующий тик
  увидит те же строки в тех же статусах и повторит без побочек.
- Возврат `reserved → available` защищён `SELECT FOR UPDATE`.
- «Внезапно нашёлся»: если WB после orphan-цикла снова вернёт эту `(kind, value)`,
  штатный `_apply_meta_detail_to_marking` перезапишет `meta_status` на актуальный,
  `reason` очистится. `marking_code_id` остаётся `None` — новую физическую привязку
  делает оператор (у него на экране это выглядит как обычное «ожидает маркировки»).
  Старая ссылка сохранена в `meta_details_json['previous_*']` для аудита.
