## Как это решают другие

Веб-поиск в этой ночной среде отрезан, поэтому опираюсь на общеотраслевые практики,
которые в разных формулировках лежат в официальных доках FastAPI/Uvicorn, Celery,
Wildberries Marketplace API v3, Shopify Admin API, Amazon SP-API и Ozon Seller API.
Для каждого утверждения ниже указан класс источника, чтобы можно было проверить
руками до dev-карточки.

### 1. CPU-bound работа в async-веб-серверах

Общее правило Python-мира: **однопоточный event loop не любит длинную синхронную
работу**. Любая операция, которая длится больше десятков миллисекунд и не отдаёт
управление через `await`, останавливает обслуживание всех соединений этого воркера.
Практика делится на три уровня.

- **Уровень 1 — вытолкнуть в thread pool.** В FastAPI: либо объявить обработчик
  как `def` (тогда фреймворк сам вызывает его через `starlette.concurrency.run_in_threadpool`),
  либо изнутри `async def` дёргать `fastapi.concurrency.run_in_threadpool(...)` или
  `anyio.to_thread.run_sync(...)`. Тредпул по умолчанию — 40 воркеров у AnyIO; можно
  ограничить через `CapacityLimiter`. Годится для чистого CPU-bound кода без побочных
  эффектов и с редкими вызовами (для нас — PDF-слияние 155–500 наклеек, ≤3 секунд,
  раз в минуты). Ссылки: FastAPI docs → «Concurrency and async / await», Starlette
  docs → `run_in_threadpool`, AnyIO docs → `to_thread.run_sync`.
- **Уровень 2 — вынести в Celery-воркер.** Более тяжёлые пакетные операции
  (агрегация, отчёты, массовый импорт) уходят в отдельный процесс. У нас Celery уже
  живёт (`celery_worker` в `docker-compose.prod.yml:63`) и режется независимо от API.
  Класс источника: Celery Best Practices (offloading long-running tasks) и типовые
  runbook'и от Sentry/GitLab/Instagram (public engineering blogs).
- **Уровень 3 — process pool / отдельные worker'ы Uvicorn.** Через `--workers N`
  (или Gunicorn с `uvicorn.workers.UvicornWorker`). Каждый воркер — отдельный
  процесс: GIL внутри воркера один, но между воркерами блокировки нет. Классическая
  формула — `2 * CPU + 1`. Цена — линейный рост RAM: каждый воркер тянет свой набор
  импортов и SQLAlchemy engine. Ссылки: Uvicorn docs → «Deployment», Gunicorn docs
  → workers.

**Как применяем к нам.** Владелец назвал одну ручку (`/marking-codes/label-artifact-tape`),
и она попадает под уровень 1: до 500 PDF, каждое слияние ≤3 с, изолированная функция
без побочных эффектов, вызывается редко. Уровень 2 — избыточен: нет очереди на печать,
оператор ждёт ответ синхронно, отдельная задача Celery только добавит хранилище и
пуш ответа обратно. Уровень 3 включим позже, но только после уровня 4 (RAM), иначе
второй uvicorn-процесс сожрёт свободные 145 МБ и упадёт первым.

### 2. Поллинг маркетплейса: «дельта каждый тик» + «полный обход редко»

Все крупные маркетплейс-API строят интеграцию по одному шаблону.

- **Wildberries Marketplace API v3.** Есть отдельная ручка «новые задания»
  `GET /api/v3/orders/new` — она отдаёт только заказы, ещё не подтверждённые
  продавцом, максимум 1000 записей, без пагинации. Есть ручка полного списка
  `GET /api/v3/orders` — с курсором `next` и `dateFrom`, до 1000 записей на страницу.
  Оба лимитированы: официально «Marketplace» имеет общий rate limit порядка сотен
  запросов в минуту на токен, но собственно `/orders/new` считается «дешёвым», а
  `/orders` — «дорогим». Ссылка: WB Marketplace API документация, раздел «Сборочные
  задания» (`suppliers-api.wildberries.ru`).
- **Ozon Seller API.** Аналогично: `POST /v3/posting/fbs/list` c cursor, `POST /v3/posting/fbs/unfulfilled/list`
  для «висящих» отправлений. Owner-side sync тоже двухуровневый: пуш webhook'ами
  + периодический sweep. Класс источника — публичная документация Ozon Seller API.
- **Amazon SP-API / Shopify Admin.** Тот же принцип: «`getOrders?LastUpdatedAfter=`»
  для delta, `NextToken`/`endCursor` для полного обхода. Реальные интеграторы (например,
  ShipStation, ChannelAdvisor) описывают в своих inbound-документах: «poll delta каждые
  1–2 минуты, full reconciliation раз в 15–60 минут». Класс источника — публичные
  developer docs SP-API и Shopify Admin.

**Как применяем.** Ровно то, что просит владелец. Каждые 3 минуты мы сейчас крутим
и лёгкую ручку, и полный обход — 25 селлеров × до 10 страниц × 5300 заказов ради
1–5 новых. Отсекаем полный обход в отдельную beat-задачу с редким расписанием. Что
именно «редкое» — ниже, в решении.

### 3. Пагинация списков заказов на экране

Стандартный паттерн больших операторских экранов (Shopify Orders, Amazon Seller
Central, Ozon кабинет продавца): **первая страница 25–100 строк + подгрузка**. Всё
подряд грузят только «архив за квартал» — и то с прогресс-баром. Реализация — cursor
(`endCursor` в Shopify, `NextToken` в Amazon), потому что offset при вставках новых
записей отдаёт кривые страницы. Для авто-обновления UI (тик 20–60 с) обновляется
**только первая страница** — если пользователь пролистал ниже, тик уже не трогает
его позицию.

**Как применяем.** На бэке курсор уже есть — использован в «Выбрать все» (`db52e9c`).
Фронтовая правка изолирована: `NEW_ORDERS_PAGE_LIMIT` 500 → 50, «Показать ещё»
(или auto-load на scroll). API не трогаем.

### 4. Память под Python-контейнерами с CPU-bound хвостом

Отраслевой минимум для Python-веб-сервера, который умеет PyMuPDF, Pillow, SQLAlchemy
и таскает бинарные BLOB'ы: **250–500 МБ на воркер в rest state**, пиковая — до 1 ГБ
на слиянии PDF. При swap ≥ 200 МБ latency растёт нелинейно (I/O страниц), процессы
OOM-killer'ит непредсказуемо. Best practice: **не запускать несколько независимых
Python-проектов на одной ноде без явного `mem_limit` в compose**, и **отделять API
от Celery-воркера как минимум по памяти**. Класс источника — общие docker/K8s
runbook'и, Twelve-Factor App, Sentry «Deployment Recipes».

**Как применяем.** Не поднимаем `--workers 2` до того, как RAM появится (сегодня
свободно 145 МБ). Оформляем документ инфраструктуре с двумя опциями: +4 ГБ RAM на
машину **или** переезд `asya-prod` на отдельную ноду (24 контейнера на одном хосте —
это симптом «дешёвого хостинга», а не архитектуры). До момента, когда RAM появится,
работаем по уровню 1 (thread pool) — этого достаточно, чтобы event loop перестал
стоять на PDF.

## Решение

Одна дорога — четыре независимые dev-карточки, каждая со своим замером до/после,
каждая перекликается с картой волны (`MAP.md`). Ни одна из них не зависит от другой
по коду; можно катить в любом порядке. Внутри карточки — минимальный, обратимый шаг.

### Карточка A — «Тяжёлая счётная работа уходит из общего потока» (Уровень 1)

**Файлы.** `backend/app/services/marking_code_service.py::build_label_artifact_tape_pdf`
(строки 643–667), `backend/app/services/marking_label_artifact_service.py`
(`merge_label_artifact_pdfs`, `merge_label_artifact_pdfs_for_print`,
`fit_label_artifact_pdf_to_page`, `pdf_bytes_to_png`, `extract_label_artifacts_from_pdf`),
`backend/app/api/marking_codes.py::post_label_artifact_tape_pdf` (1248–1264).

**Правка.** Все CPU-bound функции `marking_label_artifact_service` — чистые (нет
работы с сессией, нет побочных эффектов); оборачиваем их вызовы в
`await anyio.to_thread.run_sync(...)` или в `await run_in_threadpool(...)`. Внутри
`build_label_artifact_tape_pdf` цикл `for code_id ...` остаётся на event loop
(это чтение из БД, оно уже `await`); финальный `merge_label_artifact_pdfs_for_print`
уходит в тредпул. То же самое для `pdf_bytes_to_png` (используется в `HonestSignScreen`
и в превью наклейки).

**Замер до.** Скрипт для `docs/perf/2026-08-21-prod-slow-plan.md` (раздел 1):
`ab -n 100 -c 2 POST /marking-codes/label-artifact-tape` (body — 155 и 500 code_ids),
параллельно `while true; do curl -w '%{time_total}\n' /health; sleep 0.1; done`.
Ожидаемо: время `/health` в момент слияния — 1–3 с. Замер после: `/health` — 20–50 мс.

**Стоимость.** Дифф в трёх файлах на десятки строк, нет новых зависимостей (AnyIO уже
приходит с Starlette), нет миграций, нет фронта. Риск обратной несовместимости —
нулевой: сигнатуры функций сохраняются, меняется только точка вызова.

**Пограничный случай — `print_fbs_order_tape`.** Критик (`SVERKA.md`, находка 2) прав:
владелец её не упомянул. Значит **не в эту карточку**. Оставляю самостоятельной
подкарточкой **A′** («тот же приём для ленты заказов»), которую вытаскиваем после
того, как A прогонит замер и станет ясно, что thread-pool не съедает всё окно
uvicorn'а. Дорисовывать её сегодня не нужно.

**Пограничный случай — `NotificationBell` без `document.hidden`.** Критик (`SVERKA.md`,
находка 1) тоже прав: это идея аналитика, не требование владельца. Убираю из плана;
если через неделю выяснится, что колокольчик приносит заметный трафик — сделаем
отдельной карточкой рядом с S-04.

### Карточка B — «Частый цикл спрашивает только новые, полный обход редко»

**Файлы.** `backend/app/services/wb_marketplace_orders_service.py::sync_seller_orders`
(1449–1576), `backend/app/services/fbs_autopoll_service.py::poll_fbs_orders_all_sellers`
(289–361) и `poll_fbs_orders_for_seller`, `backend/app/tasks/background_jobs.py`
(новая задача), `backend/app/celery_app.py::beat_schedule` (17–38), `backend/app/core/settings.py`
(новая настройка `fbs_full_sweep_interval_sec`).

**Правка.**

- `sync_seller_orders` режется на две публичные функции: `sync_seller_orders_new_only`
  (тик — только `fetch_marketplace_orders_new` + upsert + `sync_order_statuses` + linker
  к поставкам) и `sync_seller_orders_full_sweep` (старый цикл `for _page in range(MAX_ORDERS_PAGES)`).
  Общий низовой код (`upsert_order_from_wb_row`, `sync_order_statuses`,
  `link_confirmed_orders_to_wb_supplies`) вытаскиваем во внутренние хелперы.
- Beat-задача `fbs-orders-autopoll` остаётся на 180 с и зовёт «легкую» ветку.
- Новая beat-задача `fbs-orders-full-sweep` — расписание `settings.fbs_full_sweep_interval_sec`,
  по умолчанию **1800 с (30 минут)**, зовёт «тяжёлую» ветку. Полный обход всех 25
  селлеров сегодня умещается в 2 минуты — при 30-минутном такте это 6.6% времени
  под WB, оставшиеся 93% минут свободны для оператора.
- `wb_seller_lock` в «тяжёлой» ветке **держим только на upsert-транзакции**, не на
  весь цикл страниц. Аргумент: полный обход идемпотентен, между страницами оператору
  можно вставить `POST /supplies/...` без риска потерять данные — следующий тик
  подхватит. **Допущение (см. ниже),** ставлю его под запись — если продакт решит,
  что лок нужен на весь sweep, переключаем `full_sweep_lock_full=True` одной строкой
  в настройках; сам механизм лока не меняем.

**Замер до.** Логи `fbs-orders-autopoll` за час: длительность цикла, число upserted
без изменения. Замер после: `fbs-orders-autopoll` — 5–15 с на 25 селлеров, скорость
`wb_seller_lock=free` при ручных операциях — 95%+ (замерить счётчик skipped за час
в логах).

**Стоимость.** Один сервис режется на три функции (без изменения сигнатур публичных),
одна новая beat-задача, одна настройка. Дифф ~200 строк, миграций нет. Ломающих
изменений нет — старая ручка `POST /fbs/sellers/{id}/sync-orders` (админский run)
продолжает работать: направляем её на «легкую» ветку с флагом `full=True` для
совместимости.

### Карточка C — «Списки грузятся страницами» (фронт)

**Файлы.** `frontend/src/screens/v2/FfFbsOrdersScreen.tsx::NEW_ORDERS_PAGE_LIMIT`
(строка 82), `load()` (533–592), `useEffect` тика (594–615).

**Правка.**

- `NEW_ORDERS_PAGE_LIMIT` 500 → **50**. Первая страница — 50 строк, кнопка
  «Показать ещё» под таблицей грузит следующие 50 (курсор с ответа сервера).
- Тик 30 с обновляет **только первую страницу** и делает merge поверх текущего state
  (добавляет новые id, обновляет статусы существующих; ниже прокрученные страницы
  не трогает).
- Вкладки «В работе / В доставке / Завершённые» — там `Promise.all([fetchFbsSupplyWorklist,
  fetchFbsWorklist], limit=500)`. Первая ручка возвращает поставки (десятки), лимит
  можно опустить до **100** без пагинации. Вторая ручка тут используется только
  чтобы найти «orders без supply» — тоже 100 достаточно (это уже edge-case).
- `document.hidden` уже проверяется на строке 604, менять не нужно.

**Замер до.** DevTools Network → вкладка «Новые» с 500 заказами: размер JSON, TTFB,
first paint. Ожидаемо — 800 КБ, 300 мс сеть, 1–2 с рендер. Замер после: 50 строк —
80 КБ, 100 мс сеть, 150 мс рендер.

**Стоимость.** Правка в одном файле фронта, ≤50 строк. API не меняем (курсор уже
поддерживается). Ломающих изменений нет.

**Обоснование лимита 50.** Пришло из отраслевой практики (Shopify Orders — 50 строк
по умолчанию, Amazon Seller Central — 25), плюс из живого замера соседней карточки
«Каталог селлера» (`0dea353`, `0c9c818`), где переход с 500 на 200 дал заметный
выигрыш при сохранении сценария. У «Новых FBS-заказов» частота обновления выше и
элемент строки тяжелее (миниатюра, чипы), поэтому берём 50.

### Карточка D — «На сервере запас памяти» (записка инфраструктуре, а не код)

**Артефакт.** Раздел 4 в `docs/perf/2026-08-21-prod-slow-plan.md`. Формат — таблица:
что есть сейчас, что предлагаем, что произойдёт после.

**Что предлагаем владельцу выбрать.**

- **Вариант D1 — увеличить RAM на текущей машине до 8 ГБ.** Стоимость — тариф
  хостинга. После этого можно поднять `--workers 2` в API (см. отдельный шаг ниже),
  Celery спокойно съест pdf-задачи, swap уходит в ноль. Риск — минимальный, откат
  тривиальный.
- **Вариант D2 — расселить проекты по разным нодам.** Сегодня на хосте живут 24
  контейнера трёх проектов. Wms уезжает на свою ноду 2 ГБ, соседние проекты остаются
  на текущей. Стоимость — тариф на вторую ноду, время на миграцию (нужен ручной
  ход по DNS/Caddy). Риск — временный downtime при переезде.
- **Вариант D3 — оптимизировать текущий образ.** Убрать `pymupdf` из dev-deps
  контейнера, если он не нужен в проде (проверить), выключить `.pyc`, добавить
  `mem_limit: 512m` на каждый контейнер. Не решает проблему, только маскирует;
  оставляем как гигиенический шаг после D1 или D2.

**Рекомендация — D1**, потому что это одно действие с известной ценой, а D2 требует
координации с двумя другими проектами. D3 — приложить как чек-лист вдогонку.

**Про `--workers N`.** Не включаем ни в этой карточке, ни в других. Ставим в
«следующая волна после D» отдельной микро-задачей: после D1 меряем `docker stats`
в бою, если запас RAM ≥ 1 ГБ — включаем `--workers 2`, ждём 24 часа, меряем
p95 latency, при отсутствии регрессий оставляем.

### Артефакт всей карточки

Один документ — `docs/perf/2026-08-21-prod-slow-plan.md` — четыре раздела в порядке
выше, у каждого три абзаца: замер до, правка (файлы и строки), критерий приёмки.
Из этого документа критик и следующий агент режут отдельные dev-карточки; резать
дальше в эту ночь не нужно, потому что тип задачи в источнике — «ТЗ пишется».

Файл `tasks/perf-prod-slow/` не создаём: это ночная волна 9, свои артефакты живут в
`night/volna-9/cards/05-prod-slow/`; на утро владелец решает, куда переносить.

### Варианты решения и цена

Рассматривал три варианта архитектуры, выбрал первый.

- **Вариант 1 (рекомендуемый) — четыре независимые dev-карточки под четыре
  требования.** Цена: каждая правка обратимая, замер до/после локальный, ни одна
  не блокирует другую. Минус — четыре PR вместо одного. Плюс — если C сломает
  фронт, A и B уже в бою и никто не заметил.
- **Вариант 2 — один большой рефакторинг «уходим на Celery».** Собрать все PDF/
  агрегации/поллеры в единый background layer через Celery. Цена — 2–3 недели,
  ломает пять сервисов, ставит новую точку отказа (Celery на дешёвой машине с
  свопом). Отклоняю: владелец просил «замеры до и после, чтобы можно было
  предъявить», а не «архитектурный редизайн».
- **Вариант 3 — только инфра, кода не трогаем.** Поднять `--workers 4`, добавить
  RAM, увеличить интервал автополла — и всё. Цена — быстро, но не решает 1
  (внутри воркера всё равно event loop встаёт), не решает 3 (500 записей по сети
  всё равно тащатся) и оставляет «5300 заказов ради 1–5 новых» как норму. Отклоняю

## Границы

**Что делаем мы (WMS).**

- Заворачиваем PDF-функции в тредпул (карточка A). Никаких новых сервисов, никакой
  очереди — просто `run_in_threadpool` на месте.
- Режем `sync_seller_orders` на две функции и заводим вторую beat-задачу (карточка B).
  Настраиваемый интервал через `settings.fbs_full_sweep_interval_sec` (по умолчанию
  1800 с).
- Меняем `NEW_ORDERS_PAGE_LIMIT` с 500 на 50 и добавляем «Показать ещё» на фронте
  (карточка C).
- Пишем записку инфраструктуре про RAM (карточка D) — отдельный документ, не код.

**Что делает Wildberries (маркетплейс).**

- `GET /api/v3/orders/new` продолжает быть дешёвой ручкой для delta-поллинга.
  Мы её не меняем и не отменяем.
- `GET /api/v3/orders` продолжает быть тяжёлой ручкой для full sweep. Мы просто
  дёргаем её реже (30 минут вместо 3).
- WB сам управляет статусами (`sync_order_statuses`) — эту ветку оставляем в
  «лёгком» тике, потому что статусы меняет он, а не мы.

**Что делает человек руками.**

- Оператор нажимает «Обновить» в `FfFbsOrdersScreen` — синхронно запускает
  `runFbsOrdersSync` (существующая ручка). Она вызывает **полный** цикл (и легкий,
  и full sweep) — сохраняем это поведение как «ручной срочный синк», потому что
  оператор жмёт её, когда что-то реально не пришло. Автопусть режем, ручную не режем.
- Владелец / DevOps выбирает вариант D1 или D2 после утреннего просмотра и
  оформляет заявку хостингу.
- Владелец решает, оставлять ли `wb_seller_lock` на full sweep целиком (см.
  открытый вопрос 2).

**Что не в границах этой карточки.**

- Оптимизация базы (индексы, EXPLAIN) — владелец сказал «база ни при чём», не
  трогаем.
- Отдельный экран «настройки автоопроса» — не нужен, всё через env-переменные.
- Кэш заказов на фронте между вкладками — идея аналитика, из требования не следует.

## Риски (что осознанно НЕ делаем в этой волне)

- **Не поднимаем `--workers N` без RAM.** Второй uvicorn-процесс сегодня съест
  свободные 145 МБ и уронит первый воркер. Ждём D1.
- **Не выносим PDF в Celery.** Оператор ждёт ответ синхронно; async-очередь потребует
  переделки UI (poll job status) без ощутимой выгоды.
- **Не меняем клиент WB.** Не добавляем retry-с-паузой, не меняем `httpx.AsyncClient`,
  не крутим `MAX_ORDERS_PAGES`. Полный обход остаётся ровно такой же по нагрузке —
  просто идёт в 10× реже.
- **Не переписываем `wb_seller_lock` таблицу.** Меняем только область удержания в
  sweep-ветке; сама блокировка остаётся тем же advisory-локом.
- **Не трогаем базу.** Индексов не добавляем, EXPLAIN не гоняем — владелец явно
  сказал «база ни при чём».
- **Не оптимизируем колокольчик, S-04 и другие тики.** Владелец назвал S-03. Если
  после карточек A–D остаётся хвост — оформляем следующей волной.
- **Не режем `_MAX_LABEL_ARTIFACT_TAPE = 500`.** После вывода в тредпул общий цикл
  перестаёт болеть, снижать планку нет причин.
- **Не делаем pagination на «В работе / В доставке / Завершённые» с бесконечной
  прокруткой.** Только опускаем лимит до 100 — там объёмы десятки-сотни, не тысячи.
- **Не завариваем API «job status» для длинных операций.** Пока укладываемся в
  секунды на тредпуле.

## Допущения (что решил за владельца и почему)

- **Допущение 1 — интервал полного обхода 1800 с (30 мин).** Из двух вариантов
  продакта (30 или 60 мин) беру нижнюю границу, потому что WB не пишет нам webhook'ов
  про ручные правки продавца в кабинете, и 30 минут — верхняя терпимая задержка
  для видимости этих правок оператору. Настройка `settings.fbs_full_sweep_interval_sec`
  оставлена переменной, поменять — одна строка в `.env`.
- **Допущение 2 — `wb_seller_lock` в full sweep удерживается только на upsert-транзакции.**
  Full sweep идемпотентен: если оператор вставил ручное действие между страницами,
  следующий тик подхватит. Ручные операции — вещь редкая и болезненная (оператор
  реально ждёт), лучше не дать sweep их блокировать. Если владелец решит иначе —
  флаг `full_sweep_lock_full=True` в настройках переворачивает поведение обратно.
- **Допущение 3 — размер страницы «Новых» = 50 строк, кнопка «Показать ещё».**
  Аргументы: Shopify default 50, тяжёлая строка (миниатюра + чипы), тик 30 с
  обновляет только первую страницу. Auto-load на scroll — вторым шагом, если
  ручная кнопка утомит.
- **Допущение 4 — планка `_MAX_LABEL_ARTIFACT_TAPE = 500` не меняется.** После
  тредпула общий цикл не встаёт, значит нет причин наказывать оператора урезанием.
- **Допущение 5 — `print_fbs_order_tape` в этой карточке не трогаем.** Критик
  прав: владелец её не называл. Оставляю подкарточкой A′ на замере после A.
- **Допущение 6 — `NotificationBell` в этой карточке не трогаем.** По той же
  причине: не в требовании владельца, идея аналитика.
- **Допущение 7 — «26 секунд» из замера владельца = 30-секундный тик минус время
  запроса.** Другого поллера в этом файле нет, `document.hidden` уже проверяется.
  Точность цифры «до/после» это не портит: сравниваем те же числа на том же
  рабочем месте.
- **Допущение 8 — Вариант инфры D1 (поднять RAM до 8 ГБ) — рекомендуемый.**
  Одно действие, известная цена, откат тривиальный. D2 (расселить проекты) требует
  координации с двумя другими проектами. D3 (образ) — гигиенический шаг после D1.

## Открытые вопросы для продакта

Не больше пяти, все — деньги/процесс, которые я не могу решить сам.

1. **Инфра-вариант D1 или D2?** Ночью запишу в записку рекомендацию «D1 + D3
   вдогонку», утром продакт (или сам владелец) выбирает окончательно. Cost
   разный: D1 — рост тарифа хостинга (RAM с 4 до 8 ГБ), D2 — вторая нода + миграция.
2. **Full sweep — 30 мин или 60 мин?** Я поставил 30. Продакт решает, какая задержка
   видимости ручных правок продавца в кабинете WB допустима: 30 минут дают вдвое
   лучшую свежесть, 60 минут — вдвое меньше трафика к WB. Живёт как настройка.
3. **`wb_seller_lock` на полный sweep — короткий (только upsert) или полный (весь
   цикл)?** Я поставил короткий. Продакт решает, важнее ли идемпотентность и
   отзывчивость оператора (мой выбор) или строгая последовательность (лок на весь
   sweep, оператор ждёт до 2 минут).
4. **Опустить лимит на `_MAX_LABEL_ARTIFACT_TAPE = 500` до 250 после тредпула?**
   Я оставил 500. Возможно, продакт считает, что печать 500 наклеек за раз —
   антипаттерн и оператору лучше бить на пачки по 100. Ответ ничего не ломает,
   меняет только константу.
5. **Куда деть подкарточку A′ («тот же приём для `print_fbs_order_tape`»)?**
   В следующую волну как отдельная фича или в довесок к A через день после её
   замера? Я поставил «следом за A», потому что риск ровно тот же и подтвердить
   выгоду в бою на однотипной ручке проще.
