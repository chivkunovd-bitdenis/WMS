# ARCH · 04-warehouse-switch · Склад мешает работать

## Кратко

Рекомендуемый вариант: **глобальный «контекст склада» в сессии оператора + один общий
переключатель в шапке + сканер склада + автоматический межскладской перенос в момент
подбора вместо костыля.** Ниже — почему именно так и что это стоит.

## Как это решают другие

Внешнего API у этой задачи нет: это внутренняя доменная модель фулфилмент-центра. Смотрю
на то, как «склад» устроен у зрелых WMS и фулфилмент-платформ.

- **SAP EWM (Warehouse Number = верхний контекст сессии).** Оператор при входе выбирает
  Warehouse Number (например, «W101»), и все транзакции RF-сканера, монитора и веб-клиента
  работают только внутри него. Перенос между складами (Stock Transfer between Warehouse
  Numbers) — это отдельный документ (`ME21N` + `MIGO 351`), его нельзя сделать «попутно»
  при подборе. Плюс модели: у оператора нет двусмысленности, любой скан однозначен. Минус
  для нашей задачи: слишком тяжело для случая «клиент работает как с одним складом» —
  переносы там никто оформлять не будет.
  Источник (архитектура): SAP EWM Master Guide, глава «Warehouse Structure».
- **Oracle WMS Cloud (Facility Switcher).** В шапке приложения — селект «Facility». Если у
  роли одна facility — селект прячется. RF-сканер поддерживает штрихкод-префикс «FAC-…»
  для быстрого переключения на площадке. Межскладской перенос — Move Order с двумя
  инвойс-строками, но у оператора подбора есть «Cross-facility allocation», который
  автоматически создаёт Move Order и списывает у источника. Ближе всего к нам.
  Источник: Oracle WMS Cloud «Warehouse Operations User Guide», разделы «Facility
  Selection», «Move Orders».
- **Manhattan SCALE / Active WM.** Warehouse — сессионный атрибут, задаётся при логине;
  переключается через «Change Warehouse» в шапке. Каждое рабочее место (Receiving,
  Picking, Packing) читает контекст молча, без дублирующего селекта. Перенос между
  складами оформляется через `Warehouse Transfer Order`.
- **1С:WMS / «Мой склад».** Есть «текущий склад пользователя» в панели, экраны переклю-
  чаются автоматически. Для случая «пользователь работает только с одним складом» —
  переключатель скрыт настройкой в профиле. Межскладской перенос — отдельный документ
  «Перемещение», который может быть создан и вручную, и автоматически по правилу пополнения.
- **ShipHero / ShipBob (фулфилмент 3PL для e-commerce).** Каждый оператор привязан к
  одной warehouse-facility, кросс-склад делает специализированный роут-оптимизатор:
  если stock physically в другом складе, система автоматически создаёт inter-warehouse
  transfer, а не даёт оператору списать «из чужой ячейки». В интерфейсе — предупреждение
  на этапе создания FBS/DTC-заказа: «Товар нужен на A, доступен только на B — переносим?».
  Ближе всего к тому, что говорит владелец («не сказав об этом словами»).

Что из этого применимо нам:
- **Глобальный контекст склада в сессии** (SAP, Manhattan, Oracle, 1С) — берём. Владелец
  прямо просит «сначала склад, потом ячейка внутри него», то есть контекст, а не селект.
- **Сканер понимает штрихкод склада и штрихкод ячейки** (Oracle FAC-префикс,
  Zebra-скрипты у Manhattan) — берём.
- **Автоматический межскладской перенос в момент подбора** (Oracle Cross-facility
  allocation, ShipHero auto-transfer) — берём как замену костылю на упаковке. Основной
  аргумент — владелец сам говорит: «клиент работает как с одним складом»; отдельный
  документ переноса до подбора оператор оформлять не будет.
- **Отдельный тяжёлый документ «Перемещение»** (SAP, 1С) — оставляем как «есть, но
  необязательно»: `TransfersScreen` (S-25) уже существует, туда попадают ручные переносы
  админа, автоматические переносы при подборе тоже туда попадают (одной ленточкой,
  чтобы был аудит).
- **Facility Switcher в шапке** (Oracle, Manhattan) — берём как единый компонент.

Что НЕ берём:
- Сложная роль «Warehouse Manager» с правом переключаться и «Operator» без такого права
  (SAP): у нас нет запроса разграничивать доступ так тонко, всё уже покрывает `role` +
  `tenant_id`.
- Auto-replenishment (правила пополнения, минимумы/максимумы, роутинг заказов): это
  отдельная эпика, владелец не просил.
- Отдельный «Warehouse Number = отдельная база данных» подход SAP: у нас общий тенант,
  склад — просто одна из осей группировки.

## Решение

### Одной фразой

Ввести **глобальный контекст «текущий склад»** в UI (Zustand/React store), сделать один
компонент-переключатель `<WarehouseSwitcher />` в шапке, добавить полю `Warehouse.barcode`,
научить единый скан-обработчик различать «код склада» и «код ячейки», а вместо костыля
`_try_deduct_from_alternative_sorting_location` при подборе делать настоящий межскладской
перенос `stock_transfer_out(X) → stock_transfer_in(Y.sorting)` одной транзакцией.

### Варианты встраивания и цена

**Вариант A (рекомендую) — контекст в сессии + автоматический перенос при подборе.**
- Что делаем: `warehouseContext` в App/SellerApp (`selectedWarehouseId` уже есть — доводим
  до статуса «единый источник правды»). Компонент `WarehouseSwitcher` в шапке `AuthedApp-
  Layout` — виден, если у тенанта больше одного «настоящего» склада (служебные `fbs-wb-*`
  не считаются). API `/warehouses` расширяется полем `is_auto_fbs` (или сразу два массива
  `real`/`auto`); клиент фильтрует по `is_auto_fbs=false`. У `warehouses` появляется поле
  `barcode` (по образцу `storage_locations.barcode`). Новый эндпоинт `/scan/resolve?code=…`
  (или локальная маршрутизация во фронте по префиксу — быстрее, но менее гибко)
  возвращает `{kind: "warehouse"|"location"|"product", …}`, фронт диспатчит: склад →
  переключить контекст; ячейка → переключить контекст на её склад + подставить её. При
  подборе, если оператор сканирует ячейку не с того склада, где привязана поставка,
  сервер (`fbs_picking_service.scan_pick_location`) вместо ошибки создаёт автоматический
  межскладской перенос (снятая сегодняшняя проверка `warehouse_id == supply.warehouse_id`
  в `transfer_on_hand_between_locations` + новый тип движения
  `stock_transfer_cross_warehouse_out`/`_in`, объединённые общим `transfer_group_id`),
  после чего товар физически «переезжает» в sorting склада поставки — и стандартный pick
  идёт как раньше. Костыль в `fbs_packaging_integration_service.py:479` удаляется.
- Стоимость: одна миграция (`warehouses.barcode` + два новых `movement_type`), правки в
  5 сервисах (`fbs_warehouse_binding_service`, `fbs_picking_service`,
  `fbs_supply_validator_service`, `inventory_service.transfer_on_hand_between_locations`,
  `fbs_packaging_integration_service`), один новый UI-компонент, правки в 8 экранах
  (`InboundScreen`, `OutboundScreen`, `TransfersScreen`, `ProductsScreen`,
  `FfFbsSupplyWorkspace`, `FbsSupplyCreateDialog`, `SellerDocumentsScreen`,
  `SellerInboundDraftScreen`), новый `frontend/src/utils/fbsWarehouse.ts` (по образцу
  WIP-ветки). Риск средний: снятие проверки «один склад в переносе» — потенциально
  меняет учёт остатков в других сценариях (миграция баз, discrepancy_act) — надо
  прикрыть тестами.
- Что ломается: экраны S-01, S-03, S-14, S-22, S-24, S-25, S-26, S-28, S-29 — все, где
  сегодня селект склада живёт отдельно, — переключаются на общий контекст. Формы
  «создать заявку» больше не показывают селект склада, если контекст задан. Тесты
  Playwright, где выбирают склад из формы, — обновить.

**Вариант B — отдельный документ «Перенос между складами» до подбора, без auto-transfer.**
- Что делаем: то же, что в A, но при попытке скана «чужой» ячейки на подборе сервер
  отвечает `cross_warehouse_transfer_required` с deep-link на `TransfersScreen`, оператор
  вручную создаёт документ «Перенос X→Y», подтверждает, возвращается к подбору. Кросс-
  складского auto-transfer нет.
- Стоимость: та же миграция, но UI-цепочка длиннее (оператор дважды переключает экран
  за один подбор). Плюсы: аудит чище, каждый перенос — документ с ответственным.
- Что ломается: то же плюс новый обязательный шаг для оператора. Именно про это владелец
  говорит «клиент работает как с одним складом» — то есть перекладывать/оформлять
  переносы не будут. Значит, оператор упрётся и придётся возвращаться к костылю. Ниже
  по эргономике, чем A.

**Вариант C — полностью автоматический подбор (без переключателя).**
- Что делаем: сервер сам решает, откуда собирать, оператор вообще не выбирает склад.
  Подбор пробегает по ячейкам всех складов тенанта в порядке «сначала склад поставки,
  потом остальные», выдаёт оператору «сходи в ячейку X склада Y», при списании
  автоматом ставит межскладской перенос.
- Стоимость: минимальная UI-часть (нет переключателя), но большая логика роутинга на
  сервере + сильный шаг вбок от того, что уже привычно оператору. Владелец прямо
  просит «переключатель прямо в рабочем месте», а не «пусть система сама решает». Не
  подходит.

**Выбор — A.** Он бьёт точно в описанный инцидент 20.08, минимально ломает привычки
оператора (сегодня селекты и так висят на приёмке/отгрузке — заменяем их на один
переключатель в шапке), даёт правильный учёт остатков вместо костыля, и одновременно
поддерживает случай «один настоящий склад — не показываем ничего».

### Сценарии оператора (после)

- **Тенант с одним настоящим складом.** Заходит — переключатель в шапке скрыт. Все формы
  создания заявок (приёмка, отгрузка, поставка FBS) не показывают «Склад для заявки».
  Всё падает в «Основной» молча. Инцидент 20.08 невозможен по построению: служебный
  `fbs-wb-*` в списке выбора не участвует.
- **Тенант с двумя настоящими складами.** Переключатель в шапке — виден. Кликом или
  сканом штрихкода склада контекст меняется, все списки/остатки/ячейки перерисовываются.
  При создании поставки, если товар физически лежит не на выбранном складе, — preflight
  показывает нотис «нужно 3 шт., на этом складе 0, ещё 3 шт. на складе „Основной“» и
  даёт «Создать всё равно / Открыть перенос». При подборе оператор может сканировать
  ячейку с другого склада — сервер автоматически регистрирует межскладской перенос
  (запись в ленте движений) и списывает у себя.
- **Селлер (портал).** По умолчанию склад тот, где у него больше остатка. Переключатель
  — если он видит больше одного склада (обычно нет).

## Границы

**Делаем мы (WMS):**
- Модель: `warehouses.barcode`, два новых `movement_type`, флаг `is_auto_fbs` в API
  `/warehouses`.
- Сервисы: правка `fbs_picking_service.*`, `inventory_service.transfer_*`,
  `fbs_stock_availability_service.*`, `fbs_supply_validator_service.*`; снос
  `_try_deduct_from_alternative_sorting_location`.
- Фронт: контекст-провайдер `warehouseContext`, компонент `WarehouseSwitcher`, единый
  скан-парсер `parseScannedCode`, чистка селектов на всех задетых экранах, preflight-
  нотисы на `FbsSupplyCreateDialog` (WIP-версию доводим).
- Тесты: unit на новую логику transfer/pick, Playwright на «один склад — нет селектов»
  и «два склада — переключатель + кросс-складской подбор».

**Делает маркетплейс (WB):**
- Ничего нового. WB продолжает знать только свой `wb_warehouse_id`; связь с WMS-складом
  — через `fbs_warehouse_binding`, как сегодня. Стороннее «переехало на другой WMS-склад»
  для WB прозрачно.

**Делает человек руками:**
- Админ ФФ один раз при заведении склада — печатает и клеит штрихкод склада (у нас
  сегодня есть шаблоны для ячеек, добавляем «Штрихкод склада» в тот же экран печати).
- Оператор физически ничего не перекладывает (по прямым словам владельца — «клиент
  работает как с одним складом»); учёт подстраивается через автоматический перенос.
- Ручной документ «Перенос между складами» (S-25) — остаётся как есть, для случаев,
  когда физически перекладывают.

**Совместное поведение:** WB может прислать заказ на склад, к которому оператор не
привязал WMS-склад — тогда WMS создаёт `fbs-wb-*` служебный (как сегодня), пряча его от
глаза оператора; при первом ручном привязывании через
`fbs_warehouse_binding_service.upsert_binding` служебный остаётся в базе (пул поставок к
нему привязан), но новые заказы едут в настоящий склад.

## Риски

Внешнего API у этой задачи нет — риски внутренние.

- **Снятие проверки «перенос только в одном складе» может задеть DEC-019 migration и
  discrepancy_act.** `transfer_on_hand_between_locations` сегодня используется в
  `migrate_all_address_balances_to_sorting` — там всегда один склад, поведение не
  меняется, но проверку снимать точечно, только для новой сестринской функции. Иначе
  можно случайно перевести inventory через границу склада тем, кто это делать не должен.
- **`transfer_group_id` в `inventory_movements` уже используется** для парных
  `stock_transfer_out`/`_in`. Новые типы `_cross_warehouse_out`/`_in` живут по тому же
  контракту, но потребители, которые фильтруют по `movement_type == "stock_transfer_out"`
  (например, отчёты), могут не увидеть новые записи. Найти всех потребителей и решить:
  либо расширять список типов в отчётах, либо ввести общий признак «is_transfer» в
  сервисном слое.
- **Кросс-складской перенос при подборе может создать «отрицательные» остатки у
  источника** в редкой гонке (два оператора одновременно подобрали одну единицу из
  одной ячейки другого склада). Защита та же, что сегодня, — `on_hand < quantity`
  внутри транзакции; но добавить лог и алерт, чтобы это ловить.
- **`WarehouseSwitcher` меняет контекст «за спиной» у формы,** которая уже открыта.
  Пример: оператор открыл «Создать поставку FBS», выбрал заказы, потом переключил
  склад в шапке — форма не обязана переоткрываться, но данные под ней уже другие.
  Решение: при смене контекста закрывать открытые модалки (`onClose()` + toast «Склад
  переключён на X»), и не давать открыть FBS-workspace на складе, к которому оператор
  не привязан.
- **`SellerApp.tsx` и админский `App.tsx` — два разных места правки.** Легко упустить
  синхронизацию. Решение: общий hook `useWarehouseContext()`, оба App-компонента
  просто подписываются.

### Чего не делаем в этой волне

- Не пересматриваем модель «служебный `fbs-wb-*` склад» — только прячем в UI.
  Автосоздание при первом WB-синке остаётся (иначе первый заказ от WB некуда положить).
- Не трогаем ролевую модель. `require_cells_access`, `require_fulfillment_admin` и
  `role='fulfillment_seller'` работают как сегодня; переключатель складов не требует
  новых прав.
- Не делаем алгоритмы автовыбора «лучший склад для заказа» (роутинг ShipHero-style).
  Оператор выбирает вручную.
- Не переписываем `TransfersScreen` (S-25). Только добавляем строки нового типа
  движения в ленту.
- Не правим Android-клиент ТСД. Мобилка сегодня работает с одним складом; правки —
  отдельным нарядом в мобильном репозитории. Пока — на ТСД сохраняется старая
  проверка «ячейка того же склада»; кросс-складской подбор — только через web-UI.
- Не мигрируем прошлые записи `_try_deduct_from_alternative_sorting_location` в новый
  формат transfer_group_id (они уже в логах, отчёты пересчитывать не нужно).
- Не делаем «Warehouse.barcode» обязательным полем — если админ забыл распечатать,
  переключатель в шапке всё равно работает кликом.

## Допущения (принял за владельца)

- **Служебные `fbs-wb-*` — прячем от глаза оператора всегда, во всех ролях.** Это
  прямо соответствует «клиент работает как с одним складом»; хочет админ их увидеть —
  зайдёт в `FfSettingsScreen` → «Склады».
  *Почему так:* иначе выбор «Основной / FBS WB 12345 / FBS WB 67890» останется, и
  инцидент 20.08 будет ждать следующего клика на служебный.
- **Кросс-складской подбор — предупреждать словами и разрешать; блокировать только
  если товара нет вообще нигде.** Соответствует «не сказав об этом словами» = warning,
  не блок.
  *Почему так:* блокировка снова остановит поставку, а сегодняшний костыль хотя бы
  собирал.
- **Автоматический перенос при подборе как основная реализация (вариант A), а не
  отдельный документ «Перенос» до подбора (вариант B).**
  *Почему так:* владелец прямо говорит, что физически никто перекладывать не будет —
  значит документ «Перенос» превратится в пустую формальность, а нам нужен правильный
  учёт остатков.
- **`Warehouse.barcode` — автогенерация `WH-<code>` при создании склада, с
  возможностью перегенерировать через админский экран.**
  *Почему так:* печать штрихкода и так делается администратором один раз; заставлять
  вводить ручной баркод — лишний шаг.
- **Контекст склада живёт в React store, не в URL.** Смена склада не меняет
  location.pathname, но триггерит перезапрос данных.
  *Почему так:* большинство экранов (S-03 FBS, S-14 упаковка) уже устроены как
  «одностраничник с текущим складом»; URL-параметр склада — путь к рассинхрону между
  вкладками. Если владелец захочет глубокие ссылки на «конкретный склад» — легко
  добавить `?warehouseId=` поверх.
- **Существующая ветка `fix/warehouse-single-20260821` — исходное состояние.** Не
  переписываю то, что там уже сделано (утилита `isAutoFbsWarehouse`, preflight
  notices, single-warehouse hide-select), а достраиваю переключатель, скан и
  cross-warehouse pick поверх.
  *Почему так:* работа целостная, бьёт точно в инцидент 20.08, отбрасывать её —
  потерять два коммита готового кода.

## Открытые вопросы (для роли product)

1. **Селлеру в портале показывать переключатель складов при multi-warehouse — или
   всегда прятать?** У нас есть тенанты, где селлеру дают доступ только к своему
   виртуальному складу, и переключатель может выглядеть как «утечка» соседей. Ответ
   влияет на UI `SellerApp.tsx` и на фильтрацию `/warehouses` для роли
   `fulfillment_seller`.
2. **Записывать ли автоматический межскладской перенос в `TransfersScreen` как
   «полноценный документ» (с ответственным и утверждением) или только в ленту
   движений?** Первое — больше аудита, но и больше кликов; второе — тише, но
   бухгалтер потом не найдёт «кто и когда перенёс 519 штук».
3. **Warehouse.barcode: автогенерация или явный ввод?** Автогенерация быстрее, ручной
   ввод — совместимость со сторонними сканерами, у которых уже есть свои префиксы.
4. **Что делать, если у оператора вообще нет права на склад X, но он сканирует ячейку
   склада X?** Молча игнорировать? Показывать «нет доступа к складу X»? Сегодня
   ролевая модель на уровне склада не различает.
5. **Preflight-нотис при полном отсутствии товара на всех складах тенанта —
   блокировать или пропускать?** Сегодня блокировка есть только на «нет остатка на
   складе поставки»; если снимаем — надо решить, до какой границы предупреждаем и
   после какой запрещаем.
