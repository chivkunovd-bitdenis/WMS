# feature-08 — сверка

ВЕРДИКТ: ЧИСТО
ТИП: домен

## Тип

Верен. Аналитик написал `ТИП: домен` — это правильно.

Первоисточник:
> Начать в системе работать с хранением … Список требований не конечный — нужно
> продумать этот раздел.

Формулировка «начать работать» + «список требований не конечный, продумать» — прямое
указание на новый раздел, которого в системе нет. Аналитик подтвердил это независимым
осмотром кода (`grep` по `storage_tariff / storage_measurement_run / storage_charge /
storage_invoice`, поиск роутов на `/storage/…`, `/billing/storage/…`, `/invoices/…` — везде
пусто; единственное «Storage» — `StorageLocation` про топологию, а не про биллинг; в
`docs/ACTUAL_BACKLOG_RU.md:199` эпик «US-I1 Биллинг литр-день» стоит как «Не начато»).
Раздела нет ни в моделях, ни в API, ни во фронте, ни в тарифах, ни в накладных. Это
классика домена: без исследования и модели данных сюда идти нельзя, нужен ресёрч и
согласование продуктовой сути с продактом. Аналитик именно так и сделал — привёл канон
`MVP_DECISIONS_RU.md:11-18` (литр-день, МСК, RUB, без НДС) и вынес 8 продуктовых вопросов
продакту.

## Расхождения

Пусто — разбор сходится с постановкой владельца.

## Проверено

Каждая просьба владельца из цитаты нашла отражение в разборе:

- «получать габариты по интеграции» → п.1 «Что должно быть» (импорт карточек WB через
  `wildberries_product_import_service._parse_dimensions_mm`, уже работает);
- «мочь их менять» → п.2 (команда «Изменить габариты» на S-01/S-16/S-31 + «Измерить и
  зафиксировать» на S-22, через уже существующий `PATCH /products/{id}/dimensions`);
- «фиксировать изменения, чтобы не перетирались загрузкой» → п.3 (таблица истории
  наблюдений с `source` = `wb_import` / `manual` / `intake_measure`, правило «manual
  импортом не перезаписывается»);
- «устанавливать цену за литр» → п.4 («тариф хранения»:
  `price_kopecks_per_liter_per_day`, `valid_from` / `valid_to`, экран «Тарифы хранения»);
- «печатать сводную накладную» → п.6 (экран «Хранение» с выбором селлера/периода,
  PDF/xlsx);
- «брать деньги с селлера за хранение» → сквозная цель, реализована связкой
  тариф → ежесуточное измерение литр-дней (п.5) → накладная (п.6);
- «список требований не конечный, продумать раздел» → тип `домен` + 8 вопросов
  продакту, а не выкатка из головы.

Просьбы «продумать» из абзаца владельца тоже разнесены:

- «на какую дату и с какой периодичностью считаем» → п.5, ежесуточная задача на
  границе суток МСК;
- «что делать с товаром, пролежавшим часть периода» → вопрос №7 продакту («момент
  хранения» при приходе/уходе в тот же день);
- «как быть, когда габаритов нет ни от кого» → п.7 «Что должно быть» + вопрос №2
  продакту (нулём / по тарному месту / блокировать приёмку);
- «кто отвечает за спор по объёму» → вопрос №3 продакту (одностороннее измерение ФФ vs
  акт разногласий).

Лишнего сверх постановки в разборе не добавлено: конкретные экраны (S-01, S-16, S-22,
S-31) — привязка функций к уже существующим точкам UI, метка «Вручную» и история —
прямое следствие «фиксировать изменения», доступ селлера к своим накладным без права
менять — прямое следствие «брать деньги с селлера» (селлер должен видеть, за что
платит).
