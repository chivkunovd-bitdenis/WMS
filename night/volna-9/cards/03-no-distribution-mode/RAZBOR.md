# 03-no-distribution-mode

## Дословно

> ### 3. Режим «без распределения» нельзя включить после создания коробов · ТЗ пишется
>
> Слова владельца: «это очень важно, убирай», «важно делай».
>
> Галка блокируется, как только создан хотя бы один короб. Оператор, который сначала создал
> короба, а потом понял, что раскладывать не нужно, оказывается в тупике: только удалять и

> «Распределено ноль из ста пятидесяти пяти» и пугала оператора красной цифрой.

> Должно стать: режим переключается, пока в короба ничего не разложено; признак живёт в

## Что сейчас

### Что было на `origin/etalon` (и это же сейчас крутится на проде)

Три дефекта из постановки владельца воспроизводятся ровно там, где он их описал:

1. **Галка «Без распределения» гаснет с первым коробом.** В шапке вкладки коробов чекбокс
   отрубается условием `disabled={!stageIsCurrent || !packagingEditable || workspace.boxes.length > 0}`
   — это `frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx:2030` (в исходной ревизии
   `origin/etalon` — та же строка, слегка сдвинутая нумерацией). Как только сервер отдал хотя
   бы один короб в списке `workspace.boxes`, галку уже не переключить.

2. **Признак живёт припиской к служебному ключу короба, а не полем.** В
   `backend/app/services/fbs_packing_box_service.py:41` он хранится так:
   ```python
   WITHOUT_DISTRIBUTION_KEY_PREFIX = "no-distribution:"
   ```
   Строка добавляется к `creation_idempotency_key` первой партии коробов (см. `_stored_creation_key`
   там же, строки 314–319), и «признак поставки» вычитывается сканом коробов
   (`_boxes_without_distribution`, строки 329–330). Никакого поля на `FbsSupply` нет —
   `backend/app/models/fbs_supply.py` таких колонок не содержит. Отсюда и следствие,
   которое владелец описал по 20.08: как только DBA переставил флаг, короба пересоздались,
   ключи ушли новые, и приписка «no-distribution:» пропала вместе с ними.

3. **Шапка показывает «Распределено 0 из 155».** Условие
   `hasNoDistributionBoxes = Boolean(workspace?.boxes.some((box) => box.without_distribution))`
   (там же, строка 1278) — снова скан коробов. Пока их нет, флаг `false`, и шапка идёт по
   ветке `Распределено ${boxDistributedCount} из ${boxTotalCount} шт · осталось ${boxRemainingCount}`
   (строка 2013). Ровно тот же путь на любом промежуточном состоянии, где короба ещё
   не размечены нужной припиской.

Реестр блокировок это уже фиксирует — `docs/blockers/S-03.md`, блокировка **B-09**
(«Без распределения» и «Добавить короба» заблокированы когда короба уже созданы», строки
162–179): условие `workspace.boxes.length > 0` названо доменным, обоснование не найдено,
поставлен вопрос «разрешать ли менять режим если все короба пустые?». То есть это ровно та
же самая история, что и в постановке.

## Что должно быть

Фактически ничего нового проектировать не нужно — поведение, которое требует владелец, уже
реализовано в `fix/no-distribution-20260821`:

- Признак «без распределения» — поле на `FbsSupply` (`boxes_without_distribution_at`), а не
  приписка к ключу короба; переживает удаление и пересоздание коробов.
- Галка переключается в любой момент, пока в короба ничего не разложено (проверка на
  `FbsPackingBoxItem` по всей поставке, не по «есть ли короба вообще»).
- Шапка вкладки коробов при включённом режиме пишет «Без распределения · коробов N» и не
  показывает «Распределено 0 из N» ни в какой момент жизни этого режима — источник истины
  для шапки тот же самый флаг на поставке.

Признак, по которому поймём, что получилось (это уже проверяет тест
`test_boxes_without_distribution_flag_survives_empty_box_list` в `backend/tests/test_fbs_packing_box.py`,
плюс живая проверка руками):

1. На пустой поставке — включить галку, короба ещё не создавать. `GET /workspace` возвращает
   `supply.boxes_without_distribution=true`, шапка вкладки пишет «Без распределения».
2. Создать один короб, потом ещё один — галка остаётся включённой, короба чистые.
3. Удалить оба короба — галка *не сбрасывается*, признак живёт на поставке.
4. Выключить галку через переключатель — `boxes_without_distribution` становится `false`,
   шапка возвращается к «Распределено X из Y».
5. Разложить заказ в короб — при выключенной галке это работает; при включённой сервер
   отвечает `409 box_without_distribution` (эта охрана уже была).
6. Разложить заказ в короб при выключенной галке, потом попробовать включить — сервер
   отвечает `409 boxes_already_distributed`, фронт показывает Tooltip «В короба уже
   разложены заказы — сначала уберите их из коробов». (Новая охрана из wip-коммита.)

Оставшийся объём работ — не разработка, а сдача уже готового: прогнать полный гейт
(`ruff/mypy/pytest` + `npm run build && npm run test:e2e`) на ветке `fix/no-distribution-20260821`,
навесить PR, влить в `etalon`, накатить на прод миграцию `20260821_0094` вместе с деплоем.
Разбор этой задачи как «фичу» или «баг» и повторный запуск разработчика через ночной
конвейер удвоит уже сделанную работу и, что важнее, породит второй набор коммитов, который
будет расходиться с первым (`_stored_creation_key`, приписка «no-distribution:», два ключа
идемпотентности) — восстановить единый источник истины после такого раздвоения дорого.

Отдельные хвосты, которые автор `cbdaad9` явно оставил в тексте коммита:
- Дефекты type-checker в `wildberries_credentials_service.py`, `fbs_stock_sync_service.py`,

  и без правок I15.
- `unused noqa: RUF001` в `fbs_workspace_service.py` и `fbs_errors.py`.

Эти хвосты не относятся к задаче 03, но при слиянии PR их придётся либо тоже поправить,

## Вопросы и допущения

- **Ветка `fix/no-distribution-20260821` — не залита на `origin`.** Локальные коммиты
  `9e2808e` (wip) и `cbdaad9` (доделка) существуют только в этой рабочей копии; при
  проверке `git branch -a --list "*distribut*"` remote-веток нет. Если в другом рабочем
  дереве кто-то пересобирал ветку с тем же именем, но с другим содержимым — расхождение
  всплывёт при пуше. Явное допущение: перед сдачей PR нужно `git fetch --all` и убедиться,
  что удалённой ветки с таким именем не появилось.
- **Прогон гейтов** (`ruff`, `mypy`, `pytest`, `npm run build`, `npm run test:e2e`) на
  ветке `fix/no-distribution-20260821` в артефактах не приложен. Автор `cbdaad9` пишет,
  что `pytest` по своему новому тесту зелёный и что «дефекты типа-чекера в других файлах —
  унаследованный долг `etalon`». Допущение: перед вливанием эти хвосты не блокируют
  merge, но их надо явно перечислить в описании PR (пять файлов из текста коммита),
  чтобы CI-гейт `Test coverage` не остановил задачу молча.
- **B-09 в реестре блокировок** уже описан шестью полями с открытым вопросом владельца
  «разрешать ли менять режим если все короба пустые?» — этот вопрос закрыт постановкой
  волны-9 («режим переключается, пока в короба ничего не разложено»), и после вливания
  PR текст B-09 в `docs/blockers/S-03.md` нужно поправить: убрать блокировку по
  `workspace.boxes.length > 0`, заменить на актуальную «пока `FbsPackingBoxItem` пусто по
  всей поставке», обоснование — постановка волны-9.
