# ARCH — 07-reporting

Задача: раздел «Отчёты» для селлера и для ФФ. Владелец прямо помечает раздел новым и
говорит «список требований не окончательный, продумать». Первый шаг — понять, как это
устроено у других, второй — вписать в наш код и назвать цену.

## Ограничения сессии

- WebSearch/WebFetch в этом стенде без интерактивного разрешения. Раздел «Как это решают
  другие» пишу по накопленному знанию отраслевых продуктов, названия и разделы их
  документации указываю как источники. Проверять источники живьём владелец сможет утром —
  ссылки приложены; я не подделываю цитаты, где не уверен — пишу «в общем виде».
- Никаких утечек секретов, обращений к боевому проду 194.87.96.144 и записи в живой
  кабинет Wildberries эта карточка не требует — раздел read-only, поверх собственных данных.

## Как это решают другие

3PL/WMS-продукты сходятся в очень узком базовом наборе отчётов для селлера. Причина
простая: селлер в кабинете 3PL задаёт всегда одни и те же пять-шесть вопросов, и весь мир
годами отвечает на них одинаковым набором панелей.

**ShipHero (Reporting/Analytics раздел брендового кабинета)** — раздел «Reports» разделён
на «Inventory Reports» (on-hand, aging, low stock, dead stock), «Orders» (что уехало
покупателю за период), «Shipping» (сколько отправлений по каналам), «Receiving» (что
приехало на склад), «Returns». Каждый отчёт — отдельная страница с одной таблицей,
периодом с — по, сравнение опционально, экспорт CSV/XLSX. У 3PL-администратора те же
отчёты, но с фильтром «по бренду/клиенту». Ссылка: shiphero.com/features/reporting.

**ShipBob (Merchant dashboard → Analytics)** — три вкладки: «Fulfillment Performance»
(SLA отгрузки, скорость), «Inventory» (on-hand, days-of-supply, replenishment), «Storage
& Billing» (сколько места занято, сколько стоит). Селлер видит только своё, ФФ-админ
видит фильтр по клиенту. Простая круговая диаграмма + бар-чарт + таблица под ней.

**Extensiv 3PL Warehouse Manager (бывший 3PL Central)** — «Reports Manager» с
конфигурируемым списком «стандартных» отчётов: Receipts by Customer, Shipments by
Customer, Inventory Detail, Inventory Aging, Storage Fees, Activity by Warehouse. Каждый
имеет фиксированный шаблон, фильтры одинаковые. Экспорт — CSV, PDF, Excel. Отдельный
раздел «Reports» в кабинете клиента (селлера) — только по своим данным.

**Cin7 Omni / Core** — «Reports» с боковым списком (несколько десятков), правая часть —
таблица, шапка одна на всех: date range, warehouse, category, product. Есть шаблон
«Compare periods» — две колонки в таблице «текущий» / «прошлый».

**Blue Yonder / Manhattan Active WMS** — тяжёлые системы, отчёты делят на «operational»
(что сейчас происходит на складе) и «tactical» (недели/месяцы). У них уже BI-подобная
надстройка, но базовый набор тот же: receiving, shipping, inventory on-hand, storage,
activity by user.

**Ozon Seller / Wildberries Личный кабинет / WBstat.pro** — селлерская сторона у самих
маркетплейсов даёт продажи, конверсию, воронку. Про склад отвечает только «сколько
единиц лежит на складе МП», но не про то, что лежит у ФФ. То есть отчётность ФФ и
селлерская отчётность маркетплейса — **разные предметы**, не пересекаются. Наш селлер
приходит в наш кабинет за ответом на вопрос «что у меня физически лежит и сколько ушло
через ФФ» — маркетплейс на этот вопрос ответить не может.

**Что из этого применимо нам:**

- Список отчётов, а не «одна страница с чем-то». Каждый отчёт отвечает на один вопрос.
- Общая шапка фильтров у всех отчётов (период, сравнение, склад, селлер для ФФ, поиск).
- Стандартный минимум: on-hand, приход, расход, движения по товару, aging. Пять штук —
  индустриальный минимум, покрывает 90% вопросов селлера.
- Селлер и ФФ ходят в **один и тот же список отчётов** — отличается только резолвер scope
  (селлер видит своё, ФФ видит tenant с фильтром).
- Данные показываем таблицей + одним простым графиком + экспорт. Никаких pivot-редакторов,
  расписаний рассылок, конструкторов дашбордов — это оставляют «зрелым» продуктам.
- Aging (мёртвые остатки) считают по суточным снапшотам остатков, не по журналу движений.
  У нас снапшот появится в карточке 08-storage — переиспользуем.

**Что нам НЕ подходит:**

- Конструктор отчётов «сам-собери-разрез» (как у Cin7 «custom reports») — MVP не нужен.
- Расписания «PDF в 8:00 на почту» — MVP не нужен.
- Прогнозы, ML, «what-if» сценарии — не про 3PL этой стадии.
- Отчёты по продажам с маркетплейса (конверсия, воронка) — это дело маркетплейса, не ФФ.

- Extensiv 3PL Warehouse Manager Reports: <https://www.extensiv.com/products/3pl-warehouse-manager>
- Cin7 Omni Reports: <https://cin7.com/product-tour/reports/>
- WBstat.pro (для сравнения предмета отчётности МП vs ФФ): <https://wbstat.pro/>

## Решение

Раздел «Отчёты» — не одна страница, а **список отчётов**, живущий по общему каркасу и в
портале ФФ, и в портале селлера. Отличие двух порталов — только в резолвере scope
(селлер видит только своё) и в списке разрешённых отчётов (у селлера нет «Операции»
и «По продавцам»).

**Первая волна — пять отчётов, покрывающих индустриальный минимум:**

1. **Движения по товару за период** — уже существует, переиспользуем как есть,
   переносим внутрь нового каркаса под id `product_movements`.
2. **Остатки сейчас** — snapshot: сколько единиц каждого товара лежит, в каких ячейках,
   на каком складе, чьи. Разрезы: по товару, по складу, по селлеру.
3. **Приход за период** — сумма приёмок и загрузок ТЗ. Разрезы: по селлеру, по складу,
   по товару, по дню.
4. **Расход за период** — сумма отгрузок FBS + отгрузок на МП + wholesale. Разрезы: те
   же плюс по маркетплейсу.
5. **Мёртвые остатки (aging)** — «сколько дней товар не двигался». Ковши 0–30 / 30–60
   / 60–90 / 90+ дней. Разрезы: по товару, по складу, по селлеру.

**Что показывает каждый отчёт:** три колонки/линии на одном экране — «за период»,
«накопительно с начала месяца», «сравнение с прошлым периодом». Таблица + один простой
график (бар/линия), кнопка «Скачать» (XLSX и CSV). Никаких переключений между вкладками
ради тех же цифр.

**Общий контракт бэка (одна ручка на все отчёты):**

```
GET  /reports/{report_id}?date_from=&date_to=&compare=previous|year_ago|none
                         &group_by=product|seller|warehouse|marketplace|day
                         &seller_id=&warehouse_id=&marketplace=&search=
     → { meta: {report_id, title, columns[], group_by, period, compare},
         rows: [...], totals: {...},
         chart: { type, series[] },
         compare?: { rows[], totals } }

GET  /reports/{report_id}/export?format=xlsx|csv&<те же фильтры>
     → файл
```

`report_id` резолвится через реестр (`reports_registry`); каждый отчёт — отдельный
сервис в `backend/app/services/reporting/reports/<name>.py`. Ручка одна, шапка фильтров
одна — новый отчёт добавляется как файл + строка в реестре.

**Общий каркас фронта:** экран `ReportsHubScreen` (двухпанельный: слева — список отчётов,
справа — выбранный отчёт с фильтрами/таблицей/графиком/кнопкой экспорта). Существующий
`FfReportsPage` перевоплощается в первый пункт списка (`product_movements`) внутри этого
каркаса. У селлера появляется пункт меню «Отчёты», ведущий на тот же каркас с меньшим
списком.

**Компонент экрана переиспользуется в обоих порталах.** Отличия — только по данным
(scope) и списку отчётов (registry фильтрует по `portal`).

### Варианты и цена

**Вариант А (рекомендуемый) — общий каркас + реестр отчётов + одна ручка `/reports/{id}`.**
- Цена: один новый бэк-модуль (`reporting/`, 5–6 файлов: period, scope, registry, три-пять
  отчётов), один новый экран `ReportsHubScreen` + селлерский пункт меню, миграция текущего
  `FfReportsPage` внутрь каркаса.
- Что ломается: старый роут `/operations/inventory-movements/summary` остаётся живым с
  пометкой deprecated — старый `FfReportsPage` в переходный период продолжает работать,
  чтобы не ловить регресс.
- Плюс: новый отчёт добавляется одной парой файлов, шестой отчёт «стоит» уже минимум.
  Один экспортёр, одна шапка фильтров, одна ролевая модель.
- Минус: первый отчёт дороже, чем у Б.

**Вариант Б — оставить каждый отчёт как отдельный экран и отдельную ручку, копипастой от
`FfReportsPage`.**
- Цена: пять экранов, пять ручек, пять фильтр-панелей, пять экспортёров.
- Что ломается: селлерский портал придётся строить в два раза больше (свои копии
  экранов), любой рефактор шапки — в пяти местах.
- Плюс: первый отчёт ставится быстро.
- Минус: через три-четыре отчёта раздел превращается в кладбище копий. Владелец
  специально просит «единый раздел», Б этому противоречит.

**Вариант В — взять BI-виджеты (react-pivot, ag-grid pivot, готовую embed-BI платформу).**
- Цена: тяжёлая зависимость, обучение пользователя, свои роли, свой рендер, свой
  экспорт — двойная сложность на все годы вперёд.
- Что ломается: контроль над UI теряется, любая мелкая правка «как выглядит колонка»
  становится войной с чужой библиотекой.
- Плюс: можно самому собирать разрезы.
- Минус: наш пользователь — оператор склада, ему нужны готовые ответы, а не редактор
  отчётов. Владелец в постановке дал закрытый список разрезов, конструктора не просил.

**Выбираем А.** Один каркас, один контракт, один экспортёр, два портала на одном UI.
Именно этот путь проходят все зрелые 3PL-продукты — потому что альтернативы дороже
владения.

### Куда что кладём в коде

Бэк:
- Новый пакет `backend/app/services/reporting/`
  - `period.py` — dataclass `ReportingPeriod` (start, end, compare_start, compare_end,
    mtd, ytd). Одно место, где считаются периоды и сравнения.
  - `scope.py` — dataclass `ReportingScope` (tenant_id, seller_ids=None|set,
    warehouse_ids=None|set, marketplace=None|set). Резолвится из роли пользователя;
    у селлера всегда жёстко один seller_id.
  - `registry.py` — реестр `report_id → ReportSpec(builder, allowed_portals, filters)`.
  - `reports/product_movements.py` — обёртка над существующим
    `inventory_movement_report_service.list_product_movement_summary` (не переписываем).
  - `reports/on_hand.py` — snapshot по `inventory_balance` + `product` + `warehouse`.
  - `reports/inbound.py` — сумма `inbound_intake` + `product_tz_import` по разрезам.
  - `reports/outbound.py` — сумма `fbs_shipment` + `marketplace_unload` +
    `outbound_shipment` по разрезам.
  - `reports/aging.py` — по последнему движению `inventory_movements` для каждого
    (product × storage_location); ковши 0–30/30–60/60–90/90+ дней. Пока налету, когда
    появятся суточные снимки 08 — переиспользовать.
  - `excel_export.py` — единый writer XLSX/CSV поверх `openpyxl` (или того же
    HTML-в-XLSX, что сейчас у фронта; выбор — при DEV, дешевле openpyxl).
- Новая ручка `backend/app/api/reports.py`:
  - `GET /reports` — список доступных отчётов (для меню-каркаса).
  - `GET /reports/{report_id}` — данные.
  - `GET /reports/{report_id}/export?format=xlsx|csv` — выгрузка.
- Старая ручка `GET /operations/inventory-movements/summary` — оставляем deprecated,
  редиректом внутри уходит в `reporting/reports/product_movements.py`.

Фронт:
- Новый экран `frontend/src/screens/shared/ReportsHubScreen.tsx` — двухпанельный
  каркас, общий для порталов. Портал берёт из props.
- Новый компонент `frontend/src/screens/shared/reports/ReportShell.tsx` — фильтры,
  таблица, график, экспорт. Один на все отчёты.
- Новый компонент `frontend/src/screens/shared/reports/ReportChart.tsx` — обёртка
  над MUI X Charts (уже семейство MUI, не тянем `recharts` — меньше зависимостей,
  один визуальный язык с остальным приложением).
- `FfReportsPage.tsx` — превращается в тонкий редирект на
  `/app/ff/reports/product_movements` (обратная совместимость роута), внутри
  каркаса становится одним из отчётов.
- `frontend/src/layouts/AuthedAppLayout.tsx` — в блоке `portal === 'seller'`
  добавить пункт «Отчёты» → `/app/seller/reports`.
- Селлерский роутер (`SellerApp` / `seller-main`) — добавить роут `/app/seller/reports`
  на `ReportsHubScreen` с `portal='seller'`.

## Границы

**Что делаем мы (WMS):**
- Собираем и агрегируем свои данные (`inventory_movements`, `inventory_balance`,
  `inbound_intake`, `fbs_orders`, `marketplace_unload`, `outbound_shipment`, `product`,
  `seller`, `warehouse`).
- Показываем два портала с одним каркасом отчётов и одним контрактом ручки.
- Отдаём экспорт (XLSX/CSV).
- Разграничиваем доступ: ФФ-админ и `PERM_CELLS/PERM_INVENTORY`-сотрудник видят
  tenant; селлер видит только свой `seller_id`.

**Что остаётся на маркетплейсе (WB/Ozon):**
- Отчёты продаж, конверсии, воронки покупателя, комиссии МП, деньги от МП — это
  их кабинет, они это уже показывают и это их предмет.
- Мы **не тянем** WB Statistics API ради «сколько на самом деле продали покупатели» —
  наш селлер за этим ходит в свой WB-кабинет. Мы отвечаем за «что физически
  прошло через ФФ», это разные предметы.
- Наш `wildberries_import_supplies_service` уже приносит факт приёмки WB — этого
  для отчёта «Расход/Отгрузка на МП» достаточно.

**Что делает человек руками:**
- Выбирает период, сравнение, фильтры.
- Скачивает выгрузку.
- Никаких «внеси цифру вручную», никаких «согласуй с админом» — все данные из журналов
  системы.

## Риски внешнего API

Внешнего API в этой карточке нет: раздел read-only поверх собственной БД. Но риски
всё равно есть.

**Риск: производительность.** За квартал по десяткам тысяч движений `SUM/GROUP BY`
рискует уехать за секунду. Митигация: индекс `(tenant_id, created_at)` на
`inventory_movements` уже есть; для aging — по последнему движению на
(`product_id`, `storage_location_id`), потребуется индекс (проверить в DEV). Если
упрётся — материализованные суточные снимки, но это отдельная карточка (связка с 05).

**Риск: разные интерпретации «прихода/расхода».** У WB «поставка» и у нас «приёмка»
могут расходиться на день-два. Митигация: отчёт показывает время события в нашей
системе, а не в WB. Комментарий на экране «время — по журналу ФФ, не по МП».

**Риск: сравнение периодов даёт «странные» числа.** У короткого месяца vs длинного —
разница по числу дней. Митигация: рядом с абсолютом показываем «в среднем в день»,
чтобы длина периода не искажала восприятие.

**Риск: XLSX для больших выгрузок.** 100k строк в openpyxl — минуты и мегабайты
памяти. Митигация: жёсткий верхний лимит выгрузки (25k строк), выше — предупреждение
«разбейте на несколько периодов». Позже — стриминговый CSV (тредпул), эта задача
попадает в 05.

**Риск: aging без суточных снимков.** Если считать «дней без движения» по
`inventory_movements.created_at`, товар, приехавший в 2024 и с тех пор не двигавшийся,
считается корректно; но товар, у которого «нулевая инвентаризация» удалила запись,
попадёт в неправильный ковш. Митигация: aging считается только по товарам с
положительным `inventory_balance` на дату отчёта.

## Чего не делаем в этой волне

- Не делаем **финансовые отчёты** («сколько я должен ФФ», «мои счета», «задолженность»)
  — это карточки 08-storage и 09-billing, они дают данные, а отчёт «Финансы» подключим
  во второй волне отчётности как шестой пункт списка.
- Не делаем **конструктор отчётов** (custom fields, custom pivot).
- Не делаем **рассылки на почту** и «отчёт по расписанию».
- Не делаем **PDF-экспорт с логотипом ФФ**. Только XLSX и CSV. PDF — во второй волне,
  если продакт скажет «нужен для формальных писем».
- Не делаем **свои дашборды на главной**. Существующий селлерский `SellerDashboardScreen`
  не трогаем — там placeholder, но это отдельная карточка «Приборная панель селлера».
- Не делаем **материализованные витрины**. Считаем налету; если упрётся — уходит в 05.
- Не делаем **отчёт по работе упаковщиков** внутри раздела «Отчёты». Это HR/зарплата,
  живёт отдельно (в S-19 или в новой карточке «Сотрудники»). Владелец в постановке
  прямо отделил её как «служебный расчёт, к отчётности не относится».
- Не делаем **отчёты по продажам с маркетплейса** (конверсии, воронки) — это дело WB и
  Ozon, мы за это не отвечаем.

## Допущения (решено вместо владельца, помечено явно)

1. **Пять отчётов первой волны, порядок такой же.** Обоснование: это индустриальный
   минимум 3PL (ShipHero, ShipBob, Extensiv одинаково), закрывает основные вопросы
   селлера, данные уже в БД, не требует новых сущностей.
2. **Селлер видит только свой `seller_id`, у него нет фильтра «выбрать селлера».**
   Обоснование: тот же паттерн, что уже работает в `seller_line_product_scope` — не
   плодим ролевую модель.
3. **Все сотрудники селлера видят все отчёты 07.** Обоснование: в 07 нет денег;
   ролевое разделение «менеджер vs владелец» решается в 09, где появятся счета.
4. **Формат экспорта — XLSX + CSV.** Обоснование: XLSX для селлера в Excel, CSV для
   собственных выгрузок в 1С. PDF — «зрелый» продукт, откладываем.
5. **Глубина истории в UI ограничена «мягкой рекомендацией» 90 дней в одном запросе.**
   Обоснование: у нас MVP-объёмы. При больших диапазонах — предупреждение, но всё
   равно считаем; когда упрётся физически — 05.
6. **«Работа упаковщиков» из раздела 07 исключается** (расхождение №1 из SVERKA).
   Обоснование: сам владелец в исходной постановке отделил её как «служебный
   расчёт, к отчётности не относится».
7. **«Обороты, счета, задолженность по продавцу» из первой волны 07 исключаются**
   (расхождение №2 из SVERKA). Обоснование: это предмет 08 и 09; в отчёты приходит
   как шестой пункт списка во второй волне.
8. **«Хотя бы три разреза у селлера» — заменяю точным списком** (расхождение №3):
   у селлера в первой волне доступны отчёты «Движения по товару», «Остатки сейчас»,
   «Приход», «Расход», «Мёртвые остатки». У ФФ — те же плюс «Операции» (кто что
   делал за период). Отчёт «По продавцам» = фильтр «Селлер» в шапке любого отчёта,
   не отдельный раздел.
9. **Сравнение с прошлым периодом = автосдвиг на длину текущего периода.**
   Обоснование: одинаково у ShipHero, ShipBob, Cin7 — понятный дефолт. «Год назад»
   доступен как пресет в переключателе.
10. **Накопительно = «с начала месяца» и «с начала года» показываем в totals-строке
    под таблицей**, не отдельным запросом. Обоснование: одно обращение к БД, один
    экран, не заставляем оператора переключаться.
11. **График — MUI X Charts** (одно семейство с остальным приложением).
    Обоснование: не тянем `recharts` — уменьшаем размер бандла и число зависимостей.
12. **Существующий роут `/operations/inventory-movements/summary` остаётся живым**
    как редирект внутрь новой ручки. Обоснование: не ломаем текущий FfReportsPage
    в переходный период.
13. **Aging считается по времени последнего движения `inventory_movements`,
    отфильтрованному по положительному текущему `inventory_balance`.** Обоснование:
    без суточных снимков (они появятся в 08) это самый честный способ, без
    ложноположительных «мёртвых» на нулевом остатке.

## Открытые вопросы для продакта (закроет решением)

1. Приоритет первого отчёта: сначала селлерский «Остатки сейчас + Мёртвые» (селлер
   получает ценность сразу) или сначала ФФ-шный «Приход/Расход» (админу срочно
   для управления)? По умолчанию — первый.
2. Нужен ли отдельный отчёт «Операции» (кто из сотрудников ФФ сколько сделал за
   период) в первой волне, или он уходит во вторую? По умолчанию — уходит во вторую,
   потому что это ближе к HR, чем к отчётности перед селлером.
3. Формат PDF — нужен ли в первой волне для формальных писем селлеру, или XLSX/CSV
   достаточно? По умолчанию — не нужен.
4. Глубина истории в UI: 90 дней в одном запросе — ок как «мягкая рекомендация», или
   ставить жёсткий лимит и предлагать разбивать? По умолчанию — мягкий.
5. Роли селлера: заводить уже в 07 отдельного «менеджера, который видит операции, но
   не деньги», или подождать до 09? По умолчанию — ждём 09, там деньги, там и роль.
