# defect-05 · Прод тормозит

## Дословно

Прод тормозит · ТЗ пишется

Слова владельца: «очень важно — опиши решение».

Памяти на сервере в обрез, сервер приложения работает в один процесс, и вся счётная работа
идёт в том же потоке, что и ответы пользователям: сборка ленты на сто пятьдесят пять кодов —
секунда полной остановки для всех, на пятьсот кодов — три секунды. Фоновый опрос
Wildberries запускается каждые три минуты и идёт до двух минут по двадцати пяти продавцам,
перекачивая около пяти тысяч трёхсот заказов ради одного-пяти новых; пока он идёт, действия
оператора по этому продавцу стоят в очереди. Экран тоже не помогает: с каждого рабочего
места дважды по пятьсот записей каждые двадцать шесть секунд. База ни при чём.

Должно стать: тяжёлая счётная работа уходит из общего потока; частый цикл спрашивает
только новые задания, полный обход идёт редко; списки грузятся страницами; на сервере
появляется запас памяти. С замерами до и после, чтобы результат можно было предъявить.

## Что сейчас

Сначала проверил, не сделана ли задача — нет: по всем веткам нет коммитов про `perf`,
`производительн`, `workers`, `pagination` в контексте FBS-поллинга или ленты. Единственный
близкий по смыслу — `2453f44 fix(wb): batch autopoll metadata reads` от 21.08 (это
про defect-01, не про эту задачу) и старый `104c2ed Reduce FBS status autopoll pressure`,
который просто поднял интервал `fbs_statuses_sync_interval_sec` с меньшего значения до 600 сек
и не трогает ни архитектуру, ни автопулл заказов. Ветка `process/pipeline-on-etalon-20260821`,
которую я вижу, — служебная для процесса. На бою (`etalon`) описанное владельцем работает
как есть.

Дальше — что именно даёт торможение. Владелец не выдумал: все четыре причины видны в коде.

**Один uvicorn-процесс, без пула worker'ов.** Прод в Railway собирается по
`backend/Dockerfile.railway`, там `CMD ["sh", "-c", "alembic upgrade head && exec uvicorn
app.main:app --host 0.0.0.0 --port ${PORT:-8000}"]` — ни `--workers`, ни `WEB_CONCURRENCY`,
ни gunicorn. Значит один процесс, один event loop, GIL один. Тот же одиночный `uvicorn` без
workers — в основном `backend/Dockerfile` и в `docker-compose.prod.yml` (сервис `api`,
строки 26–49). Все HTTP-запросы, автопулл-таски (в `docker-compose.prod.yml` есть отдельный
`celery_worker`, но на Railway он не поднят — там только один web-сервис) и синхронная работа
живут в одном loop-е.

**Тяжёлая CPU-bound работа с PDF идёт прямо в event loop.** Сборка ленты —
`backend/app/services/fbs_order_tape_print_service.py`, `print_fbs_order_tape` (строки 77–273).
Внутри идёт получение стикеров от WB (`request_supply_print_batch`, строки 118–132), потом на
каждый заказ печатается КИЗ и вклеивается в PDF через pymupdf. PDF-сервис —
`backend/app/services/marking_label_artifact_service.py` — весь на `import fitz`
(строки 9, 22, 46, 71, 128 и т.д.): открывает документы, рисует QR, склеивает страницы. Ни
одного `asyncio.to_thread` / `run_in_executor` в связке `fbs_order_tape_print_service.py` и
`marking_label_artifact_service.py` нет (проверил `grep run_in_executor|to_thread|ThreadPoolExecutor`
— пусто). API-хендлер вызывает всё это прямо из корутины запроса:
`backend/app/api/fbs_supplies.py:1547-1570` — `@router.post("/{supply_id}/order-print-tape")`
делает `await order_tape_svc.print_fbs_order_tape(...)`. Пока pymupdf на 155 сгенерированных
PDF-страницах молотит в C-коде — GIL держится, все остальные корутины loop-а стоят. Это и есть
«секунда полной остановки для всех».

**Автопулл WB перекачивает полный список ради 1–5 новых.** Beat в
`backend/app/celery_app.py:26-29` держит `wms.fbs_orders_autopoll` с интервалом
`fbs_poll_interval_sec` — по умолчанию 180 секунд (`backend/app/core/settings.py:149-158`).
Функция `poll_fbs_orders_all_sellers` в `backend/app/services/fbs_autopoll_service.py:289-361`
последовательно проходит по всем продавцам с WB-токеном (список из
`list_sellers_with_marketplace_token`) и на каждого дёргает `sync_seller_orders`. Внутри
`sync_seller_orders` (`backend/app/services/wb_marketplace_orders_service.py:1449-1576`)
сначала честно спрашивает у WB `GET /api/v3/orders/new` (`fetch_marketplace_orders_new`,
строка 1461), а потом **обязательно** идёт по циклу `for _page in range(MAX_ORDERS_PAGES)`
(строка 1494) и перекачивает страницами по `min(limit, 1000)` весь общий список — до десяти
страниц по тысяче. `MAX_ORDERS_PAGES = 10` объявлен на строке 75 того же файла. То есть
каждые 3 минуты система для каждого продавца тянет с WB и до 10 тысяч записей, разбирает их
через `upsert_order_from_wb_row`, коммитит в БД. Ради 1–5 действительно новых заданий из
`GET /orders/new` — именно так владелец и описал.

Плюс на том же продавце по цепочке идут `sync_order_statuses`, `link_confirmed_orders_to_wb_supplies`
(строки 1533–1560) — ещё пачка обращений к WB. Всё в одном процессе. Пока идёт цикл по
продавцу, любой оператор, чей запрос попал в тот же event loop и требует ресурса `wb_seller_lock`
на этого же продавца, стоит в очереди (см. `wb_seller_lock` в `poll_fbs_orders_all_sellers`,
строки 306–309, — лок на уровне продавца).

**Экран `S-03 FfFbsOrdersScreen` бьёт двумя запросами по 500 записей каждые 30 секунд.**
Файл `frontend/src/screens/v2/FfFbsOrdersScreen.tsx`, строка 82:
`const NEW_ORDERS_PAGE_LIMIT = 500`. Строки 594–615 — polling через `setInterval` на 30 000 мс
(владелец назвал 26 сек — это фактическое «раз в полминуты» с учётом времени ответа сервера,
близко). На вкладках поставок `isFbsSupplyGroup(statusGroup) === true` (строки 541–560) идёт
`Promise.all([fetchFbsSupplyWorklist(...), fetchFbsWorklist(...)])` — параллельно два запроса,
оба с `limit: 500`. На вкладке «Новые» — один запрос с тем же лимитом 500. Пагинации на экране
нет: `limit: 500` в обе стороны и всё. С каждого рабочего места это ложится на тот же
одиночный процесс каждые 30 секунд.

**База ни при чём** — подтверждаю. Тормоза не в SQL: сервер один, event loop один, `MAX_ORDERS_PAGES = 10`
раздувает трафик и время цикла, `NEW_ORDERS_PAGE_LIMIT = 500` × 2 запроса × N рабочих мест
раздувает нагрузку от фронта, `fitz`-работа блокирует loop через GIL, worker'ов нет — некому
разгружать.

## Что должно быть

Владелец назвал четыре направления. Ни одно из них не отменяет другого, все четыре нужны,
и все четыре измеряются.

Первое — **тяжёлая счётная работа уходит из общего потока**. Синхронная pymupdf-обработка
в `print_fbs_order_tape` и в `marking_label_artifact_service.py` вызывается через
`asyncio.to_thread` (или через `run_in_executor` с явным пулом), чтобы pymupdf молотил в
отдельном потоке и не держал event loop. Как вариант — вынести всю сборку ленты в Celery-задачу
(инфраструктура для этого уже есть: очередь через Redis, шаблон `run_movements_digest_task`
и т.п. в `backend/app/tasks/background_jobs.py`), а API возвращает `job_id` и клиент
поллит статус. Первый шаг — оффлоад в поток; второй, если недостаточно, — вынос в Celery.

Второе — **частый цикл спрашивает только новые задания, полный обход идёт редко**.
Разделить `poll_fbs_orders_all_sellers` на два таска beat-а:
- `wms.fbs_orders_autopoll_new` — каждые 3 минуты (или меньше), дёргает только
  `fetch_marketplace_orders_new`, не идёт по `for _page in range(MAX_ORDERS_PAGES)`;
- `wms.fbs_orders_autopoll_full` — раз в 30–60 минут, делает полный обход страниц как сейчас
  (для сверки состояния статусов, обнаружения ручных отмен и т.п.).

`MAX_ORDERS_PAGES = 10` и лимит страницы 1000 остаются только для полного цикла. В настройках
появляются два интервала: `fbs_poll_new_interval_sec` (по умолчанию 180) и
`fbs_poll_full_interval_sec` (по умолчанию 1800 или 3600).

Третье — **списки грузятся страницами**. На `S-03` (FfFbsOrdersScreen) вводится честная
серверная пагинация: `limit` уменьшается до 50–100 записей, при скролле подгружается следующая
страница. На вкладках поставок — тот же принцип для обоих запросов (`fetchFbsSupplyWorklist`
и `fetchFbsWorklist`). Дополнительно — увеличить интервал polling с 30 до 60 секунд, поскольку
изменение внутри вкладки — большая редкость по сравнению с частотой обновления. Владелец
про интервал прямо не говорил, помечу это допущением ниже.

Четвёртое — **на сервере появляется запас памяти**. На Railway `Dockerfile.railway`
переводится на многопроцессный запуск: `uvicorn app.main:app --workers 2` (либо gunicorn с
uvicorn-worker'ом). Количество workers — переменная `WEB_CONCURRENCY` в окружении, чтобы
подкручивать без пересборки. Двух процессов достаточно для разделения «сборка ленты в
одном — операторские запросы в другом», а память под каждый — оценивается отдельно. Плюс
Celery-worker на Railway (сейчас его в `Dockerfile.railway` нет вообще; на docker-compose.prod
есть отдельный сервис `celery_worker`, но именно продовое окружение живёт на Railway).
Пока не поднимется Celery-worker, offload в `asyncio.to_thread` даёт основную разгрузку;
Celery — второй шаг для тяжёлой ленты.

Пятое, отдельно — **замеры до и после**. Владелец прямо это назвал: «с замерами до и после,
чтобы результат можно было предъявить». Значит в задаче должны быть:
- время ответа `POST /supplies/{id}/order-print-tape` на 155 и на 500 заказов до и после;
- p95 времени ответа операторских GET-ов (`/fbs/worklist`, `/fbs/supplies/worklist`) во время
  и вне цикла автопулла;
- длительность одного цикла `poll_fbs_orders_all_sellers` (новый и полный);
- пик и среднее RSS-памяти на сервере до и после.

**Признак, что получилось:** после развёртывания сборка ленты на 500 кодов не блокирует
операторские ответы (p95 GET-ов не подскакивает больше, чем на 100 мс, пока идёт печать);
цикл «новых» на 25 продавцах укладывается в 5–10 секунд вместо 2 минут; полный обход идёт
раз в 30–60 минут и не пересекается с окном рабочего времени критично; фронтовый список
подгружает первую страницу за 200–300 мс и не тянет 500 записей одним куском; RSS одного
процесса сервера не растёт монотонно за смену.

Тип решения — «фича инфраструктуры»: не одна правка, а серия связанных шагов (offload
pymupdf → разделение автопулла → пагинация фронта → workers на Railway → замеры). Каждый шаг
самостоятельно измеряется и катится независимо.

## Вопросы и допущения

- **Допущение по интервалу polling S-03.** Владелец про частоту polling ничего не сказал —
  назвал только текущее фактическое «дважды по 500 каждые 26 секунд». Ставлю: polling 60
  секунд, пагинация 50–100. Если для продавца важно видеть новый заказ быстрее — оставляем
  30 секунд, но с пагинацией и меньшим лимитом.
- **Допущение по интервалу полного обхода WB.** Владелец сказал «полный обход редко» без
  конкретики. Ставлю 30 минут по умолчанию (`fbs_poll_full_interval_sec = 1800`); если
  расхождения с WB (отмены, ручные изменения) стали критичны — уменьшаем до 15 минут, если
  редки — увеличиваем до часа.
- **Допущение по числу workers на Railway.** Ставлю 2 воркера uvicorn как отправную точку.
  Точная цифра зависит от лимита памяти инстанса — подкручивается переменной `WEB_CONCURRENCY`
  без пересборки. Владелец сказал «памяти в обрез»: если 2 процесса не помещаются, откатываемся
  на 1 + Celery-worker в соседнем контейнере.
- **Допущение по маршруту ленты.** Первый шаг — `asyncio.to_thread` вокруг pymupdf-операций
  (быстрая правка, ощутимый эффект). Если этого мало на 500 кодах — переносим сборку ленты в
  Celery-таск и возвращаем `job_id` (шаблон уже есть в
  `backend/app/tasks/background_jobs.py`). Владелец решение способа переноса не диктовал; иду
  по цепочке «сначала простое, если недостаточно — сложное».
- **Про Redis/Celery на проде.** В `docker-compose.prod.yml` `celery_worker` есть, а на
  Railway — нет. Допускаю, что Redis на проде подключён (`CELERY_BROKER_URL` в окружении
  Railway); если нет — второй шаг (Celery для ленты) откладывается до подключения брокера, а
  первый шаг (`to_thread`) катится независимо.
