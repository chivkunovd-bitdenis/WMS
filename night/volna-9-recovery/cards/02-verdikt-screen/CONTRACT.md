## Контракт

### Что меняется

**K1. Единый серверный вердикт вместо клиентских догадок.**
И в строке FBS-заказа (`S-03 · таблица`), и в строке рабочего места
поставки (`S-03 · панель действий → блок упаковки`) отображается тот же
`metadata.verdict`, что вычислил сервер по правилу RESHENIYA: `filled`
без `reason` — «WB: проверяет»; `filled/optional/notRequired` с любым
непустым `reason` — «WB не принял»; `optional`/`notRequired` без `reason` —
«WB: код не требуется»; отсутствие или незнакомая подпись — «Нет ответа WB».
Клиент к вычислению вердикта не прикасается: поле readonly.

**K2. Словарь подписей вердикта фиксированный.**
Ровно шесть подписей (см. `frontend/src/screens/v2/fbsApi.ts:191–198`):
`WB: принято`, `WB: код не требуется`, `WB не принял`, `WB: проверяет`,
`WB: нужен код`, `Нет ответа WB`. Тональности — только три:
`ok` / `neutral` / `stop`. Всё, что не входит в перечень, сваливается в
`Нет ответа WB` + `stop` (fail-closed).

**K3. Вердикт словами в строке FBS-заказа.**
Зона колонки «ЧЗ»/маркировки в `FfFbsOrdersScreen.tsx`:
- `StatusChip` c подписью из K2 и тоном из вердикта;
- если у вердикта непустой `reason` — под чипом отдельная строка
  `TextCell` с человеческим переводом («WB не принял: неверный статус УИН»
  и т. п.; неизвестный `reason` показывается как есть — оператор видит
  подсказку, а не молчание);
- если подпись = `Нет ответа WB` — ниже добавляется `TextCell`
  «Сдача пока недоступна» (объясняет запрет заранее, без ожидания сдачи).

**K4. Вердикт словами в строке рабочего места поставки.**
Та же зона «ЧЗ» в строке `FfFbsSupplyWorkspace.tsx`: над кнопками ТЗ/QR/печати
показывается монопространственный хвост кода (если код привязан), под ним —
`StatusChip` из K2 и (если есть) `TextCell` с переводом причины или
подсказкой «Сдача пока недоступна». Никакого второго значка ЧЗ,
никакой второй метки статуса.

**K5. Гейт кнопки «Сдать поставку» единым правилом.**
Кнопка сдачи в панели действий рабочего места поставки — `PrimaryAction`,
блокируется, когда хотя бы у одного заказа поставки вердикт не разрешает
сдачу; в подсказке (`Tooltip`) показывается причина по конкретному заказу
из `metaStatus.disabledReason` (человеческая фраза, без кода WB).
Ровно то же правило работает на сервере, поэтому «зелёная кнопка»
не расходится с реальным ответом сдачи.

**K6. Хвост кода ЧЗ читаем, без окрашивания строки.**
В рабочем месте поставки хвост ЧЗ (`data-testid="fbs-kiz-tail"`)
показывается моношрифтом и **зелёным цветом самого текста**
(`success.dark`). Это признак, что код привязан, — цвет применяется
только к типографике внутри ячейки «ЧЗ», а не к строке целиком.

**K7. Строка заказа в рабочем месте поставки не окрашивается по WB-вердикту.**
_(уточнение по DESIGN-REVIEW · находка 1, файл
`frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx:1911, 1922–1928`)_
- Убирается связка `markingReady = Boolean(tail) && metadata.verdict.delivery_allowed`
  с `bgcolor` и `borderLeftColor` строки.
- Заливка/бордер строки означают одно из трёх и только это:
  1) `info.light` + `info.main` — активная строка сканера
     (`kizScanActive?.order_id === order.id`);
  2) `action.hover` без бордера — заказ уже полностью распечатан
     (`orderPrintDone(order)`) — «уже существующее состояние печати»,
     санкционировано дизайн-ревью;
  3) `background.paper` без бордера — обычное состояние.
- WB-вердикт транслируется исключительно через `StatusChip` в зоне «ЧЗ»
  (K4). Никакой второй сигнал (зелёный фон, зелёная граница) поверх чипа
  не выводится.

**K8. Ошибка загрузки/синхронизации.**
Отдельный `ErrorNotice`/`Alert severity="error"` в теле экрана
на языке склада, без HTTP-кода и стектрейса. Пока ошибка активна и свежий
ответ WB не пришёл — все строки уходят в `Нет ответа WB` + «Сдача пока
недоступна» (fail-closed, регрессия покрыта DEV-04).

### Что убирается

**U1.** Второй визуальный сигнал WB-вердикта на строке рабочего места
поставки: зелёная заливка `success.light` и зелёный бордер `success.main`,
завязанные на `metadata.verdict.delivery_allowed`. Тот же смысл уже
несёт `StatusChip` в зоне «ЧЗ» → R-11, R-35.

**U2.** Клиентские догадки «сдавать можно» без ответа WB
(`MARKING_ACCEPTED_STATUSES` из старой реализации, оптимистичный
`filled → ACCEPTED`, `derive_meta_status` на `check_status=ok`) — уже
закрыто DEV-01/02/03, здесь просто фиксируется, чтобы не вернулось.

**U3.** Технические подписи (`uinBadStatus`, `pending`, `assigned`,
`ACCEPTED`, `signature` в человеческом тексте) на экране не выводятся —
только продуктовый перевод из `metaStatus.ts`.

### Состояния

- **Успех:** `StatusChip` = `WB: принято` (тон `ok`), под ним пусто.
  Кнопка «Сдать поставку» — `PrimaryAction` активна, если все заказы
  поставки в состоянии успеха.
- **Ожидание WB:** `StatusChip` = `WB: проверяет` (тон `neutral`),
  под ним пусто. Кнопка сдачи неактивна, `Tooltip` — «WB ещё не
  подтвердил код».
- **Отказ WB:** `StatusChip` = `WB не принял` (тон `stop`), под ним
  `TextCell` с человеческой причиной. Кнопка сдачи неактивна,
  `Tooltip` = `disabledReason` из вердикта.
- **Код не требуется:** `StatusChip` = `WB: код не требуется`
  (тон `neutral`), под ним пусто. Заказ не блокирует сдачу.
- **Код нужен, ещё не прислали:** `StatusChip` = `WB: нужен код`
  (тон `stop`), под ним `TextCell` «Пришлите ЧЗ». Кнопка сдачи
  неактивна.
- **Нет ответа WB (ошибка/пусто/незнакомая подпись):** `StatusChip` =
  `Нет ответа WB` (тон `stop`), под ним `TextCell` «Сдача пока
  недоступна». Кнопка сдачи неактивна, `Tooltip` — «Ждём ответа
  Wildberries».
- **Пусто в списке заказов** (нет вкладок): стандартный `EmptyState`
  экрана S-03, вердикт не показывается — правило не срабатывает.
- **Ошибка загрузки:** `ErrorNotice` в теле, все строки —
  «Нет ответа WB» + «Сдача пока недоступна».

### Чего на экране нет

- Нет отдельного экрана «Вердикт WB» — вердикт живёт в двух местах S-03
  сразу после ответа WB (решение RESHENIYA).
- Нет заливки строки по WB-вердикту (K7, R-11).
- Нет технических кодов WB, нет числа `decision`, нет `signature`
  как текста.
- Нет «второго значка ЧЗ» рядом с артикулом — сущность ЧЗ показывается
  единственным чипом в зоне «ЧЗ» строки (R-35).
- Нет отдельной кнопки «повторить проверку WB» — свежий вердикт
  прилетает автополлом и разово по сохранению кода; отдельная ручная
  кнопка не решает ни одного пользовательского сценария (принцип
  простоты).
- Нет чипа/колонки «сдавать можно» — единственный признак разрешения
  сдачи это активный `PrimaryAction` «Сдать поставку»; параллельный
  бейдж создавал бы третий источник истины.

## Нехватка ui-kit

Пусто. Все нужные элементы уже есть в `frontend/src/ui-kit/index.ts`:

- `StatusChip` + тональности `ok`/`neutral`/`stop` — для чипа вердикта;
- `TextCell` — для человеческой причины и «Сдача пока недоступна»;
- `PrimaryAction` + `Tooltip` через `disabledReason` — для кнопки «Сдать
  поставку»;
- `ErrorNotice`/`Alert` — для ошибки загрузки.

Новый элемент ui-kit не требуется; правка K7 — это снятие лишней
подсветки строки, а не добавление нового виджета.
