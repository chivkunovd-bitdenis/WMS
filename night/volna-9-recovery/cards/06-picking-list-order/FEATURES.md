## Фичи

### 1. Backend: закрепить все компоненты общего ключа порядка тестом

Для оператора это сохраняет предсказуемую полную ленту: изменение любого из полей
`article → sku_code → size → product_name` не сможет незаметно развести её с
существующим листом подбора. Меняется только доказательство уже принятой серверной
сортировки: тестовые данные должны по отдельности различать каждый компонент ключа,
а не маскировать отсутствие одного поля различием остальных.

Файлы:

- `/Users/deniscivkunov/Projects/WMS/.worktrees/.night-worktrees/volna-9-recovery/lane-3-06-picking-list-order/backend/tests/test_fbs_packaging_integration.py`

Зависимости: нет; серверная реализация сортировки из принятого атома уже существует
и не меняется этой карточкой ремонта.

Проверка: целевой pytest отдельно доказывает порядок полной ленты при различии
только `article`, только `sku_code`, только `size` и только `product_name`, а также
сохраняет числовой `wb_order_id → id` внутри одной группы. Выборочный набор остаётся
в порядке, переданном оператором.

### 2. Frontend: полная лента берёт порядок из ответа сервера, не меняя список упаковки

Для оператора строки упаковки и сканирования КИЗ остаются в прежней видимой
последовательности рабочего места. При «Печати всего» в предпросмотр попадает
фактическая последовательность полной ленты, которую вернул сервер; клиент не
пытается вычислить её по отличающимся полям карточки товара и не переставляет общий
`packingOrders`.

- `/Users/deniscivkunov/Projects/WMS/.worktrees/.night-worktrees/volna-9-recovery/lane-3-06-picking-list-order/frontend/tests-e2e/ff-fbs-supply.spec.ts`

Зависимости: 1.

Проверка: Playwright создаёт намеренное расхождение между полями рабочего места и
серверным ключом листа. После «Печати всего» основной список упаковки сохраняет
свой прежний порядок, а preview и итоговая полная лента следуют серверному ответу;
mock сервера возвращает этот порядок независимо от порядка `order_ids` в запросе.
Сценарий не меняет и отдельно подтверждает прежнюю семантику строковой и выборочной
печати.

## Порядок

1. Сначала выполнить фичу 1: она фиксирует полный контракт серверного ключа, на
   который опирается проверка клиентского сценария.
2. Затем выполнить фичу 2: она убирает клиентскую альтернативную сортировку и
   подтверждает через UI соответствие preview фактическому серверному результату.

В этой ремонтной карточке параллельных атомов нет: второй атом использует
зафиксированный первым контракт и оба изменения фронтенда принадлежат одному
связанному сценарию.
