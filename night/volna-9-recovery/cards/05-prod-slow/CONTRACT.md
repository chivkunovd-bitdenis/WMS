МАКЕТ: НЕ НУЖЕН
UI-KIT: ХВАТАЕТ

Это не проектирование карточки заново, а точечное уточнение контракта по
четырём находкам из
`night/volna-9-recovery/cards/05-prod-slow/DESIGN-REVIEW.md`. Продуктовые
решения из `RESHENIYA.md` и границы `ARCH-CROSS.md` (карточка 05 меняет
только нагрузку и расписание импорта заказов и печать ленты, без нового
экрана, без новой сущности, без перекрёстных с 01 контуров marking metadata)
сохраняются буквально. Ниже описано только то, что должен доделать
screen-dev поверх уже влитой работы DEV-01…DEV-07.

## Контракт

Задеваем ровно два места:

**Экран S-03 «Заказы FBS», вкладка «Новые», таблица `fbs-worklist-table`.**
Файл `frontend/src/screens/v2/FfFbsOrdersScreen.tsx`, шапка таблицы вокруг
строки 1304 и стилизация строки в `NewOrderRow` вокруг строки 242. Меняем:

- Четыре информационных заголовка «Товар», «Селлер», «Маршрут сдачи»,
  «Отгрузить до» получают фиксированную `width` вместо одной лишь
  `minWidth`. Согласованные значения — те же, что уже подобраны как
  минимальные: 210 / 135 / 180 / 140. Это фиксирует, а не расширяет
  контракт, чтобы столбцы не расползались, когда WB присылает длинные
  подписи маршрута или названия товара. Ячейка чекбокса остаётся
  служебной (`padding="checkbox"`), пятой колонки «Статус» во вкладке
  «Новые» по-прежнему нет.
- К каждому из четырёх заголовков добавляется запрет переноса
  (`whiteSpace: 'nowrap'` или `noWrap`), чтобы при сжатии окна шапка не
  становилась двухстрочной и не рвала связь колонки с данными.
- Из строки заказа убирается жёлтая заливка при попадании в результат
  поиска (`highlighted` → сейчас заводит `bgcolor: 'rgba(255, 214, 102,
  0.24)'` и hover-вариант). Заливка на строке во всей системе означает
  ровно одно — расхождение по количеству; результат поиска расхождением
  не является и подсвечиваться цветом не должен. Оператор всё равно
  видит найденную строку — она уже поднимается в область просмотра
  существующим `scrollMarginBottom: '220px'` и `registerRow`. Проп
  `highlighted` и логика `matchingIds` могут остаться на месте (они
  дальше нужны для scroll-into-view), но визуально ничего в строке не
  меняют.

Что ещё во вкладке «Новые» **не** меняется: набор колонок (эталон
`etalon` — четыре информационных колонки без «Статуса»), плотность
`size="small"`, `stickyHeader`, `TableSkeletonBody columns=5 rows=5` в
первую загрузку, курсорная догрузка через `TableLoadMore`, тексты
пустого состояния, поведение «Выбрать все» поверх серверных курсоров.

**Модалка печати ЧЗ, состояние «Готовим ленту…».** Файл
`frontend/src/components/MarkingPrintDialog.tsx`, функция
`TapePreparationStatus`, строка 128. Меняем:

- Из ветки `state === 'preparing'` убирается блок
  `<ActionGroup><SecondaryAction onClick={onClose}>Закрыть</SecondaryAction></ActionGroup>`.
  В этом состоянии главного действия нет — сборка идёт в фоне, и
  оператору сказано «Можно продолжать работу в WMS». Одиночная контурная
  кнопка рядом с этим сообщением визуально спорит с «продолжай работу» и
  нарушает правило «контурная бывает только рядом с главной».
- Штатное закрытие модалки сохраняется: `Dialog` уже принимает
  `onClose` при клике по backdrop и по Esc (`MarkingPrintDialog.tsx`
  строка 1088). Крестик заголовка в этой модалке не заводим — это уже
  был бы новый элемент, задачи под него нет.

Состояние `state === 'ready'` (StatusChip «Готово» + PrimaryAction
«Открыть для печати») не трогаем: пара «StatusChip + одна главная кнопка»
уже соответствует канону и решению 7 из `RESHENIYA.md`.

Состояние ошибки (`expired` / `open_failed` / общее «Не удалось собрать
ленту. Попробуйте ещё раз») тоже не меняем: там `ErrorNotice` +
`PrimaryAction "Повторить"` + `SecondaryAction "Закрыть"` — контурная
стоит рядом с главной, R-31 удовлетворяет.

## Что убирается

- `ActionGroup` с одиночной `SecondaryAction "Закрыть"` из ветки
  `preparing` в `TapePreparationStatus` (`MarkingPrintDialog.tsx`,
  строка 128).

## Состояния

- **Успех вкладки «Новые».** Первые до 50 строк заказов, за таблицей —
  `TableLoadMore` с действием «Показать ещё», если сервер вернул
  `next_cursor`. Строка результата поиска видна за счёт скролла к ней,
  без цветовой заливки.
- **Пусто.** Уже покрыто в реализации: строка `EmptyState`
  «Новых заказов… нет. Автоматическая загрузка Wildberries…» — не
  меняется.
- **Ошибка списка.** `ErrorNotice` над таблицей с кнопкой повтора — не
  меняется.
- **Готовим ленту (фоновое задание).** Текст «Готовим ленту…»,
  `StatusChip label="Готовим к печати" tone="neutral"`, подпись
  «Можно продолжать работу в WMS — лента собирается в фоне». Никаких
  кнопок в самой карточке состояния: закрывать модалку — стандартными
  средствами Dialog (Esc / клик мимо).
- **Лента готова.** `StatusChip label="Готово" tone="ok"` +
  `PrimaryAction "Открыть для печати"`. Автооткрытия не появляется
  (решение 7 из `RESHENIYA.md`).
- **Не удалось собрать / истекло / не удалось открыть.** `ErrorNotice`
  с точной формулировкой + пара `PrimaryAction "Повторить"` /
  `SecondaryAction "Закрыть"`.

## Чего на экране нет

- Нет колонки «Статус» во вкладке «Новые» (эталон `etalon`).
- Нет цветовой подсветки строки результата поиска — только скролл в
  видимую область.
- Нет одиночной контурной кнопки в состоянии «Готовим ленту…».
- Нет новых чипов, статусов, тултипов, крестика в заголовке модалки,
  прогресс-бара сборки, автооткрытия готового PDF, пользовательской
  настройки расписания синка WB, отдельного экрана «производительность»
  и отдельного пользовательского уведомления о сверке (границы из
  `RESHENIYA.md` и `ARCH-CROSS.md`).

## Макет

Отдельного `MOCKUP.html` в этой карточке не создаётся и не требуется:
все изменения точечные, внутри двух уже существующих экранов из
`frontend/screens.registry.json`:

- S-03 (`/app/ff/fbs`, `FfFbsOrdersScreen`) — зона «таблица»;
- `MarkingPrintDialog` — модалка, общая для S-03 / S-14 / S-15
  (по реестру `screens.registry.json`, поле `shared`).

Никакой новой зоны экрана, нового модального окна, нового пункта меню,
нового пункта настроек эти правки не добавляют. Список зон S-03
(«шапка», «фильтры», «таблица», «панель действий», «модалка») не
меняется. Соседние экраны (S-14, S-15) через модалку `MarkingPrintDialog`
получают только уборку одной лишней кнопки в состоянии «Готовим ленту…» —
это не изменение UX этих экранов, а следствие правила R-31 в общем
компоненте.
