# Архитектура · 05-prod-slow

Карточка: `05-prod-slow`

Роль: `solution-architect`

Дата исследования: 2026-08-22

## Как это решают другие

### Wildberries: новые задания сохраняют локально, полный список используют для сверки

Wildberries разделяет два чтения FBS-заказов по смыслу. `GET /api/v3/orders/new`
возвращает все задания, которые сейчас находятся в состоянии «новое». Сам WB рекомендует
получать новые задания этим методом, сохранять их у себя и тем самым сокращать повторные
обращения. Это прямо соответствует нашей потребности в коротком частом цикле: он должен
получать только новые строки и идемпотентно обновлять локальный `FbsOrder`, а не перечитывать
всю историю. Источники: [документация FBS-заказов](https://dev.wildberries.ru/openapi/orders-fbs/),
[инструкция «Заказы FBS»](https://dev.wildberries.ru/knowledge-base/articles/019d49a4-0771-7571-aea9-11d5b597f34c/zakazy-fbs),
[ответ команды WB API о сохранении новых заданий локально](https://dev.wildberries.ru/forum/1617).

`GET /api/v3/orders` решает другую задачу: он возвращает задания за период до 30 дней,
работает с `limit` до 1000 и токеном продолжения `next`, но не возвращает актуальный
статус. Каждый запрос страницы расходует внешний лимит. Поэтому этот метод применим нам
как редкая сверка пропусков и изменений, сделанных вне WMS, но не как часть трёхминутного
цикла. Для статусов остаётся отдельный пакетный `POST /api/v3/orders/status` — до 1000 ID
за запрос. Источники: [описание `GET /api/v3/orders` и статусного метода](https://dev.wildberries.ru/openapi/orders-fbs/),
[рекомендации WB по токену продолжения](https://dev.wildberries.ru/knowledge-base/articles/019d50e0-4e66-71d7-a4df-1021f5d4447b/paginatsiia-i-rabota-s-bol-shimi-dannymi-v-wb-api).

У методов FBS-заказов, поставок и пропусков общий лимит на аккаунт продавца: 300 запросов
в минуту, минимальный интервал 200 мс и всплеск до 20 запросов; возможен ответ `429`.
Для нас это означает две вещи: продавцов можно обрабатывать независимо, но запросы одного
продавца нельзя бесконтрольно распараллеливать; повтор после `429` должен идти с задержкой
и случайным разбросом, а не немедленно. Источник:
[официальная документация WB FBS](https://dev.wildberries.ru/openapi/orders-fbs/).

### Асинхронный API: вычисления не выполняют внутри event loop

FastAPI запускает обычную синхронную функцию маршрута во внешнем пуле потоков, но обычная
синхронная вспомогательная функция, вызванная из `async def`, исполняется прямо в потоке
event loop. Это полностью совпадает с текущим дефектом: PyMuPDF вызывается из асинхронного
сервиса напрямую и задерживает все соседние запросы. Источник:
[FastAPI — Concurrency and async/await](https://fastapi.tiangolo.com/async/).

При этом простой `to_thread` не является универсальным исполнителем CPU-нагрузки: Python
указывает, что из-за GIL (глобальной блокировки интерпретатора) этот приём обычно предназначен
для блокирующего ввода-вывода; для CPU он надёжен лишь у расширений, освобождающих GIL.
Документация `asyncio` отдельно рекомендует не вызывать CPU-bound код в event loop и допускает
процессный исполнитель. Поэтому поток годится как дешёвая проверяемая заплатка, но не как
гарантированная изоляция печатной сборки. Источники:
[Python 3.11 — Running in Threads](https://docs.python.org/3.11/library/asyncio-task.html#running-in-threads),
[Python 3.11 — Running Blocking Code](https://docs.python.org/3.11/library/asyncio-dev.html#running-blocking-code).

### Фоновые задания: один планировщик, защита от наложения, отдельная очередь

Celery Beat только ставит периодические задания в очередь. Официальная документация требует
единственный активный планировщик для одного расписания и предупреждает, что периодические
задания могут наложиться, если предыдущий запуск ещё не закончился. Для нас применимы один
Beat, отдельные имена лёгкой и полной синхронизации и single-flight-блокировка — запрет двух
одинаковых синков одного продавца одновременно. Общий seller-wide lock вокруг сетевого чтения
для этого не нужен: он блокирует несвязанные ручные операции. Источник:
[Celery — Periodic Tasks](https://docs.celeryq.dev/en/main/userguide/periodic-tasks.html).

### Браузер: невидимая вкладка не должна продолжать опрос

Page Visibility API создан в том числе для панелей, которым не нужно опрашивать сервер,
когда вкладка скрыта. `FfFbsOrdersScreen` уже следует этому правилу через `document.hidden`;
архитектура сохраняет этот механизм и не добавляет параллельный поллер. Источник:
[MDN — Page Visibility API](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API).

### Память: сначала ресурсный запас и границы, потом дополнительные API workers

Uvicorn поддерживает несколько worker-процессов и перезапускает погибшие процессы, но каждый
worker является отдельным процессом. Из этого следует, что добавление второго worker на
машине, уже ушедшей в swap, увеличит суммарный рабочий набор памяти и не устранит лишние
5300 заказов или 500 PDF в одном запросе. Docker позволяет задать контейнерам лимиты и
резервы CPU/RAM; это полезно как предохранитель после разнесения WMS на машину с запасом,
но лимит сам по себе не создаёт память. Источники:
[Uvicorn — Deployment](https://www.uvicorn.org/deployment/),
[Docker Compose — resource limits and reservations](https://docs.docker.com/reference/compose-file/deploy/#resources).

Применимо нам: сначала убрать усиление нагрузки и вынести печать из API, затем разместить WMS
на отдельной машине с 8 ГБ RAM и измерить фактический пик. Не применимо в этой волне:
«лечить» задержки только количеством Uvicorn workers или бесконтрольной параллельностью Celery.

## Решение

**Рекомендуемый вариант: выделить ограниченную очередь печатных сборок, разделить WB-опрос
на частый импорт новых заданий и часовую сверку, а FBS-список грузить существующим курсором
по 50 строк — это устраняет сами источники блокировки, не создавая новый пользовательский
раздел и новые бизнес-сущности.**

Это одна архитектурная программа, но для разработки она режется на четыре атомарные карточки.
Их можно проверять и выкатывать независимо; смешивать их в одном dev-проходе не следует.

### A. Печатная сборка вне API-процесса

Только подтверждённый владельцем случай `POST /marking-codes/label-artifact-tape` переводится
в существующий механизм `BackgroundJob`:

1. API валидирует tenant, seller, список `code_ids`, размер страницы и лимит 500, создаёт
   задание типа `marking_label_tape` и отвечает `202` с `job_id`.
2. Задание направляется в отдельную очередь `print`, которую обслуживает ровно один процесс.
   Ограничение в один процесс защищает RAM от двух одновременных лент по 500 кодов.
3. Worker последовательно читает `MarkingCode.label_artifact_pdf`, собирает итог и сохраняет
   его через существующее хранилище `FbsPrintAsset`/`fbs_print_asset_storage`, расширенное
   видом `label_tape`. В `BackgroundJob.result_json` хранится только `asset_id`, не PDF.
4. Существующая модалка печати показывает одно состояние «Готовим ленту…», опрашивает
   `BackgroundJob`, а после `done` открывает скачивание существующего print asset. Новый
   экран и отдельная настройка не появляются.
5. Повтор одного и того же запроса с тем же ключом идемпотентности возвращает существующее
   незавершённое или готовое задание. Артефакт получает срок хранения; после истечения файл
   удаляется фоновой уборкой, запись остаётся пригодной для аудита без бинарного содержимого.

Внутри worker PDF следует собирать последовательно, не удерживая отдельный список всех BLOB
дольше необходимого. У очереди должны быть тайм-аут, контролируемая ошибка и ограничение RAM;
падение печатного worker не должно перезапускать API.

`POST /fbs/supplies/{supply_id}/order-print-tape` в эту карточку не включается: предыдущая
сверка правильно отметила, что владелец не давал по нему замеров. Его нужно отдельно измерить;
если он блокирует event loop тем же способом, он переезжает на ту же очередь отдельной
атомарной карточкой.

### B. Два независимых контура синхронизации WB

Текущий `sync_seller_orders` разделяется по ответственности:

- `sync_new_orders_for_seller` — каждые 180 секунд получает только
  `GET /api/v3/orders/new`, идемпотентно upsert-ит строки по существующему WB order ID и
  завершает работу. Он не листает `GET /api/v3/orders`, не связывает все поставки и не
  запускает полный статусный обход.
- `reconcile_orders_for_seller` — раз в 60 минут проходит `GET /api/v3/orders` по `next`,
  сохраняет страницы небольшими транзакциями и после успешного прохода выполняет локальную
  сверку связей с поставками. Ошибка страницы не удаляет локальные данные и не превращает
  неполный обход в «успешный».
- Существующий статусный контур остаётся отдельным и запрашивает актуальные статусы пакетами
  через `POST /api/v3/orders/status`; это необходимо, потому что полный список актуальных
  статусов не содержит.

Beat не должен выполнять один двухминутный последовательный обход 25 продавцов. Он создаёт
отдельное задание на продавца с равномерным распределением по интервалу. На текущей малой
машине одновременно исполняется не больше двух сетевых синков; после ресурсных замеров число
можно поднять, но лимит на аккаунт WB остаётся отдельным для каждого продавца.

Вместо seller-wide блокировки вводится single-flight по паре `(seller_id, sync_kind)`:
одновременно нельзя запустить два `new` или два `reconcile` одного продавца. Читающий sync
не держит блокировку ручных операций на всё время HTTP-запросов. Конфликт записи решают
уникальный WB order ID, идемпотентный upsert и короткая транзакция. Блокировки внешних
изменяющих команд WB остаются в своих операционных сервисах и не переопределяются этой
карточкой.

Для `429`, сетевого отказа и `5xx` применяется ограниченный exponential backoff с jitter
(нарастающая задержка со случайным разбросом). При `401/403` повтор не выполняется: sync
фиксирует безопасный код ошибки без значения токена. Полный проход не запускается повторно,
пока предыдущий экземпляр того же продавца не завершён или не истёк его lease.

### C. Курсорная загрузка существующего экрана

На S-03 `/app/ff/fbs` новый экран не создаётся.

- Вкладка «Новые» получает 50 строк существующей ручкой worklist и хранит
  `next_cursor`. Следующая страница загружается по явной кнопке «Показать ещё» — это проще
  и предсказуемее бесконечной прокрутки для оператора, который выделяет заказы.
- Автообновление раз в 30 секунд работает только у видимой вкладки и обновляет первую
  страницу. Уже загруженные страницы и выделение не исчезают; новые строки показываются
  сверху или через один неблокирующий признак обновления, без дополнительной колонки.
- «Выбрать все» продолжает обходить курсоры на сервере по существующей логике и не означает
  «выбрать только видимые 50».
- Для остальных вкладок первая порция ограничивается 100 строками. Если у
  `fetchFbsSupplyWorklist` нет курсора, в этой волне не создаётся фиктивная пагинация:
  сначала измеряется реальный объём этих вкладок, затем при превышении 100 оформляется
  отдельная карточка на курсор этой ручки.

`NotificationBell` и 15-секундный polling рабочего места поставки не входят в это изменение:
они не создают подтверждённые два ответа по 500 строк. Это убирает найденное предыдущей
ролью переусложнение.

### D. Ресурсный запас и измеримая приёмка

WMS следует вынести с общей 3.8-ГБ машины на отдельную ноду минимум с 8 ГБ RAM. Если
операционно быстрее расширить текущую машину, это допустимый промежуточный шаг, но три
проекта не должны остаться без изоляции и наблюдаемых границ. Для `api`, обычного Celery
worker и `print` worker задаются отдельные reservations/limits после измерения их реального
пика. До появления запаса `uvicorn --workers 2` не включается.

Замеры выполняются одним воспроизводимым сценарием до изменения и после него, на одном
наборе данных и с одинаковым числом клиентов:

- печать 155 и 500 кодов: полное время задания, очередь, peak RSS печатного worker,
  параллельный `/health` и обычный API-запрос; цель — p95 `/health` не выше 100 мс и p99
  не выше 250 мс во время сборки, без роста RSS API на размер ленты;
- WB: число запросов и полученных строк на продавца, длительность `new`, `reconcile`,
  status sync, количество `429`, повторов и пропущенных запусков; цель — частый цикл всех
  25 продавцов p95 до 30 секунд, без полного `GET /api/v3/orders` в этом цикле;
- экран: строки и байты первой загрузки, время до видимой таблицы, запросы за час у видимой
  и скрытой вкладки; цель — первая порция ровно до 50 заказов и ноль worklist-запросов от
  скрытой вкладки;
- инфраструктура: RSS по контейнерам, общий memory working set, swap in/out, OOM и рестарты;
  цель — на пиковом сценарии занято не более 70% RAM ноды, устойчивый swap in/out равен
  нулю, API и workers не перезапускаются.

Числа сохраняются в приложенном отчёте «до/после»; один удачный запрос не считается
замером — берётся минимум 30 повторов для latency и полный час для периодических циклов.

## Границы

### Что делает наша система

- хранит однажды полученные WB-задания и безопасно повторяет upsert по WB order ID;
- часто получает новые задания, отдельно сверяет полный диапазон и отдельно обновляет статусы;
- соблюдает внешние лимиты, не запускает одинаковые sync одного продавца одновременно,
  пишет метрики без токенов и персональных данных;
- собирает PDF вне API-процесса, показывает оператору простое состояние ожидания и отдаёт
  готовый артефакт в существующем окне печати;
- отдаёт экрану первую небольшую страницу и курсор, сохраняет выделение между обновлениями;
- измеряет latency, внешний трафик и память до/после.

### Что остаётся на стороне Wildberries

- создание FBS-сборочного задания и его внешний ID;
- источник новых заданий, актуальных статусов, состава поставок и внешних ошибок;
- лимиты запросов и ответы `401/403/429/5xx`;
- изменения, сделанные человеком непосредственно в кабинете WB, которые WMS обнаружит
  ближайшей статусной или полной сверкой.

### Что человек делает руками

- оператор продолжает работать на том же экране S-03: открывает заказы, подгружает следующую
  страницу при необходимости и запускает печать;
- при подготовке ленты ждёт в той же модалке и повторяет задание после понятной ошибки;
- администратор инфраструктуры выделяет ноду/память и применяет resource limits по результатам
  замера; боевой сервер `194.87.96.144` этой архитектурной ролью не затрагивается.

## Переиспользуем / расширяем / новое

| Сущность внешнего API или нагрузки | Наша сущность | Решение |
|---|---|---|
| WB FBS assembly order из `GET /api/v3/orders/new` | `FbsOrder` | **Переиспользуем** без новой таблицы; upsert по существующему WB order ID. |
| Строка редкой сверки из `GET /api/v3/orders` | `FbsOrder` | **Переиспользуем**; меняется только отдельный сервис и расписание reconciliation. |
| `supplierStatus` / `wbStatus` из пакетного status API | поля статуса `FbsOrder` | **Переиспользуем**; статусный цикл остаётся отдельным. |
| Токен продолжения WB `next` | локальная переменная одного reconciliation-run | **Переиспользуем как протокол**, постоянно не храним: неуспешный run начинается заново и не объявляется успешным. |
| Область rate limit — аккаунт продавца WB | `Seller` + существующая интеграционная привязка | **Переиспользуем**; значения токенов архитектурная роль не читает и в метрики не пишет. |
| Периодический запуск WB | Celery Beat + tasks | **Расширяем** двумя именованными задачами `new` и `reconcile`, single-flight по `(seller_id, sync_kind)`. |
| Сохранённая этикетка ЧЗ | `MarkingCode.label_artifact_pdf` | **Переиспользуем** как вход; модель кода не меняется. |

## Риски

### Внешний API: отказ, лимиты, дубли и повторы

- `GET /orders/new` возвращает состояние, а не поток событий: одинаковые задания придут
  повторно. Защита — idempotent upsert по WB order ID; повтор не создаёт второй заказ.
- Если WB недоступен, локальные данные не удаляются и экран продолжает показывать последний
  подтверждённый снимок. Ошибка sync наблюдаема, но не блокирует складскую работу с уже
  импортированными заданиями.
- `429` и `5xx` повторяются ограниченно с backoff+jitter; `401/403` не зацикливаются.
- Частично пройденный `GET /orders` не становится основанием считать отсутствующие строки
  удалёнными или завершёнными. Только полностью успешная сверка может закрыть reconciliation.
- Beat может поставить задачи повторно; single-flight с lease не допускает наложения одного
  вида sync по одному продавцу, а истечение lease восстанавливает работу после падения worker.
- Ручная операция WB и читающий sync могут встретиться на одной локальной строке; короткие
  транзакции и idempotent upsert заменяют двухминутный seller-wide lock. Внешние mutation-locks
  не снимаются этой карточкой.

### Внутренние риски

- Новый асинхронный контракт печати требует состояния `pending/running/done/failed` в модалке;
  если оставить старое ожидание бинарного ответа, оператор нажмёт кнопку повторно и создаст
  дубли. Нужны idempotency key и заблокированная повторная кнопка, пока job активен.
- Один print worker создаёт очередь при одновременной печати; это сознательная цена защиты
  RAM. В UI показывается ожидание, а метрика queue time определяет, нужен ли второй worker
  после увеличения памяти.
- `FbsPrintAsset` сейчас ориентирован на FBS-артефакты. Расширение видом `label_tape` допустимо,
  потому что модель уже хранит tenant, seller, content type и storage path; нельзя добавлять
  готовый PDF в `BackgroundJob.result_json` или новую дублирующую таблицу.
- Уменьшение страницы может сломать семантику массового выбора. Приёмка обязана доказать,
  что «Выбрать все» проходит серверные курсоры, а выделение не теряется при автообновлении.
- Увеличение RAM без устранения лишних запросов лишь отсрочит деградацию; поэтому инфрашаг
  принимается только вместе с метриками приложения.

### Чего не делаем в этой волне

- не добавляем новый экран производительности, пользовательские настройки частоты опроса,
  технические чипы, колонки или графики в S-03;
- не меняем `NotificationBell` и 15-секундный polling рабочего места поставки без отдельного
  замера;
- не переносим `order-print-tape` на новую очередь без подтверждающего нагрузочного теста;
- не внедряем WebSocket/SSE, Redis-кэш списков, Kafka, event sourcing или новую таблицу заказов;
- не увеличиваем число Uvicorn workers на 3.8-ГБ машине и не запускаем несколько print jobs
  одновременно;
- не меняем бизнес-статусы FBS, правила поставок, маркировки и складских операций;
- не читаем и не меняем токены, ключи, `.env` и кабинеты учётных данных;
- не трогаем боевой прод `194.87.96.144` и не выполняем запись в живой кабинет WB.

## Допущения

1. Полная WB-сверка идёт раз в 60 минут. Это в 20 раз реже текущего трёхминутного полного
   обхода и оставляет понятное максимальное окно восстановления изменений, сделанных вне WMS.
2. Частый импорт новых заданий остаётся раз в 180 секунд: это уже известное операторам
   ожидание и оно укладывается в лимиты WB после удаления полного обхода.
3. Первая страница «Новых» равна 50 строкам и догружается кнопкой «Показать ещё»: явное
   действие не теряет позицию оператора и проще бесконечной прокрутки.
4. Максимум 500 кодов в ленте сохраняется, но одновременно строится одна лента. Так сохраняется
   текущая полезная возможность, а пиковая память становится ограниченной и наблюдаемой.
5. WMS получает отдельную ноду минимум 8 ГБ; второй API worker рассматривается только после
   замера пикового потребления и достижения не менее 30% свободного headroom.
