- Фильтры на экране: селлер, дата с, дата по, поиск по названию/артикулу/SKU/ШК
  (`FfReportsPage.tsx:244–279`). Есть кнопка «Скачать Excel» — рендерит HTML-таблицу и
  сохраняет как `.xls` (`FfReportsPage.tsx:95–141`).
- Разрез только один — **по товару** с колонками «приход/расход» по каждой группе операций.
  Разрезов «по продавцу», «по складу», «по маркетплейсу», «по операции» самостоятельно
  нет — есть только фильтр по одному селлеру и фильтр по складу на ручке (в UI не проброшен,
  `inventory_movements.py:99`). Ни KPI, ни графиков, ни сравнения периодов, ни накопительных
  цифр, ни дашборда.
- **В портале селлера отчётности нет вообще.** У селлера есть только дашборд-заглушка
  `frontend/src/screens/v2/SellerDashboardScreen.tsx:13` с четырьмя счётчиками (заявки на
  поставку/отгрузку, товары, акты корректировки) и двумя placeholder-карточками «Мой
  контекст» / «Быстрые действия». Никаких выгрузок, никаких периодов, ни рубля денег в
  разрезе не показано.
- «Служебный расчёт работ упаковщиков», о котором говорит владелец — это
  `backend/app/services/staff_packaging_billing_service.py`: считает `units_packed` и
  `earned_kopecks` за месяц по завершённым `PackagingTask` для конкретного сотрудника ФФ.
  Это HR-калькулятор зарплаты упаковщика, не отчёт продавцу. Владелец прав, что к отчётности
  это отношения не имеет.

Проверял git по всем веткам: `git log --all --grep=report` находит только техкоммиты (TC
coverage report, UX master report, FBS acceptance report — всё документация о разработке, а не
пользовательская отчётность). `git log --all --grep=analytics` даёт один коммит
`7a68117 docs: add performance and analytics backlog items` — это про бэклог, не про код.
Веток `*report*`/`*analytic*`/`*dashboard*` с продуктовым содержанием нет (есть только
`chore/tc-coverage-report` и `codex/mp-dashboard-e2e-20260815`, оба про тестовую обвязку).

Итого: имеется MVP-отчёт «движения по товару» для ФФ. Всё остальное, о чём говорит владелец
(селлерская отчётность, разрезы по складу/МП/операции, KPI, накопительные, сравнения,
визуализация) — не сделано.

## Что должно быть

Полноценный раздел «Отчёты», доступный обоим порталам — ФФ и селлеру — с несколькими
готовыми разрезами и с одинаковой «сеткой» фильтров: период (с — по), сравнительный период
(предыдущий/год назад/произвольный), фильтр по селлеру (для ФФ), по складу, по маркетплейсу,
по товару, по операции. Каждый разрез отвечает на один вопрос пользователя, показывает
одновременно и цифры, и график, и позволяет скачать таблицу.

Признак, по которому поймём, что получилось:

- В портале селлера появился пункт меню «Отчёты» и хотя бы три разреза, отвечающих на
  вопросы «сколько у меня продали за период», «сколько сейчас лежит и сколько это стоит
  мне», «какие товары движутся, какие мёртвые».
- В портале ФФ раздел «Отчёты» перестал быть одной страницей «движения по товару» и стал
  списком отчётов с разрезами: по продавцу (обороты, счета, задолженность), по складу
  (загрузка, движения), по маркетплейсу (что уехало/пришло), по товару (текущий сейчас
  разрез), по операции (сколько приёмок/отгрузок/FBS за период, кто делал).
- В каждом отчёте видны и «за период», и «накопительно с начала месяца/года», и «сравнение
  с прошлым периодом» — три колонки/линии на одном экране, без переключения.
- Селлер видит только своё, ФФ — всё в разрезе tenant.
- Есть выгрузка (Excel и/или CSV) с той же сеткой, что на экране.

Это `домен`-задача: владелец сам говорит «список требований не окончательный, продумать».
Первым шагом здесь идёт исследование продуктового аналитика: собрать вопросы селлера
(«сколько денег заработал», «где лежат мёртвые остатки», «когда следующая приёмка», «сколько
я должен ФФ») и вопросы ФФ (загрузка склада, оборачиваемость, работа упаковщиков, выручка
по клиенту, задолженность клиентов), и только потом резать на подкарточки под конкретные
отчёты. Отдельно нужно решить, где живут накопительные агрегаты — считаем налету из
`inventory_movements` (сейчас так работает существующая ручка), или заводим материализованную
витрину, потому что за квартал по десяткам тысяч движений `SUM/GROUP BY` перестанет отдавать
за секунду.

## Вопросы и допущения

**Допущения (принял сам, помечаю явно — это новый раздел, ломать нечего):**

1. Раздел строится на **двух порталах** — и у селлера, и у ФФ. Владелец так и написал.
   Селлер видит только свои данные, ФФ видит tenant целиком с фильтром по селлеру.
2. Существующий `FfReportsPage` не удаляем, а переиспользуем как один из отчётов раздела
   («Движения по товару»). Ломать работающее хуже, чем расширять рядом.
3. Первая волна отчётов — read-only поверх уже существующих таблиц (`inventory_movements`,
   `packaging_task`, `fbs_orders`, `marketplace_unload_*`, `outbound_shipment`, `seller`,
   `warehouse`). Никаких новых сущностей на первом шаге, только запросы и агрегации.
4. Хранение данных: сначала считаем налету, витрину/материализацию добавляем в отдельной
   карточке, если запросы начнут тормозить (это связка с карточкой `05-prod-slow`).
5. Визуализация — MUI + `recharts` или встроенные бары/линии MUI. Отдельная библиотека
   графиков в этой волне не заводится.
6. Деньги (тарифы селлера, счета, задолженность) — это пересечение с карточками
   `08-storage` (хранение как биллинг) и `09-billing` (счета). В отчёты они попадают, но
   логика начисления живёт там, здесь только чтение.

**Открытые вопросы к продакту** (нужны до начала UX-разработки, но не блокируют разбор):

- Приоритет отчётов первой волны: с чего начинаем — с селлерского «сколько я заработал/сколько
  должен» или с ФФ-шного «загрузка склада и оборачиваемость»?
- Ролевая модель внутри селлера: все ли сотрудники селлера видят все его отчёты, или деньги
  видит только владелец аккаунта селлера?
- Формат выгрузки — оставить только Excel (как сейчас), добавить CSV или сразу делать
  PDF-отчёт с логотипом ФФ (нужно для формальных отчётов клиенту)?
- Глубина хранения: сколько месяцев истории отдаём в отчётах? Год, три года, всё?
