# FEATURES · 04-warehouse-switch · перепланирование после REVIEW

Три незакрытые находки из второго прохода ревью, разбиты на четыре атома. Принятые атомы 1–13 не возвращаются к разработке. Первый frontend-атом (Ф-2) создаёт ui-kit компонент; только после него идут экранные правки.

## Фичи

### 1. Бэкенд: принять warehouse_id при редактировании черновика приёмки

**Что не работает сейчас.** Схема `InboundIntakeRequestPlannedPatch` не содержит поле `warehouse_id`. FastAPI молча игнорирует поле, которое фронтенд S-28 отправляет в теле PATCH; в ответ возвращается документ со старым складом. Экран селлера трактует это как ошибку и откатывает выбор. Кейс `S-28-TC-001` не может пройти через реальный API.

**Что меняем.** В схему добавляется опциональное `warehouse_id: uuid.UUID | None`. Роутер передаёт его в сервис с флагом `warehouse_id_set`. Сервис применяет новый склад, только если черновик в статусе `draft` и склад операционный для этого tenant; в противном случае — известный `InboundIntakeError` с кодом `invalid_warehouse`. Тест проверяет: успешное сохранение нового склада, запрет смены после передачи и отказ при неоперационном складе.

**Файлы (только бэкенд):**
- `backend/app/api/inbound_intake.py` — добавить `warehouse_id` в `InboundIntakeRequestPlannedPatch`; пробросить в вызов `svc.patch_request_draft`
- `backend/app/services/inbound_intake_service.py` — принять `warehouse_id` и `warehouse_id_set` в `patch_request_draft`; добавить проверку операционности склада через уже существующий `Warehouse.is_operational`
- `backend/tests/test_inbound_intake.py` — три теста: сохраняет склад при `warehouse_id_set`, отклоняет с `409` после передачи, отклоняет с `422` при неоперационном складе

**Зависит от:** атомов 1–3 (уже приземлены; `Warehouse.is_operational` и сервисы операционного склада готовы).

**Как проверить.** `pytest -q backend/tests/test_inbound_intake.py -k "warehouse"` — зелёный. Запрос `PATCH /operations/inbound-intake-requests/{id}` с `{"warehouse_id": "<valid-operational-id>"}` на черновике возвращает `200` с обновлённым `warehouse_id`. Тот же запрос после `status != draft` возвращает `409`.

### 2. Фронтенд: ui-kit компонент WarehouseNoContextState

**Что не хватает.** Несколько экранов (упаковка, приёмка, FBS) должны показывать единообразную заглушку «Нет рабочего склада» при нулевом `selectedWarehouseId`. Сейчас каждый экран рисует свою разметку (или не рисует ничего — молчаливый пустой список), что ведёт к разнобою. Нужен один переиспользуемый компонент в ui-kit, чтобы экранные атомы импортировали его, а не дублировали вёрстку.

**Что меняем.** В `frontend/src/ui-kit/States.tsx` добавляется экспортируемая функция `WarehouseNoContextState` — обёртка над уже существующим `EmptyState` с фиксированным заголовком «Нет рабочего склада» и подсказкой «Выберите склад в верхней части страницы». В `frontend/src/ui-kit/index.ts` добавляется её реэкспорт одной строкой.

**Файлы (только фронтенд):**
- `frontend/src/ui-kit/States.tsx` — добавить функцию `WarehouseNoContextState`; не трогать существующие экспорты
- `frontend/src/ui-kit/index.ts` — добавить `WarehouseNoContextState` в строку реэкспорта из `./States`

**Зависит от:** ничего (файлы ui-kit независимы от экранных правок).

**Как проверить.** `npx tsc --noEmit -p tsconfig.app.json` без ошибок. `import { WarehouseNoContextState } from '../ui-kit'` компилируется в любом экране. Визуально компонент показывает заголовок «Нет рабочего склада» и подсказку — достаточно проверить в `UiKitShowcase.tsx` или любым unit-тестом на рендер.

### 3. Фронтенд: передавать warehouse_id в запрос списка упаковочных заданий (S-14)

**Что не работает сейчас.** Функция `load` на строке 1879 `FfPackagingPage.tsx` запрашивает `/operations/packaging-tasks` только с параметрами `status` и `search`. При двух операционных складах упаковщик получает задания обеих зон в одном списке, открывает чужое задание и упирается в серверный запрет только при подтверждении — поздняя блокировка. Контракт S-14 и `S-14-TC-001` не выполнены.

**Что меняем.** `load` читает текущий склад из `useWarehouseContext('fulfillment')` — тот же хук, что уже используется на S-03/S-04 после атома 5. При наличии `selectedWarehouseId` добавляет `warehouse_id` к параметрам запроса; при отсутствии (нулевое состояние контекста) запрос не выполняется и экран показывает `WarehouseNoContextState` из ui-kit (Ф-2). Список заданий перезагружается при смене контекста так же, как это уже реализовано на S-03. Никаких новых колонок или чипов не добавляется.

**Файлы (только фронтенд):**
- `frontend/src/screens/ff/FfPackagingPage.tsx` — добавить `useWarehouseContext`, включить `warehouse_id` в `URLSearchParams` запроса, показать `WarehouseNoContextState` при нулевом складе, включить `selectedWarehouseId` в зависимости `useCallback` и `useEffect`

**Зависит от:** Ф-2 (компонент `WarehouseNoContextState` из ui-kit), атома 5 (хук `useWarehouseContext` в `frontend/src/contexts/WarehouseContext.tsx` уже готов).

**Как проверить.** При двух операционных складах переключить на «Север» — список показывает только задания «Севера». Переключить на «Юг» — список показывает только задания «Юга». При нулевых складах список не грузится, показан `WarehouseNoContextState`. `npm run build` без ошибок; ручной сценарий в браузере.

### 4. Фронтенд: устранить гонку при смене WMS-склада в FfFbsOrdersScreen

**Что не работает сейчас.** Строка 584 `FfFbsOrdersScreen.tsx` содержит охрану `if (loadingRef.current) return`. Она предотвращает наложение поллинг-тиков, но также блокирует перезагрузку при смене склада: новый `load()` для «Юга» молча отменяется, пока ещё летит запрос «Севера». Когда запрос «Севера» завершается, он записывает данные своего склада; `wmsWarehouseId` уже изменился на «Юг», поэтому клиентская фильтрация строк показывает пустую таблицу до следующего 30-секундного тика или ручного обновления. E2E не проверяет этот сценарий, потому что тестовый сервер отвечает мгновенно.

**Что меняем.** Вводится `AbortController`: в начале каждого `load()` создаётся новый контроллер и сохраняется в `ref`; предыдущий контроллер прерывается (`abort()`). Все `fetch`-вызовы внутри `load` получают `signal`. Охрана `if (loadingRef.current) return` заменяется прерыванием предыдущего запроса с немедленным стартом нового. `catch`-блок обрабатывает `AbortError` молча (не записывает ошибку в state). Поллинг-поведение сохраняется: тик, который пришёл до завершения предыдущего, прерывает его и стартует новый — эффект «поллинг не копится» тот же, без слепых пятен при смене склада.

**Файлы (только фронтенд):**
- `frontend/src/screens/v2/FfFbsOrdersScreen.tsx` — заменить `loadingRef` + `if (loadingRef.current) return` на `abortControllerRef`; добавить `signal` в `fetchFbsSupplyWorklist`, `fetchFbsWorklist`; молча проглатывать `AbortError` в `catch`

**Зависит от:** атома 10 (уже реализовал server-side `warehouse_id` фильтр в том же файле, на который опирается этот fix). Не зависит от Ф-2 или Ф-3.

**Как проверить.** Unit-тест (можно добавить в `frontend/src/screens/v2/fbsApi.test.ts` или новый файл): смена `wmsWarehouseId` во время загрузки прерывает предыдущий `fetch` и начинает новый; в итоге state содержит данные нового склада, а не старого. `npm run test:unit -- src/screens/v2/fbsApi.test.ts` зелёный, `npx tsc --noEmit -p tsconfig.app.json` зелёный.

## Порядок

Ф-1 (бэк) и Ф-2 (ui-kit) независимы — идут параллельно.
Ф-3 зависит от Ф-2 (нужен `WarehouseNoContextState`) — стартует после.
Ф-4 независима от Ф-2 и Ф-3 — идёт параллельно с Ф-3.

```
Ф-1 (бэк: PATCH inbound warehouse_id)  ─── параллельно с Ф-2
Ф-2 (фронт ui-kit: WarehouseNoContextState) ─── параллельно с Ф-1
    └── Ф-3 (фронт: FfPackagingPage + warehouse_id) ─── после Ф-2
Ф-4 (фронт: AbortController в FfFbsOrdersScreen) ─── параллельно с Ф-3, не зависит от Ф-2
```

Рекомендуемый порядок при ограниченном ресурсе:
1. Ф-1 + Ф-2 параллельно (один-два файла каждая, быстро).
2. Ф-3 сразу после Ф-2.
3. Ф-4 в любой момент параллельно с Ф-3.

## Что осталось за бортом

- Сервисный метод `patch_request_draft` не проверяет наличие тарифа и ячеек для нового склада. Контракт S-28 этого не требует — наблюдение, не фича.
- Тест гонки из Ф-4 не запускался в живом браузере: живой Playwright-прогон за пределами этих атомов.
- `FbsSupplyCreateDialog.test.ts` содержит JSX в файле `.ts`, из-за чего полный `npm run test:unit` красный — накопленный дефект соседнего теста, не связанный с этими находками.
- `ui_guard.py` красный из-за монолитов (`WbProductPickerDialog.tsx`, `FfFbsOrdersScreen.tsx`, `FfFbsStockSyncScreen.tsx`, `FfFbsSupplyWorkspace.tsx`, `SellerInboundDraftScreen.tsx`) — разбиение вне scope.
