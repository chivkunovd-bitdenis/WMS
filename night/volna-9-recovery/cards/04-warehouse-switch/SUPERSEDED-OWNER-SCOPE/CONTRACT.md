## Контракт

### 1. Объём и границы

Карточка не создаёт новый экран и не добавляет пункт меню. Она добавляет один
переиспользуемый контекст `Склад` в уже существующие рабочие зоны S-01, S-03,
S-04, S-14, S-22, S-24 и S-25. В портале селлера S-26/S-28/S-29 склад остаётся реквизитом
его заявки, а не глобальным фильтром портала. Служебные `FBS WB *` ни в один список
выбора не попадают. (R-02, R-10; границы раздела 8)

В шапку `ScreenHeader` ничего не добавляется. `WarehouseContextSwitch` стоит отдельной
компактной строкой сразу под шапкой и до `FilterBar`, таблицы или `ScannerLine`. Так
склад виден до начала операции, но не ломает каноническую шапку. (R-02, R-03)

### 2. Когда выбор виден

- Если операционный склад один, `WarehouseContextSwitch` не рендерится вообще. Склад
  подставляется без вопроса, в том числе в новую операцию. (канон не покрывает →
  предложено R-37)
- Если складов два и больше, строка показывает `Склад` и текущее имя. Нажатие
  раскрывает одиночный список только операционных складов; каждая строка содержит
  только уже существующее имя склада. Коды, UUID, адреса, остатки и служебные пометки
  здесь не показываются. (R-10, R-30; раздел 8)
- Выбор меняется сразу, без модального подтверждения: это обратимый контекст списка, а
  не складское движение. После выбора список закрывается, данные зоны загружаются заново.
  (канон не покрывает → предложено R-37)
- Контекст живёт до выхода из учётной записи и после выхода очищается. Между экранами
  одной сессии он сохраняется. (канон не покрывает → предложено R-37)

### 4. Сканер и подбор

- До выбора места `ScannerLine` говорит: `Сканер активен — пикните ШК склада или ячейки`.
  После выбора ячейки: `Сканер активен — пикните ШК товара`. (R-25, R-26)
- Скан склада меняет склад и сбрасывает ячейку. Скан ячейки одним шагом выбирает её
  родительский склад и саму ячейку. Скан товара никогда не меняет склад. (R-26; канон не
  покрывает типы скана → предложено R-39)
- После подбора экран показывает одну короткую строку: `Взято: Склад Север / ячейка A-01-02`.
  При подборе из другого склада текст тот же: отдельный чип «межскладский» не нужен. (R-14,
  R-16, R-35; раздел 8)
- Неверный/чужой склад, неоднозначный штрихкод, пустая ячейка и чужой товар показываются
  через `ErrorNotice` на языке склада. Технический код и стек не видны; склад, ячейка и остаток не
  меняются. (R-23, R-30)
- Сетевой повтор того же скана восстанавливает уже совершённый результат и снова показывает
  строку `Взято...`; никакого отдельного диалога о дубле нет. (R-24, раздел 8)

### 5. Создание FBS-поставки

Диалог сохраняет своё название и существующее главное действие `Создать поставку`. В сводке
показан рекомендованный `Склад WMS`; при равном покрытии это текущий склад. Его можно
сменить до создания. (R-06, R-18, R-32)

- **Успех без межскладского подбора.** Показан существующий чип `Можно создать поставку`; не
  добавляются пустые метрики. (R-06, R-14, R-24)
- **Общего остатка хватает, но на выбранном складе его мало.** Один `WarningNotice`, а не повтор
  по заказам: `На складе «Север» не хватает 24 шт. по 2 товарам. Нужно подобрать: «Юг» — 24 шт.`
  Ниже — компактная разбивка по товарам с колонками `Товар`, `Нужно`, `Здесь`, `Взять со склада`; числа
  выровнены вправо. `Создать поставку` доступна. (R-07–R-10, R-16, R-36)
- **Общего остатка не хватает.** `ErrorNotice`: `Не хватает 11 шт. по 1 товару. Пополните остаток или
  уберите заказы из выборки`. Разбивка по товарам показывает `Нужно`, `Всего` и `Не хватает`.
  Главная кнопка недоступна и объясняет ту же причину в подсказке. (R-08–R-10, R-20, R-23)
- **Загрузка.** Разбивка показана как скелет строк, а кнопка недоступна с причиной `Проверяем остатки`.
  (R-20, R-22)

### 6. Портал селлера

- В S-26 нет общего складского переключателя: список документов не должен скрывать заявки селлера
  из-за внутреннего контекста ФФ. (раздел 8; канон не покрывает ролевую границу → предложено R-40)
- В новой заявке S-29 склад выбирается только при двух и больше доступных складах; при одном поле
  отсутствует. В сохранённом черновике S-28 видно `Склад: <имя>`; его можно менять, пока заявка
  остаётся черновиком. После передачи на склад это только текст документа. (R-06, R-10, R-20)
- Селлер не видит числа по чужим складам, служебные склады, коды складов и внутреннюю разбивку остатков.
  Если на выбранном складе приёмка невозможна, он видит одну понятную ошибку без складской аналитики. (R-23, R-30;
  раздел 8)

### 7. Состояния контекста

| Состояние | Что видит оператор | Поведение |
|---|---|---|
| Обычное, 2+ склада | `Склад` + текущее имя; ниже данны этого склада. | Смена по выбору или скану. |
| Один склад | Нет ни поля, ни подписи «Склад». | Сервер подставляет склад. |
| Раскрытие | Под контролом один список имён, текущее отмечено. | Клик меняет контекст и закрывает список. |
| Загрузка | Место таблицы занимает `TableSkeletonBody`; контекст не прыгает на первый склад. | Выбор недоступен до ответа. |
| Ошибка загрузки | `ErrorNotice`: `Не удалось загрузить склады. Обновите страницу`. | Операции, которым нужен склад, недоступны. (R-20, R-23) |
| Пусто: 0 операционных складов | `EmptyState`: `Нет рабочего склада. Попросите администратора добавить рабочий склад`. | Складские действия недоступны. (R-20, R-21) |
| Нет строк на выбранном складе | Табличный `EmptyState`: `На складе «Север» пока нет заказов. Выберите другой склад или дождитесь новых заказов`. | Таблица остаётся в той же форме. (R-04, R-21) |
| Закреплённый склад документа | Имя склада и недоступное раскрытие с причиной. | Контекст списка не переписывает документ. (R-20) |

### 8. Что убрано как переусложнение

Убраны отдельный экран выбора склада, пункт меню «Сменить склад», повторные поля склада в формах ФФ,
модалка межскладского переноса, чип «межскладский», колонка склада в таблице новых FBS-заказов,
коды и UUID из интерфейса. Без них все требуемые операции остаются доступными, а оператор не выирает склад дважды. (раздел 8, R-30, R-35)

**Предложения для будущего добавления в канон:**

- **R-37.** Контекстный выбор не показывается, если доступен один вариант; при нескольких вариантах он стоит перед зависимыми данными, меняется без подтверждения и живёт не дольше авторизованной сессии.
- **R-38.** Связанные технические строки одной понятной операции показываются одной строкой; техническая пара доступна только в раскрытии.
- **R-39.** Скан места может менять контекст и шаг операции; скан товара не меняет место и только выполняет текущее действие.
- **R-40.** Внутренняя складская разбивка показывается только ролям, которые физически выполняют складскую операцию; внешний пользователь видит только выбор доступного места и результат.

## Нехватка ui-kit

### `WarehouseContextSwitch`

Нужен новый переиспользуемый элемент: в
`/Users/deniscivkunov/Projects/WMS/.worktrees/.night-worktrees/volna-9-recovery/lane-1-04-warehouse-switch/frontend/src/ui-kit/index.ts`
нет ни контекстного выбора,
ни общего `Select`. Сам ui-kit в этой роли не меняется.

Предлагаемый API:

```ts
type WarehouseOption = { id: string; name: string }

type WarehouseContextSwitchProps = {
  options: WarehouseOption[]
  value: string | null
  onChange: (warehouseId: string) => void
  loading?: boolean
  disabledReason?: string
  error?: string
  testId?: string
}
```

Состояния: скрыто при 0–1 варианте (нулевое состояние экран показывает отдельно),
обычное, раскрытое, загрузка, недоступное с объяснением. Компонент принимает только уже
отфильтрованные операционные склады; он не знает о WB-складах и не рисует остатки.

### `WarningNotice`

Нужна каноническая жёлтая плашка для ситуации «работать можно, но нужно внимание». В ui-kit есть
только `ErrorNotice`, а `StatusChip` не подходит для агрегированного пояснения с числами.

Предлагаемый API:

```ts
type WarningNoticeProps = {
  children: ReactNode
  testId?: string
}
```

Состояние одно: `warning`; компонент не блокирует действие и не принимает произвольный тон. (R-16)
