# Карта задевания волны · короба и грузоместа в каталоге

В каталоге карточек находится один `RAZBOR.md`, поэтому волна состоит из одной карточки и
не допускает параллельных правок одного пользовательского потока. Рекомендуемое
встраивание: оставить короб и грузоместо сущностями приёмки, добавить отдельный
тенантный read-only API (API только для чтения) и один раскрываемый блок на существующем
экране каталога; новых экранов и новых таблиц для этой волны не создавать.

## Карта

### Карточка 01 · `01-catalog-box-lookup`

**Порядок в волне:** 1. **Полоса:** A, последовательная. **Прямой экран:** `S-16`,
`/app/ff/products`, `FfProductsCatalogScreen`.

Карточка добавляет в нижнюю часть каталога свёрнутый по умолчанию блок «Короба и
грузоместа». Обычное открытие блока лениво загружает текущие физические объекты, то есть
не утяжеляет первый показ каталога. Точный скан внутреннего штрихкода выполняет отдельный
поиск по серверу, раскрывает блок и нужный объект и прокручивает его в видимую область.
Операция остаётся чтением: она не должна вызывать существующий `open_box_by_barcode`,
потому что тот записывает `intake_opened_at` и делает `commit`.

Для короба текущим составом считается `inbound_intake_box_lines.quantity -
inbound_intake_box_lines.posted_qty`, но не меньше нуля. Полностью разложенный короб не
попадает в обычный список; при точном скане сервер всё равно распознаёт его и возвращает
состояние «товар уже разложен». Новый пустой короб незавершённой приёмки можно показать с
пустым состоянием. Грузоместо остаётся доступным по номеру и штрихкоду, но получает явный
признак `composition_tracked = false`: текущая модель не хранит его товарный состав, и
выдумывать такой состав из строк всей приёмки нельзя.

#### Задетые экраны

| Экран | Задевание | Что меняется или проверяется |
|---|---|---|
| `S-16` · `/app/ff/products` | прямое | Нижний раскрываемый блок, его загрузка/ошибка/пустота, раскрытие отдельного короба, строка товара и точный скан `INB-*`/`ICG-*`. Существующие поиск и фильтры товаров, таблица, создание/импорт, печать и резервы не меняют смысл. |
| `S-17` · `/app/ff/reception` | смежное чтение тех же данных | В модальном `FfInboundRequestView` создаются, наполняются и печатаются короба и грузоместа. Экран не правим, но перекликиваем создание короба, наполнение, печать и отображение состава: каталог обязан увидеть тот же объект, не изменить его открытость и не сломать приёмку. |
| `S-20` · `/app/ff/sorting` | смежное изменение остатка короба | Раскладка увеличивает `posted_qty`. Экран не правим, но перекликиваем частичную и полную раскладку: после обновления/повторного скана каталог показывает уменьшенный остаток, а после полной раскладки — состояние «уже разложен». |
| `S-19` · `/app/ff/settings` | граница ролей, без UI-правки | Настройки сотрудников не меняются. Нужна лишь регрессионная проверка уже выданных прав: новый API доступен администратору и сотруднику с `cells` либо `inventory`, но не расширяет доступ роли `reception` и не требует от каталога права приёмки. |

Новый маршрут, пункт навигации и запись в `frontend/screens.registry.json` не нужны: блок
живёт внутри `S-16`. `App.tsx` также не должен меняться, если API использует ту же проверку
`require_catalog_cells_read_access`, что и `GET /products/ff-catalog`.

#### Таблицы и связи

| Таблица | Режим | Что берём |
|---|---|---|
| `inbound_intake_boxes` | переиспользуем, только чтение | `id`, `tenant_id`, `request_id`, `box_number`, `internal_barcode`, времена открытия/закрытия. Уникальность `(tenant_id, internal_barcode)` используется для адресного поиска. |
| `inbound_intake_box_lines` | переиспользуем, только чтение | `product_id`, `quantity`, `posted_qty`; вычисляем только положительный текущий остаток. |
| `inbound_intake_requests` | переиспользуем, только чтение | Номер/статус документа, склад и селлер для контекста и определения нового пустого короба незавершённой приёмки. |
| `inbound_intake_cargo_places` | переиспользуем, только чтение | Номер и `ICG-*`; состава нет, поэтому ответ явно сообщает, что детализация товаров не ведётся. |
| `products` | переиспользуем, только чтение | Связь строки короба с товаром. Фото и товарные штрихкоды на `S-16` берутся из уже загруженного `GET /products/ff-catalog`, а не дублируются новой таблицей. |
| `sellers`, `warehouses` | переиспользуем при необходимости подписи | Короткий контекст, позволяющий различать «Короб №1» из разных приёмок. Отдельных фильтров склада в этой волне нет. |
| `inventory_balances`, `inventory_movements`, `inbound_intake_distribution_lines` | не читаем как источник состава и не пишем | Они описывают складской остаток и события раскладки, но фактический остаток конкретного короба уже выражен через `posted_qty`. Второй расчёт создал бы расхождения. |

Новых таблиц, колонок, индексов и миграций в рекомендуемом варианте нет. Сущности
`fbs_packing_boxes`, `fbs_packing_box_items`, `fbs_trbxes` и грузоместа поставки WB из
`fbs_*` не переиспользуются: это упаковка/отгрузка в маркетплейс, а не приёмочный короб на
складе. Совпадение слов «короб» и «грузоместо» не означает общий жизненный цикл.

#### Столкновения

Других карточек в каталоге этой волны нет, поэтому прямых межкарточных конфликтов и
необходимости параллельных полос нет. Есть три зоны повышенного риска для соседней работы:

- `FfProductsCatalogScreen.tsx` — общий и часто изменяемый экран `S-16`; новый визуальный
  блок лучше вынести в локальный компонент, оставив в экране только интеграцию;
- `backend/app/main.py` — общий реестр роутеров; правка должна состоять только из импорта и
  `include_router`, без перестройки соседних маршрутов;
- термин «грузоместо» уже используется в `fbs_*`, но эти модели, API и тесты нельзя
  объединять с приёмочными `InboundIntakeCargoPlace`.

Существующий `POST /operations/inbound-intake-requests/{request_id}/boxes/open`
конфликтует с задачей по
семантике: он открывает короб и фиксирует время. Новый каталог не вызывает его даже ради
повторного использования ответа.

## Порядок

1. **Полоса A0 — Product/UX-контракт карточки 01.** Product фиксирует, что состав ведётся
   только у коробов, основной список показывает текущие/новые пустые объекты, точный скан
   полностью разложенного короба возвращает спокойное состояние, а список остаётся
   тенантным без нового фильтра склада. UX сохраняет `MOCKUP.html` со всеми состояниями.
2. **Полоса A1 — read-модель и API.** Реализуются новый сервис и два `GET`-контракта,
   затем backend-тестами фиксируются вычисление `quantity - posted_qty`, одинаковый `404`
   для неизвестного и чужого кода, матрица прав и полное отсутствие побочных записей.
3. **Полоса A2 — блок на `S-16`.** После стабилизации API подключается ленивый список и
   точный скан, переиспользуются уже загруженные данные товара и существующие
   `ProductPhotoThumb`/правила показа ШК. Новый экран, пункт меню и выбор склада не
   создаются.
4. **Полоса A3 — пользовательский сценарий и регрессия.** Добавляется новый Playwright
   путь с `TC-ID`, затем перекликиваются `S-16`, `S-17`, `S-20` и роль сотрудника. Сначала
   проверяется частичная раскладка, затем полная: это единственный переход, который меняет
   то, что каталог должен показать внутри того же короба.
5. **Полоса A4 — независимые проверки.** После code review выполняется живой browser
   product review на реальной вкладке: обычное раскрытие, успешный `INB-*`, неизвестный и
   чужой код, `ICG-*`, пустой короб и просмотр после раскладки. Только после этого карточка
   может перейти к следующему этапу конвейера.

Параллелить A1 и A2 нельзя: UI иначе зафиксирует случайный контракт. A3 можно готовить на
уровне тестовых данных после утверждённого контракта, но запускать следует на собранном
вертикальном срезе A1+A2. Других карточек, которые могли бы занять полосу B, в этой волне
нет.
