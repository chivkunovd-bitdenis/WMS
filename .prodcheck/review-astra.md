P0 — два сценария остановки потока упаковки WB

1. **После успешной записи КИЗ скан всё ещё ждёт WB до 60 секунд; очередь следующих сканов и «Назад» стоит.**
   Места: `backend/app/services/fbs_marking_service.py:1191`, `backend/app/services/wildberries_fbs_client.py:591`, `:772`; `frontend/src/screens/v2/fbsSequentialPacking.ts:88`, `:327`, `:295`.
   Воспроизведение: QR включён, «Печатать ЧЗ» выключено; ШК товара → его КИЗ. WB принимает PUT, но последующее чтение метаданных зависает либо возвращает 429. Ограничение записи в 4 секунды не ограничивает чтение: у него 60 секунд, при 429 ещё ожидание Retry-After и повтор. Печать начинается только после завершения bind; следующие сканы, Escape и «Назад» стоят в общей последовательной очереди этой страницы. При повторяющихся задержках оператор практически прекращает сборку. Противоречит цели WMS-635 и Д2; остаточное ожидание чтения уже упомянуто в самом документе требований. **Уверенность высокая, подтверждено цепочкой кода; фактическая задержка WB сейчас не измерялась.**

2. **«Печатать ЧЗ» из пула при WB 429 не выдаёт этикетку и не завершает упаковку.**
   Места: `backend/app/services/fbs_order_tape_print_service.py:657`, `:579`, `:586`; `frontend/src/screens/v2/fbsSequentialPacking.ts:283`.
   Воспроизведение: товар требует ЧЗ, в пуле есть свободный код, «Печатать ЧЗ» включено, QR в любом состоянии; скан ШК; запись КИЗ получает 429. В отличие от операторского КИЗ, этот путь не считает 429 временным исходом: заказ исключается из результата печати, `printed_codes` пуст. Фронт выдаёт «ЧЗ выбранной единицы не подготовлен» до отправки даже QR в WMS Print и до упаковки. При ограничении запросов WB этот режим сборки останавливается. Окончательный отказ также исключает этикетку через `:644`/`:695` вместо продолжения сканового потока. Основание: WMS-635 R4.1–R4.3, Д2. **Уверенность высокая: 429 воспроизведён локально на настоящем API и SQLite, с имитацией ответа WB; существующий тест Д2 с единственной заменой 504 → 429 падает на отсутствии этикетки.**

Это условные P0: условия запуска указаны выше. Наличие такого ответа/задержки в живом WB в момент ревью не подтверждено.

P1 — неправильная привязка и сломанное восстановление

3. **КИЗ, которого нет в локальном пуле, принимается без проверки GTIN выбранного товара.**
   Места: `backend/app/services/fbs_kiz_service.py:896`, `:992`, `:1088`.
   Воспроизведение: QR включён, печать из пула выключена; выбрать товар A, отсканировать синтаксически корректный КИЗ другого GTIN, отсутствующий в `MarkingCode`. Проверка принадлежности сразу выходит при `code is None`; новая запись получает `product_id` выбранного заказа независимо от GTIN внутри кода. При WB 429 сохраняется `wb_pending_confirmation`, после чего фронт продолжает QR и упаковку. На складе можно упаковать чужую маркированную единицу под заказ A. Основание: локальная проверка товара/GTIN в WMS-635 R4.1. **Уверенность высокая: локальный API сохранил КИЗ с GTIN 04600439931253 за товаром с ШК 4600000000001. Физический товар, естественно, не проверялся.**

4. **«Назад» оставляет КИЗ в WB, если запись принята, но последующий вердикт отрицательный.**
   Места: `backend/app/services/fbs_kiz_service.py:2043`, `:2053`, `:2068`.
   Воспроизведение: обычный операторский КИЗ, QR включён; WB PUT успешен, чтение возвращает записанный код с `sgtinApplied`, WMS сохраняет `rejected` по WMS-635 Д1. Нажать «Назад». Код предполагает, что при любом `rejected` WB ничего не хранит, пропускает удаление, снимает локальную привязку и отвечает успехом. Оператор считает код свободным, хотя WB продолжает хранить его у прежнего заказа; дальнейшее использование расходится с состоянием площадки. Основание: WMS-631 откат, WMS-635 R3/Д1/Д3. **Уверенность высокая: локальный API вернул 200 на откат, имитатор WB сохранил исходный КИЗ; удаление не вызвано.**

5. **Повтор КИЗ в поле заказа после сбоя принтера упирается в `duplicate_kiz`.**
   Места: `frontend/src/screens/v2/fbsSequentialPacking.ts:473`, `:479`, `:708`; `backend/app/services/fbs_kiz_service.py:925`.
   Воспроизведение: QR включён; в поле конкретного заказа сканировать новый КИЗ, WB его принимает, затем WMS Print недоступен. Восстановить принтер, снова выбрать то же поле и сканировать тот же КИЗ. Фронт сохранил ключ попытки, но очистил pending и заново выполняет validate. Бэк разрешает собственный код только при reserved/printed или незавершённой операции; принятый `applied` отклоняет как дубль. До повторной печати выполнение не доходит. Оператор не может восстановить эту попытку ожидаемым повтором в строке; другие способы восстановления отдельно не утверждаются. Основание: WMS-631 повтор после сбоя, WMS-633 R3. **Уверенность высокая: commit → validate того же принятого КИЗ локально даёт 409 `duplicate_kiz`, status `applied`; путь фронта подтверждён чтением.**

6. **Все галки выключены, но альтернативный ШК заказа всё равно выбирает заказ.**
   Места: `frontend/src/screens/v2/fbsSequentialPacking.ts:346`; `backend/app/services/fbs_kiz_service.py:605`, `:667`.
   Воспроизведение: у заказа `order.wb_barcode=B`, у связанной карточки `product.wb_barcode=A`, A ≠ B; товар требует ЧЗ. Все галки выключены; сканировать B. Поиск стикера принимает B через резервный поиск по ШК заказа, но возвращает в `product.barcode` значение A. Единственная проверка «это товарный ШК» сравнивает B с A и пропускает скан как стикер. Вместо отсутствия выбора выбирается первый подходящий заказ и следующий КИЗ пойдёт в него. Основание: WMS-631 R9. **Уверенность высокая по коду; наличие таких двух различных ШК в сегодняшней поставке не проверено.**

P2 — число копий

7. **Прямая перепечать КИЗ без выбранного заказа игнорирует счётчик экземпляров.**
   Место: `frontend/src/screens/v2/fbsSequentialPacking.ts:662`, `:665`, `:681`.
   Воспроизведение: включить только «Перепечатывать ЧЗ», поставить 3, без выбранного заказа сканировать полный КИЗ. `directReprint` сохраняет предпочтения без `reprintChzCopies` и единожды вызывает `send`, не механизм N копий. В WMS Print уйдёт одна этикетка вместо трёх. Основание: WMS-633 R2. **Уверенность высокая по коду; физическая печать не проверялась.**

Отдельно — не подтверждено сквозным воспроизведением

- **Риск P1: очередь сканов может потерять выбранную строку.** `fbsSequentialPacking.ts:192`/`:198` определяет строку только при исполнении задания; `FfFbsSupplyWorkspace.tsx:703` читает изменяемые ссылки на текущее поле, а `:3516` очищает их при потере фокуса. Для проверки ведущему: в «Сборке» задержать первый скан, в поле заказа B отсканировать КИЗ, затем перевести фокус в строку C до освобождения очереди. Есть путь к применению КИЗ B в C либо к обычному маршруту скана. Снимок выбранного `order_id` в очередь не передаётся. Ошибка хранения цели подтверждена чтением, достижимость всего пользовательского сценария требует браузера; в число подтверждённых дефектов выше не включена.

Почему зелёные тесты это пропустили

- `backend/tests/test_wms635_kiz_no_wb_wait.py:264`: проверяет значение таймаута записи через контекст и мгновенно выброшенную ошибку; длительное чтение после успешной записи не проверяет.
