# PROCESS.md — регламент разработки WMS (ИСТОЧНИК ПРАВДЫ)

> Этот файл — единый регламент для **любого** агента (Claude Code, Cursor, Codex) и человека.
> `AGENTS.md`, `CLAUDE.md`, `.cursor/rules/process.mdc` — только указатели сюда.
> **Прочитай этот файл ПЕРЕД тем, как что-либо трогать. Правишь процесс — правь здесь, в одном месте.**

Ниже — как в WMS ведётся любая задача. Правила окружения и CI из [`AGENTS.md`](../AGENTS.md)
(вертикальный срез, разделение слоёв, обязательная таблица `### Test coverage`, зелёный CI, ветка→PR→main)
остаются в силе и здесь не дублируются — этот файл описывает **последовательность стадий и гейты** поверх них.

**Глобальные правила на каждый ответ** (действуют всегда, не только внутри задач):
[`COMMUNICATION.md`](COMMUNICATION.md) — по-человечески + пояснять термины; [`LEARNING.md`](LEARNING.md) —
обучать по продукту (разбор на гейте + добивка по дырам из [`ARCHITECTURE.md`](ARCHITECTURE.md)).

---

## 0. Хребет задачи — папка `tasks/<slug>/`

Любая работа = одна задача = одна папка `tasks/<slug>/` (slug — короткий kebab-case, напр.
`tasks/fbs-orders-intake/`). Агент, взявшийся за задачу, **обязан** складывать туда артефакты по
стадиям. Дисциплину держит не запрет, а **след**: нет артефакта стадии — стадия не пройдена, это видно.

Обязательные файлы (по мере прохождения; какие именно — зависит от маршрута, см. §1):
```
tasks/<slug>/
  00-triage.md        # тип, размер, маршрут
  01-analysis.md      # разбор + вопросы человеку (арх-коучинг)
  02-arch-decision.md # арх-решение + СТЕК + явное «ок» человека (ГЕЙТ 1)
  03-contract.md      # критерии приёмки (BA); можно пропустить для S
  04-test-cases.md    # тест-кейсы + маппинг на TC-ID (см. §5); по ним валидируется код
  05-review.md        # вердикт независимого ревью + прогон тестов
  06-doc.md           # конфа: бизнес + технически + почему (→ внешний док)
```

Артефакты заполняются **из шаблонов** в [`templates/`](templates/) (`00-triage.md … 06-doc.md`):
копируешь шаблон в `tasks/<slug>/` и заполняешь — форму не выдумываешь.

Активный агент в начале работы **читает всё, что уже есть в `tasks/<slug>/`**, и продолжает с той
стадии, где след обрывается. Не переделывает пройденное молча.

Связь с GitHub Issue (по [`AGENTS.md`](../AGENTS.md)): одна задача `tasks/<slug>/` ↔ одна Issue с
меткой `ready`. Slug и номер Issue вписываются в `00-triage.md`, чтобы след в репо и трекер не расходились.

## 1. Типы задач и маршруты

Первое действие по любой задаче — **классифицировать** (стадия 0, `00-triage.md`):

- **Тип:** `bug` | `feature` | `доработка` | `рефакторинг`.
- **Размер:** `S` (мелочь, часы) | `M` | `L`.
- **Маршрут** — из типа+размера:

| Тип / размер | Маршрут (стадии) |
|---|---|
| **bug** | 0 → 1(причина, кратко) → [ГЕЙТ 1 только если меняется архитектура] → 4(фикс) → 3(регресс-кейс) → 5 → 6 |
| **feature S** | 0 → 1 → **ГЕЙТ 1** → 4 → 3(тест) → 5 → 6 (контракт §2 пропускаем) |
| **feature/доработка M–L** | 0 → 1 → **ГЕЙТ 1** → 2 → 3 → 4 → 5 → [ГЕЙТ 2 опц.] → 6 (полный цикл) |
| **рефакторинг** | 0 → 1 → **ГЕЙТ 1** → 4 → 5(тесты-регресс зелёные) → 6 |

Маршрут масштабируется под размер: мелкое не гоняем через весь конвейер, крупное — через весь.

## 2. Конвейер стадий

Пайплайн едет **сам**: стадии идут по порядку, каждая читает артефакт предыдущей и дописывает свой.
Человека дёргаем **только на гейтах** (§3). Остальное агент делает автономно.

**Что именно делает каждая роль — в [`roles/`](roles/) (по файлу на роль: миссия, вход, выход,
что обязан сделать, DoD, что запрещено).** Ниже — сводка.

| # | Стадия | Роль | Что делает | Выход |
|---|--------|------|-----------|-------|
| 0 | **Триаж** | [Триажёр](roles/triage.md) | классифицирует (тип/размер/маршрут) | `00-triage.md` |
| 1 | **Анализ + арх-коучинг** | [Аналитик](roles/analyst.md) | разбирает по продукту и технике; **качает человека вопросами**; предлагает стек | `01-analysis.md` |
| — | **🔒 ГЕЙТ 1** | человек | подтверждает архитектуру и стек | `02-arch-decision.md` |
| 2 | **Контракт** | [BA](roles/ba.md) | критерии приёмки, границы (для S — пропуск) | `03-contract.md` |
| 3 | **Тест-дизайн** | [Тест-дизайнер](roles/test-designer.md) | тест-кейсы из контракта + маппинг на TC-ID | `04-test-cases.md` |
| 4 | **Код** | [Кодер](roles/coder.md) | пишет вертикальный срез по стандарту §4 | код + зелёные тесты |
| 5 | **Ревью + прогон** | [Ревьюер](roles/reviewer.md) | **независимый** (не автор кода) ищет, где плохо и где контракт не выполнен; прогоняет гейты | `05-review.md` |
| — | **🔒 ГЕЙТ 2 (опц.)** | человек | приёмка до merge | отметка в `05-review.md` |
| 6 | **Док** | [Доккер](roles/doccer.md) | конфа: что/зачем, бизнес+технически, **почему** → `docs/` | `06-doc.md` |

**Ревью (стадия 5) обязано быть независимым:** автор кода не оценивает свою работу сам. В Claude Code —
через отдельного субагента-ревьюера (или `/code-review`); в Cursor/Codex — отдельным проходом с явной
установкой «ищи, где плохо и где контракт не выполнен», не «подтверди, что всё хорошо».

## 3. Гейты — где пайплайн ОБЯЗАН позвать человека

Гейты только ключевые. На гейте пайплайн **встаёт и спрашивает человека, ждёт явного ответа**, потом едет.

- **🔒 ГЕЙТ 1 — Архитектура + стек (жёсткий, обязателен для feature/доработка/рефакторинг).**
  Прежде чем писать код, агент фиксирует в `02-arch-decision.md`: как решаем, каким **стеком**, какие
  затрагиваются части системы, есть ли миграции — и **явно спрашивает человека**. Без записанного «ок»
  человека — **кодить нельзя**. Для бага — только если фикс меняет архитектуру.
- **🔒 ГЕЙТ 2 — Приёмка (мягкий/опциональный).** Перед merge показать результат и критерии приёмки;
  если человек не возразил — двигаемся. Человек может сделать его жёстким для конкретной задачи.

Вне гейтов агент работает сам и человека не дёргает.

## 4. Стандарт кода

Код должен быть **человекочитаемым, не мусорным**:
- Читается как окружающий код: те же имена, идиомы, плотность комментариев, что вокруг.
- **Слои не смешиваются** ([`AGENTS.md`](../AGENTS.md)): роуты — `backend/app/api`, бизнес-логика —
  `backend/app/services`, модели — `backend/app/models`, доступ к БД — `backend/app/db`,
  фоновые задачи — `backend/app/tasks`.
- **Новые/правимые экраны ФФ — единый MUI** (эталон `FfProductsCatalogScreen.tsx`), без legacy `Card`/`Input`.
- Понятные имена; без мёртвого кода, закомментированных блоков, отладочного мусора.
- Маленькие связные коммиты (одна единица — один коммит), а не один большой в конце.
- Меняешь минимум для задачи; не тащишь несвязанный рефактор в тот же коммит.
- **Гейт перед push** (обязателен):
  - backend: `cd backend && ruff check . && mypy . && pytest`
  - frontend (при изменениях): `cd frontend && npm run build && npm run test:e2e`
- **Ветвление:** работаем в фича-ветке (`feat/…`, `fix/…`, `chore/…`), merge в `main` — только через PR
  с зелёным CI. Долгоживущих веток не держим.

## 5. Тесты и трассируемость (стык с CI-контрактом)

WMS уже требует ([`AGENTS.md`](../AGENTS.md)): каждый PR, трогающий `backend/app/api|services` или
`frontend/src`, несёт в описании блок **`### Test coverage`** — таблицу с `TC-ID` (`TC-Sxx-yyy` из
[`docs/IMPLEMENTED_PRODUCT_SCENARIOS_TEST_CASES_EN.md`](../docs/IMPLEMENTED_PRODUCT_SCENARIOS_TEST_CASES_EN.md)
или новые `TC-NEW-*`), со строкой `Y` и маркерами Given/When/Then; иначе CI красный.

Поэтому стадия 3 (`04-test-cases.md`) — **не параллельная бюрократия, а тот же спек**: каждый тест-кейс
маппится на `TC-ID`, а Playwright-сценарий проверяет **видимый результат** через `data-testid`, а не
просто HTTP 200. Таблица из `04-test-cases.md` переносится в описание PR как блок `### Test coverage`.

## 6. Документация по фиче → `docs/`

Каждая задача завершается артефактом `06-doc.md` — конфа-страницей:
- **что и зачем** сделали; для бага — **суть бага**;
- что поменяли **технически** и что это значит **бизнесово**;
- **почему** так, какие решения приняты (ссылка на `02-arch-decision.md`).

Дев-дока WMS живёт в репо, в папке [`docs/`](../docs/) (там же — MVP-решения, сценарии, бэклоги).
Куда класть конфу и как связывать со сценариями — в [`doc-store.md`](doc-store.md). Исходник конфы
остаётся в `tasks/<slug>/06-doc.md` (след задачи), а долгоживущее правило/сценарий — в `docs/`.

**RAG/внешняя вики отложены** — сейчас хватает `docs/` и поиска по репо. Навесим позже поверх тех же
markdown-страниц, переделывать доку не придётся.

## Итог одной строкой

Задача → `tasks/<slug>/` → триаж → анализ+коучинг → **[ГЕЙТ: арх+стек]** → (контракт) → тесты →
код (вертикальный срез) → независимое ревью → (приёмка) → PR с зелёным CI → док в `docs/`.
Пайплайн едет сам, человека зовёт только на гейтах.
