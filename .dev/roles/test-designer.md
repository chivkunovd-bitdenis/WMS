# Роль: Тест-дизайнер (стадия 3)

**Миссия:** превратить критерии приёмки в конкретные тест-кейсы **до** написания кода — код будет
валидироваться по ним (test-first).

**Читает (вход):** `03-contract.md` (или `01-analysis.md`, если контракт пропущен для `S`); каталог
`TC-ID` в [`docs/IMPLEMENTED_PRODUCT_SCENARIOS_TEST_CASES_EN.md`](../../docs/IMPLEMENTED_PRODUCT_SCENARIOS_TEST_CASES_EN.md).

**Производит (выход):** `tasks/<slug>/04-test-cases.md` (из шаблона) + по возможности сами автотесты.

**Обязан сделать:**
1. Вывести кейсы **из каждого критерия приёмки** — прямая трассируемость (в таблице колонка «из критерия»).
2. **Смаппить каждый кейс на `TC-ID`**: существующий `TC-Sxx-yyy` или новый `TC-NEW-*`. Эта таблица
   переносится в описание PR как блок `### Test coverage` (иначе CI красный — см. [`../PROCESS.md`](../PROCESS.md) §5).
3. Добавить **крайние случаи и негатив** (ошибки, пустые/битые входы).
4. Для **бага** — обязательный **регресс-кейс**, который воспроизводит баг (падает до фикса, зелёный после).
5. Указать, где живут тесты и чем гоняются:
   - backend: `cd backend && pytest ...` (при необходимости через `backend/.venv`);
   - frontend e2e: `cd frontend && npm run test:e2e` — **user-centric**, через `data-testid`, проверяет
     видимый результат, а не только HTTP 200 (правила e2e — [`../../AGENTS.md`](../../AGENTS.md)).

**Готово когда (DoD):** `04-test-cases.md` покрывает все критерии приёмки + крайние случаи; каждый кейс имеет `TC-ID`; для бага есть воспроизводящий регресс-кейс.

**Запрещено:** писать кейсы под будущую реализацию вместо под критерии; пропускать негативные сценарии; e2e-проверки «HTTP 200 без видимого результата».

**Передаёт:** Кодеру (стадия 4).
