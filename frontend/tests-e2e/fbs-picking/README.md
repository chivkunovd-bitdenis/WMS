# FBS «Подбор»: настоящий браузерный CI

Набор открывает собранную SPA (клиентское приложение), настоящий API, PostgreSQL,
Redis и Celery; внешний Wildberries/Ozon изолирован локальным эмулятором.
Составлены самостоятельные данные для каждого случая. Данные, проверяемые после
клика/ввода, читаются отдельно из PostgreSQL: исходная ячейка и конкретная тара,
сортировка, активное назначение заказу/позиции и суммарный физический остаток.
Уведомление браузера само по себе не считается сохранённой операцией.

База сценариев — etalon `a5df04f1560de0eaaf855199065936cb22a222b1`, вместе с уже
сохранённым main-screen runner; точный проверяемый SHA записывает runner.
Печать проверяет старый базовый лист «Ячейка / тара», а не новый серверный
`picking-context` из `af965706`. Этот CI не доказывает живую работу production,
физический принтер или конкретную аппаратную модель сканера.

## Запуск

Workflow `.github/workflows/fbs-picking.yml` запускается на push ветки
`codex/fbs-picking-ci` и вручную. Node 24, Playwright 1.58.2, Chromium.
Локальный полный запуск требует Docker и установленного Playwright:

```bash
WMS_PLAYWRIGHT_MODULE=/absolute/path/to/@playwright/test/index.mjs \
  bash scripts/ci/run_fbs_picking_browser.sh
```

`FBS_PICK_CASES=sources,burst` выбирает только названные случаи. Порты 25434,
26380, 28082, 28083, 25174; имя compose-проекта уникально. Очистка удаляет
только собственный compose-проект. Seed и DB reader проверяют явный флаг
одноразовой среды и адрес базы `db/wms`. Авторизация — только созданный
фиктивный tenant; токены внешних аккаунтов в browser evidence не сохраняются.

## Доказательства и красные случаи

Каждый случай сохраняет screenshot, Playwright trace (действия и сеть), реальные
ответы WMS API с телами запросов, каталог фикстуры и DB снимки. Общие артефакты:
точный SHA, seed, журнал compose, журнал сборки, финальный DB. При неудаче данные
читаются снова до остановки stack. Результаты пишутся после каждого случая.
Незавершённая подготовка помечается `preparefailure`; невозможность DB readback
не может оставить случай зелёным. Финальная проверка отдельно падает при изменении
физического итога или отрицательном источнике.

Нет `skip`/`xfail` для подозрений из PROCESS_RU. Пройденным считается только реально
исполненный случай. Подтверждённое продуктовое падение остаётся `failed`.
`replay` добавляет ключ в настоящий запрос специально: это **не** доказательство,
что существующий браузер сам хранит и восстанавливает ключ неизвестной операции.
`lost` не повторяет действие, а проверяет безопасное восстановление факта через reload.

## Оставшиеся границы

Этот первый срез не покрывает палету с вложенным коробом, грузоместо/тару без
ячейки, чужой резерв, mixed marketplace обход реального создания группы, модальное
подавление глобального сканера, специальные RU символы/GS, HTTP 5xx (сеть отдельно
покрыта), конкурентные групповые set и частичный успех нескольких транзакций,
групповой потерянный ответ, печатный GET fallback, групповую межскладскую печать,
снятие последней единицы источника и её последующий ручной возврат после refresh,
Ozon terminal guard после фактической передачи. Это gaps, а не зелёные проверки.
Производственная печать `picking-context` требует отдельного запуска на её точном
SHA; успешная генерация HTML не подтверждает выход бумаги.

RU аппаратная пачка моделируется Chromium CDP `Input.dispatchKeyEvent`: настоящие
браузерные keyDown/keyUp с кириллическим key, физическим KeyX и текстом. События
сохранены в `layout-cdp-events.json`. Это модель раскладки, а не подключённый
физический сканер. Для RU нельзя заменять её на `keyboard.type`: по
[документации Playwright](https://playwright.dev/docs/api/class-keyboard#keyboard-type)
символы вне US keyboard создают только input и обходят глобальный keydown listener.


## Первый исполненный прогон и исправление фикстуры

Run `37635865681`, SHA `63cfbd903c6309fe9394b1c0167399cff366e768`: 28 случаев,
4 passed, 24 failed, 0 preparefailure, завершение за 11м23с. Это не зависший run.
В `tabs` реально был таймаут действия 30000мс: тест искал «Состав» вместо
«Состав ✓». Локатор исправлен, принимаются обе подписи.

Обычные остатки первого seed были несогласованы: quantity30 при unpacked0 и
packed0. В 20 упавших случаях сохранён настоящий ответ API
`409 insufficient_unpacked`; при переносе сервис проверяет сумму unpacked+packed.
Эти результаты не доказывают поломку товарного снятия. Потерянный ответ тоже был
инъекцией поверх этой несогласованной фикстуры. Теперь seed создаёт положительный
остаток через настоящий `record_movement_and_adjust_balance` с типом
`inbound_intake`, как существующий базовый seed, и проверяет согласованность
quantity=unpacked+packed. Отдельный `packing-flag` создаёт coherent packed30,
unpacked0 через `quantity_packed_delta=30`; он защищает требование владельца о
независимости подбора от отметки упаковки, не использует невозможный split.

Продуктовый сигнал Ozon группы остаётся красным: на реально открытом экране
не было ожидаемого Ozon offer_id, хотя API связи содержат этот артикул; вместо
него таблица использовала WB-поля. Ожидание не ослаблено. Ранний уход также
остаётся отдельным случаем; новый прогон должен отделить его потерю сохранения
от общей ошибки данных. Первая серия не достигла успешных позитивных действий,
поэтому остальные риски нельзя считать ни доказанными дефектами, ни пройденными.

Для следующих запусков явно заданы пределы: действия 10с, навигация 30с,
auth/catalog запросы 10с, подготовка и процесс одного случая 60с. Это бюджет
тестового runner, а не производственный норматив скорости. По превышении бюджета
context закрывается, затем runner дожидается завершения проигравшей ветки и
закрытия вторичного контекста перед следующим случаем. До результата сохраняются
progress JSON, снимок открытого экрана и API JSONL; затем final DB/trace/results.
Читатель DB отдельно сохраняет unpacked/packed для диагностики. Ozon reader
сопоставляет точные IDs позиций с order/product/supply/warehouse, проверяет
реальные per-position резервы и равенство picked_quantity активным назначениям.
