# WMS-624: локальная проверка формы обращений

Из `frontend`: `npm ci`, затем `npm run dev -- --host 127.0.0.1 --port 16240 --strictPort`.
Открыть `http://127.0.0.1:16240/dev/developer-requests.html`.

Это отдельный вход только для Vite development, не включённый в production build. Он использует настоящие `AuthedAppLayout`, `SellerLayout` и `DeveloperRequests` с текущей темой. Пользователь, таблица и API — явно тестовые; fetch не обращается к настоящему API, Trello или кабинетам. Записи fixture сохраняются только в localStorage этого origin под `wms624.fixture.requests`. Таблица служит контекстом, не доказывает полный операционный сценарий FBS.

Переключатели позволяют выбрать портал, автора, организацию, магазин, ответ API (успех, 500 до сохранения, 422 по длине, потеря ответа после сохранения) и одну из четырёх стадий сохранённых тестовых заявок. «Панель действий» показывает закреплённую кнопку, чтобы проверить отсутствие пересечения с глобальной «?». При перезагрузке настройки fixture возвращаются к начальным; черновики и тестовые заявки остаются.

Проверки:

- Открыть «?», набрать оба типа, закрыть через отмену/крестик/Escape, переоткрыть и обновить страницу. Переключить автора/организацию/магазин и проверить изоляцию и очистку только текущего черновика.
- Заполнить обязательные поля; отправить; увидеть зелёную галочку, затем открыть список и полное описание. Сменить стадию fixture, открыть список снова.
- Выбрать 500: текст остаётся. Вернуть успех и повторить. Выбрать потерю ответа: первый вызов сохраняет тестовую строку, но даёт ошибку; повтор возвращает ту же строку.
- Выбрать «422: слишком длинное обращение»: fixture принудительно возвращает структурированный отказ до сохранения (`max_length: 16384`, тестовый `actual_length: 18100`). Набрать улучшение с длинными полями, отправить, проверить сообщение и восстановление черновика после закрытия/открытия. Сократить текст, закрыть окно, переключить «Ответ API» на «Успех», открыть и отправить: исправленный текст сохраняется. Режим инъецирует отказ и не дублирует серверный расчёт длины.
- После потери ответа изменить текст: форма сначала предлагает проверить предыдущую отправку. Проверка использует исходный payload и UUID. После подтверждения изменения остаются новым черновиком; следующее намеренное отправление создаёт отдельную запись. При серверном 409 текст также сохраняется и автоматической смены ключа нет. Действие «Продолжить как новый черновик» по явному нажатию сохраняет весь текущий текст с новым UUID, ничего не отправляя; затем можно намеренно нажать «Отправить».
- Для настоящего постоянного 409 открыть два окна fixture с одним автором/организацией/магазином. В A создать черновик; открыть его в B и изменить текст. Отправить A, затем B: B получает 409 при каждой попытке с прежним UUID. Выбрать «Продолжить как новый черновик», затем «Отправить» — список содержит обе разные заявки.
- Установить узкий viewport (390×844), ввести длинное описание, пройти Tab/Escape, проверить прокрутку, кнопки и возврат фокуса.

Автотесты: `npx vitest run src/components/developer-requests src/layouts/headerHomeLink.dom.test.tsx src/hooks/useAuth.test.ts`.
Обязательные проверки: `npx tsc --noEmit -p tsconfig.app.json` и `npm run build`.
DOM-тесты отдельно проверяют серверный 422 по суммарному объёму текста: все поля сохраняются, после сокращения текста можно отправить с прежним UUID. Произвольных ограничений длины отдельных полей нет.
