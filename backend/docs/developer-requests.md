# WMS-624: backend обращений разработчикам

`POST /developer-requests` подтверждает сохранение обращения в БД WMS. Доставка в
Trello происходит отдельно; отсутствие конфигурации или ошибка Trello не отменяет
сохранение. `GET /developer-requests` и `GET /developer-requests/{id}` возвращают
только обращения авторизованного автора в его организации. Внутренние карточки
Trello не импортируются. Перед сохранением сервер составляет полное описание
карточки тем же кодом, который использует доставка, включая клиента, серверную
дату UTC, pathname и UUID. Лимит Trello — 16384; применяется консервативный подсчёт
единиц UTF-16 (как JavaScript `String.length`: кириллица — одна, emoji вне BMP — две).
При превышении API возвращает 422 с `detail.code=developer_request_description_too_long`,
сообщением для формы и `max_length` / `actual_length` в этих же единицах. Записи и
карточки ещё нет; UI сохраняет черновик. Проверка действует и без настройки Trello,
не обрезает текст и не вводит отдельные лимиты полей. Поля формы и их подписи определены в
`../../docs/requirements/WMS-624.md`.

## Схема и запуск

Выпустить backend вместе с миграцией `20261001_2301_developer_requests.py`
(`down_revision = 20260929_0565`). Обычная команда миграции — `alembic upgrade head`.
Не применять миграцию к стенду отдельно от соответствующего кода.

Фоновая задача `wms.developer_requests_sync` зарегистрирована в существующем Celery.
Для автоматической доставки нужны действующий `CELERY_BROKER_URL`, worker
`celery -A app.celery_app worker` и планировщик `celery -A app.celery_app beat`.
Планировщик запускает задачу каждые 60 секунд по умолчанию. Один проход выбирает
до 50 записей, начиная с наиболее давно ожидающих синхронизации. GET не запускает
внешние действия. Само наличие API без worker и beat не доставляет карточки.

`docker-compose.prod.yml` передаёт `TRELLO_*` в `celery_worker`, а интервал также
в `celery_beat`. API не нужны Trello credentials для сохранения обращений.
Railway использует отдельные `railway.worker.toml` и `railway.beat.toml` с
`WMS_SERVICE_ROLE=worker` / `beat`; переменные требуются в окружении worker,
а `TRELLO_SYNC_INTERVAL_SEC` также в окружении beat. Entrypoint наследует эти
переменные штатно. Настройка настоящих окружений в эту реализацию не входила.

## Контракт серверной конфигурации

Настройки находятся в `app/core/settings.py`; frontend их не получает.

| Переменная | Назначение |
|---|---|
| `TRELLO_API_KEY` | Ключ существующего разрешённого Trello приложения. |
| `TRELLO_TOKEN` | Токен с доступом к выбранной доске. |
| `TRELLO_BOARD_ID` | ID приватной доски команды. |
| `TRELLO_REVIEW_LIST_ID` | Начальный список «На рассмотрении». |
| `TRELLO_QUEUED_LIST_ID` | Список «В очереди». |
| `TRELLO_IN_PROGRESS_LIST_ID` | Список «В работе». |
| `TRELLO_COMPLETED_LIST_ID` | Список «Готово (Клиентские)»; в WMS — «Готово». |
| `TRELLO_CLIENT_LABEL_ID` | ID существующей цветной метки «Клиент» на этой доске. |
| `TRELLO_SYNC_INTERVAL_SEC` | Интервал, минимум 30 секунд, по умолчанию 60. |

Без ключа, токена, доски либо одного из четырёх различных ID списков задача
ничего не отправляет. До отправки проверяются приватность и активность доски,
принадлежность четырёх открытых списков этой доске. ID метки необязателен для
доставки; без него остаётся текст «Клиент: организация / селлер», но цветовое
различие не настроено. Для завершения подключения команда выбирает или создаёт
метку «Клиент» штатно в Trello и указывает её ID. Внутренние карточки команда
создаёт штатно в Trello, без этой метки либо с другой меткой/цветом.

Этот документ задаёт имена переменных, но не разрешает создание, чтение или
замену реальных ключей. Живая доска, доступ к ней и её цветовое оформление
не проверялись при разработке. Ни одна реальная карточка не создавалась.

## Состояния доставки и восстановление

Пользовательские статусы `review`, `queued`, `in_progress`, `completed` отражают
список связанной карточки. Неизвестный список, удалённая/перенесённая карточка или
ошибка провайдера сохраняют последний подтверждённый статус.

Техническое `delivery_state` хранится только в БД:

- `pending`: POST ещё не выполнялся либо Trello явно отклонил его HTTP 4xx.
  Известные отказы повторяются с экспоненциальной задержкой, ограниченной одним часом.
  Один проход выполняет максимум один POST для обращения. Постоянного запрета
  после серии отказов нет: когда провайдер восстановится, заявка будет доставлена
  автоматически, без повторного ввода пользователем.
- `outcome_unknown`: факт начала попытки записан и закоммичен до POST, ответ ещё
  не подтверждён. Timeout, потеря соединения, HTTP 5xx и неполный успешный ответ
  оставляют это состояние. Разрешены только чтения для восстановления.
- `linked`: сохранён `trello_card_id`; дальше читается текущий список карточки.

Каждая клиентская карточка содержит отдельную строку `WMS-REQUEST-ID: <UUID>`.
Восстановление ищет точную строку в описаниях карточек исходной настроенной доски,
включая архивные, страницами по 1000 с `sort=-id` и курсором `before` последней
карточки страницы. Только после полного прохода одна найденная карточка связывается
с заявкой. Ошибка чтения следующей страницы, повтор курсора или одинаковый маркер
на разных страницах оставляют восстановление незавершённым. Отсутствие маркера,
ошибка чтения либо несколько совпадений не разрешают новый POST. `last_error`
содержит только код ошибки/HTTP статус, без ответа сервера, URL и секретов.

БД выдаёт одному работнику аренду записи на пять минут. Обновления проверяют
уникальный токен этой аренды. После истечения другой работник может продолжить
чтение-восстановление; поздний ответ первого не перезаписывает его результат.
Исходная доска закрепляется до POST. Смена конфигурации доски не создаёт карточку
в новой доске автоматически (`trello_board_config_changed`).

Для устойчивого `outcome_unknown` без совпадения команда проверяет исходную
доску, архив, историю и состояние первоначального вызова. Если карточка найдена,
следует восстановить её точный UUID-маркер, если он был удалён, и дождаться
следующего цикла. Если карточка существует в другой доске, сначала необходимо
разобраться с её перемещением и исходной настройкой. Не сбрасывать состояние в
`pending` лишь потому, что поиск ничего не нашёл: это не доказательство отказа.
Если результат установить нельзя, заявка остаётся сохранённой в WMS и в режиме
восстановления. Любая адресная ручная коррекция БД требует подтверждённого
результата внешней операции и обычного отдельного разрешения на production write;
публичной административной ручки для этого не добавлено.

## Проверки без внешних вызовов

Из `backend`:

```sh
ruff check .
mypy .
pytest -n auto tests/test_developer_requests.py
```

Тесты используют `httpx.MockTransport`; реальные ключи и сеть не нужны.
`WMS_TEST_DATABASE_URL` позволяет повторить тесты на выделенной локальной PostgreSQL
базе. Фикстура удаляет и создаёт таблицы, поэтому значение должно указывать только
на одноразовую тестовую БД с префиксом имени `wms_test` на localhost/127.0.0.1.
Для общей PostgreSQL базы запускать без `-n auto`;
сами конкурентные сценарии запускают независимые запросы/работники одновременно.


## Изолированная приёмка с одной живой карточкой

`dev/developer_requests_probe.py` запускает настоящий API и сервис синхронизации
на отдельной SQLite базе. Он не читает `.env` checkout и не наследует настройки
Trello или брокера в API. Состояние проверки, база и конфигурация находятся вне Git;
по умолчанию состояние — `~/.local/state/wms624-live-probe`. Это ограничитель
проверочного сценария, а источником состояния доставки остаётся строка WMS.
Секреты не передаются frontend, не печатаются и не добавляются в командную строку.

Из `backend`, используя Python окружения backend:

```sh
python dev/developer_requests_probe.py init
python dev/developer_requests_probe.py serve
```

API доступен только на `http://127.0.0.1:18240`. `init` идемпотентно создаёт
тестовую организацию, пользователей и две заявки через настоящие авторизацию/API:
ошибку, которая остаётся локальной, и первоначальную выбранную доработку.
Повторный `init` сохраняет уже выбранную заявку, в том числе после `adopt`.
База не удаляется. В другом терминале, из `frontend`:

```sh
VITE_API_PROXY=http://127.0.0.1:18240 npm run dev -- --host 127.0.0.1 --port 16241 --strictPort
```

Селлер входит на `http://127.0.0.1:16241/seller/` как `seller@wms624.example.com`,
фулфилмент — на `http://127.0.0.1:16241/` как `ff@wms624.example.com`.
Имена пользователей: `WMS624 Test Seller` и `WMS624 Test FF`; организация
`wms624-live-probe`. Пароль обеих **исключительно локальных тестовых**
учётных записей: `WMS624-local-test-only`.
Для доказательства полного пути браузер → API → БД → Trello аналитик отправляет
через «?» новую доработку, начинающуюся в поле экрана с `[WMS-624 TEST]`.
Её UUID берётся из ответа POST или списка GET настоящего локального API.
Перед первым внешним POST выбрать её можно так:

```sh
python dev/developer_requests_probe.py adopt --request-id UUID_ЗАЯВКИ
python dev/developer_requests_probe.py inspect
```

`adopt` принимает только ещё не отправленную доработку тестового селлера этой
организации с явным тестовым префиксом. После первой попытки создания выбор
заблокирован. Остальные заявки остаются локальными, пакетная синхронизация
и Celery worker/beat в этом контуре не запускаются.

Живые команды выполняются только после отдельного разрешения владельца и
подготовки конфигурации. `--config` содержит только путь к JSON вне Git с правами
`0600`, ключами `TRELLO_API_KEY`, `TRELLO_TOKEN`, `board_short_link` и при необходимости
`TRELLO_*_LIST_ID` / `TRELLO_CLIENT_LABEL_ID`. Значения доски, четырёх списков и синей
метки «Клиент» закреплены в harness по согласованному WMS-624 контуру; подмена
не допускается. Канонический ID доски определяется чтением по `WPtAFgrM`.

```sh
python dev/developer_requests_probe.py preflight --config /PRIVATE/PATH/config.json
python dev/developer_requests_probe.py deliver --config /PRIVATE/PATH/config.json
python dev/developer_requests_probe.py cycle --step queued --config /PRIVATE/PATH/config.json
python dev/developer_requests_probe.py cycle --step in_progress --config /PRIVATE/PATH/config.json
python dev/developer_requests_probe.py cycle --step completed --config /PRIVATE/PATH/config.json
```

`preflight` читает приватность/активность доски, принадлежность всех четырёх
списков и цвет/имя метки, затем сохраняет ID/списки/архивность существующих карточек
с учётом пагинации. `deliver` применяет production `sync_request` только к выбранной
заявке. Ограничитель записывает начало попытки на диск до POST и запрещает любой
второй внешний create в этом прогоне, в том числе после перезапуска. При
`outcome_unknown` повторный `deliver` использует штатный поиск по UUID-маркеру,
не создавая новую карточку. После явного отказа также нет автоматического
повторного POST: требуется разбор, а разрешение владельца на одну карточку
не превращается в разрешение новых попыток.

`cycle` без `--step` проходит все четыре статуса. С указанным шагом аналитик может
между командами обновить «Мои заявки» и открыть детали. Перед каждым переносом
проверяются точный ID связанной карточки, тестовый префикс, UUID-маркер, доска,
метка и отсутствие ID в исходном снимке. Переносится только созданная тестовая
карточка, после чего выполняются production sync и реальный HTTP GET API с
авторизацией селлера. Удаления/архивации нет; итоговая карточка остаётся на доске.
Сверка исходного снимка обнаруживает изменения прежних карточек, но не может
приписать внешние одновременные действия этому прогону.

Не удалять состояние/базу и не начинать новый `--state-dir` ради обхода запрета
повторного создания. Не запускать batch sync и не устанавливать live настройки
в API этого контура. Локальный успешный запуск не доказывает живую интеграцию:
отдельно сохраняются реальный ID карточки и результаты чтения четырёх статусов.

Проверка защит без сети и реальных ключей:

```sh
pytest -q dev/test_developer_requests_probe.py
```
