# WMS-624: backend обращений разработчикам

`POST /developer-requests` подтверждает сохранение обращения в БД WMS. Доставка в
Trello происходит отдельно; отсутствие конфигурации или ошибка Trello не отменяет
сохранение. `GET /developer-requests` и `GET /developer-requests/{id}` возвращают
только обращения авторизованного автора в его организации. Внутренние карточки
Trello не импортируются. Поля формы и их подписи определены в
`../../docs/requirements/WMS-624.md`.

## Схема и запуск

Выпустить backend вместе с миграцией `20261001_2301_developer_requests.py`
(`down_revision = 20260906_2300`). Обычная команда миграции — `alembic upgrade head`.
Не применять миграцию к стенду отдельно от соответствующего кода.

Фоновая задача `wms.developer_requests_sync` зарегистрирована в существующем Celery.
Для автоматической доставки нужны действующий `CELERY_BROKER_URL`, worker
`celery -A app.celery_app worker` и планировщик `celery -A app.celery_app beat`.
Планировщик запускает задачу каждые 60 секунд по умолчанию. Один проход выбирает
до 50 записей, начиная с наиболее давно ожидающих синхронизации. GET не запускает
внешние действия. Само наличие API без worker и beat не доставляет карточки.

## Контракт серверной конфигурации

Настройки находятся в `app/core/settings.py`; frontend их не получает.

| Переменная | Назначение |
|---|---|
| `TRELLO_API_KEY` | Ключ существующего разрешённого Trello приложения. |
| `TRELLO_TOKEN` | Токен с доступом к выбранной доске. |
| `TRELLO_BOARD_ID` | ID приватной доски команды. |
| `TRELLO_REVIEW_LIST_ID` | Начальный список «На рассмотрении». |
| `TRELLO_QUEUED_LIST_ID` | Список «В очереди». |
| `TRELLO_IN_PROGRESS_LIST_ID` | Список «В работе». |
| `TRELLO_COMPLETED_LIST_ID` | Список «Завершена». |
| `TRELLO_CLIENT_LABEL_ID` | ID существующей цветной метки «Клиент» на этой доске. |
| `TRELLO_SYNC_INTERVAL_SEC` | Интервал, минимум 30 секунд, по умолчанию 60. |

Без ключа, токена, доски либо одного из четырёх различных ID списков задача
ничего не отправляет. До отправки проверяются приватность и активность доски,
принадлежность четырёх открытых списков этой доске. ID метки необязателен для
доставки; без него остаётся текст «Клиент: организация / селлер», но цветовое
различие не настроено. Для завершения подключения команда выбирает или создаёт
метку «Клиент» штатно в Trello и указывает её ID. Внутренние карточки команда
создаёт штатно в Trello, без этой метки либо с другой меткой/цветом.

Этот документ задаёт имена переменных, но не разрешает создание, чтение или
замену реальных ключей. Живая доска, доступ к ней и её цветовое оформление
не проверялись при разработке. Ни одна реальная карточка не создавалась.

## Состояния доставки и восстановление

Пользовательские статусы `review`, `queued`, `in_progress`, `completed` отражают
список связанной карточки. Неизвестный список, удалённая/перенесённая карточка или
ошибка провайдера сохраняют последний подтверждённый статус.

Техническое `delivery_state` хранится только в БД:

- `pending`: POST ещё не выполнялся либо Trello явно отклонил его HTTP 4xx.
  Известные отказы повторяются с увеличивающейся задержкой, максимум пять POST.
  После лимита `last_error = trello_create_retry_exhausted`; локальная заявка остаётся.
- `outcome_unknown`: факт начала попытки записан и закоммичен до POST, ответ ещё
  не подтверждён. Timeout, потеря соединения, HTTP 5xx и неполный успешный ответ
  оставляют это состояние. Разрешены только чтения для восстановления.
- `linked`: сохранён `trello_card_id`; дальше читается текущий список карточки.

Каждая клиентская карточка содержит отдельную строку `WMS-REQUEST-ID: <UUID>`.
Восстановление ищет точную строку в описаниях карточек исходной настроенной доски,
включая архивные. Одна найденная карточка связывается с заявкой. Отсутствие маркера,
ошибка чтения либо несколько совпадений не разрешают новый POST. `last_error`
содержит только код ошибки/HTTP статус, без ответа сервера, URL и секретов.

БД выдаёт одному работнику аренду записи на пять минут. Обновления проверяют
уникальный токен этой аренды. После истечения другой работник может продолжить
чтение-восстановление; поздний ответ первого не перезаписывает его результат.
Исходная доска закрепляется до POST. Смена конфигурации доски не создаёт карточку
в новой доске автоматически (`trello_board_config_changed`).

Для устойчивого `outcome_unknown` без совпадения команда проверяет исходную
доску, архив, историю и состояние первоначального вызова. Если карточка найдена,
следует восстановить её точный UUID-маркер, если он был удалён, и дождаться
следующего цикла. Если карточка существует в другой доске, сначала необходимо
разобраться с её перемещением и исходной настройкой. Не сбрасывать состояние в
`pending` лишь потому, что поиск ничего не нашёл: это не доказательство отказа.
Если результат установить нельзя, заявка остаётся сохранённой в WMS и в режиме
восстановления. Любая адресная ручная коррекция БД требует подтверждённого
результата внешней операции и обычного отдельного разрешения на production write;
публичной административной ручки для этого не добавлено.

## Проверки без внешних вызовов

Из `backend`:

```sh
ruff check .
mypy .
pytest -n auto tests/test_developer_requests.py
```

Тесты используют `httpx.MockTransport`; реальные ключи и сеть не нужны.
`WMS_TEST_DATABASE_URL` позволяет повторить тесты на выделенной локальной PostgreSQL
базе. Фикстура удаляет и создаёт таблицы, поэтому значение должно указывать только
на одноразовую тестовую БД. Для общей PostgreSQL базы запускать без `-n auto`;
сами конкурентные сценарии запускают независимые запросы/работники одновременно.
