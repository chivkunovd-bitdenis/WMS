**Фронт написан, переписывать не нужно.** Код в
`frontend/src/screens/ff/sorting-objects/`. Не хватает единственного: чтобы
данные приходили с сервера, а действия туда уходили.

Общие требования по тенантности и надёжности — в

## 0. Что это за экран

Это шаг **раскладки внутри документа приёмки** (селлер → ФФ), а не отдельный
раздел. Отсюда следуют две вещи, которые не надо изобретать заново.

Во-первых, **заканчивается он как документ**: «Закрыть», «Сохранить»,
«Завершить». Отдельной «записать ячейку» нет — записывается документ целиком,
как и в сегодняшней приёмке.

Во-вторых, **задание идёт по одной поставке одного селлера**, поэтому колонки
селлера на экране нет: она повторяла бы одно и то же в каждой строке.

## 1. Модель: место вычисляется, а не хранится

Порядок работы обратный привычному: сначала собирается объект — товар в короб,
короб на палету, — и только готовый объект ставится на полку.

**Место товара нигде не хранится.** Оно вычисляется по цепочке держателей: товар
в коробе, короб на палете, палета в ячейке. Поэтому «что в коробе» и «где короб»
не могут разъехаться — это одно знание, записанное один раз, а не два числа,
которые кто-то должен сверять.

У каждого объекта и каждой строки товара есть ровно один **держатель**:

- другой объект (короб на палете, товар в коробе);
- ячейка (объект стоит на полке);
- никто — собрано или принято, но ещё не поставлено.

Это та же самая ссылка на контейнер, которую владелец утвердил для карты склада
(её раздел 0). Второй раз её заводить не нужно — экраны обязаны читать одну и ту
же правду, иначе остаток на карте и остаток в раскладке разойдутся.

## 2. Что сервер обязан отдавать

`GET /inbound-intakes/{id}/sorting`

```json
{
  "warehouse_id": "uuid",
  "cells": [
    { "id": "uuid", "code": "А 1.1", "barcode": "2000000000114" }
  ],
  "objects": [
    {
      "id": "uuid",
      "kind": "pallet | box | cargo_place",
      "code": "П-000131",
      "barcode": "2100000001311",
      "holder": { "kind": "object | cell | none", "id": "uuid | null" }
    }
  ],
  "lines": [
    {
      "id": "uuid",
      "product_id": "uuid",
      "name": "Футболка хлопок белая, M",
      "size": "M",
      "barcode": "4680123456789",
      "photo_url": "https://...",
      "qty": 24,
      "holder": { "kind": "object | cell | none", "id": "uuid | null" },
      "already_at": [{ "cell_id": "uuid", "code": "А 1.1", "qty": 24 }]
    }
  ]
}
```

Правила, которые обязан соблюдать сервер:

- **`already_at` — это остаток того же товара на этом складе**, посчитанный по
  той же таблице остатков, что читает карта склада. Не отдельный расчёт.
- **`size`** — размер с карточки маркетплейса, может быть `null`. Экран
  показывает колонку «Размер», только если размер есть хотя бы у одной строки.
- **`qty` объекта сервер не отдаёт**: экран считает его сам по составу. Если
  сервер начнёт отдавать своё число, появится второй источник правды.
- Глубже трёх уровней вложенности не бывает: палета → короб/грузоместо → товар.
- `photo_url` может быть `null` — экран покажет силуэт, как везде в системе.

## 3. Что сервер обязан принимать

### 3.1 Переложить

`POST /inbound-intakes/{id}/sorting/move`

```json
{
  "subject": { "kind": "line | object", "id": "uuid" },
  "to": { "kind": "object | cell | none", "id": "uuid | null" },
  "qty": 12
}
```

- `qty` только для `kind: "line"`; у объекта его нет — объект едет целиком со
  всем содержимым.
- Ответ — свежее состояние раскладки в формате раздела 2. Экран показывает
  перемещение сразу, не дожидаясь ответа, и сверяется с ним; разошлось —
  показывает серверную правду и говорит об этом.

Что обязан проверить сервер, потому что фронт этого гарантировать не может:

- **Товар внутри короба или грузоместа нельзя переложить напрямую** — сначала
  «вынуть». Короб и грузоместо закрыты. С палеты брать напрямую можно: там вещи
  лежат открыто.
- Палета кладётся только на ячейку. Короб и грузоместо — на палету или на
  ячейку. Товар — куда угодно.
- Внутрь самого себя не кладётся ничего, в том числе через цепочку.
- Количество не больше того, что есть в строке; остаток не уходит в минус.
- Всё принадлежит тому же арендатору: и предмет, и цель, и документ.

На каждый отказ — сообщение на языке склада, без кодов и стектрейсов.

### 3.2 Снять с ячейки

Отдельного эндпоинта не нужно: это тот же `move` с `to: { kind: "none" }`.
Снимается **целиком**, вместе с содержимым — снимают полку, а не пересчитывают.

### 3.3 Создать объект

`POST /inbound-intakes/{id}/sorting/objects` → `{ "kind": "pallet | box | cargo_place" }`

Номер и штрихкод присваивает сервер и возвращает в ответе. Экран их не
придумывает.

### 3.4 Сохранить и завершить

`POST /inbound-intakes/{id}/sorting/save` — сохранить как есть, документ
остаётся в работе.

`POST /inbound-intakes/{id}/sorting/complete` — завершить распределение.
Отказывает, пока осталось непоставленное, и говорит сколько.

### 3.5 Ячейки и печать

Новых эндпоинтов не нужно. Создание ячейки — существующий
`api/warehouses.py`, той же модалкой, что на карте склада. Печать стикера
ячейки, короба, палеты и грузоместа — стандартный диалог выбора размера
этикетки, сервер для этого ничего не отдаёт.

## 4. Чего нет в данных и что придётся завести

| Что | Сейчас | Нужно |
|---|---|---|
| Палета | модели нет | заводится волной 1 карты склада |
| Товары внутри грузоместа | строк нет вообще | заводится волной 1 карты склада |
| Держатель у строки раскладки | `InboundIntakeDistributionLine` знает только ячейку | ссылка на держатель — объект или ячейка |
| Размер товара | `wb_size` у товара есть | отдать в ответе; ничего заводить не надо |
| `already_at` | остаток по товару и ячейке есть | собрать в ответ, отдельной модели не нужно |

## 5. Порядок

1. Волна 1 карты склада (палета, ссылка на контейнер, наполнение грузоместа) —
   без неё этому экрану не на чем стоять.
2. `GET .../sorting` — чтение.
3. `move`, создание объектов, `save`, `complete`.
4. Подключение экрана к API вместо заглушек — это делаю я.

## 6. Решения и границы

Открытых вопросов не осталось.

**Решено 28.08 — нумерация наша и сквозная.** Короб, палета и грузоместо
получают наш собственный номер (`КР-000472`, `П-000131`, `ГМ-000318`), и дальше
эта единица фигурирует под ним **везде**: в раскладке, на карте склада, в
упаковке, в отгрузке. Приёмка идёт от селлера на наш склад, маркетплейс в ней не
участвует, и назначать коробу чужой формат номера незачем.

Из «сквозной» следует требование к серверу: номер выдаётся **один раз при
создании единицы** и больше не меняется никогда — ни при перекладывании, ни при
переходе документа в другой статус, ни при попадании в отгрузку. Экраны
показывают его как есть.

Стикер для Wildberries — отдельная история: по FBS идентификатор грузоместа
выдаёт сам WB ответом на `POST .../trbx`, и на этот стикер идёт именно он. По
FBO публичного метода получить код нет — он генерируется в кабинете продавца
или берётся из XLSX-шаблона. Наш номер туда не попадает и попадать не должен.

## 7. Чего в этом контракте нет

- Печати самих этикеток — это отдельная задача бэклога, сквозная по трём
  документам.
- Возврата документа из завершённого распределения обратно в работу.
- Ограничений по вместимости ячейки — на экране их нет, значит и здесь нет.
