# ЧАСТЬ II. УПАКОВКА ФБС — ПОЛНЫЙ РАЗБОР

Здесь то, до чего докопались в длинном разговоре 29.08, плюс проверка по коду.

## Как это устроено в базе

Таблица **`fbs_packaging_fulfillments`**
(`backend/app/models/fbs_packaging_fulfillment.py`). Докстринг модели говорит
прямо: *«Links one physical packaging unit to exactly one FBS order»* — одна
строка связывает одну физически упакованную единицу ровно с одним заказом ФБС.

Ключевое ограничение (строки 41–45):

```python
Index(
    "uq_fbs_packaging_fulfillments_active_order",
    "fbs_order_id",
    unique=True,
    postgresql_where=text("undone_at IS NULL"),
)
```

Уникальность по заказу среди неотменённых записей. То есть **один заказ = одна
активная запись упаковки**. А поскольку в ФБС один заказ — это одна единица
товара, счёт «сколько упаковано» физически ведётся по заказам, а не по штукам.

Каждая строка ссылается на заказ, на задание упаковки, на строку задания, на
пользователя и на движение остатка (`inventory_movement_id`). Это не просто
галочка — это след, кто и что закрыл.

## Позиция владельца и почему она справедлива

Владелец формулировал так: у нас есть поставка ФБС, с ней связаны товары и
штуки в таблице, упаковщик собрал и наклеил стикер — на кой чёрт заставлять
его отмечать каждую единицу отдельно, если это по сути **просто проводка
дальше**, утверждение факта. При нажатии надо просто ставить отметку и считать
упакованное по количеству товара в документе.

Это справедливо, и вот почему — по трём проверенным фактам:

**Первое: упаковка ничего не списывает.** Списание остатка происходит в момент
**подтверждённой доставки**, а не при упаковке. Проверено: в
`fbs_packaging_integration_service.py` нет вызовов списания на пути упаковки.
Значит нажатие кнопки не двигает деньги и товар — цена ошибки низкая.

**Второе: нехватка остатка при упаковке уже НЕ блокирует.**
`fbs_packaging_integration_service.py:606-638` — при `insufficient_stock`
система пробует альтернативную ячейку сортировки, а если и там пусто, **всё
равно продолжает упаковку** и просто кладёт предупреждение в `warnings`. Это
осознанное решение, уже принятое. То есть путь «просто проведи дальше» здесь
частично уже реализован.

**Третье: работа оператора не теряется при отмене заказа.** Я ошибочно заявлял,
что отменённые заказы приведут к переучёту в биллинге. Владелец возразил, я
проверил `_decrement_packaging_line_for_product`
(`fbs_packaging_integration_service.py:161-183`) — там при уменьшении плана:

```python
new_total = int(line.qty_total) - 1
if new_total <= 0:
    if qty_done(line) <= 0:
        await session.delete(line)
    else:
        line.qty_total = qty_done(line)   # сделанное сохраняем
```

Уже сделанная работа фиксируется как новый план, а не стирается. Переучёта нет.
Моё возражение было неверным, снято.

## Что на самом деле ломается — цепочка, проверенная по коду

**Звено 1. Сервер прямо запрещает «отметить всё разом» для ФБС.**

`backend/app/services/packaging_task_service.py:1218-1220`:

```python
fbs_supply = await get_supply_for_packaging_task(session, tenant_id, task_id)
if acknowledge_all_packed and fbs_supply is not None:
    raise PackagingTaskServiceError("fbs_acknowledge_not_allowed")
```

Тот самый одношаговый путь, которого хочет владелец, **на уровне сервиса
закрыт для поставок ФБС**. Замысел понятен: в ФБС каждая единица должна лечь
на конкретный заказ, иначе развалится связь «единица ↔ заказ», на которой
держится и стикер, и передача в WB. Но следствие — фронт вынужден идти в обход.

**Звено 2. Фронт ходит в обход — циклом по строкам.**

`frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx:1033-1078`, функция
`packEverything` за кнопкой «Всё упаковано»:

```python
for (const line of current.lines) {
  const remaining = line.qty_need_pack - line.qty_packed_in_task
  if (remaining <= 0) continue
  const response = await fetch(.../lines/${line.id}/pack, {... quantity: remaining})
  if (!response.ok) { setError(...); return }      # <-- вот здесь всё и рвётся
  current = packed.packaging_task
}
# и только потом:
fetch(.../complete, { acknowledge_all_packed: false })
```

Одно нажатие — **N последовательных запросов**, по одному на строку. И финальный
`/complete` вынужденно с `acknowledge_all_packed: false`, потому что `true`
запрещён звеном 1.

**Звено 3. Отсюда и «хвост».** Если запрос на третьей строке падает, стоит
`return`. Первые две строки **уже закоммичены на сервере**, четвёртая и дальше
не отправлялись вовсе, а `/complete` не вызывается. Задание остаётся наполовину
сделанным, транзакции нет, отката нет. Оператор видит ошибку и не понимает, что
именно закрылось, а что нет. **Это и есть хвост, про который шла речь.**

**Звено 4. И даже когда всё прошло — поставка может молча зависнуть.**
`try_promote_fbs_supply_if_ready` (`fbs_packaging_integration_service.py:694-730`)
не бросает ошибку, а **молча не переводит** статус, если у какого-то заказа не
закрыта маркировка. Оператор всё упаковал, ошибки нет, а поставка так и висит в
`assembling` без единого объяснения. Внятный `marking_required` он увидит только
дойдя до предполётной проверки перед передачей в WB — несколькими экранами
позже. Это отдельный дефект, но операторски он сливается с предыдущим в одно
ощущение «нажал, и ничего не произошло».

## Что было проверено и оказалось НЕ виновато

Чтобы новый чат не копал повторно:

- **`record_pack_progress` строки задания не режет и не добавляет.** Я утверждал
  обратное, Codex доказал кодом. Утверждение снято.
- **91 заявка ≠ 91 единица.** Каждая заявка несёт `quantity: remaining`.
- **Упаковка не списывает товар.** Владелец поправлял дважды, проверено.

## Решение, о котором договорились

Одна кнопка → **один** запрос на сервер → всё задание закрывается в **одной
транзакции**, при этом связь «единица ↔ заказ» сохраняется.

То есть нужен серверный эндпоинт, который сам разложит общее количество по
заказам поставки (логика подбора заказа под единицу уже есть —
`_resolve_order_for_pack_unit`, `fbs_packaging_integration_service.py:461-504`),
создаст все `fbs_packaging_fulfillments` разом и завершит задание. Либо всё,
либо ничего — без промежуточных состояний.

Тогда запрет `fbs_acknowledge_not_allowed` останется на месте и продолжит
защищать связь с заказами, а оператор получит ровно то поведение, которого
просит владелец: нажал — проведено.

**Что решить перед кодом:** что делать, когда заказов под единицы не хватает
или часть заказов не подобрана. Сейчас на это отвечают коды `order_not_picked`
и `no_eligible_order` (оба без человеческого текста).

сообщения. Тексты чек-листа написаны и видны на preflight («Требуется
маркировка Честный знак»), но при нажатии «Передать» приходит сырое
`marking_required`. Передать `check.message` вторым аргументом — дыра закрыта.

**«Сдать без Честного знака» снимает только НАШЕ требование.** Требование WB из
`required_meta_json` заказа ею не отменяется — заказ упрётся в
`marking_not_allowed`. Зафиксировано комментарием в коде.

**Три системные дыры с молчаливыми ошибками.** У `FbsPackingBoxError` и
`FbsShipmentPvzError` конструкторы вообще не принимают `message` — все
блокировки коробов и грузомест уходят на фронт голым кодом. Для физических
лимитов WB тексты в файле есть, но используются только в мягком preflight.

**Лимиты WB на грузоместо:** сторона ≤ 600 мм, сумма сторон ≤ 1400 мм, вес
≤ 5000 г, объём поставки ≤ 1 м³, мест ≤ «заказов + 1».

**Ozon заблокирован намеренно** — без явного провайдера заглушка всегда отдаёт
`403 code 7`.

**Главная дыра фронта — кнопка «Завершить» отгрузку**
(`FfSuppliesShipmentsPage.tsx:3227`): тултипа нет, а готовые тексты «Добавьте
товары в короба» и «Завершите упаковку» лежат в `requestShipMpUnload` и
физически не могут показаться — кнопка блокируется раньше обработчика.
