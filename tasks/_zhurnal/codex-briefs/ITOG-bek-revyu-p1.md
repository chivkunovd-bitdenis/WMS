1. Резерв направлений

`StockDirection` действительно не связан со складом. Поэтому складские остатки и складские резервы теперь сначала суммируются, а глобальный резерв направления вычитается один раз после агрегации.

Проверено:

- два склада `100 + 100`, резерв `30` → `reserved=30`, `free=170`;
- один склад `100`, резерв `30` → прежние `reserved=30`, `free=70`.

Незакрытого по этому пункту нет.

2. Многопозиционное списание Ozon

Источником факта стали реально упакованные единицы из `ozon_packed_units_json`: каждая содержит свой товар и ячейку. Они группируются по `(product_id, storage_location_id)` и списываются с фактическим количеством.

Новая миграция не понадобилась: существующий `FbsShipmentReversalLedger` уже имеет `ozon_positions_json`, рассчитанный на несколько позиций. В нём сохраняется полная расписка возврата; `shipment_movement_id` указывает на первое движение как признак проведённого списания.

Синхронизация отменённого заказа Ozon теперь вызывает возврат по той же расписке. Проверены:

- два разных товара;
- количество больше единицы;
- отмена возвращает все позиции и количества;
- одна единица работает как прежде;
- прежний WB-сценарий не изменился.

Если заказ помечен упакованным, но фактических упаковочных единиц нет, операция теперь явно останавливается с `missing_fbs_packaging_location`, а не придумывает товар или ячейку.

3. Номер палеты

`max(code) + 1` заменён атомарным счётчиком через `INSERT … ON CONFLICT … RETURNING` — тем же приёмом, которым проект выдаёт номера документов.

Два параллельных создания получили разные коды, обе палеты сохранились. Также проверено продолжение старой нумерации: после `П-000005` создаётся `П-000006`. Неожиданное столкновение идентификаторов превращается в понятный конфликт `pallet_identifier_conflict` с HTTP 409, а не 500.
