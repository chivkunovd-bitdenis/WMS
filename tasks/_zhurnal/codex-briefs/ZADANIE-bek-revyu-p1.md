# Три дефекта из ревью PR #140. Все подтверждены по коду.

## 1. Резерв направлений вычитается по разу на каждый склад — цифра клиента врёт

`fbs_stock_breakdown_by_product` в
`backend/app/services/fbs_stock_availability_service.py` (около строки 198)
берёт резерв направлений так:

    direction_map = await stock_direction_service.direction_totals_by_product(
        session, tenant_id, product_ids
    )

**Склада в этом вызове нет** — резерв глобальный по товару. А вызывающий код в
`backend/app/services/fbs_stock_rule_service.py` (около строки 321) идёт циклом
по складам продавца и складывает `row.reserved` каждого склада.

Итог: при двух складах и глобальном резерве 30 экран получает `reserved = 60`,
а свободный остаток занижается вдвое. Пример из ревью: остатки 100 и 100, резерв
30 — показывается `reserved=60 / free=140` вместо `30 / 170`.

**Что сделать.** Решить, где резерв направлений учитывается ровно один раз.
Посмотри, что такое `stock_direction_service.direction_totals_by_product` и
привязаны ли направления к складу вообще. Если направления глобальные — их
нельзя складывать по складам: вычитай один раз на товар поверх суммы складов.
Если у направления есть склад — фильтруй по нему в самом запросе.

Не сломай экран одного склада: там сейчас цифры верные, и они не должны
измениться. Это главная проверка правильности решения.

**Тесты обязательны:** два склада с остатками 100 и 100 и глобальным резервом 30
дают `reserved=30`, `free=170`. Один склад со 100 и резервом 30 — как было:
`reserved=30`, `free=70`.

## 2. Заказ Ozon с несколькими товарами списывается как одна штука

`backend/app/services/fbs_shipment_service.py`, около строки 811:

    result = {
        order_id: (product_id, storage_location_id)
        for order_id, product_id, storage_location_id in fulfillment_rows
    }

Словарь по номеру заказа схлопывает все строки выполнения заказа в последнюю.
Ниже, в `_write_off_delivered_orders_once`, расписка создаётся с `quantity=1`
жёстко и с `order.product_id`.

Значит заказ на два разных товара спишет один, а заказ на две штуки одного —
одну. Остаток на складе останется завышенным.

**Что сделать.** Списывать каждую фактически собранную позицию заказа со своим
количеством и своим местом. Смотри, что реально хранят
`FbsPackagingFulfillment` и `FbsOrderPick` — есть ли там количество, и если нет,
откуда его брать честно. Расписка `FbsShipmentReversalLedger` рассчитана на одну
строку на заказ: проверь, выдержит ли она несколько позиций, и если нет — реши,
как это сделать **добавляющей** миграцией, без удаления колонок.

Отмена после доставки должна возвращать ровно столько же, сколько списали.

**Тесты:** заказ с двумя разными товарами; заказ с количеством больше единицы;
отмена такого заказа возвращает всё списанное; заказ на одну штуку работает
как раньше.

## 3. Гонка номеров при создании палеты

`backend/app/services/pallet_service.py`, `_next_code_number` около строки 50,
считает `max(code) + 1` без блокировки. Два одновременных создания получают один
номер: один запрос пройдёт, второй упадёт пятисоткой.

**Что сделать.** Сделать выдачу номера устойчивой к одновременным запросам.
Способ выбери по тому, как в проекте уже решены похожие места — поищи, как
выдаются номера другим документам, и повтори приём, а не изобретай свой.
Отказ при столкновении должен быть понятным, а не пятисоткой.

**Тест:** два параллельных создания дают два разных номера и обе палеты живы.
