# BLG-I09: независимая критика исследования сверки КИЗ

Дата: 2026-08-21
Стадия: S04 `RESEARCH_CRITIC`
Роль: `pipeline-reviewer`
Модель: `gpt-5.6-sol` (`expensive`)
Решение: **HOLD, `RESEARCH_PASSED` не выдан**

## Итог

Read-only-first подход S03 верный: первый запуск должен только собрать полный снимок и findings,
не менять связи заказов, пул КИЗ, статусы, dispatch gate или данные WB. Граница между решением WB и
юридическим состоянием кода в «Честном знаке» также проведена правильно.

Но исследование нельзя пропустить дальше: актуальная документация WB противоречит неполной модели
`decision` в S03, а cardinality нескольких `sgtin` не доказана версионным контрактом или fixture.
Из-за этого предложенная сверка может принять разрешение на доставку за успешную проверку КИЗ,
сопоставить решение не тому значению или скрыть дубль при преждевременном превращении ответа в set.

## Блокирующие находки

### 1. Семантика `metaDetails.decision` неполна

В актуальной публичной документации WB для
`POST /api/marketplace/v3/orders/meta` ответ описан как
`orders[].metaDetails[] { key, value: string | null, decision }`. Для `sgtin` перечислены:

- допускают перевод поставки в доставку: `filled`, `deadlineExceeded`, `optional`,
  `sgtinIntroduced`, `sgtinSoldB2B`;
- не допускают: `required`, `pending`, `sgtinInvalidFormat`, `sgtinNoGS`,
  `sgtinHasInvalidSymbols`, `sgtinHasNonLatinSymbols`, `sgtinInvalidPattern`, `sgtinNotFound`,
  `sgtinEmitted`, `sgtinApplied`, `sgtinWrittenOff`, `sgtinWithdrawn`, `sgtinRetired`,
  `sgtinDisaggregated`, `sgtinDisaggregation`, `sgtinAppliedNotPaid`.

Семантика различается принципиально:

- `filled` означает, что значение закреплено, но проверка не требуется; это не доказательство
  корректности КИЗ;
- `optional` означает, что значение не закреплено и не обязательно; строка с `value = null` не
  является удалённым КИЗ;
- `deadlineExceeded` разрешает доставку, хотя проверка ещё может завершиться ошибкой;
- `sgtinIntroduced` и `sgtinSoldB2B` являются отдельными подтверждёнными положительными исходами.

Следовательно, единый локальный `accepted` для `filled`, успешной проверки и разрешения на доставку
теряет бизнес-смысл. S03 должно зафиксировать раздельные факты `attached`, `validation outcome` и
`delivery eligibility`, полный текущий enum и fail-closed обработку неизвестного значения.

Источник: https://dev.wildberries.ru/docs/openapi/orders-fbs, раздел «Идентификаторы маркировки
FBS», проверен в видимом браузере 21.08.2026. Marketplace API, sandbox и прод не вызывались.

### 2. Set-операции для нескольких `sgtin` не определены контрактно

Документация разрешает записать 1-100 КИЗ, но schema и пустой пример ответа не доказывают:

- возвращается ли ровно один `metaDetails` на каждый КИЗ;
- возможны ли строки без значения наряду со строками значений;
- гарантированы ли уникальность, порядок и одинаковый `decision` для всех значений;
- как выглядит смешанный результат проверки нескольких КИЗ.

До доказательства нельзя утверждать, что `metaDetails` является полным поэлементным удалённым
ledger. Нужен версионный OpenAPI snapshot либо проверенный sandbox/emulator fixture с 0, 1 и N КИЗ,
`value = null`, дублем и смешанными decisions. Это часть основного контракта сверки, а не только
будущий тест S15.

Алгоритм сравнения должен сначала сохранять ordered multiset без дедупликации. Затем отдельно
строятся:

- строки состояния ключа без значения (`required`, `optional` и аналоги);
- точные raw-значения с сохранённым `0x1D`;
- дубли внутри одной стороны;
- `local_only`, `wb_only` и exact intersection;
- кандидат `short/full representation`, который не считается равенством и никогда не даёт
  автоматическую mutation.

Сравнение только по `GTIN + serial` недостаточно для автоматического совпадения. Оно не доказывает
тождество полного кода, криптохвоста, физического экземпляра или владельца.

### 3. Снимок WB не восстанавливает историю расхождения

Текущий readback показывает только состояние WB на момент запуска. После удаления, замены,
закрытия заказа или смены seller-доступа он не доказывает, какой КИЗ был закреплён в дефектном окне.
Нужно разделить `CURRENT_DIVERGENCE` и `HISTORICAL_UNRESOLVED`; отсутствие строки в неполном или
недоступном batch нельзя классифицировать как пустой удалённый набор.

Снимок обязан фиксировать отдельно время чтения order status, `requiredMeta/optionalMeta` и
`metaDetails`, потому что это не атомарный внешний снимок. При смене данных между запросами run
становится `REMOTE_CHANGED_DURING_RUN`, а не основанием для repair. `401/403`, `404`, `429`, 5xx,
transport error и missing order row остаются разными findings.

Актуальная документация также говорит, что любой ответ `4XX`, а не только `409`, считается как
10 запросов лимита. План нагрузки S03 должен быть исправлен.

### 4. Read-only-first требуется сделать жёстким инвариантом

До закрытия BLG-I01/BLG-I02 и этого blocker запрещены даже status-only auto-apply и обновление
рабочего cache. Разрешён только новый immutable reconcile snapshot и findings. Запись самого снимка
не должна запускать существующие hooks, пересчёт `metadata_delivery_allowed`, уведомления поставки
или изменение `MarkingCode.status`.

Полный КИЗ допустим только в защищённом snapshot по контракту S11. В logs, receipts, dispatch,
общем CSV и этом evidence остаются только mask/fingerprint.

## Неподтверждённое состояние кода

Проверен checkout `a6a2a40ce02530a919d4ea979e4f3322591a6a49`; целевые backend-файлы чистые и не
отличаются от task base `69c271678782d7dcfa39df97cd905cbee1678727`. Это только наблюдение
репозитория, не доказательство deployed/live поведения.

Текущий код подтверждает риск, но не контракт:

- `fbs_marking_service.py` сворачивает `metaDetails` по одному `key`, а не по `(key, value)`;
- mapping не знает `optional`, `deadlineExceeded`, `sgtinIntroduced`, `sgtinSoldB2B` и текущие
  отрицательные решения;
- `wildberries_fbs_client.py` сохраняет только `key/value/decision` и продолжает legacy fallback;
- тесты покрывают одиночный synthetic `filled`/`accepted`, но не официальный текущий enum и не
  несколько `sgtin`.

Ни целевые тесты, ни sandbox, ни production, ни deployed SHA в S04 не проверялись. BLG-I01 сейчас
`WAITING` на S03 с открытым `BLK-RESEARCH-001`; BLG-I02 находится на S04. Поэтому их выводы нельзя
считать завершёнными зависимостями BLG-I09.

## Условие снятия hold

S04 можно повторить после появления amended S03/addendum, который:

1. фиксирует текущую версию schema и полный enum `decision` с тремя отдельными осями: наличие,
   результат проверки, допустимость доставки;
2. доказывает cardinality `metaDetails` для нескольких `sgtin` версионным источником или
   проверенным fixture без live/prod вызова;
3. задаёт multiset-first сравнение, null/sentinel semantics и запрет representation-based repair;
4. разделяет текущую и исторически недоказуемую дивергенцию;
5. исправляет правило rate limit на все `4XX` и закрепляет read-only snapshot как единственный
   разрешённый первый проход;
6. привязывает наблюдения к exact SHA и явно маркирует test/deploy/live состояния как непроверенные.
