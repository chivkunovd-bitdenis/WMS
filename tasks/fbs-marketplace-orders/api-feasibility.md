# Реализуемость FBS через WB API — разбор (стадия 1, углубление)

> Источник знаний: WB Marketplace API v3 (host `https://marketplace-api.wildberries.ru`), плюс скачанные
> инструкции в `wb-docs/`. Конкретные пути/параметры — по моему знанию API; **финальную сверку с живой
> докой `dev.wildberries.ru` делаю, когда сбросится лимит WebFetch (после 21:20 МСК), это дёшево.**
> Уверенность в самом факте наличия методов — высокая; в точных именах полей — средняя (сверить).

## Короткий вывод
**Да — весь WB-овский цикл FBS делается по API.** Это снимает нашу прошлую развилку «кто создаёт
отгрузку»: нам НЕ нужно, чтобы человек руками работал в кабинете WB — наша WMS может вести всё сама.
Единственное, чего у WB нет в API, — это **упаковка** (её у WB нет как отдельного шага вообще); упаковку
закрываем нашим существующим модулем «задание на упаковку».

## Ответы на твои 4 вопроса

### 1. Стикеры на товар (стикер заказа) — по API? — ДА
`POST /api/v3/orders/stickers?type={png|svg|zplv|zplh}&width=58&height=40`, тело — список `orders[]`.
Возвращает готовые стикеры заказов (тот самый уникальный код на каждую единицу). Тянем и печатаем у себя
(конструктор печати / ТСД). Ничего «выдумывать» не нужно — берём готовое от WB.

### 2. КИЗ (Честный Знак) на товар — передавать по API? — ДА
`PUT /api/v3/orders/{orderId}/meta/sgtin` — добавить КИЗ к заказу (аналогично `/meta/uin`, `/meta/imei`,
`/meta/gtin`; `GET /api/v3/orders/{orderId}/meta` — прочитать; `DELETE …/meta?key=…` — убрать).
После добавления WB сам гоняет проверку через «Честный Знак»; обязательную маркировку надо внести и
провести ДО «передать в доставку». У нас уже есть модуль ЧЗ — из него пушим КИЗ в WB per-order.

### 3. Наполнять отгрузку товаром и передавать дальше — по API? — ДА (полный цикл)
- `POST /api/v3/supplies` — создать поставку (отгрузку).
- `PATCH /api/v3/supplies/{supplyId}/orders/{orderId}` — добавить заказ в поставку (наполнение).
- `GET /api/v3/supplies/{supplyId}/orders` — что в поставке.
- `PATCH /api/v3/supplies/{supplyId}/deliver` — передать в доставку (закрыть отгрузку).
- `GET /api/v3/supplies/{supplyId}/barcode?type=…` — QR-код поставки (для приёмки на складе/СЦ).
- `DELETE /api/v3/supplies/{supplyId}` — удалить пустую.
Плюс входящие заказы: `GET /api/v3/orders/new` (новые сборочные задания), `GET /api/v3/orders`
(с пагинацией), `PATCH /api/v3/orders/{orderId}/cancel` (отмена), `POST /api/v3/orders/status` (статусы).

### 4. Этикетки коробов — по API? — ЧАСТИЧНО, и тут важный нюанс
У WB «короб» в API = **грузоместо (trbx)** и существует **только для потока в ПВЗ**:
- `POST /api/v3/supplies/{supplyId}/trbx` — создать грузоместа (кол-во);
- `PATCH …/trbx/{trbxId}` — положить заказы в грузоместо;
- `POST /api/v3/supplies/{supplyId}/trbx/stickers?type=…` — **QR-коды грузомест (этикетки коробов)** — тянем и печатаем.
Для потока **на склад/СЦ** WB грузоместа не требует, и этикеток коробов там нет — приёмка идёт по
QR поставки + стикерам заказов.
**Вывод по упаковке:** наш модуль упаковки (короба/печать/этикетки) стыкуется так:
- **ПВЗ:** наш короб = WB-грузоместо (trbx). Создаём trbx по API и печатаем **WB-шный QR грузоместа**
  (иначе в ПВЗ не примут). Наши внутренние этикетки — сверху, для своей логистики.
- **Склад/СЦ:** упаковка чисто наша, WB нужен только QR поставки + стикеры заказов. Наши этикетки коробов
  — для внутреннего учёта, WB их не касается.

## Что ещё есть в API (пригодится)
- Склады продавца: `GET/POST/PUT/DELETE /api/v3/warehouses`, зоны/офисы `GET /api/v3/offices`, пропуска `/api/v3/passes`.
- Остатки: `PUT /api/v3/stocks/{warehouseId}` (обновить), `POST …/stocks/{warehouseId}` (прочитать).
- Токен: нужна категория **«Маркетплейс»** (проверить, есть ли она у `supplies_token`, или завести поле `marketplace_token`).

## Чего в API НЕТ / что закрываем сами
- **Упаковки** как шага — нет у WB вовсе → наш `packaging_task` (короба, печать, этикетки).
- **Лист подбора** — это UI-фича кабинета WB; у нас будет свой (данные строим из состава поставки).

## Что осталось проверить (дёшево, после сброса лимита)
1. Точные имена путей/полей v3 по `dev.wildberries.ru` (особенно `meta/sgtin`, `trbx/stickers`, `deliver`).
2. Новые заказы — только поллинг `GET /orders/new`, или есть вебхук/уведомления FBS.
3. Лимиты запросов на эндпоинт (влияет на частоту автоопроса).
4. Категория токена «Маркетплейс» на живом ключе селлера.

## Мульти-селлерность (наше главное отличие — но оно уже заложено)
Каждый селлер фулфилмента = свой WB-токен (`seller_wildberries_credentials`) → свой склад продавца
(officeId) → свои заказы/поставки. В моделях уже есть `seller_id`; автоопрос и все вызовы API идут
per-seller. Отдельной большой работы под мульти-селлер не требуется — переиспользуем существующую изоляцию.
