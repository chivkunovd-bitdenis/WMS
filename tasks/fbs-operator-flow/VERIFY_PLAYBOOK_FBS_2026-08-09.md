# Как проверять ФБС: что уже проверено и как проверять дальше

Составлено 09.08.2026 по итогам живого прогона против кабинета Denmarcs.
Документ отвечает на два вопроса: **чем именно доказано, что работает**, и **что делать дальше, по шагам**.

| Что | Значение |
|---|---|
| Стенд, фронт | `https://web-production-9e7c1.up.railway.app` |
| Стенд, бэкенд | `https://wms-production-780c.up.railway.app` |
| Вход на стенд | `<WMS_STAGING_ADMIN_EMAIL>` / `<WMS_STAGING_ADMIN_PASSWORD>` |
| Селлер Denmarcs | `53692f4a-bae9-4141-b373-7fc093675ba7` |
| Склад WB | `1155120` («Дом - Дрожжино»), привязан к складу WMS `086ad3c2-176c-46b9-bfa5-e48ca79b40c4` |
| Резинки пружинки глянцевые (3 шт) | товар `11a6cbf1-2166-42f5-a29e-6d6f61cb5a79`, артикул `wb6n9771yd`, ШК `2043390974795`, chrtId `543672959` |

| База стенда | `postgresql://postgres:<пароль из railway variables --service Postgres>@reseau.proxy.rlwy.net:39731/railway` |

Ключ WB лежит в маркетплейс-слоте Denmarcs. **Важно:** он вставлен в отдельный слот, а не в контентный,
поэтому карточки продолжают импортироваться старым ключом, а весь ФБС ходит новым.

## Про два ключа — то, на чём всё встало в первый раз

Первый ключ Denmarcs был выпущен с флагом «Только на чтение». Он **читает** нормально: заказы приходят,
`GET /api/v3/warehouses` отдаёт 200. Но любая **запись** возвращает 401 с пояснением
`read-only token scope not allowed for this route`. Записью является не только остаток, но и создание
поставки, грузоместа, передача — то есть с таким ключом операторская цепочка дальше чтения не идёт.

Быстрая проверка ключа перед любым прогоном, две команды:

```bash
curl -s -o /dev/null -w "read: %{http_code}\n" https://marketplace-api.wildberries.ru/api/v3/warehouses -H "Authorization: $TOK"
curl -s -w "\nwrite: %{http_code}\n" -X PUT "https://marketplace-api.wildberries.ru/api/v3/stocks/1155120" -H "Authorization: $TOK" -H 'Content-Type: application/json' -d '{"stocks":[{"sku":"2043390974795","amount":0}]}'
```

Если первая даёт 200, а вторая 401 — ключ read-only, дальше идти бессмысленно, нужен новый.
Обрати внимание: вторая команда ставит остаток **0**, то есть безопасна — она не выставляет товар в продажу.

## Что уже проверено на живом кабинете и чем именно доказано

### 1. Признак «Продажа по ФБС» действительно защищает каталог

**Как проверял:** после деплоя запросил `GET /products/ff-catalog` и посмотрел все 210 карточек Denmarcs.

**Доказательство:** у всех до единой `fbs_stock_sync_enabled = false`. Это и есть главное свойство:
включение синхронизации больше не выгружает в WB весь склад ФФ.

### 2. Фильтр выгрузки берёт только разрешённое

**Как проверял:** включил признак ровно на двух товарах, запустил
`POST /operations/fbs-sellers/{id}/stocks/sync`.

**Доказательство:** ответ `products_targeted: 2` при 210 карточках в каталоге.

### 3. Остаток реально доехал до кабинета, и цифра правильная

**Как проверял:** приёмка 3 штук каждого товара, затем публикация, затем **независимый** запрос
в WB мимо WMS:

```bash
curl -s -X POST "https://marketplace-api.wildberries.ru/api/v3/stocks/1155120" \
  -H "Authorization: $TOK" -H 'Content-Type: application/json' \
  -d '{"skus":["2043390974795","2040318682596"]}'
```

**Доказательство:** WB вернул брюки `amount: 2` и резинки `amount: 0`. Это не ошибка и не совпадение —
цифры ровно те, что должны быть: физически по 3 штуки, но под уже приехавшие ФБС-заказы висят резервы,
и запрос в базу подтвердил их количество — 1 на брюки и 3 на резинки. То есть `3−1=2` и `3−3=0`.
Формула доступного отработала на живых данных.

### 4. Кнопка «Забрать заказы из WB» работает в браузере

**Как проверял:** зашёл на `/app/ff/fbs` под админом и нажал кнопку.

**Доказательство:** зелёная плашка «WB отдал заказов: 18, из них новых: 0. Обновлено статусов: 9».
То есть фронт реально сходил в WB, дождался фоновой задачи и показал результат.

### 5. Приёмка снимает вчерашний блокер

**Как проверял:** провёл приёмку по API: создание заявки → строки → «принято первично» → короб →
сканирование ШК по 3 раза на товар → закрытие короба → завершение приёмки.

**Доказательство:** `GET /operations/inventory-balances/summary` показывает по 3 штуки каждого товара
в ячейке сортировки. До этого `inventory_balances` по ним был пуст, и цепочка упиралась в подбор.

## Дополнено: живой прогон в браузере с рабочим ключом

С ключом, который умеет писать, прошёл в браузере на стенде:

1. **«Забрать заказы из WB»** — зелёная плашка «WB отдал заказов: 18, из них новых: 0.
   Обновлено статусов: 9».
2. **Отбор заказов галочками** — отметил два заказа по резинкам, внизу появилась панель
   «Выбрано заказов: 2».
3. **«Сформировать поставку»** — preflight ответил «Можно создать поставку», склад FBS WB 1155120,
   маршрут «Склад / СЦ».
4. **Поставка создана в кабинете WB: `WB-GI-263104461`.** Это настоящий номер WB, то есть
   запись в кабинет прошла.
5. **Экран «Остатки WB»** показывает склад 1155120 со статусом «Подтверждено», а в детализации —
   `chrtId 372587100: цель 2, подтверждено 2` и `chrtId 543672959: цель 0, подтверждено 0`.
   Ровно то же, что независимо отдаёт сам WB.
6. **Раскладка из сортировки в ячейку** — через раздел «Сортировка», после чего резинки
   перешли из сортировки в ячейку A 1.1, доступно стало 3.

### Важно: склад из автопривязки приходит без ячеек хранения

Склад `FBS WB 1155120`, созданный автопривязкой WB, содержал только зону сортировки.
Подбор такое не принимает и честно пишет: «Сканируйте ячейку хранения, а не зону сортировки».
Пришлось создать ячейку `A 1.1` вручную. **Для боевого запуска у каждого склада ФБС должны быть
заведены ячейки хранения**, иначе цепочка встанет на подборе. Это организационный шаг, не баг.

### ЦЕПОЧКА ПРОЙДЕНА ПОЛНОСТЬЮ ДО ПЕРЕДАЧИ

Поставка `WB-GI-263104461`, оба заказа по резинкам, всё кнопками в браузере:

| Шаг | Чем подтверждено |
|---|---|
| Заказы из WB | «WB отдал заказов: 18, обновлено статусов: 9» |
| Отбор заказов | «Выбрано заказов: 2» |
| Поставка создана в WB | номер `WB-GI-263104461` от самого WB |
| Подбор | вкладка «Подбор ✓», снятие 2 шт из ячейки A 1.1 |
| Упаковка | «упаковано 2 из 2», статус поставки `packed` в базе |
| Печать стикеров WB | `order-print-tape → 200`, два PNG из WB, `applied → 200`, «Напечатано 2 из 2» |
| Короб | «Распределено 2 из 2 шт · осталось 0», Короб 1 · 2 шт |
| Прогресс поставки | «2 из 2 подготовлено к отгрузке» |

**«Передать в WB» не нажата намеренно** — единственный необратимый шаг, оставлен владельцу.
Кнопка активна и доступна.

Важная деталь про гейт: вкладка «Короба» заблокирована, пока не напечатаны стикеры.
Пока «Напечатано 0 из 2» — короба серые. Это не баг, а защита: нельзя класть в короб
непромаркированный заказ. Первый раз я на это наткнулся и решил, что печать не работает.

Про ЧЗ: у резинок и брюк маркировка не требуется, поэтому диалог называется «Печать ШК ВБ»
без ЧЗ. Ветку Честного знака на этих товарах проверить нельзя — нужен товар с
`requires_honest_sign = true`.

## Что НЕ проверено и почему — читать обязательно

### Операторская цепочка в браузере дальше выбора заказов

Не проверена. Я не смог отметить чекбоксы заказов через браузерную автоматизацию: клики и пробел
не переключают их. При этом я проверил, что это **не дефект продукта**: у `input` на месте
React-обработчик `onChange`, элемент не `disabled`, hit-test показывает, что клик попадает именно
в него, ошибок в консоли нет, а кнопки на той же странице кликаются нормально.

Вывод: почти наверняка ограничение моего инструмента на MUI-чекбоксах (у них скрытый `input`
с нулевой прозрачностью). **Проверять это должен человек руками или Playwright.**

Не считай это багом, пока не воспроизведёшь руками.

### Публикация нуля при выключении признака

Логика написана и покрыта юнит-тестом, но на живом кабинете не проверялась.
Проверять так: выключить признак у брюк, дождаться публикации, запросить остатки у WB —
должен прийти `amount: 0`, а следующая синхронизация не должна больше трогать эту позицию.

### Автопубликация после движения товара

Покрыта тестами, на живом кабинете не проверялась. Проверять так: списать или переместить
одну штуку брюк и убедиться, что цифра в WB изменилась без ручного нажатия кнопки.
Учти: на стенде Railway **нет Celery-воркера**, публикация уходит фоновой задачей в процессе API.
На боевом сервере воркер есть — там же и надо проверять по-настоящему.

## Пошаговый сценарий, который осталось пройти

Делать под админом на стенде, в браузере, руками.

1. `/app/ff/fbs` → вкладка «Новые» → поиск `wb6n9771yd`.
2. Отметить 1–2 заказа чекбоксами → внизу появится панель выбора → «Сформировать поставку».
3. В карточке поставки: «Состав» → «Подбор» — подобрать позиции.
4. «Упаковка и маркировка» — «Печать ЧЗ и ШК» по каждому заказу, затем «Всё упаковано».
   Ожидаемо появляется надпись «Упаковка завершена.».
5. «Подготовка к сдаче» — создать физический короб, разложить заказы, распечатать QR грузоместа.
6. **«Передать в WB» не нажимать.** Это единственный необратимый шаг, и он оставлен владельцу.

Если на шаге 2 чекбоксы не отмечаются руками — вот тогда это баг, и его надо чинить.

## Как проверять кабинет селлера

Переключатели «Продажа по ФБС» живут в портале селлера (`/seller/`), а не в портале ФФ.
Нужна учётка селлера Denmarcs. Проверять: включить переключатель на одном товаре, убедиться,
что появилось поле лимита и подпись с фактической цифрой из кабинета; выставить лимит меньше
остатка и убедиться, что в WB уехал лимит, а не полный остаток.

## Команды, которые пригодятся

```bash
# токен стенда
curl -s -X POST https://wms-production-780c.up.railway.app/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"<WMS_STAGING_ADMIN_EMAIL>","password":"<WMS_STAGING_ADMIN_PASSWORD>"}'

# состояние выгрузки по складу
curl -s "https://wms-production-780c.up.railway.app/operations/fbs-sellers/53692f4a-bae9-4141-b373-7fc093675ba7/stocks/sync-status?wb_warehouse_id=1155120" -H "Authorization: Bearer $T"

# ручная публикация остатков
curl -s -X POST "https://wms-production-780c.up.railway.app/operations/fbs-sellers/53692f4a-bae9-4141-b373-7fc093675ba7/stocks/sync" -H "Authorization: Bearer $T" -H 'Content-Type: application/json' -d '{}'
```

## Две заслонки, о которых легко забыть

Чтобы остаток уехал в WB, должны быть включены **обе**:

1. `stock_sync_enabled` на привязке склада (`fbs_warehouse_bindings`) — это разрешение ФФ на канал.
   У Denmarcs он был выключен, и выгрузка молча не шла. Включается в интерфейсе ФФ, экран «Остатки WB».
2. `fbs_stock_sync_enabled` на товаре — это выбор селлера.

Если выгрузка возвращает `bindings_processed: 0` — дело в первой. Если `products_targeted: 0` — во второй.
