# FBS U2U test matrix

## Назначение и границы

Эта матрица описывает сквозные пользовательские сценарии FBS: от появления заказа в рабочем
списке до подтверждённой передачи поставки Wildberries. Под U2U здесь понимается полный путь
пользователя через UI с проверкой серверного состояния после каждого необратимого действия.

Матрица относится только к FBS. Она не проверяет FBO, не допускает общий остаток FBS/FBO и не
использует FBO-заказы, FBO-склады или FBO-резервы как тестовые данные.

Для каждого сценария указано, кто его выполняет:

- **seller** — пользователь конкретного продавца. FBS не входит в его интерфейс и API: он не
  видит даже собственные FBS-заказы и получает `403` при прямом вызове FBS-ручки;
- **operator** — `fulfillment_staff` с явным разрешением **«Упаковка»** (`packaging`); собирает,
  маркирует, печатает и передаёт доступные ему поставки;
- **admin** — администратор; настраивает связи продавца и складов и может диагностировать
  ошибки, но ограничения доступа других ролей не ослабляет.

## Статус источников на момент последней проверки

Матрица повторно сверена с материализованным кодом backend, frontend, WB-эмулятором и выделенным
fullstack Playwright-сценарием. Формулировки ниже являются требованиями к выпуску: наличие строки
в матрице само по себе не означает, что сценарий уже автоматизирован или физически проверен.

## Базовый набор данных

Перед прогоном создать данные через тестовые фабрики или публичные setup-API, не через прямую
правку production-таблиц.

- `seller-a`: активный продавец, токен WB валиден; пользователи `seller-a-user`, `operator-a` и
  `admin-a`.
- `seller-b`: отдельный продавец с отдельным токеном; пользователь `seller-b-user`.
- `wms-sc-a` связан с WB-складом `wb-sc-a`, схема передачи — СЦ.
- `wms-pvz-a` связан с WB-складом `wb-pvz-a`, схема передачи — ПВЗ.
- `sku-plain` не требует маркировки; `sku-marked` требует КИЗ (код идентификации маркированного
  товара); для обоих есть доступный FBS-остаток.
- Заказы `A-101` и `A-102`: `seller-a`, `wms-sc-a`, одна схема и совместимый тип покупателя,
  `createdAt` соответственно `2026-08-05T06:00:00Z` и `2026-08-05T06:05:00Z`.
- Заказ `A-103`: те же продавец и склад, но другой совместимый товар; `createdAt`
  `2026-08-05T06:10:00Z`.
- Заказ `A-201`: `seller-a`, `wms-pvz-a`; `createdAt` `2026-08-05T06:15:00Z`.
- Заказ `B-101`: `seller-b`; время совпадает с `A-102`, чтобы проверить изоляцию продавцов, а
  не случайную группировку по времени.
- Управляемый WB-эмулятор умеет один раз вернуть timeout/5xx после фактического создания
  ресурса, частичный ответ по стикерам, испорченный print asset и задержку обновления статуса.

Все проверки повторного запроса должны сопоставлять серверные идентификаторы до и после retry.
Совпадение только количества строк недостаточно: оно не ловит замену или повторное создание.

## Обязательные проверки после каждого сценария

Автоматизированный тест считается пройденным не по зелёному toast-сообщению, а только если
одновременно подтверждены:

1. ожидаемое состояние видно после полного refresh и нового входа пользователя;
2. server-side объект имеет ожидаемый seller, WMS warehouse, WB warehouse, route и order IDs;
3. число внешних вызовов WB соответствует сценарию, а retry не создаёт второй платный или
   необратимый вызов без необходимости;
4. резерв и доступный FBS-остаток изменились ровно один раз; FBO-состояние не изменилось;
5. нет дубликатов активной поставки, order membership, маркировки, стикера, грузового места или
   подтверждения доставки;
6. ошибка после refresh остаётся диагностируемой по `code`, `context` и `retryable`, но UI не
   показывает токен продавца или другие секреты.

## Уровни доказательства

- **Локальный автоматический gate:** Playwright + настоящий auth/backend на SQLite, управляемый
  WB contract mock/emulator, плюс серверные assertions по точным ID и счётчикам вызовов.
- **Интеграционный gate:** PostgreSQL, актуальные миграции, worker/Celery и тот же набор fault
  injection-сценариев. Этот уровень нельзя считать доказанным существующим supervisor handoff.
- **Ручной release smoke:** реальный ТСД/сканер, принтер, физические стикеры и QR, затем отдельный
  явно разрешённый прогон против тестового/живого WB. Без него нельзя утверждать, что физическая
  печать, сканирование и передача проверены до конца.
