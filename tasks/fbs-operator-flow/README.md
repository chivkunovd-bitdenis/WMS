## 1. Что строим

Нужен один последовательный путь оператора:

1. WMS получает заказы нескольких селлеров из WB.
2. Оператор видит реальный товар, склад, ячейку, доступный остаток, требования к маркировке и дедлайн.
3. До сетевого вызова WMS проверяет совместимость выбранных заказов.
4. WMS атомарно создаёт поставку WB и добавляет в неё совместимые заказы.
5. Оператор подбирает товар сканированием ячейки и товара. Прогресс хранится на сервере.
6. Товар упаковывается через существующее `PackagingTask`. Второй FBS-модуль упаковки запрещён.
7. КИЗ / IMEI / УИН / GTIN связываются с конкретной физической единицей и конкретным заказом WB.
8. Для каждой индивидуальной упаковки получается и печатается стикер заказа WB 58×40 мм.
9. Для ПВЗ оператор указывает число транспортировочных коробов, получает QR каждого грузоместа WB и наносит по одному QR на короб.
10. Для склада / СЦ после передачи в доставку получается QR всей поставки WB.
11. Локальный статус меняется только после подтверждения WB; дальнейшие статусы регулярно синхронизируются.

## 2. Граница модулей

### FBS владеет

- импортом и внешними статусами заказов WB;
- проверкой совместимости и составом поставки WB;
- обязательными / необязательными метаданными заказа WB;
- стикерами заказов WB;
- грузоместами и QR WB;
- передачей поставки в доставку;
- журналом сетевых операций WB.

### Существующая WMS-упаковка владеет

- физическим товаром и ячейкой;
- подбором в зону сортировки;
- `PackagingTask` и его строками;
- переводом остатка из `quantity_unpacked` в `quantity_packed`;
- Честным знаком из пула конкретного селлера;
- фактом индивидуальной упаковки;
- списанием остатка после завершения упаковки.

### Запрещённая архитектура

- отдельная упрощённая FBS-упаковка;
- `localStorage` как источник рабочего статуса;
- ручное распределение заказов по грузоместам WB;
- обязательная связь грузоместа WB с внутренним коробом `WHB-*`;
- успешный локальный статус до подтверждения WB;
- файловый путь, выдаваемый фронту как будто это base64-картинка.

## 3. Термины интерфейса

- `FbsOrder` в UI — **Заказ WB**.
- `FbsSupply` в UI — **Поставка WB**.
- `PackagingTask` — **Задание на упаковку WMS**.
- `FbsTrbx` — **Грузоместо WB** или **транспортировочный короб**.
- `PackagingBox WHB-*` — **внутренний короб WMS**.
- Нельзя писать просто «стикер». Использовать точный тип: ШК товара, КИЗ, стикер заказа WB, QR грузоместа WB, QR поставки WB, внутренний ШК короба WMS.

## 4. Подтверждённые правила WB на 03.08.2026

Перед реализацией Cursor повторно сверяет `dev.wildberries.ru`, потому что WB меняет контракты.

- Стикеры заказов: `POST /api/v3/orders/stickers`, максимум 100 заказов в одном запросе, поддерживается PNG 58×40.
- Метаданные: обязательные и необязательные типы приходят в `requiredMeta` / `optionalMeta`; текущее состояние читается через `POST /api/marketplace/v3/orders/meta`.
- Добавление заказов в поставку: актуальный batch-контракт `PATCH /api/marketplace/v3/supplies/{supplyId}/orders`, до 100 заказов.
- Передача в доставку: `PATCH /api/v3/supplies/{supplyId}/deliver`; 409 с `MetaValidationFail` является бизнес-отказом, а не техническим успехом.
- Грузоместа: создать `POST /api/v3/supplies/{supplyId}/trbx`, получить список `GET` на том же пути, получить QR `POST .../trbx/stickers`.
- Для FBS не требуется связывать конкретный заказ с конкретным грузоместом. Достаточно количества грузомест.
- В ПВЗ: сторона ≤ 60 см, сумма сторон ≤ 140 см, вес ≤ 5 кг, общий объём ≤ 1 м³, в одном грузоместе больше одного заказа.

## 5. Что считать готовым

Готовность — не сборка отдельных модулей, а сценарии из `TEST_CASES.md` через настоящий frontend → backend → PostgreSQL → очередь → WB emulator. Совместимость с текущим WB API дополнительно проверяется отдельным smoke на sandbox / тестовом кабинете: эмулятор не доказывает актуальность внешнего контракта.
