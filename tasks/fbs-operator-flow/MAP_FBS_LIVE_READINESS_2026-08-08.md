# Карта готовности ФБС к боевой работе селлеров — 08.08.2026

Что должно сложиться, чтобы селлер подключил свой ключ и начал реально отгружать заказы.

## Как устроен обмен (важно понимать до правок)

**Остаток считает WMS, а не кабинет.** `fbs_stock_availability_service` берёт `inventory_balances`
(то, что физически принято приёмкой на склад ФФ), вычитает резервы `FbsOrderReservation` под другие
ФБС-заказы и исключает ячейку сортировки. Остаток ФБО/FBW из каталога здесь не участвует.

**Остаток уезжает из WMS в WB, а не наоборот.** `put_marketplace_stocks` делает `PUT /api/v3/stocks/{warehouseId}`.
То есть кабинет получает цифру от нас. Если товар не принят на склад ФФ — в кабинет уедет ноль,
и заказы по нему собирать нечем.

**Заказы приходят из WB в WMS** через `GET /api/v3/orders/new` + `POST /api/marketplace/v3/orders/meta`.

**Один ключ на всё.** После `7a96fc2` действует `token = marketplace_token_encrypted or content_token_encrypted`,
и при сохранении контентного токена он копируется в маркетплейсный слот.

## Решения по остаткам и статусам (обсуждение 08.08.2026, к реализации)

### Как считается доступное под ФБС

```
доступно для ФБС = max(0, хранение + сортировка − резерв под отгрузку на МП − резерв под другие ФБС-заказы)
```

Склад **один**, отдельного «ФБС-склада» нет. Резерв под ФБО/FBW вычитается из того же пула,
поэтому «запланировал 1000 на ФБО из 1500» автоматически оставляет 500 под ФБС.
Ячейка сортировки **входит** в доступное.

### P0-11. Публикация остатка после каждого движения

`PUT /api/v3/stocks/{warehouseId}` — перезапись итогового количества по штрихкоду.
Реализовано в `fbs_stock_sync_service.sync_binding_stocks`, но дёргается **только вручную**
через `POST /operations/fbs-sellers/{id}/stocks/sync`. Автовызова после приёмки, отгрузки,
списания и резерва под ФБС-заказ нет — Кодекс отвязал публикацию от опроса заказов.
Следствие: списали товар — в кабинете висит старая цифра, WB продолжает продавать.
*Нужно: ставить публикацию в очередь после каждого события, меняющего остаток,
плюс фоновая сверка раз в несколько минут как страховка. Ручную кнопку оставить.*

### P0-12. Признак участия в ФБС + лимит на товар + предпросмотр

**Нельзя включать синхронизацию «в лоб»** — иначе весь склад ФФ мгновенно уедет в продажу по ФБС,
включая товар под будущие ФБО-отгрузки и всё, что продавать этим каналом не собирались.

Правило обратное: публикуем **только то, что явно разрешено**.
- Признак «участвует в ФБС» на товаре в связке с привязкой склада, по умолчанию **выключен**.
  Пока не включён — про товар в WB не пишем ничего, ни числа, ни нуля.
- Лимит на товар: публикуем `min(доступно, лимит)`. Закрывает и сценарий «оставить 500
  на подстраховку», и «выставить только часть». Одна механика вместо двух фич.
- Ноль публикуем только для товаров, которые ведём мы. Чужие позиции селлера на том же складе WB
  не трогаем — перезапись идёт по штрихкоду.
- Экран предпросмотра перед первой публикацией: товар, остаток, лимит, итоговая цифра.
  Публикуем только после подтверждения.

*Проверить перед работой: возможно, признак/лимит уже частично есть в модели товара или в привязке склада.*

### P0-15. Единый ключ — не заставлять вводить повторно

Селлер вводит ключ **один раз**. Все категории прав в нём уже есть, значит этот же ключ
используется и для маркетплейса, и для контента, и для поставок. Никаких отдельных полей
под каждый токен быть не должно — поле маркетплейс-токена из P0-1 нужно только как
аварийная перезапись, а основной путь — один ключ на всё (`7a96fc2` это уже умеет).

### Границы ответственности по складам

У селлера может быть несколько складов ФБС, и не все обслуживает наш ФФ. Остаток в WB задаётся
**на конкретный склад** (`PUT /api/v3/stocks/{warehouseId}`), у нас этому соответствует
`fbs_warehouse_bindings`. Публикуем только в привязанные к нашим складам ФФ; чужие склады селлера
не трогаем вообще. WB сам суммирует остатки по складам и маршрутизирует заказ туда, где товар есть.

Брать за истину цифру, которую селлер проставил в кабинете руками, **нельзя**: товар физически
у нас, движение знаем мы, а `PUT /stocks` — перезапись, двух хозяев у одной цифры быть не может.

## Порядок запуска для одного селлера (целевой сценарий)

1. Селлер создаёт в кабинете WB токен с категориями **«Контент» и «Маркетплейс»**.
2. Вставляет его в WMS — в поле контентного токена; он же уезжает в маркетплейсный слот.
3. WMS импортирует карточки (уже работает) и автоматически привязывает склад WB к складу WMS (уже работает).
4. Автоопрос притягивает новые заказы каждые `fbs_poll_interval_sec` — **нужен пункт 2 из P0**.
5. Товар физически принимается на склад ФФ через «Приёмку», остаток публикуется в WB.
6. Оператор собирает поставку, подбирает, упаковывает, печатает ЧЗ и ШК, раскладывает по коробам,
   печатает QR, передаёт в WB.
