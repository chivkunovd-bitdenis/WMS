## Находки (по серьёзности)

### 🔴 1. КРИТИЧНО — отмена заказа вешает отгрузку в ASSEMBLING навсегда
`fbs_cancellation_service.py`: `NON_CANCELLABLE_STATUSES` = {in_delivery, done, sorted, defect} — **ASSEMBLING/PACKED/IN_SUPPLY не защищены**. Заказ в отгрузке можно отменить (вручную `PATCH /fbs-orders/{id}/cancel` ИЛИ автоматически — WB присылает `cancel` в статус-синке `_apply_wb_status_to_order`). При этом `PackagingTaskLine.qty_total` (проставлен в `create_packaging_task_for_supply`, `fbs_packaging_integration_service.py:143`) **не уменьшается**, `is_task_complete()` никогда не станет true → `try_promote_fbs_supply_if_ready` не пропустит дальше → отгрузка навсегда в ASSEMBLING. Пути «убрать заказ из отгрузки» в коде **нет**.
**Фикс (уточнить желаемое поведение у человека — см. ⬇):** при отмене заказа, находящегося в отгрузке, — убрать его из отгрузки (`supply_id=None`, снять с trbx если ПВЗ) и **скорректировать/убрать строку упаковки** (`qty_total`), затем перепроверить промоушен; если отгрузка опустела — обработать (draft/удалить). Добавить сервисный путь «remove order from supply».
**Тесты:** отмена заказа в ASSEMBLING → отгрузка не застревает, упаковка досчитывается; отмена последнего заказа → отгрузка корректна.

### 🟠 2. ВЫСОКАЯ — гейт «КИЗ проверен WB» отсутствует вообще (правильное место — DELIVER)
По инструкции WB (`wb-docs/04-labeling/verify-product-identifiers.md`): передать поставку в доставку можно **только после того, как обязательная маркировка прошла проверку** WB («Проверено»). В коде `check_status` **не проверяется нигде** — сверено грепом: ни в `fbs_shipment_service.deliver_supply` (проверяет только `orders_not_ready` по статусам и `supply_has_cancelled_orders`), ни в `_supply_requires_marking` (смотрит лишь наличие КИЗ). Значит можно передать в доставку поставку с непроверенным/ошибочным КИЗ → WB развернёт на приёмке.
**Фикс:** гейт на `deliver_supply` — требовать `check_status=ok` по всей **обязательной** маркировке (не «наличие», а «проверено»); статусы `error`/`Неподходящий формат` блокируют deliver с внятной ошибкой. Проверку `sync_order_marking_statuses` дёргать **автоматически** (в автопросе), а не только вручную по API. Промоушен в PACKED (наличие КИЗ) можно оставить как есть — это внутренний этап сборки, гейт именно на выходе (deliver).

### 🟡 3. СРЕДНЯЯ — оверселл резерва при overlap автопроса (нет FOR UPDATE)
`_try_reserve_order` / `available_qty_for_fbs_reserve` считают остаток обычным `SELECT SUM` без `with_for_update()` (в `marketplace_unload_service` в аналогичных местах блокировка ЕСТЬ). При overlap beat (интервал по умолч. 180с, мин. 60с; цикл может быть дольше) два параллельных резерва одного товара оба увидят «остаток есть» → оверселл (uniq-констрейнт per-order, не per-product, не спасает). Плюс вставка резерва для СУЩЕСТВУЮЩЕГО заказа не обёрнута в `try/except IntegrityError` (в ветке нового заказа — обёрнута) → непойманный `IntegrityError` откатит весь тик.
**Фикс:** `with_for_update()` на остатке/резервах при резервировании ИЛИ сериализовать beat (lock/не допускать overlap); обернуть insert резерва для существующего заказа в `IntegrityError`-ретрай.

### 🟡 4. СРЕДНЯЯ — «хвост» >500 заказов навсегда выпадает из статус-синка
`sync_order_statuses`: `LIMIT 500` по `created_at_wb desc`, без пагинации; `SORTED` **не** в `TERMINAL_FBS_STATUSES`, поэтому отсортированные заказы копятся в выборке. При >500 нетерминальных самые старые перестают синкаться навсегда → их финальный статус (sold/cancel) локально не узнают, **резерв не освобождается**.
**Фикс:** пагинация/курсор по всем нетерминальным ИЛИ корректно исключать «завершённые по факту» (в т.ч. sorted, если он финален для нас); гарантировать, что каждый нетерминальный заказ рано или поздно синкается.

### ⚪ 5. НИЗКАЯ (системное) — orphan: запись в WB до локального commit
`create_supply`/`add_order_to_supply`/`put_marketplace_order_meta`: side-effect в WB идёт до `session.commit()` (коммит — в API-хендлере). При сбое между WB-вызовом и commit — WB считает сделанным, локально откат → рассинхрон/дубль. Паттерн системный (не только FBS). Низкий приоритет, но зафиксировать.
