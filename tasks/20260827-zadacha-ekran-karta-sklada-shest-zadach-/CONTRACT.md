# Контракт экрана «Карта склада»

Дата: 28.08.2026. Основание — картинка, принятая владельцем 28.08 на макете
`/warehouse-map.html`. Здесь ровно то, что стоит на экране, и ничего сверх.

Читать так: **фронт уже написан и переписывать его не нужно.** Это не картинка,
а работающий экран на заглушках — вся вёрстка, перетаскивание, сканер, фильтры,
диалоги и журнал готовы и лежат в `frontend/src/screens/ff/warehouse-map/`.
Не хватает единственного: чтобы данные приходили с сервера, а действия туда
уходили. Контракт описывает этот шов.

---

## 0. Одно архитектурное решение, которое нужно принять до кода

Сегодня «сколько чего где лежит» знает `InventoryBalance` — строка на пару
ячейка + товар. Содержимое короба знает другая таблица,
`InboundIntakeBoxLine`, и она привязана к документу приёмки, а не к складу.
То есть на один и тот же физический товар в системе два источника правды.

Экран требует иерархию ячейка → палета → короб → товар и при этом владелец
сказал прямо: «остатки товара должны быть абсолютно синхронны с нашими обычными
остатками товара». Свести это можно двумя способами.

**Вариант А (рекомендую).** У `InventoryBalance` появляются необязательные
ссылки на контейнер: `pallet_id`, `box_id`, `cargo_place_id`. «Где лежит» —
это по-прежнему ячейка, плюс, если товар в контейнере, ещё и контейнер. Тогда
остаток остаётся одной таблицей, которую читают и карта, и отчёты, и
синхронность не надо поддерживать — она устроена так по построению.
`InboundIntakeBoxLine` остаётся тем, чем он и является: составом короба **в
документе приёмки**, историческим фактом, а не текущим положением дел.

**Вариант Б.** Отдельные таблицы содержимого контейнеров. Тогда остаток и
содержимое расходятся при первой же ошибке, и появляется работа по сверке,
которой сейчас нет.

Пока владелец не выбрал, эндпоинты ниже описаны так, что их форма от выбора не
зависит. Но код писать нельзя: при варианте Б половина запросов будет другой.

## 1. Чего нет в данных и что придётся завести

| Что | Сейчас | Нужно |
|---|---|---|
| Палета | модели нет вообще | таблица палет: код, штрихкод, склад, ячейка (может быть пустой), дата расформирования |
| Товар внутри грузоместа | у `InboundIntakeCargoPlace` нет строк | либо строки, либо вариант А выше |
| Категория товара | поля нет | поле у товара, наполняется предметом карточки WB (`subjectName`) |
| Кто выполнил перемещение | у `InventoryMovement` нет автора | задача Б-1, уже в работе |

Пока палеты нет, экран честно покажет карту без уровня палет — иерархия
схлопнется до ячейка → короб → товар и ничего не сломается. Это нормальный
промежуточный результат, а не полумера.

## 2. Что сервер обязан отдавать

### 2.1 Карта склада

`GET /warehouse-map?warehouse_id=<uuid>`

```json
{
  "sellers": ["ИП Горячкина", "ООО Ситипак"],
  "categories": ["Футболки", "Кроссовки"],
  "cells": [
    {
      "id": "uuid",
      "code": "А 1.1",
      "barcode": "2000000000114",
      "qty": 49,
      "children": [ "<узел>", "..." ]
    }
  ],
  "unassigned": [ "<узел>", "..." ]
}
```

Узел-контейнер:

```json
{
  "kind": "pallet | box | cargo_place",
  "id": "uuid",
  "code": "П-000123",
  "barcode": "2100000001236",
  "seller_name": "ИП Горячкина",
  "qty": 32,
  "children": [ "<узел>", "..." ]
}
```

Узел-товар:

```json
{
  "kind": "product",
  "id": "uuid строки остатка",
  "product_id": "uuid",
  "name": "Футболка хлопок белая, M",
  "seller_name": "ИП Горячкина",
  "category": "Футболки",
  "barcode": "4680123456789",
  "photo_url": "https://...",
  "qty": 24
}
```

Правила, которые обязан соблюдать сервер, а не фронт:

- **`qty` контейнера и ячейки — сумма всего внутри**, вместе с вложенными
  коробами. Фронт это число не пересчитывает, он его показывает.
- **`seller_name` контейнера заполняется только когда внутри один селлер.**
  Иначе `null`. Смешанный короб с чьим-то одним именем врал бы прямо в строке.
- **`code` — человеческий номер** («П-000123», «КР-000451»), не идентификатор
  из базы. Сырых кодов на экране нет и не будет.
- **`unassigned`** — всё, что принято, но не лежит ни на одной ячейке: и
  никогда не разложенное, и снятое с ячеек. Один список, два источника.
- Глубже трёх уровней вложенности не бывает: палета → короб/грузоместо → товар.
- Пустой короб приходит с `children: []` и `qty: 0`. Он **не исчезает**: экран
  сам подпишет его «Пустой».
- `photo_url` может быть `null` — экран покажет силуэт, как везде в системе.

### 2.2 Журнал перемещений

`GET /warehouse-map/journal?warehouse_id=<uuid>&page=<0..>&size=<8>`

```json
{
  "total": 152,
  "entries": [
    {
      "id": "uuid",
      "at": "2026-08-27T06:12:00Z",
      "actor_name": "Смирнова Ольга",
      "subject": "Футболка хлопок белая, M",
      "qty": 40,
      "from_label": "Без ячеек",
      "to_label": "Грузоместо ГМ-000318"
    }
  ]
}
```

- `at` — UTC. В московский пояс переводит экран, как везде.
- `subject`, `from_label`, `to_label` — **готовые человеческие подписи**.
  Экран их не собирает: он не знает, что было с сущностью на момент записи.
- `qty` может быть `null` — когда переехал контейнер целиком.

История одной строки — тот же ответ с фильтром:
`GET /warehouse-map/journal?subject_kind=box&subject_id=<uuid>`

### 2.3 Поиск по штрихкоду

Отдельного эндпоинта **не нужно**: экран ищет по уже полученной карте. Это
осознанно — оператор пикает короб десятки раз за смену, и каждый пик не должен
ходить в сеть. Если карта станет слишком большой, чтобы держать её целиком, —
это отдельное решение, и тогда появится `GET /warehouse-map/lookup?barcode=`.

## 3. Что сервер обязан принимать

### 3.1 Перемещение

`POST /warehouse-map/move`

```json
{
  "warehouse_id": "uuid",
  "subject": { "kind": "balance | box | cargo_place | pallet", "id": "uuid" },
  "from":    { "kind": "cell | unassigned | pallet | box | cargo_place", "id": "uuid | null" },
  "to":      { "kind": "cell | unassigned | pallet | box | cargo_place", "id": "uuid | null" },
  "qty": 12
}
```

- `id: null` — только у `unassigned`.
- `qty: null` — переехало целиком; так всегда для контейнеров.
- Ответ — **свежая карта того же склада** в формате 2.1. Экран не собирает
  новое состояние сам: он показал перемещение сразу, не дожидаясь сервера
  (иначе перетаскивание тормозит), а ответом сверяется. Разошлось — экран
  показывает серверную правду и говорит об этом.

Что обязан проверить сервер, потому что фронт этого гарантировать не может:
остаток не ушёл в минус; цель существует и на этом складе; контейнер не кладут
внутрь самого себя; палету не кладут в короб. На каждый отказ — сообщение на
языке склада, без кодов и стектрейсов.

Каждое перемещение пишет **одну** запись в тот же журнал (см. 2.2) с автором.
Отдельного типа события под «смену ячейки после утверждения приёмки» не
заводить — владелец сказал прямо, что механизм один на все перекладывания.

### 3.2 Расформирование палеты

`POST /warehouse-map/pallets/{id}/disband` → свежая карта.

Всё, что было на палете, уезжает в «Без ячеек» и остаётся на складе. Палета
после этого не существует и собрать её заново нельзя — экран об этом
предупреждает до нажатия.

### 3.3 Создание склада и ячейки

Новых эндпоинтов не нужно, экран зовёт существующие в `api/warehouses.py`.
Код ячейки строится тем же `formatLocationCode`, что и сегодня: `{СТЕЛЛАЖ} {сторона}.{позиция}`.

### 3.4 Печать ШК ячейки

Серверу ничего не нужно: печать идёт стандартной модалкой выбора размера
этикетки, той же, что в приёмке и отгрузке.

## 4. Порядок волн

| Волна | Что | Кто | Чем проверяется |
|---|---|---|---|
| 1 | Палета: таблица, ссылка у короба и грузоместа, объединение и расформирование | Кодекс, бэк | pytest на объединение и расформирование; палета видна в базе |
| 2 | Категория товара + наполнение из карточек WB | Кодекс, бэк | у товаров проставлен предмет, фильтр непустой |
| 3 | `GET /warehouse-map` | Кодекс, бэк | тест сверяет форму ответа с этим файлом; суммы сходятся с `InventoryBalance` |
| 4 | `POST /move`, `POST /disband`, журнал с автором | Кодекс, бэк, **после Б-1** | тест на минусовой остаток, на палету в короб, на запись в журнал |
| 5 | Подключение экрана к API вместо заглушек | **я** | живой экран на настоящих данных, показ владельцу |
| 6 | Перенос блока коробов из каталога, снятие старого экрана «Ячейки» | **я** | старый экран убран, ничего не потерялось |

Волны 1–4 фронт **не трогают вообще**: ни одного файла в `frontend/`.
Волна 5 трогает ровно один файл экрана — тот, где заглушка меняется на запрос.

## 5. Границы для исполнителя бэка

Разрешено: `backend/app/models`, `backend/app/services`, `backend/app/api`,
`backend/alembic/versions`, `backend/tests`.

Запрещено: **всё в `frontend/`**. Экран написан, принят владельцем на картинке
и переписыванию не подлежит. Если по контракту чего-то не хватает — это правка
контракта и разговор, а не самостоятельная правка экрана.

Миграции только добавляющие. Все правки таблицы `inbound_intake` из бэклога
(комментарий документа, свободный текст короба, товары в грузоместе, привязка к
палете) идут **одной миграцией**, иначе получим четыре ветки с конфликтующим
`down_revision`.

---

## 6. Чего в этом контракте нет

- **Уплотнения и подсказок «что стоит переложить»** — это набросок
  `/move-lab.html`, он не согласован и в работу не берётся.
- **Как показывать лог отдельным экраном** — журнал живёт внизу карты, вопрос
  про отдельный экран истории остаётся открытым.
- **Ограничения по вместимости ячейки** — на экране их нет, значит и в контракте
  нет. Появятся отдельной задачей.
- **Прав доступа** — экран админский, как и сегодняшние «Ячейки».
