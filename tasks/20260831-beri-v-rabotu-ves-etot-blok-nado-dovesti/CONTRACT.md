# Контракт: сквозная тара — короб, палета, грузоместо живут от приёмки до отгрузки

Решение владельца дословно: «конечно одна. Они в неё кладут, а затем при сортировке ставят,
а при отгрузке ФБО или ФБС списывают из тары. Более того, и то и другое — оно и по палетам,
и по грузоместам».

Экраны: **S-17** «Приёмка на FF», **S-20** «Сортировка», **S-03** «FBS» (вкладка «Подбор»),
**S-12** «Отгрузки». Полоса: **обычная**.

## Что уже построено и работает

Замысел уже записан в коде раскладки объектами:

> Товар лежит в коробе, короб на палете, палета в ячейке. Место товара нигде не хранится —
> оно вычисляется по цепочке держателей. Поэтому нельзя рассинхронизировать «что в коробе»
> и «где короб»: это одно и то же знание, записанное один раз.

На проде уже есть:

| Что | Где |
|---|---|
| поля тары у остатка | `inventory_balances.container_kind` + `container_id` |
| опознание скана тары | `inventory_container_service`: `INB-…` → короб «КР-000366», грузоместо → «ГМ-000012», палета по коду |
| экран «Раскладка объектами» | подключён роутом и встроен в карточку приёмки |
| перенос остатка вместе с тарой | `warehouse_map_service.place_sorting_object` |
| мост «доложить содержимое короба при раскладке» | `inbound_container_putaway_service.putaway_pending_container` |
| снятие из тары при подборе ФБС | `fbs_picking_service` |
| снятие из тары при отгрузке | `marketplace_unload_pick_service`, `marketplace_unload_collect_service` |
| пересчёт с тарой | `inventory_count_service` |

## Как хранится структура «ячейка → палета → короб → товар»

Хранится **не адрес товара, а держатель у каждого объекта** — поэтому рассинхрона
«что в коробе» и «где короб» быть не может, это одна запись.

| Объект | Держатель |
|---|---|
| палета | ячейка (`pallets.storage_location_id`) |
| складской короб | палета (`pallet_id`), иначе ячейка (`storage_location_id`) |
| **короб приёмки** | палета (`pallet_id`), иначе ячейка (`storage_location_id`) |
| грузоместо | палета, иначе ячейка |
| товар | тара у остатка (`container_kind` + `container_id`) |

`warehouse_map_service.get_warehouse_map` собирает из этого дерево, и **короб приёмки
там уже полноправный узел** с подписью «КР-000366», грузоместо — «ГМ-000012».
`get_sorting_objects` разворачивает то же дерево на экран сортировки и умеет
фильтровать по конкретной приёмке (`inbound_request_id`) — «зашёл в приёмку, открыл
сортировку, видишь свои короба».

Есть и подстраховка: если у короба ячейка не проставлена, держатель вычисляется по тому,
в какой ячейке лежит его товар (`balance_location`).

Сегодня дерево вырождается в плоский список, потому что держатели пустые: у коробов
ячейка не заполнена (0 из 180), у остатков тара не заполнена (0 из 970). Как только
приёмка начнёт писать оба поля, дерево соберётся само — правок фронта не требуется.

## Где рвётся — ровно одно звено

`inbound_intake_service.apply_box_putaway` кладёт содержимое короба в ячейку **россыпью**.
Во всём `inbound_intake_service` слова `container_kind` нет ни разу. В момент раскладки
короб как держатель теряется, и цепочка держателей, на которой построен весь замысел,
обрывается на первом же шаге.

Следствие на бою:

```
коробов приёмки           180   из них в ячейке      0
складских коробов         352   из них в ячейке      0
строк остатка             970   из них с тарой       0
событий карты склада        0
палет                       0   грузомест            6
```

## Что должно стать

1. **Приёмка кладёт товар в тару, а не россыпью.** `apply_box_putaway` передаёт в движение
   остатка `container_kind="box"` и `container_id` = id короба приёмки. То же для грузоместа
   (`cargo_place`).
2. **Короб встаёт в ячейку или на палету.** У `inbound_intake_boxes` уже есть поля
   `storage_location_id` и `pallet_id` — их надо заполнять при раскладке.
3. **Подбор показывает короб.** Правок фронта не требуется: `pick-options` уже отдаёт
   `container_path` и подпись источника, сегодня всегда `is_loose = true` только потому,
   что тары в данных нет.
4. **Списание идёт из тары** при ФБС и при отгрузке на маркетплейс — уже умеет, начнёт
   работать само, как только тара появится в остатках.
5. **Палеты и грузоместа** — тот же механизм, те же поля, отдельных сущностей не заводим.

## Что НЕ делаем

- Не заводим новых таблиц и не сливаем `inbound_intake_boxes` с `warehouse_boxes`:
  `inventory_container_service` уже опознаёт обе как `kind="box"`.
- Не трогаем нумерацию: номер выдаётся один раз и не меняется (решение от 28.08).
- Не трогаем короба упаковки ФБС (`FBS-…`) и отгрузки (`WHB-…`) — они рождаются в своих
  процессах и к приёмке отношения не имеют.

## Открытый вопрос к владельцу

`inventory_balances.container_id` — голый uuid **без внешнего ключа**, потому что указывает
на четыре таблицы (складской короб, короб приёмки, палета, грузоместо), а `container_kind`
для первых двух одинаковый — `box`. Пока тары в данных нет, это безобидно; как только
короба приёмки поедут в остатки, два разных объекта окажутся под одним `kind`.
Нужно решение: различать их отдельным значением `kind` или сводить к одной таблице.

## Тесты

- приёмка: раскладка короба в ячейку кладёт остаток **с тарой**, а не россыпью;
- подбор ФБС видит источник «короб КР-000366», а не «Россыпью»;
- снятие при подборе уменьшает остаток именно в этом коробе;
- отгрузка на маркетплейс списывает из тары;
- пустой короб в ячейку не раскладывается (`nothing_to_move`);
- грузоместо ведёт себя как короб.
