Машинная матрица: [`S03-wb-rate-limit-capability-matrix.json`](S03-wb-rate-limit-capability-matrix.json).

## 1. Вывод

Для FBS Wildberries документирует только одиночное удаление метаданных сборочного задания:
`DELETE /api/v3/orders/{orderId}/meta?key=sgtin`. Успех одного элемента — пустой ответ `204`.
Пакетного FBS endpoint для удаления нескольких заказов в актуальной официальной документации нет;
значит «массовая операция» в WMS является управляемой очередью одиночных WB-вызовов, а не одним
атомарным запросом WB.

Лимит удаления разделяется со всеми методами чтения и удаления метаданных FBS одного аккаунта
продавца: 300 запросов в минуту, рекомендуемый интервал 200 мс, burst (разрешённый краткий всплеск)
20 для стандартного профиля метода. Общая статья WB отдельно предупреждает, что у Базового и
Тестового типов токенов лимиты могут быть ниже. Поэтому WMS не может считать квоту локальной для
одной кнопки или одного worker: ограничитель должен координировать все чтения и удаления метаданных
конкретного продавца и учитывать фактические rate-limit headers.

При `429` WB документирует `X-Ratelimit-Retry` — число секунд до допустимого повтора,
`X-Ratelimit-Reset` — время до полного восстановления burst, и `X-Ratelimit-Limit` — размер
восстановленного burst. Это не `Retry-After`: стандартный заголовок не назван официальным контрактом
WB для этой ошибки. Повтор раньше `X-Ratelimit-Retry` запрещён. После повторного `429` WB рекомендует
увеличивать паузу, например вдвое, и ограничить число попыток диапазоном 3–5, а не повторять
бесконечно.

Прогресс хранится по каждому `orderId`. Получивший `204` элемент больше не отправляется. `429`
оставляет элемент незавершённым и назначает `next_attempt_at`. Timeout, разрыв соединения или `5xx`
не доказывают, выполнил ли WB удаление; перед новым DELETE такой элемент нужно сверить через
`POST /api/marketplace/v3/orders/meta`, который принимает до 100 ID. Локальную привязку КИЗ можно
очистить только после подтверждённого `204` либо read-back, который однозначно показывает, что
ожидаемого `sgtin` у задания больше нет. Иначе позиция остаётся явно не обработанной.

## 3. Внешний контракт удаления

### 3.1 Один элемент

- Method: `DELETE https://marketplace-api.wildberries.ru/api/v3/orders/{orderId}/meta?key=sgtin`.
- Авторизация: токен категории Marketplace; значение токена вне исследовательского артефакта.
- `orderId`: обязательный `int64` ID сборочного задания.
- `key`: один тип метаданных; для BLG-I19 ровно `sgtin`.
- `204`: WB подтвердил удаление значения; тело ответа отсутствует.
- `400`: неверный запрос; автоматический повтор без исправления запрещён.
- `401/402/403`: авторизация, оплата или доступ; автоматический retry как rate-limit запрещён.
- `409`: ошибка удаления; WB считает такой ответ как 10 запросов этой квоты. Бесконечный повтор
  быстро ухудшит лимит, поэтому позиция уходит в terminal/review outcome с безопасной причиной.
- `429`: запрос ограничен; позиция остаётся retryable, но не раньше времени из WB headers.
- `5xx` или отсутствие HTTP-ответа: результат DELETE неоднозначен; сначала read-back, затем решение.

Официальная схема не объявляет idempotency key и не обещает, какой ответ вернётся при повторном
удалении уже отсутствующего `sgtin`. Поэтому одинаковый повтор после timeout нельзя считать
доказанно безопасным только из общей семантики HTTP DELETE.

### 3.2 Квота и scheduler

Квота относится к аккаунту продавца и группе **всех FBS metadata get/delete методов**. Следствия:

1. Ограничитель имеет общую область минимум `seller account + FBS metadata read/delete group`, а не
   `mass_operation_id` и не отдельный процесс API/worker.
2. Плановый темп для стандартного профиля не быстрее одного запроса каждые 200 мс. Burst 20 — это
   допустимый краткий всплеск, а не разрешение отправлять по 20 запросов каждым worker.
3. `X-Ratelimit-Remaining` из не-429 ответов используется для проактивного замедления. WB пишет, что
   на самом `429` этого заголовка нет.
4. На `429` время следующей попытки равно не раньше `received_at + X-Ratelimit-Retry`. Повторный
   `429` увеличивает паузу. Отсутствующее, отрицательное или нечисловое значение заголовка не
   превращается в немедленный retry: позиция получает безопасную локальную задержку и диагностический
   outcome, точное fallback-значение утверждает S13.
5. Число попыток конечно. S11/S13 выбирают точное значение 3, 4 или 5 внутри официально
   рекомендованного диапазона; после исчерпания позиция становится окончательно не обработанной.
6. Ответ `409`, который расходует десять единиц, уменьшает доступный темп для соседних операций и
   должен участвовать в том же limiter state.

WB не документирует webhook о восстановлении квоты. Возобновление выполняется локальным scheduler
по `next_attempt_at`, без активного частого polling.

## 4. Partial success и восстановление

WB DELETE обрабатывает один заказ, поэтому partial success возникает на уровне локальной массовой
операции. Один `204` не подтверждает соседние позиции, а один `429` не аннулирует уже полученные
`204`.

Минимальная исследовательская state machine одного элемента:

| Состояние | Как попадает | Следующий шаг |
|---|---|---|
| `PENDING` | элемент принят в массовую операцию | отправить, когда limiter разрешит |
| `IN_FLIGHT` | попытка записана до HTTP send | ждать HTTP outcome; после crash считать неоднозначным |
| `RATE_LIMITED` | `429` | сохранить headers/attempt и ждать `next_attempt_at` |
| `RECONCILE_REQUIRED` | timeout, transport error, `5xx` или crash после send | batch read-back до нового DELETE |
| `REMOTE_DELETE_CONFIRMED` | `204` либо однозначный read-back | только теперь разрешить локальное снятие привязки |
| `FINAL_FAILED` | non-retryable `4xx/409`, неизвестный read-back или исчерпан лимит попыток | показать позицию и безопасную причину |

Это не готовая схема БД и не архитектурное утверждение; это обязательные наблюдаемые состояния,
которые S13 должен сделать durable (переживающими рестарт worker).

Каждый элемент сохраняет минимум: `tenant_id`, `seller_id`, `operation_id`, `order_id`, `key`, hash
ожидаемого КИЗ без публикации значения в обычные логи, `state`, `attempt_count`, `last_http_status`,
`last_error_class`, `next_attempt_at`, `last_attempt_at`, `confirmed_at` и WMS correlation ref.
Значения `X-Ratelimit-Retry/Reset/Limit/Remaining` сохраняются как проверенные числа, не как сырой
набор headers.

Повторный запуск той же пользовательской операции переиспользует уже подтверждённые результаты и
создаёт попытки только для незавершённых позиций. Он не сбрасывает счётчик и не отправляет повторно
элементы `REMOTE_DELETE_CONFIRMED`.

## 5. Read-back после неоднозначного ответа

Актуальный read endpoint: `POST /api/marketplace/v3/orders/meta` с телом
`{"orders": [<orderId>, ...]}`; один запрос принимает до 100 ID. Это batch-чтение уменьшает расход
квоты, но само входит в ту же группу get/delete и планируется тем же limiter.

Для текущего ожидаемого набора `sgtin`:

- ожидаемое значение отсутствует однозначно — WB-side удаление подтверждено read-back;
- ожидаемое значение всё ещё присутствует — удаление не подтверждено, элемент можно повторить после
  разрешения limiter и retry policy;
- order отсутствует в ответе, `metaDetails` неполон/неизвестен, строки конфликтуют либо набор изменён
  другой операцией — `FINAL_FAILED`/manual review, без оптимистичного локального очищения.

Read-back использует актуальный `metaDetails`, а не удалённый из контракта legacy-объект `meta`.
Точное сопоставление current marking revision принадлежит BLG-I02; пока S04 этой зависимости не
пройден, BLG-I19 не должен получать Product-before-Dev approval, но это не блокирует завершение
узкого исследования S03.

## 6. Объём, роли и аварийный режим

- 500 одиночных удалений при 200 мс занимают минимум около 100 секунд без конкурирующего трафика,
  `409`, read-back и retries. Это нижняя оценка, не SLA.
- Для сниженного token profile либо общей нагрузки операция будет дольше; UI не должен обещать
  фиксированное время завершения.
- Оператор видит счётчики `всего / подтверждено WB / ждёт повтора / требует внимания`, а по завершении
  — точный список окончательно не обработанных заказов. Сырые токены, КИЗ и WB response body не
  показываются.
- Tenant и seller обязательны в ключах progress/limiter. Квоту и результат одного селлера нельзя
  переиспользовать для другого. Склад не является измерением внешнего rate-limit контракта.
- При недоступности scheduler/хранилища новые запросы не отправляются. Уже подтверждённые позиции
  сохраняются; незавершённые возобновляются после durable recovery.
- Ручная кнопка повтора не обходит `next_attempt_at`, общий limiter и предел попыток.

## 8. Вопросы и обязательства следующих стадий

1. **S04, non-blocking для S03:** независимо подтвердить отсутствие batch-delete FBS, текущий набор
   rate-limit headers и token-profile таблицу на canonical OpenAPI.
2. **S11/S13:** выбрать точный максимум попыток из диапазона WB 3–5 и безопасный fallback при
   отсутствующем/невалидном `X-Ratelimit-Retry`.
3. **S13:** определить durable store, lease/fencing между worker, транзакционную границу локального
   снятия КИЗ и recovery для crash между HTTP send, ответом WB и local commit.
4. **BLG-I02 / S04→S11:** утвердить read-back по current marking revision и fail-closed хранение
   вердиктов. Эта зависимость обязательна до Product-before-Dev BLG-I19.
5. **S15/S23:** emulator cases: 204; 429 с каждым числовым header; повторный 429 и предел; malformed/
   missing header; weighted 409; 400/401/402/403; 5xx/timeout с обоими read-back исходами; crash
   recovery; 500 элементов; два worker одного селлера; разные селлеры; отсутствие утечки КИЗ/токена.
