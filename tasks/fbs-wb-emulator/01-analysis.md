# 01 — Анализ + арх-коучинг

> Заполняет: агент-аналитик. Цель — разобрать задачу по продукту И по технике, и **прокачать человека
> вопросами**, а не решить молча. Человек должен после этой стадии лучше знать свой продукт.

## Продуктовая часть

- **Проблема/цель по сути:** Сейчас FBS-цепочку (заказы с WB → сборка → отгрузка на маркетплейс → стикеры → маркировка КИЗ → «передать в доставку») можно проверить только против живого Wildberries. Это тормозит разработку, ломает CI при недоступности WB и не даёт сценария «симулировать новый заказ» или «WB отменил заказ» без реальной покупки. Нужен стенд, где WMS работает **как на проде**, но конечная точка — наш эмулятор.

- **Ожидаемое поведение (для оператора ФФ и тестировщика):**
  1. На тест-контуре WMS смотрит на эмулятор (одна переменная окружения), не на `marketplace-api.wildberries.ru`.
  2. Через админ-ручку эмулятора (`POST /__admin/orders`) создаются N «новых» заказов с баркодами из каталога селлера → автопрос WMS подтягивает их в раздел FBS «Новые» с `mapping=mapped`.
  3. Оператор проходит полный цикл в UI: создать отгрузку → печать стикеров (реальный PNG 58×40) → внести КИЗ → «Передать в доставку».
  4. КИЗ с подстрокой `ERR` в значении → проверка маркировки падает → deliver блокируется (как гейт на проде).
  5. Два тест-токена (например, Виталик и другой селлер) → каждый видит только свой пул заказов.
  6. Состояние эмулятора переживает рестарт контейнера (SQLite на volume).

- **Границы (out of scope):**
  - Реальная авторизация WB, «Честный Знак», логистика, тарифы.
  - Точные тексты ошибок WB (только коды/формы, которые **читает** WMS).
  - Content API / FBW supplies API — эмулятор покрывает только **Marketplace API v3** (FBS).
  - v1 — happy-path; полнота (все краевые статусы WB) — итерациями.
  - Прод-compose и прод-env **никогда** не указывают на эмулятор.

- **Соответствие MVP-решениям:** Не противоречит. В `docs/MVP_DECISIONS_RU.md` зафиксирован «импорт-only» для классического WB (карточки, FBW-поставки). FBS-цепочка уже использует **исходящие** вызовы Marketplace API (создание отгрузки, стикеры, КИЗ, deliver) — это отдельный контур, уже в продукте. Эмулятор не расширяет MVP, а даёт **безопасный тестовый стенд** для уже запланированного FBS. Терминология UI: «отгрузка» (ФФ→МП), не «поставка» для селлер→ФФ — соблюдаем в описаниях и тест-кейсах.

## Техническая часть

- **Как устроено сейчас (по факту кода):**

  **Точка переключения API** — настройка `wildberries_marketplace_api_base` в `backend/app/core/settings.py` (по умолчанию `https://marketplace-api.wildberries.ru`; в Docker — env `WILDBERRIES_MARKETPLACE_API_BASE`). Все FBS-вызовы к WB идут через этот base URL.

  **Клиент WB (единственный источник контракта эмулятора):** `backend/app/services/wildberries_client.py`
  - Константы путей: `MARKETPLACE_ORDERS_NEW_PATH`, `MARKETPLACE_ORDERS_PATH`, `MARKETPLACE_ORDERS_STATUS_PATH`, `MARKETPLACE_SUPPLIES_PATH`, `MARKETPLACE_ORDER_STICKERS_PATH`, `MARKETPLACE_ORDER_META_PATH` и др. (строки 16–24).
  - Каждая функция показывает: HTTP-метод, body, **какие поля ответа читает** (например `order["nmId"]`, `data.get("stickers")`, `checkStatus` в meta).
  - Для e2e уже есть in-memory моки (`e2e_mock_wb_marketplace_*`) — форма данных в `_marketplace_orders_mock()`, `_marketplace_order_stickers_mock()` и т.д. (строки 206–223, 450–461).

  **Сервисы, которые дергают клиент (контекст использования):**
  - `wb_marketplace_orders_service.py` — автопрос `/orders/new`, синк статусов.
  - `fbs_supply_service.py` — создание отгрузки, добавление заказов, deliver.
  - `fbs_marking_service.py` — КИЗ: PUT/GET meta, `checkStatus`.
  - `fbs_shipment_service.py`, `fbs_shipment_pvz_service.py` — стикеры, грузоместа ПВЗ (`trbx`).
  - `fbs_seller_warehouse_service.py` — склады/офисы селлера.

  **Аутентификация:** WMS шлёт `Authorization: <token>` (токен селлера из `seller_wildberries_credentials`, категория «Маркетплейс»). Эмулятор мапит токен → `seller_key` и изолирует пулы заказов.

  **Эндпоинты, которые эмулятор должен зеркалить (из клиента):**
  | Группа | Пути (как в константах клиента) |
  |--------|----------------------------------|
  | Заказы | `GET /api/v3/orders/new`, `GET /api/v3/orders`, `POST /api/v3/orders/status`, `PATCH /api/v3/orders/{id}/cancel`, `POST /api/v3/orders/stickers`, `GET/PUT /api/v3/orders/{id}/meta[/{kind}]` |
  | Отгрузки (supplies) | `POST /api/v3/supplies`, `PATCH …/orders/{oid}`, `GET …`, `GET …/barcode`, `PATCH …/deliver` |
  | ПВЗ | `POST …/trbx`, `PATCH …/trbx/{tid}`, `POST …/trbx/stickers` |
  | Склады | `GET /api/v3/warehouses`, `GET /api/v3/offices` |

  Точные query, body и поля ответа — **строго из функций клиента**, не из внешней документации WB.

- **Где узкие/неочевидные места (риски):**

  1. **Неверные имена полей** — главный риск. WB использует camelCase (`nmId`, `orderId`, `checkStatus`). Если эмулятор отдаст `nm_id` или пропустит поле, WMS молча сломается или упадёт в середине цикла. Метод: таблица «эндпоинт → поля, которые читает клиент» перед кодом.
  2. **Загрязнение prod-compose** — случайное добавление `WILDBERRIES_MARKETPLACE_API_BASE` в `docker-compose.prod.yml` отправит прод на эмулятор или сломает прод. Жёстное правило: только тестовый compose / override.
  3. **Соблазн править WMS** — «маленький фикс в `wildberries_client.py`» разрушает принцип «один код на прод и тест». Любая доработка клиента — отдельная задача; здесь только эмулятор + env.
  4. **Засев заказов** — заказы должны ссылаться на баркоды из каталога WMS (`mapping_status=mapped`). Фикстура `seed/<seller>.json` с реальными баркодами; без этого цикл застрянет на маппинге.
  5. **Стикеры** — клиент ждёт base64 PNG в поле `file` (см. `_marketplace_order_stickers_mock`), размер 58×40; barcode supply — bytes или base64 в `file`/`barcode`/`image` (см. `_decode_barcode_payload`).
  6. **КИЗ** — `PUT …/meta/sgtin` с body `{"sgtins": [value]}`; в GET meta — `checkStatus` (`new` → через N сек или сразу «проверено»; подстрока `ERR` → `error`). Форма должна совпасть с тем, что читает `fbs_marking_service`.
  7. **Состояние SQLite** — volume обязателен; без него каждый рестарт = пустой стор, тесты нестабильны.

- **Варианты решения:**

  | Подход | Плюсы | Минусы |
  |--------|-------|--------|
  | **A. Standalone FastAPI + SQLite (рекомендуется)** | Изоляция от WMS; свой стор и админ-ручки; переключение одним env; состояние на volume | Новый сервис в compose; нужно зеркалить контракт клиента |
  | **B. Расширить e2e-моки в `wildberries_client.py`** | Уже есть ветки `e2e_mock_*` | In-memory, без персистентности; нет мультиселлера по токену; нет админ «упал заказ»; смешивает тест и прод-код |
  | **C. Record/replay реальных ответов WB** | «Как в жизни» | Зависимость от WB при записи; токены; нестабильные данные; сложный maintenance |

  **Рекомендация:** A — standalone `wb_emulator/`, контракт 1:1 с `wildberries_client.py`, переключение через `WILDBERRIES_MARKETPLACE_API_BASE`.

- **Предлагаемый стек/инструменты (для подтверждения на ГЕЙТЕ 1):**
  - **FastAPI** — HTTP-сервер, роуты `/api/v3/...` + `/__admin/...`.
  - **SQLite** — файл на volume; SQLAlchemy или aiosqlite для простого стора заказов/supplies/meta.
  - **python-barcode** (Code128) + **qrcode** или **segno** — генерация PNG стикеров заказа и QR поставки/грузоместа.
  - **Pydantic** — схемы request/response в форме клиента.
  - **pytest** — контракт-тесты: ответ эмулятора vs поля, которые читает клиент.
  - **Docker** — отдельный контейнер `wb-emulator`; тестовый compose override.
  - Линт/типы — в том же репо (`ruff`, `mypy`), пакет отдельный от `backend/app`.

## 🎓 Вопросы человеку (арх-коучинг — обязательно)

1. **Как WMS сейчас узнаёт, куда слать FBS-запросы?** Подсказка: одна env-переменная на все сервисы (`api`, `celery_worker`, `celery_beat`) — `WILDBERRIES_MARKETPLACE_API_BASE`. Если на тесте она указывает на `http://wb-emulator:…`, автопрос и «Создать отгрузку» бьют в эмулятор, код не меняется. *Проверь: знаешь ли, где в compose это задаётся и что в prod-compose этого нет?*

2. **Почему контракт эмулятора — наш `wildberries_client.py`, а не сайт dev.wildberries.ru?** WMS парсит только те поля, которые клиент явно читает; лишние поля WB не вредят, недостающие — ломают. Моки в том же файле (`_marketplace_orders_mock`) — готовый шаблон формы данных. *Проверь: можешь назвать 3–4 поля заказа из мока (`nmId`, `skus`, `cargoType`…)?*

3. **Где граница «не трогать WMS»?** Любая правка в `backend/app` для «удобства эмулятора» — отдельная задача. Здесь: новый пакет `wb_emulator/`, compose/env, фикстуры seed. Если цикл не проходит — сначала сверяем ответ эмулятора с клиентом, не патчим WMS. *Проверь: согласен ли с этим принципом для стенда?*
