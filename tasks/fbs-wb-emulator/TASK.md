# TASK — fbs-wb-emulator: эмулятор WB Marketplace API для тестовой среды

- **Эпик:** FBS. Цель — дать возможность тестировать весь цикл FBS **без реального WB и без реальных заказов**, но **в точности как на проде**.
- **Тип / размер:** feature / L (v1 — happy-path; полнота — итерациями).
- **Слои:** новый standalone-сервис (отдельный контейнер) + правки docker-compose (только тест) + конфиг env. **Код самой WMS не трогаем** (это принцип — см. ниже).

---

## 0. ГЛАВНЫЙ ПРИНЦИП (нарушишь — всё сломается)
Эмулятор — это отдельный HTTP-сервис, который **прикидывается WB Marketplace API v3**. WMS переключается на него **одной переменной окружения** `WILDBERRIES_MARKETPLACE_API_BASE` — **больше в WMS не меняем ничего**. Благодаря этому поведение WMS остаётся **идентичным проду**: тот же код автопроса, создания отгрузки, стикеров, КИЗ, deliver — просто конечная точка WB подменена.

**Контракт эмулятора = ровно то, что шлёт и парсит наш WB-клиент. НЕ угадывай реальный WB — читай наш код и зеркаль его 1:1.**

### Источник правды по контракту (ОБЯЗАТЕЛЬНО прочитать ПЕРЕД кодом)
- `backend/app/services/wildberries_client.py` — **единственный источник**: все пути `/api/v3/...` заданы константами (`MARKETPLACE_ORDERS_NEW_PATH` и т.д.), и каждая функция показывает: какой HTTP-метод, какой request body, **какие поля ответа она читает**. Эмулятор должен отдавать РОВНО эти поля (лишние — можно, недостающие — нельзя).
- Как эти вызовы используются (какие тела запросов, как разбираются ответы, какие статусы WB ожидаются):
  `wb_marketplace_orders_service.py`, `fbs_supply_service.py`, `fbs_marking_service.py`,
  `fbs_shipment_service.py`, `fbs_shipment_pvz_service.py`, `fbs_seller_warehouse_service.py`.
- Мок-ответы для e2e (форма данных): в `wildberries_client.py` есть ветки `e2e_mock_*` / фикстуры — подсмотри форму там.

**Метод работы:** выпиши из `wildberries_client.py` таблицу «эндпоинт → метод → request → поля ответа, которые читает клиент». Реализуй по этой таблице. Это гарантия, что не накосячишь с формой.

## 1. Эндпоинты (все из `wildberries_client.py`, пути — как в константах)
Заказы:
- `GET /api/v3/orders/new` — отдать пул «новых» сборочных заданий (то, что ждёт автопрос).
- `GET /api/v3/orders` — список с пагинацией (`limit`/`next`), как читает клиент.
- `POST /api/v3/orders/status` — батч-статусы по `orders[]`.
- `PATCH /api/v3/orders/{order_id}/cancel` — отмена продавцом.
- `POST /api/v3/orders/stickers?type=&width=&height=` — стикеры заказов (см. §4).
- `GET /api/v3/orders/{order_id}/meta` и `PUT /api/v3/orders/{order_id}/meta/{kind}` — КИЗ/УИН/IMEI/GTIN (см. §5).

Поставки:
- `POST /api/v3/supplies` — создать (вернуть `wb_supply_id` в форме, что читает клиент).
- `PATCH /api/v3/supplies/{sid}/orders/{oid}` — добавить заказ.
- `GET /api/v3/supplies/{sid}` (+ `/orders`) — инфо/состав.
- `GET /api/v3/supplies/{sid}/barcode?type=` — QR поставки (PNG/base64, §4).
- `PATCH /api/v3/supplies/{sid}/deliver` — передать в доставку.
- Грузоместа ПВЗ: `POST /api/v3/supplies/{sid}/trbx`, `PATCH …/trbx/{tid}`, `POST …/trbx/stickers`.

Склады/зоны:
- `GET /api/v3/warehouses`, `GET /api/v3/offices`.

> Точные query-параметры, тела и поля ответов — **строго из `wildberries_client.py`**. Если клиент читает `order["nmId"]` — отдай `nmId`, а не `nm_id`.

## 2. Аутентификация и мультиселлерность
- WMS шлёт заголовок `Authorization: <token>` (токен селлера из `seller_wildberries_credentials`, категория «Маркетплейс»).
- Эмулятор держит **конфиг тестовых токенов** (env/файл): `TOKEN -> seller_key`. По токену определяет, **чей пул заказов** отдавать. Так ты и Виталик, вбив каждый свой тест-токен в кабинете ФФ, видите **свои** заказы.
- Неизвестный токен → `401` (как WB), чтобы поведение WMS на плохой токен тоже тестировалось.

## 3. Стор и реалистичные данные
- Хранилище: **SQLite** (файл на volume — состояние переживает рестарт; на тест-контуре это важно).
- **Засев заказов из реального каталога WMS:** заказы должны ссылаться на **баркоды/nmId реальных товаров** селлера (чтобы в WMS `mapping_status=mapped`). Способ: эмулятор при старте читает список баркодов (а) из переданного фикстур-файла, либо (б) тянет из WMS API каталога — согласуй проще: **фикстура-файл `seed/<seller>.json`** с реальными баркодами/артикулами/названиями. Заполняй реалистично: цена, `cargo_type` (mgt/kgt/sgt), дедлайн (created_at + 120ч), физ/юр.
- **Админ-ручки эмулятора** (не часть WB, свой префикс `/__admin/`):
  - `POST /__admin/orders?seller=&count=` — «сымитировать покупки»: создать N новых заказов → они появятся в `GET /orders/new` → автопрос WMS их подтянет. **Это твоя кнопка «упал новый заказ».**
  - `POST /__admin/orders/{id}/wb-event` — сымитировать WB-события: `sorted` / `sold` / `canceled_by_client` (чтобы тестировать синк статусов и возвраты).
  - `GET /__admin/state` — посмотреть весь стор (debug).

## 4. Стикеры и QR (реальные картинки)
- Генерируй **настоящие PNG**: штрихкод заказа (Code128) и QR поставки/грузоместа (qr). Библиотеки: `python-barcode` + `qrcode`/`segno`. Отдавай в форме и кодировке, которую **ждёт клиент** (base64 PNG — сверь по `wildberries_client.py`, там разбор стикеров). Размер 58×40 для заказа.

## 5. КИЗ / проверка маркировки (важно для гейта deliver)
- `PUT …/meta/sgtin` — принять КИЗ, сохранить, присвоить `check_status`.
- **Симуляция проверки WB:** по умолчанию новый КИЗ → `check_status` уходит в «проверено» через N секунд (или сразу). Спец-правило для тестов: если значение КИЗ содержит подстроку `ERR` → `check_status=error` (чтобы тестировать, что WMS не даёт передать в доставку с ошибкой маркировки).
- Отдавать статусы в форме, которую читает `fbs_marking_service` при синке.

## 6. Стыковка (env + compose) — ТОЛЬКО тест, НИКОГДА прод
- Новый сервис в `docker-compose.yml` (или отдельный `docker-compose.emulator.yml`-override): `wb-emulator`, свой порт, volume под SQLite, монтирование фикстур.
- На сервисах `api`, `celery_worker`, `celery_beat` в **тестовом** compose добавить env:
  `WILDBERRIES_MARKETPLACE_API_BASE=http://wb-emulator:<port>`.
- **В `docker-compose.prod.yml` этого НЕ делать** — там реальный WB. Прод не должен видеть эмулятор в принципе.

## Критерии приёмки (DoD)
- [ ] Поднят `wb-emulator`; WMS с env на него **проходит весь цикл**: автопрос тянет заказы `/orders/new` → они видны в разделе FBS → «Создать отгрузку» (реальный `POST /supplies` в эмулятор) → стикеры печатаются (реальный PNG) → КИЗ вносится и проверяется → «Передать в доставку» проходит.
- [ ] `POST /__admin/orders` создаёт новые заказы, автопрос их подхватывает (видно новые в «Новые»).
- [ ] Разные тест-токены → разные пулы заказов (мультиселлер).
- [ ] КИЗ со значением `ERR...` блокирует deliver (гейт маркировки работает как на проде).
- [ ] Код WMS **не изменён** (кроме, если нужно, env-дефолта) — только конфиг/compose/новый сервис.
- [ ] Прод-compose не содержит переменной на эмулятор.

## Out of scope (не делаем)
- Реальная авторизация WB, реальный «Честный Знак», реальная логистика/тарифы, точные тексты ошибок WB (только коды/формы, которые читает WMS).

## Анти-косяк чеклист (проверь перед сдачей)
1. Каждый ответ эмулятора сверен с тем, какие поля читает `wildberries_client.py` (имена полей 1:1, camelCase как у WB).
2. `WILDBERRIES_MARKETPLACE_API_BASE` реально подхватывается WMS (проверь: автопрос бьёт в эмулятор, а не в WB).
3. Прод-compose чист от эмулятора.
4. Стикеры — валидный PNG (открывается), не заглушка-текст.
5. Состояние в SQLite переживает рестарт контейнера.
