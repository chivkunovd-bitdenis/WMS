# S11 PRODUCT_CONTRACT_APPROVAL - BLG-C02

## Product decision

Product approves a safe diagnostic contract for outgoing WMS requests to
Wildberries. An authorized engineer must be able to determine which controlled
WMS operation called which Wildberries host and route, when each wire attempt
finished, and whether it received an HTTP status or a transport failure. This
diagnostic result must never expose the credential, marking code, request or
response payload, raw marketplace identifier, or other sensitive value that
caused the incident.

For this contract, "request address" means only an exact allowlisted
`server_address` plus a controlled `route_template`. It never means a raw URL,
query string, redirect target, or path containing an order, supply, warehouse,
seller, barcode, or marking identifier.

BLG-C02 changes diagnostics only. It does not change an operator screen,
warehouse step, WB request payload, retry policy, marketplace outcome, stored
business data, or API response. Logging is an observation side effect: its
failure must not change the outgoing request result or the warehouse
transaction.

## Expected product and security behavior

1. WMS emits one structured `wb.http.client.completed` event for every actual
   WB wire attempt, whether the attempt receives an HTTP response, is blocked
   at a controlled redirect boundary, or ends in a classified transport error.
2. Retries and pagination keep one local `operation_ref`; every wire attempt
   receives a new local `request_ref` and an increasing positive `attempt`.
   A WB-supplied request ID is not a substitute and is never logged.
3. The event is produced only for an exact host in the approved WB production
   or official sandbox allowlists, or for the deterministic local emulator
   class used by tests. A suffix match such as arbitrary `*.wildberries.ru` is
   forbidden. Non-WB HTTP traffic produces no `wb.http.client.*` event.
4. A `2xx` status proves only that the HTTP exchange completed. It must not be
   presented as proof that a multi-item operation, warehouse action, or WB
   business process fully succeeded.
5. Unknown routes and malformed external values fail closed to `unknown` or
   `null`. There is no raw-value fallback. A redirect outside the allowlist is
   represented as `redirect_blocked` without recording the redirect target.
6. The same allowlist and denylist apply to API and background-worker paths and
   to every adjacent sink: application, HTTP client, access and task logs,
   exception output, traces, metric labels, and persisted evidence. Existing
   `wb_response_body` logging cannot remain as an unreviewed legacy lane.
7. The implementation is configuration-gated and default-off. Tests may enable
   it only in isolated deterministic fixtures. No staging or production
   activation is approved by S11.

## Allowed structured fields

The event is allowlist-only. An implementation may emit the following fields
and no others:

| Field | Product rule |
|---|---|
| `event` | Exact constant `wb.http.client.completed`. |
| `occurred_at` | UTC timestamp generated by WMS. |
| `provider` | Exact constant `wildberries`. |
| `environment` | Controlled enum `emulator`, `sandbox`, `staging`, or `production`; it is not inferred from user input. |
| `component` | Controlled enum `api` or `worker`. |
| `operation_ref` | Opaque local correlation value shared only by attempts of one logical operation. |
| `request_ref` | Unique opaque WMS-generated value for one wire attempt. It is the primary engineer search key. |
| `tenant_ref` | Optional opaque internal tenant reference; never a name, credential, or external identifier. |
| `seller_ref` | Optional opaque internal seller reference; never a name, credential, or external identifier. |
| `local_entity_ref` | Optional opaque internal WMS entity reference; never a raw WB order, supply, or warehouse ID. |
| `operation` | Controlled low-cardinality operation name from a registry. |
| `http_method` | Controlled HTTP method enum used by the registered operation. |
| `server_address` | Exact classified host from the approved WB/emulator allowlist, without scheme, credentials, port supplied by external input, path, or query. |
| `route_template` | Controlled registry template such as `/api/v3/orders/{orderId}/cancel`, or exact sentinel `unknown`; never a raw path. |
| `attempt` | Positive integer for the wire attempt within the logical operation. |
| `duration_ms` | Non-negative integer measured locally by WMS. |
| `status_code` | Integer HTTP status when a response exists; otherwise `null`. |
| `outcome` | Controlled enum `http_completed`, `http_rejected`, `auth_rejected`, `payment_required`, `operation_blocked`, `rate_limited`, `upstream_error`, `transport_error`, or `redirect_blocked`. |
| `error_type` | For no-response failures only: `timeout`, `connect`, `dns`, `tls`, `cancelled`, `protocol`, or `other`; otherwise `null`. |
| `rate_limit_remaining` | Parsed non-negative numeric value or `null`; no raw header text. |
| `rate_limit_retry_seconds` | Parsed non-negative numeric value or `null`; no raw header text. |
| `rate_limit_limit` | Parsed non-negative numeric value or `null`; no raw header text. |
| `rate_limit_reset_seconds` | Parsed non-negative numeric value or `null`; no raw header text. |

Numeric rate-limit fields are approved in the event because they help diagnose
`409` and `429` outcomes without identifying a credential. Missing, malformed,
negative, fractional, non-ASCII, or overflowing values become `null`; their raw
form is not retained in logs, traces, metrics, or evidence.

## Forbidden fields and values

No event or adjacent sink may contain:

- `Authorization`, `X-Client-Secret`, cookies, API/JWT/session tokens,
  passwords, service secrets, encryption keys, DSNs, or connection URLs;
- token type, token identity, token-derived claims, credential fingerprints,
  or partially masked credential values;
- full URL, scheme-bearing URL, query string, URL credentials, redirect target,
  raw path, or raw request/response header map;
- request body, response body, any excerpt of either body, or WB error detail;
- WB-supplied `requestId`, `origin`, arbitrary error text, exception message,
  `repr(request)`, `repr(response)`, or stack content that repeats external data;
- CIS/DataMatrix, SGTIN, UIN, IMEI, GTIN, customs declaration, barcode, sticker,
  QR, ZPL, PDF, image, label, or marking payload;
- raw order, supply, warehouse, seller, customer, product, or cargo-place ID;
- seller/customer names, product titles, email, phone, address, personal data,
  or free-form text from WB;
- newline or control characters originating in an external value;
- any extra field outside the approved schema, even when its value appears
  harmless in one fixture.

## Required redaction outcomes

- Credentials, marking values, payloads, personal data, and external free text
  are omitted completely, not partially masked and not hashed for correlation.
- A raw URL is reduced before serialization to the controlled
  `server_address` and `route_template`. Path and query values are discarded.
- Raw marketplace identifiers are represented only by optional opaque local
  references that cannot be reversed from the event.
- HTTP and transport errors are reduced to status and controlled outcome/error
  enums. The response body and exception text are discarded.
- An unknown route is recorded as `route_template=unknown`; an unknown host
  does not gain WB logging coverage. Neither case may preserve the raw input.
- A logger, serializer, or storage failure may emit only a separate bounded
  operational counter without the rejected event content. The WB request and
  warehouse result continue unchanged.

The acceptance oracle is zero leakage, not visual plausibility. Synthetic
canaries for every forbidden class must return zero exact matches when every
captured sink is concatenated. A single match fails the card.

## Operator and engineer workflow

The warehouse operator and seller portal receive no new screen, button, toast,
or technical request identifier. Their work and existing error handling remain
unchanged. When reporting an integration incident, support records only the
existing WMS business context needed to narrow the search: environment, tenant
or seller context, local WMS entity, operation, and a bounded UTC time window.
They must not ask the operator to send a WB token, KIZ, request body, response
body, screenshot of a secret, or marketplace cabinet data.

An engineer with existing authorized application-log access follows one
documented search path in the protected centralized log surface:

1. filter to `event=wb.http.client.completed`, `provider=wildberries`, the
   environment, and the bounded time window;
2. narrow by the authorized `tenant_ref`, `seller_ref`, `local_entity_ref`,
   `component`, and controlled `operation` fields that are available;
3. select the local `request_ref`, then use its `operation_ref` to compare retry
   attempts, status, duration, outcome, and safe rate-limit values;
4. if several candidates remain, narrow the safe local context or time window;
   never broaden diagnosis by requesting or logging a secret, marking code,
   raw URL, payload, or external error body.

Direct access is limited to existing WMS engineering/on-call/release roles that
already have the relevant environment and tenant-support authorization.
Warehouse operators and sellers do not receive log access. This card creates no
new public API, operator UI, database, export, dashboard, or permission grant.
Cross-tenant searches require the existing security/incident authorization;
ordinary support diagnosis stays tenant-scoped.

Events remain only in the existing protected centralized application log for a
maximum of 30 calendar days, or the platform's shorter existing retention,
whichever is shorter. They are not copied into tickets, chat, source control,
test snapshots, analytics, or a new long-term archive. S21 must document the
exact search command/query without embedding a real environment URL or secret.

## Required downstream proof

### S12 task cut

S12 must preserve one vertical result: WB-specific structured events, removal
or sanitization of every adjacent leak lane, API and worker coverage, the
engineer search path, and default-off release control. It must not split
"useful logging" from "redaction" into separately claimable cards or treat a
global HTTPX INFO logger as an acceptable implementation slice.

### S15 cases

S15 must define direct and breaker cases for:

- exact event keys, types, enums, host allowlist, route templates, locally
  generated correlation refs, retry/pagination attempts, and no duplicate
  event from API or worker initialization;
- `2xx`, `3xx` redirect blocking, `400/401/402/403/404/406/409/429/5xx`, timeout,
  connect, DNS, TLS, cancellation, protocol, malformed input, and logger/storage
  failure outcomes;
- valid, missing, independently malformed, negative, fractional, non-ASCII, and
  overflow rate-limit values, including expected missing Remaining on `429`;
- synthetic Personal, Service, Base, and Test auth fixtures, including distinct
  Service/Base `X-Client-Secret` canaries and all researched Base `401/403`
  secret-failure classes, without any credential access;
- an aggregate zero-match scan across structured events, legacy WB error logs,
  app/httpx/httpcore/access/task logs, API exception output, worker retry/failure
  logs, traces, metric labels, and persisted evidence for every forbidden
  canary and every outcome;
- non-WB traffic, unknown route, redirect to a non-WB host, query injection,
  newline/control injection, and proof that no raw fallback appears;
- one synthetic support incident in which the documented safe filters locate a
  single `request_ref` and its complete attempt chain without searching for a
  token, KIZ, raw WB ID, URL, request body, or response body;
- maximum retention/default-off configuration and proof that logging failure
  does not change the business HTTP result.

All cases use `MockTransport` or a deny-by-default local emulator. Official WB
sandbox hosts are classification fixtures only. DNS/socket egress to WB, Ozon,
or production endpoints must fail the suite.

### S16 Product before Dev

S16 may approve development only when the card and executable oracle retain the
full allowlist/denylist, all-sink zero-leak proof, API/worker parity, engineer
search journey, 30-day maximum retention, and default-off release boundary. A
plan that tests only one successful request, emits full URLs, enables global
HTTPX logging, or postpones legacy leak removal is not product-approved for
development.

### S18 implementation

After S16/S17, S18 may implement only the approved diagnostics behavior. It may
not change WB payloads, retries, operator UX, warehouse logic, credentials, or
release state. The implementation must use a shared WB-specific structured
projection for API and worker attempts, remove or sanitize existing raw WB
response/body/path logging in the covered lanes, remain default-off outside
isolated tests, and add the protected engineer runbook. No live call is
authorized as development evidence.

### S19 automation binding

S19 must bind every S15 case to executable test IDs and capture all named sinks
in one deterministic aggregate leak scan. The harness must prove deny-by-default
egress, fail when any extra event key or forbidden canary appears, exercise API
and worker paths through real application handlers into local transport, and
verify the synthetic engineer search result. A source-code grep alone is not
redaction proof.

### S20 independent review

S20 must independently review every touched WB call path and logging sink,
schema cardinality, route registry behavior, correlation semantics, API/worker
single-emission behavior, default-off configuration, access/retention runbook,
and all executable leak evidence. It must reject raw URL/body/exception
fallbacks, secret fingerprints, global HTTP client logging, unbounded external
strings, duplicate events, or a release flag that defaults on. The historical
uncommitted candidate from S03 is discovery evidence only, not an accepted
implementation or release artifact.

S21-S23 must then preserve the sanitized runbook, pass the functional and full
integration suites without live marketplace traffic, and bind the accepted
result to one immutable candidate SHA and artifact manifest.

## Release boundary

S11 does not authorize a release or activation. S26 must later assemble the
immutable full 40-character candidate SHA and artifact manifest, independent
S20-S23 evidence, the exact target environment, the default-off flag and
requested activation state, protected log destination, access and retention
proof, smoke query, stop condition, deactivation/rollback procedure, and
production trace plan.

S27 remains blocked until the owner separately approves that exact SHA,
artifact manifest, target environment, and logging activation. Approval of this
contract, a branch, a short SHA, a test result, or a release review without the
exact candidate is insufficient. Without that owner instruction the honest
state is `READY_FOR_RELEASE`/waiting at S26, not deployed or done.

S28 may begin only after S27 proves the running artifact and configuration match
the owner-approved SHA and activation. Its production trace must use only the
approved structured fields and stop immediately on any redaction, cardinality,
availability, or business-impact finding. No S27 or S28 action is performed or
approved here.

## Non-goals and current-stage limits

- No application code, test implementation, config mutation, permission grant,
  log-platform change, commit from a historical candidate, or release work is
  performed at S11.
- No operator UI, warehouse process, marketplace payload, retry/pagination
  policy, database model, or public/internal API is added or changed.
- No raw payload capture, debug logging, credential fingerprinting, long-term
  archive, analytics feed, cross-tenant support search, or general HTTP client
  observability is approved.
- No real credential is read, decoded, validated, rotated, replaced, or used.
- No live WB/Ozon, official sandbox, production, deploy, S27, S28, or secret
  operation is authorized.

## Verdict

`PRODUCT_CONTRACT_APPROVED`: BLG-C02 may proceed only as a default-off,
WB-specific, allowlist-only diagnostic event that lets an authorized engineer
find a concrete local request and its attempts by safe correlation fields while
all credentials, KIZ/marking values, payloads, raw URLs/IDs, external text, and
adjacent leak lanes produce zero disclosure. Release and activation still
require a separate owner approval naming the exact immutable SHA and target.
