# Call 75 — independent pre-development test plan: S-32 Ozon account

## Scope and test safety

This plan is derived from the owner request and Call 74 contracts only.  Slice 1
is an account/authentication slice: it may validate a candidate with one
read-only Ozon request and persist a tenant/seller-scoped encrypted pair.  It
does not touch orders, products/catalogue, physical stock, FBS/FBO, labels,
returns, provider mutations or background jobs.  Every provider test uses a
local injected transport; test data are synthetic and no credential value is
written to a test failure, snapshot, log assertion, or report.

`N/A` is an explicit scope decision, not untested behaviour: duplicate
orders/events, unmapped products, and WB/Ozon contention for physical stock
are outside slice 1.  The guard cases below prove that this account slice
cannot reach those domains.

## Numbered cases

1. **TC-S32-OZON-001 — API + Playwright, P0.** Goal: an authorised seller connects one Ozon account on the existing S-32.  Preconditions: owner or staff has `settings`, no active Ozon primary row, injected validation returns 204.  Actions: open `/seller/settings`, enter synthetic non-empty pair, click `Подключить`.  Expected observable result: the URL remains `/seller/settings`; exactly one inline Ozon card reports `Подключено` and a validation time; inputs are cleared; no selector/dashboard/sync action appears.  Data: generated tenant/seller and opaque test pair.  Method: API contract test plus visible Playwright flow with local fake transport.  Automated: yes.
2. **TC-S32-OZON-002 — API + Playwright, P0.** Goal: reject incomplete and malformed candidate input without a provider call.  Preconditions: disconnected authorised seller and counting fake.  Actions: submit missing, blank, whitespace-only, over-255 Client-Id, over-4096 Api-Key, wrong-type values, and an extra field.  Expected: exact field messages for missing values, otherwise 422; no row and fake count remains zero.  Data: boundary strings and JSON variants.  Method: parametrised API requests and browser form assertions.  Automated: yes.
3. **TC-S32-OZON-003 — API + service, P0.** Goal: a first invalid candidate cannot be saved and a replacement cannot damage a working account.  Preconditions: respectively no row or a valid encrypted row; fake returns 401 then 403.  Actions: PUT candidate / choose `Заменить данные` and submit.  Expected: 422 `ozon_credentials_invalid`, exact safe UI wording, no new row for first save, and byte-equivalent old credential/status/audit data on replacement.  Data: synthetic pairs distinguished only by opaque handles.  Method: service transaction assertions and API/UI contract.  Automated: yes.
4. **TC-S32-OZON-004 — API + service, P0.** Goal: distinguish invalid credentials from unavailable validation.  Preconditions: stored valid account or candidate; fake produces timeout, network exception, 429, 500/502, and unexpected 418 separately.  Actions: PUT and `POST .../test-connection` for each class.  Expected: timeout/network/429/5xx map to 503 `ozon_validation_unavailable`; unexpected non-2xx maps to 502 `ozon_validation_failed`; manual-test status is `unavailable` with a safe code, while failed candidate PUT preserves the old account exactly.  Empty/incomplete 2xx bodies still count as successful because the body is deliberately ignored.  Data: local response/status matrix.  Method: fake transport parametrisation.  Automated: yes.
5. **TC-S32-OZON-005 — service + API, P0.** Goal: establish idempotency and safe concurrency.  Preconditions: authorised seller and delayed fake.  Actions: replay the same normalised PUT; issue concurrent equal PUTs, concurrent differing valid PUTs, concurrent test-connection calls, and double DELETE.  Expected: one `(tenant,seller,ozon,primary)` row, equal replay retains account id/ciphertext/`credentials_updated_at`, differing pairs are serialised last-writer-wins without a second primary row, each click makes at most one provider request, and two DELETEs return 204 with no provider request.  Data: two opaque candidate handles and an async barrier.  Method: async service/API concurrency test.  Automated: yes.
6. **TC-S32-OZON-006 — API + Playwright, P0.** Goal: preserve the existing settings permission boundary.  Preconditions: fixtures for unauthenticated, FF admin, seller without settings, seller with settings, and seller owner.  Actions: call all four self routes and navigate to S-32.  Expected: 401 for unauthenticated; 403 and no Ozon card for FF/no-settings; settings-enabled staff and owner may use all actions.  No stock permission is created or consulted.  Data: role fixtures.  Method: API matrix and browser visibility test.  Automated: yes.
7. **TC-S32-OZON-007 — service + API, P0.** Goal: fail closed across tenant, seller and account-selection attacks.  Preconditions: tenant A/seller A connected; tenant B/seller B authenticated.  Actions: B calls self endpoints with injected `seller_id`, `account_id`, `account_slot`, foreign UUIDs, or delegated-seller token variations; invoke service with mismatched scope.  Expected: no request field selects A, mismatch is 404 `seller_not_found`/forbidden without account-existence disclosure, and A bytes/audit remain unchanged.  Data: two tenant fixtures and UUIDs.  Method: API payload fuzz matrix and direct service test.  Automated: yes.
8. **TC-S32-OZON-008 — service + API + schema, P0.** Goal: prevent secret and sensitive Client-Id leakage. 10. **TC-S32-OZON-010 — Playwright + API, P1.** Goal: make connected, invalid, unavailable and not-configured states truthful.  Preconditions: each seeded status and local fake scenario. 17. **N/A — duplicate orders/events, unmapped products, WB/Ozon physical-stock contention.** Layer: slice-boundary guard, P0.  Goal: prove these are not silently pulled into account connection. ## Honest pre-code baseline

Before implementation, only syntax and collection/focused local checks are authorised.  The intended backend collection is expected to be red because the contract deliberately names files/modules that do not yet exist; the intended Playwright Ozon cases are expected to be red because the approved card/testids do not yet exist.  Neither result is a passed test and neither uses a real Ozon credential or provider call.  After development, run the focused backend tests, then the existing seller-settings Playwright file, and finally the full mandatory gates; browser product approval remains a separate manual gate.
