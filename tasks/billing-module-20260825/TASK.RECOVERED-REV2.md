## 3. Волна 1 — журнал документов

**Решение по дублированию.** Подбор, упаковка и коды маркировки **уже журналируются** тремя
существующими журналами. Новый журнал их **не дублирует и не заменяет**. Он покрывает только то,
чего нет нигде: **переходы статусов документов и изменения их данных**.

Отчёты волны 4 читают из четырёх источников: новый журнал плюс три существующих. Двойного счёта быть
не должно — это отдельный обязательный тест.

**Что делаем.** Одна новая таблица `document_event`. Поля:

| Поле | Смысл |
|---|---|
| `id`, `tenant_id` | стандартные |
| `document_type` | `inbound_intake` (включая возврат), `fbs_supply`, `marketplace_unload` |
| `document_id` | идентификатор документа |
| `event_type` | `status_changed`, `line_added`, `line_removed`, `line_qty_changed`, `warehouse_changed`, `planned_date_changed`, `defect_qty_changed` |
| `actor_user_id` | автор; `null` для системных действий |
| `source` | `user` или `system` — обязательно, чтобы отличать оператора от автоопроса |
| `occurred_at` | момент |
| `payload_json` | полезная нагрузка |
| `idempotency_key` | ключ повтора, nullable |

**Схема `payload_json` задаётся здесь и в волне 4 не меняется.** Для `status_changed` — `from`, `to`.
Для строковых событий — `product_id`, `qty_before`, `qty_after`. Для остальных — `field`,
`value_before`, `value_after`. Количество хранится **отдельным числовым полем внутри payload**, а не
свободным текстом: волна 4 считает по нему штуки.

**Ключ идемпотентности.** Повтором считается запись с тем же `idempotency_key`. Ключ формируется
вызывающей стороной из документа, типа события и естественного ключа действия. Действия без
естественного ключа (два подряд одинаковых изменения количества) — это **два разных события**, и они
обязаны записаться оба.

**Правила:**

- запись в журнал **никогда не роняет операцию**: сбой пишется в лог, складское действие не
  откатывается;
- журнал только пополняется, записи не редактируются и не удаляются;
- существующие поля `*_by_user_id` в моделях остаются на месте, не удалять и не заменять;
- миграция только добавляющая.

**Фронта в этой волне нет.** Ни одного изменения на экранах.

**Файлы:** новая модель `backend/app/models/document_event.py`, новый сервис
`backend/app/services/document_event_service.py`, миграция, вызовы из
`inbound_intake_service.py`, `fbs_supply_service.py`, `marketplace_unload_service.py`.

**Тесты:** каждый переход статуса каждого из трёх типов документов порождает ровно одну запись с
правильным автором; системное действие пишется с `source = system` и без автора; сбой записи журнала
не откатывает операцию; повтор с тем же ключом идемпотентности не задваивает; два одинаковых
изменения количества подряд дают две записи.

## 4. Волна 2 — тарифная матрица

### 4.1. Модель цены

Три уровня, от общего к частному:

1. **Какие операции считаем** — включается галочкой на каждую услугу. Выключенная не порождает
   начислений.
2. **Общая цена операции** — цена за документ либо за единицу.
3. **Цена по товару** — для той же услуги индивидуальная цена на конкретный товар.

**Правило приоритета:** цена по товару перебивает общую цену той же услуги. Нет цены по товару —
берётся общая. Нет общей — начисление создаётся без цены и помечается проблемой, как сейчас.

**Единица расчёта.** Для одной услуги в один момент времени действует **ровно одна** единица.
Смена единицы — это новая версия, закрывающая предыдущую. Одновременное существование `document` и
`item` для одной услуги запрещено.

**Коды услуг.** Существующие: `inbound`, `marketplace_outbound`, `storage_liter_day`. Добавляются
два: `packing` (упаковка) и `return` (возврат). Допустимые единицы для новых — `document` и `item`.
Ограничение по складу для них такое же, как у приёмки: склад **запрещён**.

### 4.2. Как цена по товару ложится на модель — без ослабления индекса

Уникальный индекс `uq_billing_ledger_source_event` **не трогать**. Одно начисление на документ и
услугу остаётся.

Детализация по товарам живёт в **новой дочерней таблице** `billing_ledger_line`:
`entry_id`, `product_id`, `quantity`, `rate`, `amount`, `tariff_version_id`.

Сумма родительского начисления равна сумме его строк. Когда цен по товару нет — строк нет, работает
как сегодня. Идемпотентность не меняется, отчёт получает разрез по товарам.

### 4.3. Дата начала и дооценка

`valid_from` **не может быть раньше сегодняшнего дня по Москве**; сегодня — можно. Это то же правило
и тот же код ошибки, что действует сегодня для тарифа хранения.

**Дооценку сохранить, и она работает так:**

- **первая версия тарифа по услуге** дооценивает **все** непроценённые начисления этой услуги,
  независимо от даты факта — иначе задание тарифа после месяца работы оставит все приёмки без цены;
- **последующие версии** дооценивают только начисления с датой факта не раньше своей `valid_from`;
- уже оценённые начисления не трогаются никогда.

и видны счётчиком; разворачивание показывает операции; переход из операции открывает нужный документ;
выключенная услуга не попадает в отчёт; возврат виден отдельной услугой; переписанные `S-31-TC-005`
и `S-31-TC-016` зелёные.

## 6. Волна 4 — вкладка «Сотрудники»

**Доступ.** Экран Расчёты уже целиком под `fulfillment_admin`, дополнительного замка не требуется.
Если понадобится открыть вкладку старшим смены — это делается правом `shift_lead`, но **в этой задаче
не делается**.

### 6.1. Решение по упаковке — двойной оплаты быть не должно

Сдельная оплата за упаковку **уже работает** и остаётся единственным источником правды по упаковке:
ставка в карточке пользователя, снимок в задании, расчёт в `staff_packaging_billing_service`.

**Новая тарифная матрица не заводит свою цену за упаковку сотруднику.** Вкладка «Сотрудники»
показывает упаковку, беря её из существующего механизма, а подбор, приёмку, отгрузку и возврат — из
новой матрицы. Одна ставка за упаковку, в одном месте, там где она была.

### 6.2. Источник данных и правило начисления

Источник — **журнал волны 1 плюс три существующих журнала**, а не поле `performer_id` в начислении:
одну поставку подбирает один сотрудник, а упаковывает другой.

**Оплачивается фактическое действие человека, а не документ целиком.** Подобрал Сидоров — начисление
за подбор Сидорову; упаковал Петров — за упаковку Петрову. Один документ порождает столько начислений
сотрудникам, сколько в нём было оплачиваемых действий разных людей.

**Двойного счёта быть не должно:** событие, взятое из существующего журнала, не берётся повторно из
нового. Это обязательный тест.

**Сотрудник без ставки:** начисление создаётся с нулевой суммой и помечается как проблема **в самой
строке отчёта** отдельной колонкой-признаком. Существующая таблица проблем сюда не годится: она
завязана на селлера.

### 6.3. Вкладка — подробно

**Третья вкладка «Сотрудники»** рядом с существующими «Начисления» и «Счета». Вкладки уже есть,
добавляется одна.

**Сверху** — `ReportMetricStrip`: «Всего к выплате», затем по плитке на услугу — Приёмка, Подбор,
Упаковка, Отгрузка, Возврат.

**Таблица.** Колонки: Сотрудник, Операций, Штук, Начислено, признак «Нет ставки», кнопка-раскрытие.

**Раскрытие** показывает операции сотрудника: Дата, Документ, Услуга, Количество, Ставка, Сумма.
Клик по документу — тот же существующий переход.

**Фильтры** — существующие период и поиск. Своих новых фильтров не заводить.

**Тесты:** документ с разными исполнителями порождает начисления обоим; событие не учитывается дважды
из двух журналов; сотрудник без ставки виден признаком и не ломает итог; итог сходится; удалённый
пользователь не роняет отчёт; упаковка в отчёте совпадает с цифрой в панели сотрудников на Настройках.

## 7. Волна 5 — режим «Финансы»

**Смысл.** Без режима вкладка «Начисления» — отчёт товародвижения: кто, что, сколько, по какому
селлеру. С включённым появляются денежные колонки: Ставка, Начислено, Итог, и плитки итогов.

**Ролевой части нет:** экран целиком админский, ролей без доступа на нём не существует. Это
переключатель вида, а не замок.

**Элемент:** `Switch` с подписью «Финансы» в строке управления таблицей, рядом с существующими
элементами управления, **не** в ряду фильтров.

**Поведение:** выключен — сервер **не отдаёт** денежные поля, а не просто прячет их на экране;
колонки скрыты, остальные не сдвигаются и не меняют ширину.

**Состояние** запоминается в `localStorage` для пользователя. Миграций и новых полей у пользователя
не заводить.

**Совместимость:** формат ответа `/api/billing/ledger` меняется — денежные поля становятся
необязательными. Существующие потребители не должны сломаться, это отдельный тест.

**Тесты:** выключенный режим не отдаёт денежные поля с сервера; колонки не разъезжаются в обоих
состояниях, меряется `scripts/ui/invariants.js`; состояние переживает перезагрузку; ответ API с
отсутствующими денежными полями не ломает существующих потребителей.

## 8. Порядок волн

Строго по очереди, каждая доводится до конца и коммитится отдельно. Волна 1 — фундамент волны 4.

полученный лично.
