## 1. Что уже есть в нашей системе

Проверено по коду, переиспользуется как есть:

- Заявка на возврат — **это уже существующий документ**: `InboundIntakeRequest` с
  `operation_type = "return"`. Второй тип — `inbound`.
- Этапы документа: `draft` → `submitted` → `receiving` → `sorting` → `done`.
- Строка документа `InboundIntakeLine` имеет `expected_qty` (ожидалось) и `actual_qty` (принято).
- Экран `FfInboundRequestView` уже отличает возврат от приёмки (`isReturnOperation`) и уже умеет
  автопечать штрихкода при сканировании строки возврата.
- Создание возврата уже есть на экране очереди: кнопка «Создать возврат».
- У склада есть признак `is_operational` — то есть неоперационный склад системой уже поддержан.

Ничего из этого не переписывать.

## 2. Что меняется — полный список

1. При создании заявки на возврат появляется **выбор маркетплейса**: Wildberries, Ozon или без
   маркетплейса (ручной возврат).
2. Для Ozon появляется кнопка **«Получить возврат»**: тянет список возвратов из Ozon и заполняет
   строки документа.
3. Для Ozon из документа печатается **штрихкод выдачи и накладная** — чтобы сверить партию на
   стороне Ozon при получении.
4. В строках документа появляется **колонка «Брак»** — количество брака в строке. Заполняется
   вручную, необязательна.
5. При проведении документа товар расходится: **годное на обычный склад, брак на отдельный склад
   брака**.
6. **Для WB и ручного возврата убирается двойная работа**: подобрал товар, добавил строки —
   документ можно завершать, отдельный шаг приёмки не требуется.

Новых экранов, маршрутов, вкладок и этапов не появляется.

## 3. Схемы методов уже в проекте

`tasks/ozon-integration-20260825/OZON_RETURNS_OPENAPI.json` — официальная спецификация Ozon,
снятая 25.08.2026 напрямую с `https://docs.ozon.ru/api/seller/swagger.json`. Девять методов,
45 схем со всеми вложенными зависимостями.

Документация Ozon закрыта антиботом и отдаёт `403` — **в интернет не ходить, недоступность

Руками модели не писать, поля не угадывать, из сторонних зеркал не брать.

| Назначение | Метод |
|---|---|
| Список возвратов маркетплейса | `POST /v1/returns/list` |
| Сведения о возвратах FBS | `POST /v1/returns/company/fbs/info` |
| Доступна ли выдача возвратов | `POST /v1/return/giveout/is-enabled` |
| Список выдач | `POST /v1/return/giveout/list` |
| Сведения о выдаче | `POST /v1/return/giveout/info` |
| Штрихкод выдачи | `POST /v1/return/giveout/barcode` |
| Накладная выдачи PDF | `POST /v1/return/giveout/get-pdf` |
| Штрихкод выдачи PNG | `POST /v1/return/giveout/get-png` |
| Сброс штрихкода выдачи | `POST /v1/return/giveout/barcode-reset` |

Ozon-сущности: возврат связан идентификаторами `id`, `posting_number`, `order_id`,
`product.sku`, `product.offer_id` и логистическим штрихкодом. Выдача — отдельная сущность
`giveout_id` со своим штрихкодом. **Наш документ возврата и наши строки — третья, отдельная
сущность.** Приравнивать нельзя.

### Что реально отдаёт `/v1/returns/list` — сверено по схемам

Строка возврата содержит: `id` возврата, `type` (`Cancellation` — отмена до вручения, `FullReturn` —
полный возврат), `schema` (`FBS` или `FBO`), `order_id` и `order_number`, `posting_number`,
`return_reason_name` — причину возврата, `product` (`sku`, `offer_id`, `name`, **`quantity`**, цена,
комиссия), `place` — где возврат лежит сейчас (`id`, `name`, `address`), `target_place` — куда едет,
`logistic` (**`barcode` — штрихкод возвратной этикетки**, даты возврата и прибытия), `visual.status`
(`id`, `display_name`, `sys_name`), `exemplars` — идентификаторы экземпляров, `compensation_status`.

Фильтры запроса: `order_id`, `posting_numbers` (не больше 50), `offer_id`, `product_name`,
`visual_status_name`, **`warehouse_id`**, **`barcode`**, `return_schema` (FBS/FBO),
`compensation_status_id` и диапазоны дат. Пагинация — `last_id` плюс **обязательный** `limit`.

Практические следствия: тянуть возвраты можно **точечно по складу**, то есть только те, что лежат на
нужном пункте; сопоставлять с нашим каталогом надо по `product.offer_id` и `product.sku` — привязка
Ozon у товара уже есть; количество берётся из `product.quantity`.

### Как на самом деле устроена выдача — расхождение с первоначальной постановкой

**Штрихкод выдачи не привязан к партии.** У продавца **один постоянный штрихкод**, по которому ему
выдают возвраты. Методы `barcode`, `get-pdf` и `get-png` принимают **пустое тело** (`v1Empty`) — им
нечего передавать, они возвращают текущий штрихкод продавца текстом, PDF-ом и картинкой. Есть
`barcode-reset` — перевыпустить штрихкод.

Поэтому это не «QR на эту накладную», а **пропуск на получение**, и печатать его логично один раз,
а не из каждого документа.

**Товарной накладной от Ozon не существует.** `get-pdf` — это PDF со штрихкодом, а не список товаров.
Сверять партию на пункте придётся по `/v1/return/giveout/info`: он по `giveout_id` отдаёт
**артикулы товаров**, статус выдачи, название и адрес склада. Печатную форму для сверки собираем
сами из этих данных.

**Подтверждения выезда в API нет.** Среди девяти методов нет ничего вида «выехал», «подтверждаю
получение». Значит шага «поехали забирать» не делаем — это установленный факт, а не неизвестность.

**Признака брака в возвратах Ozon нет.** Есть `return_reason_name` — почему покупатель вернул, и
`visual.status` — состояние возврата в их системе. Решение «годное или брак» принимает наш склад при
осмотре. Колонка «Брак» — целиком наша механика, из Ozon её взять негде и не нужно.

**Перед работой с выдачей проверять `/v1/return/giveout/is-enabled`** — он говорит, доступно ли
получение по штрихкоду этому продавцу вообще. Недоступно — сказать словами, документ вести руками.

## 4. Процесс возврата Ozon по шагам

1. **Создание.** Оператор жмёт «Создать возврат», выбирает селлера и маркетплейс Ozon.
2. **Выбор пунктов в модалке предпросмотра.** Кнопка «Получить возврат» открывает модалку со
   **списком пунктов выдачи**: по каждому — название и адрес (`warehouse_name`,
   `warehouse_address`), сколько товаров надо забрать (`total_articles_count`), сколько подтверждено
   (`approved_articles_count`), статус, дата создания, и раскрывающийся список товаров внутри.

   Оператор отмечает галками **те пункты, куда сегодня поедет**, либо жмёт «выбрать все».
   Отмеченное попадает в **один документ возврата**, сгруппированное по пунктам.

   **Один документ покрывает сколько угодно пунктов.** Заводить отдельную заявку на каждый ПВЗ
   запрещено: у продавца пять пунктов — это один документ и один выезд, а не пять заявок.
   Ограничения «одна выдача — один документ» в API Ozon нет.

   По каждому отмеченному пункту состав тянется из `/v1/return/giveout/info` (артикулы), а
   подробности по возвратам — из `/v1/returns/list` с фильтром по складу этого пункта. Пагинацию
   отрабатывать целиком: `limit` обязателен, дальше по `last_id`, пока `has_next`.

   Товар сопоставляется с нашим каталогом по `product.offer_id` и `product.sku`; количество берётся
   из `product.quantity`. Несопоставленный товар показывается отдельной строкой с понятным текстом,
   а не теряется молча.

   **Каждая строка документа помнит, из какой выдачи и с какого пункта она приехала** —
   `giveout_id`, название и адрес склада. Плюс по возврату: `id`, `posting_number`,
   `logistic.barcode`, `return_reason_name` и `type`.

   Статус и счётчики ведутся **по каждой выдаче отдельно**: одну могут отменить или подтвердить
   частично, остальные при этом продолжают жить. Статусы выдачи: создана, одобрена, завершена,
   отменена.
3. **Документы для поездки.** Два разных документа, не путать:
   - **штрихкод выдачи — один на всего продавца, а не на пункт.** Методы `barcode`, `get-pdf` и
     `get-png` принимают **пустое тело**: `giveout_id` в них не передаётся, его там нет как
     параметра. Это личный код продавца — печатается один раз и действует на всех пунктах маршрута.
     Метод `barcode-reset` перевыпускает его, если код скомпрометирован, и тогда старые перестают
     работать везде.
     На каждый пункт свой код печатать **не нужно и негде взять**. Перед печатью проверить
     `is-enabled`; если выдача продавцу недоступна — сказать словами и вести документ руками;
   - **список для сверки** — собирается нами из `/v1/return/giveout/info` по каждому `giveout_id`:
     артикулы товаров, статус выдачи, название и адрес склада. Товарной накладной Ozon не отдаёт,
     печатную форму делаем свою, существующим механизмом печати.
     **Печатать с разбивкой по пунктам:** на каждом пункте сверяют только свою часть, а не весь
     список выезда. Разделы идут в порядке маршрута, у каждого — название и адрес пункта.
4. **Физическое получение.** Партия приезжает на склад. Подтверждения выезда или получения в API
   Ozon нет — **отдельной кнопки «поехали забирать» не делать**.
5. **Приёмка.** Оператор либо сканирует товар, либо проставляет количество руками. **Добавлять
   строки разрешено** — по факту может приехать не то, что было в списке.
6. **Брак.** В строке заполняется количество брака. Это **наше** решение по итогам осмотра: в данных
   Ozon признака брака нет, есть только причина возврата покупателем. Необязательно: не заполнено —
   значит брака нет. Количество брака не может превышать принятое количество по строке.
7. **Печать.** Из документа печатаются штрихкод товара и Честный знак — существующим механизмом,
   без изменений.
8. **Проведение.** Годное количество приходуется на обычный склад документа. Бракованное — на склад
   брака.

## 5. Склад брака

Отдельный склад с `is_operational = false`. В общих списках складов и в выборе склада оператору он
**не показывается** — он служебный. Остаток на нём виден только там, где сознательно нужен.

Заводится один раз на тенанта, автоматически при первом появлении брака. Миграции только
добавляющие.

## 6. Упрощение ручного пути — WB и возврат без маркетплейса

Это **сознательное изменение существующего поведения по решению владельца**, единственное в задаче.

Сейчас оператор сначала добавляет строки с ожидаемым количеством, а потом отдельным шагом принимает
фактическое. Для фулфилмента это двойная работа: товар уже лежит в руках, ожидаемого количества не
существует.

Как должно быть: оператор подобрал товар в существующем окне подбора, строки добавились с фактическим
количеством — документ можно завершать. Отдельный шаг подтверждения приёмки для этого пути не нужен.

Границы: это касается только возвратов (`operation_type = "return"`) для WB и без маркетплейса.
**Обычная приёмка от селлера (`inbound`) не меняется вообще** — там ожидаемое количество имеет смысл,
его присылает селлер.

## 7. Экраны — подробно

Всё собирается из `frontend/src/ui-kit/` и повторяет вид уже существующих элементов. Своей вёрстки
таблиц, кнопок, чипов не заводить.

### 7.1. Диалог создания возврата

Существующий диалог, открывается кнопкой «Создать возврат» на экране очереди приёмок.

Добавляется **один селект «Маркетплейс»** рядом с существующим выбором селлера. Значения:
«Wildberries», «Ozon», «Без маркетплейса». По умолчанию — «Без маркетплейса».

Больше в этом диалоге не меняется ничего.

### 7.2. Модалка подбора возвратов Ozon — новая

Открывается кнопкой «Получить возврат» из документа возврата, у которого маркетплейс Ozon.

**Делается по образцу существующей `MarketplaceProductPickerDialog`** (`Выбор товаров`): та же
ширина, та же плотность строк, тот же вид таблицы, тот же `ProductPhotoThumb` для фото, те же кнопки
внизу. Это не новый визуальный язык, это тот же подбор, только источник строк другой.

**Заголовок:** «Возвраты Ozon».

**Шапка модалки:**

- строка поиска — по названию, артикулу продавца, артикулу Ozon и штрихкоду возвратной этикетки;
- кнопка «Выбрать все пункты»;
- справа счётчик выбранного: «Выбрано пунктов: N · товаров: M».

**Тело — список пунктов выдачи, каждый раскрывается.** Один пункт = одна группа.

Заголовок группы, в одну строку:

| Элемент | Источник |
|---|---|
| чекбокс выбора пункта | — |
| название пункта | `warehouse_name` |
| адрес | `warehouse_address` |
| «товаров: подтверждено / всего» | `approved_articles_count` / `total_articles_count` |
| чип статуса выдачи | `giveout_status`: создана, одобрена, завершена, отменена |
| **«ждёт N дней»** | `storage.days` — сколько возврат ждёт выдачи |
| **«утилизация ЧЧ.ММ»** | `storage.utilization_forecast_date` |

Дни ожидания и дату утилизации показывать **предупреждающим тоном**, когда до утилизации меньше
недели: Ozon берёт деньги за ожидание и потом утилизирует товар, оператор должен видеть, за каким
пунктом ехать первым.

Внутри раскрытой группы — таблица товаров этого пункта. Колонки строго в этом порядке:

| Колонка | Что показывает |
|---|---|
| Фото | `ProductPhotoThumb`, как в существующем подборе |
| Артикул | наш SKU из каталога |
| ШК | штрихкод товара из каталога |
| Артикул продавца | `product.offer_id` |
| Артикул Ozon | `product.sku` |
| Наименование | `product.name` |
| Причина возврата | `return_reason_name` |
| Количество | `product.quantity`, выравнивание вправо |

Товар, который не сопоставился с нашим каталогом, показывается той же строкой, но фото, артикул и ШК
пустые, а рядом — предупреждение «Товар не сопоставлен с каталогом». Строка **остаётся выбираемой**:
оператор всё равно физически привезёт этот товар.

**Кнопки внизу:** «Отмена» и «Добавить в возврат». Вторая заблокирована, пока не выбран ни один
пункт, и в неактивном состоянии объясняет почему.

**Что происходит по нажатию:** строки выбранных пунктов добавляются в документ возврата,
сгруппированные по пунктам. Модалка закрывается. Повторное открытие показывает уже добавленные
пункты отмеченными и не даёт задвоить.

### 7.3. Документ возврата

Существующий экран `FfInboundRequestView`. Каркас, этапы, панель сортировки, механизм печати — без
изменений.

**В шапку добавляется:**

- чип маркетплейса — тот же элемент и тот же цвет, что на остальных экранах;
- кнопка «Получить возврат» — только для Ozon, в существующей зоне действий;
- кнопка «Печать пропуска» — тот самый единый штрихкод продавца, PDF;
- кнопка «Печать листа сверки» — наша форма, **с разбивкой по пунктам**, разделы в порядке маршрута,
  в каждом название и адрес пункта и его товары.

Обе кнопки печати живут рядом с уже существующими кнопками печати, отдельной панели не заводить.

**В таблицу строк добавляется одна колонка «Брак»** — справа от принятого количества, числовое поле,
выравнивание вправо, пустое значение допустимо. Больше колонок не добавляется и не убирается.

Строки визуально сгруппированы по пунктам выдачи: подзаголовок группы с названием и адресом пункта.
Группировка делается существующим способом отображения групп, новый компонент не изобретать.

### 7.4. Чего быть не должно

Новых экранов, маршрутов, вкладок, этапов документа. Отдельной панели действий Ozon. Переделки
панели сортировки, существующих кнопок печати, обычной приёмки. Своей вёрстки таблиц и чипов мимо
`ui-kit`.

## 7.5. После получения: статусы выдачи

Метода «подтвердить получение» в API нет — статус выдачи меняет сам Ozon на своей стороне, когда
товар выдан. Поэтому после проведения документа мы **перечитываем статусы выдач** методом
`/v1/return/giveout/info` по каждому `giveout_id` и показываем их на документе.

Расхождение показывается словами, а не молчанием: если выдача осталась «одобрена», хотя товар мы
уже приняли, это видно на экране. Своего «подтверждения» не изобретать и статус Ozon у себя не
подменять.

## 8. Ошибки и устойчивость

- Идемпотентных ключей Ozon не документирует: слепой повтор мутаций запрещён, после мутации —
  перечитывание состояния.
- `403 code 7` — кабинет заблокирован: сказать один раз словами, не долбить.
- `429` — свой счётчик по маркетплейсу, не общий с WB.
- Сбой Ozon не мешает принять партию руками: документ должен доводиться до конца без внешних вызовов.
- Реальные вызовы Ozon не выполняются, пока кабинет заблокирован — всё на фейке и контрактных тестах.

## 9. Тест-кейсы до кода

- создание возврата с каждым из трёх вариантов маркетплейса;
- модалка подбора: пунктов нет; один пункт; несколько пунктов; «выбрать все»; выбран один пункт из
  пяти — в документ попал только он; повторное открытие не задваивает уже добавленное;
- в модалке видны фото, артикулы, штрихкод, причина возврата и количество; несопоставленный товар
  показан с предупреждением и всё равно выбирается;
- дни ожидания и дата утилизации показаны; при сроке меньше недели — предупреждающим тоном;
- строки в документе сгруппированы по пунктам, каждая помнит свой `giveout_id`;
- печать пропуска: получен, выдача продавцу недоступна (`is-enabled` = false), ошибка;
- лист сверки печатается с разбивкой по пунктам;
- после проведения статусы выдач перечитываются; расхождение видно словами;
- «Получить возврат»: список пуст, список получен, товар не сопоставлен с каталогом, Ozon недоступен;
- печать штрихкода и накладной выдачи: получено, не готово, ошибка;
- приёмка сканированием и руками; добавление строки, которой не было в списке;
- брак: не заполнен, заполнен частично, равен принятому, больше принятого — запрещено;
- проведение: годное на склад документа, брак на склад брака, склад брака создаётся один раз;
- склад брака не появляется в списках выбора склада;
- WB и ручной возврат: подобрал и завершил без отдельного шага приёмки;
- **обычная приёмка `inbound` не изменилась** — регрессия обязательна;
- повторное проведение не задваивает остаток;
- изоляция селлеров и кабинетов; секреты не в логах.
