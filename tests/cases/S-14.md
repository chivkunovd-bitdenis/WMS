# Кейсы экрана S-14

База кейсов живёт между ночами. Номера постоянные и не переиспользуются: кейс, потерявший
смысл, помечается устаревшим, но не удаляется и номер не отдаёт.

Пройденным кейс считается только со скриншотом в `docs/evidence/<карточка>/`.
Проверка чтением кода, curl или пересказом разработчика не засчитывается.

Формат: `S-14-TC-001 · название` → начало, действия, точный ожидаемый результат.

## Кейсы

### S-14-TC-001 · Сканирование ЧЗ на упаковке — строка не переходит в «WB подтвердил» до ответа WB

**Карточка:** 02-verdikt-screen · смежный (S-14 задет картой 01/02 через мета-данные)

**Начало.** Экран `FbsPackagingPage` (S-14). Оператор упаковки вызвал заказ на сканирование
маркировочного кода. Строка заказа показывает чип «Нужен ЧЗ» (WB ждёт, код не привязан).

**Действия.**
1. Отсканировать валидный SGTIN-код для этого заказа.
2. Смотреть на статус строки заказа **сразу** после скана.

**Ожидаемый результат.** После привязки кода строка показывает **«Статус уточняется»**
(серый, neutral) или **«WB проверяет»** (жёлтый, warn) — в зависимости от того, успел ли
автополлер получить ответ от WB. Строка **не показывает** зелёный «WB подтвердил»
немедленно после скана: факт привязки кода ≠ одобрение WB. Переход в зелёный происходит
только после реального ответа `decision = "accepted"` от WB (через автополлер).

### S-14-TC-002 · Двойное сканирование одного и того же ЧЗ — второй скан отбивается с понятным сообщением

**Карточка:** 02-verdikt-screen · смежный

**Начало.** Экран `FbsPackagingPage`. Оператор уже привязал SGTIN-код к Заказу X.
Код показывает чип «WB проверяет» (жёлтый).

**Действия.**
1. Отсканировать тот же SGTIN-код второй раз (случайное повторное сканирование — частая
   ошибка при сканере в перчатках).

**Ожидаемый результат.** Система **не создаёт дублирующую привязку**. Показывается чёткое
сообщение: «Этот код уже привязан к заказу [номер]» — или аналогичный текст, не технический.
Экран не падает с 500. Первоначальная привязка к Заказу X сохраняется. Чип в строке
не сбрасывается в «Статус уточняется».

---

### S-14-TC-003 · WB вернул ошибку при проверке ЧЗ — упаковщик видит причину словами, не технический код

**Карточка:** 02-verdikt-screen · смежный

**Начало.** Экран `FbsPackagingPage`. Оператор отсканировал код, он привязался к заказу.
Автополлер получает от WB ответ: `decision = "filled"`, `reason = "uinBadStatus"`.

**Действия.**
1. Дождаться обновления статуса строки после ответа WB.
2. Смотреть на строку заказа.

**Ожидаемый результат.** Строка показывает красный чип **«WB не принял»** с читаемым
пояснением: «неверный статус УИН» (перевод из `metaStatus.ts`). Технический код `uinBadStatus`
нигде на экране не показывается. Оператор понимает, что нужно связаться с продавцом или
перепроверить код, не обращаясь в техподдержку за расшифровкой ошибки.

---

### S-14-TC-004 · Маркировочный код привязывается к заказу, у которого code already belongs to another order — система отклоняет

**Карточка:** 02-verdikt-screen · смежный

**Начало.** Экран `FbsPackagingPage`. Оператор упаковки сканирует SGTIN-код, который уже
привязан к **другому** заказу в этой или другой поставке.

**Действия.**
1. Отсканировать код, принадлежащий другому заказу.

**Ожидаемый результат.** Система **отклоняет** привязку. Сообщение оператору: «Этот код
уже используется в другом заказе» (или аналогичный текст без `marking_code_id` и других
технических ID). Строка текущего заказа сохраняет предыдущий статус (не переходит в «WB
проверяет»). Код в другом заказе не отвязывается. Оператор понимает, что нужно взять
другой стикер.
