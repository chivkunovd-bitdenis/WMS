# Кейсы экрана S-03

База кейсов живёт между ночами. Номера постоянные и не переиспользуются: кейс, потерявший
смысл, помечается устаревшим, но не удаляется и номер не отдаёт.

Пройденным кейс считается только со скриншотом в `docs/evidence/<карточка>/`.
Проверка чтением кода, curl или пересказом разработчика не засчитывается.

Формат: `S-03-TC-001 · название` → начало, действия, точный ожидаемый результат.

## Кейсы

---

### S-03-TC-001 · WB подтверждает все коды — кнопка «Сдать поставку» активна

**Начало.** Поставка (supply) в статусе `assembling`. У трёх заказов привязаны коды маркировки (КИЗ, `kind = sgtin`). В тестовой заглушке WB настроен ответ: для всех трёх кодов `decision = accepted`. Ни одного предыдущего orphan-флага нет.

**Действия.**
1. Открыть браузер, перейти на `/app/ff/fbs` (S-03, экран «FBS-заказы»).
2. Найти нужную поставку в разделе «Собирается» и нажать на строку, чтобы открыть workspace поставки.
3. Подождать не более 60 секунд (один цикл автополлера).
4. Обновить страницу (F5).

**Ожидаемый результат.**
- Кнопка «Сдать поставку» в workspace **активна** (синяя/цветная, не серая), доступна для нажатия.
- Ни одна из трёх строк заказов не отображает предупреждения о маркировке.
- В базе данных: для каждой строки `fbs_order_marking` этих трёх заказов `meta_status = 'accepted'`, `check_status = 'ok'`, поле `reason` содержит значение от WB или пустое (не дефолтное `'assigned'`). Поле `metadata_delivery_allowed` в таблице `fbs_orders` = `true`. Поле `metadata_last_checked_at` содержит время последнего тика (не `null` и не дата до деплоя карточки 01).

### S-03-TC-002 · WB отклоняет код — кнопка «Сдать поставку» серая

**Начало.** Поставка в статусе `assembling`. У одного заказа привязан код маркировки. В тестовой заглушке WB настроен ответ: `decision = rejected`, `reason = "Код не найден в ЧЗ"` для этого кода.

**Действия.**
1. Открыть `/app/ff/fbs`, найти поставку, открыть workspace.
2. Подождать один цикл автополлера (до 60 секунд).
3. Обновить страницу.

**Ожидаемый результат.**
- Кнопка «Сдать поставку» **серая** (неактивна, не кликается).
- При наведении на кнопку или рядом с ней виден текст «не все коды проверены» (или аналогичная существующая формулировка о блокировке маркировки — текст берётся из существующей разметки, карточка 01 его не меняет).
- В базе: `fbs_order_marking.meta_status = 'rejected'`, `fbs_order_marking.reason = 'Код не найден в ЧЗ'`, `fbs_orders.metadata_delivery_allowed = false`.

### S-03-TC-003 · Первый тик WB-молчания — видимое состояние не меняется

**Начало.** Поставка в статусе `assembling`. У одного заказа привязан код (`meta_status = 'assigned'`, `marking_code_id` заполнен). Тестовая заглушка WB в следующем тике не вернёт этот заказ в массиве `orders[]` (заказ просто отсутствует в ответе, HTTP-статус 200, тело валидное JSON).

**Действия.**
1. Убедиться, что заглушка WB настроена: следующий успешный ответ не содержит этот wb_order_id.
2. Дождаться прохождения одного цикла автополлера (до 60 секунд).
3. Открыть `/app/ff/fbs`, найти поставку.

**Ожидаемый результат.**
- Состояние кнопки «Сдать поставку» и строки заказа **не изменилось** по сравнению с состоянием до этого тика — UI ведёт себя идентично.
- В базе: `fbs_order_marking.meta_status` для этого заказа **не изменился** (по-прежнему `'assigned'`). `marking_code_id` **не стал null**.
- В поле `meta_details_json` для строки `fbs_order_marking` появился ключ `wb_orphan_candidate_at` с временной меткой (первый тик поставил внутренний флаг; это служебный ключ в JSON, наружу в API не течёт, проверяется только прямым запросом к БД).

### S-03-TC-004 · Два тика WB-молчания подряд — код `reserved` уходит в пул, кнопка серая

**Начало.** Поставка в статусе `assembling`. У одного заказа привязан код в статусе `reserved` (`marking_code_id` заполнен, `meta_status = 'assigned'`). Тестовая заглушка WB возвращает успешный 200 без этого заказа в двух последовательных тиках.

**Действия.**
1. Дождаться прохождения первого цикла автополлера (WB молчит — тик 1, ставит флаг `wb_orphan_candidate_at`).
2. Дождаться второго цикла автополлера (WB молчит снова — тик 2, подтверждает orphan).
3. Открыть `/app/ff/fbs`, найти поставку, проверить workspace.

**Ожидаемый результат.**
- Кнопка «Сдать поставку» **серая**.
- В базе таблица `fbs_order_marking`: `meta_status = 'missing'`, `check_status = 'new'`, `reason = 'Код отсутствует у WB'`, `marking_code_id = null`.
- В базе таблица `marking_codes`: строка, которая была `status = 'reserved'`, теперь `status = 'available'` (код вернулся в пул).
- В базе таблица `marking_code_events`: есть запись с `event_type = 'wb_orphaned'`, в поле `meta_json` содержится `wb_order_id` данного заказа и прежний `meta_status` (был `'assigned'`).
- `fbs_orders.metadata_delivery_allowed = false`.

### S-03-TC-007 · Новый код привязан между первым и вторым тиком orphan — флаг candidate сбрасывается

**Начало.** Поставка `assembling`. Заказ имеет строку `fbs_order_marking` с `meta_status = 'assigned'`, код `reserved`. После первого тика WB-молчания в `meta_details_json` проставлен `wb_orphan_candidate_at`. До второго тика оператор сканирует новый КИЗ и привязывает его к тому же заказу — `_claim_pool_code_if_present` заменяет `marking_code_id` на новый.

**Действия.**
1. Пройти первый тик WB-молчания (убедиться: `wb_orphan_candidate_at` есть в JSON).
2. До второго тика привязать к заказу новый код через UI упаковки (S-15 или S-14 — сканировать КИЗ в поле привязки).
3. Дождаться второго тика автополлера. WB заглушка по-прежнему не возвращает этот заказ (только что привязанный код WB тоже «не знает» — нормально для свежей привязки).
4. Проверить базу данных.

**Ожидаемый результат.**
- В `meta_details_json` строки `fbs_order_marking` **нет** ключа `wb_orphan_candidate_at` (флаг очищен в момент привязки нового кода).
- После второго тика строка **не** переведена в `missing`: для нового кода начинается свежий отсчёт (если WB не вернёт его и на следующем тике, только тогда появится новый кандидатский флаг).
- Первый (старый) код, который был `reserved` и был заменён, **не** получает `wb_orphaned` событие — он либо остался в пуле (если оператор его отвязал по-честному), либо сохранил свой статус. Событие `wb_orphaned` в данном сценарии не пишется.
- `marking_code_id` в базе указывает на **новый** код.

### S-03-TC-008 · WB «вспоминает» заказ на второй тик — orphan не происходит

**Начало.** Поставка `assembling`. Заказ с `meta_status = 'assigned'`, кодом `reserved`. Первый тик: WB-молчание, выставлен `wb_orphan_candidate_at`. Второй тик: WB возвращает этот заказ с `decision = accepted`.

3. Дождаться второго тика автополлера.

**Ожидаемый результат.**
- Строка `fbs_order_marking`: `meta_status = 'accepted'`, `check_status = 'ok'`.
- `marking_code_id` **не null** (код остался привязан, не возвращён в пул).
- В `meta_details_json` **нет** `wb_orphan_at` (orphan-переход не произошёл). Ключ `wb_orphan_candidate_at` либо очищен, либо перезаписан реальным ответом WB.
- В `marking_code_events` **нет** записи `wb_orphaned` по этому заказу.
- Кнопка «Сдать поставку» **активна** (delivery_allowed = true).

### S-03-TC-010 · Один заказ с двумя kind (sgtin + uin), WB возвращает только sgtin — orphan только по uin

**Начало.** Поставка `assembling`. Один заказ требует двух kind: `sgtin` и `uin` — оба в строках `fbs_order_marking`, оба с кодами `reserved`. Тестовая заглушка WB возвращает успешный 200 с `metaDetails` только для `sgtin` (`decision = accepted`), строки по `uin` в ответе нет. Это происходит два тика подряд.

**Действия.**
1. Первый тик WB-ответа: есть `sgtin`, нет `uin`.
2. Второй тик WB-ответа: снова есть `sgtin`, нет `uin`.
3. Проверить базу данных. Открыть workspace.

**Ожидаемый результат.**
- Строка `fbs_order_marking` для `sgtin`: `meta_status = 'accepted'`, `check_status = 'ok'`, код остался привязан.
- Строка `fbs_order_marking` для `uin`: `meta_status = 'missing'`, `check_status = 'new'`, `marking_code_id = null`, код `uin` вернулся в пул (`status = 'available'`).
- В `marking_code_events` одна запись `wb_orphaned` — только по `uin`-коду. Для `sgtin`-кода события нет.
- `fbs_orders.metadata_delivery_allowed = false` (заказ не полностью подтверждён — `uin` missing).
- Кнопка «Сдать поставку» **серая**.

### S-03-TC-013 · Оператор нажимает «Сдать поставку» из устаревшей вкладки после orphan — бэк блокирует

**Начало.** Два браузера (или две вкладки) открыты на workspace одной поставки. Пока обе открыты, проходит orphan-сверка: `metadata_delivery_allowed = false`. Первая вкладка обновляется — видит серую кнопку. Вторая вкладка не обновляется — кнопка «Сдать поставку» по-прежнему выглядит активной (стейл UI).

**Действия.**
1. Убедиться, что обе вкладки открыты до orphan-сверки.
2. Дождаться двух тиков WB-молчания (orphan завершён, `metadata_delivery_allowed = false`).
3. Из **второй** (устаревшей) вкладки нажать кнопку «Сдать поставку».

**Ожидаемый результат.**
- Бэкенд `_build_delivery_checks` перечитывает `metadata_delivery_allowed` из БД в момент запроса — видит `false`.
- Ответ сервера: ошибка с понятным текстом о том, что коды маркировки не подтверждены (HTTP 4xx, конкретный код зависит от реализации, но не 200).
- Поставка **не переходит** в следующий статус.
- Вторая вкладка показывает сообщение об ошибке. При обновлении страницы кнопка становится серой.

### S-03-TC-014 · Поставка переходит в следующий статус после первого тика orphan — флаг не срабатывает впоследствии

**Начало.** Поставка `assembling`. Один заказ. Первый тик WB-молчания: `wb_orphan_candidate_at` выставлен, `meta_status` ещё `assigned`. После этого тика поставка отправляется в WB через другой путь (например, ручная смена статуса в тестовой среде или прохождение кейса TC-001 с другой поставкой — здесь важно, что поставка уходит из `assembling`).

**Действия.**
1. Пройти первый тик WB-молчания (флаг стоит).
2. Перевести поставку в статус, отличный от `assembling` (например, `awaiting_delivery` или `delivered`).
3. Дождаться второго тика автополлера.
4. Проверить базу данных.

**Ожидаемый результат.**
- Автополлер на втором тике **не обрабатывает** этот заказ (он выбирает только поставки в статусе `assembling`).
- Строка `fbs_order_marking` **не изменяется**: `meta_status` остался `assigned` (или другим), `marking_code_id` не стал null.
- `wb_orphan_candidate_at` в `meta_details_json` остался, но harm'а не причиняет — он просто никогда не получит «второй тик», потому что заказ вышел из очереди обработки.
- В `marking_code_events` **нет** записи `wb_orphaned` по этому заказу.

### S-03-TC-016 · Два воркера Celery пытаются запустить autopoll для одного продавца — lock предотвращает двойную работу

**Начало.** Тестовая среда с двумя Celery-воркерами. Одна задача `wms.fbs_order_statuses_autopoll` запускается дважды практически одновременно (вручную через `celery call` или через тестовый скрипт). Поставка с несколькими заказами в `assembling`.

**Действия.**
1. Запустить два экземпляра задачи одновременно.
2. Дождаться завершения обоих.
3. Проверить базу данных и логи.
