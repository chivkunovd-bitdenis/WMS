# Кейсы экрана S-15

База кейсов живёт между ночами. Номера постоянные и не переиспользуются: кейс, потерявший
смысл, помечается устаревшим, но не удаляется и номер не отдаёт.

Пройденным кейс считается только со скриншотом в `docs/evidence/<карточка>/`.
Проверка чтением кода, curl или пересказом разработчика не засчитывается.

Формат: `S-15-TC-001 · название` → начало, действия, точный ожидаемый результат.

## Кейсы

---

### S-15-TC-001 · Задание возвращается в список «Ожидает маркировки» после orphan-сверки

**Начало.** Заказ ранее имел привязанный код маркировки (`status = 'reserved'`). После двух тиков WB-молчания прошла orphan-сверка: `meta_status = 'missing'`, `marking_code_id = null`, код вернулся в пул (`status = 'available'`).

**Действия.**
1. Открыть `/app/ff/packaging/pending-marking` (S-15, список «Ожидает маркировки»).
2. Найти заказ по артикулу или номеру.

**Ожидаемый результат.**
- Заказ **присутствует** в списке «Ожидает маркировки».
- В строке заказа поле «Код маркировки» пустое — код не привязан.
- Задание не помечено как готовое к упаковке.
- Оператор может выбрать строку заказа и привязать к нему новый код через обычный UI привязки маркировки (кнопка или поле сканирования активны).

---

### S-15-TC-002 · Оператор привязывает код в S-15 в момент параллельного autopoll — нет гонки

**Начало.** Заказ в списке «Ожидает маркировки» (нет `marking_code_id`, `meta_status = 'missing'`). В тот же момент автополлер запускается (тестово инициируется Celery-командой).

**Действия.**
1. Оператор открывает S-15, сканирует КИЗ, нажимает «Привязать» для этого заказа.
2. Точно в тот же момент (разница < 1 секунды) автополлер стартует и пытается проверить meta этого заказа у WB.

**Ожидаемый результат.**
- Операция привязки кода **завершается успехом**: `marking_code_id` заполнен, код переходит в `reserved`.
- Автополлер при обработке этого заказа видит **уже привязанный** код и не пытается его orphan-ить в этом тике (т.к. `wb_orphan_candidate_at` отсутствует для нового кода).
- Никакого `wb_orphaned`-события по только что привязанному коду не возникает.
- Данные в БД консистентны: нет ситуации «`marking_code_id` заполнен, но код уже `available`» одновременно.

### S-15-TC-003 · Заказ исчезает из «Ожидает маркировки» после подтверждения нового кода WB

**Начало.** Заказ прошёл orphan-сверку, попал в S-15. Оператор привязал новый КИЗ (`marking_code_id` заполнен, `meta_status = 'assigned'`). Тестовая заглушка WB на следующем тике возвращает этот заказ с `decision = accepted`.

**Действия.**
1. Привязать новый код в S-15 (оператор сканирует КИЗ).
2. Дождаться одного тика автополлера (WB возвращает `accepted`).
3. Обновить страницу S-15 (`/app/ff/packaging/pending-marking`).

**Ожидаемый результат.**
- Заказ **исчез** из списка «Ожидает маркировки» (оп успешно привязал, WB подтвердил).
- В `fbs_order_marking`: `meta_status = 'accepted'`, `check_status = 'ok'`.
- `fbs_orders.metadata_delivery_allowed = true`.
- Задание заказа **активно** в S-14 (редактируемо, Б-11 снят).
- Кнопка «Сдать поставку» в workspace S-03 **активна** (при условии, что все другие заказы поставки тоже подтверждены).

### S-15-TC-004 · Оператор сканирует один и тот же КИЗ дважды подряд быстро — второй скан игнорируется

**Начало.** Заказ в S-15 без кода. Оператор физически сканирует штрихкод КИЗ дважды за < 0.5 секунды (двойной скан — типичная ошибка ТСД или ручного пистолета).

**Действия.**
1. Открыть строку заказа в S-15 для привязки кода.
2. Сымитировать двойной скан: отправить два одинаковых значения КИЗ в поле ввода с интервалом < 0.5 сек.

**Ожидаемый результат.**
- Привязка выполняется **ровно один раз**: `marking_code_id` заполнен одним кодом.
- Второй запрос не создаёт дубль и не вызывает ошибку базы данных (unique constraint).
- UI показывает одно подтверждение привязки, не двойное.
- Код переведён в `reserved` один раз. В `marking_code_events` одна запись `reserved`, не две.
