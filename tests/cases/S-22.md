# Кейсы экрана S-22

База кейсов живёт между ночами. Номера постоянные и не переиспользуются: кейс, потерявший
смысл, помечается устаревшим, но не удаляется и номер не отдаёт.

Пройденным кейс считается только со скриншотом в `docs/evidence/<карточка>/`.
Проверка чтением кода, curl или пересказом разработчика не засчитывается.

Формат: `S-22-TC-001 · название` → начало, действия, точный ожидаемый результат.

## Кейсы

### S-22-TC-001 · Один настоящий склад — на форме приёмки нет селекта «Склад для заявки»

**Добавлен:** 04-warehouse-switch · 2026-08-22

**Начало:** Тенант с одним настоящим складом «Основной» и любым числом служебных `fbs-wb-*`.
Авторизован как `fulfillment_admin` или `fulfillment_seller`.

**Действия:**

1. Перейти на `/app/ops/inbound` (экран `InboundScreen`).
2. Нажать кнопку создания новой заявки на приёмку (кнопка «Создать заявку» или «+»).
3. Осмотреть форму создания заявки.

**Ожидаемый результат:**

На форме создания заявки нет поля с выбором склада (ни селекта `<Select>`, ни авто-
заполненного поля «Склад для заявки»). Форма содержит только поля, относящиеся к
самой заявке (список товаров, количество и т.д.). Заявка при сохранении создаётся
с `warehouse_id` единственного настоящего склада — это проверяется тем, что
созданная заявка отображается в списке с правильным складом «Основной».

### S-22-TC-002 · Два настоящих склада — заявка приёмки создаётся на складе из глобального контекста

**Добавлен:** 04-warehouse-switch · 2026-08-22

**Начало:** Тенант с двумя настоящими складами: «Основной» и «Дополнительный».
Авторизован как `fulfillment_admin`. Контекст шапки — «Дополнительный».

**Действия:**

1. Перейти на `/app/ops/inbound`.
2. Открыть форму создания новой заявки.
3. Заполнить необходимые поля (без поля склада), нажать «Сохранить».
4. Найти созданную заявку в списке приёмок.

**Ожидаемый результат:**

На форме нет отдельного выбора склада. Созданная заявка привязана к «Дополнительному»
(из контекста шапки) — это видно в строке заявки в списке (колонка или подпись «Склад:
Дополнительный»). Если переключить контекст в шапке на «Основной», заявка пропадает
из списка (фильтрация по складу работает).

### S-22-TC-003 · Нет настоящих складов — форма приёмки заблокирована с Alert warning

**Добавлен:** 04-warehouse-switch · 2026-08-22

**Начало:** Тенант, у которого в базе только служебные `fbs-wb-*` записи и нет ни одного
настоящего склада. Авторизован как `fulfillment_admin`.

**Действия:**

1. Перейти на `/app/ops/inbound`.
2. Попытаться открыть форму создания заявки.

**Ожидаемый результат:**

Кнопка создания заявки недоступна (disabled) или форма создания не открывается.
На экране виден Alert severity `warning` с текстом «Нет доступного склада для создания
заявки. Обратитесь к фулфилменту.» (дословно — переиспользуется существующая
формулировка). Никаких технических ошибок (500, stack trace) на экране нет.

### S-22-TC-004 · Submit формы приёмки пока в другой вкладке переключили склад — заявка на нужном складе

**Добавлен:** 04-warehouse-switch · 2026-08-22 (ломающий)

**Начало:** Тенант с двумя складами: «Основной» и «Дополнительный». Два окна браузера,
оба авторизованы под одним пользователем. Окно-A открыто на `/app/ops/inbound`,
форма создания заявки уже открыта (контекст был «Основной» в момент открытия формы).

**Действия:**

1. Окно-A: начать заполнять форму создания заявки (список товаров, количество).
2. Окно-B (параллельно): переключить контекст склада на «Дополнительный» через
   `WarehouseSwitcher`.
3. Окно-A: нажать «Сохранить» форму заявки (склад на форме отсутствует как поле).

**Ожидаемый результат:**

Заявка создаётся с однозначным `warehouse_id`. Поведение системы одно из двух: либо
заявка берёт склад, который был активен в момент открытия формы («Основной»), либо берёт
актуальный контекст в момент Submit («Дополнительный») — но не случайный из двух. Созданная
заявка в списке явно показывает, какой склад ей присвоен. Ошибки 500 нет.

### S-22-TC-005 · Прямой POST /inbound без warehouse_id — сервер отклоняет с 422

**Добавлен:** 04-warehouse-switch · 2026-08-22 (ломающий)

**Начало:** Тенант с двумя складами. Пользователь знает валидный токен авторизации.
Доступен инструмент (curl, Swagger, Postman) для отправки запросов напрямую в API.

**Действия:**

1. Отправить `POST /inbound` с телом, содержащим все обязательные поля заявки, но
   **без** поля `warehouse_id` (или с `warehouse_id: null`).
2. Посмотреть на ответ сервера.

**Ожидаемый результат:**

Сервер возвращает HTTP 422 Unprocessable Entity. Тело ответа содержит ошибку валидации,
указывающую на отсутствие `warehouse_id`. В базе данных новой строки заявки нет. Нет строки
с `warehouse_id = NULL` в таблице заявок приёмки. UI не задействован в этом кейсе — но
именно этот же механизм защищает данные при любом обходе клиентского кода.
