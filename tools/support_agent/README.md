# Агент-диспетчер обращений (WMS-641)

Отдельная программа на маке владельца. Она **не входит в боевую сборку WMS** и не ставится на Railway
или сервер. Принимает обращения из клиентских Telegram-чатов (текст и голос) и из формы «?» в WMS,
разбирает их моделями владельца через его залогиненные CLI (`claude -p` и `codex exec`, без платных
API-ключей), присылает владельцу сводку, по слову «кати» выпускает хотфикс в облегчённом режиме,
складывает несрочное в Trello. Требования: `docs/requirements/WMS-641.md`.

## Как устроено

- `support_agent/telegram.py` — Telegram long polling (у мака нет публичного адреса), надёжная отправка:
  намерение записывается до отправки, клиенту при неизвестном исходе сообщение не повторяется.
- `support_agent/pipeline.py` — стадии обращения (приём, фильтр, ворох, классификация, разбор, вопросы
  клиенту, сводка, команды владельца, партнёрский чат, форма «?»). Стадии лежат в словаре
  `Pipeline.stages`: новая стадия (разработка, вечерний отчёт, релиз) добавляется обработчиком.
- `support_agent/llm.py` — вызовы CLI: роли и модели, переключение claude <-> codex при лимите,
  сессия аналитика на обращение, Astra всегда с явным effort не выше high.
- `support_agent/hotfix.py` — облегчённый хотфикс по шагам (worktree, разработчик, проверки, одна
  перекрёстная проверка, PR, CI, merge, deploy, сверка версии, отчёт, «пробуйте»).
- `support_agent/store.py` — SQLite (`~/.wms-support-agent/state.db`): состояние переживает перезапуск.
- `support_agent/trello.py`, `wms.py`, `transcribe.py`, `mockups.py`, `runner.py` — Trello, чтение формы
  «?» с бэка, расшифровка голоса, макеты, главный цикл.

## Что нужно сделать владельцу (один раз)

1. **Два бота Telegram** (создаёт владелец в BotFather):
   - бот приёма: выключите privacy mode (`/setprivacy` -> Disable), добавьте в клиентские и партнёрский
     чаты. Он читает сообщения, задаёт клиентам вопросы, пишет «пробуйте» и согласует с партнёром задачу.
     Команды владельца он НЕ принимает вообще: в клиентском чате владелец для него обычный участник;
   - бот владельца: пишет вам сводки, предпросмотры, отчёты и уведомления о простое и принимает ваши
     команды («кати», подтверждения, уточнения, голосом и текстом). Команды принимаются только от
     `owner_user_id`, в чате `owner_chat_id` (ваш чат с этим ботом) и только через этого бота.
   Если у бота когда-то стоял webhook, снимите его (`deleteWebhook`): long polling с webhook не работает.
   Оба бота опрашиваются независимо, у каждого свой offset, состояние переживает перезапуск. Если указать
   один и тот же токен в обоих полях (или старое поле `bot_token`), работает один бот с обеими ролями.
   Проверить токены можно командой `python -m support_agent check-bots` (один getMe на бота, ничего не
   отправляется и обновления не забираются).
2. **ID.** Узнайте ID чатов (отрицательные числа) и свой Telegram user ID.
3. **Конфиг.** Один файл `~/.wms-support-agent/config.json` (права 600, вне Git). Пример без значений:
   `config.example.json`. Нужны: `telegram.intake_bot_token` и `telegram.owner_bot_token`, ID чатов с ролями (`client` с именем селлера или `partner`),
   `owner_user_id`, `owner_chat_id`, ключ и токен Trello, ID доски и списков (клиентские — как
   `TRELLO_REVIEW_LIST_ID`, метка «Клиент» как `TRELLO_CLIENT_LABEL_ID`, партнёрские задачи — список
   «Задачи», `in_progress_list_id` и `completed_list_id` — для переноса карточки формы), адрес WMS и
   машинный ключ.
4. **Машинный ключ чтения формы.** Придумайте длинную строку (например `openssl rand -hex 32`), задайте её
   в окружении API WMS как `WMS_SUPPORT_AGENT_KEY` (без неё ручки выключены и отвечают 404) и в конфиге
   агента как `wms.agent_key`. Миграций нет. Ключ даёт только чтение записей формы.
5. **Проверка версии на сервере.** `hotfix.deployed_sha_cmd` должна печатать SHA выложенного коммита, по
   умолчанию `ssh root@sellerfocus.pro git -C /opt/wms rev-parse HEAD`. Без неё хотфикс до merge не дойдёт.
   Перед выкладкой стоит добавить в `hotfix.preflight_cmd` проверку свободного диска (каждая выкладка
   делает дамп базы). `gh` должен быть авторизован (`gh auth status`).
6. **Расшифровка голоса (OpenAI, без локальных программ).** Голос уходит в OpenAI Audio Transcriptions API
   (модель `gpt-4o-mini-transcribe`, язык ru, настраивается в `transcribe`) по ключу владельца. Ключ положите
   в `~/.wms-support-agent/config.json` в поле `openai.api_key` либо задайте переменную окружения
   `OPENAI_API_KEY` (для службы launchd проще поле в конфиге). Telegram-голос (OGG/Opus) API принимает как
   есть; если формат отвергнут, агент один раз конвертирует его ffmpeg в wav и повторяет. На сервис уходит
   только аудиофайл голосового. Если расшифровка не вышла после повторов, владельцу придёт «не
   расшифровано», сообщение не теряется. Ключ нигде не печатается и в Git не кладётся.
7. **Макеты (по желанию).** `mockups.publish_cmd` — команда публикации папки макета (подстановки `{dir}`
   и `{name}`), `mockups.base_url` — адрес, по которому макет откроется без входа в WMS. Без них
   макет собирается локально, а в Telegram приходит путь и пометка, что публикация не настроена.

## Установка как службы (автозапуск и перезапуск)

```
tools/support_agent/launchd/install.sh
```

Скрипт копирует код в `~/.wms-support-agent/app` (смена ветки в репозитории службу не ломает), создаёт
venv, ставит `httpx`, проверяет конфиг (`python -m support_agent check-config`), регистрирует службу
`pro.sellerfocus.wms-support-agent` в launchd (`RunAtLoad` + `KeepAlive`: поднимается при входе в систему и
после любого падения). Если конфига нет, скрипт создаёт его из примера и просит заполнить. Лог:
`~/Library/Logs/wms-support-agent.log`. Остановить: `launchctl bootout gui/$(id -u)
~/Library/LaunchAgents/pro.sellerfocus.wms-support-agent.plist`. Обновить код: запустить скрипт ещё раз.

Пока мак спит или выключен, Telegram хранит необработанные сообщения до 24 часов; после возврата агент
один раз сообщает владельцу период простоя и сколько подобрано (если простой был дольше суток — что часть
сообщений могла потеряться). Чтобы мак не засыпал, при желании запускайте службу под `caffeinate -i`.

## Разработка и тесты

```
cd tools/support_agent
python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/python -m pytest tests -q
.venv/bin/ruff check . && .venv/bin/mypy support_agent
```

Тесты используют подделки Telegram, Trello, WMS, CLI-моделей и git/gh: реальных сообщений, карточек,
выкладок и обращений к проду в них нет.

## Что важно знать

- Граница на уровне ОС (macOS Seatbelt, `sandbox.enabled`, по умолчанию включена; если песочницы нет,
  запуск отклоняется, а не идёт без неё):
  - ruff, mypy и pytest из worktree запускает диспетчер под `sandbox-exec`: без сети, запись только в
    worktree и временный каталог, чистое окружение, чтение `~/.wms-support-agent`, `~/.ssh`,
    `~/.config/gh`, `~/.claude*`, `~/.aws`, `~/.docker`, `~/.netrc`, `~/Downloads/insurance-benchmark` и
    т. п. закрыто (список расширяется в `sandbox.extra_deny_read`).
  - Claude (разработчик, макетчик, аналитик): встроенная песочница Bash самого Claude Code
    (`sandbox.enabled`, без `allowUnsandboxedCommands`, `denyRead` по тому же списку), плюс запреты Read и
    разрешённые команды (чтение git, ruff, mypy, pytest, npm run build, npx tsc).
  - Codex-разработчик (Sol): командная оболочка и прочие инструменты Codex отключены
    (`--disable shell_tool --disable unified_exec ...`, `--ignore-user-config`), остаётся только правка файлов
    через apply_patch в его worktree под собственной песочницей Codex (`workspace-write`, без сети, `.git`
    только для чтения). Проверено вживую: shell, запись вне каталога, правка `.git/config` и чтение
    произвольного файла недоступны. Проверки (ruff, mypy, pytest) выполняет диспетчер под Seatbelt и
    возвращает результат разработчику.
  - Codex-аналитик (Sol): модельных команд у Codex нет вообще (shell и прочие инструменты отключены,
    `-s read-only`, `--ignore-user-config --ignore-rules`, штатный CODEX_HOME владельца без копий). Проект
    он читает только через доверенный MCP-читатель `support_agent/readonly_mcp.py` (list_files,
    read_file с лимитом, search, git_log, git_show): всё строго внутри корня worktree, пути
    канонизируются, `..`, абсолютные пути, символические ссылки, внутренности `.git`, `.env*` и файлы
    секретов отклоняются. Сервер запускается под `sandbox-exec` (чтение только корня и самого агента,
    без сети, без записи; чтение остального домашнего каталога закрыто). Всё, что аналитик пишет наружу
    (Telegram, Trello, имена и содержимое файлов), проходит маскировку секретов, имя файла выгрузки
    назначает агент (`export-<обращение>-<версия>.<csv|tsv|txt|json|md>`).
  - Git-метаданные: `<worktree>/.git` защищён от записи в песочнице (Seatbelt и Claude `denyWrite`); перед
    каждой привилегированной git-командой диспетчер сверяет `.git` с доверенной записью в основном
    `.git/worktrees` и подтверждает пути через `git rev-parse`; git в рабочих копиях запускается с
    `core.fsmonitor=false`, `core.hooksPath=/dev/null`, без внешних драйверов diff и без системного
    конфига; push и gh выполняются из основного репозитория.
  - Коммит (с номером WMS и Co-Authored-By), push, PR, merge, deploy и всё, что касается сервера, делает
    код диспетчера. Правка, затронувшая .github, скрипты выкладки или CI, останавливает хотфикс.
  - Ключи агента (OPENAI_API_KEY, GH_TOKEN и др.) в окружение дочерних процессов не передаются.
- Журнал службы: маскировка секретов на обработчике (включая traceback), журналирование URL у httpx выключено.
- Выкладка: `deploy.yml` и `scripts/deploy/prod-update.sh` получили НЕОБЯЗАТЕЛЬНЫЕ входы `sha` и
  `attempt_id` (обычный запуск без них работает как раньше). С `sha` сервер проверяет, что коммит входит в
  etalon, берёт скрипт выкладки из этого же коммита и выкатывает ровно его; `attempt_id` попадает в имя
  запуска. Агент передаёт коммит слияния и свой attempt_id, свой запуск опознаёт только по attempt_id,
  неизвестный исход не повторяет, а останавливается; ошибка чтения списка запусков не считается «запусков
  нет». Перед запуском агент проверяет, что в `deploy.yml` на etalon эти входы есть, и что вместе с хотфиксом
  не выложится чужих коммитов. ВАЖНО: изменение `deploy.yml` должно быть влито в etalon до первого хотфикса
  агента; иначе агент остановится с сообщением, не запуская выкладку.
- Агент не может узнать остаток лимита у CLI. Он идёт на первый из `llm.cli_order` и при отказе или
  лимите ставит CLI на паузу (`llm.cooldown_sec`) и переходит на второй. Если недоступны оба, обращение
  ждёт, владельцу приходит одно сообщение.
- Чтение боевой базы аналитиками (решение владельца В4, секция `prod_db`, по умолчанию ВЫКЛЮЧЕНО: тогда
  инструмента нет, а промпт запрещает выдумывать данные и требует `answer_needs_data`). Включённый
  режим даёт обоим аналитикам (Claude и Codex; роли analyst и review, только чтение) один инструмент
  `sql_query`. Клиент принимает один оператор SELECT, WITH или EXPLAIN (без ANALYZE), без комментариев,
  `;` внутри, обратного слеша, DML, DDL, COPY, SET, SELECT INTO, FOR UPDATE, опасных функций
  (pg_read_file, lo_*, dblink, pg_sleep и др.); SELECT и WITH оборачиваются в подзапрос с LIMIT
  `row_limit`+1, вывод режется по строкам и по размеру, есть таймаут. Сервер всё равно read-only
  (роль `wms_agent_ro`). Запрос уходит по ssh с отдельным ключом `~/.wms-support-agent/prod_ro_ed25519`.
  Формат, на который рассчитан клиент:
  ```
  ssh -F /dev/null -i <ключ> -o BatchMode=yes -o IdentitiesOnly=yes -o StrictHostKeyChecking=yes \
      -o ClearAllForwardings=yes -o ConnectTimeout=10 -T [-o UserKnownHostsFile=<known_hosts>] root@sellerfocus.pro
  ```
  SQL приходит в stdin (одной порцией, заканчивается переводом строки), на сервере forced command
  выполняет ровно `docker exec -i wms_prod-db-1 psql -U wms_agent_ro -d wms -X -v ON_ERROR_STOP=1 --csv`,
  ответ в stdout — CSV с заголовком; ненулевой код выхода трактуется как ошибка запроса (stderr, до 400
  символов, показывается аналитику), код 124 — таймаут клиента. Ключ видит только доверенный процесс
  MCP-сервера `prod_sql_mcp.py`: он запускается под `sandbox-exec` (запись запрещена, чтение домашнего
  каталога закрыто, кроме ключа, known_hosts и кода агента, сеть только исходящая на порт 22 и DNS);
  модели ключ недоступен (песочницы Claude и Codex по-прежнему запрещают `~/.wms-support-agent` и
  `~/.ssh`). Claude подключается через `--mcp-config` + `--strict-mcp-config` и в `allowedTools` получает
  только `mcp__proddb__sql_query`, Codex — вторым MCP-сервером рядом с читателем проекта. Границы
  клиентов: в промпте требуется отвечать клиенту только данными его организации и селлера из обращения;
  программной проверки этого нет (запросы свободные). Поэтому действует программное правило: если по
  обращению хоть раз успешно отработал `sql_query` (факт фиксирует доверенный сервер в файле следа в
  каталоге состояния агента, а не слова модели), то ЛЮБОЕ сообщение клиенту по этому обращению
  (уточняющий вопрос `need_data`, «пробуйте», информационный ответ) уходит только через дословный
  предпросмотр владельцу и подтверждение именно этого предпросмотра (ответом на него или «кати <номер>»;
  «всё кати» такие сообщения не подтверждает). Шаблонный вопрос о срочности не содержит текста модели и
  уходит как раньше; обращения без чтения базы работают как раньше. Лимиты вывода: stdout читается
  потоком с бюджетом байтов (при превышении процесс останавливается, результат обрезается с пометкой),
  stderr ограничен, длинное CSV-поле не роняет разбор, MCP-сервер отвечает ошибкой и продолжает работу.
- Форма «?»: при первом запуске агент берёт только новые записи (курсор ставится на момент запуска);
  разбор старых записей с даты включается явно настройкой `wms.backfill_since` (ISO-дата или время).
- Модели: Haiku — фильтр; Sonnet — рутина и хотфикс; Opus — разбор, интерфейс и макеты. При
  недоступности Claude всё это автоматически идёт на Sol 5.6 (`codex exec -m gpt-5.6-sol`), без вопроса
  владельцу. Astra — только перекрёстная проверка (работу Claude проверяет Astra high, работу Sol —
  Opus); на другую роль её поставить нельзя, код откажет.
- Информационные запросы и выгрузки: клиенту уходит только то, что владелец увидел дословно
  (текст и/или файл) и подтвердил ответом именно на тот предпросмотр. Общее «кати» или «всё кати»
  ответы клиентам не отправляет; если содержимое изменилось после предпросмотра, отправки нет.
- Выкладка катит всю голову etalon. Если там есть чужие невыложенные изменения, агент останавливается и
  спрашивает владельца (`hotfix.allow_foreign_commits=false`).
