# Доставка Telegram и сохранение истории

Это технические команды для обычного чата Codex. Они не распределяют обращения, не запускают агентов, не передают контекст и не будят чаты. Последующее поручение владельца 07.10.2026 разрешило доведение до работы и запуск; фактическую паузу, получение материалов и отправку проверяй через текущую установку.

Область доступа по последнему прямому поручению — только WMS, его служба, материалы обращений и WMS-модератор. Запрещено обращаться к страховому и другим проектам, включая их метаданные, проверку путей через stat/readlink/resolve и изменение настроек. Лишний чужой путь в профиле исправляется только в настройках WMS-чата/проекта; сам путь не исследуется. Это ограничение передаётся исполнителям и преемнику. На текущем старте активное обращение — только новый запрос распределения по коробам из чата «Короб / ФФ Империя Львов»; накопленная история остальных потоков не превращается в новые задачи.

Из `/Users/deniscivkunov/.wms-support-agent/app`:

```sh
.venv/bin/python -m support_agent.native_bridge status --json '{}'
```

Вместо `status` доступны команды ниже. Аргументы передаются JSON через `--json` или стандартный ввод. Конфигурация по умолчанию берётся из существующей установки; секреты выводить или менять не нужно.

- `status {}` — пауза, путь полной истории, последние номера сообщений и правок, краткие карточки.
- `inbox {"after_id": 856, "after_edit_id": 0, "known_materials": {"849": "сохранённый-hash"}, "limit": 100}` — сообщения и правки после указанных номеров. `edits[].current` содержит актуальное сообщение, чтобы прежняя сохранённая версия правки не подменяла текущий текст. `materials` содержит ранее прочитанные сообщения, материалы которых изменились: например, закончилась загрузка фото или появилась расшифровка голоса. `material_versions` возвращает нынешние отпечатки материалов. Сохраняй их и следующие номера после обработки. Чтение ничего не подтверждает и не распределяет.
- `watch {"after_id": 856, "after_edit_id": 0, "known_materials": {"849": "сохранённый-hash"}, "seconds": 45}` — те же данные с ожиданием до 45 секунд. Это ожидание текущего вызова, не фоновое расписание. Передавай сохранённую карту `known_materials`: без неё нельзя надёжно заметить готовое вложение сообщения, уже оставшегося до курсора.
- `history {"chat_id": 123, "limit": 100}` — последние сообщения и исходящие ответы этого чата; `before_id` позволяет читать более ранние страницы. Возвращает путь полной истории.
- `note {"chat_id": 123, "text": "Подтверждённый результат и источник", "kind": "finding", "topic_id": "обращение", "key": "устойчивый-ключ"}` — сохранить вывод. Повтор с тем же ключом не дублирует запись.
- `card {"topic_id": "обращение", "chat_id": 123, "title": "Короткая суть", "summary": "Текущий результат", "event": "Содержательное событие", "event_key": "ключ-события", "statuses": {"working": true}}` — создать или изменить единственную карточку. Возможные поля состояния: `working`, `analysis_done`, `answer_sent`, `owner_needed`, `development_needed`, `process_change`, `task_needed`, `task_created`. Ссылка задачи — `task_url`. Смысл и значения задаёт агент.
- `send {"chat_id": 123, "text": "Ответ", "key": "устойчивый-ключ"}` — одна явная отправка; дополнительно `reply_to` или `file_path`. Команда не отправляет старую очередь. Проверяй возвращённый статус; `pending` и `unknown` не означают доставку. Повторное действие при неизвестном исходе требует сначала выяснить его результат.
- `context {"thread_id": "идентификатор текущего чата"}` — последние сохранённые сведения об использовании контекста. Отсутствие счётчика не означает пустой контекст; передача остаётся решением модератора.

Ответ владельца на Telegram-карточку может содержать `case_topic_id`: это сохранённая связь с карточкой. Используй её вместе с текстом и историей, чтобы передать дополнение прежнему исполнителю. Она не является программной классификацией смысла обращения. Позиции сообщений/правок и карта версий вложений сохраняются вместе с рабочей памятью модератора и входят в сводку передачи.

`card` и `send` отказываются работать при сохранённой паузе. Возможность клиентских ответов определяется настройкой службы и поручением владельца. Сама служба принимает и сохраняет материалы в режиме `intake_only`; модератор работает в обычном чате Codex. Разрешение запуска дано владельцем отдельно; этот справочник не доказывает, что запуск или доставка уже состоялись.

Обычный видимый чат создаётся инструментом приложения `mcp__codex_app__create_thread` с проектом WMS и моделью `gpt-6.1-sol`. Его `threadId` сохраняется вместе с идентификатором единственного пробуждения. Инструмент `mcp__codex_app__automation_update` с `kind: heartbeat` продолжает этот же чат по расписанию. Это доставка сигнала агенту, без программного разбора содержания обращений. Через `list_threads`, `read_thread` и `wait_threads` можно проверить реальный чат и полученный результат; наличие записи thread id в конфигурации само по себе не подтверждает живого модератора.

Профиль запуска проверяется отдельно. `create_thread` не предоставляет параметров sandbox/approval/rootPaths, а `send_message_to_thread` меняет только модель/effort. Поэтому нельзя выдавать наличие общих `approval_policy=never`/`sandbox_mode=danger-full-access` за настройки нового чата приложения. В первом ходе чата №2 фактически сохранены `on-request` и `workspace-write` с лишними корнями записи WMS-проекта; ошибка одного такого корня привела к ожидающему ручному подтверждению. Это не автоматический отказ ревью. Изменение разрешено только в области WMS; подхват исправленного профиля доказывается следующим реальным ходом и исполнением команды. Переписывание локального файла состояния без проверки подхвата не является поддержанным API или работающим исправлением.

Проверка JSON сразу после записи подтвердила единственное изменение этого поля; другие записи и общие права не менялись. Следующее независимое чтение вернуло исходные корни: правка не сохранилась и живому чату не подтверждена. Прежняя запись только WMS и результат попытки сохранены в `var/support-conversations/moderator/wms-root-settings-correction.json`. Повторное переписывание кешируемого состояния не выполняется. Ожидающая команда не одобрялась и не исполнялась другим каналом.

Через доступные create/read/send инструменты установить профиль нельзя; доступ к UI Codex через Computer Use также отклонён самим инструментом. Не обходи этот отказ другими технологиями управления экраном. Если штатная замена чата не даст нужный профиль, резервный путь — однократная настройка владельцем самого WMS-чата: остановить ожидающий ход, выбрать режим `Full access` и продолжить тот же чат. Это не подтверждение каждой команды. Передача преемнику должна учитывать то же ограничение и проверить фактически выбранный профиль.

Последующее прямое поручение владельца разрешило остановить/перезапустить неисправный чат и дать полный доступ. Поддержанный `mcp__codex_app__fork_thread` с `environment: {type: same-directory}` создаёт обычную копию указанного Codex-чата, возвращает threadId и сохраняет его историю. Контракт не обещает наследования разрешений. Допустимая проверка — сначала завершить роль прежнего модератора, затем один раз создать форк действующего WMS-чата, новым поручением заменить унаследованную работу текущим разбором и проверить новый turn id/реальное исполнение без запроса escalation. Исторический скопированный профиль не является доказательством. Создание и активацию выполняет один ответственный, чтобы не получить двух модераторов; неподходящая проба не активируется. Форк не является переносом native-исполнителей и не отменяет правило сохранения результатов на диске.

Внутри текущего чата реальные инструменты работы с исполнителями — `collaboration.spawn_agent`, `send_message`, `followup_task`, `list_agents`, `wait_agent`. `send_message` доставляет дополнение работающему агенту, но не начинает новый ход завершённого. `followup_task` вызывает следующий ход прежнего агента, в том числе после его ответа. Для устойчивой связи сохраняются выданный agent id/полное имя и поручение. Инструмента переноса native-детей другому родителю среди доступных инструментов нет; новый чат восстанавливает недоступного исполнителя из сохранённых результатов, а не обещает прямой перенос.

Сохраняемый CLI-исполнитель запускается из его постоянного рабочего каталога, например:

```sh
codex exec --model gpt-6.1-sol --json --output-last-message /постоянный/путь/result.txt - < /постоянный/путь/task.txt
codex exec resume --model gpt-6.1-sol --json --output-last-message /постоянный/путь/result.txt SESSION_UUID - < /постоянный/путь/addendum.txt
```

Это шаблоны: подставь существующий каталог и точный id, полученный в событиях первого запуска. `--last` выбирает произвольную последнюю сессию и для привязки к обращению не подходит. Не используй `--ephemeral`: он отключает сохранение сессии. Права исполнения задаются по поручению и действующим правилам среды; эти команды не дают отдельного разрешения на секреты или внешние действия. Поддержка `exec resume` подтверждена справкой установленного Codex CLI 0.153.4; успешное возобновление конкретной сессии проверяется её реальным ответом.

При передаче около 250000 токенов обычный агент сохраняет сводку и одну отметку о переходе входящих, создаёт следующий обычный чат и переносит пробуждение на него. Старый чат только завершает прежних исполнителей и дописывает результаты, новый принимает дальнейший поток после сохранённых позиций. Подробные человеческие инструкции — в `NATIVE_MODERATOR.md`. Ни одна команда моста сама этого не делает.
