# A-2 — категория товара из предмета карточки Wildberries

## Вопросы исследования

1. Где WMS уже получает `subjectName` и почему этого недостаточно карте склада и раскладке?
2. Какое значение должно стать устойчивой категорией товара после синхронизации WB?
3. Как API должен отдавать список категорий, не смешивая тенантов и селлеров?
4. Что должно происходить, если WB не прислал `subjectName` или прислал пустую строку?
5. Какие изменения явно не входят в A-2?

## Подтверждённые факты

- В `products` нет устойчивого поля категории.
- WB уже присылает предмет карточки в `subjectName`; WMS умеет убрать внешние пробелы и отвергнуть пустое значение.
- Сейчас `wb_subject_name` вычисляется для `wb-catalog` и `ff-catalog` через соединение Product со снимком `SellerWildberriesImportedCard.raw_json`. Это не атрибут Product и не самостоятельный tenant-scoped справочник категорий.
- `upsert_products_from_wb_cards` создаёт отдельный Product для каждого штрихкода размерного варианта одной карточки. Следовательно, один предмет карточки должен попасть во все созданные или обновлённые варианты.
- Базовая товарная выдача `GET /products` уже ограничена `tenant_id`, а пользователь-селлер дополнительно ограничен эффективным `seller_id`.
- Исторические, ручные и Ozon-товары могут не иметь WB `subjectName`; выдумывать им категорию нельзя.

## Текущий WMS baseline

Пользователь уже может увидеть предмет WB в отдельных обогащённых каталогах, пока существует подходящий снимок карточки. Однако карта склада и раскладка работают с товаром как с устойчивой WMS-сущностью. Они не получают отдельный список категорий и не должны заново разбирать тяжёлый внешний JSON. A-2 переносит уже известный предмет WB в nullable-атрибут Product и даёт авторизованному потребителю список реально присутствующих категорий в его области данных.

## Противоречия

- Формулировка «у товара нет поля категории вообще» верна для модели Product, но в API уже существует вычисляемое поле `wb_subject_name` в двух специализированных каталогах. Новое поле не должно создать второй смысл: для WB-товара категория равна нормализованному `subjectName`.
- Источник категории внешний, но WMS хранит локальную копию Product. Поэтому синхронизация должна обновлять локальную категорию при непустом значении, сохраняя read-only принцип интеграции: никаких исходящих изменений карточки WB.

## Неизвестные и принятые допущения

- Владелец не задал отдельную таксономию или идентификатор категории. Принято: в A-2 хранится только отображаемое строковое имя предмета WB, без `subjectID` и без иерархии.
- Владелец не задал форму ответа. Для атомарной карточки принято: отдельная выдача категорий возвращает уникальный алфавитно отсортированный список непустых строк; точное имя маршрута Product Agent может подтвердить до dev.
- Для отсутствующего или пустого `subjectName` принято безопасное поведение: новый товар получает `NULL`, значение-заглушка не создаётся, такой товар не попадает в список категорий. Если при повторной синхронизации WB временно не прислал предмет, ранее известная непустая категория не стирается.
- Ручное назначение категории, категория Ozon и миграционный backfill из исторических `raw_json` не запрошены. Исторические Product остаются `NULL` до следующей успешной синхронизации соответствующей карточки.

## Риски

- Если список категорий строить по `SellerWildberriesImportedCard.raw_json`, карта снова будет зависеть от внешних снимков и может получить категории, не связанные с доступными Product.
- Если запрос категорий забудет `tenant_id` или seller scope, названия ассортимента одного клиента утекут другому.
- Если пустой `subjectName` превращать в `""`, `"Без категории"` или стирать им ранее известное значение, фильтр будет нестабилным после частичного ответа WB.
- Если обновить только ветку создания Product, повторная синхронизация существующего товара не исправит или не освежит категорию.
- Статический маршрут категорий должен быть объявлен так, чтобы динамический `/{product_id}` не перехватывал его.

## Конкретная передача Product Agent / архитектору

1. Подтвердить один смысл поля: `Product.category` — локальная nullable-копия WB `subjectName`, а не новый ручной справочник.
2. Зафиксировать минимальный контракт отдельной выдачи категорий: уникальные trimmed-строки из доступных Product, стабильная сортировка, `[]` при отсутствии.
3. Не расширять A-2 на фильтры или элементы экранов. Особенно запрещены любые изменения в:
   - `frontend/src/screens/ff/warehouse-map/`;
   - `frontend/src/screens/ff/sorting-objects/`;
   - `frontend/src/ui-kit/`.
4. Dev должен изменить только модель/добавляющую nullable-миграцию, обе ветки WB upsert (create и update), товарный API и backend-тесты. Исторический backfill и вызовы live WB не нужны.
5. До dev обязателен отдельный verdict `PRODUCT_APPROVED_FOR_DEV`; текущий результат — только `BA_READY`.
