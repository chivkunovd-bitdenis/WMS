# Product Before Dev — A-2 «Категория товара из предмета Wildberries»

## Что проверено

Карточка решает реальную подготовительную работу склада: перед анализом остатков или раскладкой сотруднику нужно отобрать товары по предмету, например оставить только футболки. Для этого карта и раскладка должны читать устойчивый атрибут WMS, а не каждый раз разбирать внешний снимок карточки Wildberries.

Предложенный смысл не создаёт новую товарную классификацию. В A-2 `Product.category` — это локальная nullable-копия непустого `subjectName`, полученного при read-only синхронизации Wildberries. Такой контракт минимален: он даёт будущим экранам нужный фильтр, не добавляет ручной справочник и не меняет карточку на стороне маркетплейса.

## Утверждённый продуктовый контракт

### Хранение и синхронизация

- `Product.category` хранит строковое имя предмета WB после удаления пробелов по краям. Регистр, написание и смысл значения WMS самостоятельно не исправляет.
- Поле nullable: ручные товары, товары Ozon и карточки без корректного `subjectName` остаются с `category = null`. Значения «Без категории» и пустые строки не создаются.
- Непустой `subjectName` записывается и при создании, и при повторной синхронизации во все размерные варианты Product, созданные из одной карточки.
- Если WB позднее прислал другое непустое имя предмета, локальная категория обновляется. Это нужно, чтобы исправление предмета в источнике дошло до фильтров WMS.
- Если при повторной синхронизации поле отсутствует, имеет неверный тип или состоит только из пробелов, ранее известная непустая категория не стирается. Частичный ответ внешней системы не должен внезапно убирать товар из складского фильтра.
- Отдельный исторический backfill в A-2 не требуется. Существующие WB-товары получают категорию при следующей успешной полной синхронизации карточек; WMS уже имеет штатный полный sync после deploy. Ошибка внешнего sync оставляет прежние данные без выдуманной замены.

### API товара

- Существующий `GET /products` добавляет в каждую строку поле `category: string | null`.
- Специализированное вычисляемое поле `wb_subject_name` в текущих WB/FF-каталогах не переименовывается и не удаляется в этой карточке. После успешной синхронизации его смысл для WB-товара должен совпадать с `Product.category`, но A-2 не расширяется на рефакторинг старых каталогов.

### API списка категорий

Утверждён маршрут:

```http
GET /products/categories
```

Успешный ответ — прямой JSON-массив строк без дополнительной обёртки:

```json
["Брюки", "Футболки"]
```

Правила ответа:

- только категории реально доступных вызывающему Product;
- только непустые значения;
- точная дедупликация одинаковых строк;
- стабильная алфавитная сортировка; при равных значениях порядка сортировка не зависит от плана запроса БД;
- `[]`, если в доступной области нет ни одной категории;
- без пагинации, поиска, счётчиков товаров и дерева категорий в A-2.

Статический маршрут должен быть объявлен до динамических маршрутов вида `/{product_id}`, чтобы строка `categories` не интерпретировалась как UUID товара.

### Доступ и область данных

Маршрут категорий использует тот же read-access и тот же seller scope, что `GET /products`:

- любой запрос ограничен `user.tenant_id`;
- fulfillment admin и сотрудник с действующим доступом к товарному каталогу получают категории доступного каталога своего тенанта;
- пользователь-селлер получает категории только Product своего effective seller, включая уже существующий выбор доступного магазина для seller manager;
- отсутствие авторизации и прав возвращает действующие `401/403`, а не пустой ответ, маскирующий ошибку доступа;
- передаваемый клиентом `seller_id` для FF-пользователя в A-2 не добавляется. Если будущему экрану понадобится зависимый список категорий после выбора селлера, это должно быть явно принято в карточке самого экрана вместе с его сценарием доступа.

Такая граница нужна не только для безопасности: селлер не должен выбирать категорию, в которой у него физически нет ни одного товара, а сотрудник другого фулфилмента не должен видеть названия чужого ассортимента.

## Состояния процесса

**Успех.** После успешной WB-синхронизации все варианты карточки возвращают один нормализованный предмет в `Product.category`, а список категорий содержит его один раз.

**Пустое состояние.** Товары без категории по-прежнему возвращаются через товарный API с `category: null`; отдельный маршрут категорий возвращает `[]`. Это честное состояние данных, не ошибка и не повод создавать заглушку.

**Частичное состояние.** Если синхронизация одного селлера не прошла, уже известные категории сохраняются, а новые появятся после успешного повтора. Категории других селлеров и тенантов не используются для заполнения пробела.

**Ошибка.** Ошибка WB остаётся ошибкой синхронизации и не меняет контракт чтения категорий. Ошибка авторизации или прав остаётся `401/403` согласно существующим зависимостям API.

## Обязательное доказательство в разработке

Dev и последующий reviewer должны доказать backend-тестами:

1. Одна карточка с пробелами в `subjectName` и несколькими размерами создаёт/обновляет каждый Product с одной trimmed-категорией.
2. Повторная синхронизация обновляет категорию новым непустым предметом, но пустое, отсутствующее или нестроковое значение не стирает ранее известное.
3. `GET /products` возвращает `category`, в том числе `null` для товара без источника.
4. `GET /products/categories` возвращает уникальный отсортированный непустой список и `[]` для честного пустого состояния.
5. Два тенанта и два селлера не смешиваются: seller получает только effective seller, а FF-пользователь не выходит за свой tenant.
6. Статический маршрут реально достигается и не перехватывается динамическим `/{product_id}`.

Эти проверки покрывают `TC-NEW-A2-001` — `TC-NEW-A2-004` из BA-карточки. Новый API без тестов изоляции и пустого состояния продуктово не принимается.

## Сознательные non-goals

- Любые изменения карты склада, раскладки и `ui-kit`.
- Фильтр или новый видимый элемент на существующем экране.
- Ручное редактирование категории и общий справочник категорий.
- `subjectID`, иерархия, синонимы, объединение похожих названий и статистика количества товаров.
- Категория из Ozon либо автоматическая категория для ручных товаров.
- Исходящая запись в WB.
- Отдельный seller-фильтр для FF admin/staff без утверждённого сценария будущего экрана.

## Продуктовые риски, остающиеся после approval

- До первой успешной синхронизации после выкладки исторические WB Product останутся без категории. Это допустимое переходное состояние A-2, но deploy/sync и фактическое заполнение должны проверяться отдельно от кода.
- WB может изменить написание предмета. A-2 намеренно хранит последнее непустое имя источника и не вводит собственную таксономию; из-за этого две различающиеся строки могут остаться двумя категориями.
- Прямой массив строк — минимальный контракт. Если будущему экрану понадобятся идентификаторы, счётчики или зависимость от выбранного селлера, нельзя молча менять этот ответ: потребуется отдельная совместимая карточка API.
