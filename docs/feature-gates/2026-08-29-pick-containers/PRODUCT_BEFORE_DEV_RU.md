# Product Before Dev: физическое место товара в подборе

Карточка `PICK-CONTAINERS-01` решает реальную складскую ошибку: одной ячейки
недостаточно, когда в ней стоят несколько коробов, грузомест или палета с
вложенным коробом. Оператору нужен не новый справочник и не технический UUID, а
тот же путь до товара, который уже показывает карта склада: сначала ячейка либо
«Без ячеек», затем палета, затем конечный короб или грузоместо. Если тары нет,
конечный источник должен называться «Россыпью».

Разработка разрешена как одна backend-карточка для двух `pick-options`. Развести
контракты отгрузки на маркетплейс и FBS нельзя: это одна физическая структура
склада, и разные названия или порядок заставят оператора по-разному читать одно
и то же место.

## Минимальный продуктовый контракт для Dev

Шесть существующих полей объекта в `locations` — `storage_location_id`,
`location_code`, `quantity`, `reserved`, `available`, `picked` — остаются с
прежними именами и смыслом. К объекту места добавляется одна одинаковая в обоих
endpoint структура физических источников. Технические имена может выбрать Dev,
но форма и смысл обязательны:

- список физических источников товара внутри данного места;
- у каждого источника есть его количество, явный признак россыпи и упорядоченный
  путь тары;
- путь тары — список от внешнего объекта к внутреннему: `Палета` первой,
  `Короб` или `Грузоместо` вторыми; для товара прямо на палете список состоит из
  одной палеты;
- каждый элемент пути несёт машинный вид (`pallet`, `box`, `cargo_place`), ID,
  человеческий код и готовое человеческое название. Названия строго
  `Палета <код>`, `Короб <код>`, `Грузоместо <код>`;
- для россыпи признак истинен, путь тары пуст, человеческое название источника
  равно `Россыпью`; вымышленная тара запрещена;
- человеческие коды разрешаются ровно как в `warehouse_map_service`: код палеты
  из `Pallet.code`, сквозной короб/грузоместо из
  `WarehouseBox.internal_barcode`, приёмочный короб как `КР-` плюс шестизначный
  номер, приёмочное грузоместо как `ГМ-` плюс шестизначный номер;
- `location_code` для системной ячейки `__SORTING__` наружу равен
  `Без ячеек`. Сам технический код не должен появляться ни в одном новом
  добавочном поле;
- короб или грузоместо на палете нельзя сокращать до одного конечного объекта:
  ответ обязан содержать обе ступени в указанном порядке;
- разные физические источники в одной ячейке не сливаются внутри добавочной
  структуры. Это позволяет подключающему экран разработчику показать отдельные
  источники, не ломая действующего потребителя шести старых полей;
- тара без обычной ячейки остаётся в выдаче под верхним адресом `Без ячеек`;
- контейнеры разрешаются только в tenant и на складе документа. Неразрешимую
  ссылку на тару нельзя молча превратить в россыпь или заменить объектом другого
  склада.

Пример смысла добавки (имена ключей здесь иллюстративны, не дополнительное
требование к неймингу):

```json
{
  "storage_location_id": "...",
  "location_code": "СТЕЛЛАЖ 1.1",
  "quantity": 12,
  "reserved": 0,
  "available": 12,
  "picked": 0,
  "sources": [
    {
      "quantity": 7,
      "is_loose": false,
      "source_label": "Короб КР-000041",
      "container_path": [
        {
          "kind": "pallet",
          "id": "...",
          "code": "П-000131",
          "label": "Палета П-000131"
        },
        {
          "kind": "box",
          "id": "...",
          "code": "КР-000041",
          "label": "Короб КР-000041"
        }
      ]
    },
    {
      "quantity": 5,
      "is_loose": true,
      "source_label": "Россыпью",
      "container_path": []
    }
  ]
}
```

Карточка не меняет списание, сканирование и фиксацию подбора: текущий факт
подбора остаётся привязанным к товару и ячейке. Поэтому `reserved`, `available`
и `picked` не следует выдуманно распределять по таре. Если Dev выберет плоскую
строку на каждый источник вместо вложенного списка, он обязан доказать
обратную совместимость количеств и отсутствие удвоения существующим клиентом;
без такого доказательства приемлема только добавочная вложенная форма выше.

Frontend, его типы, подписи и разметка в эту карточку не входят и изменяться не
должны.

## Rework Product Before Dev после CODE_REVIEW_FAILED

Усиленные BA-критерии принимаются без изменения продуктового контракта. Они не
добавляют новый складской процесс и не расширяют карточку за пределы backend:
они требуют доказать на границах обоих HTTP endpoint уже одобренную структуру и
fail-closed поведение (явный отказ на неконсистентных складских данных вместо
ложного ответа «Россыпью»).

Обязательный минимальный rework для Dev:

- оба HTTP-теста создают реальный положительный остаток в таре и проверяют
  непустой `sources[].container_path` с `kind`, строковым UUID `id`, `code` и
  `label`, а в том же объекте — неизменные значения шести старых полей;
- хотя бы один HTTP-тест проходит вложенный путь из двух элементов, но форма
  `sources` подтверждается отдельно через каждый из двух сериализаторов;
- общий сервис отдельными сценариями подтверждает прямой путь `Палета`, путь
  `Палета -> Короб` и путь `Палета -> Грузоместо`;
- отсутствующая или чужая тара проводится через общий построитель мест и через
  оба внешних endpoint. Она обязана завершиться осознанной HTTP-ошибкой, а не
  ответом `200` с `Россыпью`; статус и тело ошибки должны быть одинаковыми для
  двух endpoint либо различие должно быть явно обосновано существующим
  контрактом ошибок;
- frontend по-прежнему не меняется; полный pytest, npm и Playwright не входят в
  разрешённый прогон этой карточки.
