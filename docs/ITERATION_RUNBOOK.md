## 1. Что это за прогон

Итерация закрывает накопленный список правок, собранный **на живых созвонах с заказчиками**:
три записи общей длительностью около двух часов, где владелец продукта и реальные
фулфилменты прошли по экранам и отметили, что мешает работать.

Ключевое следствие: **требования уже утверждены людьми**. Их не нужно переосмысливать,
оспаривать или улучшать. Их нужно точно внести и убедиться, что экран после этого удобен
в работе. Продуктовая критика применяется к тому, **как сделано**, а не к тому, **надо ли это**.

Прошлая попытка этого прогона провалилась: продуктовую проверку в браузере поставили **до**
разработки, она проверяла ненаписанные фичи, выносила «на переделку» девять раз из девяти,
и за сутки не появилось ни строчки кода. Регламент переписан. Не повторяй эту схему.

## 3. Единица работы — экран

Задачи сгруппированы по экранам. Один агент берёт **экран целиком со всеми его задачами**
и делает их за один заход. Не по одной фиче: агент один раз разбирается в коде экрана,
а продуктовая проверка судит готовый экран, а не четыре фичи по очереди.

Каждый экран работает в своём worktree внутри `.worktrees/`, с уборкой за собой.

## 4. Сквозные правила — их соблюдают все, они не принадлежат экрану

Эти требования не назначаются отдельному агенту. Их обязан выполнять **каждый**, кто трогает
любой экран. Если сделать их «фичей одного экрана», они не приживутся нигде.

- **Единое поведение кнопок документа.** «Сохранить» сохраняет и не закрывает. «Закрыть» и
  крестик закрывают. При несохранённых изменениях — подтверждение «Закрыть без сохранения?».
- **Человеческий язык статусов.** Никаких `receiving`, `DRAFT`, `seller first` и прочих enum
  в пользовательском тексте.
- **Цвет статуса, а не только текст.** Статусы сейчас серые и тусклые. Цвет меняется вместе
  с состоянием: красный — ошибка или блокировка, жёлтый — требует внимания, зелёный — готово.
- **Нет визуального мусора.** Каждый чип, колонка, кнопка и подпись имеют рабочий смысл;
  дубли удаляются или объединяются.
- **Адресное хранение — глобальная настройка.** Выключено — ячейки нигде не обязательны
  и не мешают процессу; включено — ячейка появляется только там, где есть физическая раскладка.
- **Навигация обновляет данные.** Переход в раздел сам подтягивает актуальный список.
- **WB API-gate.** Любая WB-зависимая функция до разработки требует явного указания endpoint,
  ограничений, формата ответа, возможных ошибок и допустимого fallback.

## 6. Роли агентов на экран

По каждому экрану последовательно, по регламенту:

**Спека экрана.** Читает задачи экрана из бэклога, читает текущий код, пишет одну спеку:
что меняем, что убираем, как выглядит результат, состояния успеха, ошибки и пустоты.
Пятнадцать минут. Не технический план, а описание поведения.

**Сверка спеки.** Отдельный агент проверяет только полноту: все ли задачи экрана вошли,
нет ли противоречий, не потеряна ли деталь из бэклога. Пять-десять минут. Браузер не открывает,
удобство процесса не обсуждает.

**Разработка.** Один агент делает все задачи экрана пачкой в своём worktree. Перед сдачей
локальные проверки: `ruff check . && mypy . && pytest` в `backend/`,
`npm run build && npm run test:e2e` в `frontend/`.

**Продуктовая проверка в живом браузере.** Изолированный агент, настоящий внешний Chrome,
проходит сценарий руками: успех, ошибка, пустое состояние, перезагрузка с чтением обратно,
ширина 1280 на самых длинных реальных данных. Судит по списку «так выглядит принято».
Playwright, headless, API, скриншоты и чтение кода приёмкой **не являются**.

**Пинг-понг.** Находки приходят разом, уже разложенные по трём вёдрам и сгруппированные
по причине. Разработчик чинит одной пачкой, тот же продуктовый агент перепроверяет ровно
этот список. Максимум два раунда.

## 7. Пинг-понг — правила, чтобы не утонуть

Экран может дать двадцать находок. Правила, которые делают это подъёмным:

**Продакт сортирует сам, а не сваливает список.**

- **Стоп** — работу выполнить нельзя: нет выхода с экрана, нет нужного действия, падает,
  теряет данные, кнопка врёт. Чинится всё, потолка нет.
- **Тормоз** — работа идёт, но дороже: едет колонка, спрятана кнопка, дубль чипов, текст
  переносится, непонятная подпись. Пять штук за раунд, самых дорогих для оператора.
- **Хвост** — на работу оператора не влияет. Сразу в бэклог, в пинг-понг не попадает.

Важно: слипшиеся колонки, переносы, дубли и спрятанные кнопки — **не косметика**. Они стоят
оператору времени на каждой строке, и место им в «Стоп» или «Тормоз», а не в «Хвосте».

**Группировать по причине.** «Уехали четыре колонки» — это одна сломанная сетка, а не четыре
находки. Обычно это схлопывает список втрое.

**Клапаны.** Если первый же прогон дал больше восьми находок в «Стоп» — пинг-понг не начинается,
экран возвращается на разработку целиком. Если после второго раунда «Стоп» остались — экран
помечается незакрытым и уходит пользователю. Третьего раунда по кругу нет.

**Не переделывать аналитику из-за исполнения.** Кривая колонка, неудобная кнопка, съехавший
блок — это правки, а не смена замысла. Спека не переписывается, к стадии 1 не возвращаемся.
Возврат в начало нужен только если выяснилось, что делаем **не то**.

**Изоляция против памяти.** Первый прогон — изолированный агент, нужен свежий взгляд. Раунды
правок — **тот же** агент с сохранённым контекстом, иначе он потребует вернуть то, что вы
сознательно решили оставить. Разработчик на раундах трогает **только** список.

## 8. Когда экран готов

Одновременно: все задачи экрана внесены; ноль находок в «Стоп»; «Тормоз» пуст или явно
перенесён пользователем в бэклог; есть commit SHA. «Хвост» на готовность не влияет.

После обеих волн — общая стадия интеграции: ветки сводятся, прогоняется сквозной сценарий
через несколько экранов подряд, чтобы поймать межэкранные конфликты.

## 9. Отчётность

По каждому экрану после каждой стадии — короткий блок, всегда одинаковый:

```
Экран: <название>
Стадия: <номер и название>
Статус: <результат>
Commit: <SHA или «нет»>
Находки: Стоп N / Тормоз N / Хвост N
Раунд правок: 0 | 1 | 2
Блокеры: <список или «нет»>
```

Плюс сводка по всему прогону, обновляемая по мере движения: сколько экранов на какой стадии,
сколько закрыто, где блокеры. Она должна читаться за тридцать секунд без открытия других файлов.

Запрещено писать «готово», «принято» или «можно деплоить», если по экрану не выполнены все
условия раздела 8 и не назван commit SHA. Зелёные тесты и CI обязательны, но продуктовой
приёмкой не являются.

## 10. Чего делать нельзя

- Начинать работу, пока первая строка этого файла не `STATUS: READY`.
- Ставить продуктовую проверку в браузере **до** разработки — именно это сорвало прошлый прогон.
- Отклонять экран из-за неуверенности. Отказ — только при названной находке «Стоп» с
  объяснением, какую работу она ломает.
- Переосмысливать требования. Они утверждены живыми заказчиками. Несогласие фиксируется
  отдельной строкой пользователю, а не превращается в отрицательный вердикт.
- Обнулять работу и переписывать спеку из-за правки исполнения.
- Использовать `git add .` — staged changes всегда точечные.
- Ставить в одну волну экраны из списка пересечений раздела 5.
- Трогать секреты, токены и переменные окружения без отдельного явного запроса пользователя.
- Писать «готово» без commit SHA.

## 11. Что в эту итерацию не входит

Участники созвонов решили это отдельно, в работу не берём: чаты внутри системы вместо
телеграма; настраиваемые колонки через шестерёнку; отдельный вход для логиста; вся тема
биллинга и счетов за услуги фулфилмента — учёт веса и разгрузки, палетирование, счета
за период. По биллингу назначен отдельный разговор.
