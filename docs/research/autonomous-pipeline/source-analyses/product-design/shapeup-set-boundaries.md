# Shape Up — Set Boundaries

## 1–2. Источник и доказательность

[Set Boundaries](https://basecamp.com/shapeup/1.2-chapter-03), Shape Up, Basecamp, проверен 2026-08-24. E2: первичное описание внутренней product practice Basecamp; не эмпирическое сравнение и не software-agent protocol.

## 3–5. Задача и путь

Глава предлагает shaping до betting: одновременно задать appetite (фиксированное время/стоимость), solution boundary и необязательные детали. Appetite — не estimate и не deadline; он ограничивает, сколько проблемы стоит решать. Shape должен быть достаточно конкретен, чтобы команда не начинала discovery заново, и достаточно неполон, чтобы не проектировать каждую деталь заранее.

## 6–13. Исполнимые pre-design gates

Для **нового модуля** `SHAPE-BOUNDARY` содержит: problem, appetite (token/time/число допустимых файлов или stages), solution boundary, core path, explicit non-goals, rabbit holes, and stop/de-scope rule. Для **локальной правки** нужна сокращённая boundary: affected zone, allowed files, non-goals и максимум один rework scope; appetite малый. Controller проверяет наличие и прекращает бесконтрольный diff; модель предлагает trade-off внутри границы; owner только устанавливает appetite/подтверждает новый domain. Артефакт — scope contract, не mockup; browser/Git/retry в главе отсутствуют.

## 14. Границы

Аппетит не говорит, нужна ли фича пользователю и не заменяет evidence. Он также не должен становиться предлогом закончить плохое решение в срок.

## 15–16. WMS-применимость и вердикт

Взять ограничение свободы до разработки: «одна локальная правка» не может превратиться в redesign экрана. Для нового отчёта boundary объединяется с user/outcome gate, а не заменяет его. Вердикт: адаптировать appetite как machine-enforced budget/scope, отвергнуть формальное копирование циклов Shape Up.
