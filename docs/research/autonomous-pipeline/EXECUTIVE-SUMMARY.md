# Итог исследования простыми словами

## Главный вывод

Текущий pipeline не надо выбрасывать. В нём уже есть несколько правильных вещей: отдельные worktree,
checkpoint commits, file gates, ограниченный rework, browser evidence и попытка запретить diff вне
scope. Проблема в другом: вокруг этих механизмов построено слишком много модельных стадий, а реальное
управляющее состояние всё ещё хранится в смеси Markdown, regex, Git и живого процесса.

Из-за этого система одновременно дорогая и хрупкая:

- на один новый домен уходит примерно 16–21 модельный вызов ещё до повторов;
- маленький visible fix автоматически получает Product/UX/mockup/full review chain;
- product scope может расшириться до того, как machine allowlist начнёт что-либо защищать;
- Docker, browser, flaky test и code defect не являются полноценными разными состояниями;
- commit карточки называется «СДЕЛАНО», хотя push, интеграция и полный regression могут отсутствовать;
- независимые роли могут идеально проверить одну и ту же неверную product hypothesis.

## Что показал кейс «Остатки и движения»

Первоначальная оценка была слишком жёсткой: Product и UX действительно продумали экран. Они
определили аудитории, три основных вопроса, фильтры, показатели, график, таблицы и сознательно выкинули
финансы, продажи, PDF и конструктор отчётов.

Но затем один экран попытался одинаково обслуживать ФФ и селлера и одновременно объединить:

- снимок остатка сейчас;
- приход/расход за период;
- сравнение прошлого периода;
- разрез по товарам и операциям;
- поиск, склад, селлера и CSV.

Каждый элемент имел объяснение, но никто не проверил более простой вопрос: может ли незнакомый
пользователь без инструкции понять экран и решить с его помощью конкретную задачу. Reviewer, UI critic
и judge проверяли соответствие контракту, созданному тем же pipeline. Это замкнутая самопроверка, а не
независимая валидация пользовательской модели.

Отчёты по хранению и биллингу исследование не объявляет плохими. Владелец отдельно скорректировал эту
оценку; их нужно рассматривать самостоятельно.

## Что делают работающие системы

Собрано 279 каталожных записей (с намеренными пересечениями между кодом, papers и полевыми кейсами)
и подробно разобрано 34 источника. Их общая практическая линия:

1. Переходами, лимитами и retries владеет код, а не модель.
2. State живёт вне процесса агента и восстанавливается после падения.
3. Результат стадии имеет typed machine object и отдельный human report.
4. Agent report никогда не заменяет filesystem/Git/test evidence.
5. Retry происходит только после классификации ошибки.
6. Один связный repair лучше десятка atom-передач.
7. Тест/PR/trace — отдельные доказательства, но ни одно само по себе не означает product acceptance.
8. Новый модуль сначала доказывает user outcome и первый vertical slice; маленькая правка получает
   короткий путь без discovery и полного redesign.

## Предлагаемый минимальный pipeline

Постоянно нужны только три модельные ответственности:

- **Shaper** — только когда меняется поведение или появляется модуль; формулирует цель, границы и
  проверяемый контракт.
- **Builder** — реализует один связный slice в machine allowlist.
- **Verifier** — независимо проверяет исходную просьбу, diff, tests и живой пользовательский сценарий.

Всё остальное выполняет controller: intake, state, retries, Git, tests, browser execution, evidence,
integration и утренний отчёт.

Номинальная цена в вызовах:

- локальный `PATCH` — Builder + Verifier, 2 вызова;
- `CHANGE` существующего flow — Shaper + Builder + Verifier, 3;
- первый slice нового `MODULE` — обычно 3, иногда 4 с отдельным архитектурным research;
- один repair — ещё один Builder и повторный Verifier на замороженных findings.

## Как избежать фантазий при короткой постановке

Сразу после диктовки pipeline делает короткий preflight. Он показывает, какие задачи уже готовы к
ночи, где использует обратимые assumptions и где есть действительно необратимое решение.

Без ответа владельца:

- локальные правки выполняются;
- обратимые changes выполняются с журналом assumptions;
- новый module может дойти до purpose/shape и первого безопасного slice;
- деньги, необратимые данные, новая физическая обязанность оператора, внешний contract или secret/deploy
  authority ставят только эту карточку в `WAITING_OWNER`.

Остальная волна продолжает работу.

## Как сделать pipeline «железным»

Не обещать отсутствие сбоев. Обещать, что каждый ожидаемый сбой имеет состояние и конечный маршрут:

- controller хранит run/task/attempt в SQLite;
- перед model/test/deploy side effect создаётся attempt;
- после падения происходит reconcile по process, worktree, SHA и artifact;
- pre-start environment failure безопасно рестартуется максимум дважды;
- fail/pass test становится `flaky`, не зелёным;
- deterministic test/review failure идёт в coherent repair;
- повтор той же сигнатуры или два repair rounds завершаются точным blocker;
- неизвестная ошибка сохраняет logs/trace и не запускает retry storm.

## Что внедрять первым

Не начинать с переписывания ролей. Последовательность:

1. SQLite state, lease, attempts и restart reconciliation поверх текущего runner.
2. Failure taxonomy и evidence manifests.
3. Короткий `PATCH` route на реальной локальной правке.
4. `CHANGE` route с purpose/delta и goal-based browser acceptance.
5. Только затем `MODULE`, first-slice barrier и integration state.
6. После пилотов удалить лишние роли из default path.

Так каждый шаг отдельно доказывает пользу, а новая архитектура не становится ещё одним большим
непроверенным проектом.
