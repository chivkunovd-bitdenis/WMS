## 2. Фактическая топология

Runner — один Python-процесс. Он хранит состояние в файлах Markdown, Git-ветках карточек и
нескольких JSON/metadata-файлах. Внешнего брокера, базы состояния и отдельного durable workflow
engine нет.

Высокоуровневый путь:

```text
список владельца
  -> intake: карточки + дословные источники
  -> analyst по каждой карточке
  -> requirement-critic по каждой карточке
  -> общий MAP.md
  -> отдельные worktree карточек
  -> [для доменов] solution-architect
  -> [для 2+ доменов] общий arch-critic / ARCH-CROSS.md
  -> product
  -> ux-architect
  -> tester -> breaker
  -> splitter
  -> 1..6 последовательных dev-атомов
  -> reviewer -> ui-critic
  -> clicker -> ux-judge
  -> commit existence gate
  -> [только если все карточки завершены] общий product-acceptor
```

Для backend-бага часть стадий короче. Для видимого frontend-бага runner снова добавляет UX,
breaker, ui-critic и browser chain. Новый домен всегда получает полную цепочку.

## 3. Модели и реальная стоимость одной карточки

Ролевое поле `model` преобразуется runner так:

- `opus` → `gpt-5.6-sol`, reasoning `xhigh`;
- `sonnet` → `gpt-5.6-terra`, reasoning `high`;
- `haiku` → `gpt-5.6-luna`, reasoning `low`.

Для одной доменной карточки без повторов вызываются как минимум:

| Стадия | Профиль |
|---|---|
| intake на всю волну | Luna |
| analyst | Sol |
| requirement-critic | Sol |
| общий MAP | Sol |
| solution-architect карточки | Sol |
| product | Sol |
| ux-architect | Sol |
| tester | Terra |
| breaker | Terra |
| splitter | Terra |
| каждый dev-атом, от 1 до 6 | Luna |
| reviewer | Sol |
| ui-critic | Terra |
| clicker | Luna |
| ux-judge | Sol |
| product-acceptor на всю волну | Sol |

При двух и более доменных карточках добавляется общий `arch-critic` на Sol. Итого даже одна
простая реализация внутри доменного маршрута означает примерно 16 модельных вызовов при одном dev-атоме
и до 21 при шести — до rework и повторов. Это объясняет значительную часть стоимости и времени без
необходимости предполагать, что отдельные агенты обязательно работали плохо.

## 4. Где живёт состояние

### 4.1. Артефакты ролей

Таблица `АРТЕФАКТ` в `scripts/night.py` связывает роль с именем файла и обязательными заголовками:
`ISTOCHNIK.md`, `RAZBOR.md`, `SVERKA.md`, `ARCH.md`, `RESHENIYA.md`, `CONTRACT.md`, `CASES.md`,
`FEATURES.md`, `DEV.md`, `REVIEW.md`, `DESIGN-REVIEW.md`, `CLICKS.md`, `JUDGE.md` и `OTCHET.md`.

Сильная сторона: финальная фраза агента не управляет процессом. Если требуемого файла нет, стадия
не пройдена.

Ограничение: для большинства артефактов runner проверяет лишь наличие файла и заголовков. Это
гарантирует форму, но не истинность, полноту или соответствие исходной просьбе. Отдельные проверки
содержания есть только для узких случаев: машинного вердикта, ссылки в `ARCH.md`, числа атомов,
маркеров mockup и части scope.

### 4.2. Машинные строки

Управляющие роли обязаны писать строку вида:

```text
ВЕРДИКТ: ЧИСТО
ВЕРДИКТ: РЕШЕНО
ВЕРДИКТ: НАХОДКИ 3
ВЕРДИКТ: НЕ РЕШЕНО 2
```

Это хороший ремонт прошлого дефекта, когда свободная фраза «нарушений не найдено» была ошибочно
прочитана как наличие находок. Но протокол остаётся слабой текстовой схемой: нет JSON Schema,
перечня finding ID, класса сбоя, fingerprint входа и связи решения с конкретной версией diff.

### 4.3. Git и worktree

Каждая карточка получает отдельные branch и worktree. После каждого dev-атома controller:

1. вычисляет изменённые пути;
2. сравнивает их с файлами, перечисленными splitter в атоме;
3. добавляет только разрешённые файлы и `DEV-NN.md`;
4. создаёт checkpoint commit.

В конце runner требует, чтобы HEAD отличался от base SHA и чтобы implementation diff был чистым;
SHA записывается в `BRANCH-SHA.txt`.

Это заметно сильнее исходной версии с `git add -A`, захватывавшей чужие артефакты. Однако terminal
state `СДЕЛАНО` всё ещё не требует upstream/push, PR, интеграции с другими карточками, полного
регресса или deployed SHA. Общий `product-acceptor` явно получает указание не объединять ветки.
Следовательно, runner завершает **принятые карточные ветки**, а не готовую интегрированную фичу.

## 5. Как выбирается маршрут

Тип `баг | фича | домен` сначала определяет analyst, затем может исправить requirement-critic.
Runner предпочитает строку `ТИП: ...`, но сохраняет fallback-разбор прозы.

Маршруты:

- backend-баг: `product → tester → splitter → dev → reviewer → ui-critic → clicker → ux-judge`;
- видимый frontend-баг: `product → ux-architect → tester → breaker → splitter → dev → reviewer → ui-critic → clicker → ux-judge`;
- фича: тот же полный UX-маршрут;
- домен: перед ним добавляется `solution-architect`.

Проблемы маршрутизации:

1. Даже backend-баг содержит `ui-critic`, `clicker` и `ux-judge`, хотя экран может не меняться.
2. Любой видимый frontend-баг получает обязательный `MOCKUP.html`, даже если требуется одна локальная
   правка текста или состояния. Это прямой механизм непропорциональности.
3. Есть только три продуктовых типа. Нет явного класса «локальная правка существующего поведения»,
   «новый экран в существующем домене» и «инфраструктурное восстановление».
4. Тип выбирает модель, хотя часть классификации можно вывести детерминированно из разрешённых файлов,
   реестра экранов, миграций и интеграций.

## 6. Где принимаются продуктовые решения

После анализа все вопросы складываются в `VOPROSY.md`, но отсутствие ответа владельца намеренно не
останавливает pipeline. Роль `product` на Sol обязана самостоятельно закрыть каждую развилку.

Prompt одновременно требует:

- искать живые внешние источники;
- выбирать самый простой вариант;
- не добавлять лишних сущностей и экранов;
- не задавать вопросы владельцу;
- всё равно принять конкретное решение, чтобы ночь не остановилась.

Последние требования конфликтуют. Если исходник уровня «сделай отчёт по хранению» не определяет
пользователя, решения и обязательные показатели, product должен либо придумать их, либо нарушить
требование закрыть все вопросы. Слова «не расширяй» не устраняют этот конфликт.

Дополнительный разрыв: backend-dev в своём prompt говорит «не можешь решить — передай product», но
product уже пройден, а обратного перехода `dev → product` в state machine нет. На практике остаются
самовольное решение, неполная реализация или парковка.

## 7. Проектирование интерфейса

`ux-architect` читает продуктовые решения, канон, реестр экранов и UI-kit. Для затронутого экрана
он создаёт `CONTRACT.md` и, как правило, самостоятельный `MOCKUP.html`. Runner проверяет, что HTML
открываемый и содержит комментарий `UI-KIT`, но не способен проверить:

- что макет является дельтой к существующему экрану, а не новым самостоятельным миром;
- что каждый видимый элемент прослеживается до запроса;
- что экран отвечает одному главному пользовательскому решению;
- что информационная иерархия понятна на реальных данных;
- что mockup действительно использует компоненты и размеры React UI-kit, а не только их имена.

Следовательно, scope gate после splitter может идеально запретить лишние файлы и при этом сохранить
изначально неверный, но формально утверждённый широкий контракт.

## 8. Разработка и scope gate

Splitter ограничен шестью первичными атомами и тремя repair-атомами. Каждый атом должен принадлежать
только frontend или backend, перечислять точные файлы и выполняется последовательно.

Плюсы:

- конкретный allowlist файлов;
- checkpoint после каждого атома;
- запрет полного тестового набора на каждом мелком шаге;
- группировка повторных находок по слою и общим файлам;
- запрет разделить один файл между несколькими repair-атомами.

Минусы:

- frontend и backend одной вертикальной возможности искусственно разделены, хотя проверяемый
  пользовательский результат возникает только вместе;
- до шести последовательных контекстов dev на одну карточку увеличивают потери контекста;
- controller не умеет параллельно выполнить независимые атомы внутри карточки, хотя splitter обязан
  описывать порядок;
- точные разрешённые файлы определяет модель уже после потенциально ошибочного контракта;
- часть интеграции откладывается до reviewer: полные проверки запрещены на атомах, но отдельного
  гарантированного integrated-card test gate до reviewer в state machine нет для обычного прохода.

## 9. Review и browser acceptance

После dev идут:

1. `reviewer` — код и поведение;
2. `ui-critic` — статическое соответствие канону/контракту;
3. `clicker` — живой браузер и screenshots;
4. `ux-judge` — дорогой вердикт по `CLICKS.md`, изображениям и инвариантам.

Здесь есть важное расхождение с проектным `AGENTS.md`: он требует, чтобы судья сам открыл настоящий
браузер и руками прошёл сценарий. Фактический prompt `ux-judge` прямо запрещает ему ходить в браузер;
он судит материалы дешёвого clicker. Это может быть рациональной оптимизацией, но сейчас это неявное
изменение критерия приёмки.

Карточка 07-reporting особенно показательна. Она получила чистые reviewer/ui-critic/JUDGE и была
закрыта как браузерно принятая. При этом пользователь после просмотра назвал экран «Остатки и
движения» главным визуально непонятным примером. Значит, цепочка хорошо проверила соответствие
собственному контракту и канону, но не доказала исходный вопрос: кому предназначен отчёт, какую
задачу он решает и видит ли человек главный смысл без изучения всех контролов и графика.

Дополнительно сохранённый `CLICKS.md` карточки 07 сообщает, что MUI Select не удалось прокликать
живым browser runtime, а переключение было подтверждено Playwright. `JUDGE.md` принял эту замену.
Это ещё одно отличие «живого ручного прохода» от фактического evidence.

## 10. Повторы, rework и восстановление

Для шага, который не создал валидный артефакт, runner делает одну повторную попытку с текстом ошибки
машинного гейта. Обычный timeout — 20 минут, dev — 40 минут.

Отрицательный reviewer/ui-critic/ux-judge verdict:

1. увеличивает номер круга;
2. вызывает splitter для нового repair-plan;
3. возвращает только к dev;
4. повторяет downstream review;
5. после обычного круга использует до двух Terra-repair циклов;
6. затем паркует карточку.

Отдельно распознаются несколько текстовых признаков недоступного браузера. Тогда код не отправляется
на ремонт, `CLICKS.md`/`JUDGE.md` удаляются, а следующий resume стартует с clicker.

Сильная сторона — bounded rework и попытка отличить browser infrastructure от code finding.

Слабые стороны:

- классификация инфраструктурной ошибки основана на наборе русских/английских фраз в Markdown;
- нет структурированного `failure.json` с классом, exit code, retryability и fingerprint;
- retry повторяет почти тот же вход без обязательного изменения среды;
- Docker, disk-full, network, model limit, flaky test и deterministic test failure не образуют разные
  машинные состояния;
- durability обеспечивается файлами в worktree, но process crash между побочным эффектом и записью
  артефакта не имеет transactional reconciliation;
- `night_health.py` наблюдает процесс и стенд, но не является полноценным supervisor с ownership,
  lease и гарантированным restart/resume.

## 11. Терминальные состояния

Фактически есть три исхода карточки:

- `сделано` — цепочка артефактов пройдена и есть отдельный commit;
- `отложено` — создан `OTLOZHENO.md` с причиной;
- процесс оборвался — состояние выводится косвенно по файлам и журналу при следующем запуске.

Но `сделано` не означает:

- branch pushed;
- PR создан и required checks зелёные;
- карточки интегрированы между собой;
- полный backend/frontend regression пройден на интегрированном SHA;
- deployment создан из этого SHA;
- live browser проверил именно deployment.

Поэтому термин «СДЕЛАНО» внутри runner семантически сильнее доказательств, которые он требует.

## 12. Что уже действительно стоит сохранить

До внешнего синтеза можно уверенно сохранить как сильные локальные механики:

- отдельный worktree/branch на карточку;
- Git checkpoint после каждого осмысленного изменения;
- управление по артефакту, а не сообщению агента;
- однозначные машинные verdict strings вместо разбора свободной прозы;
- fail-closed prerequisite prefix при resume;
- bounded rework;
- отделение browser-infra blocker от дефекта кода;
- точный file allowlist на implementation;
- общий cross-card architecture barrier для связанных доменов;
- запрет объявлять волну завершённой при незавершённой карточке.

Эти элементы ещё не составляют надёжный end-to-end pipeline, но их не нужно выбрасывать только ради
новой архитектуры.

## 13. Главные вопросы для внешнего исследования

1. Как заменить Markdown-regex control protocol на минимальную typed state machine без тяжёлой
   платформы?
2. Как отделить product uncertainty от права самостоятельно расширить операторский процесс?
3. Как проверять design purpose и information hierarchy до дорогого mockup/dev?
4. Как сделать путь локальной правки действительно коротким?
5. Как классифицировать test/browser/Docker failures и безопасно retry только retryable классы?
6. Как reconcile состояние после падения controller между command, file write и Git commit?
7. Как определить настоящий terminal success: commit, push, integration, CI, browser, deploy?
8. Какие роли можно заменить кодом или объединить без потери независимой проверки?
