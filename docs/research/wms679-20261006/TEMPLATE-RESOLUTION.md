# WMS-679: официальный XLSX WB и границы интеграции

Проверено 07.10.2026 в рамках read-only исследования. Этот документ не меняет
продуктовый контракт и не утверждает, что какой-либо файл был принят WB.

## Результат

Точный бинарный шаблон `shk-excel.xlsx` **не получен**. Поэтому в репозитории не
добавлена самодельная или похожая XLSX-фикстура. Узкий блокер — скачать пустой
шаблон из конкретной FBW-поставки в WB Partners: публичная статья ведёт к кнопке
в поставке, а публичный web-клиент получает байты только с `incomeID` и
сессионными учётными данными.

Найденная в другой исторической ветке `source415.xlsx` намеренно не использована:
её отчёт описывает файл как присланную выгрузку FBS-заказов («Сборочные задания»),
а не как шаблон наполнения FBW. Его SHA-256 —
`c39f9df8d54d747560178bd1609df1a6790344b0e7444bafb722df2cbeb6be55`;
происхождение и назначение не соответствуют этой фикстуре.

## Что подтверждено официальными материалами

Официальная инструкция WB «Этап 2. Наполнение упаковки» (обновлена 05.10.2026)
предписывает в XLSX указать баркод товара, количество, срок годности при его
наличии и ШК упаковки; для нескольких товарных баркодов одного короба ШК короба
повторяется. В сохранённой иллюстрации видны четыре заголовка: «Баркод товара»,
«Кол-во товаров», «ШК короба», «Срок годности». Инструкция доступна по адресу
<https://seller.wildberries.ru/instructions/ru/ru/material/step-two-fbw-package-filling>.
Сохранённый текст имеет SHA-256
`f5512e7be7d6a0aced8c3d495a7ef0047ae19285b2a1eb1fa021adaf86c48862`,
изображение колонок —
`fa3a03f51103935e247df1222477a2acddb006e10b433ded083eebb1fa228e72`.

Это подтверждает смысл видимых колонок, но **не** имена листов, типы ячеек,
скрытые поля, правила валидации и формат даты настоящего XLSX. Статья предлагает
получить именно файл кнопкой «Скачать шаблон» внутри поставки, а не даёт
публичную ссылку на байты.

Публичный asset WB подтверждает, как кабинет получает этот файл:

- config `vol20/menu/v0.0.1/config.json` задаёт
  `https://seller-supply.wildberries.ru/ns/sm-box/supply-manager/api/v1/box/getTemplateXLS`;
- bundle `supply-detail-packaging-nano/v1.0.66/645.chunk.fa4c5ad064581d15d891.js`
  (SHA-256 исходного asset
  `175e1a59424b86bbbb15ad7d8a577ff2acd263dfca1661ba1395cb70e9186a67`)
  вызывает JSON-RPC с телом `{ "params": { "incomeID": … } }`,
  `credentials: "include"`, затем ожидает `{file, mime}` и сохраняет
  `shk-excel.xlsx`.

Локальные сохранённые извлечения config и chunks имеют SHA-256 соответственно
`c66d430a00ab6eded1a55dd0ff2328a0efa508d201e559d72f896f2cae584ee0` и
`e377c9b658275c6a228c0211270b58ed46b1bde177359b4df79b97ffb197997c`.
Это первичное доказательство механизма кабинета, но не документированный
публичный API автоматизации: запрос привязан к сессии кабинета и конкретной
поставке. В этой сессии CUA-браузер не доступен, поэтому авторизованная сессия,
cookie и кабинет не открывались.

## WHB/INB: что известно и чего нет

Официальная статья разрешает самостоятельно генерировать ШК упаковки для
XLSX. Публичный клиент WB дополнительно содержит точное сообщение об ошибке:
при самостоятельной генерации ШК короба код не должен начинаться с `WB_`.
Это отрицательное ограничение, а не полный опубликованный валидатор.

В WMS `generate_box_barcode` создаёт `WHB-` или `INB-` плюс 14 символов
Crockford Base32: 18 символов, только латиница/цифры/`_`/`-`, и не `WB_`.
Старый INB имеет форму `INB-` плюс 12 hex-символов. Следовательно, такие строки
не нарушают **известный** запрет WB и проходят собственную синтаксическую
проверку WMS. Однако это не доказывает, что WB примет конкретные existing
WHB/INB в загрузке: полного формата, уникальности в поставке и фактической
приёмки официальный публичный источник здесь не устанавливает. Проверка
загрузкой не запускалась, потому что она меняет внешнюю поставку.

Есть также локальное различие, важное для будущей реализации: для складского
WHB `MarketplaceUnloadBox` хранит `warehouse_box_id`, а API выдаёт
`warehouse_box.internal_barcode`. При attach существующего INB сервис находит
`InboundIntakeBox`, но создаёт `MarketplaceUnloadBox` без `warehouse_box_id`.
Значит, текущая связь сама по себе не сохраняет INB как экспортируемое поле;
это факт кода, не основание заменять код или добавлять сущность без решения
разработчика.

## Состав коробов и QR: нет подтверждённого публичного API

В том же публичном asset присутствуют кабинетные endpoints
`createBoxBarcodes` и `bindBarcodes`, и для них также задано
`credentials: "include"`. Это показывает механизм интерфейса WB Partners,
но не даёт публичный контракт: неизвестны официальные scope/права, точные тела,
идемпотентность и правила восстановления после неизвестного результата.

Страница `https://dev.wildberries.ru/openapi/orders-fbw` в ранее сохранённой
проверке возвращала HTTP 498 («Проверяем браузер»). Это означает только
недоступность документации из того контекста; оно не доказывает ни отсутствие,
ни наличие метода записи состава коробов или QR.

Для QR официальный путь разделён по пункту сдачи: в ПВЗ нужен QR, созданный и
распечатанный в WB Partners; для иных точек внешний сервис кодирует значение из
столбца «ШК короба для печати в сторонних сервисах» после оформления поставки.
Этот код не доказан равным existing WHB/INB и не должен подменяться внутренним
Code 128 WMS. Публичный XLSX-шаблон для загрузки не требует самостоятельно
заполнять этот печатный столбец.

## Минимум, необходимый для снятия блокера

1. Владелец либо уполномоченный пользователь скачивает **пустой** шаблон кнопкой
   WB Partners из конкретной FBW-поставки и передаёт сам исходный XLSX. Нужны
   дата получения, URL статьи/экран действия и SHA-256 файла; идентификаторы
   поставки и селлера можно обезличить. После этого можно зафиксировать
   бинарную fixture без догадок.
2. Чтобы доказать допустимость именно existing WHB/INB, нужен опубликованный WB
   валидатор либо отдельное явное разрешение на контролируемую загрузку в
   тестовую/расходную поставку. Такое действие не выполнялось и не входит в
   read-only поручение.
3. Чтобы реализовать передачу состава или печать внешнего QR через API, нужен
   точный официальный публичный OpenAPI-контракт WB: URL, авторизация и права,
   request/response, идемпотентность и обработка неизвестного результата. До
   этого допустим только честный XLSX-путь без заявлений об API-отправке.

## Срок годности в текущем проекте

В модели `Product` есть только `wb_shelf_life: String(255)` — текстовая
характеристика длительности срока. Поиск моделей и миграций не нашёл даты
окончания срока, партии либо поля, связанного с `MarketplaceUnloadBoxLine`.
Единственное найденное поле `mchd_valid_until` относится к учётным данным
маркировки продавца, а не товару. Поэтому `wb_shelf_life` нельзя преобразовать
в дату для XLSX: для товаров со сроком источник фактической даты остаётся
неустановленным.
