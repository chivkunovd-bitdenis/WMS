## Официальный XLSX и коды

Источник: [WB Partners — Этап 2. Наполнение упаковки](https://seller.wildberries.ru/instructions/ru/ru/material/step-two-fbw-package-filling), отметка «Обновлено 05.10.2026», HTTP 200. [Сохранённый текст](evidence/seller-package-filling-text.txt), [HTML в gzip](evidence/seller-package-filling.html.gz), [изображение колонок](evidence/template-columns.webp), [изображение действия загрузки](evidence/template-download.webp), [адреса и контрольные суммы](evidence/sources.json).

Официальное изображение шаблона прочитано визуально. Заголовки в нём: A «Баркод товара», B «Кол-во товаров», C «ШК короба», D «Срок годности». Пример: товар `4567788`, количество `100`, короб `234566`. Это иллюстрация формата, не реальная поставка и не доказательство того, что код короба обязан быть числовым.

Инструкция предписывает скачать шаблон в поставке, заполнить баркоды, количества, сроки годности для соответствующих товаров и ШК упаковки, затем нажать «Загрузить файл». Для разных баркодов в одном коробе повторяют его ШК в каждой строке. При ошибке «Не найден ШК короб...» статья предлагает проверить формат столбца, в том числе текстовый. Отдельной колонки размера на изображении нет: нужен баркод соответствующего размера товара из каталога WB, без выдуманного дополнительного столбца.

**Бинарный официальный XLSX не скачан.** В публичной статье нет прямой ссылки на него; инструкция направляет к кнопке «Скачать шаблон» в кабинете поставки. Не проверены имена листов, скрытые поля, проверки ячеек, даты и фактический разбор файла кабинетом. Заголовки подтверждены изображением WB, но этого недостаточно для заявления о готовой выгрузке. Минимальная зависимость перед реализацией — сам официальный файл и согласованный пример.

Статья разрешает самостоятельно генерировать ШК упаковки для заполнения XLSX, однако не задаёт здесь допустимый алфавит, длину или запрет префикса `WB_`. Регулярное выражение WMS `^[A-Za-z0-9_-]{6,30}$` и локальная проверка префикса — факты реализации, а не подтверждённый актуальный контракт WB. Проверки загрузки значений `WHB-…`/`INB-…` не выполнялись.

Для **печатной этикетки** инструкция задаёт другой контракт:

1. ПВЗ: только ШК, созданные и распечатанные в WB Partners; сторонние ШК не принимаются.
2. Другие пункты: сторонняя генерация/печать использует только данные из столбца «ШК короба для печати в стороннем сервисе» (в одном абзаце назван «…в сторонних сервисах»). WB пишет, что использование других данных приводит к отказу приёмки.
3. При заполнении упаковки через XLSX обязателен столбец «ШК короба»; специальный столбец для печати самостоятельно заполнять не нужно.

Таким образом, исходное пожелание «один код WMS и WB» сохранено, но одинаковость внутренней строки, поля загрузки и содержимого печатного QR не доказана. Требование печати для WB должно учитывать текущий официальный маршрут. Это не разрешение заменять идентификатор существующего короба или создавать другую независимую сущность.

## API: граница установленного

Официальный адрес: [FBW Orders](https://dev.wildberries.ru/openapi/orders-fbw). Проверены русская и английская страницы, а также кандидаты публичной спецификации `/swagger/orders-fbw.yaml` и `/swagger/orders-fbw.json`; все вернули 498. Для кандидатов YAML/JSON это **не доказательство ни наличия, ни отсутствия файлов**: ответ пришёл от защиты сайта. В отдельном чистом контексте Chrome страница показала «Проверяем браузер»; [текст](evidence/fbw-browser-text.txt), [ответы браузера](evidence/fbw-browser-responses.json). Авторизованные профили, ключи и кабинеты учётных данных не использовались.

Ни один официальный метод **записи FBW** для состава «код короба — товарный баркод/размер — количество» в этом ходе не подтверждён. Точные тело запроса, идентификатор поставки, права, лимиты и ограничения неизвестны; их нельзя заимствовать у FBS. Публичная инструкция XLSX также не доказывает отсутствия API.

Прочитанный код WMS:

- `backend/app/services/wildberries_client.py::fetch_supplies_list` вызывает `POST /api/v1/supplies` на Supplies API для **чтения списка FBW**. Фильтры dates/statusIDs и limit/offset не являются передачей товарного состава.
- `POST /api/v3/supplies`, `POST /api/v3/supplies/{supply_id}/trbx`, `PATCH …/trbx/{trbx_id}`, `POST …/trbx/stickers` в этом же файле относятся к **FBS**, созданию поставок/грузомест и привязке сборочных заданий; в коде используются `orderIds`, не товарные строки FBW.

Это точные найденные пути **кода WMS**, не перечень методов сегодняшней официальной спецификации WB. Исторический `docs/research/20260827-wb-box-barcodes.md` не принят за сохранённую спецификацию: он содержит авторские выводы, а текущая инструкция допускает собственные ШК в XLSX. Отсутствие функции записи в WMS не использовано как доказательство отсутствия у WB.
