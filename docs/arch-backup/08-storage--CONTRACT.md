# 08-storage · Хранение: считать, менять габариты и брать деньги · CONTRACT

Артефакт: `/Users/deniscivkunov/Projects/WMS/.worktrees/.night-worktrees/volna-9/lane-2-08-storage/night/volna-9/cards/08-storage/CONTRACT.md`.

Задача — превратить пустой `S-11 /app/ff/inventory` (`FfPlaceholderPage`, `frontend/screens.registry.json`) в реальный экран учёта хранения. Владелец описал целый раздел («получать габариты, менять руками, фиксировать изменения, устанавливать цену за литр, печатать сводную накладную, брать деньги»); согласно принципу «Реально ли без этого нельзя обойтись?» проектирую **один экран** с двумя уровнями (сводка + детализация в боковой панели), а «Историю габаритов» и «Товары без габаритов» **не выделяю в отдельные маршруты**, а прикладываю к уже существующим (карточка товара, каталог с фильтром).

Разбор, ARCH и Сверка лежат рядом в этой же папке.

## Контракт

### Экран S-11 «Хранение» (заменяет `FfPlaceholderPage`)

**Маршрут:** `/app/ff/inventory`. Портал: FF. Роль доступа: `isFulfillmentAdmin` (по образцу «Тарифов ФФ» в `FfSettingsScreen`).

**Зоны (сверху вниз):**

1. **`ScreenHeader`** — заголовок «Хранение», подстрочник «Сколько лежит и сколько стоит». Больше в шапке ничего (R-01, R-02).
2. **Блок «Тариф ФФ»** — отдельный `Paper variant="outlined"` над фильтрами. Внутри одной строкой:
   - «Общий тариф ФФ: **<X коп/литр/день>**, действует с <дата>» (крупным, без заголовка блока)
   - `SecondaryAction` «Изменить тариф» справа (R-31 контурная рядом с главным на строке; главное действие «Закрыть период» живёт в детализации селлера, но эта Secondary привязана к смысловой паре «тариф — счёт», допустима как единственный вход в редактирование тарифа; **канон не покрывает случай одиночной Secondary без соседнего Primary → предложено R-37, см. ниже**).
   - Если тарифа нет ни одного — вместо цифры плашка `ErrorNotice` с текстом «Задайте тариф — без него счёт не считается» и `PrimaryAction` «Задать тариф» (R-23 применяем шире «ошибки данных»; строгий смысл R-23 — только техническая ошибка → предложено R-38).
3. **`FilterBar`** — поиск по названию селлера (`search`), в `children` два `Select` (год + месяц МСК; по умолчанию — текущий месяц) (R-03). Отдельного «пикера периода» в ui-kit нет — пишу в нехватку.
4. **`DataTable`** «Селлеры за <месяц>» — сводка, единственная главная таблица экрана (R-04, R-07, R-09, `stickyHeader` из DataTable — R-05).
5. **Боковая панель детализации** — открывается по клику на строку селлера (`IconAction` «Открыть детализацию» в конце строки, потому что весь `TableRow` кликабельным DataTable не делает и это удобно для селектора). Панель — второй `Paper variant="outlined"` внизу под таблицей или боковой `Drawer` — **в ui-kit сейчас нет ни того ни другого способа показать детализацию** (см. нехватку ui-kit). До появления элемента панель рисуется как второй `Paper` под таблицей, чтобы не изобретать Drawer «на бумаге».
6. **Модалка «Изменить тариф»** — открывается из блока «Тариф ФФ» и из детализации селлера (там для override). MUI `Dialog` (модалка — не элемент ui-kit, но паттерн есть на десятках экранов, R-01/R-02 говорят только о теле экрана).

### Чего на экране осознанно нет (границы, R-8 канона: «не добавлять без задачи»)

- Автоматической рассылки счетов селлерам (владелец не просил, фаза 2).
- Селлерского кабинета «Мои счета за хранение» (данные для этого лягут в `billing_ledger`, но UI селлера — фаза 2).
- Прогрессивной шкалы тарифа (плоский, override на селлера).
- Тарифа по категории товара / типу ячейки / палеты.
- НДС (см. `docs/MVP_DECISIONS_RU.md`).
- Обмена с 1С / УПД / ЭДО / ЭП.
- Ежедневного снимка (`stock_daily_snapshot`) — считаем на лету из `inventory_movements`.
- Массовой правки габаритов (Excel-загрузка) — только руками по одному SKU в карточке товара.
- Полноценного документа «Invoice» с шапкой, статусами оплаты — это уровень 09-billing.
- «Открыть период заново» после закрытия. Корректировка — только сторно в `billing_ledger` (механизм 09).
- Отдельного экрана «История изменений габаритов» и отдельного экрана «Товары без габаритов» — свернуто в блок карточки товара и фильтр каталога.

### Что решено ночью за владельца (правится утром)

Взято из `ARCH.md`, повторяю чтобы утро не искало по разбору.

1. Тариф-заглушка **15 коп/литр/день** (~0,15 ₽/литр/день), с явной подсказкой «Задайте свой тариф».
2. День приёмки **считается** (сутки, где на конец дня остаток ненулевой).
3. Порога минимальной суммы счёта **нет** — любая ненулевая сумма формирует накладную.
4. Менять тариф может **только FF-админ** (`isFulfillmentAdmin`).
5. Товар в пути X→Y на конец дня считаем по `warehouse_id` последнего успешного `inventory_movement` (взаимодействие с 04-warehouse-switch).

## Нехватка ui-kit

Чтобы собрать экран без изобретательства «на бумаге», в `frontend/src/ui-kit/index.ts` не хватает трёх элементов. Все три — прямо из требований этого экрана, не «на будущее»:

1. **`MoneyCell`** — денежная ячейка для сумм в рублях/копейках (`value_kopecks` → «12 345,67 ₽», `align="right"`, `fontVariantNumeric: 'tabular-nums'`, `null → —`, опционально `muted`). Сейчас у денег нет своей ячейки: пришлось бы либо тиражировать форматирование через `TextCell`, либо гнуть `QtyCell`. Хранение — первый WMS-экран, где деньги видит оператор построчно; вторыми будут накладная 09-billing, отчёты 07, зарплата упаковщика.
2. **`SidePanel` / `Drawer` (детализация строки)** — единый способ показать «детали одной строки». Экран `S-11` требует показать по клику на селлере товары, суммы, кнопки «Закрыть» и «Скачать». Второй `Paper` под таблицей — обход, не решение: при большом числе селлеров теряется контекст выбранной строки. Аналог уже нужен и в 06 (`FfFbsSupplyDrawer`), но у него своя реализация; ui-kit-компонент закрыл бы обе задачи одним элементом.
3. **`PeriodPicker`** — выбор календарного месяца/года МСК одним контролом (для `FilterBar.children`). Пока рисуется двумя MUI `Select` (год + месяц) прямо на экране — работает, но выглядит как «оператор собирает дату вручную». Тот же контрол нужен 07 (отчёты), 09 (счета за период). Отдельного правила канона про выбор периода тоже нет — вместе с элементом должно появиться R-4X «периоды выбираются `PeriodPicker`».

Также в каноне попутно предложены **R-37, R-38, R-39, R-40** (см. секцию «Канон» выше) — их добавление или отклонение остаётся за владельцем/продактом, не блокирует ночь.
