# CONTRACT — 07-reporting

Контракт экрана раздела «Отчёты». Опираюсь на решение архитектора (`ARCH.md` вариант А:
единый `ReportsHubScreen` + реестр отчётов, одна ручка `/reports/{id}`). Первая волна —
пять отчётов, каркас общий и для портала ФФ, и для портала селлера.

Экраны новые, в `frontend/screens.registry.json` их сегодня нет. Предлагаю зарегистрировать:

- **S-33** · портал **ff** · роут `/app/ff/reports` · компонент `ReportsHubScreen`,
  зоны: `шапка`, `фильтры`, `навигация отчётов`, `таблица`, `сводка`, `график`,
  `панель действий`.
- **S-34** · портал **seller** · роут `/reports` · тот же компонент `ReportsHubScreen`,
  зоны те же (портал берётся из props, список разрешённых отчётов режется реестром).

Существующий `S-11` (`/app/ff/inventory`, `FfPlaceholderPage`) карточка не задевает —
он про модуль хранения (08-storage), это соседняя история. Существующий `FfReportsPage`
(в реестре не отмечен) внутри `ReportsHubScreen` становится первым отчётом
`product_movements`, отдельный роут не заводим.

Мобильного клиента раздел не касается — только ПК.

## Контракт

### 0. Каркас экрана (общий для обоих порталов)

- **Шапка экрана.** `ScreenHeader` из ui-kit. Название: **«Отчёты»**. Одна строка
  назначения: **«Данные по складу, приёмкам, отгрузкам и остаткам за период»**. Ни
  счётчиков, ни KPI-плашек в шапке нет.
- **Двухпанельный лейаут.** Слева — вертикальный список отчётов (навигация раздела).
  Справа — рабочая область выбранного отчёта: полоса фильтров, таблица, строка сводки,
  график, панель действий. Слева и справа — каждый в своём `Paper variant="outlined"`.
- **Список отчётов слева.** Простой вертикальный список названий (не таблица, не чипы,
  не «карточки»): каждый пункт — короткое имя отчёта + подпись `body2 secondary` из
  одного предложения «на какой вопрос отвечает». Выбранный подсвечивается фоном
  primary (тон `neutral`). Порталу селлера в списке видны только четыре отчёта:
  `product_movements`, `on_hand`, `inbound_seller`, `outbound_seller`, `aging`. Порталу
  ФФ видны те же пять плюс отдельного не заводим — «по продавцу», «по складу», «по
  маркетплейсу» реализуются переключателем разреза (`group_by`) внутри отчёта, а не
  отдельным пунктом списка (принцип «одна настройка на несколько сценариев»).
- **Пустой раздел.** Если реестр отчётов для текущего портала пуст (гипотетически) —
  `EmptyState`: «Отчётов пока нет. Появятся, когда включим новые разрезы».
- **Единый рабочий контейнер.** Правая часть — один `Paper variant="outlined"`
  (шапка отчёта + фильтры + таблица + сводка + график + действия внутри него), без
  вложенных «карточек в карточке».

### 1. Шапка выбранного отчёта

- **Название отчёта** — `Typography variant="h6"` (внутри рабочего `Paper`, не путать
  с `h5` заголовка экрана).
- **Одна строка назначения** — `body2 color="text.secondary"`, отвечает на вопрос
  пользователя: «Что показано на этом экране».
- **Одна оговорка о времени** — `body2 color="text.secondary"` серым:
  **«Время событий — по журналу ФФ, не по данным маркетплейса»** (только на отчётах,
  где это существенно: `inbound`, `outbound`, `product_movements`).
- Ни счётчиков в шапке отчёта, ни статусов, ни ссылок. Все действия — внизу в панели.

### 2. Полоса фильтров (`FilterBar` из ui-kit)

Один и тот же набор для всех отчётов (принцип «шапка одна на всех»). Каждое поле
показывается только там, где имеет смысл — R-06 (поле показывается только когда
бывает заполнено, обратной стороной: не показываем то, что не работает в конкретном
отчёте).

- **Поиск** — встроенный `search` из `FilterBar`, плейсхолдер:
  **«Поиск по названию, артикулу, SKU, ШК»**.
- **Период с — по** — два поля даты. Пресеты быстрого выбора: **«Сегодня»,
  «Неделя», «Месяц», «Квартал», «Год», «Свой»** (шесть текстовых кнопок в один
  ряд, `SecondaryAction`; активный — заполненная). По умолчанию открыто **«Месяц»**
  (умолчание вместо выбора).
- **Сравнение** — селект с четырьмя значениями: **«Без сравнения», «Прошлый
  период», «Год назад», «Свой период»**. По умолчанию — «Прошлый период»
  (индустриальный дефолт ShipHero/ShipBob/Cin7).
- **Разрез** (`group_by`) — селект. Значения зависят от отчёта:
  - `product_movements`: «По товару» (единственное значение — просто скрываем поле).
  - `on_hand`: «По товару», «По складу», «По селлеру» (для ФФ), «По ячейке».
  - `inbound`: «По товару», «По селлеру» (для ФФ), «По складу», «По дню».
  - `outbound`: «По товару», «По селлеру» (для ФФ), «По складу», «По маркетплейсу»,
    «По дню».
  - `aging`: «По товару», «По складу», «По селлеру» (для ФФ).
- **Селлер** — селект. Виден **только на портале ФФ**. У селлера selector фильтруется
  жёстко его `seller_id`, поле не показываем (умолчание вместо выбора, при одном
  доступном значении показывать не надо).
- **Склад** — селект. Если у арендатора один физический склад — поле не показываем
  (пересекается с 04-warehouse-switch: «пока склад один, выбора склада быть не должно
  нигде»). При двух и более — селект со всеми складами арендатора.
- **Маркетплейс** — селект. Виден **только в отчёте `outbound`** (в остальных отчётах
  МП не появляется как разрез — не показываем поле, R-06).

Полоса фильтров едет липко в шапке правой панели: длинные списки не должны заставлять
пользователя листать наверх ради смены периода.

### 3. Таблица отчёта — общие правила (одна для всех пяти)

- `DataTable` из ui-kit (`stickyHeader`, `size="small"`, `Paper variant="outlined"` —
  всё уже в компоненте).
- Числа — `QtyCell` (правое выравнивание, табличные цифры).
- Ширины колонок фиксированные (R-09).
- Заливок строк нет: цветом покрашена может быть только строка расхождения
  (R-11) — в отчётах эта колонка появляется только в `on_hand` (когда `актуальный
  остаток ≠ последней инвентаризации`), в остальных четырёх отчётах `hasDiscrepancy`
  не передаём.
- Скелет строк на загрузке (R-22). Спиннера поверх таблицы нет.
- Пустое состояние (`EmptyState` через `DataTable.empty`): «Нет данных за выбранный
  период — попробуйте расширить диапазон или снять фильтры». Никаких «Нет данных.» с
  точкой в конце.
- Ошибка загрузки — `ErrorNotice` над таблицей: **«Отчёт не открылся. Повторите
  запрос через минуту»** (без кода ответа и стектрейса, R-23).

### 4. Колонки по отчётам

Заголовки колонок берутся из уже прижившихся в `ui-inventory.json` и в существующем
`FfReportsPage` — не изобретаем синонимов (R-10). Ячейки собираются только из
`ProductCell`, `TextCell`, `QtyCell`, `StatusChip`.

#### 4.1. Отчёт `product_movements` — «Движения по товару»

Существующая таблица `FfReportsPage`. Переиспользуем «как есть», приводя вёрстку
на `DataTable` из ui-kit (сегодня она собрана руками). Колонки:

- Товар (`ProductCell` — фото + SKU), ширина 220.
- Артикул продавца (`TextCell`), ширина 140.
- Артикул WB (`TextCell`), ширина 120.
- Размер (`TextCell`), ширина 80.
- ШК (`TextCell`), ширина 140.
- Приёмка (`QtyCell`, align="right"), ширина 90.
- Перемещение (`QtyCell`), ширина 90.
- Загрузка ТЗ (`QtyCell`), ширина 100.
- Отгрузка на МП (`QtyCell`), ширина 110.
- FBS (`QtyCell`), ширина 80.
- Отгрузка (`QtyCell`), ширина 100.
- Корректировка (`QtyCell`), ширина 110.
- Прочее (`QtyCell`), ширина 90.

Категории движений и их подписи — те, что уже даёт бэковый

#### 4.2. Отчёт `on_hand` — «Остатки сейчас»

Колонки при разрезе «По товару» (дефолт):

- Товар (`ProductCell`), 220.
- Артикул продавца (`TextCell`), 140.
- ШК (`TextCell`), 140.
- Селлер (`TextCell`, только для ФФ), 160.
- Склад (`TextCell`, только когда складов > 1), 140.
- Ячеек занято (`QtyCell`), 100.
- Остаток, шт (`QtyCell`), 100.
- Литры (`QtyCell`), 100.
- Последнее движение (`TextCell` — дата в формате `дд.мм.гггг`), 130.

При разрезе «По складу» — строки склада (Склад / Товаров / Единиц / Литров).
При разрезе «По селлеру» (только ФФ) — Селлер / Товаров / Единиц / Литров.
При разрезе «По ячейке» — Склад / Ячейка / Товар / Остаток.

**Признак расхождения** — единственный отчёт, где `hasDiscrepancy` включён: строка
краснеет, если текущий `inventory_balance` меньше, чем зафиксировано в последнем
акте инвентаризации (`R-11` — единственный разрешённый смысл заливки).

#### 4.3. Отчёт `inbound` — «Приход за период»

Колонки при разрезе «По товару» (дефолт):

- Товар (`ProductCell`), 220.
- Артикул продавца (`TextCell`), 140.
- Селлер (`TextCell`, только для ФФ), 160.
- Склад (`TextCell`, только когда складов > 1), 140.
- Всего принято (`QtyCell`), 110.
- В т.ч. приёмка (`QtyCell`, muted), 110.
- В т.ч. загрузка ТЗ (`QtyCell`, muted), 130.
- Средний в день (`QtyCell`), 110.

Слово **«приёмка»**, а не «поставка» (R-27 — терминология: приёмка селлер → ФФ).
Разрезы «По селлеру» / «По складу» / «По дню» — колонки заменяются на строки этих
измерений (Селлер / Товаров / Единиц; Склад / Товаров / Единиц; Дата / Товаров /
Единиц). Средний в день во всех разрезах — R-29 (число как утверждение: длина
периода видна отдельно).

#### 4.4. Отчёт `outbound` — «Расход за период»

Колонки при разрезе «По товару» (дефолт):

- Артикул продавца (`TextCell`), 140.
- Селлер (`TextCell`, только для ФФ), 160.
- Склад (`TextCell`, только когда складов > 1), 140.

#### 4.5. Отчёт `aging` — «Мёртвые остатки»

Колонки при разрезе «По товару» (дефолт):

- Товар (`ProductCell`), 220.
- Артикул продавца (`TextCell`), 140.
- Селлер (`TextCell`, только для ФФ), 160.
- Склад (`TextCell`, только когда складов > 1), 140.
- Остаток, шт (`QtyCell`), 100.
- Дней без движения (`QtyCell`), 120.
- Ковш (`StatusChip`), 120.
  - `0–30` — тон `ok` (зелёный)
  - `30–60` — тон `neutral` (синий, «просто информация»)
  - `60–90` — тон `warn` (жёлтый: внимание, работать можно)
  - `90+` — тон `stop` (красный: расхождение с ожидаемой оборачиваемостью)
- Последнее движение (`TextCell` — дата), 130.

Название чипа «Ковш» — короткое слово из языка склада (R-14: статус — Chip с
коротким словом; название ковша тоже коротко). В UI-inventory сегодня нет ни одного
чипа `0–30`/`30–60` — это новые лейблы, но конфликта с существующими названиями нет.

### 5. Строка сводки (`totals`) под таблицей

Три «плитки» цифр в одну строку под таблицей, каждая — обычная типография (не
`StatusChip`, потому что это не состояние):

1. **За период** — сумма/среднее по текущему периоду.
2. **С начала месяца** — накопительно.
3. **С начала года** — накопительно.

Каждая плитка: `subtitle2` — название периода, `h5` — число, `body2 secondary` —
единица измерения («шт», «литр-дни», «дней без движения» — в зависимости от отчёта).

Если включено «Сравнение», под каждым числом — `body2` со стрелкой и процентом:
**«+12% vs прошлый период»** зелёным (тон `ok`), **«−8% vs прошлый период»** красным
(тон `stop`). Стрелка — inline unicode (`↑`/`↓`), отдельного значка ui-kit не заводим.

Сводка живёт в общей `Paper`-области отчёта (не отдельная карточка) — R-01.

### 6. График

Один простой график ниже таблицы. Тип выбирается отчётом:

- `product_movements` — бары по категориям движений (сколько единиц по каждой).
- `on_hand` — бар по разрезу (по товару — top-10, по складу — все склады, и т. д.).
- `inbound` / `outbound` — линия по дням периода (при `group_by=По дню`); в остальных
  разрезах — горизонтальные бары топ-10.
- `aging` — доли ковшей (простая горизонтальная шкала-«стопка»).

Одна серия данных. Если включено «Сравнение» — вторая пунктирная линия/более
светлые бары для прошлого периода. Легенда — минимальная (две подписи), справа
над графиком.

**График рисуется одним и тем же компонентом на все пять отчётов** (тип задаётся
параметром отчёта в реестре). В ui-kit такого элемента нет — фиксирую в разделе
«Нехватка ui-kit».

### 7. Панель действий (низ рабочей области)

`ActionGroup` из ui-kit. Две кнопки, обе размещены рядом (R-31 — контурная только
рядом с главной):

- **Главное действие** — `PrimaryAction`, подпись: **«Скачать XLSX»** (14 символов,
  укладывается в R-32).
- **Второстепенное** — `SecondaryAction`, подпись: **«Скачать CSV»** (11 символов).

Если применён фильтр, дающий > 25 000 строк:
- Обе кнопки становятся `disabled` с `disabledReason` (R-20):
  **«Больше 25 000 строк — разбейте на несколько периодов»**.

Кнопка «Печать» на отчёте **не появляется**: печатать отчёт на термопринтере
некому и незачем. Единственные «печати» в системе — этикетки (R-33, тип `Printable`
не расширяем).

### 8. Сканер

Раздел «Отчёты» сканер **не слушает**. `ScannerLine` не выводим (R-25 работает
в обе стороны: экран, который не слушает сканер, не должен об этом врать — а
пустой блок «Сканер не слушает этот экран» на аналитическом экране только шумит).

### 9. Состояния

- **Загрузка отчёта** — `TableSkeletonBody` внутри `DataTable`, плюс скелет плиток
  сводки (три `Skeleton variant="rounded"` в строке totals) и скелет графика
  (`Skeleton variant="rounded" height={180}`).
- **Пусто** — `EmptyState` внутри `DataTable.empty`. Формулировка см. п. 3.
- **Ошибка** — `ErrorNotice` над таблицей (см. п. 3). Формулировки на языке склада:
  «Отчёт не открылся. Повторите через минуту», «Период указан задом наперёд — дата
  «с» позже даты «по»», «Нет прав на этот отчёт».
- **Селлер, у которого нет доступа к какому-то отчёту** — этот пункт в его списке
  слева просто не появляется (не сереем, не показываем `EmptyState`: если пункта
  нет, вопросов не возникает).

### 10. Разграничение доступа

- ФФ-админ и сотрудники с `PERM_CELLS` / `PERM_INVENTORY` — видят раздел целиком,
  фильтр «Селлер» показан, доступны все пять отчётов.
- Селлер — видит только раздел с четырьмя отчётами (`product_movements`, `on_hand`,
  `inbound`, `outbound`, `aging`) и жёстко зашитым своим `seller_id`. Отчёт
  «Операции» (кто что делал за период — HR-разрез) в первую волну **не входит**
  вообще (`OTLOZHENO`).
- Все сотрудники селлера — одинаковые права внутри селлера (в 07 денег нет, ролевое
  разделение «менеджер vs владелец» решается в 09-billing).

### 11. Пункт меню

- Портал ФФ — в `AuthedAppLayout.tsx` пункт **«Отчёты»** уже есть
  (`data-testid="nav-ff-reports"`), не трогаем: он ведёт на новый `ReportsHubScreen`.
- Портал селлера — добавить пункт **«Отчёты»** в `AuthedAppLayout.tsx` (или где
  строится меню селлера), значок `AssessmentOutlined` (или тот же, что у ФФ, чтобы
  один язык). `data-testid="nav-seller-reports"`.

### 12. Чего на экране нет (границы)

Не показываем, не считаем, не рисуем — записано, чтобы не «доложил заодно»:

- **Финансовые отчёты** (счета, задолженность, «сколько должен ФФ») — карточки
  08-storage и 09-billing. В 07 приходят шестым пунктом второй волны.
- **Отчёт «Работа упаковщиков»** — это HR-зарплата, живёт в `S-19` (или новом
  «Сотрудники»). Владелец в исходной постановке прямо отделил её от отчётности.
- **Отчёт «Операции»** (кто из сотрудников ФФ сколько сделал) — уходит во вторую
  волну (`OTLOZHENO`, ближе к HR, чем к отчётности перед селлером).
- **Отдельные экраны «Отчёт по складу», «Отчёт по маркетплейсу», «Отчёт по
  продавцам», «Отчёт по операциям»** — не заводим (простота: «расширить существующий
  экран, а не создать соседний»). Все разрезы делаются переключателем `group_by`
  внутри отчёта и фильтром в шапке.
- **Конструктор отчётов** (drag-n-drop pivot, custom fields) — не делаем.
- **Расписания и рассылки на почту** — не делаем.
- **PDF-экспорт с логотипом ФФ** — не делаем (только XLSX и CSV).
- **Отчёты о продажах с маркетплейса** (конверсии, воронки покупателя) — не
  делаем: это дело кабинета WB/Ozon.
- **KPI-плашки на дашборде** — существующий `SellerDashboardScreen` не трогаем
  (это отдельная карточка «Приборная панель селлера»).
- **Материализованные витрины** — не делаем (считаем налету; когда упрётся —
  карточка 05).
- **Ручной ввод цифр**, «согласовать с админом», «отправить в 1С» — не делаем.
- **Кнопка «Печать»** отчёта — не делаем (см. п. 7).

### 13. Открытые вопросы к продакту

Не блокируют разработку — заранее с умолчаниями, продакт правит утром, если
не угадал:

1. Дефолтный пресет периода — «Месяц» (по умолчанию). Альтернатива — «Неделя».
2. Первый показываемый отчёт при заходе — `on_hand` для селлера, `product_movements`
   для ФФ (по умолчанию: у селлера ценность сразу «что у меня лежит»; у ФФ —
   уже существующее и знакомое).
3. Формат даты во всех отчётах — `дд.мм.гггг` (кириллица) без времени. Время
   показываем только в `product_movements` (там оно уже есть в существующей
   ручке).
4. Мягкий или жёсткий лимит 25 000 строк — по умолчанию **жёсткий** (иначе
   пользователь получает пустой XLSX через минуту ожидания).

## Нехватка ui-kit

Раздел не пустой: пять отчётов на едином каркасе требуют элементов, которых
сегодня в `frontend/src/ui-kit/index.ts` нет. Изобретать на бумаге замену нельзя —
фиксирую отдельно, чтобы screen-dev либо расширил ui-kit одной волной, либо
разбил на подкарточки.

1. **`DateRangeField`** — единый выбор «дата с — дата по» с шестью пресетами
   («Сегодня», «Неделя», «Месяц», «Квартал», «Год», «Свой»). Сейчас в проекте
   есть `frontend/src/components/WmsDateField.tsx`, но это не парное поле и не
   часть ui-kit. Раздел «Отчёты» — не единственный потребитель: та же пара
   нужна в `S-11` (хранение, 08-storage) и `S-19` (тарифы, 09-billing).
2. **`FilterSelect`** — унифицированный селект внутри `FilterBar` для полей
   «Селлер», «Склад», «Маркетплейс», «Разрез», «Сравнение». Сегодня в ui-kit есть
   только `TextField` для поиска; `FilterBar` берёт `children` — но самого канонного
   селекта, единого по высоте с поисковым полем, нет.
3. **`ReportChart`** — единый компонент графика (bar / line / stacked-bar).
   Одна серия по умолчанию, вторая пунктирная — если включено «Сравнение».
   Легенда не более двух подписей. Реализация — на MUI X Charts (то же семейство,
   что и остальное приложение), внешние библиотеки типа `recharts` не тянем.
4. **`TotalsRow`** — плитки сводки под таблицей: три или четыре плитки в один ряд,
   в каждой `subtitle2` + `h5` + `body2 secondary`, опционально — строка сравнения
   со стрелкой и цветом. Ни `StatusChip`, ни отдельная «карточка» для этого не
   подходят.
5. **`ReportsNavList`** — вертикальный список пунктов раздела (название пункта +
   подпись из одного предложения). Похоже на пункт меню, но живёт внутри экрана,
   а не в глобальной навигации. Возможно, стоит переиспользовать существующий
   компонент бокового меню — решает screen-dev.
6. **`DownloadAction`** (опционально) — обёртка над `PrimaryAction`/`SecondaryAction`,
   которая по умолчанию несёт подпись «Скачать XLSX» / «Скачать CSV» и
   `disabledReason` про лимит 25 000 строк. Не обязательно вводить — можно
   написать эти две кнопки руками через `PrimaryAction`/`SecondaryAction`; но если
   такой же паттерн выгрузки появится в 08 и 09, разумно закрепить.

Пункты 1–4 — обязательные для этой карточки. Пункт 5 — либо расширяем ui-kit,
либо переиспользуем существующее меню. Пункт 6 — «на подумать» рядом.
