# CONTRACT · 04-warehouse-switch · Склад мешает работать

Проектировщик экранов. Сборка сделана из первоисточника
(`night/volna-9/cards/04-warehouse-switch/ISTOCHNIK.md`), разбора (`RAZBOR.md`),
арх-варианта (`ARCH.md`), сверки (`SVERKA.md`) и карты волны
(`night/volna-9/MAP.md`). Задача помечена владельцем «ТЗ пишется», поэтому
контракт закрепляет доменное решение сразу на нескольких экранах и в общем
shell'е — без этого «один склад — выбора нет, много — переключатель» не
существует как единая концепция.

Опоры канона — `docs/product/UX_CANON_RU.md`, реальные подписи —
`docs/product/ui-inventory.json`, состав UI-набора —
`frontend/src/ui-kit/index.ts`.

## Контракт

### 0. Общее: контекст «текущий склад»

**Что вводится.** У пользователя (админ ФФ, оператор ФФ, селлер) в шапке
приложения (`AuthedAppLayout`) появляется **один** компонент «текущий склад».
Смена этого значения — единственный способ сменить рабочий склад во всех
рабочих местах. По ключу «текущий склад» перезапрашиваются данные всех
списков и остатков.

- **Если у тенанта один настоящий склад** (служебные `fbs-wb-*` не считаются) —
  компонент **скрыт**. Оператор видит один склад по умолчанию, ни на одной
  форме создания заявки нет селекта «Склад».
- **Если два и больше настоящих склада** — компонент виден, показывает имя
  текущего склада. Клик открывает список настоящих складов; служебные
  подстановки `fbs-wb-*` в список не попадают ни в одной роли.
- **Начальное значение при входе** — «Основной» (или первый настоящий склад
  в порядке кода); служебный `fbs-wb-*` первым выбран быть не может.

**Смена контекста «за спиной» открытой модалки.** Модалки создания
(`FbsSupplyCreateDialog`, диалоги приёмки/отгрузки) закрываются, оператор
получает информационную полоску «Склад переключён на N» (Alert `info`,
одноразовый). Открытые списки перерисовываются под новый склад.

**Чего на экране нет.** Нет отдельных «Склад для заявки»-селектов ни на
приёмке, ни на отгрузке, ни в поставке FBS, ни в диалоге создания продукта —
контекст один и лежит в шапке. Нет «All warehouses» / «Все склады» / «сводного
режима»: работать в двух складах одновременно не даём.

**Успех.** Оператор видит имя текущего склада в шапке. Клик — список настоящих
складов, выбор мгновенно перерисовывает списки. На тенанте с одним настоящим
складом компонента в шапке нет вовсе.

**Пусто.** У тенанта нет ни одного настоящего склада (например, WMS пока
знает только служебные `fbs-wb-*`). Компонент скрыт. Все формы создания
блокированы (см. существующий Alert `warning: Нет доступного склада для
создания заявки. Обратитесь к фулфилменту.` — используется и здесь).

**Ошибка.** Загрузка `/warehouses` упала — Alert `error` в шапке приложения
на языке склада: «Не удалось прочитать список складов. Обновите страницу.»

### 1. Экран S-03 · FBS-заказы / поставка (FfFbsOrdersScreen · FfFbsSupplyWorkspace · FbsSupplyCreateDialog)

**Что меняется.**

- Строки списка «Новые заказы FBS» фильтруются по **текущему складу**
  контекста. Строка-переключатель склада **над таблицей заказов** — не
  добавляется: контекст единый и живёт в шапке. Это отменяет предложение
  из MAP («строка-переключатель над таблицей») — оно дублировало бы шапку.
- Чип **«Склад / СЦ»** в строке заказа (сегодня уже показывает склад Wildberries
  из заказа) остаётся как есть — это не WMS-склад, а склад-приёмщик WB.
  Название и тон не менять (R-10, R-14).
- В **диалог создания поставки** (`FbsSupplyCreateDialog`) над кнопкой
  «Создать поставку» добавляется секция `Alert severity="warning"`
  «Товар нужен на складе N — X шт. На складе N — 0 шт., ещё X шт. на складе
  M. Создать всё равно?» Формулировка **словами, не блокирует**. Кнопка
  «Создать поставку» активна.
- В `FfFbsSupplyWorkspace` **шапка** остаётся, как в 03 (`hasNoDistributionBoxes`)
  и как проектировали 02 (вердикт) и 06 (порядок). Никакого дополнительного
  «переключателя склада» на воркспейсе нет — контекст в глобальной шапке
  выбирает какой воркспейс открыт.
- Скан ячейки чужого склада на подборе (`ScannerLine`) больше **не
  выдаёт ошибку** «Ячейка не принадлежит складу поставки». Вместо ошибки
  сервер тихо регистрирует межскладской перенос, экран показывает
  однострочный тост-информатор «Товар перенесён со склада N. Списание
  выполнено.» Ошибку возвращаем только если товара нет вообще нигде.

**Успех.** Оператор видит только заказы своего текущего склада; сканирует
ячейку любого склада тенанта, где физически есть товар — подбор идёт, в
ленте движений появляется парная запись «перенос N→M». В диалоге поставки —
предупреждающий текст словами при нехватке на выбранном складе.

**Пусто.** У складa нет заказов «Новые» — существующее пустое состояние
(в реестре не помечено пусто-alert, R-21 требует «пусто и что сделать»:
формулировка «Пока нет заказов на этом складе — переключите склад в шапке
или подождите новых заказов от Wildberries»).

**Ошибка.** Создание поставки упало на сервере — `Alert severity="error"`
в диалоге, на языке склада; тексты «insufficient_stock» и
«different_wms_warehouse» в UI не показываем (R-30).

### 2. Экран S-14 · Упаковка (FfPackagingPage)

**Что меняется.**

- Костыль `_try_deduct_from_alternative_sorting_location` удаляется. Тост
  «Товар списан из другой ячейки сортировки: N» больше **не появляется** —
  никогда.
- Экран упаковки на контекст склада **не завязан**: оператор упаковывает то,
  что подобрал в S-03. Если товар в момент подбора реально уехал через
  межскладской перенос, к упаковке это уже прозрачно.

**Чего на экране нет.** Нет «выбора склада» на упаковке — это внутренний шаг
цепочки, а не место, где решают склад. Нет «сообщения о переносе» на
упаковке: перенос уже случился на подборе (S-03), сообщать о нём здесь —
двойное упоминание одной сущности (R-35).

**Успех.** Оператор упаковывает так же, как сегодня; никаких новых чипов,
кнопок и подсказок про склады не появляется.

**Пусто/ошибка.** Существующие состояния экрана не трогаем.

### 4. Экран S-25 · Переносы (TransfersScreen)

**Что меняется.**

- В общий журнал переносов добавляется строка автоматического
  межскладского переноса, созданного в момент подбора. По R-12 в списке
  документов разных типов **тип виден колонкой и по нему есть фильтр**.
- Колонка **«Тип»** (уже существует концептуально в переносах): значения
  «Ручной перенос», «Автоперенос при подборе». Название чипа —
  `StatusChip` с тоном `default` для «Ручной» и `info` для
  «Автоперенос при подборе» (R-14, R-16 — синий = нейтральная информация).
- Фильтр по типу — в `FilterBar`.

**Чего на экране нет.** Нет отдельной модалки «создать межскладской перенос
из подбора» — эти переносы автоматические, ручного действия нет. Нет
«редактировать/отменить» на автопереносе (обратимости у списанного склада
нет).

**Успех.** Владелец, ища «кто и когда снял 519 штук со склада N», видит
эти строки в общем журнале переносов с типом «Автоперенос при подборе» и
ссылкой на поставку-виновника.

**Пусто.** «Переносов нет — создайте перенос кнопкой выше или подождите
автоматический перенос при подборе» (R-21).

**Ошибка.** Существующая `ErrorNotice`.

### 8. Сканер (общая семантика)

**Что вводится.**

- Единый вход `ScannerLine`: строка «Сканер активен — пикните ШК склада,
  ячейки или товара» (R-25). Строка **одинаковая** во всех рабочих местах,
  где сканер слушает.
- Штрихкод склада (новое поле `warehouse.barcode`, автогенерация `WH-<code>`)
  — переключает контекст склада, ничего не «выбирает» и никого не
  спрашивает. Информационная полоска «Склад переключён на N» (R-24 —
  сообщаем только о том, что реально произошло).
- Штрихкод ячейки — как сегодня, но если ячейка чужого склада —
  автопереключение контекста на её склад + подстановка ячейки (без
  ошибки, без модального подтверждения).
- Штрихкод товара — как сегодня.

**Чего на экране нет.** Нет «режима сканера» (склад/ячейка/товар) —
переключение делает экран сам по префиксу (R-26: сканер тупой, экран решает).
Нет обучения оператора формату штрихкодов складов — печать/раздача
администратором.

**Успех.** Оператор физически сканирует «WH-osnovnoy» — контекст шапки
уехал на «Основной», списки перерисовались.

**Пусто.** У склада нет распечатанного `warehouse.barcode` — переключатель
кликом работает как обычно, ошибки нет (`warehouse.barcode` не
обязательный).

**Ошибка.** Незнакомый код — `Alert severity="error"` под `ScannerLine`:
«Не распознан код: <строка>» (R-23, R-30).

### 9. Чего в этой волне нет

- Ролевого разграничения «имеет право переключить склад/не имеет». Работаем
  поверх текущих ролей.
- Автовыбора «оптимального» склада для заказа (роутинг ShipHero). Оператор
  выбирает вручную через шапку.
- Правки Android-клиента ТСД. Кросс-складской подбор — через web-UI. На
  ТСД сегодня один склад, семантика штрихкода склада приезжает отдельным
  нарядом в мобильный репозиторий (`mobile/`).
- Тарифов, литр-дней, биллинга по складам — карточки 08 и 09.
- Правки доменной модели «служебный `fbs-wb-*` склад». Автосоздание
  остаётся, служебные просто перестают быть видны оператору.

- **R-37 (предложено).** Контекст сессии (склад, роль, тенант) — один
  компонент в шапке приложения. Если контекст сегодня один — компонент
  скрыт. Отдельный селект того же контекста на форме создания — дефект.
  *Обоснование:* инцидент 20.08 (155 заказов встали) возник ровно из-за
  дублирующего выбора склада на форме поставки FBS.
- **R-38 (предложено).** Если действие можно выполнить с последствиями,
  оператору сообщается словами и разрешается («создать всё равно / открыть
  перенос»). Блокировка — только когда действие физически невозможно
  (например, товара нет вообще нигде). Владелец: «Нельзя дать создать
  поставку на складе, где нет товара, **не сказав об этом словами** в
  момент создания» — прямая формулировка правила.
- **R-39 (предложено).** Скан склада, ячейки и товара разбирается одним
  слушателем экрана по префиксу/справочнику. Оператор не выбирает «режим
  сканера». Экран сам переключает контекст; отдельного подтверждения не
  требуется. Дополняет R-26 для многоскладовой работы.

## Нехватка ui-kit

Из состава `frontend/src/ui-kit/index.ts` не хватает:

- **`WarehouseSwitcher`** — компонент шапки приложения «текущий склад» с
  двумя видами: **скрыт** при одном настоящем складе и **компактный
  открывающийся список** при двух и более. Сегодня в наборе есть только
  `StatusChip`, `PrimaryAction/SecondaryAction`, `FilterBar`, `ScannerLine`
  — ни один из них не отражает семантику «глобальный контекст сессии».
  Замену на бумаге не изобретаем: если элемент не добавляется в
  `ui-kit/`, экраны не переключить одинаково.

Всё остальное — `Alert` (тон `warning`/`error`/`info`), `StatusChip` для
«Автоперенос при подборе», `FilterBar` для фильтра по типу переноса,
`ScannerLine` для единой скан-строки, `EmptyState` для пустых списков — в
наборе есть, использовать как есть.
