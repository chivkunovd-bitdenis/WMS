# Контракт · 02-verdikt-screen

Правим один существующий экран `S-03` (FBS-заказы + рабочий экран поставки).
Новый экран не заводим (R-10, п. 8 канона). Задача — заменить нашу оптимистичную
подсказку «сдавать можно» на настоящий вердикт Wildberries словами, а гейт сдачи
завязать на этот же вердикт.

## Контракт

### 1. Где меняется

- **Экран `S-03 · FBS-заказы` (`FfFbsOrdersScreen.tsx`) — вкладки «В работе»,
  «На отгрузку», «Завершены» (не «Новые»).**
  Меняется ячейка колонки **«Статус»** в строке заказа. Состав колонок,
  ширины, порядок и заголовок не трогаются (п. 8.4 канона, R-09, R-10).
  Вкладка «Новые» не меняется: там код ЧЗ ещё не привязан, вердикта от WB нет
  и рисовать нечего (`NewOrderRow`).
- **Экран `S-03 · Рабочий экран поставки` (`FfFbsSupplyWorkspace.tsx`),
  вкладка «Упаковка», секция «Строки упаковки».**
  Меняется правый блок строки заказа (сейчас там только `ЧЗ` и хвост кода).
  Секции «Задания», «Короба», «Отгрузка», шапка воркспейса и кнопки не
  трогаются (п. 8.5, п. 8.3 канона).

### 2. Ячейка «Статус» в строке заказа — что показывается

В ячейке, где сейчас живёт единственный чип `Отклонено WB` /
`Не хватает честных знаков: N` / `FbsStatusChip`, теперь стоит
**столбик чипов «Вердикт WB по каждому Честному знаку»** плюс **основной
статус заказа** отдельной строкой снизу.

Каждой позиции `order.metadata.required[kind]` соответствует ровно один чип:

| Что реально пришло от WB (`decision` / `check_status` + `reason`) | Подпись чипа | Тон `StatusChip` | Что рядом |
|---|---|---|---|
| `accepted` / `allowedwithoutcheck` (явное одобрение) | `WB подтвердил` | `ok` | — |
| `filled` без `reason` **или** `pending` | `WB проверяет` | `warn` | `hint`: «WB получил код, ждём ответа» |
| `filled` с непустым `reason` **или** `rejected` / `replacementrequired` | `WB не принял` | `stop` | под чипом `caption` с человеческим переводом `reason` (перевод берётся из нового словаря `metaStatus.ts`; неизвестный `reason` показываем как есть) |
| `required` (WB требует, кода в заказе ещё нет) | `Нужен ЧЗ` | `stop` | `hint`: «WB ждёт код, отсканируйте стикер» |
| `optional` / `notRequired` (WB прислал, что для этой позиции код не нужен) | `ЧЗ не требуется` | `neutral` | — |
| Мета ещё не дошла (нет `decision` и нет `check_status`) | `Статус уточняется` | `neutral` | `hint`: «Ждём ответ Wildberries» |

Одна сущность — один чип: если у заказа один required kind, то и чип один.
Если два (SGTIN + УИН) — два чипа в столбик, каждый со своим вердиктом
(R-35 — «одна сущность в одном месте»; никаких дублирующих текстов
«не хватает: N» рядом уже нет, счётчик заменён именованными чипами).

**Основной статус заказа** (`FbsStatusChip` со словами `Отсортирован`,
`Упакован`, `В доставке`, `Завершён`, `Дефект`, `Отменён`, `Требует
исправления`) — оставляем как есть, отдельной строкой ниже вердиктов. На
«Отменённые» вердикт не рисуется вовсе: заказ уже закрыт, вердикт ничего
не решает — там только статус заказа.

Заливок у строки нет (R-11); красный/жёлтый/зелёный несут чипы, а сама
строка остаётся белой.

### 3. Правый блок строки в «Упаковке» рабочего экрана поставки

Сейчас в строке заказа справа только «ЧЗ» и хвост кода (`kizTail`). После
правки, **над** хвостом кода, добавляется тот же чип «Вердикт WB» из
таблицы выше — по одному на каждый required kind. Тон, подпись, `hint`
и `reason`-подсказка совпадают строка-в-строку с ячейкой «Статус» на
списке заказов (R-10: одна сущность — одно название на всех экранах).

Оператор в «Упаковке» видит рядом: (а) что он отсканировал (хвост
кода) и (б) что об этом сказал WB. До сегодня видел только (а).

Условие `MARKING_ACCEPTED_STATUSES` (что считать «готово к сдаче») в
`isOrderMarkingReady` перестаёт включать `pending` и `assigned`. Готовым
считаем только `accepted` и `allowed_without_check` без непустого `reason`.
`optional` / `notRequired` в required не входит и в счёт готовности не
попадает по построению.

### 4. Кнопка «Передать в доставку» на поставке

Кнопка уже есть, вырезаем ложь. Правила видимости и подсказки:

- Активна тогда и только тогда, когда у **каждого** заказа поставки все
  required kind закрыты вердиктом `WB подтвердил` **или** `ЧЗ не
  требуется`. Любой чип `WB не принял` / `WB проверяет` / `Нужен ЧЗ` /
  `Статус уточняется` на любом заказе — кнопка неактивна (R-20).
- Tooltip у неактивной кнопки: `«Wildberries ещё не подтвердил {N} заказ(ов).
  Проверьте столбец «Статус» — где красный или жёлтый чип, там ждём ответ WB»`
  (R-20: неактивная кнопка объясняет причину; R-30: человеческий язык
  вместо «marking_not_allowed»).
- Серверный гейт `_build_delivery_checks` / `compute_delivery_allowed`
  переводится на ту же логику: `delivery_allowed=true` только когда все
  required kind в `{ACCEPTED, ALLOWED_WITHOUT_CHECK}` **и** ни у одного
  нет непустого `reason`. Это нужно, чтобы кнопка и сервер не расходились
  (R-24: не рапортовать об успехе, которого не было).

### 5. Состояния

- **Пустое / загрузка.** Пусто и скелеты таблицы не меняются, они уже есть
  и по канону (R-21, R-22).
- **Не дошла мета от WB (никакого `decision`, никакого `check_status`).**
  В ячейке «Статус» стоит чип `Статус уточняется` тоном `neutral` с
  `hint`: «Ждём ответ Wildberries». Никакого чипа `ok` в этот момент нет
  — тишина от WB не равна «подтвердил» (R-24).
- **Успех.** У всех required kind чип `WB подтвердил` тоном `ok`.
  Основной статус заказа рисуется как обычно.
- **Ошибка.** У любого required kind тон `stop`. Отдельного `Alert` в теле
  экрана не появляется — чипа достаточно; `Alert severity="error"`
  (R-23) остаётся только для сетевых ошибок загрузки, как сейчас.

### 6. Чего на экране нет и не появляется

- Новых колонок в таблице заказов **нет** (п. 8.4 канона).
- Отдельной вкладки «Проблемные с ЧЗ» **нет** — фильтровать по вердикту
  можно глазом по чипам, отдельная сущность для этого не нужна
  (простота: признак вместо ветки, раздел «Что предпочитать»).
- Отдельной кнопки «Перепроверить у WB» **нет** — автополлер уже
  обновляет мету (карточка 05 регулирует частоту); ручная кнопка добавит
  очередь и вопрос «сработала или нет», без пользы (простота: главный
  вопрос «реально ли без этого нельзя обойтись»).
- Заливки строк по вердикту **нет** (R-11 — заливка означает только
  расхождение по количеству).
- Технических слов в подписях чипов **нет**: `meta_status`, `decision`,
  `check_status`, `marking_not_allowed`, `uinBadStatus` в интерфейсе не
  показываем; известные `reason` переводим словарём, неизвестные показываем
  как есть в мелком тексте под чипом (R-30).
- Подтверждающего модала перед сдачей поставки **нет**: если кнопка
  активна — WB подтвердил, спрашивать «вы уверены» не нужно (простота,
  раздел «Чего делать нельзя»).

| Пункт контракта | Правило |
|---|---|
| Правим существующий экран `S-03`, новый не заводим | п. 8.3, п. 8.5 канона |
| Не добавляем колонки/фильтры/кнопки, под которые нет задачи | п. 8.4 канона |
| Вердикт показан `StatusChip` с коротким словом склада | R-14 |
| Подпись чипа отличается от имени системного статуса (`accepted` → `WB подтвердил`, `filled` → `WB проверяет`) | R-15 |
| Три цвета: `stop` — мешает работать, `warn` — внимание, `ok` — закрыто, `neutral` — просто информация | R-16 |
| Одинаковая подпись вердикта в списке заказов и в рабочем экране поставки | R-10 |
| Одна сущность (Честный знак) — один чип в строке; нет параллельных подписей «не хватает: N» рядом с чипами | R-35 |
| Кнопка «Передать в доставку» неактивна объясняет причину через `Tooltip` | R-20 |
| Экран не рапортует «сдавать можно», пока WB не сказал явно | R-24 |
| Технические слова (`meta_status`, `uinBadStatus`, `marking_not_allowed`) в интерфейсе не появляются, `reason` переводится словарём | R-30 |
| Заливки строк нет — состояние несёт только чип | R-11 |
| Скелет строк на загрузке, `Alert severity="error"` только для сетевых ошибок | R-22, R-23 |
| Слово «поставка» в UI: остаётся только для FF↔MP (сдача в WB), для селлер→ФФ по-прежнему не используется | R-27 |
| Оператор в перчатках, спешит — вердикт словами в строке видно сразу после привязки, идти в другой экран не нужно | п. 0 канона («картина оператора») |

Новых правил канон не требует. **Дыр нет.** Осторожная трактовка
неоднозначных значений WB (`filled` без `reason` → `WB проверяет`, а не
`WB подтвердил`) прямо покрывается R-24 — «не рапортовать об успехе,
которого не было». Отдельное правило «пока внешний источник не
подтвердил, состояние не показывается как готово» уже содержится в R-24
в общем виде и в примере с Wildberries из R-30.

## Нехватка ui-kit

Пусто. Всё нужное уже есть в `frontend/src/ui-kit/index.ts`:

- `StatusChip` с тонами `ok | warn | stop | neutral` и опциональным `hint`
  (Tooltip) — закрывает все шесть подписей вердикта.
- Столбик из нескольких чипов в одной ячейке — обычный `Stack`, нового
  элемента не требует.
- Мелкий `caption` под чипом с переводом `reason` — это `Typography
  variant="caption"`, отдельный компонент не нужен.
- Кнопка «Передать в доставку» с `disabled` + `Tooltip` — уже есть в
  экране, оборачивать во что-то новое из ui-kit не нужно.

Новый словарь переводов `frontend/src/utils/metaStatus.ts` (рядом с
существующим `markingStatus.ts`) — это утилита данных, а не элемент
ui-kit; в набор экранных элементов не добавляется.
