## Решения

### 1. Что считать «WB подтвердил», когда явного «accepted» в живых ответах нет

- **Вопрос.** В живых ответах WB (`test_fetch_orders_meta_batch_exact_contract_and_parse`,
  [news 302](https://dev.wildberries.ru/news/302)) `decision` бывает
  `filled / required / pending / optional / notRequired` — значения, которое
  однозначно значит «WB признал код валидным», среди них нет. Как трактовать
  `filled`?
- **Решение.** `filled` без `reason` = `WB проверяет` (тон `warn`, сдача
  блокируется); `filled` с непустым `reason` = `WB не принял` (тон `stop`,
  сдача блокируется). Готовым к сдаче считаем только `accepted` и
  `allowedwithoutcheck` **и** при пустом `reason`. Никакого «зелёного»
  штампа по `filled` — как сейчас в `map_wb_decision_to_meta_status`
  (`"filled": META_STATUS_ACCEPTED`) — больше нет.
- **Почему.** Это ровно тот баг, из-за которого на бою по всем 26 заданиям
  стояло «сдавать можно», пока WB отказывал: `filled` от WB значит «селлер
  прислал значение», а не «WB признал его валидным». Общий приём в
  gate-системах при неопределённости внешнего вердикта — закрывать, а не
  открывать; ошибка в сторону «WB ещё не подтвердил» дешевле — оператор
  просто ждёт полсекунды автополлера, чем на сдаче получает отказ WB.
- **Что легко переделать.** Если WB когда-нибудь начнёт слать явный
  positive-`decision` (`verified` / `passed` / `accepted`) — добавляется одна
  строка в `map_wb_decision_to_meta_status` и UI-слой не трогается. Дорогая
  переделка одна: если владелец скажет «пусть `filled` без `reason` тоже
  считается ok» — придётся переписать смысл `META_STATUS_PENDING` и всю
  матрицу чипов, потому что тон меняется на противоположный.

### 2. Как показывать `reason` от WB, если словаря переводов у WB нет

- **Вопрос.** Список кодов `reason` (`uinBadStatus`, `weightBadFormat`, …)
  WB официально не публикует. Показывать как есть, или ждать словарь?
- **Решение.** Заводим `frontend/src/utils/metaStatus.ts` рядом с
  существующим `markingStatus.ts`. Известные `reason` кладём с ручным
  переводом («неверный статус УИН», «вес в неверном формате» и т.п.);
  неизвестные показываем **как есть** в мелком `caption` под чипом «WB не
  принял». Пополняем словарь по мере встреч.
- **Почему.** Так делают все системы, работающие с публичным API без
  каталога ошибок: сырой код — плохая, но всё-таки подсказка (оператор
  может по нему позвонить продавцу или в поддержку WB), а пустое место —
  нулевая. Показывать «Ошибка WB» без деталей хуже, чем показывать
  `uinBadStatus`.
- **Что легко переделать.** Словарь — простая мапа, дополняется одним
  ключом; ничего в компонентах и API не трогается. Дорогой переделки нет.

### 3. `optional` и `notRequired` — блокируют сдачу или нет

- **Вопрос.** WB на конкретную позицию может ответить `optional` («можно
  приложить, необязательно») или `notRequired` («не нужен вовсе»). Считать
  ли такую позицию required-препятствием к сдаче, если она числится в
  `order.required_meta_json`?
- **Решение.** Такой `kind` рисуется чипом `ЧЗ не требуется` тоном
  `neutral` и **не участвует в `compute_delivery_allowed`**, даже если он
  формально попал в `required_meta_json`. `required_meta_json` — снимок
  требований WB на момент импорта; конкретный `decision` по позиции
  свежее и главнее.
- **Почему.** Иначе получим ровно исходный баг с другой стороны: WB
  явно сказал «не нужно», а мы всё равно тормозим сдачу. Дословная
  просьба владельца — «сдача разрешена только тогда, когда Wildberries
  подтвердил»; для `optional/notRequired` WB своё «подтверждение» дал
  явным «не требую».
- **Что легко переделать.** Правится в двух местах — `compute_delivery_allowed`
  и матрице чипов. Если утром окажется, что владелец хочет всё-таки
  видеть эту позицию в списке «на проверку» — меняется тон чипа с
  `neutral` на `warn` без переписывания логики гейта.

### 4. Что запрещено добавлять на экран (закрепляю от переусложнения)

- **Вопрос.** Соблазн «раз мы уже переделываем ячейку — давайте заодно
  добавим кнопку „Перепроверить у WB“, модал подтверждения сдачи и
  вкладку „Проблемные с ЧЗ“».
- **Решение.** Ни одного из этих элементов на экране нет и не появляется:
  ручная перепроверка — автополлер (карточка 05) обновляет мету сам;
  модал перед сдачей — если кнопка активна, WB уже подтвердил, спрашивать
  нечего; отдельная вкладка «Проблемные» — фильтровать по вердикту можно
  глазом по красным чипам, а колонка «Статус» и так на месте.
- **Почему.** Главный вопрос простоты — «реально ли без этого нельзя
  обойтись». Ни один из трёх пунктов не проходит: без ручной кнопки
  можно (есть автополлер), без модала можно (кнопка сама решение), без
  вкладки можно (столбец «Статус» уже показывает вердикт).
- **Что легко переделать.** Утром при желании владельца любой из
  пунктов добавляется одним экранным элементом без переделки API. Но
  добавлять сейчас — значит дать оператору три места, где ошибиться,
  и три новых куска для поддержки.

### 5. Один или несколько чипов в ячейке «Статус»

- **Вопрос.** У заказа может быть один required kind (только SGTIN)
  или два (SGTIN + УИН). Один общий чип «суммарный вердикт» или
  столбик по одному чипу на каждый kind?
- **Решение.** Один чип на каждый required kind, в столбик. Основной
  статус заказа (`FbsStatusChip`) — отдельной строкой ниже.
- **Почему.** Общий чип «худший из вердиктов» скрывает от оператора
  причину: он видит `stop`, идёт разбираться и не знает, какой из
  двух кодов виноват. Столбик из двух-трёх чипов — не перегруз (шире
  других колонок не станет, обычно kind один), а действие оператору
  подсказывает точное.
- **Что легко переделать.** Компонент — обычный `Stack` из
  `StatusChip`; свернуть в один общий чип — переписать функцию
  `orderVerdictChips`, ничего снаружи не трогая.
