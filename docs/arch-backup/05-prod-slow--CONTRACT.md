# CONTRACT · 05-prod-slow

Роль: UX-архитектор. Тип задачи в карточке — «домен» (инфра + бэк + фронт).
Из четырёх кусков плана (`ARCH.md`) фронта касается только один — карточка C
(«списки грузятся страницами»). Карточка A (тредпул PDF), B (расщепление
автополла) и D (записка про RAM) видимых изменений на экран не приносят —
для них контракт «оставить как есть», подробности ниже.

Единственный затронутый экран — **S-03 `FfFbsOrdersScreen`**
(`frontend/screens.registry.json:118–219`, `route: /app/ff/fbs`, зоны: шапка,
фильтры, таблица, панель действий, модалка). Соседние `S-04 FfFbsStockSyncScreen`,
`FfFbsSupplyWorkspace`, `FbsPrintPreviewDialog`, `HonestSignScreen`,
`HonestSignProductPage` — в контракт не входят: там ускорение прозрачно для
оператора, кнопки и подписи не меняются (R-канон границы, п.8.5).

## Контракт

### 1. S-03 · вкладка «Новые» · таблица

**Что меняется.**

- Первая загрузка вкладки «Новые» приходит **50 строк** (было 500). Число
  «50» — это размер страницы, не лимит на количество показанных: оператор
  добирает следующие 50 кнопкой в футере таблицы (см. п.2).
- Пока страница летит с сервера, тело таблицы — `TableSkeletonBody`
  (`ui-kit/States.tsx`, R-22), 5 строк-заглушек по числу колонок вкладки.
  Спиннер поверх пустоты не показываем.
- Если сервер отдал пустой ответ (новых заказов нет) — `EmptyState`
  (`ui-kit/States.tsx`, R-21) с текстом «Новых заказов пока нет» и подсказкой
  «Заказы приходят из Wildberries автоматически, обновление каждые 3 минуты».
  Кнопки действия в `EmptyState` нет: оператор здесь ничего не делает.
- Если сервер ответил ошибкой — `ErrorNotice` (`ui-kit/States.tsx`, R-23)
  под шапкой экрана, формулировка «Не удалось получить список заказов»
  (без кода ответа, без стектрейса, R-30). Таблица под плашкой остаётся с
  последним удачным снимком, если он был; иначе — пусто без скелета.

**Что НЕ на экране.**

- Нет номера страницы, нет «страница 2 из 7», нет курсора в URL — курсор
  живёт в состоянии компонента и наружу не выведен (общее число «Новых» до
  полного обхода неизвестно; печатать «показано 50 из 500» — обман, R-29).
- Нет автоскролла к верху таблицы при тике/подгрузке.
- Нет «свежесть в секундах» — существующая надпись `formatFreshness`
  («N минут назад») уже есть в шапке (`FfFbsOrdersScreen.tsx:904–913`),
  оставляем как есть, не дублируем в футере.
- Нет колонки «Приоритет», «Возраст», «Осталось до крайнего срока» и
  никаких новых столбцов — колонки вкладки «Новые» остаются ровно эталонной
  четвёркой `Товар / Селлер / Маршрут сдачи / Отгрузить до` (CLAUDE.md,
  раздел «Эталонное состояние кода»).

### 2. S-03 · вкладка «Новые» · футер таблицы («Показать ещё»)

**Что меняется.**

- Под `TableBody` добавляется строка футера с текстовой кнопкой
  **«Показать ещё»**. Кнопка видна тогда и только тогда, когда сервер вернул
  непустой `next_cursor`; последняя страница футер прячет автоматически
  (иначе оператор жмёт «Показать ещё» и получает то же — обман действия).
- Во время подгрузки надпись меняется на **«Загружаем…»** и кнопка
  недоступна (spinner внутри кнопки, `size="small"`), чтобы двойной клик не
  дёргал API дважды.
- Ошибка при подгрузке — `ErrorNotice` над футером с текстом «Не удалось
  подгрузить следующие 50 заказов» и кнопка «Показать ещё» снова доступна
  (`R-20` — причина не показывается, потому что кнопка активна и `Alert`
  выше уже объясняет).

**Что НЕ на экране.**

- Нет бесконечной автоподгрузки при скролле. Ручная кнопка — сознательное
  решение: авто-scroll на плотной таблице оператора мешает искать глазами
  «свой» заказ.
- Нет «Показать всё» / «Загрузить N следующих» — только одна следующая
  страница за клик.
- Нет пагинации «вперёд/назад» и номеров страниц — таблица односторонняя
  (только вниз), назад ничего не убираем.

### 3. S-03 · вкладки «В работе / В доставке / Завершённые»

**Что меняется.**

- Лимит на первую загрузку падает **500 → 100**. Кнопки «Показать ещё» на
  этих вкладках нет: работа идёт с поставками, объём — десятки, редко
  сотни; если у клиента внезапно окажется >100 поставок в работе,
  открывается отдельная задача.
- Скелет/пустое/ошибка — те же три состояния, что и на вкладке «Новые»
  (`TableSkeletonBody`/`EmptyState`/`ErrorNotice`), формулировки — на
  языке склада: «Поставок в работе нет», «Поставок в доставке нет»,
  «Завершённых поставок за период нет».

**Что НЕ на экране.**

- Нет отдельного фильтра «показать больше 100» — если понадобится, это
  отдельная задача с макетом.
- Нет пересчёта существующих счётчиков вкладок — счётчики вкладок сейчас
  ведёт сервер по всем строкам (не по странице), правка лимита их не
  трогает.

### 4. S-03 · автотик 30 с (фоновое обновление)

**Что меняется (поведение, не UI).**

- Существующий `setInterval` 30 с (`FfFbsOrdersScreen.tsx:594–615`) остаётся
  ровно 30 с, проверка `document.hidden` уже есть — не трогаем.
- Тик обновляет **только первую страницу текущей вкладки** и мержит её в
  состояние: новые строки добавляются к первой странице (визуально —
  подъезжают сверху), существующие обновляются на месте. Позиция скролла
  оператора не двигается. Уже подгруженные вторая/третья/… страницы тик
  не трогает и не сбрасывает (иначе оператор, скроллнувший вниз, теряет
  найденный заказ).
- Пока идёт тик, скелет строк повторно не показываем — визуально экран
  не должен «моргать» дважды в минуту. Индикатор «идёт обновление» —
  только надпись `formatFreshness` в шапке: она перескакивает с
  «N минут назад» обратно на «только что». Отдельного спиннера в шапке
  тика нет.

**Что НЕ на экране.**

- Нет «Идёт обновление…» баннером, нет прогресс-бара.
- Нет кнопки «Пауза автообновления» — если оператор не хочет тика, он
  переключается на другую вкладку браузера, `document.hidden` уже это
  ловит.
- Нет уведомления «пришло N новых заказов после последнего тика» — это
  отдельная задача, здесь не нужна.

### 5. S-03 · «Обновить» и «Забрать заказы из WB» (шапка)

**Что меняется.** Ничего.

Обе кнопки (`FfFbsOrdersScreen.tsx:914–935`, тексты `«Обновить»` и `«Забрать
заказы из WB»`/`«Забираем заказы…»`) остаются как есть. По коду
(`ARCH.md`, «Границы») ручное «Забрать заказы из WB» продолжает запускать
**полный** цикл (лёгкий тик + full sweep) — потому что оператор жмёт эту
кнопку, когда что-то реально не пришло, а автотик режется отдельно на
редкий full sweep.

**Что НЕ на экране.**

- Нет отдельной кнопки «Полный обход WB сейчас» / «Тяжёлый синк» — терминов
  «light/sweep» оператору не показываем (R-30).
- Нет настройки интервала автополла из UI — интервал живёт в
  `settings.fbs_full_sweep_interval_sec`, меняется в `.env`. Отдельного
  экрана «настройки автоопроса» задача не открывает.

### 6. Модалка `FbsPrintPreviewDialog` (сборка ленты ЧЗ)

**Что меняется.** Ничего визуально.

Сервер по этой ручке (`POST /marking-codes/label-artifact-tape`) уходит в
тредпул (карточка A из `ARCH.md`), для оператора это значит только «ответ
приходит без замирания соседних экранов». Заголовок диалога, кнопки
«Печать» / «Печать всех готовых» / «Печать только этого»
(`FbsPrintPreviewDialog.tsx:200–215`), состояние `Alert severity="warning"`
«Готовых изображений нет. Печать не будет открыта.» — всё остаётся.
Существующие подписи попадают под R-19/R-33: печать называется тем, что
поедет на принтер, но переносить эти кнопки на канонический `PrintAction`
из ui-kit — за границами карточки (R-канон границы, п.8.6: существующие
экраны не переделываются ради `РАЗНОБОЙ` — только когда экран и так в
работе; здесь модалка в работе не по этому поводу).

**Что НЕ на экране.**

- Нет прогресс-бара «Собираем PDF…» — тредпул съедает те же 1–3 с, что и
  сейчас, но не блокирует остальной API; для оператора время ожидания не
  меняется, отдельного индикатора не заводим.
- Нет счётчика «X из 500 наклеек готово» — сборка на сервере не даёт
  промежуточных статусов.

### 7. Карточка D (RAM) — визуальных изменений нет

Записка инфраструктуре живёт в `docs/perf/2026-08-21-prod-slow-plan.md`
(если создан ночью — иначе в этой же папке `night/volna-9/cards/05-prod-slow/`).
Оператору D невидим: свободнее память → меньше рестартов
`asya-prod-api-1` (61 рестарт за час 20.08) → меньше пятисекундных
провалов «сервер не отвечает». Отдельной иконки/плашки «сервер здоров»
или «идёт перезагрузка» в UI нет и не заводим (R-30 — техническое
состояние сервера в интерфейсе не показываем).

### Предложенные новые правила канона (для утверждения владельцем утром)

- **R-37 · ДЫРА → предложено.** «Показать ещё» под таблицей — текстовая
  кнопка (`variant="text" size="small"`) в отдельной строке футера
  `TableRow` с `colSpan` во всю ширину, не входит в `ActionGroup` и не
  выравнивается по 168 пикс. Не `SecondaryAction`, потому что R-31
  запрещает отдельно стоящую контурную кнопку. Не `PrimaryAction`,
  потому что главное действие экрана — в шапке (`«Забрать заказы из WB»`),
  а вторая заполненная кнопка снизу спорит с ней по весу и оператор
  начинает искать «где же главное». Состояние «Загружаем…» на кнопке,
  автоподгрузка при скролле — отдельная задача, не по умолчанию (авто
  на плотной таблице мешает оператору искать глазами «свой» заказ).
  На вкладках с малой мощностью (десятки-сотни строк) кнопка не нужна —
  первый лимит просто ставится в 100, курсор не открывается наружу.
- **R-38 · ДЫРА → предложено.** Фоновый тик списка обновляет только
  первую страницу и не смещает позицию скролла оператора. Скелет строк
  на тике не показывается — только на первый рендер таблицы. Индикатор
  «идёт обновление» — надпись «только что / N минут назад» в шапке
  (уже реализована `formatFreshness`), спиннера в шапке тика нет.
  Отдельной кнопки «Пауза тика» нет — работает `document.hidden`.

## Нехватка ui-kit

Один недостающий примитив.

- **`TableLoadMore` (или расширение `States.tsx`).** Нужен, потому что
  «Показать ещё» под таблицей не ложится ни на `PrimaryAction` (спорит
  с главным действием шапки), ни на `SecondaryAction` (R-31 запрещает
  solo-outlined), ни на `IconAction` (это не иконка). Форма: строка
  `TableRow` с `TableCell colSpan={columns}`, внутри — `Button
  variant="text" size="small"` с надписью «Показать ещё» / «Загружаем…».
  Скрывается, если `hasNext=false`. `data-testid` обязателен.
  Пока элемента нет — карточка C формально не проходит R-канон п.«элементы
  из `ui-kit/index.ts`». Владельцу утром решать: разрешить временную
  локальную вёрстку в `FfFbsOrdersScreen.tsx` с обязательством вынести в
  ui-kit следующим шагом, или сначала добавить `TableLoadMore` в
  `frontend/src/ui-kit/States.tsx`.

Ничего больше не требуется: `TableSkeletonBody`, `EmptyState`,
`ErrorNotice`, `ScreenHeader`, `PrimaryAction`, `SecondaryAction`
(в шапке «Забрать заказы из WB» — заполненная), `PrintAction` (в
модалке — расширение под R-33 не в границах карточки) уже есть.

## Находки (нарушения канона / данные / сохранность)

- `NEW_ORDERS_PAGE_LIMIT = 500` (сейчас) на вкладке «Новые» — нарушение
  здравого смысла страничной таблицы (Shopify default 50, Amazon Seller
  Central 25); канон явно этого числа не покрывает, но R-24 «экран не
  рапортует об успехе того, чего не делал» соседствует по духу: тянуть
  500 строк каждые 30 с ради 1–5 новых — это ложная «полнота».
- В шапке экрана уже есть надпись `formatFreshness` (R-канон её не
  описывает, но она полезная — оставляем; кандидат в R-38).
- Персональных данных селлеров/операторов в контракте нет.
- Секретов в затрагиваемых файлах фронта нет.
- Боевой прод 194.87.96.144 контракт не трогает (только описание, не
  доступ).
- Сторож записи в WB не активируется — все правки на чтение WB или на
  фронт.

## Что дальше и кому передавать

Передать **screen-dev** (роль реализации фронта S-03). На стороне
бэка/инфры параллельно уходят карточки A (тредпул), B (расщепление
автополла), D (записка инфре) — они UX-контракт не задевают, их берёт
`backend-dev` по `ARCH.md`.

До старта screen-dev владелец должен утвердить (или отклонить одним
словом) два новых правила канона: **R-37** («Показать ещё» текстовой
кнопкой под таблицей, без бесконечной автоподгрузки) и **R-38**
(фоновый тик обновляет только первую страницу, скролл не двигается,
скелет на тике не показываем). Если владелец правила не принимает —
screen-dev откатывается на локальную вёрстку внутри
`FfFbsOrdersScreen.tsx` и вопрос уезжает в `docs/product/REDESIGN_DEFERRED_RU.md`.
