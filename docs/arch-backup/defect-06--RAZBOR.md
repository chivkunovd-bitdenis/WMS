# defect-06 · Порядок в листе подбора не совпадает с порядком ленты

## Дословно

>

## Что сейчас

По жалобе владельца я проверил три разных места, где формируется «порядок» — они реально не
совпадают ни попарно, и наклейки в ленте вообще не нумерованы. Оператор сопоставляет строку
листа с наклейкой глазами по фото/артикулу.

**Экранная версия листа подбора** (диалог `FfFbsPickList`, кнопка внутри workspace).
`frontend/src/screens/v2/FfFbsPickList.tsx:75` дергает `GET /operations/fbs-supplies/{id}/picking-list`,
серверная реализация — `backend/app/services/fbs_supply_service.py:1574 get_picking_list`. Она
схлопывает заказы поставки в товарные строки ключом `(article, sku_code, size, product_name)`
и в строке 1601 отдаёт `sorted(groups.items())` — то есть по алфавиту артикула. Никакой
нумерации у строк нет, только `article/size/quantity`.

**Печатная версия листа подбора** (кнопка «Печать листа подбора», строки 1611 и 1661 в
`frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx`). Идёт через `printPickingList`
(там же, 1196) → `buildFbsPickingListPrintHtml` в `frontend/src/screens/v2/fbsUx.ts:68`.
Данные — `pickingRows` (`FfFbsSupplyWorkspace.tsx:1084`): та же свёртка «один заказ → одна
строка товара», но собранная на фронте из `workspace.orders` в том порядке, в котором заказы
пришли с бэка (`_load_supply_graph` не задаёт `order_by` для relationship `FbsSupply.orders`).
Нумерация в печати есть — `<td class="number">${index + 1}</td>` (`fbsUx.ts:77`), плюс
колонка «Заказы WB» перечисляет `wb_order_id` каждой единицы через `<br />` (`fbsUx.ts:85`).

**Лента наклеек и КИЗ** (кнопка «Печать всего» на этапе упаковки, `FfFbsSupplyWorkspace.tsx:1774`).
Идёт через `openBulkOrderMarkingPrint(packingOrders)` (`FfFbsSupplyWorkspace.tsx:909`), где
`packingOrders` (там же, 1224) — это `[...workspace.orders].sort` по `product.name`
локалью ru, затем по `wb_order_id`. То есть уже другая сортировка, чем у экранного листа
подбора. На бэке `print_fbs_order_tape`
(`backend/app/services/fbs_order_tape_print_service.py:99 _orders_in_requested_order`) честно
уважает порядок `order_ids` из запроса — сортирует ровно так, как прислал фронт. Наклейки
складываются в HTML секциями `<section class="label">` (`MarkingPrintDialog.tsx:695` и
`FbsPrintPreviewDialog.tsx:118`) без порядкового номера — только фото/QR/КИЗ.

**Итого три порядка, никакой сквозной нумерации:**

| Место | Порядок | Нумерация |
|---|---|---|
| Экран листа подбора (`GET picking-list`) | по алфавиту `(article, sku_code, size, name)` | нет |
| Печатный лист подбора (`buildFbsPickingListPrintHtml`) | в порядке `workspace.orders` с бэка, свёртка по `product.id` | `index+1` строки товара |
| Лента наклеек / КИЗ | `product.name` (ru), затем `wb_order_id` | нет |

Владелец сказал верно: единственное, что уже свели 21.08, — это состав (см. коммит
`a28c24e fix(fbs): лента печатает все заказы листа подбора, а не молча короче`, где ленту
доуравняли по количеству заказов). Порядок и нумерация — не сделаны, я не нашёл ни коммитов
(`git log --all --grep 'сквозн|нумерац|numbering|один порядок'` пусто), ни веток по теме
(`git branch -a --list '*picking*' '*tape*' '*pick-list*'` пусто).

## Что должно быть

Один главный порядок формируется на сервере — из него получают и лист подбора, и ленту. Оба
документа проходят по этому порядку в одну сторону; каждый физический элемент (заказ WB и его
наклейка) получает сквозной номер, который печатается и в листе подбора, и на наклейке. Тогда
оператор берёт наклейку с номером 7, находит в листе строку с номером 7, идёт в её ячейку и
клеит.

Признак, по которому поймём, что получилось: если распечатать лист подбора и ленту одной и
той же поставки — номер N в листе подбора соответствует N-й наклейке в ленте, при любой
сортировке товаров и любом составе заказов. Проверяется одной поставкой на 10 разных товаров:
номера на наклейках 1…N идут строго по возрастанию, каждый номер встречается ровно один раз в
листе подбора (в строке своего товара или в диапазоне строки, если товар схлопывается).

Ключевые продуктовые решения, которые задают форму фичи (сложены допущениями, поскольку
владельцу вопросы не задают, а «ТЗ пишется» прямо приглашает выбрать):

- **Единый порядок берём с сервера, а не считаем на фронте.** Иначе экран и печать снова
  разъедутся. Реализация: `get_picking_list` возвращает не только строки, но и сквозной
  порядковый номер для каждого заказа WB внутри поставки; лента печатается ровно по этой
  последовательности `order_ids`.
- **Порядок сортировки — по товару, потом по `wb_order_id`.** Это ближе всего к текущей
  ленте и к тому, как оператор ходит по складу: сначала все единицы одного товара, потом
  следующего. Внутри товара номера идут по `wb_order_id` (стабильно, воспроизводимо).
  Допущение: сортировка товаров — по имени товара локалью ru (текущее поведение ленты).
  Альтернатива «по коду ячейки» = требует адресного хранения, у клиента его сейчас нет
  (см. defect-04).
- **Лист подбора остаётся схлопнутым по товару**, но в каждой строке добавляется диапазон
  номеров наклеек: «№ 7–12» или «№ 7, 8, 9, 10, 11, 12». Стартовая колонка «№» листа
  начинает нумерацию строки с номера первой наклейки этого товара, а не с 1.
- **Лента печатает номер на каждой наклейке** — над QR или в углу секции, крупно. Формат:
  «7 / 155» (текущий номер / всего). Печатается и на секции QR заказа WB, и на секции КИЗ
  (если товар маркированный).
- **Тот же сквозной номер отдаётся в API workspace** (`workspace.orders[*].sequence_no`),
  чтобы экран упаковки и экран подбора могли показать оператору номер строки/наклейки, не
  дожидаясь печати. Тогда сканирование ленты «наклейка 7» = поиск заказа с
  `sequence_no = 7` — прозрачно и для человека, и для сканера.

Тип задачи — фича, потому что нужно ввести новый видимый признак (сквозной номер), поменять
серверный контракт `picking-list` и `order-print-tape`, и синхронизировать три разошедшихся
источника порядка. Багом это не назвать: сейчас каждая точка работает как задумано, просто
задумки — три разные.

## Вопросы и допущения

**Допущение 1 — сортировка «по имени товара локалью ru, потом по `wb_order_id`».** Владелец
сказал «один главный порядок», не назвал какой. Взял ближайший к текущей ленте — оператор
уже привык к такому порядку наклеек. Если владелец захочет «по артикулу» (как сейчас у
экранного листа) или «по ячейке подбора» — правится одной строкой на сервере.

**Допущение 2 — номер печатается как `N` (без «/ всего») на наклейке, диапазоном в строке
листа подбора («7–12»).** Владелец сказал «сквозная нумерация» — конкретную визуальную форму
не назвал. Формат «7 / 155» на наклейке спорен: он занимает место на этикетке 58×40 мм и
может конфликтовать с QR. Пусть будет крупное `№7` в углу — если тесно, можно перенести в
подпись под QR.

**Допущение 3 — номер не переиспользуется при перепечатке частичной ленты.** Если оператор
допечатывает только один заказ (перепечатка после зажёванной бумаги), у него на новой
наклейке всё равно номер этого заказа в поставке, а не «1». Это уменьшает риск клеить не ту
наклейку не на тот товар. На сервере это уже так работает: `print_fbs_order_tape` уважает
переданный `order_ids`, номер берётся из порядка поставки, а не из выбора.

**Допущение 4 — рамки задачи ограничены `S-03`.** Диалог `FfFbsPickList` (сейчас — отдельный
экран с отметками «Собрал/Упаковал», сортированный по алфавиту) тоже поедет по новому
порядку и получит колонку с номером/диапазоном наклеек — иначе оператор увидит на трёх
поверхностях (экран, лист бумаги, наклейка) три разных номера, что противоречит смыслу
задачи.
