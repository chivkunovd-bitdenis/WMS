## 1. Подтверждённый дефект A-P1: явный отказ Ozon превращается в запрет повторить действие

**Приоритет P1, воспроизведён реальным сервисом и SQLite, внешняя граница — FakeMarketplaceTransport.**

В «Коробах» оператор выбирает «Без ГТД и РНПТ». `send_exemplar_payload` отправляет один полный SET, получает явный HTTP429 и сохраняет `state=rejected`, `in_flight=false`. Это собственная классификация сервиса как завершённого отказа, не потерянный ответ. Но `choice.all_required_absent` и `choices` остаются. `absent_documents_selected` возвращает true независимо от отказа. Любой следующий вызов `save_absent_exemplar_documents` попадает только в resume/STATUS. Новая запись не разрешается после восстановления площадки; исходное намерение не имеет доступного пути повторного исполнения.

Точные места кандидата:

- `backend/app/services/ozon_exemplar_documents_service.py:279–283`: `all_required_absent` без проверки исхода даёт selected=true.
- Тот же файл, `send_exemplar_payload:628–632`: 400/401/403/404/409/422/429 сохраняются как rejected. Это не доказательство, что все эти статусы всегда означают отказ у площадки; в воспроизведении выбран однозначно смоделированный неприменённый429.
- Тот же файл, `save_absent_exemplar_documents:749–760`: selected=true безусловно возвращает resume, не claim новой версии.
- `frontend/src/screens/v2/OzonDocumentsAbsence.tsx:109–111,131–133`: selected ведёт к GET, checked остаётся true, обратный клик не вызывает действие. UI также не даёт выполнить разрешённый явный повтор. Нельзя исправлять это слепым повтором неизвестного SET или массовым absent=false.

Сохранены [проба](astra-a-retry-probe.py) и [точный RED](astra-a-retry-red.txt). Проба использует существующие `_seed_order`, `_remote_snapshot`, `_transport`, реальные `save_absent_exemplar_documents`/БД и синтетический отказ только на SET. После первого отказа transport исправляется, STATUS отвечает `update_available` с прежними значениями, затем вызывается новое явное действие с текущей версией. Результат:

```
FIRST rejected True 1 1
RETRY unknown True 1 1
AssertionError: 1 != 2
1 failed in 0.67s
```

Здесь столбцы — state, absence_selected, version, число SET. Перед окончательным proof была исправлена ошибка конструктора MarketplaceProviderError в самой временной пробе; первоначальный TypeError не является RED продукта. В окончательном прогоне setup успешен, падение на бизнес-ожидании. Вариант STATUS validation_in_process тоже давал один SET, но для итогового доказательства взят update_available. Никакой реальный429 Ozon этим аудитом не воспроизводился.

Запуск из backend кандидата: `PYTHONDONTWRITEBYTECODE=1 PYTHONPATH="$PWD:$PWD/tests" WMS_TEST_DATABASE_URL=sqlite+aiosqlite:////tmp/wms_test_release_a.sqlite WMS_TEST_DATA_DIR=/tmp/wms_test_release_a_data /Users/deniscivkunov/Projects/WMS/backend/.venv/bin/python -m pytest -c pyproject.toml -p tests.conftest -p no:cacheprovider -n 0 -q -s /tmp/test_wms_release_a_retry.py`. Для повторения скопировать сохранённую probe в этот временный test filename. Product/test файлы кандидата не менялись.

Основание — действующее R11 WMS-663: повтор записи допустим после доказанного отказа/завершения и нового явного действия. Текущее owner-уточнение сохраняет R5–R7/R9–R13/R15 и требует восстановимость без слепых SET; оно отменяет строковые формы и массовое стирание, но не разрешает бессрочно блокировать действие после известного отказа. C8/C11 старого UI нельзя считать покрытием новой галки: старый компонент больше не является production-входом. Ведущий отдельно подтвердил, что это исправление существующего отказ→продолжение, не новая функция.

Минимальный контракт для отдельного тестировщика перед исправлением:

1. Явный429, SET не применён → причина сохранена; новый явный retry после устранения отказа создаёт ровно одну новую версию и один новый полный SET. Проверить и сервер, и настоящий checkbox, включая refresh/reopen.
2. Unknown/timeout/5xx с возможным применением → только STATUS, нового SET нет; старый update_available с несовпавшими значениями не является доказательством неприменения.
3. Accepted → повтор/обратный клик не отправляет SET и не стирает документы; маркировка сохраняет намерение и полный payload.
4. В mixed batch ранее accepted/pending posting не пишутся второй раз; повторяется только явно rejected posting, tenant/seller/order/version остаются точными.
