## 1. Прямое поручение владельца следующему исполнителю

Довести незавершённые функции, указанные в актуализированном каноне, до работающего
production и новой сборки Android, которая устанавливается через встроенное
обновление приложения. Работать параллельно. По уточнению владельца 10.09.2026
разработку ведут **Opus extra (`xhigh`)**;
за чат отвечает отдельный агент. Не заканчивать на макете, локальном diff,
зелёных тестах или словах «API подключён».

После аудита Codex по новому прямому поручению владельца сам запускает Claude
через CLI и ведёт выполнение до результата; процессная задача — **WMS-415**. Агент
`mobile_finish`, начавший продолжение WMS-401, остановлен по команде владельца.
Повторная проверка mobile Git после остановки: HEAD
`364e8aed004069ced37b9692fa788dd0eb8d95b2`, рабочее дерево чистое.
Нельзя считать его прежний запуск продолжающейся разработкой.

Новые слова владельца про простой чат имеют приоритет над старыми требованиями
сохранять сложный макет без изменений. Правила сохранности склада и денег остаются:
упаковка — только признак; она не меняет склад и не блокирует работу. Вкладки FBS
свободны; проверки целостности относятся к самой передаче. Значение лимита остатков,
заданное оператором, не расходовать по журналу заказов. Не создавать вторые счётчики
и новые жизненные циклы там, где достаточно существующих данных.

## 2. С чего продолжать и что считать доказательством

Сначала прочитать раздел свежей сверки WMS-414 в каноне и соответствующие
постановки. Для каждой выбранной задачи взять её точный остаток и доказательства,
проверить текущий Git и доступность нужного контура. Старые заголовки внутри
исторических отчётов не являются очередью на повторное выполнение.

Проверка кода WMS-414 выполняется по `0229831f7442823f086f0147ffa85aed05b8ca66`
и отдельно по относящимся к задаче более новым веткам. В **19:20:52 UTC
09.09.2026 (22:20:52 МСК)** заново проверено: этот SHA стоит в `/opt/wms`;
429 Python-файлов в каждом из API, worker и beat побайтово совпадают с ним.
Все 179 файлов веба совпали с сохранённым ранее подтверждённым выпуском.
Четыре службы работают без состояния перезапуска, `/api/health` и `/` вернули 200.
[Свежая проверка](artifacts/wms414-audit-20260909/verification.json).
Это доказательство состава работающего кода, не проверка каждого операторского
сценария и не новое чтение исторических клиентских данных.

В проекте одновременно есть старые и новые экраны/API. Проверять путь, открываемый
из текущего `App.tsx`, а не только первый найденный файл. Например, сохранение
правила остатков в `screens/ff/products-fbs/FfProductsFbsPage.tsx` и в
`screens/v2/FfProductsCatalogScreen.tsx` — разные обработчики. Область дефекта
нужно подтверждать достижимым маршрутом. Старый текст канона может описывать
один из них, хотя второй уже исправлен.

### Не откатывать согласованные колонки FBS

Текущий код основной таблицы содержит восемь колонок; это не обнаруженная
регрессия данного выпуска. Root заново прочитал первичные сообщения владельца
01.09, разрешавшие отдельные артикул, SKU, ШК и размер, и
[разбор колонок](wms-fbs-columns-check-20260909.md). Старое правило про четыре
колонки конфликтует с этим последующим разрешением. Задачи поиска WMS-390 и
названия склада WMS-120 не являются поручением откатить согласованные столбцы.
При редакционной сверке AGENTS учитывать историю; не начинать переделку экрана
на основании старой фразы. Свежая попытка открыть production FBS привела к
экрану входа: самой таблицы root в этом проходе не видел.

### Обязательная общая правка остатков WMS-338/341

Поздний контракт владельца **ещё не соблюдён полностью**. Формула публикации
`min(число, свободный остаток)` уже есть, старый FbsStockPoolDebit в рабочих
сервисах не читается. Однако другое существующее поле
`FbsBindingStockPool.quantity`, которое задаёт оператор, реально изменяется:
резервирование заказа уменьшает его, отмена до передачи увеличивает,
недостача при инвентаризации и передача без резерва также уменьшают.
Root проверил `inventory_service.py:190–310, 930–934, 1674–1736` и реальный
вызов из `wb_marketplace_orders_service.py:479–502` в production SHA.

Поручить **одному агенту** устранение этих мутаций и проверку всех потребителей
существующего числа. Операторское значение меняет только оператор, физический
остаток и существующие резервы определяют доступное количество. Не добавлять
журнал, новый счётчик, дату отсечки или возврат расходной квоты. Снять дубли
старых постановок WMS-329–337 через ссылки на этот общий остаток, а не делать
несколько конкурирующих исправлений. Прочитать актуальные карточки канона:
старые тесты могут закреплять расход числа и не являются продуктовым контрактом.

### Свежие данные, которые нельзя заменять прежними числами

его нельзя смешивать со всеми 6135 историческими FBS-фактами и объявлять любой
неоплаченный факт подтверждённой отгрузкой. Дата начала биллинга по-прежнему NULL;
ставок FBS/упаковки нет ни в v2, ни в старом механизме. WMS-013/022/023/025

## 3. Чат: новая постановка WMS-397/399, отдельный агент

Сделать простой полноценный мессенджер внутри WMS. У каждого селлера всегда
существует **один основной чат по умолчанию**. Дополнительные чаты можно создавать,
но они не заменяют основной. Повторное открытие документа или параллельная
отправка не должны создавать дубликаты основного чата.

В каждом заказе, отгрузке, документе FBS и приёмке доступно компактное действие
«Написать сообщение». Оно раскрывает небольшую форму рядом с документом:
ввести текст, прикрепить нужное и отправить. Рядом — кнопка перехода в полноценный
чат. Не встраивать на каждый экран весь сложный интерфейс переписки.

Сообщение из документа отправляется **в основной чат его селлера**. В ленте
показываются карточка вложенного документа и связанный с ней текст сообщения,
по образцу карточек документов в прежнем макете. Нажатие карточки открывает
реальный документ. Не создавать отдельный чат автоматически на каждый документ.
В основной чат можно писать и просто так, без привязанного документа.

Каждый сотрудник работает под собственной учётной записью. Можно создавать
другие чаты и добавлять сотрудников с учётками. Переиспользовать существующих
пользователей, селлеров и права WMS; не вводить вторую систему логинов для чата.
Участие в чате не даёт права читать чужого селлера или запрещённый документ.
Для документа с несколькими селлерами отправлять только разрешённый контекст
конкретного селлера; не раскрывать ему строки остальных клиентов.

Обязательные возможности: отправка и редактирование сообщений, файлы,
изображения и скриншоты. Вставка **Ctrl+V, на Mac также Cmd+V**, должна принимать
картинку из буфера, показывать её как изображение в редакторе и затем в ленте,
а не превращать в безликий файловый блок. Обычные файлы сохраняются вложениями.
Текст и вложения должны сохраняться на сервере и быть доступны второму участнику
после перезагрузки. Ошибка отправки не теряет черновик, повтор не дублирует сообщение.

Сначала прочитать прототип
`.worktrees/wms399-chat-design/prototypes/wms399-chat` (commit
`6bacd06b6d0c4290eb3c199ead61299bab3726c7`) и прежний контракт
`.worktrees/wms396-stage/docs/reviews/wms397-backend-contract-20260909.md`.
Переиспользовать полезные карточки документов, отображение вложений и компоненты.
Старые предложения автоматически заводить документные каналы, сложные панели,
треды или дополнительные режимы не входят в новую минимальную постановку.
Прежний контракт — исследование, не доказательство реализованного backend.

Агент отвечает за полный срез: минимальный экран, серверное хранение, права,
передачу файлов, переходы в документы и проверку с двумя реальными учётками
учебного контура. Если остаётся обязательное решение, представить владельцу
конкретный простой вариант; не возвращаться к уже решённому вопросу, нужен ли
основной чат и можно ли упростить макет.

## 5. Параллельная работа и проверка результата

Координатор делит оставшиеся задачи канона на независимые участки. Разработка —
Opus с усилием high. Чат — отдельный агент, мобильный FBS/обновляемая сборка —
другой; серверные исправления распределять по независимым сервисам. За общие
файлы и интеграцию отвечает один назначенный человек/агент. Списки ID, пути,
ветки и текущий этап фиксировать в каноне или в привязанных протоколах,
не заводить ещё один постоянно расходящийся бэклог.

Каждый исполнитель читает существующую реализацию, правит, проверяет свой
пользовательский путь и сохраняет commit с WMS-номером. Не запускать полный набор
тестов по кругу. Локально — относящиеся к изменению тесты и обязательные проверки
типов/сборки; полный набор выполняет CI для согласованного среза. Новый прогон
оправдан изменением кода, ошибкой или конкретным непроверенным риском. Не заменять
ручную проверку кнопки десятками искусственных сценариев, повторяющих код.

Когда срез готов, через CLI передать **GPT-6 Astra, high** независимое ревью
точного SHA/diff: постановка, исправления, проверенные пути, границы, миграции,
влияние на склад/деньги, ошибки и повторы. Исправить существенные замечания,
дать ревьюеру только изменённую часть и необходимые связи. Затем пройти
стенд, согласованный merge/release и проверить SHA реально работающего production.
Не сливать старые PR только потому, что они открыты.

После завершения **Opus проверяет результат и делает финальное ревью**.
Если порог лимита уже сработал, финальное Opus-ревью ждёт восстановления
достаточного остатка; Astra продолжает разработку, не запуская Opus ниже порога.
Не объявлять отложенное ревью выполненным.

## 6. Недельный остаток, остановка Opus и передача Astra

Монитор Codex **`wms-claude`** включён в текущем чате: квота каждые **10 минут**,
полный контроль работ каждые **20 минут**
по поручению владельца 10.09.2026. Он проверяет существующий процесс и продолжает
работу без дублирующих запусков; сообщает о существенном результате или препятствии.
Отдельное правило квоты во время активной работы:
Каждые **10 минут** читать свежий недельный лимит того Claude-аккаунта,
которым работают Opus-агенты. Остаток = `100 − использовано`; если есть отдельный
ограничивающий недельный лимит Opus, учитывать и его. Не подменять это остатком
Codex, контекстом беседы, пятичасовым окном или расходом долларов.

Источник — штатный `/usage` Claude Code либо проверенный поддерживаемый сигнал
лимитов. На машине при подготовке установлен **Claude Code 2.1.123**.
В текущей официальной документации поля statusline
`rate_limits.seven_day.used_percentage` требуют **2.1.251 или новее**; нельзя
обещать, что они уже доступны в этой установленной версии. Не извлекать OAuth
токены из хранилища ради самодельного обхода. Если показание отсутствует или
устарело, это «неизвестно», а не 100% остатка: восстановить штатное чтение,
не увеличивать параллелизм вслепую.

Когда свежий остаток **менее 7%**:

1. Прекратить выдавать новую работу Opus. Остановить активных агентов в безопасной
   точке; не прерывать вслепую уже идущую миграцию или внешнюю передачу.
2. Сохранить относящиеся изменения каждого агента в его Git-ветке. Незавершённый
   код можно сохранить как явно помеченный WIP, не выдавая его за готовый выпуск.
   Проверить, что commit не захватывает чужие изменения и секреты.
3. Дописать подробный хэндоф: ID задачи, владелец, checkout, branch, SHA, patch,
   что сделано и осталось, точный последний тест/ошибка, процессы/PID, стенд и
   production, миграции, операции с данными, APK и источник обновлений. Указать
   процент, время чтения лимита и время сброса. Предварительные заметки вести
   по ходу работы, чтобы не пытаться восстановить всё на последних процентах.
4. Проверить остановку Opus-исполнителей. Не оставлять параллельных писателей
   в тех же файлах и не удалять их checkout.
5. Через CLI запустить **Astra 6 high** и передать точный путь нового хэндофа.
   Astra продолжает в мультиагентном режиме, проверяя фактическое состояние,
   а не переигрывая операции по старому тексту. Не запускать второй координатор,
   пока первый ещё раздаёт работу.

Источники: [Claude Code /usage](https://code.claude.com/docs/en/commands),
[поля лимитов statusline](https://code.claude.com/docs/en/statusline).
Монитор не должен открывать платные кредиты, автоматически покупать лимит
или расходовать Codex reset — этого владелец не поручал.

## 7. Проверенные команды CLI

При подготовке проверены `codex-cli 0.153.4`, `claude 2.1.123`, их `--help`;
`codex features list` показывает `multi_agent` как stable, включённую функцию.
В локальном каталоге моделей доступна `gpt-6-astra` с усилием `high`.
Проверка синтаксиса не означает принятия задачи. Фактический запуск и его состояние
сохраняются в [журнале WMS-415](wms415-claude-launch-20260910.md).

Интерактивный координатор Claude, после перехода в выбранный постоянный checkout:

```sh
CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 CLAUDE_CODE_EFFORT_LEVEL=xhigh \
  claude --model opus --effort xhigh --teammate-mode in-process --permission-mode auto
```

Используется интерактивная сессия: современная документация Claude отличает
agent teams от обычных подагентов в `-p` режиме. Попросить координатора создать
команду Opus с раздельными владельцами файлов; он должен подтвердить реальные
запуски агентов. В версии 2.1.123 доступен прежний TeamCreate-порядок; при
отсутствии инструмента использовать явных параллельных подагентов и точно
зафиксировать фактический режим. [Документация команд агентов](https://code.claude.com/docs/en/agent-teams).

Передать ему этот документ и актуальный канон. Полномочия подпроцессов выбирать
в рамках разрешённой задачи; не добавлять обход ограничений по умолчанию.

Ревью Astra: сначала записать конкретный запрос в обычный файл, указав SHA,
состав задачи и запрет изменений. Затем из выбранного checkout:

```sh
codex exec -m gpt-6-astra -c 'model_reasoning_effort="high"' \
  -s read-only -o astra-review-result.md - < astra-review-request.md
```

Передача разработки Astra при пороге: в `astra-continuation-request.md` указать
абсолютный путь хэндофа, текущие SHA, инструкцию продолжать несколькими агентами,
границы доступа и запрет повторять уже выполненные внешние операции:

```sh
codex exec -m gpt-6-astra -c 'model_reasoning_effort="high"' \
  --enable multi_agent --approve-for-me \
  -o astra-continuation-result.md - < astra-continuation-request.md
```

Это примеры проверенного синтаксиса. Имена файлов запроса/результата выбираются
в постоянном checkout под соответствующим WMS-номером. Запускать в нужном
checkout, а не в домашней папке. Получить фактический результат/ошибку запуска;
сам факт вызова CLI не означает, что модель приняла задачу.
[Справочник CLI](https://learn.chatgpt.com/docs/developer-commands?surface=cli),
