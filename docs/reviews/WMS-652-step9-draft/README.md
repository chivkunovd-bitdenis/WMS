# WMS-652 · Шаг 9: материалы барьеров

Verifier и правка deploy workflow перенесены в действующие пути отдельным поручением
WMS-652. Ruleset и CODEOWNERS остаются неактивными материалами для решения владельца;
ruleset имеет `enforcement: disabled`. Не импортировать JSON и не переносить
CODEOWNERS без отдельного разрешения. Файлы не меняют секреты или SSH.

## Состав и доверие

- `CODEOWNERS.example` — будущий `.github/CODEOWNERS`. Защищены workflow,
  правила, CI/deploy-скрипты и весь каталог guards, включая будущий манифест.
  Владелец также проверяет общие `backend/tests/conftest.py`, `backend/pyproject.toml`,
  `frontend/vitest.config.ts`, `frontend/package.json` и lock-файл зависимостей:
  через них можно изменить выполнение неизменных защищённых тестов. При добавлении
  бизнес-проверок нужно проследить используемые фикстуры (подготовку тестовых данных)
  и вспомогательные функции и включить нужные пути в защиту. Это не требует
  одобрения всех изменений продуктового backend.
- `etalon.ruleset.disabled.json` — PR обязателен, запрещены force-push и удаление,
  список обхода пуст, включая администраторов. Защищённые пути требуют владельца;
  общий счётчик одобрений равен 0, чтобы обычная PR не ожидала человека.
  `require_last_push_approval: false` также не вводит одобрение для каждой PR.
- `scripts/ci/verify_ci.py` — применённая проверка допуска выкладки. Использует только
  `gh api --method GET`; сам не запускает CI, не повторяет его и не выполняет deploy.
- `deploy.yml.patch` — проект изменения workflow WMS-641 на коммите
  `c96dbb4821e59aa74f1e5a6e982f7acd7ca2f8f3` (`origin/feat/wms641-support-agent`
  при подготовке). Перед будущим применением нужен повторный diff с принятым WMS-641.

Имена обязательных checks: `baseline`, `backlog`, `backend`, `frontend-build`, `охрана`.
`baseline` — новая задача шага 4, определяющая базовый коммит для сравнения.
От неё зависят `backlog` и `охрана`: при её сбое они пропускаются. GitHub допускает
`skipped` для required status checks, поэтому сама `baseline` также обязательна
в ruleset. Verifier дополнительно требует реальный успех всех пяти задач.
У задачи охраны YAML id — `guards`, но GitHub видит её `name: охрана`.
Источником checks в JSON указан GitHub Actions, integration ID `15368`:
подтверждено read-only ответом check-runs WMS для коммита `567db1786` при подготовке.
До включения сверить имена с новым успешным прогоном. Одноимённый check из другого
GitHub App не подходит. При этом само имя плюс App ещё не доказывает, что запуск
принадлежит нужному workflow: поэтому verifier дополнительно проверяет его ID,
путь, репозиторий, исходный репозиторий, событие и ветку.

Проверка запускается из checkout **коммита доверенного deploy workflow**
(`${{ github.sha }}`), а не из выкладываемого старого коммита. Workflow допускает
только dispatch ветки etalon. CI должен поступать из `.github/workflows/ci.yml`
в этом же репозитории, на `push` в etalon, строго для полного SHA выкладки.
Нужны `completed/success` всего запуска и каждой из пяти обязательных jobs.
Пропущенная, отсутствующая, нейтральная, отменённая задача или повтор имени
не разрешает выкладку. Проверяется также GitHub Actions App у check suite.

## Повторы, страницы и результат

Выбирается последний запуск указанного workflow для этого SHA: максимальные
`run_number`, затем `id`. Старый зелёный запуск не перекрывает новый красный
или ещё работающий. Используется только текущий `run_attempt` выбранного запуска.
Частичный rerun, в котором нет всех обязательных jobs, отклоняется: нужно выполнить
**Re-run all jobs**. Успехи разных попыток не склеиваются. После чтения jobs список
запусков читается ещё раз: появление нового запуска или попытки отменяет допуск.

Списки runs и jobs читаются по всем страницам. Несогласованный total, дубли между
страницами, неполный ответ либо достижение лимита 1000 отфильтрованных запусков
означают отказ. Ошибка API не трактуется как успех. Коды возврата:

| Код | Смысл для вызывающего WMS-641 |
|---|---|
| 0 | Успех; stdout JSON содержит SHA, run_id, run_attempt |
| 2 | Проверка провалена либо обязательное доказательство недопустимо |
| 3 | Ответ API недоступен/неполон/повреждён; инфраструктурная ошибка |
| 4 | Нет нужного push-CI, он ещё работает либо изменился во время проверки; ожидание CI |

Это ещё не интеграция в WMS-641: будущий вызывающий код должен различать эти
состояния и ожидание решения владельца, не объявляя каждое из них ошибкой продукта.
Сам verifier не выполняет скрытых повторов. Небольшой интервал между последней
проверкой и SSH остаётся: это проверка факта на момент допуска, не транзакционная
блокировка GitHub. Версия исходников при этом неизменна.

Параметры WMS-641 `sha` и `attempt_id`, их валидация и run-name сохраняются.
При пустом `sha` один GET фиксирует голову etalon в полном SHA; этот SHA проверяется
и передаётся через `DEPLOY_SHA` на сервер. Последующее движение etalon не меняет
цель. Перед исполнением скрипта сервер проверяет принадлежность коммита etalon
и наличие поддержки `WMS_DEPLOY_SHA`. Старый скрипт без неё отклоняется даже при
пустом исходном параметре: безопасного fallback на новую голову ветки нет.
Сам prod-update уже проверяет точное совпадение checkout с запрошенным SHA.

## Будущее включение владельцем

1. Владелец отдельно выбирает и создаёт аккаунт агента (machine user). Даёт ему
   только write, без admin и без обхода правил. Владелец сам решает, какие новые
   учётные данные выдать и как удалить доступ агентов к своему аккаунту; этот
   документ не даёт агенту разрешения открыть кабинеты, читать или менять ключи.
2. После решения владелец организует PR **от другого аккаунта** с CODEOWNERS,
   скриптом и обновлённым patch. Автор PR не может одобрить собственную PR.
   Если автор — `chivkunovd-bitdenis`, его одобрение как единственного CODEOWNER
   не решает задачу; перенос авторства/выбор другого владельца решается заранее,
   без временного admin bypass. В исходной ветке назначения CODEOWNERS ещё нет,
   поэтому первоначальный перенос отдельно проверяет владелец.
3. Сначала принять CI на push в etalon и провести успешный прогон с реальными
   пятью jobs; перенести CODEOWNERS и verifier/deploy совместимо с WMS-641.
   Проверить доступ владельца, точные имена checks и доступность rulesets/CODEOWNERS
   для тарифа и видимости этого репозитория. Не включать требование несуществующего
   check: оно остановит каждую PR.
4. До включения обязательной `охрана` отдельно утвердить и проверить доверенную
   процедуру обновления защищённого контракта. Текущий строгий checker отклоняет
   **любое изменение манифеста относительно BASE**, в том числе после обычного
   одобрения PR владельцем. Первоначальная установка (bootstrap) разрешённого
   пустого набора не создаёт пути для его последующего пополнения. Поэтому этот
   черновик пока не готов к включению required `охрана` для регулярного развития
   набора. Нужно доказать, что утверждённое изменение текущего SHA проходит,
   неутверждённое — отклоняется, а новый SHA после одобрения требует новой проверки.
   Процедура ещё не реализована; в этой задаче новая система одобрений не создаётся.
   Автоматическое переписывание хэшей и admin bypass не заменяют такую процедуру.
   Основание и ограничения разобраны в [разделе 3 ревью плана](../REVIEW-2026-10-03-regression-guard.md#3-хэши-и-codeowners-решают-разные-задачи-но-не-дают-независимые-барьеры).
5. После выполнения этого условия владелец отдельно разрешает активацию ruleset
   (`active`) и ограничивает production
   environment веткой etalon. Последнее обязательно: старый deploy workflow в другой
   ветке иначе способен использовать production environment в обход нового gate.
   Доступ администратора к изменению ruleset и доступ к root SSH остаются обходами;
   владелец отдельно решает ограничения SSH. Никакого admin bypass в JSON нет.
6. На тестовой ветке/стенде подтвердить: обычная PR проходит без владельца;
   защищённая PR от агента без владельца не сливается; правка после одобрения
   сбрасывает его; чужой App/красный или неполный CI не допускает merge/deploy;
   пустой `sha` остаётся закреплённым при движении etalon. Прод ради проверки не трогать.

Пока эти действия не разрешены и не проверены, нельзя утверждать, что агент не
обойдёт защиту. CODEOWNERS применяется по файлу базовой ветки и защищает изменение
самого CI только вместе с активными серверными правилами и раздельными аккаунтами.
Права `write` сами по себе не создают разрешения на управление секретами.

## Локальная проверка verifier

Из корня репозитория:

```sh
python3 -m unittest discover -s scripts/ci/tests -p 'test_*.py' -v
```

Тесты используют синтетические ответы API, сеть и учётные данные не нужны.
Они проверяют допуск exact SHA, отказы по неверному workflow/ref/event/App,
старый зелёный при новом красном запуске, обязательные jobs, частичный rerun,
изменение попытки между чтениями и пагинацию. Это проверка программы допуска,
а не доказательство активной защиты GitHub или успешной выкладки.

Основания форматов: [GitHub repository rules API](https://docs.github.com/en/rest/repos/rules),
[workflow runs](https://docs.github.com/en/rest/actions/workflow-runs),
[jobs конкретной попытки](https://docs.github.com/en/rest/actions/workflow-jobs),
[CODEOWNERS](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners).
