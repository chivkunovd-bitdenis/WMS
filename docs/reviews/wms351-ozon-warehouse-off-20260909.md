# WMS-351: подтверждённый ноль перед отключением Ozon, 09.09.2026

В `configure_fbs_seller_warehouse` существовал реальный дефект: service сохранял `stock_sync_enabled=false`, после чего route отправлял нулевые остатки. При отказе/неполном подтверждении Ozon настройка уже была выключена; повтор не видел перехода ON→OFF и не повторял ноль. Исключение после service также проходило мимо штатного преобразования в HTTP502.

Проверена цепочка `PUT /fbs-sellers/{seller}/warehouses/{id}` → `fbs_warehouse_binding_service.configure_seller_warehouse` → `_clear_previous_ozon_stock` → существующий Ozon provider. Название файла уточнено по коду: изменения относятся к `fbs_warehouse_binding_service.py`, не к справочнику `fbs_seller_warehouse_service.py`.

Обнуление перенесено внутрь service после проверки входных данных и получения binding FOR UPDATE, до изменения адреса/галок и commit. Используется тот же `marketplace_seller_lock`, что уже есть у `upsert_binding` и фоновой публикации; его отдельное соединение удерживает существующую блокировку до завершения локального commit. Ошибка оставляет ON и прежнюю привязку, выходит через существующий HTTP502 mapper. Удалён Ozon cleanup после commit в route. В обоих изменённых routes прежний предварительный read выполняется только для WB: Ozon теперь не приносит старый ORM binding к ожиданию блокировки. Общий `_get_binding_row` не менялся. WB сохраняет прежний фоновый путь. Снято только условие `existing.served` из cleanup в `_upsert_binding`: обслуживание заказов не является признаком публикации.

В `tests/test_ozon_stock_binding_cleanup.py` новый параметризованный HTTP-тест вызывает настоящий API приложения при подменённом provider: первый запрос получает исключение либо неполное подтверждение; binding в новой сессии должна остаться ON; повтор подтверждает zero и сохраняет OFF; третий OFF не отправляет ещё один ноль. Соседний тест с `served=false, stock_sync_enabled=true` теперь требует обнуления прежнего адреса и по-прежнему исключает товар без правила.

Red на старом коде: **3 failed** — оба HTTP-сценария обнаружили сохранённый false после отказа; unserved-сценарий не обнаружил требуемый zero. После исправления `pytest -q tests/test_ozon_stock_binding_cleanup.py tests/test_fbs_warehouse_binding.py`: **33 passed**, 16.94 секунды. После стилевых исправлений повторены только три затронутых regression cases: **3 passed**, 1.75 секунды. Ruff для route/service/test passed; mypy для двух изменённых application-файлов с `--follow-imports=silent --cache-dir=/dev/null` passed. После последнего ограничения предварительного read только WB Ruff и mypy снова passed. Повтор семи тестов профильного файла не дошёл до сценариев: 7 setup errors при создании SQLite и Errno 28 (диск заполнен); это инфраструктурный незавершённый повтор, а не дополнительный зелёный прогон. Runtime `/Users/deniscivkunov/Projects/WMS/backend/.venv/bin/python`; только изолированная SQLite из conftest, без новой PostgreSQL БД. Предупреждения — прежние SWIG deprecation.

Все внешние операции и credentials тестовые. Реальный Ozon/WB, настройки стенда, склад, подбор, отгрузка, упаковка, auth и frontend не изменялись. PostgreSQL-конкуренция в этом срезе не тестировалась; использован существующий lock-контракт, без новой сущности. Внешний HTTP и commit БД не образуют общую транзакцию: при сбое commit после подтверждённого нуля настройка может остаться ON; повтор снова безопасно обнуляет. Нового механизма восстановления не добавлено.

Commit включает только свои route/service/test и этот отчёт. Canonical, push и общий выпуск остаются за root; этот результат не является доказательством live-публикации Ozon.
