## Официальный путь

Для приёмки ЧЗ рекомендует True API: `cises/info` проверяет сведения о коде, а `cises/check` — криптографическую часть. Кассовый API разрешительного режима для приёмки применять запрещено; переносить сюда CDN/KKT-проверку нельзя. [Разъяснение ЧЗ от 22.01.2025](https://markirovka.ru/community/rezhim-proverok-na-kassakh/proverka-markirovannoy-produktsii-v-moment-priyemki-po-kriteriyami-razreshitelnogo-rezhima-po-api).

Актуальный публичный документ удалось прочитать с `docs.crpt.ru` обычным curl с проверкой TLS; web-reader остановился на ограничении размера документа. Контракт из разделов 1.5, 5.1.2 и проверки крипточасти:

- `POST https://markirovka.crpt.ru/api/v3/true-api/cises/info`, `Authorization: Bearer <token>`, JSON-массив нормализованных КИ, например `["<КИ>"]`. Ответ содержит `cisInfo.status`; `INTRODUCED` означает оборот. До 1000 КИ; `pg` необязателен.
- `POST <базовый URL True API>/cises/check`, тело `{ "codes": ["<полный КМ>"] }`. Возвращает `result` и `quantity` при одинаковом результате для всех; при смешанном результате — список невалидных `codes`. Нельзя подставлять массиву один общий зелёный результат без проверки этой семантики.
- Нужен токен зарегистрированного участника с подключённой товарной группой. Авторизация: `auth/key`, затем `auth/simpleSignIn` с подписанными УКЭП данными. Токен действует не более 10 часов. Документ предусматривает JWT до конца 2026 года и единый UUID-токен с `unitedToken`; автоматическое обновление всё равно требует разрешённой подписи.

[Официальное описание True API](https://docs.crpt.ru/gismt/True_API/). Статус оборота сам по себе не подтверждает криптографическую подпись полного отсканированного кода.

## Минимальный дальнейший срез

Сначала проверить только наличие текущего токена у точного селлера приёмки. Если он уже есть и разрешён для этого контекста, одна разрешённая проверка официального API может подтвердить его действительность и доступ к нужной группе. Ошибка авторизации должна остаться недоступной проверкой, а не признаком плохого товара. Ни восстановление подписи, ни выпуск новых токенов в этом исследовании не разрешались и не выполнялись.

После подтверждения доступа узкая реализация — заменить транспорт и интерпретатор в существующей фоновой проверке, используя scoped credentials и прежний `cz_check` в событии приёмки. Сохранённый полный КМ передавать в криптопроверку; для информации о КИ нужна соответствующая официальному формату проекция без порчи сохранённого оригинала. Обрабатывать по-кодовые ошибки, сопоставлять ответы с запрошенным кодом; неизвестный/неполный ответ оставлять `unavailable`. Зелёный возможен только после подтверждения оборота и криптопроверки, при отсутствии подтверждённого блокирования. Для первого ограниченного запроса один код устраняет неоднозначность агрегированного криптоответа; для рабочего потока соблюдать документированные ограничения и не делать повторный запрос на каждый повторный показ списка.

Новые сущности, отдельный учёт склада, изменение жизненного статуса `MarkingCode`, блокировка приёмки/упаковки и UI-переделка не требуются. Используется существующий job вне DB-lock во время HTTP. Если действующей авторизации нет, это конкретная внешняя зависимость WMS-396, которую нельзя закрыть очередным endpoint без подписи. Доступность официального метода из staging/production и валидность credentials пока не подтверждены; синтетический код не является положительным эталоном криптоподписи.

Тесты приложения не запускались: исходники не менялись. Для будущего изменения достаточно целевых проверок раздельных info/crypto результатов, неверного/истёкшего токена, отсутствующего кода, смешанного crypto-ответа и неизменности количеств/жизненного статуса; затем одна реальная разрешённая проверка и браузерное чтение сохранённого результата. Этот отчёт не подменяет такую проверку.

## Изолированный адаптер True API, 09.09.2026

Реализация выполнена в `codex/wms396-true-api` от `origin/etalon` (`054897e270533d3e0fc65b651d420b3af8332fce`). Этот раздел заменяет только прежнее предложение будущего транспорта; исторические HTTP451 и отсутствие положительной live-проверки выше остаются фактами прежней проверки. Реальные credentials и коды в этой работе не читались, реальные API проверки не вызывались.

Повторно прочитана [официальная документация True API](https://docs.crpt.ru/gismt/True_API/), включая адрес production `https://markirovka.crpt.ru/api/v3/true-api`, методы `cises/info` и `cises/check`, их тела/ответы и интервал 2 секунды, до 1000 кодов в пакете. [Официальное описание проверки при приёмке](https://markirovka.ru/community/rezhim-proverok-na-kassakh/proverka-markirovannoy-produktsii-v-moment-priyemki-po-kriteriyami-razreshitelnogo-rezhima-po-api) различает получение статуса и проверку подписи, требует True API JWT и исключает использование кассового разрешительного API при приёмке. Статья 2025 года приводит другие частотные значения; реализация следует более строгому текущему документу — 2 секунды между запросами.

`true_api_marking_check.py` — узкий адаптер только этих двух методов. `info` получает массив коротких КИ (AI01+AI21 до первого GS), `check` — исходные полные КМ в `codes`. Сохранённый raw/GS не переписывается. При отсутствии однозначного GS-разделителя граница serial не угадывается: возвращается человеческое unavailable с просьбой отсканировать полный код. Ответ info сопоставляется по requestedCis и cis, а не позиции массива; дубли/чужие/неполные ответы не дают зелёного. Crypto принимает полное подтверждение result+quantity либо смешанный список невалидных `codes` (не `invalidcodes`). Короткий invalid-КИ, неоднозначный для двух разных подписей, оставляет пакет неподтверждённым. INTRODUCED становится зелёным только с явным положительным результатом криптопроверки и без указанного блокирования ogvs.

Существующий job собирает pending-вложения по селлеру, разбивает на пакеты до 1000 и обновляет прежний cz_check в импортном событии. Чтение short/full, tenant/seller и токена завершается до HTTP; сохранение результатов выполняется отдельной короткой транзакцией. Удалённые вложения пропускаются, добавленные во время проверки подхватываются прежним drain-loop. Автоматическая проверка не обновляет завершённые ответы; ручная force сохраняет прежнюю семантику. Lifecycle MarkingCode, количества, склад, упаковка, приёмка и frontend не менялись.

`get_cz_token_for_seller` выбирает только зашифрованный cz_token с tenant/seller scope. OMS и marketplace secrets не выбираются и не расшифровываются. Отсутствующий/нечитаемый токен, HTTP401,429,451, сетевой отказ или неподтверждённая форма ответа дают unavailable. Нет выпуска JWT, обновления токена, КЭП или автоматических повторов HTTP.

Ограничение частоты использует существующий process-local MarketplaceBackoff, с резервированием двухсекундного интервала до каждого запроса. Между отдельными процессами/репликами общего ограничителя нет; это явно принятая граница текущего минимального среза. При нескольких workers нельзя обещать общий лимит учётной записи. Новых таблиц, Redis-механизмов, журналов, счётчиков или DB-lock на время HTTP не добавлено.

Проверки на SQLite `:memory:` и HTTP mocks: 39 целевых cases passed за 3.00s (парсеры, malformed/missing, crypto ambiguity, 401/429/451/offline, scoped CZ-only credential, interval 0→2→4, worker idempotency/no-stock, manual/automatic, удаление во время HTTP, printed pool). Дополнительно один новый пакетный case passed за 0.74s: два КИЗ одного селлера дают один info и один crypto запрос, оба raw сохраняются. Остальные тесты профильного receiving-файла не перезапускались. Ruff прошёл на пяти затронутых Python-файлах; mypy с `--follow-imports=silent --cache-dir=/dev/null` прошёл на трёх application-файлах. Использован существующий `backend/.venv/bin/python`; установок, новой PG БД, полной suite, APK или сборки frontend не было.

Адаптер локально проверен на синтетических ответах. Положительная проверка действующего ЧЗ-токена, настоящего КМ и браузерное чтение результата не выполнены; это не подтверждение готовности live-проверки и не разрешение менять секреты. Дальнейшие review, CI, развёртывание и отдельная разрешённая приёмка остаются этапами основного исполнителя.

## Дополнение: запись ответа старого worker после ручного повтора

Независимое замечание Astra подтверждено отдельной конкурентной проверкой на PostgreSQL. Старый worker уже получил ответ и прочитал job.running; параллельный штатный schedule_check(force=True) переводит просроченную job в failed и создаёт новую pending. Пока новая транзакция держит блокировки, старый worker до исправления ждёт event-lock со старым объектом job; после её commit записывает introduced поверх pending новой проверки. На старом коде целевой тест действительно упал: ожидался pending, получен introduced.

Исправление только в короткой фазе сохранения HTTP-ответа: _request(lock=True) → перечитать BackgroundJob с populate_existing → проверить running → event-locks → сохранить. Это тот же порядок блокировок, что у schedule_check. HTTP по-прежнему выполняется до открытия этой сессии, новые сущности не добавлены.

Тот же тест после исправления: 1 passed, 34 deselected, 2.48s. Он использует две реальные транзакции, фиксирует PostgreSQL wait_event_type=Lock, проверяет сохранение pending и фактическое выполнение новой проверки со своим отличающимся ответом. Подменён только внешний check_batch; новые реальные КМ/credentials/API не использовались. Ruff и mypy изменённого service прошли. Собственная БД wms396_trueapi_race_20260909_01 после проверки удалена, отсутствие подтверждено pg_database, выполнен CHECKPOINT локального сервера. Чужие БД не менялись. Полный набор не запускался.

Процессное ограничение частоты и отсутствие положительной live-приёмки из предыдущего раздела остаются незакрытыми границами; эта поправка их не скрывает и не добавляет новую инфраструктуру.
