## D3 — P2: после отмены preview состояние busy не снимается

**Относится к F3; WMS-442 R9a, C15/C17.** Место: `frontend/src/screens/ff/warehouse-map/WarehousePrinterDialog.tsx:54–65`, также reset при открытии `:46–50`.

Прежнее неправильное назначение B после preview A устранено: code/warehouse захвачены, matching проверяется, устаревший ответ подавляется. Однако та же обязательная последовательность теперь оставляет диалог без работающей проверки.

**Точный сценарий:** ввести A → «Проверить» → пока HTTP задержан, изменить код на B → дождаться ответа A. inspect выставил busy=true; changeCode увеличил version, но busy не сбросил. Устаревший finally закономерно не исполняет setBusy(false). Preview A не показывается, но «Проверить» для B и проверка состояния остаются заблокированы сообщением «Проверяем код», хотя запрос завершился. Закрытие/повторное открытие также не сбрасывает busy.

**Собственное воспроизведение:** использован прежний исполняемый harness фактического transpiled компонента с управляемыми hook/fetch адаптерами. На новом коде assertions подтвердили `oldPreviewSuppressed=true`, `busyAfterSettledPreview=Проверяем код`, то же после close/reopen. Сервер/браузер/реальный pairing не использовались. Проба `/tmp/wms-final-printer-delta-probe.cjs` — удобство передачи, причинная цепочка полностью зафиксирована здесь.

**Минимальная правка Terra:** при инвалидировании операции новым кодом/складом/закрытием освобождать принадлежащее ей состояние busy, не позволяя старому finally снять busy более нового запроса. Reset открываемого диалога должен включать busy. Повторить ровно A-delay→B→response→успешная новая проверка B и close/reopen; нового UI не требуется.

## D4 — P2: неизвестный результат печати всё ещё нельзя явно перепечатать

**Относится к остаточной части F4; WMS-442 R8, C5/C8.** Место: `mobile/android/app/src/main/java/ru/wms/tsd/features/sorting/SortingScreen.kt:170–180`; неизменённый guard `SortingViewModel.kt:250–252`.

Обычный pending теперь имеет достижимую «Проверить» и после ответа done освобождает прежнее намерение — эта часть F4 исправлена. Но handoff намеренно оставляет «Печать ещё раз» только для terminal результата, что не выполняет уже существующее R8.

**Точная цепочка:** PC мог передать файл в ОС, но завершился без квитанции. По действующему серверному контракту (`backend/app/services/fbs_print_job_service.py:612–616`) такой job остаётся running; автоматического перевода в pending/failed нет. ТСД получает running, хранит unresolvedPrint и всегда предлагает только «Проверить». Повторные GET честно возвращают то же running. После физической проверки принтера работник не может явно заказать новую копию с новым UUID: все остальные пути подтверждения печати возвращаются из-за unresolvedPrint!=null. Рестарт не помогает. Это не просьба автоматически повторять печать и не новое требование: прежний отчёт F4 прямо требовал выполнить разрешённый R8 ручной повтор при неизвестности.

**Минимальная правка Terra:** сохранить проверку старого job и дать предусмотренный R8 явный повтор после осознанного подтверждения возможного дубликата, новым UUID; не переводить старый job в выдуманный успех и не выполнять второй spool автоматически. Проверить running без будущей квитанции → осознанная повторная печать → один новый job. Не добавлять отдельный раздел/режим печати.

## D5 — P2: восстановленный done-документ закрывается до чтения print receipt

**Относится к F5; WMS-442 R3/R5/R8, C4/C8/C12.** Место нового guard: `mobile/android/app/src/main/java/ru/wms/tsd/features/sorting/SortingScreen.kt:58–59,78–79`; необходимая правка загрузки: `SortingViewModel.kt:153–162`.

Карточка сохранённой печати теперь делает done-документ выбираемым после рестарта. Guard также учитывает unresolvedPrint, но **к моменту первого documentDone=true оно ещё не загружено**.

**Точная последовательность:** сохранить pending print, завершить сортировку, перезапустить приложение. Очередь открывает существующий документ по print receipt. Новый SortingViewModel начинает с unresolvedPrint=null. Он читает request и locations, затем строками153–160 публикует loading=false/documentDone=true. После этого выполняется suspend `loadPrintDestination(request)` и только затем `recoverSavedPrint()`. Если GET назначения задержан, Compose видит done=true и все unresolved=null, canLeaveCompletedSorting=true, вызывает onBack. ViewModel уходит до загрузки receipt. Каждое ручное переоткрытие при той же задержке повторяет закрытие. Новый unit-test проверяет уже подготовленное состояние с unresolvedPrint и потому не покрывает этот промежуточный реальный переход.

Это подтверждённая последовательность состояния и точки сетевого ожидания по коду; новый device-pass не заявляется. Она непосредственно продолжает прежний F5, а не расширяет пакет.

**Минимальная правка Terra:** прочитать durable print receipt до первого опубликованного done/разрешённого auto-exit, как уже сделано для loose/cargo. Ошибка локального чтения не должна выглядеть отсутствием receipt. Не ставить восстановление в зависимость от GET назначения нового принтера. Проверить request=done, сохранённый print, задержанный/ошибочный destination: экран не закрывается до установления наличия receipt; затем тот же job восстанавливается. Штатный Back к другому документу сохраняется, складской done не откатывается.
