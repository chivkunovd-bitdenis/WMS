## Почему продукт проходит ревью

Вся лента остаётся одним HTML-документом и одним вызовом print. Ограничивается только одновременно запускаемая работа decode, не количество коробов и не число страниц. Следующая группа начинается после успешного завершения предыдущей; перед print должны завершиться все группы. Ошибка любого изображения, включая позднее, отклоняет подготовку, удаляет непригодный iframe и возвращает ошибку экрану. Ни передача, ни успешные отметки ещё не происходят. Между группами есть два кадра родительского окна и ограниченный таймер ожидания: скрытый iframe не становится источником бесконечного ожидания кадров.

Синхронная запись точного HTML, идентификатора попытки, исходных timestamps и списка путей выполняется непосредственно перед print. Если запись не удаётся, управление не достигает print. Неизвестный результат print сохраняется как unknown; следующий вызов сначала читает документ и не печатает повторно автоматически. Ответ оператора о проверенном результате лишь разрешает последующее отдельное подтверждение перепечатки. afterprint используется для освобождения источника, а не как доказательство выхода бумаги.

После состоявшейся передачи сохраняется transferred, затем последовательно записываются только существующие технические отметки. После потерянного ответа восстановление сначала читает исходный документ: timestamp, изменившийся относительно сохранённого printedBefore, исключает повтор уже принятой отметки; неизменившиеся/пустые остаются в исходном списке. Сохранение уменьшенного списка после каждого ответа позволяет продолжить хвост без второй передачи ленты. Ошибка загрузки результата или записи локального состояния не разрешает молчаливую повторную печать. Синхронный ref защищает два быстрых подтверждения в одном экране до первого await.

Сохранение использует существующую запись восстановления, разделённую по API/tenant/user/document, с сохранением соседних pending/totals. Новый серверный журнал или бизнес-статус не введён. Вызовы ограничены чтением документа и прежними mark-label-printed; создание коробов, остаток, резерв и расположение не меняются. Существующие backend-проверки tenant/request/box прочитаны и не изменены. Перегрузка без beforeTransfer остаётся void и сохраняет прежний путь подготовки для непрерывной FBS scan-to-print и одиночного вызова утилиты; новый отклонённый Promise этим потребителям не навязывается. Разметка, размеры и построение CODE128 не менялись. Общие действия одиночного короба/грузоместа продолжают пользоваться исходными targets и путями, получая защиту передачи и восстановления без нового бизнес-ограничения.

## Почему коррекция тестов проходит отдельно

Это **разрешённое семантическое изменение контракта**, а не замаскированная fixture-only правка. Обязательное одновременное начало всех N заменено проверкой реально перекрывающихся decode в удерживаемой группе; сохраняются отзывчивость, ноль ранних передач/отметок и готовность всех N перед единственной передачей. Фиксированное число 32 не превращено в бизнес-ожидание. N200/300, DPR4, качество PNG, порядок, размеры и количество PDF-страниц, проверка CODE128 из raster PDF остаются прежними.

PDF-помощник декодирует каждое исходное изображение настоящим native decode, но не создаёт искусственную нагрузку all-N одновременно. Реальная ошибка native decode по-прежнему отвергается. C5 теперь ждёт фактическую ошибку и освобождение busy, а не наступление невозможного при группах состояния all-N-start. Проверяются отказы 150 и 299 и полный явный повтор с 300 отметками. C6 усилен с неполного ограничения количества до точного состава, порядка и однократности всех 200 отметок после одной передачи.

Последующая коррекция 6b6 убирает ожидание завершения native promises уже уничтоженного iframe — это не бизнес-результат. Счётчик готовности теперь принадлежит конкретному iframe, поэтому не переносит готовность старой ленты в новую. Только наблюдатель остановленных кадров использует таймерный polling; его timeout 30 секунд не повышен. Общий FAIL первого запуска сохранён. Негативные snapshot-контроли действительно проверяют функции assertions, но не выдаются за прогоны мутированного продукта.

Проверенные пары blobs: browser `13d6d57bf1734f90d45598428997e8cf84ec3f29` → `ba1a936a2951970c71edb2bd8c1dc441038f7b72` → `3f29649e56f986e8e549da592937474197197418`; DOM `0fe83393d9a981f7a67c8c6df01c134703db6c7a` → `d29e1134cf728bb114c3c35a868df2fba2b7ce8e`. Тела C3/C7/C8/C10 дополнительно сравнены программно с `0e6a7fbc`: неизменны. node --check browser-контракта и git diff --check прошли. DOM-коррекция прочитана, её выполнения в этом ревью нет.

## Доказательства и точные ограничения

Исходный независимый результат тестировщика опубликован в `ad722d8b7e12ccbc32f3603dc5870880d74f08a3`: [отчёт](../evidence/WMS-672/testwriter-remote-result.md). Прочитаны сохранённые pins, blobs, журналы и состав assertions, а не только итоговое слово PASS. В source-hashes обоих запусков product-source.manifest и product-runner.manifest имеют одинаковый SHA256 `26a096a52bfe5a92e68a9844cf1679d5193d0690036e010dcf8262ccb4f5f5b6`.

- Run 37440457090: приёмка300 и возврат300 — реальный PDF ровно 300 страниц 58×40, текст/порядок каждой страницы и распознавание raster CODE128 страниц 1/151/300; C6 — двойное подтверждение, все 200 отметок один раз. C4/C5 этого запуска остаются FAIL ошибочных новых наблюдателей, а не переписанным историческим PASS.
- Run 37441324711 на неизменном продукте: C4/C5 PASS, включая реальные удерживаемые decode, отзывчивость, поздние отказы 150/299, полный повтор и остановленные кадры. Измерения подготовки 1/200/300: 710.005 / 3780.237 / 5073.350 ms. Они включают удержание оснасткой, не являются обещанием времени принтера. Ранее успешные C1/C2/C6 повторно не гонялись.
- Собственная ограниченная проверка ревьюера: TypeScript AST извлёк именно текущую функцию printInboundInternalLabels из TSX; она транспилирована и выполнена в Node VM с моделируемыми storage/HTTP/print. Четыре сценария PASS: потерянный ответ принятой отметки 150; то же при уже существовавших timestamps перепечатки; потерянный ответ неприменённой отметки; неизвестный результат print. Первые три после новой VM/сброса React ref доводят исходные 300 до complete/пустого списка с теми же ID/HTML и единственной передачей. Принятая отметка не повторяется; непринятая 150 повторяется ровно один раз. Unknown остаётся без новой передачи. Это исполнение реальной функции с синтетическими границами, не браузерный тест reload и не проверка сервера.

Старые браузерные C7/C8 доказывают только сохранение попытки/источника и отсутствие второй передачи. Их HTTP-fixture не моделирует обновлённые timestamps и не доказывает завершение всех 300 отметок после потери ответа. **Этот пробел полного браузерного доказательства остаётся**, собственный узкий probe его не переименовывает в закрытый C7/C8. Он относится к уже заданному восстановлению R5/R6, а не к новой архитектуре или новому бизнес-требованию. Отдельный повтор HTTP-запроса/серверная идемпотентность не доказаны браузерным C6. Само отсутствие такого доказательства не является найденным дефектом просмотренного кода; аналитику нельзя приписывать этим тестам более широкий результат.

C9/C11/C12 этим ревью не закрыты, полная приёмка остаётся за аналитиком. Физическая бумага, очередь реального принтера, live API, CI и деплой не проверялись. Новые навыки/агенты, Mac-браузер, БД и локальная сборка не запускались. Повтор многоминутных неизменных тестов не выполнялся. При завершающей проверке возник ENOSPC для shell heredoc; простой read-only node -e затем успешно проверил идентичность кода и неизменные тела тестов. Чужие файлы не удалялись.

Итог: **PASS реализации двух точных продуктовых коммитов; отдельный PASS двух точных тестовых коммитов в рамках 6f1b196b.** Необходимости продуктовой переделки по найденному дефекту нет. Для следующего этапа сохранить перечисленные границы доказательств в заключении аналитика; данный документ не подменяет его приёмку и не разрешает выпуск.
