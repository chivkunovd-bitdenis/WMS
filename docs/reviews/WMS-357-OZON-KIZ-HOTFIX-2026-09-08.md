# WMS-357: сканирование ЧЗ Ozon на упаковке

Основание: отдельное поручение владельца 08.09.2026. Ветка `codex/hotfix-ozon-kiz`, база `6b1bd3d8`. Это изолированный diff: перед выкладкой его нужно перенести поверх актуального production, сохранив WMS-351. Production и внешние API при подготовке не изменялись.

## Официальный контракт

Публичная документация Ozon Seller API просмотрена в Safari 08.09.2026:
- [Set V6](https://docs.ozon.ru/api/seller/#operation/PostingAPI_FbsPostingProductExemplarSetV6): асинхронная проверка наличия в обороте ЧЗ и сохранение; HTTP 200 означает создание задачи, результат читается отдельным status.
- [Status V5](https://docs.ozon.ru/api/seller/#operation/PostingAPI_FbsPostingProductExemplarStatusV5): `validation_in_process` — проверяется, `ship_available` — сборка доступна; `ship_not_available` — сборка недоступна.

Для схем validate/ship дополнительно прочитан существующий точный снимок официального OpenAPI от 25.08.2026: `tasks/ozon-integration-20260825/OZON_FBS_OPENAPI.json`, provenance в соседнем `OZON_FBS_API.md`. Новый download swagger через web/curl остановился на redirect/challenge, поэтому новый снимок не заявляется. Validate V5 проверяет состав и количество символов. Ship V4 переводит отправление в awaiting_deliver и рекомендует проверить результат через posting/get; он не вызывается сканированием ЧЗ. В текущем WMS ship выполняется при получении QR упаковок, позже ввода маркировок.

Set требует повторно передавать полный уже внесённый набор. Пример документации: сначала 10 экземпляров, затем добавляются 60 — повторно передаются все 70. Документ не даёт явной гарантии принятия первого кода неполного отправления и не требует в этом описании присылать пустые экземпляры create-or-get. `ship_not_available` не объясняет сам по себе, вызван ли отказ плохим кодом или неполнотой отправления. Эти границы не подменены предположением; реальные Ozon вызовы не выполнялись.

## Подтверждённые разрывы и изменение

`FfFbsSupplyWorkspace` вызывает существующие lookup → validate → commit. Lookup раньше проверял только WB-поля стикера, теперь у Ozon сначала проверяется исходный posting_number и известные дочерние posting_numbers. Неоднозначность Ozon возвращает явную ошибку; порядок и выбор первого WB-совпадения сохранены. API отдаёт marketplace и читаемый номер отправления; в панели Ozon больше не показывается технический отрицательный WB-ID.

Предварительная проверка кода из пула раньше сравнивала product_id с первой родительской позицией заказа. Для Ozon теперь используется существующий resolve_marking_position, как в commit; сохраняются tenant/seller/product/занятость и проверка дублей. Повтор собственного активного кода допускается и не отправляет его второй раз. Нормализация raw CIS остаётся общей с WB, включая GS; UI удаляет только хвост клавиатурного сканера, не внутренний разделитель GS.

Commit Ozon возвращает фактический meta_status. API сохраняет прежнюю форму WB-ответа без нового null-поля. Оператор видит «Ozon проверяет», пока статус pending; строка становится зелёной только по существующему признаку полной подтверждённости. Metadata теперь показывает все текущие Ozon экземпляры, а не один последний код. Новый знаменатель из количества всех товаров не введён.

Кнопка «Проверить ЧЗ» вызывает существующий POST /markings/sync и перечитывает workspace. Она нужна, потому что обычный load читает локальные данные, а sync_marking_statuses_for_assembling_supplies фильтрует marketplace=wb. Кнопка не повторяет set. Ошибки сохраняют видимый текст; pending не выдаётся за accepted.

Для замены подтверждение спрашивается после определения конкретной позиции; WB masked-текст сохранён. Полный payload Ozon исключает прежний код только для заменяемого SKU+exemplar_id+mark_type, сохраняя другие экземпляры и типы. До изменения тест воспроизводил 4 mandatory_mark вместо 3 при замене кода второго товара; после изменения отправляются 3.

Штатный start_supply_work создаёт PackagingTaskLine для всех Ozon product_positions с их quantity. Ручной браузерный seed не создаёт task/lines: проверка должна нажать штатное «Начать работу с поставкой». Новых сущностей, статусов, gates, складских операций или изменений резервов этот diff не вводит. Упаковка остаётся фактом, а не разрешением для скана или навигации.

Реальную работу с кабинетом Ozon и физическим сканером эта изолированная приёмка не утверждает.
