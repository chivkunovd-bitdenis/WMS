## Остаточный доступный путь: абсолютное количество подбора не приводит документ к нулю

**Места:** `backend/app/api/marketplace_unload_requests.py:1395` вызывает `set_pick_allocation`; `backend/app/services/marketplace_unload_collect_service.py:716–743` возвращает stock и вызывает только sync_lines_from_pick_allocations. Коробочный состав и legacy baseline этот путь не корректирует. При отсутствии allocation `packaging_task_service.sync_lines_from_pick_allocations` возвращает прежний task; следующий box sync видит оставшиеся строки коробов.

Реальные web-вызывающие прочитаны в coordinator: `frontend/src/screens/ff/FfMpUnloadPickPanel.tsx:277` и `frontend/src/screens/ff/unload-pick/FfUnloadPickPage.tsx` отправляют POST `/operations/marketplace-unload-requests/{id}/pick/set`. Это существующее действие, а не придуманная внутренняя функция; браузерное выполнение этих форм здесь не заявляется.

**Воспроизведение на текущем SHA:** historical box/allocation2 ready1/work1 плюс реально подобранная unpacked1. Исходно boxed3/picked3, task ready1/work2, baseline1/1, stock0. При включении pick/set в C20 это **P1**, препятствующий общему PASS. Исправление remove_from_box эту доступную форму изменения количества не покрывает.

**Честная атрибуция:** прочитан тот же путь в исходном `c6e5734b`. Он уже возвращал остаток и удалял allocation без изменения коробов; sync при пустом подборе уже делал early return, box sync использовал прежнее confirmed и оставшийся boxed. Следовательно, базовая рассогласованность полного нуля унаследована, а не доказанно внесена последним diff. Новые legacy-поля теперь также остаются в этом незакрытом пути. Точная динамическая последовательность на c6 не запускалась; историческая атрибуция основана на чтении кода, текущий результат — на PostgreSQL-пробе. Коробочный PASS от этого не отменяется.

## Граница для исходного БА и передача

C20 требует полного нуля и проверки обеих затронутых форм изменения количества. Ведущий подтвердил реальные web-вызывающие pick/set. Исходному БА через ведущего передаётся короткая неоднозначность: входят ли именно эти две формы абсолютного подбора в записанный C20, либо предполагались только варианты коробочного удаления. Ревьюер не сужает контракт самостоятельно и не закрывает его общим PASS при сохранённом результате выше. Факт текущей несогласованности остаётся при любом решении о границе; нового запрета действия не предлагается.

Нужны явное сопоставление C20 с действующими формами и, если pick/set входит в него, исправление этого пути тем же разработчиком. Повтор всей матрицы без изменений не нужен: corrected box flow уже проверен. Сохранены [матрица и pick/set воспроизведение](artifacts/wms444-astra-r13-review/wms444_final_matrix.py), [отдельный C19](artifacts/wms444-astra-r13-review/wms444_final_c19.py). Скрипты направлены только в собственную БД с current_database guard; диагностический pick/set печатает нарушение, поэтому exit0 скрипта не означает общий PASS. Синтаксис проверен AST, diff — на пробелы. Приёмка аналитика, UI, отгрузка, отчёт селлера и деплой этим отчётом не принимаются.
