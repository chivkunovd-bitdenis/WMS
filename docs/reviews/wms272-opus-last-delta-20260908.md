# WMS-272: заключительная сверка двух малых исправлений

Claude CLI --model opus --effort max, tools отключены; переданы точные diff частичного победителя и очистки ложного timeout, без запросов к живым сервисам. Фактическая основная модель: claude-opus-4-7. Изменения сохранены в общей ветке f76a4c9d и ad116f0d.

Одобряю обе правки, дефектов не вношу.

**Первая правка (`_resume_from_orders_operation`, ветка `CONFIRMED`).** Смысл: когда победитель получил от WB частичное подтверждение (часть заказов приняли, часть отвергли), возобновление проигравшего должно приклеивать к поставке-победителю **только фактически принятые** заказы, а не весь исходный набор запроса. Раньше `missing = [o for o in orders if int(o.wb_order_id) not in bound]` тащил и отвергнутые. Теперь фильтр `accepted - bound` (разность множеств: «принятые, ещё не привязанные») отбирает только те, что WB действительно взял. Плюс `workspace["partial_rejection"]` из `response_summary_json` — чтобы возобновившийся клиент увидел ту же картину отклонений, что и первичный вызов. Ветвление корректно: при `partial_confirmation is True` берём `accepted_wb_order_ids` из ответа, иначе — все запрошенные (полный успех). Тест `partial_winner` явно фиксирует, что 27200 привязан к победителю, а 27201 остаётся `supply_id is None, status == "new"`, и что `partial_rejection.accepted_orders / rejected_orders` доходят до вызывающего.

**Вторая правка (`create_supply_from_orders`, успешный путь).** Хелпер `mark_operation_pending_confirmation` универсально проставляет `error_code = wb_timeout` как безопасный дефолт для тайм-аут-вызывателей (когда мы уходим в `pending_confirmation`, не зная финального ответа WB). На успешном создании такой маркер — это ложный «истёк таймаут WB» на операции, которая на самом деле прошла и просто ждёт `confirm_operation`. Один строкой `operation.error_code = None` до коммита это чистится ровно в успешной ветке; поведение хелпера для настоящих таймаутов не меняется. Тест это стережёт: перед `_close_pending_operation_if_complete` на `name == "add"` стоит `assert op.error_code is None`.

**Что проверил на предмет незаметных багов и не нашёл.** Разность множеств в первой правке безопасна при пустом `accepted` и при полном совпадении с `bound` — получается `missing == []`, нулевой эффект. `dict(operation.response_summary_json or {})` защищает от `None`. Во второй правке присваивание попадает в тот же коммит, что и `mark_operation_pending_confirmation`, состояние операции остаётся `pending_confirmation` до реального ответа WB. Новых сущностей, статусов, флагов, API и UI не заведено — правки лежат внутри существующих полей и веток.
