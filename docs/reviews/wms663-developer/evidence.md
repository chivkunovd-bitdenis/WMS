## Изменение

В существующей строке Ozon на «Упаковка и маркировка» появился раскрываемый блок
«ГТД / РНПТ». Он показывает реальные SKU/экземпляры, отдельные поля номера и
явные галки отсутствия; открытие не выставляет отсутствие. Ввод номера сохраняется
строкой. Ошибки Ozon остаются у экземпляра, пользователь может переходить между
заказами и вкладками. Компонент закреплён за supply/order и не переносит ответы
или черновики на соседний заказ; тихое чтение не затирает несохранённый ввод.

GET `/operations/fbs-orders/{order_id}/ozon-exemplar-documents` читает статус;
PUT сохраняет явный выбор с expected_version. Если Ozon ещё не вернул экземпляры,
отдельная явная кнопка вызывает POST `/prepare` и один create-or-get.
Создание экземпляров не запускается фоном при показе списка.

Намерение, версия и незавершённая операция сохраняются в существующем
`FbsOrder.meta_details_json.ozon_exemplar_documents`, без новой таблицы/реестра.
Все новые `/set` проходят через один механизм короткого захвата строки и
долговечного checkpoint до внешней записи. HTTP не держит этот замок. Действующая
операция сериализует писателей; просроченный preparer, ещё не записавший /set,
отсекается новой версией. Перед повторным явным действием при unknown сначала
читается status. Timeout/5xx не создают очередь повторных set. Старый
update_available с несовпавшими значениями не освобождает unknown-запись.

И документы, и последующий КИЗ используют полный create-or-get snapshot,
сохраняют прочие товары/экземпляры, номера/absent, допустимые типы маркировок,
weight и multi_box_qty. Локальные коды накладываются только на реальные
provider IDs; исторические IDs не создаются заново. Неполный состав ответа
не отправляется как полный. Tenant и marketplace проверяются до provider call.

Сохранён отдельный результат документов: accepted только после ship_available,
совпадения значений/флагов и отсутствия ошибок/неизвестных непустых document
check_status. update_available означает разрешение правки, update_not_available
не назван документным отказом. Ozon-периодический опрос находит незавершённую
операцию по JSON заказа, включая случай без FbsOrderMarking.

Старый последовательный скан КИЗ не блокируется только из-за validation_in_process
предыдущего **подтверждённого** marking set без документов: новый код создаёт новую
версию полного набора. Неопределённая запись/одновременно выполняемый writer
сначала разрешаются чтением статуса. При потерянном ответе marking set
пустой/старый status не подтверждает новый код.

Остатки, резервы, списание, непрерывный scan-print, WB и соседние действия UI
не изменены. Generated Ozon-схемы, замороженные тесты/ожидания, guards и бизнес-
постановка не менялись.

после `db_session.expire_all()`, до входа в resume: тест читает `order.tenant_id`
синхронно, вызывая MissingGreenlet. Разработчик не менял тест и не добавлял
expunge/особое поведение продукта для обхода этой строки. Отдельный
`check_recovery.py` с сохранёнными до expire идентификаторами подтверждает

Он также проверяет потерянный set + старый update_available: unknown остаётся,
следующий Save сначала читает status и не отправляет второй set.
Это дополнительное evidence, не замена результата замороженного теста.

Целевая регрессионная матрица (`pytest -n auto`: WMS-663, process contract,
Ozon lane, box assembly, OpenAPI models) дала **116 PASS / 1 FAIL / 1 SKIP**.
Единственный FAIL — тот же frozen-test MissingGreenlet. Последний прогон с
автоматическим количеством работников занял 127 секунд; `-n 4` ранее занял
11–30 секунд с тем же результатом. Это целевые проверки, не полный CI.

Гонка двух сессий выполнена настоящим замороженным тестом на отдельном локальном
PostgreSQL `127.0.0.1:56663/wms_test663`: **PASS**, один set, второй клиент получает
конфликт версии. Для всей PostgreSQL-матрицы сначала получено 10 PASS / 7 setup
ERROR из-за разных asyncio loops у кешированных asyncpg-соединений. Без изменения
тестов запуск с `-o asyncio_default_fixture_loop_scope=session
-o asyncio_default_test_loop_scope=session` дал **16 PASS / 1 FAIL** — остаётся
тот же MissingGreenlet на строке 364. Это настройка инфраструктуры, а не изменение
ожиданий. Тестовый PostgreSQL создан отдельно от существующих баз.

Замороженный DOM C16: **FAIL**, а дополнительный developer probe: **PASS**.
C16 ищет первую кнопку с textContent «Сохранить» по всему document. Раньше
нового блока в DOM стоит отключённая кнопка сохранения даты отгрузки
`cal-02-fbs-shipment-date-save` (FfFbsSupplyWorkspace.tsx); тест кликает её,
поэтому ожидаемого PUT нет. Соседнее действие не переименовывалось и тест не
подменялся. Developer probe воспроизводит эту неоднозначность и проверяет
контекстную кнопку экземпляра: точный payload/version 4, сохранённый ввод и
`gtd_invalid`, исправление с version 5. Замороженный C16 не объявляется зелёным.

Загрузка полного workspace в Vitest действительно долго идёт до исполнения:
collect 160–197 секунд в первых прогонах, 105 секунд в последнем. Это не вечный
deadlock: после collect выполняются тесты. Существующая assembly DOM-матрица
дала **18 PASS**. Узкий developer probe собирается за несколько секунд.
