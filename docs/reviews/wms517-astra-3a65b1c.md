## F3: ошибка остаётся у одной строки, здоровая сохраняется

В `backend/app/services/wb_sales_report.py` добавлен `_json_integer` и передан
как `parse_int` в разбор HTTP-страницы. Вызов `int(value)` сохраняет прежний
тип и значение обычных целых чисел. Только при `ValueError` возвращается
исходная числовая лексема — текст числа без преобразований. Синтаксис JSON
продолжает проверять стандартный декодер; произвольная невалидная строка
не становится корректным числом благодаря этому callback.

5000 цифр теперь проходят границу чтения страницы, сохраняются в основании
попытки и отклоняются существующим `sale_cost` по диапазону. Ошибка
`invalid_sale_price` записывается только плохому item. Глобальный предел
Python не выключается и не изменяется; перехода на float, округления,
подстановки цены или изменения лимитов стоимости нет.

Независимый запуск четырёх frozen-тестов подтвердил публичный HTTP 200
в комбинациях single/healthy-neighbor и exception-trace/http-status.
Плохая позиция имеет `failed`, `product_cost=None`, `invalid_sale_price`,
не имеет документа и сохраняет все исходные 5000 цифр в evidence. В обоих
mixed-сценариях здоровая позиция остаётся `pending` с ровно **1234 копейками**;
набор выбранных позиций не теряется. Документы и внешние отправки не создаются.

Контракт `backend/tests/test_wms517_raw_integer_price.py` побитово совпадает
с отдельным тестовым коммитом `eeaafc9f8bbb753e84fbd02a76ecf89eb0f93a72`:
Git blob в обоих случаях `87b0d1f17ec79daa48b234479bdbce76dd06aedb`.
После frozen-коммита тесты вообще не менялись. Его RED-доказательство
«4 failed, HTTP 409 вместо 200» прочитано в handoff тестировщика; здесь
повторно не воспроизводилось и не выдаётся за новый собственный запуск.
