## 1. Задача простыми словами

Владелец хочет уйти от хотфиксов и хаоса. Задачи утверждаются днём, делаются
ночью в авторежиме, утром — честный отчёт. Главное условие: то, что уже работает,
не должно ломаться. Сейчас ломается постоянно, и каждый раз чинится
перезапуском агента «в надежде, что починится».

Идея, которую владелец сформулировал сам и подтвердил:

1. Поведение ключевых процессов записывается конкретными примерами
   («было 10, подобрали 3 — на складе по-прежнему 10; провели — осталось 7;
   повтор проведения — всё ещё 7»).
2. Примеры превращаются в автоматические тесты.
3. Эти тесты агент не может изменить. Изменил — работа не проходит.
4. Код, который эти тесты не проходит, не попадает в релиз.
5. Набор растёт сам: чек-лист аналитика по каждой задаче становится тестами,
   и часть из них остаётся в защищённом наборе навсегда. Описывать все процессы
   заранее не нужно — владелец этого делать не будет.

## 3. Как будет работать процесс (целевая картина)

### Днём — владелец

1. Запрос приходит (Telegram, чат, голос). Аналитик по навыку
   wms-product-analyst пишет docs/requirements/WMS-NNN.md: требования R1…,
   проверки C1… (подготовка → действие → ожидаемый результат).
2. **Новое:** у каждой проверки аналитик ставит класс:
   - **навсегда** — поведение, которое должно жить дальше (уйдёт в защищённый набор);
   - **разово** — проверка именно этого изменения (миграция данных, разовая чистка);
   - **руками** — то, что автомат не докажет (бумага из принтера, звук сканера).
3. Владелец утверждает требования и проверки (в Telegram: «описание согласовано»).
   С этого момента проверки — контракт задачи.

### Ночью — конвейер

4. **Тестировщик** (отдельный агент, не разработчик) пишет тесты по проверкам
   «навсегда» и «разово» ДО кода. Каждый новый тест обязан упасть на текущем
   etalon (доказывает, что проверяет новое поведение). Тесты коммитятся
   отдельным коммитом; их хэши записываются в манифест задачи.
5. **Разработчик** пишет код, пока тесты не позеленеют. Тесты из шага 4 и весь
   защищённый набор он менять не может (см. раздел 4).
   Если он считает, что проверка неверна, — не трогает её, а пишет об этом
   в отчёт («C3 противоречит R2, нужно решение владельца»). Задача остаётся
   невыпущенной до решения.
6. Ревью и приёмка аналитиком — как сейчас, но приёмка опирается на
   результаты тестов, а не на слова исполнителя.
7. **Выпуск.** Кандидат собирается из etalon плюс готовые задачи. Прогоняются:
   защищённый набор + тесты задач пакета + полный CI. Задача, которая валит
   защищённый набор, из пакета исключается, остальные идут. Выкладка — только
   SHA из etalon с зелёными обязательными проверками.
8. После выпуска проверки «навсегда» переносятся в защищённый набор
   (в той же PR или отдельной, которую утверждает владелец — см. 4.3).

### Утром — отчёт

По каждой задаче одно из трёх:
- выпущено (SHA, какие проверки прошли);
- не выпущено — упала проверка Cn на шаге X: ожидалось A, получено B;
- ждёт решения владельца — агент считает, что проверка противоречит требованию.

Принцип: «не выпущено с понятной причиной» лучше, чем «выпущено и сломано».

### Срочный баг

Тот же путь, только вне очереди: маленький PR в etalon → защищённый набор и
проверки затронутого процесса обязаны быть зелёными → выкладка SHA из etalon.
Срочность сокращает посторонние проверки, но не проверку затронутого правила.
Выкладка мимо etalon (образ из ветки, правка на сервере) запрещена.

## 4. Как защищаемся (механика)

### 4.1. Защищённый набор

- Каталоги: backend/tests/guards/ и frontend/src/guards/ (или
  frontend/tests-guards/ — выбери по устройству vitest-конфига).
- Каждый тест в шапке содержит: процесс, номер задачи/инцидента, цитату решения
  владельца, дату. Пример:
  «WMS-632 · 02.10.2026 · владелец: остаток списывается только при проведении
  отгрузки (FBS — „Передать в WB“, FBO — „Провести“)».
- Текст падения — человеческий: «нарушено решение от 02.10: …».
- Манифест guards/MANIFEST.json: путь → sha256 каждого защищённого файла.

### 4.2. Проверка «охрана» в CI

Отдельная быстрая задача CI (цель — не больше 3–5 минут):
1. Сверяет все защищённые файлы с манифестом. Расхождение → красный с текстом
   «изменён защищённый тест X без утверждения владельца».
2. Прогоняет защищённый набор (бэк + фронт).
3. Запускается на pull_request в etalon И на push в etalon.

### 4.3. Почему агент не сможет это обойти

Без этого пункта всё остальное — декорация.

1. **Отдельный GitHub-аккаунт для агентов** (machine user, например
   wms-agent-bot) с правом write, без admin. Токен владельца из окружения
   агентов убрать (gh, Codex, Claude, бот WMS-641). Без этого агент может сам
   отключить защиту ветки — у него admin.
2. **Защита etalon (ruleset):** слияние только через PR; обязательные проверки
   «охрана», backend, frontend; запрет force-push и удаления ветки; обязательное
   одобрение CODEOWNERS.
3. **CODEOWNERS** — владелец (chivkunovd-bitdenis) для: .github/,
   backend/tests/guards/, frontend/…/guards/, guards/MANIFEST.json, scripts/ci/,
   scripts/deploy/, AGENTS.md, CLAUDE.md. Обычная PR, не трогающая эти пути,
   сливается без владельца. PR, трогающая их, ждёт его одобрения (с телефона).
   Это и закрывает лазейку «поменять CI-workflow в своей же PR, чтобы охрана
   всегда была зелёной» — изменение workflow требует владельца.
4. **Выкладка:** deploy.yml перед SSH проверяет через API GitHub, что у SHA
   все обязательные проверки зелёные. Нет — отказ.
5. **SSH на прод.** Пока у агентов root, они могут поставить что угодно мимо
   etalon. Предложение: агентам — отдельный ключ только на чтение
   (SELECT в БД, логи, git log), выкладка — только через deploy.yml.
   Это решение владельца, см. раздел 7.
6. **Хук Claude Code / правило Codex** на запрет правки защищённых путей —
   дополнительный, ранний барьер (не основной: основной — 1–3).

### 4.4. Тест должен доказать свою пользу

Защищённый тест принимается только с доказательством: на тестовых данных
вернули старую поломку → тест покраснел с понятным текстом. Сохранить это
доказательство (патч-поломка + вывод) рядом с тестом или в docs/evidence.
Тест, который не краснеет на своей поломке, в набор не попадает.

- G-STOCK-7. В потоке заказов/отмен нет журнала квоты (FbsStockPoolDebit,
  _debit_stock_pool, FbsShipmentReversalLedger как механизм возврата).
  Структурный тест по коду.
- G-STOCK-8. Публикуемый остаток FBS = min(лимит оператора, свободный остаток);
  продажи лимит не расходуют. Настройка WB не меняет Ozon и наоборот.
Известные расхождения кода с правилом владельца (WMS-632, Д2 и Д4: отмена
заказа после подбора не возвращает штуку; FBO списывает при укладке в короб) —
не прятать: тест пишется по правилу владельца, помечается ожидаемо падающим
со ссылкой на задачу исправления, и становится обязательным после исправления.
Как именно это оформить — твоё решение на ревью.

Шаг 7. **Защищённые проверки — скан и печать FBS.** Сначала аналитик собирает
таблицу «галочки (Печатать QR / Печатать ЧЗ / Перепечатывать ЧЗ / число копий)
× тип товара (маркируемый / нет) × место (обычная поставка / сборочное
задание) → что происходит при скане». Каждая строка — со ссылкой на решение
владельца (WMS-630, 631, 633, 642, 643 и др.) и с фактическим поведением кода.
Строки без решения или с расхождением — вопросом владельцу, НЕ закреплять
текущее поведение кода. После утверждения — тесты. Минимум:
- скан выбирает заказ нужного товара; чужой ШК не засчитывается (WMS-628);
- маркируемый товар: ждём КИЗ, печать до КИЗ не уходит;
- после КИЗ: привязка у этого заказа, ровно одно задание печати в WMS Print
  (тестовый приёмник), окно печати браузера не открывается;
- снятая галка — печати нет и WMS Print не требуется (WMS-643);
- скан в поле КИЗ строки попадает именно в этот заказ (WMS-630);
- синхронизация и частичный подбор не удаляют строки с записанными КИЗ (WMS-622);
- скан КИЗ не ждёт ответа WB (WMS-640/642);
- лента: нужное число непустых страниц в нужном порядке (WMS-613, PDF-тест);
- кнопки печати и создания отгрузки на месте и доступны (пропавшая кнопка —
  тоже регрессия; уровень DOM-теста или браузера на эмуляторе — твоё решение).
Уровень каждого теста (pytest / vitest DOM / браузер на эмуляторе) выбирать
по принципу: самый дешёвый уровень, на котором старая поломка воспроизводится.

- Правила тестов (коротко, в навыке тестировщика): проверять результат для
  пользователя и данных; не подменять проверяемую операцию заглушкой; для бага —
  показать падение на старой ошибке; не менять ожидание ради зелёного.

Шаг 11. **Встроить в ночной конвейер WMS-641** (этапы 6–7 твоей схемы):
тестировщик → разработчик → охрана + тесты задачи + CI → выпуск только зелёного
по каждой задаче отдельно → перенос «навсегда» в защищённый набор →
утренний отчёт в формате раздела 3.

Шаг 12. **Разбор существующих тестов** (параллельно, агенты Sol уже запущены
владельцем): по группам — какую поломку ловит, дублирует ли, проверяет ли
настоящий результат, сколько времени и почему. Решение по каждой группе:
оставить / ускорить / объединить / переписать / удалить с объяснением.
Полный прогон не урезать, пока не доказано, что сокращённый набор ловит то же.

## 6. Критерий «забетонировано»

Готово, когда на тестовом стенде показано:
1. Старые поломки остатков и печати из раздела 2 возвращены по одной — каждая
   останавливает PR красной «охраной» с понятным текстом.
2. Попытка изменить защищённый тест или CI-workflow в PR без владельца — не
   сливается.
3. Выкладка SHA с красными проверками — отказ deploy.yml.
4. Следующая обычная выкладка не теряет уже выложенный хотфикс (он в etalon).
5. Etalon зелёный, тесты фронта и PDF-тест реально исполняются.

Число зелёных тестов критерием не является.

## 7. Решения владельца (нужны до включения шага 9)

1. Завести GitHub-аккаунт для агентов и убрать токен владельца из их окружения.
2. Включить ruleset и CODEOWNERS на etalon (меняет правила репозитория для всех).
3. SSH на прод: оставить агентам root или дать ключ только на чтение.
4. Утвердить черновики G-STOCK-1…8 и таблицу скан-печати (шаг 7).
5. Как оформлять известные расхождения кода с правилом (Д2, Д4 WMS-632):
   ожидаемо падающий тест или сначала исправление.

## 8. Что прошу проверить на ревью особенно

- Не превращается ли охрана в источник «пустых ночей» (вечно красное).
  Если видишь риск — предложи, как разделять задачи пакета.
- Реально ли закрыта лазейка «агент правит workflow в своей PR» при
  pull_request-триггере. Если CODEOWNERS на .github/ недостаточно — предложи
  альтернативу (например, проверка манифеста из базовой ветки).
- Не дублирует ли манифест хэшей то, что уже даёт CODEOWNERS. Если одно из
  двух лишнее — убери (правило проекта: не вводить лишних сущностей).
- Не закрепляем ли где-то текущее поведение кода вместо решения владельца.
- Совместимость с уже идущей реализацией WMS-641.
