# WMS-058: запрет изменения подбора после передачи Ozon

Изолированная ветка `codex/wms-release-ozon-terminal` от
`a1b64752ffcc4eb8dfc5151c783407530cee931f`. Изменены только два сервиса,
целевой тест и документация. Фронт и API-контракт не менялись.

## Подтверждённый дефект

У Ozon подбор переносит единицу из выбранного короба в сортировку. После
`_finish_ozon_delivery` товар списан, но `FbsOrderProductPick` остаётся активным.
Старый API-запрос undo проходил без проверки передачи, переносил другую
оставшуюся в сортировке единицу в исходный короб и уменьшал `picked_quantity`
у уже переданного заказа.

На исходном коде тест
`test_late_undo_cannot_return_other_sorting_stock_to_old_box[in_delivery]`
получил HTTP 200 вместо ожидаемого 409; ответ показывал `picked_quantity=0`.
Регрессия использует реальные сервисы подбора и локальной финализации передачи,
HTTP endpoint отмены и отдельную PostgreSQL с синтетическими данными.
В окончательной фикстуре заказ содержит одну единицу; ещё одна единица заранее
находится в сортировке независимо от этого заказа.

## Исправление и граница блокировки

Изменяющие подбор вызовы берут блокировку строки поставки и перечитывают её
вместе с заказами после ожидания. Ozon запрещает новые изменения при
`delivered_at`, `in_delivery` или `done`. Успешный повтор уже выполненной отмены
остаётся чтением: HTTP 200 без повторного движения.

Первый checkpoint передачи сохраняет существующую операцию `pending` и
отпускает SQL-блокировки перед внешними HTTP-вызовами. Поэтому одной проверки
статуса поставки недостаточно. Существующие `pending`, `pending_confirmation`
и `confirmed` операции также закрывают изменение подбора; после `failed`
проверяется уже существующий снимок перевозки. Если создание перевозки началось,
номер/подтверждение перевозки получены либо сработала альтернативная передача,
нужно завершить проверку результата передачи. При явном отказе до перевозки,
когда снимок пуст либо содержит лишь собранные отправления, подбор снова доступен.
Новые журналы, флаги и сущности не добавлялись.

После внешних checkpoint финализация повторно берёт блокировки в порядке
«поставка → заказы», перечитывает актуальные данные и лишь затем завершает
локальное списание. Автоматическая запись грязных ORM-объектов выключена на
время получения первой блокировки, чтобы данные ответа Ozon не поменяли порядок
блокировок. Долгие HTTP-вызовы остаются вне этих SQL-блокировок.

Упаковка не участвует в проверке. Снятие подбора после `pack_status=packed`
и повторный подбор до передачи проходят. Читающие поверхности и навигация
не получили блокеров. Поздняя отмена заказа не открывает уже переданный подбор,
потому что `delivered_at` поставки остаётся фактом передачи.

## Проверка

Изолированная БД: `wms058_ozon_terminal_20260909` на PostgreSQL 17,
`127.0.0.1:5432`, создана специально для этой проверки; перед первым pytest
проверены текущая БД, пользователь, адрес сервера и отсутствие таблиц.
Боевые и staging БД не использовались; Ozon API не вызывался.
Первый запуск остановился на DiskFull до выполнения теста; после восстановления
локального PostgreSQL и освобождения места root-агентом регрессия выполнена заново.

Покрыты HTTP undo/manual/set после передачи, `in_delivery`, `done`, поздняя
отмена, повтор undo, упаковка до передачи, активная передача, неопределённый
результат и явный отказ до перевозки. Два PostgreSQL-теста используют отдельные
транзакции: undo ждёт строку поставки и затем видит свежий `delivered_at` даже
при уже загруженном старом ORM-объекте; финализация после checkpoint ждёт
`SELECT ... fbs_supplies ... FOR UPDATE`. Последний тест отдельно запускался
с исходным `fbs_shipment_service.py` и упал: исходная реализация ждала лишь
неявный `UPDATE fbs_supplies`, который не перечитывает данные после ожидания.
