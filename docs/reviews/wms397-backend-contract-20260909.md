## 2. Минимальное хранение: четыре записи, без параллельного склада

Новые логические данные неизбежны: существующее уведомление описывает доставку
одному получателю, а не общий разговор двух сторон. Хранение разговора в его
`payload_json` дублировало бы текст для каждого получателя и потеряло единые
ответы, правки, доступ и прочитанность. Предлагаемая конкретная схема:

| Новая запись | Минимальные поля/ограничения | Почему не помещается в существующий объект |
| --- | --- | --- |
| `ChatConversation` | UUID, tenant, kind, seller/warehouse, типизированная ссылка на существующий документ, created_at. Unique: tenant+seller для общего канала; tenant+kind+document+seller для документа; tenant+warehouse для внутреннего. | Нужен один устойчивый адрес разговора; никакой существующий складской документ не представляет общий или внутренний канал. |
| `ChatMessage` | UUID, conversation, author, created/updated/deleted_at, неизменяемая visibility, kind, text, client_message_id, reply_to/thread_root, document_ref и версия документа при вставке. JSON-поля для mentions, reactions, read_by, followup, прошлых редакций. Unique(author, client_message_id). | Общий текст, авторство, ссылки ответов и повтор отправки не являются уведомлением или операцией склада. |
| `ChatParticipant` | Unique(conversation,user); участие, кто/когда добавил/удалил, pin/mute/archive для этого пользователя, история изменений членства в этой же записи. | Реальные участники показаны в drawer; доступ и персональные настройки нельзя хранить одним общим флагом канала. User не представляет участие в конкретном разговоре. |
| `ChatAttachment` | UUID, tenant, uploader, conversation, nullable message_id, внутренний storage_key, безопасное имя, mime/size/hash, размеры изображения, результат проверки, created_at. | Файл существует до отправки сообщения; нужны отдельное получение статуса/повтор загрузки, проверка владельца и запрет присоединить чужой файл. |

Глобальные настройки уведомлений можно хранить одним JSON-полем существующего
User, без пятой таблицы preferences. Для первого среза не нужны отдельные
сущности треда, реакции, прочитанности, очереди сообщений, события транспорта
или счётчика непрочитанного. Тред — ссылка на корневое сообщение; reactions и
read_by — множества в сообщении; обновление под блокировкой той же строки.
Непрочитанное, число ответов, последнее видимое сообщение и открытые followup
считаются из доступных сообщений. JSON редакций хранит фактические прежние
редакции по требованию аудита, а не второй источник текущего текста.

Чтение передаёт конкретные `message_ids`, а не «прочитано всё до времени»:
якорь может открыть середину истории, оставив непрочитанное выше. Нельзя
обнулить весь канал или прочесть внутренние сообщения за селлера, как делает
упрощённый reducer макета. `read_by` в ответе отфильтрован по допустимым для
адресата участникам. История правок доступна только FF-admin, не включается
в обычный Message DTO, поиск или уведомление. Удаление оставляет тумбу и
ответы; исходное содержимое доступно только разрешённому аудиту.

## 3. Одно правило области доступа для всех методов

Базовая проверка: текущий user/tenant → разрешённый канал → видимое сообщение
→ разрешённый связанный объект. Её используют также поиск, счётчики,
превью инбокса, уведомления, вложения и будущие realtime-события. Фильтрация
после получения данных на фронте не является защитой.

Предложение для согласования: FF-admin видит каналы своего tenant; FF-staff
получает канал только по явному участию, назначенному администратором, и не
обретает через него прав на документы. Селлер получает только shared-сообщения
каналов текущего effective_seller, где он участник; членство не позволяет
перейти к другому seller/tenant. Внутренний складской канал — только явно
назначенные FF-участники. Это узкая политика участия из макета, а не новая
система складских ACL. Автоматически приглашать всех операторов tenant нельзя.

Документный канал дополнительно требует существующего права раздела и
проверки его документа. Право пользователя селлера `documents` и делегированный
магазин проверяются сервером. Текущий FBS workspace API предназначен только
FF; передавать его полный ответ селлеру ради карточки в чате запрещено.
Если документ недоступен, возвращается безопасная карточка «Нет доступа» без
полей/строк; ссылка не расширяет права существующего экрана документа.

Для общей приёмки с товарами нескольких селлеров документный канал разделён
по seller в уникальном ключе; проекция документа содержит только разрешённые
этому seller строки. Иначе один разговор мог бы раскрыть сведения соседнего
селлера. `ensure` не является обходом приглашения: FF-staff открывает только
назначенный канал; FF-admin создаёт/назначает, а селлер может начать свой
общий разговор с собственным участием. Участие другого человека добавляет
только FF-admin, существующие права на документ при этом не меняются.

reply_to и thread_root должны принадлежать тому же каналу. Ответ в треде
наследует visibility корня; менять её при редактировании нельзя. При общей
shared-реплике нельзя цитировать внутренний корень. Автор и упоминаемые
пользователи берутся из разрешённых участников; `@channel` — только FF-admin,
`@seller` во внутреннем сообщении не создаёт доставку селлеру.

Канал общего селлера — один на tenant+seller согласно §3.1 требований и
нынешней форме Conversation. Формулировка вступления «на пару селлер↔склад»
не превращается в несколько общих каналов молча. Документный канал можно
материализовать при первом открытии/сообщении атомарным ensure по unique:
логически чат есть у документа с создания, но пустые строки не заполняют
инбокс. Это соответствует тексту `ConversationScreen.tsx:55–56`; новый
массовый backfill каналов для всех исторических документов не нужен.

Номера/строки/план/факт/доступ читаются из этих объектов. Статусы адаптируются
явным отображением фактических значений к нынешним StatusChip, а не записываются
назад в склад. Таймлайн показывает только существующие подтверждённые события;
неполная история не дополняется seed-событиями. `outdated` определяется сравнением
показанной при вставке версии с текущими разрешёнными полями; если у источника
нет единого updated_at, допустим вычисляемый отпечаток этой проекции.

## 6. Файлы, доставка и границы первого подключения

Минимальный безопасный файловый путь: существующее приватное хранилище,
ключ `chat/<tenant>/<attachment-id>`, server-side проверка содержимого,
ограничение размера до чтения всего тела, EXIF-очистка изображений, проверка
до присоединения к опубликованному сообщению. Типы берутся из §6 требований:
PNG/JPEG/WebP, PDF/XLSX/CSV/DOCX, без видео и голосовых. Предложенные в макете
25 МБ/файл, 100 МБ/сообщение и 10 файлов надо принять явно в решении ниже.

Сервис антивируса в прочитанном коде отсутствует. Если он или устойчивое
хранилище не доступны, API не должен возвращать uploadStatus=done и публиковать
непроверенный файл. Первый программный срез может честно ограничиться текстом
и документными ссылками; файловые кнопки не выдаются за работающие. Для полного
файлового среза нужны проверка и уже доступное хранилище, а не незаметная покупка
сервиса или настройка ключей. Удаление неотправленного upload выполняется по
его сроку хранения; удаление сообщения не обходится публичной ссылкой на файл.

В требованиях §6.3 написаны отдельные бакеты/подписанные URL, но handoff §9
оставляет выбор бакета открытым. Предлагаемый первый вариант — существующий
приватный backend с tenant-prefix и авторизованным proxy-download. Он позволяет
перепроверять отозванный доступ на каждой выдаче и не требует нового бакета.
Это конкретное упрощение для согласования, не заявление, что нынешний storage
уже выдаёт подписанные URL или проходит антивирусную проверку.

Для уведомлений создаётся одна существующая Notification на user-получателя
в транзакции сообщения, с type chat.*, ссылкой на канал/якорь и разрешённым
preview. Повтор отправки Message не создаёт уведомления повторно. **Фильтр
доступа обязателен также в старых list/count/read/read-all уведомлений**:
обычный NotificationBell сейчас видит все user-строки даже при смене активного
магазина; отдельный новый chat-эндпоинт сам по себе эту утечку не закрывает.
Распознавать chat-строки следует по выделенному type, а все их ссылки проверять
через один chat-scope. Смена роли/удаление участника/soft-delete сообщения не
должны оставлять недоступный preview в общем колокольчике.

В первой интеграции использовать предусмотренный handoff fallback-опрос
через 3–5 секунд: обновлять видимые страницы канала, инбокс и уведомления,
останавливать опрос скрытой вкладки. Не нужен новый сервер realtime или
таблица событий доставки. WS можно позже подключить как сигнал перечитать
данные; потерянный сигнал не является потерянным сообщением, БД — источник.
Настоящий offline retry сохраняет client_message_id и драфт отдельно для
tenant/user/seller/channel; demo-флаг offline не является очередью доставки.

Push-подписки, digest-расписание и «последний онлайн» не реализованы текущими
сервисами чата. Ни браузерное разрешение, ни поле prefs не означают отправку.
Они остаются явно неподключёнными частями имеющегося макета. Назначать новый
постоянный presence-счётчик, почтовый провайдер и push-ключи этому срезу не нужно.

## 7. Различия требований и фактического макета не маскируются backend

В §3/§5 требований есть закрытие треда, аудит участников и last-online.
Нынешний ThreadPanel содержит ответы и закрытие панели,
а ParticipantsDrawer — демо-приглашение; готовых обработчиков всех перечисленных
действий нет. Их нельзя объявить подключёнными через один API или самовольно
дорисовать. Аналогично sender-status sending/failed — клиентский транспорт,
не новый бизнес-статус склада. Формулировка о полном продукте не отменяет этих
конкретных границ первого подключения.

## Одно минимальное решение владельца

**Предлагается разрешить следующий backend-срез:** четыре описанные записи
ChatConversation/Message/Participant/Attachment, персональные prefs в User,
доступ FF-оператора через назначение администратором в рамках существующих
прав документов; сначала текст, ссылки, ответы/реакции/прочтение и уведомления
в портале с fallback-опросом. Файлы подключать через существующий приватный
storage и авторизованную выдачу только после проверки содержимого, с лимитами
макета 25/100 МБ и 10 файлов. Push/digest, observer, недостающие действия UI
и отдельный realtime-сервис этим решением не включать.

Это один конкретный вариант вместо абстрактного «можно ли делать чат».
Доказано, почему новые данные разговора нужны и почему отдельные новые
журналы/счётчики/очереди не нужны. Сейчас таблицы не создавались. После принятия
этого среза остаются обязательными API-проверки изоляции, повторов/гонок и живой
обмен между двумя реальными порталами; ни текущий документ, ни прежняя
демонстрация seed-макета не являются готовностью чата.
