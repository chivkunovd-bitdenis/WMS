## Что изменено и почему

Основной чат создаётся при чтении списка для каждого доступного селлера. Повторные
и конкурентные открытия сходятся на существующем уникальном индексе. Дополнительный
чат требует явного участия даже для администратора; создатель включается автоматически.
Список участников использует существующие FF- и seller-аккаунты своей организации и
своего селлера. Есть создание группы, выбор участников и добавление после создания.

Текст, правки и файлы хранятся сервером. Повтор сообщения использует тот же client ID.
Конфликт из другого чата возвращает 409. Вставка и привязка файлов находятся в одной
вложенной транзакции; строки вложений блокируются в постоянном порядке. Конкурирующая
привязка одного файла не оставляет второе сообщение без вложения. Устранён полный
rollback чужой работы сессии при конфликте основного чата/участника/сообщения.
История возвращает последние сообщения и курсор предыдущих; время новых сообщений
записывается с микросекундами, чтобы последовательные отправки не перемешивались в SQLite.

Сервер проверяет существование, tenant, seller и текущие документные права для
`fbs_order`, `fbs_supply`, `inbound_intake`, `marketplace_unload`, `outbound_shipment`.
Клиентский заголовок не считается источником данных. Смешанные документы показывают
только строки выбранного селлера. При последующем запрете документа его карточка
скрывается из прочитанной заново ленты. Прикрепляется ID конкретного заказа, а не
подменяющая его поставка. Карточки открывают страницу текущего документа с составом;
для FF оттуда доступны существующие рабочие экраны. В составе FBS-поставки можно
открыть её конкретный заказ.

Форма сообщения — компактный MUI Popover рядом с действием документа. Полная лента
остаётся в отдельном чате, доступном также из верхней панели FF и seller. Точки входа:
строки FBS-заказов, существующая FBS-поставка, FF/seller-приёмка, FF/seller-отгрузка
на МП, обычная отгрузка. Смешанный документ предлагает разрешённый контекст селлера.
Исправлены найденные вручную переходы: всплывающая форма больше не активирует строку
FBS-таблицы; обычная отгрузка открывается через действующий маршрут; FF-модальное окно
документа закрывается при переходе в полный чат.

Редактор принимает обычные файлы и изображения из буфера, показывает превью. При
сбое сохраняет текст и Files, повторно использует уже загруженные вложения. При
неопределённом ответе повторяет неизменённое сообщение с тем же ID. Файлы скачиваются
по запросу через авторизованный API, картинки показываются в ленте. Удалённый участник
не может скачать даже собственное вложение. MIME изображения проверяется по сигнатуре
и разбору существующим PyMuPDF; SVG остаётся обычным файлом. Заголовки download запрещают
sniffing/кэширование и задают sandbox. Клиент создаёт blob обычного файла с
`application/octet-stream`, чтобы HTML/SVG не исполнялись с origin приложения.
Ограничения сохранённого контракта: 25 MiB на файл, 100 MiB и 10 файлов на сообщение.

Использованы четыре уже существующие в исходном HEAD chat-таблицы и его миграция
`20260910_0300`; новых доменных сущностей, журналов, счётчиков и изменений stock не добавлено.
Упаковка, cap, FBS-навигация и складские операции этим срезом не меняются.

## Границы и обязательные проверки ревью/стенда

Mac первоначально был locked, затем доступ появился и позволил пройти описанные
выше сценарии. В конце ручного прохода снова получен точный ответ CUA:
«The Mac is locked and automatic unlock could not unlock it». Поэтому не заявляется
полная ручная перепроверка последнего diff. После этого ещё упрощён сброс состояния
chat-компонентов при смене документа/сессии для устранения ESLint errors; это покрыто
типами/сборкой, но требует повторного клика на финальном SHA.

Не проверено руками: последняя seller marketplace-unload точка входа; чтение
сообщения дополнительной группы селлером (сама группа видна); полный круг кликов
всех пяти карточек на финальном SHA; физический Ctrl+V на Windows. Cmd+V на Mac
проверен, обе платформы используют один onPaste. Adversarial ACL и смешанный документ
проверены API-тестами, отдельный ручной проход под третьей/чужой учёткой ещё нужен.

Для приёмки координатору/независимому ревьюеру нужно перечитать итоговый diff,
повторить последние перечисленные клики, проверить разрешённый tenant-контур на
интеграционном SHA после сборки. Проверить применимость миграции рядом с ветками
остальных исполнителей и реальную устойчивость attachment storage после рестарта
стенда. S3/object storage на удалённом окружении не проверялся. Автоматическая уборка
неотправленных upload-объектов не добавлялась; отправленные файлы проверены на локальном
хранилище. Непосланный черновик живёт в открытом редакторе, его сохранение между
закрытием вкладок/перезагрузками не заявляется.

CI, независимое ревью, merge, deploy и production proof в этот результат не входят.
Канонический статус обновляет только координатор: реализация и локальные проверки
есть; продуктовая приёмка/публикация на стенд ещё не подтверждены.
