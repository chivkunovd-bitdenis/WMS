## Подтверждённые причины и исправления

**P2 №3, namespace.** Страница /app/ff/fbs-stock создавала WB-строку с ключом123,
а правило могло содержать wb:123 и ozon:123. Теперь строка использует существующий
warehouseRuleKey. Значения процентов и штук квалифицируются существующим
qualifyWarehouseRuleValues по активным сохранённым привязкам ОБЕИХ площадок,
полученным из существующего warehouse-bindings API. Не выбирается случайная первая
строка; неоднозначный legacy numeric key даёт явный отказ. Сохранённый ozon:123
сохраняется при редактировании wb:123. В ручке сопоставления склада из namespace
извлекается числовая часть существующим warehouseNumberFromRuleKey.

**P2 №4, неверное обещание количества.** В API view есть суммарные on_hand/free,
но нет полной разбивки входов расчёта черновика по физическим складам. Нового API,
счётчика или второй складской арифметики не добавлено. toProduct переносит имеющийся
server published_now как необязательное поле savedPublishedNow. Общий диалог
показывает его с подписью «Расчёт публикации по сохранённому правилу при последней
загрузке» и явно сообщает, что изменения окна ещё не учтены. При отсутствии
серверного числа сообщает недоступность расчёта, не выдумывает0.

Ложные расчёты по общей сумме удалены из итогового числа, строк направлений, подписей
процентных ползунков и нераспределённого количества. Сам ввод процентов сохраняется
на существующем MUI Slider; суммы/проверки ввода не расширялись. Серверная формула
min(cap,free) и её распределение по физическим складам не менялись. Основной каталог
использует тот же toProduct и общий диалог: его файл менять не потребовалось.
Результат в диалоге — расчёт по сохранённому правилу, НЕ подтверждение отправки в MP
и НЕ прогноз ещё не сохранённого черновика.
