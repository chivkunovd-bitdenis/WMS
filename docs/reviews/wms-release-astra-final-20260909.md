## 1. P1 — отмена подбора Ozon после подтверждённой передачи может переместить другой товар

Основное место: `backend/app/services/fbs_picking_service.py:1269–1278`, дальнейшее движение — `1342–1364`. В production-версии перед веткой Ozon стоял запрет undo для упакованного заказа. Кандидат правильно убрал зависимость от упаковки, но не защитил физическую отмену подбора после уже состоявшейся передачи.

Путь доступен оператору через `POST /operations/fbs-supplies/{supply_id}/pick/{order_id}/undo` (`backend/app/api/fbs_supplies.py:1482–1502`). `_load_supply` проверяет tenant и ID поставки, но не её передачу и не берёт блокировку (`fbs_picking_service.py:1501–1522`). Выбор активного подбора проверяет `undone_at IS NULL`, но не наличие последующего списания (`1302–1316`).

Конкретный сценарий: единица Ozon подобрана из короба в сортировку, заказ упакован и передан. Передача вызывает `write_off_order` через `fbs_shipment_service.py:1263–1273`. Функция списывает сохранённый состав источников и заполняет существующий ledger, но не закрывает записи `FbsOrderProductPick` (`fbs_ozon_packaging_service.py:349–413`). После этого поздний undo из оставшейся открытой страницы или того же разрешённого API снова находит подбор и перемещает единицу **из сортировки в старый короб**. Если в сортировке есть другая единица этого SKU, проверка физического остатка проходит, хотя отправленная единица уже списана. Одновременно у переданного заказа уменьшается `picked_quantity` и устанавливается `pick_status=pending`. При пустой сортировке движение может быть отклонено, но это не защищает сценарий с оставшимся товаром.

Минимальное исправление: согласовать новое физическое изменение подбора с существующей операцией передачи и проверять её подтверждённый результат до движения. Проверки `delivered_at` без сериализации недостаточно. Начальная блокировка поставки в Ozon отпускается при checkpoint до HTTP (`fbs_shipment_service.py:2021–2024, 2070`, commit в `1813`); сам HTTP защищён отдельной существующей блокировкой `ozon-delivery`, которой undo не пользуется (`1895–1900`). Ozon-финализация `1691–1704` также не получает заново блокировку parent. Исправление должно защищать физический источник и в этом окне, используя существующую операцию/блокировку передачи, а не ограничиваться одним поздним чтением статуса. Повтор уже исполненного undo может возвращать сохранённый результат без новых движений. **Упаковка по-прежнему не запрещает undo; навигацию и состояние вкладок не блокировать.** Новая сущность не нужна.

## 2. P1 — выключение публикации Ozon сохраняется до подтверждения последнего нуля

Основное место: `backend/app/api/fbs_sellers.py:318–342`; преждевременный commit — `backend/app/services/fbs_warehouse_binding_service.py:579–583`.

Новый контракт `PUT /operations/fbs-sellers/{seller_id}/warehouses/{wb_warehouse_id}` принимает `marketplace=ozon, stock_sync_enabled=false`. Обработчик запоминает переход из ON (`302–314`), вызывает `configure_seller_warehouse`, а тот сохраняет OFF и делает commit. Только после этого обработчик вызывает `clear_marketplace_stock`. При отказе или неполном подтверждении Ozon `_clear_previous_ozon_stock` выбрасывает `ozon_stock_cleanup_failed` (`fbs_warehouse_binding_service.py:347–365`). Ошибка находится за пределами имеющегося `try/except` обработчика. Состояние OFF уже сохранено; текст исключения «Настройки не изменены» в этом пути также неверен.

Следующий такой же запрос прочитает OFF, поэтому `publication_was_on=false` и повторной отправки нуля не будет. Штатный `sync_ozon_stocks` выбирает только ON-привязки (`ozon_fbs_sync_service.py:324–335`). Получается достижимое устойчивое состояние: WMS больше не публикует, а маркетплейс хранит прежний положительный остаток. Настройки могут говорить «выключено», хотя товар продолжает предлагаться покупателю. Эта новая API-ветка проверена чтением; наличие конкретного UI-вызова этого поля не заявляется.

Есть второй вход в тот же дефект последнего нуля. Существующий `_upsert_binding` обнуляет Ozon только при `existing.served` (`fbs_warehouse_binding_service.py:422–427`). Кандидат намеренно разрешил штатную публикацию при `served=false` (`ozon_fbs_sync_service.py:333–335`). Поэтому у действующей ON-привязки с `served=false` выключение через `/warehouse-bindings` вообще пропускает обнуление; сбой сети здесь не требуется. Разделение «обслуживание» и «публикация» проведено в отправке положительных остатков, но не в этом условии очистки.

Минимальное исправление: применять один существующий путь «подтвердить ноль старому собственному адресу → сохранить OFF» с последовательной защитой изменения привязки; при ошибке сохранять прежнее ON и отдавать штатную бизнес-ошибку. Убрать `served` из условия очистки, поскольку оно больше не определяет публикацию. Не добавлять журнал или новый статус. Отдельное выключение только `served` по-прежнему не должно отправлять ноль.

## 3. P1 — конкурентная проверка оплат теряет оплаченный месяц

Основное место: `backend/app/services/subscription_payment_service.py:173–208`, особенно продление на основе загруженного объекта `tenant` в `190–195`. Само арифметическое продление — `148–153`.

Кнопки проверки и возврат со страницы оплаты вызывают `POST /subscription/sync`. API заранее загружает tenant без блокировки (`backend/app/api/subscription.py:44–48, 120–122`). Сервис читает список pending-платежей, ждёт ЮKassa, затем меняет эти же объекты и прежнее значение оплаченной даты. Перед commit нет повторного чтения состояний или сериализации по tenant.

Достаточный сценарий потери денег:

1. Запрос A читает оплаченную дату D и единственный pending-платёж P1, затем ждёт HTTP.
2. Создаётся второй платёж P2. Запрос B читает всё ещё D и оба pending-платежа P1/P2.
3. B получает подтверждение обоих и фиксирует D+60; оба платежа становятся `succeeded`.
4. Поздний A получает подтверждение P1 и записывает свою вычисленную дату D+30 поверх D+60.

Оба платежа в БД уже `succeeded`, поэтому следующие проверки не возвращают потерянные 30 дней. Уникальный provider ID защищает от двух строк одного платежа, но не от перезаписи даты. Имеющийся тест `test_one_payment_extends_only_once` выполняет два последовательных запроса (`backend/tests/test_subscription_payment.py:173–193`), поэтому этот сценарий им не проверяется.

Минимальное исправление: получить внешние результаты без удержания блокировки БД на время HTTP, затем в короткой транзакции заблокировать и перечитать tenant, перечитать статусы соответствующих платежей и продлить дату только за ещё не засчитанные подтверждённые оплаты. Изменения статусов и даты фиксировать атомарно. Нужны свежие значения, в том числе при уже загруженных ORM-объектах; одной блокировки без их обновления недостаточно. Существующих таблиц достаточно.

## 4. P2 — одноразовая ссылка допускает два конкурентных изменения пароля

Основное место: `backend/app/services/auth_service.py:315–323`.

Новый `POST /auth/set-password` использует отпечаток прежнего хеша пароля как признак неиспользованной ссылки. Сервис загружает пользователя обычным `session.get`, сравнивает отпечаток, записывает новый хеш и делает commit. Два запроса, в том числе в разных процессах API, могут прочитать один старый хеш до первой фиксации и оба пройти проверку. Они сохранят разные пароли, второй перезапишет первый, а оба запроса выпустят access token (`325–330`). Это нарушение обещанной однократности, а не возможность пройти без подписанной ссылки.

Имеющийся `test_invite_link_works_once` ждёт полного окончания первой установки до второй (`backend/tests/test_auth_email_links.py:90–112`); он доказывает последовательный повтор, но не атомарное расходование ссылки.

Минимальное исправление: выбирать и актуализировать пользователя под `FOR UPDATE`, затем проверять отпечаток и менять пароль в этой же транзакции. Новая таблица использованных токенов не требуется. Сама схема отпечатка позволяет оставить решение простым.

## 5. P2 — новая ссылка установки пароля перехватывается существующей сессией

Основные места: `frontend/src/App.tsx:2803–2817`, `frontend/src/apps/seller/SellerApp.tsx:270–304`.

`useAuth` восстанавливает сохранённый токен (`frontend/src/hooks/useAuth.ts:51`). Обе оболочки показывают `PublicAuthScreen` только при отсутствии своего токена, а разбор `/set-password?token=…` находится исключительно внутри этого экрана (`PublicAuthScreen.tsx:30–39, 53`). Поэтому человек с действующей сессией, открывший письмо, не попадает в форму установки пароля. Отдельного маршрута установки пароля в авторизованной части нет.

Дополнительный явный сценарий: у браузера есть только FF-сессия, человек открывает приглашение `/seller/set-password`. `SellerApp.tsx:272–291` сначала показывает «Нет доступа», поскольку путь не `/`; до разбора токена письма выполнение не доходит. Кнопка перехода ко входу ведёт на корень портала, а не к установке пароля по ссылке.

Минимальное исправление: дать распознанному пути установки пароля приоритет перед обычной проверкой сохранённой сессии и перед этим сообщением другого портала. Использовать уже существующую форму, без изменения дизайна или управления чужими сессиями. Это подтверждённая развилка исходников; ручное воспроизведение экрана в рамках данного ревью не выполнялось.

Ничего из этих скриптов данным ревью не применялось. Работоспособность миграции на конкретной production-БД этим чтением не заявляется.

## Продуктовые границы отдельно от дефектов кода

Сведения о полном CI и ручной staging-приёмке получены из зафиксированной постановки `tmp/release-opus-prompt.txt` и переданных root результатов, а не из нового запуска этого агента: CI `34283438910` SUCCESS, 2154 passed; web deploy `0843e44c` SUCCESS. В них есть реальные synthetic-WB проверки create/retry, упаковки без движения, передачи из точного источника и повторной передачи без дополнительного списания. Это полезное свидетельство конкретных сценариев, но оно не закрывает перечисленные конкуренции и Ozon.

WMS-396 честно различает недоступную проверку и положительный результат: `interpret_check` требует одновременно `INTRODUCED`, `checkResult=true` и `verified=true` (`inbound_marking_service.py:400–434`). Сообщённые HTTP 451 из stage и production не превращаются в «введён в оборот». Сама приёмка и сохранение raw GS/экспорт были проверены root на synthetic-документе. **Положительная живая проверка ЧЗ остаётся непроверенной и фактически недоступной в использованном контуре**; feature целиком принятой на этом основании считать нельзя. Дополнительный код True API не входит в этот SHA. Из прочитанной реализации недоступность ЧЗ не выводит новый запрет на упаковку или существующую WB-навигацию.

Аналогично, наличие КИЗ в эмуляторе WB и успешная привязка не доказывают принятие метаданных WB: root сообщил несовпадение ответа эмулятора и ожидаемого `metaDetails`. Ослаблять условия принятия реального WB ради этого эмулятора оснований нет. Живой Ozon с многопозиционным составом, внешним нулём и передачей не принимался: безопасного synthetic-контура stage не было. Реальные операции клиента вместо такого контура не выполнялись. Почтовая доставка и весь seller invite/reset в текущем выпуске также не получили полной ручной приёмки.

Исторические денежные/складские коррекции WMS-047/048/013, перенос WMS-084 и расписание WMS-277 не являются предлагаемым условием выпуска несвязанных исправлений. Канонический бэклог и код этим ревью не менялись. Последующие исправления должны проверяться отдельным diff от этого замороженного кандидата; перечисленные здесь дефекты нельзя молча считать закрытыми только потому, что другой исполнитель уже начал их править.
