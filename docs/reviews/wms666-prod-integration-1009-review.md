## Результат проверки продуктового кода

Общая панель использует действия и выбор каждой отдельной поставки. Очередь фиксирует идентификаторы выбранных заказов, получает текущий обработчик нужной поставки и продолжает следующую поставку только после успешного завершения диалога. Отмена и смена контекста останавливают продолжение. Перед открытием следующего диалога проверяется сохранность состава заказов. Регистрация действий через стабильный callback и мемоизированные данные не создаёт обнаружимого цикла обновления родителя и дочерних карточек.

Ручная печать QR/ЧЗ сохраняет существующее построение ленты и макетов. После отправки ленты неудачное подтверждение QR оставляет список неподтверждённых ресурсов и их исходные ключи идемпотентности; кнопка повтора отправляет только эти подтверждения, не строит и не отправляет ту же ленту повторно. Успешное завершение всех подтверждений разрешает продолжение очереди. Частичный результат с ошибками не объявляется полным успехом.

Обычная и групповая упаковка используют свежий снимок поставки для автоматической подготовки. Исторический статус исключает автоматическое создание задания и получение новых стикеров. Ошибка получения стикеров имеет явный повтор в том же контексте поставки. Ручная выдача ЧЗ больше не зависит от наличия задания упаковки: доступность передаётся для товара, а выделение кода из пула и привязка к заказу выполняются в одном savepoint. Сохраняются фильтры tenant/seller/product, блокировка выбираемых кодов и существующая защита привязки. Число копий не превращается в выдачу нескольких разных кодов.

Историческая печать WB в `in_delivery` / `done` использует только уже привязанный код даже при наличии строки задания; отсутствие такого кода не расходует новый код из пула. Явная перепечатка операторского КИЗ остаётся отдельным действием. Изменённая ветка не вводит списание остатков или новый обязательный этап упаковки.

Проверено сохранение отдельных контекстов WB/Ozon, кнопок проверки WB и действий над выбранными строками. Ветка распределения КИЗ по позициям Ozon, последовательный сканер и его маршруты не заменены кодом из старого staging. Изменения общей панели используют существующие обработчики снятия/возврата/переноса и упаковки. В diff сохранены production-реализация подбора WMS-709, построение листа и этикеток WMS-702, а также helper получения стикеров из hotfix a19. Самостоятельный расширенный стек проверки устаревших привязок из старого staging в эту узкую интеграцию не переносился и не считается проверенным этим заключением.

## Адресная повторная проверка отката

Первоначально найден P2: после частичного `compose up` либо временной ошибки HTTP-проверки уже восстановленные образы отвергались повторным запуском как последующий чужой релиз. Из-за этого начатый откат нельзя было завершить штатным повтором.

Исправление закрывает это замечание. `prepare` сохраняет прежние образы; `arm` после сборки и до замены контейнеров фиксирует точные новые image IDs; `seal` сверяет контейнеры с ними. Откат допустим из `armed` и `deployed`, поэтому прерывание выкладки до `seal` также покрыто. До изменения любых тегов проверяются все четыре сервиса: разрешены только записанный старый или записанный новый образ, третий образ приводит к отказу. Уже восстановленный сервис не мешает повтору после частичной ошибки. Проверка учитывает остановленные контейнеры.

Скрипт возвращает только образы API, worker, beat и web с `--no-deps --no-build`. Команд восстановления БД, Redis, томов или запуска миграций нет. Названия тегов соответствуют текущему production Compose. После восстановления сверяются image IDs, отпечаток прежней страницы и HTTP health. Запись о завершённом откате создаётся только после этих проверок.

Прочитан сохранённый журнал `docs/evidence/WMS-666/prod-integration-1009/rollback-recovery-test.txt`: интегратор сообщает PASS для обычного и повторного отката, частичной выкладки до seal, повтора после частичного compose failure, повтора после временного health failure и отказа при чужом последнем образе без изменения тегов. Ревьюер эти проверки повторно не запускал; собственный вывод основан на чтении исправленного скрипта.

Сборщик проверяет checkout против `GITHUB_SHA`, успешность обязательных case IDs и записывает run ID/attempt в итоговый артефакт. Отсутствующий или неуспешный обязательный результат не превращается в PASS.
