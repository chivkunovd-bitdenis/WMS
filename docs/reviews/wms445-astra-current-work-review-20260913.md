## Замечания для Terra

### F1 — P1: область селлера не удерживается в двух списках

В изолированной базе подготовлены сотрудник `fulfillment_staff` с правом
`can_packaging=true` и `seller_id=A`, два селлера A/B его организации, по заказу
и активной поставке каждого. Использованы настоящие зависимости авторизации
и HTTP-маршруты приложения, без подмены `get_effective_seller_id`.

Обычный `GET /operations/fbs-orders/worklist?status_group=tsd_working&marketplace=wb`
правильно возвращает только A. Однако тот же запрос с `seller_id=B` возвращает
заказ B с HTTP 200. В `backend/app/api/fbs_orders.py:546` явный параметр заменяет
действующую область селлера; последующая проверка ограничивает только организацию.

Одновременно `GET /operations/fbs-supplies/worklist?status_group=active&marketplace=wb`
без параметра селлера возвращает активную поставку B. Android делает именно этот
запрос в `FbsViewModel.kt:190`. Маршрут `backend/app/api/fbs_supplies.py:1230`
вообще не получает `get_effective_seller_id` и передаёт `seller_id=None` сервису.
Таким образом лента заказов и «В работе» показывают разную область данных.

Оба серверных пробела существовали до проверяемого diff. Это **незакрытое явное
R12**, а не утверждение, что новый фильтр впервые создал уязвимость. Смешения
разных организаций этим воспроизведением не обнаружено; два tenant отдельно
проверены штатным тестом и изолированы.

Исполнителю: применить действующую область селлера к обоим запросам, сохранив
всех селлеров своего tenant для сотрудника без seller scope. Явный чужой seller ID
не должен расширять scope. Не фильтровать по автору и не вводить новые сущности.
Добавить проверки scoped/unscoped сотрудника, двух селлеров и двух tenant для
заказов и активных поставок, включая явный параметр seller_id.

### F2 — P2: после успешной смены scope сохраняются выбранные ID прежнего входа

В том же экземпляре ViewModel: загрузить A с новым заказом `1`, отметить его,
сменить возвращаемый ApiProvider контекст на B и вызвать `loadOrders(append=true)`.
Ответ B содержит только заказ `2`; список правильно заменяется, но
`state.selected` остаётся `{1}`. Это воспроизведено отдельным Kotlin-тестом:
`Selected A IDs remain in B scope: [1]`.

Причина — fallback `?: state.value.selected` в `FbsViewModel.kt:207`.
`FbsScreens.kt:88` показывает кнопку «Новая поставка (1)» по этому набору,
а `create()` использует старые выбранные ID, хотя их уже нет в текущей ленте.
Это несоответствие контракта смены scope; нативный вход другого сотрудника
на устройстве в этом ревью не воспроизводился.

Исполнителю: при обнаруженной смене scope убрать выбор и контекст предыдущего
входа; сохранённую попытку восстанавливать только для нового scope. При обычном
обновлении того же входа не терять его выбор и начатую попытку. Проверить обе ветви.

### F3 — P1: ошибка загрузки нового scope оставляет данные старого tenant

В том же экземпляре ViewModel: загрузить контекст A с заказом `1`; переключить
ApiProvider на B; на новом `orders()` вернуть `IOException`. После выполнения
`loadOrders(append=true)` ошибка показана, но `state.orders` по-прежнему содержит
заказ A. Отдельный тест падает с `Old tenant order IDs remain: [1]`.

В `FbsViewModel.kt:179–201` различие scope вычислено до запросов, но замена
состояния отложена до успешного завершения **обоих** запросов. Общий `perform()`
при исключении сохраняет старое состояние и меняет только ошибку/busy.
Следовательно той же очистки нет и при отказе второго запроса поставок.

Исполнителю: при подтверждённом изменении scope очищать прежние данные до сети
и не публиковать ответ, если его контекст уже сменился. Добавить случаи отказа
orders и supplies и продолжение после повтора. Не удалять долговременную попытку
предыдущего сотрудника: при его возвращении она должна восстанавливаться в его
собственном scope. Проверка выполнена на ViewModel; утверждение о конкретной
production-сессии или межорганизационном раскрытии на устройстве не делается.

## Аналитическая приёмка C16–C20: выполненная техническая часть

По отдельному поручению координатора после повторного ревью эта Astra-сессия
выполнила техническую часть приёмки по исходному документу. **Это замена прежней
сессии аналитика**, а не продолжение первоначальной постановки. Перечитаны
сохранённые исходный запрос, уточнения, R11–R12/C16–C21; ожидания не смягчались.
Эмулятор-5580 и 18082 в это время зарезервированы приёмкой WMS-441/443, поэтому

- C17/C18: на каждой площадке 105 done-заказов возрастом 500 дней стоят перед
