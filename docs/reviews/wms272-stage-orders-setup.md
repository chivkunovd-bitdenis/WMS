# WMS-272 — два новых заказа для ручного создания поставки на staging

09.09.2026, около 00:45 МСК. Это подготовка отдельных синтетических заказов
через штатный эмулятор и обычную синхронизацию WMS. Создание поставки,
подбор, упаковка и ручная браузерная проверка остаются координатору.

## Почему существующие new не видны во вкладке «Новые»

Свежий GET `/operations/fbs-orders?seller_id=50110328-fa03-4604-b2e4-8ca27fc8bb41&limit=500`
вернул 55 заказов, из них 20 со status=new. Worklist status_group=new вернул
0, а status_group=expired — 20 при server_now=2026-09-08T21:41:16Z.
Пример — WB500013: created_at_wb=2026-09-01T11:56:37Z,
deadline_at=2026-09-06T11:56:37Z. Поля supplier_status/wb_status в WMS для всех
этих 20 были null. Это отсутствие сохранённого статуса, а не доказательство
внешней отмены.

Прочитанный fbs_worklist_service.py требует для группы new одновременно
подходящий локальный статус, supplier_status null/new, неистёкший deadline
и активную обслуживаемую WB-привязку. Для expired условие срока обратное.
GET привязок подтвердил warehouse501001 → «Тестовый», is_active=true,
served=true. Поэтому в данном снимке причиной нуля является срок,
а не отключённое обслуживание склада.

Через существующий credential ровно этого селлера из WMS-контейнера выполнен
GET `/api/v3/orders/new` к проверенному эмулятору: HTTP200, 40 записей,
WB500013 присутствует. Read-only SQLite SELECT на стороне эмулятора для
WB500013 подтвердил seller_a/new/waiting/cancelled=0. Проверка одного
примера не означает отдельную полную сверку внешнего статуса всех 20 заказов.

## Подтверждение границы эмулятора

Свежий Railway SSH в WMS, project c28e681d-4535-4c96-ac97-c7b600a7f8e4,
environment58a08b66-1290-45a2-8737-e3d7408389e5, подтвердил разобранное
значение runtime settings.wildberries_marketplace_api_base:
**http / wb-emulator.railway.internal / 8000**. Это установленный staging,
хотя имя environment исторически production. Ни адрес боевого WB, ни Ozon
в этих запросах не использовались.

На работающем wb-emulator прочитан OpenAPI и код create_orders_for_seller:
POST `/__admin/orders` поддерживает seller, count, warehouse_id, chrt_id,
создаёт новые ID и current UTC createdAt, не вызывает seed/reset.
Runtime-шаблоны для111001 и111002 подтвердили требуемые EMU-артикулы.
Read-only SELECT перед созданием: тестовые эмуляторные запасы45 и51;
штатная покупка потребляет по одной единице соответствующего запаса эмулятора.
Ручных изменений WMS-остатков, прямого DB-seed и изменения старых заказов
эмулятора не было.
