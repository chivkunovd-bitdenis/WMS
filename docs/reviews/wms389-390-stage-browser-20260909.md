## WMS-389: два выбранных товара

Из штатного списка «Инвентаризация» нажато «Создать». В форме выбраны склад «Тестовый» (`307c0ccd-9a6b-41df-9180-f8ed68022237`), селлер «Эмулятор WB» (`50110328-fa03-4604-b2e4-8ca27fc8bb41`), без категории и ровно два товара через существующий поиск:

- `EMU-B2B-LEGAL`, «Куртка демо юрлицо», product `4cc917f5-0600-4d8b-8e55-1a975710d912`;
- `EMU-KIZ-OPTIONAL`, «Куртка демо ЧЗ необязателен», product `45587c50-451f-4d0a-b233-98c07be4dc9d`.

В форме до создания визуально подтверждены оба выбранных товара и текст ограничения состава. Комментарий: «WMS-389 browser QA 09.09.2026: два выбранных товара; не проводить». `POST /api/operations/inventory-counts` вернул 201. Зафиксированное тело содержит `source:planned`, `filters.product_ids` ровно из этих двух UUID, `all:false`, выбранные seller_id/warehouse_id и category:null.

Создан **ИНВ-8AE5F9EE**, ID `8ae5f9ee-2e95-4ab4-bea2-42d185a2b4ca`, время API `2026-09-08T22:10:52.059839Z`, статус `draft`. `GET /api/operations/inventory-counts/{id}` вернул 200: множество `lines.product_id` равно ровно двум выбранным UUID, других товаров нет. Всего четыре адресные строки: каждый товар лежит в своём коробе (40) и общем грузоместе (20). Это два товара, а не ошибочное включение четырёх товаров или всего склада.

Экран документа показывает «Черновик», 4 строки, посчитано 0, излишек 0, недостача 0; раскрытое дерево содержит только указанные два товара. После reload новый документ найден в списке и повторно открыт: оба товара видны. Во всех четырёх строках API `actual_quantity=null`, `posted_delta=null`, expected/current совпадают; `posted_at=null`. Факт не вводился, «Провести», отмена документа и создание тары не нажимались. Новый разрешённый черновик оставлен для последующего просмотра. Исторические документы и остатки не корректировались.

Цепочка в прочитанном коде: `InventoryCreateDialog` передаёт `productIds`; `FfInventoryPage.create` кладёт их в `filters.product_ids`; `inventory_count_service.create_count` добавляет `Product.id.in_(filters.product_ids)` к прежнему tenant/seller/warehouse отбору. Никакого обхода формы или прямого создания документа через SQL не было.

## WMS-390: старая WB-поставка

В штатном FBS открыта вкладка «В работе», в общий поиск введён `WB-GI-245619454EE7`. Браузер отправил:

`GET /api/operations/fbs-supplies/worklist?limit=500&status_group=active&search=WB-GI-245619454EE7`

Ответ 200, `total=1`, единственный результат `id=4e38cabf-b129-4a28-85b0-3dd3631da6a4`, `name=FBS 04.09.2026`, `wb_supply_id=WB-GI-245619454EE7`. На экране «Найдено 1», указанная поставка, селлер «Эмулятор WB», склад WB501001 / WMS «Тестовый». Скриншот просмотрен. Это подтверждённый серверный поиск через UI, не локальное отсеивание уже загруженного массива. Совпадение за пределами 500 строк этим небольшим существующим набором не доказывается; новых данных ради него не создавалось.

Синхронизация заказов, изменения поставки, упаковка и отгрузка не запускались. Цепочка `FfFbsOrdersScreen.load` передаёт `activeSearch` в `fetchFbsSupplyWorklist`; соответствующий сервис применяет поиск по поставке и связанным заказам. Точечные браузерные проверки выше прошли; pytest/сборки/дополнительные тесты не запускались. Собственный браузерный контекст закрыт.
