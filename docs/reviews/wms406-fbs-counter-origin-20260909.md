# WMS-406 — что означает «Отгружено FBS 878» у Loviana

09.09.2026. Проверка только чтением. Production: `743a794bf0ee9e20cccf7f87c05138b035604ec9` по подтверждённому root выпуску; перечисленные ниже UI/services сверены с этим Git SHA без различий. UI заново в браузере не открывался. SQL выполнен через SessionLocal контейнера `wms_prod-api-1`: `SET TRANSACTION READ ONLY`, `SET LOCAL statement_timeout = '15000ms'`, затем rollback; `transaction_read_only=on` подтверждено. Приложение, факты, начисления и склад не менялись, тесты не запускались.

**878 — сумма штук в сохранённых системных фактах `fbs_order`, а не число нажатий складом кнопки «Отгрузить» в выбранные даты.** Исторически такой факт появлялся по подтверждению WB `sorted` или `sold` (внутренний `done`), а также мог достраиваться отдельным скриптом за прошлое. Нынешний код добавляет запись при успешной передаче поставки маркетплейсу, но это не меняет происхождение и даты уже существующих фактов.

## Точный состав и дата периода

Область проверки: tenant `7b98a8aa-c03c-4649-9677-a645be45c622`, seller Loviana `9819f2c6-b28e-401e-a163-6ffe9e420da6`. Для 01.08–09.09 включительно отчёт фильтрует `OperationFact.occurred_at` от 01.08 00:00 МСК включительно до 10.09 00:00 МСК исключительно: UTC `[2026-07-31 21:00, 2026-09-09 21:00)`. Это не фильтр по времени создания записи, обновления заказа или нажатию кнопки. Общий cutover фактов — 01.07.2026 00:00 UTC, выбранный период он не сокращает.

Свежий SELECT нашёл 878 фактов по 878 различным заказам, сумма `item_quantity=878`. Все имеют `billable_service_code=fbs_order`, `marketplace=wb`, `source=system`, `source_kind=fbs_order`, `actor_user_id=NULL`, `integrity_status=complete`, `reversal_of_id=NULL`. У всех `source_event_id=document_id` и ключ `fbs-order:<UUID заказа>`. `complete` здесь означает полноту записи факта, а не отдельное подтверждение от WB; актор отсутствует также у нынешнего пути подтверждённой передачи, поэтому это не доказательство отсутствия действий оператора.

| Сохранённая дата `occurred_at` | Фактов | Что проверено |
| --- | ---: | --- |
| Ровно `FbsOrder.packed_at` | 702 | Совпадение с текущим сохранённым временем упаковки, а не временем передачи |
| Ровно `FbsOrder.created_at_wb` | 2 | Дата появления заказа у WB, а не работы склада |
| Время обработки/записи | 174 | Не совпадает с packed_at, picked_at, created_at_wb или сохранённым supply.delivered_at; находится на 0.865115–5.937078 секунды позже created_at самого факта |

Последние 174 записаны 03.09 — 77, 04.09 — 11, 05.09 — 86. У всех сейчас есть иное `packed_at`. PostgreSQL задаёт `created_at` факта через `now()` на начало транзакции; старый writer задавал `occurred_at` через Python `datetime.now(UTC)` при обработке. Именно этому механизму соответствуют сохранённые секунды. Точная версия запущенного процесса для каждой строки не записана.

Минимальная дата факта — 17.08.2026 11:05:20.932014 UTC, максимальная — 08.09.2026 13:32:07.401914 UTC. Физически записи созданы 03–08.09.2026; отдельно видны 263 записи, созданные 07.09 в 16:19–16:20 UTC с августовскими датами операции. Сам по себе этот пакет не доказывает имя запущенного скрипта.

На момент чтения текущие статусы этих заказов: 318 done/sold, 233 sorted/ready_for_pickup, 190 sorted/sorted, 124 cancelled/canceled_by_client, 13 defect/defect; у всех supplier_status=complete. Это текущий снимок, не сохранённый статус на момент создания факта. Наличие cancelled/defect не удаляет исходную запись из натурального показателя. Сохранившиеся или потерянные связи поставок не использованы как доказательство нажатия либо ненажатия отгрузки.

## Цепочка кода и изменение правила

`frontend/src/screens/ff/FfBillingScreen.tsx:337` показывает «Отгружено FBS» из `report.totals.fbs_items`. В `backend/app/services/billing_seller_report_service.py:129–153` это сумма item_quantity строк услуги fbs_order, кроме строк с result reversed/not_billable. `_operation_entries:223–233` выбирает факты по occurred_at; `:357–374` переносит количество и услугу из факта. Текущий статус заказа и наличие supply_id не являются условиями этого счётчика. Строка без денежной оценки также учитывается. Денежное сторно и натуральный факт — разные записи; `fbs_cancellation_service.reverse_fbs_order_billing:114` работает с денежным начислением, а не удаляет исходный OperationFact.

Писатели и их смысл:

- `fbs_order_billing_service.record_fbs_order_confirmed:86–157` записывает один факт на заказ. `wb_marketplace_orders_service:761–804` вызывает его при WB sold/sorted. Сам supplier_status complete этим вызовом не является. Ozon имеет отдельный вызов в `ozon_fbs_sync_service:749–765`, но все исследованные 878 — WB.
- Нынешний `fbs_shipment_service._apply_local_delivered:1193–1219` после подтверждённой передачи вызывает `charge_handed_over_orders`. Для in_delivery требуется явное `confirmed_handover_at`; один импортированный in_delivery недостаточен. Приоритет даты нынешнего writer: confirmed_handover_at → явно переданный occurred_at → сохранённый supply.delivered_at → packed_at → picked_at → created_at_wb → текущее время.
- `backend/scripts/backfill_fbs_order_facts.py` создаёт недостающие исторические факты с тем же source и ключом. Текущий вариант берёт confirmed statuses, пропускает in_delivery без подтверждения передачи и использует передачу либо fallback времени заказа. Он может поправлять старую дату при расхождении более суток, но после WMS-013 не меняет её при начислении либо ссылке из счёта. В этом расследовании скрипт не запускался.
- `operation_fact_recovery_service.py` восстанавливает события подбора `fbs_pick`, не эти факты услуги `fbs_order`. `backfill_billing_charges.py` создаёт деньги по фактам, а не служит источником исследованных 878 фактов.

История Git отделяет старое поведение от нового: `46d63075` от 02.09 ввёл услугу по sorted/done с датой обработки `datetime.now(UTC)`; `9fa78f68` от 03.09 заменил дату на packed_at → picked_at → created_at_wb и добавил исторический backfill. `20a61902` (WMS-391) от 08.09 добавил подтверждённую передачу и её дату; `7024a92e` (WMS-013) ограничил изменение уже учтённых дат backfill. Даты коммитов не выдаются за время развёртывания каждой версии.

`operation_fact_service.write_operation_fact:368–392` при повторе возвращает уже существующий факт без изменения occurred_at. Поэтому современное подтверждение не превращает старую дату обработки или упаковки в дату передачи. Обычный writer и backfill используют одинаковый `fbs-order:<id>`; модель OperationFact не хранит имя процесса/скрипта или первоначальный статус WB. **Точную атрибуцию каждой из 878 записей конкретному запуску восстановить из этих полей нельзя.** Доказаны общая семантика, возможные писатели и фактический состав дат; подмена этого числа количеством заказов со связанной поставкой не предлагалась.
