# WMS-415/416: аудит организации работы, 10.09.2026

Аудит выполнен root по прямому запросу владельца о затянутой работе. Это разбор исполнения существующих задач, не новый бэклог. Новые тесты, сборки и ревью для аудита не запускались. Прочитаны Git, записи запусков, видимые сообщения исполнителей, конкретные результаты ревью и GitHub CI/PR. Скрытые рассуждения и закрытые mobile-логи не использованы. Стоимость в деньгах и полное распределение часов не измерены; соответствующих оценок здесь нет.

## Вывод

Основная причина затягивания — управление работой: слишком широкий незавершённый объём, последовательные повторные передачи между авторами и ревьюерами, поздняя проверка настоящего пользовательского пути, запоздалое отделение независимых результатов. Ответственность root, а не объяснение «модели медленные». Реальные ошибки исправлялись, но процесс постоянно производил новые проверки и расширения вместо завершения ограниченного результата.

## Проверяемые факты

### 1. Ревью превратилось в длинную цепочку

В `artifacts/wms415-astra-takeover-20260910/resumed/` найдено 32 отдельных descriptor-файла запуска/возобновления ревью с разными PID (имя начинается с `review` или `opus5`). Это НЕ 32 завершённых полных аудита одного кода: сюда входят отдельные задачи, повторные проверки исправлений и прерванные запуски. Для 26 немобильных запусков подтверждено наличие видимых сообщений; защищённые mobile-events не читались. Отдельные шесть ранее запрошенных владельцем Opus-ревью WMS-417 в это число не включены.

11 записей относятся к входу, proxy и процедуре выпуска. Восемь из них предшествовали неудачной выкладке WMS-270/377: review-deploy-followup, review-deploy-navigation-final-delta, review270377-auth-proxy-final, review377-network-preflight-final, review377-stopped-retry-final, review270-377-narrow-release, review270-minimal-deploy и review270-minimal-deploy-final. Ещё три — последующие Caddy/Opus-проверки. Часть находок была реальной; количество проверок не обеспечило проверку нужного свойства до выпуска.

Конкретный дефект: в Git `1922a224:deploy/Caddyfile.http` стояло `{http.request.client_ip}`; API фактически получил эту буквальную строку для двух источников и объединил лимиты входа. В отчёте `wms270-377-independent-auth-proxy-20260910.md` явно сказано, что два настоящих Caddy не исполнялись; в следующем `wms270-377-narrow-independent-final-20260910.md` доверие опиралось на ранее принятую конфигурацию. Проверку реального поведения следовало поставить ДО production. Последующее локальное выполнение на Caddy 2.11.2 прошло восемь HTTP-проверок; повторять их без изменения кода/окружения не нужно.

### 2. Не подтверждено объяснение «двадцать полных CI одного изменения»

GitHub показывает семь CI-запусков по четырём сегодняшним выпускным веткам:

| PR | CI run | Результат |
|---|---|---|
| 213, mobile API | 34451081425, 34452470232 | два PASS на разных SHA |
| 214, Ozon | 34456316470, 34458094624 | FAIL, затем PASS на исправленном SHA |
| 215, вход/порты | 34462255065, 34464471258 | два PASS на разных SHA |
| 216, фильтр | 34462815600 | один PASS |

Отдельные локальные команды многократно содержат pytest/tsc/build, но простой поиск строки завышает число исполнений: он захватывает генерацию скриптов, чтение результатов и запись документации. Эти совпадения не выдаются за количество прогонов или потраченные часы. Подтверждены и оправданные повторы: новые ошибки конкурентных операций, исправления двух P2 чата, смена интегрированного кода. Нет основания объявлять каждый повтор пустым. Проблема — отсутствие короткой конечной цепочки принятия и поздняя проверка главного сценария.

### 3. Готовый независимый результат задерживался общей очередью

Фильтр WMS-418 передан root с ручной проверкой в `31a0ea4c` в 12:01 МСК. Отдельный PR216 создан в 12:50:01, CI завершён в 13:00:38, merge в 13:02:07, контейнеры запущены в 13:05:28. Около часа после передачи нельзя объяснить десятиминутным CI. Между передачей и отдельным выпуском продолжались интеграция, общие складские проверки и подготовка auth-выпуска. Изоляцию готового фильтра нужно было сделать сразу.

Чат принят в интеграцию `ba47e9d6` в 12:15; локальный переход FBS → сообщение → полный чат → тот же документ подтверждён в 13:10–13:12 (`wms179-397-live-followup-20260910.md`). Вместо последовательного завершения оставшихся пользовательских сценариев работа продолжала переключаться на аудит и выпуск входа.

### 4. Расширялся объём аудита WMS-325

Последовательные задания охватили права сотрудников/тару, печать и блокировки, приёмку и MP-документы, реквизиты/тарифы/счета, конкурентную отмену счёта, маркировочные пулы и шаблоны печати. Это подтверждают descriptor-файлы audit325-* и коммиты `c771af4f`, `0684cbbd`, `3d160fca`, `c7082fb8`, `0caa6f6a`, `5ec40106`.

Работы относились к разрешённому бэклогу, однако root неверно управлял очередностью: «взять ещё десять после этих» стало одновременным расширением незаконченного первого набора. Общий аудит не должен удерживать APK или чат. Последний завершённый прогон 46 целевых тестов уже принят; не запускать его снова из-за новой сессии.

### 5. Была работа по неподтверждённому требованию

Root выбрал WMS-111/112 по тексту бэклога, не установив первичное требование владельца на фоновое создание WB-возврата и реестр. После возражения пришлось замораживать, архивировать и исключать исполненный срез. Коммит `5ec3df40` изменяет 16 файлов и удаляет из кандидата 1506 строк (включая тесты). Это измерение переделки, не оценка её стоимости. Правильные Ozon-требования WMS-231 найдены отдельно и относятся к существующей приёмке типа «возврат».

### 6. Выпуск нарушил фактический доступ операторов

В 13:26 WMS-270/377 закрыли 8088/15174. По фото владелец продолжал работать на 194.87.96.144:8088. Root не обеспечил предварительный переход операторов и не предупредил; недоступная страница — последствие наших действий. Исправление входа пришлось откатить: в 13:40:37 API восстановлен из `120b106c`, web и закрытие портов оставлены. Сам адрес в APK также мог остаться старым: обновление намеренно сохраняет адрес сервера. Адрес конкретного физического ТСД не проверен, поэтому общая готовность устройства не доказана.

### 7. Мониторинг и статусы вводили в заблуждение

Запись о запуске принималась за продолжающуюся работу. При запросе статуса около 14:15 root обнаружил отсутствие coordinator25612 и последних исполнителей; автоматический контроль не обеспечивал непрерывного исполнения. Точный момент остановки и длительность простоя не установлены: последнее видимое событие не равно времени завершения процесса.

Канон содержит новые доказательства над старыми заголовками «НЕ СДЕЛАНО» и прежними PID. Автоматизация накапливала длинные противоречивые дополнения. Это увеличивает стоимость восстановления контекста и риск повторно запустить завершённое. Статус нужно заменять, а историю складывать отдельно в существующей карточке. Сообщать следует «проверено/осталось/кто жив», а не «почти готово» без конечного критерия.

Также ранний запуск нарушил изоляцию: подагенты получили неверную Git-базу и писали в общий checkout; затем требовалось восстановление. Это зафиксировано в `wms415-claude-launch-20260910.md`. Проверку точных путей, базы и модели следовало выполнять до начала параллельной работы.

## Что реально получено, а что нельзя закрывать

- Ветка фильтра выпущена отдельно; Ozon API и совместимый mobile API также имеют отдельные подтверждённые выпуски.
- APK v10 опубликован до запрета владельца; реальные кнопки 9→10, сохранение PIN/сервера/документов приняты на Android15-эмуляторе (`wms363-network-update-acceptance-20260910.md`). Это не доказательство физического ATOL/сканера и не разрешение повторять публикацию.
- Белый экран после долгой паузы не закрыт, возврат из формы сервера потребовал перезапуска. Сетевая печать WMS-402 пока имеет контракт, а не законченную реализацию. Нельзя называть всё приложение готовым или сводить остаток только к «потестировать принтер».
- Чат и складские правки имеют сохранённый код и частичные проверки, но общий завершённый пользовательский результат не подтверждён. Не обнулять выполненное и не объявлять оставшееся формальностью.

## Немедленные изменения организации

1. Root остановил coordinator39993, chat40379, mobile40380 и Opus40378; отсутствие всех четырёх подтверждено. Монитор wms-claude PAUSED, чтобы не перезапустить старую очередь во время аудита. Dirty и результаты сохранены.
2. Запрет владельца на production остаётся без исключений. Никаких выкладок, откатов, restart, миграций, live-data и публикации APK/update manifest.
3. Не возобновлять весь WMS-415/416 одним пакетом и не наращивать аудит325. Оставшиеся задачи не отменены; их порядок фиксируется только в каноническом бэклоге.
4. Для следующего локального прохода: один владелец мобильных конкретных дефектов и один владелец оставшихся сценариев чата. Root интегрирует и проверяет пользовательский путь. Нет отдельной постоянно вращающейся очереди reviewers. Новая проверка — только для нового кода, конкретной ошибки или ещё не проверенного требования.
5. До начала каждой правки указать один наблюдаемый результат и точную оставшуюся проверку. После её успеха завершать срез. Недоступное физическое оборудование отмечать как границу, а не бесконечно заменять новыми эмуляторными кругами.
6. Повтор после доказанного дефекта допустим; повтор того же успешного теста на том же коде из-за нового агента запрещён. Финальное запрошенное владельцем ревью не должно каскадом открывать новые несвязанные задачи.
7. Отчёт root: завершённый результат, точный остаток, реально работающий исполнитель и препятствие. Ни «всё готово» по одному emulator update, ни «работают агенты» по старому PID.

Аудит не требует ещё одного ревью самого аудита. Следующий шаг — исполнение ограниченного остатка, а не расширение анализа.
