## Контракт, прямо следующий из слов владельца

- Использовать существующий документ приёмки с типом «возврат», кнопку «Создать возврат», выбрать селлера/маркетплейс.
- Для Ozon по кнопке получить список возвратов; предварительный просмотр пунктов выдачи и товаров внутри. Выбирать пункты по одному или все.
- Несколько выбранных пунктов попадают в ОДИН текущий документ, сгруппированными по пунктам; не создавать отдельный документ на каждый.
- Из документа печатать доступный пропуск/штрихкод и форму сверки товаров. Исходный вопрос об общем/раздельном QR — вопрос, а не разрешение придумать API; сверенная спецификация описана в RETURNS-PROCESS.md.
- После физического получения принимать сканированием или ручным количеством. Владелец разрешил добавлять строки. Необязательная колонка «Брак»: часть фактически принятого. После проведения годное на обычный склад, брак отдельно на склад брака.
- Для WB нет получения возвратов этим API-путём: после подбора фактического товара не требовать повторного ввода приёмки, разрешить завершение.
- Никакого редизайна/нового раздела. Минимальные перечисленные изменения, разрешённый подбор Ozon с фотографиями/колонками внутри существующей цепочки.
- В этих сообщениях НЕТ требования создавать возвратные документы фоном по отменам WB. WMS111/112 не заменяют WMS231 и остаются приостановленными по спорному происхождению.

## Сопоставление с сохранённой постановкой и текущим кодом

`tasks/ozon-integration-20260825/RETURNS-PROCESS.md`, разделы2/4/7, описывает эту цепочку, включая отдельное разрешение на подбор Ozon.

Root прочитал текущие `frontend/src/screens/ff/useOzonReturnWorkflow.ts`: openPicker запрашивает preview для существующего request_id, importGiveouts передаёт выбранные giveout_ids в import и перечитывает detail/groups. `backend/app/api/ozon_returns.py` использует путь `/operations/inbound-intake-requests/{request_id}/ozon-returns`. `backend/app/services/ozon_return_service.py` проверяет operation_type=return/marketplace=ozon, строит preview и добавляет выбранное в строки этого же request_id. Это проверка кода, не новая живая приёмка/печать и не доказательство всех критериев.

Дальнейшая сверка должна опираться на эти первичные сообщения. Автоматическое создание документа по WB-отмене не выводится из того, что имеющийся ручной возврат требует действий оператора.
