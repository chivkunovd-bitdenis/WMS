# Батч 01. Карта ролей, входа и ориентации

## Граница проверки

Проверен только батч 1: доступные роли, первый и повторный вход, role landing, общее меню, активное состояние навигации, dashboard, уведомления, browser back/forward/reload, прямые URL и отображение на 1280×720 и 1920×1080 при DPR 1. Seller workflow, приёмка, отгрузка, FBS, маркировка и настройки интеграций не оценивались как сквозные процессы: в этом батче их экраны открывались только для доказательства reachability (достижимости), названия, меню и ориентации.

Это разделение принципиально: факт, что route открылся, не означает, что физический процесс на нём корректен. Empty state подтверждает только empty state. Populated-состояние подтверждает только увиденные строки и действия.

## Роли и физическая работа

| Роль | Физическая ситуация | Что нужно сразу после входа | Передача следующей роли |
|---|---|---|---|
| Администратор ФФ | Руководитель/диспетчер смены за рабочим ПК видит план и исключения по всему складу | Понять организацию, текущую неделю, входящие приёмки, отгрузки и перейти к нужному документу | Назначить/подготовить работу сотруднику приёмки, сортировки, упаковки либо селлеру |
| Сотрудник ФФ | Оператор получает ограниченный набор разделов; в проверке выданы «Приёмка» и «Отгрузки на МП» | Увидеть только разрешённые очереди и конкретную работу смены, без админских действий | Провести физический товар к следующей зоне, оставив понятное состояние документа |
| Селлер | Сотрудник бренда планирует передачу товара ФФ и отгрузку на МП | Понять, чей кабинет открыт, увидеть свои документы и очевидное следующее действие | Создать корректную заявку, которую однозначно увидит ФФ |

## Фактические цепочки входа

### Администратор ФФ

`/` → публичный вход ФФ → `/app/ff/dashboard` → меню ФФ. Ошибка с неверными данными остаётся на форме и допускает исправление. Logout показывает публичную форму, хотя URL защищённого route остаётся прежним. Вход с корня ведёт именно на dashboard.

### Селлер

Администратор создаёт запись селлера и email → селлер открывает `/seller/` → для первого входа обязан оставить пароль пустым → задаёт новый пароль → попадает на `/seller/documents`. Отмена установки возвращает к входу, несовпадение паролей объясняется. На общей машине браузер автоподставил пароль администратора в seller login, поэтому «оставьте пароль пустым» фактически не гарантировано и потребовало осознанного выделения и удаления значения.

### Сотрудник ФФ

Администратор создаёт сотрудника → включает разрешения → сотрудник на FF-портале оставляет пароль пустым → задаёт новый → попадает на `/app/ff/dashboard`. Меню отфильтровано до Dashboard, «Отгрузки на МП», «Приёмка», «Сортировка».

## Reachability отдельно от продуктового результата

| Поверхность | Reachability | Продуктовый verdict |
|---|---|---|
| Admin menu routes | Все пункты реально открыты, active nav виден | Reachability в основном PASS; это не подтверждает процессы батчей 2–10 |
| Admin dashboard | Empty и populated открыты; populated строка кликом открыла диалог приёмки №000005 | Процесс перехода существует, но действие строки невидимо и недоступно с клавиатуры; статус `submitted` технический |
| Seller shell | Все четыре пункта и notifications открыты | Landing понятен по документам, но role context показывает `fulfillment_seller`, не показывает название селлера/организации |
| Staff shell | Меню корректно сокращено | На MP route виден сырой `forbidden` вместе с данными; это не безопасно завершённый процесс |
| Нерелевантные direct URL | Seller→FF показывает FF login; staff settings возвращает на dashboard | Staff `/sellers` всё же открывает админский экран с сообщением о запрете; reachability не равна разрешению |

## Физический смысл dashboard

До действия товар физически ожидается у селлера или в пути на ФФ; dashboard должен дать диспетчеру план по датам и открыть конкретную заявку. В populated-состоянии клик по строке `2026-08-09 / 2 / Denmarcs` открыл диалог «Приёмка №000005», показал статус «В сортировке», две товарные строки, короба и блок распределения по ячейкам. Это точный наблюдаемый outcome. После закрытия сотрудник вернулся к dashboard. Однако строка не имела роли link/button, `tabindex` и подсказки действия; курсор был pointer. Оператор мышью может продолжить, клавиатурой и при низкой цифровой грамотности — действие не обнаруживает.

## Fixture и границы доказательства

- Использованы отдельные синтетические admin/seller/staff записи. Значения паролей не записаны в evidence/log.
- Создан один synthetic seller и один synthetic FF staff штатными UI-формами; read-back подтверждён reload.
- Existing staging admin дал populated входящие заявки. Populated «Отгрузки на МП» на dashboard отсутствовали, поэтому row action этой таблицы — `BLOCKED_FIXTURE`.
- Seller documents/products были empty; populated seller row action — `BLOCKED_FIXTURE`.
- Никакие реальные WB ключи, sync, import, create shipment, mark-all-read и другие изменяющие внешние/операционные данные действия не выполнялись.
