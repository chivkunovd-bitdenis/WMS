Код не редактировался. Verdict основан на BA/UX-артефакте F22, карточках F08/F10/F22, текущем backend sync/availability коде и текущем seller UX остатков.

## Короткий verdict

F22 надо отдавать в dev как отдельную P0-защитную фичу. Без F22 нельзя отдавать в staging или дальше текущую синхронизацию остатков WMS -> WB, потому что текущий путь может трактовать отсутствие FBS-пула или пустую доступность как `amount=0`.

Продуктовое правило простое: включение sync не должно превращать неопределенность в ноль. Если WMS не доказала, сколько именно надо отправить в WB по seller + WB warehouse + product variant, она не отправляет ничего. Пользователь должен увидеть человеческое "не отправлено" и действие "настроить FBS-пул" или "повторить", а WB-остаток не должен стать `0` из-за ошибки, пустого расчета или отсутствующей настройки.

## Почему approved, а не rework

BA/UX F22 уже правильно описал бизнес-инцидент, safe-sync инварианты, нужные состояния и обязательный browser QA: в WB было `20`, включили sync, при отсутствующем FBS-пуле или ошибке WB должно остаться `20`, а UI должен показать понятную причину без технического мусора.

Карточки F08 и F10 остаются важными зависимостями: F08 задает распределение остатка и FBS-пул, F10 требует отправлять в WB только FBS-пул. Но F22 является P0-защитой поверх них. Ее нельзя блокировать до "идеальной" реализации всех направлений, потому что текущий риск уже может портить внешний продающий остаток в WB.

Поэтому verdict: `PRODUCT_APPROVED_FOR_DEV` для узкой F22-защиты. Это не approval на широкий редизайн seller catalog, не approval на выпуск F08/F10 целиком и не approval на staging без browser-доказательства F22.

## Ответы на продуктовые вопросы

### Должен ли enable sync сразу публиковать 0, если FBS-пул не задан?

Нет. Это запрещено.

Отсутствие FBS-пула означает "WMS не знает безопасное количество для FBS-публикации", а не "надо снять товар с продажи". Если в ЛК WB сейчас `20`, а в WMS нет явного FBS-пула, включение sync должно только поставить товар в состояние `Не отправлено: FBS-пул не настроен` или не дать включить публикацию до настройки. Внешнего `PUT amount=0` быть не должно.

### Разрешаем ли в этой итерации публикацию 0 вообще?

Да, но только как доказанный бизнес-ноль, а не как fallback.

`0` можно отправить в WB в этой итерации только если одновременно выполнены все условия:

1. Есть явная связь seller + WB warehouse + WMS warehouse.
2. Есть явная FBS-настройка для товара: WMS отличает "FBS-пул задан и равен 0" от "FBS-пула нет".
3. Количество к отправке рассчитано из FBS-пула, а не из `None`, пустого словаря, ошибки, отсутствующего product id, отсутствующего `chrtId`, общего остатка ФФ, свободного FBO или старого sync item.
4. Пользователь видит, что в WB уйдет `0 шт`, и подтверждает это как опасное действие. Формулировка должна быть складская: "Отправить в WB 0 шт" / "Снять FBS-остаток с продажи", а не техническая.
5. WMS делает WB `PUT` и затем обязательный readback. Успех можно показать только после readback `0` по тому же seller + WB warehouse + `chrtId`.
6. Если `PUT` прошел, но readback не подтвердил `0`, UI показывает не успех, а состояние сверки/ошибки. Last confirmed amount не перезаписывается неподтвержденным значением.

Автоматический `0` при первом enable sync, массовом включении, пустой availability, missing mapping, WB error, readback mismatch или отсутствии FBS-направления запрещен.

### Какой UX нужен

Нужен компактный рабочий UX внутри текущего экрана товаров и drawer распределения. Не нужен новый большой экран и не нужна раздутная таблица.

В строке товара достаточно:

- `На ФФ`;
- `В ячейках`;
- `Свободный FBO`;
- компактная ячейка `Распределение`: `FBS N шт`, `резервы N шт`, кнопка `Распределение`;
- компактная ячейка `Публикация FBS в WB`: человекочитаемый статус, одно основное действие.

Не добавлять колонку `Лимит` как постоянный столбец. Если лимит технически остается в модели или участвует в старом API, он не должен раздувать основной seller stock экран. Нельзя добавлять raw-коды вроде `warehouse_mapping_missing`, `pending_confirmation`, `wb_upstream_error_500` как основной текст UI. Эти коды допустимы в логах и code review evidence, но селлер видит человеческую причину.

Разрешенные компактные статусы:

- `FBS-пул не настроен`;
- `В WB не отправлено`;
- `Проверяем WB`;
- `WB подтвердил N шт`;
- `Ошибка WB`;
- `Публикация на паузе`.

Основные действия:

- `Настроить FBS-пул`;
- `Включить`;
- `Повторить`;
- `Отправить 0 шт` только после явного опасного подтверждения.

## Обязательные product constraints для dev

1. Разделить три состояния в backend-модели расчета: `missing/unknown`, `known positive`, `known zero`. Сейчас логика вида `availability.get(product.id, 0)` продуктово неприемлема, потому что она склеивает "нет данных" и "ноль".
2. Availability service должен позволять отличить "направления нет" от "FBS-пул явно есть и равен 0". Если текущие модели не дают этого доказать, publish zero блокируется.
3. `_build_publish_plan` не должен создавать `_PublishTarget(amount=0)` для товара без явного FBS-пула.
4. Старые confirmed sync items нельзя использовать как повод отправить `0` по товарам, которые выпали из текущего безопасного product/FBS-плана. Такой zeroing может быть отдельной фичей, но не частью F22.
5. `fbs_stock_limit` не является источником безопасного нуля. Лимит может только ограничить уже доказанный FBS-пул; он не должен превращать неизвестное количество в `0`.
6. Ошибки WB, токена, сети, mapping, duplicate `chrtId`, readback mismatch и empty availability не должны менять WB на `0` и не должны показываться как success.
7. Last confirmed sync result обновляется только после readback. Неподтвержденный `PUT` оставляет состояние `Проверяем WB` / `Ошибка WB`, а не `WB подтвердил`.
8. Bulk enable не имеет права массово отправить нули. Для строк без FBS-пула bulk должен оставить `В WB не отправлено` и дать путь к настройке.
9. Роль и секреты не трогаются. Никаких кабинетов ключей, токенов, Railway variables или secret panels в рамках F22.
10. Dev работает только с F22. Не чинить "заодно" F08/F10 UX шире утвержденных F22-границ.

## Обязательные constraints для code review

Code review должен явно проверить и записать finding/pass по этим пунктам:

1. В diff нет ни одного пути, где `None`, отсутствующий ключ словаря, пустой список, exception или mapping miss превращается в publishable `0`.
2. `amount=0` покрыт отдельной веткой `known zero` и требует явного FBS-пула плюс UX-подтверждения.
3. Нет `PUT 0` для "zeroed old targets" из старых sync items без текущего безопасного product/FBS-плана.
4. Нет destructive `DELETE` для обычного зануления WB-остатка.
5. Readback обязателен для success, включая `0`.
6. Tests доказывают incident path: WB/emulator starts with `20`, enable sync without FBS pool does not change WB to `0`.
7. Tests доказывают WB error/readback mismatch: UI не показывает success, last confirmed value не меняется.
8. Tests доказывают allowed zero path, если dev реализует его в этой итерации: explicit FBS zero + confirm + PUT 0 + readback 0.
9. UI не содержит колонки `Лимит`, raw JSON, stack trace, технических кодов как основного текста, новых лишних чипов или дублирующих кнопок.

## Обязательные constraints для browser QA

Browser QA не может засчитать F22 по API-тестам или unit-тестам. Нужен живой проход в браузере на seller stock/catalog UI.

Минимальный browser QA:

1. Открыть seller products stock screen.
2. Подготовить товар, где WB/emulator readback до действия равен `20`.
3. Проверить отсутствующий FBS-пул: включение/попытка sync не отправляет `0`, WB/emulator после действия остается `20`, UI показывает `FBS-пул не настроен` или `В WB не отправлено`.
4. Проверить ошибку WB/readback: last confirmed WB amount не меняется, UI не показывает success.
5. Проверить nonzero happy path: FBS-пул `N`, sync, readback `N`, UI `WB подтвердил N шт`.
6. Если zero path реализован: проверить только явный confirmed zero path с подтверждением, readback `0` и понятным текстом. Если zero path не реализован, QA должен доказать, что UI-пути отправки `0` нет.
7. Проверить визуально таблицу на обычном desktop viewport: нет `Лимит` как отдельной колонки, нет технических кодов, нет лишних чипов, кнопки не раздувают таблицу.

## Staging / release gate

Нельзя отдавать в staging или показывать клиентам текущую синхронизацию WMS -> WB как безопасную без F22.

Причина: текущий `fbs_stock_sync_service` строит publish plan так, что отсутствие записи в availability может стать `amount=0`, а `fbs_stock_availability_service` при отсутствии stock direction возвращает `0`. Это допустимо как внутренний расчет "нет выделенного FBS", но недопустимо как внешняя публикация в WB без явного безопасного основания.

После dev F22 можно пускать дальше только если:

- code review прошел все P0-пункты выше;
- browser QA доказал incident path с WB/emulator `20 -> 20`, а не `20 -> 0`;
- committed SHA известен;
- для staging отдельно проверено, что staging собран именно из этого SHA.

## Итог

`PRODUCT_APPROVED_FOR_DEV`.

Dev разрешен только на узкую F22-защиту safe sync. Текущую WMS->WB синхронизацию нельзя отдавать в staging/release без F22 и без browser QA, доказывающего, что ошибка, пустой расчет или отсутствующий FBS-пул больше не публикуют `0` в WB.
