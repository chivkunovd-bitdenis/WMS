# Батч 03. Карта процесса физической приёмки

## Граница батча

Проверяется только путь сотрудника фулфилмента после того, как селлер уже передал заявку на склад: очередь «Приёмка» → доказательство конкретного документа → фактический пересчёт товара россыпью/сканером → работа с коробами → расхождение → завершение приёмки → видимый переход в «Сортировку» и появление принятого количества в зоне сортировки. Раскладка по адресным ячейкам относится к B04 и здесь не выполняется.

Источник входного fixture — B02: isolated synthetic seller, два manual товара `B02-UX-35204480-A` и `B02-UX-35204480-B`, submitted inbound с планом A=3, B=2 и двумя коробами. Seller-facing ID в B02 не сохранён, поэтому выбирать первую строку очереди запрещено.

## Физический процесс и роли

| Момент | Кто и где физически | Что он знает | Что должна дать система | Результат для следующей зоны |
|---|---|---|---|---|
| Прибытие | Приёмщик у ворот/стола приёмки; перед ним короба селлера | Селлер, дата, накладная/маркировка коробов | Быстро найти ровно нужную заявку, не угадывая по порядку строк | Открыт доказанный документ, чужой товар не затронут |
| Первичная сверка | Приёмщик видит физические короба и состав заявки | План: 2 позиции, 5 единиц, 2 короба | Человеческий номер, seller, план коробов, SKU/name и заявленное количество в одном экране | Понятно, что и сколько считать |
| Поштучный пересчёт | Товар сканируется/считается в шуме, возможно в перчатках | Штрихкод или SKU, текущий факт | Фокус и Enter-цикл без мыши; +1 с немедленным feedback; неизвестный код не меняет факт | Зафиксирован фактический состав |
| Ручная коррекция | Исключение: пересорт, повреждение, лишнее/недостача | Точный пересчитанный факт | Целое количество ≥0; понятная ошибка; read-back после reload | Факт совпадает с реальностью, а не с планом |
| Работа с коробами | Приёмщик сохраняет физическую группировку | Номер/ШК короба и его содержимое | Короб можно создать, наполнить, исправить; нельзя тихо потерять содержимое | Короб и состав однозначно прослеживаются |
| Завершение | Старший/приёмщик закончил пересчёт | Итог по каждой позиции и коробам | Явное последствие; отдельное предупреждение при расхождении; защита от повторного завершения | Остаток появляется только в зоне «Сортировка» |
| Передача | Сортировщик получает принятый товар | Сколько реально принято и что осталось разложить | Документ исчезает из приёмки, появляется в сортировке; stock-семантика объяснена | B04 может начинать размещение без повторного выяснения факта |

## Твёрдые продуктовые правила

1. Очередь должна позволять идентифицировать документ без перебора и памяти: номер/ID, seller, дата, статус и итог состава.
2. `submitted/receiving/verifying` и другие коды реализации не являются допустимым языком оператора.
3. До первого изменения обязано быть доказано совпадение seller, даты, двух строк, SKU A/B, A=3, B=2 и плановых коробов=2.
4. Скан неизвестного товара, пустой/повторный скан и неверное ручное количество не должны менять факт и должны давать заметное русское сообщение.
5. Ноль — допустимый фактический результат недостачи, но он обязан визуально считаться расхождением, а не «не заполнено».
6. Превышение плана — допустимый факт, но не должно проходить без явного расхождения и осознанного подтверждения.
7. Любая мутация проверяется после reload. Cancel должен реально отменять незавершённое действие, Back/Forward — не терять ориентацию.
8. Завершение выполняется один раз только на доказанном isolated документе. После него повторная кнопка должна исчезнуть/заблокироваться, а состояние — читаться с сервера.
9. Завершение приёмки создаёт on-hand в виртуальной зоне «Сортировка», но не делает товар доступным к резерву до размещения. В B03 проверяется только этот handoff, не раскладка.
10. Любой визуально не открытый экран/диалог получает `NOT_RUN`; отсутствие безопасного fixture — `BLOCKED_FIXTURE`.

## Инвентарь UI

- `/app/ff/reception`: populated queue, empty/loading, строка, статус, seller, lines, plan date, created date.
- Reception detail: номер документа, план коробов, дата, русский статус, close, waybill, строки `Заявлено/Принято`, ручное редактирование.
- «Скан приёмки»: ввод, Enter, кнопка, unknown/error snackbar, повторные сканы.
- Короба приёмки: create, row, fill dialog, box scan/manual +/- controls, close/dismiss, delete empty, delete non-empty protection, print controls (без реальной печати, если Browser print нельзя доказать безопасно).
- Расхождение: visual hint, completion confirmation dialog, cancel, confirm.
- После completion: success handoff message, locked fact/boxes, «Редактировать» до начала B04, queue transition.
- `/app/ff/sorting`: одна matching row, remaining qty=accepted total; detail reachability только для handoff, без distribution mutation.
- `/app/ff/products` или seller product read-back: в сортировке/на складе/доступно — только если exact synthetic products можно доказать без двусмысленности.

## Протокол поиска exact fixture

1. Снять populated очередь без клика по первой строке.
2. Отфильтровать кандидатов только визуальными полями queue: seller `B01 UX Seller 960724`, плановая дата, `Строк=2`, статус «Передано».
3. Если кандидатов несколько, открыть каждого по очереди без mutation и проверить detail: план коробов=2; обе строки имеют SKU suffix A/B и заявлено 3/2.
4. Зафиксировать human document number и внутренний `data-request-id` только как sanitized идентификатор evidence.
5. Любая несовпадающая заявка закрывается без изменения; завершение запрещено, пока совпадение не доказано одним detail.

## Stop boundary

Не выполнять WB sync, credential/key actions, операции чужих seller, создание/подтверждение внешней отгрузки, раскладку по ячейкам и проведение B04. Если exact submitted fixture уже изменён/исчез, destructive completion не выполняется; остальные экраны проверяются read-only, а gate получает `BLOCKED_FIXTURE`.
