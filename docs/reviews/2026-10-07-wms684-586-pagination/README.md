# Узкое независимое ревью пагинации WMS-684 / WMS-586 — FAIL

Проверен продуктовый SHA **4717552e1a59acb1746fdf5dd9b92b2af5c276b6** после отдельного test-before-fix **49ba6eb0c121c7f75e1b5a7f0668b35f315ca061**. Предыдущий независимый отчёт — [77efb37d5a6e60fdedbebb64bdb99cd1f60433d1](../2026-10-07-wms684-586-followup/README.md).

Прежний HTTP 500 для 64 строк устранён. Полнота текста, однократность количеств и итога подтверждены реальным API для 64 и 128 строк между обычными товарами. Однако **F1 остаётся открытым по двум подтверждённым дефектам новой пагинации: наложение последней строки имени на следующий товар и полностью пустые страницы при последовательных пустых переносах**. F2–F4 остаются PASS и не затронуты этим fix.

## F1.1 — [P2] Последний фрагмент занимает часть следующей строки товара

Место: [inbound_acceptance_act_service.py](../../../backend/app/services/inbound_acceptance_act_service.py), **строки 269–276, 369–375 и 388–394**. Нарушена читаемость WMS-586 R14 при продолжении длинной строки через страницы.

В реальном PDF завершённой приёмки три товара имеют план/факт 5/3, 6/4, 4/5. Среднее имя содержит 128 строк «Х», разделённых переводами строк; его длина ровно 255 символов, `ProductCreate` принимает его. Получены четыре страницы. На последней странице **последняя «Х» среднего товара пересекает название «Следующий товар»**. Разделитель строки проходит через нижнюю часть продолжающегося текста. Это видимый дефект на том же 128-строчном случае, который заявлен в handoff; сохранение всех символов и глобальные границы страницы его не исключают.

Точные координаты PDF (pt):

- Последняя «Х»: `[50.000, 271.675, 54.095, 281.478]`.
- Первая «С» следующего товара: `[50.000, 276.361, 54.507, 286.163]`.
- Пересечение прямоугольников: `[50.000, 276.361, 54.095, 281.478]` — высота около **5,117 pt**.

Доказательства: [pagination-128.pdf](pagination-128.pdf), [последняя страница](pagination-128-page-4.png), [увеличенная граница](pagination-128-boundary.png), [boundary-results.json](boundary-results.json), [boundary_probe.py](boundary_probe.py) и [его предметный отказ](reviewer-round3-boundary.log). В 64-строчном случае разделитель также пересекает нижнюю часть «Х63»: [увеличенная граница](pagination-64-boundary.png). Основной однозначный контрпример наложения двух названий — 128 строк.

`_pdf_row_fragment` возвращает высоту через `height - space`; вызывающий код использует её для разделителя и следующей строки. Измерение успешного размещения текста внутри страницы не гарантирует, что эта возвращённая высота покрывает фактическую нижнюю границу всех уже размещённых символов. В данном файле следующая строка начинается до окончания предыдущего текста. Нужен корректный размер последнего фрагмента с безопасным разделением строк; смена тестовых ожиданий или присвоение визуальной приёмки не устраняет наложение.

## F1.2 — [P2] Пустые фрагменты текста создают полностью пустые PDF-страницы

Место: тот же сервис, **строки 248–270 и 368–376**. Проверка продвижения опирается на количество потреблённых символов, а переход на следующую страницу выполняется даже после фрагмента, состоящего только из переводов строк.

Узкая проверка того же лимита: имя `"Х" + "\n" * 253 + "Я"` содержит **255 символов**, 254 строки, принимается текущим `ProductCreate` и сохраняется без изменения в Excel. Это проверка границы допустимого текста, не утверждение о частоте таких данных в работе операторов. Через настоящий API PDF и Excel возвращают 200; PDF содержит шесть страниц, **страницы 3, 4 и 5 полностью пустые**: нет ни извлечённого текста, ни графических объектов. Растр страницы 3 визуально белый. Сам текст, соседние товары, количества и итог при этом сохранены; дефект относится именно к ненужным пустым страницам.

Доказательства: [pagination-empty-lines.pdf](pagination-empty-lines.pdf), [Excel того же состояния](pagination-empty-lines.xlsx), [пустая страница 3](pagination-empty-lines-page-3.png), [empty-line-results.json](empty-line-results.json), [адресный API-отказ проверки](reviewer-round3-empty-lines.log). Проба в [pagination_api_probe.py](pagination_api_probe.py) использует изолированную pytest SQLite, проверяет допустимость имени, сохраняет реальные API-файлы и только затем проверяет отсутствие пустых страниц. Подмены функции рендера или HTTP-ответа нет.

Нужно избежать создания страниц для фрагментов, не содержащих видимых данных, сохранив полный текст, остальные поля и нормальное продолжение строки. Новый запрет на уже допустимые имена не требуется и не заменяет корректную пагинацию.

## Что прошло

**Два неизменённых regression-контракта PASS**: пятистрочное имя и новый HTTP-контракт 64 строк из 49ba6eb0. Реальный PDF вместо 500 возвращает 200, сохраняет текст, количества и итог. [Лог](reviewer-round3-contract.log).

**Адресная API-проверка 64/128 строк PASS по данным**: длинное имя помещено между «Предыдущий товар» и «Следующий товар», оба формата скачаны из одного состояния. 64 строки дают три страницы, 128 строк — четыре. На каждой из этих страниц есть данные; пустого хвоста нет. Все семь страниц просмотрены через `view_image`; затем границы последних фрагментов дополнительно просмотрены крупно, что выявило F1.1.

Проверены полные имена, артикулы, SKU и штрихкоды в исходных колонках: каждый реквизит каждого товара присутствует один раз. Все 64 уникальные строки имени присутствуют один раз и в исходном порядке; для второго случая присутствуют ровно 128 «Х». Колонки количества и номера строк дают точно:

| Колонка | Извлечено из реального PDF |
|---|---|
| Номер строки | `1, 2, 3` |
| План | `5, 6, 4, 15` |
| Факт | `3, 4, 5, 12` |
| Расхождение | `−2, −2, +1, −3` |

Единственный итог **15/12/−3** расположен на последней странице. Глобальных текстовых координат вне страницы нет. Это положительное доказательство полноты/однократности данных, **не доказательство отсутствия пересечения соседних строк**. Все координаты и исходные строки сохранены в [pagination-results.json](pagination-results.json); файлы — [64 PDF](pagination-64.pdf)/[Excel](pagination-64.xlsx) и [128 PDF](pagination-128.pdf)/[Excel](pagination-128.xlsx). [Лог API-пробы](reviewer-round3-pagination.log).
