## F1. Повтор запроса добавляет количество второй раз после промежуточного добавления другого оператора

**Место:** `backend/app/services/fbs_packing_box_service.py:519–525, 552–565`; хранение — `backend/app/models/fbs_packing_box.py:123–127`.

Сервер узнаёт повтор только по `last_idempotency_key` у текущей строки. Следующее осознанное добавление перезаписывает этот ключ. После этого повтор первого, уже выполненного запроса снова прибавляет количество. Замок поставки не спасает: ошибка воспроизводится при последовательных транзакциях.

**Воспроизведено на настоящем сервисе и SQLite в памяти**, с отдельной сессией и commit для каждого вызова. У позиции заказа количество 5, короб пуст. Запрос A добавляет 1, запрос B добавляет 1 в ту же позицию того же короба, затем повторяется исходный A с тем же телом и ключом:

```text
request=A quantity=1 last_key=A
request=B quantity=2 last_key=B
request=A quantity=3 last_key=A
```

Ожидание — 2, факт — 3. Это соответствует двум операторам: ответ A потерялся, пока первый оператор восстанавливает связь, второй добавил B; повтор A не является третьей физической укладкой. При меньшем остатке вместо повторного успешного ответа получится ошибочный `ozon_box_quantity_exceeded`.

**Почему дефект:** WMS-453 R6 требует узнавать повтор той же отправки после потери ответа; AGENTS.md §3 требует защиты от повторного применения запроса. Решение аналитика Д4 о хранении последнего ключа технически недостаточно для R6 при нескольких операторах. Это не новая продуктовая развилка и не основание запрещать второму оператору работу.

**Проверка исправления:** A → B → A должно оставлять 2; A → A — 1; новое осознанное добавление C — 3. Проверять через отдельные транзакции. Существующий `test_repeat_idempotency_key_is_a_no_op_and_new_key_adds_to_existing_row` проверяет только A → A → B и дефект не обнаруживает. Исправление должно сохранять возможность распознать уже применённый A после B, без блокировки обычного добавления.

**Блокирует:** да, WMS-453: сохранённая раскладка расходится с фактически выполненными действиями оператора.

## F2. Откат миграции молча превращает неполную раскладку в полную

**Место:** `backend/alembic/versions/20260917_0500_wms453_ozon_box_quantity.py:95–112`.

Downgrade запрещён только при нескольких строках одной позиции. Но новое допустимое состояние — 10 из 100 штук в единственном коробе — тоже нельзя представить в старой схеме: старая строка означает всю позицию целиком. Проверка `COUNT(*) > 1` такое состояние пропускает, после чего колонка количества удаляется.

**Воспроизведено выполнением настоящих upgrade/downgrade на SQLite в памяти:** позиция 100, одна строка состава; upgrade правильно заполняет 100; строка получает допустимое частичное количество 10; downgrade проходит; по старому правилу эта строка уже означает 100. Повторный upgrade окончательно записывает в неё 100:

```text
after_upgrade 100
actual_partial_quantity 10
downgrade_succeeded, old_code_quantity 100
remaining_rows 1
after_second_upgrade 100
```

Старый смысл строки подтверждён чтением базовой версии: `git diff 388f389b..HEAD -- backend/app/services/ozon_box_assembly_service.py` показывает замену `quantity=int(position.quantity)` на `quantity=int(item.quantity)`. Это потеря данных, а не только изменение отображения. Условие downgrade одинаково для SQLite и PostgreSQL; на PostgreSQL выполнение не заявляется.

**Почему дефект:** сохранность работы операторов по AGENTS.md §§1, 3 и смысл WMS-453 R1/R11. R11 и C14 явно требуют отказ при нескольких коробах, но такой отказ не покрывает все новые состояния, не представимые в старой схеме. Для воспроизведения не нужны повреждённые данные: «первые 10 из 100 в первом коробе» — прямой сценарий владельца.

**Проверка исправления:** откат с одной строкой 10/100 должен отказать до удаления индексов/колонок; с одной полной строкой 100/100 — пройти; при нескольких коробах — сохранить существующий отказ. Дополнить C14 и тест миграции этим случаем. Действующий тест откатывает только полную строку и не проверяет частичную одиночную.

**Блокирует:** да, безопасный выпуск WMS-453 с этой миграцией. Исправить защиту отката; ограничивать оператору раскладку не требуется.

## F3. Тест конкуренции общей корзинки ждёт событие, которое не может выставиться

**Место:** `backend/tests/test_wms455_shared_pool.py:588–608, 629–631`; фактическая сессия замка — `backend/app/services/fbs_stock_rule_service.py:767–775`.

Тест записывает `session.info['first'] = True` в сессию сохранения. Сервис создаёт отдельную `lock_session = AsyncSession(bind=session.bind)` и передаёт её в `marketplace_seller_lock`. Обёртка теста читает `info['first']` уже у этой другой сессии. Маркера там нет, поэтому `first_locked.set()` не выполняется, а `wait_for(first_locked.wait(), 10)` истекает до запуска второго сохранения.

**Подтверждение:** в пробном вызове реального `set_rule_for_products` передан тот же маркер в рабочую сессию; обёртка существующего замка вывела:

```text
caller session.info={'first': True}
lock marketplace=ozon session.info={}
lock marketplace=wb session.info={}
```

Проверка проводилась на SQLite и подтверждает передачу разных сессий; реальная конкуренция PostgreSQL не запускалась. Вывод о недостижимом событии следует из этой передачи и прочитанного условия строки 594. В текущем pytest тест пропущен из-за SQLite. При прохождении PostgreSQL-условия он не сможет выполнить заявленный сценарий C16: первым барьером будет тайм-аут ожидания события.

**Почему дефект:** WMS-455 C16 заявлен как проверка двух одновременных сохранений для R5/R6, но тест не запускает второе сохранение. Это дефект теста, а не установленная гонка рабочего сервиса.

**Проверка исправления:** привязать барьер к вызывающей операции/задаче, а не к другой сессии. Проверить, что первый вызов действительно удерживает замок, второй действительно стартует до его освобождения, оба завершаются, сохранены целые индивидуальные настройки. Вариант `(True, {})` в финальной проверке также не подтверждает сохранность исходных долей 60/40 при результате с включённым режимом.

**Блокирует:** подтверждение C16 и завершение технической проверки WMS-455. Сам по себе не доказывает дефект публикации или сохранения в production.
