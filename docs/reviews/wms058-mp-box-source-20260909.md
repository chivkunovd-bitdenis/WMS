# WMS-058: явный источник при наполнении МП-короба

Ветка `codex/wms058-mp-box-source` создана от `origin/etalon` в существующей
`.worktrees/wms394-kiz-ui`. Предыдущие отчёты WMS-275 сохранены в опубликованной
ветке `codex/wms394-kiz-ui`, коммиты `52f9f0c7` и `5b4f414e`.
Этот срез не входит в кандидат `7259d630`, который развёртывался параллельно.

## Исправленное поведение

В существующем диалоге «Наполнить короб» скан складского короба, грузоместа
или паллеты выбирает конкретный источник. Он не переносит его состав целиком.
Следующий скан товара передаёт `container_kind`, `container_id` и адрес при
включённом адресном хранении. Существующий небольшой чип показывает код тары;
скан или выбор другой ячейки и очистка чипа снимают выбор контейнера.
Новые колонки, большие элементы управления и дизайн FBS не добавлялись.

Расчёт доступного в выбранном источнике использует существующий `source.available`:
выбранная ячейка означает россыпь, выбранный контейнер — именно его остаток.
Сумма содержимого соседней тары не выдаётся за доступность россыпи. Очередь
сканов читает актуальный источник после завершения предыдущего скана, включая
случай, когда React ещё не успел перерисовать поле.

Сервер использует существующие `resolve_container_scan`, `validate_container`,
`resolve_container_location` и `available_pick_source_quantity`.
Проверяются tenant, склад, соответствие вида/ID контейнера, его сохранённое
место, товар в поставке и селлер. Явное противоречие location/container
возвращает HTTP 422. Пара kind/id обязательна целиком; случайного выбора
одного из нескольких источников нет.

`collect_into_box` передаёт точный container в проверку физической доступности,
выбор/создание allocation и `apply_marketplace_unload_pick`.
Россыпь и контейнер в одной ячейке остаются отдельными строками подбора.
Недостаток выбранного контейнера не восполняется россыпью, соседней тарой или
другой ячейкой.

Для уже подобранного, но ещё не разложенного товара scanner использует
существующий `add_manual_qty_to_box` / `_place_picked_into_box`. Он добавляет
строку короба без нового складского движения; только недостающее количество
идёт через подбор. Размещение сериализовано блокировкой существующей строки
поставки. Новых таблиц, журналов, резервов или складских счётчиков нет.
Локальный SQLite-прогон не доказывает поведение PostgreSQL-блокировки при гонке.

## Готовый короб и совместимость

Скан складского `WarehouseBox` теперь возвращает `kind=container`, а не пустой
успех `ready_box`. Прямой старый вызов разворачивания готового WarehouseBox
без реализованного чтения его состава получает существующую ошибку
`box_needs_location`, даже когда физический остаток в коробе ненулевой.
Состав не выдумывается.

Путь готового приёмочного короба `INB-…` с существующим подтверждением сохранён;
его прежний целевой тест также прошёл. Этот тест не доказывает все варианты
остатков приёмочного короба внутри тары: его исходная фикстура содержит россыпь.
Изменение не объявляет этот исторический путь полностью проверенным.
Клиент box-scan должен понимать новый ответ `kind=container`; веб-диалог
обновлён здесь, физический мобильный клиент отдельно не проверялся.

## Выполненные проверки

Три новых integration-теста проходят через настоящие HTTP-маршруты локального
ASGI-приложения, с отдельным SQLite `/tmp/wms058-mp-box-source.sqlite`.
Никакие production/staging или чужие базы не использовались. Фикстура создаёт
пять единиц: две в россыпи и три в коробе одной ячейки.

1. Скан короба только выбирает источник и не создаёт движения; затем по одной
   единице из россыпи и короба сохраняют разные allocations. Остатки равны
   соответственно 1 и 2.
2. После предварительного подбора трёх единиц из короба три скана в короб
   назначения дают количество 1 → 2 → 3. Остатки и число движений не меняются.
3. Неверная ячейка для контейнера и несуществующий контейнер получают 422;
   после исчерпания выбранного контейнера следующий скан отказывает, оставляя
   две единицы россыпи нетронутыми. Старое разворачивание WarehouseBox с
   ненулевым остатком получает ошибку вместо успеха с нулём.

Дополнительно выполнен существующий
`test_box_scan_ready_box_into_open_box_mp018`. Итог: **4 passed за 6,05 с**.
Пять предупреждений относятся к библиотечным SWIG-типам.
Первый запуск остановился на SQLite `unable to open database file` при создании
схемы; повтор с явно заданным `SQLITE_TMPDIR=/tmp` дошёл до проверок.
Тест неверного источника выявил недостающее сопоставление ошибки (500 вместо
422); оно исправлено, финальный прогон зелёный.

Команда целевого прогона из `backend`:

```sh
PYTHONDONTWRITEBYTECODE=1 SQLITE_TMPDIR=/tmp WMS_TEST_DATABASE_URL=sqlite+aiosqlite:////tmp/wms058-mp-box-source.sqlite /Users/deniscivkunov/Projects/WMS/backend/.venv/bin/python -m pytest tests/test_marketplace_unload_box_source.py tests/test_marketplace_unload_tsd_scan_contract.py::test_box_scan_ready_box_into_open_box_mp018 -q --tb=short -p no:cacheprovider
```

Ruff проходит для трёх изменённых backend-модулей и нового теста.
Mypy с `--cache-dir=/dev/null --follow-imports=silent` проходит для тех же четырёх
файлов. Frontend `npx tsc --noEmit -p tsconfig.app.json` и `npm run build` прошли
на существующем symlink node_modules, без установки зависимостей; Vite сообщил
обычное предупреждение о крупных чанках. Полный pytest не запускался.

## Граница проверки

После этой реализации браузер новой версии ещё не открыт: необходим отдельный
согласованный staging-деплой следующего выпуска. Предыдущие успешные замеры
WMS-275 и его 422 не выдаются за приёмку нового кода. Нужны собственный учебный
документ, скан выбранной тары → товара, очистка/смена источника, отказ исчерпанной
тары и скан уже подобранного с перечитыванием остатка и движений.
Production, чужие активные документы, внешняя передача WB, реальная печать и
физический ТСД в этом срезе не затрагивались.
