# WMS-058: явный источник при наполнении МП-короба

Ветка `codex/wms058-mp-box-source` создана от `origin/etalon` в существующей
`.worktrees/wms394-kiz-ui`. Предыдущие отчёты WMS-275 сохранены в опубликованной
ветке `codex/wms394-kiz-ui`, коммиты `52f9f0c7` и `5b4f414e`.
Этот срез не входит в кандидат `7259d630`, который развёртывался параллельно.

## Исправленное поведение

В существующем диалоге «Наполнить короб» скан складского короба, грузоместа
или паллеты выбирает конкретный источник. Он не переносит его состав целиком.
Следующий скан товара передаёт `container_kind`, `container_id` и адрес при
включённом адресном хранении. Существующий небольшой чип показывает код тары;
скан или выбор другой ячейки и очистка чипа снимают выбор контейнера.
Новые колонки, большие элементы управления и дизайн FBS не добавлялись.

Расчёт доступного в выбранном источнике использует существующий `source.available`:
выбранная ячейка означает россыпь, выбранный контейнер — именно его остаток.
Сумма содержимого соседней тары не выдаётся за доступность россыпи. Очередь
сканов читает актуальный источник после завершения предыдущего скана, включая
случай, когда React ещё не успел перерисовать поле.

Сервер использует существующие `resolve_container_scan`, `validate_container`,
`resolve_container_location` и `available_pick_source_quantity`.
Проверяются tenant, склад, соответствие вида/ID контейнера, его сохранённое
место, товар в поставке и селлер. Явное противоречие location/container
возвращает HTTP 422. Пара kind/id обязательна целиком; случайного выбора
одного из нескольких источников нет.

`collect_into_box` передаёт точный container в проверку физической доступности,
выбор/создание allocation и `apply_marketplace_unload_pick`.
Россыпь и контейнер в одной ячейке остаются отдельными строками подбора.
Недостаток выбранного контейнера не восполняется россыпью, соседней тарой или
другой ячейкой.

Для уже подобранного, но ещё не разложенного товара scanner использует
существующий `add_manual_qty_to_box` / `_place_picked_into_box`. Он добавляет
строку короба без нового складского движения; только недостающее количество
идёт через подбор. Размещение сериализовано блокировкой существующей строки
поставки. Новых таблиц, журналов, резервов или складских счётчиков нет.
Локальный SQLite-прогон не доказывает поведение PostgreSQL-блокировки при гонке.

## Готовый короб, атомарность и итог повторного review

Обычный scanner одинаково обрабатывает складской короб и приёмочный INB:
`kind=container` выбирает источник, затем скан товара снимает только указанное
количество. Специальный INB-перехват и подтверждение переноса целого состава
из обычного поля удалены. Отдельная публичная операция `/boxes/attach` остаётся
операцией целого короба.

Целый короб теперь читается по текущим положительным InventoryBalance с точными
`tenant/container_kind/container_id`, а не по историческим строкам распределения
приёмки. Проверяются его текущее место, товар/селлер/план и доступность общим
сервисом. Пустой контейнер даёт `box_empty`; содержимое соседней россыпи не
подставляется. Общий helper используется готовым коробом и привязкой короба,
две копии исторического распределения удалены.

Повторный review выявил реальную частичную запись: скан quantity=4 при одной
уже подобранной единице сначала сохранял эту единицу в короб, затем добор
трёх из источника с двумя единицами давал 422. Теперь `collect_into_box` и
`_place_picked_into_box` только делают flush. Завершение manual/scan, ready,
attach и copy выполняет сохранение после всех проверенных строк. Существующий
синхронизатор упаковки владеет финальным commit; если связанной задачи нет,
финализатор коммитит сам. Новых флагов транзакции, таблиц или API-режимов нет.
Первоначальные шесть вызовов collect проверены: два ready и два attach сведены
в общий current-contents helper, manual и copy сохранены с финализацией.
Copy передаёт kind/id существующей allocation. Ответы сохраняют загрузку
связанных product/lines до сериализации.

Обнаружен дополнительный ограниченный факт существующей приёмки: публичный
whole-box putaway сохраняет физический InventoryBalance в целевой ячейке,
но InboundIntakeBox.storage_location_id может остаться старой сортировкой.
Глобальный warehouse_map и приёмка этим срезом не менялись. Только MP box-source
выбирает адрес по DISTINCT положительным остаткам точного контейнера: один адрес
используется после tenant/warehouse-проверки, несколько дают отказ без угадывания.
Для пустой тары сохранён существующий resolver; проверка доступности по-прежнему
идёт исключительно по её kind/id, без добора россыпи. Это уточнение адреса,
а не новая формула свободного остатка. Остальные потребители старой INB-метаинформации
этим изменением не объявляются исправленными.

Первоначальное замечание review о возврате remove в россыпь не признано
достижимым в этом срезе: внешний remove разрешён в draft, внутренний collect
ожидает confirmed/collecting. Подменять состояние документа в тесте не стали.
Отмена всей МП-поставки по явному TASK-019 возвращает в сортировку; этот код
не менялся и не переопределялся.

## Выполненные проверки

Финальный целевой прогон: **6 passed за 16,10 с**, отдельный SQLite
`/tmp/wms058-mp-box-source.sqlite`, настоящее локальное ASGI-приложение и публичные
HTTP-маршруты. Production/staging и чужие базы не использовались. Пять
предупреждений относятся к библиотечным SWIG-типам.

1. Тест source-selection: скан короба не создаёт движения; отбор из россыпи и
   короба одной ячейки сохраняет разные allocations и точные остатки.
2. После предварительного подбора трёх единиц три скана в короб дают 1 → 2 → 3
   без изменения балансов и числа движений.
3. Неверная ячейка, отсутствующий и исчерпанный контейнер получают 422;
   две единицы соседней россыпи не используются.
4. Смешанный публичный scan quantity=4 при picked=1 и физическом container=2
   даёт 422; последующий GET видит пустой короб, прежнюю allocation=1,
   прежние балансы и число движений.
5. Настоящая приёмка через API, whole-box putaway четырёх единиц INB рядом с
   россыпью 20, скан INB → товара: INB 4 → 3, россыпь остаётся 20.
   Публичный `/boxes/attach` забирает текущие три; повтор на пустом INB
   получает 422 `box_empty`, россыпь остаётся 20.
6. Существующий `test_marketplace_unload_box_remove_copy_delete` прошёл после
   переноса финализации, включая свой прежний контракт копирования и удаления.

Команда финального прогона из корня worktree:

```sh
PYTHONDONTWRITEBYTECODE=1 SQLITE_TMPDIR=/tmp WMS_TEST_DATABASE_URL=sqlite+aiosqlite:////tmp/wms058-mp-box-source.sqlite /Users/deniscivkunov/Projects/WMS/backend/.venv/bin/python -m pytest backend/tests/test_marketplace_unload_box_source.py backend/tests/test_marketplace_unload_tsd_scan_contract.py::test_box_scan_ready_box_into_open_box_mp018 backend/tests/test_marketplace_unload_and_discrepancy_acts.py::test_marketplace_unload_box_remove_copy_delete -q --tb=short -p no:cacheprovider
```

Ruff проходит для изменённых backend-модулей и двух файлов тестов. Mypy с
`--cache-dir=/dev/null --follow-imports=silent` проходит для API, двух сервисов
и нового тестового файла. `npx tsc --noEmit -p tsconfig.app.json` и
`npm run build` прошли после изменения INB scanner на существующем symlink
node_modules, без установки зависимостей. Vite предупредил о крупных чанках.
Полный pytest и PostgreSQL-проверка гонок не запускались.

При промежуточном запуске диск заполнился до нуля ещё до выполнения pytest;
удалены только собственные регенерируемые frontend/dist и backend/.ruff_cache.
После освобождения места финальные проверки выполнены успешно.
