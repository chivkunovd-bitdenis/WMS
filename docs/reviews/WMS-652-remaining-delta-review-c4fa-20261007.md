# WMS-652: независимое ревью оставшейся дельты c4fa

**Вердикт: FAIL** для известного неизменяемого кандидата `c4faeb3a58c42e2d2e04bff790230532e8970b90`. Прежнее замечание R1 из `ee1bf745308489f83cc1e0b98103d60e647f158d` исправлено. Однако новая коррекция WMS-680 принимает полное имя, собранное из двух разных строк настоящего PDF, хотя ни одна ячейка не содержит этого имени. Финальный кандидат и полный шаблон активации ещё не предъявлены.

Это та же независимая сессия Sol 6.1 high. Сохранены прежние отчёты и их границы; неизменённые проверки ef154…6da повторно не запускались. Применимые AGENTS и полные owner/failure libraries сохранены из исходной сессии. Код новой дельты прочитан только из Git-объектов `6da0eb63…` → `c4faeb3a…`; dirty-файлы интегратора не проверялись как опубликованный код. В собственной ветке изменены только этот отчёт и review evidence.

## R2 — блокирующий дефект PDF-контракта WMS-680

В `frontend/src/utils/wms680PrintGeometry.test.ts`, функция `pdfTextFragments`, строки 258–273 кандидата, последовательные слова соединяются при совпадении левой координаты и неубывании вертикальной координаты. Ограничения принадлежности одной строке/ячейке нет. `expectPdfTextFragments` и полная `assertRealPdfGeometry` принимают найденное соединение как полное имя в одной ячейке. Проверка правой границы до «Артикул» не определяет строку товара.

Независимое воспроизведение использовало существующий Chrome и настоящий `pdftotext -bbox-layout`, а не выдуманную квитанцию. В HTML созданы две отдельные строки таблицы: первая содержит `PACKAGING-LONG-`, вторая — `NAME-01-680`. Остальные колонки пусты, заголовки «Артикул», «Цвет», «Размер» присутствуют. В полученном PDF обе части имеют x=37.499998, но первая заканчивается на y=67.475095, а вторая начинается на y=189.244621: расстояние между ними **121.769526 пункта**. Ни одна ячейка не содержит `PACKAGING-LONG-NAME-01-680`.

Несмотря на это, **полная функция проверки PDF-геометрии из точного Git blob c4fa принимает PDF**. Старый помощник из 6da на том же PDF отклоняет отсутствие полного имени. Дополнительные чистые проверки подтверждают: соседние переносимые фрагменты принимаются, одиночный обрезок отклоняется, суффикс в другой колонке отклоняется, но суффикс в другой строке той же колонки молча принимается. Значит, новая канарейка удаления последнего фрагмента покрывает один обрезок, но не покрывает introduced объединение чужих строк. Это противоречит заявленному условию полного имени внутри собственной физической ячейки и ослабляет отрицательную защиту.

Нужно сохранить приём полного перенесённого имени внутри его ячейки и отказ имени, полученного объединением разных строк/ячеек, при сохранении остальных geometry/rows проверок. Исправление принадлежит исполнителю; ревьюер его не вносил.

Реальные [HTML](../evidence/WMS-652/remaining-review-c4fa-20261007/cross-row.html), [PDF](../evidence/WMS-652/remaining-review-c4fa-20261007/cross-row.pdf), XML координат, точные фрагменты и воспроизводимые скрипты сохранены в [review evidence](../evidence/WMS-652/remaining-review-c4fa-20261007/README.md). Созданный ревьюером Chrome остановлен с ожиданием завершения; удалён только его собственный профиль. Нормальные 7+3 результатов исполнителя из `c4fa` прочитаны, но они не опровергают этот дополнительный отрицательный случай. Полный их повтор не требовался для подтверждения дефекта.

## Закрытие прежнего R1 и остальные узкие проверки

Selector в `09456c10e84a2d15d2643fe3ab13a4e8b69a25b9` извлекает точные WMS-IDs из всего заголовка. Обе ранее принятые ошибочные формы теперь отклоняют запрещённый файл; `WMS-6840` не принимается за WMS-684. Собственный адресный запуск на c4fa: **7 PASS**, включая старые четыре случая, две canaries прежнего FAIL и отрицательный prefix-collision. Четыре прежних тестовых определения не изменены. Чужой коммит при объединении ветвей по-прежнему разрешён; allowlist продуктовых путей и проверка защищённых обработчиков не расширены. **R1 закрыт**.

Коррекция `5868c3b1300d0969bf4283b5df18635eec9481f2` следует явному аналитическому уточнению `683a820fd11a144f73e5743ebed201654308071c`. Сохранены все **19 DOM + 5 PDF = 24 прежних случая**, их названия и single/group параметры. Только утверждённая структура стала 12 колонками: собственный артикул отделён от товара, цвет остаётся индексом 4, размер перенесён на 5, сдвинуты последующие индексы. Проверки значений WB/Ozon, заказов/штрихкодов, seller/product aggregation, количества, fallback, escaping, read-only API и явного повтора не удалены. Для компактных колонок добавлены относительные ограничения ширин. В renderer изменены ровно число колонок 11→12 и текст соответствующей ошибки; SHA-256 точного HTML, совпадение артефактов, PDF bbox, страницы и принадлежность одной строке сохранены по байтам.

Опубликованное `24f0ad3cc…` описывает 5/5 реальных PDF с хешами HTML/PDF и честно не объявляет зависший DOM-прогон успешным. Ревьюер этот реальный пятислучайный прогон заново не выполнял. Найденный отдельно сырой Linux JSON с пятью PASS имеет сопроводительный source `9f96c0c53fa82c5343d4640eac59c1b886f640ab`; его тестовый blob отличается от c4fa, поэтому он **не использован как доказательство нового 5868**. Такое ограничение сохранено вместе с provenance, вместо подмены старого receipt новым.

В seller-info correction `88ec22d59…` прежние проверки одного обращения seller-info, реквизитов и одного journal event сохранены. Handler считает seller-info только на его точном пути; отдельно требует два taxonomy GET в точном порядке, одинаковый исходный auth и точные limit/offset второго GET. Неизвестный путь отклоняется. Остальные восемь тестовых определений, включая параметрические случаи, совпадают с 6da. Опубликованное `17b0d75e…` содержит результат 13 PASS; собственный повтор этих backend-тестов здесь не заявляется.

Ожидание завершения собственного Chrome перед удалением его профиля в 4ed0 прочитано отдельно от дефекта объединения слов: удаление чужих профилей, массовый kill, новый skip или bypass в этой дельте не появились.

## Политика, P/S и ещё не предъявленная финальная дельта

Политика c4fa сохраняет все исходные **1146 IDs и 18 report/format/exact привязок** SOURCE `0151a555ac429957d0eee591317cc4326e909dfd`, а также все IDs 6da. Текущие числа: **262 пути / 23 suite / 1644 cases**. Добавлены пять scope IDs и четыре ранее отсутствовавших C10 IDs. Прежние три несовпадающих хеша исправлены; теперь в этом снимке расходится только хеш `frontend/src/utils/wms680PrintGeometry.test.ts`, и новая PDF-canary ещё не зарегистрирована. Это заранее объявленный остаток финального замыкания, отдельно от R2.

Предложенная P `5868c3b…` действительно имеет те же продуктовые Git-пути и bytes, что c4fa, согласно существующему неизменённому классификатору: включая уже проверенную no-op migration и новый test renderer. Но это проверка соответствия предложенной ссылки, не активация P и не PASS нового PDF-контракта.

ROOT handoff получен со статусом **pending**, `final_candidate: null`, `proposed_P: null`. Он перечисляет ещё не опубликованные 684 async harness, изолированный PostgreSQL producer 658 и точную 680 activation template. Указанный template-path отсутствует в Git c4fa. Доступный `proposed-final-P-S.json` — лишь предложение полей: в нём нет окончательного exact before/after/pure-commit edge и полного механического diff для последней дельты. Поэтому **финальный кандидат, 684/658 изменения и детерминированный post-PASS шаблон не проверены и не одобрены**. Будущий SHA отчёта не выдуман и не подставлен. Активация на основании этого FAIL недопустима; P ≠ последующая S остаётся обязательным условием.

Не заявляются полный CI, main/etalon bootstrap, production, deploy или операционная приёмка WMS-675. После отдельного исправления R2 и публикации оставшейся дельты нужен точный SHA и полный ограниченный template. Неизменённые принятые части повторять не требуется.
