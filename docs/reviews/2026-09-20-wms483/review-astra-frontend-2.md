# WMS-483 · повторное перекрёстное ревью интерфейса

Ревьюер: тот же отдельный агент gpt-6-astra, high; проверен коммит `7fbbf39984a11fa6e86871a7ba27ed99d29180cc` на чтение, без изменения файлов, production или WB.

**Вердикт: FAIL.** Оба замечания первого ревью закрыты: `fbsRuleApi.ts` передаёт `units_mode` и `units_by_warehouse` с явным нулём, а групповой запрос вкладывает правило в `{ product_ids, rule }`. Ответ об ошибке возвращается в существующее окно без потери введённых данных.

Остаётся **P2 · несовпадение ключа склада**. `FfProductsFbsPage.tsx:166` создаёт ID строки WB как `"123"`, а `toRule` на строке 91 переносит ответ API без нормализации. Когда у одного продавца есть WB №123 и Ozon №123, сервер намеренно выдаёт `"wb:123"` и `"ozon:123"`. Сохранённый WB 0 или положительный лимит выглядит пустым. Ввод нового 0 добавляет `"123"` и PUT получает `warehouse_id_collision` в `fbs_stock_rule_service.py:265`; очистка поля также не удаляет скрытый `"wb:123"`. Нарушены R7/C7/C11. Нужно согласовать чтение, ID строк и запись, сохранив невидимое на этом экране правило Ozon; простого префикса только при отправке недостаточно.

Новые тесты подтверждают форму тела запроса, но не покрывают одинаковый номер у WB/Ozon. Браузерный сценарий с API, production и живой WB не выполнялись. Это техническое ревью, не приёмка аналитика.
