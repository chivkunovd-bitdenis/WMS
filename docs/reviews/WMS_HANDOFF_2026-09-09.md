## 1. С чего начать прямо сейчас

Последнее поручение владельца: **«ну так надо доделать»** после обнаружения, что в Android-приложении отсутствует вызов финальной передачи поставки в WB. Затем он попросил этот хэндoff. **Код этой доработки ещё не написан.** Не нужно снова спрашивать, делать ли её.

Начни с WMS-401: подключи финальную передачу из мобильного экрана к существующему серверному процессу, которым пользуется веб. Повтори его обработку предварительного подтверждения, ключа защиты от повторной операции, ошибок и неопределённого результата WB. Не создавай новую серверную механику отгрузки, начисления или списания. Проверяй фактические вызовы из экрана, а не только объявления в интерфейсе API.

После этого — целевые тесты, сборка APK, настоящий проход в эмуляторе на собственной учебной поставке: передача, результат, повтор без повторного списания. Не передавать рабочую клиентскую поставку ради теста. Пользователь сейчас может самостоятельно работать в оставленном эмуляторе: сначала проверить его экран и не менять документ у него под руками.

Следующий мобильный пункт — WMS-412, обновление приложения по кнопке. Запрос записан, код не начат. Обсуждён простой процесс: скачать APK на ТСД → штатное подтверждение Android → обновить поверх старого приложения с сохранением данных. Оценка владельцу была 2–4 часа, это предварительная оценка, не выполненная работа.

Параллельные задачи не отменены, но они не должны задерживать выпуск уже проверенных основных исправлений. На момент передачи **готовой новой серверной пачки, ожидающей production, в текущем прогоне не установлено**: последний проверенный серверный срез уже выпущен. Старые открытые PR не являются автоматически очередью на выкладку.

## 2. Непереговорные требования владельца

- Не ломать ни один участок ФБС, не вводить блокировки этапов. Подбор, упаковка, стикеры, метаданные и короба не являются разрешениями на навигацию.
- Упаковка — признак выполненной работы. Не меняет склад, не списывает товар, не двигает количество между «упаковано» и «неупаковано», не создаёт резервы и не блокирует оператора.
- Передача маркетплейсу сохраняет существующую защиту повторов и единичное списание. Ошибка или неизвестный результат вызова не означают подтверждённую передачу.
- Веб-дизайн не менять. Только точечные изменения, прямо описанные владельцем. Мобильные экраны можно доделывать в рамках его мобильной постановки. Дизайн чата от Opus не переделывать по своему вкусу.
- Не плодить сущности. Использовать существующие методы и данные; новые таблицы требуют обоснования и решения по правилам проекта. Архитектуру расчётов WMS-408 до утверждения не реализовывать.
- Локально — только затронутые проверки; полный набор в CI. Не повторять полные CI и оплачиваемые ревью одного и того же среза.
- Владелец отдельно пожаловался на расход Opus. Последний сохранённый режим: **не запускать новые полные Opus-ревью без нового прямого поручения**, использовать уже полученные замечания и целевые проверки. Это уточняет прежние общие просьбы «Opus Max перед каждым выпуском».
- Проверять UI руками. Код/API/тесты не выдавать за нажатую кнопку. Отличать доказанный вызов интеграции от принятия операции настоящей площадкой.
- Доступ искать самостоятельно в согласованном проектном контексте. Не просить владельца каждый раз открывать staging. При этом не открывать кабинеты ключей, не выпускать/менять/отзывать секреты без конкретного прямого поручения; не выводить их в чат/логи/Git.
- Готовый результат сохранять отдельным commit и push. Деплой доказывать отдельно по SHA работающей сборки. Не захватывать чужие изменения и не делать произвольный merge в main.

### Какие цепочки действительно подключены

Сверено по файлам текущего APK и серверного исходника, входящего в production:

- `android/app/src/main/java/ru/wms/tsd/features/fbs/FbsScreens.kt`: реальные обработчики экранов.
- `.../features/fbs/FbsViewModel.kt`: вызовы сервера и обработка результатов.
- `.../core/api/fbs/FbsApi.kt`: маршруты Retrofit.
- `.../core/api/ApiProvider.kt`: общий клиент, настроенный адрес WMS и существующая авторизация. Прямого токена WB в телефоне нет.

Получение заказов/поставок, создание поставки, добавление заказов, упаковка, ЧЗ, короба и запросы этикеток подключены к серверу WMS. Скан подбора идёт через общий `/operations/fbs-supplies/{id}/pick/scan`, который вызывает `fbs_picking_service.pick_scan`. Нельзя утверждать, что буквально каждый мобильный маршрут совпадает с каждой веб-кнопкой: веб также использует отдельные scan-location/scan-product. Общая складская логика остаётся на сервере.

ЧЗ: `FbsViewModel.commitAction` → `FbsApi.commitKiz` → `POST /operations/fbs-orders/kiz/commit` → `backend/app/api/fbs_kiz.py:commit_fbs_order_kiz` → `fbs_kiz_service.commit_kiz_pairs` → `_commit_one_kiz_pair` → `fbs_marking_service.attach_order_meta_to_wb_and_sync` → `wildberries_client.put_marketplace_order_meta` → **PUT `/api/v3/orders/{order_id}/meta/sgtin`**, затем чтение результата WB. Веб `FfFbsSupplyWorkspace`/`FbsKizScanDialog` используют тот же commit endpoint. В учебной среде внешний адрес/режим задаётся сервером; тестовый WB не доказывает принятие настоящим WB.

**Недоделка финальной передачи:** `deliveryPreflight`, `deliver`, `syncTracking` объявлены в `FbsApi.kt`, но поиск по всему `android/app/src/main` обнаружил только объявления. `FbsSupplyScreen` содержит ровно три перехода: pick/pack/boxes. Нет кнопки и ViewModel-вызова передачи.

Готовый веб-образец: `frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx`, обработчик `deliver` около строки949; `frontend/src/screens/v2/fbsApi.ts`, `deliverFbsSupply` около1090. Сервер: `backend/app/api/fbs_supplies.py:deliver_fbs_supply` → `fbs_shipment_service.deliver_supply` → `wildberries_client.deliver_marketplace_supply` → PATCH WB `/api/v3/supplies/{id}/deliver`. Подключить этот процесс; не переписывать его.

Ближайший результат — новая сохранённая сборка APK, в которой владелец сможет из поставки выполнить существующую передачу WB, увидеть понятный результат и повторно открыть состояние. В статусе всегда разделять: код написан → commit → опубликован безопасный исходник → APK собран → экран проверен → серверный runtime → реальная площадка/физическое устройство. Нельзя опять отвечать «всё подключено», обнаружив только объявление Retrofit-метода. Нельзя откладывать чтение методов под предлогом того, что пока не проверена реальная отгрузка: эти два вопроса проверяются отдельно.
