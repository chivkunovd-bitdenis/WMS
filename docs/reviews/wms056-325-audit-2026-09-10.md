# WMS-056 + WMS-325 · Extending the existing audit trail

## Продолжение Astra, 10.09.2026

Исходный отчёт ниже описывает предыдущий срез и неверно сужает WMS-325 до прав: исходная постановка требует автора для каждого изменения данных. Полного покрытия всех мутаций этот срез не доказывает, задача остаётся частичной.

Root обнаружил, что записанный staff_user нельзя запросить через публичный API (Literal исключал тип). Тип добавлен с прежним доступом только FF-admin и фильтром tenant; HTTP-тест доказывает автора, before/after и пустой ответ для другого tenant. Для четырёх staff create/update точек actor_user_id теперь берётся из уже проверенного acting_user, а не теряется при сервисном вызове без HTTP ContextVar. Изменения прав перечитывают пользователя/права под блокировкой перед снимком before.

Изменение ставки упаковки также добавлено в тот же DocumentEvent: проверенный acting_user, before/after в копейках, без дубля при повторе; расчёт ставки не изменён. Локальные синтетические тесты: 23 passed, 1 skipped (PostgreSQL-only существующая проверка), scoped 6 файлов; ruff check backend PASS; mypy . PASS (436 файлов). Производственных данных и внешних настроек не касались. Независимое review нового diff, полная инвентаризация прочих мутаций и выпуск ещё не выполнены.

## Что взяли за существующий аудит

Каноническая append-only таблица —
[`DocumentEvent`](../../backend/app/models/document_event.py) (модель
`DocumentEvent`, `document_type` + `document_id` + `event_type` +
`actor_user_id` + `source` + `occurred_at` + `payload_json`). Актор берётся
из проверенного JWT через глобальный middleware
[`DocumentEventActorMiddleware`](../../backend/app/services/document_event_service.py)
и хранится в `ContextVar`. Именно из этого источника мы дёргаем `acting_user`
в новых точках — без параллельной таблицы, без нового счётчика.

Никаких новых таблиц не заведено. В модели `DocumentEvent` добавлены только
строковые константы: тип документа `staff_user`, три новых события
(`tare_line_qty_changed`, `permissions_changed`, `staff_user_created`). Схема
таблицы не поменялась → alembic-миграция не нужна.

## WMS-056 · снятие из приёмочной тары

Точка вставки — существующая граница правки состава тары, тот же коммит-момент,
что и физическое изменение строки.

| Путь | Файл (worktree) | Ссылка |
| --- | --- | --- |
| Ручное «квантование» короба (PUT `.../boxes/{box_id}/lines/{product_id}`) | [`inbound_intake_box_service.py:set_product_quantity_in_open_box`](../../backend/app/services/inbound_intake_box_service.py) | `qty=0 → session.delete(line)`; до commit пишем `EVENT_TARE_LINE_QTY_CHANGED` через `_record_tare_edit` |
| Скан +1 в открытый короб (product_id-hint путь и barcode-путь) | [`inbound_intake_box_service.py:scan_product_into_box`](../../backend/app/services/inbound_intake_box_service.py) | обе ветки пишут qty_before/qty_after |
| Ручное «квантование» грузоместа (PUT `.../cargo-places/{place_id}/lines/{product_id}`) | [`inbound_cargo_place_service.py:set_line_quantity`](../../backend/app/services/inbound_cargo_place_service.py) | `qty=0 → session.delete(line)`; до commit пишем `EVENT_TARE_LINE_QTY_CHANGED` |

`payload_json` содержит `container_kind` (`box|cargo_place`), `container_id`
(UUID), `qty_before`, `qty_after`. `product_id` пишется в отдельное поле
события, `qty` — `qty_after`, `actor_user_id` — из JWT, `occurred_at` — время
события UTC.

Что осталось «out-of-scope, потому что WMS-056 сам по себе не про это»:

- Кнопка «Разложить в ячейку» (putaway) — идёт через `InventoryBalance`
  движение, у которого автор уже есть (WMS-325 частично закрыт по документам и
  движениям). Не трогаем.
- Пересечение состава на границе «переоткрытия» короба (`intake_reopened_at`) —
  сам по себе флаг, а не редактирование состава; пишется отдельным событием на
  верхнем документе, здесь не нужен.

## WMS-325 · логирование смен прав сотрудника

Enumerated card mutations (что перечислено в источнике постановки WMS-325 и
её эталонных evidence-ссылках):

| Мутация | Endpoint / сервис | Статус | Файл |
| --- | --- | --- | --- |
| PATCH прав FF-сотрудника | `PATCH /auth/staff-accounts/{id}/permissions` → `update_staff_permissions` | fixed | [`staff_permissions_service.py`](../../backend/app/services/staff_permissions_service.py) |
| PATCH прав seller-сотрудника | `PATCH /auth/seller-staff-accounts/{id}/permissions` → `update_seller_staff_permissions` | fixed | [`seller_staff_permissions_service.py`](../../backend/app/services/seller_staff_permissions_service.py) |
| Создание FF-сотрудника (первичный набор прав) | `POST /auth/staff-accounts` → `create_staff_user` | fixed | [`auth_service.py`](../../backend/app/services/auth_service.py) |
| Создание seller-сотрудника (первичный набор прав) | `POST /auth/seller-staff-accounts` → `create_seller_staff_user` | fixed | [`seller_staff_permissions_service.py`](../../backend/app/services/seller_staff_permissions_service.py) |

Все четыре пишут одну строку в существующий `document_event`:

- `document_type = "staff_user"`, `document_id = target_user_id`
- `event_type ∈ {permissions_changed, staff_user_created}`
- `actor_user_id` — из JWT-контекста (`_actor_context.get()`)
- `payload_json = {role, target_user_id, acting_user_id, before, after}`

Мутации, которые формально касаются «сотрудников», но НЕ прав, — оставлены
`out-of-scope` этого лейна:

| Мутация | Endpoint | Почему не тут |
| --- | --- | --- |
| PATCH ставки упаковки FF-сотрудника | `PATCH /auth/staff-accounts/{id}/packaging-rate` → `update_staff_packaging_rate` | биллинговая ставка, не право. Отдельный TODO WMS-325 при желании расширить журнал на биллинговые ставки. |
| Регистрация нового ФФ (админа) | `POST /auth/register` → `register_fulfillment` | у первого админа нет `acting_user`, событие «созданный сам себе» бесполезно; фиксируется существующим tenant-created flow (не трогаем). |
| Смена пароля / инвайт-ссылка / login | `POST /auth/set-password`, `POST /auth/login` | это аутентификация, не права. |
| Массовое отзыв прав при `delete_staff` | В сервисах не найдено (нет удаления учёток) | нет мутации — нет пробела. |

Единственный «remaining gap», не закрытый этой веткой, — расширение того же
`document_event` на изменение ставки упаковки (`packaging_rate_kopecks`). Это
не право, поэтому явно не входит в текст WMS-325; заводить отдельное WMS
не стал — при желании реализовать, точка вставки уже готова: `update_staff_packaging_rate`
+ вызов `record_document_event_safely(..., event_type=<новое>, payload_json={before, after})`.

## Границы честности

- Существующая рабочая БД (production) в этом заходе не читалась и не
  проверялась; вывод про «строк-историю снятий сейчас нет» опирается только
  на код и evidence-ссылки из карточки WMS-056.
- Alembic-миграция не добавлялась: схема `document_event` не менялась. Если
  прод сейчас работает без первой миграции document_event — это отдельный
  риск, вне лейна.
- Браузер не открывал: точки правки по коду.
- Ограничение на количество/дубликаты событий: `record_document_event_safely`
  проглатывает ошибки записи (best-effort observer) — если запись аудита
  сорвётся, складская операция не откатывается. Это соответствует уже
  зашитой политике аудита (см. `document_event_service._write_rows_safely`).

## WMS-417: проверенный actor, 10.09 09:41 МСК

Middleware больше не разбирает JWT повторно: get_current_user устанавливает
actor после проверки токена, tenant и подписки. Это закрывает воспроизведённый
разный выбор первого/последнего Authorization при дублированном заголовке.
На двух действительных токенах разных tenants запрос и событие принадлежат
одному первому пользователю. Middleware очищает контекст после запроса, фоновые
задачи сохраняют SYSTEM. Известный acting_user при создании сотрудника/правках
FF и seller permissions явно даёт SOURCE_USER, независимо от внешнего контекста.
История сортируется также по id для устойчивого порядка равных timestamps.

Ruff/mypy436 PASS. В первоначальном scoped прогоне 15passed,1PGskip и один отказ
нового теста из-за отсутствующего planned_box_count в synthetic fixture. Fixture
исправлена, целевой duplicate-header тест PASS. Затем на отдельной PostgreSQL
wms325_actor_20260910 четыре целевых сценария PASS: duplicate Authorization,
настоящий триггер с изоляцией его сбоя, direct API transition и explicit staff
actor из system context. Клиентские данные и секреты не использованы.

Замечание Opus о GUC, якобы запрещающем INSERT audit row, опровергнуто чтением
миграции: условие относится к пропуску системного status UPDATE trigger, не INSERT.
Дополнительный обход GUC не добавлен. Требование ограничивать управляющего
сотрудника его собственными операционными правами не вводилось молча: существующее
право управления сотрудниками отдельно. Полная инвентаризация всех WMS325 mutations,
независимое ревью, CI/deploy/browser ещё не приняты.
