## Подтверждённый дефект

**Пустой (или пробельный) `idempotency_key` сервер принимает как полноценный ключ попытки**

**Severity:** средняя. В сегодняшнем production не стреляет — текущий Android ключ вообще не шлёт. Но API его явно разрешает, а закрывать дыру надо до того, как мобильный клиент начнёт ключ передавать, то есть прямо сейчас, в этой же задаче.

**Триггер.** Клиент отправляет `POST /operations/packaging-tasks/{task}/lines/{line}/pack` с телом `{"quantity": 1, "idempotency_key": ""}` (или `" "`). Схема это позволяет: `backend/app/api/packaging_tasks.py:54` задаёт только `max_length=128`, без `min_length`.

**Что наблюдается (воспроизведено мной на реальном PostgreSQL).** Оператор физически упаковывает три штуки, три раза нажимает подтверждение, три раза получает `HTTP 200` — а сервер держит единицу и не двигается:

```
operator packs real unit 1: HTTP 200, server qty_packed=1
operator packs real unit 2: HTTP 200, server qty_packed=1
operator packs real unit 3: HTTP 200, server qty_packed=1
complete after 3 real units: HTTP 422 detail=packaging_incomplete
```

То есть человек не просто теряет учтённую работу — он ещё и не может закрыть задание, потому что `is_task_complete` считает по `qty_packed_in_task` (`packaging_task_service.py:177-192`), а сдельный расчёт сотрудника берёт оттуда же (`staff_packaging_billing_service.py:96-103`). Вторым эффектом ключ выжигается на весь тенант: после первого использования `""` любой другой документ с тем же пустым ключом получает жёсткий отказ — в моём прогоне оба независимых задания вернули `409 idempotency_conflict`.

**Где.** `backend/app/services/packaging_task_service.py:911-912` — условие `if idempotency_key is not None:` и следом `uuid.uuid5(tenant_id, f"pack-progress:{idempotency_key}")`. Пустая строка проходит проверку «не None», и все такие запросы тенанта схлопываются в один и тот же идентификатор события. Соседняя FBS-ветка того же самого эндпойнта ведёт себя противоположно и правильно: `fbs_packaging_integration_service.py:622` делает `base_key = idempotency_key or str(uuid.uuid4())`, то есть пустую строку считает отсутствием ключа. Одно поле одного API трактуется двумя ветками по-разному.

**Минимальное воспроизведение.** Создать обычное (не FBS) задание упаковки на 3 штуки и дважды отправить `{"quantity": 1, "idempotency_key": ""}` на одну строку. Ожидание: 1, потом 2. Факт: 1 и 1, оба ответа 200.

**Требуемое исправление.** Привести non-FBS ветку к семантике соседней: перед вычислением `event_id` нормализовать ключ, например `key = (idempotency_key or "").strip() or None`, и дальше работать с `key`. Пустой ключ должен означать «идентичности попытки нет», как и `null`. Дополнительно можно поставить `min_length=1` в схеме, но главное — сервис, потому что он вызывается и напрямую.

## Что в патче проверено и претензий не вызывает

Выбор хранилища идентичности правильный по духу правил проекта: новой таблицы, колонки и журнала не заведено, распиской о выполненной работе служит уже существующее `PackagingTaskEvent`, а его `id` вычисляется детерминированно из тенанта и ключа. Второго источника количества не появилось.

Защита от гонки построена честно: сначала advisory-lock (замок уровня сессии PostgreSQL, который держится до конца транзакции) по ключу, затем `SELECT ... FOR UPDATE` по строке задания, и только после этого перечитывание документа. Тонкое место здесь — перечитывание могло бы вернуть устаревшие объекты из кэша сессии SQLAlchemy, но `get_task` объявлен с `populate_existing=True` (`packaging_task_service.py:268`), поэтому значения действительно обновляются после чужого коммита. Именно на этом держится сценарий C7 «два независимых ключа на последнюю штуку»: второй запрос видит остаток 0 и получает штатный отказ, а не пакует сверх потребности.

Разбор конфликта соответствует R6: чужое количество, чужая строка, чужой документ, другой автор или другое действие дают `409 idempotency_conflict` (`packaging_task_service.py:929-939`, маппинг в `api/packaging_tasks.py:339`), а не ложный успех. Тенанты разделены самой конструкцией идентификатора — пространство имён uuid5 это `tenant_id`, поэтому чужую расписку прочитать нечем.

Деньги патч не трогает: на повторе биллинг не вызывается вовсе, а сам `finalize_task_billing` выходит сразу, пока задание не переведено в `done` (`staff_packaging_billing_service.py:76-79`), так что факт упаковки по-прежнему не означает новой платы селлеру. Дублирование факта операции невозможно и на втором рубеже — `write_operation_fact` дедуплицирует по `source_event_id` (`operation_fact_service.py:368-374`).

Повтор после завершения и после отмены ведёт себя так, как заявлено: отмена не удаляет событие, а проставляет `reversed_at` (`packaging_task_service.py:1155-1157`), поэтому повторная доставка старого запроса возвращает текущее состояние документа и не воскрешает отменённую работу. Совместимость вызывающего без ключа сохранена — я это видел и в тесте, и в собственном зонде: без ключа два подтверждения дают 1 и 2, как и раньше.

## Границы этого PASS

Проверен только серверный D1 и требования R6/C6/C7/C14. **Сквозной D1 не закрыт**, и это не претензия к патчу: мобильный клиент по-прежнему шлёт `PackProgressIn(quantity = qty)` без ключа (`mobile/.../OutboundAssemblyViewModel.kt:208`), так что до android-части потерянный ответ всё ещё удвоит работу. Постановке Android важно передать: ключ должен быть уникальным на попытку (UUID), стабильным при ретраях и не пустым — трактовка ключа сделана в пределах тенанта, поэтому повторно используемые «1», «2» дадут законной работе 409.

Рядом остаётся однотипная незакрытая дыра в `/scan`: `record_pack_scan` ключ не принимает и не передаёт вовсе. Требование R6 сформулировано про `/pack`, мобильный клиент сканером не пакует, поэтому дефектом этого патча я это не считаю — фиксирую как известную границу.

Не проверял и не выдаю за проверенное: «Расчёты» и отчёт (C15/C16), приёмку, отгрузку ФБО, передачу FBS, Ozon, авторство в UI — по поручению это после 440/441/443/445. Браузер и эмулятор не открывал: объём чисто серверный. Конкурентность гарантируется только на PostgreSQL — на SQLite ни advisory-, ни строчного замка нет, но это только тестовый контур. Про всю WMS-444 никакого вывода не делаю: задача не принята и не выложена.
