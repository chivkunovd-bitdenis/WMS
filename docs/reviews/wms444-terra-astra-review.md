## P1-2. Старые документы с правомерно готовой частью становятся новой оплачиваемой работой

**Место:** миграция `20260913_0305_wms444_mp_box_source.py:27–33` создаёт оба поля как NOT NULL DEFAULT 0; `backend/app/services/packaging_task_service.py:699–711` считает ноль достоверным происхождением и безусловно заменяет существующие `qty_confirmed_packed`/`qty_packed_in_task`. Вызов доступен и через обычные GET в `backend/app/api/packaging_tasks.py:425,449`.

**Воспроизведение на PostgreSQL:** подготовлено представимое историческое состояние после этой миграции: источник уже израсходован, остаток 0; существующие allocation3 и box3 получают новые поля quantity_packed=0; сохранённая строка упаковки содержит legitimate confirmed3/work0. Обычный пересчёт даёт confirmed0/work3 при прежнем общем итоге3. Последующее существующее complete сотрудником со ставкой700 коп/шт сохраняет оплату2100 коп вместо0.

```json
{"case":"historical-ready-source-consumed","after":{"confirmed":0,"work":3,"total":3,"alloc":[3,0],"balance":[0,0]},"earned_kopecks":2100}
```

Это не просьба массово исправлять старые данные. Новая версия сама меняет ранее сохранённый правомерный результат при чтении/завершении. Неизвестное историческое происхождение нельзя приравнивать к доказанному unpacked; требуется совместимый переход, сохраняющий доказанную готовую часть, без её восстановления по текущему остатку. Способ хранения и перехода выбирает разработчик. Связь: R5/R12, C5p/C5s/C8/C17.

## P1-3. Удаление из конкретного короба возвращает другую готовую часть; повторная сборка её удваивает

**Место:** `backend/app/services/marketplace_unload_collect_service.py:739–753` выбирает allocation по убыванию общего количества и снимает его packed. `remove_from_box:797–809` возвращает эту часть на склад. Независимо от этого `821–828` уменьшает packed у строки удаляемого короба. Связи между фактически удалённой готовой частью и частью возврата нет.

**Воспроизведение на PostgreSQL через реальные сервисы:** один товар/документ, план3; источник A содержит packed2, B — unpacked1. `collect_into_box` собирает A2 в короб A и B1 в короб B. Начало: общий итог3, confirmed2/work1, allocation packed2. Удалить единственную unpacked единицу из короба B существующим `remove_from_box`. Выбирается крупнейший allocation A2; на склад A возвращается packed1. В коробе A остаются packed2, а суммарно в allocation — packed1. Затем существующим `add_manual_qty_to_box` добрать возвращённую packed1 с A в короб B. Итог коробов3, confirmed3/work0, хотя allocation по-прежнему содержит только packed2 и unpacked1. Ошибка уже отражена в основании расчёта сотрудника.

```json
{"before":{"confirmed":2,"work":1,"total":3,"alloc":[3,2],"balance":[0,0]},"removed":{"confirmed":2,"work":0,"total":2,"alloc":[2,1],"balance":[1,1]},"recollected":{"confirmed":3,"work":0,"total":3,"alloc":[3,2],"balance":[0,0]}}
```

Требуется согласованно сохранять готовую часть между конкретным удалением, остатком, allocation и коробом; нельзя исправлять это запретом законной перекладки. После исправления повторить удаление/добор из разных источников и возврат смешанной строки. Связь: R5/R12, C5m/C17.
