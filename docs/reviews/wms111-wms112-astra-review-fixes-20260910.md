## Что исправлено относительно восьми замечаний

1. В WB status handler и локальном завершении отмены helper вызывается **до**
   detach. В существующем JSON заказа сохраняется `source_supply_id` — исходная
   ссылка, которая иначе удаляется. При следующих чтениях дата берётся из
   существующего подтверждения операции либо delivered_at исходной поставки;
   второй сохранённой даты передачи или флага передачи нет. Ссылка также
   участвует в отображении поставки и её фильтре реестра после detach.
2. Создание и реестр используют `cancellation_handover_dates` и одну проверку
   `transfer_at <= cancelled_at`. Поздняя строка WB с отменой раньше передачи
   не создаёт документ. Для старой строки без достоверного времени классификация
   остаётся неизвестной (`null`), даже если есть изменяемый updated_at.
3. HTTP-модель FbsCancelledAfterPackItemOut сохраняет четыре поля:
   `cancelled_at_source`, `cancelled_after_transfer`, `transfer_at`,
   `return_document_id`. Проверен реальный запрос через ASGI/FastAPI с авторизацией
   тестового FF-администратора, а не только сериализация класса в памяти.
4. Helper самостоятельно блокирует существующую строку FbsOrder и перечитывает
   её JSON до autoflush. Он видит маркер другой транзакции даже при устаревшем
   ORM-объекте. Независимые pending-правки остальных ключей JSON сохраняются;
   stale cancellation marker поверх актуального не копируется.
5. Наблюдение отмены сохраняется вне savepoint, документ и ссылка на него — внутри.
   Реальные ошибки БД при INSERT документа и после записи маркера откатывают
   только документ; сессия явно перечитывает заказ и продолжает отмену/commit.
   Последующий sync_order_statuses, seller sync (включая new-feed-only) и повтор
   ручной отмены пытаются достроить отсутствующий документ из сохранённых фактов.
   Исправление отсутствующего склада/товара также покрыто. Терминальные заказы
   для этого не отправляются обратно в WB polling.
6. Новые записи помечаются `observed_at`, а не выдают время обработки за WB-время.
   В ответах batch status и import feeds наблюдение фиксируется до следующих
   страниц и блокировок; tracking/shipment фиксируют его сразу после ответа.
   При ручном завершении — при входе в локальный обработчик после ответа WB.
   Время сохраняется и до передачи, и при отсутствии товара/склада/документа,
   и для впервые импортированного уже отменённого заказа. Повтор его не сдвигает.
   При позднем появлении точного WB-времени оно заменяет observation source,
   в том числе при уже существующем документе.
7. Tracking и shipment передают исходный `row` и observation timestamp.
   Оба реальных сервисных пути проверены с тестовым ответом WB и реальной БД.
8. Фильтрация, total, сортировка и пагинация используют время, показываемое в
   cancelled_at, с legacy fallback только при отсутствии сохранённого времени.
   PostgreSQL использует timestamptz, SQLite — julianday для сопоставимости
   разных представлений дат. HTTP-тест задаёт updated_at в обратном порядке,
   проверяет сортировку, limit и точную границу периода по дате WB.

Новых таблиц, колонок модели, журналов, квот или счётчиков не добавлено.
Возврат остаётся существующим InboundIntakeRequest: `return`, `wildberries`,
`draft`, ожидаемая строка и `posted_qty=0`, `actual_qty=None`. Приход не вызывается.
Правки не добавляют навигационных блокировок FBS и не превращают упаковку в движение.

Последний PostgreSQL-прогон: **15 passed**, 2.87 секунды, без skips.
Fixture создаёт ORM-схему только в этой выделенной тестовой базе. Для повторения
нельзя подставлять клиентскую/общую БД: fixture очищает свою тестовую схему.

Concurrent replay использует два AsyncSession/два backend PID, каждый заранее
прочитал заказ без документа. Внутри обеих транзакций проверено `READ COMMITTED`.
Первая создаёт документ, вторая действительно ждёт row lock: тест проверяет
`pg_stat_activity.wait_event_type = 'Lock'` до commit первой. В первой транзакции
также выполнен повтор helper. После обоих commit ровно один документ и одна
строка, оба вызова вернули одинаковый ID. Pending JSON второго вызова сохранён.

Перед этим тест создал существующий остаток **17** (12 unpacked + 5 packed) и
существующее приходное движение +17 в собственной тестовой ячейке. Полные строки
InventoryBalance и InventoryMovement до/после сравниваются: они не изменились.
Это доказательство отсутствия прихода от helper создания документа. Снятие
резерва в общем пути отмены — отдельная существующая операция inventory_service,
её операторский потолок исправляет другой исполнитель.

## Что координатору ещё нужно проверить и отразить в каноне

Предлагаемый статус обеих карточек: **СЕРВЕР ИСПРАВЛЕН В ВЕТКЕ; ЦЕЛЕВЫЕ И
POSTGRESQL-ПРОВЕРКИ ПРОЙДЕНЫ; ОЖИДАЕТ НЕЗАВИСИМОГО РЕВЬЮ/ИНТЕГРАЦИИ/ВЫПУСКА**.
Старый текст «СДЕЛАНО В ВЕТКЕ» в наследованной записке не означает приёмку.

- Независимое read-only ревью конкретного commit, затем общая интеграция и CI.
  Особенно сверить совместимость с исправлениями inventory_service другого
  исполнителя. Этот worker не делал merge, не создавал release, не деплоил.
- Проверить SHA работающего backend после разрешённого выпуска; исходные миграции
  и триггеры production в этом локальном тесте не исследовались.
- На собственном учебном заказе проверить доступный пользователю цикл отмены
  после подтверждённой передачи: один draft возврата, повтор без дубля, без
  прихода до физической приёмки, исходная поставка и дата в реестре.
  Отдельно проверить отмену до передачи и период/сортировку на экране.
- Frontend этому исполнителю не назначен. В прочитанном файле
  frontend/src/screens/v2/FbsCancelledAfterPackDialog.tsx строки 107/111 ещё
  используют supply_departed и подпись «Обновлено». Новые четыре HTTP-поля
  сервер отдаёт, но отображение источника времени, исторической границы и
  перехода в return document должно быть принято отдельно владельцем frontend.
  Браузер worker не открывал; HTTP-тест не является проверкой интерфейса.
- Исторические отмены без маркера автоматически не восстанавливаются и не
  получают выдуманную дату. При улучшении WB-времени или последующей коррекции
  подтверждения передачи ранее созданный документ не удаляется/не проводится
  автоматически; коррекция существующего документа требует проверки основания.

Доказанных незакрытых ошибок в выполненных целевых проверках нет. Перечисленные
границы проверки и независимая приёмка остаются открытыми, DONE worker их не снимает.
