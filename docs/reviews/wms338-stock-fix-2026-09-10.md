# WMS-338 / WMS-341 / WMS-329 · Операторский потолок остатка ФБС — фиксация контракта

Дата: 2026-09-10. Ветка: `feat/wms338-stock-min-formula`. Автор: агент запаса
складов, работавший под задачей WMS-415.

## Контракт владельца

`FbsBindingStockPool.quantity` — это **операторский потолок**. Меняет его
только оператор. Публикация уезжает как `min(cap, свободный остаток)`. Никаких
журналов расхода, дополнительных счётчиков, регистров резерва или возврата
квоты. Один источник правды на одну величину.

Инцидент 04.09.2026 (335 единиц товара выпали из витрины) — прямая иллюстрация
второго счётчика над одной и той же величиной: журнал квоты и физический
остаток расходились, вопрос был только когда.

## Что удалено в inventory_service.py

Пять точек, где код исторически мутировал операторское число. Все убраны в
одной атомарной правке (`ea472236`). Позиции ниже — итоговые номера строк в
рабочей копии на 2026-09-10. Исходные позиции из хэндоффа (`~225 / ~259 / ~306 /
~1721` в SHA `0229831f`) сдвинулись из-за добавления комментариев в тех же
местах, но семантически это ровно те же пять точек.

### 1. Резерв заказа не расходует потолок — `update_fbs_order_reservation`, reserve-ветка

Раньше:
```python
pools[pid] = pool
...
for pid, pool in pools.items():
    pool.quantity -= required[pid]
```

Сейчас (файл `backend/app/services/inventory_service.py`, `update_fbs_order_reservation`, около строк 200–226):
```python
if product.fbs_units_mode:
    pool = await _order_stock_pool(session, order, pid)
    if pool is None:
        # Правило поштучного режима задаётся существованием pool.
        order.reserve_status = RESERVE_STATUS_NOT_PUBLISHED
        return
...
available = await fbs_available_qty_for_product(
    session, order.tenant_id, order.warehouse_id, pid,
    exclude_fbs_order_id=order.id,
)
if available < quantity:
    order.reserve_status = RESERVE_STATUS_NO_STOCK
    return
```

Резерв больше не проверяется через `pool.quantity >= quantity` — он идёт через
общее `fbs_available_qty_for_product`, которое учитывает физический остаток,
чужие резервы и уже созданные брони. Сам потолок не расходуется.

### 2. Отмена до передачи не возвращает ничего в потолок — `update_fbs_order_reservation`, release-ветка

Раньше:
```python
for reservation in reservations:
    product = products[reservation.product_id]
    if not shipped and product is not None and product.fbs_units_mode:
        pool = await _order_stock_pool(session, order, reservation.product_id)
        if pool is not None:
            pool.quantity += reservation.quantity
    await session.delete(reservation)
```

Сейчас (около строк 253–260): та ветка удалена. Осталось только `await session.delete(reservation)`.

### 3. Инвентаризационная недостача — `_deduct_inventory_from_fbs`

Раньше (около строк 300–310):
```python
for pool in pools:
    take = min(remaining, pool.quantity)
    if take:
        deductions.append((product.id, pool.binding_id, take))
    pool.quantity -= take
    remaining -= take
```

Сейчас: последняя строка `pool.quantity -= take` убрана. Атрибуция остаётся —
она нужна для показа «сколько отняли у ФБС-потолка», но само число оператора
не расходуется. Физическое уменьшение баланса пойдёт через `record_movement`.

### 4. Передача без резерва — `apply_fbs_supply_write_off`

Раньше (около строк 1694–1721): большой блок с pull-lock заказа, суммированием
двух видов резерва (`FbsOrderReservation` + `FbsOrderProductReservation`),
вычислением `unreserved` и мутацией `pool.quantity = max(0, pool.quantity - unreserved)`.

Сейчас (`apply_fbs_supply_write_off`, около строк 1697–1707): осталась только
sanity-проверка принадлежности заказа арендатору:
```python
if fbs_order_id is not None:
    sanity_order = await session.get(FbsOrder, fbs_order_id)
    if sanity_order is None or sanity_order.tenant_id != tenant_id:
        raise ValueError("fbs order not found")
```

Она защищает от подложенного `fbs_order_id` — списывать чужой физический товар
по чужому идентификатору нельзя. Регресс на эту проверку — в новом файле тестов
(см. ниже).

### 5. units-mode reserve-check через общий предикат — не удалено, но переработано

Раньше `if pool is None or pool.quantity < quantity` внутри `update_fbs_order_reservation`
рассматривало pool.quantity как счётчик и одновременно как признак существования
правила. Стало (около строк 205–210): наличие `pool` = «правило задано», а
доступное считается через `fbs_available_qty_for_product`. Один смысл — одна
проверка.

## Смежные исправления

### WMS-060 — коммит `ac79e809`

Экран `/ff/fbs-stock` (`FfProductsFbsPage.tsx`) в `saveRule` не передавал
`units_mode` и `units_by_warehouse`. API подставлял дефолты, и сервис молча
сбрасывал режим штук и обнулял потолок. Добавлены оба поля в тело PUT.

### WMS-384 — коммит `8f748ccb`

Одинаковая SQL-проверка «правило задано» жила двумя копиями в
`fbs_stock_sync_service` и `fbs_warehouse_binding_service`. Введена одна
функция-хелпер `fbs_stock_rule_service.product_has_rule_predicate()`,
возвращающая SQLAlchemy-выражение. Точная Python-проверка `_has_rule`,
учитывающая per-binding pool_rows, оставлена отдельной — она сложнее и
не выражается одной колонкой.

## Ozon-импорт (WMS-352 / WMS-386)

Grep по `backend/app/services/ozon_*.py` не находит ни одной мутации
`FbsBindingStockPool.quantity`. Ozon-импорт заказов и товаров не трогает
операторский потолок. Резерв, если он делается, идёт через
`_try_reserve_order → update_fbs_order_reservation`, где — после наших
правок — `pool.quantity` неизменен по контракту. Отдельного теста именно на
Ozon-импорт не добавляли: сама механика (`update_fbs_order_reservation`)
покрыта тестами выше.

## Что осталось непроверенным без реальных endpoint

- Полный сценарий «оператор задал N → WB опубликовал min(N, free) → покупатель
  оформил заказ → мы зарезервировали → WB прислал sold → мы списали товар с
  ячейки → следующая публикация уехала с новым min(N, free-1)» не запускался
  против реального Marketplace API. Юнит-тесты покрывают каждый шаг, но между
  шагами есть сеть, ретраи и eventual consistency WB.
- То же для Ozon: import с реальным `client_id/api_key` не запускался. Мокнутые
  тесты (`test_ozon_fbs_*`) остаются зелёными.
- UI `/ff/fbs-stock` вручную в браузере под этим агентом не открывался: правка
  чисто TS, компиляцию проверить в этом worktree без `node_modules` не
  смогли, но семантически рулю на существующий тип `FbsRule`, где `unitsMode` и
  `unitsByWarehouse` уже есть.
