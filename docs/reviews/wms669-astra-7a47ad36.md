## Что проверено независимо

Набор константы сопоставлен со всеми кодовыми точками Unicode текущего Python:
`set(_DISPLAY_WHITESPACE) == {chr(i) for i in range(0x110000) if chr(i).isspace()}`.
Длина — ровно 29. Внешние символы удаляются, внутренние сохраняются.
U+200B и U+FEFF не входят в набор и сохраняются, как в Python `strip()`.

На каждом движке выполнены **298 сравнений трёх настоящих SQL-выражений** из
`_catalog_fields()` с действующими функциями отображения
`subject_name_from_card()`, `_size_for_product()` и
`_all_size_labels_from_card()`. Это не только проверка отдельного `trim`:
запрос читает тестовые Product и SellerWildberriesImportedCard, включая
коррелированное разворачивание размеров и выбор размера товара.

Матрица воспроизводится следующим набором: NULL, пустая строка, весь набор
пробельных символов без текста и вокруг `48`; для каждого из 29 символов и двух
непробельных контролей — сам символ, символ вокруг `48` и между `4` и `8`.
Каждое из 97 значений проверено в трёх конфигурациях: основное поле с запасным
значением `fallback`; второе поле при числовом первом; основное поле без
запасного значения. Сохранённый размер товара принимает то же значение.
Ещё семь случаев проверяют JSON 148, 0, false, true, массив, объект и null в
основном поле со строковым запасным значением, окружённым TAB/NBSP.
Все 298 сравнений на SQLite и все 298 на PostgreSQL — PASS; изменения матрицы
отменены откатом транзакции. NULL/пустота корректно дают запасное значение либо NULL,
числа не превращаются в отображаемый размер.

Замороженные HTTP-тесты подтверждают непрерывность одинаковых видимых категорий,
сохранение строк на страницах, выбор показанного размера 48 при числовом
techSize=148, сохранение отдельного строкового размера 148, выбор собственного
варианта через ProductBarcode(source="wb"), неполные JSON и прежние данные Ozon.
Для TAB и NBSP проверены `/page`, `/keys`, total и страницы по одной строке.
Никакие сервисы, SQL или функции обогащения в этих тестах не подменяются.

Чтением кода подтверждено: `/page` и `/keys` получают выражения из того же
`_catalog_fields()` и передают их в `_catalog_extra_filters()`. Условия входят
в SQL-ветви до count/LIMIT/OFFSET. Подсчёт и страницы используют один
`seller_catalog_universe`; группировка использует нормализованные category/size.
Проверка строкового типа JSON, порядок techSize → wbSize, собственный штрихкод,
корреляция подзапросов и ограничения tenant/seller сохранены побайтно вне трёх
вызовов `trim`. Варианты не размножают строки каталога.

Старый список категорий и `_card_category_filters()` по-прежнему используют
сырой subjectName, как отмечено в предыдущем ревью. Этот неизменённый участок
не выдан за новый дефект рассматриваемой разницы.
