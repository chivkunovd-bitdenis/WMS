## Блокирующие замечания

**F1 / P1 — R19: уже ожидающий запрос игнорирует новый Retry-After.**
В `backend/app/services/wb_sales_report.py:178–199` `_wait_slot` резервирует
время один раз и после сна не сверяет общий запрет. `_defer` меняет Redis key,
но не уже вычисленный срок B. A получает 429/Retry-After:120, B отправляет GET
на своей старой отметке +61s. Это независимо воспроизведено опубликованным
контрактом `3243caa26`, `test_wms517_sales_waiting_rate.py:111`.
Исправление должно переоценивать разрешённое время перед HTTP атомарно между
репликами, сохранять интервалы >=61s между перенесёнными запросами, продление
только своей workflow lease и отсутствие DB locks во время ожидания. Не вводить
скрытый HTTP retry. После исправления нужны этот RED→GREEN, сценарий нескольких
ожидающих callers и проверка реального Redis Lua. Последовательный fake Redis
тест и старый Redis smoke этот дефект не закрывают.

**F2 / P2 — R22: крайняя числовая цена может обрушить разбор всей страницы.**
В `read_sales_report`, блок `json.loads(response.content, parse_float=Decimal,
parse_constant=str)`, перехватываются только ValueError/UnicodeDecodeError.
Для допустимого синтаксиса JSON `[{"finishedPrice":1e9999999999999999999}]`
сам Decimal-конструктор выбрасывает `decimal.InvalidOperation`, который не
является ValueError. Исключение возникает до `sale_cost` и не перехватывается
внешним обработчиком HTTPError/RedisError. Значит исправленная проверка строки
цены не защищает числовой JSON-вариант: вместо ошибки одного КИЗ прекращается
вся подготовка, здоровый сосед не продолжается. Это независимо воспроизведено
маленьким стандартным Python probe с точным выражением парсера; полный API500
для этого нового случая в этом ревью не запускался.

Нужен отдельный контракт с сырым числовым finishedPrice сверх диапазона Decimal
и здоровым соседом. Разбирать денежные JSON-лексемы без вычисления/float
(например, сохранять лексему parse_float и валидировать её в sale_cost), либо
использовать эквивалентный безопасный подход. Просто считать всю страницу
битым JSON не выполняет R22 о продолжении здоровых строк. Проверить также
сохранение исходной лексемы/evidence, отсутствие документа у плохой строки и
штатный документ у здоровой.

Проверены изменения пяти продуктовых файлов и новый wb_sales_report на точном
SHA; перед прогоном их diff относительно этого SHA пуст. Поздний HEAD
`3243caa26` добавляет отдельный тест R19, не меняет проверяемый продуктовый код.

  не заменяют S-sale. R/неизвестный тип/конфликт исключают соответствующий rid;
  повтор S не размножает строку, неоднозначность нескольких локальных заказов
  не даёт использовать одну sale как несколько заказов.
* Чтение идёт по flag=0 до пустого массива, без ограничения четырьмя/80 или
  первой найденной продажей. Курсор передаётся без форматирования; седьмая цифра
  учитывается и при выборе последнего evidence. PostgreSQL использует один
  ARRAY-параметр, а не тысячи bind-параметров. SC9 проверяет 305 и 10000 отдельных
  заказов/КИЗ. Их повторный большой прогон здесь не выполнялся; это проверка
  кода и содержания контрактов, не новый результат полной серии.
* Неполный HTTP-отчёт не публикуется в cache; create/retry/final build обходят
  cache. Для отсутствующей истории старше 90 дней полный реестр честно отказывает,
  выбранные актуальные доказанные строки могут продолжаться. Это не доказательство
  полного реального sold-набора конкретного селлера.
* Финальное чтение sales выполняется после CRPT preflight, до builder; после
  ожидания перепроверяются lease, локальная привязка и auth expiry. Цена берётся
  из точной продажи. Decimal tuple scaling не округляет длинную дробную копейку;
  обычные невалидные цены остаются ошибкой item, без старого price fallback.
* Mixed A→R + healthy B сохраняет исходный selection hash, оба item и исходное
  S-основание A плюс свежую причину/R evidence. У A нет документа, B получает
  единственный документ с собственной ценой. Локальный emulator-прогон прошёл
  подпись-заглушку, submit и terminal recovery B; A остаётся failed.
* Существующий request/claims возобновляет ту же operation. Submitted/unknown
  reauth возвращается до fresh sales/builder; exact bytes/hash/certificate binding
  и GET recovery не заменяются новым выводом. Ошибка fresh prep не разрешает
  повторный внешний POST. Реальная подпись и внешняя отправка не выполнялись.
