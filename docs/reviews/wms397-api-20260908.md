## Изменение и контракт для mobile

В `POST /operations/fbs-supplies/{supply_id}/pick/scan` добавлено необязательное
поле `order_id: UUID | null`. На публичном сервере этот путь находится под
существующим префиксом `/api`. Пример тела продуктового скана:

```json
{
  "barcode": "штрихкод товара",
  "order_id": "UUID выбранного заказа",
  "storage_location_id": "UUID выбранного места"
}
```

Mobile выбирает нужный заказ своего рабочего списка и передаёт его ID.
Сервер не вводит новый порядок сортировки: без `order_id` или при `null`
сохраняется существующий выбор заказа с ближайшим `deadline_at`. Подсказка
`product_id` и парные `container_kind` / `container_id` продолжают работать.
Скан места или тары остаётся выбором источника, не подбором заказа.

Diff приложения состоит ровно из четырёх добавленных строк: поле в теле
запроса, его передача в `picking_svc.pick_scan`, необязательный аргумент сервиса
и передача аргумента уже существующему `scan_pick_product(order_id=...)`.
Модели, миграции, форма ответа и складская логика не изменены.

Проверенная цепочка: маршрут с `require_fbs_operator_access` → tenant из
авторизованного пользователя → `_load_supply` по tenant и supply → проверка
товара/места/контейнера → существующий выбор заказа из подходящих строк этой
поставки и товара. Чужой, отменённый, отсутствующий или уже подобранный заказ
не заменяется другим подходящим заказом. В WB подбор записывает существующий
факт и точный источник, не вызывает перенос товара и не списывает остаток.

`Idempotency-Key` относится к одному скану в данной поставке. При сетевом
повторе mobile сохраняет исходный ключ; для следующего скана создаёт новый.
Существующий повтор ключа возвращает результат без нового подбора, даже если
клиент ошибочно передал другой `order_id`. Новая попытка уже подобранного
заказа с новым ключом получает обычную ошибку, а не выбирает следующий заказ.
Форма ответа по-прежнему сообщает количества, поэтому для актуального
состояния конкретных заказов клиент перечитывает существующий workspace.

## Целевые проверки

Новый `tests/test_wms397_pick_scan_order.py` проверяет весь HTTP-маршрут через
ASGI на изолированной SQLite-базе:

- конкретный старый заказ выбирается вопреки более близкому сроку другого;
- отсутствие поля и явный null сохраняют старый выбор веба;
- повторы одного ключа не создают новый подбор; новый ключ не повторяет уже
  подобранный заказ, следующий заказ с новым ключом подбирается;
- заказ другой поставки, другого товара, отменённый или отсутствующий
  отклоняется без автоматического выбора другого заказа;
- чужие tenant/order, tenant/product и tenant/supply отклоняются;
- паллета, короб и грузоместо сохраняются как точный источник выбранного заказа;
- неполная пара контейнера и несуществующий контейнер не обходят проверки;
- Ozon использует существующую строку подбора позиции выбранного заказа,
  сетевой повтор не создаёт вторую строку или второе перемещение.

В WB-сценариях сравниваются складские количества, записи движений и реальные
резервы до/после: изменения отсутствуют. Проверки выполняются с реальной
логикой сервиса; вызов `scan_pick_product` не подменён заглушкой.

Выполнены целевые `ruff check --no-cache`, `mypy --cache-dir=/dev/null` двух
изменённых исходников и pytest одного нового файла: **15 passed за 15,19 с**.
Локальные SQLite-файлы этого прогона удалены после проверки; PostgreSQL-базы
не создавались. Полный pytest, новый Opus,
внешние API, мобильный экран и реальные сканеры здесь не запускались.
Мобильная приёмка и интеграция ветки остаются отдельным продолжением WMS-397.
