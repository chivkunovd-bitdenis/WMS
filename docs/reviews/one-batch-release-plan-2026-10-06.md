## Решение владельца

Владелец отменил выпуск готовой части отдельно: production останавливается и
обновляется один раз, когда готовы все задачи согласованного пакета. Уже принятые
изменения не скрываются и не переделываются, но сами по себе больше не дают права
на отдельный deploy. До прямого указания ведущего на собранный и полностью
проверенный общий SHA новые production workflow не запускаются.

## Как собрать один frozen candidate

1. Дождаться завершения всех перечисленных продуктовых дорожек. Для каждой нужны
   отдельные требования, tests-before-code, неизменённые ожидания тестов,
   реализация, независимое ревью, аналитическая приёмка и опубликованный SHA.
2. Только после этого создать одну именованную integration-ветку внутри
   `WMS/.worktrees` от свежего `origin/etalon`. Не использовать временный клон и
   не переносить незакоммиченные изменения.
3. Сначала перенести готовые CLEAN-компоненты, затем конфликтующие WMS-517 и
   WMS-667 после их обновления на свежую базу; WMS-662/663, WMS-669 и WMS-672/673
   добавлять только по финальным принятым SHA. Точный порядок уточнить по diff и
   зависимостям, а не по номеру задачи.
4. Любой конфликт разрешать с владельцем соответствующей дорожки и повторять
   затронутые целевые проверки. Нельзя выбирать сторону конфликта только ради
   зелёного merge.
5. После последнего продуктового коммита заморозить SHA. На нём один раз выполнить
   package-level Astra high review, аналитическую приёмку всего состава,
   критические staging journeys и полный CI. Документальные отчёты, которые
   меняют HEAD после проверки, должны либо жить в отдельной evidence-ветке, либо
   вызвать полный CI нового финального SHA.
6. Слить один проверенный PR в `etalon`, дождаться обязательного push-CI exact
   merge SHA и только затем один раз вызвать штатный `Deploy Production` с
   immutable target. Gate workflow, CI и миграции не обходить.
7. После deploy отдельно доказать фактически обслуживаемый SHA/код, migration
   head, healthy API/web/worker/beat/Redis, публичный smoke и безопасные
   операторские сценарии. Физическую печать и внешнюю передачу площадке не
   подменять HTTP 200; если они входят в конкретную задачу, фиксировать отдельно.

## Что запрещено до общего выпуска

- не запускать production deploy готовых пяти, WMS-651 или другого subset;
- не создавать каждые несколько минут новый candidate и новый полный CI;
- не ослаблять gate, тесты, migration guard или требования ради дедлайна;
- не включать незавершённые задачи как «оговорки после выпуска»;
- не менять production secrets и не выполнять отдельный `alembic stamp`, SQL или
  миграцию вне соответствующего общего кода;
- не объявлять Railway staging production-средой.

Этот документ — integration plan и снимок границ, а не разрешение на merge или
deploy. Финальный запуск требует нового прямого сообщения ведущего после того,
как все строки пакета имеют PASS.
