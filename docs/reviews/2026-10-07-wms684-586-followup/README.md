## F1 — частично исправлено; оставшийся [P2] дефект переполнения

Место: [inbound_acceptance_act_service.py](../../../backend/app/services/inbound_acceptance_act_service.py), **строки 282–301**, особенно **290–291**. Затронуты WMS-586 **R8, R9, R14**: оператор должен сохранять PDF существующего акта с полными реквизитами допустимых товаров.

Исправление теперь учитывает явные переносы и измеряет результат `insert_textbox` до сохранения строки. Старое название `Худи\nРазмер XL\nЦвет чёрный\nЗимняя коллекция\nУтеплённый хлопок` (61 символ, пять строк) полностью присутствует в реальном PDF API; Excel содержит то же имя. Длинное имя из 255 широких кириллических символов также сохраняется полностью, измерение увеличивает строку вместо молчаливого пропуска текста. Оба PDF открываются, содержат итог 10/8/−2, не имеют пустых страниц или слов вне страницы; растры просмотрены через view_image.

Однако новый `max_row_height` равен **467 pt**, а название с 64 короткими строками `Х00`…`Х63`, разделёнными переводами строк, содержит ровно **255 символов** и получает начальную высоту **613 pt**. На строке 291 выбрасывается необработанный `ValueError("acceptance_act_pdf_row_too_tall")`. В итоге **GET acceptance-act.pdf возвращает HTTP 500, text/plain, Internal Server Error**, а **GET acceptance-act.xlsx того же документа возвращает 200 и сохраняет полное имя**.

Это проверка границы допустимых данных, а не утверждение о частоте такого имени у действующих операторов. Текущий `ProductCreate` принимает это имя без изменения: его ограничение `max_length=255` соблюдено. Внутренние переносы `catalog_service.create_product` не удаляет. Документ в тесте завершён (`sorting`), права действуют, численные данные обычные (план 10, факт 8); причиной отказа является именно размер строки PDF. Нельзя считать F1 полностью исправленным, пока допустимые данные вместо файла приводят к 500.
