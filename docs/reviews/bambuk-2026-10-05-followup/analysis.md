## Проверка официальных API

### Что удалось получить сейчас

05.10 web.open прямого `https://dev.wildberries.ru/openapi/orders-fbs` вернул
498; альтернативный официальный URL также не открылся напрямую. Поиск вернул
содержимое официальной документации WB с пометкой индекса «5 months ago»:
[WB FBS, статусы и передача](https://dev.wildberries.ru/en/docs/openapi/orders-fbs?locale=ru)
и [официальная песочница WB, модель статусов](https://dev.wildberries.ru/ru/openapi-other/sandbox-environment).
Это доступная индексированная официальная документация, не доказательство
свежего ответа Seller API на 05.10. Противоположного текущего контракта не найдено.

Документация различает статус продавца и статус WB. Complete возникает при
передаче, confirm — при включении в сборку. Передача меняет статусы заказов;
закрытие родительской поставки само по себе недостаточно для состава. Песочница
отдельно различает передачу и приёмку WB, а также отказ покупателя после передачи.
Эти сведения использованы в таблице WMS-662, не заменены догадкой по слову done.

`https://docs.ozon.ru/api/seller/` через web.open вернул redirect loop; три
адресных поиска по официальному домену не нашли доступных карточек методов.
[official-live-check.json](official-live-check.json) уже содержит результат
предшествующего прямого чтения с TLS-ошибками. Защита TLS не отключалась,
учётные данные/кабинеты секретов не читались и внешние Seller API не вызывались.
**Актуальность Ozon-спецификации онлайн не подтверждена.**

### Сохранённая официальная спецификация Ozon

Прочитан `tasks/ozon-integration-20260825/OZON_FBS_OPENAPI.json` из текущего etalon.
SHA-256 файла:
`b31282086acccf22f7a292c4060882e7f825b8d241a58215b2e6363e4a441eb2`.
Дата в имени каталога не выдаётся за дату свежести всех методов.

Для WMS-662 прочитаны paths `/v3/posting/fbs/get`, `/v1/carriage/get`,
`/v1/carriage/create`, `/v1/carriage/approve`, `/v1/carriage/set-postings`;
описание create ссылается на `/v2/posting/fbs/act/get-postings` для состава.
Схемы: `v3FbsPostingDetail`, `posting.v4.PostingFbsListResponse.Postings`,
`carriageCarriageGetResponse` и вложенная Cancellation.

Ключевые границы:

- Сборка Ozon и сдача различны. `cancelled_after_ship` описан как отмена **после
  сборки**. Нельзя считать его доказательством складской передачи.
- У list и get разные перечни терминальных представлений: get перечисляет
  delivered; в list существенны posting_delivered/received. Нельзя сравнивать
  только строку локального status или прекращать восстановление на локальном done.
- `carriageCarriageGetResponse.status` перечисляет received/closed/sended/cancelled.
  Описание approve говорит «Сформирована», но response-schema не перечисляет formed.
  Код `_CARRIAGE_CONFIRMED_STATUSES` принимает formed на основании старого живого
  наблюдения WMS-428. Это достаточное объяснение существующего кода, но не новое
  официальное подтверждение положительного наблюдения из внешнего кабинета.
- Частичная перевозка имеет `is_partial`; принадлежность/количество надо брать
  из точного состава, а не распространять parent status на все локальные заказы.

Для WMS-663 прочитаны paths `/v6/fbs/posting/product/exemplar/set`,
`/v6/fbs/posting/product/exemplar/create-or-get`, `/v5/fbs/posting/product/exemplar/status`
и связанные request/response схемы, ProductExemplar и ExemplarsMarks.
Полный перечень их generated Python-имён находится в документе требований.

Подтверждены поля gtd/rnpt и отдельные is_gtd_absent/is_rnpt_absent, обязанность
полного products/exemplars payload, асинхронность 200 и чтение результата status.
На уровне экземпляра возвращаются значения, флаги и отдельные ошибки документов.
Доступность редактирования — самостоятельное свойство. В gtd/rnpt_check_status
нет enum: переносить passed/failed из marks.check_status нельзя.

Операторский выбор не даёт универсального освобождения от документов. WMS
передаёт поддержанный выбор и показывает конкретный ответ Ozon. Не добавлены
«отсутствуют все документы», сертификаты, универсальная галка для УИН/IMEI/ЧЗ.

## Проверенный код и места, где простой вызов сломает учёт

1. WB `_apply_wb_status_to_order` и Ozon `_apply_status` снимают резерв по
   терминальным состояниям без расхода склада. Новое проведение должно быть
   согласовано с этими ветками, иначе доступное количество временно/навсегда растёт.
2. `sync_ozon_order_statuses` исключает finished rows. Новый механизм обязан
   находить ещё не проведённые существующие done-заказы, но ограничивать выборку
   порциями; это не разрешение бесконечно обходить всю историю каждого селлера.
3. `fbs_supply_reconcile_service.reconcile_supply_delivered` сейчас читает только
   supply.done. Его старый результат не является достаточным доказательством
   нового обратного проведения.
4. `fbs_shipment_service._finish_ozon_delivery` перечитывает все заказы поставки.
   Передача подсписка не сохраняет границу частичной сдачи. Нужен явный состав
   локального проведения и повторная сверка после взятия блокировки.
5. `fbs_ozon_packaging_service.write_off_order` использует первый movement_id как
   завершение всего заказа, а prepare_shipment_sources пропускает такой ledger.
   Частичный child/quantity должен проходить отдельные ожидания R4/C7–C8 до кода;
   нельзя молча превратить первый проведённый кусок в признак полного проведения.
6. `inventory_service.update_fbs_order_reservation(reserve: bool)` обрабатывает
   заказ целиком. Для части Ozon необходим расчёт оставшегося обязательства
   в существующих резервах, согласованный с проведёнными количествами.
7. `_full_exemplar_products` собирает marks из FbsOrderMarking. Текущее поведение
   не гарантирует сохранность ГТД/РНПТ/weight и удалённо введённых сведений. Все
   writers общего `/set` должны использовать единый полный набор, иначе следующий
   скан КИЗ отменит операторский выбор документов.
8. `submit_marking` принимает общий ship_available без проверки целевых document
   fields; fixture старого теста возвращает products=[]. Новый документ не должен
   принимать такой ответ за подтверждение именно отправленной ГТД.
9. `_call` делает retries только при read=True, provider.call мутации не повторяет.
   Классификация create-or-get как чтения только по имени опасна; намерение и
   неизвестный исход сохраняются до повтора, а не только в памяти процесса.

Точные функции, схемы, fixtures и существующие имена тестов перечислены в каждом
документе. Код и тесты в этом проходе не менялись и не запускались. Проверка
заполненности для финальной приёмки здесь не заявляется: вердикты обязаны быть пустыми.
