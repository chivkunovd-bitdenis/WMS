## Что изменено

Production-diff затрагивает только `backend/app/services/fbs_print_asset_service.py`.
Прочитаны реальные пути `assemble_box_order → _invalidate_old_label`, создание и
обновление этикетки в сервисе печати, confirm-applied и вызов content из API.
Восстановление сборки Ozon держит Order и затем обновляет PrintAsset.
Открытие содержимого теперь соблюдает тот же порядок: **Order → PrintAsset**.
Другие writers не редактировались.

Новый внутренний `_load_content_asset` сначала читает только идентификатор связанного
заказа без блокировки. Затем блокирует заказ нужного tenant, перечитывает его с
`populate_existing=True`, блокирует актив с проверкой tenant и неизменности связи,
тоже с `populate_existing=True`. Последующая проверка статуса и изменение
sticker_status используют именно этот перечитанный заказ.

Если связь изменилась, точка отката освобождает блокировки устаревшей попытки,
и поиск повторяется с актуальным идентификатором. Предварительный результат не
считается разрешением читать актив или менять старый заказ. У актива без заказа
блокируется только актив с условием `fbs_order_id IS NULL`. Если связанный заказ
не принадлежит tenant, содержимое не выдаётся. Для `record_print_opened=False`
сохранён путь без новых блокировок.

Автор события по-прежнему берётся из аутентифицированного контекста. Helper аудита,
снимок имени, его savepoints и правила rollback не менялись. Нет NOWAIT,
нового навигационного блокера, проверки прав ради аудита, складских движений,
начислений, таблиц или новых состояний. Остальные изменения `a40c124d` сохранены.

## Доказательство прежней взаимной блокировки

Из Git прочитана **точная функция `get_asset_binary_content` исходного SHA**.
Её AST загружен в память модуля сервиса в отдельном процессе pytest; файл рабочего
дерева при этом не заменялся. Использовавшийся ею `_load_asset` в исправлении
не изменён. Таким образом тест запускал прежний код открытия, а не имитацию SQL
или искусственно выброшенное исключение.

Один и тот же `test_open_content_vs_ozon_recovery_has_no_deadlock` использует два
разных `pg_backend_pid()` и настоящий `assemble_box_order`. Подменён только
ответ внешнего провайдера существующим FakeMarketplaceTransport. После реального
захвата Order операция Ozon приостанавливается на чтении ответа; тест запускает
открытие и дожидается фактического ожидания PostgreSQL через `pg_blocking_pids`.
После этого Ozon продолжает настоящий `_invalidate_old_label`.

**На исходной функции тест падает с SQLSTATE `40P01` — deadlock detected.**
[Свидетельство](artifacts/wms325-print-lock-order-20260910/baseline-deadlock.txt).
Ожидание синхронизировано по состоянию базы, а не по предположению о скорости
потоков. Контрольные таймауты установлены только в тестовых соединениях.

**На исправленном коде тот же тест проходит.** Ozon коммитит восстановленные номера
отправлений и переводит этикетку в `requesting`. Открытие после ожидания перечитывает
это состояние и возвращает уже существующий `asset_not_ready`; прежний готовый
файл не выдаётся, ложное событие открытия не появляется. Ни одна транзакция не
прерывается из-за взаимной блокировки.
