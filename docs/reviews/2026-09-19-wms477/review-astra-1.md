# WMS-477 — независимое перекрёстное ревью Astra № 1

**Вердикт: FAIL.** Найдены три подтверждённых технических дефекта: запоздавший
ответ WB перезаписывает более свежий вердикт; наличие локального кода ошибочно
определяется по статусу и отключает повторную проверку; минутный цикл игнорирует
существующую паузу после ограничения запросов. Отдельно найден неточный счётчик
обновлений в журнале. Основание FAIL — эти дефекты, а не продуктовые сомнения
или отсутствие браузерной приёмки.

Проверены ветка `feat/wms477-marking-recheck`, исходный диапазон
`b480cc49..2b6f6b7efa1849d8e21ca9a7ea81849037437deb`, бэкенд-коммит `186bbacd`,
фронтенд-коммит `2b6f6b7e` и документные изменения `ad0c9d93`, `5b6b0ade`,
`47e4a7c1`. Все ссылки на строки ниже относятся к этому HEAD. Код продукта,
требования и бэклог ревьюер не изменял.

## Находки

### 1. Блокер — более старый ответ WB отменяет уже записанное подтверждение

**Место:** `backend/app/services/fbs_marking_service.py:1180`, `:1215`;
используемая защита — тот же файл, `:796–823`, применение — `:854–889`.
Вызов нового цикла — `backend/app/services/fbs_autopoll_service.py:984`.

Перед HTTP сохраняются только ID записей маркировки. Под замком строки
`_sync_order_meta_from_wb` проверяет, что набор ID не изменился. Это защищает
снятие/замену кода, но не защищает более свежий вердикт для того же кода.
Замок всего минутного цикла не распространяется на кнопку и общий опрос.

**Воспроизведено на изолированной SQLite-базе, с двумя отдельными сессиями
и управляемыми ответами WB:**

1. Новая `sync_marking_verdicts_for_seller` выбирает `pending` и ждёт ответ.
2. Существующая `sync_marking_statuses_for_assembling_supplies` получает
   `sgtinIntroduced`, сохраняет и коммитит `accepted`.
3. Первой сверке разрешается вернуть более старый `pending` для того же кода.
4. После её commit в базе снова `pending`.

Фактический вывод пробы: `REAL_NEW_AND_GENERAL_SERVICES: accepted -> pending`.
Аналогичная последовательность воспроизведена двумя вызовами нового сервиса
по поставке. Это проверка порядка прихода ответов; PostgreSQL-взаимоблокировка
здесь не имитировалась и не заявляется. В момент последней записи вторая
транзакция уже завершена: наличие `FOR UPDATE` не исправляет саму потерю
свежести ответа.

**Чем грозит:** подтверждённый код снова становится неподтверждённым; новый
отказ тоже может быть затёрт старым положительным ответом, поскольку применение
не проверяет свежесть ни для одного решения. Существующий механизм был
переиспользован, но новый независимый минутный писатель делает этот пробел
непосредственно применимым к WMS-477. R6 не обеспечено полностью.

**Как исправить:** вместе с набором кодов сохранить снимок существующих полей
вердикта/`metadata_last_checked_at` до HTTP и после захвата замка пропускать
ответ, если другая сверка уже изменила этот снимок. Общая защита должна действовать
в месте применения для всех писателей. Новые таблицы, счётчики и замок селлера
для этого не нужны. Добавить управляемый конкурентный тест «старый запрос
завершается после нового», включая новый цикл против общего цикла и кнопки.
Не решать проблему вечным запретом менять `accepted`: свежий отказ WB также
должен применяться.

### 2. Блокер — сохранённый код со статусом `missing` выключает «Проверить в WB»

**Место:** `frontend/src/screens/v2/fbsUx.ts:417–418`;
`frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx:1533`, `:2066`.
Серверный источник состояния —
`backend/app/services/fbs_marking_service.py:856–857`.

`fbsMarkingVerdictsSummary` считает код внесённым только при
`state.status !== 'missing'`. Однако `missing` здесь не означает отсутствие
локальной записи: ответ WB `decision=required`, `value=''` переводит
существующий `FbsOrderMarking` в `missing`, сохраняя его `value`.

**Воспроизведено:** новая HTTP-ручка вызвана на заказе с локальным кодом, ответ
WB подменён на указанный `required`. Получены HTTP 200, сохранённая запись с
прежним `value` и состояние рабочего места
`{kind: 'sgtin', status: 'missing', decision: 'required', value_tail: '77987477'}`.
Затем исполнена настоящая функция `fbsMarkingVerdictsSummary`, извлечённая
из исходника TypeScript: при `missing` и непустом `value_tail` она вернула
`{confirmed: 0, withCode: 0}`. Условие кнопки при такой единственной строке
даёт `disabled=true`. Это проверка API и функции, не визуально наблюдённый клик.

**Чем грозит:** оператор не может повторно спросить WB по коду, который всё ещё
привязан локально; сообщение также исключает этот заказ из Y. Нарушены R1 и R2
о наличии кода любого статуса. Сервер при прямом вызове такой заказ выбирает,
поэтому интерфейс и сервер расходятся.

**Как исправить:** определять наличие кода по существующему `value_tail`,
как уже делает действие «Очистить ЧЗ» рядом, а подтверждение — отдельно по
вердикту. Проверить два разных случая: `missing` с локальным значением и
`missing` без значения. Новая сущность или дополнительный сохранённый флаг
не нужны.

### 3. Блокер — минутный цикл не соблюдает `_MARKETPLACE_BACKOFF`

**Место:** `backend/app/services/fbs_autopoll_service.py:1025–1041`.
Для сравнения: общий цикл проверяет паузу в `:692`; её объект объявлен в `:66`.

Новый цикл сразу вызывает сервис каждого селлера. Проверки
`_MARKETPLACE_BACKOFF.remaining_seconds('wb')` нет. Обработчик
`WildberriesClientError` только пишет ошибку и продолжает обход.
Это прямо расходится с R6(в), где требуется соблюдать действующую паузу.

**Воспроизведено:** в процессе пробы установлен новый `MarketplaceBackoff`
с паузой WB на 300 секунд; список селлеров и нижний сервис заменены
контролируемыми функциями. При положительном остатке паузы реальная функция
`sync_fbs_marking_verdicts_all_sellers` всё равно вызвала сервис селлера один
раз и вернула `orders_checked=1`.

**Чем грозит:** новый путь продолжает запросы в период, который существующий
процесс уже считает периодом ограничения. Утверждение относится к доступному
данному процессу объекту backoff; межпроцессной общей памяти у этого объекта нет.
Повтор одного HTTP-запроса после `Retry-After` в
`wildberries_fbs_client.py:755–764` сохранён, но это другая защита и проверку
паузы цикла не заменяет.

**Как исправить:** перед обработкой очередного WB-селлера учитывать существующий
backoff. Обработку окончательного 429 согласовать с этой же паузой; не вводить
отдельный журнал ограничений. Добавить тест с заранее активной паузой и тест
исчерпанного повтора по 429. Сам существующий HTTP-повтор не удалять.

### 4. Замечание — `updated` включает ответ, который не был применён

**Место:** `backend/app/services/fbs_marking_service.py:1215–1236`;
журнал — `backend/app/services/fbs_autopoll_service.py:1065–1072`.

Если во время HTTP оператор заменил код, `_sync_order_meta_from_wb` правильно
возвращается без применения старого ответа (`:821–823`). Вызывающая функция
не различает этот исход и всё равно увеличивает `orders_updated`.

**Воспроизведено:** пока новая сверка ждала WB, отдельная сессия удалила старую
запись маркировки и сохранила новую с другим ID и статусом `assigned`.
После завершения сверки новый код остался `assigned`, но результат сообщил
`orders_updated=1`. Вывод: `REPLACED_ID_PRESERVED: assigned reported_orders_updated: 1`.

**Чем грозит:** по журналу нельзя отличить применённый ответ от пропущенного
устаревшего. Кроме того, счётчик измеряет заказы, а не изменившиеся коды,
упомянутые в R6(г).

**Как исправить:** возвращать из применения явный результат «применено/пропущено»
либо иначе учитывать фактическое применение и точно назвать единицу в журнале.
Это результат функции в памяти, а не повод заводить таблицу или постоянный счётчик.

### 5. Наблюдение — `unknown` намеренно не входит в минутный фильтр

**Место:** `backend/app/services/fbs_autopoll_service.py:974`;
`backend/app/services/fbs_marking_service.py:1271–1273`;
`docs/requirements/WMS-477.md`, D3 и раздел 8.

Фоновый фильтр действительно содержит ровно `pending/sending`; `unknown`
и `assigned` не добавлены. Ручная сверка по поставке не фильтрует статус
маркировки и достигает существующего подтверждения `pending_confirmation`
в `_sync_order_meta_from_wb:869–880`.

**Практическая граница:** не каждая серая строка обязана обновиться за минуту.
Включение `unknown` в новый фильтр было бы изменением постановки, а не исправлением
этого ревью. Нарушения R5 здесь нет; расширять фильтр по инициативе ревьюера
не требуется. Полный сценарий `unknown` с записью операции в этой сессии отдельно
не исполнялся — указанная ветка подтверждена чтением кода.

### 6. Наблюдение — большой diff OpenAPI допустим как воспроизводимый экспорт

**Место:** `tasks/fbs-operator-flow/openapi/fbs-operations.openapi.json:4032`;
`backend/scripts/export_fbs_openapi.py:20–41`;
`backend/tests/test_fbs_openapi_contract.py:68–77`.

Штатный скрипт фильтрует только `paths` и оставляет все `components`, поэтому
перегенерация включает накопившиеся изменения других моделей. Обычный тест
действительно сравнивает только маршруты.

**Проверено дополнительно без перезаписи JSON:** результат
`_filter_fbs_paths(create_app().openapi())` целиком равен сохранённому JSON,
включая все `components`. Между базой и HEAD добавлен единственный путь
`/operations/fbs-supplies/{supply_id}/markings/sync`; изменённых прежних путей — 0.
Добавлены схемы `InboundIntakeCompleteBody`, `LoosePutawayBody`, `NameLoginBody`,
`PairBegin`, `PairConfirm`, `ProfilePatch`, `ResultBody`, `SortingJobBody`;
удалённых схем нет. Есть изменения существующих схем, в том числе FBS-моделей.

**Риск и решение:** шум затрудняет чтение diff, но технического расхождения
экспорта с приложением не обнаружено. Сужать `components` вручную в WMS-477
не требуется: это нарушило бы точное соответствие штатному генератору.
Проверку полного экспорта можно укрепить отдельной технической правкой;
это не новое обязательное требование данной задачи.

### 7. Наблюдение — нижний пакетный клиент и применение вердикта переиспользованы

**Место:** `backend/app/services/fbs_marking_service.py:1149–1237`;
`backend/app/services/fbs_autopoll_service.py:357–444`.

Кнопка и новая задача используют один `sync_marking_verdicts_batch`, существующие
`fetch_marketplace_orders_meta_batch` и `_sync_order_meta_from_wb`. Второй

**Риск и решение:** две организации обхода потребуют учитывать различие политик
ошибок: старый путь пропускает упавший пакет, новый обязан отменить применение
всех пакетов. Это ограниченное дублирование, не самостоятельный блокер.
Переписывать общий цикл ради формального объединения в рамках WMS-477 не требую:
R7 прямо сохраняет его поведение. Исправление защиты свежести из находки 1
следует делать в общей точке применения.
