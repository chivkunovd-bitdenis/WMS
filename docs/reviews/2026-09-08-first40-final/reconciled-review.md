### R2a. Обязательная часть R2 — порядок блокировок нельзя исправлять только в одной функции

В текущем коде есть следующие последовательности захвата строк:

| Путь | Проверенный порядок |
|---|---|
| Массовая упаковка | `supply → task → lines → orders` — `packaging_task_service.py:1232–1259` |
| Новая печать FBS | `line → pool code → order` при flush и затем `supply` через уведомление — `marking_code_service.py:1604–1612,1710–1723`; `fbs_order_tape_print_service.py:537–553,628–641,342–349`; `fbs_marking_service.py:917–923,1037–1056`; `fbs_packaging_integration_service.py:721–736,665–677` |
| Отвязка КИЗ | `order → marking → line` — `fbs_kiz_service.py:1161–1174` |
| Скан уже назначенного КИЗ | `order → marking → code → line` — `fbs_kiz_service.py:1220–1236,1253–1259` |
| Скан нового КИЗ | `order → line/task/supply → code` — `fbs_kiz_service.py:1220–1236,1270–1277,919–955`; для Ozon аналогичный JOIN в `ozon_kiz_service.py:50–68,195–196` |

Пример обратной зависимости: печать держит строку задания, массовая упаковка уже держит поставку и ждёт строку задания (либо строку задания-задачи, занятую ссылочной проверкой печати); печать затем запрашивает поставку через `_notify_supply_marking_update`. Другой пример: скан/отвязка удерживает заказ и ждёт line, а печать удерживает line и пытается обновить тот же order. Поздний order-lock при WB-сверке не помогает: ожидание начинается уже на сохранении привязки/изменений заказа.

Это проверенная по коду обратная зависимость, а не результат запуска deadlock-теста. Нельзя исправить R2 простым добавлением `order FOR UPDATE` перед line: тогда останется обратный порядок с массовой упаковкой. Нельзя оставлять поздний захват supply после дочерних строк. У JOIN-запросов `_packaging_line_for_order` и Ozon `_packaging_line` стоит `FOR UPDATE` без `OF`, то есть они блокируют также строки присоединённых таблиц; их нельзя считать «блокировкой только line».

**Граница минимального решения:** одна согласованная последовательность существующих строк для пересекающихся операций FBS: сначала поставка, затем задание/строки, затем заказы/привязки/коды. Одинаковые наборы строк блокировать в стабильном порядке по ID, сохраняя прежний порядок этикеток только на этапе формирования результата. Для WB уведомление, которое после блокировки поставки сразу делает no-op (`fbs_packaging_integration_service.py:674–677`), можно завершать без ненужного захвата этой строки. Но это само по себе не решает инверсию order/line у скана и отвязки. После перемещения блокировок обязательно перечитать привязки; read-only discovery идентификаторов до lock не считается свежим состоянием.

Речь о короткой сериализации конкурирующих изменений уже существующих записей, а не о новых бизнес-разрешениях. Не добавлять lease, pending-флаг печати, retry-запрет, ожидание завершения упаковки или выключенную кнопку. Не удалять row-lock строки, уже защищающий обычную печать от двойной выдачи. Не дробить этот участок между двумя параллельными исполнителями: они затрагивают одни и те же функции и порядок блокировок.

**Конкретные проверки пакета R1/R2:** PostgreSQL, два независимых session с заранее загруженными пустыми markings печатают один и тот же заказ из строки потребностью 2 — одна привязка, один расход из пула, второй запрос возвращает тот же code; затем второй заказ получает другой code. Повторить при пуле ровно на оставшуюся потребность, чтобы preflight не помешал повтору. Отдельные барьеры конкуренции: печать/pack-all, печать/скан КИЗ, печать/отвязка — нет взаимного ожидания; снятие/назначение кода отражается в следующем чтении, счётчик строки соответствует сохранённым кодам. Существующий тест печати строки также сохраняет свою защиту. Полный набор тестов здесь не запускать.

### R3. P2 — Ozon-подбор из сортировки исчезает из учёта выбранного короба; Astra №3 подтверждено

**Код:** `backend/app/services/fbs_picking_service.py:225–250,361–379,469–548,1038–1052,1102–1114,1316–1339`; `backend/app/models/fbs_order.py:424–434`; `backend/app/services/pick_option_location_service.py:327–340`.

Если исходное место уже является сортировкой, Ozon не делает transfer: `inventory_movement_id` остаётся NULL. Факт подбора существует, но отдельных полей исходной тары у `FbsOrderProductPick` нет. Новый фильтр требует совпадения тары именно у присоединённого `InventoryMovement`. При NULL никакой короб не совпадает. Получается `active=[]`, хотя товар уже подобран.

Достаточно двух единиц в коробе на сортировке и потребности Ozon 2: `pick/set quantity=1`, затем ещё раз конечное `quantity=1` с новым ключом. Второй запрос добавляет ещё одну единицу; `quantity=0` для того же короба не находит ничего для отмены. Ответ `quantity` берётся из той же неверной группировки, а GET показывает неизвестный источник как «Россыпью». Клиент отправляет конечное количество и выбранную тару (`frontend/src/screens/ff/unload-pick/FfUnloadPickPage.tsx:374–384`); endpoint генерирует новый UUID при отсутствии Idempotency-Key (`backend/app/api/fbs_supplies.py:1339–1355`).

Наличие подбора отдельно от движения подтверждает и `active_fbs_picks_by_source`: NULL Ozon-подборы учитываются как `unlocated`, а не игнорируются (`pick_option_location_service.py:65–67,105–111`). Поэтому проблема не решается объявлением таких записей «устаревшими»: эта ветка создаёт их и сейчас. Регрессия относительно базы — введённое сопоставление строго через движение; прежний запрос находил назначения по месту.

**Минимальная корректная правка:** согласовать источник в `set`, возвращаемом количестве, `pick/scan`, GET и выборе точного `pick_id` для undo. Только `OR movement_id IS NULL` не является полным исправлением: исчезновение из GET и ложное приписывание россыпи останутся, а при двух коробах источник неизвестен.

Для новых прямых подборов точную тару можно хранить в самой существующей записи `FbsOrderProductPick` двумя nullable полями источника, аналогично уже существующему `FbsOrderPick.source_container_kind/source_container_id`. Это запись факта из существующего запроса, без новой таблицы, резерва, журнала расхода или фиктивного движения. Здесь необходимость дополнительных фактических полей доказана: у записи нет движения и нет иного поля, из которого можно восстановить выбранный короб. Существующее реальное движение продолжает давать источник для старых подборов, где оно есть.

Если объём поручения исключает даже эти два поля, допустим ограниченный возврат к прежнему учёту по месту для ветки без движения, но он должен быть одинаковым в GET/set/undo и не изображать точный короб. Старые NULL-записи нельзя автоматически приписывать одному из коробов; точного источника у них нет. Это граница достоверности данных, не повод запретить отмену подбора или двигать склад ради нового идентификатора. Дизайн экрана и WB-подбор менять не требуется для варианта с фактическими полями существующей записи.

**Конкретные проверки:** Ozon, короб на сортировке, потребность 2: `set 1 → set 1 → set 0` с новыми ключами даёт `1 → 1 → 0`, GET и response совпадают, новые movements отсутствуют, склад и резерв неизменны. Два разных короба на одной сортировке не делят один показатель. Обычный Ozon-подбор с реальным движением сохраняет возврат в исходный короб; WB и MP не меняют свою формулу доступности. Для старого NULL-подбора проверить явно выбранный fallback без выдуманной тары.

## Остальные замечания Opus: что делать не требуется

**Мёртвый `packaging_not_done` — подтверждено как старый технический мусор, не средний функциональный дефект.** Остались два значения в API mapper (`backend/app/api/marketplace_unload_requests.py:692,730`) и перевод (`frontend/src/utils/readApiErrorMessage.ts:31`). Поиск рабочего backend/frontend не нашёл производителя этой ошибки. Маппер сам не блокирует операцию и не является новой сущностью. Удаление трёх строк допустимо как небольшая чистка рядом с R4, но не является обязательным условием staging и не требует отдельного согласования дизайна. Не возвращать производство ошибки ради имеющегося перевода.

**WMS-115/110 только WB — подтверждённая и прямо согласованная граница, не недоделка этой пачки.** Фильтры находятся в `fbs_cancelled_after_pack_service.py:198,476`, клиентская ветка — `FfFbsSupplyWorkspace.tsx:1314` и `FfFbsOrdersScreen.tsx:1227–1230`. Не снимать фильтр `wb` ради симметрии. Расширение Ozon может быть отдельным решением владельца, но для завершения текущей пачки новый вопрос владельцу не требуется.

**WMS-391, внешние sorted/done — существующий fallback подтверждён, описание Opus о `now()` неверно.** `record_fbs_order_confirmed` допускает эти статусы без локальной передачи (`fbs_order_billing_service.py:94–109`); вызывается также WB/Ozon-синхронизацией (`wb_marketplace_orders_service.py:786–809`, `ozon_fbs_sync_service.py:745–760`). Но `order_work_moment` выбирает `packed_at`, затем `picked_at`, затем `created_at_wb` (`fbs_order_billing_service.py:67–83`); последнее поле в модели обязательно (`backend/app/models/fbs_order.py:238`). У нормальной сохранённой строки отсутствие локальной передачи не означает `now()`.

Diff подтверждает, что этот fallback и тарификация sorted/done были в базе; пачка добавляет подтверждённый in_delivery и дату handover, не создаёт старый путь заново. Постановка прямо просит добавить in_delivery к sorted/done (`docs/KANONICHESKIY_BACKLOG.md:584–590`). Поэтому не удалять старую тарификацию и не переписывать прошлые деньги в рамках замечания Opus. Если владелец отдельно потребует начислять абсолютно все внешние sorted/done только при наличии нашей передачи, это отдельное уточнение правил для старого пути; нынешнее замечание не доказывает новую регрессию. Формулировку «никакой импортированный статус сам по себе не начисляет» использовать нельзя: guard охватывает именно in_delivery.

**«Ozon сначала коммитит confirmed, потом списывает» — отклонено, ветки перепутаны.** В `_persist_confirmed_delivery` Ozon (`source_plan is None`) выполняет `_apply_local_delivered → mark_deliver_operation_confirmed → commit` (`fbs_shipment_service.py:1691–1705`). Фактический вызов из `_finish_ozon_delivery` не передаёт source_plan (`:2167`). WB выполняет сохранение источников и confirmed, первый commit, затем local apply и второй commit (`:1707–1730`). WB-восстановление и сохранение прежнего confirmed_at как раз проверяются сценарием `local_error` (`backend/tests/test_fbs_handover_billing.py:37–54,99–143`). Поэтому заявленного Opus окна именно у Ozon здесь нет. Не менять порядок транзакций или просить отдельный Ozon-retry только на основании этого ошибочного объяснения. Существующие промежуточные Ozon snapshots — иной механизм (`fbs_shipment_service.py:1798–1813`), сам по себе он не подтверждает замечание.

## Информационные пункты и ограничения обоих отчётов

`total` действительно считается только при поиске (`fbs_worklist_service.py:312–317`); исправление не требуется. Фильтр `MarkingCode.source == pool` действительно снят в `_ledger_filtered_stmt` (`marking_code_service.py:2746–2783`) при сохранённом tenant-фильтре; это соответствует отчётному объёму WMS-084 (`docs/KANONICHESKIY_BACKLOG.md:901–904`). У Opus название `_gate_ledger_filtered_stmt` и строка 2704 неточны, сам вывод о включении external-событий подтверждён.

Частичные статусы WMS-084/087/275 и решение о WMS-013 не превращать в «сделано». WMS-217 вообще не входит в замороженные актуальные 40: состав явно заменяет его на позднее добавленные задачи (`docs/KANONICHESKIY_BACKLOG.md:112–120`). Не расширять пачку только из-за упоминания WMS-217 в информационном списке Opus. WMS-277 остаётся без расписания до решения о частоте/охвате (`:128`).

Граница WMS-272 в Astra подтверждена: ожидающие возвращают read-only соединение через rollback (`marketplace_seller_lock_service.py:49–62`); владелец create держит ту же сессию до unlock (`:65–94`, `fbs_supply_service.py:586–596`). Resume завершает транзакцию перед HTTP и обновляет ORM после ответа (`fbs_supply_service.py:940–971,989–996,1026–1034`). Это не полное освобождение соединения create-владельца; не вводить новый механизм блокирования ради повышения статуса задачи.

Правило `assembling → picking` не восстановлено: `_compute_stage` выбирает поверхность по фактическому подбору/коробам, а `_compute_workspace_blockers` возвращает пустой список (`fbs_workspace_service.py:381–440`). Но общий вывод Opus «упаковка ничего не блокирует» отвергается R1. Его положительные выводы об отдельных удалённых складских вызовах не опровергают оставшийся запрет печати.

Исторические apply WMS-047/048/013, физическое перемещение кодов WMS-084, изменение секретов, live-WB/Ozon операции и production-деплой этим отчётом не разрешаются. Утверждение Opus «WMS-393 уже на проде» не подтверждалось мной; наличие записи в каноне и кода не является свежей проверкой production SHA. Эту проверку ведёт оркестратор отдельно.

Эти три пакета можно выполнять одновременно: у них нет общих исходных файлов при указанном владении (пакет 1 не меняет `fbs_order.py`). Канон/итоги обновляет один оркестратор после интеграции; статусы должны отражать новый SHA и фактически выполненную проверку. Перечень пакетов — состав исполнения существующих WMS-номеров, не новый бэклог. Результаты исправлений нужно сохранить отдельными коммитами в постоянных именованных ветках, после объединения пройти требуемый технический гейт и ручные операторские действия; этот отчёт не заменяет ни commit/push, ни CI, ни staging SHA, ни браузерную приёмку.
