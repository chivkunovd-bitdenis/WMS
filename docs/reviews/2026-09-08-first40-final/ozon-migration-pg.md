## Наблюдения в PostgreSQL

После первого и повторного upgrade information_schema показывает:

| Поле | Тип | nullable | default |
|---|---|---|---|
| source_container_kind | varchar(16) | YES | NULL / отсутствует |
| source_container_id | uuid | YES | NULL / отсутствует |

У старой строки оба новых поля и inventory_movement_id остаются NULL. После downgrade новые колонки отсутствуют, все прежние поля строки совпадают с baseline. После повторного upgrade они вновь появляются с NULL.

На каждом этапе сравниваются все сохранённые строки 105 таблиц (исключая служебную alembic_version; для целевой таблицы при upgrade из сравнения вычитаются ровно два новых NULL-поля). Во всех 12 непустых таблицах строки полностью совпали с исходными. Пустые таблицы остались пустыми. В частности:

- inventory_balances: одна прежняя строка, quantity9, unpacked9, packed0;
- inventory_movements: одно прежнее движение +9 inbound, нового движения нет;
- fbs_order_product_reservations: один прежний резерв quantity2;
- все остальные резервы/упаковочные таблицы остаются в исходном состоянии.

Дополнительно у старой строки на всех этапах совпали PostgreSQL ctid и xmin (положение строки и версия её записи), у таблицы совпал relfilenode (физический файл). На этой БД nullable ADD/DROP не переписал старую строку/таблицу.

Сгенерированный Alembic SQL содержит только два `ALTER TABLE ... ADD COLUMN` без DEFAULT/NOT NULL и обновление номера alembic_version. В миграции нет DML по прикладным данным, backfill, новых таблиц/резервов/журналов. Поэтому nullable DDL не требует придумывать тару для старых NULL-movement подборов и не перемещает их товар.

Downgrade удаляет два новых столбца по своему DDL; эта проверка сохранности относится к прежним данным со значениями NULL. Сохранность новых ненулевых значений provenance при DROP COLUMN не утверждается.
