## 1. P1 — «Всё упаковано» по-прежнему запрещает первую печать ЧЗ

**Происхождение:** сохраняющийся дефект внутри прямо обязательной WMS-392; сам запрет существовал до этой пачки. Он не выдаётся за новую строку регрессии.

**Основное место:** `backend/app/services/marking_code_service.py:1618–1619`. Связанные места: `backend/app/services/packaging_task_service.py:1294–1295,1331`; `backend/app/services/fbs_order_tape_print_service.py:503–537`; `frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx:1806–1807,2046`.

У WB-поставки с требуемым ЧЗ и ещё не назначенным кодом оператор может нажать «Всё упаковано»: проверка наличия маркировки здесь выполняется только для не-WB, после чего задание становится `done`. Кнопка «Печать ЧЗ и ШК» остаётся доступной. Её путь через `POST /operations/fbs-supplies/{id}/order-print-tape` вызывает `_print_or_reprint_order_code`; при отсутствии прежней привязки он вызывает `print_codes_for_packaging_line`. Эта функция разрешает только `draft`/`in_progress` и отвергает завершённое задание с `task_not_active` до выдачи кода. Сервис ленты превращает это в ошибку конкретного заказа (`fbs_order_tape_print_service.py:323–330`); код для него не возвращается.

Воспроизводимый вход: активная WB-поставка, задание упаковки, один заказ с обязательным ЧЗ, свободный подходящий код в пуле, отсутствие `FbsOrderMarking`; сначала `pack-all-and-complete`, затем `order-print-tape` с `reprint=false`, раскладкой ЧЗ и этим заказом. Получается отказ из-за выполненной упаковки, хотя прямой контракт WMS-392 запрещает упаковке блокировать печать. Для уже назначенного pool-кода обход через ранний возврат существует, поэтому проверка одной перепечатки этого дефекта не выявляет.

**Минимальное исправление:** убрать зависимость допустимости FBS-печати от состояния завершения упаковки. Сохранить проверки принадлежности кода, потребности и фактической отмены документа; не добавлять стадию, навигационный запрет или требование переоткрыть упаковку. Отдельно проверить этот же вызов для обычных заданий: общий guard также стоит до ветки перепечатки.

## 2. P1 — блокировка строки упаковки не закрыла гонку печати одного FBS-заказа

**Происхождение:** незакрытый существующий дефект в объёме WMS-080. Новая блокировка правильно обновляет общий счётчик строки, но не охватывает уже загруженную привязку конкретного заказа. Это не утверждение, что новая блокировка сама создала гонку.

**Основное место:** `backend/app/services/marking_code_service.py:1604–1612` вместе с `backend/app/services/fbs_order_tape_print_service.py:503–537`. Доказательная цепочка: загрузка `order.markings` в `fbs_order_tape_print_service.py:405–420`; повторная проверка той же коллекции и INSERT в `:606–621`; ограничения модели `backend/app/models/fbs_order.py:448–469`; commit endpoint в `backend/app/api/fbs_supplies.py:1959`.

Воспроизводимый вход: два ещё немаркированных WB-заказа одного товара в одной строке упаковки с потребностью 2 и не менее двух доступных кодов. Два запроса `order-print-tape` одновременно печатают **один и тот же первый заказ**, с `include_order_qr=false`, `reprint=false`. Оба успевают загрузить пустую `order.markings` до завершения первого запроса.

Первый запрос получает блокировку строки, печатает код A, привязывает его к заказу и фиксирует транзакцию. Второй ждёт строку и затем действительно перечитывает `qty_marking_printed=1`; однако общая потребность равна 2, поэтому выдача ещё одного кода допустима для строки. Ранее загруженная коллекция `order.markings` второго запроса не перечитывается: решение об отсутствии привязки уже принято на строке 503, а `_assign_printed_code_to_order` снова использует ту же старую коллекцию. В итоге он выдаёт B и вставляет вторую привязку того же вида тому же заказу. Ограничение `(order_id, kind, value)` допускает две разные величины A/B, а уникальность по самому коду этому не препятствует. Более позднее получение блокировки заказа при WB-синхронизации происходит после выдачи и INSERT и не отменяет их.

**Последствие:** повторная печать одного заказа расходует новый код; оба кода оказываются связанными с первым заказом, общий счётчик печати исчерпывает потребность строки, хотя второй заказ ещё не получил своего ЧЗ. Это именно денежный и операционный дефект, ради которого поставлена WMS-080. Добавленная PostgreSQL-проверка `backend/tests/test_marking_print_pool.py:278–336` вызывает нижний сервис строки напрямую и не охватывает stale-коллекцию конкретного FBS-заказа.

**Минимальное исправление:** включить проверку существующей привязки FBS-заказа в ту же сериализованную операцию: после ожидания существующей блокировки перечитать актуальную привязку **до** выделения нового кода и вернуть уже назначенный код, если первый запрос его создал. Согласовать порядок уже существующих row-lock, не вводить отдельный lease, счётчик, сущность или запрет оператору повторить печать.

## 3. P2 — новый фильтр тары теряет Ozon-подбор непосредственно из сортировки

**Происхождение:** новая регрессия изменений подбора WMS-058. Отсутствие сохранённой тары у Ozon-подбора без движения существовало раньше; именно новый обязательный фильтр превращает это ограничение в потерю существующего назначения для `set`/`undo`.

**Основное место:** `backend/app/services/fbs_picking_service.py:367–372`. Связанные места: `:225–250,469–532,540–548,1050–1052,1104–1114`; `backend/app/models/fbs_order.py:424–434`; endpoint `backend/app/api/fbs_supplies.py:1345–1355`.

При Ozon-подборе из короба, стоящего в самой ячейке сортировки, `scan_pick_product` закономерно не делает перемещения между ячейками: условие на строке 1051 требует, чтобы исходная ячейка отличалась от сортировки. Сохраняется действующий `FbsOrderProductPick` с `inventory_movement_id=NULL`. В модели этого факта нет отдельных полей исходного контейнера. Новый `_active_assignments_for_product_location` связывает тару только через `InventoryMovement` и требует равенства его `container_kind/container_id` выбранному коробу. Для такого действующего подбора обе колонки JOIN равны NULL, поэтому он исключается из `active`.

Конкретная последовательность: на сортировке в коробе есть минимум 2 доступные единицы; Ozon-позиция требует 2. Первый `pick/set` с этим коробом и конечным `quantity=1` создаёт один подбор. Повторный операторский ввод конечного `quantity=1` с новым ключом снова видит `active=[]` и добавляет вторую единицу вместо сохранения количества 1. Запрос с `quantity=0` к тому же коробу ничего не отменяет: `current_quantity` тоже равен 0. Выходное `quantity` и `get_pick_options` также не показывают этот подбор у выбранного короба, потому что новая группировка помещает NULL-движение в ключ россыпи. До добавления контейнерного фильтра `active` находил его по месту.

Этот сценарий доступен существующему клиенту: `frontend/src/screens/ff/unload-pick/FfUnloadPickPage.tsx:374–384` посылает именно конечное количество и выбранную тару, без постоянного `Idempotency-Key`; сервер создаёт ключ для каждого такого запроса. Здесь нельзя отождествлять отсутствие движения с отсутствием подбора.

**Минимальное исправление:** явно сохранить рабочую обработку Ozon-назначений без движения в согласованных `get-pick-options`/`set`/`undo`; для этой уже существующей ветки допустим прежний учёт по месту, без ложного заявления о точном контейнере. Назначения, у которых реальное движение есть, продолжать сопоставлять с его исходной тарой. Не создавать фиктивное складское движение или дополнительный резерв только ради идентификатора. Строгий учёт короба в ветке без движения требует отдельно решить сохранение фактического источника; текущий NULL-фильтр такую задачу не решает.
