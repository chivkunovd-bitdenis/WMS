# WMS-058 — сохранить источник при подтверждении сверх плана

База: `8cc97a07e6a8fa89e9506f7b79ef2474eb8a735b`, изолированная ветка
`codex/wms058-overplan-source`. Производственный diff ограничен
`frontend/src/screens/ff/FfMarketplaceUnloadBoxAddDialog.tsx`. Backend, FBS,
разметка, размеры и текст существующего диалога не менялись.

В исходном компоненте воспроизведена последовательность: выбор A → POST товара P
из A, ожидающий ответ → поставленный в очередь B → 422 `plan_limit_exceeded` →
подтверждение. Получились POST P с `container_id=A`, затем выбор B, затем POST P
с `allow_over_plan=true`, но уже `container_id=B` и другой ячейкой. Причина:
ожидание решения не удерживало очередь, сохранялся только barcode, а повтор
заново читал `sourceRef`. Маршрут `scan_marketplace_unload_box` передаёт именно
полученные location/container в `scan_barcode_into_box` и далее
`add_manual_qty_to_box`: сервер не может восстановить потерянный выбор A.

Теперь элемент очереди ждёт решения оператора. Его локальное тело POST сохраняет
barcode, product_id, quantity, ячейку и контейнер; подтверждение меняет только
`allow_over_plan`. Следующий скан не выполняется и следующий отказ не подменяет
подтверждение. Источник по-прежнему определяется при исполнении элемента:
уже поставленный в очередь товар после ещё не завершившегося скана A увидит A.

Отмена и Escape завершают ожидание без повтора товара и освобождают очередь.
Закрытие, размонтирование, смена request/box, прав или токена инвалидируют старую
сессию сканирования и освобождают решение. Старые элементы после этого не
отправляются; новая сессия начинает отдельную очередь с очищенным источником.
Ответ старого HTTP не открывает подтверждение и не меняет источник нового
диалога. Уже отправленный запрос нельзя объявить отменённым на сервере:
поздний успешный ответ вызывает перечитывание через существующий `onUpdated`.
Это ограничение честно сохраняется, отката складских операций на клиенте нет.

## Проверка

Одноразовый скрипт `scripts/wms058-overplan-source.cjs` собирает **настоящий
React-компонент** существующим esbuild в памяти и открывает его в установленном
Chrome. Все HTTP-ответы синтетические; обращения к staging/production,
токены и складские данные отсутствуют. Это регрессия поведения клиента,
не проверка реального списания. Новые зависимости и сервер тестов не добавлены.
Браузер и контексты закрываются в `finally`.

На исходнике сначала выполнен `--baseline`, который подтвердил подмену A→B.
После исправления прошли восемь сценариев: подтверждение с точным сравнением
обоих POST; отмена перед следующим отказом Q; тот же путь через Escape;
закрытие при открытом подтверждении; закрытие и повторное открытие до позднего
422; смена request; смена box; размонтирование. Последующие новые сканы
выполнялись, старые — нет; новый диалог не наследовал A. Во всех сценариях товар
P был поставлен в очередь ещё до ответа выбора A, что проверяет нужный порядок
определения источника. Ошибок JavaScript не было.

Команды из `frontend`:

```sh
node ../docs/reviews/scripts/wms058-overplan-source.cjs
./node_modules/.bin/tsc --noEmit -p tsconfig.app.json
npm run build
```

TypeScript и production build прошли на существующем node_modules. Полный
pytest и установка зависимостей не выполнялись. Проверку с настоящим ответом
staging и настоящими остатками отдельно выполняет Parfit; её результат этот
локальный отчёт не подменяет. Деплой данным коммитом не выполнялся.
