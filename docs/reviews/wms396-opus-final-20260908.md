### Проверка шести принятых исправлений

1. **Отмена ошибочной привязки до завершения.** `delete_code` (`inbound_marking_service.py:310–397`) блокирует запрос `for_update`, требует `RECEIVING_STATUSES`, ловит `own` события по `request_id`, отдельно проверяет `is_printed_pool = source in {pool,pool_id set} AND status="printed"`. Для собственного печатного пула удаляется только событие (код сохраняется вместе с `source/status/pool/printed_*/introduced_at`); для внешнего FBS-кода — событие + сам код после барьеров `packaging_task_line_id`, `reserved_*`, `transferred_at`, `consumed_at`, `replaced_by_code_id`, `FbsOrderMarking`, `MarkingReprintRequest`, `MarkingCode.replaced_by_code_id`. `attach_code` больше не пишет `code.product_id` (строка снята после проверки `not in (None, product.id)`), так что печатному коду не переписывается product. API-роут `DELETE /marking-codes/{code_id}` мапит `marking_code_not_found → 404` через дополненный `_error`. Фронт: `remove` в хуке использует `epoch`/`readSequence` идентично `load`, поэтому конкурентный поллинг не воскрешает удалённую строку, кнопка `CloseOutlined` появляется только в `receivingActive && isFulfillmentAdmin`, disabled по `busy || removingCodeId !== null`, ставится в `receivingScanQueue`. В `App.tsx:3650` проп `isFulfillmentAdmin={canReceptionOps}`, то есть кнопка доступна и админам, и FF-staff с `reception` (что подтверждает адъюдикация про отклонённый staff-prop).

2. **Печатный пул только для инспекции.** В `attach_code:249–274` пуловый код с `status="printed"` пропускается только если он «чист»: нет `packaging_task_line_id`, `reserved_*`, `consumed_at`, `transferred_at`, `replaced_by_code_id` и нет `FbsOrderMarking.marking_code_id`. Иначе — `marking_code_already_used`. Для `status != "printed"` — `marking_code_in_pool`. `is_unbound_received_code` (`marking_code_service.py:3705–3730`) остался жёстко на `source == "external_fbs"` — исключение FBS не расширено на пул.

3. **Green только при `verified is True`.** `interpret_check:419–424` требует одновременно `outer == "INTRODUCED"`, `checkResult is True`, `resolved.get("verified") is True`. `resolved = {}` при отсутствии/некорректном `codeResolveData` (строка 411) → пропущенное `verified` даёт None → падение в дефолт `unavailable`. Параметрический `test_green_requires_explicit_verified_true` фиксирует случаи `None, {}, {"verified": None}, {"verified": 1}`.

4. **Auto сохраняет ответы, ручной перечекивает всё.** `schedule_check` получил `*, force: bool = False`; при `force=False` (`schedule_after_posting`) фильтрует события по `.cz_check.status in {None, "pending"}`, и если пустой набор — коммитит без создания job. При `force=True` (`_schedule` из `check_codes` API) обходит фильтр и переводит все события в pending, создавая новый job. Барьер по активному job на ≤1 ч сохранён.

5. **Добор pending внутри работающего job.** `_run_check_job` теперь оборачивает per-event цикл во внешний `while True`: каждая итерация под коротким `req` FOR UPDATE считывает pending-события; пустой батч → `job.done + finished_at + return`. Внутри per-event цикл дважды проверяет `_meta(event).cz_check.status in {None, "pending"}` (до HTTP и после, под FOR UPDATE на MarkingCodeEvent), так что пришедший позднее ответ ЧЗ не затирает свежий (в т.ч. ручной). Тест `test_deletion_during_check_and_rescan_are_drained_without_stuck_job` показывает, что новый код, добавленный во время исполнения, обрабатывается, а старое удалённое событие — пропускается (session.get → None → continue) без застревания job.

6. **Failed фиксируется независимо от восстановления событий.** `run_check_job:544–574` сначала `commit` job.failed + finished_at + error_message, затем во внутреннем try/except пытается перевести оставшиеся pending события в `unavailable`; исключение (в т.ч. `request_not_found` из удалённой приёмки) откатывает вложенный TX и логирует warning, но не отбрасывает уже закоммиченный failed. Дополнительно `_active_job` проверка не даёт затирать pending-снапшот более свежего перезапуска. `test_failed_job_is_persisted_when_receipt_was_deleted` покрывает.

**Skip удалённого события в воркере** — оба места (`session.get(MarkingCodeEvent) is None` перед HTTP и `session.scalar(... with_for_update) is None` перед записью) корректно ведут `continue`. **UI мини-кнопка** — размер `small`, `CloseOutlined`, `aria-label`, tooltip. Дизайн экрана и колонки не тронуты. Кнопка «Повторить проверку ЧЗ» видима теперь при `receptionClosed && marking.items.some(cz_status !== 'introduced')` — покрывает problem/unavailable/pending, не только два прежних. Никаких навигационных ворот, изменения остатков или резервов приёмка/удаление не делают.

### Найденные замечания

- **P2 · `remove` не рефрешит `checking`.** Место: `frontend/src/screens/ff/useInboundMarkingCodes.ts:68–86`. Триггер: удаление последнего pending-события; `data.checking=true` остаётся до следующего 2-секундного тика поллера, потому что после успешного DELETE вызывается только `setData(items.filter)`, но не `load()`. Вред косметический — минимум 0, максимум ~2 с ложного `Проверяем коды в Честном знаке…`. Минимальный фикс: `await load()` в успехе `remove` внутри `epoch === generation.current`.
- **P2 · `check_codes` (ручной recheck) при активном job молча no-op.** Место: `backend/app/services/inbound_marking_service.py:441–445` + `backend/app/api/inbound_marking.py:106–117`. Триггер: кнопка «Повторить проверку ЧЗ» кликнута, пока предыдущий job активен и младше часа — `schedule_check` возвращает None, роут возвращает `{"checking": true}` без перезагрузки статусов. Кнопка в UI disabled по `marking.checking`, так что реален только редкий race. Минимальный фикс не обязателен: адъюдикация специально запретила плодить сущности; текущее поведение согласуется с идемпотентностью.
- **P2 · `_run_check_job` кратковременно держит `SELECT ... FOR UPDATE` на request между батчами.** Место: `inbound_marking_service.py:487–504`. Триггер: активная проверка одновременно с быстрым сканом/удалением; операторский `attach_code`/`delete_code` ждёт на локе. Практически лок берётся на миллисекунды между итерациями внешнего while, и `attach_code` уже брал тот же лок в базовой линии, — существенной задержки не измерено. Минимального исправления не требую.

Ни одного P0/P1 в изменённых участках не подтверждено. Отсутствие композитного индекса `(tenant_id, event_type, document_number)` из отчётов Opus/Astra остаётся baseline вне задачи. Отклонённые в адъюдикации замечания (staff-prop, sorting-панель, «other line same product») не воспроизвожу.
