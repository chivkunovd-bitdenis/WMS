## P1-R1. Частично собранный исторический документ перестаёт учитывать новые единицы

**Строки:** `backend/app/services/packaging_task_service.py:707–712` полностью пропускает пересчёт товара при наличии хотя бы одного NULL box marker. При доподборе `backend/app/services/marketplace_unload_collect_service.py:396–400` оставляет marker существующей строки короба NULL и не сохраняет отдельно известное происхождение добавленной части.

**Воспроизведение:** план3, исторические allocation1/box1 с NULL marker, правомерно confirmed1/work0; оставшиеся2 unpacked ещё находятся в источнике. Реальный `collect_into_box(quantity=2)` добавляет их в тот же короб и расходует остаток. Получены allocation3 и box3, но sync оставляет confirmed1/work0/qty_done1. `complete_task` отвечает `packaging_incomplete`, хотя все3 уже собраны и новая работа2 выполнена.

```json
{"case":"historical-partial-plus-new-unpacked","expected":{"confirmed":1,"work":2,"total":3},"after":{"confirmed":1,"work":0,"total":1,"alloc":[3,0],"balance":[0,0]},"complete":"packaging_incomplete"}
```

Ноль в `alloc[1]` диагностического снимка — результат агрегирования sum(NULL) через coalesce; реальные исторические markers остаются NULL. Требования R5/R12, C5m/C17: сохранить историческое доказанное количество и учитывать фактические новые операции. Полный пропуск пересчёта убирает возможность завершить обычный частичный документ; новый запрет или принудительное пересоздание документа не требуются.

## P1-R2. Один исторический allocation дважды расходуется внутри одного возврата

**Строки:** `backend/app/services/marketplace_unload_collect_service.py:780–793`. Для unknown allocation обычная ветка считает всё количество unpacked и вызывает `take_from`; затем ветка NULL вычисляет `unknown_available` из `already_taken`, сохранённого **до** первого take. Одна и та же единица снова доступна в том же проходе цикла.

**Воспроизведение:** исторические allocation A2 и box2 с NULL marker; дополнительно реально подобрать fresh unpacked1 из B в тот же короб. Сохранённый итог: box3 NULL, allocation A2 NULL и B1 known0. Удалить все3 из короба. Из крупнейшего A2 обычная ветка забирает2, затем NULL-ветка ещё1. Возврат кладёт A3, удаляет allocation A, но оставляет allocation B1; box уже удалён. Ожидались возврат A2/B1 и отсутствие подбора. Следующая операция продолжает видеть лишнюю подобранную единицу помимо возвращённых3.

```json
{"case":"historical-unknown-removal","expected_alloc":0,"remaining_alloc":1,"returned_total":3,"return_A":3,"return_B":0}
```

Подтверждена несогласованность `остаток + подобранное`: до возврата3, после возврата4. Это не утверждение о создании четвёртой строки InventoryMovement; ошибка — двойное использование части источника и сохранившийся ложный allocation. Требования R5/R12, C5m/C17. Нужно исключить повторное использование одного количества внутри возврата и повторить именно этот сценарий; ограничивать законные операции не требуется.
