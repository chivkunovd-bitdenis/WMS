## F1 — P1: старый локальный выбор затирает свежий документ из кабинета

`backend/app/services/ozon_exemplar_documents_service.py:209–216,575` и
`backend/app/services/ozon_fbs_process_service.py:520` накладывают **весь**
накопленный `choices` на свежий полный ответ create-or-get. После завершения
операции старые choices остаются. Поэтому после принятия ГТД A в WMS, исправления
A в кабинете и сохранения документа B либо сканирования КИЗ WMS возвращает A
к старому значению. Это нарушает R3/R5: соседние документы из актуального ответа
должны сохраняться, изменяется только явный текущий выбор.

Независимая локальная проба вызвала настоящую `apply_saved_documents`:
remote exemplar 81 содержал `gtd=NEW-CABINET`, `rnpt=NEW-RNPT`, оба absent=false;
старый choices для того же экземпляра содержал `gtd=OLD-WMS`, пустой rnpt,
is_rnpt_absent=true. Фактический результат:

```text
gtd=OLD-WMS, rnpt='', is_gtd_absent=False, is_rnpt_absent=True
```

Исправление должно различать незавершённое намерение текущей операции и историю
уже принятых значений. Добавить проверку «принято в WMS → изменено в кабинете →
запись другого экземпляра/КИЗ», включая неизменность обоих документов соседа.

## F2 — P1: кнопка проверки не обновляет сохранённый запрет редактирования

`backend/app/services/ozon_exemplar_documents_service.py:258–328` обращается к
Ozon только для pending-state либо при отсутствии snapshot. Первое открытие
со статусом update_not_available сохраняет snapshot и state=editable.
Любой последующий GET возвращает этот сохранённый результат без внешнего чтения.
UI «Проверить в Ozon» вызывает именно GET. Поля остаются disabled, а `/prepare`
и claim также запрещены сохранённым update_not_available. Даже когда площадка
разрешила правку, оператор не может снять этот запрет штатным действием.
Аналогично отклонённый результат не перечитывается кнопкой проверки.
Нарушены R8/R9 и сценарий C8 с переходом к update_available.

Независимая локальная проба настоящей `get_exemplar_documents` с подменой только
загрузки заказа/представления и счётчиком fake-provider дала:

```text
state=editable, stored status=update_not_available, snapshot exists
GET result: editable=False, status=update_not_available; provider_calls=0
```

Явная проверка должна читать текущий статус даже после rejected/editable/accepted,
сохраняя локальный ввод и защиту от устаревшего ответа. Нужна проверка полного
перехода через GET, а не только чистой функции классификации статуса.

## F3 — P2: принятые документы отключают продолжение последовательного сканирования

`backend/app/services/ozon_exemplar_documents_service.py:79–87` разрешает следующий
КИЗ после подтверждённого set с validation_in_process только при пустом choices.
После любого сохранённого документа choices больше не пуст. Последовательность:
документы приняты → первый КИЗ получает set=200 и validation_in_process → второй
КИЗ получает 409 до отправки, хотя незавершённого HTTP writer уже нет. Аналогичный
заказ без истории документов продолжает сканирование. Это регрессия непрерывной
упаковки, связанная именно с добавлением документов (R12/R15).

Локальная проба настоящей `claim_exemplar_write` с подменённой загрузкой заказа:
kind=marking, state=checking, in_flight=false, set_acknowledged=true и непустой
choices дала `ozon_exemplar_documents_conflict`, HTTP 409. Нужна регрессия с двумя
последовательными КИЗ после принятой ГТД; сохранить защиту unknown и одновременно
работающего writer, не разрешать слепой повтор неопределённой записи.
