## 2. Подтверждённые дефекты

1. **Набор инструментов модели не ограничен только чтением.**  
   В [wms_assistant_agent.py:351](tools/assistant-agent/wms_assistant_agent.py:351) передаётся `--tools Read,Grep,Glob`, но отсутствует ограничение подключённых MCP-инструментов — инструментов внешних сервисов. Согласно [официальному описанию CLI](https://code.claude.com/docs/en/cli-reference), `--tools` ограничивает встроенные инструменты и не отключает MCP.

   Условие воспроизведения: запуск в окружении Claude Code с уже настроенным и разрешённым MCP-инструментом записи. Собранная скриптом команда оставляет этот дополнительный канал доступным. Подтверждено чтением команды и документации; фактическую операцию записи через модель я не выполнял. Заявление README о физически гарантированном режиме «только чтение» неверно. **R9, R18; C14.**

2. **Фильтр пропускает запрещённое содержимое и отклоняет нормальный ответ по кнопкам.**  
   [assistant_safety.py:35](backend/app/services/assistant_safety.py:35), идентичная копия — в исполнителе.

   Проверками функций подтверждено, что фильтр пропускает:

   - блок Python, оформленный четырьмя пробелами: `Вот пример:\n\n    def post_supply():\n        return True`;
   - многострочный SQL: `SELECT\n id,\n email\nFROM users`;
   - текст `Таблица assistant_messages; функция submit_executor_result`;
   - синтетическую строку вида ключа `sk-…`, разделённую невидимыми символами U+200B.

   Первые два примера дополнительно переданы в настоящий `submit_executor_result` на SQLite в памяти: **оба сохранены без замены**. Обратная ошибка: нормальный ответ «Откройте `Создать` (кнопка справа).» заменяется отказом. Шаблон инлайн-кода начинает новое совпадение с закрывающей обратной кавычки и захватывает следующую скобку. Последствия — раскрытие технического содержимого и отказ на обычную инструкцию. **R12, R17; C12–C13.**

3. **Непроверенный вывод модели записывается в Git раньше фильтрации.**  
   В [wms_assistant_agent.py:632](tools/assistant-agent/wms_assistant_agent.py:632) карточка публикуется с `backlog_summary` либо исходным `answer_text`. `sanitize_answer` вызывается только после этого, на строке 646, и содержимое карточки не проверяет.

   Воспроизведено с подменёнными внешними вызовами: ответ с `needs_backlog_card=true` и `backlog_summary="SELECT * FROM users"` передал этот SQL без изменений в функцию регистрации карточки. Поэтому безопасный ответ в чате не означает, что запрещённый вывод модели не сохранён в репозитории. Это относится к выводу модели, а не к требуемому дословному сохранению пользовательского обращения. **R17; запрет в instruction.md:145–153.**

4. **После первой опубликованной карточки следующая регистрация упирается в переключение ветки.**

Во втором запуске файл уже локально изменён относительно `etalon`, а целевая ветка содержит первую карточку в этом же файле. Переключение отклоняется из-за несохранённых изменений — это подтверждается порядком операций и [правилом Git checkout](https://git-scm.com/docs/git-checkout). Реальную запись Git в этой песочнице я не выполнял.

7. **Одновременные результаты перезаписывают друг друга.**  
   В [assistant_service.py:301](backend/app/services/assistant_service.py:301) проверка наличия ответа выполняется по прочитанному объекту, после чего идёт обычное обновление без условия «ответ ещё отсутствует».

   Воспроизведено на настоящем сервисе и SQLite в памяти: две сессии прочитали сообщение без ответа; первая сохранила «Первый ответ» / `WMS-900`, вторая — «Второй ответ» / `WMS-901`. **Оба вызова приняты, второй результат заменил первый.** Последовательный тест повторного `/result` этого не обнаруживает.

   Пересечение исполнителей предусмотрено самой схемой возврата в очередь; дополнительно сервер освобождает захват через три минуты, а CLI разрешено работать пять минут, ещё без учёта Git-операций. **R10; C16.**

8. **Таймауты и часть невалидных ответов завершают исполнителя целиком.**

   Следовательно, после такого сбоя скрипт перестаёт опрашивать очередь. В поставке нет запуска через службу с автоматическим восстановлением; описанный запуск — обычный процесс в терминале. Ненулевой код выхода CLI и текстовый не-JSON CLI обработаны, но перечисленные случаи — нет. **R10, R22; C16, C19.**

9. **Копия кода не обновляется до версии, работающей у пользователя.**  
   [wms_assistant_agent.py:203](tools/assistant-agent/wms_assistant_agent.py:203).

   Сценарий: локальный `etalon` указывает на A, в удалённой ветке и на сервере уже B. `prepare_code_checkout` клонирует локальный репозиторий, меняет адрес `origin`, но не получает из него новые коммиты. При отсутствии версии читает локальный A; при явно переданном B, которого локально нет, завершает checkout ошибкой. Простая смена URL репозитория его содержимое не обновляет.

   Обычные вопросы проходят именно этот путь, без `fetch`, который есть в отдельной процедуре нумерации карточек. Ответы основаны на старом коде либо не формируются после обновления сервера. **R9; C21.**

10. **Номер задачи выдаётся даже после неудачного чтения актуальных веток.**  
    В [wms_assistant_agent.py:413](tools/assistant-agent/wms_assistant_agent.py:413) результат `fetch --all` игнорируется; ошибки перечисления и чтения веток также не останавливают выделение номера.

    Проверка: `fetch` возвращает ошибку сети, локальный максимум — `WMS-500`. Функция всё равно возвращает `501`. Если `WMS-501` уже существует в ещё не полученной ветке, номер занят. Последующий успешный `fetch` при публикации карточки не вызывает повторного расчёта. Ошибка воспроизводится без одновременного создания задач — достаточно временного отказа первого получения веток. **R15, решение 4.3; C8.**

- **Проверка трёх вопросов ограничивает поле `questions`, но не текст `answer_text`.** Схема также допускает сочетание пожелания, непустых вопросов и `needs_backlog_card=true`; собственный валидатор его принимает. Инструкция предписывает правильное поведение, но устойчивость самого ответа модели по C10–C12 этим не доказана.
- **Сводная таблица бэклога заполняется пустыми колонками.** В [wms_assistant_agent.py:500](tools/assistant-agent/wms_assistant_agent.py:500) вставляется только номер; дата, вид и тенант остаются пустыми, хотя ниже в карточке они есть. Многострочные слова пользователя также цитируются знаком `>` только на первой строке.
- **README переоценивает уборку каталогов.** При обычном завершении обработки и большинстве исключений `finally` удаляет копию. Но прерывание во время подготовки checkout не покрывается `except Exception`, а уборки оставшихся каталогов при следующем запуске нет. Утверждение «удаляется вне зависимости от исхода» нужно сузить.
- **В `deps.py` существующая логика входа не менялась.** Добавлена отдельная проверка исполнителя; в `main.py` — подключение маршрутов; в настройках — два поля. Побочных изменений складских операций в рассматриваемом diff нет.

## 5. Что проверено и совпало с требованиями

У исполнителя запущены все **39 unittest-тестов: 35 прошли, четыре остановились из-за запрета создания временных каталогов**. Ошибками продукта эти четыре результата не считаю.

Дополнительно подтверждено:

- Переписка фильтруется одновременно по пользователю и тенанту; администратору исключения не дано. Общий API фоновых заданий не читает таблицу помощника. Тесты изоляции и соответствующего 404 прошли.
- Повторная отправка сообщения защищена уникальностью пары `user_id + client_message_id`; последовательный повтор результата не создаёт второго ответа.
- Условный захват выдержал отдельную проверку на SQLite: две сессии прочитали одну свободную запись, затем выполнили конкурирующий путь обновления; результат — **одна получила запрос, другая нет**. Для PostgreSQL при `Read Committed` повторная проверка условия `UPDATE` соответствует [документированному поведению](https://www.postgresql.org/docs/16/transaction-iso.html). Живой конкурентный прогон PostgreSQL не выполнен.
- Пустой, отсутствующий и состоящий из пробелов секрет закрывает очередь. Используется `secrets.compare_digest`; обычный пользовательский JWT её не открывает. В проверенных файлах секрет задан именем переменной, а не рабочим значением.
- У миграций единственная вершина — `20260912_0305`; её предшественник `20260911_0304` существует, отсутствующих предшественников нет. Модель использует общий `Base`, типы и сессии проекта. Применение миграции на PostgreSQL не проверено.
- Отдельные таблицы очереди, журналы и счётчики не введены. Разрешённая минимальная таблица сообщений одновременно служит очередью; ожидание вычисляется по отсутствию ответа.
- Текст экрана обрезается, роль и организация собираются сервером. Пользовательский текст, экран и история обозначены в инструкции как недоверенные данные. Git-команды записи направлены в отдельный checkout и ветку `assistant/chat-backlog`; команд push в `etalon` или `main` нет. При этом получение веток для нумерации выполняет `fetch` в исходном репозитории, поэтому README неточно называет все обращения к нему исключительно чтением.
