## 3. Новые подтверждённые дефекты

### №33. Фильтр пропускает код после удаления отступа, пустой строки или смены кавычек

Места: [assistant_safety.py:129](backend/app/services/assistant_safety.py:129), [assistant_safety.py:147](backend/app/services/assistant_safety.py:147), [assistant_safety.py:230](backend/app/services/assistant_safety.py:230). Такие же условия — в [wms_assistant_agent.py:136](tools/assistant-agent/wms_assistant_agent.py:136) и [wms_assistant_agent.py:171](tools/assistant-agent/wms_assistant_agent.py:171).

**Воспроизведение и наблюдение:**

| Вход | Результат |
|---|---|
| `    import os\n    import sys` | Прямая `contains_unsafe_content` распознаёт код, но `sanitize_answer` сначала вызывает `strip()`, убирая отступ первой строки. Двух соседних строк с отступом больше нет. Настоящий сервис сохраняет `import os\n    import sys` без безопасной замены. |
| `Вот пример:\n\n    total = 1\n\n    enabled = True` | Пустая строка сбрасывает счётчик соседних строк кода. Обе копии фильтра пропускают ответ; настоящий сервис сохраняет его без замены. |
| `Вот пример:\n\n    def post_supply():\n        # сохранить результат\n        return True` | Комментарий между строками также сбрасывает счётчик. Обе копии пропускают фрагмент. |
| `Таблица "assistant_messages", функция 'submit_executor_result'` | Шаблон теперь учитывает только обратные кавычки. Обычные кавычки обходят проверку; настоящий сервис сохраняет внутренние имена без замены. |
| `Таблица users хранит пользователей.` | Обе копии пропускают название таблицы без подчёркивания и смены регистра. |

Обратная ошибка тоже сохраняется:

> В таблице `FBS` выберите заказ и откройте поставку.

Обе копии отклоняют эту инструкцию; сервис сохраняет безопасный отказ. Без обратных кавычек тот же текст проходит. Название раздела FBS от оформления внутренним идентификатором не становится.

**Последствие:** техническое содержимое попадает в сохранённый пользовательский ответ, а допустимая инструкция заменяется отказом. Проверка только `contains_unsafe_content` не подтверждает безопасность фактического пути через `sanitize_answer`.

**Требование:** R12, R17; C12–C13. Прежние №14 и №26 полностью не закрыты. Особенно важно проверять эти входы через сохранение результата, поскольку один из обходов возникает именно при предварительном `strip()`.

### №34. Закрытие и повторное открытие окна во время старого GET удаляет отправленное сообщение и выключает опрос

Места: [AssistantPanel.tsx:249](frontend/src/components/assistant/AssistantPanel.tsx:249), [AssistantPanel.tsx:271](frontend/src/components/assistant/AssistantPanel.tsx:271), [AssistantPanel.tsx:283](frontend/src/components/assistant/AssistantPanel.tsx:283).

**Воспроизведение на коде компонента:**

1. Открытие окна начинает GET №1. Его пустой ответ задержан.
2. Пользователь отправляет A. POST успешно возвращает серверную строку с `waiting=true`; A отображается, опрос включён.
3. Пользователь закрывает и снова открывает окно до завершения GET №1.
4. Закрытие очищает `localOnlyIdsRef`.
5. Загрузка при повторном открытии пропускается: `loadInFlightRef` ещё установлен.
6. Старый GET №1 возвращает пустой список. Ответ применяется; локальная защита A уже очищена.

Получено:

```json
{
  "open": true,
  "rows": [],
  "hasWaiting": false,
  "timers": 0,
  "getCount": 1
}
```

**Последствие:** успешно отправленное сообщение исчезает из открытого окна, опрос прекращается. После освобождения `loadInFlightRef` новая загрузка автоматически не запускается. Ответ на A сам в ленту не приходит.

Это **регрессия №22 при исправлении №32**. Исходный сценарий №22 без закрытия окна проходит.

**Требование:** R5, R7, R22; C4–C6, C19. Повторное открытие должно получить актуальную переписку; ответ запроса, начатого до отправки и закрытия окна, не должен становиться окончательным состоянием ленты.

## 5. Замечания без блокировки

**Откат неуспешной отправки исправлен не для всех пересечений запросов.** Без пересекающегося GET проверки начальной выборки из 499, 500 и 501 строки прошли: после отказа POST возвращается прежняя отображаемая выборка — соответственно 499, 500 и 500 строк. Текст восстановлен, повтор использует прежний `client_message_id`.

Однако при 500 строках воспроизведён дополнительный порядок: GET уже начат → добавлена временная строка → GET возвращает 500 ответивших обращений → слияние обрезает начало → POST завершается ошибкой. После удаления временной строки остаются **499 строк**, текст восстановлен, опрос выключен. Это оставшаяся разновидность замечания третьего круга; данные на сервере не удаляются, следующая загрузка возвращает выборку.

**Фокус и выделение текста при переносе контейнера визуально не проверены.** В этом круге браузерная проверка не выполнялась; нового подтверждённого дефекта по этому пункту нет.
