## P2: bounded file stream before complete allocation

The actual file method is FbsApi.asset (called file in the review). It now uses
@Streaming. ResponseBody.readLabelBytes rejects a declared size above16MiB before
reading the body; unknown lengths are read with an8192-byte scratch buffer and
one overflow-detection byte at the boundary. No overflow bytes enter the growing
output buffer. The stream/ResponseBody close on success, overflow and read error.
The output byte array is created only after a bounded successful read. Reading and
PDF conversion run on Dispatchers.IO; an outer use also covers cancelled dispatch.

A test uses the production generated ApiClient with an injected generated source:
Retrofit returns the oversized body's headers with zero source bytes consumed,
then the limit rejects with zero consumed bytes and closes the response. Tests
also cover unknown length overrun (no more than limit + one Okio8192-byte source
buffer read), exact boundary, small unknown-length success, read exception cleanup,
and ViewModel error without PDF decoding or printDocument. The generated test
source does not preallocate the oversized payload.

## Batch resource assessment; no invented page-count prohibition

The16MiB bound controls one compressed download, not total print memory. The current
pipeline reads one accepted file, writes its temporary PDF, renders each page into
one ARGB bitmap (longest side1000), compresses PNG, retains base64 strings for every
page of that PDF, then retains HTML page strings for all selected assets. Joining
pages creates an additional large string; WebView and the OS print service add
separate allocations. Bitmap/renderer/temp-file cleanup does not bound retained
batch strings. Barcode canvases also add WebView allocations independently of PDF.

Concrete size accounting: an accepted16MiB file can briefly coexist with the
ByteArrayOutputStream's16MiB buffer and final16MiB byte array. A square1000px ARGB
bitmap is4,000,000bytes. Base64 takes4*ceil(PNG_bytes/3)characters per image before
HTML copies. These are source-level bounds/counts, not measured peak heap claims.
The32-page guard is perPDF, not perbatch. A targeted two-PDF decoder test produces
64 HTML pages without truncation. No arbitrary total-page UX refusal was added.
