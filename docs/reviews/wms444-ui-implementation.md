## Реализация в пределах существующего submitPack

Сохранён написанный Opus Retrofit-контракт обычной упаковки: POST `/operations/packaging-tasks/{task}/lines/{line}/pack` с точным количеством и UUID попытки, ответ содержит `packaging_task`. Остаётся существующая запись pending intent через синхронный `EncryptedSharedPreferences.commit()` до HTTP; новый журнал или экран не добавлен.

Продолжение Astra разделяет записи по серверу, tenant, user, заданию и строке. Идентификаторы tenant/user берутся из claims текущего JWT только для локального ключа хранения; авторизацию по-прежнему проверяет сервер. Email больше не является идентичностью исполнителя. Другой сотрудник не перезаписывает незавершённую попытку первого. HTTP-запрос связывается с той же сохранённой сессией; очистка после ответа адресует захваченный контекст, даже если сотрудник или сервер поменялся во время HTTP.

При повторном открытии задания сохранённые попытки отправляются с прежним UUID и количеством до предложения следующей операции. Успешный повтор возвращает текущее состояние сервера. Ошибка сети/5xx и 401/403 сохраняет запись для восстановления. Ошибки локального чтения/удаления записи не оставляют `packBusy` включённым; повреждённая запись не превращается молча в новую попытку. Следующая отдельная упаковка после подтверждённого ответа получает новый UUID.

Файлы экранов `OutboundAssemblyScreen.kt`, `PackagingPanel.kt`, их дизайн и бизнес-условия не изменены. Соседние процессы FBS, сортировки, приёмки и входа не переписаны; в `AuthStore` изменены только добавленные Opus методы хранения pack intent.

## Реальный осмотр: C5/C6 недостижимы описанным способом

На ранее установленном APK в `emulator-5580`, с обычной synthetic сессией `admin@example.com`, открыт раздел «Отгрузка». Сначала он был пуст. После разрешённого перезапуска тестового API18082 ведущим создана только собственная fixture в `wms_tsd_20260913`: селлер «WMS444 осмотр упаковки», склад «WMS444 осмотр ФБО», товар `WMS444-FBO-UI`, ФБО-план 3, закрытый короб с 3 штуками и allocation подбора 3. Начальное `qty_packed_in_task=0`. Это подготовленное состояние для осмотра, а не заявление о прохождении сборки с ТСД.

- Отгрузка `2f34e653-a99c-4e18-828b-9adb905d61df`, display number `444001`.
- Задание `52a59f50-d2e4-4805-b0f8-5b6d351352e6`.
- Строка `192357af-38b0-4433-a885-aa3e5165d3be`.

Настоящие GET документа, `/packaging-tasks/by-unload/{id}` и `/packaging-tasks/{id}` привели к `qty_packed_in_task=3`, `qty_done=3`, `is_complete=true`. Packaging events: **0**. Прямой запрос OperationFact по ID задания: **0**. POST pack не отправлялся. Ответы сохранены в [fbo-api-inspection.json](artifacts/wms444/fbo-api-inspection.json); API source `5d90fa03` сообщён ведущим после запуска, самим исполнителем версия процесса независимо не аттестована.

В UI пройдено «Отгрузка» → `444001` → товар. [Экран задания](artifacts/wms444/fbo-collected.png) показывает «Собрано 3 из 3», «Упаковка 3 из 3», кнопку «Завершить упаковку». [Шторка строки](artifacts/wms444/fbo-line-sheet.png) показывает «Упаковано 3 из 3 шт» и «Всё упаковано по этой строке», без кнопки ручного pack.

Причина соответствует реальному коду: `OutboundAssemblyScreen` показывает панель при `allCollected`, который определяется количеством в коробах. Оба серверных GET вызывают `sync_mp_task_packed_from_boxes`, устанавливающую упакованное количество из тех же коробов. `PackLineSheet` показывает ручной ввод только при `packRemaining > 0`. Поэтому полная сборка уже делает строку упакованной до ручного действия.

Условия `allCollected`, синхронизация количества из коробов и ответы GET **не подменялись**. Расхождение C5/C6 передано исходному БА444 и ведущему. Нужен разбор действительного доступного процесса и соответствующая постановка. Нельзя объявить проход UI→потеря ответа после commit→повтор, которого не было. Приёмочная таблица требований исполнителем не изменялась.
