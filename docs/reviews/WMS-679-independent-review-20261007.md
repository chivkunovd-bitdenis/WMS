## Подтверждённые замечания

### F1 · P2 · Экспорт не проверяет клиентский контур и склад связанного WarehouseBox

Место: `backend/app/services/marketplace_unload_wb_fbw_export_service.py:136`, валидация строк начиная с `:182`. Требования R2/R7/R11.

Запрос ограничивает тенант самой отгрузки и проверяет владельца товара, но читает WarehouseBox по одному id. Ни tenant_id, ни warehouse_id физического короба не выбираются и не сравниваются с отгрузкой. Поэтому доступная оператору отгрузка с несогласованной сохранённой связью экспортирует чужой физический идентификатор как свой.

Воспроизведение на SQLite в памяти через **настоящий маршрут** `GET /operations/marketplace-unload-requests/{id}/wb-fbw-packaging.xlsx`: взять синтетическую отгрузку из контрактной фикстуры; изменить warehouse_box_id первого MarketplaceUnloadBox на существующий WarehouseBox другого тенанта, сохранив собственные товары/количества; вызвать экспорт от лица собственного селлера. Получено **200**, в колонке C есть `WHB-FOREIGN-REVIEW`. При связи с другим складом того же тенанта также получено **200** и `WHB-OTHER-WAREHOUSE`.

Это проверка повреждённой/несогласованной сохранённой связи, а не доказательство, что пользователь может создать такую связь обычной ручкой привязки. Существующий `attach_existing_box_by_barcode` проверяет тенант при разрешении кода и warehouse_mismatch; обход этой ручки не заявляется. Однако экспорт должен отказывать в выдаче недостоверного файла при такой связи, как уже делает для чужого товара и отсутствующего WarehouseBox. Состав и внутренние коды при отказе менять не нужно. Достаточно проверять контур и склад в том же снимке запроса, сохранив понятную ошибку короба.

### F2 · P2 · Детерминированная упаковка ZIP не обеспечивает стабильный порядок строк

Место: `backend/app/services/marketplace_unload_wb_fbw_export_service.py:117–159`. Контракт C1–C4/C7 и обещание `_stable_xlsx` о совпадающих повторных скачиваниях.

SQL-запрос не содержит ORDER BY, а Python передаёт его порядок непосредственно в workbook. Поля box_created_at / line_created_at / id выбраны, но для сортировки не используются. Фиксированные даты XLSX и ZIP не устраняют различие содержимого листа.

Воспроизведение без изменения данных: экспорт контрактной фикстуры, затем `PRAGMA reverse_unordered_selects=ON` и ещё один экспорт. Это диагностическая настройка SQLite, меняющая обход запросов без ORDER BY, а не конкурентная запись. Первый файл содержит количества в порядке `[2, 3, 1, 4]`, второй — `[4, 1, 3, 2]`; `first.content == second.content` равно **False**. Оба файла содержат те же пары короб/товар и количество, поэтому смешение снимков этим опытом не доказано. Доказано отсутствие устойчивого порядка и гарантии одинаковых повторных файлов. Нужен определённый порядок коробов/строк с уникальным дополнительным ключом до формирования листа.

### F3 · P2 · Пустая WB-отгрузка получает ложную причину ошибки

Место: `backend/app/services/marketplace_unload_wb_fbw_export_service.py:135,161–170`. Требования R5/R12 об объяснимой ошибке в документе.

Внутренний JOIN с MarketplaceUnloadBox даёт ноль строк как для Ozon, так и для WB без созданных коробов. Проверка существования документа после этого всегда выдаёт «Выгрузка XLSX доступна только для отгрузки WB», не проверяя marketplace.

На существующем WB-документе без коробов настоящий API вернул **422** с `{"detail":"Выгрузка XLSX доступна только для отгрузки WB."}`. Кнопка отображается именно в WB-документе, поэтому сообщение предлагает исправлять площадку вместо состава. Следует различать неподходящую площадку и отсутствие коробов: сообщить истинную причину либо выдать согласованный пустой файл. Это замечание не вводит запрет складских действий или новое требование о количестве коробов.
