## Повтор, одновременность и края

В коробе и грузоместе входной параметр — абсолютное целевое количество, а не величина вычета. Для корректного запроса `quantity >= 0` дельта не может быть меньше отрицательного прежнего количества этой строки. Поэтому запрос «снять больше, чем есть» в таком API означал бы отрицательное целевое количество: HTTP отвергает его с 422, документ не меняется. Это проверено для обоих типов тары. Защита уже существовала; нового пользовательского запрета коммит не добавляет.

`inbound_intake_service.py:649` использует `FOR UPDATE` вместе с `populate_existing=True`: после получения блокировки ORM перечитывает документ и связанные строки. Короб вычисляет `qty_before` после этой загрузки; грузоместо дополнительно перечитывает свой состав. Скан грузоместа сохраняет ту же транзакцию до вызова установки количества. Изменение тары, россыпи/итога и запись ключа повтора сохраняются в одной транзакции штатного сервиса. Новая ветка не вводит отдельного вычета, который мог бы повторно сработать вне этой транзакции.

Дополнительный HTTP-прогон повторов был сильнее простого «дважды поставить 0»: тару обнулили с ключом K, затем новым сканом положили в неё единицу, после чего повторили старое обнуление с K. И короб, и грузоместо сохранили новую единицу. Так проверено, что действует сохранённый ключ попытки, а не только естественное свойство абсолютного PUT.

После «Редактировать» штатный `reopen_receiving` отменяет приход и переводит документ в `receiving`; этот статус не исключён из новой ветки. C5 подтвердил остатки в сортировке 2 → 0 → 1 при завершении, переоткрытии, исправлении и повторном завершении. Состояния `sorting` / завершённые, наоборот, исключены существующей проверкой.

Для старого черновика синтетически задана прежняя форма строки: `expected_qty=3`, `actual_qty=NULL`, тары ещё нет. Чтение показывает 3. Два скана в тару дают итог 3 и россыпь 1; уменьшение тары 2 → 1 даёт итог 2 и россыпь 1. Сценарий проверен через HTTP для обоих типов тары. Реальные исторические документы не менялись. Отдельные существующие тесты перехода через legacy `submit` / `begin-receiving` также прошли в наборе WMS-440.
