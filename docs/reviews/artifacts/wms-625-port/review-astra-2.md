## N1 — P0. Квитанция .4 игнорируется для `failed_before_submit`; новый сайт автоматически отправляет вторую этикетку

**Место:** `tools/print-agent/wms_print_direct_macos.swift:232`, **`:238–242`**; разрешение повторной отправки — `:396–400`. Автоматическое продолжение на сайте — `frontend/src/utils/durableDirectQr.ts:267–270`.

При старте новая программа сначала читает `direct-jobs.json`, затем загружает `jobs-v2` поверх импортированных записей. Новая сверка квитанции старой программы выполняется исключительно для `job.status == "saved"`. Однако после доказанного отказа до очереди остаётся другое безопасно повторяемое состояние — `failed_before_submit`. Старая программа может напечатать и такое задание между двумя запусками новой.

Воспроизведён следующий сценарий, без повреждения файлов и без ручной смены ключа:

1. Новая программа получает ключ K, сохраняет PNG/описание, но принтер по умолчанию не выбран. Получается `failed_before_submit`; внешних отправок нет, в старом журнале K отсутствует.
2. Оператор запускает .4 после настройки принтера и повторяет K. .4 отправляет одну этикетку и сохраняет `receipt=old-1`. Ответ сайту теряется, поэтому исходный заказ ещё требует завершения.
3. Оператор возвращает новую программу. В старом файле есть правильные hash и receipt, но загрузка `jobs-v2` перекрывает их прежним `failed_before_submit`. Сверка строк 238–242 пропускает это состояние.
4. Повторный скан получает `failed_before_submit`. `dispatchDurableQr` сам вызывает `/jobs/K/retry`; новая программа отправляет K ещё раз и заменяет старую квитанцию своей. Получаются **две внешние отправки одной этикетки**.

**Подтверждение:** скомпилированы реальные `Printer` из `.4` (`9a33b651c`) и HEAD, без изменения их методов. Заменены только системная очередь и `submit` тестовыми функциями; каждый этап запускается отдельным процессом, файлы журнала настоящие. HTTP-потеря моделируется тем, что результат .4 не подтверждается сайту; код импорта/повтора от этого не меняется. Вывод:

```text
new fail:    status=failed_before_submit receipt=nil   submissions=0
old print:   receipt=old-1                             submissions=1
new inspect: status=failed_before_submit receipt=nil   submissions=0
new retry:   status=accepted             receipt=new-1 submissions=1
```

Счётчики относятся к отдельным процессам; сумма внешних приёмов — 2. Это доказательство двух вызовов отправки, не наблюдение двух физических листов. Положительный контроль `new saved → .4 print → new inspect` возвращает `accepted/old-1` без новой отправки: дефект именно в неполном наборе состояний сверки.

**Что исправить:** до разрешения отправки согласовывать с журналом .4 все состояния, которые новая программа считает повторяемыми. Квитанция старой программы с тем же ключом и хешем должна завершать исходное намерение; запись о начатой отправке без квитанции должна запрещать автоматический второй экземпляр. Добавить сценарии для `failed_before_submit`, а не только `saved`, включая потерянный ответ .4 и восстановление через настоящий frontend `/retry`.

Воспроизводитель: [review-astra-2-rollback-probe.py](review-astra-2-rollback-probe.py); вывод: [review-astra-2-rollback.log](review-astra-2-rollback.log). ## Старый файл, запись до печати и гонки

Формат совместим с реальной .4: `[ключ: {hash: String, receipt?: String}]`, дополнительное `v2: true` допустимо для её `JSONDecoder`. Хеш совпадает: PNG + `|58.0x40.0` в обеих Swift-версиях. Проверен не только похожий декодер, но и настоящий `Printer.printJob` .4: запись с квитанцией возвращает её без отправки; запись с `v2:true` без квитанции читается и возвращает прежний отказ «Задание уже передавалось», `submissions=0`. Печать другого ключа в .4 штатно переписывает файл без `v2`; новая программа затем нормально читает результат.

В новой программе `mirrorLegacy`/`forgetLegacy` вызываются под общим `NSRecursiveLock`, запись сначала атомарно заменяет файл и лишь затем меняет `legacyEntries`. Worker отправки последовательный; обновление результата наблюдателем берёт тот же замок. Внутрипроцессного сценария потери соседнего ключа из-за двух одновременных перезаписей не найдено. Обычные серверы обеих версий занимают один локальный порт, причём bind выполняется до открытия Printer. Общего файлового замка с .4 нет; два принудительно запущенных сервера на разных портах не являются проверенным/защищённым сценарием.

При ошибке записи старого файла до `submit` отправки нет, остаётся `failed_before_submit`; соответствующая собранная Swift self-test прошла. После доказанного отказа запись удаляется из старого файла. Именно такое состояние делает N1 практически достижимой. Если запись квитанции в старый файл не удалась **после** отправки, первоначальная запись без квитанции сохраняет защиту от дубля, но откатившаяся .4 откажет в продолжении. Это граница доступности при отказе хранения, а не доказательство отсутствия отправки. Повторное наблюдение новой программой может дописать квитанцию.

Атомарная замена старого файла не использует `fsync/F_FULLFSYNC`, в отличие от `jobs-v2`. Следовательно, проверена защита от ошибки операции записи/обычной смены процессов, но стойкость зеркала при внезапном отключении питания не доказана. Отдельного P0 по гипотетической потере питания не заявляю.

## Текущий production-клиент с новой программой

Исполнен настоящий `handle` из HEAD с HTTP-запросами старого формата через пару локальных сокетов (`socketpair`, без открытия TCP-порта); использованы настоящие файлы Printer и тестовый `submit`. Получены следующие ответы:

| Старый POST `/print` | Ответ новой программы | Внешние отправки |
|---|---|---|
| Новый ключ | `200`, `accepted`, `receipt=test-1` | 1 |
| Тот же ключ после «потерянного» первого ответа | `200`, та же `receipt=test-1` | По-прежнему 1 |
| Ключ из старого журнала с квитанцией | `200`, `accepted`, `receipt=old-7` | Новых нет |
| Ключ из старого журнала без квитанции, два повтора | Оба `409`, `unknown`, receipt отсутствует | Новых нет |

Первым трём ответам достаточно прежнего клиента: дополнительные поля не меняют его правило успеха. Для свежего задания обработчик ждёт квитанцию до 18 секунд, worker живёт независимо от HTTP-ответа; повтор возвращает тот же сохранённый результат, а не новый экземпляр.

**Для импортированной записи без квитанции автоматического завершения заказа нет.** `retry` и `reprint` запрещены при `legacy`, а `observeQueue` не восстанавливает такой исход без сохранённых очереди/уникального имени (`Swift:157–162, 398, 404`). Повтор старого POST остаётся ошибкой. Это уже существовало в .4 и прямо сохранено последним уточнением требований как прежнее поведение; не выдаю его за новую регрессию исправлений. Но утверждать «вечной блокировки нет во всех четырёх сценариях» нельзя: четвёртый штатно не завершается автоматически и требует отдельного разбора исхода.

Дополнительная граница старого клиента: после нового `failed_before_submit` один лишь повтор `/print` возвращает прежний отказ — он не вызывает `/retry`. Для доказанно неотправленного нового задания есть действие восстановления в истории программы; новый сайт вызывает `/retry` сам. Это отличается от .4 при отказе выбора принтера и не должно теряться в обещании полной прозрачности обновления программы.
