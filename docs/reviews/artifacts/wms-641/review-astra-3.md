## Остаток F2: маскировка не заменяет ограничение чтения

**Серьёзность: блокер прежнего F2; R21, R37.** Это незакрытая часть круга 2, а не новый полный аудит аналитика.

В `llm.py:248` выключение инструментов действует только для `text` и `write`. У `readonly` остаются shell и режим `read-only`; запреты из `sandbox.deny_read_paths` к этому запуску Codex не применяются. Раздел 11 прямо подтверждает чтение домашнего каталога аналитиком. После чтения результат команды уже находится в контексте модели; `scrub`, выполняемый при подготовке исходящих сообщений, не защищает этот этап.

Для сценария, в котором аналитик выполняет инструкцию из недоверенного обращения и цитирует прочитанное, новая маскировка также не даёт надёжной границы. На исключительно синтетических данных повторено:

- обычный фиктивный токен вида `sk-proj-…` скрывается;
- JSON `{"password": "SYNTHETIC-PASSWORD-MARKER"}` проходит `scrub` без удаления значения;
- тот же распознаваемый токен, разделённый пробелом после `sk-proj-`, проходит маскировку обеими частями;
- имя вложения обходит маскировку даже без преобразования токена — N4 ниже.

Это не утверждение, что живая модель обязательно подчинится такой инструкции: проверены предусмотренные кодом полномочия и конкретный пропуск фильтра, а не вероятность воздействия на модель. Настоящие секреты не читались. Закрывать нужно чтение файлов вне предоставленной области у сессии, которая обрабатывает недоверенные обращения; расширение регулярных выражений может быть дополнительной защитой, но не заменяет эту границу.

Для Codex-разработчика отдельно: прежний запуск с сетью, доступом записи в `~/.codex` и `danger-full-access` удалён. По текущему коду прямого shell-пути у него нет. Тесты argv и справка CLI не доказывают исчерпывающий набор доступных модели инструментов, невозможность всех способов чтения или успешность реальной разработки без shell. Полноценный первый вызов и resume с синтетическими файлами вне worktree в этом круге не запускались. Отчёт разработчика о его живом опыте не выдан за независимое подтверждение ревьюера.

## Новые находки в изменённых местах

### N3 — высокая серьёзность: входной SHA старого коммита фактически выкатывает вершину etalon

**Место:** `.github/workflows/deploy.yml:79–88`, контракт с `scripts/deploy/prod-update.sh:16–26`. Связь с F4: обещание выкладывать ровно закреплённую версию.

Workflow принимает любой существующий коммит из истории etalon и исполняет `prod-update.sh` именно из него. Только новый вариант скрипта знает о `WMS_DEPLOY_SHA`. Если выбранный коммит старше этого исправления, переданная переменная игнорируется, и старый скрипт выбирает `origin/etalon`.

**Воспроизведение:** создан временный синтетический origin с тремя коммитами. В `c1` помещён настоящий `prod-update.sh` из `4e2b1ef8`, в `c2/c3` — нынешний. В тестовой серверной копии предварительно выбран `c1`. Выполнен серверный блок нынешнего workflow с `DEPLOY_SHA=c1`, временным HOME/Git-конфигом и `WMS_DEPLOY_GUARD_ONLY=1`, который останавливает настоящий скрипт до сборки и базы.

Получено:

```text
requested = 1e4911a576f8d76c9c02d09327c7e85a67aade9b  (c1)
actual    = 183361ea61f7b86fd8a0f04ca0fedb0a042f25ce  (c3, текущий etalon)
exit_code = 0
Deploy guard passed; WMS_DEPLOY_GUARD_ONLY=1, stopping before build.
```

Это локальные идентификаторы синтетического репозитория, не production SHA. Docker и база не запускались. Проверка версии пройдена для неправильного коммита; без тестовой остановки дальнейшая сборка использовала бы `c3`.

Обычный новый хотфикс, созданный после включения обеих правок в etalon, содержит новый скрипт и этим конкретным сценарием не ломается. Ошибка относится к новому общему входу workflow: ручной запуск с историческим SHA либо обработка старого merge SHA после обновления workflow. Внешняя проверка наличия слова `attempt_id` только в текущем etalon (`hotfix.py:538–541`) совместимость скрипта выбранного коммита не доказывает.

**Что исправить:** до исполнения скрипта выбранного коммита обеспечить его поддержку закреплённой версии или явно отказать для несовместимой версии. Нельзя молча переходить к вершине ветки. Проверка только после сборки/выкладки слишком поздняя. Добавить именно смешанный сценарий «старый скрипт в целевом SHA, новый workflow»; нынешние тесты проверяют новый скрипт во всех версиях либо подставной скрипт, лишь печатающий вход.

### N4 — высокая серьёзность: секрет проходит в исходящем имени файла

**Место:** `pipeline.py:575–597`; отправка `telegram.py:88–90`. Связь с F2/R37 и новой маскировкой исходящих данных.

Текст ответа и содержимое выгрузки проходят `scrub`, а `info_file.filename` — только замену недопустимых символов пути. Токен вида `sk-proj-…` состоит из допустимых символов и остаётся в имени. `TelegramClient.send_document` помещает это имя в HTTP multipart-поле `filename` без маскировки.

**Воспроизведение:** через обычный конвейер информационного обращения передан ответ поддельного аналитика: безобидный CSV и имя `<синтетический sk-proj-токен>.csv`. Предпросмотр автоматически подготовлен и отправлен владельцу через FakeTelegram. Затем тот же документ передан настоящему `TelegramClient` с `httpx.MockTransport`, перехватывающим запрос в памяти.

```text
normal_body_token_masked = true
filename_reaches_owner = true
fake_token_in_multipart_filename = true
network_used = false
```

Для утечки в Telegram достаточно предпросмотра: подтверждение отправки клиенту ещё не требуется. После подтверждения клиенту уйдёт тот же файл с тем же именем. Настоящего токена и реального запроса в Telegram в опыте не было.

**Что исправить:** применять защиту к имени файла до фиксации предпросмотра и отправки либо выбирать контролируемое нейтральное имя. Проверять полный исходящий multipart, включая имя, а не только текст, подпись и содержимое. Это дополнительный пропуск конкретного поля; он не заменяет исправление ограничения чтения в F2.

## Выполненные проверки и ограничения

Команда владельца:

```text
cd tools/support_agent && ./.venv/bin/python -m pytest -q -p no:cacheprovider
150 passed, 5 failed
```

Четыре отказа вызваны средой ревью: `test_sandboxed_code_cannot_replace_or_modify_dot_git` и два теста `test_sandbox_live.py` получают `sandbox_apply: Operation not permitted` / отсутствие ожидаемого вывода; тест с локальным сокетом получает запрет `bind(127.0.0.1)`. Они не подтверждают дефект службы вне внешней песочницы, но не дают здесь объявить живую OS-изоляцию проверенной.

Пятый отказ повторён отдельно: `test_workflow_server_part_refuses_foreign_or_malformed_sha_before_running_anything` принимает uppercase SHA в серверном блоке. Подпроцесс Python находит `/bin/bash 3.2.57`. Контрольный `set -e; [[ x == y ]]; echo survived_failed_compound` в нём продолжает исполнение, а в `/opt/homebrew/bin/bash 5.3.9` завершается с кодом 1. Поэтому самостоятельный `[[ … ]]` в серверном блоке не даёт обещанный отказ в этой тестовой среде. Runner-валидация использует явный `if …; exit 1` и этот дефект не повторяет. Это отдельно объяснённая переносимость проверки, не доказательство инъекции или отказа настоящего Linux-сервера. Полностью зелёный набор не заявляется.

Дополнительно выполнены адресные опыты через Python stdin:

- прежний `fsmonitor` через настоящий Git и методы диспетчера — блокируется;
- старый скрипт внутри закреплённого SHA — N3;
- значения `$(touch <маркер>)`, кавычка с `; touch …`, перевод строки с командой для обоих inputs: runner отклонил все шесть вариантов с кодом 1, маркер не создан; данные передаются через env, прямой подстановки inputs в shell-текст нет;
- синтетические проверки маскировки текста и полного HTTP-поля имени вложения — остаток F2/N4;
- проверка установленной версии Codex, справки и флагов без обращения к модели.

Реальные модели, GitHub Actions, production, Telegram и Trello не вызывались. Временные репозитории использовались только как удаляемые тестовые фикстуры; продуктовый checkout и его Git-метаданные не менялись. Живое прохождение CLI-разработчика, его resume, сеть SSH-action и фактический SHA на сервере не проверялись. Первоначальная гонка F4 для новых совместимых версий закрыта по коду и локальным тестам; подтверждения настоящего деплоя это не даёт.
