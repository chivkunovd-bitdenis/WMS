## Повтор N4 и короткий корпус кавычек

Основной пакет воспроизведения сохранён без сокращения существенных операторов:

```sql
EXPLAIN SELECT 1 AS a$$;
COMMIT;
SET default_transaction_read_only=off;
COMMIT;
ALTER ROLE CURRENT_USER SET statement_timeout=0;
SELECT current_user AS b$$
```

Повтор с `$tag$` вместо `$$` дал тот же отказ. Также отвергнут пакет с `CREATE TEMP TABLE wms641_probe(n int)`, `INSERT ... VALUES (641)` и чтением этой таблицы между двумя долларовыми идентификаторами. Это именно запрет до исполнения, а не ошибка PostgreSQL после части пакета. Клиент вернул `SqlRefused: символ $ запрещён (долларовые строки и параметры)`, шлюз — код 3. Отдельно отвергнуты `$1`, `'$'`, `$$x$$` и `"a$b"`: запрет любого `$` соответствует явно принятому решению раздела 11.

Для серверных повторов запускался отдельный процесс исходного `gateway.py`; AGENT_DB_PSQL указывал на `/usr/bin/false`, чтобы непредвиденное прохождение фильтра не обращалось к рабочей БД. Ожидаемый код 3 и текст `refused` отличают отказ проверки от запуска этой команды, который дал бы код 1. В клиенте использован runner-счётчик: ни один запрещённый запрос до него не дошёл. Это не выдаётся за цепочку с живой PostgreSQL.

Короткая проверка других форм:

```sql
EXPLAIN SELECT E'x'; COMMIT; SELECT 2
EXPLAIN SELECT E'x\'; COMMIT; SELECT 'y'
SELECT U&'a\003b'; SELECT 2
SELECT U&'a!003b' UESCAPE '!'; SELECT 2
EXPLAIN SELECT 1 AS "a;"; COMMIT; SELECT 2 AS "b;"
EXPLAIN SELECT 'a'';b'; COMMIT; SELECT 'c'
EXPLAIN SELECT 1 AS "a"";b"; COMMIT; SELECT 2
```

Все строки отвергнуты обеими проверками: при наличии обратного слеша — по нему, в остальных случаях — по настоящему разделителю операторов. Напротив, `SELECT E'a'';b' AS x`, `SELECT U&'a!003b!0027!0022' UESCAPE '!' AS x`, `SELECT 1 AS "a;"`, `SELECT 1 AS "a"";b"` и строка с удвоенной одинарной кавычкой проходят фильтры как один запрос. По правилам PostgreSQL Unicode-экранирование формирует содержимое литерала/идентификатора; получившиеся символы не становятся отдельными SQL-операторами. Это сверка правил языка и фильтров, а не новый живой прогон парсера PostgreSQL. [PostgreSQL 16: Lexical Structure](https://www.postgresql.org/docs/16/sql-syntax-lexical.html).

## Строка подключения и настройки роли

В `gateway.py:65–76` имя базы проверяется до сборки строки; `session_guard=True` включён только для sql-ветки. Получено:

```text
dbname=wms options='-c default_transaction_read_only=on -c statement_timeout=20s -c idle_in_transaction_session_timeout=30s -c lock_timeout=3s -c row_security=on -c search_path=public,pg_catalog'
```

Текст запроса, включая строковый литерал с текстом `dbname=wms options=...`, не участвует в построении этого значения. Роль берётся из проверенной SSH-команды и передаётся через `-U`; SQL остаётся аргументом `-c`. Код не запускает командную оболочку. Из SQL-параметра нет пути присвоить AGENT_DB_NAME или AGENT_DB_PSQL.

Кроме разбора строки через `psycopg.conninfo_to_dict`, выполнен отдельный опыт с настоящей Homebrew libpq: `PQconnectStartParams` с раскрытием dbname и `PQconninfo` для чтения фактически выбранных параметров. Окружение было чистым и задавалось самим испытанием. Проверены PGOPTIONS с `default_transaction_read_only=off`, `statement_timeout=0`, `row_security=off`, затем совместно PGDATABASE со строкой подключения к postgres, PGUSER=postgres и PGOPTIONS с `role=postgres`. Во всех случаях библиотека сохранила базу `wms`, роль `wms_agent_s_11111111111111111111111111111111` и все фиксированные options. Намеренно некорректный `hostaddr=not-an-ip` останавливал соединение до сетевого обращения; этот опыт не проверяет серверное применение настроек. Учётные данные не использовались.

Результат согласуется с контрактом libpq: переменные окружения заполняют параметры, которые не были явно заданы. Проверка с PGSERVICE ограничилась сборкой аргументов шлюза; отдельный service-файл и успешное соединение не испытывались. [PostgreSQL 16: Database Connection Control Functions](https://www.postgresql.org/docs/16/libpq-connect.html), [Environment Variables](https://www.postgresql.org/docs/16/libpq-envars.html).

AGENT_DB_NAME со значениями `dbname=wms user=postgres`, `wms options='-c statement_timeout=0'`, `postgresql:///wms?options=...` и вариантами разделителей получил код 4 / `gateway error` до запуска дочерней команды. Отдельно обнаружено обычное свойство Python-якоря `$`: имя `wms` с одним завершающим LF проходит текущий regex. Однако libpq разбирает его как ту же базу `wms`, options остаются прежними; добавить после LF второй параметр не удалось — такая строка отвергается. Это не обход N4 и не основание для нового блокирующего требования. Произвольная подмена AGENT_DB_PSQL остаётся изменением доверенной конфигурации исполняемой команды, а не возможностью модели через sql_query.

В `seller_access.py:249–259` все шесть ALTER ROLE SET стоят вне условия создания роли. Следовательно, повторный ensure снова выдаёт их и для существующей роли. Более того, этот эффект уже был у версии круга 9: новая правка выносит значения в общий SESSION_SETTINGS, а не добавляет ранее отсутствовавшее восстановление. Независимый запуск обоих генераторов на колонках всех моделей дал полностью одинаковый SQL. Для административных вызовов find/ensure `session_guard` остаётся выключен; при штатном AGENT_DB_NAME=wms их аргументы, `-X`, `ON_ERROR_STOP`, переменная поиска и фиксированный запрос не изменились.
