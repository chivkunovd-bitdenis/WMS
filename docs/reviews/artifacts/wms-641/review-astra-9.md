## Новая находка N4 — P2, средняя серьёзность: несколько операторов проходят обе проверки, модель может постоянно изменить настройки своей роли

**Место.** `scripts/agent_db/sql_contract.py:58–66` считает любое `$$` или `$tag$` началом строкового литерала, не учитывая, что эти символы могут быть частью некавычного SQL-идентификатора. Затем строки 84–94 ищут запрещённые слова и `;` уже в неверно замаскированном тексте. Аналогичная логика есть в клиенте `tools/support_agent/support_agent/prod_sql.py:75–84`. В `wrap_limit()` запросы с начальным EXPLAIN передаются без обёртки подзапросом, поэтому этот путь доступен через штатный `sql_query`, а не только при прямом вызове SSH-входа.

**Минимальный повтор через настоящий gateway.py:**

```sql
SELECT 1 AS a$$; SELECT 2 AS b$$
```

```text
returncode = 0
stdout = 'a$$\n1\nb$$\n2\n'
```

Для PostgreSQL `a$$` и `b$$` — имена колонок. Для фильтра всё между первым и вторым `$$` — якобы строка; разделитель операторов исчезает до проверки. Повтор с `a$tag$` и `b$tag$` также исполнил скрытый `SET application_name` и вернул установленное значение.

**Существенный сценарий через клиент агента и шлюз.** В инструмент передан запрос:

```sql
EXPLAIN SELECT 1 AS a$$;
COMMIT;
SET default_transaction_read_only=off;
COMMIT;
ALTER ROLE CURRENT_USER SET statement_timeout=0;
SELECT current_user AS b$$
```

Настоящий `prod_sql.run_query()` с заменой только SSH-транспорта на локальный gateway.py принял его и вернул:

```text
QUERY PLAN
Result  (cost=0.00..0.01 rows=1 width=4)
COMMIT
SET
COMMIT
ALTER ROLE
b$$
wms_agent_s_<UUID тестового S1>
```

В **следующем отдельном процессе шлюза и новом соединении** запрос `SELECT current_setting('statement_timeout') AS timeout, current_user` вернул `0` и ту же роль S1. Таким образом, это не просто несколько строк результата: агент через инструмент «только чтение» изменил сохранённую настройку роли, сняв установленный генератором предел выполнения SQL в 20 секунд. Перед опытом роль создана штатным генератором с `NOCREATEROLE`; обычной роли достаточно права менять собственную настройку. Настройка временной роли после проверки восстановлена в `20s`, что подтверждено ещё одним запросом.

Дополнительно аналогичный пакет после отключения read-only создал временную таблицу, вставил `641` и прочитал эту строку через клиент. После закрытия соединения таблица исчезла, запрос каталога вернул 0 таких таблиц. Короткий вариант с обычным `SET statement_timeout=0` проведён и через `prod_sql_mcp.handle()`: `isError=false`, результат содержит `SET` и `0`, след обращения записан.

**Граница доказательства.** Получены запись в собственную настройку роли и запись во временную таблицу тестовой БД. Чтение чужого селлера и изменение рабочих таблиц этим опытом не доказаны. Скрытый `SET ROLE postgres` дошёл до PostgreSQL, но получил `42501: permission denied`; следующий обычный запрос под S1 по-прежнему видел ровно одного селлера. Серверный и клиентский пределы буферов не обойдены, поэтому N2 не переоткрывается. Однако обещанные единственный оператор, запрет записи и запрет команд управления сессией нарушены; гарантия завершения оставшегося в контейнере запроса по таймауту роли из раздела 11 больше не может опираться на неизменность этих 20 секунд.

**Что исправить.** В обеих проверках отличать долларовые символы внутри SQL-идентификатора от начала долларовой строки; не скрывать реальные разделители и запрещённые команды. Проверить этот корпус через gateway.py и через клиент с EXPLAIN: варианты `a$$/b$$` и `a$tag$/b$tag$` с несколькими операторами должны отклоняться до psql, а обычные SELECT/WITH/EXPLAIN и настоящие долларовые литералы должны сохранять заявленное поведение. Сверки клиента и сервера между собой недостаточно, если они повторяют одну ошибку разбора. Для регрессии существенны также отсутствие изменения настройки роли в следующем соединении и отсутствие исполнения временной записи.

Причина согласуется с документацией PostgreSQL: долларовая строка после идентификатора требует отделения пробелом, иначе `$` относится к самому имени. [PostgreSQL 16: Dollar-Quoted String Constants](https://www.postgresql.org/docs/16/sql-syntax-lexical.html#SQL-SYNTAX-DOLLAR-QUOTING).

## Отдельная проверка psql -c, переменных и окружения

`-c` само по себе не является запретом метакоманд: psql допускает отдельную обратнослещевую команду в этом аргументе. Здесь её блокирует проверка любого обратного слеша на сервере; stdin дочернего процесса дополнительно закрыт через DEVNULL. Смешанный ввод `SELECT 1` с `\gexec` также отвергнут до запуска. Созданная уже SQL-выражением строка `chr(92)||'! printf WMS_GATEWAY_SHELL_PROBE'` вернулась как текст CSV, не была исполнена. Несколько SQL-операторов внутри одного `-c` psql поддерживает — именно поэтому N4 исполняется. [Документация psql, параметр -c](https://www.postgresql.org/docs/16/app-psql.html#APP-PSQL-OPTION-COMMAND).

Проверены `SELECT :q` и `SELECT :'q'` с намеренно заданной тестовой переменной `-v q=1; SELECT current_user` в базовой команде psql. Оба запроса через шлюз получили `42601` у двоеточия: подстановки psql в SQL-аргументе `-c` не произошло. `find-seller` остаётся отдельным фиксированным запросом через stdin с `:'q'`; перенос этого маршрута на `-c` не выполнялся и поиск не сломан. Флаг `-X` сохранён; по контракту psql он отключает стартовые psqlrc-файлы. [Документация psql](https://www.postgresql.org/docs/16/app-psql.html).

Для окружения выполнены следующие дополнительные опыты через gateway.py с локальным psql временного кластера:

| Тестовое изменение окружения | Фактический результат |
|---|---|
| `PGUSER=postgres`, `PGDATABASE=postgres` | Явные `-U <роль S1> -d wms` сохранили S1; `session_user` также S1, виден один селлер. |
| `PGOPTIONS=-c role=postgres` | Соединение отказало: `permission denied to set role`. |
| `PGOPTIONS=-c session_authorization=postgres` | Соединение отказало: `permission denied to set session authorization`. |
| `PGOPTIONS=-c row_security=off` | Запрос отказал из-за RLS, дополнительные строки не открыл. |
| `AGENT_DB_NAME=dbname=wms user=postgres` | При намеренном изменении доверенной конфигурации тестового процесса подключился postgres и увидел четыре тестовых селлера. |

Последняя строка — граница доверия конфигурации, а не доказанный путь из SQL: значение `-d` может быть строкой соединения, чьи параметры имеют приоритет над отдельным `-U`. `AGENT_DB_PSQL` также по назначению задаёт исполняемую команду. Эти переменные нельзя считать недоверенными пользовательскими параметрами. В проверенном коде нет передачи их значений из текста sql_query или разрешённой строки SSH-команды; возможность установить их с удалённой стороны через настройки SSH не установлена. Настройки боевого SSH и окружение контейнера не проверялись, поэтому отдельный блокирующий дефект на основании такой возможности не заявляется. [Документация psql, параметр -d](https://www.postgresql.org/docs/16/app-psql.html#APP-PSQL-OPTION-DBNAME), [переменные окружения libpq](https://www.postgresql.org/docs/16/libpq-envars.html).

Штатный запуск использует `docker exec` без `-e`: опыты с PGOPTIONS выше относятся к непосредственному локальному psql, а не доказывают передачу окружения хоста в боевой контейнер. Подмены AGENT_DB_PSQL и AGENT_DB_NAME в испытаниях задавались самим ревьюером только для временного кластера.
