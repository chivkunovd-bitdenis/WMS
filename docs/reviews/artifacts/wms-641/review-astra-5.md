## N6 — высокая серьёзность: новый читатель обходит собственный запрет секретных путей

**Места:** `tools/support_agent/support_agent/readonly_mcp.py:64–72,109–146`.

`resolve()` проверяет все компоненты явно переданного пути. Но рекурсивный `_walk()` исключает из обхода лишь SKIP_DIRS и ссылки, а `check_name()` применяет только к имени конечного файла. Поэтому файл `secrets/data.txt`, который нельзя прочитать через read_file, доступен через `search(pattern=".*", path=".")`. То же относится к файлам внутри `.env.private` и `credentials`. Фильтр срабатывает при прямом обращении, но не при обходе из родителя.

Временная фикстура содержала только строку `SYNTHETIC_PRIVATE_MARKER`. Настоящие Reader и call_tool вернули:

```text
read_file("secrets/data.txt") -> ОТКАЗ: файл похож на секрет и недоступен
search("SYNTHETIC_PRIVATE_MARKER", ".") -> isError=false
.env.private/data.txt:1: SYNTHETIC_PRIVATE_MARKER
credentials/data.txt:1: SYNTHETIC_PRIVATE_MARKER
secrets/data.txt:1: SYNTHETIC_PRIVATE_MARKER
```

Другой воспроизведённый обход той же границы: проверка `.git` чувствительна к регистру, хотя файловая система этого Mac — нет. В фиктивном `.git/config` записан `SYNTHETIC_GIT_CONFIG`. Вызов `read_file(".GIT/config")` вернул эту строку с `isError=false`; существование `.GIT` при создании `.git` также подтверждено. В обычном checkout это открывает внутренние файлы Git; в worktree аналогично становится доступен файл-указатель `.git`. Реальный Git-config проекта и реальные секреты для опыта не читались.

**Сценарий и последствие:** недоверенное обращение побуждает аналитика выполнить широкий поиск по проекту или прочитать `.GIT/config`. Если в проекте находится каталог с закрытыми данными или в Git-конфигурации есть чувствительное значение, оно поступает модели через разрешённый MCP. Для этого не требуются shell, запись, гонка или отключение песочницы: корень проекта разрешён профилем. Поздняя маскировка исходящего ответа не отменяет уже выполненного чтения моделью.

**Что исправить:** применять одну проверку полного относительного пути ко всем найденным файлам и отсекаемым каталогам; запрет `.git` должен учитывать регистр целевой файловой системы. Проверить перечисленные обходы через реальный MCP-вызов. Это доведение уже заявленных запретов, а не требование распознавать произвольные секреты по содержимому.

## N7 — средняя серьёзность: профиль MCP блокирует историю Git в штатном worktree аналитика

**Места:** `tools/support_agent/support_agent/sandbox.py:81–89`, `llm.py:231–242`, `readonly_mcp.py:149–172`; штатное создание каталога — `hotfix.py:130–143`.

Аналитик работает в `<repo>/.worktrees/support-agent-etalon`, созданном через `git worktree add`. Его `.git` — файл-указатель: настоящие метаданные находятся в `<repo>/.git/worktrees/support-agent-etalon`, а объекты и общие ссылки — в `<repo>/.git`. Новый профиль запрещает чтение данных во всём домашнем каталоге и разрешает исключения только для корня аналитика, каталога кода MCP и интерпретатора. Внешние Git-метаданные под эти исключения не попадают.

Проверка реального расположения **текущего** worktree через `git rev-parse --absolute-git-dir` дала:

```text
root   = /Users/deniscivkunov/Projects/WMS/.worktrees/wms639-support-agent
gitdir = /Users/deniscivkunov/Projects/WMS/.git/worktrees/wms639-support-agent
gitdir_under_home = true
gitdir_under_read_exceptions = false
```

Штатный `analysis_dir()` создаёт такую же структуру. Следовательно, при применении этих правил git_log/git_show не смогут прочитать HEAD, ссылки и объекты. Обычное чтение исходников при этом остаётся доступным, поэтому проверка одного README через живой Codex эту регрессию не обнаруживает. Нынешний успешный тест Git использует обычный временный репозиторий с `.git` внутри корня и запускает Reader без профиля; он не покрывает штатную структуру.

**Сценарий и последствие:** запасной Codex-аналитик получает обращение, для которого требуется история изменения или файл предыдущей версии; оба специально предоставленных Git-инструмента отказывают из-за недоступных метаданных. Это регрессия нового ограничителя чтения, а не предложение расширить аналитические функции.

**Граница доказательства:** вывод сделан по фактическим путям, коду создания worktree и сформированным правилам доступа. Живой отказ именно git_log/git_show под Seatbelt в этом круге не воспроизведён: среда запрещает вложенный sandbox-exec. Не выдаю статическую проверку за выполненный системный вызов.

**Что исправить:** предоставить доверенному Git-пути доступ к проверенным метаданным именно нужного worktree/репозитория, сохранив запрет их прямого чтения моделью, либо получать историю через другой ограниченный доверенный механизм. Проверить git_log и git_show на настоящем связанном worktree под профилем, а не только на обычном `git init`.

## Проверка инструментов Codex и предел вывода об approve

Настройка `mcp_servers.wms.default_tools_approval_mode` имеет область одного сервера; это подтверждается и её положением в argv, и [официальным описанием конфигурации](https://learn.chatgpt.com/docs/config-file/config-reference). Тест JSON-RPC подтверждает ровно пять объявленных инструментов сервера: list_files, read_file, search, git_log, git_show; запрос write_file отвергается. Вызов subprocess в читателе передаёт массив аргументов фиксированной команде Git без shell. На фиктивном репозитории отдельный fsmonitor-маркер не появился.

Однако выключение перечисленных features и список tools/list самого MCP не являются инвентаризацией **всех** инструментов CLI. Например, официальный справочник отдельно описывает `tools.view_image`, которого нет среди явных отключений build_codex. Это основание обозначить границу проверки, но не подтверждённый в этом круге эксплойт: доступность такого инструмента конкретной модели и возможность чтения им вне корня не воспроизведены. Также не подтверждаю отсутствие других встроенных инструментов только по отчёту разработчика «shell-инструмента нет».

Живые модельные вызовы не выполнялись; платные лимиты не расходовались, авторизация владельца не читалась. Для закрытия этой части нужен фактический список доступных инструментов используемой сборки/модели и проверка, что за пределы MCP нельзя выйти другим инструментом чтения или исполнения. Само значение `approve` глобального обхода разрешений в проверенных материалах не создаёт.
