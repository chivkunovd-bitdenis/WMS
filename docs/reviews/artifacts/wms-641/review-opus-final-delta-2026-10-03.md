### d6dfde89 — заморозка первого исходящего текста при ретраях

Ключи `owner_digest` и `queue_reply` до правки включали `_digest(body)` — одно и то же обращение + одна и та же задача + перефразированный текст давали НОВЫЙ ключ, обходили outbox-дедуп и уходили повторным сообщением. После: ключ использует стабильный `slot` (`_slot(value)` → валидация `[A-Za-z0-9_-]{1,40}`, по умолчанию `"default"`, пустая строка → `"default"`, невалидное → `ToolDenied("invalid_action_slot")`). Ключи:
- `agent_digest:{event_id}:{tid|0}:{slot}`
- `agent_reply:{event_id}:{chat_id}:{tid}:{slot}`

Ответ инструмента теперь содержит `frozen_text = row["text"]`, то есть модель видит фактический поставленный в очередь текст и может скорректировать поведение. Для реально различных сообщений одному адресату — явный `slot` (например, `first`/`second`). Нового события (`event_id`) достаточно, чтобы ключ сменился и ушло новое сообщение — что сохраняется для нормального продолжения разговора.

Инструкция в `agent_instructions.md` описывает это правило: «повторный вызов… сохраняет первый поставленный в очередь текст; для двух разных сообщений — передай каждому свой устойчивый `slot`; исправленный текст после уже поставленной отправки требует нового поручения владельца».

Проверочные тесты в `test_agent_tools.py` подтверждают: тот же `event_id` + default slot → один outbox-ряд, `frozen_text` = первый текст; новое сообщение (новый `event_id`) → новый ключ; `slot="second"` → новый ключ; `queue_reply` с перефразированным `text` при том же `event` → `queued=False`, `frozen_text` = первый. Корректно.

Побочные эффекты: предшествующий дедуп `_tool_owner_digest` через `agent_task_notice_event:{event_id}` срабатывает ДО вычисления `slot` — не ломается. `_slot("")` → `"default"` — молча, но безопасно. Блокеров нет.

### 24d58ef2 — обновление thread при смене набора инструментов

Добавлена `agent_capability_signature(tools, cwd)`: детерминированный SHA-256 от сортированных по `name` спецификаций инструментов (включая вложенные `namespace.tools`) и рабочего каталога. В `agent_turn` на пути Codex:
- `if (state.get("rollover") or state.get("capability_signature") != signature) and session_id:` запускает handoff в старой сессии (`AppServerTurn(..., mode="readonly", tools=[], session_id=session_id)`), затем создаёт новый thread с актуальными `developerInstructions` + `dynamicTools` в `thread/start`.
- При совпадении сигнатуры и отсутствии rollover `thread/resume` переиспользуется (нормальная персистенция подтверждена `native-resume-smoke`).
- `started()` колбэк и финальный `kv_set` сохраняют `capability_signature` вместе с `thread_id`/`handoff`/`rollover`.

Тест `test_capability_change_rolls_thread_but_identical_tools_resume` подтверждает: два подряд вызова с идентичным `tools=first` переиспользуют `thread-1`; смена на `tools=second` даёт пару вызовов (handoff в `thread-1`, затем новый thread). Логика корректна и соответствует R82/C83: валидный fix моего прежнего пункта №12 — именно для случая изменившихся capabilities, отдельно от обычного resume. Прошлое смешение №12 с №1 признаю ошибочным: это была моя оценка на основе чтения кода/схем, а не новое явное снятие владельцем; формулирую как evidence-based correction.

Побочное: `cwd` входит в сигнатуру — смена worktree для того же `session_key` тоже форсирует новый thread (разумно). Claude-ветка не затронута: она ежеходово передаёт список сервисных инструментов через JSON-мост, поэтому не нуждается в сигнатуре. Хэши стабильны, overhead JSON-сериализации несущественный. Блокеров нет.
