## Оценка остатка F2

Внешний профиль действительно добавляет защиту известных чувствительных каталогов. Это существенное улучшение по сравнению с предыдущим запуском. Но `sandbox.py:60–78` начинает с `(allow default)`, а `llm.py:362–365` добавляет лишь перечисленные запреты чтения и явно разрешает сеть. Это не ограничение чтения предоставленным проектом. Проверка сформированного профиля показала, что синтетические пути `Documents/private.txt` и `Projects/other/.env` вне worktree не попадают под запрет, тогда как `.ssh/id_test` попадает. Файлы пользователя для этой проверки не открывались; это проверка правил, а не выполненное чтение через Seatbelt.

«Собственный токен Codex» здесь означает собственную **копию файла**, но не отдельные полномочия. `_prepare_codex_home` побайтно копирует файл авторизации владельца. На синтетическом источнике равенство копии и источника подтверждено. Аналитик сохраняет shell, внутри Codex получает `danger-full-access`, а внешний профиль разрешает чтение этой копии и сеть. Поэтому команда, которую модель выполнит вследствие недоверенной инструкции, получает возможность прочитать эту авторизацию и обратиться наружу напрямую. Такая передача вообще не проходит через `scrub`, предпросмотр и подтверждение владельца. Расширять регулярные выражения для этого сценария бессмысленно.

**Как явно задокументированный остаток запасного пути это не принимаю.** Запасной путь автоматически включается на тех же недоверенных обращениях; название «запасной» не меняет границу доступа. Авторизация самого процесса CLI необходима, но доступ произвольной модельной команды к той же авторизации и внешней сети из этого не следует. Это продолжение прежнего F2, а не новое требование получить идеальную маскировку всех возможных секретов.

Самое небольшое направление исправления, уже согласующееся с используемой в проекте техникой: отключить произвольный shell и внешние инструменты у запасного аналитика, а чтение нужного кода выполнять доверенным ограниченным читателем и передавать результат модели. Если сохранять shell, нужны ограничения именно его чтения и сети, отделённые от доступа самого CLI к авторизации. Одно выключение всей сети сломает CLI, а ещё несколько путей в списке запретов не устранят саму причину. Конкретный вариант должен сохранить предусмотренный R36 запасной разбор; отключение Codex целиком не предлагается. Работоспособность нового варианта здесь не заявляется — реализации такого варианта в проверяемом коммите нет.

## Новая существенная находка

### N5 — высокая серьёзность: доступный аналитику CODEX_HOME стал источником привилегированной записи

**Места:** `tools/support_agent/support_agent/llm.py:360–370,384–418`. Это непосредственная регрессия исправления F2: в предыдущем варианте этих переноса авторизации и постоянного каталога не было.

Диспетчер допускает запись аналитика в его CODEX_HOME, затем без посредника вызывает `_sync_codex_auth`. Проверка «валидности» сравнивает только наборы ключей JSON и наличие непустых строк в `tokens`. Она не устанавливает, что изменения внесены механизмом обновления авторизации, а не shell-командой модели. Поэтому аналитик может заменить значения токена и аккаунта, сохранив форму, а диспетчер сам запишет их в основной файл владельца за пределами песочницы. Это нарушает заявленную границу «расследование только на чтение» и может сломать авторизацию последующих запусков. Обновлением настоящего токена произвольная непустая строка не становится.

**Воспроизведение через настоящий путь вызова.** В Python stdin использован существующий тестовый `tests.test_llm_router.router`: он создаёт только фиктивный `fake-codex-auth.json` во временном каталоге и указывает его в `codex_auth_path`. Создано обращение, выполнен `llm.ask(..., mode="readonly", ticket_id=tid, session_key="analyst", cli_only="codex")`. Вместо живой модели функция `exec_fn` получила построенную команду, нашла переданный CODEX_HOME, заменила в его `auth.json` только `tokens.access_token` и `tokens.account_id` на синтетические строки, записала обычный ответ в путь `-o` и вернула успех. Остальной код маршрутизатора, включая синхронизацию, работал без подмены. После возврата оба значения в исходном фиктивном файле оказались заменены:

```text
copy_equals_owner_credential = true
owner_access_replaced       = true
owner_account_replaced      = true
network_denied              = false
```

В том же новом переходе доверия есть второй вариант: при повторной подготовке постоянного каталога `target.write_bytes(...)` следует по символической ссылке, а не создаёт гарантированно обычный файл. В опыте `CODEX_HOME/auth.json` заменён ссылкой на соседний фиктивный файл **вне CODEX_HOME**. Следующий `_prepare_codex_home` затёр этот файл содержимым фиктивной авторизации и применил к нему chmod:

```text
outside_file_overwritten = true
```

Этот второй опыт подтверждает поведение доверенного Python-кода при уже подставленной ссылке. Создание ссылки живой моделью под Seatbelt здесь не проверено: запуск вложенной песочницы запрещён средой. Первый сценарий не требует ссылок: достаточно обычной записи в файл внутри явно разрешённого каталога.

**Что исправить:** не переносить управляемый моделью auth.json обратно в авторизацию владельца как доверенное обновление; отделить обновление авторизации от модельных команд. При подготовке повторно используемого каталога исключить запись по подставленным ссылкам, включая проверку самого каталога и безопасную замену файла. Нужны проверки сохранности исходной авторизации при подмене значений с прежней формой и сохранности внешнего файла при ссылке. Добавление ещё одной проверки формы JSON не закрывает оба сценария.

Это локальные опыты с фиктивными данными и подделкой исполнителя CLI. Настоящие ключи, файлы авторизации и кабинеты не читались и не менялись; обращения к моделям и внешней сети не выполнялись. Вероятность того, что живая модель подчинится вредной инструкции, не измерялась: проверены полномочия и последствия её допустимой записи.
