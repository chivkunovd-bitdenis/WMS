## N1 — P1: совпадение версии скрывает отсутствующий RLS или политику

**Место:** `scripts/agent_db/seller_access.py:274–276`, `scripts/agent_db/gateway.py:184–186`.

`preflight_sql()` читает `relrowsecurity` и наличие политик, но `is_current()` использует только комментарий роли и вычисленный отпечаток схемы/спецификации. Ни отсутствие RLS, ни отсутствие политики на решение не влияют. В результате уже существующие ветки восстановления в `render_sql()` вообще не вызываются.

**Сценарий:** роль один раз успешно подготовлена новой версией; затем при обслуживании/миграции `products` остаётся без включённого RLS либо без своей политики. Имена колонок и комментарий роли прежние. Следующий ensure получает соответствующее состояние из каталога, но отвечает `state=unchanged` и выполняет только настройки роли. Если выключен RLS, сохранённые права SELECT позволяют читать строки других селлеров; если RLS включён, но собственная политика удалена, роль перестаёт видеть строки. Отдельно удаление `agent_ro_all` оставляет без строк общую роль. Это последствия правил PostgreSQL: выключенный RLS игнорирует политики, а включённый RLS без подходящей разрешающей политики закрывает строки ([документация PostgreSQL 16](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)).

Это **не утверждение, что новый ensure сам выключает RLS**, и не описание текущего продового инцидента. Дефект — успешный ответ проверки при уже прочитанном несоответствии. Предыдущая версия при очередном ensure включала RLS и пересоздавала политики; новая теряет это восстановление. Аналогичный случай без явного отключения RLS — пересоздание таблицы с теми же именами колонок: комментарий роли переживает замену таблицы, версия совпадает, права и политики для нового объекта не подготавливаются.

**Подтверждение:** вызван настоящий `gateway.ensure_seller()` с подставленным CSV каталога и перехватом SQL вместо выполнения в БД. Для текущего комментария поочерёдно убраны `products` из `rls_enabled`, собственная политика и `agent_ro_all` из `policies`. Во всех трёх случаях получены `state=unchanged` и отсутствие восстанавливающего SQL. Проверка в PostgreSQL в этой сессии недоступна; последствия для чтения следуют из документированной семантики RLS.

**Исправление:** разрешать короткую ветку только при совпадении версии **и** наличии включённого RLS и требуемых политик на всех включённых таблицах. Использовать уже полученный каталог; при несоответствии запускать существующую полную транзакцию с таймаутами. Это сохраняет отсутствие DDL на исправном текущем состоянии. Добавить регрессионные проверки: текущая метка + выключенный RLS; текущая метка + отсутствующая политика; после восстановления видны только свои строки. Проверку короткой ветки под удерживаемой блокировкой сохранить.

## N2 — P1: изменение правила секретных колонок не меняет версию прав

**Место:** `scripts/agent_db/seller_access.py:255–262`; правило, которое пропущено в версии, — `SECRET_NAME_RE` и его применение в `is_secret()` / `allowed_columns()`.

Версия учитывает явный словарь `SECRET_COLUMNS` и имена колонок, но не учитывает регулярное выражение, которым также определяется запрет чтения секретов. Поэтому изменение фактически разрешённого списка колонок не обязательно меняет версию прав.

**Сценарий:** разрешённая таблица содержит колонку `access_key`. Нынешнее правило её не распознаёт, ensure выдаёт ей SELECT и записывает комментарий версии. Следующий релиз расширяет `SECRET_NAME_RE`, добавляя `access_key`, без изменения схемы или `SECRET_COLUMNS`. Генератор теперь считает колонку секретной, однако отпечаток остаётся прежним. Ensure возвращает `state=unchanged`, REVOKE не выполняется, ранее выданное право чтения сохраняется и при дальнейших повторах через шесть часов. Предыдущая версия пересчитывала права при каждом ensure и применяла бы новое правило.

**Подтверждение:** в памяти создан каталог с `products.access_key` и текущей меткой; затем только на время проверки расширен `SECRET_NAME_RE`. Получено одновременно `is_secret('products', 'access_key') == True`, `is_current(catalog) == True`, ответ шлюза `state=unchanged` и отсутствие REVOKE в переданном SQL. Файлы генератора не менялись, настоящие секреты не использовались.

**Исправление:** включить в отпечаток прав фактические списки колонок, рассчитанные через `allowed_columns()` для каждой таблицы, сохранив остальные необходимые составляющие версии. Так изменение правила классификации меняет версию именно тогда, когда меняются выдаваемые права. Допустим и явный учёт шаблона/флагов регулярного выражения, но отпечаток результата также учитывает дальнейшие изменения логики классификации. Проверить на PostgreSQL переход «колонка ранее разрешена → теперь секретная»: после ensure SELECT этой колонки запрещён, обычные колонки доступны, существующие политики не пересозданы.

## Блокировки, атомарность, гонки и миграции

- **Пути к ACCESS EXCLUSIVE без `lock_timeout` в проверенном ensure не найдено.** Обе ветки изменения начинают одну транзакцию с `SET LOCAL lock_timeout = '2s'` и `SET LOCAL statement_timeout = '60s'` до команд роли/прав/политик. Предварительный SELECT селлера выполняется отдельно и без этих SET, но ACCESS EXCLUSIVE он не запрашивает. Он всё ещё может ждать чужой DDL; это не тот неограниченный эксклюзивный запрос, ради которого сделана правка.
- **Частичного коммита внутри apply по коду нет.** ENABLE RLS, политики, права и комментарий находятся между одним BEGIN/COMMIT. `psql -X -v ON_ERROR_STOP=1` завершает выполнение при SQL-ошибке; незавершённая транзакция откатывается. При lock/statement timeout новая роль либо изменения старой роли не должны сохраняться частично. N1 относится к пропуску восстановления уже неполного состояния, а не к нарушению атомарности этой транзакции.
- **Два ensure не сериализуют чтение каталога и применение.** Оба могут получить состояние до первого коммита. Проигравший вызов может встретить конфликт создания роли/политики либо обновления системного каталога и завершиться ошибкой; вся его транзакция откатится. Это допустимый повторяемый отказ в заданном объёме задачи: пути к частично сохранённым политикам или дополнительным правам из этой гонки не обнаружено. Клиент выдержит паузу; следующий вызов заново прочитает каталог. Живой параллельный прогон здесь не выполнен, успешность обоих одновременных вызовов не заявляется.
- **Обычное добавление секретной колонки обработано правильно.** Добавление `products.new_api_token` меняет версию прав; колонка исключается из GRANT, а прежние политики не пересоздаются. Это проверено генерацией SQL. Изменение явного `SECRET_COLUMNS` также меняет версию. Изменение `TABLES` меняет версию политик, появление ранее отсутствовавшей разрешённой таблицы — версию прав. N2 касается отдельного пропущенного входа — правила распознавания секретов.
- **Таймауты не являются общим двухсекундным/шестидесятисекундным бюджетом транзакции.** `lock_timeout` ограничивает каждое ожидание блокировки, `statement_timeout` — отдельную команду; уже полученные блокировки удерживаются до конца транзакции. Поэтому при обновлении большого числа политик нельзя обещать, что весь проход займёт максимум две секунды. Это свойство выбранного исправления, не дополнительная находка ([документация PostgreSQL 16](https://www.postgresql.org/docs/16/runtime-config-client.html)).
