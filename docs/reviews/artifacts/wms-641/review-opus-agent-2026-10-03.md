### Серьёзные дефекты

1) **Dynamic tools теряются при resume Codex thread → ломает R82/C83/C85 после перезапуска.** `app_server.AppServerTurn.run` при `session_id` отправляет только `thread/resume` с `{"threadId": session_id}` (`tools/support_agent/support_agent/app_server.py:149-153`). По установленной схеме протокола (`.bot-audit-20261003/app-server-schema/v2/ThreadResumeParams.json`) и `TurnStartParams.json`, `dynamicTools` принимается ТОЛЬКО в `thread/start`; ни `thread/resume`, ни `turn/start` эту таблицу не принимают. Следовательно, если Codex не персистит динамические инструменты вместе с rollout (документация этого не гарантирует), после рестарта службы и resume существующего `agent_session:*` thread модель получит пустой набор сервисных инструментов. Поведение R82 «после перезапуска считай сохранённые задачи… авторитетнее памяти беседы» и C83 «переполнение контекста/сбой процесса… новая сессия получает handoff» не воспроизводится, потому что handoff-ветка (`llm.py:243-275`) включается лишь при `state.get("rollover")`, а обычный resume (без rollover) сразу идёт в `thread/resume` без повторной привязки `remember`/`task_record`/`project_job`. Fake-сервер в `tests/test_agent_runtime.py:fake_server` на resume никаких toolов не проверяет, поэтому тест не ловит регрессию. Нужно либо на resume сверять, что dynamicTools всё ещё активны (и форсировать `thread/start` с handoff при расхождении), либо явно переоткрывать thread при каждом рестарте.

2) **`AgentCoordinator._run_job` стирает поле `cancel_requested=True` при `_save_job`.** На пути успешного завершения `job.update(status="done", result=..., finished_at=...)` и далее `_save_job(job)` сливает локальный `job` (без ключа `cancel_requested`) с текущим состоянием через `{**current, **job}` (`agent_coordinator.py:238-245`). Защиты для `cancel_requested` в `_save_job` нет (защищены только `phase`, `status=done`, `preflight_status`, `deadline_status`). Если владелец вызвал `cancel_job`, пока модель уже возвращала ответ, `_save_job` объявит задачу `done` и потеряет флаг отмены — повторная отправка `cancel_job` после этого отвечает `job_not_found`-подобным/бессмысленным; отчёт в Telegram уйдёт как успешный. Нужно сохранять `cancel_requested` в merge-политике и/или прерывать завершение при наличии флага.

3) **`AgentCoordinator._run_job` локальный snapshot `deadline_at` неразогреваемый → игнорирует перенос дедлайна владельцем.** Cancel-коллбэк (`agent_coordinator.py:388-393`) смотрит `job.get("deadline_at")` из локальной переменной, снятой в начале `_run_job`. Если владелец через будущий инструмент/CLI обновляет deadline (или `tick()` переключает `deadline_status` на `finalizing` на другом треде), `_run_job` этого не видит. По R80 «срок пакета сохраняется с временем/зоной» и «готовое можно выпускать раньше по разрешению, к сроку — только безопасную готовую часть»: сейчас изменение дедлайна в живой задаче либо игнорируется (ранний старт после `tick`), либо приводит к рассогласованию между `finalizing` в KV и локальным `finalizing`-булевым. Чтение `self.store.kv_get(f"agent_job:{job_id}", {}).get("deadline_at")` в самом коллбэке решает проблему.

4) **`_tool_trello_sync` зависает в `"creating"`/`"unknown"` при переизвестном исходе.** В `tools/support_agent/support_agent/agent_tools.py:456-470`, если первый `trello.create_list()` потерял ответ, `list_state.status` остаётся `"creating"`. На следующем ходе ветка `list_named()` возвращает ID (список уже создан) — тогда ОК. Но если `list_named()` в этот момент ответил ошибкой (`TrelloError` → проброс), либо список был сразу закрыт на доске, повторная попытка попадает в `return {"status": "unknown", ...}` вечно, пока не отработает `list_named`. Это допустимо, но у `kv_set(list_key, {"status": "sending"/"creating"})` нет TTL/sweep — если первая попытка на самом деле не создала список и ответила rejected, state может оказаться `"rejected"` и этап «Описание согласовано» (R74/C78) перестаёт когда-либо работать до ручного вмешательства владельца. Нужна возможность сбросить state (например, после `list_named` отрицательного ответа при `status=="rejected"` разрешать повторный create).

5) **`send_job_file` принимает модельный `path` относительно cwd сервиса, не worktree.** `agent_coordinator.py:434-436`: `path = Path(str(args.get("path", ""))).resolve()` без anchor-а в `root`. Если модель отдаёт относительный путь (`"out/export.csv"`), `resolve()` интерпретирует его относительно текущего cwd процесса сервиса (не worktree). Чаще всего это каталог запуска launchd, не репозиторий. Проверка `root not in path.parents` отбракует всё лежащее за пределами, то есть вернёт ошибку — но для нормального сценария из R85 («сохрани файл под job worktree, вызови `send_job_file`») владелец/модель будут получать `file_not_in_job_worktree`, пока не угадают абсолют. Безопасно, но ломает заявленный путь. Нужно разрешать «относительно worktree»: `path = (root / args["path"]).resolve()` и затем сверять с `root`.

6) **Mockup worktree не удаляется и не отслеживается в `active_jobs` при неуспехе → копии остаются и блокируют повторную попытку.** `AgentCoordinator._submit_mockup` держит ключ `mockup:{tid}` только в `active_jobs` на время выполнения. `MockupRunner.run` при `StepFailed` ставит `set_stage(tid, "failed")` и возвращается, НО путь `.worktrees/mockup-wms-support-{tid}-{version[:12]}` остаётся на диске; `_submit_mockup` не делает cleanup. Следующая попытка (например, после правки описания и queued с новой версией) создаст НОВЫЙ worktree с другим `version[:12]` суффиксом — забивая `.worktrees/`. Также при повторном вызове с ТОЙ ЖЕ версией `if not path.exists():` обойдёт `worktree add`, но ветка `branch` может уже существовать локально с мусором. По R82/R35 должен выясняться исход внешнего состояния до повтора — здесь нет. Это существовавший до разделения моделей паттерн, но стал заметнее с частым перезапуском Sonnet mockup.

7) **`AgentTools._tool_task_record` под `confirm_author=True` для КЛИЕНТА вызывает `_tool_trello_sync(..., event, owner=True)` вопреки scope.** В `agent_tools.py:311-312`: `card = self._tool_trello_sync({"ticket_id": tid, "action": "create"}, event, True)`. Здесь `owner=True` подставлено жёстко, хотя исходный `owner` в `_tool_task_record` может быть `False` (автор клиента подтверждает описание). В теле `_tool_trello_sync` используется только `self._ticket(tid, event, owner)` для проверки scope. Для клиента `_ticket` при `owner=True` пропустит обращение из любого чата. Но реальная логика у клиента всегда указывает `ticket.chat_id == event.chat_id`, так что эффект маленький. Проблема в том, что принцип «scope checked by code, not model» формально нарушен: клиентский путь поднимает флаг owner, минуя `AgentTools.dispatch`. Корректно: передавать настоящий `owner` или вызывать внутренний `_trello_create(tid, event)` без флага.

### Средние замечания

8) **`AgentCoordinator._submit_job` допускает параллельный повторный submit после аварии потока.** Проверка `if job_id in self.active_jobs` под `job_lock` снимается в `finally`. Если `_run_job` поднимает BaseException (например, KeyboardInterrupt при сигнале), `finally` снимет, но `_save_job` c `needs_review`/`cancelled` не выполнится; следующий `tick()` увидит `status in ("queued", "running")` и снова submitnet. Для прерывания OK, но нет инварианта «на одной job_id единожды активная работа при грубом сбое». Low-risk.

9) **`_hourly` может пропустить тик при длинном расписании.** `agent_coordinator.py:485-491`: ставит `next_at = now + interval` ДО submit в пул. Если `self._hourly` упал внутри (сетевой сбой Trello), следующий тик произойдёт только через `interval`. Небольшой пропуск сводки; совместимо с R79. Low.

10) **`_claude_agent_turn` tool-loop лимит 20 — потенциальная тупиковая остановка.** `llm.py:343-386` ограничивает ход 20 вызовами сервисных инструментов, затем `raise LlmError`. Для сложного владельческого сообщения или сверки нескольких обращений это может быть недостаточно; `process_chat` ловит `LlmError` и помечает сообщение `attempts+1`, но после 3 попыток объявляет `error` и прекращает работу (`pipeline.py:308-316, 317-322`). При reproducible loop (например, модель всегда повторяет один и тот же вызов `read_context`) сводка R75 потеряется для владельца. Low-mid.

11) **`persist_task` коммитит до проверки гонки версий (`agent_tools.py` → `canonical_tasks.py:97-110`).** Между write/add/commit и финальным `with store.transaction()` возможен сценарий: описание изменилось → `CanonicalTaskError("description changed during Git publication")`, но локальная ветка уже хранит старый коммит и будет запушена при следующем `persist_task` ровно так же. Retry перепишет файл и сделает новый коммит поверх; работоспособно, но история ветки замусоривается промежуточными устаревшими версиями. Не блокер, но стоит сверять версию ДО коммита (локальный rollback через `git reset --hard HEAD~1`).

12) **`AgentTools.specs("owner")` динамически расширяется — но resumed-сессия Codex о новых инструментах не узнает (см. п.1).** Если позднее добавятся новые тулы (например, Trello comment), владельцевская старая сессия с их отсутствием продолжит жить до истечения контекста. Явно не R-требование, но ломает естественное ожидание владельца «новые возможности появились сразу».
