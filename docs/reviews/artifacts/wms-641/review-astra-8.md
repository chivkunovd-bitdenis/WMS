## N1 — средняя серьёзность (P2): SQL-ошибка с прочитанным значением обходит предпросмотр

**Сценарий.** Аналитик выполняет допустимый запрос `SELECT name::integer FROM sellers`. База читает доступное роли название, не может преобразовать его в число и возвращает название прямо в тексте ошибки. Это бывает и при обычной ошибке выбора типа; успешный SQL-запрос для получения значения не нужен. Модель использует значение из ошибки в `need_data.points`. У обращения нет `db_used`, поэтому уточняющий вопрос немедленно уходит клиенту, без дословного предпросмотра владельцу. Таким же признаком управляется отправка «пробуйте».

**Причина и место.** В `tools/support_agent/support_agent/prod_sql_mcp.py:56–63` след пишется только после нормального возврата `run_query()`. Между тем `prod_sql.py:250–252` включает до 400 символов серверного stderr в `RuntimeError`, а MCP возвращает этот текст модели. `_note_db_use()` в `llm.py:486–497` не видит следа; `send_client_gated()` в `pipeline.py:687–692` разрешает автоматическую отправку. Ошибочный результат тоже способен содержать прочитанные данные, поэтому условие «успешный запрос» недостаточно для N1 круга 7 и R44.

**Воспроизведение.** На временном PostgreSQL 16.14 под сгенерированной ролью S1:

```sql
SELECT name::int FROM sellers;
-- код psql 3:
-- ERROR: invalid input syntax for type integer: "ИП Иванов"
```

Это собственная строка S1; обход RLS и чтение чужой строки этим запросом не заявляются. Затем отдельно проверена цепочка настоящих `prod_sql_mcp.handle()` → `_note_db_use()` → `_ask_data()` → отправка через два поддельных бота. Подменён только ответ SSH на ошибку того же вида с синтетическим значением `SELLER_A_PRIVATE_VALUE_7319`; текст вопроса задан как возможный ответ аналитика. Получено:

```text
validate_sql('select name::integer from sellers') — принят
MCP isError — true; значение присутствует в тексте ответа
файл следа — пуст
db_used — отсутствует
стадия — await_client_data
владелец — 0 сообщений
клиент — «Чтобы разобраться, пришлите, пожалуйста:
1. ОШИБКА: ошибка запроса (код 3): ERROR: invalid input syntax for type integer: "SELLER_A_PRIVATE_VALUE_7319"»
```

**Исправление.** Учитывать обращения к БД, после которых модели возвращается любой серверный текст, включая ошибки. Проще фиксировать факт отправки валидного запроса до выдачи модели результата, независимо от кода psql. Либо ошибки должны возвращаться без любых значений данных, но тогда это должно обеспечиваться кодом, а не предположением о безопасном stderr. Если след не удалось записать/прочитать, нельзя считать это доказательством отсутствия чтения и разрешать автоматическую отправку. Проверить ошибку преобразования поля из БД и отсутствие предшествующих успешных запросов: вопрос и «пробуйте» должны попасть в предпросмотр. На обычном успешном чтении исправление круга 7 работает; находка относится к непокрытому пути ошибки.

## N2 — средняя серьёзность (P2): неограниченное накопление SQL-ответа переместилось в серверный шлюз

**Сценарий.** Через штатный SQL-инструмент проходит `SELECT repeat('x', 8388608)` — одна строка, которую внешний LIMIT не уменьшает. Клиентский читатель теперь ограничивает stdout потоком, но до него результат целиком накапливается в Python-процессе шлюза на сервере. При больших текстовых/JSON-полях и нескольких параллельных запросах это создаёт неограниченное потребление памяти на хосте WMS. Клиентский лимит начинает действовать только после такого накопления.

**Причина и место.** `scripts/agent_db/gateway.py:50–52` вызывает `subprocess.run(..., capture_output=True, text=True, timeout=120)`. В `main():89–92` stdout и stderr отправляются в SSH лишь после завершения этого вызова. Ни строкового, ни байтового бюджета в `run_psql()` нет. Таймаут ограничивает длительность, но не объём вывода. Это вновь введённое звено между psql и исправленным `prod_sql.default_runner()`.

**Воспроизведение.** Настоящий `gateway.run_psql()` запущен с заменой только `psql_argv()` на синтетический Python-процесс, печатающий большой ответ. Он вернул целиком:

```text
returncode = 0
stdout_bytes = 8 388 611
stderr_bytes = 1 048 576
```

Ни psql, ни боевая БД в этом опыте не использовались. Исчерпание памяти намеренно не воспроизводилось. Подтверждено полное накопление существенно больше клиентского бюджета 60 КБ, включая stderr. Штатные тесты ограниченного клиентского чтения и длинного CSV проходят: исходное падение CSV-парсера устранено, но гарантия ограничения ответа не охватывает новый шлюз.

**Исправление.** Ограничить накопление stdout и stderr непосредственно в шлюзе до создания полного `CompletedProcess.stdout/stderr`: читать и передавать ответ потоком с бюджетом либо прекращать запрос при достижении серверного предела. Согласовать признак усечения/отказа с клиентом и завершение дочернего запроса. Проверить большой ответ через сам `gateway.py`, большой stderr, многобайтное поле и следующий нормальный запрос. Повторная обрезка уже собранной строки недостаточна.

## N3 — высокая серьёзность (P1): forced-command шлюз допускает shell и переподключение в postgres через метакоманды psql

**Сценарий.** Отправитель, имеющий возможность вызвать разрешённый SSH-вход `sql wms_agent_s_<uuid>`, передаёт в stdin не SQL, а команды psql. Проверка имени роли проходит, но дальше `psql` интерпретирует `\!` как запуск shell, а `\connect` — как создание нового соединения с другой ролью. Таким образом, запрет `sql postgres` на входе шлюза обходится без `SET ROLE` и без членства роли селлера в других ролях. Политики RLS нового соединения postgres не ограничивают.

**Причина и место.** `scripts/agent_db/gateway.py:88–90` передаёт весь stdin в psql без проверки. Параметры `-X` и `ON_ERROR_STOP=1` из строк 43–52 не выключают метакоманды. При штатной конфигурации psql запускается внутри контейнера через `docker exec`; `\!` исполнится с правами пользователя этого процесса внутри контейнера. Это не утверждение о получении shell самого хоста root.

**Воспроизведение.** Через настоящий `gateway.py`, с локальным psql временного кластера вместо Docker и ролью S1, созданы два независимых процесса. В обоих `SSH_ORIGINAL_COMMAND` — разрешённая форма `sql <роль S1>`:

```text
stdin: \! printf WMS_GATEWAY_SHELL_PROBE
returncode: 0
stdout: WMS_GATEWAY_SHELL_PROBE
```

```text
stdin:
\connect wms postgres
SELECT current_user, count(*) FROM sellers;

returncode: 0
stdout:
You are now connected to database "wms" as user "postgres".
current_user,count
postgres,4
```

В обычном соединении этой роли виден один селлер; после переподключения видны все четыре тестовых селлера двух организаций. Тестовый кластер использует локальную trust-аутентификацию. На проде переподключение зависит от локальной аутентификации; штатные `ensure-seller` уже рассчитаны на возможность запуска psql под postgres тем же серверным процессом. Shell-метакоманда вообще не требует прав роли PostgreSQL. Продовый вход не проверялся.

**Точная граница доказательства.** Текущий `prod_sql.validate_sql()` запрещает любой обратный слеш, а модель не получает SSH-ключ. Поэтому это подтверждённый обход ограничения *самого шлюза* при прямом вводе в его stdin, а не доказанный способ передать эти строки через текущий `sql_query`. Нельзя приписывать успешную атаку модели. Но объявленная принудительная команда не ограничивает этот SSH-вход тремя операциями: она даёт дополнительный командный интерпретатор и возможность смены соединения.

**Исправление.** В ветке `sql` исключить интерпретацию ввода как команд psql на серверной стороне. Использовать выполнение SQL через драйвер либо до запуска psql строго отвергать его метакоманды, как минимум любой обратный слеш, и проверять серверный контракт допустимого запроса. Проверки должны выполняться в самом шлюзе, а не только в MCP-клиенте. Добавить испытания stdin с `\!`, `\connect`, `\gexec` и `\copy ... PROGRAM`: ни shell-маркер, ни новое соединение создаваться не должны. Доверенные фиксированные запросы поиска и генератора следует сохранить отдельно от пользовательского SQL.

## Остальные проверенные границы

**RLS и разрешающий список.** Штатные 82 теста на временной базе прошли: строки всех включённых таблиц сверяются для четырёх селлеров двух организаций, включая одинаковые названия, остатки через товар, цепочки дочерних строк, отсутствующих родителей и конфликтующие `packaging_tasks`. В генераторе прямое равенство seller_id не пропускает NULL; `via` требует существующего подходящего родителя; `all_present` требует хотя бы одного родителя и принадлежности каждого заполненного родителя тому же селлеру. На проверенных путях RLS не найдено получения чужой строки обычным SQL.

Дополнительно в живом тестовом кластере выполнены `ANALYZE products; ANALYZE sellers;`, затем запросы статистики под ролью S1. `pg_stats` по этим таблицам вернул ноль строк; `pg_statistic.stavalues1` — `permission denied`; `pg_stats_ext` — ноль строк. Локальное определение `pg_stats` содержит проверку `row_security_active`. Приведение имени чужого селлера к integer при фильтре, исключающем S1, не вернуло ни строки, ни ошибки со значением. `EXPLAIN (VERBOSE, FORMAT TEXT)` показал выражение политики и условие запроса, без значений чужих строк. `regclass` и `pg_get_viewdef` дали сведения о схеме, но не обход доступа к строкам. Кавычный вызов `"set_config"('role','postgres',false)` отклонён PostgreSQL; выключение `row_security` заканчивается отказом чтения, а не расширением выборки. Проверки запрещённых представлений, SECURITY DEFINER-функции, записи и секретных колонок также прошли. SECURITY DEFINER-функция существует только в тестовой подготовке; на проде их отсутствие принято из поручения.

**Поиск и генератор.** Внешний маршрут `ensure-seller` принимает только UUID; генератор повторно проверяет UUID и SQL-идентификаторы. `find-seller` передаёт строку через `:'q'` psql, экранирует шаблон LIKE и не собирает из неё исполняемый SQL. Штатные опыты с апострофом, кавычками, подчёркиванием и запрещёнными командами прошли. Подтверждённой SQL-инъекции через эти два маршрута или генератор не найдено. N3 относится к stdin отдельной ветки `sql`.

**Привязка и выбор роли.** Команда владельца и подтверждение проверяются доверенной нормализацией Telegram; подтверждение связано с сохранённым предложением и исходным chat_id. Поиск и все ответы с кандидатами идут владельцу, минуя модель; проверки нулевого, одного и нескольких кандидатов, отказов и устаревшего подтверждения в режиме двух ботов прошли без исходящих сообщений бота приёма. Последовательная перепривязка сохраняет seller_id старого обращения, новые обращения получают новую привязку. Роль вычисляет `LlmRouter.ticket_db_role()` по записи обращения; у SQL-инструмента нет параметра выбора роли, общая `wms_agent_ro` не допускается. У непривязанных обращений инструмента нет. В форме поля добавлены в серверную схему ответа; сама запись создаётся из пользователя на сервере, а не из текста формы. Эти пути сверены чтением кода и тестами агента; отдельный новый прогон API-тестов формы не выполнялся.

Параллельные пути привязки просмотрены: обработка исходного чата и чата владельца использует разные задания; подтверждение состоит из нескольких операций хранилища. Дополнительный доказанный сценарий раскрытия чужих данных именно из-за этой конкуренции не получен; успешного стресс-теста гонок этот отчёт не заявляет.

**Python на сервере.** `gateway.py` и импортируемый `seller_access.py` прошли разбор синтаксиса с `feature_version=(3, 10)`. Используемые в шлюзе конструкции и стандартные модули совместимы с 3.10; подтверждённой несовместимости не найдено. Локального исполняемого Python 3.10 нет, поэтому это проверка кода и синтаксиса, не запуск на продовом 3.10.12. `python3 scripts/agent_db/seller_access.py --help` завершается с кодом 0 без вывода: файл сейчас является модулем генератора, справку командной строки не реализует.
