## Замечания

### F1 — блокер: А12 обходится при одновременном добавлении разных WB-карточек

**Место:** `backend/app/services/seller_fulfillment_catalog_service.py:715` (проверка) и `:728` (запись).

Проверка занятого артикула/ШК и импорт не являются одной защищённой операцией. Два запроса с разными nmID, но одним артикулом, одновременно видят отсутствие конфликта. Затем существующий upsert разрешает гонку уникальности повторным поиском товара и переписывает его nmID, ШК и название под вторую карточку. Оба запроса сообщают `added`, хотя на фулфилменте осталась только одна из выбранных карточек. Уникальные индексы предотвращают дубли строк, но не захват чужой идентичности.

**Почему:** R9, А12; правило сохранности связанных данных. Это именно технический дефект, который нельзя закрыть продуктовым одобрением. Сценарий «две вкладки добавляют одну карточку», имеющийся в тестах, не проверяет конфликт двух разных карточек.

**Воспроизведение — выполнено:** через HTTP с токеном селлера создать снимки `nmID=901/902`, `vendorCode=SAME-SKU`, разные ШК `900901/900902`. Отправить два POST `/seller-catalog/add-to-fulfillment`, каждый с одним nmID. Для детерминированного пересечения поставить тестовый барьер после двух реальных проверок `_card_has_vendor_code_conflict`, до импорта. Оба ответа — HTTP 200, оба содержат `added` и пустой `skipped`; в БД один товар `SAME-SKU` с одним nmID. Таким образом, одна карточка, объявленная добавленной, фактически исчезла из выбранных. PostgreSQL этим воспроизведением не проверен; отсутствие атомарной защиты видно и в коде.

Нужна атомарная проверка принадлежности при добавлении, включая путь повторного поиска после конфликта уникальности. Исправление не должно переписывать внутренности `upsert_products_from_wb_cards` вопреки границе WMS-535 или удерживать общий замок обмена, блокирующий FBS (случай B01).

### F2 — блокер: добавление Ozon может перезаписать уже выбранную карточку

**Место:** `backend/app/services/ozon_product_import_service.py:605`, `:630`, `:640`.

`process_one_ozon_card` сначала ищет готовую привязку через `_link_matches`: достаточно совпадения любого из `offer_id`, `sku`, `id`. Если совпал артикул, но идентификатор карточки другой, существующая привязка переезжает на новый `external_product_id`, получает новые ШК, при этом непустой `external_sku` остаётся от старой карточки. Защита `taken_product_ids` здесь не выполняется: она относится только к ветке поиска товара, когда готовая привязка не найдена.

**Почему:** R9, R10, А3, смысл защиты А12 и одобренный принцип одной физической вещи с согласованными идентификаторами площадок. Решение D3 вообще не применять аналог А12 к Ozon технически необоснованно: новый путь явного добавления может захватить существующую привязку. При этом обычную привязку Ozon к ещё не занятому WB-товару запрещать не нужно — это требование R13.

**Воспроизведение — выполнено:** у одного селлера в снимке Ozon две карточки: `id=801, sku=1801` и `id=802, sku=1802`, обе с `offer_id=SAME-OFFER`, разные ШК. Такое состояние снимка не запрещено схемой; старые записи при обновлении не удаляются. Через HTTP сначала добавить 801, затем 802. Оба ответа успешны. В БД остаётся одна привязка `(external_product_id=802, external_sku=1801, external_barcodes=[OZN1802])`; GET `/seller-catalog/page?on_fulfillment=no` снова показывает `ozon:801`. Повторное добавление старой карточки может переключать привязку обратно. Остатки физически не удаляются, но идентичность их получателя на площадке меняется.

Нужно различать обновление той же карточки и конфликт с уже заполненной идентичностью другой карточки, не допуская такого переключения из нового действия добавления.

### F3 — существенное: после ошибки одной карточки следующая роняет весь запрос

**Место:** `backend/app/services/seller_fulfillment_catalog_service.py:701` и `:732`; аналогичная конструкция Ozon — `:811` и `:836`.

Снимки всей порции заранее загружены как ORM-объекты — объекты строк базы. После `session.rollback()` SQLAlchemy помечает их атрибуты требующими повторного чтения. Локальное копирование полей защищает только текущую карточку. На следующей итерации чтение `card.vendor_code`/`card.raw_json` выполняется до `try`, пытается неявно обратиться к базе и вызывает `MissingGreenlet`. Ответ с `skipped` не возвращается, остальные карточки не обрабатываются. Аналогично устроена ветка Ozon; её общий контекст привязок тоже нуждается в восстановлении после отката.

**Почему:** R9: пропустить проблемную карточку, добавить остальные и сообщить результат. Связано с проверками восстановления после частичного сбоя из B05/B09.

**Воспроизведение — выполнено для WB:** два валидных снимка 701 и 702, один HTTP POST с обоими nmID. Тестовая подмена импорта выбрасывает `RuntimeError` только для 701. Обработчик делает rollback, затем вместо добавления 702 наружу выходит `MissingGreenlet` (HTTP-приложение в тестовом ASGITransport пробрасывает серверное исключение; обычный сервер вернул бы 500). Подмена нужна только для воспроизводимого сбоя первой карточки; авторизация и сам запрос проходят настоящий HTTP-маршрут.

Нужно подготовить простые значения для всей порции до возможного отката либо явно перечитывать следующую карточку и восстанавливать контекст. Проверить оба маркетплейса и внутренний rollback самого WB-upsert при гонке.

### F4 — существенное: селлер с одним Ozon не может синхронизировать каталог кнопкой

**Место:** `frontend/src/screens/v2/SellerProductsStockScreen.tsx:554`–`:560`.

Кнопка безусловно вызывает синхронизацию WB и при любом неуспехе выходит до проверки Ozon. Если WB не подключён, API возвращает `missing_content_token`; единственная подключённая площадка Ozon вообще не вызывается. Истёкший ключ WB также блокирует исправное подключение Ozon. Кроме того, сетевое исключение при самом Ozon-sync поглощается внутренним `catch`, хотя комментарий обещает игнорировать только сбой проверки подключения.

**Почему:** R12 прямо требует обновлять каждую подключённую площадку; А6 допускает каталог только Ozon. Ограничение одной площадки не должно отключать другую (смысл случая B08).

**Воспроизведение:** селлер с подключённым Ozon без WB → «Товары» → «Синхронизировать по API». WB отвечает 409; запрос `/integrations/ozon/self/sync-products` отсутствует. Поток подтверждён чтением обоих обработчиков; отдельно исполнялось извлечённое без правок тело функции с подставным ответом 409, без браузера. Требуется независимый выбор подключённых площадок и видимый результат ошибки Ozon.

### F5 — существенное: добавление одной WB-карточки загружает и обходит весь снимок Ozon

**Место:** `backend/app/services/seller_fulfillment_catalog_service.py:891` и `:899`–`:903`; `backend/app/services/ozon_product_import_service.py:605`.

После каждой порции WB `_link_unmatched_ozon_twins` читает `.scalars().all()` для всех непривязанных Ozon-карточек, включая полный `raw_json`, а затем перебирает их. Контекст дополнительно загружает все действующие Ozon-привязки и ключи всех товаров селлера. Для каждой карточки готовая привязка ищется линейным перебором списка `links`, поэтому при большом числе карточек и уже имеющихся привязок цена этого участка растёт как произведение их количеств. Ограничение POST на 500 идентификаторов не ограничивает эту работу. Она повторяется после каждой следующей порции WB.

**Почему:** R15, А8 и урок WMS-538: постраничный экран сам по себе не устраняет полный обход каталога в другом синхронном запросе. Ограничение памяти нарушено непосредственно; отказ 413 или конкретный таймаут здесь не заявляются как воспроизведённые.

**Воспроизведение — выполнено:** создать у тестового селлера 15 000 непривязанных снимков Ozon и одну WB-карточку без двойника. Через HTTP добавить только эту WB-карточку; счётчик вызовов, оборачивающий настоящий `process_one_ozon_card`, фиксирует **15 000** обработанных Ozon-карточек. Исходный код показывает одновременную материализацию всех строк. В этом же тесте GET страницы возвращает 100 из 15 000, поиск по ШК — одну строку, `/keys` — 15 000 ключей, все с HTTP 200: замечание именно к добавлению, не к пагинации.

Нужны ограниченное чтение и сопоставление кандидатов для добавленных товаров без полного снимка в памяти; повторный поиск существующих связей должен быть индексирован по идентификаторам, а не линейно перебирать все связи на каждую карточку.

### F6 — существенное: после добавления Ozon-карточка перестаёт находиться по своему ШК

**Место:** `backend/app/services/seller_fulfillment_catalog_service.py:212`–`:227`.

Пока Ozon-карточка не выбрана, поиск читает её JSON и находит ШК. После выбора карточка исключается из ветки снимков, а поиск товаров учитывает у Ozon-связи только `external_sku` и `external_offer_id`, пропуская `external_barcodes`. Импорт специально не копирует Ozon-ШК в `Product.wb_barcode`, поэтому другой проверяемой колонки с этим кодом нет.

**Почему:** R2/R7 — поиск по ШК работает по всему каталогу, в том числе после добавления, R12 — тот же процесс для Ozon.

**Воспроизведение — выполнено через HTTP:** снимок Ozon `id=805, offer_id=SEARCH-OFFER, sku=1805, barcodes=[SPECIAL-BAR-805]`. GET `/seller-catalog/page?search=SPECIAL-BAR-805` до добавления возвращает одну строку. POST добавления 805 успешен; тот же GET после добавления возвращает ноль. Для исправления использовать существующие ШК привязки, не дублировать их в поле WB.

### F7 — мелкое: окно выбора остаётся открытым после полного успеха

**Место:** `frontend/src/screens/v2/SellerCatalogSelectionDialog.tsx:417`–`:423`.

Обработчик снимает отметки добавленных, перечитывает страницу и вызывает `onAdded`, но не вызывает `onClose`. Родительский `onAdded` только обновляет счётчик WB, поэтому закрытия не происходит ни в одном из этих мест. Пользователь должен отдельно нажать «Закрыть».

**Почему:** R3 явно говорит «Окно закрывается». При ошибках и пропусках оно, напротив, должно оставаться открытым по R9.

**Воспроизведение:** после первого ключа выбрать одну валидную карточку, получить успешный ответ добавления без `skipped`. Диалог остаётся открытым с нулём выбранных. Подтверждено кодом; отдельно исполнялось извлечённое тело обработчика с полностью успешным ответом, без браузера. Закрывать после полного успеха, сохраняя окно и выбор при частичном результате.

## Проверено без замечаний в указанных границах

- **Обоснование таблицы Ozon (А6):** новая сущность необходима для полного каталога селлера без преждевременного создания складских товаров. `product_marketplace_links` требует товар WMS, а снимок WB имеет другую идентичность. Отдельный флаг выбора не добавлен, «на фулфилменте» выводится из существования товара/связи. Само введение таблицы оправдано; F5 относится к способу чтения.
- **Миграция:** создаёт только таблицу снимка и её индексы; не удаляет и не преобразует существующие товары, остатки, резервы, ячейки и настройки. Модель и миграция согласованы, Alembic показывает единственную вершину `20260927_0548`. Фактический upgrade/downgrade PostgreSQL здесь не выполнялся.
- **WB R4/R5:** отбор выбранных nmID применяется в сохранении ключа, ручной и фоновой синхронизации; снимок сохраняет весь список. Проверены новые размеры выбранной карточки, отсутствие товаров для невыбранной и новой карточки, разграничение продавцов и сравнение синхронизации полностью выбранного селлера с прежним импортом. Внутренности `upsert_products_from_wb_cards` не изменены — граница WMS-535 соблюдена.
- **Каталог:** объединение складских товаров и невыбранных снимков, подсчёт, фильтры и LIMIT/OFFSET выполняются в SQL; обогащаются товары текущей страницы. HTTP-проверка 15 000 снимков, 100 строк страницы, поиска и всех ключей выполнена без 413. Это не доказательство полного C15 с созданием всех товаров и параллельным входом другого пользователя.
- **Базовая изоляция R14:** у нового роутера единая зависимость роли, разрешения «Товары» и эффективного магазина; запросы снимков/товаров ограничены tenant_id и seller_id. Набор HTTP-тестов проверяет отказ роли ФФ, запрет списка сотруднику без права, недоступность чужих карточек, игнорирование подставленного магазина у обычного селлера. Чужой/несуществующий ID возвращается как `not_found` без артикула. Приёмка реального переключения делегированных магазинов в браузере не выполнялась.
- **Обычное добавление:** HTTP-тесты покрывают создание размеров WB, повтор, последовательный конфликт артикула и ШК без изменения чужого товара, привязку ручного товара без nmID, ограничение 500 ID, Ozon и двусторонний сценарий WB/Ozon-двойника. Сценарии F1–F3 этими зелёными тестами не закрываются.
- **R6/R11:** новые снимки сами по себе не создают складской Product; в diff нет изменений FBS-резервирования, сканеров, приёмки, инвентаризации, отгрузок и передачи остатков. Существующий целевой тест подтверждает последующее сопоставление ранее несопоставленного WB-заказа и однократный резерв. Полный HTTP/браузерный путь C6/C11 для обеих площадок не пройден, поэтому независимая операторская приёмка не заявляется.
- **R16:** изменены только два существующих экрана селлера и новый диалог; экраны ФФ и общий диалог остатков не менялись. Кнопки снятия/«Не отображать», новая таблица выбора, отдельный статус выбора и объяснительные блоки не добавлены. Используются существующие компоненты темы, фото и значки площадок. Визуальные ширины и сравнение с эталонами лично не проверены: браузер недоступен; результаты ведущего не выдаются за собственные.
- **Частичные порции на фронте:** ID разбиваются по 500, подтверждённые снимаются с выбора, неподтверждённые остаются для повтора. Старые действия каталога применяются к выбранным Product-строкам, а не к снимкам. Реальное выполнение всех этих действий браузером в этом ревью не заявляется.

Масштабный сценарий F5 и исчезновение поиска F6 тоже подтверждены отдельно: всего **пять HTTP-сценариев воспроизведения**. Исполнение извлечённых тел обработчиков F4/F7 дало соответственно только вызов WB с `missing_content_token` и `onAdded=1, onClose=0`; это проверка логики, не проверка экрана.

PostgreSQL, живые маркетплейсы, браузер, физические операции и деплой не проверялись. Проверка SQLite не доказывает конкурентное выполнение и миграции PostgreSQL. Требования всё ещё содержат исходные «реализации нет / не проверено»; их приёмочную часть должен обновить аналитик по фактическим результатам. Пять ожидаемых расхождений C7 при интеграции с WMS-547 из вводной дефектом WMS-548 не считаются.
