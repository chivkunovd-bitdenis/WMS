## F1–F7: результат проверки исправлений

### F1 — не закрыт, блокер: замок может остаться на соединении после завершения запроса

**Место:** `backend/app/services/seller_fulfillment_catalog_service.py:134–160`, вызов на `:808–829`; внутренние commit/rollback — `backend/app/services/wildberries_product_import_service.py:269–271`, `:309`, `:392–399`.

Внутрипроцессный `asyncio.Lock` действительно охватывает проверку конфликта и импорт целиком. Новый тест двух конфликтующих nmID прошёл. Однако этот замок разделяют только задачи одного процесса Python. Указание владельца о боевом `uvicorn --workers 2` означает два независимых таких замка; комментарий в коде на строках 109–116 об однопроцессном сервере неверен. Боевой процесс в этом ревью не опрашивался: конфигурация двух workers взята из вводной владельца.

Сессионный `pg_advisory_lock` берётся **на рабочей AsyncSession**, а импорт внутри блока коммитит отдельные размеры. После commit SQLAlchemy возвращает физическое соединение в пул; следующий запрос этой же AsyncSession может получить другое соединение. Сессионный advisory-замок остаётся у первого соединения. `pg_advisory_unlock` на втором возвращает `false`, что код вообще не проверяет. Исключение при снятии тоже только журналируется, без вывода опасного соединения из пула. Это повторяет механизм WMS-435, подробно зафиксированный в основном бэклоге на строках 13373–13375, а не просто похожее имя блокировки.

Последствие для двух workers: запрос на другом процессе может ждать уже законченный импорт, потому что оставшийся в пуле замок никто не снимет. В новом коде используется блокирующий `pg_advisory_lock` без собственного предела ожидания. Отсутствие ошибки у первого запроса не означает освобождение блокировки.

**Выполненная диагностика.** Без изменения исходника извлечены три функции `_wb_claim_lock`, `_wb_claim_advisory_key`, `_wb_card_identity_claim`. На настоящих AsyncSession и пуле SQLAlchemy из двух SQLite-соединений выполнен commit внутри неизменённой обёртки; только PostgreSQL-функции были заменены моделью сессионного замка и подставлено имя диалекта для входа в нужную ветку. Получено:

```text
acquire: connection 1
before_commit: connection 1
after_commit: connection 2
unlock: connection 2, returned false
remaining_modeled_locks: 1
```

Это непосредственно подтверждает смену соединения рабочей сессии и игнорирование неуспешного unlock. **Это не прогон PostgreSQL и не наблюдение pg_locks.** Временный PostgreSQL не запустился: `initdb` получил `shmget ... Operation not permitted`; проба подключения к локальному PostgreSQL также остановлена sandbox с `Operation not permitted`. Обход ограничений не выполнялся. Исходник диагностического сценария находится во временном `/private/tmp/wms548-review2/pool_probe.py`; для повторения на PostgreSQL достаточно пула из двух заранее открытых соединений, входа в обёртку, commit рабочей сессии и проверки lock с независимого соединения после выхода.

**Сравнение с транзакционным замком.** `pg_advisory_xact_lock` автоматически освобождается на commit/rollback. Простая замена имени функции на рабочей сессии устранит утечку, но снимет защиту уже после первого сохранённого размера, пока остальные размеры ещё обрабатываются. Поэтому такая замена сама по себе F1 не закрывает. При текущем импорте с внутренними commit нужна отдельная закреплённая сессия/соединение, живущая на протяжении всей операции проверки и записи: либо сессионный замок с гарантированным снятием на том же соединении и безопасной обработкой сбоя снятия, как сделано в WMS-435, либо отдельная непрерываемая транзакция, владеющая транзакционным замком. Семантика обоих видов подтверждается [документацией PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html#ADVISORY-LOCKS).

**FBS и обмен, B01.** Новый ключ вычисляется из `wms548:wb-claim:<tenant>:<seller>` через SHA-256; общий ключ FBS/обмена — из `wms:fbs:marketplace:seller:` через BLAKE2b (`marketplace_seller_lock_service.py:18–36`). Общая блокировка обмена не переиспользуется, и полного сетевого обхода площадки внутри новой блокировки нет. Прямой повтор B01 через один и тот же ключ не обнаружен. Но зависшие ожидания удерживают соединения общего пула API и могут косвенно мешать соседним запросам; реальная нагрузочная проверка FBS этим ревью не выполнена. SQLite-тесты используют только локальный asyncio-замок, поэтому не проверяют ни межпроцессную защиту, ни утечку PostgreSQL. `pytest -n auto` не превращает один сценарий гонки в проверку двух процессов API.

**Для закрытия:** проверить на PostgreSQL независимые соединения/процессы, конфликт разных nmID с общим артикулом и с общим ШК, многоразмерную карточку, commit и rollback внутри импорта; после каждого исхода независимый запрос должен брать тот же замок, а в pg_locks не должно оставаться владельца законченной операции. Сохранить отдельный ключ от FBS/обмена. Тест из одного event loop недостаточен.

### F3 — закрыт: откат карточки не инвалидирует вход следующей карточки порции

### F9 — существенное: отказ проверки подключения WB теперь молча отменяет синхронизацию

**Место:** `frontend/src/screens/v2/SellerProductsStockScreen.tsx:304–316`; симметричная конструкция Ozon — `:333–345`. Основание — R12, сохранение прежней обратной связи и правило восстановления после сбоя (B05).

Новая предварительная проверка WB начинает с `wbConnected = false`. Ответ 403/500/503, сбой сети или неразбираемый JSON оставляют это значение неизменным; `wbFailure` остаётся null. Тем самым «не смогли узнать, подключён ли WB» приравнено к подтверждённому отсутствию ключа. POST синхронизации не вызывается, обработчик перечитывает каталог без сообщения, и пользователь не узнаёт, что действие не выполнено. В etalon прямой POST показывал отказ; новая предварительная проверка убрала эту обратную связь. Молчаливый пропуск допустим для успешного ответа `has_content_token: false`, но из ошибки GET отсутствие подключения не следует.

**Воспроизведено исполнением функций из текущего исходника без изменения их тел:** GET `/integrations/wildberries/self/tokens` → 503 (повторено с 403), GET Ozon → 200 `{connected:false}`. Вызваны только два GET, ни одного POST; результат в обоих случаях `{wbFailure:null, ozonFailure:null}`. Проверка выполнена с подставными fetch-ответами, не в браузере и без сетевых обращений площадок.
