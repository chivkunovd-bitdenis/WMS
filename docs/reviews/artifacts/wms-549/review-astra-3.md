## F3 — закрыт: точная SQL-граница и полный порядок

Места: `backend/app/services/billing_invoice_v2_service.py:816–863`,
`:897–922`, `:934–938`, `:965–968`, `:989–996`.

Итоговый порядок — `(issued_at DESC, origin DESC, id DESC)`. Для фиксированной
ветки `_seek_where` правильно сводит условие «строго после курсора» к трём случаям:

| Отношение origin ветки к origin курсора | SQL-граница |
|---|---|
| origin ветки меньше | `issued_at <= cursor_time` |
| origin ветки больше | `issued_at < cursor_time` |
| origin совпадает | `issued_at < cursor_time OR (issued_at = cursor_time AND id < cursor_id)` |

Это условие применяется до LIMIT. Обе SQL-ветки теперь сортируют и дату, и ID
по убыванию. Поэтому каждая даёт правильные первые `limit + 1` оставшихся строк;
из объединения этих двух префиксов можно получить первые `limit` строк общей
истории и достоверно установить наличие следующей страницы. Повторная фильтрация
в Python больше не вычищает окно из уже показанных строк. При одинаковом ID
в разных таблицах различие origin сохраняет полный порядок; внутри одной таблицы
повтор ID запрещён первичным ключом. Поля даты обязательны, случая NULL здесь нет.

Независимо выполнено:

  `test_wms549_invoice_pagination.py`, прошли. Сценарии совпадающих дат проверяют

  таблицами. У legacy разные месяцы, чтобы не нарушить уникальность месячного счёта.
  Проверены все даты одинаковые и даты группами по три, лимиты **1, 2, 3, 20, 50,
  200**. Во всех 12 обходах получено **102 из 102**, без повторов пары `(origin,id)`

  и по числовому значению даёт одинаковый порядок для всех 64 значений.

### PostgreSQL: порядок UUID подтверждён, серверный прогон не выполнен

В моделях обеих таблиц ID имеет тип `Uuid(as_uuid=True)`; компиляция запроса
для PostgreSQL использует нативный UUID, без преобразования в текст и без collation.
В официальном [исходном коде PostgreSQL 17, uuid.c](https://raw.githubusercontent.com/postgres/postgres/REL_17_STABLE/src/backend/utils/adt/uuid.c)
`uuid_internal_cmp` сравнивает 16 байтов через `memcmp`; операторы `<`, `>` и
компаратор B-tree используют именно эту функцию. Каноническая строка Python UUID
записывает те же байты шестнадцатеричными цифрами фиксированной длины; дефисы
стоят в одинаковых позициях. Следовательно, порядок нативного UUID PostgreSQL
и `str(uuid)` Python совпадает для любых значений UUID. Origin сравнивается
в Python с литералом своей SQL-ветки, поэтому зависимость от SQL-сортировки
строк здесь также не возникает. Это вывод по реализации типов, а не результат
запуска приложения на PostgreSQL.

Попытка создать отдельный временный PostgreSQL локально остановилась в initdb:
`could not create shared memory segment: Operation not permitted`, вызов `shmget`.
К действующим базам и production не подключался. Полный SQL-прогон и
`EXPLAIN ANALYZE` PostgreSQL не выполнены; SQLite за них не выдаётся.

### Производительность

На страницу сервис выполняет две выборки, каждая ограничена `limit + 1`;
в Python поступает максимум `2 * (limit + 1)` строк, максимум 402 при лимите 200.
Нет вычитывания всех счетов в Python, OFFSET или цикла по всей истории внутри
одного запроса. Объём работы БД этим пределом не ограничен.

Индекс V2 `(tenant_id, issued_at, id)` существует; у legacy индекса по дате нет.
Независимый SQLite `EXPLAIN QUERY PLAN` для отбора ID с tenant/seller, точной
границей и сортировкой показал V2-индекс с ограничением даты, а у legacy — индекс
tenant/seller и `USE TEMP B-TREE FOR ORDER BY`. Это проверка сокращённой выборки
ID, не замер полной выдачи со снимками счетов и JOIN.

Для PostgreSQL остаётся проверить план именно с OR-границей, фильтром seller,
большой группой одинаковых дат и глубокой страницей. Нельзя по одному наличию
индекса обещать постоянное время: оптимизатор может сканировать и отфильтровывать
существенный префикс. Измеренной новой деградации не установлено. Ранее отмеченный
риск сортировки legacy остаётся; миграций индексов в исправлении нет. Закрытие
F3 означает исправление полноты и порядка, а не нагрузочную приёмку PostgreSQL.

## F6 — не закрыт полностью: одинаковая область представлена двумя способами

Место: `frontend/src/apps/seller/SellerApp.tsx:101–109`, особенно строка 107.

Основной случай исправлен: разные iat/подпись при одинаковых
`tenant_id/sub/seller_id` оставляют ключ прежним. Четыре существующих DOM-теста
независимо прошли, включая сохранение второй страницы и смену магазина со старым
профилем. При последующем приходе нового `/auth/me` ключ повторно не меняется.

Но сервер допускает токен без `seller_id`: для менеджера это основной магазин
из `user.seller_id` (`backend/app/api/deps.py:50–67`). Ключ фронта в таком случае
содержит `no-seller`. При перевыпуске с явным ID того же основного магазина
получается другой ключ, хотя пользователь, tenant и фактическая область прежние.

**Независимое доказательство на сервере.** На тестовой базе создан менеджер
с основным S1 и делегированным S2. Настоящий подписанный токен без `seller_id`
принят `/auth/me` с HTTP 200 и `active_seller_id=S1`. Запрос
`POST /auth/switch-seller` с этим токеном и целью S1 принят с HTTP 200 и вернул
токен с `seller_id=S1`, теми же sub/tenant. Затем S2 и возврат к S1 тоже успешно
выдали соответствующие claims. Значения токенов в отчёт не включаются.

**Независимое доказательство на фронте.** Настоящий `FfBillingInvoicesPanel`
в jsdom, тот же `sellerCatalogScopeKey`, HTTP-ответы-заглушки с одинаковой историей:

```text
A: {tenant_id: "t", sub: "manager"}, профиль active_seller_id=home
загрузить HOME-FIRST, нажать «Загрузить ещё» → HOME-SECOND виден
B: {tenant_id: "t", sub: "manager", seller_id: "home"}, профиль тот же
ключ: t:manager:no-seller → t:manager:home
после передачи B: HOME-FIRST виден, HOME-SECOND отсутствует
```

Проверка сохранности второй страницы падает. Так же снимаются другие состояния
раздела вследствие смены ключа. Это остаток F6, а не смешивание магазинов из F1.

**Практическая граница.** Все найденные текущие пути обычного входа передают
`seller_id=user.seller_id`. Обычный `handleSwitchShop` не отправляет запрос при
повторном выборе текущего магазина (`SellerApp.tsx:275`). Автоматического refresh
в этом ревью не обнаружено. Поэтому сценарий относится к поддерживаемому токену
без claim и его замене/принудительному перевыпуску; сбой штатного клика по уже
выбранному магазину или регулярную потерю данных в production не заявляю.
По той же причине это узкий остаточный дефект, не новый production-блокер.

**Что требуется.** Для ключа различать фактические области и нормализовать
отсутствующий seller claim как основной магазин пользователя, а не как отдельный
магазин `no-seller`. Нельзя подставлять устаревший *активный* магазин вместо
нового seller claim — это вернуло бы F1. Совместно проверить: отсутствующий claim
→ явный ID того же основного магазина; отсутствующий claim → делегированный
магазин до `/auth/me`; возврат домой; обычный перевыпуск; новый профиль без
повторного пересоздания. Изменения остальных экранов ради этого не требуются.

### F1 и чтение claims без подписи

Для реального переключения исходный F1 **не воспроизведён**. Если исходный токен
не содержит seller_id, сервер считает его основным магазином. Успешный
`/auth/switch-seller` всегда записывает ID цели в новый токен
(`backend/app/api/auth.py:509–516`), и ключ сразу меняется. Два токена без seller_id
при неизменном пользователе не могут обозначать два разных выбранных магазина
по текущему серверному контракту. Это проверено чтением цепочки и дополнительными
серверным/DOM-прогонами; делать из отсутствующего claim самостоятельную утечку
S1 → S2 неправильно.

Чтение payload JWT без подписи здесь используется только для React key — выбора
экземпляра компонента. Проверки доступа не перенесены на клиент: каждый запрос
по-прежнему проходит проверку подписи, пользователя, tenant, прав и делегирования
на сервере. Нечитаемый JWT использует полный токен и профиль как запасной ключ.
Это может избыточно сбросить состояние, но не выдаёт разрешения читать чужие данные.

## Новое замечание F7 — разные origin с одним UUID склеиваются на фронте

Место: `frontend/src/screens/ff/FfBillingInvoicesPanel.tsx:262–266`, `:453`.
Связано с R6 и явно запрошенной проверкой любых совпадений origin/id.

У двух таблиц отдельные первичные ключи; общего ограничения уникальности UUID
между legacy и V2 нет. Сервер правильно считает идентичностью пару `(origin,id)`:
origin входит в сортировку/курсор и определяет ручку открытия. В дополнительном
серверном прогоне обе записи с одним UUID сохранены и возвращены.

Фронт объединяет страницы только по `row.id`. Если на первой странице есть V2
с ID X, а на второй legacy с ID X, строка legacy отбрасывается. После этого
`next_cursor=null` скрывает дочитку. В таблице React key тоже построен только
по ID, поэтому для двух таких записей на одной странице идентичность неоднозначна.

**Независимое воспроизведение.** Настоящий компонент в jsdom получает:

```text
первая страница:  [{origin: "v2",     id: X, number: "V2-FIRST"}], cursor=PAGE2
вторая страница:  [{origin: "legacy", id: X, number: "LEGACY-SECOND"}], cursor=null
после «Загрузить ещё»: V2-FIRST виден; LEGACY-SECOND отсутствует
```

Тест, ожидающий обе строки, падает. Ни backend `_seek_where`, ни обновление ключа
сессии эту потерю не вызывают: это отдельный дефект существовавшего объединения
строк, обнаруженный расширением проверки совпадений. F3 именно в SQL закрывается,
но сквозная гарантия полноты при *любых* совпадениях ID пока не выполнена.
