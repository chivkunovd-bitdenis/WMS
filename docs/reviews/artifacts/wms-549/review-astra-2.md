### F1: исходное смешивание устранено, проверка соседних разделов имеет ограничения

Места: `frontend/src/apps/seller/SellerApp.tsx:65–69`, `:349`, `:554`;
`frontend/src/apps/seller/SellerApp.dom.test.tsx:63–120`.

При переходе `token=S1, me=S1 → token=S2, me=S1` ключ теперь меняется сразу.
В настоящем React-компоненте `FfBillingInvoicesPanel` после двух страниц S1 и
передачи S2 со старым профилем строки S1 исчезают, запрос S2 отправляется без
курсора S1. Этот существующий тест независимо запущен и прошёл. Снятие всего
`FfBillingScreen` также снимает окно счёта и остальные его локальные состояния;
это вывод по дереву компонентов, отдельный клик по открытому счёту не выполнялся.

Ключ используется не только в расчётах: документы, создание/редактирование приёмки,
товары, «Честный знак», отчёты и настройки тоже получают его. Уведомления этого ключа
не имеют. Поэтому утверждение «соседние разделы вообще не затронуты» неверно:
момент их пересоздания изменён. После прихода нового профиля ключ меняется ещё раз:
`S1-token:S1 → S2-token:S1 → S2-token:S2`. При разнесённых ответах это два
пересоздания и возможные повторные первоначальные запросы. Сквозную браузерную
проверку всех соседних разделов этим ревью не выполнял; подтверждённую потерю
состояния при неизменном магазине описывает F6.

Результат разработчика «55 + 2 счёта, задержанный /auth/me, браузер» — внешнее
свидетельство из задания. Здесь независимо выполнена проверка DOM в jsdom
(программной модели браузерного документа), а не повтор этого браузерного прохода.

### F2: подпись и границы конверта проверены

Места: `backend/app/api/seller_billing.py:64–104`, `:208–230`;
`backend/app/core/settings.py:28–31`, `:380–385`.

Подпись — HMAC-SHA256, то есть проверка целостности с серверным секретом. Ключ для
этой цели выводится из `settings.jwt_secret_key` отдельным HMAC с контекстом
`wms:seller-billing-invoice-cursor:v1`. Это отделяет подпись курсора от других
применений того же исходного секрета. Сравнение выполнено через
`hmac.compare_digest`, предназначенный для сравнения за постоянное время.
Значение рабочего секрета не читалось; проверены источник настройки, минимальная
длина и запрет штатного значения по умолчанию в режиме production.

Формат — URL-safe base64 от JSON с `payload` и `signature`. Подписывается
канонический JSON всего payload, включая `tenant_id`, `seller_id`, внутренний
курсор. После проверки подписи сверяются обе границы доступа и тип внутреннего
курсора. Затем его исходный формат проверяет общий сервис. Конверт проверяется
до вызова сервиса истории.

Независимые запросы к настоящему приложению с тестовыми подписанными токенами:

| Вход | Результат |
|---|---|
| Курсор другого селлера | 422; существующий новый HTTP-тест прошёл |
| Курсор другого арендатора | 422, `{"detail":"invalid_cursor"}` |
| Изменённая подпись | 422, тот же ответ |
| Изменённый seller в payload без переподписи | 422, тот же ответ |
| Внутренний курсор ФФ вместо конверта селлера | 422, тот же ответ |
| JSON-массив, null, числовая или не-ASCII подпись | 422, тот же ответ |
| Свой неизменённый курсор | 200, дочитка своей истории |

Отказ не содержит данных счетов или имён селлеров. Старый курсор ФФ намеренно
не принимается новой ручкой селлера. Сама ручка ФФ продолжает использовать прежний
неподписанный формат: её обработчик, `_list_cursor` и `_parse_list_cursor` этим
diff не менялись, переходы по страницам и серверные регрессионные тесты проходят
за исключением оставшегося F3.

**Срок:** полей выпуска/истечения нет, конверт сам по времени не истекает; смена
секрета инвалидирует подпись. Он не даёт доступ вместо авторизации: каждый запрос
снова проходит действующую проверку роли, прав и активного магазина. R3 не требует
срока жизни курсора; отсутствие TTL само по себе не объявляю дефектом. Нельзя
утверждать, что курсор истекает вместе с access token: такого условия в коде нет.

### F3: граница по одной дате всё ещё отсекает историю

Существенное замечание к R6, остаётся открытым.
Места: `backend/app/services/billing_invoice_v2_service.py:849–860`,
`:874`, `:904`, `:922–927`.

До SQL LIMIT добавлено только `issued_at <= cursor_issued_at`. Уже показанные
счета с той же датой снова занимают окно `limit + 1`. После этого Python удаляет
их точным сравнением `(issued_at, origin, id)`. В окне остаётся слишком мало строк,
`tail` становится пустым и API возвращает `next_cursor=null`, хотя более старые
или ещё не показанные счета с той же датой существуют.

Есть и вторая часть той же проблемы: SQL сортирует только по `issued_at`, а
Python — по дате, типу и ID. При совпадениях SQL LIMIT может отобрать не тот
набор ID, который должен стоять первым по итоговому порядку. Добавить одно
сравнение ID без согласования сортировки недостаточно.

Воспроизведение выполнено на отдельной SQLite in-memory базе через настоящий
`create_app()`, HTTPX/ASGI и настоящую авторизацию. Основа данных —
`_seed_many_invoices()` из нового теста: 61 V2 и 1 legacy, лимит 20.
После подготовки выполнены последовательные запросы до исчезновения курсора.

| Данные | `/seller-billing/invoices` | `/billing/invoices-v2` |
|---|---|---|
| Исходные различные даты | 20 + 20 + 20 + 2 = **62** | 20 + 20 + 20 + 2 = **62** |
| Всем V2 установлен `2026-09-01T00:00:00Z`, legacy старше | 20 + 2 = **22**, потеряно 40 | 20 + 2 = **22**, потеряно 40 |
| Legacy тоже имеет ту же дату, что 61 V2 | 20 + 2 = **22**, потеряно 40 | 20 + 2 = **22**, потеряно 40 |
| У V2 даты `base + timedelta(minutes=index // 3)`, legacy старше | 20 + 20 + 19 = **59**, потеряно 3 | 20 + 20 + 19 = **59**, потеряно 3 |

Во всех этих прогонах повторов ID не было, завершение истории было преждевременным.
Отсутствие повторов не компенсирует пропуски. PostgreSQL независимо не запускался;
причина потери видна в порядке SQL LIMIT и последующей фильтрации и не зависит
от особенности SQLite с часовыми поясами. Конкретный набор потерянных ID при
неполной SQL-сортировке может зависеть от плана выполнения.

Новые тесты разработчика используют `timedelta(minutes=index)`
(`backend/tests/test_wms549_invoice_pagination.py:67`): одинаковых дат там нет.
Один legacy всегда старше всех V2. Поэтому зелёный результат этих двух тестов
согласуется с обнаруженной потерей на стыках.

**Что требуется для закрытия.** В каждой SQL-ветке до LIMIT применить полную
границу итогового порядка, учитывая постоянный `origin` этой ветки; сортировку
согласовать с `(issued_at DESC, origin DESC, id DESC)`. Внутри одной таблицы это
дата и ID. Проверить обе ручки на группах одинаковых дат больше одной страницы,
маленьких группах на стыке страниц и смешанном наборе нескольких legacy/V2 с
одинаковыми датами. Сравнить полный набор и порядок, а не только число страниц.
Формат внешнего курсора ФФ менять для этого не требуется.

**Совместимость ФФ.** Параметры, фильтры tenant/seller/status/number, сериализация
сумм, структура ответа и формат курсора остались прежними по diff. Серверные
регрессионные тесты выставления, повторов, отмены и истории прошли. Это подтверждает
сохранение проверенного контракта; корректную полную пагинацию ФФ заявлять нельзя,
поскольку F3 воспроизведён непосредственно на её ручке.

**Производительность и индекс.** Для V2 есть индекс
`ix_billing_invoices_v2_tenant_issued (tenant_id, issued_at, id)` в модели
`backend/app/models/billing.py:546` и миграции `20260827_0114_billing_invoice_v2.py:55`.
Для legacy модель и миграции не содержат индекса по `issued_at`; есть отдельные
индексы tenant/seller и ограничения уникальности. Независимый SQLite
`EXPLAIN QUERY PLAN` для запроса по tenant с границей даты и LIMIT 21 показал:

```text
billing_invoices:
  SEARCH ... USING INDEX ix_billing_invoices_tenant_id (tenant_id=?)
  USE TEMP B-TREE FOR ORDER BY
billing_invoices_v2:
  SEARCH ... USING COVERING INDEX ix_billing_invoices_v2_tenant_issued
  (tenant_id=? AND issued_at<?)
```

Сравнение с полем даты допускает использование существующего V2-индекса, но
утверждение об индексном чтении обеих таблиц неверно. Для legacy остаются отбор
и сортировка набора арендатора; это существующий риск масштаба, а не измеренная
новая задержка в production. При исправлении полной границы следует проверить
план с tenant/seller на PostgreSQL и необходимость соответствующего legacy-индекса.
Миграции, нагрузочный прогон и измерения рабочего стенда здесь не выполнялись.

## Новое замечание

### F6 — при новом токене того же магазина пересоздаются разделы и теряется состояние

Место: `frontend/src/apps/seller/SellerApp.tsx:65–69`, `:349` и все восемь
использований `key={catalogScopeKey}` в маршрутах. Это побочный эффект исправления F1.

Полная строка токена включена в ключ компонента. Поэтому перевыпуск токена при
неизменных пользователе, tenant и магазине выглядит для React как новый раздел.
Расчёты теряют выбранную вкладку/период, панель счетов — дочитанные страницы и
открытый счёт. У соседних разделов аналогично сбрасывается локальное состояние;
например, у товаров есть фильтры, выделенные товары и состояние редактирования
(`SellerProductsStockScreen.tsx:164–180`). Потеря ввода именно в соседних экранах
отдельно не воспроизводилась; их пересоздание следует из общего изменённого ключа.

**Независимое воспроизведение.** Временный диагностический вариант существующего
DOM-теста использует настоящий `FfBillingInvoicesPanel` и тот же ключ из SellerApp:
загрузить первую и вторую страницу S1, затем передать новый токен того же S1,
оставив `me.active_seller_id='s1'`. Заглушка HTTP возвращает одну и ту же историю
для обоих токенов. На текущем коде:

```text
firstPageVisible=true
secondPageVisible=false
новый запрос: /api/seller-billing/invoices?status=all
```

Проверка сохранности второй страницы падает. Контрольный запуск того же
диагностического теста с прежним выражением ключа, изменённым только во временной
обёртке, проходит: обе страницы видны, курсор сохраняется. Продуктовый код для
этого опыта не менялся. Это доказывает добавленный сброс состояния, а не просто
существовавший повтор fetch при изменении prop token.

**Граница серьёзности.** Автоматический refresh access token в текущем `useAuth`
не найден. `reloadMe()` перечитывает профиль с тем же токеном, а `applyToken()`
в SellerApp вызывается при смене магазина. Поэтому не утверждаю, что сегодня
по таймеру регулярно теряются пользовательские данные на стенде. Замечание
подтверждает несовместимость с явно запрошенным сценарием «новый токен, прежний
магазин» на уровне компонентов; текущий операционный триггер автоматического
refresh не установлен. Самостоятельного production-блокера из этого не делаю:
безусловное основание возврата — F3.

При корректировке нужно сохранить немедленное снятие данных прежнего магазина,
но отличать изменение области сессии от обновления удостоверяющего её токена.
Просто убрать токен из ключа нельзя — это вернёт F1. Проверки смены магазина
с задержанным профилем и обновления токена того же магазина должны проходить вместе.

Других новых замечаний F7… по рассматриваемому diff не установлено.
