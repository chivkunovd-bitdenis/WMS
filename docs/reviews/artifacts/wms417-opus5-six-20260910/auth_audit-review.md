# Ревью пакета WMS-417 (Opus 5, независимая сессия)

## Краткий вердикт

Пакет содержит **два несвязанных куска работы**: правку входа и портов (WMS-270/WMS-377) и аудит прав сотрудников (WMS-325). Заявленный WMS-056 в пакете **отсутствует как код** — есть только константа события, писателя нет; подробности ниже.

По сути: оракул на входе действительно убран и ограничитель частоты действительно появился — это видно в коде. Аудит смены прав действительно пишется в существующую таблицу `document_event`, новых сущностей не заведено, правило владельца соблюдено. Но в обеих правках есть дефекты, из-за которых заявленный эффект в бою может не наступить: закрытие портов сделано ровно для двух сервисов из пяти в том же файле, а новые аудит-события пишутся по пути, который, судя по коду того же модуля, может молча отбрасываться базой. Плюс нашлась возможность повышения прав, которую существующая защита `self_update_forbidden` не закрывает.

Всё ниже — **статическое чтение замороженных исходников по указанным SHA256**. Я не запускал тесты, не открывал браузер, не ходил в сеть и не смотрел боевой хост. Ни одно утверждение о runtime не является доказанным наблюдением.

## Приоритетные дефекты

### 1. WMS-377 закрыт наполовину: база, Redis и сам API остались смотреть наружу

`docker-compose.yml` — в одном и том же файле автор правки добавил bind-адрес (адрес интерфейса, на котором Docker публикует порт) двум сервисам и не добавил трём:

* `docker-compose.yml:113-114` — `web`: `"${WMS_WEB_PORT_BIND:-127.0.0.1}:${WMS_WEB_PORT:-15173}:80"` — закрыт;
* `docker-compose.yml:126-127` — `web_seller`: закрыт;
* `docker-compose.yml:51-52` — `api`: `"${WMS_API_PORT:-18080}:8000"` — **публикуется на 0.0.0.0**;
* `docker-compose.yml:11-12` — `db`: `"${WMS_DB_PORT:-5433}:5432"` — **0.0.0.0**, при этом логин/пароль в строках 8-10 захардкожены как `postgres/postgres`;
* `docker-compose.yml:21-22` — `redis`: `"${WMS_REDIS_PORT:-16379}:6379"` — **0.0.0.0**, без пароля.

Почему я считаю, что это про боевой хост, а не про абстрактную возможность. Замороженное свидетельство WMS-377 фиксирует HTTP 200 ровно на **8088 и 15174**, и не фиксирует 15173. Это в точности отпечаток связки `docker-compose.yml` + `docker-compose.wms-host-8088.yml`: оверлей заменяет порты `web` на 8088 (`docker-compose.wms-host-8088.yml:9-10`), а 15174 — дефолт `web_seller` из базового файла. То есть хост почти наверняка поднят этими двумя файлами — а значит из этого же запуска опубликованы и 5433, и 16379, и 18080.

Смысл исходной задачи — «пароли не должны ходить голым HTTP». Порт 18080 это ровно `/auth/login` по голому HTTP, то есть исходная проблема не устранена, а только переехала на другой номер. А 5433 с дефолтными кредами — это уже не перехват трафика, а прямой доступ к данным склада.

**Минимальная правка:** дописать тот же префикс `${…_BIND:-127.0.0.1}:` в строках 12, 22 и 52. Для `db` и `redis` правильнее вообще снять секцию `ports` — они нужны только внутри сети compose, наружу их публиковать незачем.

**Что подтвердить перед выводом «сделано»:** внешняя read-only проверка 18080/5433/16379 с чужого адреса, либо `docker compose ps` на хосте. В пакете нет ни `network-readonly.json`, ни фаервольных правил, поэтому статически я реальную достижимость этих портов доказать не могу — только асимметрию в самом файле правки.

**Риск при выкатке (проверить до, а не после):** привязка к `127.0.0.1` работает только если фронтирующий Caddy живёт в сетевом пространстве хоста. Если он контейнер в своей bridge-сети, он до `127.0.0.1` хоста не достучится, и сайт ляжет целиком. В пакете нет ни его конфига, ни `frontend/deploy/Caddyfile.ff.local` — нужен upstream-адрес из конфига соседнего Caddy.

### 2. Автор события в аудите берётся из второго, независимого разбора заголовка — и его можно подменить

`document_event_service.py:130-143`. Middleware сам, заново, парсит `Authorization` и декодирует JWT, чтобы узнать, кто действует. Проблема в строке 131:

```python
headers = {key.lower(): value for key, value in scope.get("headers", [])}
```

Это словарь: при **двух** заголовках `Authorization` побеждает **последний**. А Starlette в `Headers.get`, на котором стоит `HTTPBearer` и вся авторизация, возвращает **первый**. Сценарий воспроизведения: клиент шлёт запрос с двумя заголовками `Authorization: Bearer <A>` и `Authorization: Bearer <B>`, где оба токена валидны. Запрос авторизуется как A, а все события, которые попадут в `document_event` через автоматический сборщик (`_document_rows`, строка 374 — `actor = _actor_context.get()`), будут подписаны пользователем B. То есть человек с двумя аккаунтами может выполнить действие своими правами и записать в историю чужое имя. Это касается всей автоматической части аудита — inbound, FBS-заказов и поставок, отгрузок.

Достижимость зависит от фронтирующего proxy: некоторые склеивают дубли в одно значение через запятую, тогда оба парсера сломаются одинаково. Проверить нечем — конфига proxy в пакете нет.

Но дефект глубже одного словаря: **личность для аудита не должна выводиться повторным разбором токена**. `get_current_user` может проверять то, чего не проверяет `decode_access_token` (в пакете `app/api/deps.py` и `app/services/tokens.py` отсутствуют — назвать разницу я не могу). Любое расхождение двух парсеров = неверный автор в append-only журнале.

**Минимальная правка (без новых сущностей):** заменить строку 131 на выбор **первого** заголовка — тем же перебором, что делает Starlette. Правильнее — устанавливать `document_event_actor(user.id)` в зависимости аутентификации, где личность уже проверена, и убрать разбор заголовка из middleware совсем.

### 3. Новые события WMS-325 пишутся мимо режима, который включает штатный путь

В автоматическом пути перед вставкой событий выставляется настройка сессии Postgres (GUC — переменная сеанса):

```python
799: if connection.dialect.name == "postgresql":
800:     connection.execute(
801:         select(func.set_config("wms.document_event_writer", "application", True))
```

Явный путь `record_document_event`, которым пользуются все новые записи WMS-325, этого **не делает** — `document_event_service.py:240-243` сразу выполняет `INSERT`. У переменной с именем «writer = application» осмысленный потребитель ровно один: триггер или RLS-политика на таблице, разрешающая запись только приложению (это же обычная защита append-only-журнала от ручных правок).

Если такой сторож есть, цепочка получается такая: PATCH прав → `record_document_event_safely` → `record_document_event` → база отбивает вставку → исключение ловится в `document_event_service.py:271-278`, пишется в лог и возвращается `False` → **права меняются, событие не записывается, ошибка наружу не выходит**. На SQLite в тестах ничего этого нет, тесты зелёные.

**Минимальная правка:** три строки в `record_document_event` перед `await connection.execute(insert(...))` — тот же `set_config` под тем же условием диалекта.

**Чего не хватает для окончательного вывода:** миграции, создающей `document_event` (`backend/alembic/versions/*document_event*`). По ней видно, есть ли триггер/политика. Если её нет — тогда отдельный вопрос, зачем вообще выставляется эта переменная, и не теряются ли уже сегодня в бою все явные события (например, у передачи FBS, откуда взялась ветка идемпотентности в строках 244-255).

### 4. `source` берётся из окружения, а автор — из зависимости; расхождение роняет запрос в 500

Три места: `staff_permissions_service.py:176-177`, `seller_staff_permissions_service.py:175-176` и `243-244`. Везде одинаково:

```python
source=actor.source,          # из ContextVar, заполняется middleware
actor_user_id=acting_user.id, # из проверенной зависимости, всегда не None
```

А валидатор в `document_event_service.py:169-170` требует: если `source == "system"`, то `actor_user_id` обязан быть `None`. И `record_document_event_safely` (строки 269-270) `DocumentEventError` **не глушит, а пробрасывает**. Значит любой вызов этих сервисов в контексте, где middleware не отработал, не «пропустит аудит», а **уронит операцию**. Достижимо тремя способами: middleware не зарегистрирован в приложении (в пакете нет `backend/app/main.py` — проверить нечем); прямой вызов сервиса из теста/скрипта/миграции; вызов из Starlette BackgroundTask, который принудительно переводится в системный контекст (`document_event_service.py:107-109`).

**Минимальная правка:** во всех трёх местах написать `source=SOURCE_USER` и убрать `current_document_event_actor()`. Действующий пользователь здесь известен точно, брать его «источник» из окружения нечего.

### 5. Повышение прав: запрет менять права себе обходится созданием второго аккаунта

Код явно пытается запретить самоповышение: `staff_permissions_service.py:138-139` и `seller_staff_permissions_service.py:225-226` бросают `self_update_forbidden`. Но защиты нет.

Сценарий для ФФ (все три шага — обычные ручки, права одни и те же):
1. Сотрудник с единственным правом `settings` вызывает `POST /auth/staff-accounts` — допуск проверяется через `can_manage_ff_staff` (`staff_accounts.py:216`), пароль нового аккаунта берётся **из тела запроса** (`staff_accounts.py:222-227`, `auth_service.py:192-197`).
2. Вызывает `PATCH /auth/staff-accounts/{новый_id}/permissions` со всеми флагами `true` — это не он сам, проверка на строке 138 не срабатывает, ограничения «не выдавать больше, чем есть у тебя» нигде нет.
3. Логинится под новым аккаунтом с известным ему паролем и получает `shift_lead`, `inventory`, `packaging`, `mp_shipments`, `reception`, `cells`.

У селлера то же самое ещё короче: `create_seller_staff_user` принимает набор прав из запроса без потолка (`seller_staff_permissions_service.py:154-161`), включая `can_staff=True`.

**Минимальная правка (арифметика, не механика):** перед выдачей сравнить запрошенный набор с собственным набором действующего пользователя и отказать, если просят больше. Для админа (`ADMIN_ALL`) и владельца-селлера (`OWNER_ALL`) ничего не изменится:

```python
own = (await get_staff_permissions(session, acting_user)).as_dict()
if any(v and not own[k] for k, v in permissions.as_dict().items()):
    raise PermissionError("cannot_grant_more_than_own")
```

Ту же проверку — в путь создания, иначе она обходится обратно.

### 6. Ограничитель входа считает только IP, и за proxy это один общий счётчик на всех

`login_rate_limit.py:35-37`: ключ — `request.client.host`. Параметр `email` в `check_login_rate_limit` (строка 54) принимается и **нигде не используется** — счётчика по учётной записи нет. Отсюда два следствия.

Первое: распределённый перебор пароля одной конкретной почты с разных адресов не ограничен ничем — по 5 попыток с адреса, адресов сколько угодно. Именно это в WMS-270 и требовалось прикрыть.

Второе, более неприятное: если `request.client.host` — это адрес фронтирующего proxy (uvicorn доверяет `X-Forwarded-For` только с адресов из `--forwarded-allow-ips`, по умолчанию это `127.0.0.1`, а контейнерный Caddy приходит с адреса bridge-сети), то **все клиенты попадают в одно ведро**. Тогда любой человек из интернета пятью неудачными логинами в минуту закрывает вход всей организации. Это не гипотеза о коде — это прямое следствие строки 37 при отсутствии доверенного разбора заголовка; чего именно не хватает, чтобы закрыть вопрос, я называю ниже.

Тест `test_wms270_login_rate_limit.py:136-147` («подделанные заголовки не сбрасывают лимит») даёт ложную уверенность: он зелёный именно потому, что код заголовки вообще не читает, а в бою читать их (из доверенного источника) как раз обязан. Докстринг теста на строках 92-97 утверждает про «две шкалы — по IP и по паре (IP, почта)» — второй шкалы в коде нет.

**Минимальная правка:** добавить второе окно в тот же словарь по нормализованной почте (`email.strip().lower()` — сейчас в `auth.py:258` передаётся ненормализованная строка) и зафиксировать `FORWARDED_ALLOW_IPS`/`--forwarded-allow-ips` на адрес конкретного proxy. Новой таблицы это не требует.

### 7. Переполнение таблицы клиентов отключает вход всем новым адресам

`login_rate_limit.py:60-70`. Когда приходит новый IP, код сначала проходит **по всем** известным ключам, а если после чистки их всё ещё `>= _MAX_CLIENTS` (10 000) — отдаёт 429 новому клиенту. Значит, залив 10 000 адресов по одному запросу (для IPv6 из одной /64 это дёшево), атакующий получает состояние, в котором **любой новый клиент получает 429**, пока окно не истечёт. Плюс сам обход — O(числа известных клиентов) под глобальным мьютексом, синхронно, внутри асинхронного обработчика: каждый запрос с нового адреса на это время останавливает event loop целиком.

**Минимальная правка:** заменить растущий словарь на массив фиксированного размера, ключ — `hash(ip) % N`. Память ограничена по построению, обход не нужен, глобального отказа нет; ценой становятся редкие коллизии, а не отключение входа.

### 8. Два теста, скорее всего, не выполняются

`test_wms270_login_rate_limit.py:136` и `:195` — асинхронные тесты **без** `@pytest.mark.asyncio`, тогда как остальные четыре в этом файле (строки 38, 61, 91, 116) декоратор имеют. В строгом режиме pytest-asyncio такие функции не запускаются, а тихо пропускаются с предупреждением. Это ровно те два теста, которые проверяют самое интересное — подделку заголовков и конкурентный залп. Чтобы сказать наверняка, нужен `backend/pyproject.toml` (или `pytest.ini`) с `asyncio_mode`; в пакете его нет.

## Что подтвердилось из уже известного (не новое)

**WMS-270, оракул** — закрыт по коду: `auth_service.py:86-88` объединяет «нет пользователя» и «пароль не задан» в один `invalid_credentials`, и обе ветки прогоняют bcrypt через `_DUMMY_PASSWORD_HASH` (строка 70), так что грубой разницы по времени нет. `auth.py:263-270` отдаёт неизменяемый 401. Заявленный в бэклоге `password_setup_required` в пакете отсутствует.

Одна неточность рядом: докстринг `auth_service.py:74-80` перечисляет среди одинаково отвечающих причин «аккаунт заблокирован», а такой ветки в функции нет — проверяются только `user is None`, `must_set_password` и пароль. Либо у `User` нет признака блокировки и надо править комментарий, либо признак есть и вход его не смотрит — это уже дыра. Разрешается файлом `backend/app/models/user.py`, которого в пакете нет.

**WMS-325** — доказанный пробел закрыт: смена прав ФФ-сотрудника и seller-сотрудника пишется append-only в существующий `document_event`, до `commit`, в одной транзакции с самой правкой (`staff_permissions_service.py:168-186`), с `before`/`after` и обоими пользователями в `payload_json`. Событие пишется только при реальном изменении (`before != after`) — правильно. Читается через `document_events.py:73` (`staff_user` добавлен в `Literal`). Новых таблиц не заведено.

Осталось внутри той же задачи, по коду: создание **ФФ**-сотрудника события не пишет (`auth_service.py:183-216`), хотя для селлера аналогичное событие есть (`seller_staff_permissions_service.py:169-185`) — то есть менее защищённый путь как раз не покрыт; создание аккаунта селлера-владельца (`auth_service.py:146-180`) тоже не покрыто; константа `EVENT_STAFF_RATE_CHANGED` (`document_event.py:52`) объявлена, но писателя в пакете нет — ставка это деньги, проверить нужно в `backend/app/services/staff_packaging_billing_service.py`, которого здесь нет.

Мелочь по чтению истории: `document_event_service.py:300` сортирует по `occurred_at desc, created_at desc`, а оба поля в одной вставке равны (`_event_row`, строка 194). При совпадении отметок постраничная выдача может дублировать и терять строки. Добавить `DocumentEvent.id.desc()` третьим ключом.

**Неограниченные ручки рядом со входом.** `auth.py:306-324` (`/auth/request-password-reset`) не проходит через ограничитель вообще: перечисление почт закрыто одинаковым 204, но забрасывание письмами любого известного адреса и создание фоновых задач на каждый запрос — нет. Ограничитель здесь тот же самый, отдельная сущность не нужна.

## Границы этой проверки и чего в пакете нет

Проверено ровно то, что перечислено в блоках SOURCE, по их SHA256 (`BASE_HEAD` 95691999 для WMS-270 и 45177be5 для аудита). Часть файлов не закоммичена и правится параллельно — вывод относится к этим хэшам, а не к будущему HEAD.

**По критериям поручения, для которых кода в пакете просто нет:**

* **WMS-056 (снятие товара из короба стирает историю)** — не проверяемо. Есть только константа `EVENT_TARE_LINE_QTY_CHANGED` (`document_event.py:44-47`). Писателя нет ни в одном файле пакета, а автоматический сборщик `_document_rows` (`document_event_service.py:373-407`) обрабатывает `InboundIntakeLine` и `MarketplaceUnloadLine` и **не обрабатывает** `InboundIntakeBoxLine` ни в `session.deleted`, ни в `session.dirty`. Нужны: `backend/app/services/inbound_intake_box_service.py`, `backend/app/services/inbound_cargo_place_service.py`, `backend/app/models/inbound_intake.py` и миграция.
* **Чат селлера** (основной чат у каждого селлера, участники и права, вложения, редактирование, точный документ, вставка картинки по Ctrl+V) — в пакете нет ни одного файла. Нужны модели/роуты `backend/app/models/chat*.py`, `backend/app/api/chat*.py` и экраны `frontend/src/**/Chat*`. Полная UI-приёмка в любом случае делается руками в браузере, статикой не заменяется.
