# Ревью пакета WMS-417 (Opus 5, независимая сессия)

## Краткий вердикт

Пакет **не готов к слиянию**: в нём есть тест, который по текущему коду сервиса обязан падать, и три пути, на которых оператор загоняет документ инвентаризации в непроводимое состояние без возможности выйти из него через интерфейс. При этом надо отдать должное — по сравнению с тем, что утверждала сверка WMS-414 от 09.09, часть критериев уже закрыта: склад при регистрации создаётся, все три поведения WMS-153 реализованы, комментарий редактируется, блокировка строки акта расхождений появилась. Ниже — что именно я проверил по коду и что нашёл нового.

Сразу оговорю рамку: это статический разбор ровно тех файлов и хэшей, что даны в пакете. Я ничего не запускал, браузер не открывал, runtime-доказательств не привожу. Файлы, которых в пакете нет, я перечислил в конце — по ним выводов не делаю вообще.

## Новые доказанные дефекты, по убыванию приоритета

### 1. Красный тест: сервис больше не бросает `container_has_no_stock`

`backend/tests/test_inventory_counts.py:527-544` требует, чтобы создание документа по пустой таре вернуло `409 container_has_no_stock`. В `inventory_count_service.py` этого кода ошибки нет ни в одном месте — я прошёл весь файл. В `create_count` (строки 347-365) ветка контейнера вычисляет `warehouse_id` и предикаты, получает пустой список балансов (строка 370) и спокойно создаёт документ без строк, возвращая 201. Код `container_has_no_stock` остался только мёртвым элементом маппинга ошибок в `backend/app/api/inventory_counts.py:648`.

**Вход и порядок:** POST `/operations/inventory-counts` с `{"source":"object","object":{"type":"box","id":<пустой короб>}}` → 201 вместо ожидаемого 409.

**Почему это важно:** гейт CI на этом файле красный, а значит, весь пакет не проходит собственный гейт проекта. Плюс сам по себе документ из нуля строк — это документ, который потом упадёт на проведении с `empty_count` (строка 1503-1504), то есть оператор получит бесполезную сущность.

**Минимальное исправление:** решить, что здесь истина. Если пустую тару теперь **можно** брать в пересчёт (а это логично: именно в пустой короб пишут находку), то удалить тест 527-544 и строку 648 из `_http_error`. Если нельзя — вернуть проверку в `create_count` после строки 370. Одно из двух, но не оба.

### 2. Находка в подтверждённо пустую тару делает документ непроводимым

Цепочка полностью внутри пакета:

1. Оператор выделяет пустой короб B и жмёт «Здесь пусто» (`FfInventoryCountScreen.tsx:468-489` → POST `/empty-place`).
2. `mark_place_empty` (`inventory_count_service.py:648-664`) кладёт `{"kind":"box","id":B}` в `count.empty_containers`. Строк документа в коробе нет, обнулять нечего.
3. Короб теперь защищён от прунинга (`api/inventory_counts.py:552-553` добавляет пометки в `created_container_ids`), то есть остаётся видимым в дереве — оператор может в него пикнуть.
4. Оператор сканирует туда товар. `record_found` (`inventory_count_service.py:1101-1120`) создаёт строку `expected=0, actual=1` и **не трогает `empty_containers`** — в отличие от `save_actuals`, где такая очистка есть (строки 525-530).
5. Проведение: цикл строк создаёт движение +1 и баланс в коробе B, затем `await session.flush()` (строка 1558), затем цикл удаления пометок (1559-1565) вызывает `delete_document_container`, где `_direct_balance("box", B)` возвращает 1 → `container_not_empty` (строки 891-892) → 409.

Документ проводить нельзя. Снять пометку из интерфейса нечем: кнопки «отменить пусто» на экране нет, а единственный путь очистки — прислать эту строку в PUT `/lines` с ненулевым значением, чего скан находки не делает.

**Минимальное исправление:** сделать `record_found` и `add_manual_line` симметричными `save_actuals` — при записи строки в тару убирать эту пару из `count.empty_containers`. Это две одинаковые строки кода в двух функциях, новых сущностей не нужно. Альтернатива похуже: в `post_count` вместо падения пропускать непустые пометки.

### 3. «Здесь пусто» на ячейке с тарой приёмки — тот же тупик, но без единого скана

`mark_place_empty` для `kind == "cell"` (`inventory_count_service.py:637-646`) обходит карту склада и **рекурсивно собирает всю тару внутри ячейки** в `refs`, а затем целиком пишет её в `empty_containers` (строки 662-664). Никакой фильтрации по принадлежности к приёмке там нет.

Между тем `delete_document_container` намеренно отказывается трогать тару приёмки: `container_linked_to_inbound` на строках 848-849 (палета), 889-890 (складской короб с `inbound_request_id`) и 905-906 (короб/грузоместо самой приёмки, `InboundIntakeBox`/`InboundIntakeCargoPlace`). А узлы приёмочных коробов в карту склада попадают — см. `warehouse_map_service.py:568-584`.

**Сценарий:** в ячейке A-01 стоит один пустой короб приёмки. Оператор встаёт на ячейку, жмёт «Здесь пусто», ставит факты по остальным местам, жмёт «Провести» → 409 `container_linked_to_inbound`, откат, и снять пометку опять нечем.

**Минимальное исправление:** в `mark_place_empty` не класть в `empty_containers` то, что документ заведомо не имеет права удалять — то есть фильтровать тару с непустым `inbound_request_id` и id из таблиц приёмки. Одна проверка на входе вместо сторожа в рантайме.

### 4. «Здесь пусто» затирает уже посчитанное, вопреки собственному контракту

Документация действия на экране (`FfInventoryCountScreen.tsx:196-203`) обещает буквально: «все ещё не тронутые строки внутри выбранного места получают actual = 0; уже введённые значения не трогаем (человек мог посчитать несколько строк и потом ошибиться кнопкой)».

Сервер обещание не выполняет: `inventory_count_service.py:660-661` — `for line in lines: line.actual_quantity = 0`, без проверки `is None`.

Хуже того, для ячейки условие отбора строк — `InventoryCountLine.storage_location_id == place_id` (строка 647), а у строк, лежащих в таре, `storage_location_id` — это как раз ячейка, где тара стоит (адрес берётся из баланса при наполнении документа, строки 392-403). То есть «пусто» по ячейке обнуляет и всё посчитанное внутри коробов этой ячейки, а не только россыпь.

**Сценарий:** оператор пересчитал короб в ячейке A-01 (18 шт), затем встал на саму ячейку, чтобы отметить, что россыпи там нет. Все 18 превращаются в 0, при проведении товар списывается.

**Минимальное исправление:** `if line.actual_quantity is None: line.actual_quantity = 0` — ровно то, что обещает UI. Если владелец хочет обратного поведения, надо править текст на экране, а не оставлять два разных обещания.

### 5. «Здесь пусто» на ячейке без тары не записывает вообще ничего

Продолжение той же функции: `refs` наполняется только узлами `box`/`cargo_place`/`pallet` (строка 641), сама ячейка туда не попадает никогда. Если в ячейке нет ни строк документа, ни тары, то после запроса не меняется ни одна строка и `empty_containers` остаётся прежним. API вернёт 200 и неизменённый документ, оператор решит, что подтвердил пустоту, а при проведении получит `empty_count` (строка 1503), если это было его единственное действие.

Это ровно тот критерий WMS-154, который считался невыполненным, и он остаётся невыполненным для самого частого случая — пустой ячейки.

**Минимальное исправление:** класть в `empty_containers` и саму ячейку (`{"kind":"cell","id":...}`), а в цикле удаления `post_count` (строка 1561) пропускать элементы с `kind == "cell"` — ячейки не удаляются, они только фиксируют факт нулевого пересчёта. Две строки, без новой таблицы.

### 6. «Переложить сюда» может списать чужой остаток

`move_line_to_container` защищается от конфликта только по строкам документа (`inventory_count_service.py:730-740`): ищет другую строку **этого же документа** с тем же товаром в целевой таре. По живому остатку проверки нет. Между тем `line.expected_quantity` после переезда не пересчитывается (комментарий на строках 694-698 объясняет это как осознанный выбор), а проведение считает `delta = actual - current` от фактического баланса нового адреса (строки 1516-1533).

**Сценарий, воспроизводимый через интерфейс:**

- Документ заведён по объекту «короб A» (`source=object`, `type=box`) — в нём только строки из короба A.
- Короб A стоит на палете PL. На самой палете россыпью лежит тот же товар, 10 шт (баланс с `container_kind='pallet'`).
- Палета PL видна в дереве, потому что у неё есть непустой ребёнок — короб A (`_prune_empty_containers`, `api/inventory_counts.py:387-426`). При этом остаток 10 шт на палете **на экране не показан**: `_container_tree` копирует из карты склада только узлы тары и отбрасывает продуктовые (строки 370-372), а строк документа по этому остатку нет.
- Оператор выделяет палету, у строки товара жмёт «Переложить сюда». Конфликт не находится, `move_object` переносит 4 шт, балансы сливаются в 14.
- Оператор вводит факт 4 (он именно 4 и переложил). Проведение: `current = 14`, `delta = -10` → списание десяти штук, которых оператор никогда не видел.

Предупреждение `changed_balances` при этом вернётся, но движение всё равно пройдёт.

**Минимальное исправление:** расширить проверку на входе с «строки документа» на «живой остаток» — перед вызовом `move_object` отклонять перенос, если в целевой таре уже есть ненулевой баланс этого товара. Это одна проверка, и она заодно поглощает существующую `product_already_at_destination`.

### 7. WMS-179: `onDirtyChange` из приёмки всегда сообщает `false`

Сверка WMS-414 записала FF-приёмку в «защищено». По этому пакету это не так. В `FfInboundRequestView.tsx` проп `onDirtyChange` используется ровно в одном месте — эффекте на строках 536-541:

```tsx
useEffect(() => {
  if (!sortingView) onDirtyChange?.(false)
  return () => onDirtyChange?.(false)
}, [onDirtyChange, sortingView])
```

Больше `onDirtyChange` не вызывается нигде в файле. Признак несохранённого ввода `hasUnsavedActualChange` считается (строки 2070-2078), но живёт только внутри компонента и используется только в `handleClose` (2094-2100). То есть родительский `closeFfDocument` получает `dirty=false` всегда, и любой путь закрытия мимо кнопки «Закрыть» самого компонента проходит без переспроса.

**Минимальное исправление:** заменить тело эффекта на `onDirtyChange?.(!sortingView && hasUnsavedActualChange)` с зависимостью от `hasUnsavedActualChange`, оставив cleanup со `false`.

### 8. WMS-155: `comment_changed` проверяется после того, как строки уже изменены

В `save_actuals` порядок такой: сначала мутируются `actual_quantity` всех переданных строк (`inventory_count_service.py:521-524`), затем пересобирается `empty_containers` (525-530), и только потом сверяется `expected_comment` и бросается `comment_changed` (531-532). Исключение уходит наружу без `rollback` внутри сервиса.

Практического ущерба, скорее всего, нет — сессия закрывается через зависимость и незакоммиченная транзакция откатывается, — но проверять оптимистичную блокировку после мутации неправильно: любой будущий вызов этой функции внутри уже открытой транзакции (как это делает `delete_document_container` с `commit=False`) получит наполовину применённые изменения.

**Минимальное исправление:** перенести блок 531-532 сразу после проверки статуса на строке 502.

### 9. `create_sorting_object` откатывает чужую транзакцию при `commit=False`

`warehouse_map_service.py:1336-1350`: в ветке короба/грузоместа `except WarehouseBoxError` безусловно делает `await session.rollback()`, даже когда `commit=False`. Вызывает её `inventory_count_service.create_document_container` (строки 579-589) именно с `commit=False`, уже удерживая `SELECT ... FOR UPDATE` на документе.

Сравните с эталоном рядом: `catalog_service.create_warehouse` (строки 76-80) в такой же ситуации делает `if not commit: raise` и чужую транзакцию не трогает. Здесь этой защиты нет.

**Минимальное исправление:** тот же `if not commit: raise` перед `rollback`.

### 10. Тест ручного добавления строки не выполняется

`backend/tests/test_inventory_counts.py:1368` — `async def test_inventory_count_manual_line_without_selection_uses_sorting_zone(...)` объявлен без декоратора `@pytest.mark.asyncio`, в отличие от всех соседних тестов файла. Если режим asyncio в проекте не `auto`, этот тест не выполняется, и главный сценарий ручного добавления строки (адрес по умолчанию → зона сортировки) остаётся непокрытым.

**Минимальное исправление:** добавить декоратор. Чтобы утверждать, выполняется он или нет, нужен `backend/pyproject.toml` либо `pytest.ini` — их в пакете нет.

## Подтверждения по коду: что закрыто, а что нет

Здесь я отделяю уже известное из сверки WMS-414 от того, что реально в пакете.

**Закрыто, вопреки старым статусам.** WMS-062: `auth_service.py:58-68` создаёт «Основной» с `code=main` через существующий `catalog_service.create_warehouse` с `commit=False`, в той же транзакции, что tenant и администратор — то есть ровно как просила постановка, без дублирования модели. WMS-153: все три поведения на месте — ячейка при создании тары (`create_sorting_object`, проверка ячейки на строках 1304-1315), перенос (`move_line_to_container`), удаление пустой тары (`delete_document_container`). WMS-155: комментарий редактируется той же ручкой сохранения фактов, без отдельного PUT документа — это правильное решение по правилу «не плоди сущностей». WMS-156 в части конкуренции: `get_act` получил параметр `lock` (`discrepancy_act_service.py:60-80`), и `approve_act`/`reject_act`/`submit_act`/`add_line`/`delete_line` вызывают его с `lock=True` — два параллельных approve теперь сериализуются на строке акта, второй получит `bad_status`. Проблема, описанная в WMS-156 как незащищённая, в этом пакете исправлена.

**Не закрыто, и это подтверждается кодом сервиса.** Главный критерий WMS-156 остаётся открытым: в `discrepancy_act_service.py` нет **ни одной** функции, которая устанавливала бы `inbound_intake_request_id` после создания акта — связь задаётся только в `create_act` (строки 30-57). При этом `approve_act` без неё отказывает (`inbound_link_required`, строки 172-173), а `FfInboundRequestView.tsx:678-681` показывает акты только если `inbound_intake_request_id === requestId`. Значит акт, созданный с пустым телом, не только нельзя утвердить — его вообще не видно из документа приёмки, и починить его нечем. Это не гипотеза, а прямое следствие состава функций сервиса.

**Замечание по WMS-174.** Признак повреждения короба во фронте есть: поле `is_damaged` в типе `InboundBox` (строка 117), чекбокс «Короб пришёл повреждённым» (строки 3098-3104) и PATCH `/boxes/{id}/damaged` (`setBoxDamaged`, строки 1895-1913). Два наблюдения по нему. Первое: чекбокс, в отличие от соседних кнопок «Наполнить» и «Удалить», не заперт `receivingActive` — отметить повреждение можно и после завершения приёмки. Второе, важнее: обработчик подменяет короб целиком объектом из ответа (`current.boxes.map(...)`), и если ответ не содержит `lines`, содержимое короба исчезнет с экрана, а кнопка «Удалить» разблокируется, потому что её условие — `visibleLines.length > 0` (строка 3126). Проверить схему ответа я не могу: `backend/app/api/inbound_intake.py` в пакет не входит.
