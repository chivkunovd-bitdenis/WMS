# Ревью пакета WMS-417 (сессия Opus 5 xhigh)

## Краткий вердикт

Пакет — не «тот же код, что в аудите WMS-414». По трём задачам он заметно продвинулся, и это надо зафиксировать честно, чтобы не повторять чужие выводы: **все мутации `pool.quantity` из `inventory_service` действительно убраны** (резерв, отмена, недостача, передача без резерва), **`merge_products` действительно берёт `SELECT ... FOR UPDATE` на обе карточки до чтения балансов и перечитывает балансы под блокировкой**, **автоимпорт Ozon действительно больше не требует товарной галки публикации**. Всё это я проверил по строкам, а не по отчётам.

При этом пакет содержит **три дефекта высокого приоритета, которых в прежних отчётах нет**, и один незакрытый хвост WMS-338, который прежний аудит называл, а пакет не убрал. Самое опасное — не остатки: это тихая запись «маркировка не требуется» для отправлений Ozon и безвозвратное обнуление операторских потолков при сохранении правила доли.

Runtime-доказательств я не привожу: инструменты не использовались, тесты не запускались, экраны не открывались. Всё ниже — чтение зафиксированных в пакете файлов по указанным SHA256.

## Новые доказанные дефекты

### 1. Автоимпорт Ozon подписывает «маркировка не нужна» там, где он этого не знает

**Где:** `wms352-ozon-publication/backend/app/services/ozon_fbs_sync_service.py:803` и `:813-814`.

Функция `_requirement_kinds` (строки 222–239) возвращает **пару**: список требуемых видов маркировки и флаг «Ozon вообще ответил про требования». Её собственный docstring объясняет, зачем флаг нужен: пустой список при «ответил» означает «не требуется», а при «не ответил» — «мы не знаем», и гейт выпуска не имеет права трактовать незнание как разрешение. `_apply_requirements` (653–671) этот контракт соблюдает: `if not seen: return`.

Но в `sync_ozon_orders` флаг **выбрасывается** на строке 803 (`required_kinds, _ = _requirement_kinds(row)`) и на строке 814 жёстко подменяется на `requirements_seen = True` с комментарием «строку отправления мы разобрали — значит про требования знаем». Разобрать строку и получить от Ozon поле `requirements` — разные вещи. Соседняя функция того же файла, `sync_ozon_order_statuses:1012`, использует настоящий флаг — то есть код противоречит сам себе внутри одного модуля.

**Сценарий:** ответ `/v4/posting/fbs/unfulfilled/list` приходит без ключа `requirements` (или с не-словарём). `_requirement_kinds` → `([], False)`. Строка 803 флаг теряет, 814 ставит `True`. `_apply_requirements` записывает `order.required_meta_json = []` и `meta_details_json["ozon_requirements"] = {"kinds": []}`. Для гейта выпуска это уже не «не знаем», а «не требуется». Строки 809–812 частично прикрывают ситуацию: SGTIN (код Честного знака) добавляется из каталога по `requires_honest_sign`. Но UIN (ювелирные изделия) и IMEI (техника) из каталога не выводятся — по ним отправление уйдёт без кодов.

**Минимальное исправление:**

```python
required_kinds, requirements_seen = _requirement_kinds(row)   # :803
...
if MARKING_KIND_SGTIN not in required_kinds and await _honest_sign_required_by_catalog(...):
    required_kinds.append(MARKING_KIND_SGTIN)
    requirements_seen = True                                   # каталог — тоже знание
# строку 814 удалить
```

### 2. Сохранение правила доли безвозвратно обнуляет операторские потолки штук — по обеим площадкам

**Где:** `wms338-stock-min-formula/backend/app/services/fbs_stock_rule_service.py:845-854` (массовый `UPDATE ... SET quantity=0`) и `:874-878` (та же логика построчно).

Прямо над этим кодом, на строках 841–843, стоит утверждение: «Доля не стирается при переходе в штуки и наоборот: переключил галку обратно — работает то, что было. Оба числа лежат рядом, режим решает, какое из них читает публикация». Для доли это правда: `product.fbs_percent` и `pool.percent` сохраняются. Для штук — нет: при `rule.units_mode == False` все `pool.quantity` продавца зануляются.

Отдельно: комментарий WMS-342 на строках 818–828 обещает, что зачистка ограничена «ТЕМИ площадками, чьи склады правило перечисляет». Фактический фильтр на 829–835 берёт `marketplace.in_(sorted({binding.marketplace for binding in bindings}))`, где `bindings` — **все активные привязки продавца** (`_seller_bindings(..., publishing_only=False)`, строка 698). То есть фильтр совпадает с «все площадки продавца» и ни от чего не защищает. Авария, ради которой писали WMS-342 — «оператор сохранял правило доли для Wildberries и молча стирал штуки, выделенные на Ozon» — воспроизводится этим кодом дословно.

**Сценарий:** товар в поштучном режиме, потолки WB = 50, Ozon = 30. Оператор сохраняет по нему правило доли (`units_mode=False`). После `set_rule_for_products` оба `pool.quantity` = 0. Обратное включение штук даёт нули — числа, которые задавал оператор, не восстанавливаются ниоткуда. Это нарушает «число оператора меняет только оператор»: оператор менял долю WB, а потерял потолок Ozon.

Достижимость усиливается уже известной WMS-060: отдельный маршрут `/app/ff/fbs-stock` полей режима не шлёт, и правило приезжает с `units_mode=False` без намерения оператора. Подтвердить эту цепочку по пакету я не могу — ни `FfProductsFbsPage.tsx`, ни `backend/app/api/products.py` в пакет не включены.

**Минимальное исправление** — не изобретать фильтр площадок, а вообще не трогать чужое число:

```python
# :845-854 — блок UPDATE ... values(quantity=0) удалить целиком
# :874-878
if rule.units_mode:
    pool.quantity = int(units or 0)
# else-ветку убрать: в процентном режиме quantity не читается вовсе
```

Что `quantity` в процентном режиме действительно не читается, видно в `split_amounts:409-419`: там берётся `pool.percent`. Единственное следствие зануления — потеря операторского ввода. После такой правки `governed_bindings` (829–835) перестаёт быть нужен и уходит вместе с блоком.

### 3. `record_movement_and_adjust_balance` не единственный писатель — блокировки товара берутся в неотсортированном порядке

**Где:** `wms338-stock-min-formula/backend/app/services/marketplace_unload_service.py:745-755` (`replace_lines`), а также `:797-805` (`plan_request`) и `:859-867` (`confirm_request`).

`_assert_available_for_unload_quantity:505` берёт `lock_stock_product`, то есть `SELECT ... FOR UPDATE` на строке товара (эксклюзивная блокировка строки до конца транзакции). В `replace_lines` цикл идёт по `normalized.items()` — порядок вставки словаря, то есть порядок, в котором товары пришли от клиента. В `plan_request`/`confirm_request` — по `req.lines`, загруженным через `selectinload` без `order_by`, то есть порядок из БД не гарантирован.

Все остальные места проекта берут блокировки в возрастающем порядке идентификатора: `inventory_service.update_fbs_order_reservation:158` (`sorted(product_ids, key=str)`), `fbs_stock_rule_service:653-658` (`order_by(Product.id)`), `product_merge_service:314` (`sorted(ids)`). Здесь — единственное исключение.

**Сценарий:** два оператора одновременно правят две разные отгрузки, обе с товарами A и B, но в противоположном порядке строк. Транзакция 1 держит A и ждёт B, транзакция 2 держит B и ждёт A. PostgreSQL обнаруживает взаимную блокировку и откатывает одну из транзакций с кодом 40P01; оператор получает 500 и теряет введённое.

**Минимальное исправление:** сортировать перед циклом блокировок, тем же ключом, что в `inventory_service:158`:

```python
for product_id, qty in sorted(normalized.items(), key=lambda kv: str(kv[0])):   # :745
for ln in sorted(req.lines, key=lambda ln: str(ln.product_id)):                 # :797, :859
```

### 4. Объединение карточек: окно для тихой потери строки, созданной параллельно

**Где:** `wms349-merge-service/backend/app/services/product_merge_service.py:96-112` (комментарий и блокировки ссылок), `:358-366` (перенос FK и удаление карточки).

Комментарий на строке 101 утверждает: «Product locks prevent new FK references while this check and merge run». Это неверно для части писателей. Блокировка `Product` мешает создать ссылку только тем, кто эту блокировку берёт. `marketplace_unload_service.add_line` её берёт (через `_assert_available_for_unload_quantity`), а вот `inventory_service.sync_outbound_line_reservation:668-701` создаёт `InventoryReservation` с `product_id` без всякого `lock_stock_product`. Row-lock существующих строк, который берёт `_lock_references_and_check_conflicts:108-112`, вставку новых строк не предотвращает — в PostgreSQL `SELECT FOR UPDATE` блокирует только уже видимые строки.

**Сценарий:** merge выполнил `UPDATE ... SET product_id = target` по всем FK-таблицам (строки 358–361). Параллельная транзакция вставляет `InventoryReservation` со старым `product_id = source`. Merge делает `DELETE FROM products WHERE id = source_id` (строка 366). Если внешний ключ объявлен `ON DELETE CASCADE` — а комментарий `_product_fk_columns:147-153` прямо говорит про каскад — новая строка резерва исчезает молча, без ошибки.

Здесь важна оговорка: какие именно FK объявлены каскадом, по пакету не проверить — моделей в нём нет. Если конкретный FK — `RESTRICT`, `DELETE` упадёт в `IntegrityError`, будет свёрнут в `merge_conflict` и откачен, то есть безопасно.

**Минимальное исправление** без новых сущностей — повторить проверку после переноса, перед удалением:

```python
for table, column in _product_fk_columns():
    await session.execute(update(table).where(column == source_id).values({column.name: target.id}))
await session.flush()
# новая проверка: ссылок на исчезающую карточку не должно остаться
for table, column in _product_fk_columns():
    if await session.scalar(select(column).where(column == source_id).limit(1)) is not None:
        raise ProductMergeError("merge_busy")
await session.execute(delete(Product).where(Product.id == source_id))
```

Заодно стоит поправить комментарий на строке 101: он описывает гарантию, которой нет.

### 5. Экран показывает не то число, которое уедет, если у продавца больше одного физического склада

**Где:** `fbs_stock_rule_service.py:453-462` (`get_rule_view`), `:524-560` (`get_rule_views`) против `:958-981` (`publish_amounts_for_binding`).

`get_rule_view` считает свободный остаток через `_free_stock_for_bindings` (237–271), которая **суммирует** свободное по всем `wms_warehouse_id` привязок продавца, и один раз клампит этой суммой `split_amounts`. Публикация же (`publish_amounts_for_binding:963-969`) сначала сужает список привязок до одного склада (`row.wms_warehouse_id == binding.wms_warehouse_id`), а свободное берёт из `fbs_stock_breakdown_by_product` **по этому одному складу**.

**Сценарий:** продавца кормят два физических склада, на каждом свободно по 3 штуки, потолок оператора — 5 на один адрес WB, привязанный к первому складу. Экран покажет `published_now = min(5, 6) = 5`. Реально `publish_amounts_for_binding` посчитает `min(5, 3) = 3`. Оператор видит пять, в кабинет уезжает три, и никакого объяснения расхождению на экране нет — три числа «на складе / занято / свободно» тоже посчитаны по сумме.

**Минимальное исправление:** в `get_rule_view`/`get_rule_views` считать `published_now` тем же разрезом, что публикация — группировать `publishing` по `wms_warehouse_id`, для каждой группы брать свой `free` (у `_free_stock_for_bindings` уже есть нужная сигнатура — она принимает список привязок) и суммировать результаты `split_amounts`. Отдельного счётчика при этом не заводится, меняется только группировка существующего расчёта.

### 6. Дублирующийся `external_warehouse_id` роняет весь круг импорта Ozon

**Где:** `ozon_fbs_sync_service.py:503-510`.

`_binding_for_row` ищет привязку по `external_warehouse_id` и завершает запрос `scalar_one_or_none()`. Уникальность в БД, судя по `fbs_warehouse_binding_service.py:472-480`, объявлена по паре «продавец + `wb_warehouse_id`», а не по `external_warehouse_id`. При этом `_upsert_binding:407` принимает `external_warehouse_id` от вызывающего и уникальность по нему не проверяет.

**Сценарий:** у продавца две активные Ozon-привязки с разными `wb_warehouse_id`, но одинаковым `external_warehouse_id`. `scalar_one_or_none()` бросает `MultipleResultsFound` — необработанное исключение прерывает цикл `sync_ozon_orders` целиком, а не пропускает одну строку. Все остальные отправления этого круга не импортируются.

**Минимальное исправление:** `.order_by(FbsWarehouseBinding.wb_warehouse_id).limit(1)` и `.scalars().first()` — детерминированный выбор вместо падения. Схемы API привязок в пакете нет, поэтому подтвердить, что оператор может задать произвольный `external_warehouse_id` через ручку, я не могу; сам сервисный слой это допускает.

### 7. `_clear_product_publication` не коммитит WB-ветку

**Где:** `fbs_stock_rule_service.py:608-635`.

Функция открывает отдельную сессию `zero_session`. Ozon-ветка после `_clear_previous_ozon_stock` вызывает `await zero_session.commit()` (строка 618). WB-ветка (621–635) вызывает `publish_explicit_zero_for_binding(zero_session, ...)` и коммита не делает — при выходе из `async with` сессия откатывается. Если эта функция пишет след опубликованного нуля (по CLAUDE.md такой след для WB существует — `fbs_stock_sync_items`), он потеряется, и после подтверждённого обнуления система будет считать, что ноль не отправляли.

Подтвердить, что она действительно пишет, по пакету нельзя: `fbs_stock_sync_service.py` в пакет не включён. Но асимметрия между двумя ветками одной функции видна и требует объяснения либо `await zero_session.commit()` после строки 630.

## Ранее известное, перепроверенное по коду пакета

**WMS-338, хвост про `consume_fbs_pool` — не закрыт.** `inventory_service.py:1677-1691`: `apply_fbs_supply_write_off` по-прежнему импортирует `stock_direction_service` и вызывает `consume_fbs_pool` при `product is None or not product.fbs_units_mode`, глотая `insufficient_fbs_pool`. Заголовочный комментарий той же функции (1665–1667) утверждает, что передача без резерва больше не расходует потолок — про этот вызов он умалчивает. Тест `test_inventory_stock_cap_wms338.py:288-324` этот путь **не покрывает**: `_seed` создаёт товар с `units_mode=True`, то есть проверяется ровно противоположная ветка. Минимальное исправление — удалить строки 1677–1691 и добавить в тест сценарий с `units_mode=False`. Что именно делает `consume_fbs_pool`, по пакету не проверить: `stock_direction_service.py` в него не включён.

**WMS-338/341/329, главное требование — выполнено.** Ни одной мутации `pool.quantity` в `inventory_service.py` не осталось: `update_fbs_order_reservation:190-263` только читает пул (`_order_stock_pool:76-95`) как признак поштучного правила, `_deduct_inventory_from_fbs:268-280` возвращает отчёт и ничего не пишет, `apply_fbs_supply_write_off` потолок не трогает. Формула `min(cap, free)` живёт в одном месте — `split_amounts:400-422`. Тесты `test_inventory_stock_cap_wms338.py` этому коду соответствуют: я сверил арифметику каждого ассерта с веткой в `record_movement_and_adjust_balance` (в том числе `deduct_prefer="packed"` при нулевом `quantity_packed`, строки 953–963) — расхождений не нашёл.

**WMS-352/386 — выполнено.** `_warehouse_is_served_for_row:513-519` теперь проверяет только `binding is not None and binding.served`; фильтр по товарной публикации из автоимпорта убран (`sync_ozon_orders:806-808`), и адресный путь по `selected_posting_numbers` проходит ту же проверку. Побочное следствие: ветка `elif binding is None` на `:890-891` стала мёртвой — до неё дело не доходит из-за `continue` на 808, и `RESERVE_STATUS_WAREHOUSE_UNMAPPED` для Ozon больше не выставляется нигде. Это не ошибка, но статус остался в коде как обманка.

**WMS-349 — сериализация выполнена.** `merge_products:314-327` блокирует обе карточки `FOR UPDATE` строго по возрастанию `id`, `_sum_inventory_balances:211-228` перечитывает балансы под блокировкой с `populate_existing=True`. Я проверил всех писателей баланса в пакете: `record_movement_and_adjust_balance:780` и `apply_fbs_supply_write_off:1668` берут `lock_stock_product`, `reclassify_balance_container:1087-1098` и `apply_packaging_convert:1187-1222` работают через row-lock самой строки баланса, которую merge уже держит. Заявленная гонка «13 вместо 16» этим действительно закрывается.

Два хвоста при этом остались. Первый — пункт 4 выше. Второй: `_lock_references_and_check_conflicts:114-127` ищет уникальные ключи только среди `UniqueConstraint` в `table.constraints`; уникальные **индексы** (`Index(..., unique=True)`) туда не попадают, и для них предусмотрены ровно три хардкод-исключения (121–127). Для остальных таблиц конфликт всплывёт позже как `IntegrityError` и свернётся в безымянный `merge_conflict` (370–372) — именно тот случай, ради которого заведён словарь `_CONFLICT_LABELS`. Какие таблицы пострадают, по пакету не определить: моделей в нём нет.

**WMS-338, второй счётчик, которого прежний аудит не называл.** `fbs_warehouse_binding_service.py:673-823` — целый живой легаси-путь прошлого поколения квоты: `set_binding_stock_pool_quantity` в непоштучном режиме пишет `pool.quantity` напрямую, валидируя против `product.fbs_stock_limit` (строка 730), а `get_binding_stock_pool_summary:786-823` отдаёт наружу тройку `limit / allocated_total / available`. Одно и то же поле `pool.quantity` имеет двух писателей с несовместимой семантикой: правило зануляет его (пункт 2), легаси-путь заполняет. Плюс `fbs_stock_rule_service.reset_legacy_limits_for_products:913-917` ставит `fbs_stock_limit = 0`, после чего легаси-путь навсегда отвечает `pool_quota_exceeded` на любое положительное число. Это ровно та «квота с журналом», от которой отказались 04.09.2026, и её надо сносить вместе с моделью журнала, а не после.

**Идемпотентность отмены отгрузки на маркетплейс.** `marketplace_unload_service.cancel_request:1173-1202`: ранний выход стоит только на `req.status == STATUS_CANCELLED`, а ветка отмены для уже отгруженного документа статус **не меняет**. Повторный вызов снова выполнит `record_operational_reversal` по обеим услугам и снова запишет `record_marketplace_unload(..., reversal=True)`. Складской факт при этом не трогается — это соответствует правилу «автодокумент возврата не приходует физически». Идемпотентность целиком зависит от `billing_ledger_service` и `operation_fact_service`, которых в пакете нет.
