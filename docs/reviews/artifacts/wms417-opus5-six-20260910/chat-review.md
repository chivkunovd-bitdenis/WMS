# Ревью пакета WMS-397/WMS-399 (чат селлер↔склад)

## Краткий вердикт

Пакет — это уже не макет: в нём настоящий вертикальный срез (модели → сервис → роуты → экраны), и ключевые вещи, ради которых обычно ломаются мессенджеры, сделаны аккуратно. Идемпотентность основного чата и повторной отправки реально держится на уникальных индексах, а не на «проверке перед вставкой»; подмена заголовка документа в карточке не проходит — сервер перечитывает документ и затирает присланное клиентом; захват чужого вложения и гонка «двух сообщений на один файл» закрыты через `SELECT … FOR UPDATE` с последующей проверкой. Складских записей чат не делает вообще: `chat_document_service.py` от начала до конца состоит из `select(...)`, ни одного `add`/`update`/движения по остаткам.

Но принимать в таком виде я бы не стал. Есть один дефект, который селлер увидит в первую же минуту (он попадает не в свой основной чат), и три, которые проявятся не сразу, но неприятно: лента тянет из сети все вложения целиком, включая 25-мегабайтные файлы; каждое сообщение с карточкой документа перечитывается из БД на каждом опросе раз в 4 секунды; черновики вложений никто и никогда не удаляет. Плюс пакет физически неполон — в нём нет миграции на четыре новые таблицы и нет подключения роутера и маршрутов, то есть по этому пакету нельзя утверждать, что фича вообще поднимается.

Всё перечисленное ниже — **новое**. Прежние отчёты по WMS-397/399 говорили про коммиты `0229831f` и `6bacd06b`, которых в пакете нет; повторять их выводы я не могу и не буду.

## Доказанные дефекты, по приоритету

**1. Селлер по умолчанию попадает не в основной чат.** Сортировка списка для FF и для селлера написана зеркально: `chat_service.py:212` сортирует `kind.desc()` (значение `main` идёт раньше `extra`), а `chat_service.py:230` для селлера — `kind` по возрастанию, то есть `extra` раньше `main`. Фронт при этом выбирает чат так: `ChatScreen.tsx:33-34` ищет `kind === 'main' && seller_id === desiredSeller`, где `desiredSeller` — это `?seller_id=` из адреса. Сценарий: у селлера есть хотя бы один дополнительный чат, он открывает раздел «Чаты» из меню (без query-параметра) → `desiredSeller === null` → `find` не срабатывает → берётся `rows[0]`, а это дополнительный чат. Прямое требование владельца «у каждого селлера всегда один основной чат по умолчанию» нарушено. Правка минимальная: в `chat_service.py:230` поставить `ChatConversation.kind.desc()`, как в ветке FF; для надёжности в `ChatScreen.tsx:34` сделать запасной вариант `rows.find((r) => r.kind === 'main')`.

**2. Лента скачивает каждое вложение целиком, ещё до клика.** `ChatAttachmentView.tsx:12-27` в `useEffect` безусловно делает `fetch` содержимого и кладёт результат в `URL.createObjectURL`, и только потом (строки 29-32) решает, показать картинку или подпись-ссылку. Для картинок это оправдано — эндпоинт требует заголовок `Authorization`, обычный `<img src>` не годится. Для обычного файла — нет: сообщение с накладной на 25 МБ выкачивается в память браузера просто потому, что попало в видимую ленту. Ограничения (`chat_attachment_storage.py:24-28`) разрешают 10 файлов по 25 МБ на сообщение, то есть одно сообщение — до 250 МБ трафика без единого клика. Правка: префетчить только при `attachment.is_image`, а для файлов рисовать кнопку, которая делает тот же `fetch` в обработчике клика и отдаёт blob на скачивание.

**3. N+1 на карточках документов, помноженный на опрос раз в 4 секунды.** `chat_routes.py:247-272` для каждого сообщения с прикреплённым документом заново вызывает `read_document`, а тот делает запрос прав, запрос документа, запрос строк и `resolve_seller` — порядка четырёх запросов на сообщение (для `fbs_supply` ещё один на заказы). Лимит по умолчанию — 200 (`chat_routes.py:449`), фронт перезапрашивает список каждые 4000 мс (`ChatScreen.tsx:53`). Открытый чат, где в истории 200 карточек, — это сотни запросов каждые четыре секунды на одну вкладку. Причём в модели снапшот карточки уже лежит (`models/chat.py:189-193`) и комментарий прямо говорит, что он «used to render the card», — а API его не использует ни разу. Побочный эффект того же места: если документ удалят, карточка молча исчезнет из истории у всех, хотя снапшот на месте. Правка: рендерить снапшот, а права проверять на клике — маршрут `GET /operations/chat/documents/{kind}/{id}` их и так проверяет; если прятать карточку от «не имеющих прав» обязательно, делать одну проверку прав на запрос и один `select … where id.in_(...)` на вид документа, а при `document_not_found` откатываться на снапшот (он заведомо не подделан, его писал сервер).

**4. Черновики вложений накапливаются вечно, и общий лимит проверяется слишком поздно.** Загрузка (`chat_routes.py:604-628`) создаёт строку с `message_id = NULL` и кладёт байты в хранилище. Суммарные 100 МБ на сообщение проверяются только при отправке — в `chat_service.py:526-529`. Сценарий: любой авторизованный пользователь (а основной чат любого селлера читаем всем ролям FF, см. `chat_service.py:248-249`) грузит 10 файлов по 25 МБ, получает 413 при отправке и повторяет. 250 МБ на итерацию остаются в хранилище и в `chat_attachments` навсегда — ни одного места, где удаляются висящие черновики, в пакете нет, `delete_object` из `chat_attachment_storage.py:69-71` не вызывается ниоткуда. Правка без новых сущностей: считать сумму `size_bytes` уже загруженных черновиков этого пользователя в этой беседе прямо в момент загрузки и отклонять превышение (ограничение на вводе, а не в рантайме), плюс удаление строк `message_id IS NULL` старше суток в уже существующей периодической задаче.

**5. `GET /conversations` — это запись в базу.** `chat_routes.py:286-293` на каждый вызов выбирает всех селлеров тенанта и для каждого зовёт `ensure_main_chat`, затем коммитит. Для тенанта с сотнями селлеров это сотни SELECT’ов и потенциальных INSERT’ов на каждое открытие экрана и на каждое нажатие «Обновить список». Гонка сама по себе закрыта (`order_by(Seller.id)` даёт одинаковый порядок блокировок, `IntegrityError` перечитывает), но GET, меняющий состояние, — плохая опора. Правка: один `INSERT … SELECT … ON CONFLICT DO NOTHING` по недостающим селлерам вместо цикла.

**6. Слишком длинный `Content-Type` роняет загрузку в 500 и оставляет мусор в хранилище.** `chat_routes.py:579` берёт `file.content_type` как есть, без обрезки, а колонка — `String(128)` (`models/chat.py:244`). Имя файла обрезано до 255 (`chat_routes.py:580`), тип — нет. Сценарий: составленный вручную multipart с заголовком части `Content-Type` длиной 300 символов и неграфическим телом (ветка с проверкой картинки не сработает) → `put_bytes` уже записал объект → INSERT падает на PostgreSQL с переполнением varchar → 500, объект осиротел. На SQLite не воспроизведётся: там длина не проверяется. Правка — `[:128]` в той же строке.

**7. «Селлер» определяется двумя разными способами.** В `chat_routes.py:287` и `:738` признак селлера — `user.role == FULFILLMENT_SELLER`, в `chat_service.py:246` — тоже роль, а в `chat_routes.py:312` — `if effective_seller_id is not None`. Если зависимость `get_effective_seller_id` возвращает не-None и для сотрудников FF (например, при работе в контексте выбранного селлера), то сотрудник FF получит 403 при попытке открыть основной чат другого селлера — при том, что список чатов ему этого селлера показывает. Если она всегда None для FF — строка просто написана не по правилу. Утверждать, какой из двух вариантов реализован, я не могу: `backend/app/api/deps.py` в пакет не включён. Несогласованность при этом доказана самим пакетом; правка — привести строку 312 к проверке по роли.

**8. Порядок сообщений опирается на `func.now()`.** `models/chat.py:200-202` задаёт `server_default=func.now()`, а `chat_service.py:330` сортирует по `created_at DESC, id DESC`, где `id` — случайный uuid4. На SQLite `func.now()` компилируется в `CURRENT_TIMESTAMP` с точностью до секунды: все сообщения, отправленные в пределах одной секунды, получают одинаковую метку, и порядок в ленте определяется случайным UUID, а не порядком отправки. На PostgreSQL `now()` — это время начала транзакции, а не коммита, так что две пересекающиеся отправки тоже могут лечь в обратном порядке. Тест `test_document_identity_rights_and_latest_pagination:677-682` (строгое равенство списков id) на SQLite от этого становится плавающим. Правка в одну строку и без новых сущностей: заменить `server_default=func.now()` на питоновский `default=lambda: datetime.now(UTC)` — микросекундная точность одинаково на обеих СУБД, тайбрейк по `id` остаётся.

**9. Кнопка «Написать сообщение» исчезает молча.** Цепочка целиком видна в пакете: `chat_document_service.py:56-63` для сотрудника FF (не админа) требует право `packaging`/`reception`/`mp_shipments` в зависимости от вида документа; `chat_routes.py:751-754` при коде `forbidden` роняет весь запрос `document-options` в 403; `ChatDocumentAction.tsx:15-19` глушит любую ошибку через `.catch(() => {})`, после чего строка 20-21 возвращает `null`. Оператор, который документ видит, а права `packaging` не имеет, просто не находит кнопку чата и не получает объяснения. Правка: не проглатывать ошибку, а показывать отключённую кнопку с подсказкой о недостающем праве. Отдельно отмечу, что связка «`outbound_shipment` → право `mp_shipments`» смешивает два разных семейства документов; подтвердить или опровергнуть это по пакету нельзя — `app/services/staff_permissions_service.py` в него не входит.

**10. Карточка документа не открывает настоящий документ у селлера и у FBS-заказа.** Владелец требовал: «карточка документа кликабельна и открывает настоящий документ с проверкой прав». Фактически `AttachedDocCard.tsx:35-38` ведёт на промежуточный экран `/chat/documents/...`, а переход в рабочий документ (`ChatDocumentScreen.tsx:48-52`) обусловлен `base === '/app/ff' && kind !== 'fbs_order'` — то есть для селлера его нет вовсе, и для FBS-заказа его нет ни у кого. Это расхождение с постановкой, а не техническая ошибка, но закрывать задачу с ним нельзя.

**11. Докстринги расходятся с кодом в двух местах, и оба про доступ.** `chat_service.py:11-14` обещает «fulfillment admin implicit-owner exception» для дополнительных чатов — в `can_read_conversation` (`:244-256`) такой ветки нет, поэтому админ, не являющийся участником, не может ни прочитать чужой extra-чат, ни добавить в него участника (`chat_routes.py:430` бьёт 403). Если учётку создателя удалить, строки участников уйдут по каскаду и чат станет неуправляемым. Второй: `models/chat.py:107-111` утверждает, что для основного чата «only the seller-side user is stored explicitly», — ни одна строка кода этого не делает. Правка: либо разрешить админу тенанта управлять составом без права чтения (снять проверку `can_read_conversation` в `add_participant`, оставив `require_fulfillment_admin` и совпадение тенанта), либо привести докстринги в соответствие. Заодно — добавление участника в основной чат сейчас разрешено и не значит ничего: доступ к `main` и так неявный, строки-пустышки стоит отклонять на входе.

**12. Мёртвый код, который придётся сопровождать.** Не вызывается ниоткуда: `chat_service.create_attachment` (`:446-472`, причём именно в ней живёт проверка `size_bytes <= 0`, которой нет в реальном пути загрузки), `_known_chat_kinds` (`:552`), `delete_object` и `ChatStorageUnavailable` в хранилище. Колонка `deleted_at` (`models/chat.py:197-199`) не пишется никем — это ровно «сущность с жизненным циклом, которой пока нет». Форм-поле `is_image` (`chat_routes.py:571`) принимается и молча игнорируется: решение принимает `detected_image` (`:582`), а тест `:798-804` фиксирует это как норму — значит поле нужно убрать, а не оставлять вводящим в заблуждение. Строка `chat_routes.py:681` намеренно гасит неиспользуемые импорты. Комментарий `ExtraChatCreateDialog.tsx:6-7` ссылается на `GET /auth/staff-accounts`, а код зовёт `participant-options`.

Отдельно, не как дефект, а как решение, которое стоит проговорить владельцу: `chat_routes.py:255-257` подставляет в подпись автора его e-mail, то есть селлер видит почтовые адреса сотрудников склада.

## Что проверить не смог и чего в пакете нет

Проверка была чисто статической: тесты не запускались, браузер не открывался, ни одного утверждения о поведении в рантайме здесь нет. Вывод относится к присланным хэшам, а не к будущему HEAD.

По бэкенду не хватает: **миграции Alembic** на `chat_conversations` / `chat_participants` / `chat_messages` / `chat_attachments` вместе с частичным уникальным индексом `uq_chat_conversations_main` — без неё вся идемпотентность основного чата держится ни на чём, потому что индекс единственный, кто её обеспечивает; **подключения роутера** (`app/main.py` или где собираются роутеры) — по пакету нельзя сказать, что эндпоинты вообще существуют; `app/api/deps.py` (`get_effective_seller_id`, `require_ff_or_seller`, `require_fulfillment_admin`), `app/core/roles.py` (состав `FF_PORTAL_ROLES`), `app/models/user.py` (существование `user.seller_id`, на которое опирается `_eligible_participant` в `chat_routes.py:684`), оба сервиса прав, `object_storage_service.py`, `app/db/session.py` (уровень изоляции и `expire_on_commit` — от второго зависит, не упадут ли `chat_routes.py:437` и `:629`, где атрибуты читаются сразу после `commit()` без `refresh`), `tests/conftest.py` (на какой СУБД идут тесты) и файл зависимостей с версией PyMuPDF. Последнее важно: `chat_routes.py:596-603` вызывает `fitz.open(stream=raw)` без `filetype` и сверяет `metadata["format"]` с точной строкой `"Image"`, перехватывая только `RuntimeError`/`ValueError`. Подтвердить или опровергнуть, что эта связка пропускает нормальный PNG, по пакету невозможно; надёжнее передавать `filetype` из уже вычисленных magic-байтов и не завязываться на литерал в метаданных.

По фронтенду не хватает: `frontend/src/components/chat/chatApi.ts` — там `makeClientMessageId` (от его уникальности зависит вся защита от дублей), `ChatApiError`, `sendMessage`, `uploadAttachment`, `ensureMainChat`; `frontend/src/api.ts`; и главное — правок `App.tsx` / `SellerApp.tsx`, регистрирующих маршруты `/chat` и `/chat/documents/:kind/:documentId`, а также монтирования `ChatOpenButton`/`ChatDocumentAction` в четыре документа (заказ, отгрузка, FBS, приёмка) — прямое требование владельца. В пакете есть только сами компоненты; ни одного места их использования нет, поэтому «компактная форма во всех четырёх документах» статически не подтверждается. Не подтверждаются и целевые экраны из `ChatDocumentScreen.tsx:48-52` — нужно доказательство, что `/app/ff/fbs`, `/app/ff/reception`, `/app/ff/supplies-shipments`, `/app/ff/mp-shipments` понимают параметры `supply_id`, `open`, `open_outbound`, `open_mp`. Полная UI-приёмка чата, как и оговорено в задании, — отдельно и руками.

Остальные критерии задания к этому пакету не относятся и я их не оцениваю: кода про квоту остатка (`min(cap, free)`), про блокировку вкладок FBS, про автодокумент возврата и про мобильное обновление (подпись APK, проверка скачанного файла, канал обновления) в присланных файлах нет ни строки. По чату могу утвердительно сказать только одно смежное: он не может ничего оприходовать или списать — весь доступ к документам идёт через `chat_document_service.py`, где нет ни одной операции записи.
