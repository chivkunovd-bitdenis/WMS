# Ревью пакета WMS-417 (Opus 5, независимая сессия) — WMS-363 / 401 / 402 / 412

## Краткий вердикт

Пакет проверен статически, по тем хешам, что в нём указаны. Итог такой: **мобильная часть WMS-401 в этом срезе ушла вперёд замороженного канона** (сортировка и порядок разделов первого экрана уже исправлены — см. ниже), **но появились новые дефекты в бэкенде Ozon-путей и в мобильном обработчике ошибок передачи**, а WMS-363 в текущем виде даёт только фильтр по маркетплейсу — сквозного Ozon-процесса на ТСД нет и он физически не может быть выполнен доступными клиенту эндпоинтами. WMS-402 в пакете отсутствует полностью (есть только системный диалог печати Android, что соответствует статусу «есть только контракт»). WMS-412 в пределах пакета выглядит целостно; единственный существенный риск — подпись релизной сборки, а `build.gradle.kts` в пакет не включён.

Ни одного runtime-утверждения ниже нет: инструменты отключены, тесты не гонялись, экран не открывался, физический ТСД не трогался.

## 1. Доказанные дефекты, по приоритету

### 1.1 КИЗ: любая доменная ошибка привязки кода превращается в 500 (новое, критично для оператора)

`wms363-ozon-tsd/backend/app/api/fbs_kiz.py:195–217` — обработчик `commit_fbs_order_kiz` вызывает `kiz_svc.commit_kiz_pairs(...)` **без `try/except kiz_svc.FbsKizError`**, тогда как три соседних обработчика в этом же файле (`lookup` — 162–171, `validate` — 180–189, `delete` — 226–235) оборачивают вызов и зовут `_raise_from_service`.

Почему это точно ошибка, а не стилевая мелочь: таблица маппинга `_raise_from_service` (`fbs_kiz.py:79–109`) содержит коды, которые **может породить только commit** — `needs_confirmation` (строка 98) и `meta_validation_fail` (99). У `lookup` «нужно подтверждение» возвращается полем ответа (`FbsKizLookupOut.needs_confirmation`, строка 41), а не исключением; `validate` возвращает `ok/hints`. То есть таблица писалась под commit-путь, а commit-путь её не использует. Туда же уходят `duplicate_kiz`, `cross_seller_code`, `missing_marketplace_token` и всё семейство `wb_*`/`ozon_*` (строка 107), которое обязано отдаваться как 502.

Сценарий: оператор на ТСД сканирует ЧЗ, уже привязанный к другому заказу этой же поставки → сервис поднимает `FbsKizError("duplicate_kiz")` → FastAPI отдаёт **500** вместо 409. Мобильный клиент проходит через `required { ... }` → `readableError()` (`FbsViewModel.kt:105–109`) и показывает общий текст вместо «код уже привязан». Оператор жмёт «Повторить» (`FbsScreens.kt:38`), получает тот же 500 и остаётся заперт на упаковке.

Минимальная правка — обернуть тело так же, как в `validate_fbs_order_kiz`:

```python
    async with httpx.AsyncClient() as http_client:
        try:
            rows = await kiz_svc.commit_kiz_pairs(...)
        except kiz_svc.FbsKizError as exc:
            _raise_from_service(exc)
```

Отдельно, но в том же обработчике: `commit_fbs_order_kiz` и `delete_fbs_order_kiz` **не делают `session.commit()`**. Коммитит ли сам сервис — по пакету не видно, нужен `backend/app/services/fbs_kiz_service.py` (см. раздел 4).

### 1.2 Ozon-ветки синхронизации не коммитят транзакцию (новое)

`wms363-ozon-tsd/backend/app/api/fbs_orders.py:683–694` — Ozon-ветка `sync_fbs_order_statuses` возвращает `statuses_updated=ozon_updated` и уходит из функции без коммита. WB-ветка **того же самого обработчика**, работающая с той же сессией и делающая ту же по смыслу работу, коммитит явно на строке 706. Одна из двух веток заведомо неправа — это доказывается внутри пакета, без сторонних файлов.

Тот же разрыв в `start_fbs_orders_sync`: `fbs_orders.py:495–506` — `await sync_ozon_orders(...)` и сразу `return FbsOrderSyncOut(id="", status="done")`, коммита нет.

Конвенция файла `fbs_supplies.py` подтверждает направление: там `await session.commit()` стоит после **каждой** мутации (1082, 1164, 1185, 1321, 1365, 1398, 1460, 1484, 1507, 1573, 1629, 1657, 1685, 1713, 1732, 1785, 2056, 2092, 2280, 2307, 2370 и т.д.). Если бы `get_db` коммитил сам, все эти строки были бы лишними.

Сценарий, попадающий ровно в WMS-363: `POST /operations/fbs-orders/sync` с `marketplace="ozon"` для селлера с активным Ozon-аккаунтом и включённым live-транспортом → ответ `{"id":"","status":"done"}` → повторный `GET /operations/fbs-orders?marketplace=ozon` пуст. Ozon-заказы «синхронизируются» и исчезают. Второй сценарий: `sync-statuses` рапортует `statuses_updated: 3`, а статусы в базе прежние — то самое «число без источника», против которого написано второе главное правило.

Минимальная правка: `await session.commit()` перед `return` на строках 506 и 694.

### 1.3 Мобильный клиент выбрасывает idempotency-ключ передачи там, где сервер уже что-то записал (новое)

`wms397-mobile/.../core/api/fbs/FbsDelivery.kt:16` объявляет «неопределённым» только три кода:

```kotlin
val pending = code in setOf("wb_timeout", "wb_pending_confirmation", "operation_in_progress")
...
throw FbsDeliveryError(message, pending || code == null || code() in setOf(401, 403))
```

То есть `keepRequest = false` по умолчанию для **любого** прочего кода. А `FbsViewModel.kt:225–229` на `keepRequest == false` стирает сохранённый на диске запрос (`api.saveFbsDelivery(supplyId, null)`) и переводит экран в «нужен новый preflight», после чего `confirmDelivery` (строка 209) генерирует **новый** `UUID` в качестве ключа идемпотентности.

Проблема доказывается бэкендом из этого же пакета: `fbs_supplies.py:2303–2306` явно коммитит состояние при `meta_validation_fail` наравне с `wb_timeout`/`wb_pending_confirmation`. Значит, при `meta_validation_fail` сервер уже что-то записал, а клиент в этот момент теряет ключ. В список кодов, для которых `exc.http_status` пробрасывается как есть (`fbs_supplies.py:871–888`), входит и `fbs_shipment_checkpoint_incomplete` — по названию это ровно состояние «результат вызова WB не дописан», и оно тоже попадает в `keepRequest = false`.

Правка минимальная и в одну строку — инвертировать умолчание: держать запрос всегда, кроме явного белого списка «сервер точно ничего не сделал» (`stale_preflight` и валидационные 4xx до вызова WB):

```kotlin
val discardable = code in setOf("stale_preflight")   // сервер до WB не дошёл
throw FbsDeliveryError(message, !discardable)
```

Насколько далеко это заходит — второй вызов WB `deliver` или нет — по пакету не проверяемо: нужен `backend/app/services/fbs_shipment_service.py`.

### 1.4 Ozon-процесс на ТСД физически не собирается из доступных клиенту эндпоинтов (новое, прямо по WMS-363)

Список методов в `wms397-mobile/.../core/api/fbs/FbsApi.kt:14–108` полный, и в нём **нет** ни `…/boxes/{box_id}/retry-qr`, ни `…/cargo-places`, ни `…/boxes-without-distribution`, ни удаления/очистки короба. При этом единственная точка входа в Ozon-сборку короба на бэкенде — именно `retry-qr`: `fbs_supplies.py:1741–1786`, где при `supply.marketplace == "ozon"` вызывается `ozon_assembly_svc.assemble_box_order(...)` и затем печатный ассет `kind="order_sticker"`. С ТСД её вызвать нечем.

Дальше цепочка обрывается ещё в трёх местах:

* `FbsScreens.kt:136` — весь блок передачи (`Передать поставку в WB` / `Обновить статус WB`) закрыт условием `ws.supply.marketplace == "wb"`. У Ozon-поставки на ТСД нет финального действия вообще.
* `FbsViewModel.kt:463–467` — `printBoxes` требует `box.qrAsset`, иначе бросает «WB ещё не вернул QR для короба». Для Ozon короб QR не получает (см. выше — ассет вешается на заказ).
* `FbsModels.kt:201` — `AssignOrdersBody` умеет только `order_ids`. Бэкенд же принимает `order_product_ids` (`fbs_supplies.py:526–528`) и имеет отдельные отказы `ozon_order_positions_required`, `ozon_box_distribution_required`, `ozon_box_multiple_orders` (841–858). Многопозиционный Ozon-заказ с ТСД в короб не разложить — клиент не умеет выразить нужное тело. Плюс `setBoxQuantity` (`FbsViewModel.kt:395`) шлёт в один короб сразу несколько `order_ids`, что для Ozon упирается в `ozon_box_multiple_orders` (409).
* `FbsModels.kt:123–131` — `FbsBox` не читает `ozon_assembled`, который бэкенд отдаёт (`fbs_supplies.py:541`), так что состояние сборки оператору не показать даже справочно.

Отдельно: `oldestMatchingOrder` (`FbsViewModel.kt:22–25`) сопоставляет скан только с `product.barcode/sku/sellerArticle` и игнорирует `positions[]` (модель есть, `FbsModels.kt:109–116`). Для многопозиционного заказа скан второй позиции даёт `order = null`, и запрос уходит без `order_id`/`product_id` — то есть выбор заказа молча отдаётся серверу вместо явного «старейший подходящий», как это заявлено для WB.

### 1.5 Слой API подставляет второе значение «доступно» (новое, нарушение правила «одно число — один источник»)

`wms363-ozon-tsd/backend/app/api/fbs_supplies.py:1269–1270`:

```python
available=(source.available
           if source.available is not None else source.quantity),
```

Когда сервис подбора не смог посчитать доступность, маршрут подставляет **валовое количество в таре**. Это число доходит до оператора без изменений: `FbsViewModel.kt:47` фильтрует источники по `it.available >= 1`, а `FbsScreens.kt:251` печатает «доступно N». Резерв при таком fallback не учтён, и оператору предлагается тара, в которой свободного товара может не быть. Исполнение по-прежнему на сервере, так что списания «мимо резерва» отсюда не следует, но это ровно второй расчёт одной величины на лишнем слое. Минимальная правка — не выдумывать число: либо поднять расчёт в сервис и сделать поле `int`, либо отдавать `available=None` и не показывать источник как выбираемый. Когда именно `source.available is None`, по пакету не видно — нужен `backend/app/services/fbs_picking_service.py`.

### 1.6 Разъезд правил доступа между заказами и поставками (новое; окончательный вывод требует `deps.py`)

Внутри пакета доказуемо следующее. Обработчики заказов используют зависимость `get_effective_seller_id` и проверяют tenant у переданного `seller_id`: `fbs_orders.py:201, 210–214` (отменённые после упаковки), `527, 536–540` (worklist), `590, 599–606` (список). Обработчики поставок в `fbs_supplies.py` не делают **ни того, ни другого**: `get_fbs_supplies_worklist` (1216–1238) принимает `seller_id` и передаёт его в сервис без проверки принадлежности к тенанту и без сужения по эффективному селлеру; `get_fbs_supply_workspace` (1537–1549) скоупится только по `tenant_id`, хотя отдаёт те же заказы внутри `FbsWorkspaceOut.orders`.

Второе, тоже видное по коду: во всех трёх местах приоритет инвертирован — `filter_seller = seller_id if seller_id is not None else effective_seller_id`. Параметр запроса перебивает вычисленное сервером значение. Если `get_effective_seller_id` — это ограничение (а имя и способ применения говорят именно об этом), то ограничение снимается передачей `?seller_id=<чужой>`.

Правку писать до чтения `backend/app/api/deps.py` нельзя: если `require_fbs_operator_access` пускает только сотрудников ФФ, это не утечка, а лишь несогласованность. Если пускает пользователей портала селлера — это межселлерная утечка на четырёх эндпоинтах. Файла в пакете нет; это первое, что надо открыть.

### 1.7 Повтор скана короба показывает ошибку по успешной операции (новое, мелко, но чинится одной строкой)

`FbsViewModel.kt:364–379` (`scanBox`) в отличие от соседнего `setBoxQuantity` (строки 380–383, где стоит и комментарий, и `refresh(supplyId)`) не перечитывает воркспейс. Сценарий: сеть теряет ответ `assignOrders` → `perform` кладёт весь `scanBox` в `retryAction` → оператор жмёт «Повторить» → локальный `assigned` по-прежнему не содержит заказ → повторный `assignOrders` → 409 `order_already_in_box` (`fbs_supplies.py:836–842`). Оператор видит ошибку по операции, которая прошла. Правка: `refresh(supplyId)` первой строкой `scanBox`.

### 1.8 Повтор печати ленты ЧЗ переспрашивает сервер заново

`FbsViewModel.kt:415–441`: на любой частичной неудаче код обнуляет `tape = null` и бросает ошибку, а `retryAction` — это весь блок целиком. Повтор снова дёргает `order-print-tape`. Тело (`FbsModels.kt:315–320`) не несёт ключа идемпотентности, `reprint = false`; серверное тело (`fbs_supplies.py:322–328`) — тоже без ключа. Тратит ли повтор коды из пула — по пакету не определить, нужен `backend/app/services/fbs_order_tape_print_service.py`. Это единственное место в мобильном FBS, где повтор заведомо порождает новый серверный вызов вместо переиспользования результата.

### 1.9 Мелочи, подтверждённые кодом

* `FbsViewModel.kt:370` и `393`, `FbsScreens.kt:211` — «старейший» считается лексикографическим сравнением строки `createdAt`, хотя рядом, на `FbsViewModel.kt:22–34`, есть корректный компаратор через `Instant` с добиванием по `wbOrderId`. Правка — переиспользовать его.
* `FbsScreens.kt:101` — `isDeadlineNear(order.deadlineAt)` берёт `Instant.now()` в момент композиции; карточка, у которой срок подошёл при открытом экране, покраснеет только при следующей рекомпозиции по другой причине.

* `UpdateViewModel.kt:26` — `check()` делает `mutableState.value = UpdateState(busy = true)`, затирая уже скачанный `file`. Повторная проверка обновления заставляет оператора снова нажимать «Скачать» (файл на диске переиспользуется в `UpdateRepository.kt:122–124`, так что сеть не тратится, но шаг лишний).

## 2. Что уже было известно и подтверждается пакетом

* **WMS-402** — в пакете нет ни модели агента, ни очереди, ни клиента: единственный печатный путь — `FbsPrinting.kt`, то есть системный диалог Android `PrintManager` с медиаразмером 58×40 мм (2283×1575 mils — пересчёт верный). Статус «НЕ СДЕЛАНО · ЕСТЬ ТОЛЬКО КОНТРАКТ» подтверждается.
* **WMS-412** — цепочка проверок в коде целостная: `AppUpdate.validate` (https, отсутствие логина/пароля в URL, размер, SHA-256), `saveApk` пишет в `.part` и переименовывает только после совпадения размера и хеша, `verifyIdentity` сверяет пакет, versionCode, minSdk и набор подписантов, `UpdateFileProvider` не экспортирован (`AndroidManifest.xml:23–29`). `latest()` форсирует сеть (`CacheControl.FORCE_NETWORK` плюс cache-busting параметр, `UpdateRepository.kt:108–109`). Это статическое подтверждение формы, а не канала — канал не проверялся.
* **WMS-363** в части бэкенда — фильтр `marketplace` действительно есть на `GET /operations/fbs-orders` (`fbs_orders.py:595`), `…/worklist` (529) и `fbs-supplies/worklist` (1221), и `_order_out` (434–470) действительно проставляет значение из `FbsOrder.marketplace`.

## 3. Что в пакете расходится с замороженным каноном (проверять заново, а не переписывать)

Канон WMS-401 от 09.09 фиксирует два открытых пункта, которых **в этом срезе кода уже нет**:

* «активные поставки стоят выше списка заказов» — в `FbsScreens.kt:71–83` порядок обратный: заголовок «Все заказы» и сами заказы идут первыми (72–73), «Поставки в работе» — после (80–81);
* «полная сортировка списка по старшинству не доказана» — `sortedOrders` объявлена в `FbsViewModel.kt:32–34` с явной ссылкой на WMS-401 и применена на первом экране (`FbsScreens.kt:73`).

Это статическое наблюдение по хешам пакета (`FbsScreens.kt` SHA256 `7c78ff…`, `FbsViewModel.kt` SHA256 `ec4b19…`, BASE_HEAD `b90d20ab`), а канон ссылается на mobile-коммит `364e8ae`. Статус в бэклоге переписывать по одному этому нельзя — нужен прогон на устройстве; но и повторять формулировку «отклонение существует в текущем коде» уже нельзя: для этих хешей она неверна.

## 4. Границы проверки и чего в пакете нет

Инструменты отключены; тесты, сборка, эмулятор и браузер не запускались; выводы относятся строго к перечисленным хешам, а часть файлов, как предупреждено, параллельно правится.

Критерии из задания, по которым **в пакете нет кода для проверки** — называю поимённо, чтобы не выдавать отсутствие находок за их отсутствие:

* **Чат селлера** (основной чат на селлера, участники и права, вложения, редактирование, «точный документ», вставка изображения по Ctrl+V) — в пакете **нет ни одного файла чата**. Нужны `backend/app/models/chat*.py`, `backend/app/api/chat*.py`, `backend/app/services/chat*.py` и фронтовые экраны `frontend/src/**/Chat*`. Полная UI-приёмка — отдельно и руками.
* **Автодокумент возврата не приходует физически** — нет ни `backend/app/services/fbs_cancellation_service.py`, ни `fbs_cancelled_after_pack_service.py`, ни сервиса, создающего сам документ возврата. В пакете видны только их импорты (`fbs_orders.py:28–33`) и схемы ответа.
* **Целостность остатков, `min(cap, free)`, отсутствие вторых счётчиков** — сервисный слой отсутствует целиком: `fbs_picking_service.py`, `fbs_shipment_service.py` (в т.ч. цитируемые в WMS-401 строки 1681–1730), `fbs_packing_box_service.py`, `fbs_supply_service.py`, `fbs_workspace_service.py`, `fbs_order_tape_print_service.py`, `fbs_kiz_service.py`, `ozon_box_assembly_service.py`, `wb_marketplace_orders_service.py`, `ozon_fbs_sync_service.py`.
* **Доступ и tenant/seller** — `backend/app/api/deps.py` (тела `require_fbs_operator_access` и `get_effective_seller_id`) и `backend/app/db/session.py` (`get_db`: коммитит ли он сам). Без них пункты 1.2 и 1.6 остаются доказанными как внутренняя несогласованность, но не как окончательный вердикт о потере данных/утечке.
* **Достижимость Ozon-маршрута на ТСД** — `Navigation.kt:67–78` объявляет `composable("fbs")`, но переход идёт через `section.route` из `HomeSection`, а `android/.../features/home/HomeScreen.kt` в пакет не включён. То есть даже наличие кода экрана не доказывает, что оператор до него дойдёт — это ровно то, на чём стоял вердикт WMS-363.
* **`marketplace` в worklist-ответе** — `FbsWorklistOrderOut.marketplace` (`fbs_orders.py:357`) имеет умолчание `"wb"`, а заполняет его `fbs_worklist_service.fetch_worklist_page`, которого в пакете нет. При этом `backend/tests/test_wms363_ozon_tsd.py` покрывает `/operations/fbs-orders` и `/operations/fbs-supplies/worklist`, но **не** `/operations/fbs-orders/worklist` — именно тот эндпоинт, который зовёт ТСД (`FbsApi.kt:18`). Если сервис не кладёт ключ, Ozon-строки молча приедут как `"wb"`, и ни один тест этого не заметит.
* **WMS-412, подпись релиза** — `android/app/build.gradle.kts` в пакет не включён. `verifyIdentity` (`UpdateRepository.kt:48`) требует совпадения набора подписантов установленного APK и скачанного; если опубликованная релизная сборка подписана не тем ключом, что стоит на ATOL, обновление будет отвергнуто и приложением, и системой. Проверять до публикации следующей версии.
