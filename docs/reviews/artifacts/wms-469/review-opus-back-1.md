## Находки

### Б1 · БЛОКЕР. Частичное сохранение ломает правило нетронутой legacy-привязки

**Где:** `backend/app/services/fbs_stock_rule_service.py:972–988` (запись product-level полей в ветке `by_binding`) в сочетании с `:341–380` (`_binding_rule_from_state`, чтение legacy-строки через поля Product) и `:430–462` (`_binding_has_rule`).

**Что не так.** В ветке `by_binding` после записи пулов только по привязкам из запроса код безусловно переписывает поля товара:

```python
product.fbs_units_mode = any(item.publish and item.mode == "units" for item in combined.values())
product.fbs_same_everywhere = False
product.fbs_percent = 0
```

Но привязка, которой в запросе не было и у которой строка пула старая (`publish_enabled IS NULL`) либо строки нет вовсе, по‑прежнему читается через эти же поля (`_binding_rule_from_state`, ветка `pool is None or pool.publish_enabled is None`). После первого частичного сохранения её правило меняется без участия оператора.

**Чем подтверждено** (проба 1 и 2, SQLite и PostgreSQL, одинаково):

- Проба 1: товар с legacy `same_everywhere=True, fbs_percent=50`, привязки WB и Ozon, свободно 50. До сохранения Ozon: `percent 50, published_now 25`, `publish_amounts_for_binding(ozon) == {p: 25}`. Сохраняю **только WB** `{publish: true, mode: units, value: 10}`. После: Ozon → `publish=True, mode='units', value=0, published_now=0`, `publish_amounts_for_binding(ozon) == {}` — Ozon больше не обновляется, в кабинете остаётся прежнее положительное число; поля товара стали `same_everywhere=False, percent=0, units_mode=True`.
- Проба 2: legacy пулы по складам `percent=40` у WB и у Ozon (`publish_enabled NULL`). Сохраняю только WB как штуки 10. После: Ozon → `units, 0, publish=True`, `publish_amounts_for_binding(ozon) == {p: 0}` — **явный ноль в Ozon** (Ozon шлёт ноль каждый цикл, следа подтверждения у него нет — см. WMS-376), хотя строка пула Ozon в базе не тронута `(40, 0, None)`.
- Проба 5 (явные строки WMS-469 у обеих привязок, затем частичное сохранение) — проходит: ломаются только legacy-строки, то есть **все строки на бою в момент выкатки**.

**Почему это достижимо на бою.** Окно шлёт не все привязки: `frontend/src/screens/ff/products-fbs/fbsStockBlocks.ts:340` — `if (!binding.served) continue` (R7: строка скрыта), плюс скрытые по WMS-468 и Ozon-блок у WB-only товара. У Горячкиной, Loviana, Заколюкина, Манкаева, Фэшн на бою есть такие «лишние» привязки (WMS-468). Также всегда частичен путь `set_binding_stock_pool_quantity` (`_binding_quantity`).

**Что ожидается.** Контракт §4: «`by_binding` можно передать частично: отсутствующая соседняя привязка не меняется». R7: «сохранённый лимит и состояние публикации не меняются… при повторном включении строка возвращается с прежней настройкой». R8, R24, B08 («ползунок WB изменяет публикацию Ozon»), B10, WMS-376 («ноль — только на переходе», «не зануляй карточки, которыми не управлял»). Направление исправления, не навязывая: при сохранении `by_binding` материализовать явные строки (`publish_enabled`, режим, значение из `old_rules`, т.е. из `combined`) для **всех** привязок товара, а не только пришедших, и лишь потом менять поля Product — либо не трогать поля Product при частичном запросе. Тест на частичное сохранение поверх legacy-состояния (same_everywhere и by_warehouse) обязателен.

### Б2 · БЛОКЕР. Событийная публикация: бесконечный цикл на занятой блокировке, без склейки, три полных прогона на любую ошибку

**Где:** `backend/app/services/fbs_stock_publish_service.py:85–158` (`publish_target`), в частности `:100` (`wait_timeout_sec=1`), `:103–109` (`if not acquired: … continue` без счётчика и без предела), `:122–147` (повтор при `except Exception` и при `errors or binding_errors`), `:37–38` (3 попытки, пауза 1 с).

**Что не так.**
1. Ветка «блокировка занята» не считает попытки и не спит сама: `continue` → новая итерация `while True`. `marketplace_seller_lock` (`marketplace_seller_lock_service.py:57–71`) ждёт 1 с и возвращает False — и так до бесконечности, пока замок не освободится. Раньше было: ждать 30 с и уйти («deferred»), страховкой оставалась сверка раз в 300 с.
2. Склейки событий нет: каждое событие (резерв заказа, движение, направление) порождает свою задачу; все они одновременно крутятся, а когда замок освобождается — **каждая** делает полный прогон по продавцу. При Celery (на бою есть worker и beat) это ещё и занятые слоты воркера на всё время удержания замка. B01 показывает, что замок продавца удерживается фоновым обменом минутами.
3. Повтор не отличает временную ошибку от постоянной: `result.errors` включает конфликты chrt и заблокированные цели (`fbs_stock_sync_service.py:711`: `result.errors = errors + result.conflicts + blocked_error_count`), `binding_errors` — любой `error_code` привязки (404 удалённого склада WB, 401 отозванного ключа, `product_mapping_missing` у Ozon). Для продавцов с известными постоянными проблемами (Чжоу/Комаров/Беляев — 401 withdrawn; Фэшн 1865709 — 404; см. WMS-457) каждое складское событие теперь даёт **три** полных прогона вместо одного. Бэкофф 429 из автоопроса (`_MARKETPLACE_BACKOFF`) здесь не применяется — при 429 три удара подряд с паузой 1 с.

**Чем подтверждено** (пробы 6–8):
- Проба 6: замок всегда занят → `publish_seller_stocks_now` не завершился за 0,5 с, 2214 попыток взять замок (в пробе замок без задержки; на бою — 4 запроса `pg_try_advisory_lock` в секунду на каждую висящую задачу).
- Проба 7: 5 событий встали в очередь на занятом замке; после освобождения — **5** полных публикаций.
- Проба 8: `sync` возвращает `errors=1, binding_errors=1` (постоянная ошибка одной из трёх привязок) → **3** полных прогона за одно событие. То же фиксирует подправленный старый тест `test_marketplace_foundation.py:163–164` (`calls.count("ozon") == 3`).

**Что ожидается.** R21: попытка не теряется из‑за занятого замка и повторяется без ожидания полной сверки — но R20/D1 говорят о секундах, а не о неограниченном ожидании; «до трёх быстрых попыток» из контракта §6 должно ограничивать и ветку busy. Нужны: предел ожидания/повторов для busy, склейка (одно ожидание на пару продавец×площадка, а не по задаче на событие — например, пометка «нужна повторная публикация» на уже ждущей задаче), и повтор только для временных ошибок (сеть/5xx/таймаут/неполное подтверждение), а не для `conflicts`, `blocked`, 401/404/`product_mapping_missing`, с уважением бэкоффа 429. Новый журнал для этого не нужен.

### Д3 · Дефект. Транспорт привязки Ozon включается, когда публиковать нечего

**Где:** `fbs_stock_rule_service.py:990–992`:
```python
for binding_id, binding_rule in saved_rules.items():
    if binding_rule.publish:
        binding_by_id[binding_id].stock_sync_enabled = True
```
Берётся `saved_rules` (до применимости), а не `applied`. Проба 3: товар без карточки Ozon, привязка Ozon с `stock_sync_enabled=False`; сохраняю `ozon: {publish: true, percent 50}` → `product.fbs_ozon_stock_sync_enabled=False`, в ответе `publish=False, applicable=False` (правильно), но `binding.stock_sync_enabled` стал **True**. В цикле Ozon это даёт «nothing_to_publish» без вызова API (`ozon_fbs_sync_service.py:415–421`), поэтому не блокер; но это включение публикации по складу, которого оператор не просил (ср. комментарий про Фэшн 1865709 в legacy-ветке `:1129–1147`, где включают только по `product_rules` с уже применённой применимостью). Ожидается: включать транспорт только если после применимости хотя бы один товар публикуется по этой привязке (R3, R24).
