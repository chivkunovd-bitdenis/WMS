## Находки

### F1 — P2: отказ получения этикетки подменяется советом подождать минуту

**Место изменения:** `frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx:1919–1928`, прежде всего строка **1923**. Связанный существующий контракт: `backend/app/api/fbs_supplies.py:2022–2030`, `backend/app/services/fbs_print_asset_service.py:888–901`, `backend/app/services/fbs_workspace_service.py:601–619`.

**Сценарий.** Заказ успешно прошёл сборку либо уже собран. Во время следующего шага Ozon отклоняет запрос этикетки, например с ошибкой подключения/доступа. `request_supply_print_batch` ловит `MarketplaceProviderError`, сохраняет причину в `PrintBatchResult.order_errors` и возвращает результат, а не выбрасывает исключение. Существующий `retry-qr` этот результат игнорирует и возвращает обычный успешный HTTP-ответ со снимком поставки. В снимок коробов попадают только готовые печатные активы, поэтому конкретной ошибки в `qr_asset` тоже нет.

Новый цикл попадает в ветку `ready === false` и записывает для заказа «Этикетка Ozon ещё не готова — повторите получение через минуту». В итог попадает номер заказа, но причина Ozon/WMS теряется. Оператору советуют ждать даже при отказе, который ожиданием не исправить. Это нарушает R6 и часть C8 о выводе причины; продолжение остальных заказов при этом сохраняется.

**Подтверждение.** В отдельном локальном процессе с SQLite в памяти вызван настоящий обработчик `retry_fbs_packing_box_qr` и настоящий `request_supply_print_batch`. Только сборка заменена успешным ответом, а получение этикетки — `MarketplaceProviderError('ozon', 403, {}, code='ozon_account_blocked')`; внешних обращений не было. Перехваченный результат печати содержал `ozon_account_blocked` / «Ozon отклонил данные подключения.». Обработчик успешно вернул `FbsWorkspaceOut`; у обоих коробов `qr_asset = null`, текста причины в ответе не оказалось. Выбор общей фразы новым фронтом подтверждён строкой 1923, без браузерного воспроизведения.

**Исправление.** Донести `order_errors` существующего механизма печати до вызывающего кода и использовать конкретную причину для соответствующего заказа в итоговом сообщении. Общий совет подождать оставлять только для случая, когда этикетка действительно ещё не готова и более точной причины нет. Сохранить продолжение цикла, раскладку и прежнюю защиту сборки от повтора; изменение контракта проверить и для ручного `retry-qr` (R11). Одного чтения `box.qr_asset.error` на фронте недостаточно: текущий серверный снимок ошибки этого пути не содержит.

Добавить проверку именно сочетания «сборка успешна → этикетка отклонена → `retry-qr` возвращает результат»: итог называет причину отказа, следующий заказ обрабатывается, повтор не создаёт короба и не повторяет уже подтверждённую сборку. Нынешний тест форматирования `fbsOzonLabelFailuresText` эту потерю данных не обнаруживает.

### F2 — P3: «Создано коробов» считается относительно устаревшего экрана

**Место:** `frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx:1887`, **1911**, 1932.

**Сценарий.** Два оператора открыли поставку без коробов и почти одновременно нажали автоматическое создание. Первый серверный вызов создаёт N коробов. Второй после освобождения блокировки видит, что раскладывать уже нечего, и возвращает те же N коробов без создания новых. Но у второго оператора `boxIdsBefore` взят из прежнего локального снимка, поэтому его итог тоже сообщает «Создано коробов: N». Аналогично в счётчик могут попасть короба, которые другой оператор только что добавил вручную.

Это не дублирование коробов в базе: неверно число, приписанное конкретному нажатию. Сценарий выведен из кода двух ответов и формулы счётчика, а не воспроизведён двумя PostgreSQL-сессиями. Он затрагивает точность итога R6 в предусмотренном R8 сценарии двух операторов.

**Исправление.** Возвращать из атомарной серверной операции фактическое число/идентификаторы созданных именно ею коробов и использовать это значение в итоге. Новая таблица или журнал для этого не нужны. Проверка: две операции над одной поставкой возвращают соответственно N и 0; обе получают одинаковый конечный состав коробов. Простое обновление экрана непосредственно перед запросом не устраняет гонку.

## Что проверено

**Раскладка и транзакция.** Новая операция сначала блокирует строку поставки через `SELECT … FOR UPDATE`, затем выбирает ещё не назначенные позиции неотменённых заказов. Выборка ограничена клиентом и поставкой; новые номера продолжают текущий максимум. Для каждой позиции создаётся новый короб и вызывается существующее назначение позиции целиком. Порядок `deadline_at, order.id, position_index` держит новые позиции одного заказа рядом. Старые и пустые короба не переиспользуются и не удаляются.

В ветке Ozon у `create_boxes` и назначения позиций нет промежуточного `commit` и нет запросов в маркетплейс. Единственный commit новой операции находится в API после успешного завершения. При исключении управление выходит до commit; закрытие сессии откатывает транзакцию. Тест ошибки в середине подтверждает откат коробов и назначений внутри savepoint; он не является проверкой настоящего HTTP-обрыва или отдельной транзакции через API.

**Повторы и PostgreSQL по коду.** Два вызова автоматической раскладки должны последовательно брать один и тот же замок поставки и только после него читать набор свободных позиций. Этот же замок используют существующие создание и ручное назначение коробов. В SQLite реальное ожидание `FOR UPDATE` не проверяется, поэтому тест последовательного повтора не доказывает конкурентный сценарий C7. Ошибки в самом порядке блокировка → чтение → запись → commit при просмотре не найдено.

**Выбор этикеток и продолжение.** План фронта пропускает отменённые заказы, заказы без позиций, неполностью разложенные и уже имеющие готовую этикетку. Полностью разложенный вручную заказ без этикетки включается. На заказ выбирается один короб; отправляется существующий `retry-qr`, автоматического открытия печати нет. Ошибка одного запроса добавляется в итог и не прекращает обработку остальных. Новая синхронная ref-защита закрывает повторный вход в обработчик до перерисовки кнопки; поведение двойного клика в компоненте не тестировалось.

**Защита сборки.** Прочитан `ozon_box_assembly_service`: перед внешней сборкой сохраняется намерение `ozon_assembly`; повтор перечитывает отправление и при неопределённом результате не отправляет `/ship` заново. Пройдены существующие тесты повторов через разные короба и восстановления после ошибки провайдера. Они последовательные; одновременный вызов двух операторов не воспроизводят. Все короба одного заказа получают один общий печатный актив; существующие тесты подтверждают, что неполный набор этикеток разделённых отправлений не становится готовым PDF. Поэтому проверка `some(fbsOzonBoxLabelReady)` сама по себе не является найденным дефектом при нынешнем контракте.

**Соседние процессы и ограничения.** Тела `create_boxes`, ручного назначения, сборки/передачи, остатков и статусов diff не меняет; новых таблиц, миграций и режимов нет. WB отклоняется новой операцией, новая кнопка выводится только при `isOzonSupply`. На фронте изменено условие отключения «Добавить короба» на время автоматической операции; остальные действия коробов используют существующий `busy`. Новых условий по завершению подбора/упаковки нет. Проверены существующие серверные тесты WB-коробов, ручной раскладки Ozon и сборки.

**Дизайн по коду.** Кнопка находится в шапке существующего блока коробов, рядом с печатью и добавлением; используется существующий `Button` без залитого варианта и существующий ряд с переносом. Новых окон и экранов нет. Читаемость и отсутствие наложений на ширинах 1440/1024 без браузера не подтверждаю.
