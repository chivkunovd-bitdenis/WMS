## Находка

### T1 — P2: новые тесты не защищают от возврата остатка F5

**Место:** `backend/tests/test_ozon_box_assembly.py:876` — `clear_box` и `assign_orders` завершаются до вызова обработчика на строке 893; `backend/tests/test_ozon_box_assembly.py:928` — назначение B в пустой короб завершается до вызова обработчика на строке 942. **Сценарий и последствие.** Если вернуть предварительный resolver и обработчик из `26bee62b`, оба новых теста всё равно проходят: resolver сразу увидит B, поскольку все изменения короба уже закоммичены. Это подтверждено запуском, а не только чтением: в отдельном процессе функции `_resolve_ozon_box_order_id`, `retry_fbs_packing_box_qr` и `assemble_box_order` подставлены из `26bee62b` через AST без изменения файлов; тестовый импорт обработчика направлен на прежнюю функцию. **Исправление.** Оставить исходный A в коробе либо оставить новый короб пустым до начала `retry_fbs_packing_box_qr`. Именно такое чередование проверено отдельно в этом ревью: на `33a06814` оба варианта проходят, на `26bee62b` первый записывает причину A, второй теряет причину B. ## Что проверено и закрыто

**F5 — исправлен в коде.** В `backend/app/api/fbs_supplies.py:2054` обработчик сразу вызывает сборку, предварительного определения заказа больше нет. Сервис сначала блокирует поставку (`backend/app/services/ozon_box_assembly_service.py:172`), проверяет короб и читает его фактические позиции, затем блокирует и обновляет заказ с фильтрами клиента и поставки (строки 208–216). Обработчик исключений после этой проверки прикрепляет UUID заказа к исключению (строки 372–378). В API UUID извлекается до rollback (`fbs_supplies.py:2075`) и используется для записи причины после него (строки 2085–2089). Повторного определения заказа по коробу после rollback нет.

Дополнительное воспроизведение использовало настоящий обработчик, сервис сборки и операции с коробом; подставлялась только обёртка входа в сборку, которая вставляла действия другого оператора перед получением замка. Пользователь — настоящий прикреплённый к сессии `User`, результаты перечитаны новой сессией. Для A использованы две позиции в двух коробах, для B — одна свободная позиция той же поставки. Во втором варианте создан отдельный пустой короб.

| Чередование внутри выполняющегося запроса | `33a06814` | Прежние функции `26bee62b` — контроль воспроизведения |

| Короб A → `clear_box` + commit → `assign_orders(B)` + commit → настоящая сборка | 503 `ozon_live_handoff_blocked`; фактический заказ B; у A причины нет, у B причина есть | Тот же 503; фактический заказ B; причина записана A, у B её нет |

Это детерминированное воспроизведение допустимого чередования транзакций на SQLite, а не проверка реального ожидания `FOR UPDATE` на PostgreSQL.

**Причина «Обмен с Ozon выключен» сохраняется.** Проверка `ozon_live_api_enabled()` находится в `ozon_box_assembly_service.py:226`, после определения и блокировки заказа, внутри нового `try`. Она по-прежнему идёт после `order_packages`: если раскладка неполная, возвращается соответствующая прежняя ошибка раскладки. При корректной раскладке и отсутствии явно переданного тестового провайдера выключенный флаг даёт 503; catch прикрепляет заказ и API сохраняет точные код и текст. Обе дополнительные проверки смены состава подтвердили сохранённое у B значение:

```json
{"code":"ozon_live_handoff_blocked","message":"Обмен с Ozon выключен настройкой."}
```

**F3 и защита `ozon_assembly` сохранены.** UUID прикрепляется до rollback вызывающего обработчика. Отдельно проверен поздний отказ через retry-qr с настоящим `User` и тестовым провайдером: `/ship` отвечает 502 после сохранения намерения. **Порядок блокировок и F4 сохранены в просмотренном пути.** Сборка по-прежнему начинает с поставки, затем берёт заказ.
