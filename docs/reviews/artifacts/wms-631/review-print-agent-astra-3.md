## Дефекты

### P0

В выполненных проверках не выявлены. Необоснованного изменения штатных аргументов `lp`, параметров DEVMODE или штатной раскладки 58×40 не найдено. На исправных журналах повторная отправка проверенных старых ключей и ключа чистой новой установки не произошла.

### P1 / R3-01 — перенос прежней истории сохраняет хэш, несовместимый с обратным запуском

**Где:** `tools/print-agent/wms_print_direct_macos.swift:395`–`:411`, `:513`–`:516`; старый Python `1bdd6cdf:tools/print-agent/wms_print_direct.py:214`–`:223`; старый Swift `9a33b651:tools/print-agent/wms_print_direct_macos.swift:180`–`:192`.

При зеркалировании старого JSON код делает `INSERT ... [key, job.hash, job.receipt]`. Но `job.hash` от `9a33b651` — хэш PNG с `|58.0x40.0`, а Python ожидает хэш PNG с `|580x400`. Исправление на строке 466 выбирает правильный Python-хэш только для **новых** заданий. Возврат уже известной квитанции на строке 436 заканчивает обработку без нормализации перенесённой записи.

Воспроизведение на настоящих классах из указанных коммитов, с одинаковым PNG, ключом `k` и размером 58×40:

1. `9a33b651` сохранил в JSON квитанцию `old-mac-1` через подменённую отправку.
2. HEAD Swift открыл каталог, создал SQLite, перенёс JSON-запись и вернул `old-mac-1`; новых отправок 0.
3. Старый Python `1bdd6cdf` открыл тот же каталог и получил **«Содержимое этого задания изменилось»**, новых отправок 0. HEAD Python отвечает так же.

Есть и симметричный результат: запись, созданная старым Python и импортированная HEAD Swift в JSON, читается HEAD правильно, но `9a33b651` отвергает её из-за Python-хэша в JSON. Это одна проблема форматов истории, а не два независимых дефекта.

**Последствие:** ожидаемая старая квитанция не возвращается; неизменённое задание ошибочно объявляется изменённым. Дубля нет, поэтому это P1, а не прежний P0 о повторной печати. Новые задания HEAD Swift имеют правильные хэши в обоих журналах и этот сценарий проходят.

**Что требуется от исправления:** обеспечить согласованное представление идентичности для поддерживаемого обратного перехода и проверять его запуском настоящих старых читателей, включая импортированные записи. Как минимум, при подтверждённом совпадении известного запроса есть исходный PNG и размер для записи хэша соответствующего читателя. Из одного старого SHA-256 восстановить другой SHA-256 без исходных данных нельзя; простое копирование строки хэша полной совместимостью не является. Критерий проверки — именно возврат прежней квитанции, а не только отсутствие второй отправки.

### P1 / R3-02 — общий срок обходится ожиданием Python-lock до SQLite под блокировкой отмены

**Где:** `tools/print-agent/wms_print_direct.py:287`–`:297`, `:322`–`:331`, `:401`–`:405`; браузер прекращает ожидание через 30 секунд: `frontend/src/utils/printDirectQr.ts:11`.

`mark()` удерживает `gate["lock"]`, вычисляет оставшееся время и передаёт его в `_execute`. Но `_execute` сначала без срока ждёт `self.lock`; этот же lock другой запрос удерживает во время ожидания SQLite. После получения Python-lock SQLite всё ещё получает старую величину timeout, вычисленную до ожидания. В момент истечения 25 секунд основной поток пытается захватить `gate["lock"]` и сам блокируется, вместо того чтобы вовремя ответить браузеру.

Воспроизведение использовало неизменённые `PRINT_TIMEOUT=25`, `MINIMUM_TO_START=6`, настоящий `Printer`, настоящую SQLite и два запроса. Подменена только работа адаптера; печать в ОС не выполнялась:

1. Запрос A прошёл начальную проверку истории и остановился в подготовке до отметки отправки. Отдельная SQLite connection взяла `BEGIN EXCLUSIVE`.
2. На 17-й секунде запрос B с другим ключом вошёл в `_begin`, захватил `self.lock` и начал ждать SQLite до 10 секунд.
3. На 18-й секунде A продолжил подготовку, вошёл в `mark`, захватил `gate` и передал в `_execute` оставшиеся примерно 7 секунд; затем стал ждать `self.lock` за B.
4. B получил `database is locked` на общей отметке **27,421 с**. Только после этого A смог перейти к своей записи SQLite, используя уже устаревший timeout.
5. Внешняя блокировка SQLite снята на 32-й секунде. A записал и удалил отметку после проверки истёкшего срока; ответ A пришёл через **32,092 с**. Результат: `PrintNotSent`, новых отправок **0**, таблица `jobs` пустая.

**Последствие:** браузер успевает прервать ожидание раньше ответа программы, несмотря на заявленный общий срок. Исправление второго круга действительно запретило позднюю отправку; данный результат этого не опровергает. Дефект — оставшийся обход срока ответа при конкуренции за журнал, а не доказанный дубль или поздний вызов ОС.

**Что требуется от исправления:** включить ожидание `self.lock` в абсолютный deadline и заново вычислять остаток перед SQLite; путь отмены не должен безусловно ждать блокировку, удерживаемую операцией с просроченным бюджетом. После отказа до ОС сохранять доказанную неотправку и возможность повторить тот же ключ. Проверка только с одной заблокированной SQLite connection без конкурирующего HTTP-запроса этого случая не покрывает.
