## Новые дефекты

### P0

Не выделены. Подтверждённый условный дубль ниже классифицирован как P1: он требует сочетания восстановления после неотправки, ошибки записи служебного файла и потери результата следующей отправки.

### P1 / R5-01 — неудачное удаление сохранённого признака «не отправлено» разрешает дубль после перезапуска

**Где:** `tools/print-agent/wms_print_direct.py:318`–`:332`, `:446`–`:449`, `:297`–`:300`. Аналогичное подавление ошибки сохранения перед повторной отправкой присутствует в Swift: `tools/print-agent/wms_print_direct_macos.swift:382`–`:383`, `:505`–`:506`; отдельно на Swift этот сценарий не исполнялся.

`_unsent_remove` сначала удаляет ключ из памяти, затем пытается записать файл. Ошибка записи подавляется. `_unsent_take` всё равно сообщает успех; следующий `mark()` заменяет строку и допускает отправку в ОС. Если эта отправка имеет неизвестный результат, строка остаётся с `receipt=NULL`, а на диске всё ещё лежит **старое** доказательство неотправки. При перезапуске `__init__` считает его актуальным и удаляет строку, защищавшую уже отправленное задание. Следующий запрос повторно отправляет тот же ключ.

**Независимое воспроизведение на неизменённом Python-коде:**

1. Подмена отправки возвращает `PrintNotSent` после `mark()`. Только DELETE подменён ошибкой `sqlite3.OperationalError('database is locked')`. Настоящий файл `direct-unsent.txt` содержит `scan-1`, SQLite — строку без квитанции.
2. На время следующей попытки по пути `direct-unsent.tmp` создаётся каталог. Это реальная файловая ошибка записи временного файла; методы сохранения не подменяются. Подмена ОС считает отправку и бросает `UnknownPrintOutcome` — модель принятого ОС задания с потерянным ответом.
3. После ответа проверены обе записи: файл по-прежнему содержит `scan-1`, строка SQLite по-прежнему имеет `receipt=NULL`.
4. Препятствие записи убирается, создаётся новый `Printer`. Его инициализация удаляет строку. Повтор того же тела возвращает квитанцию `duplicate`.

**Результат: две отправки одного ключа.** Это новый дефект внесённого механизма, а не отсутствие физической проверки. Ошибка удаления признака неотправки должна препятствовать переходу к новой отправке либо признак должен быть надёжно связан с конкретной попыткой. Нельзя использовать устаревший признак для удаления защиты более поздней попытки.

Материал: `/private/tmp/wms631-astra5/duplicate.py`. Существенные шаги и результат приведены здесь, чтобы вывод не зависел от временного файла.

### P1 / R5-02 — Swift удаляет доказательство неотправки после очистки SQLite, оставляя незавершённую запись в JSON

**Где:** `tools/print-agent/wms_print_direct_macos.swift:388`–`:396`, `:362`–`:373`, `:436`–`:443`, `:564`, `:580`.

Это вывод по конкретному пути кода; успешное исполнение отдельного Swift-воспроизведения в этом круге **не заявляется**.

После доказанной неотправки `retractLocked` записывает `direct-unsent.json`, удаляет ключ из памяти и пытается очистить `direct-jobs.json`. Если именно последняя запись временно не проходит, прежняя запись без квитанции остаётся на диске. Из-за короткого вычисления `clean && …` удаление из SQLite тоже не выполняется. Таким образом, оба журнала содержат незавершённую запись, а отдельный файл правильно доказывает неотправку.

При следующем запуске JSON загружается в `jobs`. `importLegacy` находит тот же ключ в SQLite и `unsent`, успешно удаляет его **только из SQLite**, затем удаляет признак из `unsent` и сохраняет это удаление. Загруженная запись `jobs[key]` и JSON-файл при этом не очищаются. В `knownResult` условие освобождения на строке 564 уже ложно, поскольку признак стёрт. Повтор отвергается как неизвестный исход. Последующие перезапуски не помогают: JSON по-прежнему содержит запись, а доказательство неотправки потеряно.

**Последствие:** временная ошибка записи JSON превращается в постоянную блокировку доказанно неотправленного ключа. Признак нельзя удалять до подтверждённой очистки обоих журналов. Это отдельная проблема согласования двух журналов, не тот же механизм, что R5-01.
