## Проверка путей освобождения ключа

В Python есть единственный SQL DELETE — в `_retract`. Он вызывается либо внутри `mark`, когда бюджет закончился до возврата управления адаптеру (`:405–407`), либо при `PrintNotSent` (`:418–423`). В производственных адаптерах Windows подготовка изображения и страницы выполняется до `mark`, после которого начинается `StartDoc` (`:223–254`); ошибки после этой границы не превращаются в `PrintNotSent`. Mac вызывает `cupsPrintFile` после `mark` и при неподтверждённом результате оставляет неизвестный исход (`:82–94`). Завершение worker освобождает оперативный признак обработки, но сохраняет историю отправки. Очистка выполняется до освобождения этого признака, поэтому не остаётся отложенного DELETE, способного удалить отметку следующей попытки.

В Swift `retractLocked` вызывается при неудаче записи зеркала до отправки, исчерпании бюджета внутри `mark` и доказанной неотправке из адаптера. После успешного запуска процесса `run` не выдаёт `.notSent`: этот тип ошибки используется при отказе `Process.run()` запустить процесс (`:84–86`). Удаление `jobs[key]` при неудачной первоначальной записи JSON (`:486–488`) также происходит до ОС. Откат свежего импорта из SQLite (`:427–429`) сохраняет исходные строки в SQLite и оставляет импорт незавершённым: следующий запрос должен снова пройти его. Эти удаления не открывают повтор для уже отправленного задания. Между шагами очистки доказанно неотправленного задания перезапуск может оставить блокировку; это допустимый консервативный исход.

Сохранность истории — предпосылка этой защиты: удаление/утрата всех журналов, физический отказ носителя и поведение ранее выпущенной программы при откате на неё этим кругом не проверялись. Проверка текущего кода не является доказательством отсутствия дубля при уничтожении истории.
