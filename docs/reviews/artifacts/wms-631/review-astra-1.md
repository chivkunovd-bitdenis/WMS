## Дефекты

### P0-01. Возврат прежнего КИЗ падает после удаления нового; повтор не восстанавливает заказ

**Где:** `backend/app/services/fbs_kiz_service.py:1761–1780`, вызов удаления на `1752`.

K1 заменён K2. «Назад» удаляет K2 через `cancel_order_kiz`, который сам завершает транзакцию. Затем `rollback_scan_kiz` вызывает `session.rollback()` и читает `previous_code.id`. Rollback делает загруженный объект SQLAlchemy устаревшим; синхронный доступ к его полю пытается сходить в БД и падает с `MissingGreenlet`. **Воспроизведено** на настоящей SQLite-сессии: состояние «K2 уже снят, нужно восстановить K1» стабильно падает на строке 1764 до вызова восстановления. Первый проход оставляет заказ без КИЗ, повтор также падает. Аналогично нельзя оставлять чтение `replaced.id` после сброса транзакции.

**Минимальное исправление:** сохранить необходимые скалярные ID до rollback, перечитывать записи явно через await и восстановить весь переход, включая повтор после снятого K2. Одного переноса ID недостаточно: исправить также P0-02/03. Если прежняя маркировка не имела `marking_code_id`, событие замены сейчас вообще не записывается (`1557`); молчаливый успех с пустым КИЗ в `1758` не выполняет предусмотренное Д13 сообщение о необходимости заново отсканировать прежний код.

### P0-02. Возвращаемый КИЗ публикуется свободным до привязки; внешний код может сменить источник учёта

**Где:** `backend/app/services/fbs_kiz_service.py:1770–1780`; классификация — `1099–1105`, `1480`, `1580–1586`; получение кода — `backend/app/services/fbs_marking_service.py:599–647`.

Независимый дефект следующей стадии восстановления, который останется после исправления P0-01. K1 переводится из `void` в `available`, после чего выполняется commit, и только потом отдельный `commit_kiz_pairs` пытается занять его. Между транзакциями другой оператор/автопечать может забрать K1; исходный заказ уже без K2. Кроме того, возврат внешнего кода с `source=external_fbs` проходит через общий `_prepare_code_for_binding`: для обычного доступного кода без события приёмки/операторской отмены возвращается `from_pool=True`. Новая привязка получает `source=pool`, меняются счётчики печатной/внешней маркировки. Событие замены не сохраняет прежний источник привязки.

**Минимальное исправление:** держать возвращаемый код занятым за исходной операцией до завершения, не коммитить промежуточный `available`; восстанавливать прежний источник и состояние из точного события замены. Проверить отдельно прежний pool-код, внешний скан и код из приёмки. Конкурентный PostgreSQL-прогон не выполнялся; разрыв транзакций и ветвь классификации подтверждены кодом.

### P0-03. Между проверкой текущего КИЗ и его удалением теряется блокировка — можно удалить более новый код

**Где:** `backend/app/services/fbs_kiz_service.py:1748–1752`; вызываемый `cancel_order_kiz` — `1285–1288`.

Откат проверяет, что текущий код равен K2, удерживая блокировку маркировки. Затем `cancel_order_kiz` начинает с `session.rollback()`, отпускает эту блокировку и заново выбирает текущую маркировку. Другой запрос успевает заменить K2 на K3. Отмена удаляет уже K3, хотя проверка `kiz_rollback_changed` относилась к K2. Это удаление чужого более позднего действия. Поиск события только по значению нового кода, без ID исходной привязки/скана (`1738–1741`), также не различает повторные использования одного КИЗ в истории.

**Минимальное исправление:** передавать и проверять точный ID привязки/события скана; сравнение и удаление выполнять под одной блокировкой без внутреннего rollback между ними. При изменённой версии ничего не менять. Это вывод по коду, не натурная гонка с WB.

### P0-04. После потерянного ответа WB откат вслепую повторяет удаление

**Где:** новый вызов `backend/app/services/fbs_kiz_service.py:1752`; существующие `cancel_order_kiz:1310–1318`, `_delete_sgtin_from_wb:1134–1157`.

WB удалил SGTIN, но ответ потерялся. `_delete_sgtin_from_wb` только преобразует исключение; локальная транзакция отменяется, подтверждённой записи/проверки результата удаления нет. Повтор «Назад» опять делает DELETE. Если между попытками в WB появилась другая маркировка, DELETE по ключу `sgtin` удалит её. Комментарий нового rollback о соблюдении lost-response rules неверен для удаления: сверка, существующая у PUT привязки, сюда не подключена. Проблема старого примитива теперь является зависимостью нового R19/U8, где запрет слепого повтора указан явно.

**Минимальное исправление:** сохранять намерение удаления конкретной версии; после неоднозначного ответа читать фактическую мету WB и завершать тот же переход. Повторять внешнее удаление только после проверки результата. Изолированный транспортный сценарий в этом ревью не запускался.

### P0-05. После «Назад» новый скан ЧЗ использует уже отработавшие ключи печати и упаковки

**Где:** `frontend/src/screens/v2/fbsSequentialPacking.ts:275–284`, `42–43`, `570–606`; серверный повтор упаковки — `backend/app/services/packaging_task_service.py:985–1019`, `fbs_packaging_integration_service.py:637–682`.

M6 завершён: K1 и QR напечатаны, заказ упакован. U1 возвращает его в ожидание ЧЗ, сохраняя тот же `result.scan_id`. Оператор сканирует K2. Копия имеет прежний ключ `${scan_id}:copy`, а серверная цель `chz` уже `started`: новая этикетка K2 не печатается. На вещи остаётся K1, в заказе K2. Упаковка тоже идёт с прежним `${scan_id}:packed`; сервер прямо возвращает исторический результат, не применяя отменённую упаковку заново. **Воспроизведено** контроллером: до и после undo одинаковые `print:scan-1` и `pack:scan-1:packed`; серверная ветвь повторов прочитана.

После U1 очищенная при завершении запись localStorage не восстанавливается. Повтор ШК вместо ЧЗ создаёт новую попытку и попадает в проверку «Сервер вернул другой заказ» (`360–364`) либо конфликтует с сохранённым выбором. Это отдельная сторона того же несогласованного восстановления.

**Минимальное исправление:** развести неизменный ID выбора и новое намеренное действие после отката; новая привязка/копия и новая упаковка получают новую идентичность, а сетевой повтор каждого действия — прежнюю. QR, который уже напечатан и не требует копии, повторно не отправлять. Восстанавливать согласованную запись незавершённого выбора.

### P0-06. Esc и «Назад» не сериализованы со сканом и очередью

**Где:** `frontend/src/screens/v2/fbsSequentialPacking.ts:267–305`, `333–342`, `372–390`; `FbsPackingScanBar.tsx:26–35,38–49,59–74`; `FfFbsSupplyWorkspace.tsx:1918–1948`.

`selecting` защищает только первоначальный выбор. Во время bind, печати и упаковки он false; «Назад» в сборке доступна и вызывает undo отдельно от очереди `useScanIntake`. В самих `scan/scanOrder` нет защиты от `undoing`. **Воспроизведено:** остановить `deps.print`, нажать undo — в undo уходит шаг ещё с `packKey:null`; после отпускания print старый обработчик всё равно вызывает pack, очищает восстановленный pending, и заказ упакован уже после отката КИЗ.

**Воспроизведено также:** остановить bind, нажать Esc, затем дать bind завершиться. Выбор уже освобождён, КИЗ сохраняется, но печать/упаковка пропускаются, поскольку `finish()` видит `pending=null`. История появляется уже после отмены. На сервере `validate_bound_reprint_context` не проверяет событие отмены выбора. При Esc во время выбора с «Печатать ЧЗ» сервер может уже выделить КИЗ, а ветвь `400–406` освобождает только выбор и не сохраняет шаг для отката КИЗ. Очереди уже принятых кодов Esc тоже не пересогласует.

**Минимальное исправление:** один последовательный исполнитель сканов, отмены и undo; отмена в полёте должна дождаться известного результата и компенсировать именно его. Не ограничиваться disabled у кнопки: нужны серверная проверка отменённого поколения и защита продолжений после await.

### P0-07. История строится по полученным ответам и теряет реально сохранённые последствия при сбое

**Где:** `frontend/src/screens/v2/fbsSequentialPacking.ts:200–204`, `335–338`, `374–387`, `415–416`, `621–629`.

Три воспроизведённых контроллером случая:

- Commit КИЗ успешен, ответ потерян. Повтор того же КИЗ возвращает `newly_bound:false`; шаг получает `kiz:null`, и «Назад» код не снимает. Восстановление через ШК (`369–370`) вообще не создаёт шаг записи КИЗ.
- Pack выполнен, ответ потерян, либо упал последующий запрос добавления в короб. `packKey` заполняется только после полного возвращения `deps.pack`. «Назад» получает `packKey:null`, может удалить КИЗ, оставив заказ упакованным. При повторе explicit-скана уже обновлённый workspace считает заказ packed (`612`) и возвращается до исправления короба; потерянная привязка к коробу не восстанавливается.
- Пул был пуст; после пополнения повтор возвращает `printed_codes` и печатает ЧЗ. Обновляется `current.result`, но не `current.step.result/kiz`; в истории остаётся `kiz:null`. «Назад» распаковывает и освобождает заказ, оставляя КИЗ из пула привязанным.

**Минимальное исправление:** восстанавливать последствия по серверным квитанциям конкретного скана, фиксировать идентификаторы намерений до запросов; отдельно доводить упаковку и добавление в короб. Не выводить «этого действия не было» из отсутствующего ответа или `newly_bound:false` повтора. Все три вида восстановления должны входить в тесты R19.

### P0-08. Переоткрытие страницы теряет идентичность скана стикера и допускает повторную QR-этикетку

**Где:** `frontend/src/screens/v2/fbsSequentialPacking.ts:215–240`, `501–504`.

Стикер выбрал заказ; QR принята WMS Print, следующий ответ/шаг потерян, страница переоткрыта. `selectNew` сначала пробует стикер как товарный ШК, даже если localStorage уже содержит orderId/scanId этого стикера. Сервер ищет подходящий товар до возврата сохранённого события и отвечает `scan_product_not_found`. `deps.select` удаляет сохранённую попытку. Затем lookup стикера создаёт новый ключ и новый scan_id. Прежний QR-ключ больше не участвует в защите от дублей.

**Воспроизведено настоящими `makePackingScanDeps` + контроллером, с localStorage и HTTP-подменой:** `STICKER_REOPEN sameId:false`; повтор сначала отправляет старый ключ без order_id, затем новый ключ с order_id.

**Минимальное исправление:** при сохранённой попытке восстанавливать её точный способ выбора и order_id до товарного поиска; не удалять её на диагностической попытке другого способа поиска. Прогнать M3/M15/M17 с потерей ответа и переоткрытием.

### P0-09. Прямая копия ЧЗ не сохраняет ключ попытки между перезагрузками

**Где:** `frontend/src/screens/v2/fbsSequentialPacking.ts:437`, `510–533`.

M16/M18: программа приняла копию, ответ потерялся. Идентичность запроса `saveFbsDirectKizReprint` находится только в `directKeys` (Map в памяти). После перезагрузки того же кода создаётся новая запись перепечати, новый `row.id` и новый `kiz-copy:${row.id}`. Идемпотентность WMS Print не объединяет разные ключи — выйдет вторая копия. Обычный pending product scan это не спасает: код не используется как сохранённый ключ прямой копии.

**Минимальное исправление:** долговечно сохранять незавершённое намерение прямой копии на пользователя/поставку/код, подтверждать его завершение по прежнему ключу. Новую осознанную копию после успеха по-прежнему разрешать. Установлено чтением кода, перезагрузка живого браузера не выполнялась.

### P0-10. Ошибка в поле КИЗ уничтожает ключ уже начавшейся печати

**Где:** `frontend/src/screens/v2/fbsSequentialPacking.ts:343–346`, завершение хранения — `490`.

После успешной привязки в поле строки QR дошла до программы, но HTTP-ответ или следующая печать копии потерялись. Catch очищает pending **и** сохранённую попытку независимо от стадии ошибки. Повтор поля получает новый scan_id и может напечатать QR второй раз. **Воспроизведено:** `ROW_RETRY sameId:false` на настоящих зависимостях хранения/выбора, ошибка внедрена в print.

**Происхождение:** общий catch уже был в продовой сборке `c26530f7`; это унаследованный дефект, который новая унификация распространяет на обычную поставку и на добавленную печать ЧЗ. Не выдаётся за новую строку, введённую d7dc1130. Он непосредственно мешает новым R10/R13/R15.

**Минимальное исправление:** после ошибки привязки снимать фокус строки, но отдельно сохранять незавершённое намерение печати после подтверждённой привязки/возможной отправки. Следующие обычные сканы не должны захватываться полем, а повтор этой строки должен продолжать прежнюю печать.

### P1-01. Состояния `started`/`outcome_unknown` у копии ЧЗ не позволяют штатно восстановить скан

**Где:** `frontend/src/screens/v2/fbsSequentialPacking.ts:366–370,409–411,596–606`; `backend/app/services/fbs_scan_auto_print_service.py:722–727,772–777`; `frontend/src/screens/v2/fbsKizAutoReprint.ts:69–77`.

После QR и копии ЧЗ произошёл сбой упаковки. После переоткрытия `reprint_recovery.status='started'`, но `bound` true только для `available`; заказ снова ждёт ЧЗ, а повтор ШК не завершает его. Если WMS Print приняла копию, а запрос `markStarted` не дошёл, сервер сохраняет active claim. `claim_reprint_kiz_recovery` отказывает даже владельцу с тем же attemptKey; до программы, которая могла бы вернуть прежнюю квитанцию, повтор вообще не доходит. Это зависание в новом режиме перепечати, а не дефект принтера.

**Минимальное исправление:** раздельно восстанавливать факт привязки и состояние доставки каждой этикетки; `started` не означает отсутствующий КИЗ. Дать той же попытке безопасно сверить квитанцию и завершить active claim, не создавая нового печатного намерения. Проверено по коду.

### P1-02. «Назад» сравнивает сырой скан с нормализованным КИЗ и отказывает исправному сканеру

**Где:** `frontend/src/screens/v2/fbsSequentialPacking.ts:338,377,643`; `backend/app/services/fbs_kiz_service.py:1720,1751–1756`.

Bind удаляет AIM-префикс `]d2`, исправляет поддерживаемую раскладку и возвращает `bound_kiz`. История сохраняет исходный raw, а rollback ищет/сравнивает его без нормализации. Принятый скан `]d2<КИЗ>` сохраняется в заказе как `<КИЗ>`, и «Назад» отвечает `kiz_rollback_changed`, хотя ничего постороннего не менялось. **Воспроизведено на сервере** с настоящей маркировкой; `normalize_scanned_cis` подтверждает эквивалентность, rollback всё равно отказывает.

**Минимальное исправление:** использовать канонический результат bind и ID его операции; как минимум одинаково нормализовать вход rollback. Не восстанавливать идентичность действия только по строке КИЗ.

### P1-03. Отменяется событие упаковки другой единицы той же строки

**Где:** `backend/app/services/packaging_task_service.py:1610–1642`.

Оператор A упаковал заказ A, затем оператор B — заказ B того же товара/строки задания. A нажимает «Назад». Fulfillment найден правильно по ключу A, но `pack_event` берётся как **последнее** неотменённое событие строки с quantity=1 — то есть B. Событие B помечается отменённым, а `OperationFact` сторнирует чужой факт работы. Это искажает историю действий и связь отмены с выполненной работой; итоговая единица A при этом распаковывается. Подтверждено запросом в коде, двухоператорный DB-прогон не выполнен.

**Минимальное исправление:** находить точное событие по сохранённому ключу (`record_pack_progress` уже вычисляет `uuid5(tenant_id, 'pack-progress:'+key)`), проверять его принадлежность строке/действию и сторнировать именно его.

### P1-04. Запрет отката завершённого/перенесённого заказа проверяется не для всех шагов

**Где:** `backend/app/services/packaging_task_service.py:1558–1588`; `frontend/src/screens/v2/fbsSequentialPacking.ts:631–643`; `backend/app/services/fbs_kiz_service.py:1719–1723`.

Проверка закрытого задания выполняется только при найденном активном fulfillment для переданного packKey. Для изменения КИЗ на уже упакованной строке packKey отсутствует; отдельный rollback КИЗ не получает исходный supply_id и не проверяет завершённость задания. Если заказ после скана перенесли, запрос всё равно адресует order_id и может удалить его КИЗ уже в новой поставке. При завершении задания кнопкой после изменения КИЗ тоже нет обязательного запрета. Supply status в `undo_fbs_scan_unit` отдельно не проверяется; защита короба срабатывает только если box_id передан.

**Минимальное исправление:** до любых изменений проверять исходную поставку, точное событие, состояние поставки/задания для **всех** видов шага, включая без упаковки и без короба. Связать scan_id с переданным order_id: сейчас cancel проверяет свой order отдельно и не доказывает, что это тот же order, который распаковывает запрос. Права оператора и tenant сами по себе этих проверок не заменяют.

### P1-05. Неудачный возврат КИЗ уже оставляет распаковку и освобождение выбора зафиксированными

**Где:** `frontend/src/screens/v2/fbsSequentialPacking.ts:634–643`; `backend/app/services/packaging_task_service.py:1660–1663`.

Для U4 клиент сначала вызывает scan-undo: распаковать, убрать из короба, освободить резерв — commit. Только затем отдельным HTTP-запросом возвращает КИЗ. WB отказывает/связь пропадает, UI сохраняет шаг как неотменённый, но заказ уже доступен следующему товарному скану с прежним КИЗ. Другой оператор может занять его до окончания отката. После этого повтор первого шага может отказать из-за новой упаковки и даже не дойти до доведения КИЗ. Это не атомарное действие R19 и не гарантированный повтор того же шага.

**Минимальное исправление:** серверная операция отката должна сохранять стадии и удерживать исходный выбор до завершения внешней сверки/возврата КИЗ; повтор продолжает её. Не держать SQL-транзакцию бесконечно на сети, но и не публиковать заказ свободным между независимыми клиентскими запросами. По коду.

### P1-06. В сборке Ozon появились галки WB

**Где:** `frontend/src/screens/v2/FbsPackingScanBar.tsx:85–88`; `FfFbsSupplyAssembly.tsx:414–418`.

Общая полоса сборки рендерится и при `ozonOwnsPackingScan`; это условие только делает enabled=false. Новые `FbsScanPrintToggles` выводятся без условия WB и без общего disabled. Поэтому в сборке только с Ozon появились три активные галки WB и неактивная кнопка «Назад». Ozon-контроллер не выполняет эти режимы, но галки меняют общую сохранённую настройку WB. Это прямое нарушение R16/R17, несмотря на неизменённый обработчик скана Ozon. Установлено по JSX; скриншот не получен.

**Минимальное исправление:** рендерить новые элементы только в контексте WB, не менять прежний вид Ozon-полосы; проверить отдельно Ozon-only и смешанную сборку.

### P1-07. Повтор задания заново рисует ЧЗ с текущим размером вместо сохранённого содержимого

**Где:** `frontend/src/screens/v2/fbsSequentialPacking.ts:459–462,585–588,598–600`; доступный выбор размера — `FbsPackingScanBar.tsx:89`.

ЧЗ принята программой, ответ потерялся. Оператор меняет размер этикетки и повторяет незавершённый скан. `renderCzLabelPng` рисует другой растр с текущим `loadLabelSizeId()`, но idempotencyKey остаётся прежним. Direct-программа проверяет не только ключ, но и хэш PNG: этот повтор будет отвергнут как другое содержимое. Даже без потери ответа изменение размера во время QR позволяет одной последовательности QR→ЧЗ получить разные размеры. В сохранённом попытке нет ни размера, ни готового PNG.

**Минимальное исправление:** фиксировать размер и канонический растр каждого печатного намерения до первой отправки и повторять их неизменно; новый выбор размера применяется к следующему новому действию. Дефект установлен по коду, живое переключение размера с потерянным ответом не проверялось.

### P1-08. Esc оставляет уже отменённый выбор в истории «Назад»

**Где:** `frontend/src/screens/v2/fbsSequentialPacking.ts:295–304`, чтение последнего шага — `266–269`.

После успешного выбора A создаётся шаг history. Esc освобождает резерв и очищает pending, но history не меняется. Кнопка остаётся активной, и следующее «Назад» тратится на уже отменённый A вместо последнего ещё неотменённого действия. Если в истории были более ранние сканы, требуется лишнее нажатие; если A за это время снова упакован, повторный cancel старого выбора может отказать и перекрыть доступ к более ранним шагам.

**Минимальное исправление:** после подтверждённого Esc удалить/пометить отменённым точный шаг выбора, сохранив более раннюю историю. Делать это вместе с сериализацией P0-06, чтобы завершение запроса не вернуло отменённый шаг. По коду.

## Продуктовые развилки — отдельно от дефектов

1. **Д5 против исходной фразы «сосканить QR, и печатается ЧЗ».** Реализация соблюдает утверждённую матрицу: стикер не выделяет ЧЗ из пула. Если владелец имел в виду именно стикер WB, R7/M13 требуют изменения; сейчас это не технический дефект относительно документа.
2. **Д11 против R19 для обычной поставки только с товарами без ЧЗ.** На `FfFbsSupplyWorkspace.tsx:3622` вся полоса, включая новую кнопку «Назад», скрыта при `anyOrderNeedsHonestSign=false`. Д11 велит сохранить это условие, R19 требует кнопку в обоих местах, U5 включает M9/M12. Нужно определить разрешённое место «Назад» без добавления лишней полосы. При текущем решении оператор не имеет этой кнопки; это нельзя засчитать как U5 через UI.
3. **Д13, старые/импортированные маркировки без полного локального кода.** Новый event покрывает только замены с известным `marking_code_id`. Необоснованно обещать полный возврат любой старой записи. Разрешённый документом fallback должен быть явным и не выдавать пустой КИЗ за восстановленный прежний; код такого сообщения сейчас не делает (см. P0-01).
