# WMS-631 — ревью opus, круг 1

Дата: 02.10.2026. Проверены изменения c26530f7..d7dc1130 (4b33922a и d7dc1130) в ветке feat/wms631-unified-packing. До ревью прочитаны целиком AGENTS.md, owner-cases.md, failure-cases.md, docs/requirements/WMS-631.md и раздел дефектов print-agent-astra.md. Код не менялся, тесты проекта не запускались. Экран в браузере не открывался. Единственный живой опыт — отдельная HTML-страница в headless Chromium 1217 (из кэша Playwright), которая повторяет алгоритм czLabelPng: SVG с foreignObject превращается в canvas, а затем вызывается toDataURL.

Номера строк указаны по d7dc1130.

Итог: 2 дефекта P0, 6 дефектов P1, 11 дефектов P2, плюс 4 продуктовые развилки.

## Дефекты

### P0-1. При неудачном откате замены КИЗ прежний код навсегда остаётся «свободным» в пуле и может уйти другому заказу

**Где:** backend/app/services/fbs_kiz_service.py:1766–1781 (rollback_scan_kiz). Выбор из пула: marking_code_service.py:2603–2614 и 2727–2738.

**Сценарий (U3 + U8).** У заказа A был код K1, сканом его заменили на K2. Оператор нажимает «Назад». Сервер снимает K2, затем переводит K1 из VOID в AVAILABLE и делает отдельный commit. Только после этого вызывается commit_kiz_pairs для возврата K1. Если WB отклоняет запись K1 (ошибка без неопределённости: 4xx или meta_validation_fail), commit_kiz_pairs откатывает только свою транзакцию. K1 остаётся AVAILABLE, хотя его этикетка физически наклеена на единицу A. Выбор из пула берёт любой код в статусе AVAILABLE, начиная со старых, и источник кода не проверяет. Поэтому следующий скан с «Печатать ЧЗ» по этому GTIN с большой вероятностью выдаст K1 другому заказу. Итог — один КИЗ на двух единицах. Повторное нажатие «Назад» тоже ничего не исправляет: K1 уже AVAILABLE, ветка с VOID не срабатывает, и после следующей ошибки WB код так и остаётся в пуле. Кроме того, даже при успешном откате между commit и захватом кода в _claim_pool_code_if_present есть окно, в котором K1 видна как свободная (тот самый «временно свободен» из сомнения 2).

**Минимально исправить.** Не делать отдельный commit с AVAILABLE. Возвращать K1 в той же транзакции, что и привязку, либо привязывать через путь, который принимает VOID-код, заменённый этим событием, без выхода в пул. Если запись в WB не удалась, возвращать K1 в VOID (или оставлять его в VOID) и сообщать ошибку. Нужен тест: WB отклоняет возврат → K1 не AVAILABLE, и выбор из пула его не выдаёт.

### P0-2. Скан стикера после перезагрузки (или переоткрытия сборки) создаёт новый скан и печатает QR второй раз

**Где:** frontend/src/screens/v2/fbsSequentialPacking.ts:233–244 (selectNew сначала вызывает selectByProduct) и 501–505 (deps.select удаляет сохранённую попытку при scan_product_not_found). Сервер: fbs_scan_auto_print_service.py:304–307 (явный выбор берёт ключ wms630-row по digest нового ключа).

**Сценарий (R6, R13, по образцу C17).** Включена «Печатать QR». Оператор сканирует стикер A, и сервер создаёт выбор S. Затем скан ЧЗ, QR уходит в WMS Print с ключом S. После этого упаковка падает по сети, либо ответ WMS Print теряется. Оператор перезагружает страницу и снова сканирует стикер. Сначала срабатывает selectByProduct: claim возвращает сохранённую попытку стикера (ключ K), сервер отвечает scan_product_not_found, потому что стикер не ШК товара. deps.select удаляет попытку K. Затем selectBySticker создаёт новый ключ, сервер создаёт новый выбор S′, ЧЗ уже привязан, а QR печатается с ключом S′. Получается вторая бумажная этикетка того же заказа. Для ШК товара та же ситуация восстанавливается правильно (повтор S), то есть путь R6 нарушает И2.

**Минимально исправить.** Если для raw уже есть сохранённая попытка с orderId, восстанавливать её по тому пути, которым она была создана: явный выбор с тем же ключом и order_id. Либо не вызывать selectByProduct для raw, у которого есть сохранённая попытка явного выбора. В попытку нужно записывать признак «стикер».

### P1-1. После «Назад» на скане ЧЗ повторный скан ЧЗ не упаковывает заказ, и ошибки при этом нет

**Где:** fbsSequentialPacking.ts:42–44 и 621–623 (ключ упаковки всегда равен scan_id:packed). Сервер: packaging_task_service.py:965–1003 (повтор по ключу) и fbs_packaging_integration_service.py:636–668 (поиск fulfillment по ключу без фильтра undone_at).

**Сценарий U1 → повторный скан ЧЗ.** «Назад» снимает упаковку, и заказ снова ждёт ЧЗ с тем же scan_id. Оператор сканирует ЧЗ, и finish отправляет pack с тем же ключом. Событие с id = uuid5(tenant, "pack-progress:" + ключ) уже существует, поэтому сервер идёт по ветке повтора, находит отменённый fulfillment и возвращает 200, ничего не упаковав. Фронт считает заказ упакованным и записывает packKey в шаг. Заказ остаётся неупакованным, хотя оператор прошёл сценарий до конца.

**Минимально исправить.** Добавить в ключ упаковки номер поколения (например, scan_id:packed:N, где N увеличивается после каждого успешного отката упаковки этого скана). Либо на сервере считать повтор по отменённому fulfillment новым действием. Нужен тест «U1 → ЧЗ → заказ упакован».

### P1-2. Выбор стикером уже упакованного заказа нельзя снять ни Esc, ни «Назад» — сканы захватываются как ЧЗ

**Где:** fbs_scan_auto_print_service.py:379–382 (scan_selection_packed для любого штрихкода, кроме order:). Вызовы: fbsSequentialPacking.ts:295–305 (cancel) и 631–641 (undo, release_selection для шага select).

**Сценарий.** Включена «Печатать QR» или «Перепечатывать ЧЗ». Оператор сканирует стикер заказа, который уже упакован (перепроверка, замена ЧЗ, M17 для упакованного). Сервер даёт явный выбор, шаг select записывается в историю, а товару нужен ЧЗ. Esc падает с ошибкой «Заказ по этому скану уже упакован; выбор не снят», выбор остаётся. Повторный скан стикера даёт «Товар уже выбран. Сканируйте его Честный знак». Любой следующий код уходит в bind как ЧЗ этого заказа. «Назад» на этом шаге падает с той же ошибкой и закрывает доступ ко всем более ранним шагам истории. Выйти можно только перезагрузкой страницы. Это противоречит R20 и И9.

**Минимально исправить.** Запрет scan_selection_packed применять только к выборам, которые упаковал сам этот скан (по fulfillment с его ключом), а не по общему pack_status. Для явных выборов (стикер) снятие выбора разрешать всегда.

### P1-3. После «Назад» на скане ЧЗ повторный скан того же ШК даёт «другой заказ» и навсегда резервирует соседнюю единицу

**Где:** fbsSequentialPacking.ts:276–285 (восстановленный pending без сохранённой попытки), 358–365 (повтор ШК при needsKiz) и 205 (finish уже вызвал complete(barcode)).

**Сценарий.** M1 завершён, затем «Назад» один раз (U1): заказ A снова ждёт ЧЗ, но попытка в localStorage была удалена ещё в finish. Оператор по привычке сканирует ШК товара. claim создаёт новый ключ, сервер считает A занятым (выбор S не отменён) и резервирует следующий заказ B новым событием. Фронт отвечает «Сервер вернул другой заказ для незавершённого скана» и remember не вызывает. Дальше каждый скан этого ШК повторяет B и даёт ту же ошибку. После скана ЧЗ для A попытка удаляется, а резерв B остаётся навсегда. Обычный скан B больше не выберет: в конце будет scan_product_exhausted при неупакованном B, и спасут только стикер, поле строки или «Всё упаковано». Это и есть сомнение разработчика 4, но в другом месте. После перезагрузки ШК товара восстанавливается правильно: попытка не была завершена.

**Минимально исправить.** При восстановлении pending после отката снова сохранять попытку (claim с исходным ключом, scanId и orderId). Либо в ветке raw === barcode для восстановленного шага отвечать «Сканируйте ЧЗ» без запроса select.

### P1-4. «Назад» на скане с «Печатать ЧЗ» удаляет из WB код, который был у заказа до скана

**Где:** fbsSequentialPacking.ts:415–416 (step.kiz = printed_codes[0] без проверки, что код выдан именно этим сканом). Сервер: fbs_order_tape_print_service.py:822–834 (печать повторно использует уже привязанный код заказа).

**Сценарий.** Заказ A получил код из пула раньше: через «Печать всего/выбранного» или через прошлую печать ленты. Скан ШК с «Печатать ЧЗ» выбирает A, сервер не выдаёт новый код, а возвращает существующий K в printed_codes. Нажатие «Назад» вызывает rollback_scan_kiz(K), current равен K, и выполняется cancel_order_kiz. Код, которого этот скан не записывал (его этикетка уже на товаре), удаляется из WB и возвращается в пул. Это нарушает R19(а): «возвращается к прежнему состоянию».

**Минимально исправить.** Сервер должен сообщать, выдан ли код этим сканом (флаг в ответе scan-auto-print или событие выдачи с scan_id). Записывать step.kiz только для новых кодов, как уже сделано для newly_bound у ручного скана.

### P1-5. После «Сдать без Честного знака» сборка начинает ждать ЧЗ — регрессия относительно прода

**Где:** fbsSequentialPacking.ts:103–105 (requiresKiz берёт binding_target.requires_honest_sign первым). Сервер: fbs_kiz_service.py:690–703 (order_requires_sgtin, без honest_sign_skipped). Для сравнения fbs_order_tape_print_service.py:366–369, где пропуск учитывается.

**Сценарий.** Поставка в состоянии honest_sign_skipped, товар с ЧЗ, включена «Печатать QR». На проде (c26530f7) сборка брала result.requires_honest_sign, который при пропуске равен false: скан ШК сразу печатал QR и упаковывал заказ. Теперь binding_target.requires_honest_sign всегда true для такого товара, заказ ждёт скан ЧЗ, и выйти можно только сканом кода, который потом уйдёт в WB, хотя поставку сдают без ЧЗ. Так же ведут себя выбор стикером (localSelection берёт target.requires_honest_sign) и обычная поставка. Нарушено условие владельца «не должны сбиться никакие функции».

**Минимально исправить.** В _binding_lookup_for_order учитывать supply.honest_sign_skipped_at так же, как печать ленты (требование false, если пропуск включён и кода нет). Либо на фронте при пропуске не ждать ЧЗ. Нужен тест на поставку с пропуском.

### P1-6. Этикетка ЧЗ не рисуется для кодов, у которых в последних 12 символах есть разделитель GS

**Где:** frontend/src/utils/czLabelPng.ts:43–50. Текст кода берётся из printMarkingCodeLabel.ts:240–256 (displayCode = maskCisTail, то есть последние 12 символов полного кода с \x1d).

**Сценарий.** Внутри SVG-изображения XHTML разбирается как XML, а символ U+001D в XML 1.0 запрещён. Старая печать через HTML-iframe этот символ терпела. У кодов формата 01…21…GS93xxxx (короткий криптохвост 93; в проекте такой формат распознаётся, см. kiz_reprint_service.py:79) последние 12 символов содержат GS. Изображение не загружается, и для «Печатать ЧЗ» и «Перепечатывать ЧЗ» появляется ошибка «Не удалось подготовить этикетку ЧЗ для печати». Печать стоит в finish перед упаковкой, поэтому заказ залипает: каждый повтор падает так же. Для кодов одежды и обуви (91/92 с подписью 44 или 88 символов) хвост GS не содержит.

**Проверено в headless Chromium 1217** на той же сборке SVG: строка «…ABCdef123456» нарисовалась, «…12345\x1d931abc» вызвала onerror.

**Минимально исправить.** Перед вставкой в XHTML вырезать или заменять управляющие символы (U+0000–U+001F, кроме табуляции и переводов строки) во всём тексте раздела. Либо собирать разметку через DOM и XMLSerializer. Нужен тест с кодом формата 93.

### P2-1. Откат упаковки помечает отменённым последнее событие упаковки строки, а не событие этого скана (сомнение 3)

**Где:** packaging_task_service.py:1610–1625. Если в строке несколько заказов одного товара, reversed_at и original_event_id достаются чужому событию. Количество при этом сходится, а привязка «какое действие отменено» в журнале задания — нет. **Исправить:** у события упаковки этого скана детерминированный id uuid5(tenant_id, "pack-progress:" + ключ) (строка 965), его и нужно брать.

### P2-2. Esc не убирает шаг select из истории

**Где:** fbsSequentialPacking.ts:295–305. После E1 первое нажатие «Назад» снова «отменяет» уже снятый выбор: внешне ничего не происходит, и оператор не понимает, сработала ли кнопка. Если этот заказ потом упакуют, шаг упрётся в scan_selection_packed и закроет историю. **Исправить:** при успешном cancel удалять шаги этого scan_id из history.

### P2-3. Гонки Esc и «Назад» с идущим сканом ЧЗ

**Где:** fbsSequentialPacking.ts:267–268 (undo блокируется только флагом selecting), 297–299 (cancel при needsKiz срабатывает и во время bind). FbsPackingScanBar.tsx:22–36 и 61–77: в сборке кнопка и Esc не блокируются занятостью скана. Если во время сохранения ЧЗ (вызов WB) нажать Esc или «Назад» в сборке, выбор снимается на сервере, а начатый скан всё равно доходит до печати и упаковки. Это расходится с R20 («ничего не сохраняется») и C35. **Исправить:** запрещать cancel и undo, пока идёт bind или finish (флаг занятости контроллера), и выключать кнопку на это время.

### P2-4. Возврат прежнего кода меняет его источник и счётчики (сомнение 2) — не проверено до конца

**Где:** fbs_kiz_service.py:1772–1782, затем _prepare_code_for_binding (1083–1105). Код, ставший AVAILABLE, захватывается как «код пула», поэтому from_pool и source могут стать pool у кода, который вносил оператор, а qty_marking_printed или qty_marking_external могут сдвинуться повторно. Я не прошёл учёт cancel_order_kiz для этих счётчиков и не берусь утверждать итог. Нужен тест «замена K1→K2, откат, сверка source, qty_marking_*» для оператора и для пула.

### P2-5. Для шагов, где менялся только ЧЗ, откат не проверяет состояние задания и поставки

**Где:** fbsSequentialPacking.ts:631–643. Если у шага нет packKey и boxId (поле строки у упакованного заказа, F1), сервер не вызывается и сразу идёт rollback_scan_kiz, где нет проверки «задание завершено или поставка передана» (R19). Если cancel_order_kiz сам не запрещает изменение в замороженных статусах, откат удалит код из WB у сданного заказа. Я этот запрет не прочитал, поэтому это гипотеза для проверки, а не подтверждённый сбой.

### P2-6. Сбой печати нельзя сбросить Esc, хотя решение Д8 это предусматривает

**Где:** fbsSequentialPacking.ts:297 (при !needsKiz cancel возвращает false). По решению Д8 заказ держится «до повторного скана его ШК … либо до Esc». Вместе с дефектом P1-04 программы WMS Print (ключ навсегда «уже передавалось») заказ со сбойной печатью нельзя ни допечатать, ни сбросить Esc: печать стоит в finish перед упаковкой. Остаются только «Назад» или «Всё упаковано».

### P2-7. Смена размера этикетки между попытками ломает повтор того же ключа

**Где:** fbsSequentialPacking.ts:459–463, 585–588 и 598–600. PNG ЧЗ и копии перерисовывается при каждой попытке с текущим loadLabelSizeId(). Если размер сменили, хэш другой, и WMS Print отвечает «Содержимое этого задания изменилось» на тот же ключ — заказ залипает. **Исправить:** запоминать размер (или сам PNG) в попытке.

### P2-8. Прямая копия ЧЗ (M16/M18) защищена от повтора только памятью страницы

**Где:** fbsSequentialPacking.ts:510–534. directKeys хранится только в памяти. Если ответ потерян и страница перезагружена, повтор создаёт новую строку перепечати и новый ключ, а значит вторую копию. Окно узкое.

**Где:** fbsSequentialPacking.ts:233–255. Сначала всегда пробуется ШК товара, потом стикер, потом копия. В старой обычной поставке стикер проверялся первым. На путях R6 и M16 к каждому скану добавляется лишний запрос с ответом 404.

## Сомнения разработчика — ответы

1. **«Испорченный» canvas.** В Chromium 1217 картинка из data:-SVG с foreignObject canvas не портит: toDataURL отработал, картинка DataMatrix из data:-URL внутри нарисовалась. Шрифт берётся системный (Arial), загрузки нет. Проблема в другом — управляющий символ GS (P1-6). Визуально с прежней этикеткой я не сравнивал. Отличия по коду: добавлено image-rendering: pixelated, а высота .label на 1,5 мм меньше PNG (запас из ленточного CSS).
2. **Откат замены КИЗ.** Подтверждаю окно «временно свободен» и более тяжёлый случай — код остаётся в пуле после ошибки WB (P0-1). Учёт источника — P2-4. Откат прежнего кода работает только при наличии события wms631_kiz_replaced, которое пишется лишь если у прежней маркировки есть marking_code_id. Иначе откат молча оставляет заказ без КИЗ, без строки «отсканируйте прежний КИЗ заново», которой требует Д13.
3. **Чужое событие при откате упаковки.** Подтверждаю (P2-1). Хуже то, что тот же ключ блокирует повторную упаковку (P1-1).
4. **«Другой заказ» после переоткрытия.** Для ШК товара после перезагрузки восстановление верное, потому что попытка сохранена. Ошибка возникает после «Назад» (P1-3). Для стикера после перезагрузки ошибки нет, но создаётся новый скан и вторая этикетка QR (P0-2).
5. **Новое поле в ответе поиска по стикеру.** Поле добавлено с умолчанием false, тип на фронте необязательный, существующих полей оно не меняет. В исходниках ТСД разбора этого ответа не нашёл. Сгенерированный клиент ТСД не смотрел. Смысл поля расходится с печатью ленты при пропуске ЧЗ (P1-5).

## Проверено — верно

- Матрица M1–M18 по коду контроллера: решение «печатать QR / ЧЗ из пула / копию», порядок QR → ЧЗ → копия → упаковка, отсутствие ЧЗ из пула для стикера и поля строки (Д5, Д6), M10 даёт ошибку sticker_not_found, M16/M18 печатают прямую копию без упаковки. Окон подтверждения и window.confirm в упаковке WB больше нет: при needs_confirmation выполняется повторный commit с confirmed:true (R18). Печати браузером на пути скана нет: всё уходит в printDirectQr на 127.0.0.1:17843 без запасного варианта.
- Ключи WMS Print: QR — scan_id, ЧЗ — scan_id:chz, копия — scan_id:copy; серверные заявки на печать для QR и ЧЗ не освобождаются после неопределённого исхода.
- Новые эндпоинты (cancel, scan-undo, kiz/rollback) требуют require_fbs_operator_access и фильтруют по tenant_id. Scan-undo блокирует поставку и заказ в одной транзакции, удаление из короба не делает commit внутри и проверяет, что поставка изменяема. Отмену выбора может сделать только тот же пользователь, отмена идемпотентна по событию.
- Генерации ключа резерва после отмены не пересекаются: счётчик отмен только растёт, повтор собственного ключа возвращается раньше, чем считается генерация.
- Поле строки: при сбое pending очищается, следующие сканы не захватываются (R15, C21). Уже упакованный заказ повторно не упаковывается (И7).
- Ozon: оба флага assemblyWbPacking и ordinaryWbPacking выключены, остаются прежние обработчики. Исключение — P2-10.
- AGENTS.md и CLAUDE.md в рабочем каталоге совпадают.

## Продуктовые развилки (не дефекты)

1. **Обычная поставка без заказов с ЧЗ.** По Д11 полоса скана скрыта, но вкладка продолжает принимать сканы, а с умолчанием Д2 («Печатать QR» включена) они печатают QR и упаковывают. Ошибки (R15) и «Назад» (R19) при этом показать негде. Решение Д11 противоречит R15 и R19 — нужно решение владельца.
2. **Откат U4.** Напечатанный код из пула по существующему правилу крестика возвращается в AVAILABLE, хотя бумага с этим кодом уже существует. Повторная выдача того же кода даёт вторую физическую этикетку. Нужно решить, возвращать ли такой код в пул.
3. **Заблокированный шаг.** Шаг, который нельзя отменить (заказ перенесён, задание закрыто), по R19 остаётся на вершине истории и закрывает доступ ко всем более ранним шагам. Возможно, такой шаг стоит пропускать.
4. **Д5** остаётся открытым: «сосканить QR, и печатается ЧЗ».
