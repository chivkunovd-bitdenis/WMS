## Дефекты

Приоритеты ниже соответствуют запросу владельца: P0 — достижимый сценарий повторной отправки этикетки или остановки складской печати; это не утверждение, что такой инцидент уже произошёл на складе. Воспроизведения использовали временные журналы и подмену отправки, без настоящего принтера.

### P0-01. Ошибка чтения SQLite превращается в разрешение повторно отправить старый ключ

**Где:** `tools/print-agent/wms_print_direct_macos.swift:222–242`, `:271–281`.

**Сценарий и доказательство.** `legacyJobs` возвращает пустой словарь при ошибке открытия/prepare, а `sqlite3_step` вообще не проверяется на итоговый `SQLITE_DONE`: ошибка во время чтения даст неполную историю. Инициализация Printer продолжается. В изолированном тесте создан настоящий SQLite с ключом `previously-printed`, тем же hash PNG и receipt `old-1`. Другая connection удерживала `BEGIN EXCLUSIVE`. Swift написал «импорт пропущен», затем на тот же ключ вызвал submit и вернул `duplicate-1`, число новых отправок — 1. Отдельно повреждённый SQLite также был проигнорирован. Это не только гипотеза про порчу диска: достаточно временной блокировки корректной БД.

**Минимальное исправление.** Сделать импорт бросающим ошибку; если старый файл существует, не начинать новую отправку до полного успешного чтения. Проверять результат каждого шага и окончательный `SQLITE_DONE`, допускается короткий ограниченный повтор чтения при BUSY. Не считать частичный результат полным. Успешно импортированный журнал сохранять до перехода в рабочее состояние; ошибку сохранения не прятать. Это защита конкретных уже отправленных ключей, а не общий запрет работы оператора.

### P0-02. Обратный запуск Python после Swift по-прежнему позволяет дубль

**Где:** Swift `tools/print-agent/wms_print_direct_macos.swift:271–286`, `:338–340`; Python `tools/print-agent/wms_print_direct.py:171–180`, `:190–192`.

**Сценарий.** Импорт односторонний. Новые квитанции Swift остаются только в JSON, Python читает только SQLite. Оператор закрывает новую программу и открывает прежнюю распакованную Python-версию: свободный порт и singleton это разрешают, и прежний ключ из JSON снова отправляется. Проверено текущим Python Printer на временной паре журналов с корректной JSON-квитанцией `swift-77`: получена новая `python-new-1`, submit вызван один раз. Сама квитанция этого отдельного теста была подготовлена синтетически; чтение Python только из SQLite установлено непосредственно по коду.

Это остаток прямо указанного в исходном P1-03 требования учитывать обратный запуск, а не новый дефект обычного Swift → Swift обновления. Вчерашняя и сегодняшняя Swift-версии пользуются одним JSON, для этой пары миграционного дубля не установлено.

**Минимальное исправление.** Сохранять отметку о возможной отправке и результат в совместимой общей истории, которую увидит допускаемая к запуску Python-версия, до обращения к ОС; либо обеспечить реально проверяемый запрет запуска несовместимой старой программы после миграции. Простой файл версии, который старый бинарник не читает, такой защиты не даёт. Не объявлять односторонний импорт защитой от downgrade.

### P1-01. Автоматический media переопределяет рабочий Borderless обычным форматом

**Где:** `tools/print-agent/wms_print_direct_macos.swift:125–136`, `:205–206`.

**Сценарий.** Для строки `PageSize/Media Size: 58x40mm *58x40mm.Borderless` функция возвращает `58x40mm`. Воспроизведено настоящей `matchMedia`. Звёздочка текущего выбора отбрасывается, приоритет plain задан безусловно. У двух PPD-форматов может совпадать размер бумаги, но отличаться ImageableArea — область, на которой драйвер разрешает печатать. Тогда fit-to-page получает другую область, может уменьшить код и изменить поля; иной фильтр/драйвер может изменить смещение или обрезку. Нельзя утверждать, что именно московский Xprinter обязательно обрежет этикетку: его PPD и выходной растр здесь не получены.

Основание не в названии `.Borderless` как таковом: в [тестовом PPD самого Apple CUPS](https://raw.githubusercontent.com/apple/cups/master/cups/test.ppd) у Letter и Letter.Fullbleed одинаковая PaperDimension 612×792, но ImageableArea соответственно `18 36 594 756` и `0 0 612 792`. Это пример контракта PPD, не драйвер Xprinter. [Документация CUPS](https://www.cups.org/doc/options.html) подтверждает, что media задаёт формат задания и доступные варианты определяет PPD.

**Минимальное исправление.** Для этого выпуска убрать выбор media и дополнительный вызов lpoptions из рабочей отправки. Сохранить вчерашнюю команду. Если позже понадобится выбор другого размера, проверять конкретные PPD и итоговую печать, сохраняя текущий точный вариант при совпадении размеров; одна перестановка предпочтения «сначала Borderless» также не гарантирует сохранения настроек всех очередей.

### P1-02. Таймауты по-прежнему не ограничивают весь запрос 30 секундами

**Где:** Swift `tools/print-agent/wms_print_direct_macos.swift:96–97`, `:139–141`, `:208–209`, `:306–330`; Python `tools/print-agent/wms_print_direct.py:234–256`; браузер `frontend/src/utils/printDirectQr.ts:7–14`.

**Mac.** `NSLock.lock()` ждёт без срока и удерживается во время всей подготовки/печати. За ним последовательно идут defaultPrinter до 10 с, lpoptions до 5 с, lp до 20 с, плюс завершение процессов и работа с PNG/диском. Например, успешные 9 с на lpstat, 4 с на lpoptions и 19 с на lp уже дают 32 с даже без конкуренции. Два окна могут накопить запросы на lock: браузер уже отказался ждать, а сервер позднее начнёт отправку этикетки. Установка SIGKILL для одного процесса не устраняет очередь ожидающих HTTP-запросов.

**Windows.** До worker.join(25) отдельно допускаются 10 с ожидания slot и обращение к default printer. `GetDefaultPrinter()` вызывается вне защищённого таймаутом worker. На настоящем классе с уменьшенными интервалами первый запрос закончился по лимиту 0,2 с, второй после ожидания предыдущего — через 0,36 с при том же лимите 0,2 с. В штатных величинах ожидание 8 с + работа 25 с пересекают браузерные 30 с.

**Минимальное исправление.** Ввести один deadline от начала обработки, меньше браузерных 30 с с запасом; его остаток применять к ожиданию очереди, подготовке и системным вызовам. Если срок истёк до необратимой границы, поздно начинать отправку нельзя. Состояние уже начатой отправки продолжать сверять по прежнему ключу. Проверить параллельные вкладки, а не только последовательную Promise-очередь одной вкладки.

### P1-03. Зависший Windows worker не освобождается; повтор уже отправляемого ключа ошибочно назван «не отправлялся»

**Где:** `tools/print-agent/wms_print_direct.py:194–221`, `:234–235`, `:256–260`.

**Сценарий и доказательство.** Поток после 25 с остаётся жив и держит slot до фактического возврата драйвера. Если драйвер никогда не вернётся, все следующие запросы будут отказаны через 10 с сколько угодно долго; предложение повторить через минуту ничего не исправляет. Повтор того же ключа также сначала ждёт slot, а не читает уже сохранённую отметку.

В тесте первая отправка оставалась внутри submit и получила UnknownPrintOutcome. Повтор **того же ключа** вернул PrintNotSent с буквальным текстом «Это задание не отправлялось». После освобождения submit этот же ключ вернул настоящую позднюю квитанцию `q-1`. То есть текст второго ответа опровергнут результатом первого задания. Автоматического дубля того же ключа тест не показал; опасность — оператор поверит сообщению и создаст отдельную копию, пока исходная ещё может выйти.

**Минимальное исправление.** До отказа из-за занятого slot читать историю конкретного ключа: прежний receipt вернуть, возможную отправку назвать неизвестной, «не отправлялось» применять только к действительно новому ключу. Для прекращения бесконечно зависшего GDI использовать отдельный рабочий процесс с контролируемым завершением, сохраняя неизвестный результат и запрет слепого повтора. Убийство worker само по себе не доказывает отмену задания в spooler.

### P1-04. Сохранённая отметка без receipt всё ещё не имеет пути восстановления

**Где:** Swift `tools/print-agent/wms_print_direct_macos.swift:208–216`, `:308–312`, `:338–340`; Python `tools/print-agent/wms_print_direct.py:198–200`, `:213–216`, `:239–244`.

**Сценарий.** После сохранения mark процесс падает до запуска lp/StartDoc либо после принятия задания, но до сохранения квитанции. После перезапуска ключ навсегда возвращает «уже передавалось». Swift также переводит любое завершение lp с ненулевым статусом в неизвестный исход, без восстановления по конкретному заданию. Сбой сохранения успешной квитанции оставляет ту же проблему после рестарта. Запрет слепого повтора нужен, но он не выполняет исходный P1-04 про восстановление результата.

Подготовка PNG/драйвера до mark теперь исправлена; претензия относится именно к оставшемуся окну неопределённости. Встроенные тесты подтверждают блокировку неизвестного ключа, но не его восстановление. В настоящую очередь искусственные ошибки не вносились.

**Минимальное исправление.** Сохранять доступные сведения для сопоставления с ОС (очередь и стабильный идентификатор/название задания, номер ОС сразу после его появления), добавить проверку прежнего результата. При принципиально неизвестном исходе требуется явное решение оператора после проверки очереди/бумаги. Отсутствие задания в короткой истории ОС само по себе не доказывает, что оно не печаталось. Не очищать mark по таймеру и не подменять повтор новым ключом.

## Рекомендации по рискованным изменениям

### Mac: media и number-up

**Автоматический media — откатить.** Причина и воспроизводимый выбор неправильного относительно default варианта приведены в P1-01. На совпадение только 58×40 полагаться нельзя.

`number-up=1` сам по себе задаёт одну страницу на лист и не выбирает другой носитель; CUPS по умолчанию использует 1-up. Это разумная защита, если требуется исключить унаследованный n-up. Но сейчас она зачем-то связана с успешным matchMedia: при отсутствии точного имени не применяется вообще. Для строгого сохранения вчерашнего поведения в этом выпуске рекомендую откатить добавленную пару опций целиком. Позже `number-up=1` можно вводить отдельно от media после сравнения растра/бумаги. Утверждения, что именно number-up=1 портит этикетку при исходном 1-up, оснований нет. [Контракт number-up в CUPS](https://www.cups.org/doc/options.html).

### Mac: RGBA → белый фон

**Само сведение прозрачности — оставить.** Оно нужно для canvas-PNG, где наличие RGBA ещё не означает фактически прозрачный фон. Контекст создаётся с исходными image.width/image.height, изображение рисуется 1:1; дополнительных resize и поворота нет. Изолированный тест 464×320 с чёрными непрозрачными модулями и прозрачным окружением дал точное совпадение всех RGB-пикселей с эталонным alpha-composite на белом: 40 000 чёрных и 108 480 белых, промежуточных серых нет. Это проверка растра, не декодирование настоящего DataMatrix и не бумага. Полупрозрачные исходные края закономерно станут серыми; тест не доказывает отсутствие сглаживания, уже внесённого canvas.

**Метаданные — доработать.** `CGImageDestinationAddImage(destination, flat, nil)` на строке 188 теряет исходные DPI. Проверено PNG с 203×203 DPI: до преобразования есть DPIWidth/DPIHeight и PNG XPixelsPerMeter/YPixelsPerMeter, после нет; пиксельные размеры 58×40 сохранены. Новый контекст принудительно sRGB, произвольный входной профиль не сохраняется побитово. Для проверенного sRGB чёрно-белого растра пиксели не изменились. Непрозрачный PNG без alpha возвращается побайтно прежним; RGBA даже с alpha=255 проходит перекодирование.

Не утверждаю, что потеря одинаковых DPI по двум осям обязательно изменит размер при fit-to-page: при вписывании в ту же область и том же отношении сторон масштаб обычно задаёт область страницы. Для другого PNG/фильтра, неравных DPI или профиля эквивалентность не доказана. Минимально сохранять разрешение и проверить свойства выходного PNG, явно отключить интерполяцию для дополнительной защиты 1:1 пути. Не откатывать белый фон ради метаданных; не обещать читаемость ЧЗ без печати и сканирования.

### Windows: поворот и DPI

**Оставить исправление физических пропорций и дискретный поворот.** Формула использует дюймы на пиксель исходника, затем отдельно DPI X/Y, то есть квадратный модуль остаётся физически квадратным при разных разрешениях осей. `Image.Transpose.ROTATE_90` — поворот на 90° против часовой стрелки без интерполяции; не отражение. Направление может изменить положение текста относительно выхода рулона, но не искажает геометрию QR/DataMatrix.

Для обычного изображения 580×400 и области 464×320 при 203×203 DPI проверено `(rotate=false, x=0, y=0, w=464, h=320)`: вчерашний прямоугольник сохраняется. Для портретной области 320×464 — `(true, 0, 0, 320, 464)`. Для физически тех же 58×40 при 203×600 DPI — 464×946, без поворота. Поэтому изменение не должно разворачивать обычную согласованную 58×40 очередь; это подтверждено математикой и подменой device caps, не реальным драйвером.

Порог строго >10% сравнивает линейный масштаб, а не площадь. Поворот сработает и для необычных пропорций растра/печатаемой области, если даёт такой выигрыш. Если драйвер уже правильно развернул область, дополнительного поворота на обычном размере нет. Код всё ещё не задаёт размер бумаги из widthMm/heightMm: выбранный в Windows A4 останется A4. Это прежнее ограничение исходного P1-02, и исправление DPI его не закрывает; не менять всем рабочим очередям DEVMODE без проверки соответствующего сценария.

### Singleton, история и таймауты

**Mutex/SO_EXCLUSIVEADDRUSE, flock, SIGTERM → SIGKILL и чтение pipe — оставить.** Это целевые улучшения. Но завершить обработку проблем P0/P1 выше: более быстрый ошибочный ответ не равен восстановлению печати.

## Проверено — верно

- Mac arm64: исходник HEAD с новыми CoreGraphics/ImageIO/SQLite3 собран `swiftc -module-cache-path /private/tmp/wms631-review-swift-cache -O -whole-module-optimization ...`; `--self-test` завершился `WMS Print Direct macOS: package OK`. Встроенные проверки миграции обычного журнала, отката первой неудачной записи, белого фона, завершения игнорирующего SIGTERM процесса и вывода 400 КБ прошли. Первоначальная попытка использовала недоступный cache вне sandbox; после переноса только compiler cache во временный каталог сборка прошла.
- Python: `PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tools/print-agent -v` — 63 теста, **60 прошли, 1 skipped, 2 ошибки среды на bind localhost**. Windows-only invocation пропущен. Полностью зелёный прогон не заявляется. Дополнительные проверки реальных классов воспроизвели P0-01, P0-02 и P1-03, сумму ожиданий P1-02 и вычисления размещения Windows.
- Подготовка Windows PNG и DC теперь до mark/StartDoc. Swift декодирование, временный файл и выбор очереди — до mark/lp. Первый сбой persist откатывает Swift-состояние в памяти. Доказанный PrintNotSent позволяет повтор; неизвестный результат не отправляется автоматически. Hash считается по исходному PNG, поэтому само перекодирование RGBA не ломает дедупликацию прежнего ключа.
- Обычный успешный SQLite → JSON импорт переносит hash, receipt и NULL receipt, добавляет только отсутствующие ключи. Повторный импорт не стирает свежую JSON-квитанцию. JSON пишется атомарной заменой, внутри текущего Swift-процесса защищён lock. Повреждённый существующий JSON останавливает запуск и не превращается в пустой журнал. Ошибки/неполное чтение SQLite защищены иначе и дефектны — P0-01.
- В нормальном Mac-запуске flock удерживается открытым fd; наличие старого файла instance.lock после падения само по себе не удерживает блокировку. При втором экземпляре порт не перехватывается. В Windows named mutex дополняется SO_EXCLUSIVEADDRUSE до bind; согласно [контракту Microsoft](https://learn.microsoft.com/en-us/windows/win32/winsock/using-so-reuseaddr-and-so-exclusiveaddruse) это правильная защита от совместного bind. Реальную Windows-сессию тесты не заменяют.
- Старая версия без lock, но с /health, распознаётся после неудачного bind; первый процесс не убивается. Обычная чужая программа без правильного app получает понятную ветку ошибки. Проверка app — идентификация по ответу, не доказательство версии, состояния драйвера или физической печати.
- Браузер ждёт 30 с, не делает автоматический retry, последовательность Promise ограничена одной вкладкой/модулем. Сервер рассматривает ключ как целую строку: `scan`, `scan:chz`, `scan:copy:1` будут независимыми заданиями; повтор одной и той же строки с тем же PNG возвращает прежнюю квитанцию либо неизвестный исход. По одному этому нельзя доказать корректность ключей во всей связке QR/ЧЗ/копий.
- Сборщик Mac использует именно Swift, Windows — direct Python. Матрица содержит arm64, Intel и Windows x64, build.json сохраняет SHA. Новый SQLite3 импорт успешно слинковался на доступном arm64 без ручного добавления библиотек. Нативная локальная компиляция не является проверкой всех CI-архивов.
