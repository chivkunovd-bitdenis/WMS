## Новые дефекты

Ниже — дополнительные воспроизведения и незакрытые части прежних замечаний. Их наличие на складе не утверждается. Все отправки в проверках заменены функциями, возвращающими тестовую квитанцию; настоящий принтер не использован.

### P0 / R2-01 — двойная запись не защищает чистую Swift-установку и прежние JSON-ключи

**Места:** `tools/print-agent/wms_print_direct_macos.swift:313`, `:321`, `:330`, `:347`, `:371`; `tools/print-agent/wms_print_direct.py:198`, `:209`.

В первом сценарии настоящий Swift `Printer` печатает в новом временном каталоге и возвращает `swift-1`. Проверка сразу после вызова: `sqliteExists false`. Затем настоящий Python `Printer` открывает тот же каталог, получает тот же ключ и тот же PNG, возвращает `python-new-1`; счётчик новых отправок равен **1**. Ничего повреждать или удалять для этого не нужно: `mirror` включается только после чтения уже существующей БД, которой у чистой Swift-установки нет.

Во втором сценарии в каталоге есть корректный JSON с `swift-1` и корректная SQLite-таблица прежней версии, но этого ключа в ней нет. Новый Swift возвращает `swift-1`, а SQLite остаётся пустой (`sqliteRows [:]`). Последующий Python снова отправляет тот же ключ один раз. Это соответствует обновлению с версии, которая сохраняла новые задания только в JSON: исправление зеркалирует будущие записи, но не переносит уже имеющуюся историю в обратную сторону.

Это незакрытая часть P0-02, а не утверждение, что обычный Swift → Swift создаёт дубль. Для обратной совместимости нужен совместимый SQLite и перенос существующих JSON-ключей при нормальной установке; нельзя считать лишь будущие двойные записи полной защитой. Согласованную отдельную политику для повреждённого SQLite этот вывод не отменяет.

### P1 / R2-02 — повтор, начавший ожидание до mark, получает ложное «не отправлялось»

**Места:** `tools/print-agent/wms_print_direct.py:279` и `tools/print-agent/wms_print_direct_macos.swift:348`.

Последовательность: первый запрос ещё готовит задание, второй запрос с тем же ключом читает пустую историю и ждёт общий слот; первый сохраняет отметку и входит в медленную отправку; второй исчерпывает ожидание. В ветке неудачного захвата блокировки нет повторной проверки ключа — она есть только после успешного захвата.

Python-воспроизведение с бюджетом 0,4 с: первый ответ — `UnknownPrintOutcome`, второй через 0,405 с — `PrintNotSent` с «Это задание не отправлялось». После освобождения тестовой отправки в SQLite появилась квитанция `late-1` для этого же ключа. Swift-воспроизведение с сокращённым сроком второго запроса: второй вернул «Принтер занят предыдущим заданием. Это задание не отправлялось; повторите», затем первый и следующий запрос вернули `race-1`. Отметка первого уже существовала к моменту ошибочного ответа второго.

Автоматический дубль в этом тесте не возник. Дефект — ложная информация оператору, который может вслед за ней создать отдельную копию. Нужно повторно определить состояние конкретного ключа и при отказе по сроку ожидания, сохранив различие между новым заданием и уже возможной отправкой.

### P1 / R2-03 — ожидание записи SQLite разрешает начать отправку после 25 секунд

**Места:** `tools/print-agent/wms_print_direct.py:204`, `:231`, `:235`, `:298`, `:300`; вызов ОС после mark: `:154`.

`mark()` проверяет оставшееся время только до записи БД. Затем `_execute()` может ждать SQLite до 10 секунд, удерживая `gate["lock"]`. Когда общий срок истекает, основной поток тоже ждёт этот lock и не может установить отмену. После успешной записи worker выставляет `marked = True` и продолжает отправку без повторной проверки времени.

Воспроизведено с неизменёнными штатными параметрами `PRINT_TIMEOUT=25`, `MINIMUM_TO_START=6`: тестовая подготовка занимает 18,5 с; другая настоящая SQLite connection удерживает `BEGIN EXCLUSIVE` ещё 7,7 с непосредственно перед mark. Блокировка снимается до локального sqlite timeout, запись завершается. Фактический результат: ответ пришёл через **26,244 с**, а тестовая отправка началась на **26,244 с**, уже после общего срока. Это не измерение настоящего GDI, но это реальная запись/блокировка SQLite и настоящий код дедлайна.

Нужно учитывать оставшийся срок внутри ожидания записи и повторно проверять разрешение на отправку после записи, до границы ОС. При отказе до ОС состояние журнала должно сохранять правдивый результат «не отправлялось». Один `join(остаток)` не ограничивает последующий безусловный захват lock.

### P2 / R2-04 — одинаковый build всё ещё не означает «работает»

**Места:** `tools/print-agent/wms_print_direct.py:366`, `:437`, `:458`; `tools/print-agent/wms_print_direct_macos.swift:532`, `:797`, `:813`.

Это оставшаяся часть прежнего P2-01, не новая регрессия. Python специально читает тело HTTP 503, Swift вообще не проверяет статус ответа; обе реализации берут только app/build. Поэтому существующий процесс с тем же build, но ошибкой определения принтера, при втором запуске объявляется работающим. `/health` Python также не проверяет `printer.hung`, поэтому зависший обработчик при доступном default printer выглядит здоровым.

Сравнение версий исправлено правильно. Для утверждения «работает» нужно отдельно учитывать доступность печати либо ограничить сообщение проверенным фактом «эта сборка уже запущена». Вывод подтверждён чтением обеих веток, живой HTTP 503 в текущем sandbox не воспроизводился.

Ошибки относятся к запрету среды на открытие порта, не к проверенным утверждениям singleton; полностью зелёный прогон не заявляется. Дополнительные проверки R2-01/02 использовали настоящий класс Swift из временной копии исходника с заменённой точкой входа, затем настоящий Python-класс. **При нормальной доступной для записи SQLite с ожидаемой схемой остановка печати из-за новой двойной записи не воспроизведена:** штатный тест зеркалирования прошёл. При отсутствии SQLite Swift также продолжает работу — именно поэтому обратный запуск Python остаётся незащищённым. BUSY блокирует отправку по принятому решению и позволяет продолжить после снятия блокировки; битый старый SQLite не мешает запуску и отправке. Не вводилось дополнительного требования о запрете работы на повреждённом legacy-файле.

Ключ с неизвестным исходом остаётся заблокированным после перезапуска по решению P1-04. Отдельно бесконечно зависший Python worker всё ещё удерживает общий слот до завершения процесса: теперь текст предлагает перезапуск, а самостоятельного завершения такого worker нет.
