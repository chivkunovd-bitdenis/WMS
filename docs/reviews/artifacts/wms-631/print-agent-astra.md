## Дефекты

### P1-01. Mac не задаёт носитель и ориентацию; известный конфликт PageSize не исправлен

**Где:** `tools/print-agent/wms_print_direct_macos.swift:87–106,141–151`; `tools/print-agent/wms_print_direct.py:47–54,122–132`; поля размеров объявлены в `frontend/src/utils/printPreparedQr.ts:3–8`.

**Сценарий:** Swift выполняет `lp -d <queue> -o fit-to-page -o copies=1 -- label.png`. Python передаёт в `cupsPrintFile` только `fit-to-page`, `copies`, `number-up`. Ни один путь не читает `widthMm/heightMm`, не проверяет доступные размеры очереди, не задаёт `media/PageSize` и `orientation-requested`. При `DefaultPageSize=58x40mm`, когда PPD содержит только `58x40mm.Borderless`, программа сохраняет неоднозначность драйвера. Присланное владельцем поведение Letter/поворот/обрезание здесь не устранено; конкретный выбор Letter в этой сессии не воспроизводился. По [документации CUPS](https://openprinting.github.io/cups/doc/options.html), fit-to-page масштабирует относительно выбранной страницы, а размер и ориентация задаются отдельными параметрами. В Swift дополнительно не переопределён `number-up`: сохранённая настройка нескольких страниц на лист может влиять на размер.

**Минимально исправить:** сопоставлять запрошенные миллиметры с поддерживаемым форматом очереди, включая точное имя `58x40mm.Borderless`; передавать выбранный media, однозначную ориентацию и одну страницу на лист в конкретном задании. Проверять итоговую геометрию без изменения глобальных настроек очереди. Отдельно прогнать конфликт DefaultPageSize/PPD и физический рулон 58×40.

### P1-02. Windows игнорирует миллиметры, не поворачивает этикетку и сохраняет пропорции только в пикселях

**Где:** `tools/print-agent/wms_print_direct.py:60–93`; создание DEVMODE — `tools/print-agent/wms_print_runtime.py:359–408`.

**Сценарий:** direct-адаптер заменяет проверку размера проверкой «печатаемая область положительная». DEVMODE меняет копии, но не PaperWidth/PaperLength/Orientation. `ratio=min(HORZRES/image.width, VERTRES/image.height)` вписывает любую картинку в текущую страницу. Выбор 58×40 в WMS не изменяет формат задания; при A4 получится большая этикетка на A4. При портретной области 320×464 и изображении 580×400 тест получил прямоугольник `(0,121,320,342)`: рисунок уменьшен примерно до 40×27,65 мм, а не повёрнут на 58×40. При разных DPI по X/Y пиксельное сохранение пропорций искажает физические модули: на тестовых 203×600 dpi область рисунка 464×320 означает примерно 58,06×13,55 мм. Это расчёт и тест адаптера с подменённым драйвером, не физический Windows-прогон.

**Минимально исправить:** учитывать миллиметры, DPI каждой оси, физический формат и печатаемую область; выбирать ориентацию задания и согласовывать DEVMODE через драйвер. Поворот — кратно 90°, размеры кода после размещения — проверяемые. Не масштабировать молча на произвольный формат по умолчанию.

### P1-03. Обновление Mac Python → Swift сбрасывает защиту от уже выполненных заданий

**Где:** Python — `tools/print-agent/wms_print_direct.py:109–117,133–149`; Swift — `tools/print-agent/wms_print_direct_macos.swift:120–134,155–168`; выбор Swift — `tools/print-agent/build_console.py:27–37`.

**Сценарий:** Python сохраняет `direct/direct-jobs.sqlite3`, Swift читает исключительно `direct/direct-jobs.json`. Импорта SQLite или проверки существования старого журнала нет. После смены программы повтор того же ключа и PNG становится новым заданием. **Воспроизведено:** старый Python записал квитанцию `old-python-1` в настоящий временный SQLite; Swift, получив тот же каталог, ключ и PNG, вызвал подменённую отправку ещё раз и вернул `new-swift-1`.

**Минимально исправить:** до первой печати выполнить атомарный перенос старых ключей, хешей, квитанций и неизвестных исходов. Не начинать с пустой истории при найденном старом журнале. Учитывать обратный запуск старого бинарника после обновления; одной миграции вперёд недостаточно, если обе версии продолжают независимо писать разные журналы.

### P1-04. Достоверный отказ до отправки навсегда превращается в «уже передавалось»; неизвестный исход не восстанавливается

**Где:** Python — `tools/print-agent/wms_print_direct.py:133–149` и декодирование/создание DC на `68–77`; Swift — `tools/print-agent/wms_print_direct_macos.swift:137–169` и создание временного файла на `88–96`.

**Сценарий:** отметка без receipt сохраняется раньше декодирования PNG/подготовки Windows-драйвера или создания временного файла Swift. Даже доказанная ошибка до `StartDoc/lp` блокирует все повторы ключа. **Воспроизведено в обеих реализациях:** первая подменённая отправка отказала до приёма ОС; вторая попытка не вызвала отправку, ответила «Задание уже передавалось». Отдельно Swift после отказа первого `persist()` оставляет отметку в памяти: устранение ошибки записи не помогает до перезапуска, хотя отправки вообще не было. Это тоже воспроизведено.

При сбое после приёма ОС, но до сохранения receipt, запрет слепого повтора правильный. Однако нет поиска результата в spooler/CUPS, состояния достоверного отказа, сохранённого файла этикетки или способа завершить именно этот запрос. Уже сохранённая квитанция также возвращается, если задание затем отменили в ОС. Гарантируется ограничение повторных отправок в узких условиях, но не доставка каждой этикетки.

**Минимально исправить:** полностью готовить и проверять файл/драйвер до необратимой границы; различать доказанный отказ и возможную отправку. Сохранять идентификатор задания в ОС и данные для сверки, восстанавливать наблюдаемый результат. Для действительно неизвестного результата оставить явное решение оператора после проверки очереди, не снимать защиту таймером и не выдавать новый ключ автоматически. При неудаче первой записи Swift откатывать только ещё не отправленное состояние в памяти.

### P1-05. Зависший драйвер блокирует все последующие задания; браузерный таймаут не останавливает печать

**Где:** Windows — `tools/print-agent/wms_print_direct.py:69–84,133–147`; Swift — `tools/print-agent/wms_print_direct_macos.swift:37–62,153–168`; браузер — `frontend/src/utils/printDirectQr.ts:7–14,20–24`.

**Сценарий:** общий lock удерживается весь вызов системной печати. У Windows нет предела ожидания GDI; [Microsoft документирует StartDoc как блокирующую функцию](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-startdoca). Swift по таймауту посылает SIGTERM, но затем без предела ждёт завершения; stdout/stderr читает лишь после `waitUntilExit`, поэтому заполнение pipe тоже может остановить процесс. **Проверка Swift:** ребёнок, игнорирующий SIGTERM, при timeout=0,1 с вернул управление лишь через 2,07 с, после собственного завершения.

Браузер отменяет ожидание через 30 с, Mac допускает 60 с на `lp`. Первый job может уйти в принтер после показанной ошибки. Браузер затем допускает следующий запрос; несколько запросов могут ждать lock сервера и пережить свои клиентские таймауты. Это не доказанный дубль одного ключа, но оператор больше не знает, какие этикетки ещё выйдут и в каком порядке между вкладками.

**Минимально исправить:** ограничить жизнь рабочего процесса печати, читать pipe во время исполнения, отделить приём/проверку состояния от блокирующего драйвера. После клиентского таймаута сверять прежний ключ; не считать abort отменой задания. Принудительное завершение рабочего процесса означает неизвестный исход и не разрешает автоматическую повторную печать.

### P1-06. Windows: занятый порт не является надёжной защитой от второго экземпляра

**Где:** `tools/print-agent/wms_print_direct.py:18,242–249`; в отличие от старого runtime direct не вызывает `single_instance` (`wms_print_runtime.py:121–158`).

**Сценарий:** используется стандартный `ThreadingHTTPServer`. В поставляемом Python 3.13 `HTTPServer.allow_reuse_address=1` ([исходник CPython](https://raw.githubusercontent.com/python/cpython/3.13/Lib/http/server.py)); Windows не получает `SO_EXCLUSIVEADDRUSE`. По [контракту Winsock](https://learn.microsoft.com/en-us/windows/win32/winsock/using-so-reuseaddr-and-so-exclusiveaddruse) повторный bind с SO_REUSEADDR может пройти, а получатель соединений становится неопределённым. Следовательно, ветка `except OSError: уже запущена` не обеспечивает singleton на Windows. При одном SQLite первичный ключ всё ещё препятствует двум INSERT одного id, но конкурирующие экземпляры могут давать ошибки; разные пользовательские каталоги имеют независимую историю. Реальный двойной запуск на Windows не воспроизводился; вывод основан на коде и контракте ОС.

**Минимально исправить:** независимая блокировка экземпляра плюс эксклюзивный bind Windows. При занятом порте проверить ответ/версию уже работающего WMS Print и корректно завершить второй запуск; чужой процесс отличать от своего. Не завершать произвольного владельца порта.

### P2-01. Повторный запуск не проверяет живость/версию; direct не имеет автозапуска и восстановления процесса

**Где:** Python — `tools/print-agent/wms_print_direct.py:242–249`; Swift — `tools/print-agent/wms_print_direct_macos.swift:331–365`; упаковка — `tools/print-agent/build_console.py:40–59`.

**Сценарий:** на Mac второй экземпляр при занятом порте пишет «уже запущена либо локальный порт занят» и выходит с кодом 1; Python при OSError пишет то же и выходит штатно. Нет проверки `/health`, соответствия версии или понятного различения чужого процесса и рабочего WMS Print. Если старая версия осталась запущена, открытие новой папки не обновляет действующую программу. Процесс direct требует открытой консоли; после её закрытия, аварии или перезагрузки автоматического восстановления нет. Это ограничение direct, а не отсутствие кода LaunchAgent/Task Scheduler в старом runtime.

**Минимально исправить:** при повторном запуске проверять identity/version и состояние существующего сервера; добавить контролируемую замену процесса при обновлении. Если требуется работа после входа/сбоя — регистрировать именно direct-бинарник в штатном механизме ОС. Сохранить существующий журнал. До этого оператору явно нужна повторная ручная загрузка программы после перезапуска компьютера.

### P2-03. PNG проверяется по восьми байтам; прозрачность Windows может превратиться в чёрный фон

**Где:** `tools/print-agent/wms_print_direct.py:68,127–131,145–147`; `tools/print-agent/wms_print_direct_macos.swift:146–151,164–166`; тестовая фикстура — `test_wms_print_direct.py:9–12`; Swift self-test — `wms_print_direct_macos.swift:315–318`.

**Сценарий:** строка, содержащая лишь PNG-сигнатуру, проходит общую валидацию и получает отметку «отправлялось». Тесты сами используют недекодируемые изображения. На Windows реальное декодирование откажет уже после записи маркера; на Mac файл будет передан CUPS, а поздний отказ фильтра не отслеживается. Ограничены сжатые байты, но не размеры/число пикселей. Кроме того, `.convert("RGB")` отбрасывает альфа-канал без белой подложки. **Проверено Pillow:** `(0,0,0,0)` → `(0,0,0)`. Чёрный DataMatrix на прозрачном PNG может получить чёрное окружение. Для текущих серверных PNG с `alpha=False` этот конкретный риск не установлен.

**Минимально исправить:** до фиксации начала печати полностью декодировать PNG, ограничить разумный размер растра, свести прозрачность на белый фон. Проверять реальными PNG, а не одной сигнатурой. Не добавлять сглаживающее масштабирование чёрно-белых модулей.

### P2-06. Старый Windows NSIS восстанавливает файлы при ошибке обновления, но не запускает прежний процесс

**Где:** `tools/print-agent/windows-installer.nsi:15–22,38–54`; штатный старт — `tools/print-agent/wms_print_runtime.py:688–700`.

**Сценарий:** старый процесс остановлен перед заменой. Ошибка распаковки либо регистрации/запуска фоновой задачи приводит к возврату `.previous` и Abort. В ветках отката нет команды запуска восстановленного runtime. Сообщение «previous version was restored» не означает, что печать возобновилась. Код прочитан; настоящий NSIS upgrade/rollback на Windows не запускался. Дефект относится к paired-пакету, не к direct ZIP.

**Минимально исправить:** после успешного возврата файлов восстановить регистрацию и запуск старой версии, проверить результат; при неуспехе явно сообщить, что файлы сохранены, но программа остановлена. Приватное состояние не удалять.

### P2-07. Старый runtime не сохраняет новое сопряжение до первого внешнего запроса

**Где:** `tools/print-agent/wms_print_runtime.py:809–855`; обещание восстановления — `tools/print-agent/README.md:35–36,143–146`.

**Сценарий:** новый `connection_id/device_token` создаётся на 825–831, `/pairing` вызывается на 833, а `connection.json` записывается только после полного сопряжения на 854. Потеря первого ответа/закрытие окна до этого момента теряет локальную идентичность запроса; следующий запуск создаёт другое сопряжение. README обещает сохранить её до первого POST. Это только прежний paired-контур; direct не использует сопряжение.

**Минимально исправить:** сохранять незавершённое новое сопряжение до первого POST; при reconnect держать его отдельно от действующего подключения, чтобы не затереть рабочий профиль. Завершение повторять с теми же идентификаторами.

**Минимальный модуль при 203 dpi.** Одна точка = `25,4 / 203 = 0,12512 мм`; две = `0,25025 мм`; три = `0,37537 мм`; четыре = `0,50049 мм`. Одна точка — физический шаг, не универсальный допустимый минимум для ЧЗ. Размер модуля определяется применимым профилем маркировки и качеством печати; условие «не меньше 0,25 мм» даст минимум 2 точки, а «не меньше 0,255 мм» уже 3. Для символа N×N с белым полем хотя бы один модуль с каждой стороны требуется минимум `(N+2)×k` точек при k точках/модуль. Например, 44×44 при k=3 занимает 138 точек ≈17,27 мм вместе с минимальным полем. [GS1 требует quiet zone не меньше одного модуля](https://www.gs1.org/standards/gs1-datamatrix-guideline/25). Это расчёт для проектирования; читаемость складским сканером не проверена. 58×40 мм при 203 dpi — приблизительно 464×320 точек до полей драйвера. Уменьшение всей этикетки может уменьшить модуль ниже нужного размера, даже если PNG очень высокого разрешения. Для ЧЗ нужны итоговый растр в разрешении принтера, сохранение квадратных модулей без дробного/сглаживающего пересчёта и независимое декодирование с бумаги.
