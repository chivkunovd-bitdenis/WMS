## Замечания

### F1 — блокер: после перехода по истории реквизиты сохраняются другому селлеру

**Место:** `frontend/src/screens/v2/SellerCardScreen.tsx:144–149` — новое использование окна без пересоздания при смене селлера. Связанное поведение: `frontend/src/screens/ff/FfBillingProfilesDialog.tsx:72–78,140–151`; маршрут `frontend/src/App.tsx:3577–3580`.

**Что не так.** При смене параметра `:sellerId` в том же маршруте React сохраняет экземпляр карточки и её окна. В `FfBillingProfilesDialog` адрес чтения и сохранения определяется состоянием `scope`, которое принимает `sellerId` только при первом создании компонента. Новый `sellerName` меняет заголовок окна, но `scope` остаётся прежним. Поэтому в карточке A окно озаглавлено именем A, а GET и PUT идут к B. Проверка прав на сервере не остановит такую запись: оба селлера принадлежат этому администратору.

Это регрессия нового места использования окна: раньше отдельная строка списка имела постоянный `key={s.id}` и постоянного селлера. `SectionErrorBoundary` тоже не пересоздаёт исправный компонент при смене адреса (`frontend/src/components/errors/ErrorBoundary.tsx:67–73`).

**Почему это дефект.** Нарушены [R2 и R5](../../../requirements/WMS-491.md#4-требования): карточка и существующее окно должны относиться к открытому селлеру. Нарушен контекст действия из «Плохого случая 1» библиотеки владельца; применим B08 — изменение одного объекта не должно изменять соседний. Последствие — запись банковских/юридических реквизитов не тому селлеру.

**Как воспроизвести.**

1. Под админом ФФ открыть карточку A, вернуться в список, открыть карточку B.
2. Через меню истории кнопки «Назад» перейти сразу на карточку A, пропустив промежуточный список. Эквивалент в проверке роутера — `navigate(-2)` после последовательности A → список → B.
3. Нажать «Реквизиты», затем «Сохранить»; для проверки последствия можно изменить поле.
4. Ожидается PUT `/api/billing/profiles/sellers/A`. Фактически отправляется PUT `/api/billing/profiles/sellers/B`, хотя карточка и заголовок окна относятся к A.

**Доказательство:** воспроизведено на смонтированной карточке с реальным окном. Проверка ожидаемого пути PUT упала: ожидался `seller-a`, получен `seller-b`. Реальную запись в БД не выполнял. При исправлении нужно связать жизненный цикл/состояние окна с текущим селлером, сохранив обычный выбор реквизитов ФФ в «Расчётах».

### F2 — существенное: нажатие пункта меню не сбрасывает фильтр, полученный из карточки

**Место:** `frontend/src/screens/v2/FfProductsCatalogScreen.tsx:644–654`, `frontend/src/screens/ff/FfBillingScreen.tsx:267–277`. Пункты меню: `frontend/src/layouts/AuthedAppLayout.tsx:265,270`.

**Что не так.** Эффект применяет селлера и удаляет `seller_id` из адреса через `replace`. После этого на экране остаётся локальный фильтр A, а адрес уже совпадает с обычным адресом из меню. Клик по пункту меню того же раздела не пересоздаёт компонент и не сбрасывает его состояние. В эффектах нет обработки такого входа: при отсутствии параметра они сразу завершаются.

**Почему это дефект.** Прямое нарушение [R9/C9](../../../requirements/WMS-491.md#6-проверки): сразу после перехода с фильтром A открытие раздела из меню должно показывать «Все селлеры». Сейчас человек видит неполный каталог/отчёт после обычного открытия раздела. Пустой каталог на стенде мог скрыть разницу в строках, но состояние фильтра ошибочно независимо от наличия товаров.

**Как воспроизвести.**

1. Из карточки A нажать «Товары» и дождаться применения A.
2. Не уходя на другую страницу, нажать «Каталог» в меню.
3. Фильтр остаётся A вместо «Все селлеры». Повторить «Выставить счёт» → «Расчёты» в меню: результат тот же.

**Доказательство:** две независимые проверки настоящих экранов с обычной ссылкой меню. В «Расчётах» значение селекта после клика — `seller-a`, ожидалось `all`; в каталоге скрытый input фильтра также сохраняет `seller-a`. Исправление должно отличать очистку параметра самим экраном от нового входа из меню и не возвращать старый фильтр после его ручной смены.

### F3 — существенное: при смене закреплённого селлера панель смешивает счета разных селлеров

**Место:** `frontend/src/screens/ff/FfBillingInvoicesPanel.tsx:243–247` — новый эффект `fixedSellerId`; накопление строк `:253–269`; использование без ключа селлера — `frontend/src/screens/v2/SellerCardScreen.tsx:197`.

**Что не так.** Новый эффект меняет только `sellerId`, оставляя `cursor`, `rows`, поиск, статус и открытый счёт от предыдущего селлера. Если нажимали «Загрузить ещё», новый запрос идёт с курсором старого селлера, а ответ добавляется к старым строкам вместо замены. Чужие для текущей карточки счета остаются в таблице постоянно; колонка «Селлер» в этом режиме скрыта, поэтому отличить их нельзя. Это смешение селлеров одного тенанта, не доказанная межтенантная утечка.

**Почему это дефект.** [R6](../../../requirements/WMS-491.md#4-требования) прямо требует все счета только открытого селлера. Применим B08: проверка единственного селлера не выявляет побочное влияние на другого.

**Как воспроизвести.**

1. Посетить карточку A → список → карточку B, у B должно быть более одной страницы счетов.
2. В B нажать «Загрузить ещё» и дождаться второй страницы.
3. Через меню истории вернуться сразу на A, как в F1.
4. В запросе счетов A остаётся курсор B; таблица сохраняет строки B и добавляет полученные строки A. При некоторых датах курсора часть счетов A также будет пропущена.

**Доказательство:** при смене `fixedSellerId` на настоящем компоненте после дозагрузки DOM содержал одновременно `A-INVOICE-1`, `A-INVOICE-2` и `B-INVOICE-1`. Ответы API имитированы; реальная пагинация БД не запускалась. При смене закреплённого селлера нужно начинать независимый список с первой страницы и очищать относящееся к предыдущему селлеру состояние, включая открытый счёт.

### F4 — существенное: поздний ответ загрузки затирает актуальные реквизиты

**Место:** `frontend/src/screens/v2/SellerCardScreen.tsx:102–121`, повторная загрузка после сохранения `:148`.

**Что не так.** Каждый `loadProfile()` безусловно записывает свой результат через `setProfile`. Нет отмены предыдущего запроса, проверки его актуальности или привязки ответа к текущему селлеру. Запросы возникают и при входе, и при поступлении общего списка селлеров, и после сохранения. Более старый ответ может завершиться позже нового и заменить уже правильные данные. Пересоздание карточки по id само по себе не устранит гонку двух загрузок одного селлера до и после сохранения.

**Почему это дефект.** Нарушены [R4 и R5](../../../requirements/WMS-491.md#4-требования): карточка должна показывать реквизиты своего селлера и сохранённые новые значения. AGENTS §3 требует согласованного поведения после сбоев; B08 отдельно предлагает проверять, что остаётся последнее изменение.

**Как воспроизвести.**

1. В тестовой среде задержать ответ первого GET реквизитов карточки A, сохранив в нём старый снимок данных.
2. Открыть окно реквизитов, сохранить актуальные значения. GET окна и GET после сохранения должны завершиться раньше первого; убедиться, что карточка уже показывает новые значения.
3. Отдать задержанный старый ответ. Карточка заменит новые реквизиты старыми, хотя сохранение прошло успешно.
4. Второй вариант: задержать GET A, сменить маршрут на B без пересоздания карточки, получить B, затем отдать A — под именем B появятся реквизиты A.

**Доказательство:** оба порядка ответов воспроизведены. После успешного нажатия «Сохранить» и перечитывания карточка показывала `Legal NEW`; поздний ответ заменил его на `Legal OLD`. В проверке двух селлеров после загрузки B карточка заменила `Legal seller-b` на `Legal seller-a`. Проверки обращаются к реальному окну и эффектам, не вызывают `onSaved` напрямую.

### F5 — существенное: ошибка чтения выдаётся за отсутствие реквизитов/селлера

**Место:** `frontend/src/screens/v2/SellerCardScreen.tsx:108–115`; аналогичная подмена ошибки поиска селлера — `:85–89`.

**Что не так.** Любой неуспешный HTTP-ответ и сетевой сбой чтения профиля превращаются в `profile=null`, после чего карточка пишет «Не заполнены». Пользователь получает утверждение об отсутствии данных вместо сообщения, что они не загрузились. Самостоятельная загрузка списка селлеров тоже превращает ошибку в успешное завершение поиска с пустым результатом и показывает «Селлер не найден», если общий список ещё не пришёл.

**Почему это дефект.** [R4](../../../requirements/WMS-491.md#4-требования) разрешает «Не заполнены», когда реквизитов нет; HTTP 500 этого не доказывает. [R11](../../../requirements/WMS-491.md#4-требования) отличает несуществующего/чужого селлера от сбоя чтения. Применимы AGENTS §3 (продолжение работы после сбоя), B03 и B05 — ошибку нужно показывать как ошибку в контексте действия. Краткое сообщение о реальном сбое не является запрещённой владельцем повествовательной подсказкой.

**Как воспроизвести.** Для существующего селлера с заполненным профилем подменить GET `/billing/profiles/sellers/A` ответом 500 или сетевой ошибкой и открыть карточку. Фактически появляется «Не заполнены», сведений о сбое нет. Для второй ветки задержать общий список App и вернуть 500 самостоятельному GET `/sellers` карточки.

**Доказательство:** HTTP 500 профиля воспроизведён на настоящей карточке: появился `data-testid="seller-card-requisites-empty"` с текстом «Не заполнены». Ветка ошибки `/sellers` проверена по коду, отдельно не исполнялась. Необходимо различать успешное отсутствие данных и ошибку чтения; при ошибке повторного чтения не выдавать прежние сохранённые данные за отсутствующие.
