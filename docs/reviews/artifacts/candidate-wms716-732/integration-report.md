### 2.3 Слияние c (721, 732): конфликт backend/app/services/fbs_supply_service.py — главный содержательный

Сторона WMS-716: supply_worklist_statement(…) — единое SQL-выражение отбора поставок для строк списка и для чисел на вкладках (fbs_counts_service использует его в подзапросе).
Сторона WMS-721: вкладка поставки Ozon определяется производным статусом (supply_display_statuses по статусам отправлений), а не сохранённым; кандидаты читаются пачками, фильтр по производному статусу применяется до лимита; новая вкладка «shipped».
Разрешение: в supply_worklist_statement добавлен флаг ozon_candidates (для списка: все Ozon-поставки — кандидаты; без флага — прежняя строго SQL-выборка WMS-716); общий отбор вынесен в select_worklist_supplies (производный фильтр пачками, как в 721, и без лимита для чисел); list_supply_worklist использует его. Это моё слияние двух реализаций, не копия ни одной из них.
Следствие, которое пришлось чинить: без правки числа вкладок WMS-716 для Ozon считались бы по сохранённому статусу и расходились бы со списком WMS-721. В fbs_counts_service для групп active/delivery/done WB-поставки берутся SQL-подзапросом (marketplace != ozon), Ozon-поставки — тем же производным отбором. Добавлен тест backend/tests/test_wms716_721_candidate_counts.py; проверено, что без правки он падает (0 против 1).
Риск: на каждый запрос чисел производный отбор читает все Ozon-поставки арендатора вместе с заказами (без позиций). Нагрузку на большом арендаторе не измеряли.
Прочее: импорты sqlalchemy — Select (716) + delete, update (722).
