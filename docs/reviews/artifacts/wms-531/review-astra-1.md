## Находки

### F1 · P1 · Excel строится квадратично и держит весь журнал периода в памяти

**Место:** `backend/app/services/reporting_service.py:1525`; загрузка данных — `:1467–1478`, создание обычной книги — `:1497`.

В `_append` после каждой добавленной строки вызывается `sheet.max_row`. В установленном openpyxl это `max(self._cells)[0]`: просмотр уже накопленных ячеек. Следовательно, построение N строк повторно обходит растущую книгу N раз. Это квадратичный рост работы, независимо от скорости SQL. Дополнительно `scalars().all()` загружает все ORM-объекты движений периода; одновременно существуют обогащённые словари, индексы по товарам и полная книга в памяти.

**Воспроизведение:** выполнен отдельный локальный замер того же цикла `sheet.append(11 ячеек) → sheet.max_row → row_dimensions[index].outlineLevel = 2`: 1 000 строк — 1,381 с, 2 000 — 4,003 с, 4 000 — 20,225 с. Это диагностический замер конкретного участка, не измерение production и не полный тест годового объёма. Полная локальная выгрузка меньшего набора из 515 движений прошла, что не опровергает проблему роста.

**Почему дефект:** R15 требует полного большого отчёта. Новый XLSX-путь содержит подтверждённую причину резкого замедления; память также растёт со всем журналом периода. Ограничение дат в одном запросе журнала Ozon этого не устраняет. Нужны постоянный счётчик номера строки и обработка данных/книги ограниченными порциями либо иной подход без повторного обхода всей книги. После исправления нужен C11 на согласованном объёме PostgreSQL.

Дополнительно для оценки R15: `build_overview` читает все движения текущего и предыдущего периода в Python (`:733`, `:749`); поиск документов Ozon при каждом раскрытии может прочитать все JSON-позиции арендатора за выбранный период (`:1074`). Обогащение документов пакетное, обычного запроса на каждый товар/движение не найдено, но отсутствие такого N+1 не означает ограниченного расхода памяти. Фото и сведения о товарах загружаются до обрезания страницы товаров (`:550–567`).

### F2 · P2 · Документ второй позиции Ozon теряется, если журнал подготовлен раньше периода списания

**Место:** `backend/app/services/reporting_service.py:1086–1087`.

Новый поиск по `ozon_positions_json` ограничен датой создания **журнала**, хотя отчёт ограничивает дату **движения**. Предположение в комментарии, что они создаются одной операцией, неверно: `fbs_ozon_packaging_service.py:299–346` готовит журнал до внешней передачи, а `:349–412` позднее записывает движения в сохранённый рецепт. Восстановление после сбоя или переход через границу суток/месяца дают разные периоды.

**Воспроизведение:** Ozon-заказ с товарами P1/P2; журнал создан 31.08, оба списания — 10.09. `shipment_movement_id` указывает P1, JSON содержит точный ID списания P2. Запрос сентября с `operation=FBS` на общей странице находит документ обоим основным движениям через P1. Запрос того же периода с `product_id=P2` возвращает для P2 `document=null`. Аналогичная потеря возможна при разделении движений по страницам. Связь существует и не требует угадывания.

**Почему дефект:** нарушены R2–R4 и R13: документ зависит от соседних строк страницы, а раскрытие товара может отличаться от Excel. Искать нужно по сохранённым ID движений, не отбрасывая точную связь по дате подготовки журнала.

### F3 · P2 · Разделённое списание второй позиции Ozon не наследует документ по группе

**Место:** `backend/app/services/reporting_service.py:1113–1116`.

Поиск связанного соседа группы соединяет его только с `FbsShipmentReversalLedger.shipment_movement_id`. У многотоварного Ozon-заказа это ID первой позиции всего заказа; основная строка второй позиции связана через `ozon_positions_json`. Её дополнительные строки из разных мест/тары этот JOIN не находит.

**Воспроизведение:** P1 списан движением M1, P2 — движениями M2 и M3 с общим `transfer_group_id`; журнал указывает `shipment_movement_id=M1`, JSON содержит M1/M2. Все даты внутри сентября. В раскрытии P2 результат M2 — `Заказ Ozon №OZON-PROBE`, M3 — `document=null`. Сценарий воспроизведён отдельно от F2, после переноса даты журнала внутрь периода.

**Почему дефект:** R3 прямо требует документ для частей разделённого списания по общей группе с уже связанной строкой. Нужно учитывать и соседа, связанного через JSON-позицию, сохраняя запрет угадывать заказ по товару/времени/количеству.

### F4 · P2 · Поиск применяется к итогам операции, но игнорируется при раскрытии её движений

**Место:** `backend/app/api/reports.py:74–99`; `backend/app/services/reporting_service.py:1331–1381`.

У ручки движений и сервиса нет параметра `search`. Поэтому переданный клиентом поиск молча теряется. Группировка операций и Excel при этом используют поиск по товару.

**Воспроизведение:** у одного селлера Alpha с приходом 3 и Beta с приходом 7. `/reports/inventory?group_by=operation&search=ALPHA` возвращает «Приёмка», приход 3. `/reports/inventory/movements?operation=Приёмка&search=ALPHA` за те же даты возвращает оба товара с суммой 10. Это получено реальными локальными HTTP-запросами. Текущий фронт передаёт общий набор фильтров в раскрытие (`FfReportsPage.tsx:282–286`).

**Почему дефект:** R11 требует равенства суммы раскрытия приходу/расходу строки, R13 — равенства Excel и раскрытия при тех же фильтрах. Пробел существовал и раньше, но остаётся невыполненным условием этой задачи. Требуется единая область поиска для агрегата, количества страниц, движений и выгрузки.

### F5 · P2 · График использует селлера движения вместо текущего селлера товара, включая кабинет селлера

**Место:** `backend/app/services/reporting_service.py:672`, `:690`.

Плитки и таблицы переведены на `Product.seller_id`, но дневной ряд, сравнение с предыдущим периодом и часть предупреждений остаются на `InventoryMovement.seller_id`. Это снимок прошлого состояния, который может отличаться или быть пустым.

**Воспроизведение:** товары принадлежат A; у одного приход 3 записан со снимком B, у второго приход 7 — со снимком A. Фильтр A даёт плитку прихода 10, дневной ряд 7; фильтр B — плитку 0, дневной ряд 3. Затем сценарий повторён с 450 движениями и **входом под созданной тестовой учётной записью B**: `/reports/overview` вернул `in_qty=0`, но сумма `daily.in_qty=450` по товарам A.

**Почему дефект:** R10 требует отнесения всех движений к текущему владельцу товара. Кабинет показывает агрегаты товаров другого текущего селлера; это также нарушение изоляции области отчёта. Чужие названия/товарные строки в этом сценарии не раскрыты, утечка подтверждена именно для количеств графика. Нужен текущий товарный фильтр во всех частях overview. Старый фильтр не новый сам по себе, но после изменения основной области отчёта он оставляет наблюдаемое противоречие.

### F6 · P2 · Неполное перемещение без номера группы не вызывает предупреждения

**Место:** `backend/app/services/reporting_service.py:349`.

Проверка неполных перемещений заранее исключает строки с `transfer_group_id IS NULL`. Однако откат начала/конца их учитывает, а приход и расход исключают, как и требуется для расположения.

**Воспроизведение:** текущий остаток 5, в периоде единственное `stock_transfer_out=-5`, `transfer_group_id=null`. API возвращает `opening_balance=10`, приход 0, расход 0, `closing_balance=5`, `integrity_error=false`; overview — `has_incomplete_transfer=false`.

**Почему дефект:** R7 специально требует предупредить о неполном движении расположения, повлиявшем на общий остаток. Получено необъяснённое `10 + 0 − 0 ≠ 5`. Это проверка повреждённой/исторической записи, а не утверждение, что нормальный текущий писатель обязан создавать её. Нельзя достраивать вторую сторону; нужно обнаружить и обозначить расхождение.

### F7 · P2 · В Excel кабинета селлера остаётся уровень селлера и безымянный дубль итогов

**Место:** `backend/app/services/reporting_service.py:1542–1563`; аналогичный уровень операций — `:1598`.

`include_seller=False` удаляет только колонку и имя. Строка агрегата добавляется безусловно, товары остаются на уровне 1 и скрыты, движения — на уровне 2. При открытии файла видна безымянная строка четырёх чисел и «Итого», а товары нужно раскрывать из лишней группы.

**Воспроизведение:** выгрузка кабинета с одним товаром, приход 9, расход 2, остаток 7. Чтение созданного XLSX даёт:

```text
строка 2: уровень 0, видима, названия нет, числа 0 / 9 / 2 / 7
строка 3: уровень 1, скрыта, Excel product, числа 0 / 9 / 2 / 7
строки 4–5: уровень 2, скрыты, движения
строка 6: уровень 0, Итого, числа 0 / 9 / 2 / 7
```

**Почему дефект:** прямое нарушение R12.9 «без уровня и колонки Селлер». В кабинете товары/виды должны стать верхним уровнем, движения — следующим; безымянная строка селлера не нужна. Тест `test_excel_export_for_seller_cabinet_has_no_seller_column_or_level` этот дефект пропускает: проверяет заголовки и отсутствие имени, но не уровни и лишнюю строку.

### F8 · P2 · Любая положительная строка fbs_shipment названа сторно, в том числе известные ручные правки

**Место:** `backend/app/services/reporting_service.py:883–884`.

Подпись зависит только от знака. Наличие связи с историческим сторно, дата и происхождение записи не учитываются. При отсутствии всех связей результат будет **«FBS, сторно» / «без документа»**, количество войдёт в приход и группу FBS.

**Проверка:** прямое чтение ветки `row_operation_label` и ветки отсутствующего документа в `_enrich_movement_rows`. Для любого `fbs_shipment` с положительным количеством и без связей ответ однозначен. Ведущий сообщил четыре пакета разовых правок без автора: 04.09 09:26 — 384 шт. «Империя», 04.09 12:08 — 3 шт., 22.09 08:57 — FFAdam 43 и «Империя» 70. По сообщённому происхождению это не доказанные сторно заказов. Производственные строки в этом ревью повторно не запрашивались.

**Почему дефект:** отчёт приписывает данным неподтверждённый бизнес-смысл. R2 описывает положительные строки как историческое сторно до 05.09; эта предпосылка не охватывает приведённые правки. R3 правильно оставляет «без документа», но честное отсутствие документа не исправляет неверный вид операции. Нельзя объяснять это «старым кодом на проде»: ведущий прямо подтвердил свежий etalon. Нужна согласованная с аналитиком нейтральная подпись для положительных FBS-записей без доказанной связи со сторно; нельзя автоматически угадывать ни заказ, ни точную причину корректировки по дате/знаку.

### F9 · P2 · В Excel у приёмок и отгрузок теряется название вида документа

**Место:** `backend/app/services/reporting_service.py:1573–1574`, `:1609–1610`.

Excel записывает только `document["number"]`. Для приёмки/возврата/отгрузки этот номер не включает требуемый префикс; `kind` при формировании текстовой ячейки игнорируется. Для FBS номер уже полный, поэтому ошибка не видна на проверке только заказов.

**Воспроизведение:** штатный тестовый набор `_seed_excel_scenario` с приёмкой `display_number="№000042"`. В созданном файле ячейка «Документ» содержит ровно `№000042`, вместо «Приёмка №000042». Это подтверждено чтением XLSX. Особенно неоднозначна строка акта расхождений: в «Движении» стоит корректировка, а в документе остаётся голый номер связанной приёмки.

**Почему дефект:** R2 задаёт подписи «Приёмка №…», «Возврат №…», «Отгрузка №…»; R12 переносит документ в файл. JSON может передавать структурированные поля для форматирования фронтом, но XLSX — уже конечный результат. Требуется единое форматирование подписи документа без дублирования знака номера. Текущий тест `:1092` закрепляет неполную подпись.

### F10 · P2 · Текстовые поля экспортируются как формулы Excel

**Место:** `backend/app/services/reporting_service.py:1524`, `:1556–1558`, `:1603`.

Названия, артикулы и прочие текстовые значения передаются в `sheet.append` без принудительного текстового типа. openpyxl интерпретирует строку, начинающуюся с `=`, как формулу.

**Воспроизведение:** товар с названием `=1+1`. После выгрузки и повторного открытия через `load_workbook` ячейка B3 имеет `value="=1+1"`, `data_type="f"` (формула), хотя это имя товара. Исполнение формул во внешнем Excel не запускалось и не требуется для установления изменения типа ячейки.

**Почему дефект:** выгрузка меняет смысл пользовательского текста и не гарантирует равенство экрану по R13. Такие ячейки должны сохраняться текстом; числовые итоги и даты при этом должны остаться числовыми/датными. Проверять достаточно безвредной строкой `=1+1`.

5. **Товары без движений:** проходят случаи ненулевого остатка без движений вообще и в выбранном периоде; товар с нулями и без движений исключается. Товарные строки и их суммы относятся к текущему селлеру. Исключение — оставшиеся фильтры overview из F5. Равенство расчёта сумме InventoryBalance подтверждено; сквозная сверка с готовым экраном каталога WMS-532 и копией прода не проводилась. Прочитанный `/products/ff-catalog` возвращает карточки без количества, поэтому его HTTP 200 не выдаётся за такую сверку.
6. **Документы обычных путей:** тест C1 покрывает приёмку, возврат, акт расхождений, отгрузку на МП, WB/Ozon, историческое сторно через `reversal_movement_id`, старый подбор, инвентаризацию, передачу между селлерами, служебную приёмку передачи, загрузку ТЗ, ручную корректировку и старую отгрузку. Обогащение использует сохранённые связи, совпадение времени/количества не используется. Номер инвентаризации соответствует формуле API. Найденные исключения — F2/F3/F8/F9. Открытие документов в браузере здесь не проверялось.
7. **Постраничность и полнота файла:** штатный тест проходит 66 товаров и 210 движений товара. Отдельная выгрузка на 66 товарах, 450 движениях одного товара и 65 остальных движениях дала **515 строк движений в каждой группировке**, приход 515, итог `(0, 515, 0, 515)`. Локально полное формирование и чтение заняли 1,716 с «По товарам» и 1,089 с «По операциям». Это проверка отсутствия лимитов 50/200 в файле, а не C11. При поиске раскрытие операции расходится с агрегатом — F4.
8. **Excel обычных значений:** один лист, заголовок первой строкой, закрепление A2, уровни ФФ селлер → товар/вид → движения, числовые итоги, даты по Москве, последняя строка «Итого», MIME XLSX и `filename*` с периодом — подтверждены тестами и чтением созданных книг. Пустая область возвращает 422 `nothing to export for the selected period`. 367 суток возвращают 422 `period cannot be longer than 366 days`; русский текст на экране должен обеспечить фронт. Сортировка файла, кстати, не повторяет все переданные `sort_by/sort_order`: параметры валидируются, далее используются собственные сортировки по имени; это отмечено как ограничение согласования с фронтом, не отдельный блокирующий пункт R13 о числах.
9. **Права и обычная изоляция:** проверки `assert_inventory_read_access` и принудительного `seller_scope` сохранены. Повторно прошли сценарии запрещённых/разрешённых ролей, подмена `seller_id` другим селлером того же арендатора и чужого арендатора, поиск чужого товара и отсутствие его в XLSX/JSON. Обычная выгрузка чужих товарных строк не найдена. Подтверждённое исключение по данным графика описано в F5. Связи документов в основном читаются по глобальным ID из уже отобранных движений; произвольное повреждение межарендаторных FK отдельно не моделировалось.

## CSV и достоверность тестов

R12.1 и D6 требуют убрать **CSV из интерфейса**, а не однозначно удалить серверный адрес. C16, однако, прямо упоминает «удалённый CSV», поэтому замену серверной ручки нельзя уверенно назвать самовольным нарушением согласованной задачи. Объяснение исполнителя «два формата — два источника цифр» технически необязательно: форматы могли бы использовать общий расчёт. Практическая граница выпуска важнее: текущий `frontend/src/screens/ff/FfReportsPage.tsx:373` ещё вызывает `/reports/inventory/export.csv`. Этот бэкенд нельзя выпускать отдельно от согласованной замены фронта, иначе кнопка выгрузки получит 404. В пределах порученного отдельного бэкенд-ревью отсутствие новой кнопки не записывается как недоработка этого исполнителя.

Проверка изоляции из удалённого `test_reports_csv_export.py` **не потеряна полностью**: `test_wms488_product_api_matrix.py:354–387` перенесён на XLSX, содержит собственный товар, чужого селлера внутри арендатора и другого арендатора, подмену seller_id и поиск чужого товара. Проверка ролей тоже перенесена на XLSX. Удаление CSV-тестов само по себе не доказывает ухудшения этой защиты.

При этом покрытие слабее заявлений в названиях некоторых новых тестов:

- `test_ozon_positions_lookup_is_scoped_to_the_requested_period` (`test_reports_wms531.py:950–1006`) датирует старый **order/movement**, но не `created_at` самого журнала (`:983–989`). Журнал получает текущую дату БД. Проверяемый результат `document is None` для другого ID был бы тем же и при чтении всего журнала. Тест не измеряет объём чтения, не отличает старую реализацию и не выполняет R15.
- Тест кабинета селлера (`:1127–1157`) не проверяет уровни, хотя обещает это названием; пропускает F7.
- Тест Excel ожидает голый `№000042` (`:1092`), закрепляя F9.
- В C1 комментарий «Приёмка + отмена + повтор через Редактировать» (`:136`) сопровождает только один приход +10; отмена и повтор не создаются. Комментарий «Старое fbs_order_pick + отмена» (`:277`) также не сопровождается движением `fbs_order_pick_undo`. Поиск по `test_reports*` не нашёл отдельного сценария этого типа. Эти части C1 нельзя считать выполненными по названию/комментарию.
- C1 создаёт связи прямыми вставками. Для читающего отчёта это нормальная изоляция теста, но не доказательство, что тест воспроизвёл жизненный цикл подготовки/восстановления Ozon. Поэтому F2/F3 требуют отдельных сценариев.
- Тест постраничности использует 66/210 вместо полного сценария C7 с 120/450, не сравнивает все движенческие суммы с Excel. Дополнительный запуск этого ревью проверил выгрузку 450 движений одного товара, но не заменяет проверку кнопок будущего экрана.
- Тесты исключения расположения и изменения ожиданий прошлого остатка в существующих файлах обоснованы R1/R6; это не признано подгонкой тестов. Общие агрегаты работают по заданной модели, а не подбирают начало из прихода/расхода.

## Заключение

Передать находки исполнителю Sonnet для исправления, затем повторить именно затронутые сценарии и передать результат аналитику на приёмку. Для F8 нужно уточнить постановку с учётом уже известного происхождения производственных правок; по знаку движения нельзя приписывать документу сторно. После исправлений остаются отдельные проверки нового фронта, C11 на PostgreSQL и C13 на копии производственных данных. PASS, приёмка, CI и деплой этим отчётом не заявляются.
