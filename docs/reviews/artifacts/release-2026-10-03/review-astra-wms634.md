## Находки

### 1. P2 — очистка поля оставляет прежнюю дату в сохраняемых данных; дефект уже есть в базе сравнения

**Место:** `frontend/src/components/WmsDateField.tsx:56–59`;
потребитель `frontend/src/screens/v2/SellerInboundDraftScreen.tsx:591–595`.

**Воспроизведение:** открыть черновик приёмки с датой `02.10.2026`, выделить всё
содержимое поля даты, удалить, уйти из поля и нажать «Сохранить».
Поле визуально пустое, но родительское состояние продолжает содержать `2026-10-02`.
`saveDraftFields` отправляет прежнюю дату. Аналогично общий компонент не сообщает
очистку другим своим потребителям.

**Почему это дефект:** пользователь видит пустое поле, а сохраняемые данные всё ещё
содержат дату. В `commitDraft` значение `null` безусловно отбрасывается, поэтому
`onChange(null)` не вызывается. У FBO-потребителей дополнительно есть собственная
проверка `!iso`, которая тоже не позволяет отправить очистку.

**Доказательство:** в проверке настоящего компонента через React/jsdom после
Ctrl+A → Delete → уход из поля массив вызовов `onChange` остался пустым, внешнее
значение осталось `2026-10-02`. Чтение `git show 6e44f1f3e:frontend/src/components/WmsDateField.tsx`
подтвердило, что отбрасывание `null` присутствует в production-базе без изменений.
Это существующий дефект, обнаруженный по прямо запрошенному сценарию, а не новая
регрессия WMS-634. Самостоятельно расширять исправление на него не требуется для
выполнения R1–R3, но утверждать, что очистка даты работает, нельзя.

**Новых находок P0/P1/P2, внесённых проверяемым diff WMS-634, не обнаружено.**

## Проверка общего поля даты и соседних экранов

| Сценарий | Фактический результат и граница проверки |
|---|---|
| Выбор 15 октября в календаре | Сразу один `onChange('2026-10-15')`, подтверждено настоящим компонентом в jsdom. |
| Посимвольный ввод `02.10.2026` | После первых трёх цифр года вызовов нет; после последней цифры до ухода из поля вызовов тоже нет; уход из поля даёт ровно `2026-10-02`. |
| Замена дня `02` на `15`, переход к месяцу | Промежуточная дата не сохраняется, переход между секциями не сохраняет; уход из поля даёт один вызов с `2026-10-15`. |
| Вставка полной даты и уход из поля | Итоговая дата сохраняется один раз. |
| Enter, затем уход из поля | Дата сохраняется один раз; последующий уход не дублирует сохранение. |
| Очистка | Пустое значение не передаётся; сохраняется прежнее внешнее значение. Существующий P2 описан выше. |
| Набор и сразу кнопка действия | Настоящий `SellerInboundDraftScreen` отправляет новую дату и по «Сохранить», и по «Передать на склад». В последнем случае после PATCH вызывается POST передачи. |
| `minDate='2026-10-10'`, ввод 5 октября | `onChange` не вызывается. День 5 октября в календаре выключен и не выбирается. |
| Дата ровно `minDate` | 10 октября сохраняется. Ни один текущий потребитель `WmsDateField` не передаёт свой `minDate`; проверки выполнены на общем компоненте с явно заданной границей. |

Особенности точек использования:

- **`SellerInboundDraftScreen.tsx:846`** держит дату в локальном состоянии, затем
  сохраняет её кнопкой или перед передачей на склад. Интеграционные проверки
  настоящего экрана подтвердили новую дату в теле PATCH после набора и прямого
  перехода к каждой из этих двух кнопок.
- **`FfSuppliesShipmentsPage.tsx:2435`** вызывает `patchMpPlannedDate`, который сразу
  кладёт новую дату в `confirmDate` и отправляет её в PATCH (`:805–816`). Общий
  компонент проверен динамически, подключение и обработчик этого экрана — по коду.
  Полный экран в jsdom отдельно не монтировался.
- **`FfInboundRequestView.tsx:2336`** содержит поле, но оно не отображается:
  `plannedDateFieldEnabled = false` на строке 558. Поэтому утверждение, что оператор
  может сейчас редактировать дату в этом экране, было бы неверным. В отключённой
  ветке обработчик обновляет локальное состояние и вызывает `patchPlannedDate`;
  общий компонент проверен отдельно. Нового изменения видимости в WMS-634 нет.
- **`SellerMarketplaceUnloadDialog.tsx:780`** сразу начинает PATCH по завершённому
  вводу. В проверке настоящего окна переход с набранной даты к кнопке действия
  отправил `2026-10-15`.

Сохраняется явно записанная в заключении требований особенность FBO: первый клик
после набора может уйти на сохранение даты, а для самого действия потребуется
повторный клик. Причина видна по коду: уход из поля запускает PATCH и синхронно
включает `modalBusy`, от которого выключается кнопка «Запланировать»; у экрана ФФ
аналогичное состояние занятости. Это не потеря даты: отправляемое значение проверено.
Обещать выполнение самого действия первым кликом на основании этого ревью нельзя.
Точный порядок физических событий мыши в браузере остаётся проверкой ведущего;
jsdom-проверка имитирует перевод фокуса и последующий click отдельными событиями.

Изменение даты и её проверки доступа не меняет строки, резервы, движения остатков
или задания упаковки. Изменений общих обработчиков клавиатуры также нет: новые
события ограничены самим полем даты.

Этот вывод относится к WMS-634. В полном diff релизной ветки есть отдельные изменения
FBS других задач; их корректность этим ревью не утверждается.
