## 3. Находки

### F1 — ДЕФЕКТ первого ревью закрыт

Тест создаёт короба через `create_boxes`; WB проходит штатную локальную цепочку с имитацией внешнего клиента, Ozon возвращается из ветки без WB-клиента. Проведение выполняется настоящей `_apply_local_delivered`, которая пишет `delivered_at`; момент детерминированно передан через `SimpleNamespace(confirmed_at=...)`. Это тестовый объект операции, а не реально проведённая внешняя операция WB. C6 допускает прямое использование данной функции, поэтому отсутствие внешней передачи и заказов не является обходом его требований.

До проведения A1 сводка возвращает 0 при уже созданном коробе. После проведения и подготовки остальных данных проверены общий итог 3, селлер А — 2, селлер Б — 1, чужой тенант — отдельно 1, детали А/Б — 2/1, существующая строка А — 2. За предыдущие сутки общий итог 1 от A2: вклад A1 там равен 0; комментарий теста о «соседних сутках 0» относится к A1, а не ко всему набору. Пустой период даёт 0 и пустые rows. Всё это прошло для обоих вариантов include_finance.

Запреты штатных функций и отдельная подмена временной границы теперь обнаруживаются. Оба основания F1 устранены.

### ЗАМЕЧАНИЕ — продуктовая правка минимальна и остаётся в R2/R7

В `billing_seller_report_service.py:842–843` изменены только две привязки границ сравнения; остальное изменение функции — пояснение. Интервал по-прежнему получен из `moscow_interval`: начало включительно, начало следующих суток исключительно. Преобразование создаёт новые datetime для этого запроса, не меняя start/end у вызывающей функции или соседних запросов. Столбец БД не обёрнут SQL-функцией; join, count, группировка и ограничения tenant/seller не изменены. Новых сущностей, записей, блокировок, миграций и расширения продуктового объёма нет.

Для `timestamptz` это представление тех же абсолютных моментов. Вывод основан на сравнении сгенерированного SQL и параметров, типе модели и правилах PostgreSQL: значения с указанным смещением приводятся к UTC при хранении. Это согласуется с [официальной документацией PostgreSQL, раздел Time Stamps](https://www.postgresql.org/docs/current/datatype-datetime.html#DATATYPE-DATETIME-INPUT-TIMESTAMPS). Живое выполнение SQL в моей среде этим не подменяется.

Фраза нового docstring «всегда пишется как datetime.now(UTC)» неточна: прочитанная `_apply_local_delivered` сначала использует уже имеющийся `delivered_at`, затем `operation.confirmed_at` и лишь затем текущее время. Исполняемый код эту последовательность сохраняет; на доказанное равенство моментов в PostgreSQL неточность комментария не влияет.
