## B1 — закрыт

Одиночный скан по области «селлер» или «арендатор» больше не грузит каталог. resolve_product_code (product_code_resolver_service.py:171–358 и 512–538) делает три точечных запроса по самому коду: товары по lower(wb_barcode) или lower(sku_code); дополнительные WB-коды по lower(barcode); активные Ozon-связи по вхождению кода в текст JSON и, если политика разрешает, по external_sku и external_offer_id. Селлер и арендатор заданы условиями в SQL, а не списком идентификаторов. build_product_code_index остался только для документа приёмки (inbound_intake_service.py:1306–1322): его область — строки документа.

## Проверка новых рисков

**Изоляция WMS-488 в точечных запросах — сохранена.** Все три запроса фильтруют арендатора; при области селлера — селлера и у товара, и у дополнительного кода или связи. Дополнительные коды и Ozon-связи соединяются с товаром по трём полям (id, арендатор, селлер), поэтому запись с чужим владельцем не принимается даже при области «весь арендатор». Проверено живым вызовом: Ozon-связь селлера B, указывающая на товар P селлера A, не находит P ни по коду из external_barcodes, ни по offer_id — ни в области селлера A, ни во всём арендаторе. Код, общий у товара R селлера A и товара P2 селлера B: в области селлера A — найден R, чужой P2 не участвует; во всём арендаторе — неоднозначность R и P2, как и раньше для ФФ.

**Регистр — работает, включая кириллицу.** «фа_мод8-4А/083/42» находит P с артикулом «ФА_МОД8-4а/083/42» точечно и через индекс документа одинаково. Это зависит от локали базы: lower() в PostgreSQL понижает кириллицу только при UTF-8 ctype. Локальная база en_US.UTF-8; docker-compose.prod.yml поднимает официальный образ postgres:16 без своих параметров локали, а он по умолчанию инициализируется в en_US.utf8. Саму боевую базу я не проверял; одна команда `SELECT datctype FROM pg_database WHERE datname = current_database();` на бою закроет вопрос. В тестах (SQLite) lower() понижает только латиницу, поэтому регистр кириллицы в точечном пути автотестом не покрыт — это ограничение тестовой базы, не кода.

**Раскладка — работает.** Сырая «Сршт-56005» не найдена, кандидат «Chin-56005» найден, used_layout_candidate = true. Исходная строка проверяется первой; второй запрос выполняется только после полного промаха.

## Замечания второго круга

**N1 (мелочь). Кириллический Ozon-код, записанный приложением, точечный поиск не находит.** product_code_resolver_service.py:266–272 ищет подстроку `"код"` в тексте JSON-колонки external_barcodes. Колонка типа JSON, приложение пишет её через json.dumps с экранированием не-ASCII, поэтому «ОЗОН-Q» хранится как `["ОЗОН-Q"]`. Проверено: такой код точечно — not_found, а через индекс документа — found. То есть приёмка находит его, пока товар в документе, но не в каталоге, отгрузке, инвентаризации и scan/resolve. То же касается кодов с кавычкой или обратной косой чертой. Прежний helper искал так же, так что относительно версии до задачи это не регрессия; реальные Ozon-коды — латиница и цифры («OZN…», EAN). Исправление при желании: сравнивать элементы массива в SQL (json_array_elements_text) или писать external_barcodes без ASCII-экранирования.

**N2 (мелочь). SQL lower() и Python casefold() расходятся на редких символах.** Точечные запросы отбирают строки по lower(), а Python сверяет по casefold(). Для «ß»/«SS», лигатур и подобного индекс документа найдёт совпадение, а точечный путь — нет. На штрихкодах и артикулах WMS не встречается; упоминаю для полноты.

**N3 (для аналитика). Клиент FBS-подбора Ozon-поставки теперь индексирует external_sku и external_offer_id.** В FbsPickOptionProductOut.scan_codes для Ozon-поставки добавлены external_sku и external_offer_id (fbs_picking_service.py:394–412, get_pick_options), и клиентский индекс подбора их использует (pickScanSource.ts:39–51). По поведению это согласовано с сервером: для Ozon-поставки сервер эти идентификаторы принимает (R4), поэтому подсказка совпадёт. Но в R4 записано: «Клиентская общая функция их не индексирует». Нужно либо поправить формулировку R4 для этого места, либо убрать их из scan_codes.
