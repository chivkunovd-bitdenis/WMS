## Риски перехода на единый поиск товара по коду

1. **Сейчас уже есть несколько локальных «единых» функций, и они не эквивалентны.**

   - [inboundScanLookup.ts](/Users/deniscivkunov/Projects/WMS/.worktrees/wms535-wb-all-barcodes/frontend/src/screens/ff/inboundScanLookup.ts:9) строит `Map` только по загруженным строкам документа и WB-каталогу. При дубле последний товар молча перезаписывает предыдущий.
   - [resolveProductByBarcode.ts](/Users/deniscivkunov/Projects/WMS/.worktrees/wms535-wb-all-barcodes/frontend/src/utils/resolveProductByBarcode.ts:8) линейно ищет SKU, основной и дополнительные WB-коды в уже загруженном массиве и возвращает первый товар. Не знает `external_barcodes` и не сообщает неоднозначность.
   - Эту вторую функцию вызывают picker, приёмка, обычная отгрузка, MP-короб и MP-подбор. Поэтому замена только server resolver не переведёт «все места» на один слой.

2. **На сервере поиск тоже размножен.** Общий [scan_resolver_service.py](/Users/deniscivkunov/Projects/WMS/.worktrees/wms535-wb-all-barcodes/backend/app/services/scan_resolver_service.py:240), приёмка в россыпь, короб и грузоместо, инвентаризация и FBS-подбор имеют собственные пути поиска. Ozon `external_barcodes` сейчас подключается в нескольких местах отдельным fallback через `find_product_ids_by_marketplace_barcode`.

3. **Код товара живёт в общем пространстве с другими объектами.** Один текст может одновременно быть:

   - `Product.sku_code` или `wb_barcode`;
   - кодом/штрихкодом ячейки;
   - коробом, палетой или грузоместом;
   - техническим WB-стикером заказа;
   - складом.

   Общий server resolver намеренно собирает все совпадения и возвращает `scan_ambiguous`. Экранный product-only поиск, напротив, обычно берёт первый товар. При переносе нельзя потерять контекст операции: scan товара в приёмке и общий «что это за объект?» — не одно и то же действие.

4. **Порядок классификации критичен в FBS.** В актуальном workspace сначала проверяется стикер заказа, потом полный КИЗ, затем товарный ШК для WMS-514. Если поиск товара поставить первым, технический код заказа или часть КИЗ может попасть не в тот процесс. Этот порядок уже закреплён тестом R-22.

5. **Универсальная нормализация не может безусловно удалять управляющие символы.** `normalize_scan_code()` общего resolver удаляет все Unicode-категории `Cc`/`Cf`, следовательно удаляет и настоящий GS `\x1d`. Для товара это приемлемо как framing-cleanup, для КИЗ — разрушение данных. КИЗ должен остаться в отдельной lossless-классификации до product lookup.

6. **Регистр обрабатывается неодинаково.**

   - Клиентские product lookup сравнивают без учёта регистра.
   - `Product.wb_barcode == code` и `Product.sku_code == code` в общем server resolver — регистрозависимы.
   - Ячейки и склады сравнивают ручной `code` без учёта регистра, но barcode буквально.
   - Русская раскладка чинится в keyboard hook и нескольких предметных сервисах, но не является общей нормализацией всех серверных входов.

   Значит перенос одной функции без матрицы идентификаторов изменит существующее поведение части экранов.

7. **Ozon-коды сейчас именно fallback.** В общем resolver сначала проверяются `wb_barcode`/`sku_code`; только при нуле прямых совпадений читаются `external_barcodes`. Это защищает старый WB-путь, но означает, что одинаковый код в прямом поле одного товара и `external_barcodes` другого сейчас не объявляется неоднозначным. WMS-536 должна явно учесть эту существующую границу; сейчас отдельного теста на такую межисточниковую коллизию нет.

8. **Множественные WB-коды уже поддержаны только в части клиентов.** `wb_barcodes[]` читают локальные inbound lookup и `resolveProductByBarcode`, но общий server resolver на проверенном SHA смотрит только `products.wb_barcode`. Именно поэтому WMS-535 является зависимостью WMS-536.

9. **Не найдено зафиксированного правила преобразования EAN-13 ↔ GTIN-14 и ведущих нулей.** Текущая семантика — точное строковое сравнение. Автоматическое добавление нуля в общем слое изменит область совпадений и может создать новые коллизии.

10. **«Не найдено» не всегда должно означать одно и то же действие.**

    - В пустой приёмке ФФ известный каталогу товар должен создать строку.
    - В документе селлера чужой товар должен остаться ошибкой.
    - В инвентаризации неизвестный код может стать находкой.
    - В общем resolver это просто 404.
    - В KIZ-пути мусор нельзя отправлять в WB.

    Поэтому общий поиск товара может быть общим, но реакция на его результат остаётся операционной.

11. **Нельзя потерять разделение физического scan и сетевого replay.** В приёмке второй настоящий scan — вторая штука. В инвентаризации, WMS-489 и WMS-514 повтор доставки с тем же id — тот же запрос. Попытка сделать «дубликаты всегда игнорируются» вернёт ошибочную постановку WMS-175.

12. **Автопокрытие не заменяет физические границы.** В текущих тестах хорошо покрыты нормализация клавиатурного ввода, GS, неоднозначность, области селлеров и idempotency. Не покрыты реальным устройством Tab/no-suffix, возврат фокуса, MUI Enter/blur, прокрутка, Android ATOL и считывание бумажного DataMatrix. Эти пробелы особенно важны, потому что именно там уже происходили реальные регрессии.
