## Что фактически считается товарным кодом

В текущем коде нет одного общего ответа:

- Приёмка в короб и без короба использует общий для этих двух операций серверный `resolve_scanned_product_id`. Он учитывает SKU, доступный `wb_barcodes`/`wb_primary_barcode` и Ozon `external_barcodes`, умеет сообщить неоднозначность.

- Сборка отгрузки использует другой индекс. Он учитывает только `wb_barcodes` и `wb_primary_barcode`, не учитывает Ozon `external_barcodes`, SKU и не обнаруживает неоднозначность.

- Размещение вообще не ищет товар по коду: товар без короба выбирается тапом.

Есть дополнительная существенная граница WMS-535. Текущий каталог формирует `wb_barcodes` так: если `products.wb_barcode` заполнен, возвращается только он; до `sizes[].skus` импортированной карточки код уже не доходит ([seller_wb_catalog_service.py:106](</Users/deniscivkunov/Projects/WMS/.worktrees/wms535-wb-all-barcodes/backend/app/services/seller_wb_catalog_service.py:106>)). Все штрихкоды WB из карточки используются только когда `products.wb_barcode` пуст. Поэтому даже места, которые формально обходят `row.wb_barcodes`, сейчас не получают дополнительные 2–3 ШК размера при заполненном основном поле.

## Риски перехода на единый поиск товара по коду

1. **Локальные распознавания нельзя незаметно заменить товарным поиском.** Короб приёмки, короб сборки и ячейка сейчас выбираются по уже загруженному документу/списку, без сетевого запроса. Изменение порядка или перевод всего на сервер изменит реакции при потере сети и на устаревших данных.

2. **Порядок проверок является частью текущего поведения:**

   - приёмка: короб текущей заявки → loose-товар → товар в открытый короб;
   - размещение: короб → ячейка;
   - отгрузка: собственный короб → ячейка → палета/короб/грузоместо → товар.

   Один код может одновременно быть кодом товара и физического объекта. Сейчас в такой ситуации объект, стоящий раньше, побеждает молча.

3. **Нормализация раздроблена и несовместима.** Мобильный общий слой делает только `trim()`. Приёмочный товарный resolver дополнительно пробует uppercase; сортировка и отгрузка сравнивают регистрозависимо. Нигде в текущих мобильных процессах нет:

   - исправления русской/английской раскладки;
   - снятия AIM-префиксов;
   - преобразования GTIN-13/GTIN-14;
   - сохранения/разбора GS/FNC1 по правилам конкретного вида кода;
   - единого правила регистра;
   - специальной обработки ведущих нулей.

4. **Удаление управляющих символов опасно для ЧЗ.** Имеющийся, но не используемый мобилкой `GET /operations/scan/resolve` удаляет все Unicode-категории `Cc` и `Cf` ([scan_resolver_service.py:60](</Users/deniscivkunov/Projects/WMS/.worktrees/wms535-wb-all-barcodes/backend/app/services/scan_resolver_service.py:60>)). Это удалит в том числе внутренний GS `\x1d`, который разделяет группы GS1 DataMatrix. Такой нормализатор нельзя считать эквивалентным сохранению полного КИЗ.

5. **`/operations/scan/resolve` сейчас не является единым товарным поиском WMS-536 и мобилкой не вызывается.** Его товарная ветка сначала ищет только `Product.wb_barcode`/`sku_code`, затем Ozon external barcode; дополнительные WB `sizes[].skus` она не использует. Кроме того, endpoint возвращает объект любого типа, тогда как рабочим операциям нужны контекст документа, допустимость товара и действие над количеством.

6. **Неоднозначность обрабатывается тремя разными способами:**

   - приёмка товара возвращает `barcode_ambiguous`;
   - outbound-товар молча оставляет последний товар в словаре;
   - локальные списки коробов/ячеек берут первый;
   - общий `/scan/resolve` возвращает 409 и полный список объектов;
   - физическая тара outbound возвращает `invalid_container_reference`.

   Мобильный интерфейс ни в одном рабочем экране не умеет предложить оператору выбор.

7. **Ozon `external_barcodes` покрыты только приёмкой.** Тот же Ozon-код, успешно принимаемый на входе, не будет найден при сборке отгрузки. Это прямой риск регрессии, если единый слой сначала подключить только к одному из процессов.

8. **WB дополнительные ШК сейчас отсутствуют в фактическом индексе при заполненном `products.wb_barcode`.** Это относится и к приёмке, и к outbound, хотя внешне оба кода перебирают `wb_barcodes`.

9. **QR WB/Ozon, стикер заказа и товарный ШК не разделены по семантике.** Камера умеет технически читать QR, но текущие три обработчика не различают QR поставки, order sticker, товарный QR и обычную строку. Совпадение с товарным alias может породить товарную операцию; в остальных случаях будет «не найдено».

10. **ЧЗ DataMatrix и КИЗ в текущей mobile-ветке не обрабатываются.** Есть только распознавание формата камерой и показ количества уже напечатанных кодов. Привязки КИЗ к QR WB/Ozon, проверки пары и вызова marking API нет.

11. **Keyboard wedge может одновременно менять поле и запускать скан.** Символы специально пропускаются в UI. Если открыт ввод количества либо поле авторизации, скан попадёт в `TextField`; на рабочем экране он одновременно может уйти в ViewModel. Финальный Enter скана будет поглощён.

12. **Быстрые серии могут теряться без сообщения.** Общий `SharedFlow` имеет `extraBufferCapacity=1`, очереди трёх ViewModel — по 16 элементов, а результаты `tryEmit`/`trySend` не проверяются. Камера дополнительно отбрасывает любые распознавания в течение двух секунд после предыдущего, даже если это другой код.

13. **Экран коробов приёмки уже создаёт ложное подтверждение скана.** Камера показывает зелёную рамку, но обработчика нет. При переносе на единый поиск это место нельзя пропустить, иначе сохранится текущая иллюзия успешного действия.

14. **Mobile OpenAPI-клиент отстаёт от текущего backend-контракта контейнеров.** Его локальный `openapi.json` не содержит `container_kind`, `container_id`, `container_code`, тогда как текущий сервер возвращает `kind=container`. ViewModel считает любой незнакомый `kind` веткой `ready_box`, не сохраняет контейнер и не объясняет оператору результат.

15. **Физические источники скана ещё не дают одинаковой строки.** Broadcast берёт vendor-specific string extra, wedge зависит от Android-раскладки и настроенного суффикса, камера отдаёт ML Kit `rawValue`. Код не содержит теста, подтверждающего одинаковый результат для GS1/DataMatrix, QR и Code 128 через все три источника.

Это статическая опись текущих исходников и контрактов. APK, эмулятор и физический ТСД в рамках этой read-only задачи не запускались; распознавание камерой, vendor-intent и реальные строки с GS/FNC1 на железе здесь не подтверждены.
