## Блокер

### B1. Каждый скан строит индекс по всему каталогу селлера или арендатора

**Где.** Ядро product_code_resolver_service.py:149–255: первым запросом грузит все карточки области, затем двумя запросами грузит дополнительные WB-коды и Ozon-связи через IN по списку всех этих идентификаторов (строки 193 и 218), затем в Python строит словарь всех алиасов. Вызывается на каждый скан с областью «весь селлер» или «весь арендатор» в местах:

- обычная приёмка россыпью, в короб и в грузоместо — inbound_intake_service.py:1380 (для обычной приёмки индекс всегда строится по всему каталогу селлера, в том числе когда клиент прислал product_id);
- подбор и короб отгрузки на маркетплейс — marketplace_unload_pick_service.py:429, marketplace_unload_box_service.py:416;
- находка инвентаризации — inventory_count_service.py:1180 (по селлеру пересчёта, а если у пересчёта нет селлера — по всему арендатору);
- общий scan/resolve — scan_resolver_service.py:368 (для ФФ-пользователя по всему арендатору).

**Почему это откат.** 22.08.2026 была авария на бою: «после скана товара оператор ждёт несколько секунд», причина — «backend на каждом скане повторно загружает… каталог селлера». Исправление 5f8572df и 0b6c0ff2 (tasks/20260822-hotfix-scan-fastpath) прямо записало границу: «Не загружать весь каталог селлера, если документ уже задаёт конечный набор товаров», и ввело быстрый путь по product_id. WMS-536 возвращает загрузку всего каталога в горячий путь, а тесты, которые охраняли исправление, переписаны в обратную сторону:

- test_inbound_intake_box_ondemand.py:340–374 раньше требовал, чтобы поиск шёл только по товарам документа ([{pid}]×4), теперь требует [None]×4, то есть весь каталог на каждом из четырёх сканов;
- из test_inbound_intake_box_ondemand.py:378 удалена проверка «product_id fast path must not rebuild the WB catalog»;
- в test_marketplace_unload_tsd_scan_contract.py:157 и :289 проверка «catalog must not be loaded» заменена на утверждение, что индекс каталога строится ровно один раз на скан.

Это противоречит R13 («на большом документе индекс строится один раз», «не должно вернуть 15–20-секундный scan»), R5 («обычная приёмка — сначала товары документа, затем каталог») и H-12 из истории регрессий.

**Замеры (повторяемые прогоны, локальный PostgreSQL 17):**

| Что | Время одного разрешения кода |
|---|---|
| Новое ядро, область документа на 300 товаров | 12–25 мс |
| Новое ядро, весь селлер на 55 000 карточек | 1,3–1,5 с (SQL около 0,45 с, остальное — разбор строк и построение словаря в Python) |
| Новое ядро, весь арендатор на 85 000 карточек | отказ: psycopg.OperationalError «number of parameters must be between 0 and 65535» → HTTP 500 |
| Было: индекс документа приёмки (300 товаров) через list_seller_wb_catalog_rows | 20–31 мс |
| Было: полный каталог селлера на 55 000 через list_seller_wb_catalog_rows | 2,0–2,2 с |
| Было: запрос находки инвентаризации (lower(wb_barcode)/lower(sku_code) по арендатору 85 000) | 45 мс |
| Было: запрос товара в scan/resolve | 10 мс |

Отдельно проверено, что лимит 65 535 — это лимит протокола PostgreSQL на число параметров одного запроса: SQLAlchemy разворачивает IN в отдельный параметр на каждый идентификатор, на 66 000 идентификаторах psycopg отказывает до отправки запроса.

**Что это значит для каждого пути:**

- Веб-приёмка (россыпь, короб, грузоместо): было около нуля — клиент присылал product_id, каталог не грузился; стало 1,3–1,5 с на скан у селлера на 55 000 карточек. Скан при этом выполняется под SELECT … FOR UPDATE заявки (get_request_for_receiving_scan, inbound_intake_service.py:659–674; для короба и грузоместа — get_request(for_update=True)), так что второй оператор на той же заявке ждёт.
- Приёмка на ТСД: было 20–31 мс при попадании в документ (обычный случай) и около 2 с только при промахе; стало 1,3–1,5 с на каждый скан.
- Веб-отгрузка на маркетплейс (подбор и короб): было около нуля по product_id; стало 1,3–1,5 с.
- Сборка отгрузки на ТСД: было 2,0–2,2 с (полный каталог и раньше), стало 1,3–1,5 с — здесь стало быстрее.
- Находка инвентаризации: было 45 мс; стало 1,3–1,5 с по селлеру; у пересчёта без селлера в арендаторе больше 65 535 карточек — 500 на каждой находке.
- scan/resolve: было 10 мс; стало 1,3–1,5 с по селлеру и 500 для ФФ-пользователя в арендаторе больше 65 535 карточек. Смягчение: ни веб, ни ТСД этот endpoint сейчас не вызывают (проверено поиском по frontend/src и mobile/android).
- Селлер больше 65 535 карточек — 500 уже на каждом скане приёмки, отгрузки и инвентаризации этого селлера. По данным ведущего, самый крупный селлер сейчас около 55 000 карточек, это 84 % от порога. Сколько карточек у самого крупного арендатора целиком, я не проверял; это нужно посмотреть на бою до решения.

FBS-подбор, WMS-514, упаковка и распределение строят индекс по составу поставки, задания или документа — там всё быстро, их это не касается.

**Что исправить.** Не строить полный индекс каталога на каждый скан. Варианты, которые не противоречат требованиям:

1. В обычной приёмке вернуть порядок R5: индекс по товарам документа, неоднозначность считается в документе; каталог селлера — только при промахе, как было до задачи. Это одновременно чинит V1 ниже.
2. Там, где каталог селлера обязателен по R5 (отгрузка без подсказки, находка инвентаризации, scan/resolve), искать по самому коду, а не грузить весь каталог: WHERE lower(wb_barcode) = :код OR lower(sku_code) = :код с фильтром по селлеру/арендатору, product_barcodes по коду, Ozon-связи по вхождению кода в JSON (старый helper делал это через LIKE по тексту JSON). Неоднозначность при этом считается так же — по всем найденным товарам области, а число запросов остаётся постоянным.
3. В любом случае не передавать в IN неограниченный список идентификаторов: область «селлер» или «арендатор» выражается соединением с products по seller_id/tenant_id, а не списком из десятков тысяч UUID.

Вернуть охранные тесты 22.08 в исходном смысле (попадание в документ не грузит каталог; подсказка не грузит каталог) и добавить C26 с проверкой, что размер запроса не растёт с размером каталога.

## Важно

### V1. Обычная приёмка ищет сразу по всему каталогу селлера, а не «документ → каталог»

**Где.** inbound_intake_service.py:1364–1400 (resolve_scanned_product_id): для обычной приёмки со известным селлером вызывается только _seller_catalog_barcode_index.

**Что требует документ.** R5: «обычная приёмка — сначала товары документа, затем каталог её селлера»; матрица 4.1, B/S-INB-03: «Подключается: документ → seller catalog». Так же работал код до задачи, и так же сейчас работает клиент: inboundScanLookup.ts:86–90 сначала ищет в документе и только при промахе — в каталоге.

**Сценарий, воспроизведён живым вызовом.** На тестовой базе у товара P основной WB-код 4600000000001, P есть в документе. У товара Q того же селлера, которого в документе нет, артикул 4600000000001. Вызов resolve_scanned_product_id для обычной приёмки даёт barcode_ambiguous и без подсказки, и с подсказкой product_id = P. До задачи результат был P: подсказка принималась сразу, а без подсказки код находился в индексе документа, и каталог не открывался. Клиент при этом считает товар найденным (P есть в документе) и отправляет подсказку P, а сервер отвечает 409 — фронт и бэк расходятся в области поиска.

**Последствие на бою.** Ведущий назвал код 4680163562209 у ArtMaks/«Фабрики» (WB-код одной карточки и артикул другой). При текущей реализации приёмка этой карточки остановится даже в документе, где есть только она. По R5 такая приёмка проходила бы, а ошибка оставалась бы только для скана вне документа.

**Исправить.** Сначала индекс документа, неоднозначность — внутри документа; каталог селлера — только при not_found. Добавить тест на этот сценарий (P в документе, Q только в каталоге). Если же аналитик решит, что неоднозначность должна считаться по всему каталогу даже при попадании в документ, это изменение R5 и клиентской логики, и его надо записать в требования, а не оставлять расхождением.

### V2. ТСД покажет оператору машинный код «barcode_ambiguous»

**Где.** marketplace_unload_box_service.py:419 → API _map_box_err отдаёт detail = "barcode_ambiguous" строкой; приёмка отдаёт тот же код через _map_inbound_box_err и _map_inbound_svc_err. Мобильный ApiErrors.kt переводит только коды из своего словаря, остальные показывает как есть (readableError: ERROR_CODES_RU[detail] ?: detail). Кода barcode_ambiguous в словаре нет.

**Сценарий.** Сборка отгрузки на ТСД (M/S-OUTBOUND-04), код общий у двух товаров селлера. Раньше сервер молча брал последний товар словаря; теперь правильно останавливает операцию, но на экране ТСД будет строка «barcode_ambiguous». В приёмке на ТСД так было и до задачи, но теперь неоднозначностей станет больше (дополнительные WB-коды, Ozon-коды и регистр участвуют одновременно).

**Почему это несоответствие.** R2: «оператор в каждом изменённом экране видит понятный смысл»; R14: «если backend error code новый, существующий мобильный generic error обязан показать понятный текст сервера; добавлять mobile UI… нельзя». Формат ответа для ТСД при этом совместим: успешные ответы (строка приёмки, строка короба, BoxScanResult) не изменились, detail по-прежнему строка.

**Исправить.** Это развилка для аналитика: либо эти два endpoint'а отдают понятный текст в detail (и веб должен продолжать узнавать ошибку по коду — нужно согласовать контракт), либо явно записать разрыв и вынести перевод в мобильную задачу. Молча оставлять нельзя.

## Мелочи

**M1. validated_product_ids_from_resolution избыточна.** scan_resolver_service.py:79–179. После 154484a2 ядро само соединяет Ozon-связь с товаром по владельцу (Product.seller_id == ProductMarketplaceLink.seller_id) с теми же фильтрами (арендатор, ozon, активна) и той же нормализацией (края + casefold). Повторная проверка всегда подтверждает то, что уже отобрало ядро; расхождения я не нашёл. Цена — лишний запрос на каждый скан, найденный только по Ozon-коду, и лишняя сложность в пяти местах. Можно удалить.

**M2. Несовпадение подсказки product_id сообщается тремя разными кодами.** Приёмка — product_not_found (404), FBS — wrong_product (409, с понятным текстом «Переданный product_id не соответствует отсканированному коду»), отгрузка — barcode_unknown (422), который на ТСД и в вебе читается как «Штрихкод не найден в этой заявке», хотя код найден. Мутации нигде нет, но формулировка вводит в заблуждение. Лучше один код для несовпадения.

**M3. FBS-подбор разрешает код дважды.** pick_scan (fbs_picking_service.py:778) находит товар, затем вызывает scan_pick_product с тем же кодом (:839), и тот строит индекс заново (:1043). Область маленькая (состав поставки), так что это шесть лёгких запросов вместо трёх; проще передать найденный товар.

**M4. WMS-514 считает неоднозначность и по товарам отменённых заказов.** fbs_scan_auto_print_service.py:218 строит область из всех заказов поставки, включая отменённые и недопустимые для перепечати ЧЗ. До задачи коды сравнивались только с подходящими заказами. Теперь товар отменённого заказа с тем же кодом превращает скан в scan_product_ambiguous. Редко, но область лучше строить из eligible_orders.

**M5. Края строки теперь срезаются уже, чем раньше.** По R6 снимаются только пробел, TAB, CR, LF — так и сделано. Раньше приёмка, упаковка и отгрузка вызывали Python-овский strip(), который снимает также \x0b, \x0c, \x1c–\x1f (включая GS), NBSP и \x85. Сканер, настроенный на суффикс GS или RS, раньше работал, теперь получит «не найдено». Это следствие требования, а не ошибка исполнителя, но стоит отметить при приёмке. Мелкая несогласованность: упаковка проверяет пустоту через strip(), а ищет по исходной строке (packaging_task_service.py:1123 и :1131), FBS-подбор срезает strip() на входе.

**M6. Сверка повтора в коробе и грузоместе приёмки идёт после разрешения кода.** inbound_intake_box_service.py:419→431, inbound_cargo_place_service.py:151→160. Если ответ потерялся, а между исходным сканом и повтором кто-то изменил каталог так, что код стал неоднозначным, повтор с тем же mutation_id вернёт 409 вместо сохранённого результата; оператор увидит ошибку на уже засчитанной единице. Окно узкое. Надёжнее сначала искать уже записанную мутацию по mutation_id.

**M7. Снимок инвентаризации стал тяжелее.** inventory_counts.py:443 добавляет в _detail_out три IN-запроса по всем товарам пересчёта, а _detail_out возвращается после каждой находки и каждой правки. Замер (два прогона): +130–150 мс на 5 000 товаров, +450–470 мс на 20 000, +1,4 с на 55 000; для сравнения, уже существующая загрузка фото по тем же товарам — 34 и 139 мс на 5 000 и 20 000. Порог 65 535 тот же, что у уже существующей загрузки фото, так что новый класс отказа здесь не появляется. Карта склада получает те же три запроса один раз на открытие.

## Ответы на вопросы ведущего

**(1) Серверная сверка product_id и клиентские пути.** Все текущие веб-пути, которые шлют product_id, шлют именно тот код, по которому нашли товар: приёмка (FfInboundRequestView, FfInboundBoxAddDialog) и короб отгрузки (FfMarketplaceUnloadBoxAddDialog) — matchedCode, включая латиницу после исправления раскладки; поле подбора FfUnloadPickPage раскладку не исправляет и шлёт исходный код. Старый экран приёмки (App.tsx:1656) и ТСД product_id не шлют. Ручные пути без скана не сломаны: ручной FBS-подбор передаёт пустой код и продолжает брать товар по product_id (fbs_picking_service.py:1043–1052, manual_pick_product), ручное количество в приёмке, отгрузке и ручная строка инвентаризации идут через отдельные endpoint'ы без resolver. Единственное расхождение — область поиска в обычной приёмке (V1): клиент находит товар в документе, сервер объявляет неоднозначность по каталогу.

**(2) validated_product_ids_from_resolution.** Избыточна, расхождения нет — см. M1.

**(3) Регистронезависимое сравнение там, где было точное.** В FBS, упаковке и отгрузке теперь совпадают артикулы и коды в другом регистре. Новая коллизия возникает только если в одной области у двух товаров алиасы отличаются лишь регистром; результат — явная неоднозначность без мутации, а не выбор неверного товара. Для числовых WB-кодов регистр ничего не меняет. Отдельно: в отгрузке на маркетплейс артикул sku_code раньше вообще не искался (индекс знал только WB-коды), теперь ищется — это расширение, ведущее к новым коллизиям вида «WB-код одной карточки = артикул другой». Сколько таких кодов на бою, я не считал; ведущий назвал три.

**(4) Ozon-коды в WB-поставке и отгрузке; WMS-514.** В FBS-подборе WB-поставки, в упаковке и в отгрузке Ozon external barcode теперь находит товар (политика по умолчанию), как и записано в R3. WMS-514 остаётся WB-only тремя замками: отказ scan_auto_print_wb_only для не-WB поставки (fbs_scan_auto_print_service.py:185–186), выборка только WB-заказов, политика WB_ONLY_PRODUCT_CODE_ALIAS_POLICY без Ozon-кодов. Тест test_wms536_scan_auto_print_uses_wb_only_product_aliases проверяет, что Ozon-код даёт scan_product_not_found. external_sku и external_offer_id включены только в scan/resolve, находке инвентаризации и подборе Ozon-поставки — ровно по R4.

**Понятно ли оператору про три боевые неоднозначности.** В FBS-подборе и упаковке сервер отдаёт понятный текст «Код относится к нескольким товарам. Проверьте штрихкоды карточек»; в приёмке, отгрузке и инвентаризации — машинный код, который веб переводит сам (это проверяет ревьюер фронта), а ТСД — нет (V2). Исправить конфликт оператор на месте не может, нужен человек с правом правки карточек. Для кода ArtMaks текущая реализация дополнительно блокирует приёмку даже там, где это не требуется по R5 (V1).

**(5) Упавший в полном прогоне test_cargo_place_rejects_product_not_on_request.** Прогнал отдельно: падает на tests/test_inbound_cargo_place_api.py:346 — 404 product_not_found вместо 200. На строке 344 тест шлёт barcode = артикул товара A (он есть в заявке) и product_id = товар B (его нет в заявке) и ждёт, что в грузоместо добавится B. Это ровно тот обход кода подсказкой, который R10 запрещает («несовпадение подсказки останавливает операцию до записи»), так что классификация «устаревший тест» верна: новое поведение правильное, старое ожидание нет. Реальных клиентов с таким расхождением я тоже не нашёл (см. ответ на вопрос 1).

Но удалять тест нельзя: кроме подсказки он проверяет WMS-473 — PUT без строки даёт product_not_on_request, скан товара каталога сам создаёт строку и засчитывает единицу, повторный скан даёт 2, код вне каталога даёт product_not_in_seller_catalog. Исправить так: на строке 344 слать согласованную пару barcode = артикул B и product_id = B; расхождение A+B вынести в отдельную проверку, что ответ 404 product_not_found и количество грузоместа и строки документа не изменились (это заодно закрывает C21 для грузоместа). И самое важное: этот тест исполнитель не прогнал, поэтому полный набор красный. До повторного ревью полный прогон должен быть зелёным.

## Итог

Логика единого товарного поиска на сервере сделана правильно, но в пяти горячих путях она подключена через построение полного индекса каталога на каждый скан. Это возвращает класс аварии 22.08, упирается в жёсткий лимит драйвера на каталогах больше 65 535 карточек и сопровождается переписыванием тестов, которые от этого защищали. Для повторного ревью нужны: зелёный полный прогон (сейчас падает test_cargo_place_rejects_product_not_on_request, см. вопрос 5), исправление B1 и V1 (порядок «документ → каталог» в приёмке и поиск по коду вместо загрузки каталога там, где каталог нужен), решение аналитика по V2 и восстановленные охранные тесты. Мелочи M1–M7 можно исправить тем же заходом или оставить с явной записью.
