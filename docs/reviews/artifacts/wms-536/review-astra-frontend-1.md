Ревью выполнено Astra по коду, тестам функций и React-компонентов с подменённой сетью. Браузер, Postgres, production и физический сканер ревьюер не запускал. Сообщение ведущего о проверке экранов разработчиками принято как отдельный факт, а не как собственная браузерная проверка.

## Находки, требующие исправления

### F1 — блокер. Исправленная раскладка товара документа побеждает настоящий кириллический SKU каталога

**Место:** `frontend/src/screens/ff/inboundScanLookup.ts:86–94`; вызовы `FfInboundRequestView.tsx:1740` и `FfInboundBoxAddDialog.tsx:376`. Затронуты F/S-INB-05 и F/S-INB-06, включая короб и грузоместо. Нарушены R7, R11, R17, C23.

**Сценарий:** у одного селлера есть P с настоящим SKU `ФА_МОД8-4а/083/42` и Q с SKU `AF_VJL8-4f/083/42`. В обычной приёмке пока есть только Q, а каталог содержит обе карточки. Оператор сканирует кириллический код P. Wedge корректно передаёт оба чтения, но `resolveInboundProductScan` сначала разрешает **оба** кандидата в документе. Исходного P там нет; запасной латинский кандидат находит Q. Возврат происходит до проверки исходного кода по каталогу.

**Фактический результат воспроизведения:**

```text
input: raw=ФА_МОД8-4а/083/42, layout=AF_VJL8-4f/083/42
document: Q; seller catalogue: P,Q
expected: {status: 'send', barcode: 'ФА_МОД8-4а/083/42'}
actual:   {status: 'send', barcode: 'AF_VJL8-4f/083/42', productId: 'LATIN'}
```

Серверная сверка hint здесь не спасает: клиент уже заменил barcode на допустимый код Q, поэтому barcode и product_id согласованы. Текущий `inbound_intake_service.resolve_scanned_product_id` (`:1375`) для обычной приёмки проверяет весь каталог селлера и однозначно принимает этот латинский код Q. Получается штатное увеличение количества **другого товара**, а P даже не доходит до сервера. До WMS-536 wedge вообще терял исходную кириллицу; задача должна была устранить этот дефект, но устранила его только когда P уже находится в локальном документе либо документ пуст.

**Исправить:** выполнять raw-first во всей разрешённой области операции. В обычной приёмке сначала проверить исходный код документа/каталога, и только после полного `not_found` проверять раскладку. Возвратную приёмку сохранить ограниченной документом; для этого вызывающий должен явно передать допустимость catalog fallback. Не заменять raw-код кодом другой карточки до такой проверки. Добавить тесты: кириллический P вне документа + латинский Q внутри; raw неоднозначен в каталоге + layout однозначен в документе; возвратный документ; loose/box/cargo HTTP payload. Недостаточно добавить очередную проверку совпадения product_id на сервере.

### F2 — важно. Товарная неоднозначность блокирует распознавание ячейки/тары раньше их классификатора

**Места:** `frontend/src/screens/ff/unload-pick/FfUnloadPickPage.tsx:446–449`; `frontend/src/screens/ff/FfMarketplaceUnloadBoxAddDialog.tsx:456–462`. Затронуты F/S-OUT-01 (MP и FBS) и F/S-OUT-02. Нарушены R8, C10/C13/C14 с OBJ, R-19/R-21.

**Сценарий:** `CELL-DUP` — действующий код ячейки, одновременно SKU P и Ozon-ШК либо SKU Q двух товаров плана. Оператор сканирует ячейку для выбора нового источника. До изменения frontend выбирал первый товар как hint и отправлял исходный код; сервер проверял ячейку/тару до товарной ветки. Теперь `ambiguous` приводит к throw/return **до HTTP**. Оператор получает «Код относится к нескольким товарам…» и не может выбрать совершенно определённую ячейку. Аналогично блокируются короб, палета и грузоместо, распознаваемые сервером раньше товара.

**Воспроизведение:** два отдельных React-теста с существующими компонентами, двумя товарами `CELL-DUP` и ответом сервера `kind=location` ожидают один scan-запрос. Оба получили **0 запросов**. Сценарий с единственным товаром, имеющийся в `FfMarketplaceUnloadBoxAddDialog.dom.test.tsx`, проходит, но не покрывает эту коллизию.

**Исправить:** выполнить классификацию ячейки/тары до окончательного отказа товарного resolver. В этих server-classified полях можно отправлять исходный код без неоднозначного product_id и принимать серверную товарную ошибку, поскольку сервер уже гарантирует отказ без мутации. При этом сохранить точный выбранный source и не запускать автоматический выбор товарного источника до установления типа объекта. Проверить ячейку и все виды тары с коллизией двух товаров, в том числе переключение A → B и следующий товарный скан. Для product-only полей локальная остановка при ambiguity остаётся правильной.

### F3 — важно. В Ozon FBS-подборе общий клиентский resolver не получает полный набор кодов

**Места:** `frontend/src/screens/ff/unload-pick/FfUnloadPickPage.tsx:375–380`, `pickScanSource.ts:39–51`. Граница данных: `backend/app/api/fbs_supplies.py:222` и `:1527`, `backend/app/services/fbs_picking_service.py:90` и `:356–390`. Затронут F/S-OUT-01, C10, R3/R13/R17.

Фронт намеренно отключает каталог для Ozon (`NO_CATALOG`). Новый индекс рассчитывает получить остальные коды через `pickOptions[].scan_codes`. Но в **реальной** модели ответа `FbsPickOptionProductOut`, в сервисном `PickOptionProduct` и сборке ответа поля `scan_codes` нет. Для Ozon передаются только внешний SKU в поле `sku_code` и первый external barcode в `barcode`; внутренний Product.sku_code, основные/дополнительные WB-коды и остальные external barcodes не доходят до локального индекса. Тест «scan_codes … если сервер их отдал» подставляет поле, которого этот сервер не отдаёт.

**Сценарий:** товар Ozon имеет `OZN-FIRST` и `OZN-SECOND` и лежит в единственном доступном физическом источнике. Ничего ещё не выбрано. По первому коду frontend находит P и сам передаёт единственный source. По второму — не находит, отправляет без hint и со `storage_location_id=null`. Сервер товар теперь распознаёт, но при адресном хранении `_implicit_pick_location` (`fbs_picking_service.py:646–657`) отвечает `location_required`, даже когда место только одно. Одинаковые коды одной карточки дают разные операторские действия; единого обещанного поведения нет. С заранее выбранным источником серверный путь может успешно принять второй код — это не доказывает product-first сценарий.

**Воспроизведение:** React-тест с фактической формой Ozon DTO без выдуманного `scan_codes`. Для `OZN-SECOND` получено `storage_location_id: null`, отсутствует `product_id`; ожидались P и CELL-1. Серверная ветка отказа проверена чтением кода, не запросом к БД.

**Исправить:** пакетно добавить полный набор допустимых alias и внутренний SKU в фактический FBS pick-options контракт либо дать этому экрану эквивалентный scoped-источник. Сохранить прежний внешний Ozon SKU там, где он был разрешён; не распространять offer_id на WB/MP. Тестировать реальный сериализованный контракт, а не необязательное поле только в mock. Проверки: каждый alias → один и тот же единственный source; несколько источников → прежняя просьба уточнить; общий код → ambiguity после классификации объекта.

## Замечание без блокировки

**F4 — мелочь, смежный backend.** `scan_resolver_service.py:79–174` повторно проверяет принадлежность Ozon-связи в `validated_product_ids_from_resolution`. После добавления `Product.tenant_id == ProductMarketplaceLink.tenant_id` и `Product.seller_id == ProductMarketplaceLink.seller_id` в ядро (`product_code_resolver_service.py:220–222`) это дублирование. В текущем стабильном снимке расхождения правил не найдено: те же active Ozon links, владельцы, matched_sources и normalize/casefold. Но внешний-only match вызывает дополнительный SQL и повторный разбор alias; при изменении связи между чтениями возможен уже другой снимок. Docstring «core currently accepts … by product_id alone» устарел. Убрать дублирование после сверки всех consumers с ядром, оставить адресные WMS-488 tests. Это не frontend-блокер и не доказательство утечки данных.

## Матрица конкретных вводов

Это прослеживание кода HEAD относительно старого поведения, а не заявление о выполнении каждой комбинации на реальном сервере. Для product-колонок подготовлены фикстуры раздела 9 требований. В колонке «чужой» тот же код есть у разрешённого P и у чужого селлера. В object-only поле товарные строки не получают специальной товарной семантики: если буквально совпали с допустимым объектом, срабатывает объект.

Обозначения: **P** — локально найден единственный товар; **B** — код передан для серверного поиска товара без локального выбора; **A** — ошибка ambiguity до товарной мутации; **N** — товар не найден; **O** — предметный объект; **K** — отдельный КИЗ-процесс; **S** — sticker lookup; **L** — layout только после raw miss; **F** — found-запрос инвентаризации, а не локальный +1. P/B запускают только существующую операцию места. «Нет» в чисто объектных полях означает отказ как неизвестному объекту, не товарный resolver.

### useBarcodeScanner и все подписчики

### Проверка hint и ручные действия

INB-05/06 отправляют `product.barcode`; OUT-02 отправляет `productLookup.matchedCode`; OUT-01 не имеет layout correction и отправляет исходный barcode, который был проверен тем же консервативным resolver. Это устраняет обычное несовпадение «нашли по исправленной раскладке, послали неисправленную». Но F1 показывает принципиально другой сбой: и barcode, и hint уже принадлежат неверной карточке.

Ручное добавление/редактирование количества не перенаправлено в scan API: приёмка использует прежние line/actual/quantity действия; MP box — PUT lines с выбранным product_id и количеством; подбор — отдельную allocation-операцию; picker/план — API строк. Новое требование проверки barcode не создаёт фронтового пустого barcode для этих ручных путей. Подменённый напрямую hint обязан отклонить backend; полноценный C21 с БД относится к backend-ревью, здесь он не заявляется выполненным.

### WMS-488, D6, карта и инвентаризация

Общий frontend resolver сам область не расширяет: он индексирует только переданный набор, не делает глобальных запросов и не выводит productIds из ambiguity в UI. Catalog adapter включает только `marketplace === 'ozon'`; external_sku/offer_id общими aliases не стали. Seller/tenant авторизация остаётся на API. Legacy INB-01 и FF-карта могут получать более широкие FF-наборы — общий код между селлерами тогда может быть неоднозначен внутри разрешённого снимка, что следует отличать от утечки seller-пользователю. Полный backend WMS-488 gate здесь не подменяется локальным тестом массива.

D6 реализован в общем `WbProductPickerDialog`: exact resolver проверяется по Enter до изменения quantity. `SellerWbProductPickerDialog` — export того же компонента; MP-план использует его же. Единственная строка частичного фильтра больше не выбирается по Enter, ручной клик и текстовый фильтр остались. Это явно предусмотренное изменение, а не незапрошенная блокировка.

На карте отдельный первый обход ищет только ячейки/контейнеры. Поэтому товар из «Без ячеек» больше не перехватывает barcode ячейки/короба глубже в дереве. После этого по единственному product_id находится первая физическая строка; одинаковая карточка в нескольких местах не конфликтует сама с собой.

В inventory index ключом карточки стал productId, а не id строки остатка. При двух разных productId общий код даёт ошибку до выбора открытой тары и до found. При одном productId в нескольких местах выбирается прежний физический контекст. В production быстрый пересчёт открывает server count через `createObjectCount`, не `countFromMapRow`; у него есть sku и scan_codes из API. Preview-преобразование не выдаётся за доказательство production-контракта.

### Ошибки и три известных production-коллизии

`readApiErrorMessage` переводит строковые и структурированные `detail.code` для `barcode_ambiguous`, `barcode_is_ambiguous`, `scan_product_ambiguous` одним текстом. `FbsApiError` делает то же по коду до fbsErrorText; межтиповой `scan_ambiguous` не переименован. Ошибки `sendIntakeMutations` уже проходят через этот reader, поэтому удаление локального перевода из inboundReceivingHelpers не оставляет ffDraft без перевода. MP box отдельно переводит строковую серверную ambiguity в своём ручном parser.

Для переданных ведущим OZN2670717853, QB512 и 4680163562209 ожидается отказ без изменения товара там, где оба товара находятся в допустимой области. Сообщение объясняет причину и действие: «Код относится к нескольким товарам. Проверьте штрихкоды карточек». Оно не раскрывает чужие карточки и не предлагает случайный выбор. SKU/другой уникальный alias может быть рабочим обходом, но автоматического выбора первой карточки больше быть не должно. Эти production-данные ревьюер не перечитывал. Конкретный баг F2 относится к другой коллизии — когда тот же текст является ещё и кодом складского объекта.

### WB-only WMS-514

`FfFbsSupplyWorkspace.tsx`, KizReprintDialog и предметные KIZ/sticker файлы не изменены. В свободном поле сначала lookup заказа; при Ozon или выключенных режимах product endpoint не вызывается; exact KIZ reprint идёт перед product-auto-print при соответствующей галке. На сервере `fbs_scan_auto_print_service.py:185` отказывает не-WB поставке, а `:229` передаёт `WB_ONLY_PRODUCT_CODE_ALIAS_POLICY`, где `include_external_barcodes=False`. Поэтому новое принятие Ozon external barcode в WB-подборе/MP-отгрузке **не** включает его в WB-автопечать. Совпадение той же строки с собственным WB/SKU alias остаётся разрешением по этому WB/SKU alias, а не использованием Ozon policy.

## Проверки и производительность

1. `npx tsc --noEmit -p tsconfig.app.json` — **PASS**, exit 0, без вывода ошибок.
2. Основной адресный прогон 24 файлов: **338 тестов, 335 PASS, 3 FAIL**. В него вошли новые core/wedge/picker/inbound/outbound/inventory/map/error тесты и существующие product→KIZ, foundQueue, FBS WMS-514/load/auto-print/UX регрессии.

4. Третье падение — performance-порог `InventoryScan.test.ts` в общем параллельном прогоне: 1000 сканов по 1000 строкам за 1367 ms при пороге 1000 ms. Отдельный повтор всего файла с одним worker: **39/39 PASS**, тот же сценарий **427 ms**; сценарий 10 000 карточек со всеми alias и 100 сканов — **732 ms**. 5. Дополнительно `inboundDraftPersistence.test.ts` и `ScannerLine.test.tsx` — **12/12 PASS**. Это подтверждает unit-контракты retry/отказа и структуры scanner, а не работу физического сканера.

Все четыре дали ожидаемый для обнаруженного дефекта красный результат: F1 — неверный barcode+productId; F2 — 0 запросов вместо 1 в двух компонентах; F3 — null source и отсутствующий hint при фактическом Ozon DTO. Сценарии и результаты полностью приведены выше, поэтому заключение не зависит от сохранности временного каталога.

Индекс каталога кэшируется WeakMap по массиву; inbound catalog — по Map; документный inbound индекс memoized по lines/catalog; picker — по catalog; map — по снимку; inventory переносит индекс при изменении только actual. Каждый символ wedge не строит индекс. OUT-01/02 memoized по загруженному плану/каталогу; обновление pick-options после скана пересоздаёт индекс по новому массиву, даже если изменились только количества. В inbound новое detail.lines также перестраивает document index; аналогичная зависимость была у старого map. Это ограничение мемоизации, не найденный новый N+1.

Сам lookup стал Map-поиском, но весь scan не стал O(1): inventory ещё обходит дерево мест, находит строки карточки и обновляет actual; map отдельно обходит объекты и найденный product. По сравнению с прежним единым обходом количество проходов дерева выросло, хотя кодовые alias больше не сравниваются на каждой строке. Программный 10k тест проходит; утверждать по нему, что любой реальный документ или браузерный render не стал медленнее, нельзя. C27 с реальным viewport/focus и сопоставимым baseline остаётся отдельной проверкой.

Предоставленные ведущим 75 ms БД по 55 тыс. товаров относятся к серверному чтению. Фронт не добавил сетевой запрос на символ/alias, но эти 75 ms не включают получение всех alias, сборку Python-индекса и сериализацию. F4 добавляет лишнее серверное чтение на external-only совпадении. Полного замера backend-пути ревьюер не делал, поэтому «ни один одиночный скан не стал тяжелее» здесь не заявляется.
