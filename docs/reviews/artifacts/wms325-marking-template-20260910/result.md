## Concurrency and lock review

Pool replacement serializes competing replacements using a transaction advisory lock scoped to tenant + pool ID, without locking the parent pool row. Existing link rows are read/locked in ID order with `populate_existing=True`; deletes are taken from those rows, and actual inserts are identified using `ON CONFLICT DO NOTHING ... RETURNING`. A competing additive writer can commit without waiting for a new parent-row lock; if it wins the insert, replacement emits no event for that link. This removes the potential parent-lock/FK-insert inversion identified during author review of intermediate `e36b8c15`, before push. The additional two-connection regression pauses replacement immediately before insertion and executes the actual existing `add_pool_products` writer to completion, then confirms one link and no falsely attributed replacement event. Existing additive/removal/import functions were read and remain unchanged.

Threshold changes acquire only the selected pool's `FOR NO KEY UPDATE` row lock and use `populate_existing=True`; they acquire no link locks. Replacement does not rewrite thresholds. All new advisory keys include a purpose namespace and concrete tenant/object scope; none is a global application lock.

Template update/delete first read scalar scope columns, take a **PostgreSQL transaction advisory lock for this tenant + owner + product/seller scope**, then reread the target under `FOR NO KEY UPDATE` with both tenant/scope predicates and `populate_existing=True`. Default creation and all existing default-clear helpers use the same scope lock before template-row writes. Default peers are read/locked in ID order. This serializes opposing default switches and creation into an empty scope; locking existing template rows alone would not cover an empty scope or a newly inserted default. There is no global or tenant-wide advisory key, explicit foreign User/Seller/Product row lock, NOWAIT, operator blocker or navigation gate. Ordinary template reads are unchanged. PostgreSQL is the verified concurrency backend; the explicit PostgreSQL regression tests skip other databases.

Receipt removal retains the existing request → code → attachment-event locks and refresh behavior; no new lock is added to that path. Concurrent successful repeated setters write one event. After a first rollback, the second mutation owns the only saved event. Concurrent deletion retains the existing not-found rejection for the losing caller after a first commit, with no extra event; after a first rollback the second deletion succeeds with its own actor.
