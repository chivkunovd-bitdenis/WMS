## Находки

### F1 · P1 — новый товар в подтверждённой отгрузке на МП не получает резерв

**Место:** `backend/app/services/marketplace_unload_service.py:639–661`, особенно `:659–661`. Вход доступен администратору ФФ через `backend/app/api/marketplace_unload_requests.py:1079–1087`.

`add_line(..., allow_ff_confirmed=True)` проверяет общее Доступно под блокировкой товара, сохраняет строку и ставит `ff_modified`. Однако для добавленной строки не создаётся `MarketplaceUnloadReservation`. После commit блокировка освобождена, а общий расчёт продолжает считать эту единицу свободной. `_apply_reservations` вызывается при первоначальном планировании/подтверждении, но не здесь.

**Воспроизведение:** у селлера два товара P и Q, по одной единице на складе А. Создать черновик Ozon-отгрузки на складе Б с Q и датой; вызвать настоящий `confirm_request`. Q получает резерв 1. В подтверждённый документ добавить P × 1 через `add_line(..., allow_ff_confirmed=True)`. Затем импортировать/зарезервировать WB-заказ P на складе А через `update_fbs_order_reservation`.

Получено локально:

```text
CONFIRM_INITIAL_Q OrganizationStockTotals(on_hand=1, reserved=1, available=0)
ADD_P_TO_CONFIRMED OrganizationStockTotals(on_hand=1, reserved=0, available=1)
WB_AFTER_ADD_P reserved
```

**Ожидание:** после добавления P в подтверждённую отгрузку его Резерв = 1, Доступно = 0; новая бронь WB получает `no_stock`. Сейчас два действующих документа претендуют на последнюю единицу даже последовательно, без конкурентного исполнения. Публикация также продолжает видеть её свободной до появления другой брони.

**Почему это дефект:** нарушены R2, R4, R8 и цель R15. Наличие общего `FOR UPDATE` не помогает, если результат проверки не закреплён резервом в той же транзакции. Этот пропуск существовал в родителе, но является незакрытым сценарием явно запрошенного аудита всех путей WMS-530; он не объявляется новой регрессией данного diff.

**Исправление:** создавать/синхронизировать бронь новой строки подтверждённого документа до освобождения блокировки товара. Не запрещать оператору добавление строки. Повторная проверка должна включать последовательное воспроизведение выше и PostgreSQL-гонку такого добавления с FBS на другом складе.

### F2 · P2 — API окна FBS скрывает отрицательное Доступно

**Место:** `backend/app/services/fbs_stock_rule_service.py:635–640`, `:662–674`.

`get_rule_views` берёт `total.available_for_checks`, затем помещает это же обрезанное число в `FbsRuleView.free_stock` и каждый `FbsBindingRuleView.free_stock`. Эти значения без восстановления исходной разности сериализуются в одиночный `fbs-rule` и `fbs-rule/bulk` (`backend/app/api/products.py:1675`, `:1696`, `:1749`, `:1770`).

**Воспроизведение:** товар с Остатком 1 и ручным резервом 2 — допустимое состояние после уменьшения остатка инвентаризацией, прямо предусмотренное D3. Добавить активную WB-привязку и вызвать общий расчёт и `get_rule_views`.

```text
organization_stock_totals_by_product: on_hand=1, reserved=2, available=-1
FbsRuleView:                       on_hand=1, reserved=2, free_stock=0
FbsBindingRuleView:                on_hand=1, reserved=2, free_stock=0
published_now=0
```

**Почему это дефект:** R3/D3 требуют показывать отрицательную разность; R4/R6 требуют одинаковых чисел каталога и окна. Здесь `1 − 2 ≠ 0`. Ноль в `published_now` правилен; ноль в отображаемом `free_stock` скрывает перебор резерва. Ошибка находится в изменённом коде бэкенда, а не в незавершённом фронтенде.

**Исправление:** разделить отображаемую разность и неотрицательную базу для проверок/публикации. Проверить одиночный и bulk API, каждый блок привязки, публикацию 0 и отказ новой брони при том же снимке данных.

### F3 · P2 — рабочий список возвращает заказу брони всех соседних заказов

**Место:** `backend/app/services/fbs_worklist_service.py:729–751`, особенно `:739–744`; использование результата — `:1049–1053`.

В исключение общего расчёта попадают сразу все IDs заказов переданного списка. Затем одинаковое число сохраняется по ключу `(warehouse_id, product_id)`. Такой ключ не позволяет различить собственную бронь двух заказов одного товара на одном складе. После изменения глобальный список исключений дополнительно объединяет заказы разных складов.

**Воспроизведение:** Остаток P = 2; два реально забронированных WB-заказа P × 1, один на складе А, другой на Б. Общий Резерв = 2, Доступно = 0. Вызвать `_load_availability_by_warehouse_product` для обоих заказов, затем только для первого. Для контроля вызвать общий расчёт с исключением только первого заказа.

```text
global available=0
available excluding first order only=1
two_order_list=[2, 2]
one_order_list=[1]
```

**Почему это дефект:** R4 и R10 требуют исключать бронь этого заказа, а не всей страницы/подборки. Доступное количество одного заказа меняется при изменении состава списка без движения товара. Один и тот же дефект проявляется для нескольких заказов на одном складе; объединение разных складов расширяет его в данном diff. Новую блокировку выбора заказа это не создаёт, но ответ API недостоверен.

**Исправление:** общий расчёт выполнить пакетно, затем прибавить каждому заказу только его собственный резерв и хранить результат с различением заказов. Не возвращаться к поштучному полному расчёту для каждого заказа. Проверить одинаковый товар на одном/разных складах, заказ без брони, Ozon-позиции и независимость значения от фильтра списка.

### F4 · P2 — инвентаризация без адресного хранения всё ещё считает иной остаток и требует один склад

**Место:** `backend/app/services/inventory_count_service.py:258–259` и `:372–377`. Файл не изменён коммитом; это пропущенный потребитель из R4/R9.

При выключенном адресном хранении `_balance_query` оставляет только ячейки с кодом `__SORTING__`. Штатная ячейка брака имеет код `__DEFECT__` и исчезает из инвентаризации всего товара, хотя R1/D2 включают её в Остаток. Если сортировки есть на нескольких рабочих складах, `create_count` вместо общего документа выдаёт `warehouse_required_without_address_storage`.

**Воспроизведение А:** безадресное хранение, 5 единиц P в сортировке и 1 в штатной defect-ячейке. Создать инвентаризацию объекта `CountObject(type="product", id=P)` без склада/ячейки/тары.

```text
organization totals: on_hand=6, reserved=1, available=5
sum(count.lines.expected_quantity)=5
```

Ожидается «Числится» 6: это инвентаризация Остатка, а не продаваемого количества. Создание defect-ячейки выполнялось штатным сервисом; строка баланса — синтетическая фикстура.

**Воспроизведение Б:** тот же режим; P × 1 в сортировке склада А и P × 1 в сортировке склада Б. Та же инвентаризация всего товара возвращает:

```text
warehouse_required_without_address_storage
```

Ожидается документ с суммой «Числится» 2 и сохранением строк по местам. Это прямо соответствует R9 и не требует изменения физического размещения.

**Почему это дефект:** R1/R4/R9/R11 не выполнены для разрешённого режима хранения. Новый C1 проверяет только режим по умолчанию и поэтому не обнаруживает расхождение. Исправлять нужно включение строк и обработку общего документа, а не исключать брак из Остатка или вводить требование включить адресное хранение.

### F5 · P3 — публикация сохраняет N+1 запросов к правилам товаров

**Место:** `backend/app/services/fbs_stock_rule_service.py:1316–1317`; `_pool_rows` — `:234–244`.

После пакетного получения остатков публикация делает отдельный SELECT пулов/правил для каждого товара. Замер выполнен через SQLAlchemy `before_cursor_execute`, на одном селлере с одной активной WB-привязкой, без внешних вызовов; правила 100 %, товары без pool-строк:

| Вызов | 1 товар | 100 товаров |
|---|---:|---:|
| `get_rule_views` | 10 SQL | 10 SQL |
| `publish_amounts_for_binding` | 9 SQL | 108 SQL |

**Почему это важно:** на большом каталоге число обращений к БД линейно растёт, а при нескольких публикующих привязках цикл повторяется. Общий агрегат сам по себе этот участок не устраняет. Это подтверждённая существующая проблема производительности, а не новая регрессия 9391a374 и не измеренная задержка production. Она не является самостоятельной причиной отказа в приёмке WMS-530. Разумное исправление — пакетное чтение pool-строк, аналогично уже реализованному `get_rule_views`.

## R15: блокировки и границы доказательства

Общий лок реализован как `SELECT Product ... FOR UPDATE` с tenant-фильтром (`inventory_service.py:62–76`). Он не зависит от склада. Прослежены основные пути:

- WB/Ozon: блокируются все затронутые товары в стабильном порядке, существующие брони перечитываются после ожидания; затем проверка и создание брони находятся в той же транзакции (`:162–181`, `:224–263`). Повтор существующей брони не добавляет вторую.
- МП draft → submitted/confirmed: `_assert_available_for_unload_quantity` берёт тот же лок; `_apply_reservations` и commit выполняются после проверок. Для нескольких товаров установлен стабильный порядок.
- Старая «Отгрузка»: `sync_outbound_line_reservation` берёт тот же лок перед общей проверкой/созданием резерва. Перенос этой проверки на организацию не оставил складского локa вместо товарного.
- Подбор МП уменьшает остаток и резерв; возврат из подбора восстанавливает их. Обычные пути изменения остатка проходят через `record_movement_and_adjust_balance`, который также блокирует товар. Это не новый независимый счётчик.

Но абсолютное утверждение «общий лок есть во всех операциях с Резервом» неверно: ручные направления создаются/редактируются без него (`stock_direction_service.py:156–226`). D3 явно оставляет проверку направления против Остатка и допускает превышение совокупного Резерва; поэтому это не основание самовольно заменить её запретом по Доступно. Здесь не заявляется воспроизведённая PostgreSQL-гонка направлений. Основной подтверждённый провал защиты активного документа — F1, где лок есть, а фиксации резерва нет.

Предоставленный PostgreSQL-прогон `test_wms530_single_stock.py` не закрывает весь C15. В `:490–505` заказ Ozon создаётся **без `FbsOrderProduct`**, поэтому резервируется по fallback-пути `FbsOrderReservation`, а не через настоящие позиции Ozon. В файле также нет гонки FBS против планирования/подтверждения/добавления строки МП и против старой «Отгрузки». По чтению кода общий механизм для первоначального планирования согласован, но реальное конкурентное исполнение этих сочетаний этим отчётом не подтверждено.

## Что проверено без новых находок

**Формула R1–R3.** Общий `organization_stock_totals_by_product` суммирует подписанные строки InventoryBalance по tenant/product, без отсечения сортировки, складов, тары и старого псевдосклада. Направления прибавляются один раз. Брак включается в Остаток и Резерв. MP-резерв ограничен `submitted/confirmed/collecting`; старый outbound — `draft/submitted`; WB/Ozon учитываются общим объединением строк брони. Собранное МП исключается из резерва через уменьшение количества брони. Лимиты публикации в эту сумму не входят. Сам агрегат возвращает отрицательное доступное, а его `available_for_checks` корректно возвращает 0.

На новой in-memory БД непосредственно выполнены тела трёх существующих тестов с подменой только фонового планирования публикации:

```text
test_c1_balance_spread_across_places_matches_everywhere PASS
test_c2_reserve_composition_lifecycle_matches_everywhere PASS
test_r15_retry_import_does_not_double_reserve PASS
```

Это самостоятельное выполнение сценариев сервисов, **не** новый полный pytest-прогон и не PostgreSQL-проверка блокировок. C1 включает сумму 21 по разным местам и инвентаризацию в адресном режиме; C2 — состав резервов и исключение собственной брони МП; третий тест — последовательный повтор WB-брони.

**WMS-376/455/469/483 и served.** `split_amounts` продолжает независимо ограничивать каждую привязку через `min(share, max(0, available))`; общего потолка между WB/Ozon не введено. Код брони не расходует operator pool quantity. Различие `publish_enabled` и `units_configured` сохранено. Проверка периодического нуля WB использует тот же free-снимок, что публикация. Трансляция отбирается по `stock_sync_enabled`, а не по `served`; изменение базы не меняет включение приёма заказов. Новых дефектов в этих ветках по diff не найдено. Повтор внешних нулей/реальный WB/Ozon readback самостоятельно не выполнялись.

**Изоляция.** В новых агрегатах есть tenant и product фильтры; defect-запрос дополнительно ограничивает склад и ячейку tenant. Summary сначала ограничивает продукты seller scope, МП проверяет seller документа и продукта, списки правил выбирают продукты tenant и группируют их по селлеру. Изменение warehouse-scoping на organization-scoping не снимает эти ограничения.
