Проверен коммит `ca2f031ef7921b1c3893320523320d2c3c9e6f58` в ветке `fix/wms537-draft-supply-stickers`, рабочий каталог `/Users/deniscivkunov/Projects/WMS/.worktrees/wms537-draft-stickers`. База сравнения — `89680ae3`. Перед проверкой прочитаны целиком AGENTS.md, обе библиотеки `owner-cases.md` и `failure-cases.md` из основного checkout по указанным владельцем путям, требования WMS-537 и WMS-475. ## Находки

### F1 · P2 — проверка отменённого заказа остаётся зелёной при запросе его стикера в WB

**Место:** `backend/tests/test_wms537_draft_supply_stickers.py:869`; такое же неверное число стоит на строке 861.

Тест `test_cancelled_order_already_in_draft_is_not_requested_when_adding_another` создаёт заказ A с номером **537801** (строка 807), переводит его в `cancelled` и добавляет другой заказ, 537802. Но обе проверки обращений к WB ищут **537701**, которого в этом сценарии вообще нет. После `start-work` тест проверяет только HTTP 200 и отсутствие этого постороннего номера. Поэтому запрос стикера настоящего отменённого заказа остаётся незамеченным. Результат `order_cancelled`, упомянутый в комментарии теста, тоже не проверяется.

**Воспроизведение.** В отдельном процессе Python исходный текст `request_supply_print_batch` прочитан через `inspect.getsource`; единственное условие `if order.status == FBS_ORDER_STATUS_CANCELLED:` заменено на `if False:`. Изменённая функция скомпилирована и подставлена только в память этого процесса. Файлы приложения на диске не менялись. Запущен только указанный тест с настоящим тестовым API, SQLite и существующим моком WB. Перед вызовом получения этикеток добавлен вывод номеров тестовых заказов. Получено:

```text
REVIEW_WB_REQUEST ['537802']
REVIEW_WB_REQUEST ['537801']
1 passed, 5 warnings in 1.62s
```

Первая строка — нормальное получение стикера нового заказа; вторая — запрещённое R5 получение стикера отменённого A при начале работы. Тест ошибочно считает оба действия корректными. Это дефект проверки, а не обнаруженный запрос отменённого заказа в неизменённом продукте.

**Требуемое исправление:** проверять номер созданного A (`537801`, лучше через переменную, использованную при создании), после добавления ожидать обращения только за E, а после `start-work` — отсутствие новых обращений за отменённым A. Перехватить результат общего запроса печати и проверить `order_errors` с `order_cancelled` для A либо отдельно проверить этот результат существующим API печати. Исправленная проверка должна падать при отключённом фильтре и проходить на неизменённой продуктовой реализации.

### F2 · P3 — в требованиях неточно указан существующий отказ Ozon

**Место:** `docs/requirements/WMS-537.md:51`; та же неточность повторяется в C10 на строке 84 и в описании процесса.

R6 требует сохранить прежнее поведение Ozon, но называет внешний код `409 marketplace_not_supported`. В действительности `add_orders_to_existing_supply` сначала выполняет проверки состава (`backend/app/services/fbs_supply_service.py:1951`), а `supply_order_link_discrepancy` отвергает любую не-WB поставку с `different_marketplace` (`backend/app/services/fbs_supply_composition_service.py:117`). Обёртка возвращает `409 order_incompatible` с этой причиной в `issues`. Более поздняя проверка `marketplace_not_supported` на строке 1967 в таком сценарии не достигается.

**Воспроизведение:** `test_ozon_draft_add_is_rejected_before_any_marketplace_or_sticker_call` прошёл в независимом прогоне; он изолирует проверку совместимости с существующей поставкой, подменяя общий предварительный расчёт. В базе `89680ae3` порядок проверок и функция совместимости те же: diff этих участков отсутствует. Следовательно, это **неточность постановки, не дефект реализации WMS-537**. Менять продуктовый код отказа под ошибочное описание не нужно; аналитику следует уточнить R6/C10. Полный набор `test_fbs_ozon_lane.py` в нашем SQLite-прогоне также прошёл.

По аналогичной причине в C9 следует различать общий `order_incompatible` и вложенную причину `order_bad_status`: новый тест отменённого добавления правильно ожидает общий код 409. Это уточнение описания существующего поведения, не основание менять API.

P0 и P1 не обнаружены. Других подтверждённых P2/P3 нет.
