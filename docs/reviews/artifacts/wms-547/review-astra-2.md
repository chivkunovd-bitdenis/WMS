## F1 — закрыт

Ручное сохранение больше не проигрывает автоматическому созданию записи
между первоначальным чтением и INSERT. В
`backend/app/services/billing_configuration_service.py:152–172` сначала
открывается savepoint — точка частичного отката транзакции, затем внутри
`try` создаётся и добавляется объект и выполняется `flush`. Следовательно,
автоматический flush при `begin_nested()` не может преждевременно вставить
этот объект. При конфликте уникальности откатывается именно savepoint,
запись перечитывается по тем же `tenant_id` и `seller_id`, после чего все
восемь полей получают ручные значения через общий `_apply` (строки 123–130).
Если конфликтную запись найти не удалось, исключение не маскируется успехом.

Обе очерёдности проверены тестами разработчика через настоящий HTTP PUT
с авторизацией. Дополнительные независимые проверки использовали HTTP PUT
для ручного сохранения и административный HTTP PATCH для подключения WB:

1. **Ручная запись первой.** Автозаполнение уже прочитало отсутствие профиля;
   во время ожидания WB выполняется ручной PUT. Последующая автоматическая
   вставка не меняет профиль. PATCH и PUT возвращают 200; в базе одна строка
   со всеми восемью ручными полями, в журнале одно событие ручного изменения.
2. **Автоматическая запись первой.** Ручной PUT уже прочитал отсутствие профиля;
   перед его вставкой выполняется PATCH с автозаполнением. Отдельным чтением
   подтверждено, что автоматический профиль действительно создан и сохранён.
   Затем ручной PUT завершается с 200. В базе одна строка со всеми восемью
   ручными полями; оба события журнала сохранены, включая ручное изменение.

Проверки используют отдельные сессии и настоящие запросы/ограничения SQLite;
подменены внешние ответы и точки переключения между операциями. Это проверка
заданных очерёдностей, а не нагрузочная проверка блокировок PostgreSQL.

Нового пути перезаписи ручных данных автозаполнением нет:
`seller_marketplace_requisites_service.py:303–339` по-прежнему либо выходит
при существующем профиле, либо делает прямой INSERT и откат при конфликте.
Вызова `save_profile` и пути UPDATE в автозаполнении нет. Общий `save_profile`
используется только двумя ручными обработчиками billing: реквизиты ФФ и
реквизиты селлера. Его проверки входных полей сохранены; снимок `before` для
журнала при конфликте берётся из перечитанной записи, а не остаётся `None`.

**PostgreSQL — корректность по коду.** Порядок `begin_nested → add → flush →
rollback savepoint → SELECT → UPDATE` соответствует рекомендованной защите
от нарушения уникальности: внешний transaction остаётся пригодным для работы.
`nested.commit()` освобождает savepoint; окончательный commit остаётся у
HTTP-обработчика вместе с записью журнала. Это согласуется с
[документацией SQLAlchemy о SAVEPOINT](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html#using-savepoint).
При стандартном для PostgreSQL `READ COMMITTED` повторный SELECT видит
успевшую закоммититься автоматическую запись, даже если первый SELECT её
не видел — см. [уровни изоляции PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html#XACT-READ-COMMITTED).
В `backend/app/db/session.py` уровень изоляции не переопределён; в коде приложения
и миграциях переопределений также не найдено. Настройки живого сервера не
проверялись. Вывод относится к `READ COMMITTED`; доказательство для изменённой
серверной настройки `REPEATABLE READ`/`SERIALIZABLE` здесь не заявляется.

## F2 — закрыт

В `backend/app/services/dadata_party_service.py:78–94` синтаксически неверный
JSON перехватывается как прежде, а теперь и любой JSON верхнего уровня,
не являющийся объектом, превращается в `DadataError("dadata_unavailable")`
до вызова `_first_party`. Проверка типа охватывает не только три примера
первого ревью, но и числа, логические значения, непустые массивы и пустую строку.
Журнал нового обработчика содержит только имя типа, без содержимого ответа.

Независимо проверены 11 тел ответа через настоящий `lookup_party_by_inn`
на `httpx.MockTransport`: буквальный `null`, `[]`, `[{}]`, строка
`"unexpected"`, пустая JSON-строка, `0`, `1.5`, `true`, `false`, сломанный JSON
`{` и пустое HTTP-тело. Для каждого выполнены три проверки:

- прежний `GET /billing/profiles/lookup-inn` возвращает **502** с кодом
  `dadata_unavailable`, а не необработанный 500 и не `party_not_found`;
- административный PATCH подключения WB возвращает **200**, и автоматический
  профиль действительно сохраняется с ИНН/наименованием WB и пустым КПП;
- новый GET `marketplace-requisites?marketplace=wb` возвращает **200** с теми
  же данными WB и пустым КПП.

Легитимный ответ `{"suggestions": []}` отдельно проверен через старый HTTP
эндпоинт: **404 / party_not_found**. Корректная непустая подсказка также
проверена через него: **200**, наименование и КПП сохранены в ответе.
Таким образом, исправление не превращает штатное отсутствие организации
в ошибку доступности и не ломает успешную подстановку.

Поиск по `backend/app` нашёл ровно два непосредственных потребителя клиента:

1. `backend/app/api/billing.py:497–514` — старая кнопка «Заполнить по ИНН».
   Она уже перехватывает `DadataError`; новый код попадает в существующее
   отображение 502. Во фронте `FfBillingProfilesDialog.tsx:157–188` неуспешный
   ответ показывает существующий текст `LOOKUP_ERRORS.dadata_unavailable`,
   не изменяет форму и освобождает кнопку через `finally`.
2. `backend/app/services/seller_marketplace_requisites_service.py:214–225` —
   `overlay_dadata`, общий для новых кнопок WB/Ozon и автозаполнения.
   Перехват `DadataError` возвращает исходные реквизиты площадки. Исправление
   находится до этой развилки и распространяется на обе площадки; дополнительный
   HTTP-прогон с настоящим клиентом DaData выполнен на пути WB.

Граница вывода: исправление не вводит полную проверку схемы объектов DaData.
Например, словарь без `suggestions`, с `suggestions: null` или первым элементом
не-объектом по прежнему `_first_party` тоже классифицируется как
`party_not_found`. Это существующее поведение, не изменение данного diff;
оно не вызывает описанные в F2 падение или потерю данных площадки.
«Все непригодные ответы теперь всегда дают dadata_unavailable» было бы
слишком широким утверждением. Закрыт дефект F2 из первого ревью: необработанный
JSON не-объект и вызванная им потеря доступных реквизитов.

Есть точность тестового покрытия, которую важно сохранить в свидетельствах:
в установленном httpx `Response(200, json=None).content == b''`. Поэтому
существующие параметризации с именем `null` фактически проверяют пустое тело.
Буквальный JSON `null` независимо проверен здесь через `content=b'null'` и
тоже проходит. Это не оставшийся дефект продукта и не основание вернуть F2.
