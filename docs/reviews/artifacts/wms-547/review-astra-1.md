## Замечания

### F1 — существенное: ручное сохранение может проиграть автозаполнению и получить 500

**Место в изменениях:** `backend/app/services/seller_marketplace_requisites_service.py:327–339`.
Связанный существующий путь: `backend/app/services/billing_configuration_service.py:124–141`
и `backend/app/api/billing.py:393–408`. Текущий тест:
`backend/tests/test_seller_requisites_autofill.py:392–452`.

Прямой INSERT с перехватом `IntegrityError` защищает только одну очерёдность:
человек первым завершил сохранение, после чего автоматическая запись проиграла
уникальному ограничению и была отменена. Обратная очерёдность не защищена.
Ручной `save_profile` сначала читает запись и, если её нет, тоже готовит INSERT.
Между этим чтением и INSERT автозаполнение может успеть создать реквизиты.
Тогда уже ручное сохранение получает `IntegrityError`, который его HTTP-обработчик
не перехватывает. Человек получает 500; в базе остаются автоматические реквизиты.

Это не утверждение, что уже успешно сохранённые ручные значения перезаписываются:
подтверждённый дефект — отказ ручного сохранения при предусмотренной требованиями
одновременной работе. Новое автозаполнение создаёт этого конкурирующего писателя.

**Почему:** R8 требует корректного результата при одновременном ручном и
автоматическом заполнении. AGENTS §3 требует защиты связанных записей от
конкуренции; применим B05 — пользователь должен суметь сохранить документ и
продолжить работу после сбоя. Наличие одной строки в БД само по себе не означает,
что весь путь сохранения прошёл.

**Как воспроизвести:**

1. Создать тестового селлера без реквизитов. Админом ФФ отправить
   `PATCH /integrations/wildberries/sellers/{id}/tokens` с тестовым ключом.
   Ответ подставного WB `seller-info` задержать.
2. Другим HTTP-запросом этого админа начать
   `PUT /billing/profiles/sellers/{id}` с ручными ИНН и наименованием.
   Остановить выполнение после того, как `save_profile` прочитал отсутствие
   `BillingProfile`, но до записи.
3. Разрешить ответ WB с корректными ИНН и другим наименованием и дождаться
   commit автоматического заполнения. PATCH завершится с 200.
4. Продолжить ручной PUT. Фактически получен **500**. Последующий GET профиля
   вернул автоматическое наименование, а не ручное.

Воспроизведено на изолированной SQLite БД тестового контура. Блокировки ожидания
в тесте задавали только очерёдность; чтение, INSERT, уникальное ограничение,
авторизация и HTTP-обработчики были настоящими. На PostgreSQL отдельно не проверено.

**Что исправить:** согласовать оба пути создания так, чтобы ручное сохранение
корректно завершалось и при появлении автоматической записи после его чтения.
Не возвращать автозаполнение к безусловному обновлению через `save_profile`:
это сломает уже работающую защиту ручных значений. Проверить обе очерёдности
через HTTP с токенами. Нынешний C8 вызывает ручной `save_profile` напрямую и
проверяет только вариант «ручной commit раньше автоматического INSERT».

### F2 — существенное: некорректная структура ответа DaData ломает успешное получение реквизитов

**Место в изменениях:** `backend/app/services/seller_marketplace_requisites_service.py:219–225`.
Причина в вызываемой функции: `backend/app/services/dadata_party_service.py:38–39,78–84`.

Новый `overlay_dadata` восстанавливается только после `DadataError`.
Существующий клиент DaData при HTTP 200 с JSON `null`, массивом или строкой
вызывает `.get()` на значении, которое не является словарём. Возникает
`AttributeError`, а не `DadataError`. В новом эндпоинте кнопки это становится
необработанным **500**, хотя WB уже вернул корректные ИНН и наименование.
При автоматическом заполнении внешний `except Exception` сохраняет успешный
ответ на подключение ключа, но выбрасывает полученные реквизиты целиком.

**Почему:** R4 и R11 требуют использовать полученные данные площадки, когда
DaData недоступна или не дала пригодного ответа. Применим B03 — некорректная
структура внешнего ответа не должна ронять доступный пользователю путь.
Ошибка находится в старом клиенте, но новый вызов WMS-547 обещает мягкий отказ
этой необязательной подстановки и фактически его не обеспечивает.

**Как воспроизвести:**

1. В тесте настроить подставной DaData-токен; WB `seller-info` возвращает HTTP 200,
   корректный ИНН `500100732259` и непустое наименование.
2. Подставной HTTP-ответ DaData: по очереди `200 null`, `200 []`, `200 "unexpected"`.
   Использовать настоящий `lookup_party_by_inn`, подменяя только HTTP-транспорт.
3. Сохранить WB-ключ через административный PATCH: фактически **200**,
   автозаполнение завершается через обработчик неожиданной ошибки.
4. Вызвать `GET /billing/profiles/sellers/{id}/marketplace-requisites?marketplace=wb`
   с токеном админа: во всех трёх вариантах фактически **500**.

Ожидаемый результат кнопки — 200 с ИНН/наименованием WB и пустым КПП;
существующий КПП и банковские поля формы остаются нетронутыми.

**Что исправить:** нормализовать непригодный внешний ответ в штатную ошибку
подстановки и сохранить возврат к данным площадки. Добавить HTTP-проверки этих
ответов с настоящим клиентом DaData на подставном транспорте. Текущие C3
подменяют сам `lookup_party_by_inn` и заранее выбрасывают `DadataError`, поэтому
эту ошибку разбора не обнаруживают.

## Проверено без замечаний в указанном объёме

- **Контракт WB:** официальный опубликованный ответ содержит `name`, `tin`,
  `sid`, `tradeMark`; используются только `name` и `tin`. Метод — GET на
  `common-api`, доступен токену любой категории. Это подтверждено доступной
  индексированной [официальной документацией WB](https://dev.wildberries.ru/en/docs/openapi/api-information)
  и [официальной записью о добавлении ИНН](https://dev.wildberries.ru/en/news/302).
  Банковские поля и КПП из ответа WB не выдумываются.
- **Разбор и ошибки площадок:** проверка ИНН переиспользует `validate_inn`.
  Отсутствующий/null/пустой/некорректный ИНН WB обрабатывается; отсутствие
  объекта `company` у Ozon не роняет сервис. Приоритет `company.legal_name`
  над `company.name` соответствует требованиям. Ozon вызывается через
  `build_ozon_provider`; 403 с кодом 7 распознаётся отдельно. Штатные 401,
  429, 5xx, таймаут и битый JSON WB не отменяют сохранение ключа.
- **Существующие реквизиты:** автозаполнение сначала проверяет наличие любой
  записи и сразу выходит, не меняя ни одного поля. Прямой INSERT оправдан:
  он не превращается в незаметный UPDATE вручную сохранённых данных.
  Направление гонки «ручной commit первым» работает; обратное описано в F1.
- **Повторное сохранение ключа:** дополнительная HTTP-проверка двух одинаковых
  административных PATCH дала два ответа 200 и всего один вызов WB seller-info.
  Уникальный индекс существующей таблицы предотвращает вторую запись.
- **Сессия и журнал:** автозаполнение открывает собственную `SessionLocal`,
  не использует сессию закончившегося HTTP-запроса; профиль и событие журнала
  фиксируются одной транзакцией. Конфликт INSERT откатывается. WB запускает
  эту функцию через `BackgroundTasks`; Ozon ожидает её до ответа — это
  синхронное ожидание асинхронной функции, а не отдельная фоновая задача.
  Штатный отказ реквизитов не отменяет уже сохранённый ключ.
- **Права:** новый GET использует ту же `require_fulfillment_admin`, что окно
  реквизитов, и проверяет селлера в тенанте до получения ключей. HTTP-тесты
  подтвердили 404 для чужого/несуществующего селлера и 403 для роли селлера.
  Дополнительная HTTP-проверка сотрудника ФФ с `settings=true` дала 403 для
  WB и Ozon, без обращения к площадке. Ключи выбираются по целевому селлеру
  с проверкой тенанта; новая ручка не принимает ключ от клиента.
- **Секреты в обработанных отказах:** новые ответы содержат только реквизиты
  или фиксированный код ошибки. Тест C12 с синтетическими WB/Ozon-значениями
  прошёл: значения ключей отсутствуют в ответах и проверяемых сообщениях
  журналов. Сырые тела ошибок площадок новый сервис не возвращает.
  Это подтверждение проверенных путей, а не доказательство безопасности
  произвольного неожиданного исключения в общем `logger.exception` на строке 362.
- **Нет автоматического опроса:** поиск всех мест вызова подтвердил только
  сохранение WB/Ozon-ключа и явный GET по кнопке. Вызовов из открытия карточки,
  списка, периодических задач или циклов повторения нет. В проверке C4
  повторные чтения профиля не расходуют обращения к WB.
- **Форма и границы фронтенда:** по diff и восьми тестам новые кнопки видны
  только при `sellerId` и соответствующем признаке подключённой площадки.
  Они делают GET и меняют состояние формы, не вызывают PUT. Банковские поля
  не меняются; null/отсутствующий КПП не стирает введённый. Ошибка остаётся
  в существующем `ErrorNotice`, `finally` освобождает кнопки.
  В «Расчётах» без `sellerId` кнопок нет. Кроме добавления кнопок и переноса
  строки при нехватке ширины, разметка окна не изменена; новых поясняющих
  блоков, подписей источника и чипов нет. Визуальная проверка не заявляется.

## Как оформить пять падений C7 при объединении с WMS-548

`backend/tests/test_seller_requisites_autofill.py:290–303` фиксирует старый
результат подключения ключа, включая `products_created=1`. Для этой базы
это корректное ожидание, и пять параметризованных C7 прошли в текущей ветке.
По сообщению ведущего WMS-548 намеренно переносит создание товаров на момент
после выбора, поэтому старый снимок ответа становится неверным при объединении.
Само пробное слияние и его пять падений здесь заново не выполнялись.

Это следует записать как **несовместимость тестового контракта объединённой
ветки с изменённым процессом WMS-548**, а не как доказательство поломки
автозаполнения WMS-547. Отсутствие текстовых конфликтов не означает, что
интеграция проверена. Перед принятием общей ветки нужно:

- В требованиях/результатах проверок обеих задач явно зафиксировать новый
  порядок: сохранение ключа → выбор товаров → создание выбранных товаров.
  Проверка реквизитов не должна возвращать прежний немедленный импорт.
- Переписать C7 для объединённого контракта: ответ и состояние подключения
  при сбое seller-info совпадают с контрольным сценарием той же версии
  WMS-548 без сбоя реквизитов. Сохранить проверки ключа, отсутствия реквизитов
  при отказе, отсутствия повторов и возможности повторить подстановку кнопкой.
- В сценариях WMS-548 проверить, что до выбора товары не созданы, а после
  выбора создаются только выбранные. Не ослаблять тест до одного HTTP 200
  и не оставлять пять падений под skip/xfail. В чистой текущей ветке WMS-547
  механически заменять `products_created=1` на 0 нельзя.
- Зафиксировать результат совместного прогона с SHA объединённой ветки.

По прямому поручению ревью сохранено только в этом файле, без commit/push.
Статус требований и аналитическая приёмка не изменялись.
