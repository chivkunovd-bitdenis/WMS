# WMS-675: конкретный следующий запуск

Нужна одна операция: **исполнить опубликованный `collect_ozon_bound.py` в уже настроенной штатной среде WMS backend с обычным приложением и его seller-bound подключением Bambook**. Это не запуск синхронизации и не кнопка «Передать»: они могут менять WMS-учёт. SQL-шлюз эту операцию не предоставляет; менять его, использовать обходной SSH, копировать credentials или выпускать JWT нельзя. В данном агентском сеансе backend execution transport отсутствует. Если у ведущего есть существующий разрешённый runner приложения, он подходит; иначе необходим оператор с доступом именно к выполнению штатного приложения, а не к кабинету API-ключей.

До запуска нужен независимый review новой дельты: сборщик и offline-проверки. Они находятся в этой ветке вместе с матрицей конкретных31 позиций. Независимая приёмка/CI продуктового662 не заменяют review утилиты. Код662 не копировался и не менялся.

В штатной среде Python должны быть доступны пакет `app` текущего WMS backend, PostgreSQL и обычные настройки живого Ozon. Не менять флаги/настройки: если live transport выключен или host отличается от `https://api-seller.ozon.ru`, сборщик завершится без внешнего запроса. Сначала сохранить manifest такой попытки, не включать live API ради аудита.

Поместить **два проверенных файла** `collect_ozon_bound.py` и `ozon_read_plan.json` рядом в отдельный постоянный каталог runner; это не требует менять checkout/версию работающего API. Команда внутри существующей штатной среды backend (пути к runner/proofs задаются её оператором):

```sh
cd /app
PYTHONPATH=/app python /audit/wms675/collect_ozon_bound.py \
  --output /audit/wms675/proofs-20261006-attempt1
```

`/app` — рабочий каталог backend в существующем контейнере WMS; `/audit/wms675` — отдельный постоянный каталог, предоставленный штатным runner. Для обычного checkout вместо `/app` указать его `backend`. Команду нельзя выполнять через tenant SQL gateway или заменять её произвольным серверным доступом. Каталог `--output` должен быть новым: существующий сборщик не перезаписывает. stdout содержит только статус, число карточек и путь. Все карточки читаются ровно один раз в этом проходе. Читатель ограничен124 уникальными карточками; превышение остаётся незавершённым, а не успешным доказательством.

Вернуть только файлы из нового каталога: `manifest.json`, `scope_snapshot.json` и `posting-*.json`. Никаких environment dumps, конфигов подключения или raw HTTP. Manifest сохраняется после каждой карточки; отдельные результаты имеют timestamps/status/server Date/SHA-256. Ошибки остаются `unknown`, без скрытых retry. Список связанных отправлений получен исключительно от Ozon, включая связанные весовые номера; ни один child не конструируется из суффикса. Сборщик читает больше подробностей, чем старый status-fetch (включает related_postings), но ничего не сохраняет в WMS.

`READ_COMPLETE_REQUIRES_ACCOUNTING_PLAN` означает только завершение чтения. Он не подтверждает расход: нужно оценить реальный граф parent/children, отмены, совпадение SKU/offer/quantities и текущие правила662. Отсутствующий products/split остаётся неизвестным. Циклы/пересечения/неполный граф/незнакомый подстатус нельзя превращать в положительное проведение. Весь старый снимок31, включая четыре отмены и одно ожидание сборки, нужен для полного чтения; это не план списать31.

После чтения ведущему предъявляется новая версия плана по каждой исходной позиции: exact postings/SKU/quantities, доказательство, уже проведённое и `missing = max(0, proved_unique_quantity - already_conducted_quantity)`. Сейчас эти поля в `recovery_plan_pending.json` честно `null`. Предыдущие ledger/history доказывают0 расхода лишь на06:53–06:54UTC; перед проведением повторно проверяется свежий учёт под штатными блокировками662. Ни этот файл, ни возврат HTTP200 не разрешают мутацию. После предъявления плана выполняется только согласованная локальная часть662 на проверенной deployed версии, с атомарным расходом/ledger/reserve и нулевой повторной дельтой. Обычный `deliver_supply`, Ozon ship/carriage/approve, внешние КИЗ, печать и ЭЦП не используются.

Локально выполнено: шесть offline-проверок и ruff новой утилиты прошли. Эти проверки не запускают приложение, не читают настройки и не вызывают сеть; live запуск, независимое ревью и восстановление остаются невыполненными.
