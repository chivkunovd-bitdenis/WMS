## F1 — P1: повтор старого завершения снова закрывает уже переоткрытую приёмку

Нарушены R7 и R6; связаны C7/C8 и правило B09 о восстановлении прежней операции. Место: coordinator `backend/app/services/inbound_intake_service.py:1563–1577`, web `frontend/src/screens/ff/FfInboundRequestView.tsx:1970–1972`, Android `InboundDraftViewModel.kt:180–182`.

Защита завершения ограничена текущим статусом `sorting/done`. У попытки завершения нет собственного идентификатора: оба новых клиента сохраняют и повторяют пустой POST. В отличие от создания, добавления и исправления количества сервер не записывает результат именно этой попытки.

Воспроизведено через API: создать ФФ-документ A=3 → отправить `complete-receiving` (ответ клиенту считаем потерянным) → другим операторским действием `reopen-receiving` → повторить **тот же** старый `complete-receiving`. Перед повтором документ `receiving`, после повтора — опять `sorting`; сумма движений снова +3. Повтор старого запроса закрывает чужую текущую правку без нового намеренного завершения. Это не удвоение конечного остатка до6: дефект — новое оприходование после предусмотренной отмены первого прихода и срыв редактирования. В браузере сохранённый pending-запрос допускает именно такой повтор.

Исправление должно различать старый повтор и новое осознанное завершение после исправлений, сохраняя совместимость прежнего API. При проверке старый повтор не закрывает новую фазу редактирования; отдельное новое завершение исправленного факта выполняется один раз. Новая сущность или запрет переоткрывать документ для этого не требуются.

## F2 — P2: окончательный отказ первой строки пакета навсегда запирает веб-документ

Нарушены R7 и R2; C6/C10/C11, B05. Место: `frontend/src/screens/ff/inboundDraftPersistence.ts:45–51` и `:31`; вызывающий `FfInboundRequestView.tsx:1482`.

После окончательного 4xx pending очищается только если в нём одна строка. Для двух и более строк отказавшая первая мутация и оставшиеся сохраняются неизменными. «Проверить результат» повторяет тот же заведомо неверный body, а исправленная попытка отклоняется строкой31. Перезагрузка оставляет блокировку в localStorage; UI не имеет действия исправить/отменить этот отказавший пакет.

Воспроизведение: в каталоге выбрать A с количеством1000000001 и B=2. Picker допускает такой ввод, applyPicker фильтрует лишь целое положительное число. Сервер отказывает A по установленной границе количества. В Vitest на фактической функции воспроизведён ответ422 первой строки; два повтора и попытка отправить A=1 оставляют прежний `[A,B]` и отказ «Проверьте результат предыдущего запроса приёмки». Тот же дефект возможен при окончательном отказе товара/доступа первой строки; большой ввод здесь только воспроизводимый пример.

Нужно сохранять пользовательский набор для исправления после подтверждённого отказа, разрешить продолжение и при этом не повторять уже успешно добавленные строки. Не путать окончательный отказ с неизвестным сетевым результатом.

## F3 — P2: настоящий штрихкод Ozon не работает в новом Android-пути

Нарушены R1/R2/R9/R11, C1/C2/C10/C13/C14. Место: Android `features/inbound/InboundDraftViewModel.kt:192–200`, DTO `core/api/inbound/InboundDraftApi.kt` (`DraftProduct`). Связанные серверные границы: `catalog_service.py:list_products`, `_barcode_index_for_request` в `inbound_intake_box_service.py` и `inbound_cargo_place_service.py`.

Обычный каталог отдаёт настоящий штрихкод Ozon в `marketplace_bindings[].external_barcodes`. Новый Android DTO это поле не читает, а скан без тары дополнительно сначала вызывает каталог с `search=barcode`, где поиск не включает external_barcodes. Даже если получить весь каталог, точный фильтр Android проверяет лишь WB-поля, внутренний SKU и идентификаторы Ozon, не штрихкоды Ozon. В выбранную тару Android отправляет только barcode без разрешённого product_id; серверные индексы тары также не знают external_barcodes.

На собственной БД создан товар с настоящим отдельным внешним штрихкодом `2000000440998` (не совпадает с SKU/артикулом). API полного каталога вернул его в external_barcodes; поиск этим кодом вернул `[]`; проверка точного набора полей Android дала отсутствие совпадения; POST скана в короб вернул404 `barcode_unknown`. Сам Android на устройстве не запускался, вывод о его UI следует из фактического ответа и кода. Нельзя заменить исправление копированием штрихкода Ozon в WB-поле тестового товара. Проверить скан снаружи тары, в короб и в грузоместо для Ozon и объединённого товара, с сохранением обработки неоднозначного кода.

## F4 — P2: новая веб-колонка площадки скрывает WB у обычного и объединённого товара

Нарушены R9/R10 и явное правило AGENTS об обозначении площадки; C1/C10/C11. Место: `frontend/src/screens/ff/FfInboundRequestView.tsx:3712`.

Колонка читает `marketplace_bindings`, но этот серверный массив здесь описывает Ozon-коды, а не полный набор площадок. Список площадок уже есть отдельно в `marketplaces`. На API подтверждено: у объединённого товара `marketplaces=[wb,ozon]`, bindings содержит только `ozon`. Текущий JSX показывает только «Ozon»; у WB без Ozon bindings пустой, поэтому показывается «—». Самостоятельная визуальная браузерная проверка этого места не выполнялась; результат однозначно следует из проверенного payload и JSX.

Использовать существующий полный признак площадок; проверка должна покрыть WB, Ozon и объединённый товар. Другие подписи, изменённые443, сюда не относятся.

Это чтение исходников, не фактический проход эмулятора. Сохранить защиту реальных несохранённых изменений (включая D6), но не считать простой просмотр изменением.
