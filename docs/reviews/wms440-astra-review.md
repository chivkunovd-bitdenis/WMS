## F1 — P1: повтор старого завершения снова закрывает уже переоткрытую приёмку

Нарушены R7 и R6; связаны C7/C8 и правило B09 о восстановлении прежней операции. Место: coordinator `backend/app/services/inbound_intake_service.py:1563–1577`, web `frontend/src/screens/ff/FfInboundRequestView.tsx:1970–1972`, Android `InboundDraftViewModel.kt:180–182`.

Защита завершения ограничена текущим статусом `sorting/done`. У попытки завершения нет собственного идентификатора: оба новых клиента сохраняют и повторяют пустой POST. В отличие от создания, добавления и исправления количества сервер не записывает результат именно этой попытки.

Воспроизведено через API: создать ФФ-документ A=3 → отправить `complete-receiving` (ответ клиенту считаем потерянным) → другим операторским действием `reopen-receiving` → повторить **тот же** старый `complete-receiving`. Перед повтором документ `receiving`, после повтора — опять `sorting`; сумма движений снова +3. Повтор старого запроса закрывает чужую текущую правку без нового намеренного завершения. Это не удвоение конечного остатка до6: дефект — новое оприходование после предусмотренной отмены первого прихода и срыв редактирования. В браузере сохранённый pending-запрос допускает именно такой повтор.

Исправление должно различать старый повтор и новое осознанное завершение после исправлений, сохраняя совместимость прежнего API. При проверке старый повтор не закрывает новую фазу редактирования; отдельное новое завершение исправленного факта выполняется один раз. Новая сущность или запрет переоткрывать документ для этого не требуются.

### F1-R2 — P2: успешный второй UUID теряется при отказе фоновой проверки

R7/R6, C7/C8. Точное место: backend `inbound_intake_service.py:1581–1592`, возврат из ветки `SORTING_STATUSES | DONE_STATUSES` после записи новой попытки. Связанный путь — `api/inbound_marking.py:39–47` и `inbound_marking_service.py:427–459`.

Основной UUID, который выполнил приход, коммитится вместе с ним и корректно переживает reopen. Но если другой сотрудник/клиент завершает тот же документ собственным UUID B, когда первый UUID A уже перевёл его в sorting, новая запись B не фиксируется в `complete_receiving`. В обычном API-пути её случайно фиксирует последующая фоновая проверка маркировки. Если эта необязательная стадия падает, её обработчик делает rollback, при этом API всё равно возвращает200/sorting. Запись успешной B теряется.

Воспроизведение на отдельной PostgreSQL БД: создать A=3 → complete с UUID A → complete с UUID B, только на этом втором запросе подменить `inbound_marking_service.schedule_check` исключением `RuntimeError` → получить200/sorting и проверить отсутствие DocumentEvent с ключом `inbound:complete:B` → снять подмену → reopen → повтор A (остаётся receiving, контроль исправления проходит) → повтор B (получается sorting, сумма движений снова+3). Проба выполнена: **1 passed**, причём утверждения проверяют наличие остаточного дефекта. Без инъекции ошибки receipt B сохраняется — эта более узкая граница специально проверена и не выдаётся за общий отказ обычного пути.

Нужно закрепить результат каждого принятого UUID на собственной успешной границе `complete_receiving`, включая ответ «уже завершено», до best-effort стадии. Ошибка фоновой проверки не должна лишать успешную попытку защиты повтора. Повтор B после reopen не должен делать новый приход; новый осознанный UUID C должен завершать исправленный документ.

### F2-R2 — P1: исправление второй строки повторно добавляет уже сохранённую первую

R7/R3/R6, C6/C10/C11. Места: web `inboundDraftPersistence.ts:45–52,62–63`; `FfInboundRequestView.tsx:1477–1486`; `WbProductPickerDialog.tsx:318–328`.

Новая очистка pending после окончательного отказа устраняет исходную блокировку, но теряет связь между частично сохранённым набором и всё ещё открытым picker. Если A успешно добавлен, а B получает4xx, окно сохраняет выбранные A/B и количества. После исправления B `applyPicker` заново создаёт UUID для **всех** выбранных строк, включая уже добавленный A. Сервер правомерно считает A новым increment и увеличивает физический факт второй раз.

Точные шаги: новый ФФ-черновик → выбрать A=3 и B=1000000001 → «Добавить товар». API сохраняет A=3, отказывает B по границе количества; pending очищен, picker остаётся открытым. Исправить только B на2 → повторить «Добавить товар». Итог A=6/B=2 вместо A=3/B=2. Можно воспроизвести меньшими числами, подменив второй ответ на окончательный4xx после успешного первого. Независимая Vitest-проба фактического `sendIntakeMutations` и того же преобразования `applyPicker` подтвердила A=6/B=2: **1 passed**, проверяющий дефект, а не приёмку.

Нужно передать окну результат по уже применённой части: продолжать только исправленные/неотправленные строки, сохранив пользовательский ввод и защиту неизвестного ответа. Нельзя просто очистить весь pending и повторить исходный набор новым UUID. Проверить успешный A → окончательный отказ B → исправление B; успешный A → потеря ответа B → retry; отказ первого A без применённых строк.

### F6 — P2: неоднозначный внешний штрихкод молча выбирает один из товаров тары

R2/R9/R11, C2/C10/C13/C14; проверка неоднозначности уже была указана в F3 первого раунда. Места: backend `inbound_intake_box_service.py:323–328`, `inbound_cargo_place_service.py:175–180`; аналогичные новые присваивания в `_request_barcode_index` и `_seller_catalog_barcode_index` общего сервиса.

Дополнительные aliases записываются в словарь `barcode → product_id` с перезаписью прежнего значения. У двух реальных товарных карточек допустим одинаковый внешний штрихкод (поле не уникально); в выбранном документе могут присутствовать обе. Сервер молча берёт последний product_id из индекса и записывает единицу в его состав. Это выбор товара без достаточного идентификатора, а не допустимый выбор физической тары оператором.

Проба на той же отдельной БД: два товара A/B одного селлера имеют один `external_barcodes` код; оба добавлены в ФФ-draft по3; создать короб и грузоместо; отправить в каждый `/scan` только с общим barcode и отдельным mutation_id.
