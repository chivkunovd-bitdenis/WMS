# WMS-058: прямой скан товара при остатке в нескольких контейнерах

Исходная версия `ad116f0d`, изолированная ветка `codex/wms-pick-container-scan`.
Разбор и исправление выполнены без изменений backend, складских данных,
упаковки, внешнего WB/Ozon, дизайна или состава экранов.

## Воспроизведение и причина

Root вручную получил на staging отказ «Недостаточно товара в выбранном месте
подбора» при скане `2000000000015` без выбранного источника. Поставка
`4e38cabf-b129-4a28-85b0-3dd3631da6a4`, товар `EMU-CAN-PVZ-TRUE`.
В одной ячейке FBS-VIDEO-01 есть паллета с грузоместом и коробом.
Независимый read-only снимок другого агента после явного подбора/отмены:
physical 60, cargo 20 / available 19, box 40 / available 40, location available 59.
Этот агент экран staging сам не нажимал и SQL staging не выполнял.
Root отдельно подтвердил: явный скан короба, затем товара работает; отмена
восстанавливает факт подбора, физический остаток и движения не меняются.

Прочитанная цепочка: FfFbsSupplyWorkspace → FfUnloadPickPage.scan → POST
`/operations/fbs-supplies/{id}/pick/scan` → fbs_picking_service.pick_scan →
available_pick_source_quantity → physical_on_hand_in_container.

FfUnloadPickPage раньше считал candidates по ячейкам. Одну ячейку с двумя
контейнерами отправлял как storage_location_id с container_kind/id=null.
NULL в серверном контракте означает именно россыпь; такой остаток равен нулю.
Расчёт источника на сервере корректен — превращать его в сумму контейнеров
нельзя: тогда потеряется конкретное место будущего списания.

UnloadPickScreen сначала вызывает handleServerScan и возвращается из него
в том числе при ошибке. Ветка локального выбора с раскрытием нескольких
источников поэтому не выполнялась. Отсюда одновременно ложная для оператора
ошибка нехватки и отсутствие раскрытия при неоднозначном источнике.
Тело исходного browser-запроса не перехвачено; описанная ветка проверена по
коду для товара, распознанного по загруженному каталогу.

## Минимальное изменение

Для распознанного товара существующий адаптер скана выбирает физические
источники из pick-options, используя готовое server source.available, без
повторного вычитания резервов или собственной арифметики остатков.

* Единственный доступный источник передаётся с точными location/container.
* Несколько источников не вызывают POST: раскрывается существующая строка
  товара и показывается существующая просьба уточнить место/ввести число.
* Явно отсканированный контейнер передаётся неизменным. Его актуальность и
  доступность проверяет сервер; отсутствие в старом snapshot не запрещает скан.
* Россыпь остаётся NULL-container. Ручной ввод количества не менялся.
* Успешный результат отмечается у точного источника, а не у родительской ячейки.
  После ответа перечитывается существующий pick-options, включая случай,
  когда адреса выключены и сервер скрывает адрес в ответе.

Общий адаптер используется WB FBS, Ozon FBS и отгрузкой на маркетплейс.
Их URL/тела/серверные операции не менялись. Новый transient Error хранит
идентификатор товара только для раскрытия существующей строки, не создаёт
доменного статуса, журнала или разрешения на операцию.

## Проверки и границы

Шесть focused unit cases проверяют stage-форму (два контейнера в одной ячейке),
один реально доступный контейнер, явный контейнер вне snapshot, loose baseline,
отсутствие подмены исчерпанного контейнера россыпью и выбор между ячейками.
Существующий SSR-тест колонок подтверждает неизменность товарной разметки.
Итог: 7 tests passed; `tsc --noEmit -p tsconfig.app.json` и `npm run build`
прошли на существующих node_modules без установки зависимостей. Первый build
остановился из-за отсутствующего в sparse checkout seller/index.html; после
восстановления tracked frontend/seller и frontend/public сборка прошла. Полный pytest не запускается: backend не менялся.

Числовой штрихкод, отсутствующий в доступном каталоге, как и раньше попадает
на серверное распознавание. Исторический employee 403 linked-wb-catalog этим
исправлением не решается; права не расширяются. В текущей проверке root вошёл
как fulfillment_admin, ШК/фото/SKU отображались. Нужен повтор исходного скана
на staging после интеграции, затем явный источник и проверка сохранённого факта.

## Уточнение после независимого review

Автоматическое определение физического источника применяется только когда
источник не выбран вообще. Явная ячейка остаётся прежним location/NULL-container
(россыпью), даже если рядом есть контейнеры или россыпь исчерпана; актуальную
доступность проверяет сервер. Явный контейнер также сохраняется без подмены.
Два новых regression cases (loose 0 + box и loose 4 + box) сначала воспроизвели
замечание на 821e2f31, после раннего возврата любого selected-source прошли.
Все 8 целевых проверок helper и проверка TypeScript пройдены; полная сборка
для этой узкой корректировки не повторялась.
