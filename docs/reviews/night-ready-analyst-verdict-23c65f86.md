## Принятый безопасный WB-срез

Источник действий — опубликованный отчёт исполнителя
`night-ready-staging-acceptance-23c65f86.md` в коммите
`d764a920292327a5b49ca9a1a961748867663f2d` и его контрольное сообщение.
Аналитик сверил результат с R1–R3 WMS-660; сам браузером и БД не управлял.
Исполнитель подтвердил Railway SHA
`ac05c29bcdbdf0d542c45fe723869ea3de63c1e2`, SUCCESS backend deployment
`37211419-8747-4c89-b65c-cae5293830a4`, frontend deployment
`77e072f5-85a6-472f-a13b-a2546e2fe172`, exact commitHash и HTTP 200/200.

Администратор, селлер «Эмулятор WB», товар `EMU-NORMAL-B2C`
(`95aebe2c-5824-4ee7-aa61-8e5e0d609b91`): каталог ФФ показал основной
`2000000000011` и временный `WMS660STAGE1006` раздельно, поиск alias нашёл
ожидаемый товар; приёмка №000046 показала оба кода. В поставке
`WB-GI-6F54BE8C8AD9` alias выбрал WB-заказ №500008, затем выполнена штатная
отмена последнего скана. Контроль подтвердил: заказ `pending`, поставка
`assembling`, печатный ресурс `ready`, выбор=1, отмена=1, связанных последующих
событий=0, временный alias удалён (`alias_rows=0`). Принимается именно путь
«alias → ожидаемый заказ → отмена» и указанные экраны ФФ.

Этот срез не подтверждает seller-экраны, Ozon-only, коллизии разных товаров,
все физические коды ural toys, режимы и восстановление печати. Упаковка,
отгрузка, физическая бумага и внешнее действие маркетплейса не выполнялись и
для безопасного среза не требовались.

## Историческая блокировка стенда до финального восстановления

Самостоятельный `git diff 23c65f86 ac05c29 --
frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx` обнаружил 14 строк отличий.
В стендовом `productBarcodeOptionsForOrder` вместо нормализации
`marketplace_bindings` и фильтра Ozon возвращается единственный
`order.product.barcode` с меткой выбранной площадки. Это меняет варианты
баркода этикетки и способно предложить WB-код под меткой Ozon. Проверка WB
скана/отмены не доказывает сохранность этого маршрута R3 WMS-660.

Разница не меняет общий скан `scanFbsProductForAutoPrint`, alias-поиск на
сервере или группы ошибок WMS-653. Целевой diff генератора WMS-657, экрана
приёмки WMS-659, товарного окна WMS-670, сервиса скана и общего barcode
компонента пуст. Поэтому узкий WB-срез принят, но нельзя утверждать полное
равенство продукта стенда и кандидата.

По поручению ведущего исполнитель создал staging-коммит
`e271648f7a5542f57fc78c114506a50f3038172f` с точным деревом кандидата.
Аналитик самостоятельно сверил Git: оба SHA имеют tree
`2872fa22eec69439f113dc9bbe69910fd39c370c`, diff пуст.
Frontend этого SHA выложился успешно (Railway deployment
`f0a2bc15-8563-4078-a654-118bb1ab6a76`), но backend deployment
`51e21b75-f868-40e0-a362-61549d9b0561` не запустился, `/health` вернул 502.

Опубликованный отчёт исполнителя установил причину: entrypoint кандидата
требует `CELERY_BROKER_URL` общего Redis — сервиса очереди фоновых задач.
На данном Railway-стенде отсутствуют Redis, worker (исполнитель очереди) и
beat (планировщик). Прежний staging Dockerfile обходил этот entrypoint
прямым запуском миграций и API. Поэтому зелёный CI не доказывает возможность
старта кандидата в существующей конфигурации стенда. Замена общего брокера
памятью отдельного процесса не является проверенным или допустимым решением.
Причина и Railway-статусы приняты по опубликованному отчёту исполнителя;
аналитик сам настройки сервисов и секреты не читал и не менял.

Чтобы восстановить работу, исполнитель сохранил staging-историю и выложил
коммит `351e31cfbc9b8d1bb40518fbb7972e47a4657bd9` с прежним деревом
`ac05c29b`. Самостоятельная Git-сверка подтвердила общий tree
`897639d7eb8e013f76305f86131b0c990c3d5781` и пустой diff этих версий.
По отчёту Railway backend `32c7a7e9-71bc-4049-8ad9-660a55d3c0a8` и frontend
`30fe414a-2da6-4f6e-8605-5c11a23324e0` — SUCCESS, свежий smoke — HTTP
200/200. Это подтверждает восстановление стенда, но не выкладку точного
кандидата или успешный повтор его операторского сценария.

## Финальная дельта WMS-660: оставшееся условие закрыто

Эту ограниченную финальную дельту выполняет замещающий аналитик Sol 6.1.
Предыдущий временный аналитик `dc7112798` недоступен; замена прямо поручена
владельцем. Проверены AGENTS.md, существующее заключение, требования WMS-660
и только новое доказательство
[night-ready-wms660-cli-api-proof-727575a0.md](night-ready-wms660-cli-api-proof-727575a0.md)
из точного commit `62785150e56d111857a155838896a5f863b22828`.
Остальные четыре задачи повторно не принимались, их вердикты сохранены.
Навыки, браузер, агенты, Telegram, production и секреты не использовались;
тесты и полный CI повторно не запускались. Факты нового прогона приняты по
сохранённому отчёту исполнителя, а не выданы за собственные live-действия аналитика.

Новое доказательство достаточно для существующих R1–R3. Для R1 четыре
компонентные проверки точного кандидата подтверждают основной код первым,
отдельные строки без пустых значений и дублей, обычный вид одного кода и
Ozon fallback без смешения с WB. Для R2 изолированный прогон настоящего
ASGI-маршрута (API приложения без внешнего сервера) после выкладки включает
все десять основных проверок WMS-660: физические alias, основной код и код
заказа, границы поставки/seller/tenant, коллизии и явный order_id. Для R3
дополнительные проверки подтверждают отмену с безопасным повтором, повтор
скана без продвижения и выбор следующей единицы, подготовку восстановления
печати и запрет повторной печати при неизвестном внешнем результате.
Итого в отчёте `14 passed` API и `4 passed` frontend; ошибки и неоднозначность
не создают событие скана, повтор не создаёт вторую операцию.

Связь этого безопасного прогона с выложенным продуктом подтверждена SHA
`727575a0fd47dec56f34b38b987925686626c2b9`, совпадением хеша сервиса скана у
кандидата, staging-коммита и фактически запущенного API-контейнера, совпадением
компонента баркодов у кандидата и staging, а также наличием маршрута в OpenAPI
запущенного приложения. Внешний read-only запрос дал ожидаемый 401 без
авторизации. Это подтверждает маршрут и защиту доступа, а не успешное действие
живого оператора. Все операции функционального прогона выполнены в изолированной
тестовой БД; реальные остатки и поставки стенда не изменялись.

По уже принятой технической сверке staging имеет tree
`f87eb17954f1b5ea3f3ed2053618d4c3b916008d`; его отличие от кандидата ограничено
девятью историческими миграционными файлами. Migration-compatible версия
