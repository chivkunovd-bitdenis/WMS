**Почему предложенная защита недостаточна.**

- Два локальных продавца одного кабинета имеют разные `seller_id`. И индекс, и текущие блокировки разрешают им независимо создать строки с одним номером WB.
- При смене кабинета у существующего продавца старые поставки сохраняют тот же `seller_id`. Даже будущее заполнение `MarketplaceAccount.external_account_id` будет описывать текущее подключение, а не доказанную принадлежность каждой старой поставки.
- Несколько локальных аккаунтов одного кабинета не становятся одной внешней идентичностью от добавления ссылки на локальный аккаунт: их локальные ID различаются.
- Обычный `UNIQUE` и частичный уникальный индекс с `WHERE external_supply_id IS NOT NULL` оба пропускают строки с пустым внешним ID. Усиление в `f5b42158` происходит за счёт заполнения значения, а не смены разновидности индекса. [Правила PostgreSQL](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE-CONSTRAINTS).

Не получится и просто вернуть поставку другого продавца при конфликте: существующая проверка состава явно отклоняет связь заказа с поставкой другого продавца или арендатора. Здесь требуется решение о принадлежности документа, а не `ON CONFLICT` с произвольным выбором строки. [Проверка принадлежности](/Users/deniscivkunov/Projects/WMS/.worktrees/wms121-supply-identity/backend/app/services/fbs_supply_composition_service.py:105).

**Миграцию `0258` выпускать в представленном виде нельзя.** Она выбирает старшую строку по `created_at, id`, меняет имя остальных, при необходимости обрезает его до 255 символов и пропускает эти строки при заполнении внешнего ID. Принадлежность кабинету и содержимое связанных документов не проверяются. При этом последующий импорт ищет по прежнему `wb_supply_id` через `LIMIT 1` и не исключает переименованные строки. Значит, префикс в имени даже не обеспечивает заявленного исключения дубля из работы. Обратная миграция восстанавливает индекс, но не первоначальные имена. **Минимальная безопасная последовательность для координатора такая:**

1. **Исключить автоматический разбор дублей из выпуска.** Не удалять, не переименовывать и не обнулять идентичность клиентских строк. Применялась ли `0258` где-либо, в этой проверке не устанавливалось; переписывать историю уже применённой миграции без этого знания нельзя.
2. **Сначала установить источник кабинета.** Существующее `MarketplaceAccount.external_account_id` подходит для хранения полученного от WB ID профиля текущего подключения. Это не новая сущность, но и не готовое решение WMS-122. Нужна отдельно разрешённая интеграция с `seller-info`, проверка фактического FBS-подключения и согласованное правило смены кабинета. Одинаковый подтверждённый `sid` при ротации доступа должен сохранять идентичность; другой или неизвестный `sid` не должен автоматически переписывать принадлежность истории.
3. **До миграции определить принадлежность исторических строк.** Текущий `sid` продавца нельзя массово приписать всем его старым поставкам. Заполнять можно только доказанные соответствия. Неизвестные строки сохраняются; это незавершённая миграция, а не полная защита.
4. **После этого решить судьбу подтверждённых совпадений.** Две сохранённые строки с одной доказанной идентичностью невозможно одновременно включить в строгий уникальный индекс. При запрете удаления, слияния, изменения принадлежности и исключения строк из ограничения миграция должна остановиться до изменения данных. Выбор «старшая главная» не является допустимым решением.
5. **Только затем вводить ограничение и обработку гонок во всех трёх путях.** Конфликт должен обрабатываться после отката неуспешной вставки и повторного чтения подтверждённой идентичности. Повторять создание в WB после локального конфликта нельзя: внешний вызов уже мог успешно завершиться.

Ozon нужно сохранить отдельно: там `external_supply_id` заполняется `carriage_id` после передачи, а черновики допускают пустое значение. Нельзя вводить общий `NOT NULL` или кодировать кабинет внутри номера, который используется в обращении к провайдеру. [Запись результата Ozon](/Users/deniscivkunov/Projects/WMS/.worktrees/wms121-supply-identity/backend/app/services/fbs_shipment_service.py:2129).

**Точный блокер полного исправления:** существующие поля не сохраняют неизменную связь «эта поставка — этот внешний профиль на момент операции». Требуется решение владельца о способе сохранения этой связи, о принадлежности поставок при нескольких локальных продавцах и о границе уникальности между арендаторами. Дополнительно нужны доказательства принадлежности старых строк. Без них можно подготовить получение идентичности текущего подключения и проверки перед миграцией, но нельзя честно выпустить защиту WMS-122. Спекулятивную схему для обхода этого ограничения не предлагаю.
