**P2 — удаление пустой тары из другого документа ломает сохранение и проведение первого пересчёта.**

Срез `b41fe008`, файл [inventory_count_service.py:641](https://github.com/chivkunovd-bitdenis/WMS/blob/abb2beba/backend/app/services/inventory_count_service.py#L641).

Воспроизведение по разрешённым операциям сервиса:

1. В черновике пересчёта A оператор подтверждает пустой складской короб X. Его ID сохраняется в `A.empty_places`.
2. В черновике B того же склада оператор удаляет действительно пустой X. `delete_document_container` допускает это; удаления только собственной созданной тары здесь не требуется.
3. Оператор сохраняет A — даже только комментарий. `save_actuals` безусловно вызывает `_clear_empty_confirmation` на строке 539.
4. Для сохранённого X выполняется `_container_scope`, который после удаления короба возвращает `object_not_found` на строках 216–217. Сохранение A прерывается.

Причина сохраняется и при попытке провести A: [строки 1641–1646](https://github.com/chivkunovd-bitdenis/WMS/blob/abb2beba/backend/app/services/inventory_count_service.py#L1641) повторно вызывают удаление X, а отсутствующая тара даёт `container_not_found`. Удаление из B очищает `empty_places` только у B — [строки 993–995](https://github.com/chivkunovd-bitdenis/WMS/blob/abb2beba/backend/app/services/inventory_count_service.py#L993).

Это не предположение о потере остатков: **подтверждённая проблема — отказ работы с A из-за устаревшей ссылки на уже законно удалённую тару**. Сценарий установлен чтением последовательности операций; на БД я его не запускал.

**Merge `aa8fc1b7` / source `40fcf693`.** Прежнюю инверсию Product/Order считаю исправленной в рассмотренном сценарии. **Претензию Opus №4 о незаблокированной вставке нового FK-резерва отклоняю.** Реальный FK `inventory_reservations.product_id → products.id` есть и в модели, и в [миграции:37](https://github.com/chivkunovd-bitdenis/WMS/blob/abb2beba/backend/alembic/versions/20260411_0016_inventory_reservations.py#L37). PostgreSQL при проверке вставки берёт `FOR KEY SHARE` на родительской строке; он конфликтует с используемым merge `FOR UPDATE`. Если вставка первой получила эту блокировку, merge ждёт её завершения и затем видит ссылку. Если Product первым заблокировал merge, вставка ждёт; после удаления source она не может успешно зафиксировать ссылку на него. Это подтверждается [реализацией FK-проверки PostgreSQL](https://github.com/postgres/postgres/blob/REL_17_STABLE/src/backend/utils/adt/ri_triggers.c) и [матрицей блокировок](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS). Дополнительный слепой SELECT эту претензию не обосновывает.

**Warehouse `b41fe008/e45fd897`.** Помимо описанного P2, старые претензии о двойном approve и удалении тары одновременно с приходом подтверждения не получили. Approve блокирует и перечитывает акт, затем блокирует Products в стабильном порядке и обновляет загруженные балансы. Writer остатка берёт `FOR SHARE` на складскую тару; удаление берёт `FOR UPDATE` и после ожидания проверяет живой ненулевой остаток.

Whole-empty намеренно обнуляет все строки выбранного места внутри документа. При ограничении пересчёта селлером/категорией непоказанный живой товар не становится разрешением удалить тару: проверка полного остатка отклоняет удаление. Это граница операции, а не основание списывать скрытый товар. `e45fd897` меняет только отчёт.
