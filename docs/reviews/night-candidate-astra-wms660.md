## Что проверено в коде

Прочитан полный продуктовый diff merge WMS-660 относительно первого родителя. Между merge и кандидатом побитово сохранены `fbs_scan_auto_print_service.py`, `ProductBarcodeCell.tsx`, `productBarcodes.ts`, три экрана каталогов/приёмки селлера и оба целевых тестовых файла WMS-660. Из семи продуктовых файлов WMS-660 дальнейшее изменение есть только в `FfInboundRequestView.tsx`.

В `select_order_for_product_scan` дополнительный поиск `ProductBarcode` ограничен `tenant_id`, `supply.seller_id` и product_id заказов текущей поставки. Сама поставка и заказы ограничены WB. Основной код товара и код заказа остаются допустимыми; совпадения alias/primary разных товаров объединяются до проверки неоднозначности, поэтому произвольный товар не выбирается. Явный `order_id` обходит alias-поиск и остаётся ограничен заказами той же поставки. Новое условие не меняет блокировку строки поставки, журнал повторов, выбор следующей единицы, печать, КИЗ, резерв или списание.

В актуальном `FfFbsSupplyWorkspace.tsx` общий скан отправляет исходный `raw` в `scanFbsProductForAutoPrint`, без отсечения по единственному основному коду на клиенте. Последующий diff WMS-653 в workspace и его API добавляет представление ошибки передачи; не заменяет маршрут распознавания WMS-660. При выключенной печати сохраняется прежний отдельный сценарий; WMS-660 не вводит новое поведение этого режима.

`normalizeProductBarcodes` сохраняет основной код первым, удаляет пустые значения и повторы, сохраняет ведущие нули. Каталог селлера берёт `wb_barcodes` у товарной строки либо `barcodes` именно у соответствующей карточки площадки. Каталог фулфилмента передаёт `displayMeta.wb_barcodes`, приёмка селлера — коды соответствующего `cat` с прежним запасным кодом строки. Общий компонент не подтягивает коды чужой карточки.

В приёмке фулфилмента обе формы строки — товар и содержимое короба — сохраняют нормализацию WB-списка и прежний Ozon-only fallback только при отсутствии WB-кодов. Последующие изменения WMS-659 касаются создания коробов, состояния окна и временного отключения перехвата сканера внутри окна количества; рендер всех баркодов и данные товара ими не заменены. Печать по-прежнему использует свой прежний выбор кода, а не новый массив отображения. Изменений импорта, схемы БД или маркетплейс-связей WMS-660 не вносит.

## Точные оставшиеся проверки для release-агента

Все пункты ниже **НЕ ПРОВЕРЕНЫ этим ревью**. Выполнять на разрешённом тестовом/операторском контуре с фиксацией URL, фактически обслуживаемого SHA, роли, tenant/seller и ID документа. Нельзя подменять их скриншотом синтетического компонента.

1. Открыть каталог селлера, каталог фулфилмента, приёмку селлера и приёмку фулфилмента. Для UT0123/0 увидеть отдельными строками `04640556102658`, `2055629421109`, `4610264735875`; для UT0127/0 — `04640556141886`, `2055629422335`, `4610264735912`. Основной сохранённый код первый, без дублей и пустых строк. В приёмке ФФ проверить также содержимое короба. Проверить длинное название и отсутствие перекрытия действий; обновление страницы сохраняет вывод.
2. В тех же экранах проверить отдельную Ozon-карточку, WB-карточку и Ozon-only товар без WB-кодов. Чужие коды между отдельными строками площадок не появляются, Ozon-only сохраняет прежний отображаемый код. Проверка не должна создавать отсутствующую ProductMarketplaceLink либо менять SKU/остатки ради заполнения колонок.
3. В тестовой WB FBS-поставке с несколькими доступными заказами этих товаров сканировать каждый сохранённый код, включая оба физических дополнительных кода. В действующем режиме печати каждый код выбирает заказ соответствующего товара этой поставки. Основной код и стикер заказа продолжают работать. Зафиксировать сетевой запрос, возвращённый order_id и состояние после обновления; новая сознательная попытка берёт следующую допустимую единицу, повтор того же запроса — прежнюю.
4. На тестовых данных проверить код только чужого seller/tenant/поставки и коллизию alias одного товара с primary другого: нет выбора чужого/произвольного товара и нет нового scan-события. После отказа явно выбрать строку второго заказа и продолжить; адресат — её order_id, первый заказ не изменён. Проверить выход из ошибочного скана и возврат обычного ввода.
5. Проверить пересечение с WMS-659: открыть окно создания коробов приёмки, отменить либо завершить разрешённое тестовое создание, вернуться к товару/содержимому короба. Все коды остаются на месте, скан после закрытия окна снова работает, количество созданных коробов не зависит от скана товара.

Проверить сохранение режима печати и восстановления на тестовой рабочей станции: дополнительный баркод использует прежний выбранный код этикетки и тот же QR/КИЗ-маршрут; при отказе печати повтор не создаёт вторую копию, снятие галки следует существующему сценарию.
