# WMS-396: контракт приёмки ЧЗ и совместимость FBS

Проверено чтением кода 08.09.2026 в исходном checkout `63dd7245`.
Этот документ фиксирует исследование контракта, а не реализацию или приёмку UI.

## Существующая модель

`marking_codes.status` управляет складским жизненным циклом, а не только ответом
ЧЗ. WB (`fbs_kiz_service._ensure_kiz_not_occupied_in_pool`,
`fbs_marking_service._claim_pool_code_if_present`) и Ozon
(`ozon_kiz_service._claim_or_create_code`) отклоняют найденный код со статусом,
отличным от `available`. При этом выдача кодов для печати и замены в
`marking_code_service` выбирает `available` без ограничения `source='pool'`.
Поэтому ни прямая запись внешнего `INTRODUCED` в `status`, ни присвоение
`available` всем полученным кодам не совместимы с существующим поведением.

Минимальное предложенное решение без новых таблиц или полей:

- Новый физически отсканированный внешний код: существующие значения
  `source='external_fbs'`, `status='applied'`, без строки упаковки и пула.
- Существующий код сохраняет источник, статус и привязки. Проверка ЧЗ не
  переписывает складской жизненный цикл или время ввода в оборот.
- Одна существующая запись `MarkingCodeEvent` хранит привязку к приёмке:
  `event_type='imported'`, номер документа, `meta_json.source_process='reception'`,
  идентификаторы заявки/строки и снимок проверки. Повторная проверка обновляет
  снимок на этой записи, а не создаёт новый журнал проверок.
- На трёх входах FBS нужно разрешить конкретный случай свободного внешнего
  кода: `external_fbs + applied + packaging_task_line_id is None`. Проверки
  принадлежности продавцу/товару и занятости другим заказом сохраняются.
- Повторное использование такого кода идёт с `from_pool=False`. Иначе
  существующий код увеличивает `qty_marking_printed` вместо внешней маркировки.
  Источник `external_fbs` уже поддержан существующей отменой WB.

Предложение передано исполнителю backend и ведущему агенту. Сохранение этого
документа не подтверждает, что перечисленные изменения уже сделаны.

## Проверка внешнего endpoint

08.09.2026 выполнен один POST без авторизации в
`https://mobile.api.crpt.ru/mobile/check`, тело
`{"code":"WMS396_SYNTHETIC_INVALID_CODE"}`. Коды клиентов не отправлялись.
Получен HTTP 200 и JSON со следующими полями:

```json
{
  "codeFounded": false,
  "checkResult": false,
  "status": "not_found_dm",
  "warning": "not_found",
  "codeResolveData": {
    "verified": false,
    "valid": true,
    "found": false,
    "known": false,
    "isBlocked": false
  }
}
```

`outerStatus` отсутствовал. Следовательно, HTTP 200 и `valid=true` не являются
подтверждением правильности кода. Этот ответ означает «Код не найден», а не
успешную проверку или сетевой сбой.

Положительный ответ с реальным кодом в данном исследовании не получен. В
канонической постановке есть описание прежней живой проверки
`APPLIED/checkResult=false` и `INTRODUCED/checkResult=true`, но сырого JSON в
просмотренных файлах проекта не найдено. Нельзя выдавать это описание за
повторно проверенный текущий положительный контракт.

[Официальная документация True API ЦРПТ](https://docs.crpt.ru/gismt/True_API/)
подтверждает значения `APPLIED` («Нанесён») и `INTRODUCED` («В обороте»).
Она не документирует контракт мобильного endpoint. Публичной официальной
спецификации его ответа в этом исследовании не найдено.

Правило разбора: зелёный требует явно распознанного положительного ответа;
неизвестная форма, отсутствующие обязательные поля, отрицательная
криптопроверка, блокировка, HTTP-ошибка, таймаут или не-JSON не допускают
зелёного. В строках и Excel нужно различать установленный плохой результат
и невозможность подтвердить статус. Ни один результат проверки приёмки не
должен добавлять навигационные блокировки FBS.
