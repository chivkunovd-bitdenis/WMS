## Изменённое поведение

1. `fbs_stock_rule_service.py`: прежние и уменьшенные потолки сохраняются при
   падении свободного остатка. Новое/увеличенное число проверяется по общей
   сумме и каждому физическому складу под существующей блокировкой Product;
   проверка выполняется отдельно для каждого товара массовой операции.
   Выключенная публикация не позволяет ввести новый потолок сверх остатка.
   Старые значения пула перечитываются из БД после блокировки, даже если
   текущая сессия уже держала устаревший ORM-объект. Скрытые неактивные потолки
   больше не вычитаются как физический резерв.
2. `fbs_stock_availability_service.py`: совместимая функция бывшего выделения
   возвращает пустое распределение физических резервов. Это устраняет вычитание
   потолков также у её потребителя `stock_direction_service.distributions_by_product`,
   которым исполнитель не владеет. Действующие резервы заказов считаются отдельно.
3. `marketplace_unload_service.py`: потолок исключён из проверки количества
   отгрузки и списка доступных товаров; резервы FBS, исходящих документов,
   коробов отгрузки и направлений сохранены.
4. `inventory_service.py`: сообщение инвентаризации описывает физическую
   недостачу без вымышленной отдельной FBS-части на основании потолка. Операция
   по-прежнему списывает физический баланс движением; потолки и резервы не меняет.
5. `fbs_warehouse_binding_service.py`: ручная настройка передаёт однозначный
   ключ площадка:склад, в том числе когда числовые номера WB/Ozon совпадают.
6. `FbsStockDialog.tsx`: прежний/уменьшенный потолок не блокирует кнопку после
   падения свободного. Массовую проверку каждого исходного числа выполняет
   сервер; у модалки нет индивидуальных старых правил всех выбранных товаров.
   Подпись поля и подсказка обозначают именно потолок публикации.
   Сохранение units из `FfProductsFbsPage.tsx` сохранено из исходного HEAD.

Формула публикации и общий порядок распределения между WB/Ozon не менялись:
свободный остаток раздаётся последовательно с ограничением потолком каждого
направления. Упаковка, навигация FBS, TSD API, чат, App.tsx, Ozon sync,
корневой checkout и frozen worktree не редактировались. Новых таблиц,
счётчиков, журналов, миграций и клиентских операций с данными нет.

## Содержательные проверки

- Изолированная недостача при on_hand=5, cap=5, shortage=3: старый код реально
  уменьшил бы cap. Теперь cap=5, движение −3, on_hand/free/published=2.

  недостача 150, FBO доступно 250, потолки всё ещё 300; повтор не проводит снова.
- Резерв/отмена проверяют строки резервов, свободный и физический остаток.
- WB/Ozon, с резервом и без него: передача, удаление резерва, физическое списание,
  публикация, повторная передача/отмена, неизменность потолка.
- Ozon: нехватка второй позиции не оставляет ни одной товарной строки резерва.
- Прежний потолок 5 при free=4 сохраняется, включая ручной endpoint привязки;
  уменьшение выше текущего free допустимо, повторное увеличение отклоняется.
- FBO разрешает свободные четыре при cap=5 и реальном резерве 1; пятую
  запрещает. Список доступного и распределение каталога возвращают те же четыре.
- Массовый ввод проверяет товар без свободного остатка отдельно; выключенная
  публикация не обходит проверку нового числа; одинаковые номера WB/Ozon
  не смешиваются; устаревшая сессия не освобождает увеличение от проверки.
- PostgreSQL 17.10, отдельная локальная БД `wms338_astra_test_20260910`:
  конкуренция двух заказов за последнюю штуку. Тест удерживает Product lock
  первой транзакции и проверяет `pg_blocking_pids` второй до освобождения.
  Итог: одна строка резерва на одну штуку, reserved/no_stock у двух заказов,
  физический остаток 1, free/published=0, cap=5.
