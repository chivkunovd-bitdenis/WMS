Проверены текущие пути: public `/api/health` доступен; production `/api/openapi.json` не предоставляет схему. В коде нет предоставленного чистого posting-reader. Обход шлюза, JWT, роли, credentials и кабинеты не использованы.

Сборщик использует внутренний `MarketplaceAccountService.stored_credentials` и штатный Ozon provider/HTTP transport. Проверяет exact tenant/seller/draft/WMS-origin/31 postings/склад, включает PostgreSQL transaction READ ONLY, завершает её до HTTP. Читает только `/v3/posting/fbs/get` (физически POST, семантически чтение), все возвращённые связанные номера тем же seller, с ограничением124 карточки, без retry. Каждая карточка и manifest сохраняются отдельно, только по списку разрешённых полей; нет клиентских адресов, марок, credentials или raw error payload. Это подготовка, **live запуск не выполнен**.

**Требуемая операция ведущего:** после независимого ревью точной дельты запустить сборщик в уже настроенной штатной среде production backend (его обычные права и подключение Bambook), передав только новый каталог для очищенных proofs. Не запускать через SQL gateway, sync, кнопку передачи или административный обход. Точный порядок и команда в [инструкции](wms675-evidence-20261006/RUN_BOUND_READER.md). Мне в текущем сеансе такой execution transport не предоставлен. Нужен либо один такой запуск, либо существующий seller-bound reader с несекретной точкой вызова.
