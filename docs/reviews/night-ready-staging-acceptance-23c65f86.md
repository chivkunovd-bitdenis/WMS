## Границы проверки

Этой браузерной проверкой подтверждены каталог фулфилмента, приёмка фулфилмента и безопасный WB FBS-сценарий «скан → выбор заказа → отмена». Она не подтверждает физический принтер, фактическую отгрузку, seller-роль, Ozon-сценарии, конфликт одинаковых штрихкодов у разных товаров или полный набор ручных проверок из требования WMS-660. Эти пункты нельзя считать пройденными по данному документу.

Дополнительно обнаружено важное расхождение первоначального стенда с кандидатом: в `frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx` staging `ac05c29b` строит `productBarcodeOptionsForOrder` только из `order.product.barcode`, тогда как кандидат `23c65f86` использует marketplace-aware `resolveProductBarcodeOptions` и отдельно фильтрует Ozon. Это не мешает уже подтверждённому WB-сканированию дополнительного штрихкода, но не позволяет переносить результат проверки на печать товарного штрихкода, сохранение marketplace-привязки или Ozon.

Для устранения этой неоднозначности был подготовлен exact-tree staging commit `e271648f7a5542f57fc78c114506a50f3038172f`, дерево которого побайтно совпадает с деревом кандидата `23c65f86`. Frontend этого SHA успешно выложился Railway deployment `f0a2bc15-8563-4078-a654-118bb1ab6a76`. Backend deployment `51e21b75-f868-40e0-a362-61549d9b0561` не прошёл запуск: entrypoint потребовал общий `CELERY_BROKER_URL`, которого нет в конфигурации стенда, после чего `/health` вернул HTTP 502.

Обязательная проверка брокера появилась в commit `82889771c2813f0d8e8161190537e45d332e472f` (`WMS-517: harden True API withdrawal readiness`). Первоначальный staging работал только потому, что merge `63bc002c812b95ed6c0bd0addfa5280465fbf044` (`WMS-612 preserve staging...`) заменил entrypoint в `backend/Dockerfile.railway` на прямой `alembic upgrade head && uvicorn` и прямо зафиксировал отсутствие Redis/worker/beat topology. Текущий Railway status показывает WMS, web, wb-emulator и Postgres, но не Redis, worker или beat. Репозиторный production-контур, напротив, поднимает Redis и передаёт один брокер API, worker и beat через `docker-compose.prod.yml` и `scripts/deploy/prod-update.sh`.

Значения секретов не открывались и конфигурация Railway не менялась. Минимальное действие для снятия инфраструктурной блокировки требует отдельного разрешения владельца: добавить или привязать Redis-сервис к этому Railway-стенду и передать API ссылку на общий брокер через `CELERY_BROKER_URL`. Для полного контура WMS-517/WMS-624 также нужны worker и beat из уже существующих `backend/railway.worker.toml` и `backend/railway.beat.toml`, подключённые к той же БД и тому же брокеру. Возврат к брокеру в памяти процесса не является допустимым обходом.

Чтобы не оставить стенд с 502, опубликован fast-forward rollback commit `351e31cfbc9b8d1bb40518fbb7972e47a4657bd9` с рабочим деревом `ac05c29b`. Его Railway deployments `32c7a7e9-71bc-4049-8ad9-660a55d3c0a8` (backend) и `30fe414a-2da6-4f6e-8605-5c11a23324e0` (frontend) завершились `SUCCESS`; свежий smoke снова дал backend `/health` HTTP 200 с `{"status":"ok"}` и frontend `/` HTTP 200. Поэтому exact-tree стенд нельзя считать выложенным целиком, а повторная сквозная проверка exact-tree не выполнена.
