# WMS-396: проверка серверной части, 08.09.2026

Реализация сохранена в ветке `codex/wms396-backend`: основной код —
`2f82a8d0bf66edc8bda385e92e51853007f8b4c6`, ограничение для уже существующих
кодов и дополнительные проверки — `0a6bbeefd2c1aa1c4cfb54462438c570c278e2ab`.
Этот отчёт и проверки одновременной привязки WB/Ozon сохранены следующим
коммитом этой же ветки. Push и включение в общую ветку выполняет ведущая задача.

## Реализованное поведение

Скан КИЗ прикрепляет полный код, включая GS-разделители и криптохвост, к строке
приёмки. Количество товара и движения остатков от этого не меняются. Повтор
того же кода в той же строке возвращает существующую запись. Число разных кодов
ограничено фактически принятым количеством, включая короба и грузоместа.

Новый физически нанесённый код получает существующее состояние `applied` и
источник `external_fbs`. В пул печати он не попадает. Результат проверки ЧЗ
хранится отдельно от складского жизненного цикла, в `meta_json` существующего
события импорта; там же лежит связь с приёмкой и строкой. Новых таблиц и полей нет.
Повторная проверка обновляет этот снимок, не создавая журнал проверок.

После независимого ревью это ограничение уточнено в `676d6a29` (в общей ветке
`a808eae3`): существующий код пула в состоянии `printed`, подходящий товару и
селлеру и свободный от упаковки, резерва и FBS, допускается к проверке приёмки.
Его исходное состояние, товар, пул и история не меняются. Код `available`
по-прежнему отклоняется, чтобы приёмка не возвращала физическую маркировку в печать.
Исключение FBS для внешнего приёмочного кода на печатный пул не распространяется.

Во время приёмки можно убрать ошибочную привязку. У нового внешнего неиспользованного
кода удаляется собственное событие и сам ошибочный ввод; у прежнего печатного кода
только событие приёмки. FBS, перепечатка, замена и другие прежние связи защищены.
Складские движения и количество приёмки при этом не изменяются.

Завершение приёмки и совместимые старые маршруты запускают существующий механизм
фоновых заданий после фиксации складской операции. HTTP к ЧЗ выполняется без
открытой сессии и блокировок БД, по одному коду, с таймаутом 10 секунд и паузой
250 мс. Сбой запуска проверки не отменяет приход. Неизвестный ответ и недоступность
не считаются успешным введением в оборот. Excel содержит проблемные и непроверенные
из-за ошибки коды с причиной; успешные и ещё ожидающие проверки коды исключаются.
Формулы отключены типом текстовой ячейки. GS записан обратимым текстом `\u001d`,
поскольку управляющий символ недопустим внутри XML-файла Excel.

Для WB и Ozon разрешена ровно одна новая ситуация: физически нанесённый внешний
код с подтверждённым событием приёмки, без строки упаковки, пула и прежней связи
с FBS-заказом. Он привязывается как внешний, без увеличения количества напечатанных
кодов. Остальные проверки занятости сохранены.

## Выполненные проверки

- `ruff check .` — успешно.
- `mypy .` — успешно, 432 исходных файла.
- Целевые тесты приёмки, весь `test_fbs_kiz.py`, применение КИЗ и привязка кодов к
  печати: **149 passed, 1 xfailed**, 50,39 секунды. `xfail` существовал ранее.
- Финальный файл приёмки на SQLite до добавления двух межпроцессных гонок:
  **21 passed, 2 skipped**, 8,04 секунды. Пропущены проверки блокировок PostgreSQL.
- На отдельной созданной для этой задачи базе PostgreSQL 17.10 две гонки приёмки:
  **2 passed**, 3,53 секунды. Проверяется реальное ожидание `Lock` через
  `pg_stat_activity`, затем ровно одна запись для повторного скана либо отказ
  второго разного кода при исчерпанном фактическом количестве. Движений товара нет.
- На той же отдельной базе гонки **WB → Ozon** и **Ozon → WB**:
  **2 passed**, 4,45 секунды. Второй участник заранее загружает устаревший объект,
  затем действительно ждёт блокировку строки кода. После фиксации первой привязки
  получает `duplicate_kiz`. Повторно код не привязывается.

База проверки: `wms396_backend_races_20260908_01`, локальный PostgreSQL,
`127.0.0.1:5432`. Проверки использовали только синтетические товары и коды.
После проверки эта отдельная база удалена. Остальные базы не изменялись.

## Границы доказательства

После ревью изменённый файл приёмки проверен отдельно на PostgreSQL: 39 случаев
прошли вместе, затем исправлена неполная синтетическая фикстура FBS-заказа и
оставшийся случай прошёл отдельно. Всего есть положительное свидетельство для
40 случаев, включая четыре реальные гонки PostgreSQL. Ruff изменённых файлов
и mypy двух модулей прошли. Полный прежний набор повторно локально не запускался.
Автоматический вызов теперь сохраняет готовые ответы, ручной повторяет проверку;
работник подбирает новые коды перед завершением и пропускает удалённые события.
Зелёный требует явных INTRODUCED, checkResult=true и verified=true.

Серверные тесты подменяют ответ публичного ЧЗ. Успешная проверка реального КИЗ
этой задачей не выполнялась. Проверку интерфейса, общий CI, push и соответствие
стенда итоговому SHA выполняет ведущая задача; этот отчёт их не подтверждает.
