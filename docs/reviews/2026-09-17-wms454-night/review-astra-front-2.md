## F2 — дефект (подтверждён кодом/тестом), средний приоритет: обрыв тела ответа справочника по-прежнему отменяет открытие окна

**Код:** `frontend/src/screens/ff/products-fbs/fbsStockDialogLoader.ts:44–49,83–110,119–138`; место вызова — `frontend/src/screens/v2/FfProductsCatalogScreen.tsx:632–649`. Непокрытая граница тестов — `fbsStockDialogLoader.test.ts:37–50,81–107`.

`settle` защищает только ожидание `fetch`. После получения `Response` с успешным HTTP-статусом тело читается через `await wb.response.json()` или `await ozon.response.json()` уже вне этой защиты. В воспроизведении `fetch` успешно возвращает `Response` со статусом 200, но поток тела заканчивается ошибкой. Загрузчик отклоняется на чтении JSON, не собирает сохранённые строки и не возвращает данные окна. В каталоге `setFbsDialog(await loadFbsStockDialog(...))` не выполняется, управление переходит в общий `catch`.

**Последствие:** даже при успешно полученных правилах и сохранённых активных привязках окно не открывается. Оператор не видит предусмотренные строки «№ …», чипы «название недоступно» и причину в нужной площадке. Отказ справочника Ozon таким способом мешает открыть даже WB-товар: все четыре запроса загружаются до фильтрации видимых площадок (`fbsStockDialogLoader.ts:83–92`; `FbsStockDialog.tsx:140–141`).

**Нарушение:** WMS-457 R3 прямо требует показать активные привязки, если список не получен из-за сети (`docs/requirements/WMS-457.md:114–120`); R4 включает обрыв/тайм-аут (`:122–136`). Это оставшаяся ветка уже поставленного требования, а не новое требование принимать повреждённые данные за корректный список. Нужен тот же результат `received:false`, который уже используется при отказе до получения ответа.

**Воспроизведение без браузера и БД:** вызвать настоящий `loadFbsStockDialog` с одним товаром и успешными ответами правил/привязок; для одного справочника вернуть следующий настоящий `Response`, для второго — обычный полный JSON:

```ts
function interruptedDirectoryResponse() {
  return new Response(new ReadableStream({
    start(controller) {
      controller.enqueue(new TextEncoder().encode('[{"name":'));
      controller.error(new TypeError('terminated while reading response body'));
    },
  }), {
    status: 200,
    headers: { 'Content-Type': 'application/json' },
  });
}
```

Локально в Node выполнены исходники загрузчика, сборщика строк, ключей и правила после компиляции `typescript.transpileModule`. Функции `toProduct`, `toRule`, `fbsRuleBody` извлечены из текущего файла через TypeScript AST; формулы не переписаны в проверочном коде. Подменены `fetch` и построение базового URL. Правила: WB 60 / Ozon 40, активные привязки WB 501001 и Ozon 1020005029603630, склад WMS `w`. Ошибка вводилась отдельно для каждой площадки. Зафиксирован вывод:

```text
{"scenario":"wb-body","opened":false,"error":"terminated while reading response body"}
{"scenario":"ozon-body","opened":false,"error":"terminated while reading response body"}
```

Здесь `opened` означает, что загрузчик вернул данные для установки окна; это не заявление о клике в браузере. Оба вызова вместо возврата данных выбросили исключение. Контрольные прогоны с `fetch`, отклоняющимся сразу с `TypeError('Failed to fetch')`, вернули данные окна для обеих площадок, верные причины отказа и WB-количество 72. Значит первоначальное воспроизведение F2 действительно исправлено, но вся требуемая ветка сетевого отказа ещё не закрыта.

**Что исправить и проверить:** обработкой необязательного справочника охватить и получение ответа, и чтение его тела; после обрыва оставить список неполученным, сохранить причину и собрать активные привязки. Ошибка обязательного запроса правил должна по-прежнему останавливать открытие. Добавить в тест загрузчика оба варианта с успешным `Response`, у которого чтение тела отклоняется. Сейчас тесты моделируют либо полностью готовый JSON, либо отклонение `fetch` до `Response` (`fbsStockDialogLoader.test.ts:37–50`), поэтому этот дефект они не ловят. Новые окна, запросы, сущности или пользовательские блокировки для исправления не нужны.
