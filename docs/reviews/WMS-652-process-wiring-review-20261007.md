# WMS-652: независимое ревью подключения отчётов WMS-686

**Вердикт: PASS в заявленном процессном scope для `14c340a76db5f77c248794183b44d8b13880ef81`. Финальный выпуск не одобрен.** Подтверждённых дефектов в этой дельте не обнаружено: настоящие результаты 11 замороженных тестов WMS-686 стали обязательным входом общего process-proof, а прежняя защита сохранена. Это заключение отдельного ревьюера, который не разрабатывал продукт, CI, политику или тестовый контракт.

Ревью выполнено 07.10.2026 в постоянном integration worktree, ветка `codex/night1007-integration`. Исходный HEAD проверен до запуска; рабочее дерево было чистым. Прочитаны AGENTS.md, полные owner-cases.md и failure-cases.md, CI-DELTA.md, process-wiring-20261007/result.json, README и исходные отчёты, сравнение базы в PLAN.md/base-preservation.json, а также контракты `1ab749c2bb9eb68272eaaff8eb5840f3d79e1a7a` и `5ca749eaa048465fbc9d717c4b3a52e34b524b35`. После fetch origin/etalon его AGENTS.md совпадает с текущим. Приоритетные риски из библиотеки сбоев здесь — сохранность прежних проверок при объединении, исправление причины красного CI, отказ при отсутствующем обязательном исполнении и различение локального результата от выпуска.

## Что фактически проверено

Сравнение выполнено непосредственно по Git-объектам старого SOURCE `0151a555ac429957d0eee591317cc4326e909dfd` и проверяемого SHA, а не только по заявлениям разработчика. Все 222 прежних защищённых пути присутствуют и сохраняют Git modes (режимы файлов). У 220 путей совпадают и хэши, и байты; два разрешённых изменения — `.github/workflows/ci.yml` и отдельно подготовленный тестировщиком `scripts/ci/tests/test_ci_release_additions.py`. Остальные процессные скрипты, парсеры, server gate, проверяющая программа main и прежние проверки не меняются. Дельта scripts/ci состоит только из указанного теста и двух новых fixture JSON (фиксированных тестовых входов). Никакого обхода защиты в workflow не добавлено.

Сохранены все 1146 прежних case IDs (полных имён проверок), включая их порядок внутри наборов. Для всех 18 старых suites (наборов проверок) сохранены report, format и exact. Значение exact определяет, обязан ли отчёт содержать ровно перечисленные проверки; оно нигде не ослаблено. Прибавка до 1161/19 объясняется ровно четырьмя новыми тестами в ci-shards и отдельным node-tap набором wms686-model с 11 исходными именами. Прибавка до 225 путей объясняется двумя fixture JSON и исходным model.test.ts. Полный перечень старых IDs и additions сохранён в [verification.json](../evidence/WMS-652/process-wiring-review-20261007/verification.json).

Тестовые файлы интеграционных переносов `72e4fde5c75dde123c536571bc6ea422060597ed` / `977aa7f6bb9da2ccb2850c091f765759fa161cfd` побайтово эквивалентны соответствующим исходным контрактам `1ab749` / `5ca749`; разработчик в `14c340a` их не менял. model.test.ts совпадает с исходным test commit `ed4b88703` и принятой веткой `0d054a2256322428e815ed78fc8d149b0c140aa6`. Его ожидания и состав не переписаны ради нового результата.

Workflow разобран как YAML и сравнен структурно. Все прежние jobs (задания CI) и производители отчётов остаются неизменными. У process-proof сохранены baseline, backend, frontend-build, guards, print-regressions и printer-windows; к needs добавлен wms686-mockup. У нового обязательного производителя нет условного отключения или continue-on-error. Node закреплён на 24. Команда `node --test --test-reporter=tap docs/mockups/WMS-686/model.test.ts` выполняет весь исходный файл без фильтра и пишет TAP (сырой поимённый отчёт тестов) в `$RUNNER_TEMP/wms686-model.tap`. Ненулевой код завершения не подавляется.

Upload выполняется с always(), чтобы сохранить результат при падении последующих шагов; отсутствие файла даёт ошибку. Имя upload и download одинаковое: `wms686-executed-contracts-${{ github.sha }}-${{ github.run_id }}-${{ github.run_attempt }}`. Поэтому загрузка ищет конкретные SHA, запуск и попытку текущего CI, а не старый зелёный артефакт. Download помещает TAP в общий каталог process-proof. Сам process-proof допускается штатными needs только после успеха всех обязательных производителей; падение model, установки зависимостей или сборки демонстрации не превращается в успешный proof.

Прочитана вся цепочка проверки: `process_contracts.py` → `build_process_proof.py` → `verify_process_ci.py`, а также `trusted_process_check.py` и серверная проверка. Policy closure (полнота защищённых исходников и обязательных результатов) локально подтверждена для 225 файлов. Реальный TAP новой suite проходит существующий парсер вместе с настоящим JUnit ci-shards; не только итоговые числа, но и точные имена совпадают с policy. Build proof требует все 19 policy reports, связывает execution.json с проверяемым Git SHA, head, base, run, attempt и хэшем policy и копирует именно проверенные отчёты. Парсер отчётов не заменялся.

На неизменённом `verify_process_ci.verify_execution` отдельно проверено чтение настоящих Node TAP байтов внутри тестового архива: положительный сценарий признаёт 11 cases, отсутствие TAP member и неверные SHA/head/run/attempt/policy либо имя артефакта другой попытки отвергаются. API identity и metadata в этих адресных пробах синтетические, архивы существуют только в памяти и не являются настоящими receipts GitHub или доказательством релиза. Ни synthetic archive, ни контролируемые испорченные отчёты не сохранены как release proof.

## Граница PASS и следующие обязательные доказательства

`P` — независимо принятая продуктовая ссылка. Сейчас это только `d61805978b3e7878d1056c99b4e6e0823edf49a5`: literal product_scope command и действующая protected fixture согласованы. Top-level final_reviewed_source равен null, status — pending-final-independent-freeze. Controlled accepted fixture проверяет механизм будущего перехода на другом известном SHA и отвергает HEAD, `${GITHUB_SHA}`, непроверенного кандидата и прежний pin после моделируемого freeze; она не объявляет этот SHA финальным продуктом всего пакета. Защищённые fixture/test bytes нельзя самовольно переизбрать из кандидата. Автоматическая проверка формы acceptance SHA сама по себе не доказывает независимую приёмку: выбор будущего P требует фактического отдельного заключения.

`S` — последующий источник защиты, содержащий pin финального P, CI и policy, принятый отдельным процессным ревью. P и S различны; собственный будущий SHA workflow не подставляет. Настоящий общий финальный продукт P ещё не заморожен, финальный S и его полный CI ещё не предъявлены. Поэтому это **PASS текущего подключения отчётов и сохранности защиты**, а не утверждение, что `14c340a` уже годится как окончательный SOURCE всего пакета.

Локальный bootstrap integrity на base `4b298efc95be7b4b6b7fe5665be9f3671f1fe747`, у которого нет policy, подтверждает внутреннее соответствие 225 файлов, но не является независимым anchor (внешней обязательной защитой ветки). Старая SOURCE намеренно отвергает новые хэши. Нужны финальный независимо принятый P, согласованный с ним exact pin/fixture, последующий проверенный S, полный CI точного кандидата с настоящими отчётами всех suites и положительная/отрицательная проверка штатной защиты с точным SOURCE pin. Это ревью не выполняло GitHub artifact upload/download, не запускало полный CI и не подтверждает уже установленный новый main pin.

В ходе этой работы изменены только настоящий отчёт ревью и принадлежащие ему evidence. Product, CI, policy, tests, секреты, main, etalon и deploy не менялись. Требования, приёмка и выпуск остаются у соответствующих независимых ролей; никакой final release approved здесь не объявлен.
