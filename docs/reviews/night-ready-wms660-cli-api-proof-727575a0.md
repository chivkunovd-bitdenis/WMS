# WMS-660 — безопасная CLI/API-проверка после выкладки same-product staging

Дата проверки: 06.10.2026, 11:35–11:37 Asia/Tbilisi.

## Что именно проверено

Railway staging продолжает обслуживать commit
`727575a0fd47dec56f34b38b987925686626c2b9`. Последние deployments API, web,
worker и beat имеют статус `SUCCESS` и один commit hash `727575a0`; Redis также
имеет статус `SUCCESS`. Production в этой проверке не менялся.

`git diff` между продуктовым кандидатом
`23c65f86dee1a71f0703b2c6c29990707f502445` и staging `727575a0` вне
`backend/alembic/versions` пуст. Значит, различаются только уже проверенные
исторические migration-файлы, а код WMS-660 совпадает. Дополнительно сверены
хеши целевых файлов:

- `fbs_scan_auto_print_service.py` —
  `40b2e0e6ac8a34ebe493799ac9e9cf015885721e053e3070dddb3891ed64ecd9` у
  кандидата, staging-коммита и фактически запущенного API-контейнера;
- `ProductBarcodeCell.tsx` —
  `d64172fc5b07a4f717229ccf54c5cf4062739ee5467297a362cbd8e9e23f7085` у
  кандидата и staging-коммита.

Внутри запущенного API-контейнера штатный OpenAPI подтвердил наличие маршрута
`/operations/fbs-supplies/{supply_id}/scan-auto-print`. Внешний запрос без
авторизации получил ожидаемый HTTP 401: маршрут доступен, но не был вызван от
имени реального оператора и поэтому не мог изменить данные стенда.

После выкладки выполнен узкий end-to-end API-прогон того же продуктового кода на
изолированной тестовой БД, создаваемой `backend/tests/conftest.py`. Защита
фикстуры принудительно заменяет `DATABASE_URL` на отдельную SQLite-БД в каталоге
тестов; реальные остатки, поставки, события и учётные записи staging не читались
и не менялись. Команда:

```text
pytest -n 0 -q tests/test_wms660_scan_barcode_aliases.py \
  tests/test_wms631_scan_undo.py::test_scan_undo_releases_selection_and_is_idempotent \
  tests/test_wms514_scan_auto_print.py::test_product_scan_selects_one_order_and_replay_does_not_advance \
  tests/test_wms514_scan_auto_print.py::test_successful_product_bind_atomically_prepares_reprint_recovery \
  tests/test_wms514_scan_auto_print.py::test_reprint_product_blocks_unknown_print_outcome
```

Результат: `14 passed` за 13,80 секунды. Через настоящий ASGI endpoint
приложения проверены оба набора физических WB-кодов из требований, основной код,
код заказа, повтор с тем же idempotency key, переход к следующей единице, границы
поставки/seller/tenant, отказ при коллизии alias с другим товаром, явный
`order_id`, штатная отмена скана и два состояния восстановления печати. Проверки
отдельно подтверждают, что ошибочная или неоднозначная попытка не создаёт
scan-событие, а повтор не создаёт вторую операцию.

Для отображения и разделения площадок после выкладки повторён компонентный
контракт exact candidate SHA `23c65f86`:

```text
npx vitest run src/components/ProductBarcodeCell.wms660.test.tsx --reporter=verbose
```

Результат: `4 passed`. Подтверждены основной код первым, удаление пустых и
повторяющихся значений, отдельная строка каждого кода, сохранение обычного вида
для одного кода и Ozon fallback только при отсутствии WB-кодов. Это тест
рендеринга без Chrome и без запуска нового браузерного процесса.

## Граница доказательства

Проверка закрывает функциональную матрицу R1–R3 через опубликованный код,
запущенный маршрут и изолированный API-контур без риска для реальных остатков.
Она не заявляет физическую печать, бумагу, внешнюю передачу в WB/Ozon либо новый
браузерный прогон под живой учётной записью. Эти действия не требуются для
проверки отсутствия регрессии WMS-660 и намеренно не выполнялись. Итоговый
продуктовый вердикт принимает аналитик; настоящий файл фиксирует факты и не
подменяет его заключение.
