## Реальная область нового теста

Единственный новый файл —
`backend/tests/test_wms662_batch_handoff_lock_order.py`. Три существующие
WMS-поставки A/B/C, один селлер, три отдельных заказа и два товара:
A расходует P1, B и C расходуют по одной единице P2. В публичный
`sync_ozon_order_statuses` через неизменённый helper `sync` попадают только A/B.
Обычная передача C вызывает публичный `deliver_supply` через неизменённый
helper `normal_handoff`. Один `conduct_supply` вместо внешнего sync-цикла
не используется. Лимит опроса равен двум, отметка последнего опроса C новее;
проверяется, что запросы sync содержат A/B и не содержат C. UUID поставок
упорядочены A/B/C для настоящего production-цикла по UUID.

Только внешний транспорт и синтетические учётные данные подменены. Live HTTP
запрещён прежней fixture. Продуктовые функции, SQL и складские операции настоящие.
При захвате Seller batch останавливается; независимый наблюдатель PostgreSQL
отпускает его только по фактическому `pg_blocking_pids`. PID фиксируется перед
любой блокирующей записью, включая ожидание внешнего ключа до явного Product
SELECT. Состояния взаимного ожидания и текущие SQL сохраняются в диагностике.
Ошибки драйвера захватываются через `handle_error`, включая 40P01, который может
быть перехвачен вложенной транзакцией начисления. Время не отпускает барьер;
таймауты механизма явно отделены от ошибки продукта.

Бизнес-ожидания: расход P1=1/P2=2, три движения, точные уменьшения остатка,
нулевые резервы обоих видов и позиций, проведение исходных трёх документов,
по одному факту работы и по два начисления количеством 1 на каждый заказ,
деньги **1800 на каждый заказ**, неизменность тарифов. Независимое чтение
использует новые сессии. После первого результата предусмотрены настоящее
восстановление и повтор: стабильные деньги, остатки, резервы, движения, факты,
операции и отсутствие второй внешней передачи. Успешное восстановление не
удаляет первоначальную SQL-ошибку или потерю денег из результата контракта.
В единственной попытке эти ожидания после конкурентного участка ещё не достигнуты.

## PostgreSQL и точная остановка

Перед созданием базы SQL подтвердил `wms_test`, порт **55466** и **0 других
client backend connections** на сервере. Создана только собственная изолированная
база `wms_test_662_batch`, владелец `wms_test`. Старую `wms_test_662_f6` и другие
базы тест не изменял, сервер не останавливался. Один pytest-процесс,
без xdist. Маленькие fixtures: три заказа, два товара, три поставки.

Единственная команда воспроизведения из backend:

```sh
WMS_TEST_DATABASE_URL=postgresql+asyncpg://wms_test@127.0.0.1:55466/wms_test_662_batch \
WMS_TEST_DATA_DIR=/private/tmp/wms662-batch-test-data \
PYTHONDONTWRITEBYTECODE=1 \
/Users/deniscivkunov/Projects/WMS/backend/.venv/bin/python -m pytest \
  -q -p no:cacheprovider tests/test_wms662_batch_handoff_lock_order.py \
  --tb=short --show-capture=no
```

Результат: **1 failed, 6 warnings in 1.48s**, exit 1. Это HARNESS FAIL:
в `BatchSchedule.before` прежнее выражение
`assert self.pids.setdefault(worker, pid) == pid` сравнило **28085 и 28086**.
Публичный sync уже прошёл сохранение observations и дошёл до
`lock_order_batch_packaging_rows → lock_packaging_rows`, но ещё не до проведения
A. Сохранение observations завершает прежнюю транзакцию; следующая получает
другое соединение пула. Требование неизменного PID на весь публичный вызов
ошибочно. В коде теста оно заменено регистрацией текущего writer PID перед
каждой блокирующей записью, как в исправленном F6. Эта коррекция после единственной
попытки не исполнялась. Второй writer не стартовал, взаимное ожидание не измерено,
SQLSTATE 40P01 не наблюдался; нельзя объявлять данное падение продуктовым RED.

product ef9225bb и отчёт ревью не менялись. F6 PASS и прежние 92/11/37 результаты
не переопределяются и не выдаются здесь за собственные прогоны. Изменение

остаётся выводом опубликованного ревью, а не новым исполненным доказательством.

Следующий шаг — отдельное разрешённое выполнение исправленного тестового
механизма на той же собственной базе. Только фактические два writer PID,
наблюдаемое ожидание PostgreSQL, реальный 40P01 и/или потеря бизнес-результата
дают основание возвращать дефект исходному разработчику. Commit/push этого
контракта не означает приёмку, CI, выпуск, merge либо deploy.

## Повтор отдельным тестировщиком: фактический GREEN

По новому прямому поручению ведущего выполнены ограниченные повторы на той же
собственной базе. SQL перед запуском подтвердил
`wms_test_662_batch|wms_test|127.0.0.1|55466|0` других подключений.
Полный исходный `astra-review-ef9225bb.md` прочитан; product не изменялся.
Новые серверы и базы не создавались, старые тесты не редактировались.

Первый повтор уже прошёл прежнюю ошибку PID, но закончился таймаутом наблюдателя
без содержательной диагностики. В новом тесте наблюдатель теперь явно очищает
снимок статистики `pg_stat_clear_snapshot()` перед каждым чтением текущих PID;
его timeout сообщает весь trace, результат writers и ошибки барьера. Это
только коррекция механизма наблюдения, не освобождение барьера по времени.

Второй повтор установил другую ошибку fixture: обычный внешний транспорт
`ApproveRaceTransport` до approve требовал одну operation во всём tenant.
Настоящая batch-порция A/B уже создала свои операции, поэтому их три.
Обычный writer прекращался на `assert 3 == 1` ещё до складской части;
барьер истекал и billing перехватывал scheduling timeout. Это HARNESS FAIL,
не deadlock продукта. Только в новом тесте добавлен `BatchOrdinaryTransport`:
операции фильтруются по exact C `local_entity_id`, затем сохранены прежние
проверки единственной операции C, точного order scope, product quantity 1,
posting number, одного внешнего approve и его ответа. Общий helper и прежний
тест не менялись. Все финансовые/складские ожидания и recovery/retry сохранены.

Третий прогон дал **1 passed, 6 warnings in 2.53s**. Последний, третий ограниченный
повтор после первой попытки, добавил только вывод фактической диагностики и дал
**1 passed, 6 warnings in 3.16s**. Команда та же, с `-s` для PG evidence.
Это два настоящих GREEN, содержательного RED и SQLSTATE 40P01 не получено.

Последний снимок PostgreSQL:

- batch PID **47386**, ordinary PID **47362**;
- `pg_blocking_pids(47362) = [47386]` при обычном
  `SELECT products ... WHERE tenant_id=$1 AND id=$2 FOR UPDATE`;
- batch в этот момент держит `SELECT sellers.id ... FOR NO KEY UPDATE`,
  `pg_blocking_pids(47386) = []`;
- до первого Seller в trace batch уже четыре раза успешно захватил Product;
  ordinary только пытается получить Product и получает его после batch;
- взаимный цикл **false**, перехваченных SQL errors нет, оба результата `None`;
- деньги каждого из трёх заказов **1800**, остаток P1 **12** (был 13), P2 **10**
  (был 12), позиционные резервы пусты, business issues пусты;
- настоящие восстановление и повтор сохранили деньги/склад/резервы/движения/
  факты/операции и не повторили внешнюю передачу.

Следовательно, достаточное расписание, предложенное прежним ревью, **не достигнуто
в исполненном публичном пути**: обычный C не получает Product до ожидания Seller.
Он уже ждёт batch на Product, поэтому заявленное обратное ребро Product → Seller
не возникает в этом прогоне. Явные Product-блокировки, неявное удержание через
внешние ключи и источник конкретного раннего удержания следует различать;
trace не записывает UUID каждого SQL-параметра и не доказывает универсальную
невозможность другого расписания или другого WB/import-пути.

Передача ведущему: вернуть эти доказательства отдельному Astra high ревьюеру
для уточнения причинного вывода о публичном batch-пути. Не передавать исполнителю
придуманное product FAIL, не снимать invoice fence по этому GREEN. Общая приёмка,
CI и разрешение выпуска остаются за отдельными этапами. В новый commit входят
только коррекция нового теста и это продолжение отчёта.
