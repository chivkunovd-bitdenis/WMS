# WMS-662 C19 — RED-контракт перед исправлением интерфейса

Отдельный TESTWRITER662 выполнил прямое поручение без навыков, дочерних агентов,
нового аналитического цикла и продуктовых правок. Прочитаны локальный AGENTS.md,
полный WMS-662, свежий origin/etalon:AGENTS.md
(`4b298efc95be7b4b6b7fe5665be9f3671f1fe747`) и
[фактическая приёмка C19](wms662-c19-acceptance-245b09e2.md).
Рабочая база — `217562b36ad39dafebf397d203004f708f719a5c`, включая отчёт
`864434806` и все сохранённые снимки. `backend/app` и прежний `frontend/src`
совпадают с product `245b09e27288d09569b80a702711a4291793b864`.
Существующая ветка продолжена; перенос нового etalon поверх неё не выполнялся.

Добавлен один изолированный
[DOM-тест](../../../frontend/src/screens/v2/FfFbsSupplyWorkspace.wms662.c19.dom.test.tsx)
на настоящем `FfFbsSupplyWorkspace`, таблице состава и `FbsSupplyHistoryDialog`.
Он напрямую читает уже сохранённые HTTP-ответы
[facts.json](c19-run-37440990542/facts.json): один и тот же документ,
partial №662000 `in_delivery` / №662001 `in_supply`, затем оба `in_delivery`.
Новые внешние ответы, сущности и события истории не сочинялись.

Для каждой стадии выполнены открытие, закрытие/повторное открытие и имитация
обновления страницы: полный сброс React-состояния с новым GET `/workspace`
и сохранением штатного sessionStorage. Это jsdom, не браузерная визуальная приёмка.
Операторская вкладка «Упаковка и маркировка» сохраняется; `assembling` не
возвращает человека на подбор. Переданные и ожидающие заказы проверяются
по собственным строкам состава существующими подписями `FbsStatusChip`:
«В доставке» и «В отгрузке». Проверка исключает скрытый текст; она не предписывает
новую колонку, chip, расположение или новый экран. Колонка «Подбор» у обоих
заказов по-прежнему содержит «Ожидает» независимо от передачи.

Сообщение «Поставка уже передана в WB» отсутствует при partial и присутствует
при full. История открывается настоящим компонентом с сохранённым событием
«Поставка создана»; новые события от разработчика этим контрактом не требуются.
Все fetch перехвачены и ограничены сохранёнными GET-ответами. Проверяются
отсутствие shipment/print/stock-запросов, `window.open`, `window.print` и
PDF-печати. Исходные фикстуры остаются неизменными. Это охрана побочных действий
интерфейса; новое доказательство серверного списания или физической передачи
этот DOM-тест не заявляет.

Команда из `frontend`, один worker и один файл, предел сценария 15 секунд:

```sh
./node_modules/.bin/vitest run src/screens/v2/FfFbsSupplyWorkspace.wms662.c19.dom.test.tsx --maxWorkers=1 --minWorkers=1 --no-file-parallelism
```

Использована уже установленная общая `WMS/frontend/node_modules` через
игнорируемую Git символическую ссылку; npm install, новые зависимости, PostgreSQL,
Mac-браузер и реальные API не запускались. В общей установке отсутствует
`pdf-lib`: только вход `buildFbsPdfPrintTape` подменён наблюдаемой функцией,
которую сценарий обязан не вызвать. Карточка, таблица, история и подписи настоящие.
Начальные ошибки загрузки `pdf-lib` и URL фикстуры не считались RED; обвязка
исправлена только в новом тесте. Временные предупреждения MUI о вкладках до
прихода workspace не являются причиной отказа.

Фактический RED: полный сценарий заканчивается кодом 1 из-за отсутствующих
подписей передачи в строках обоих заказов на всех шести контрольных точках.
Последний прогон окончательного файла: Vitest 3.2.6, начало 13:23:08,
82.61 секунды всего (78.74 — загрузка модулей, 3.35 — сам сценарий),
`Test Files 1 failed; Tests 1 failed`; ошибок загрузки и таймаута нет.
Например, для partial №662000 ожидается «В доставке», получено
`№662000 … 1 шт. Не требуется Ожидает`; для №662001 ожидается «В отгрузке».
Остальные проверки доходят до конца без отказа. Мягкие проверки (`expect.soft`)
позволяют увидеть обе стадии и повторные чтения в одном сценарии, сохраняя RED.

показав уже возвращаемый `order.status` отдельно от подбора. Переиспользовать
существующий формат статуса; не переопределять parent done, pick, историю API
или серверное проведение ради текста. Ожидания нового контракта и старые тесты
не менять. После кода запустить ту же команду; root независимо проверит новую
UI delta. Этот этап не содержит саморевью, новой приёмки, полного CI или деплоя.

Ownership: новый тест, этот handoff и только ссылка «Тест» в строке C19
`docs/requirements/WMS-662.md`. Класс «руками» и актуальный FAIL сохранены.
Продукт, старые тесты, runner, guards и чужие файлы не менялись;
чужие записи индекса не затрагивались.
