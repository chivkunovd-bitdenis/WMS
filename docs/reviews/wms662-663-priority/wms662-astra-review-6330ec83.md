## F1 · P1 · Сохранённый approve доказывает лишние отправления

Источник: `backend/app/services/ozon_fbs_sync_service.py:1127–1134`.
Ветка восстановления проверяет только наличие `carriage_approved`, `carriage_id`
и принадлежность заказа нынешней поставке. После этого `expected_quantities(order)`
целиком превращается в доказанное количество. Сохранённые
`ozon_handoff_progress.posting_numbers` вообще не сверяются. Сохранённый рецепт
и количества на момент approve также не ограничивают это решение.

Следствие: заказ, добавленный в ту же поставку после подтверждения перевозки,
или иное неподтверждённое отправление текущего состава списывается на основании
чужого checkpoint. Это нарушает R1–R4, R7 и R12: наличия когда-то успешной
перевозки у родителя недостаточно для доказательства текущего состава.

Воспроизведение выполнено через существующие seed/checkpoint/sync/saved из
`tests/test_wms662_observed_handoff.py`, в отдельной SQLite-базе conftest,
с FakeTransport и запретом реальной сети. Через in-memory pytest collection hook
заменён только вызываемый объект одной проверки, файлы тестов не редактировались.

1. `seed(db_session, 'ozon', count=2)` создаёт A и B по одной единице.
2. Сохраняется checkpoint carriage 901, `carriage_approved=True`,
   `posting_numbers=[A]`, `shipped_postings=[A]`.
3. У обоих текущих заказов выставлен обычный `ozon_assembly.posting_numbers=[свой ID]`.
4. Карточки обоих возвращают `awaiting_deliver / posting_in_carriage`, перевозка formed.
5. Запускается реальная `sync_ozon_order_statuses`, результат читается новой сессией.

Получено: `approved posting count=1, current supply orders=2, actual shipped=2`.
Проверка `assert actual == 1` падает. Новый расход B ничем не доказан.
Штатная положительная C6 проверяет только одного текущего участника и не ловит
расширение области старого checkpoint.

Исправление должно ограничить восстановление точными доказанными posting и
количествами сохранённой операции. Недостаточное/противоречивое доказательство
остаётся unknown; угадывать состав перевозки и выполнять новый approve нельзя.

## F2 · P1 · Отмена дочернего posting не освобождает оставшийся резерв

Источники: `backend/app/services/fbs_observed_handoff_service.py:282–289`,
`backend/app/services/ozon_fbs_sync_service.py:748–752`,
`backend/app/services/fbs_observed_handoff_service.py:387–420,551–566`.

Сверка читает все дочерние карточки разделённого отправления, но сохраняет лишь
положительные количества. Подтверждённая отмена дочерней части теряется.
Обработчик статуса parent `cancelled_from_split_pending` сразу возвращается,
а остаток резерва вычисляется как первоначальное количество минус расход.
Отменённые дочерние единицы поэтому остаются зарезервированы бессрочно.

Воспроизведение на той же изолированной fixture:

1. `seed(..., 'ozon', quantities=(3,2))`, затем штатный `split_cards`.
2. Child A подтверждает передачу двух единиц первой позиции; child B содержит
   оставшиеся 1+2 и первоначально awaiting_deliver. Первый sync списывает 2.
3. Статус B меняется на `cancelled`. Выполняются ещё два sync.
4. Независимое чтение: `proved child A=2, cancelled child B=3; shipped=2,
   reserved=3, supply status=assembling`.

Расход 2 корректен; `assert reserved == 0` падает. Свободный остаток занижен на
три отменённые единицы. Все неотменённые единицы уже переданы, но текущая проверка
полноты продолжает сравнивать расход с исходными пятью и не может завершить документ.
Нарушены R4, R5, R9 и R12. Отмена не должна создавать обратный приход для уже
переданного A; требуется освободить только подтверждённо отменённое обязательство B
и учесть его при полноте документа, сохраняя точные связи child/позиция/количество.

## Остальная проверка и её границы

В новом наблюдаемом пути не обнаружены вызовы deliver/ship/create/approve,
печать, новые таблицы или синтетические внешние номера. Используется существующая
FbsWbOperation. G1 без checkpoint и G4 не превращены в положительный wire-контракт.
Сохранение наблюдения отделено commit от локального списания; применение перечитывает
заказы, поставку и ledger. Порядок supply → orders → ledger виден в коде.
HTTP нового status-poll пути выполняется перед этими блокировками.

Проверка отмены целого заказа не равна проверке отмены части split: первая есть
в контракте и коде, вторая обнаружила F2. Конкуренция проверена чтением реальных
PostgreSQL-тестов автора; повторный запуск этой общей выделенной базы ревьюером
не выполнялся во избежание вмешательства в параллельную работу.

`git diff 77dc127344ff164417cc13c8d2b218af3ac09266 HEAD --` для обоих файлов
WMS-662 тестов пустой: контракт тестировщика сохранён. `git diff --check` успешен.
Независимый запуск исходного SQLite-контракта:

`pytest -q tests/test_wms662_observed_handoff.py --tb=short`

Результат: **84 passed, 8 setup errors**, 47.20 s. Первичная причина setup errors —
`sqlite3.OperationalError: database or disk is full`, затем
`unable to open database file` при пересоздании схемы. `df -h .` показал 121 MiB
свободного места, 100% использования. Это не бизнес-падения и не независимое
подтверждение 92/92. Оба приведённых выше целевых контрпримера до этого завершились
полностью и упали именно на конечных бизнес-assert, а не при создании среды.
Заявленные автором 102/185 pass, ruff и mypy не выдаются за повторённые ревьюером.
