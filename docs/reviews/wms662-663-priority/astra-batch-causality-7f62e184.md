## Новый тест не подменяет публичные пути и не отпускает барьер по времени

Существуют три разные поставки и заказа одного селлера: A(P1), B(P2), C(P2).
Настоящий `sync_ozon_order_statuses` получает A/B через обычный helper `sync`;
лимит 2 и более свежий `last_wb_sync_at` у C выводят C за порцию. UUID A/B/C
задают порядок настоящего цикла поставок. Запрошенные posting проверяются
после исполнения. C вызывает настоящий `deliver_supply` через
`normal_handoff`, а не одиночный внутренний `conduct_supply` вместо batch.
Подмена ограничена внешним транспортом и синтетическими credentials;
fixture запрещает настоящий HTTP.

Остановка batch происходит ПОСЛЕ успешного Seller SELECT. Второй writer
запускается при удерживаемой блокировке. Наблюдатель получает реальные PID
и отпускает batch только при `batch_pid in pg_blocking_pids(ordinary_pid)`.
`pg_stat_clear_snapshot()` обновляет статистический снимок перед каждым
чтением; он не коммитит writers и не освобождает их блокировки. Пауза 10 мс
задаёт частоту наблюдения. Освобождение в `finally` — уборка после завершения
или ошибки; timeout записывается как HARNESS FAIL, в том числе если его
перехватил billing savepoint. Оно не превращает такой timeout в PASS.

Регистрация текущего PID перед DML/блокирующим SELECT корректна: публичные
пути коммитят observations и пред-HTTP checkpoint, после чего пул может выдать
другое соединение. Требовать один PID на весь публичный вызов было ошибкой.
`handle_error` сохраняет SQLSTATE ниже обработчика billing; финальное
ожидание запрещает любые сохранённые SQL errors, включая 40P01. Recovery не
стирает первоначальные ошибки либо потерянные деньги.

`BatchOrdinaryTransport` устраняет ровно ложное `len(tenant.operations)==1`:
в batch закономерно уже есть операции A/B. Проверяется единственная операция
точной поставки C в независимо прочитанной области tenant; сохранены exact
order scope, P2 quantity=1, posting C, запрет второго approve, прежний
синтетический ответ. Прочие endpoints делегируются прежнему транспорту.
Это допустимая коррекция fixture, не обход обычной передачи.

Сравнение 043fe7056 → 7f62e184 подтвердило одинаковые AST функций
`business_issues` и `tariffs`, а также побайтово одинаковый хвост от
`assert not schedule.harness_errors` до конца: все бизнес-assertions,
recovery/retry и отказ при первоначальных ошибках сохранены. Нет добавленных
skip/xfail или разрешения потерять начисления ради зелёного результата.

`pg_cycle=False`, `sqlstates=[]`, `results=[None, None]`, business issues пусты.
Каждый заказ получил **1800**, P1 уменьшился **13→12**, P2 **12→10**,
резервы обоих видов сняты; три исходных документа проведены, расходы,

предварительную явную блокировку всех товаров batch. Гипотеза о такой общей
блокировке также не должна становиться новым объяснением GREEN.

## Конкретное отличие fixture и ранний Product FK

Комментарий нового теста `no transition/FK audit before conduct` достигается
не полностью. Fixture выставляет A/B `status=in_delivery` и
`wb_status=delivering`, но оставляет `supplier_status=NULL` и
`required_meta_json=NULL` из `seed`. Реальный цикл опроса до первого conduct
для КАЖДОГО A/B исполнил в одной транзакции два UPDATE:

1. `last_wb_sync_at=<polled_at>` — autoflush перед запросом
   `_requirements_by_sku` (`ozon_fbs_sync_service.py:1150–1159`).
2. `supplier_status='delivering', required_meta_json=[]` — нормализация
   `_apply_status`/`_apply_requirements`, autoflush перед проверкой
   `_is_wms_supply_order` из `_charge_confirmed_order` (:1161–1172).

Оба UPDATE B до Seller зафиксированы дополнительным SQL-наблюдателем.
В схеме этой PostgreSQL непосредственно проверены немедленный
`fbs_orders_product_id_fkey` и AFTER UPDATE `RI_FKey_check_upd` на Product.
Повторное обновление версии строки, уже созданной текущей транзакцией,
может потребовать повторной проверки FK даже без изменения `product_id`;
проверка внешнего ключа удерживает ключ родительской строки Product и
конфликтует с чужим `FOR UPDATE`. Это объясняет раннее ожидание C на P2,
несмотря на отсутствие явного Product(P2) SELECT batch до Seller.
Это причинное объяснение по реальному DML и схеме, **не прямое измерение
конкретного tuple lock через pg_locks**: исходный наблюдатель сохраняет
блокирующие PID/SQL, а не каждую внутреннюю FK-проверку.

Статусный audit нельзя автоматически назвать причиной этого прогона:
status A/B уже стабилен, и `_fbs_order_change_rows` создаёт событие с Product
при смене status/supply. Начальные события переноса/статуса созданы и
закоммичены fixture до writers. В прежнем F6 действительно был отдельно
разобран FK wait до явного Product SELECT; это не разрешает приписать ему
любой новый wait без сверки фактического SQL. Здесь ordinary уже дошёл до
явного `FOR UPDATE P2`, но ещё не владеет им и не ждёт Seller, удерживая P2.

**Одна конкретная коррекция следующему тестировщику:** в этом же fixture
до существующего setup commit полностью нормализовать оба A/B:
`supplier_status='delivering'` и `required_meta_json=[]`, сохранив уже
заданные status/wb_status, реальные три заказа/два товара, лимит,
публичные пути, транспорт C, барьер и ВСЕ бизнес-ожидания. Это один вариант
начального состояния «повтор уже обработанной карточки, расход ещё не
проведён». Не отключать FK, autoflush, audit или Product locks. В диагностике
сохранить UUID Product вместе с attempt/acquired и ранние UPDATE, чтобы
проверить, действительно ли второй UPDATE B исчез и C получил P2 до Seller.
В этом ревью такая коррекция не внесена и второй прогон не выполнен.

Текущий GREEN честно проверяет реальную подготовленную сцену; освобождение
барьера при реальном ожидании P2 не является жульничеством. Но эта сцена
не доказывает старое утверждение о полностью неизменном предварительном
проходе A/B. Следующий тест может дать RED либо ещё один GREEN — результата
заранее нет. До него нельзя объявлять новый product FAIL или предписывать
универсальную перестройку блокировок.

## Причинность относительно baseline и общий вердикт

На baseline `43f4bdbae7fff1fcbaf7a47d7293a7faaf5428a1` отсутствуют новый
observed conduct batch и явный Seller fence в `record_fbs_order_confirmed`.
Коммит `ca4808f002a81607364d874087e9e7896dd7f083` действительно добавил
шесть строк Seller `FOR NO KEY UPDATE` для `handed_over_quantities`.
На ef9225bb последовательность внутри внешней транзакции остаётся
conduct A → Seller → conduct B → commit. Это проверенные изменения кода.
Они не доказывают достижимость встречного ребра C(P2→Seller): его в трёх
опубликованных GREEN-прогонах, включая этот, не было. Поэтому прежнее
«новый достижимый цикл установлен» заменяется на **условную гипотезу,
не подтверждённую исполнением**, с одним указанным различием fixture.
Назвать ca4808f причиной фактического deadlock этого теста нельзя: deadlock нет.
ef9225bb не добавляет batch-порядок и не меняет stock/transport.

| Часть WMS-662 | Итог и источник |
|---|---|
| F1/F2, frozen approve scope, split/cancellation; F3 cumulative continuation | PASS сохранён по независимому c36-отчёту и предыдущей цепочке; заново не запускались. |
| F4 document packing и F5 полное атомарное сторно, issued invoices | PASS c36 сохранён; ef922 меняет точную блокировку отмены, не состав сторно или invoice fence. |
| F6 отмена другого заказа против normal/observed handoff | PASS ef922: предыдущий независимый отчёт подтверждает 4 настоящих PG PASS; старый c36 RED был реальным 40P01. Здесь не переоткрывается. |
| Stock-boundary 92, financial 11, adjacent 37 | PASS на неизменном ef922 по developer report; это сохранённые результаты, не собственные новые прогоны. |
| Новый public batch A/B против ordinary C | PASS фактической сцены: два GREEN tester плюс один GREEN reviewer; все бизнес-проверки сохранены. |
| Прежнее утверждение о новом доказанном batch deadlock | Отозвано как недоказанное. Один конкретный пробел steady-state fixture описан выше; установленного нового product blocker нет. |

Итого: **не возвращать продукт разработчику с batch FAIL по отчёту 853be478;
invoice fence не снимать, общий механизм блокировок не переписывать.
Для завершения проверки прежней причинной гипотезы вернуть тестировщику
только указанное начальное состояние A/B.** Это не универсальный тестовый
рефакторинг и не подмена положительного результата обязательным RED.

Продуктовая граница владельца сохранена: обычный статус WB/Ozon, сборка,
упаковка и закрытый parent сами по себе не вводят новый расход. Исключение —
существующая source=wms поставка с точным доказательством передачи;
допроводится только отсутствующее количество один раз. Резервы и отмена
сохраняют прежнюю политику, отмена не приходует физический товар.
