## Изменение поведения

Сверка WB получает точные статусы заказов и состав существующей WMS-поставки.
Только допустимое положительное сочетание статусов и принадлежность этому
составу разрешают недостающий расход. Закрытый родитель без состава не проводит
документ. Ozon сопоставляет номер отправления, SKU и количества карточки;
для разделённого заказа читает реальные связанные дочерние отправления и
проверяет их совокупный состав перед частичным расходом.

Перед складскими изменениями доказательство сохраняется в существующем
`FbsWbOperation` с видом `observed_handoff`. Сохранённый снимок содержит точную
привязку заказа, состав и доказанные количества; после внешнего ожидания они
сверяются с перечитанным состоянием. Затем один локальный commit сохраняет
движения, существующий ledger (рецепт списания), уменьшение соответствующего
резерва и штатные начисления. При сбое evidence переживает rollback складской
части и позволяет восстановление без второго внешнего действия.

HTTP завершается до блокировок. Порядок локального применения — поставка,
заказы, ledger и складские источники. Существующая отмена и reversed ledger
не оживают от запоздалого положительного ответа. Отмена не приходует товар:
это прежняя политика отдельного документа возврата. Для переданной WB-части
сохранённая история подтверждает выполненную работу при последующей отмене.

Рецепт Ozon сохраняет уже выполненные движения и дописывает только оставшиеся
количества. Резерв позиций уменьшается на проведённую часть; полный резерв
освобождается после полного расхода или штатной отмены. Дата передачи и статус
всей поставки появляются после всех неотменённых единиц. Локальный done с
отсутствующим или частичным расходом остаётся в ограниченной очереди опроса,
а полностью проведённый done исчезает из неё. Путь импорта существующей
карточки также выполняет сверку при неизменившемся статусе.

Новая таблица, документ, пользователь, синтетический внешний номер, упаковка,
печатный актив и расход операторского лимита не создаются. Обычная кнопка
после полного наблюдаемого проведения возвращает сохранённый результат.
Положительная ветвь formed без подтверждённого checkpoint (G1) и догаданный
API состава перевозки (G4) не реализованы. Ни deliver/ship/approve/create,
ни печать из нового наблюдаемого пути не вызываются.

F1 исправляется ограничением approve точными сохранёнными posting_numbers и
количествами. Новая обычная операция до HTTP сохраняет полный неизменный
снимок участников/позиций/количеств; первый approve отдельно закрепляет его
список отправлений. Повтор не расширяет этот список новыми участниками.
Исторический рецепт фиксируется до подготовки расширенного локального состава,
поэтому повтор со старым approve не меняет исходное подтверждённое количество.
Checkpoint без posting list пригоден только для однозначного старого singleton
с сохранённым рецептом; он не распространяется на расширенную поставку.

F2 исправляется сохранением точных результатов каждого child в существующем
наблюдении. Отмена child снимает его непереданное обязательство, сохраняет
движения других children и учитывается при завершении всей поставки.
Отменённый child остаётся отменённым после временного unknown или старого
положительного ответа. Выполненные движения связываются с доказанными child
количествами в том же рецепте; неиспользованные строки сохраняют exact
`cancelled_postings` без movement. Поэтому отмена после уже выполненного расхода
не создаёт второго освобождения или автоматического прихода, а терминальный
repair учитывает разрешённые отменой количества без бесконечного опроса.
Начисление завершённого частичного документа использует проведённые количества:
в F2 это две переданные единицы, а не первоначальные пять.

## Точный состав обычной передачи после HTTP

При продолжении обнаружен тот же риск в обычном callback: он перечитывал весь
текущий состав после ответа Ozon и списывал его целиком. Ведущий потребовал
закрыть этот путь в том же цикле. Отдельный тестировщик до исправления сохранил
контракт `8cd304a4d01ba7b0b17b5f1159c4aaedde44aadb` и передачу
`5fe999dd3` в `wms662-approve-scope-tester-handoff.txt`.
Два случая реально добавляют B либо увеличивают A с 1 до 2 отдельной DB-сессией
внутри fake approve HTTP. Перед этим свежая сессия проверяет долговечный снимок
A/1. Оба бизнес-RED получили расход 2 вместо 1 без setup errors.

Обычная операция теперь проводит только собственный пред-HTTP снимок, не
создавая наблюдаемую operation. Позиции, источник, reserve и факты/начисления
используют один подтверждённый объём; добавленный товар остаётся зарезервирован.
Только завершённый нынешний состав получает supply.delivered_at. Даже при
увеличенном A начисление за подтверждённую передачу ограничено A/1, а сам заказ
не маскирует незавершённый остаток статусом полного проведения. Повтор с тем же
ключом возвращает сохранённый результат без нового approve или движений.
При восстановлении callback исторический рецепт фиксируется до перепланирования,
а участники HTTP не расширяются новыми current orders. Без снимка или рецепта
старое подтверждение не доказывает расширенный состав; однозначный старый
singleton из одной единицы сохраняет существующую совместимость.

Подтверждённые cumulative quantities теперь явно включают узкое монотонное
дополнение существующих FBS записей. Writer блокирует и перечитывает запись,
сохраняет ID/дату/ключ и дополняет количество её товарных строк, не снижая его
от stale ответа. Начисление за сборку и упаковку сохраняет старые тарифные
версии/снимки/ставки уже известных строк; сумма меняется от дополнительного
количества, не от нынешнего тарифа. Новая товарная строка разрешает тариф по
исходной дате начисления. Защита от повторных записей не снята; остальные
операции не включают новый opt-in и сохраняют прежний immutable return.
