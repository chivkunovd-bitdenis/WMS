## Что было неверно и что изменено

`LockSchedule.hierarchy()` сохраняет только внешние транзакции, в которых
явно захвачены BOTH Product и Seller. Старое условие требовало непустыми
одновременно `hierarchy['handoff']` и `hierarchy['cancel']`. Тем самым тест
ошибочно предписывал отмене обязательный Seller lock, хотя это деталь
реализации, а не бизнес-требование. Это блокировало согласованное минимальное
исправление: вместо нового Seller fence отмена берёт точный tenant/order
FOR UPDATE; существующий order lock передачи сериализует тот же заказ,
а цикл между разными заказами исчезает.

В тесте изменено именно структурное ожидание, а не только описание области
проверки. Теперь известная трасса передачи с обоими ресурсами обязательна;
для всех реально записанных пар Product/Seller по-прежнему запрещены
противоположные направления захвата. Отмена без Seller может пройти только
при успешном выполнении всех настоящих конкурентных бизнес-проверок.
Новые обязательные имена блокировок не введены; helper и расписание неизменны.

Никакие assertions для четырёх PostgreSQL-сценариев не ослаблены:
отсутствие SQL errors/40P01, независимые backend PID, внешнее завершение
обеих операций, начисление A ровно 1800, полное сторно B с сохранением
исходных записей, расход одной штуки, движения и резервы, статусы, а также
идемпотентность повторов денег/склада/движений/фактов/операций/внешней передачи
сохранены дословно. Изменились только требование наличия пары у отмены,
его пояснение и сообщение об ошибке для противоположных направлений.

Этот документ уточняет ошибочное требование об одинаковой паре у обеих
операций в исходном `wms662-f6-testwriter.md`; исторический handoff не правился.
Ownership: только новый F6 test и этот отдельный test-correction handoff.
Другие frozen tests, guards, требования и продуктовый код не изменялись.

## Повторное доказательство RED на старом коде

На исправленном test commit с продуктовой базой c36 выполнен целевой прогон
на настоящем PostgreSQL, без xdist. Все четыре комбинации снова дали RED:

| Отмена B | Передача A | Причина падения |
|---|---|---|
| local | normal | SQLSTATE 40P01 |
| local | observed | SQLSTATE 40P01 |
| observed_status | normal | SQLSTATE 40P01 |
| observed_status | observed | SQLSTATE 40P01 |

Результат: **4 failed in 3.58s** (6 предупреждений библиотек).
В каждой диагностике реальные операции вернули `[None, None]`, однако
handoff поймал 40P01 внутри биллинга: A=`in_delivery`, B=`cancelled`, остаток
11 вместо исходных 12, резервы пусты, начисление A **0 вместо 1800**.
Тест падает на сохранённой проверке SQL errors раньше структурного условия.
Таким образом, ошибка старого продукта по-прежнему обнаруживается после
коррекции ложного требования к реализации. GREEN на новом продукте этим
тестировщиком не заявляется; разработчик должен исполнить все последующие
бизнес-проверки на своём исправленном SHA.
