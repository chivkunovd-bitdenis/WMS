# WMS-396: подтверждена прежняя живая проверка ЧЗ без токена

09.09.2026 повторно прочитаны исходные вызовы инструментов и их результаты из локального журнала сессии `c00aad3b-56f1-4fb8-808c-5a3d18b0bbb8`. Это проверка сохранённого свидетельства; новых запросов к ЧЗ, изменений приложения и тестовых запусков не было.

## Что действительно произошло 08.09

В **12:01:41–12:01:42 UTC (15:01 МСК)** локальный macOS shell выполнил `curl` POST в `https://mobile.api.crpt.ru/mobile/check`. В явных заголовках был только `Content-Type: application/json`, авторизации и токена в команде нет. Тело содержало полный код с GS-разделителями. Вызов шёл с Mac: в этой команде нет SSH или контейнерного запуска curl.

Сохранённый результат показывает два разных ответа настоящего сервиса:

| Проверяемый случай | outerStatus | checkResult | status | codeResolveData.verified |
|---|---|---|---|---|
| Ранее отклонённый код | APPLIED | false | wrong | true |
| Ранее принятый контрольный код | INTRODUCED | true | ok | true |

В **12:02:08–12:02:20 UTC** отдельный цикл проверил десять ранее отклонённых кодов: все десять вернули `APPLIED`, `checkResult=false`, `verified=true`. Коды читались из production для этой исторической проверки, но сами HTTP-вызовы выполнялись локальным curl после чтения. Это реальные сетевые ответы, а не заглушки автотестов.

Исходный файл: `~/.claude/projects/-Users-deniscivkunov-Projects-WMS/c00aad3b-56f1-4fb8-808c-5a3d18b0bbb8.jsonl`, строки **1299/1303** (сравнение) и **1307/1308** (десять кодов). [Обезличенная выписка](wms396-public-api-live-proof-20260909.json) содержит временные метки, UUID и SHA256 исходных строк для повторной сверки. Полные КИЗ, их части/криптохвосты, номера заказов, данные товаров и импортёров не перенесены.

Команды этой серии не сохраняли числовой HTTP-статус: доказан успешно разобранный содержательный JSON, включая положительный ответ, но приписывать именно этой серии HTTP200 нельзя. Отдельный документ [исследования контракта](wms396-contract-20260908.md) фиксирует HTTP200 на синтетический несуществующий код; это другое наблюдение.

## Что исправлено в выводе

Последующие два HTTP451 из staging/production на искусственный код не отменяют предыдущий успех с Mac и **не доказывают необходимость токена для mobile/check**. Причина этих отказов не установлена; запросы выполнялись из других сред и с другим входом. Ни региональную причину, ни изменение доступа этим сравнением не устанавливаем.

Требование токена в выпущенной реализации появилось при замене mobile/check на True API: коммит `5457d187`, выпущенный в `40b722a4`. В `backend/app/services/inbound_marking_service.py` job получает seller cz_token; `backend/app/services/true_api_marking_check.py:152` при его отсутствии сразу возвращает `unavailable`, а `:139` передаёт Bearer при вызове `/cises/info` и `/cises/check`. Поэтому текущая ошибка «У селлера не настроен токен» объясняется выбранной реализацией, а не доказанным новым требованием прежнего публичного endpoint.

Историческая положительная проверка подтверждена. Успешный полный сценарий приёмки через нынешний production True API этим свидетельством не подтверждён; WMS-396 остаётся частичной. Нового выбора реализации этот документ не делает.
