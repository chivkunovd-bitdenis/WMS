# WMS-669 · Передача независимого тестового контракта

Тестировщик работает по прямому поручению владельца без навыков и вложенных
агентов. Вход — опубликованная постановка
`b64f9cb73c9eecc16ecfc0e73d0b3f563bf220d6`; `origin/etalon` обновлён и его
AGENTS.md прочитан на `0f1460b023700a99f17b504d6af3934a02bc68cc`.
Это тесты до продуктового кода. R1–R9 и классы C1–C11 не переопределены.
Оба поведения подтверждены: пересечение фильтров и видимые группы.

## Зафиксированный интерфейс

Расширяются только существующие `/seller-catalog/page` и `/seller-catalog/keys`:
`article` и `size` — необязательные строки, `stock_only` — boolean с исходным
значением false, `group_by` — необязательное `category_article_size`.
Экран передаёт последнее значение постоянно; остальные потребители могут
сохранить прежний порядок. Пустые новые условия не меняют прежний набор.
Все фильтры применяются до SQL LIMIT/OFFSET; ключи — прежние уникальные строки.
Форма товарной строки остаётся прежней, группы создаются из её известных полей.
Для полностью зарезервированного товара применяется quantity > 0,
а не available, лимит оператора или подтверждённое опубликованное количество.

## Файлы и покрытие

[Постоянные API-проверки](../../backend/tests/test_wms669_seller_catalog_contract.py)
используют HTTP через ASGITransport (вызов настоящего приложения без сетевого
порта), настоящие проверки прав, SQL и существующие сервисы. Общая
[подготовка данных](../../backend/tests/wms669_catalog_fixtures.py) создаёт только
тестовые организации, магазины, пользователей и балансы с валидными связями.
В ней две организации, два селлера внутри первой, два склада с сортировкой,
ячейкой и тарой; quantity 4 с настоящей FBS-бронью 4; положительный остаток
при лимите/публикации 0; quantity 0 при лимите/публикации 999; -1, отсутствие
баланса и +5/-5; карточки WB 46/48 с fallback wbSize и Ozon offer id.
Связанный с двумя площадками товар остаётся одной строкой. Соединения PostgreSQL
освобождаются после теста до закрытия его asyncio loop; общая conftest не менялась.

- C1: `test_c1_intersection_and_exact_article_size`,
  `test_c1_each_endpoint_filters_exact_values` (page и keys независимо),
  `test_c1_control_empty_filters_keep_previous_catalog`.
- C2: `test_c2_quantity_not_free_limit_or_published` проверяет через summary
  исходные 4/4/0, через page — публикацию 0 и 999, затем ожидаемый stock-only.
- C3: `test_c3_aggregate_before_limit_offset`: сумма двух складов/мест,
  отсутствие положительности у +5/-5 и нахождение товара вне первой страницы.
- C4: `test_c4_server_order_and_unique_rows_across_pages`,
  `test_c4_control_variants_keep_identity_name_color_and_separate_stock`:
  порядок категория/артикул/размер/ключ, отдельные строки, цвета и числа,
  уникальность страниц и отсутствие удвоения WB/Ozon.
- C5: `test_c5_imported_size_membership_fallback_and_ozon_offer`,
  `test_c5_each_endpoint_imported_sizes_and_offer_id` (page/keys отдельно),
  `test_c5_control_missing_values_are_not_guessed`.
- C9: `test_c9_scope_parity_and_summary` для Все/WB/Ozon,

  `test_c9_control_permissions_and_shop_switch`: чужие ключи/остатки не видны,

[Разовые C10](../../backend/tests/test_wms669_seller_catalog_once.py) хранятся
отдельно от постоянного файла. `test_c10_reading_has_no_writes` сравнивает все
строки всех таблиц тестовой БД до и после чтения page/keys, включая карточки,
балансы, резервы, лимиты и опубликованные состояния.
`test_c10_postgresql_json_sizes_and_stock` выполняет настоящее чтение JSON
размеров и сочетание stock-only на PostgreSQL. В SQLite он явно пропускается;
это не засчитывается как PostgreSQL-доказательство.

[Постоянные DOM-проверки](../../frontend/src/screens/v2/Wms669SellerCatalog.dom.test.tsx)
монтируют настоящий React-компонент. Подменён HTTP, не компонент и не функции
группировки/отбора. По C6 каждый новый фильтр меняется со второй страницы при
остальных активных условиях; проверяются offset=0, параметры и новая строка.
C4/C7 проверяют три уровня подзаголовков, запрет выбора заголовков, оригинальные
строки, остатки и действия, повтор контекста на второй странице.
C5 проверяет «Без категории/артикула/размера» и одну карточку набора «46, 48».
C7 сохраняет выбор через страницы и фильтр, а массовое действие получает только
исходные product IDs. C8 отдельно проверяет поздний ответ нового поля,
старого поиска, старого селлера для page и summary, а также отсутствие прежних
строк/чисел, пока новый магазин ещё загружается. Mock намеренно не исполняет
AbortSignal: корректность должна сохраняться и после прихода такого ответа.

## Воспроизведение

Из backend, в окружении с установленными dev-зависимостями:

```sh
python -m pytest -n 2 tests/test_wms669_seller_catalog_contract.py tests/test_wms669_seller_catalog_once.py tests/test_wms548_seller_catalog_page.py tests/test_seller_wb_catalog_isolation.py -q --tb=short
```

SQLite создаётся существующей conftest отдельно на каждый worker. Для PostgreSQL
использован собственный временный кластер PostgreSQL 17 на loopback-порту 56669
и база `wms_test_669_contract`. Кластер использует локальную тестовую trust-auth,
не сохранённые ключи/пароли. Это не порт приложения и не общий стенд.
Для воспроизведения нужен свой изолированный loopback/CI PostgreSQL с базой,
начинающейся на `wms_test`; conftest очищает её между тестами.

```sh
WMS_TEST_DATABASE_URL=postgresql+asyncpg://wms669_test@127.0.0.1:56669/wms_test_669_contract python -m pytest tests/test_wms669_seller_catalog_contract.py tests/test_wms669_seller_catalog_once.py -q --tb=short
```

Из frontend:

```sh
npm run test:unit -- src/screens/v2/Wms669SellerCatalog.dom.test.tsx src/screens/v2/SellerCatalogAsync.dom.test.tsx
npx tsc --noEmit -p tsconfig.app.json
npm run build
```

## Доказательство до реализации

Проверки выполнены на исходном продуктовом коде `b64f9cb73`. В сохранённых
журналах убраны только хвостовые пробелы и пустые строки в конце файла:

- SQLite, новые тесты и два прежних контрольных файла: **20 FAILED,
  16 PASSED, 1 SKIPPED**. Из 16 успешных 10 — новые контрольные сценарии,
  6 — неизменённые прежние тесты. SKIPPED — только явно PostgreSQL-проверка C10.
  [Полный журнал](WMS-669-test-evidence/sqlite-red.log).
- Собственный PostgreSQL 17, все новые API-тесты: **21 FAILED, 10 PASSED**,
  без ERROR/SKIPPED. Дополнительный FAILED — C10 на настоящем PostgreSQL.
  [Полный журнал](WMS-669-test-evidence/postgresql-red.log).
- Настоящий компонент в DOM и прежний `SellerCatalogAsync.dom.test.tsx`:
  **8 FAILED, 24 PASSED**. Новые — 8 FAILED/4 PASSED; прежние — 20 PASSED.
  [Полный журнал](WMS-669-test-evidence/dom-red.log).
- Полный `ruff check .` — PASS, `mypy .` — PASS (551 файл).
  `npx eslint src/screens/v2/Wms669SellerCatalog.dom.test.tsx` — PASS.
  `npx tsc --noEmit -p tsconfig.app.json` и `npm run build` — PASS.
  Сборка сообщает только обычное предупреждение о крупных JS-бандлах.

API возвращает 200, но игнорирует новые условия: в page/keys остаются лишние
товары, карточки 148/без размера и позиции с нулевым/отрицательным остатком.
C3 получает прежнюю первую строку вместо положительного товара вне первой
страницы. C4 видит SKU-порядок вместо порядка категории/артикула/размера.
Это assertion failures по бизнес-выдаче, не ошибки загрузки фикстуры.

DOM-контракт показывает отсутствие новых полей и подзаголовков. Отдельный C8
через уже существующий поиск доходит до двух ответов: сначала показан
`Пуховик current`, затем после позднего старого ответа появляется
`Пуховик stale`. Транспорт намеренно игнорирует отмену — экран обязан проверить
актуальность ответа перед применением. Смена магазина существующим новым
токеном и очистка прежних строк/чисел проходят в контрольных сценариях.
Ошибки первоначальной подготовки данных и пула asyncpg были исправлены в новых
тестовых файлах до фиксации контракта; они не являются доказательством RED.
Доказательство относится только к assertion failures бизнес-ожиданий.

## Граница передачи

После отдельного коммита `WMS-669: контракт тестов` и публикации ветки разработчик
может реализовать R1–R9. Ожидания, набор тестов и охрана не меняются разработчиком.
Приёмку делает аналитик после реализации и перекрёстного ревью; затем нужен CI
точного итогового SHA. C11 остаётся ручным, не проведённым сценарным сравнением
авторизованного экрана. DOM/jsdom не проверяет геометрию и читабельность в браузере.

Продуктовые файлы, старые тесты, guards и MANIFEST не менялись. Production,
стенд, Telegram, реальные кабинеты и секреты не использовались. Merge в main,
деплой, продуктовая приёмка и включение постоянной охраны здесь не выполняются.
