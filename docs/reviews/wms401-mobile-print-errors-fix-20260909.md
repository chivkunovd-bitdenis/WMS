# WMS-401 — reject incomplete KIZ print tapes before preview

The printing response already includes per-order `order_errors` with `order_id`, `wb_order_id`, `code` and `message`. The mobile DTO discarded that field. When QR assets were available, `failed=0` could coexist with a marking error and an absent order row; the mobile code then fetched the QR separately and silently omitted the marking code. The analysis supplied by opus_resume identified this exact path and the existing operator-code print restriction. No printing API was invoked again for diagnosis.

Mobile commit `7bb418103819e5d823627bd30408d2344c4ac554`, based on `30d8e52c656296cb71a2e315a80d1268d1b382cc`, adds the existing error array to the mobile response DTO and validates it before generating pages or fetching label assets. `operator_kiz_print_forbidden` is displayed as “WB <номер>: Печать введённого оператором кода ЧЗ запрещена.” Other human-readable server messages retain their order number. An unknown machine-only message receives a generic human-readable failure. A missing requested tape/workspace order is also an explicit failure when KIZ copies were requested. The failed tape is discarded so a retry reads a fresh result. QR-only printing retains the existing print-assets path and does not request a KIZ tape.

The final targeted run passed 23/23: 20 ViewModel tests and 3 transport-contract tests. The new transport case verifies that `order_errors` survives the real generated HTTP conversion even with zero counters. ViewModel regressions verify that a partial tape never opens a preview, a retry fetches fresh data, an omitted requested row cannot fall back to QR-only success, and QR-only printing still produces a document without calling the KIZ printing endpoint. The QR-only test initially used an incorrect text/plain image fixture; it was corrected to PNG and uses the JVM Base64 encoder in place of Android's unit-test stub. No production behavior was changed for that test correction.

The final build completed successfully and produced one new APK after the fix: `/Users/deniscivkunov/Projects/WMS/outputs/wms401-android-20260909/WMS-TSD-FBS-7bb4181-debug.apk`, SHA256 `0a3517d66501246a2d99ca9171c126e41a0666986faf7ac2d7498139225d8ef8`, 45,350,978 bytes. Inspection of the actual APK DEX confirms the new error DTO and the human-readable operator error string are present. `apksigner` verified the same existing Android Debug certificate SHA256 `e343ab0cccc6284b271a72da42a67b14a0f0893d92b9ca461f1cac3d0be1aeb6`.

No dependency, backend rule, stock operation or web frontend was changed. No new Opus run was started. The local mobile source is committed and clean; its full Git history is not published. The APK was handed to mobile_resume for the actual refusal-without-preview, pool-code tape and QR-only checks. The author did not operate the AVD, and final APK acceptance remains with that separate run.
