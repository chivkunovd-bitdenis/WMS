# WMS-402 — минимальный контракт локальной печати, 09.09.2026

Это проектирование по текущему коду, а не работающая печать. Исходники сервера
прочитаны на `c7c19adf9ebb223b5663deb4ad50b585d93ce706`, мобильные — на
`dfcb7624216a6bb26bae1641357d4145764b85cf` в существующем мобильном worktree.
Постановка сверена с WMS-402 в каноническом бэклоге рабочего дерева
`wms396-stage`. Приложение, настройки, ключи и данные не менялись; сеть склада,
компьютер клиента и физический принтер не проверялись. Тесты не запускались.

Минимальный вариант: оператор на ТСД выбирает заранее разрешённую очередь
принтера склада. WMS сохраняет задание, а установленный на компьютере склада
агент сам получает его по исходящему HTTPS и передаёт файл в очередь печати ОС.
Для этого не нужен входящий доступ к LAN или туннель: обе стороны обмена с
облаком инициирует агент. Такой вариант требует у компьютера исходящего доступа
к WMS; фактическую доступность ещё предстоит проверить. Облачный браузер не
получает возможность обнаруживать устройства внутри склада.

## Как оператор выбирает принтер

Нужна устойчивая привязка: арендатор → склад → понятное имя принтера →
идентичность разрешённого агента → точное имя очереди ОС. WMS возвращает ТСД
только разрешённые привязки его склада. При отправке сервер заново проверяет
права оператора, принадлежность файла и связь заказа/поставки со складом;
присланному клиентом `warehouse_id` нельзя просто доверять. Агент получает
только задания своей привязки, а не все задания арендатора.

Агент на компьютере может сообщать установленные очереди ОС по своему
исходящему соединению; уполномоченный пользователь явно выбирает нужную.
Это не сканирование всей сети. В первом срезе принтер должен уже работать в ОС
компьютера; установка драйвера, выбор протокола термопринтера и разрешения ОС
зависят от ещё неизвестного клиентского оборудования. Удалённая настройка
назначения очереди через WMS не равна удалённой установке любого драйвера.

У существующих `Tenant` и `Warehouse` такой привязки нет.
`tenant_settings_service.py:12–17,59–72` хранит конкретные настройки в колонках
Tenant, а не универсальный JSON-конфиг. `PrintTemplate.layout_json` описывает
макет, не разрешённое устройство. Хранить постоянную конфигурацию принтера в
случайном завершённом BackgroundJob означало бы смешать назначение и задание.

**Решение владельца перед реализацией:** разрешить одну минимальную логическую
привязку конечной точки печати со перечисленными полями и возможностью отозвать
доступ агента. Отдельные сущности попыток, сессий и истории печати не нужны.
Новая таблица не доказана как единственный способ хранения: для одного
принтера склада достаточно конфигурации в существующем Warehouse; для нескольких
разрешённых очередей отдельная компактная запись удобнее, но это уже выбор
владельца. В этом документе ни схема хранения, ни выпуск учётных данных не
утверждены. Без такой привязки можно сделать только заранее настроенный на
один принтер прототип; это ещё не встроенная настройка принтеров через WMS.

## Предлагаемый обмен — этих операций агента пока нет

Названия ниже обозначают контракт, а не существующие URL. Реализация должна
использовать выделенные маршруты печати, не расширять доступ агента ко всему API.

| Операция | Минимальный контракт |
| --- | --- |
| Список принтеров для ТСД | Разрешённые привязки склада: ID и имя. Сетевые адреса и произвольные команды клиент не присылает. |
| Создать задание | UUID намерения, ID привязки, ID одного готового файла, число копий. Сервер сохраняет неизменяемый payload с проверенными checksum, типом и размерами, warehouse и автором. |
| Агент получает следующее | Только `pending` своей привязки. Короткая атомарная операция переводит одну строку в `running` и фиксирует `started_at` до возврата файла/метаданных. Два параллельных запроса не получают разрешение выполнить одну строку дважды. |
| Получить содержимое | Только файл назначенного этому агенту задания; повторно проверяется доступ и checksum. Смена или недоступность файла — явная ошибка, не получение новой этикетки из WB. Произвольных URL, путей и команд в payload нет. |
| Подтвердить передачу | ID задания и квитанция очереди ОС в `result_json`; повтор того же подтверждения возвращает тот же результат. Противоречащее подтверждение отклоняется. |
| Посмотреть результат на ТСД | Существующий job UUID и понятный результат доставки. Он не меняет подбор, упаковку, метаданные WB, остатки или доступность вкладок. |

Для первого среза одно задание содержит **один готовый файл**; последовательность
выбранных файлов создаёт отдельные задания с отдельными сохранёнными UUID.
Это исключает ложное «всё не напечатано», если в многофайловой операции первая
этикетка уже передана, а следующая не передалась. Отдельной сущности партии нет.
Формат запроса можно сразу ограничить одним asset, не вводя режимы обработки.
Полученный файл агент проверяет до вызова ОС. Поддержка его content type и
размера должна быть проверена выбранным адаптером ОС; отправлять неизвестный
PDF/PNG как произвольные байты в порт термопринтера нельзя.

## Повтор запроса и неопределённый физический результат

ТСД создаёт UUID один раз на явное нажатие печати и сохраняет его до разрешения
результата запроса, включая перезапуск приложения. Повтор HTTP использует тот же
UUID — существующий первичный ключ BackgroundJob может обеспечить уникальность
без нового счётчика. При конфликте вставки сервер сверяет tenant, тип, автора
и неизменяемый payload. То же намерение возвращает прежнее задание; изменённое
содержимое с тем же UUID отклоняется. Чужой UUID не раскрывает чужое задание.
Намеренная повторная печать получает новый UUID после явного действия оператора.
Срок хранения заданий должен покрывать допустимый срок повтора; удаление записи
и повторное принятие того же UUID не сохраняют эту гарантию.

Это защищает очередь WMS от дубля HTTP. Между транзакцией WMS и физической
печатью общей транзакции нет. Поэтому здесь не обещается «ровно одна физическая
печать при любом сбое»:

- `pending` означает «ожидает получения агентом». Отключённый агент не удаляет
  задание и не переводит его в успех.
- `running` означает «выдано агенту, конечного подтверждения нет». Если ответ
  получения потерян, процесс упал или связь исчезла после вызова ОС, задание
  **не возвращается автоматически в pending** и не выдаётся на печать снова.
  Даже если бумага фактически ещё не печаталась, сервер не угадывает это.
- `done` означает только «очередь ОС подтвердила приём», с её квитанцией.
  Пользовательская надпись — «Передано в очередь принтера», не «Напечатано».
  Отсутствие бумаги, замятие или последующая ошибка устройства этим не исключены.
- `failed` допустим, когда агент достоверно не передал задание в ОС: например,
  проверка файла завершилась ошибкой до отправки. Сбой во время передачи,
  при котором приём неизвестен, остаётся `running` без конечной квитанции.
  Истечение времени само по себе не доказывает, что печати не было.

Агент выполняет только свежевыданное задание один раз. Он может повторять
отправку уже полученной квитанции, но не повторяет отправку файла в ОС ради
восстановления подтверждения. После перезапуска он не исполняет сохранённые
`running` заново. Доступ к перечню своих незавершённых заданий нужен для
диагностики, не для автоматического воспроизведения. Если конкретная очередь
ОС допускает надёжный поиск квитанции по job UUID, можно подтвердить ранее
принятое задание; отсутствие записи в очереди не доказывает отсутствие печати.

На ТСД такой случай показывается как «Подтверждение не получено; результат
печати неизвестен». Оператор проверяет принтер и сам решает, требуется ли
новая печать с новым UUID. Возможность дубликата при таком решении сохраняется.
Новый статус БД и отдельный журнал попыток для этой консервативной схемы не
нужны. Изменение назначения принтера не должно незаметно перенаправлять уже
выданные задания: адресат зафиксирован в payload, новый выбор относится к новым
намерениям печати.

## Что можно сделать следующим вертикальным срезом

После решения о хранении привязки и узком доступе агента можно реализовать
выбор одного назначенного принтера на ТСД, создание задания готового asset,
получение/подтверждение локальным агентом и просмотр результата. Основу составят
нынешние модели, без новой таблицы заданий и без новых складских операций.
Проверяемые программно границы: повтор создания, конкурентное получение,
изоляция арендаторов/складов/агентов, checksum и потеря подтверждения без
повторной отправки. В этой работе такие проверки не запускались.

Для фактической приёмки всё ещё нужны ОС клиентского компьютера, установленная
очередь, модель принтера, доступ локального агента и бумажная этикетка: правильный
размер, читаемый код, поведение при отключении принтера и обрыве связи. Ни
системный диалог Android, ни ответ облака, ни квитанция ОС по отдельности не
доказывают эти результаты. Полная лента с маркировкой и встроенная установка
драйверов не выдаются за закрытые этим первым срезом требования.
