## F1 — P1: запрет проверяется отдельно от захвата на отправку

Место: `tools/support_agent/support_agent/telegram.py:297–302`,
`tools/support_agent/support_agent/store.py:468–490,520–526`.

`flush_outbox` сначала вызывает `outbox_delivery_allowed`, затем отдельно
`claim_outbox`. Между ними нет общей транзакции. `claim_outbox` проверяет только
`status='pending'`; пауза, источник разрешения и версия обращения уже не проверяются.
Операторский CLI пишет через другое SQLite-соединение, поэтому его успешная
транзакция может завершиться именно в этом промежутке. После её завершения
dispatcher переводит строку в sending и отправляет запрещённый ответ.

На точном SHA выполнены три детерминированных воспроизведения через два Store
одной синтетической БД. Смена состояния вставлена непосредственно перед
настоящим вызовом claim_outbox, то есть после настоящей проверки разрешения.
Это управляемое воспроизведение допустимого порядка операций двух процессов,
не имитация отказа самого guard:

1. В очереди обычный ответ, паузы ещё нет. Проверка проходит; второе соединение
   вызывает pause_client_replies и **завершает транзакцию**; затем настоящий
   claim_outbox проходит. Записывающий двойник Telegram получает ответ клиенту.
2. Пауза установлена, новый ответ имеет точное разрешение. После проверки
   второе соединение меняет текст источника на отзыв и revision на 2.
   Захват и отправка всё равно происходят.
3. При тех же условиях второе соединение меняет текущую версию обращения
   с v1 на v2. Ответ, одобренный для v1, всё равно отправляется.

Во всех трёх случаях фактически получено `flush_outbox == 1` и одна клиентская
отправка. Ожидание по R10/R11 — ноль отправок, поскольку запрещающее изменение
уже сохранено **до захвата строки и до внешнего действия**. Это не требование
отозвать уже ушедший сетевой запрос и не неопределённость продукта.

Минимальное направление исправления: объединить актуальное чтение строки,
проверку паузы/точного разрешения и переход pending → sending в одну короткую
операцию с транзакционной защитой SQLite, общей для разных соединений.
Один Python-lock или ещё одна отдельная проверка оставят гонку. Не требуется
новая таблица, режим или большой механизм авторизации. Границу уже начавшейся
отправки и неизвестного внешнего результата сохранить; не возвращать такой
результат в автоматическую повторную отправку. Исполнитель должен закрепить
три описанных порядка операций отдельными проверками и передать новый SHA.

### Воспроизведение F1 без изменения тестовых файлов

Из корня checkout, с `PYTHONPATH=tools/support_agent`, выполнить следующий Python
код. Он использует существующую синтетическую fixture, временную БД и
RecordingTelegram; сети, конфигурационных файлов и рабочей базы здесь нет.

```python
from pathlib import Path
from tempfile import TemporaryDirectory
from tests.test_owner_client_reply_pause import paused, CLIENT_CHAT, OWNER_CHAT, OWNER_ID
from tests.test_owner_client_reply_pause_cli import _source
from support_agent.store import Store
from support_agent.telegram import flush_outbox

for change in ("pause", "source_revision", "ticket_version"):
    with TemporaryDirectory(prefix="wms676-review-") as folder:
        fixture = paused.__wrapped__(Path(folder))
        e = next(fixture)
        other = Store(e.path)
        try:
            if change == "pause":
                e.store.execute("DELETE FROM kv WHERE key=?",
                    (f"owner_client_reply_pause:{CLIENT_CHAT}",))
                e.store.queue_message(key="queued-before-pause",
                    chat_id=CLIENT_CHAT, text="Old queued answer")
            else:
                body = "Конкретный проверенный ответ"
                source = _source(e, e.store.client_reply_approval_text(
                    CLIENT_CHAT, e.ticket, "v1", body))
                e.store.approve_client_reply(chat_id=CLIENT_CHAT,
                    ticket_id=e.ticket, version="v1", text=body,
                    owner_user_id=OWNER_ID, owner_chat_id=OWNER_CHAT,
                    source_message_id=source)
            original_claim = e.store.claim_outbox

            def interleave(outbox_id):
                if change == "pause":
                    other.pause_client_replies(chat_id=CLIENT_CHAT,
                        ticket_ids=[e.ticket], owner_user_id=OWNER_ID,
                        source_message_id=e.source)
                elif change == "source_revision":
                    other.set_message(source, text="Разрешение отозвано", revision=2)
                else:
                    other.patch_data(e.ticket, agent={"version": "v2"})
                return original_claim(outbox_id)

            e.store.claim_outbox = interleave
            sent = flush_outbox(e.store, e.tg, e.cfg)
            # Это проверка воспроизведения дефекта; исправленный код должен дать 0.
            assert sent == 1 and len(e.tg.sent) == 1
            print(change, "REPRODUCED forbidden send")
        finally:
            other.db.close()
            fixture.close()
```

```sh
  tools/support_agent/tests/test_owner_client_reply_pause_cli.py
```

Git diff подтвердил побитовое отсутствие изменений frozen-файла и требований
между d13dfa1f и b1e3b7dd. Исторические шесть RED на d13dfa1f взяты из переданного
контракта; отдельный повтор старого кода здесь не запускался. Заявленные
исполнителем 41 соседний PASS и ruff/mypy четырёх модулей повторно не запускались
и не выдаются за независимый результат этой сессии. `git diff --check` проходит.

Пауза хранится в существующем kv точного чата. При уже сохранённой паузе оба
process reply и обычный queue_reply запрещены до enqueue. Старая очередь,
файлы, финальные ответы, notice и строки без ticket_id подавляются. После
перезапуска и истечения времени запрет остаётся. Другой чат и приватный канал
владельца работают. История и анализ сохраняются. Новых сущностей, изменений
jobs/tickets/config или массового снятия запрета в diff нет.

Операторский pause-client-replies доверяет оператору в интерпретации смысла
сообщения, но проверяет происхождение: Telegram, реальный owner_user_id, точный
чат источника и принадлежность перечисленных обращений. Поэтому source 333
нельзя использовать для произвольного чужого чата. В рамках переданного
верифицированного запрета 333/470 это соответствует R9; автоматического
распознавания запрета по произвольному тексту контракт не требует.

Для approve-client-reply такого доверия к одному нажатию CLI нет: проверяется
точная фраза разрешения с chat_id, ticket_id, текущей версией и полным телом
ответа. Записываются ключ новой строки и revision источника. Общий owner-флаг,
более поздний номер сообщения, семантическое approved или прежний final не
разрешают отправку. Чужой автор/чат, другое тело/обращение/версия и старый
источник отклоняются. Повтор команды не создаёт новый ответ; пауза остаётся.

Дополнительный отрицательный сценарий выполнен через **настоящий main CLI**
с подменой только загрузки конфигурации на синтетическую: источник паузы
перенумерован в 333/msg470, новое сообщение настоящего владельца записано
как 334/msg473 с текстом «Сначала анализируй и сообщай гипотезы владельцу».
Произвольное тело финального ответа передано в approve-client-reply.
Получены код 1 и `specific_owner_reply_approval_required`, очередь пуста.
Это синтетическое воплощение смысла переданного отрицательного примера,
не новая проверка или дословная выгрузка живого сообщения.

До начала flush изменения source/revision, тела, версии и новая пауза
корректно запрещают отправку — это покрывают четыре новые проверки. F1
относится именно к изменению между проверкой и захватом, которого они не покрывают.

Отдельно синтетически проверены unknown и прерванный sending: после открытия
нового Store, recover_after_restart, повторного approve_client_reply с тем же
источником и двух flush клиент получает **ноль** повторных сообщений; строка
остаётся unknown. При заведомом not_sent строка остаётся pending и после
перезапуска отправляется **один** раз, последующий flush не дублирует её.
Эта защита существующего outbox сохранена.
