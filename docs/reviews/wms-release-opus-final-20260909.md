## По каждой из пяти находок

**1. Поздний Ozon undo после списания + окно между HTTP-чекпоинтами.** Закрыто в коде. Дефект был в том, что `undo_pick`/`scan_pick_product`/`set_pick_quantity` для Ozon не сериализовались с уже состоявшейся передачей и не видели её через операцию. Правка стоит в трёх местах одновременно:

- `_load_supply(..., for_update=True)` (`fbs_picking_service.py:1506–1533`) берёт `SELECT ... FOR UPDATE` и `populate_existing`, поэтому клиент, который загрузил старую поставку до чекпоинта, после ожидания читает свежую строку.
- `_ensure_ozon_pick_editable` (`fbs_picking_service.py:1536–1568`) под этой блокировкой отказывает при `delivered_at IS NOT NULL`, `status ∈ {in_delivery, done}`, любой существующей операции доставки в состояниях `confirmed`, `pending`, `pending_confirmation`, а также при `carriage_create_started`, `carriage_id`, `carriage_approved`, `used_fallback`, взятых из сохранённого `ozon_handoff_progress`. Идемпотентный повтор (`undo_pick:1283–1305`, `scan_pick_product:928–930,948–958`) возвращает workspace без прохода через guard — это чтение, не движение.
- `_finish_ozon_delivery` (`fbs_shipment_service.py:2131–2178`) после внешних чекпоинтов заново берёт `refresh(supply, with_for_update=True)` под `no_autoflush`, затем `_supply_orders_stmt(...).with_for_update().execution_options(populate_existing=True)`. Порядок `поставка → заказы` совпадает с отменой и упаковкой; никакой обратной последовательности не заведено.
- Дополнительно `ozon_fbs_process_service.py:1104–1128` очищает `state.carriage_create_started` и сохраняет снимок при явных отказах `400/401/403/422/429` и в create, и в fallback; для `503`/таймаута/иной неопределённости marker намеренно сохраняется. Guard видит очищенный marker и разрешает undo, старый снимок из production `9729c52c` (проверка root 22:49:23 UTC — 0 rows) новыми правилами не блокируется, автоочистки неопределённого 503 в код не занесено.

Внутри `_configure_seller_warehouse` (`523–640`) на переходе `ON → OFF` (`613–620`) вызывается `_clear_previous_ozon_stock` **до** любой записи флагов и `session.commit()`. При отказе Ozon (`_clear_previous_ozon_stock:347–366`) поднимается `FbsWarehouseBindingError("ozon_stock_cleanup_failed")`, привязка остаётся `stock_sync_enabled=True`, mapper в `api/fbs_sellers.py:179–180` возвращает HTTP 502. Обёртка `configure_fbs_seller_warehouse:302–316` теперь запоминает `publication_was_on` только для WB и не делает пост-commit очистки для Ozon; тот же ветка `upsert_binding` (`_upsert_binding:422–427`) больше не требует `existing.served` для очистки, поэтому вход через `/warehouse-bindings/…` (`api/fbs_sellers.py:393–411`) больше не пропускает финальный ноль для непубликуемого-но-обслуживаемого склада. **3. FROM tenants WHERE id = ? FOR UPDATE ... populate_existing` (`198–201`) и `SELECT ... FROM subscription_payments WHERE id IN (results) AND status IN (_PENDING_STATUSES) FOR UPDATE ... populate_existing` (`202–209`). `extend_paid_until` применяется только к строкам, которые ещё pending — если конкурент уже перевёл платёж в `succeeded`, он выпадет из `pending` и не будет учтён снова. `test_overlapping_payment_sync_preserves_both_paid_months` воспроизводит именно последовательность «A пауза на P1 → появление P2 → B применяет P1+P2 → A возвращается»; после исправления `paid_until = initial + 60 дней`, оба платежа `succeeded`, поздний A возвращает `activated=False`, HTTP GET у обеих сессий проверяется вне транзакции (`http_transactions == [False, False, False]`).

**4. ## Есть ли новый достижимый блокирующий дефект именно из дельты

**Не найден.**

Проверил все входы, которые дельта затрагивает, и вокруг них — реальные вызывающие функции:

- `session.get(User, ..., with_for_update=True, populate_existing=True)` — стандартный SQLAlchemy 2.0 API; kwargs корректны, поведение подтверждено тестом; SQLite ветка тестом skip.
- Advisory-lock под Ozon через отдельный `AsyncSession(bind=session.bind)` — так уже устроен `upsert_binding` (`fbs_warehouse_binding_service.py:271–286`); новых порядков блокировок не введено. HTTP-обнуление живёт **внутри** row-lock и advisory-lock — это тот же профиль, что и раньше у Ozon-пути, а не новое удержание.
- Порядок блокировок в `_finish_ozon_delivery` (`fbs_shipment_service.py:2144–2150`) `поставка → заказы` совпадает с уже существующими путями отмены и упаковки. Пикинг тоже начинает с поставки. Взаимной блокировки не возникает.
- `sync_pending_payment` теперь коммитит перед HTTP; сессия, которую отдаёт `Depends(get_db)`, использует `expire_on_commit=False`, поэтому `session.execute` после `commit()` штатно начинает новую транзакцию. Ошибку HTTP `SubscriptionPaymentError` route ловит и превращает в HTTP-ответ; висящих транзакций не остаётся. `SubscriptionPayment.id.in_(results)` итерирует ключи dict, что валидно для SQLAlchemy.
- `_ensure_ozon_pick_editable` вызывается только в изменяющих подбор путях (`scan_pick_product`, `set_pick_quantity`, `undo_pick`); в чтении workspace и ветке идемпотентного повтора guard не участвует. Никакой навигационной блокировки вкладок сюда не занесено, правила `assembling → picking` не восстановлено.
- Фронтовый `endsWith('/set-password')` использует только `location.pathname`, поэтому query-строка на решение не влияет; для нестандартного пути (`/foo/set-password`) откроется публичный экран, но без валидной подписи в токене API отклонит — риска обхода нет.
- Очистка `carriage_create_started` строго ограничена явными отказами `{400, 401, 403, 422, 429}`; для `503`/`None` и любого другого кода marker сохраняется. Автоочистки старых снимков в БД дельта не выполняет и обосновано полагается на актуальный `state`, а SQL-снимок production `9729c52c` от 2026-09-08 22:49:23 UTC показывает 0 таких строк; выдумывать массовую разблокировку исторических операций я и не должен.

Отсутствие живого положительного ответа — внешняя функциональная неготовность, а не свойство кода этого выпуска; ослаблять `interpret_check` под 451 не следует.

- **Живой Ozon.** Синтетический контур stage для многопозиционной Ozon-поставки не собран; правки Ozon проверены через `FakeMarketplaceTransport` и PostgreSQL-конкуренцию, а не через реальный кабинет.

- **Полный `pytest -n auto`.** Отчёты фиксируют целевые прогоны (52 Ozon PostgreSQL, 9 payment PostgreSQL, 8 auth PostgreSQL, 33+7 publication SQLite/PG), а также общий CI `34287539602` для Ruff/mypy/фронта; полный pytest в момент чтения ещё шёл.
