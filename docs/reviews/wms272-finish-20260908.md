# WMS-272: освобождение соединения при создании поставки WB

База ветки: `693ac992bd7df7a73c90a50c6682658b7a234908`.
Рабочая ветка: `codex/wms272-finish`. Проверка выполнена 08.09.2026.

## Причина и изменение

Первоначальный `create_supply_from_orders` удерживал сессионную PostgreSQL
advisory-блокировку и соединение на протяжении создания поставки, добавления
заказов и чтения подтверждения WB. Уже интегрированные исправления освобождали
только ожидающие запросы и отдельный путь продолжения существующей операции.

Теперь короткая подготовительная транзакция использует транзакционную
advisory-блокировку **с тем же ключом продавца**, что существующая сессионная.
Они взаимно исключают друг друга. В этой транзакции заново проверяются заказы и
ключ повтора, сохраняются существующие `FbsWbOperation` и черновик поставки.
Commit одновременно делает попытку видимой другим запросам, освобождает
блокировку и возвращает соединение в пул. Новых таблиц, полей, статусов, сроков
аренды или журналов нет. Остальные пользователи lock helper сохраняют прежнее
поведение по умолчанию; Ozon не переключается на транзакционную блокировку.

Во время HTTP соединение свободно. Полученный номер WB сохраняется отдельным
commit **до** добавления заказов; поэтому повтор продолжает именно эту поставку.
После HTTP читаются свежие строки перед применением результата. Подтверждённая
конкурентная попытка не перезаписывается; отменённый заказ или уже начатый более
поздний складской этап не возвращается в `in_supply`. Изменения склада, резервов,
упаковки и навигационных разрешений не добавлялись. В legacy-создании пустой
поставки завершена только подготовительная read-транзакция перед HTTP.

Внешние вызовы сохраняют существующий `httpx timeout=60.0` в
`wildberries_client.py`: это таймаут HTTP-запроса, не обещание длительности всей
операции из нескольких запросов. Дополнительного операторского режима нет.

## Повтор, конкуренция и неопределённый ответ

Существующая незавершённая операция содержит набор своих заказов. На границе
создания повтор того же запроса или новый ключ с пересечением этого набора не
выпускает второй POST в WB. Независимые заказы того же продавца могут создаваться,
пока первая поставка ждёт WB. Заведомо отклонённый начальный HTTP-запрос переводит
операцию в существующий `failed` и удаляет пустой местный черновик; новый ключ
может повторить создание. Завершённые/отклонённые попытки не держат чужие заказы.

Потерянный ответ первоначального POST, ответ без номера и серверная ошибка не
доказывают, что WB ничего не создал. Сохраняются прежняя операция и её местный
черновик; повтор возвращает их идентификаторы, не создавая поставку ещё раз.
Это не автоматическая сверка неизвестного номера: в текущем проекте нет
надёжного способа восстановить WB ID по одному имени поставки. Существующий
`reconcile_actual_wb_supply_composition` явно отклоняет `PENDING-*` как
`supply_without_wb_id`. Нового эвристического поиска по имени не добавлено.
Для такого исхода нужна предметная сверка с WB; механизм не выдаёт пустой
черновик за подтверждённое создание и не забывает идентичность попытки.

Ошибка чтения после успешного добавления заказов сохраняет известный номер WB и
`pending_confirmation`. Повтор использует существующий путь сверки/продолжения,
не повторяя первоначальный POST создания.

## Проверка

Все обращения WB в тестах заменены контролируемыми ответами. Живые поставки,
коды клиентов и кабинеты учётных данных не использовались.

Создана отдельная локальная PostgreSQL-база `wms272_finish_20260908_20650` на
`127.0.0.1:5432`. В ней прошёл целевой набор:

```text
pytest -q tests/test_fbs_create_http_connection.py \
  tests/test_fbs_create_lock_connection.py \
  tests/test_fbs_supply_from_orders.py \
  tests/test_fbs_resume_connection.py \
  tests/test_fbs_supply_assembly.py
41 passed
```

Новые проверки приостанавливают HTTP на создании, добавлении и чтении состава.
В это время независимый `SELECT 1` получает соединение из настоящего пула
размером **1**, а другая сессия видит сохранённые данные операции. Проверены
повторы с прежним/новым ключом, независимый запрос того же продавца, неизвестный
ответ, явный отказ, известный номер перед добавлением, ошибка чтения и отмена
заказа во время HTTP. Отдельный PostgreSQL-тест подтверждает совместимость
сессионной и транзакционной блокировок на одном ключе и освобождение при
commit/rollback. Существующий конкурентный API-тест также прошёл на PostgreSQL.

`ruff check .` прошёл. `mypy .` прошёл для 430 файлов backend. Полный pytest
локально не запускался. После последнего ограничения защитного bind только
WB повторены новые семь проверок отдельно: `7 passed` на PostgreSQL.

Ручной сценарий в браузере, CI и деплой этой ветки в этом исследовании не
проводились. Локальная PostgreSQL-база после проверки удалена командой `dropdb`;
использованные данные были синтетическими.
