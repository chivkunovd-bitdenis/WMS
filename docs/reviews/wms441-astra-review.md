# WMS-441 — независимое ревью Astra, 13.09.2026

**Вердикт: CHANGES REQUIRED.** Исправленные три замечания прежнего backend-ревью подтверждены, но обнаружены два дефекта в границе между сортировкой и общим перемещением склада. Первый воспроизведён идентичным HTTP-запросом с тем же UUID и действительно повторно расходует товар. Это техническое ревью, не приёмка аналитиком. Требования и канонический бэклог не изменены. Ревью выполняет отдельная Astra-сессия по явному назначению владельца после незавершённой сессии Opus.

## F1 — P1: веб повторно расходует товар внутри грузоместа с тем же operation_id

**Требования:** R4, R7, R8. Это повтор одной подтверждённой попытки после потери ответа; второго решения оператора разместить ещё одну вещь нет.

`frontend/src/screens/ff/sorting-objects/FfSortingObjectsPage.tsx:136–140` сохраняет тело запроса и UUID для всякого `payload.kind === 'product' && payload.cellId`. Однако `product` означает любую строку физического остатка, включая товар внутри тары. `SortingObjectsScreen.tsx:161–172` отправляет такие строки через один `moveGoods`, а `ObjectsTree` позволяет вызвать это действие у вложенного товара (`:389–394`).

В `backend/app/services/warehouse_map_service.py:1875–1895` идентификатор распознаётся только когда источник находится в сортировке **и** `balance.container_id is None`. Товар грузоместа проходит дальше в `move_object` без `operation_id`. Сервис `apply_received_balance_putaway` проводит каждую доставку как новую порцию товара. После потери ответа `FfSortingObjectsPage.load()` сам повторяет сохранённое тело (`:88–95`), поэтому ошибка достигается обычным reload.

Точная граница: ошибочный web-контракт включает `kind=product` с источником внутри `cargo_place` (воспроизведено), внутри `box`/иной тары либо из уже занятой ячейки (та же ветка кода, отдельным прогоном здесь не проверено). Для `kind=cargo_place`, `box`, `pallet` web этот UUID не сохраняет; их не следует смешивать с F1. Защищённый серверный путь сейчас только `kind=product`, исходная зона сортировки, отсутствие контейнера, назначение в ячейку.

Независимый API-прогон в отдельной PostgreSQL:

1. Документ с фактом 3; все 3 единицы одного SKU находятся в грузоместе в сортировке.
2. POST `/warehouses/{warehouse}/sorting-objects/place`: `kind=product`, `id=<InventoryBalance cargo>`, `qty=1`, `cell_id=A`, `inbound_request_id=<документ>`, `operation_id=X`. Ответ 200; в A одна единица, posted=1.
3. Повторить **тот же JSON целиком, включая X**. Ответ снова 200; в A уже две единицы, posted=2, у грузоместа posted=2.
4. В движениях четыре строки и две группы передачи, хотя оператор подтвердил только одну единицу.

Проверка `test_web_cargo_contents_exact_operation_replay_spends_another_unit` и вывод сохранены в [артефактах](artifacts/wms441-astra-review/test_cargo_stale_sorting.py). Это не предположение о сетевых ретраях: в пробе дважды отправлен идентичный запрос, а автоматическая повторная отправка подтверждена чтением действующего web-кода.

**Нужное исправление:** согласовать границу сохраняемого/повторяемого web-намерения с реальной серверной защитой от повтора. При отправке вложенного товара нельзя автоматически воспроизводить операцию, которую сервер считает новой. Если этот путь получает UUID-контракт, проверить повтор после commit, промежуточного failed GET и reload; один расход и одна группа движений. Если путь остаётся общим перемещением, web не должен выдавать его за защищённую UUID-операцию: неизвестный результат требуется выяснять без повторного физического действия. Не запрещать законное новое размещение остальных штук или законное общее перемещение по складу.

## F2 — P1: потеря ответа cargo-putaway оставляет в ТСД прежний объект выбранным и позволяет расставить его снова

**Требования:** R2, R4, R7, R8. Граница дефекта — рабочий экран сортировки с невыясненным результатом, а не самостоятельное новое перемещение уже размещённой тары на карте склада.

В новой `SortingViewModel.confirmCargoPlacePutaway()` `:179–201` до запроса снимается только `pendingLocation`. При исключении сети ветка `ApiResult.Err` (`:199`) меняет лишь `flash`: не перечитывает документ, не сохраняет неопределённую попытку и не снимает `target`. Состояние `unresolvedPutaway` применяется только к россыпи. Даже первоначального GET после ошибочного POST в cargo-ветке нет.

Достижимая последовательность по клиентскому коду:

1. Выбрать грузоместо из списка, сканировать A, подтвердить. Сервер проводит грузоместо и завершает документ, но ответ теряется.
2. ТСД показывает сетевую ошибку, прежнее количество, ту же выбранную цель и подсказку «Теперь отсканируйте ячейку». Это не успешное перечитывание и не осознанное начало нового общего перемещения.
3. Отсканировать B. `processScan` сохраняет B в `pendingLocation` для оставшегося `target`; обычный шит снова предлагает «Разместить грузоместо» с прежним количеством.
4. Подтвердить. `CargoPlacePutawayBody` содержит только `kind`, `id`, `cell_id`: документ и идентификатор попытки отсутствуют. Общий складской маршрут законно перемещает уже стоящее в A грузоместо в B; прежнее размещение в A исчезает.

Серверная часть независимо воспроизведена пробой `test_stale_sorting_cargo_can_be_placed_a_second_time`: первая отправка A и вторая B обе возвращают 200; posted остаётся 2/status=done, A=0, B=2. Появляются исходные `stock_transfer_out -2`/`stock_transfer_in +2` и дополнительные `warehouse_map_move -2/+2`. Это само по себе допустимое поведение общего склада, но показывает последствия оставленной ТСД цели. Связка с UI установлена чтением всех переходов состояния; новый device-прогон этой последовательности не выполнялся.

**Нужное исправление:** при неопределённом cargo-ответе восстанавливать фактический результат исходной операции, не предлагать прежний остаток как новую сортировку. Должны сохраниться выход и открытие другого документа; после восстановления чтения уже размещённое грузоместо исчезает, последняя операция возвращает в очередь. Проверить POST commit → loss → ошибка чтения → повторный вход/восстановление и скан другой ячейки до выяснения результата. Это не основание запрещать отдельное общее перемещение тары.
