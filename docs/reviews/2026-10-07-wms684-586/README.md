## Подтверждённые дефекты

### F1 — [P2] PDF теряет допустимое многострочное название товара

Место: [inbound_acceptance_act_service.py](../../../backend/app/services/inbound_acceptance_act_service.py), строки **144–151, 167–179**, вызов **256–269**. Нарушены WMS-586 **R3, R6–R7, R9, R14**: PDF и Excel одного акта не содержат одинаковые полные реквизиты товара.

Название `Худи\nРазмер XL\nЦвет чёрный\nЗимняя коллекция\nУтеплённый хлопок` содержит 61 символ. Текущая модель `ProductCreate` принимает его без изменения; `catalog_service.create_product` применяет только `.strip()`, сохраняющий внутренние переносы. Это допустимые данные существующего продукта, не требование новой функции. Расчёт `_pdf_row_height` резервирует высоту по общему числу символов и игнорирует явные переносы строк. Все попытки `insert_textbox` возвращают отказ размещения, а последний отказ на строке 179 игнорируется. В результате вся ячейка названия исчезает, хотя её артикул и численные значения остаются.

Доказательства: [act-multiline.pdf](act-multiline.pdf), [изображение страницы](act-multiline-page-1.png), [тот же Excel](act-multiline.xlsx), [pdf-probe.json](pdf-probe.json) (`lost_names: [1]`, Excel B4 содержит исходное имя), [multiline-validation.json](multiline-validation.json). [pdf-probe.py](pdf-probe.py) вызывает реальные функции экспорта с одним синтетическим документом, подменяя только чтение документа из БД. HTTP-путь и права отдельно проверены неизменёнными API-контрактами.

Исправление должно учитывать фактическую высоту текста, включая явные переносы, и обрабатывать невозможность размещения без молчаливой потери данных. Запрет многострочных имён или изменение ожиданий замороженных тестов не исправляет дефект экспорта.

### F2 — [P2] Новый макет изменяет грузоместа и короба отгрузки

Место: [printBarcodeLabel.ts](../../../frontend/src/utils/printBarcodeLabel.ts), строки **68–77**. Нарушен WMS-684 **R4** и требование сохранять соседние процессы.

Ветка CSS выбирается только по `layout === 'internalBox' && labelSize`; наличие новых реквизитов приёмки не участвует в выборе. Поэтому смена сетки с трёх на четыре строки, уменьшение заголовка 13→10 pt и кода 9→7 pt, а также новое растяжение изображения применяются и к вызовам без `metadata`. Такие вызовы реально существуют: грузоместа в `FfInboundRequestView.tsx:1639–1647` и короба отгрузки в `FfSuppliesShipmentsPage.tsx:1066–1071`. Это изменение защищённого соседнего макета независимо от того, декодируется ли его штрихкод.

Доказательства: [cargo-before.html](cargo-before.html) и [cargo-after.html](cargo-after.html) получены одним одинаковым вызовом настоящего общего принтера для `Грузоместо № 1`, 58×40, без реквизитов приёмки; исходный модуль взят через `git show` из frozen SHA. [frontend-probe.json](frontend-probe.json) фиксирует `cargoHtmlEqual: false` и обе сетки. Проба использует jsdom только для получения HTML, не открывает браузер и не печатает. Существующий тест `keeps cargo, default and storageCell printing free of receipt metadata` проверяет отсутствие текста приёмки, но не равенство макета грузоместа прежнему.

Нужно ограничить новый макет коробами приёмки, сохранив прежний макет остальных вызовов `internalBox`. Накладная и её вызов действительно остались неизменными; замечание относится к общему принтеру внутренних этикеток.

### F3 — [P2] Дата стикера без часового пояса зависит от компьютера оператора

Место: [FfInboundRequestView.tsx](../../../frontend/src/screens/ff/FfInboundRequestView.tsx), строки **443–449**. Нарушен WMS-684 **R1**, включая решение аналитика о московской дате документа.

`new Date(value)` интерпретирует ISO-время без зоны как местное время браузера. Между тем API `inbound_intake.py:610` отдаёт `created_at.isoformat()`, а SQLite возвращает дату без зоны — именно этот случай разработчик исправил в серверном `_document_date` на строках 45–52. При `created_at = '2026-09-28T21:30:00'` серверный акт считает исходное время UTC и показывает **29.09.2026**, а новый стикер на компьютере в Москве или Тбилиси показывает **28.09.2026**. Строка с явным `Z` во всех проверенных зонах работает правильно. Ошибка условна: она касается ответа без зоны; для обычного PostgreSQL-ответа с зоной её не утверждаем.

Доказательство: [frontend-probe.cjs](frontend-probe.cjs) извлекает и исполняет фактическую функцию `inboundReceiptDate` из проверяемого файла; [frontend-probe.json](frontend-probe.json) сохраняет результаты для UTC, Europe/Moscow и Asia/Tbilisi. Замороженный K4 проверяет только значение с `Z` и поэтому не ловит этот случай.

Нужно согласовать трактовку времени без зоны с существующим серверным контрактом UTC, сохранив обработку явного смещения и отсутствующих/невалидных дат.

### F4 — [P2] Стикер обходит действующее правило пользовательского номера

Место: [FfInboundRequestView.tsx](../../../frontend/src/screens/ff/FfInboundRequestView.tsx), строка **1644**. Нарушен WMS-684 **R1** и явное решение аналитика использовать `formatHumanDocumentNumber(detail)`.

Экран уже вычисляет пользовательский номер через `formatHumanDocumentNumber` на строке 669, но новая подпись использует прямой `display_number || document_number`. Когда `display_number=null`, `document_number='INB-000684'`, карточка показывает **№000684**, стикер — **INB-000684**. Если `display_number=' '` и прежний номер доступен, карточка всё ещё показывает №000684, а стикер показывает «—». Для невалидного запасного номера `broken` прежний форматтер возвращает отсутствие номера, а новая подпись печатает `broken` вместо согласованного «—».

Доказательство: [frontend-probe.json](frontend-probe.json), раздел `numbers`, сравнивает действующую функцию из `documentDisplay.ts` с точным новым выражением подписи. В обычном случае с заполненным `display_number` контракт проходит; запасной путь номера тест не покрывает.

Нужно использовать существующий форматтер с согласованным fallback «—», не создавать второе правило представления номера.
