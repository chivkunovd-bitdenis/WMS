# WMS-442 — независимое Astra review Windows и постоянной работы

Дата: 13.09.2026. **Вердикт: CHANGES REQUIRED.** Проверен implementation commit `e76c5c4b67c768039decfbb419fc32027c36f335` относительно BA `fbb343a85486c92f9910432464a90440e8ca1537`. Windows-программа не готова: есть подтверждённые технические дефекты, а Windows CI завершился ошибкой до сборки установщика. Это независимое техническое ревью, не физическая или продуктовая приёмка.

До проверки повторно прочитаны основной `AGENTS.md`, полный `docs/requirements/WMS-442.md`, `owner-cases.md`, `failure-cases.md`. Проверена дельта целиком; изменения требований441/443/444/445 принадлежат отдельному BA-аудиту и не являются реализацией442. Применимые критерии: один внешний результат без скрытого повтора (B02/B09/B10), возможность продолжить после сбоя (B07), сохранение контекста и отсутствие придуманных ограничений. Продуктовый код, БД, принтеры, системные задачи и общие процессы review не меняет. Параллельные незакоммиченные исправления Terra не входят в этот вердикт.

## Подтверждённые дефекты для того же Terra high

### F1 · P1 · XML автозапуска содержит недопустимый RestartOnFailure Count

`tools/print-agent/wms_print_runtime.py:520` задаёт `<Count>999</Count>`. В опубликованной Microsoft XML-схеме Count имеет тип unsignedByte с минимумом1, то есть1–255. Такой XML не соответствует контракту регистрации; после сопряжения `_register_windows_task` не может считаться рабочим. Текущий unit test подменяет весь `schtasks` ответом0 и не валидирует XML.

[Microsoft Count/restartType](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-count-restarttype-element) и адресная проба подтверждают значение999 за пределами схемы. Реальная регистрация именно этого XML на Windows в данном review не запускалась — это подтверждение по коду и официальному контракту, не выдуманный Windows traceback.

Исправить допустимое значение и проверить настоящий register → query → run → аварийное завершение → restart в пользовательском профиле Windows. R14, C21/C22.

### F2 · P1 · Unicode-настройка и русская ошибка не сохраняются на обычной Windows

`tools/print-agent/wms_print_runtime.py:100–101` открывает JSON без encoding и пишет `ensure_ascii=False`; чтение на115 также использует неявную кодировку. На Windows с ANSI cp1252 русское имя очереди/сообщение нельзя записать. Это уже **реальная ошибка Windows CI**: `test_destination_and_size_mismatch_are_rejected_before_native_call` падает в `write_private → json.dump → cp1252` с `UnicodeEncodeError`. Следствие — не только невозможность сохранить «Принтер склада»: отрицательная квитанция не доходит до сервера, хотя отказ был до передачи.

Адресная проба повторяет запись кириллической очереди в cp1252 без изменения продукта. Использовать явное согласованное UTF-8 чтение/запись локального состояния; если нужен переход со старых файлов, определить совместимость отдельно. Проверить настоящие Unicode queue/config/error round trips на Windows с обычной ANSI-локалью, не скрывать дефект одной переменной UTF-8 в CI. R13/R16/R17, C20/C24.

### F3 · P1 · Установщик заменяет/удаляет файлы до подтверждённой остановки, rollback отсутствует

`tools/print-agent/windows-installer.nsi:15–19` вызывает `--stop`, ждёт фиксированные1500мс и перезаписывает рабочий каталог; на33–39 удаление тоже не ждёт worker. В runtime625–639/782–788 `--stop` только сигнализирует событие и сразу выходит0. Worker читает событие лишь после HTTP/печати, на857; штатный сетевой вызов или драйвер легко работает дольше1,5с. `ExecWait` ждёт процесс команды `--stop`, а не процесс печати.

В результате обновление попадает в заблокированные DLL/exe или частично заменяет bundle, удаление может оставить работающий процесс/файлы после удаления записи программы. Установщик не проверяет результат stop, не сохраняет предыдущий целый bundle и не восстанавливает его при отказе в середине копирования. R18 требует возможность вернуться к прежней версии с сохранённым состоянием; фраза README о сбое только «до замены файлов» не закрывает это.

Нужны подтверждённая остановка/освобождение блокировки, проверяемая замена целой версии с восстановлением при неудаче и честный результат удаления. Проверить обновление/удаление при задержанном HTTP и после начала spool, плюс отказ копирования в середине. R18, C27/C28.

### F4 · P1 · Обновление и переустановка запускают worker в обход автозапуска

`tools/print-agent/windows-installer.nsi:28–29` при наличии сохранённого `connection.json` выполняет только `wms-print.exe --run`. В runtime824–829 эта ветка **не регистрирует** задачу и не запускает её через Планировщик. После удаления задача уже стёрта `disable_autostart`; переустановка сохраняет настройку, запускает печать сейчас, но следующий вход ничего не запустит. После обновления самостоятельный процесс также не управляется `RestartOnFailure`; аварийный выход оставит печать выключенной до будущего входа/ручного запуска.

После установки/обновления/восстановления использовать общий путь регистрации и запуска ровно одного worker через штатный механизм, сохраняя connection_id. Проверить remove → reinstall → reboot/login без повторного сопряжения и аварийный restart после update. R13/R14/R18, C21/C22/C27/C28.

### F5 · P1 · Размер bitmap не задаёт размер бумаги и параметры драйвера

`tools/print-agent/wms_print_runtime.py:328–355` создаёт `CreatePrinterDC(queue)` с текущими параметрами драйвера, читает только DPI88/90 и рисует прямоугольник от0,0. Размеры58×40 влияют лишь на bitmap; настройки бумаги, ориентация, printable area/physical offsets не задаются и не проверяются. При очереди с иной формой/непечатаемыми полями файл может обрезаться или уйти на другой формат, а код всё равно вернёт `windows-N`. Число копий дополнительно умножается циклом, но собственное число копий драйвера не нормализовано.

Адресная GDI-проба фиксирует только CreatePrinterDC, DPI, draw464×320, две страницы и квитанцию: вызова конфигурации/проверки формы нет. Это проверка границы вызовов, **не имитация отпечатанного листа**. [Microsoft DEVMODE](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/ns-wingdi-devmodea) описывает отдельные параметры бумаги и копий; [создание printer DC](https://learn.microsoft.com/en-us/windows/win32/printdocs/retrieving-a-printer-device-context) допускает передачу этих параметров.

Согласовать с драйвером размер/ориентацию/копии и проверить итоговую геометрию, либо до spool честно сообщить неподдерживаемый формат без обрезанной «успешной» этикетки. Проверить PNG и настоящий PDF, разные размеры, ненулевые поля, один/несколько экземпляров, затем физический C25. R4/R15, C25/C26.

### F6 · P2 · Переподключение и повторный запуск настройки заблокированы собственным фоном; macOS update не перезапускает версию

`tools/print-agent/wms_print_runtime.py:817–823` захватывает тот же exclusive lock до обработки `--reconnect`. После введённого обязательного фона он постоянно занят worker: указанная в README команда смены очереди теперь получает общий отказ вместо настройки. Проба с реально удерживаемой временной POSIX-блокировкой возвращает1 и не доходит до переподключения. На Windows логика владения та же.

На macOS `build_package.py:81–86` копирует bundle поверх работающего и запускает настройку; остановки/перезапуска LaunchAgent нет. Даже после освобождения lock повторный `launchctl bootstrap` на уже загруженный label (runtime590–600) не является идемпотентным запуском. Настройка не должна объявлять уже подключённую программу неподключённой только из-за собственного фонового экземпляра.

Дать рабочий путь повторного открытия/смены назначения с координированной остановкой и возобновлением, а macOS-update — остановку, сохранение состояния и запуск новой версии. Сохранять старое назначение jobs; не удалять ключи сервера и не вводить новый экран. R13/R18/R19, C20/C27/C29/C30.

### F7 · P2 · Windows worker собирается консольным приложением

`tools/print-agent/build_package.py:39–72` собирает один обычный console executable; задача с `InteractiveToken` (runtime514/522) запускает его напрямую. Нет windowless worker, скрывающего launcher или управляемого отделения консоли. Поэтому требование фона реализовано новым постоянным консольным окном пользователя; его закрытие завершает worker, после чего Планировщик может открыть его снова.

Это следует из вызова сборки и [документированного default PyInstaller console](https://pyinstaller.org/en/stable/usage.html); адресная проба фиксирует отсутствие windowed/hide режима. Окно на чистой Windows я не наблюдал. Сохранить простую настройку, но обеспечить действительно фоновый worker без постоянного терминала и проверить его stdout/error поведение. Не превращать это замечание в новый продуктовый UI. R14, C21/C22.

### F8 · P1 · Сброс удаляет незавершённое состояние, пока worker ещё может печатать

`tools/print-agent/wms_print_runtime.py:795–799` после одного сигнала stop сразу удаляет connection/inflight, не дождавшись worker и не взяв его lock. Сам worker уже держит config в памяти и может находиться внутри submit/ack; затем он способен заново записать outbox поверх объявленного сброса или продолжить печать старого соединения. Удаление задачи само по себе не подтверждает завершение запущенного процесса.

Адресная проба держит lock от имени worker, вызывает именно CLI reset с подставленной доставкой stop и получает0 при реально удалённых connection/inflight. Это воспроизведение отсутствующего барьера, без настоящего сервера/принтера. Явное согласие на сброс разрешает удалить состояние, но не устраняет гонку с прежним исполнителем. После подтверждённой остановки сброс должен владеть состоянием эксклюзивно; предупреждение о незавершённости должно предшествовать удалению. R17/R18/R19, C24/C28.

## Проверки и ограничения

[GitHub run34773072757](https://github.com/chivkunovd-bitdenis/WMS/actions/runs/34773072757) проверен через `gh run view` на точном SHA. Windows job103766105214 завершён `failure`:18tests,4failures/2errors; build/self-test/upload пропущены. Среди причин — реальная Unicode-ошибка F2, POSIX `0600` проверки на Windows и запуск shell-fixture с WinError193. Исправить платформенные тесты, сохранив проверки прав/повторов на настоящих Windows API; просто пропустить эти проверки нельзя. macOS job103766105302 прошёл tests/build/self-test/upload. Повторный полный локальный запуск тех же18tests не выполнялся без основания.

[Адресные пробы](artifacts/wms442-astra-windows-review/probe.py) загружают продуктовые модули через `git show e76c5c4b:...`, поэтому не затрагивают и не случайно принимают параллельные исправления Terra. [Результат](artifacts/wms442-astra-windows-review/probe-results.json) содержит проверки F1/F2/F5/F6/F7/F8. Пробы используют временный синтетический профиль и mock границы ОС; реальные задачи, драйверы, ключи, печать и WMS не вызываются.

Положительное по коду: серверная дельта ограничена `win32` и Unicode-именем очереди; tenant/warehouse/connection/claim проверки не ослаблены. Сохраняются проверка MIME/размера/checksum, явная очередь, durable `submitting`, повтор только квитанции и отсутствие скрытого повторного spool при неопределённом исходе. NSIS использует user/HKCU/LocalAppData; в аргументах autostart нет доступа агента. Windows ACL применяет текущий SID и SYSTEM, но проверка фактического доступа вторым обычным Windows-пользователем остаётся C20; POSIX mode-биты её не заменяют. Новый web/Android UI, новая серверная очередь и складские ограничения в implementation diff не добавлены. Сохранение прежнего CUPS пути подтверждено кодом и macOS CI; это не снимает F6 и аппаратную границу.

Сам текущий `--self-test` на Windows использует synthetic command spooler и **не создаёт WindowsAdapter**, не доказывает доступность pywin32/PIL/PyMuPDF в установленном bundle и не проверяет NSIS install/update/uninstall или настоящий Task Scheduler. Поэтому даже исправленный зелёный build job будет только промежуточным доказательством. Нужен artifact, запуск установленного пакета на Windows с перечислением реальных очередей/декодированием PDF/PNG, C19–C30 применимо к каждой заявленной ОС и физическая бумага C13/C25. Ссылка на исходники/CI без доступного сотруднику установщика не закрывает R12. Конкретный Windows artifact этого SHA отсутствует из-за пропущенного build/upload; готовность матрицы Windows10/11 не заявляется.
