# WMS-277: периодическое обновление каталога WB

Изолированная ветка `codex/wms277-catalog`, база `origin/etalon`
`054897e270533d3e0fc65b651d420b3af8332fce`. Канон ведёт координатор.

## Объём и источники

`ITOGI_BACKLOGA.md`, раздел «Каталог должен обновляться сам», требует существующий
WB-импорт после исправления полной пагинации WMS-276 и прямо исключает Ozon,
изменения физических остатков, квоты, историю заказов и новые экраны. Первичный
разбор там же не задаёт частоту. Для этого первого выпуска координатор выбрал
раз в час на 17-й минуте; это решение координатора, не цитата владельца.

Celery beat вызывает новую тонкую task-обёртку существующего
`run_wb_products_sync_all_sellers`. Обход последовательный. Выборка соединяет
существующего Seller с непустым Content credential; у Seller нет soft-delete
или отдельного признака активной интеграции. Удалённые Seller и очищенные/пустые
Content credentials не входят в обход. Marketplace scope, складская публикация
и Ozon не используются как условие включения чтения WB-каталога и не меняются.

У каждого продавца заканчивается собственная сессия чтения до HTTP. Общий
`fetch_all_cards` получает все страницы по 100 с существующей паузой 0,6 секунды;
база/блокировка не удерживается на запросах и паузах. После HTTP новая сессия
повторно проверяет продавца и Content token: отключение/замена во время fetch
означает пропуск ответа. Используются прежние snapshot/Product upsert, включая
варианты размеров и существующую защиту измерений. Результат одного продавца не
мешает обработке остальных при ошибке WB или сохранения.

Каталог не создаёт складские движения, остатки или резервы. В
`wb_marketplace_orders_service._update_existing_order_from_wb_row` последующий
обычный импорт заказа сопоставляет ранее отсутствовавший product_id и вызывает
штатную попытку резерва. Сам scheduler историю заказов не запускает.

## Совместимость и границы

Ручной FF-путь `App.tsx` запускает `wildberries_cards_sync` и читает
cards_received, затем перечитывает snapshots. SellerSettingsScreen и
SellerProductsStockScreen используют синхронный `/self/sync-products`, который
возвращает cards_received/cards_saved/products_*. Все эти API, ответы и ручные
исполнители оставлены без изменений. Из существующего Products service выделено
только общее сохранение с прежними полями результата.

Перед periodic fetch проверяется существующий pending/running ручной
BackgroundJob того же tenant/seller. Такой продавец пропускается; чужой job не
меняется. Не добавлены durable claim, TTL, новые сущности, блокировки ручного
повтора или удержание соединения для advisory lock на HTTP.

Это намеренно **не строгий межпроцессный dedup**: synchronous seller button,
одновременный старт ручного job после проверки и перекрытие двух длительных
periodic runs могут выполнить concurrent fetch. Координатор выбрал этот узкий
вариант вместо нового механизма аренды. Существующие уникальности snapshots
`(seller_id, nm_id)` и Products `(tenant_id, seller_id, sku_code/wb_barcode)`
не дают продублировать ключи. Product upsert уже обрабатывает IntegrityError;
snapshot collision может завершить импорт конкретного продавца ошибкой и
повторится на следующем часовом запуске. Гарантия отсутствия concurrent write
не заявляется. Старый зависший manual running job может приводить к пропуску
periodic для этого продавца; ручной повтор по-прежнему доступен, автоматическое
восстановление старых job сюда не добавлено.

Проверка отключения сделана на границе HTTP/сохранения. Отключение, начатое уже
во время существующего многошагового upsert, не является транзакционной отменой
частично сохранённого каталога. Новые требования атомарности этого прежнего
импортера в задачу не включены.

## Проверки

- Новый файл `test_wb_catalog_schedule.py`: hourly task binding, WB Content
  eligibility при false Marketplace scope, изоляция двух tenant/seller с
  одинаковым SKU/ШК, сохранение snapshots+Products без stock, отсутствие открытой
  read-сессии на HTTP, ошибка первого продавца с продолжением обхода, pending и
  running manual skip, terminal manual допускает следующий импорт, отключение
  Content во время HTTP отбрасывает ответ. Только синтетические credentials и
  HTTP MockTransport, никаких реальных API/ключей.
- Существующий `test_wildberries_products_full_sync.py`: пагинация 205 карточек,
  обычное последующее сопоставление заказа и один резерв без физического движения;
  отдельная проверка отклонения зацикленного курсора.
- Первый целевой запуск на SQLite memory: **7 passed, 1 failed**. Единственное
  падение — existing reserve scenario, `no such savepoint: sa_savepoint_1` на
  SQLite memory. Повтор только этого сценария на собственном
  файловом SQLite: **1 passed**, 2,36 секунды. Scratch DB удалена после проверки.
- Ruff по четырём затронутым Python-файлам прошёл. Mypy без дискового cache по
  трём app-файлам: **Success: no issues found**.
- Дополненный сценарий повторного часового импорта: **1 passed**, 0,63 секунды;
  второй запуск обновляет те же два товара/снимка, products_created=0.
  Ruff после дополнения прошёл повторно.

## Приёмка

Новый scheduler в настоящем stage-браузере пока **не проверен и не выложен**.
Content API по умолчанию направлен на реальный WB; blanket all-seller запуск
на стенде не выполнялся. Ключи/настройки стенда не читались и не менялись.
Для браузерной приёмки нужен изолированный synthetic Content transport с
последующей проверкой конкретного нового товара в каталоге и существующего
заказа обычным FBS-импортом. Тесты и сохранение Git не заменяют эту приёмку.
