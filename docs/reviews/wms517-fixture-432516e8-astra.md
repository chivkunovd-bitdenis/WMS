## Почему это оснастка, а не изменение ожидаемого поведения

До коррекции `seed` создавал локальные заказ, маркировку, поставку и прежний
ценовой снимок, но не создавал synthetic sales/credential. Сам frozen
`fixture_order` уже задавал точный `wb_rid`, добавлял собственную синтетическую
учётную запись и передавал строки продаж через `SalesHTTP`. Так проверяется
реальная логика приложения: соответствие продажи заказу, возвраты, цены,
неполный ответ и сохранение попытки.

Новый legacy adapter добавляет продаже старых тестов входные данные через
HTTP. Его ContextVar по умолчанию равен False; autouse fixture включает
его только для собственного legacy-модуля и сбрасывает после теста.
Импорт одного `seed` не активирует эту fixture. Поэтому нельзя утверждать,
что каждый прежний вызов frozen `seed(db)` автоматически начал добавлять
legacy evidence. Явное `sales_evidence=False` гарантирует сохранение исходной
подготовки frozen-контракта даже при включённом legacy-контексте: не добавляет
конкурирующую synthetic sale/credential и не заменяет строки `SalesHTTP`.

Старый ценовой снимок остаётся, что существенно: SC5 и SC10 продолжают
проверять запрет использовать legacy цену вместо отсутствующей/ошибочной
продажи. Коррекция не удаляет данные, которые должны выявлять этот fallback.
Тесты с пустыми sales, чужим rid, возвратом и ошибочной ценой сохраняют
прежние ожидания и проходят в полном прогоне.

Исторический companion подменяет `httpx.AsyncClient.send` только на границе
ввода-вывода: WB получает synthetic JSON и пустой терминатор по dateFrom;
разрешены лишь GET `/api/v1/supplier/sales`, `flag=0`. Другие обращения
проходят только через MockTransport/ASGITransport; реальный HTTP transport
отвергается. Redis заменён `RedisBoundary`, длинные ожидания пропускаются,
короткие сохраняют планирование конкурентных сценариев. Это не проверка
настоящего Redis limiter и не подтверждение реального WB API.

Frozen использует собственный `SalesHTTP` (то есть fake sales boundary),
который только поставляет строки/страницы отчёта или транспортные ошибки.
Он не подменяет выбор допустимых строк, расчёт цены, repository/service
или результат проверки бизнес-условий. Вызовы приложения, SQLite-записи
и построение документов остаются реальными локальными вызовами; ЧЗ обслуживает
существующий MockTransport emulator. Ни WB, ни ЧЗ снаружи не вызывались.

Для второй записи `fixture_corrections` нового протокола фактические поля
независимого review таковы:

```json
{
  "model": "gpt-6-astra",
  "effort": "high",
  "verdict": "PASS",
  "source_commit": "042d9dbac5da202050ba165574a3c471e143af62",
  "correction_commit": "432516e88d3e5c1f055b1b8f697616fab496a8b8",
  "evidence": "docs/reviews/wms517-fixture-432516e8-astra.md"
}
```

`evidence_commit` берётся из отдельного коммита этого отчёта,
`evidence_blob` — через `git rev-parse <evidence_commit>:<evidence>` после
сохранения. Эти поля нельзя заменять SHA продукта или исторического SC10 review.
Исходный `contract_commit` остаётся `f5ca85534198feae8ad720ae2875730ae351229c`;
transform frozen-файла — `wms517-explicit-sales-fixture`; точные blob-пары выше.

Этот отчёт предоставляет недостающий независимый PASS, но сам не устанавливает
новый checker и не мигрирует существующий ledger. Общий GREEN checker/CI этим
отчётом не заявляется. До отдельной записи уполномоченным исполнителем прежний
governance blocker не считается автоматически снятым.

`427fc2cba5d09c78c691ca12277e66cff804fc69` — отдельная миграция бизнес-ожиданий
