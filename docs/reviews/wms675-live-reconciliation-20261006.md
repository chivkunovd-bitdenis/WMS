## Свежая карточка Ozon: конкретный оставшийся блокер

В текущем инструментарии нет callable WMS/Ozon-reader, привязанного к этому seller. Проверен существующий штатный путь: `MarketplaceAccountService.stored_credentials(tenant_id,seller_id)` → `build_ozon_provider()` → `/v3/posting/fbs/get`; он получает подключение внутри приложения и проверяет seller в tenant. Но он не предоставлен текущему аналитику как исполняемый bound reader. `SellerDirectory` даёт SQL-доступ, а принудительный SSH gateway принимает `sql`, `find-*`, `ensure-*`; он не выполняет marketplace-provider. Его доступность не означает доступность живого Ozon-клиента.

Проверены маршруты `fbs_orders`/`ozon_integration`: штатные sync/status-refresh сохраняют локальные данные, поэтому запускать их как read-only проверку нельзя. Перенос credentials через SQL, чтение окружения, административный SSH/Docker, изменение gateway и заимствование чужих credentials не выполнялись. Запрос на несекретную точку входа существующего bound reader передан владельцу; отсутствие ответа не является разрешением на другой путь. Ozon API **не вызывался**; HTTP статус, items и split relationships нельзя выдать за полученные.

Подготовлен [точный план31 read-запроса](wms675-evidence-20261006/ozon_read_plan.json): только `/v3/posting/fbs/get`, `with.related_postings=true`, без аналитики, финансов, юридических данных, штрихкодов и экземпляров маркировки. В штатной среде требуется живой transport, без FakeMarketplaceTransport и без изменения флага. Каждый реально возвращённый `related_postings.related_posting_numbers` читается тем же привязанным seller-клиентом; номера children не выдумываются из суффиксов. Сохраняются статус/подстатус, SKU, offer_id, quantity, реальные связи и поля отмены, время запроса/ответа и доступные HTTP-метаданные. Покупатели, адреса, auth headers и секреты не сохраняются. ## Проверяемая будущая схема восстановления после WMS-662 deploy

Это **схема будущей работы**, не выполненный ремонт и не разрешение на production mutation. Она использует уже согласованные требования [WMS-662](../requirements/WMS-662.md), не изменяет их и не вводит новые продуктовые сущности.

1. Проверить фактический production SHA и наличие принятого/прошедшего CI WMS-662 именно на нём. Не считать общий checkout, дату запуска контейнера или merge доказательством deployed версии. Убедиться, что доступен предусмотренный WMS-662 путь локального восстановления по наблюдаемой передаче; не подменять его обычным `deliver_supply`, который может создать/approve перевозку.
2. Получить свежие31 карточки и полный граф реальных children штатным bound client с точными request/response timestamp. Сверить posting_number, seller, SKU→product_id и quantity с текущими позициями draft. Не ограничиваться26 cached candidates: отменённый parent может иметь children; parent+child не расходовать дважды. Неполный ответ/ошибка/цикл/дубликат/несовпадение количества остаются unknown для затронутых единиц.
3. По каждому `(исходный order/position, фактический posting, SKU)` отдельно определить подтверждённое уникальное количество из допустимого для WMS-662 доказательства. `delivering`, `driver_pickup`, `delivered` оцениваются по контракту WMS-662; awaiting_packaging/awaiting_deliver/QR/сборка сами по себе не дают расход. Отмена, спор, не принято или сохранённая локальная отмена не оживляются положительным cache. Арбитраж/неизвестное состояние не маскировать успешным проведением. Данный draft не имеет ID перевозки, поэтому не выдумывать carriage как альтернативное proof.
4. Перед исполнением предъявить точную версию плана с конкретными postings, SKU, подтверждённым количеством, уже проведёнными единицами, источником и **дельтой недостающего проведения**.
