# WMS-277: contain an existing SKU collision before dimension-query autoflush

Isolated change based on production commit `40b722a4d2d0ff1a6a5899cdb2713a98d1265bc5`. Application ownership is limited to `wildberries_product_import_service.py`; no production data repair or manual synchronization was performed.

Read-only SQL in the two reported tenant/seller scopes confirmed both incident shapes. For seller `bf8eea6b-eaa6-47ea-8dfc-289142372dab`, the saved WB card changed the sizes associated with two existing barcodes from 37/38 to 38/37. Both destination SKU values were already owned by separate Product IDs. For seller `06b2e991-0533-4adf-83f3-d6cf21251433`, the WB card grouped two existing barcodes under the same size, while WMS retained separate Product IDs and SKU values for the prior sizes. Both cards supplied dimensions. Only Product identity fields and these two card snapshots' sizes/dimensions were read; credentials were not inspected.

The importer expands WB sizes into barcode variants, derives the SKU from vendor/size, and matches an existing Product by seller-scoped barcode before falling back to seller-scoped SKU. It applies incoming fields, then reads dimension events. That SELECT automatically flushed the changed Product before execution entered the existing commit-time IntegrityError handler. An occupied destination SKU therefore aborted the seller import instead of following the existing skip-conflicting-variant behavior. FBS order matching uses the existing seller-scoped CHRT/barcode/NM identifiers; merging or replacing Product identities here would affect that matching and is not part of this fix.

The fix explicitly flushes changed SKU fields inside an IntegrityError guard immediately after applying variant fields, before dimension queries. A collision rolls the variant back, increments the existing products_skipped result, and continues. Both existing Product IDs, SKU values, barcodes and relationships remain intact; the skipped variant receives no dimension event. An unchanged SKU incurs no extra flush. The existing commit guard remains. No new flags, entities, stock/reservation changes, or automatic product merges were introduced.

The SKU fallback behavior was deliberately left unchanged. In the observed grouped-barcode card, multiple barcodes share NM/CHRT, so treating every different nonempty barcode as a different product would risk changing legitimate existing import behavior. This patch addresses the reproduced autoflush defect, not an unverified redesign of identity matching.

Validation used the existing HTTP regression for saving/importing a content token, with synthetic mocked WB responses. Adding dimensions reproduced HTTP 409/product_conflict with the query-invoked unique-key autoflush error. After the fix, the scenario verifies repeated imports, unchanged identities, no dimension event on the skipped Product, and continued dimension update on the following non-conflicting Product. A second parameter covers swapped sizes; both variants remain unchanged and skipped. Nine focused size/dimension/seller-isolation tests passed before the final unchanged-SKU optimization; after that optimization, both collision parameters passed again. Ruff passed for both changed Python files, and mypy passed for the importer.

The first file-backed SQLite attempt failed during fixture CREATE INDEX with `unable to open database file` on the nearly full local disk; it did not reach application code. The subsequent reproduction and checks used SQLite in memory. No PostgreSQL race or live post-fix import was claimed. The failed attempt's own scratch SQLite was removed; the emulator's private backups and reports were not altered. Deployment and live acceptance of this fix remain for the coordinator's review/release process.
