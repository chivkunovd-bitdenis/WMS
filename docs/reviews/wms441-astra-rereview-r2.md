## F1 закрыт: ошибка и восстановление вложенного товара действительно проверены в браузере

`SortingObjectsScreen` передаёт исходный `sourceHolder`, а `canRememberSortingPlacement` разрешает сохранение/replay только для верхнеуровневой россыпи (`kind=product`, `cellId != null`, `sourceHolder == null`). Товар внутри коробов, грузомест, паллет и уже размещённый на ячейке не получает новый автоматический replay.

Для вложенного товара остаётся прежний общий складской путь: после неизвестного результата перечитать факт. Это допустимо в исходном объёме F1 — новая автоматическая повторная отправка не должна превращать этот унаследованный путь в двойной расход. Ревью не требует распространять новый mobile UUID-контракт на все общие перемещения склада.

Независимая browser-harness загрузила **настоящий** `FfSortingObjectsPage` и дочерние компоненты из предъявленного checkout в отдельный Vite с автоматически выделенным loopback-портом и собственный headless Chrome. Весь `/api/**` перехвачен синтетическими ответами; к общему API запросы не направлялись.

Путь: товар 3 в грузоместе → штатное действие «Вынуть» → в существующем диалоге выбрать ячейку A и количество 1 → имитированный успешный commit с обрывом ответа → GET 503 → reload после восстановления GET.

Наблюдения:

- после обрыва видна явная фраза «Результат размещения пока неизвестен»;
- failed GET убирает рабочее дерево, поэтому прежний остаток нельзя подтвердить ещё раз;
- в localStorage нет сохранённого UUID вложенного перемещения;
- после reload в грузоместе 2, ячейка A показывает 1;
- число POST за весь сценарий осталось **1**. Утрата ответа не вызвала повторное физическое действие.

Уточнение к R1: прямой плюс у товара внутри cargo/box отключён существующим `insideClosed`. Однако «Вынуть» открывает тот же диалог с изменяемым назначением, из которого ячейка доступна. Этот фактический путь теперь проверен кликами; прежняя ссылка только на `onPlace` была недостаточно точной.

## F2: одиночная неподтверждённая попытка исправлена, остаётся серверная конкуренция — P1

В Android до HTTP сохраняется cargo-body с `inbound_request_id` и `operation_id`; прежняя цель очищается. Пока результат неизвестен, выбор нового товара/тары и сканы не создают следующую цель; выход сохраняется. После restart попытка восстанавливается по серверу/сотруднику/документу. Удаление сохранённой попытки происходит после успешного POST и успешного GET. Эти переходы прочитаны; новые Android unit/build/device проверки ревьюер не выполнял, потому что ресурсы зарезервированы WMS-440.

Независимая ASGI+PostgreSQL-проба подтвердила нормальный контракт: первое размещение грузоместа в A → 200; точный повтор body/UUID → 200, **одна пара движений**; тот же UUID с подменённой ячейкой B → 409.

**Но R4/C5 не выполнены для двух клиентов с уже открытой сортировкой.** В `backend/app/services/warehouse_map_service.py:1928–1940` после отсутствия квитанции по новому UUID сразу вызывается общий `move_object`. Нет проверки, что данное грузоместо всё ещё является неразмещённым остатком выбранной сортировки. После первой операции второй запрос с собственным UUID превращается в законный для общего склада перенос A → B, хотя он пришёл из старого sorting-контекста.

Независимое воспроизведение:

1. Документ в sorting, одно cargo с 2 единицами. Два клиента открыли этот исходный остаток до первого размещения.
2. Через `asyncio.gather` отправлены два POST `kind=cargo_place`, тот же cargo и `inbound_request_id`, но UUID X/ячейка A и UUID Y/ячейка B. Это две попытки **сортировки**, не работа с уже размещённой тарой на карте склада.
3. Оба HTTP **200**. Первая операция размещает cargo в A; вторая создаёт дополнительные `warehouse_map_move` и переносит A → B.
4. Итого две расходные операции, A=0, B=2, posted=2. Первое назначение потеряно, хотя остаток этой сортировки уже исчерпан.

**Исправить узко:** после проверки повтора сохранённого UUID отличать новую sorting-попытку по данному грузоместу от общего перемещения уже размещённой тары. Проверка должна выполняться под существующей блокировкой документа и учитывать остаток именно cargo, в том числе когда весь документ ещё не завершён из-за другого товара. Повтор прежнего UUID обязан по-прежнему работать после done. Общий складской перенос без этого sorting-контракта оставлять законным. Новых экранов не требуется.

## Новый дефект cargo-replay для полностью бракованного грузоместа — P2

**R4/R7/R8, C9/C12.** `warehouse_map_service.py:1866–1870` комментирует отдельный случай полностью бракованного cargo, но `normal_destinations` собирается из **всех** положительных движений, включая специальную зону брака. Поэтому исходная выбранная ячейка A отсутствует в множестве, и тот же запрос считается подменённым.

Независимая проба: actual=2, defective=2, cargo=2 → POST с UUID X и выбранной A возвращает 200 и проводит брак в предусмотренную сервисом зону → точный повтор того же JSON с X возвращает **409 `operation_conflict`**. Подмены данных запроса нет. В ТСД это ошибочно попадает в окончательный отказ и удаление квитанции; успешное последующее чтение может восстановить документ, но серверный результат одной и той же выполненной попытки уже противоречив.

**Исправить:** различать исходное назначение операции и фактическую зону брака при проверке повтора. Полностью и частично бракованное cargo должны узнавать исходную попытку без нового движения; подмена назначения у обычного грузоместа должна остаться конфликтом. Сохранить существующий учёт брака, не менять его под UUID-проверку.
