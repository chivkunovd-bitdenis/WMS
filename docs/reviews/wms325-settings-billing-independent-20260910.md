Конкретный сценарий: два администратора одновременно отменяют один выпущенный счёт. Оба запроса читают `issued`: legacy использует обычный `SELECT` на строке 668, V2 — такой же запрос в `get_invoice_v2` на строке 748. Каждый сохраняет before=`issued`, меняет свой объект на `cancelled` и вставляет событие **до commit изменения счёта**. Последующее ожидание при UPDATE не пересчитывает уже записанный before/after. Обе транзакции могут завершиться, оставив два события отмены с разными авторами, хотя фактический переход состояния один.

Это дефект нового аудита: сумма и итоговый статус счёта не удваиваются, но история ошибочно приписывает успешный переход обоим запросам. Общий helper сравнивает переданные снимки и не устраняет такой дубль. Прочитанные тесты проверяют последовательные повторные отмены, этот сценарий они не покрывают.

Исправление должно связывать событие с **фактически выполненным переходом**: например, условный UPDATE только из `issued` с проверкой результата либо блокировка и актуальное перечитывание строки перед снимком. Для закрытия P2 нужна узкая проверка двух соединений для legacy и V2: при двух успешных запросах остаётся одно событие; при откате первой отмены событие принадлежит второй сохранённой транзакции.
