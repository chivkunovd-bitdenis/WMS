## Подтверждённые findings для Terra

### F1 — P1: смена сотрудника оставляет FBS recovery в контексте предыдущего человека

**Требования:** WMS-443 R3/R4/R7/R8, C5/C12/C15; WMS-445 R2/R10, C5/C15; затрагивает интеграционное авторство WMS-444 R10.

**Место исправления:** `mobile/android/app/src/main/java/ru/wms/tsd/core/api/ApiProvider.kt:82–100` и симметричные строки103–111. `AppGraph.kt:26` хранит один ApiProvider на весь процесс. `client()` сбрасывает `cachedFbsPendingIdentity` только при пересоздании клиента для другого URL; общий interceptor при этом берёт токен **текущего** человека на каждом запросе.

**Воспроизведение:** A на сервере S открывает FBS, `/auth/me` заполняет кэш A. Его create/add сохраняет попытку до HTTP; ответ теряется. Через обычное «Сменить» входит B на том же S, без убийства процесса. Новый FbsViewModel в `loadOrders()` (строки181–192) вызывает pendingFbsSupplyCreate/Add. `fbsPendingIdentity()` возвращает A до какой-либо проверки текущей сессии; AuthStore читает ключ A и показывает его набор B. `resumePendingSupplyMutation()` отправляет это тело через общий клиент уже с токеном B; при подтверждённом ответе `saveFbsSupplyCreate(null)`/add очищает ключ A. Если запрос A ещё не дошёл, B продолжает чужую попытку; если дошёл, B получает/очищает чужое восстановление. При разных организациях сервер сохраняет свою границу доступа, но локальный выбор A уже раскрыт B и попытка ошибочно загружается в его экран. Отсутствие серверного межклиентского доступа не исправляет локальную подмену.

**Собственное доказательство:** JVM-проба на настоящем ApiProvider с состоянием кэша после `/auth/me` A и текущей AuthSession B вызвала реальные pending/save методы. Проба получила тело A и проверила чтение **и удаление** `tenant-A/A/supply_create`; `auth.getCurrentSession()` не вызывался ни разу. Кэш подготовлен reflection как контролируемое исходное состояние, HTTP не имитировался как настоящий сервер. Достижимость этого состояния подтверждена AppGraph, AuthManager.logout и client/interceptor. Исходный AuthStore не подменяет ключи: он использует ровно переданные tenant/user.

**Минимальная правка:** привязать cached identity к нормализованному server и конкретной текущей user/session identity, проверять до возврата кэша. Захватывать контекст сохраняемой create/add попытки до HTTP и использовать его для чтения/отправки/очистки, как уже делает pack attempt WMS-444. При смене человека прежняя попытка не отправляется за нового и не удаляется из его ответа. Проверить A→B на одном сервере, разные tenant, возврат A и смену во время запроса; API-права/дизайн не расширять.

### F2 — P2: допустимым тёзкам недоступен предусмотренный вход с контекстом организации

**Требования:** WMS-443 R2/R3, C4/C15; решение3 явно использует организацию для различения людей.

**Место исправления:** `frontend/src/hooks/useAuth.ts:222–234`; `mobile/android/app/src/main/java/ru/wms/tsd/core/auth/IdentityAuthApi.kt:11`; соответствующие существующие формы PublicAuthScreen/LoginScreen. Сервер уже принимает `organization` в `backend/app/api/auth.py:65–68`, фильтрует его в `backend/app/services/auth_service.py:405–410`.

**Воспроизведение:** в двух организациях создать разрешённых сотрудников с одинаковыми ФИО и паролем, без email. Сервер без organization закономерно возвращает401, с organization каждой организации — правильный отдельный ID. Web всегда отправляет только full_name/password, Android NameLoginBody вообще не содержит organization. На обеих формах способ указать нужный контекст отсутствует. Для новых без-email сотрудников переходный логин обходом не является. Это не случай полного совпадения внутри одной организации, где отказ предусмотрен требованиями.

**Собственное доказательство:** существующий `test_homonyms_same_and_other_organization_never_select_first` запущен отдельно на новой SQLite `/tmp/wms-final-review-identity.sqlite`: **1 passed**. Он подтверждает401 без контекста и успешные разные ID с контекстом. Затем прослежены реальные тела обоих клиентов: получить подтверждённый этим тестом успешный путь пользователь не может.

**Минимальная правка:** передать предусмотренный R2 контекст организации из существующей формы входа в существующий API. Не делать ФИО уникальным, не выбирать первую запись, не показывать каталог чужих людей и не требовать email. Проверить обе формы на описанной паре организаций.

### F3 — P2: поздний preview кода A разрешает назначение непроверенного кода B

**Требования:** WMS-442 R9a/R11, C15/C16. Администратор подтверждает именно показанную очередь; изменение кода снимает прежний preview.

**Место исправления:** `frontend/src/screens/ff/warehouse-map/WarehousePrinterDialog.tsx:48–59`, `:69–76`. Связанная проблема устаревшего destination: `:31–38` без проверки версии перед setState.

**Воспроизведение:** ввести A, нажать «Проверить», задержать HTTP preview. Пока поле доступно, заменить код на B. changeCode убирает preview, но не увеличивает version. Приходит ответ A: сравнение request===version успешно, экран снова показывает Queue_A и «Подключить». Нажатие отправляет **нынешний B** в `/pair`, поскольку код в preview не захвачен. Backend законно назначает очередь B. Последующий GET уже не отменяет произведённую неправильную привязку.

**Собственное доказательство:** исполнен фактический TypeScript-компонент после transpile с управляемыми React hook/fetch адаптерами. Последовательность действий вызвана через обработчики отрисованного дерева. Assert: `/pair/preview` получил A, после задержанного ответа показывался Queue_A, `/pair` получил B. Это исполнение клиентской логики, не новый browser/production проход. Все коды синтетические, внешних запросов нет.

**Минимальная правка:** инвалидировать все зависимые ответы при изменении кода/склада/сессии/закрытии; хранить в preview проверенные код и склад, подтверждать только их при совпадении текущего контекста. Guard нужен и успешному readDestination/reconcile, а не только catch. Не блокировать дальнейшую работу склада. Воспроизвести задержанные A/B, смену склада и закрытие/повторное открытие.

### F4 — P2: обычное ожидающее задание печати нельзя проверить с текущего экрана

**Требования:** WMS-442 R1/R2/R5/R8, C5/C8/C10/C12.

**Место исправления:** `mobile/android/app/src/main/java/ru/wms/tsd/features/sorting/SortingScreen.kt:165–183`; `SortingViewModel.kt:250–252`, `:350–358`.

**Воспроизведение:** отправить первую этикетку. Нормальный202 содержит job.status=pending. finishKnownPrint сохраняет одновременно printJob и unresolvedPrint, что правильно для устойчивости. Но ветка job!=null рисует только «Печать ещё раз», открывающую выбор товара. «Проверить» находится в else-if и недостижима при любом известном pending/running job. Таймера чтения статуса нет. Даже когда программа ПК уже прислала квитанцию и сервер done, экран её не читает. Оператор выбирает следующую этикетку/ячейку и подтверждает, а confirmPrint молча возвращается из-за unresolvedPrint!=null. Получается нерабочая кнопка до ухода и повторного открытия документа; для running после рестарта та же проблема.

**Доказательство:** полный переход createSortingPrintJob→finishKnownPrint→Compose action→confirmPrint прочитан; сохранённый `SortingViewModelTest` на строках455–481 прямо фиксирует pending printJob вместе с unresolvedPrint, но не проверяет достижимость следующего действия в Compose. Это подтверждённая статическая причинная цепочка, не аппаратный прогон.

**Минимальная правка:** в существующем блоке результата дать доступ к чтению **того же** job при pending/running и корректно освобождать подтверждённое намерение после terminal ответа. Явную повторную печать при неизвестном результате реализовать по уже заданному R8 с новым UUID и предупреждением о возможном дубле, без автоматического повторного spool. Проверить «товар→квитанция→ячейка» в одном открытом документе.

### F5 — P2: автозавершение сортировки оставляет сохранённую печать без достижимого восстановления

**Требования:** WMS-442 R3/R5/R8, C4/C8/C12; интеграция с WMS-441 R5. Печать не должна останавливать размещение, её результат должен оставаться доступен после выхода и рестарта.

**Место исправления:** `mobile/android/app/src/main/java/ru/wms/tsd/features/sorting/SortingScreen.kt:72–75`; `SortingListScreen.kt:76–82`; `SortingViewModel.kt:313–317`.

**Воспроизведение:** создать print job в сортировке, оставить pending либо потерять его ответ после commit. Не меняя смысла размещения, завершить последнюю единицу. SortingScreen сразу вызывает onBack по documentDone, не учитывая сохранённый print. Сервер исключает done-документ из обычной очереди. Единственный дополнительный вход очереди ищет только cargo receipts. pendingSortingPrint читается лишь внутри SortingViewModel конкретного документа; после перезапуска выбрать этот done-документ в сортировке нельзя. Даже принудительное открытие маршрута снова закрывается по documentDone. Квитанция/ошибка и явное решение о повторе остаются недоступны.

**Доказательство:** прочитаны оба маршрута навигации, durable store и единственное место вызова recoverSavedPrint; сохранённые интеграционные smoke не включали «незавершённая печать+последнее размещение+рестарт». Новый device-проход не заявляется.

**Минимальная правка:** сохранить доступ к результату уже подтверждённой печати в существующем потоке после завершения документа; не удерживать складское завершение и не отправлять второй print автоматически. Учесть pending/running/lost-create и перезапуск, а также явный выход к другому документу. Не решать это новым статусом склада или новым разделом.

### F6 — P2: явный выход из cargo recovery снова автоматически открывает тот же документ

**Требования:** WMS-441 R7, C8/C9/C11. После ошибки оператор вправе выйти и открыть другой документ.

**Место исправления:** `mobile/android/app/src/main/java/ru/wms/tsd/features/sorting/SortingListScreen.kt:79–82`, `:117–127`; consumeRecoveryRequest `:95–96` очищает только текущее поле UI.

**Воспроизведение:** имеется сохранённый cargo A после потерянного ответа, дальнейшее чтение/повтор пока неуспешны. Очередь автоматически открывает A и потребляет recoveryRequestId. Оператор нажимает штатную стрелку назад, чтобы работать с B. LifecycleResumeEffect очереди вызывает load; сохранённый A вновь становится recoveryRequestId, LaunchedEffect немедленно открывает A. Цикл продолжается до удаления receipt; B не удаётся выбрать обычным возвратом. Это не новый запрет API, а фактическая блокировка навигацией.

**Собственное доказательство:** отдельный JVM-тест настоящего SortingListViewModel с сохраняемой cargo A дал `A→consume→null→load при возврате→A`. Конкретный автоматический onOpenRequest и повторный load подтверждены Compose-кодом. Device-артефакт [native-cargo-recovery.md](wms441-native-cargo-recovery.md) доказывает удачное восстановление после снятия fault, но не проход выхода к B при сохраняющемся fault.

**Минимальная правка:** однократный автоматический вход не повторять на каждом явном Back; помнить его потребление в жизни навигационного контекста, сохраняя сам durable receipt для последующего восстановления. Оставить доступ к другим документам и защищённый повтор A. Не удалять неопределённую попытку ради выхода. Проверить A fault→Back→B, затем возвращение A и повтор того же UUID.

## Что проверено в интеграции и что сохраняется из прежних доказательств

**Сортировка/приёмка.** UI loose использует атомарный apply_loose_putaway с документным замком, существующей distribution-line receipt и точным источником; рост posted, завершение и `_record_charge_if_done` проходят одним серверным путём. Cargo передаёт operation_id/inbound_request_id, сервер сверяет исходный объект и квитанцию, сохраняет transfer_group и не делает новое размещение завершённого cargo. Box расходует только remaining через серверный условный UPDATE; loose вычитает непройденные boxes/cargo. Современный web ограничил автоматический UUID replay именно верхней россыпью, а вложенный товар после неизвестности перечитывается, не воспроизводится физически. Сохранены [предыдущие независимые регрессии](wms441-astra-review.md) и последующее [нативное recovery-доказательство](wms441-native-cargo-recovery.md); старый F1 веб-повтора и старый F2 второго адреса cargo не объявляются вновь открытыми. F6 — другой непроверенный ранее переход.

**Печать.** Сервер использует существующие BackgroundJob/FbsPrintAsset, проверяет документ/товар/ячейку/tenant и конкретный connection; неизменяемый intent отличает повтор от нового задания. Подключение ПК ограничено print API; resolve_pairing берёт warehouse/connection lock, повтор уже использованной привязки не возвращает старый default. Claim исключает двух потребителей, файл проверяется по размеру/MIME/checksum; локальная outbox runtime не отправляет файл повторно после возможного spool, повторяет только квитанцию. Смена очереди сохраняет прежний connection у уже созданного задания. Существующий Android PrintManager FBS сохранён. Прочитаны [backend/web handoff](wms442-web-printer-implementation.md), [Android handoff](wms442-ui-implementation.md), тесты sorting_print/runtime. Эти механизмы не устраняют клиентские F3–F5.

**Идентичность.** User сохраняет прежний ID, новые full_name/job_title не меняют роль, должность не участвует в разрешениях. Legacy login и reset/set-password остаются; backend tests подтверждают непереатрибутирование событий, замену старого email-снимка связанным именем и запрет чужой правки профиля. Общие actor-подписи используют display_name, оба web header передают job_title; замечание об отсутствующей должности из раннего отчёта исправлено. Auth/PIN читает профиль до новой сессии и разделяет user/server/org. F1 расположен в отдельном FBS-кэше поверх этого рабочего auth, F2 — в клиентском доступе к уже работающему backend.

**ФБО/упаковка/расчёты.** Сохранено коробочное действие ТСД и существующий общий PackagingTask, устаревшая Android shelf-кнопка удалена без ручного нового этапа. Known packed/unpacked фиксируется при фактическом расходе, unknown не объявляется known; complete считает employee units из оставшейся работы, системные пересчёты не становятся отдельной платой селлеру. Прочитаны конечный сервис и [финальное независимое покрытие C20](wms444-astra-c20-source-rereview.md): шесть сочетаний классов источников, неполная раскладка, historical ready/work, set0/repeat0/новая unpacked, единичный возврат и отсутствие раннего ledger.
