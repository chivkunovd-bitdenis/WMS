# WMS-084: обычная отмена WB освобождает привязку, сохраняя наклейку

Ветка `codex/wms084-rebind`, база `origin/etalon`
`054897e270533d3e0fc65b651d420b3af8332fce`. Из-за заполненного диска checkout
создан sparse в постоянном `.worktrees/wms084-rebind`; canonical и UI не меняются.

## Проверенный контракт

Текущий диалог отмены обещает снять ошибочную привязку в WMS и WB, а не уничтожить
наклейку. `cancel_order_kiz` использует единственную существующую причину
`отмена оператором`; замена кода вызывает общий локальный обработчик с другой
причиной. Внешняя отмена — существующий DELETE метаданных WB, после успешного
ответа выполняется локальная отмена. Исключение/timeout не освобождают код.

Теперь именно операторская отмена WB снимает старую связь с PackagingTaskLine.
Физический код остаётся applied, прежний introduced сохраняется. available не
используется: существующие print SELECT выбирают этот статус без ограничения
source=pool и могли бы снова напечатать уже существующую наклейку.
Terminal/defective статусы не восстанавливаются. Обычная замена и Ozon сохраняют
прежний void-путь. Нового API, параметра, режима, поля или типа события нет.

Событие EVENT_VOIDED с существующей причиной `отмена оператором` остаётся записью
аннулирования привязки; состояние самого кода теперь applied/introduced. Причина
и ссылка события на прежнюю строку упаковки сохраняются. Исторические void-коды
не переписываются и повторно не допускаются.

Повторный WB bind допускается через узкую проверку: applied/introduced,
packaging_task_line_id отсутствует, нет ни одной FbsOrderMarking для этого кода
(включая rejected), есть существующее событие операторской отмены. Mutating claim
читает это под row lock кода с populate_existing. Контроль tenant/seller/product,
полный CIS/GS и уникальности FbsOrderMarking остаются прежними. Код получает новую
строку под тем же lock. Непривязанный applied без такого события не получает
нового разрешения. Ранее реализованный receipt admission не расширялся.

Происхождение pool/external_fbs сохраняется при повторном назначении. Старые
счётчики пересчитываются существующим cancel-кодом по оставшимся кодам строки;
новая строка получает печатный либо внешний код согласно source. Печать нового
кода, складское движение, изменение резерва, факта упаковки или начисление оплаты
при отмене не добавлены. Прочитанный staff_packaging_billing_service рассчитывает
оплату по упакованным единицам/фактам, а не этим двум счётчикам маркировки.

## Границы

Это исправление «отменить ошибочную привязку → отсканировать на другом заказе»,
а не атомарный перенос двух заказов. Новый WB PUT и подтверждение идут прежним
путём, включая существующее состояние неопределённого ответа. Проверки final
orders сохранены: разрешены new/in_supply/assembling/packed, остальные состояния
отклоняются существующим _get_order_for_kiz.

Ozon не объявляется исправленным: нынешняя общая отмена требует WB token и не
удаляет Ozon exemplar, хотя назначение реально отправляет exemplar/set. Нужен
отдельный контракт отмены конкретной позиции/экземпляра с сохранением остальных.
Ни реальных отмен, ни реальных HTTP, ни изменений credentials не выполнялось.

## Техническая проверка

- Два варианта API cancel→validate→commit→повтор того же ключа→попытка другого
  заказа: external_fbs/applied и pool/introduced. Проверяются сохранность full GS,
  source, PDF-артефакта, правильные старые/новые счётчики, одна привязка и отсутствие
  складских движений. Оба прошли на собственном файловом SQLite.
- Timeout WB DELETE сохраняет привязку/состояние; final in_delivery/shipped
  отклоняет отмену до HTTP. Прошёл.
- Существующий тест обычной confirmed replacement оставляет старый код void.
  Прошёл. В старых tape concurrency сценариях обновлены только три ожидания
  operator cancel: applied вместо void; ожидания новой печати не менялись.
- Первый файловый прогон: 3 passed, 1 skipped (PG), 1 failed на регистрации
  external fixture с `unable to open database file` при заполненном диске.
  Повтор только external case: 1 passed, 1,53 секунды. Scratch SQLite удалён.
- Ruff без cache по шести затронутым Python-файлам прошёл. Mypy с
  `--cache-dir=/dev/null` по трём service-файлам прошёл.
- PostgreSQL race подготовлен: первый bind задержан на mocked PUT, второй
  достиг реального ожидания row lock через pg_stat_activity, после первого commit
  второй должен получить duplicate_kiz. Выполнение и результат дополняются ниже.

### Дополнение: PostgreSQL, 09.09.2026

После освобождения места координатором перед созданием БД было 483 MiB свободно.
На собственной `wms084_rebind_race_20260909_01` выполнены ровно **5 проверок**:
новая гонка двух заказов за освобождённый код; печать одновременно с отвязкой;
отвязка перед ожидающей печатью; оба варианта (обычный/фоновый) задержанного
metadata GET, который не должен восстановить удалённую привязку.

Результат: **5 passed**, 5,42 секунды. В новом тесте второй запрос действительно
дождался PostgreSQL row lock; после успешного первого назначения получил
duplicate_kiz, и в БД осталась одна привязка. HTTP во всех сценариях подменён
тестовыми ответами, реальных WB-запросов не было. Полные наборы не запускались.

После завершения собственная БД удалена, выполнен локальный CHECKPOINT;
проверка pg_database вернула 0 для её имени. Чужие БД не менялись.

Браузерная приёмка и выкладка не выполнены; координатор проведёт короткую
проверку на синтетическом WB-эмуляторе после review и отдельного деплоя.
