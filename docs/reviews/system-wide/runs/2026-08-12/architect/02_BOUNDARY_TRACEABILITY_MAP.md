# Boundary and traceability map

## State ownership

PostgreSQL is the authoritative source for WMS documents, balances, movements, reservations, packing progress, local FBS/FBO snapshots, users, permissions and print metadata. Wildberries is authoritative for external orders, external supply/delivery state, WB warehouse binding data, stickers and QR assets; local tables are a reconciled working copy. The browser and Android device are clients, not owners of warehouse quantity. Generated print files may also live in configured object storage, with database metadata pointing to them.

The most important invariant boundary is: a local physical mutation must be committed once, an external call must be reconciled by durable external identity, and the UI/device must read back the committed object rather than infer success from a response animation.

## Separation and isolation conclusions

- FBS and marketplace unload/FBO are separate document families and reservation tables. They meet only through shared physical inventory, packaging/marking utilities, and availability math. This separation is structurally clear, but the shared-stock subtraction is asymmetric (`ARCH-P2-004`).
- Every reviewed service query normally carries `tenant_id`; product-to-seller ownership checks are explicit in the principal mutation services. JWT tenant mismatch is rejected in `backend/app/api/deps.py:69-106`, and delegated seller selection is revalidated against a same-tenant enabled delegation at `:34-66`.
- Those are static controls, not runtime proof. The requested cross-tenant object mutation/read test and limited-staff direct-route/API denial were not delivered, so tenant/seller isolation and authorization remain `STATIC_REVIEWED_RUNTIME_NOT_RUN`.
- Seller-shop manager eligibility contains email-marker and test-domain shortcuts in `backend/app/services/seller_shop_service.py:21-58`. The target shop still needs a stored, enabled same-tenant delegation, so this is not by itself a cross-seller data bypass; it is a brittle ownership policy that should be treated as configuration debt.

## Core invariants

| Invariant | Enforcement observed | Verdict |
|---|---|---|
| `on_hand` changes equal auditable movement deltas | Inventory service writes balance and movement together | Broken at the business-operation layer by double inbound completion: two valid transactions for one document operation |
| `quantity = quantity_unpacked + quantity_packed` | Packaging conversion updates the split inside the inventory transaction; fields exist on one balance row | Static implementation present; no database check constraint and no runtime invariant sweep in this review |
| `reserved <= on_hand` across all owners | Individual contours subtract some active reservations | Not centrally enforced; divergent owner sets create a static overbooking risk |
| A physical unit is packed at most once | FBS fulfillment has unique task/idempotency and active-order constraints | Strong for FBS when client sends stable identity; mobile does not send the key. Non-FBS pack progress has no request idempotency key |
| Tenant and seller never cross | Token tenant checked against user; object queries filter tenant; seller products checked against request seller | Static controls widespread; runtime cross-tenant/seller proof not run |
| FBS and FBO documents never alias | Different models, APIs and state machines | Structurally separated; only shared stock/packaging surfaces connect them |
