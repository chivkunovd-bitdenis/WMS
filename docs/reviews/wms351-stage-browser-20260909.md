## Граница внешних вызовов

До сохранений независимый read-only runtime-разбор Hubble подтвердил WB stock host `http://wb-emulator.railway.internal:8000`; `fbs_stock_sync_service._marketplace_stocks_url` формирует `/api/v3/stocks/501001` на этом base. У тестового селлера одна WB binding `042a7d0e-40db-466b-afe2-b84fe558b1ae`, склад WMS `307c0ccd-9a6b-41df-9180-f8ed68022237`, `served=true`, `stock_sync_enabled=true`. Ozon account/bindings у этого селлера отсутствуют. Общий Ozon transport staging реальный (`api-seller.ozon.ru`), поэтому другие аккаунты не использовались.

По прочитанной цепочке сохранения `_clear_product_publication` обходит bindings выбранной площадки и выключаемых продуктов; при нуле Ozon bindings в этом контексте внешнего обнуления Ozon нет. Включение планирует существующую публикацию только для изменённой площадки и этого селлера. Проверка Ozon ниже подтверждает сохранение флага в WMS, **не внешнюю публикацию или финальный ноль Ozon**. Секреты не выводились, не менялись и не выпускались.

## Что нажато и что перечитано

До изменения `POST /api/products/fbs-rule/bulk` вернул: `publish=true`, `publish_ozon=true`, `same_everywhere=true`, `percent=100`, `units_mode=false`, пустые `by_warehouse` и `units_by_warehouse`. `on_hand=60`, `reserved=9`, `free_stock=51`, `published_now=51`.

1. Снята только галка WB, нажато «Сохранить». `PUT /api/products/fbs-rule` — 200. Вложенное `rule` содержит `publish:false`, а поля `publish_ozon` в запросе нет. Повторное открытие: WB false, Ozon true; физический остаток 60, резерв 9, свободно 51, публикация 0.
2. В том же UI включён WB, сохранение 200. Передан только `publish:true` вместе с прежними параметрами доли. Повторное открытие: обе галки true.
3. Снята только галка Ozon, сохранение 200. Передан `publish_ozon:false`, поле `publish` отсутствует. Повторное открытие и чтение: WB true, Ozon false; остаток 60, резерв 9, свободно 51, публикация WB 51.
4. Без Ozon склада UI выключает возможность включить его галку обратно. По прямому разрешению root прежний Ozon true восстановлен существующим `PUT /api/products/fbs-rule`, без поля WB и без изменения доли/привязок. Ответ 200. Выполнены полный reload, открытие окна и независимый `GET /api/products/4cc917f5-0600-4d8b-8e55-1a975710d912/fbs-rule`: обе галки true, остальные перечисленные поля и числа совпали с исходными. Скриншот перечитан глазами. Диалог закрыт кнопкой «Отмена».

Цепочка: `FfProductsCatalogScreen.tsx` открывает `FbsStockDialog`; `changedPublication` отправляет только тронутую галку. `api/products.py` передаёт правило в `set_rule_for_products`, где отсутствующий флаг берётся из прежнего правила конкретного товара. Повторное открытие заново вызывает read API; результат выше получен из сервера, а не только из состояния React.

## Процентный FBO и оставшиеся наблюдения

В настоящем каталоге тот же процентный товар после reload показывает «В ячейках 60», «На ФФ 60», **«Свободный FBO 51»**. В диалоге видно «На складе 60 шт, занято 9 — свободно 51». Резерв учтён при выключенном поштучном режиме. Код release checkout уже содержит `0fc61502`: `stock_direction_service.distributions_by_product` вычисляет `quantity_free_fbo` с вычетом существующего FBS reservation независимо от `units_mode`. Это закрывает наблюдение о показе FBO для проверенного процентного товара; сценарий с именованным направлением не создавался и заново не исполнялся. `marketplace_unload_service` в обеих прочитанных ветках расчёта вычитает FBS reserve; реальная FBO-отгрузка этой проверкой не заявляется.

Окно при каждом открытии показывает красную ошибку загрузки складов WB. Точный повторный read-only `GET /api/operations/fbs-sellers/{seller}/warehouses` дал 502 с `detail.code=wb_upstream_error_401`. Сохранённая WB binding всё же отображается, и проверенные сохранения выше проходят. Этот путь вызывает `fbs_seller_warehouse_service.list_seller_warehouses` и **отдельный** `wildberries_marketplace_warehouse_api_base`; нельзя объяснять отказ по base stock-публикации или считать его отказом записи остатков.

Также при исходных двух true окно обещает «51 шт уйдёт в Wildberries и Ozon», хотя у селлера нет Ozon account/binding. Реальная Ozon отправка из этого текста не следует. Подтверждены независимость сохраняемых флагов и восстановление исходного состояния, но не весь внешний Ozon-контур. Нового кода под эти наблюдения не добавлялось.

Исходники приложения и канонический бэклог не менялись. Pytest, сборка и новое ревью не запускались: выполнены браузерные действия и ограниченное чтение. Сохранён только этот отчёт.
