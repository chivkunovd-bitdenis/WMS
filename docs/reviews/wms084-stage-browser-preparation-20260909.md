# WMS-084 / WMS-395: подготовка браузерной проверки

Это подготовка, не результат браузерной приёмки. До отдельного сообщения root
`deployment-ready` выполнены только GET и scoped SQL в READ ONLY. Скан, отвязка,
создание поставки, подготовка стикеров и печать не выполнялись.

## Разрешённые учебные объекты

Используется существующий tenant **WMS Staging**
`9c31f3f4-ce62-4c1f-891a-295b278f1e69`, селлер **Эмулятор WB**
`50110328-fa03-4604-b2e4-8ca27fc8bb41`.
Текущая сессия администратора проверена GET `/api/auth/me`: HTTP 200,
`fulfillment_admin`, tenant совпадает. Значение токена читается только в память
из уже предоставленного `.secrets/staging-token.txt`, в Git и вывод не попадает.

Пара заказов одного товара `3d6050c5-0d29-4612-9e30-e90ecbf9408a`,
SKU **EMU-CAN-PVZ-TRUE**, имя **Куртка демо ПВЗ** (сверено текущим SQL):

- A: **WB500033**, `cf303d12-426b-4a38-a59f-ac0c18ccb68b`.
- B: **WB500035**, `b620419c-79b3-4369-beb0-5fdc21c53ddb`.

Свежий SQL подтвердил у обоих `new`, `supply_id=NULL`, подбор/упаковку `pending`,
стикер `not_requested`, отсутствие маркировок. Root явно согласовал эту пару.
Общие ранее проверенные WB500038 и его код не используются.

Код `1be09c79-4fd1-465e-9688-a77183af289f` принадлежит тому же селлеру и пулу

Полная строка считывается в память непосредственно перед сканом.

Runtime WMS сообщает FBS host `wb-emulator.railway.internal`. Скрипт прекращает
работу при другом адресе, tenant, селлере, продукте или занятом fixture.
Восстановлением эмулятора владеет Huygens; этот сценарий его не перезапускает.

## Исполняемый сценарий

Файл: `docs/reviews/scripts/wms084-stage-browser.cjs`.
Без аргументов он выполняет только проверку существующей сессии и SQL-снимок.
`node --check` и этот read-only проход выполнены успешно. При первом проходе
исправлено имя FK в запросе резервов: `fbs_order_id`, а не `order_id`.

После сообщения root о готовности точного app deployment:

```sh
node docs/reviews/scripts/wms084-stage-browser.cjs --execute-after-deployment-ready=<полный SHA stage-выкладки>
```

Аргумент — фиксация внешнего разрешения, скрипт не объявляет deployment готовым
самостоятельно. Если runtime публикует `RAILWAY_GIT_COMMIT_SHA`, требуется
точное совпадение. До запуска root отдельно проверяет backend/frontend hashes.

Публичная подготовка создаёт только именованную поставку
**WMS-084 QA 2026-09-09 · 500033 → 500035**, с постоянным ключом идемпотентности
и двумя согласованными заказами. Генерируются обычные WB order-sticker assets;
аппаратный принтер и выдача этикеток ЧЗ не вызываются. При необходимости кнопка
«Начать работу с поставкой» нажимается в Chrome.

В одном headless Chrome, закрываемом через `finally`, выполняются:

1. Просмотр сгенерированных WB-стикеров и вкладки «Упаковка и маркировка».
2. Обычное поле `fbs-kiz-scan-input`: стикер A → КИЗ → реальный UI commit.
3. Маленький крестик `fbs-kiz-undo-inline` **в строке A**, затем подтверждение
   «Отменить КИЗ» в диалоге. Путь через меню перепечатки не используется.
4. То же поле: стикер B → та же строка КИЗ → реальный UI commit.

Снимки снимаются до подготовки, после подготовки, непосредственно перед КИЗ,
после A, после отвязки и после B. Для трёх операций КИЗ отдельно сравниваются
все балансы выбранного товара, набор IDs движений и резервы; изменения при
создании поставки не выдаются за результат маркировки.

После отмены тот же MarkingCode сохраняет физическое состояние, происхождение
и даты, теряет только привязку к строке упаковки. Публичный GET available-кодов
пула должен исключать его. После повторного скана требуется ровно одна новая
FbsOrderMarking для B с **тем же MarkingCode.id**, без старой привязки A.
В финале код остаётся на B и именованная QA-поставка сохраняется. Ручного
возврата кода в `available`, удаления истории, укладки или отгрузки нет.

JSON-доказательство не содержит токена, полной строки КИЗ или PDF. Скриншоты
показывают только согласованные синтетические данные. При частичном выполнении
скрипт сохраняет состояние и останавливается; повторный запуск не сбрасывает
fixture и не делает вид, что предыдущих действий не было. После реального
прохода нужно осмотреть изображения и отдельно закоммитить фактический результат.
