# WMS-445 — реализация FBS на ТСД

Мобильная реализация сохранена отдельными коммитами nested-репозитория `mobile`:
`ad945b29100db43bddb7b9da56855a119cb51d48` (`WMS-445 restore TSD FBS work context`) и
`67dc649` (`test(WMS-445): cover restored FBS add intent`).
Восстановимый исходный diff от APK11 (`af9693126d19d16918abd5cc7b7fbe99dfebc142`) находится в
[`artifacts/wms445/mobile.patch`](artifacts/wms445/mobile.patch).

Первый экран FBS по-прежнему начинается с заказов. Карточка теперь показывает
площадку, селлера, маршрут и статус; для Ozon дополнительно видны количества
каждой позиции, включая уже упакованные единицы. Компактная ссылка «В работе»
переключает тот же рабочий список на существующие поставки, не добавляя второй
длинный хвост поставок под заказами. Карточка и экран поставки показывают её
селлера, площадку, маршрут, состав и сохранённый прогресс.

Перед созданием или добавлением заказов ТСД показывает выбранный состав и его
контекст. В Ozon маршрут отображается как полученный способ доставки, без
выбора WB «ПВЗ/Склад». При добавлении скрываются только поставки, которые
явно противоречат известным полям ответа сервера; неполные данные не становятся
новым локальным запретом. Окончательное решение остаётся за серверным
контрактом.

Для create/add запрос сохраняется точный idempotency UUID и body до сети в
зашифрованном FBS-specific store. Ключ хранения содержит нормализованный server,
`tenant_id` и `user.id`, полученные через существующий authenticated `/auth/me`;
email и display name в ключ не входят. После перезапуска сохранённый выбранный
набор и диалог восстановления открываются в прежнем контексте, повторно
проверяют тот же запрос с тем же UUID и при ошибке оставляют повтор в том же
диалоге. Запись удаляется только после подтверждённого ответа сервера.

Проверено без устройства:

- `ANDROID_HOME=/opt/homebrew/share/android-commandlinetools GRADLE_OPTS=-Xmx1200m ./gradlew --max-workers=2 -Dkotlin.compiler.execution.strategy=in-process :app:testDebugUnitTest --tests ru.wms.tsd.features.fbs.FbsViewModelTest` — успешно.
- `:app:assembleDebug` — успешно.
- `:app:lintDebug` — успешно.

Целевые тесты включают несовместимость по известному контексту, повтор создания
после потерянного ответа с тем же body и восстановление сохранённого create после
перезапуска. Отдельный тест add после перезапуска проверяет, что повтор уходит в
тот же `supplyId` с тем же body, включая исходный idempotency UUID.

## Проверка на Эмуляторе-5580

Проверка выполнена на **Эмуляторе-5580**, а не на физическом ТСД, с debug APK и
только локальным synthetic API `127.0.0.1:18082`.

1. WB-заказ `445000005` селлера A создан в поставке
   `WMS445-android-wb-a` (`7354349e-645a-40ea-9b7c-45ff8676e790`). В карточке
   и создании были видны площадка, селлер и маршрут; далее на том же экране
   прошли подбор с выбором `WMS445-A`, упаковка, короб, подтверждение передачи
   и reread. Сервер сохранил статус `in_delivery`.
2. Ozon-заказ `445-b-0` селлера B создан в поставке
   `WMS445-android-ozon-b` (`4095c41a-8333-41f6-8279-bbc5034b826b`), не
   затрагивая общий `445-a-0`. Экран показал маршрут Ozon и две позиции с
   количествами 2 и 1. Кнопкой позиции первая была упакована двумя отдельными
   действиями, вторая — одним; затем созданы/наполнены короба, подтверждена
   сборка и передача. После reread статус также `in_delivery`.
3. Для буквенного Ozon-штрихкода проверен существующий debug receiver. Команда
   `adb -s emulator-5580 shell am broadcast --receiver-registered-only -a ru.wms.tsd.DEV_SCAN --es barcode OZN445200`
   дошла до экрана и дала предметный ответ «Сначала отсканируйте место, из
   которого снимаете товар». Это подтверждает action, extra и сохранение
   регистра кода. Полный Ozon-подбор через этот receiver до выбора места и
   списания не выполнялся: документ уже `in_delivery` и намеренно не менялся.
   Для BA сохранён свежий Ozon fixture, на котором проверяется штатная
   последовательность «место → OZN445200 → подбор».

## Сохранённые серверные следы

| Поставка | Подбор и упаковка | `inventory_movements` | Начисления `billing_ledger_entries` |
| --- | --- | --- | --- |
| WB `7354349e-645a-40ea-9b7c-45ff8676e790` | 1 событие `picked`, 1 упаковочная запись, 1 позиция в коробе | 0 | `fbs_order`: 1 × 4000; `packing`: 1 × 3000; всего 7000 |
| Ozon `4095c41a-8333-41f6-8279-bbc5034b826b` | 3 записи упаковки (2 + 1 единицы), 2 короба, 2 позиции в коробах | 0 | `fbs_order`: 3 × 4000; `packing`: 3 × 3000; всего 21000 |

Нулевое число `inventory_movements` — наблюдённый результат этих двух
сценариев, а не заявление о списании. У Ozon в сохранённом документе
`pick_status=pending`, потому что его полный подбор до передачи сознательно не
проводился; добавлять для этого новую блокировку доставки требование не даёт.

Нативно воспроизвести именно потерю ответа **после** commit для create/add пока
не удалось: общий API не имеет разрешённой fault-инъекции для этих двух POST.
Поведение зафиксировано двумя целевыми JVM-тестами; для сквозной проверки нужен
изолированный response-drop после commit у `from-orders`/add-orders, без
перезапуска общего контура. Сквозные C1–C15, независимое ревью и приёмка этим
отчётом не закрываются.
