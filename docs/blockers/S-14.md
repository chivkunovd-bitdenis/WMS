# Блокировки · S-14

> Экран: упаковка (`FfPackagingPage`).

## Блокировки

### B-01 · У открытого задания упаковки нельзя сменить склад

**Что блокируется.** Оператор не может сменить контекст склада, пока открыто
конкретное задание упаковки. Склад открытого задания не переписывается сессионным
контекстом очереди.

**Каким условием.** При `selected !== null` экран передаёт в
`WarehouseContextSwitch` склад `selected.warehouse_id`, заменяет обработчик смены
на no-op и задаёт причину недоступности в
`/Users/deniscivkunov/Projects/WMS/.worktrees/.night-worktrees/volna-9-recovery/lane-1-04-warehouse-switch/frontend/src/screens/ff/FfPackagingPage.tsx:1927`.

**Где живёт проверка.** На экране и на серверной границе. Экран не вызывает
`onWarehouseChange` для открытого задания. В
`/Users/deniscivkunov/Projects/WMS/.worktrees/.night-worktrees/volna-9-recovery/lane-1-04-warehouse-switch/backend/app/api/packaging_tasks.py`
нет `PATCH` или `PUT`, меняющего `warehouse_id`: идентификатор склада принимается
только при создании задания (`:368-387`), а последующие операции адресуются к
самому `task_id` (`:432-610`). Поэтому API не предоставляет путь смены склада уже
созданного задания; слои совпадают.

**Что видит оператор.** В переключателе показано фактическое имя склада задания,
а выбор недоступен с пояснением `Склад закреплён: открыто задание упаковки`.

**Как разблокировать.** Закрыть задание и вернуться в очередь упаковки; там снова
доступен сессионный контекст склада. Склад самого уже созданного задания не меняется.

**Зачем бизнесово.** Упаковка выполняется в физическом складе и ячейке задания.
Запрет не даёт показать оператору противоречивый активный склад, а затем выполнить
операцию по заданию другого склада; это сохраняет складской факт, очередь и
операцию согласованными. Правило соответствует S-14 в контракте карточки
`04-warehouse-switch` (`CONTRACT.md`, раздел 3): открытое задание показывает свой
склад и ячейку, без незаметной работы с другим складом.
