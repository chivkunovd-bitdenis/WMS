### 1. Кнопка «Остатки» отключена без привязки склада

**Что блокируется:** открыть диалог распределения остатков товаров по WMS-складам для выбранного WB-склада.

**Каким условием:** `disabled={!row.binding}` на строке 908 файла `frontend/src/screens/v2/FfFbsStockSyncScreen.tsx`.
```js
<Button
  size="small"
  variant="outlined"
  onClick={() => void openPool(row)}

  data-testid="fbs-stock-pool-btn"
  sx={{ minWidth: 0, px: 1 }}
>
  Остатки
</Button>
```

**Где живёт проверка:** только на экране (фронт). На сервере нет явной проверки перед открытием статуса; проверка там — только при синхронизации остатков в `list_active_stock_sync_bindings` (которая фильтрует по `is_active` и `stock_sync_enabled`, но сама структура данных биндинга не запрещает открытие диалога).

**Что видит оператор:** серая кнопка без всякого tooltip или пояснения. При наведении мыши ничего не появляется. Оператор видит только неактивную кнопку и вынужден гадать, почему нельзя открыть остатки.

**Как разблокировать:** выполнить привязку WB-склада к WMS-складу через UI (выбрать WMS-склад в выпадающем списке строки, что создаёт binding).

**Зачем бизнесово:** обоснование не найдено. Непонятно, почему нельзя открыть диалог остатков если привязка не создана — возможно, диалог позволяет создать распределение заранее, ещё до сохранения привязки? Нужно уточнить у владельца: это ограничение по дизайну или техническое?

### 2. MenuItem «Выгрузить остатки сейчас» отключена при нескольких условиях

**Что блокируется:** запустить синхронизацию остатков одного конкретного WB-склада к Wildberries прямо сейчас (вне фона).

**Каким условием:** `disabled={busy || !row.isMapped || !row.stockSyncEnabled}` на строке 934 файла `frontend/src/screens/v2/FfFbsStockSyncScreen.tsx`.
```js
<MenuItem
  onClick={() => {
    setRowMenuAnchor(null)
    void handleSync(row)
  }}
  disabled={busy || !row.isMapped || !row.stockSyncEnabled}  // ← блокировка
  data-testid="fbs-stock-sync-one"
>
  Выгрузить остатки сейчас
</MenuItem>
```
Где:
- `busy` = глобальный флаг: идёт какой-то синхронизация (запрос на сервер)
- `row.isMapped` = `binding?.is_active && wms && !technical` (привязка активна, WMS-склад не техн.)
- `row.stockSyncEnabled` = `Boolean(mapped && binding?.stock_sync_enabled)` (синхронизация включена в binding)

**Где живёт проверка:** на экране (фронт). На сервере в `start_fbs_stock_sync` (api/fbs_sellers.py:451) нет явных проверок активности binding — API принимает `seller_id` и опциональный `wb_warehouse_id`, затем вызывает `sync_seller_stocks`, которая вызывает `list_active_stock_sync_bindings` и фильтрует по `is_active` и `stock_sync_enabled`. Значит, сервер молча пропустит биндинг, если он не активен или stock_sync отключен, **но оператор получит кажущийся успех в UI, хотя на самом деле ничего не выгрузится** — это расхождение слоев!

**Что видит оператор:** серый пункт меню, без tooltip или объяснения. Если отключено из-за `!row.isMapped`, оператор не понимает, почему нельзя выгружать. Если из-за `!row.stockSyncEnabled`, оператор видит, что синхронизация отключена (в чипе сказано «публикация отключена»), но нет подсказки, как её включить.

**Как разблокировать:** (а) дождаться завершения текущей синхронизации (busy=false); (б) активировать привязку (binding.is_active=true); (в) включить синхронизацию остатков (binding.stock_sync_enabled=true, переключатель в UI).

**Зачем бизнесово:** обоснование не найдено явно. Логично заблокировать если синхронизация отключена (нельзя выгружать то, что отключено), но почему нельзя выгружать если привязка неактивна — не ясно из кода или документации.

### 4. MenuItem «Отключить сопоставление» отключена при нескольких условиях

**Что блокируется:** отключить (деактивировать) привязку WB-склада к WMS-складу и, как следствие, остановить синхронизацию остатков и обработку заказов на этот склад.

**Каким условием:** `disabled={!row.binding?.is_active || savingWbId === row.wbId}` на строке 954 файла `frontend/src/screens/v2/FfFbsStockSyncScreen.tsx`.
```js
<MenuItem
  onClick={() => {
    setRowMenuAnchor(null)
    setPendingDisable(row)
  }}
  disabled={!row.binding?.is_active || savingWbId === row.wbId}  // ← блокировка
  data-testid="fbs-stock-disable-binding"
  sx={{ color: 'error.main' }}
>
  Отключить сопоставление
</MenuItem>
```
Где:
- `row.binding?.is_active` — привязка уже активна (иначе нечего отключать)
- `savingWbId === row.wbId` — идёт операция сохранения для этого строки (блокировка от двойного клика)

**Где живёт проверка:** на экране. На сервере в `disable_binding` (backend/app/services/fbs_warehouse_binding_service.py:177-197, SERVER.md:1800-1806) есть явные проверки:
- `binding_not_found` (строка 189)
- `active_fbs_reservations` (строка 193) — блокировка: если есть активные резервирования FBS на этом binding, отключить нельзя

Сервер более строг: на фронте просто проверяем `is_active`, а сервер кроме того проверяет наличие активных резервов. **Расхождение слоев:** фронт может позволить нажать кнопку (binding активен), но сервер вернёт 409 `active_fbs_reservations`.

**Что видит оператор:** красный пункт меню (при активном binding). Нет tooltip'а. Если пункт отключён, оператор видит серый текст и не понимает почему — то ли привязка уже отключена, то ли идёт сохранение, то ли есть резервы?

**Как разблокировать:** убедиться что binding активен (`binding.is_active=true`) и не идёт операция сохранения. Если сервер вернёт 409 из-за резервов, нужно сначала очистить резервы.

**Зачем бизнесово:** отключение привязки — деструктивная операция (останавливает обработку), поэтому логично её блокировать. Но блокировка только на фронте, а сервер может вернуть ошибку (расхождение). Нужно синхронизировать проверки: либо все на фронте, либо все на сервере и фронт только отображает ошибку.

## Разошлись слои

### Блокировка 2: выгрузка остатков
- **Фронт:** отключает, если `!row.isMapped || !row.stockSyncEnabled`
- **Сервер:** в `list_active_stock_sync_bindings` фильтрует по `FbsWarehouseBinding.is_active.is_(True)` и `FbsWarehouseBinding.stock_sync_enabled.is_(True)`
- **Расхождение (подтверждено):** если вызвать API напрямую с неактивным/выключенным binding, сервер возвращает 200 OK с `bindings_processed=0` — оператор получает видимость успеха без реальной выгрузки. Фронт это закрывает блокировкой кнопки.
- **Уточнение по техническим складам (поправка к исходному описанию):** исходный BLOCKERS.md утверждал, что проверка `!technical` есть только на фронте. Это неверно: сервер тоже фильтрует технические склады через `is_auto_fbs_wms_warehouse(warehouse)` (fbs_autopoll_service.py:105). Расхождения по этому условию нет.

### ~~Блокировка 3: просмотр статуса синхронизации~~ — расхождения нет (снято по коду)
- **Фронт:** отключает, если `!row.binding`
- **Сервер:** `get_binding_stock_sync_status` (fbs_autopoll_service.py:180-182) делает `binding = scalar_one_or_none(); if binding is None: raise FbsStockSyncError("binding_not_found")` → HTTP 404.
- **Факт:** оба слоя одинаково запрещают операцию при отсутствии binding. Утверждение «сервер его разрешит» **не подтвердилось по коду**.

### Блокировка 4: отключение привязки
- **Фронт:** отключает, если `!row.binding?.is_active`
- **Сервер:** кроме проверки на наличие binding, есть дополнительная проверка `active_fbs_reservations` (строка 1792-1806 SERVER.md)
- **Расхождение:** фронт меньше проверяет. Можно нажать кнопку на экране, но сервер вернёт 409. Оператор не ожидает ошибку.

### 1. Ложное расхождение слоёв — Блокировка 3 («Статус синхронизации»)

binding — если нет записей, вернёт пустую структуру. Расхождение: экран блокирует чтение, сервер
его разрешит.»

**Что в коде:**
`backend/app/services/fbs_autopoll_service.py`, функция `get_binding_stock_sync_status`, строки 180-182:

```python
binding = (await session.execute(stmt)).scalar_one_or_none()

```

Это `FbsStockSyncError("binding_not_found")` → `_raise_from_stock_sync` → HTTP 404. Сервер не
«разрешает» чтение без binding — он возвращает ошибку так же, как фронт блокирует кнопку.
Расхождения нет. Запись в разделе «Разошлись слои» для Блокировки 3 **не подтвердилась**
и перенесена в исправленном виде прямо в описание блокировки в BLOCKERS.md.
