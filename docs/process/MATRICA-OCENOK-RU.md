# Матрица оценок: какая задача каким путём идёт

Оценка ставится **до** работы и определяет, сколько ролей задача пройдёт. Смысл матрицы —
соразмерность: задача на два файла не должна получать проектный документ на четыреста строк,
а новый денежный модуль не должен уходить в код без архитектуры.

## Оценка 1 — правка

Меняется поведение в одном-двух местах. Экран остаётся тем же: те же колонки, те же кнопки,
тот же смысл. Новых сущностей, таблиц и роутов нет.

Примеры: кнопка печатает не то, что показывает предпросмотр; список грузится целиком вместо
страниц; порядок сортировки не совпадает с лентой; залипший статус не снимается.

**Путь:** аналитик → тестировщик → разработчик → ревьюер → кликер → судья

Проектировщика нет: проектировать нечего, поведение уже описано. Дизайнера нет: вид экрана
не меняется. Продакта нет: решать нечего, есть правильное и неправильное поведение.

## Оценка 2 — фича на существующем экране

Меняется состав данных или набор действий на экране, который уже есть. Появляется новая
кнопка, колонка, модалка, вкладка. Сущностей не больше одной.

Примеры: кнопка «Сдать без Честного знака»; подтверждение при закрытии с несохранённым;
переключатель склада в рабочем месте; признак «можно на ПВЗ» в проверке способа сдачи.

**Путь:** аналитик → проектировщик → дизайнер-приёмщик (только если меняется вид) →
тестировщик → ломатель → разработчик → ревьюер → критик исполнения → кликер → судья

Продакт включается, только если у аналитика остались открытые вопросы.

## Оценка 3 — новый раздел

В системе нет ни экрана, ни ручек, ни постановки. Требуется решить, как это вообще устроено:
какие сущности, откуда данные, кто что видит, как считаются деньги.

Примеры: отчётность для селлера и ФФ; хранение с тарификацией; счета и учёт работ;
подключение нового маркетплейса.

**Путь:** аналитик → архитектор (ресёрч, варианты, границы) → **нарезка на фичи** →
дальше каждая фича идёт как оценка 2, независимо и параллельно

Нарезка обязательна. Раздел целиком одному разработчику одним заходом не отдаётся:
так рождается код, который компилируется и ломает соседнее, а переделка становится
пересборкой раздела вместо правки одной вещи.

## Совместная архитектура — на всю волну, а не на карточку

Независимо от оценки, **все задачи волны проходят один совместный архитектурный шаг**
после постановок и до исполнения. Один агент видит все задачи разом, ищет пересечения
и противоречия, правит постановки и задаёт порядок работ.

Покарточный архитектор остаётся только у оценки 3 — там нужен ресёрч и выбор варианта
именно по этой задаче.

Причина: архитекторы, работающие по одной карточке параллельно, не видят решений друг
друга. Два разумных по отдельности решения дают несовместимую пару, и обнаруживается это
в коде через восемь часов работы.

## Поперечные признаки — добавляют роли к любой оценке

| Признак | Что добавляется |
|---|---|
| меняется вид экрана | дизайнер-приёмщик после проектировщика |
| трогает деньги, остатки, резервы | ревью обязательно, круги правок не сокращать |
| появляется новый роут или таблица | тест обязателен вместе с кодом |
| задача уже сделана в другой ветке | путь обрывается: проверить и влить, а не делать заново |

## Чего матрица не делает

Не оценивает сложность в часах и не считает строки. Оценка — про **объём проектирования**,
а не про трудоёмкость. Правка может быть трудной в отладке и всё равно остаться оценкой 1,
если проектировать в ней нечего.
