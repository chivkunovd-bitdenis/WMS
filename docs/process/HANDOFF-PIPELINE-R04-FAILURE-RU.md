## 7. Системные дефекты процесса

### P0. Неверный порядок `ui-critic`

Сейчас:

```text
ux-architect -> ui-critic -> tester -> breaker -> dev
```

Должно быть по смыслу процесса:

```text
ux-architect -> tester/breaker -> dev -> reviewer -> ui-critic -> clicker -> ux-judge
```

Иначе `ui-critic` неизбежно проверяет старый код и останавливает карточку за отсутствие будущей реализации.

### P0. Баги идут без контракта

Сейчас:

```text
tester -> dev -> reviewer
```

Для экранных багов это ломает роль `screen-dev`, потому что она требует контракт. Минимум нужен короткий контракт/наряд перед dev, даже если это баг.

### P0. Старый owner/product gate всё ещё попадает в контекст

Контракты 07/08/09 сами остановили разработку до владельца. Это ровно тот сценарий, который должен был быть убран для ночной автономности: вопросы владельцу должны стать утренней повесткой, а не ночным стопом.

### P1. Парсер типа не понимает отрицательную коррекцию

Формулировка `нет, тип неверный: ... это домен` не была понята как `домен`, потому что рядом осталось слово `фича`.

### P1. `есть_находки()` слишком примитивна

`Нарушений не найдено` под `## Находки` стало находкой. Нужна структурная форма вердикта или нормализация отрицательных формулировок.

### P1. Reviewer смешивает рабочие артефакты стадий с реализацией

По 01/02 reviewer считал изменения `tests/cases/*.md` нарушением границ screen registry. Это тестовые артефакты стадии tester, а не изменение экрана. Процессу нужно либо отделять stage artifacts от implementation diff, либо явно разрешить такие файлы для роли tester.

### P1. Карточки не создают коммит реализации

Все ветки остались на `a5b3561`. Даже 03, где был diff реализации, не была закоммичена из-за reviewer-блока. Поэтому восстановимого результата карточек нет.

## 8. Что не делать при следующем запуске

Не надо просто перезапускать ту же волну как есть. Она снова сожжёт бюджет и снова упрётся в те же места:

- 01/02 снова придут к dev без контракта;
- 04-09 снова попадут к `ui-critic` до разработки;
