Автор: агент-архитектор процесса. Дата: 20.08.2026.
Основание: [задание](TASK-PIPELINE-ARCHITECT-RU.md), [реестр инцидентов](INCIDENTS-REGISTRY-RU.md),
фактическое состояние кода на 20.08.2026.

**Статус: проект. Не реализовывать до строки подтверждения владельца в разделе 12.**

---

## 1. Главная идея в одном абзаце

Существующий конвейер — это цикл вокруг **одного наряда**. Пачка не добавляет второй цикл;
она добавляет **фабрику нарядов перед ним**. Тридцать просьб превращаются в тридцать карточек,
карточки сводятся в один план с волнами, план режется на обычные наряды — и дальше каждый наряд
идёт по нынешним стадиям без единого изменения. Точка стыковки одна: `scripts/naryad.py new`.
Всё, что до неё, — новое. Всё, что после, — существующее.

Второе изменение, независимое от пачки, но обязательное: **лестница доказательства**. Сейчас
«проверено» означает у разных ролей разное, и из 24 инцидентов ни один не был найден тестами.
В конвейер добавляется ступень «проверено на реальных данных» между кодом и браузером, и статус
«сделано» не ставится ниже верхней ступени.

---

## 2. Что физически мешает пачке сегодня

Три конкретных препятствия в коде, не в теории:

1. **`tasks/_current` хранит ровно один slug.** На нём построены все хуки: карточка правил,
   `require_naryad.py`, сторож после правки. Тридцать одновременных нарядов туда не помещаются.
2. **Границы наряда считаются, но не сравниваются между нарядами.** `naryad.py` разворачивает
   экраны в список файлов и умеет показать общие файлы с владельцами
   (`screens.registry.json` → `shared`), но пересечение двух нарядов никто не вычисляет.
3. **Продакт-функции нет как роли.** Восемь агентов начинаются с `ux-architect`, которому уже
   нужен ответ «какой экран и что меняем». Кто даёт этот ответ — владелец в чате. При тридцати
   задачах владелец становится узким местом на входе и на приёмке одновременно.

Никого не убираю. `ui-critic` сужается: механику (кнопки, чипы, таблицы, цвета) уже считает
`ui_guard.py`, ему остаются формулировки, плотность и состав колонок — то, что регуляркой
не поймать.

### 3.1. Почему `product-analyst` — это продакт, а не аналитик-переписчик

Его вход — дословная просьба и код. Его выход — ответ на вопрос «что оператор делает сегодня
и что должен делать после». Не «добавить кнопку», а «оператор не может внести КИЗ, потому что
строки скана нет». Он **не проектирует экран** (это `ux-architect`) и **не решает, брать ли
задачу** (это владелец). Он выясняет предмет и цену: какие экраны, какие слои, какие блокировки,
что сломается у соседей, есть ли это уже в системе.

Последнее — прямая защита от `FfFbsPickList.tsx`: полноценный экран листа подбора, написанный
и не подключённый никем. Поле «уже есть в системе?» в карточке обязательное.

### 3.2. Почему `data-judge` — отдельная роль, а не расширение судьи

Из трёх случаев паттерна П2 два **не видны в браузере вообще**: QR на этикетке кодировал
технический `barcode`, а хранили человеческий номер; pydantic-схема молча выбрасывала поле
`value_tail`. Первое ловится сверкой этикетки прода с базой, второе — сверкой ответа API
с тем, что положил сервис. Живой браузер здесь бесполезен: он покажет прочерк, но не скажет,
на каком слое поле потерялось.

**`data-judge` не заменяет браузер ни в каком случае.** Он добавляет ступень между «прочитал
код» и «прошёл сценарий». Правило «проверка кодом и API вместо живого экрана не засчитывается»
остаётся в силе дословно.

## 4. Поток: одна задача (нынешний, с двумя вставками)

```
владелец в чате
   │
   ├─ мелкая полоса ─────────────────────────────────────────────┐
   │     наряд → screen-dev → guard → ui-critic → ux-judge →      │
   │     доказательства → влить                                   │
   │                                                              │
   ├─ обычная полоса                                              │
   │     наряд                                                    │
   │       ↓                                                      │
   │     [1]  ux-architect → CONTRACT.md ──────────── владелец ✓  │
   │       ↓                                                      │
   │     [1б] test-designer → CASES.md          ← НОВОЕ           │
   │       ↓                    (параллельно с [2], автор ≠ dev)  │
   │     [2]  screen-dev ∥ backend-dev                            │
   │       ↓                                                      │
   │     [3]  guard → ui-critic → reviewer                        │
   │       ↓                                                      │
   │     [4а] data-judge  ← НОВОЕ  (слои, таблица-свидетель)      │
   │       ↓                                                      │
   │     [4б] ux-judge (живой браузер)                            │
   │       ↓                                                      │
   │     [5]  доказательства → [6] влить в main                   │
   │                                                              │
   └─ аварийная ── минимальный фикс → [4б] → влить → вернуть в обычную
```

Стадия 0 (`solution-architect`) остаётся ровно как есть: новый домен → `ARCH.md` → подтверждение
владельца строкой с датой → только потом контракт.

**Вливание в `main` ≠ выкатка.** Прод WMS выкатывается вручную и только по явной команде
владельца. Поэтому наряд вливается в тот же день, а решение «на склад» принимается отдельно
и после приёмки. Это не послабление: это разделение двух разных рисков.

```

   │

   │                            (дословный текст, ничего больше)

   │        экраны · слои · блокировки · ценность · дубли · ≤2 вопроса
   │        └─ обязан завести в реестр блокировок каждое найденное правило
   │
   П2  pool.py plan  → машинная матрица пересечений (файлы из реестра экранов)
   │        ↓
   │   pool-architect (один, opus, видит все 30 карточек) → POOL.md
   │        волны · слияния · обязательная очерёдность · отклонённые
   │        · ёмкость волны числом · ≤5 вопросов на весь пул

   │
   П3  pool.py cut  → naryad.py new × N для волны 1, каждый в своём git worktree
   │
   П4  далее — обычный конвейер раздела 4, N нарядов параллельно
   │
   П5  pool-acceptance → ACCEPTANCE.md: одна страница на волну
   │        по задаче: просьба → что стало → скриншот до/после →
   │        уровень доказательства → таблица-свидетель → что не сделано
   │        ↓
   │   владелец пишет строкой: «принято P-01..P-14, вернуть P-15, P-22»
   │
```

Дельта к существующему конвейеру: **шесть стадий до наряда и одна после вливания**. Внутри
наряда не меняется ничего.

### 5.1. Как машина решает, что две задачи не пересекаются

Не на слово архитектора. `pool.py plan` для каждой пары задач считает пересечение множеств:

1. **файлы экранов** — `screens.registry.json` → `files` по всем `S-xx` из карточки;
2. **общие файлы** — `screens.registry.json` → `shared` (там уже записано, какие экраны
   завязаны на `src/api.ts`, `ProductPhotoThumb.tsx` и прочее);
3. **пути бэкенда** — из раздела «API и данные» карточки: роутеры, сервисы, модели;
4. **миграции** — любые две задачи с миграциями пересекаются всегда (порядок ревизий);
5. **общие таблицы БД** — запись в одну таблицу двумя задачами = пересечение.

Пустое пересечение → задачи идут в одну волну. Непустое → архитектор выбирает: слить в один
наряд (если это один экран — это уже правило `AGENTS.md`), развести по волнам или явно разрешить
с указанием, кто владеет файлом.

**В момент исполнения то же самое проверяется повторно**: `require_naryad.py` учится читать
список открытых нарядов и запрещает правку файла, попавшего в границы двух из них. Плюс
физическая изоляция — каждый наряд волны в своём `git worktree`, уборка worktree входит
в закрытие наряда (иначе повторится И24: тридцать осиротевших копий с 11.08).

### 5.2. Ёмкость волны — число, а не «максимум параллельности»

Ширина ограничена не числом агентов, а **числом одновременных живых браузеров**: стенд один,
`ux-judge` ходит по нему руками. Пока стенд один, судьи идут последовательно, и волна шириной
больше 6–8 нарядов упрётся в очередь на судью, а не в разработку. Это открытый вопрос №2
в разделе 11.

становится воротами и проверяет, что у каждого пункта статуса есть машинное подтверждение —
файл контракта, файл кейсов, папка доказательств, зелёный прогон сторожей. Незакрытый наряд
не попадает в `ACCEPTANCE.md` и не считается сделанным при подсчёте волны.

## 7. Ответ на прямой вопрос: какая стадия поймала бы каждый паттерн

| Паттерн | Стадия и ворота | Честно |
|---|---|---|
| **П1** правило в двух слоях (4 случая) | В8 реестр блокировок + `data-judge`, сверяющий оба слоя + кейс в `CASES.md`, дёргающий экран и сервер | машина **не докажет** эквивалентность двух реализаций; она заставит записать правило один раз и написать один тест на оба слоя |
| **П2** проверено не то (3 случая) | лестница доказательства + В9 + `data-judge` перед `ux-judge` | закрыт полностью: «сделано» ниже верхней ступени не ставится |
| **П3** немые сигналы (4 случая) | В10 таблица-свидетель; `docker build` и `Cache-Control` — в проверку выкатки | закрыт для фич; для инфраструктуры нужен отдельный сторож выкатки |
| **П4** артефакт не подключён (2 случая) | В11 + В12 | закрыт |
| **П5** статус без смысла | поле «ущерб при снятии» в реестре блокировок, пустое = кандидат в дефекты | закрыт частично: качество ответа проверяет человек |
| **П6** фон против ручного (2 случая) | **дыра** | ни одна стадия конвейера не ловит deadlock на 155 заказах. Нужна отдельная проверка «оператор и автоопрос одновременно» на копии данных — это не стадия, это нагрузочный кейс, и его надо завести отдельно |
| **П7** данные расходятся (3 случая) | **дыра** | два склада «основной», дубли карточек, товары в разных тенантах — это дефекты данных, а не кода. Конвейер кода их не ловит в принципе. Нужен ночной `data_guard` (см. 9.3) |

Две дыры названы честно и не заклеены стадиями, которые их не ловят.

### 8.2. Сторона первая: разработка смотрит на набор, когда пишет

До правки 21.08 момента «посмотреть» в потоке не хватало: `screen-dev` получал контракт,
написанный словами («кнопка Печать», «таблица заказов»), и мог выбрать вёрстку сам.

Что меняется:

1. **Контракт называет элементы именами из набора.** `ux-architect` пишет не «кнопка печати»,
   а `PrintAction`; не «таблица», а `DataTable` с колонками `TextCell`, `QtyCell`, `ProductCell`;
   не «статус», а `StatusChip tone="warn"`. Разработчик тогда не выбирает вёрстку — он собирает
   по спецификации.
2. **Дефицит объявляется до кода.** Нужного элемента в наборе нет → контракт обязан написать
   это отдельной строкой: «требуется `Modal`, в наборе отсутствует». Это заявка на пополнение.
3. **Пополнение — стадия между контрактом и разработкой.** Недостающий элемент пишется
   **в `ui-kit`**, а не в экран. Так набор растёт из реальных задач, а не из благих намерений,
   и не может отстать от экранов.
4. **Ворота В12**: новый экран или новая зона существующего экрана обязаны импортировать
   `ui-kit`. Старое не трогаем — храповик уже так и работает.
5. **Инструкции агентов дополнены**: BA/UX/Product/Dev/Guard обязаны называть и проверять
   компоненты из набора, а недостающий элемент фиксировать как `DESIGN_SYSTEM_GAP`.

### 8.3. Сторона вторая: «перекрасить все кнопки»

Сегодня операция невозможна. Проверка: регулярка по однострочному JSX находит 21 кнопку
с `variant`, а всего кнопок 283 — остальные многострочные, с пропсами вразнобой. Кнопки как
перечислимого множества не существует.

Что делает её выполнимой, по шагам:

1. **Один элемент — одно место определения стиля.** `PrimaryAction` уже такой: перекрасить
   все главные кнопки = правка одного файла. Вся ценность машиночитаемости достигается только
   через переезд экранов на набор — без переезда пункты 2 и 3 бессмысленны.
2. **Инвентарь элементов, генерируемый из кода.** С 21.08 `ui-inventory.json` содержит
   раздел `components`: какой элемент набора, какая зона, обязательные props, где он уже
   используется. Когда экраны начнут переезжать, «найти все кнопки» станет запросом к JSON,
   а «проверить, что после перекраски ничего не разъехалось» — прогоном `invariants.js`
   по списку экранов из инвентаря.
3. **Кодмод для переезда.** `scripts/ui/codemod_actions.py` механически заменяет тривиальные
   `<Button variant="contained">` → `<PrimaryAction>` в файлах одного экрана, запускается внутри
   наряда, результат проходит обычные ворота. Честно: кодмод возьмёт только простые случаи;
   кнопки с `sx`, обработчиками и условным рендером — руками. Сколько осталось, видно в базовой
   линии, и число обязано убывать.
4. **Порядок переезда** — по волнам, начиная с экранов, которые и так в работе. Переписывать
   56 файлов разом нельзя и не нужно.

## 9. Артефакт 2: реестр блокировок и то, что к нему прилагается

### 9.1. Состав

`docs/product/BLOCKS-REGISTRY-RU.md` — человеческий текст, `docs/product/blocks.json` —
машинная часть. На каждую блокировку:

| Поле | Пример из И1 |
|---|---|

| что видит оператор | кнопки «Начать работу с поставкой» нет |

Поле «ущерб при снятии» — детектор. Блокировка «кнопка только при `draft`» не защищала ничего:
сервер создаёт задание при любом статусе. Пустое поле = кандидат в баги, и стоило это
десяти зависших поставок.

Отдельным разделом — **правила, реализованные в двух слоях по-разному**: это паттерн П1,
главный источник инцидентов, четыре случая из двадцати четырёх.

### 9.2. Принудительное пополнение

`scripts/ci/rules_guard.py` по образцу `ui_guard.py`: храповик. Ищет в коде условия показа
и запрета (`disabled=`, `status ===`, `if ... raise HTTPException`) и считает, сколько из них
не имеют ссылки на блок реестра (комментарий `// БЛ-07` / `# БЛ-07`). Число не растёт.
Добавил блокировку и не описал — CI красный.

Пополняют агенты: `product-analyst` на стадии П1 обязан внести каждое найденное правило,
`ux-architect` — каждое новое из контракта. Владелец не пишет туда ни строчки.

### 9.3. Третий артефакт, которого владелец не называл: сторож данных
