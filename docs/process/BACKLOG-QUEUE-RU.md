# Единая очередь backlog

Машинный источник очереди — docs/product/backlog-queue.json. Он собирает незакрытые и частично закрытые пункты из docs/BACKLOG-2026-08-19-CHAT-RU.md, включая разделы D, F, I, K и клиентские входящие. Закрытый или подтверждённый как ошибка разбора пункт в очередь не переносится.

Каждый элемент имеет стабильный id вида `BLG-*`. `source_section` сохраняет трассировку к исходному разделу, `type` описывает характер работы, `priority` — важность, а `readiness` — ближайший допустимый вход в конвейер. `dependencies` содержит только IDs этой очереди: сначала закрываются указанные предпосылки, затем задача может получить собственную карточку.

Короткий `title` служит только для навигации. Обязательное поле `business_meaning` содержит минимум
три предложения: что происходит сейчас, какое бизнес-последствие это создаёт и какой результат
ожидается после задачи. Именно весь `backlog_item` с этим полем передаётся агенту; додумывать задачу
по одному заголовку запрещено. Читаемая версия полного списка лежит в
`tasks/20260820-night-bug-queue/BACKLOG-BUSINESS-MEANING-RU.md`.

`traits` и `suggested_stages` — начальная маршрутизация, а не разрешение на запуск. Значения `needs_product`, `needs_research`, `needs_arch` и зависимости означают, что до Dev нужны соответствующие Product/BA/Research/Architect артефакты, receipt или закрытие зависимости.

Для крупных входящих вроде `BLG-KC01` допускается поле `client_items`: это машиночитаемый
список клиентских подпунктов, каждый со своим повествовательным `business_meaning`. Такие подпункты не являются прямыми
Dev-задачами, пока Product/BA не разрежет их на отдельные карточки с экраном, контрактом,
тест-кейсами и границами файлов.

Очередь не является autopilot: `owner_approved_wave: false`, Product receipt и обычные гейты pipeline остаются обязательными. Изменение JSON должно сопровождаться `python3 scripts/ci/check_backlog_queue.py`; скрипт проверяет JSON, обязательные поля, повествовательное описание минимум из трёх предложений у каждой основной и клиентской карточки, уникальность IDs и ссылки зависимостей.

Минимальный управляемый запуск выбранной волны:

```bash
python3 scripts/pipeline/run.py start-wave --backlog-ids BLG-I04,BLG-I12 --owner-approved-by <owner>
```

После этого `dispatch.py` выдаёт агенту роль, модель и бюджет, а `advance`
принимает stage только с usage receipt.

Новые входящие требования 21.08 уже заведены в очередь:

- `BLG-I07` — capacity/performance remediation прода, включая свежий сигнал “система тормозит”.
- `BLG-K02` — блок аналитической отчётности для селлера и фулфилмента.

Аналитический блок намеренно стоит как `needs_research`: pipeline должен сам
пройти Product/Research/Architecture stages до разработки, а не получать готовое
ТЗ от диспетчера.
