# WMS-523 — Автозагрузка КИЗ: отдельный пул на каждую новую группу товар+GTIN

Запись задачи: [канонический бэклог, WMS-523](../KANONICHESKIY_BACKLOG.md#wms-523).

## 1. Исходный запрос и уточнения

> господи долбоёбы сосоздай новый пул прямо снйчас быстро для авпак по всем загруженным без пулов и бери задачу на исправление - по каждорму товару при автозагрузке, каждый пул кодов, это пул

Предыдущее уточнение владельца:

> пул — агрегация загрузки, не должен отсекать общие остатки товара

Срочное исправление уже загруженных AVpack-кодов выполняется отдельно. WMS-523
описывает постоянное исправление новых загрузок и не ждёт production repair.

## 2. Проверенный текущий процесс и цель

WMS-476 `auto_import_marking_codes` и `assign_import_rows_to_product` сейчас создают
новые `MarkingCode` с `pool_id=None`, прямым `product_id` и `import_batch_id`.
Если у товара есть хотя бы одна `MarkingPoolProduct`, `_code_filter_for_product` и
batch count переходят на связанные пулы и перестают учитывать прямые коды этого
товара. Поэтому успешная автозагрузка может быть видна в результате импорта, но не
попасть в общий доступный остаток и реальную выдачу печати.

Цель: каждая фактическая новая загрузка WMS-476 создаёт собственные обычные пулы по
группам `товар + GTIN`; те же правила действуют при ручном назначении остатка этого
auto-процесса. Старые пулы не переиспользуются и не объединяются.

## 4. Решение аналитика

Новая сущность не нужна: используются действующие `MarkingPool` и
`MarkingPoolProduct`. Граница пула — текущий import batch, товар и GTIN. Создавать пул
следует только после того, как для группы установлено наличие хотя бы одного реально
нового кода; пул и коды сохраняются одной транзакцией. Это выполняет запрос и не
возвращает ошибочное переиспользование пулов по одному GTIN.

## 6. Сверка с запросом

Новый пул на каждую новую загрузку покрыт R1–R3; запрет склеивания по GTIN — R2;
сохранность существующих данных — R4; отсутствие пустых/повторных пулов — R5;
обязательная сумма и реальная тестовая выдача «старый + две новые» — R6/C5;
изоляция seller — R7/C6; отсутствие UI, общей переделки и production-печати — R8.
Срочный AVpack repair явно оставлен за границей продуктовой реализации.

## Заключение

Продуктовый commit `664f41b160f0be7751ffe00262313fe180920409`
**принят по C1–C7 в локальной code/test границе**. Каждая непустая новая группа
`import batch + product + GTIN` получает отдельный обычный pool/link; auto и assign
не склеивают прежние пулы, сохраняют product/import/PDF/status/event и не оставляют
пустой пул при duplicate. Главный пользовательский результат проверен не только по
строкам БД: старый пул плюс две загрузки дают count=5 в каталоге и упаковке, а
packaging print service выдаёт пять различных кодов и обнуляет доступный остаток.

Независимый Opus 4.7 xhigh review проверил introduced delta и реальный print fixture
и завершился PASS без blockers. Повторно уже зелёные тесты reviewer не запускал.
Production deployment продуктового исправления и физическая печать не выполнялись.

В final release candidate `00bc9df62a887e8c5b1d80651009eff47e4dfa21`
продуктовый commit WMS-523 сохранён вместе с ранее принятыми WMS-469/483/514/519.
Merge-стык не ослабил R1–R8: developer получил 185 passed, Astra — 114 overlap
passed и high PASS exact merge SHA. Это final software acceptance; product deploy
и физическая печать по-прежнему не заявляются выполненными.

Отдельная срочная операция AVpack не смешивается с R8: script `5e615ca3` и evidence
`d541c1be` восстановили существующие production-данные — 408 кодов распределены в
27 пулов для 22 товаров, кодов без pool осталось 0; catalog/package readback дал
58 для PAL_BROWN_AV, 64 для XS и 68 для L. У кодов изменён только `pool_id`, а
production print не запускался. Этот repair закрывает старые данные, но не заменяет
выкладку принятого продуктового commit для будущих auto/assign-загрузок.
