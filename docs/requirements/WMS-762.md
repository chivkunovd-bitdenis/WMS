# WMS-762 · Печать этикетки на Windows всегда падает: «Windows не вернула номер задания»

**Статус:** В работе. Ветка fix/wms762-print-windows-startdoc от a253fbf89. Меняет только агент печати tools/print-agent (прямой WMS Print и старый агент с очередью). Сервер и веб не меняются. Новый zip для Windows собирает CI, публикацию релиза делает модератор.

## Жалоба (10.10.2026)

Клиент ArtMaks на Windows 11 запускает WMS Print, сканирует в WMS, и экран показывает «Windows не вернула номер задания». Ни одна этикетка не печатается, принтер и драйвер ни при чём. Серверных ошибок нет: все вызовы по поставке прошли, но ни одного отчёта «задание принято очередью» (applied) от этого клиента не пришло.

## Причина

Агент после StartDoc требовал целое число больше нуля (tools/print-agent/wms_print_direct.py, до правки строки 77–79; такая же проверка в wms_print_runtime.py, до правки строки 430–434) и иначе поднимал UnknownPrintOutcome. Настоящая библиотека pywin32 возвращает из StartDoc значение None и бросает исключение при ошибке. Это подтверждено на настоящей Windows, а не только по исходникам: на GitHub-раннерах windows-latest и windows-2022 (Python 3.13, pywin32 311, принтер «Microsoft Print to PDF») вызов win32ui StartDoc вернул type=NoneType repr=None, а страница и документ после него печатаются и создают PDF (2047 байт). Значит, печать на Windows падала при каждом успешном StartDoc. Тест с подделкой возвращал 442, поэтому ошибку не видел.

Второй дефект: ошибка после успешного StartDoc поднималась до блока, который вызывает AbortDoc, и в очереди Windows мог остаться незавершённый документ.

## Требования

- R1. Печать на Windows проходит, когда StartDoc вернул None (как настоящая pywin32). Квитанция для веба непустая и уникальная для каждой печати (веб требует непустой receipt, а сервер требует непустой queue_receipt для старого агента). Если драйвер всё же вернул целое число больше нуля, оно используется как номер задания. Класс: навсегда.
- R2. Задание не остаётся незавершённым. Любая ошибка после того как документ мог быть открыт (непонятное значение StartDoc, сбой StartPage, отрисовки, EndPage, EndDoc) вызывает AbortDoc. Если сам StartDoc бросил исключение, оператор видит понятную ошибку «Windows не приняла задание печати. Проверьте очередь принтера.», страницы не печатаются, контекст устройства освобождается. Значение StartDoc, которое не None и не целое больше нуля, — ошибка с отменой документа. Класс: навсегда.

Автоматического повтора и состояния «неизвестный исход» это не меняет: ошибки по-прежнему поднимаются как UnknownPrintOutcome, повтор без решения оператора запрещён.

## Что изменено

- wms_print_runtime.py: общие функции start_document и abort_document; WindowsAdapter.submit использует их.
- wms_print_direct.py: DefaultWindowsAdapter.submit_default использует те же функции.
- Квитанция: windows-<номер>, если номер вернулся, иначе windows-<12 hex знаков случайного идентификатора>.

## Что не охвачено

Физический принтер ArtMaks не проверен: «Microsoft Print to PDF» проверяет, что GDI-цепочка и агент проходят до конца и что StartDoc возвращает None, но не поведение конкретного термопринтера и его драйвера. Это проверка C5.

## Заключение

Итог: не принято. Код и автоматические проверки готовы, разработчик подтвердил их на Mac и на двух настоящих Windows-раннерах GitHub. Ревью отдельной сессией, приёмка аналитиком и ручная проверка C5 у клиента не проводились, поэтому задача не принята. Выпуск: новая Windows-сборка из CI, публикацию релиза делает модератор.
