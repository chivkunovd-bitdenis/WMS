# WMS-665 · Подготовка пробного вывода AVpack

## Исходный запрос и границы

05.10.2026 владелец поручил отдельному агенту найти первые четыре точных КИЗ AVpack/Виталия, привязать их к заказам и товарам и подготовить безопасный локальный скрипт для работы с ЭЦП Виталия. Фактический вывод из оборота, production-изменения и управление секретами не разрешены. Отдельное уточнение разрешило узкую production read-only выборку по точному tenant через существующий клиент проекта. Skills не используются по прямому указанию владельца.

В сегодняшнем Telegram не было самих КИЗ: сообщения владельца 317/320 просили их выгрузить, ранняя фоновая выборка остановилась из-за отсутствующей привязки. AVpack оказался фулфилментом (tenant), а не названием селлера. Прямой SELECT под ролью `wms_agent_ro` подтвердил tenant `d6e1ad21-8afa-4acf-8d0b-907b9f2adcfe`, пользователя Виталия и его активный домашний seller «ИП Горячкина Т.И.» `0b8da5d8-f43a-42f5-a2ec-43173ea844bd`.

## Требования

- R1. Сохранить точные четыре строки и источник. Выборка повторяет текущий eligibility WMS-517 (передача WB, не отменено/не возвращено, свой КИЗ, нет отклонения) и дополнительно требует `wb_status=sold`, отсутствие активного withdrawal claim. Это текущий статус WB в WMS, не доказательство из недельного финансового отчёта и не актуальная проверка статуса в ЧЗ.
- R2. Помощник работает только на production seller-странице вывода и только при подтверждённых через `/api/auth/me` tenant/seller и правах. Он не меняет доступ, серверные разрешения или данные.
- R3. Dry-run по умолчанию читает реестр за 18–19.09.2026, сверяет полный CIS, row_id, WB order id, статус `not_withdrawn`, отсутствие операции. Запросы только GET, без подписи и изменения выделения. По умолчанию один первый код; любой другой код выбирается явно из четырёх.
- R4. Execute повторяет проверки и только выделяет проверенные строки и открывает существующий диалог выбора сертификата. Он не нажимает «Подписать и отправить», не извлекает ключ, не подписывает, не вызывает POST. Окончательный запуск выполняет Виталий штатным интерфейсом после проверки состава и сертификата.
- R5. При несовпадении кода/клиента, отсутствии/дублировании строки, неизвестном заказе, процессе/завершённом выводе, ранее выделенных строках, другом сайте, ошибке API помощник останавливается. Токен сессии не попадает в результат или ошибки. После неоднозначной отправки пользователь проверяет существующую операцию, не создаёт повтор.
- R6. Инструкция объясняет установку CryptoPro CSP/Browser Plug-in, сертификата/драйвера токена; выбор сертификата по владельцу/ИНН/сроку и отпечатку; источник кодов, dry-run и execute. Физическая ЭЦП, PIN, успешная отправка/приём ЧЗ и браузер Виталия не считаются проверенными локальными тестами.

### Уточнение после production-проверки 05.10

В `billing_profiles` нет строки указанного seller/tenant. Для read-only роли действует политика чтения `true`, поэтому пустой результат не является скрытием строк. Функция `participant_inn()` прочитана непосредственно в работающем backend: она берёт ИНН только из этого профиля и выдаст `seller_billing_inn_missing_or_invalid`.

Ведущий передал прямое уточнение владельца: до открытия execute помощник обязан показать этот блокер и остановиться, не обходить вводом ИНН в скрипте. **R7 заменяет разрешающую часть R4:** текущая версия dry-run показывает проверенные строки и неизменяемый известный блокер; execute всегда останавливается до изменения UI. Ни флага обхода, ни ввода ИНН, ни создания профиля нет. Seller-readable GET профиля в текущем API отсутствует (чтение требует fulfillment_admin), поэтому блокер честно помечен как результат проверки 05.10, а не как свежая API-проверка. После отдельно разрешённого заполнения реквизитов нужна новая production read-only проверка и новая версия помощника; текущая версия execute не откроет диалог даже после внешнего исправления.

### Уточнение владельца и устранение блокера 05.10

Владелец прямо поручил взять реквизиты из уже подключённой информации WB о
селлере и сохранить их в карточке селлера. Штатный read-only вызов
`GET /api/v1/seller-info` вернул ИП Горячкину Татьяну Ивановну и ИНН
`132608771877`. Существующий идемпотентный путь WMS-547 создал один
`billing_profiles` для точных tenant/seller; повторное чтение подтвердило запись
и системное событие `data_changed`. Банковские поля и КПП WB не возвращает, для
вывода КИЗ они не нужны.

**R8 заменяет R7 после устранения блокера.** Execute обязан повторить все проверки
R2/R3/R5, убедиться, что на экране до запуска ничего не выбрано, выделить ровно
указанные проверенные строки и открыть существующий диалог выбора сертификата.
Помощник не вызывает POST, не выбирает сертификат и не нажимает «Подписать и
отправить». После явного действия Виталия существующий WMS-517 подписывает
challenge авторизации attached CAdES-BES и точные байты документов detached
CAdES-BES локально через CryptoPro; наружу уходят подписи, а не закрытый ключ.

Решение сохраняет существующий WMS-517 процесс и не создаёт второй True API клиент. Это операционный помощник для существующего экрана, без изменения самого фронта или бэка.

### Уточнение владельца: четыре КИЗа — только проба, цель сегодня — все проданные

Владелец уточнил, что четыре первоначальные строки нужны только для проверки
интерфейса. Операционная цель 05.10 — вывести все КИЗы этого seller, для заказов
которых WMS хранит точный статус WB `sold`. Production read-only выборка по тому
же eligibility WMS-517 дала 80 строк из 80 заказов и 12 товаров за 18.09–02.10;
активных withdrawal claim нет, у всех 80 есть валидный снимок финальной цены WB.
При этом текущий реестр содержит ещё 173 подходящие по старым условиям строки с
другими статусами WB. Поэтому штатное «Выбрать все» без ограничения небезопасно,
а фильтры даты и товара не отделяют все 80 от непроданных.

- R9. Для сегодняшней операции используется замороженный точный список 80
  `row_id`, полученный production read-only запросом с дополнительным условием
  `FbsOrder.wb_status == "sold"`. Полные КИЗы в новый скрипт и Git не сохраняются.
- R10. Новый локальный помощник сначала повторно проверяет точные tenant/seller,
  наличие каждой из 80 строк в текущем реестре, статус `not_withdrawn`, отсутствие
  связанной операции и отсутствие предварительного выделения. Любая пропажа,
  дублирование или изменение строки останавливает запуск целиком.
- R11. В execute помощник временно подменяет только GET списка реестра в текущей
  вкладке и показывает штатному React-экрану ровно проверенные 80 строк. POST и
  URL операций никогда не перехватываются. После этого он штатными элементами
  экрана выбирает все 80 и открывает диалог сертификата. При ошибке или смене
  seller-сессии исходный `fetch` восстанавливается; после перезагрузки вкладки
  подмена исчезает.
- R12. Подписание и отправка остаются полностью в существующем WMS-517: Виталий
  выбирает сертификат и явно нажимает штатную кнопку. Помощник сам не подписывает,
  не отправляет, не извлекает закрытый ключ и не создаёт операцию в БД.

### Уточнение владельца: запуск на macOS без DevTools

Виталий не должен открывать DevTools или вставлять JavaScript вручную. Владелец
поручил подготовить один `.command`, который на уже открытой авторизованной
странице вывода в Chrome загрузит проверенный помощник всех 80 строк и доведёт
подготовку до штатного окна выбора сертификата.

- R13. Один самодостаточный macOS `.command` использует системный `osascript`
  и уже работающий Chrome; установка Node/Python, скачивание кода при запуске,
  ввод логина/пароля и ручной JS не нужны. Обрабатывается ровно одна открытая
  вкладка точного production origin/path; отсутствие или неоднозначность вкладки
  останавливает запуск. После подготовки найденная вкладка и её окно выводятся
  на передний план. Вложенный помощник совпадает с проверенным исходником.
- R14. Запуск проверяет разрешение Chrome на JavaScript from Apple Events и
  macOS Automation. При запрете — короткая инструкция и отказ без повторных
  попыток; настройки разрешений сам скрипт не меняет. Токены, PIN, сертификаты
  и ключи не читаются/не выводятся оболочкой запуска; секреты остаются внутри
  существующего браузерного процесса.
- R15. Execute вызывается один раз, результат ожидается ограниченное время.
  Повторный запуск не создаёт вторую параллельную подготовку. Успех сообщается
  только после подтверждения `certificate_dialog_open` для 80 строк; ошибка или
  таймаут не вызывают автоматического повтора. Виталий сам выбирает сертификат
  и нажимает «Подписать и отправить». Подпись и отправка launcher не выполняются.

### Срочное уточнение владельца 06.10: исправить production-адрес

Исходные слова владельца: «Блять, и Виталику надо починить эту историю с выводом
кизов. Прямо сейчас на прод.»

Последующее уточнение владельца: «Я имею в виду его разовую ссылку вот эту».
Ведущий нашёл переданную инструкцию в Telegram 667 / outbox 342: ссылка на
страницу указывала неверный домен и возвращала 404; raw-ссылка GitHub на
`70c505acf6f7ce8202b94fcb16cc05545324eb3f/scripts/ops/avpack-sold-kiz.command`
возвращала 200, но содержала тот же неверный домен во вложенном помощнике.
Исправлению подлежит именно этот разовый запуск замороженных 80 строк. Старую
неизменяемую ссылку с SHA не переписывают: владельцу возвращают новую ссылку
на опубликованный исправленный файл. Это уточнение сохраняет R16–R18 и не
расширяет задачу на WMS-517.

Ведущий проверил HTTP-ответы: адрес
`https://sellerfocus.pro/seller/honest-sign/withdrawals` возвращает 404, а
`https://wms.sellerfocus.pro/seller/honest-sign/withdrawals` возвращает 200 и
seller-приложение. В коде seller-приложения существует маршрут
`/honest-sign/withdrawals` внутри `/seller`. При этом оба помощника, оболочка
запуска, генератор `.command` и инструкция содержат первый, неверный адрес.
Это объясняет, почему уже переданный Виталию конкретный файл не находит рабочую
production-вкладку. HTTP 200 сам по себе не подтверждает авторизацию, открытие
диалога сертификата, подпись или принятие документа ЧЗ; живой браузер проверяется
ведущим отдельно.

Решение аналитика: продолжить WMS-665 узким исправлением адреса существующего
помощника. Логика отбора всех фактически проданных кодов относится к отдельному
изменению WMS-517 и здесь не дублируется. Для этого исправления не нужны новые
экраны, серверная логика, таблицы или изменения production-данных.

- R16. Когда Виталий оставляет в уже работающем Chrome единственную вкладку
  `https://wms.sellerfocus.pro/seller/honest-sign/withdrawals`, исправленный
  `.command` и оба существующих помощника распознают её как production-страницу
  и продолжают прежние проверки. Точный origin (протокол и домен) —
  `https://wms.sellerfocus.pro`; путь прежний. Допустимость завершающего `/`,
  query и hash для оболочки сохраняется. Старый `https://sellerfocus.pro`,
  другой домен, протокол или путь не принимаются: помощники отказывают до
  сетевых запросов и изменения UI, оболочка не внедряет код в такую вкладку.
  Основание: поручение срочно восстановить существующий запуск и проверенная
  причина отказа, вместе с действующими R2/R5/R13.
- R17. При исправлении адреса сохраняются точные tenant/seller R2, замороженный
  состав 80 `row_id` R9, прежние проверки и безопасные отказы R10–R15.
  Успешная подготовка заканчивается только штатным диалогом для тех же 80 строк.
  Подпись и отправку выполняет Виталий: помощники и оболочка не выбирают
  сертификат, не нажимают «Подписать и отправить» и не создают POST операции.
  Основание: восстановление уже переданного файла в существующих границах
  задачи, без расширения на отдельную реализацию WMS-517.
- R18. Все способы запуска и инструкция используют один правильный адрес:
  `avpack-kiz-helper.js`, `avpack-sold-kiz-filter.js`,
  `avpack-macos-launcher.js`, `build-avpack-macos-command.cjs`, повторно
  сгенерированный `avpack-sold-kiz.command` и
  `docs/reviews/WMS-665-AVPACK-RUNBOOK.md`. Генерация воспроизводит сохранённый
  `.command`, а вложенные исходники точно совпадают с проверенными помощником
  и оболочкой; в исполняемом файле и инструкции нет старой рабочей ссылки.
  Основание: восстановить именно самодостаточный файл Виталия, а не только
  один исходник, по действующему R13.

## Заключение

Первоначальная подготовка прошла независимое ревью Astra high. После нового прямого
поручения владельца профиль реквизитов создан штатным путём и R8 зафиксирован
тестовым коммитом `afbaa0422` до изменения помощника: 6 тестов были RED, что
доказало старую блокировку. Первое повторное ревью нашло две гонки настоящего DOM
adapter; их регрессионные тесты зафиксированы отдельным тестовым коммитом
`86d7af1b6` до исправления и воспроизвели 3 RED. После исправления 38/38 тестов и
синтаксическая проверка проходят. Итоговое повторное ревью Astra high: PASS;
обе гонки повторно воспроизведены как безопасный отказ без открытого диалога.

Реальный вывод пока не выполнялся. Блокер ИНН устранён штатным production-путём,
но браузер Виталия, его сертификат и результат ЧЗ ещё не проверены. Execute должен
только подготовить точное выделение и открыть диалог: окончательный выбор
сертификата и действие «Подписать и отправить» остаются за Виталием. Удалённый CI
точного итогового SHA проверяется отдельно после публикации; merge/deploy не
выполняются.

После уточнения цели добавлен второй помощник для всех 80 WB sold строк. Его
контракт сохранён отдельным RED-коммитом `05bc6ea9b` до реализации. Локально
проходят все 53 теста вместе с первоначальным четырёхстрочным помощником.
Независимое повторное ревью Astra high на точном SHA `97a441a39` завершилось
PASS после исправления жизненного цикла локального фильтра, отката UI при смене
сессии и подключения нового контракта к CI. Публикация SHA и реальная проверка на
компьютере Виталия остаются отдельными шагами; фактический документ в ЧЗ не создавался.
Исходный агент постановки повторно сверил C8–C12 и выдал заключение **ПРИНЯТО**
именно для подготовки 80 строк к ручной подписи, не для фактического вывода в ЧЗ.

Расширение R13–R15 принято исходным агентом постановки после независимого
Astra high ревью и закрытия всех трёх P2 в ходе повторных проверок. Итог кода
`83c77ee2b0573c3e48a3398d47eeb6fbe8d54d1c`: один самодостаточный `.command`
без DevTools, 35/35 новых и 88/88 общих локальных тестов. Повторное ревью той же
сессии подтвердило PASS двух последних регрессий на системном JXA с подставными
объектами. Синтаксис и check_task_documents проходят. Приёмка относится к
подготовке и безопасному запуску оболочки; реальная машина Виталия, системные
разрешения, ЭЦП и принятие документа ЧЗ не проверены. Полный CI опубликованного
итогового SHA проверяется отдельно, production hotfix/merge/deploy не выполнялись.

Срочное исправление разового файла Виталия от 06.10 **ПРИНЯТО ПО КОДУ**
исходным агентом постановки по R16–R18/C16–C19 после независимого ревью
`vitalik_url_review` с PASS на точном SHA
`c42f4d318c094253ce82ba6947c80a342cda57e0`. Требования опубликованы до тестов
и реализации; отдельный тестовый коммит — `9cd974e01`. При приёмке повторно
прошли 106/106 целевых тестов, синтаксис четырёх JS/CJS исходников и `.command`.
Собственное сравнение с `70c505acf6f7ce8202b94fcb16cc05545324eb3f` подтвердило:
после обратной замены домена все шесть изменённых артефактов, включая
декодированные вложения, побайтово совпадают с исходными. Дополнительных
ограничений, изменений состава 80 строк, tenant/seller или действий подписи нет.

Исправленный файл опубликован. Ведущий получил по raw-ссылке GitHub точного
SHA c42f4d318 HTTP 200 и SHA-256
`79db92582937f423a62f42e2abca00a8cc6d24cdfde0d3d0dce47f1da2c4a559`;
аналитик независимо вычислил тот же хеш локального файла. Ведущий открыл
правильный production-маршрут в браузере и увидел seller login, без 404.
Это подтверждает доступность файла и страницы, но машина Виталия, его
авторизованная сессия, системные разрешения, реальный диалог ЭЦП, подпись,
отправка и принятие документа ЧЗ не проверены. Старый файл по старому SHA
не меняется; требуется новая ссылка на исправленный файл. Полный CI итогового
SHA после коммита приёмки ожидается. Merge в main и деплой серверного кода
не выполнялись; исправлен опубликованный разовый помощник для существующего
production-экрана. Логика всех фактически проданных кодов остаётся в WMS-517.
