# WMS-665 · Подготовка пробного вывода AVpack

## Исходный запрос и границы

05.10.2026 владелец поручил отдельному агенту найти первые четыре точных КИЗ AVpack/Виталия, привязать их к заказам и товарам и подготовить безопасный локальный скрипт для работы с ЭЦП Виталия. Фактический вывод из оборота, production-изменения и управление секретами не разрешены. Отдельное уточнение разрешило узкую production read-only выборку по точному tenant через существующий клиент проекта. Skills не используются по прямому указанию владельца.

В сегодняшнем Telegram не было самих КИЗ: сообщения владельца 317/320 просили их выгрузить, ранняя фоновая выборка остановилась из-за отсутствующей привязки. AVpack оказался фулфилментом (tenant), а не названием селлера. Прямой SELECT под ролью `wms_agent_ro` подтвердил tenant `d6e1ad21-8afa-4acf-8d0b-907b9f2adcfe`, пользователя Виталия и его активный домашний seller «ИП Горячкина Т.И.» `0b8da5d8-f43a-42f5-a2ec-43173ea844bd`.

## Требования

- R1. Сохранить точные четыре строки и источник. Выборка повторяет текущий eligibility WMS-517 (передача WB, не отменено/не возвращено, свой КИЗ, нет отклонения) и дополнительно требует `wb_status=sold`, отсутствие активного withdrawal claim. Это текущий статус WB в WMS, не доказательство из недельного финансового отчёта и не актуальная проверка статуса в ЧЗ.
- R2. Помощник работает только на production seller-странице вывода и только при подтверждённых через `/api/auth/me` tenant/seller и правах. Он не меняет доступ, серверные разрешения или данные.
- R3. Dry-run по умолчанию читает реестр за 18–19.09.2026, сверяет полный CIS, row_id, WB order id, статус `not_withdrawn`, отсутствие операции. Запросы только GET, без подписи и изменения выделения. По умолчанию один первый код; любой другой код выбирается явно из четырёх.
- R4. Execute повторяет проверки и только выделяет проверенные строки и открывает существующий диалог выбора сертификата. Он не нажимает «Подписать и отправить», не извлекает ключ, не подписывает, не вызывает POST. Окончательный запуск выполняет Виталий штатным интерфейсом после проверки состава и сертификата.
- R5. При несовпадении кода/клиента, отсутствии/дублировании строки, неизвестном заказе, процессе/завершённом выводе, ранее выделенных строках, другом сайте, ошибке API помощник останавливается. Токен сессии не попадает в результат или ошибки. После неоднозначной отправки пользователь проверяет существующую операцию, не создаёт повтор.
- R6. Инструкция объясняет установку CryptoPro CSP/Browser Plug-in, сертификата/драйвера токена; выбор сертификата по владельцу/ИНН/сроку и отпечатку; источник кодов, dry-run и execute. Физическая ЭЦП, PIN, успешная отправка/приём ЧЗ и браузер Виталия не считаются проверенными локальными тестами.

### Уточнение после production-проверки 05.10

В `billing_profiles` нет строки указанного seller/tenant. Для read-only роли действует политика чтения `true`, поэтому пустой результат не является скрытием строк. Функция `participant_inn()` прочитана непосредственно в работающем backend: она берёт ИНН только из этого профиля и выдаст `seller_billing_inn_missing_or_invalid`.

Ведущий передал прямое уточнение владельца: до открытия execute помощник обязан показать этот блокер и остановиться, не обходить вводом ИНН в скрипте. **R7 заменяет разрешающую часть R4:** текущая версия dry-run показывает проверенные строки и неизменяемый известный блокер; execute всегда останавливается до изменения UI. Ни флага обхода, ни ввода ИНН, ни создания профиля нет. Seller-readable GET профиля в текущем API отсутствует (чтение требует fulfillment_admin), поэтому блокер честно помечен как результат проверки 05.10, а не как свежая API-проверка. После отдельно разрешённого заполнения реквизитов нужна новая production read-only проверка и новая версия помощника; текущая версия execute не откроет диалог даже после внешнего исправления.

Решение сохраняет существующий WMS-517 процесс и не создаёт второй True API клиент. Это операционный помощник для существующего экрана, без изменения самого фронта или бэка.

## Заключение

Приёмка подготовки проведена исходным агентом, составившим постановку, после независимого ревью Astra high. Локальная подготовка принята в границах R7: четыре кода получены production read-only, 35/35 тестов и синтаксическая проверка проходят, инструкция дополнена после P2 ревью. [Отчёт ревью](../reviews/WMS-665-REVIEW.md). Тестовый контракт сохранён до кода: `9c0aa2028f33a049e50a9d63ab554fb08815ab69`, дополнение R7 — `4d0d8768b585231751fd19f7f10797c12cb703ac`; RED обоих — отсутствие ещё не созданного модуля. Исполнитель не менял ожидания тестов. Отдельный тестировщик подключил контракт в CI (`e2f60206ee06c48fc521adfdffa86d8131304be9`).

Реальный вывод не принят и не выполнялся: его блокирует отсутствующий профиль ИНН селлера; текущая версия execute намеренно остановится. Браузер Виталия/сертификат/ЧЗ не проверены. Наличие строки в БД не подтверждает её видимость в реальном браузере. Удалённый CI точного итогового SHA проверяется отдельно после публикации; merge/deploy не выполняются.
