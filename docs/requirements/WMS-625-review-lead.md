# WMS-625 — проверка ведущим агентом

## Проверяемый результат и границы

Проверяется сохранность прямой печати из релиза `.4`, совместный контракт браузера
и локальной программы, восстановление исходной операции и подключение обычного
WB-скана. Независимое ревью Astra high находится в
[отдельном отчёте](WMS-625-review-final.md). Этот документ не заменяет заключение
независимого ревьюера или приёмку аналитика.

Точная исходная сборка скачана по ссылке владельца. SHA256 ZIP:
`962a755b685d839adb545710878218efb7372d0c6cc655aa945fe0c18c4a60ef`.
Её `build.json` указывает исходный commit
`9a33b651c309796707053e1056c7f80dff7194d5`.

## Существенные замечания и решения

В исходной версии постоянный журнал сохранял только хеш и необязательную
квитанцию; PNG удалялась после отправки. Отказ до отправки и неизвестность после
отправки оставались одним `nil`, поэтому повтор мог навсегда застрять без
восстанавливаемого изображения. Новая программа сохраняет изображение,
контекст и состояние до обращения к очереди, а затем наблюдает очередь.
Само принятие системой не считается доказательством выхода бумаги.

При проверке совместной реализации ведущий передал исполнителям следующие
замечания:

- Асинхронный HTTP 202 без квитанции несовместим со старым браузером, ожидающим
  квитанцию. Новый асинхронный контракт включается явным `protocolVersion: 2`;
  старый клиент получает действительный результат ожидания, без выдуманной
  квитанции. Отказ/отмена не должны стать успехом только из-за прежней receipt.
- Сохраняемые tenant/user/WB order поля должны совпадать с контрактом браузера.
  Иначе правильное задание ошибочно выглядит чужим при восстановлении.
- Восстановленный повреждённый record нельзя распаковывать через принудительное
  извлечение необязательных размеров. Повреждение и отдельная PNG без JSON
  должны сохраняться как причина диагностики и запрет слепого повтора.
- Ошибка записи результата не должна оставлять захваченный lock. Ограничение
  числа пикселей проверяется до полного декодирования изображения. Ограниченный
  внешний процесс должен завершаться принудительно после истечения срока,
  включая случай игнорирования TERM.
- Повтор безопасно неотправленного задания не должен теряться между окончанием
  worker и удалением признака его активности. Исполнитель добавил повторное
  планирование сохранённого задания в этой границе.
- Дочерняя осознанная допечатка должна оставаться связанной с исходным заданием,
  а её успешный результат — проверяться браузером до завершения исходного
  заказа. Потеря дочернего record не является разрешением повторить прежний
  child key. Зарезервированный ключ должен защищаться и в `/reprint`, и в
  обычном `/print`.
- Позднее наблюдение очереди не должно затирать новую связь с допечаткой.
  Сравнение только статуса и времени с точностью до секунды недостаточно;
  требуется проверять весь исходный снимок записи.
- Обычный WB-скан должен сохранять свою попытку до server selection и свою QR
  до native dispatch. Нельзя переносить в него bulk-контроллер с автоматической
  упаковкой `quantity: 1` или молча освобождать server claim после неизвестного
  результата внешней печати.

## Заключение

Проверка ведущим выявила существенные разрывы между браузером, долговечным
журналом и внешней отправкой. Замечания переданы отдельным разработчикам;
продуктовый код ведущий не изменял. Runtime `53507d82` и frontend `7ecc4d99`
прочитаны; существенные замечания ведущего исправлены. Общий независимый вердикт
и заключение аналитика на момент этой записи ещё ожидаются.
Технические тесты не устанавливают причину конкретных 17 ночных пропусков и не
подтверждают физический выход этикетки.

## Итоговые доказательства браузера и пакета

01.10.2026 ведущий открыл реальный скомпилированный Mac runtime `53507d82`
с явным `--self-test-http` и подменённой очередью. В локальной истории Chrome
проверены поиск по `TEST625`, состояние «Ошибка очереди», исходная PNG, контекст
заказа, receipt и история saved → submitting → accepted → aborted.
Физический принтер не вызывался; тестовый процесс остановлен по его точному PID.

В ordinary browser fixture исходный baseline был selectedOrders=2/printPosts=3.
Потеря POST-ответа при обычном QR+ЧЗ дала order-3, selectedOrders=3/printPosts=4,
qrStarted=false/chzStarted=true и ordinaryChzCount=1. После выключения галочек
и reload прежние настройки и ключ остались в pending. Повтор дал accepted,
ordinaryCompleted=[order-3], selectedOrders=3/printPosts=4 и ordinaryChzCount=1.
Исходные PNG и размер 70×120 сохранились; массив bulk packed не изменился.
Это проверка настоящих helpers и хранилищ в Chrome, с подменёнными WMS/native API,
а не исполнение на production или доказательство бумажного вывода.

Mac-пакет `53507d82` локально собран оптимизированным Swift, подпись и self-test
проверены после распаковки. Кроссплатформенный
[workflow 36890473461](https://github.com/chivkunovd-bitdenis/WMS/actions/runs/36890473461)
завершился успешно для Mac arm64, Mac Intel и Windows x64. Его head —
`a8c00ece3a01d9d88ef9187ef897a7e47d78091c`; runtime-исходники в нём совпадают
с `53507d82`. Windows CI проверяет упаковку и тестовые адаптеры, а не реальный
принтер склада.

При совместном чтении также найдено различие контрольной суммы: Swift использует
размеры `58.0x40.0`, JavaScript/Python — `58x40`. Frontend `7ecc4d99` проверяет
точное изображение с этими двумя известными представлениями; произвольный hash
не разрешён. Для связанной допечатки сохранено обязательное булево подтверждение
риска. Окончательную проверку реального Swift-ответа выполняет независимый ревьюер.
