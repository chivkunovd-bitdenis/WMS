## Источники и восстановленный процесс

Актуальные [правила проекта](../../AGENTS.md), включая отсутствие обязательного завершения подбора/упаковки для открытия рабочих вкладок, выше старых документов.

1. [WMS-401](../KANONICHESKIY_BACKLOG.md#wms-401), раздел «Прямое поручение владельца»: отдельный FBS в настоящем приложении, первоначально **все заказы**, фото, ШК, поступление/срок; галочки → добавить в поставку. Подбор сканом — старейший ещё не подобранный подходящий заказ; источник ячейка/короб/палета/грузоместо сохраняется; зелёная строка и прогресс после возвращения. Упаковка — только признак, без складских изменений и блокировок. Крупная печать заказа, количество ШК/ЧЗ, QR в той же ленте, общая печать; QR заказа → ЧЗ через общий сервер. Короба: открыть, сканировать, закрыть, изменить количество, распечатать QR. Последующее прямое «ну так надо доделать» распространяет путь на финальную передачу через существующий сервер.
2. [WMS-363](../KANONICHESKIY_BACKLOG.md#wms-363) задаёт использование существующего Ozon-процесса и позиций отправления. [WMS-339](../KANONICHESKIY_BACKLOG.md#wms-339) фиксирует жалобу на навигацию по сущностям базы вместо работы сотрудника. Предложения старого HTML-макета не выдаются за согласованную замену всего приложения: текущая задача ограничена FBS.
3. [Финальный веб-handoff 06.08](../../tasks/fbs-operator-flow/FINAL_FBS_UI_HANDOFF_2026-08-06_RU.md) подтверждает контекст заказа/поставки, совместимость выбранных заказов, сохранение состояния и повторов, различие WB ПВЗ/склад. Его старые ограничения готовности и инструкции о моделях не переопределяют актуальные AGENTS и мобильную WMS-401. [Ранний correction-handoff](../../tasks/fbs-operator-flow/CURRENT_FBS_UI_CORRECTION_HANDOFF_2026-08-06_RU.md) — история отвергнутого разнесения упаковки и печати, а не разрешение вернуть прежние шесть обязательных этапов.
4. [APK11 recovery](../reviews/wms401-login-recovery-candidate-20260910.md), [Ozon implementation evidence](../reviews/wms363-astra-20260910.md): отделяют уже сделанное от оставшегося. История доказательств не заменяет приёмку новой сборки.
5. Применены актуальные навыки постановки/приёмки и продуктового решения из основного checkout `docs/reviews/2026-09-11-analyst-draft/skills/`, библиотека owner-cases (действие в контексте документа, срок Ozon не запрещает работу), failure-cases B01–B04, B06–B09 (повторы, внешняя неопределённость, переключение документа после ошибки).

Оператор ФФ работает с импортированными заказами выбранной площадки. Выбранные заказы формируют **существующую поставку FBS сервера**, либо попадают в уже существующую совместимую. Из её контекста доступны подбор, упаковка с маркировкой/печатью, короба и явная передача площадке. Это один документ в вебе и ТСД. Обычные отгрузки из другого раздела приложения не являются вторым способом провести тот же FBS-заказ.

### Проверенная исходная реализация

Мобильная база: `af9693126d19d16918abd5cc7b7fbe99dfebc142` (APK11), отдельный Git в `mobile`. Проверены FbsScreens.kt, FbsViewModel.kt, FbsModels.kt, FbsApi.kt, Navigation.kt, HomeScreen.kt. PROGRESS и материалы подписи не открывались согласно ограничению координатора.

Уже есть переключатель WB/Ozon, список всех заказов **перед** поставками, разбор дат с часовыми поясами, старейший подходящий заказ, признаки подбора, многопозиционный Ozon, общие API подбора/упаковки/ЧЗ/коробов/печати/передачи. Это сохраняем, а не реализуем заново. Упаковка при необходимости создаёт существующее задание через start-work; неверно утверждать, что этот вызов отсутствует.

Статически подтверждённые пробелы:

- `OrderCard` не выводит имя селлера, маршрут сдачи и обычный статус заказа; `FbsNamedRef` теряет идентификатор. Поэтому оператор не различает совместимость похожих заказов и состояние неподобранных строк. API worklist уже возвращает seller, склады, delivery_route, can_pvz и selection_blockers.
- `chooseSupply` показывает все активные поставки выбранной площадки, только имя, без проверки соответствия селлеру/складу/маршруту выбранных заказов. Веб уже выбирает совместимые поставки и объясняет пустой результат; сервер отклоняет несовместимость. Наличие серверного отказа не делает выбор понятным.
- Диалог создания показывает один и тот же выбор WB «Склад / СЦ» и «ПВЗ» для Ozon, хотя worklist возвращает маршрут Ozon из метода доставки. Само наличие этого выбора ещё не доказательство серверного сбоя создания.
- При нажатии «Создать»/выборе поставки диалог закрывается до ответа. Ошибка показывается над общим списком без состава и маршрута неудачной попытки. Повтор хранится лишь в текущей ViewModel; передача уже сохраняет запрос до сети. Создание после потери ответа/выхода требует отдельной проверки, нельзя объявлять дубль без воспроизведения.
- Открытие существующей поставки доступно через строку заказа либо длинный хвост «Поставки в работе». На карточке поставки не показаны площадка, селлер, маршрут и состав, только имя и счётчики; оператору приходится открывать операцию, чтобы увидеть заказы.
- Для Ozon кнопки упаковки всех позиций остаются одинаково доступными, пока весь заказ не packed; контракт экрана не показывает остаток упаковки каждой позиции. Это риск повторной упаковки уже завершённой позиции; необходимость исправления подтверждается сценарием C8.

13.09.2026 аналитик открыл в браузере изолированный `http://localhost:5197/app/ff/warehouse-map` и FBS `/app/ff/fbs`. В «Ячейках» визуально проверены светлая тема, читаемая иерархия, действия внутри рабочего блока и таблица. Веб FBS начинает работу с заказов и имеет группы статусов и фильтры. Данных FBS пока нет: этот проход не доказывает создание и проведение документа. Затем на выделенном emulator-5580 аналитик открыл настоящий APK11: Home → FBS, переключил WB → Ozon и вернулся назад. Оба экрана показывают «Все заказы» и «Заказов пока нет», переключатель площадки работает, навигация возвращает Home. Снимки фактически просмотрены; данные/складские операции не изменялись. Наполнение изолированной базы ещё требуется; статические пробелы выше не названы воспроизведёнными сбоями устройства.

## Решения аналитика и вопросы

**D1.** Сохраняем первую точку входа «Заказы» и добавляем рядом компактный доступ «В работе» к уже существующим поставкам FBS. Не дублируем поставки вторым длинным блоком под всеми заказами. После выбора/создания открывается один контекст поставки с составом и действиями. Это устраняет смешение очереди и документов без новой сущности и без общего перепроектирования главного экрана. Обычный раздел отгрузок остаётся самостоятельным процессом; его не удаляют ради FBS.

**D2.** Селлер/маршрут/статус — короткие текстовые строки в текущей карточке и шапке документа, по существующей теме Compose; не переносим вебовую широкую таблицу на узкий ТСД. Данные берём из общего ответа API. Для Ozon показываем известный метод доставки вместо выбора маршрута WB. Сервер определяет допустимую совместимость; отсутствие имени не подменяем другой площадкой или выдуманным маршрутом.

**D3.** Уже рабочие подбор, печать, ЧЗ, упаковку и доставку не переписываем. Исполнитель проходит обязательные проверки ниже и исправляет подтверждённые дефекты; наличие API-метода/юнит-теста не закрывает операторский путь. Сетевой агент печати не добавляется в WMS-445 и не может удалить имеющуюся Android-печать.

Неизвестного намерения владельца, требующего нового вопроса, сейчас нет: желаемый путь восстановлен из прямой WMS-401. Остаётся техническая подготовка синтетических заказов и отдельного эмулятора площадок для полного прохода. Никаких настоящих заказов или внешних действий ради приёмки.

## Проверки

Среда: изолированные API18082/UI5197, собственная новая БД; Android API24+ с APK предъявленного SHA. Нужны два селлера, WB ПВЗ и склад/СЦ, Ozon с двумя позициями и количеством минимум 2, новые/начатые/переданные заказы, одинаковый товар в старом и новом заказе, два складских источника с остатком, отдельный эмулятор WB/Ozon. Физический принтер/ТСД и live-площадки обозначаются отдельно и не подменяются эмулятором.

## Заключение

**WMS-445 не принята.** Сохранены реальные локальные положительные примеры WB и Ozon: device-документы дошли до `in_delivery`, Ozon API-emulator дал один create/approve/formed, расход3 и один набор начислений, а технический Astra-review закрыл FBS identity recovery. Однако ни одна составная проверка C1–C15 не имеет полного набора требуемых шагов на финальной интеграции. Подтверждённого дефекта после Astra closure нет; Terra handoff не требуется.

Приёмку блокируют нативная потеря ответа create/add после настоящего commit, оба маршрута WB, полный подбор Ozon, ЧЗ и восстановление после ошибки, раскладка по нескольким коробам, полный печатный набор и единое web/ТСД reread передачи. Реальные WB/Ozon, физическая передача, production, публикация APK и deploy не проверялись. Приёмку провёл новый Sol-аналитик как явная замена прежних BA-сессий.

## Уточнение владельца о моделях — 2026-09-13

По последнему уточнению владельца разработку выполняет Terra high. Бизнес-анализ, постановку требований, приёмку, независимое ревью и оркестрацию выполняет Astra. Сохранённые изменения и результаты проверок передавать следующему исполнителю, не повторять пройденные проверки без изменений или новых оснований. ## Дополнение аналитика: актуальность рабочей ленты — 13.09.2026

### Проверенные факты и предел доказательства

Ветка `codex/tsd-package-20260913`, исходный снимок перед этим дополнением `d9a85c1d`. В `FbsViewModel.loadOrders` Android вызывает `orders(marketplace=..., group=null, sort=oldest)`. `FbsApi.orders` обращается к `GET /operations/fbs-orders/worklist`. В `fbs_worklist_service._fetch_orders_page` отсутствие `status_group` означает отсутствие ограничения по статусам. Поэтому серверная выдача допускает завершённые, отменённые и переданные заказы, а старейшая сортировка выносит их наверх. Отдельный запрос поставок уже использует `status_group=active` с `draft/assembling/packed`.

Существующая группа заказов `active` не решает задачу: не включает `new` и включает `external_processing`. Для WB этот статус означает, что заказ ушёл в обработку кабинета вне нового складского заказа. Для Ozon в него отображается в том числе `awaiting_deliver`, если отсутствует сохранённый локальный этап складской работы. Синхронизация Ozon сохраняет локальные `in_supply/assembling/packed`: нельзя повторно классифицировать их по сырому статусу площадки и потерять собственную незавершённую поставку. Источники: `backend/app/services/wb_marketplace_orders_service.py`, `ozon_fbs_sync_service.py`, `fbs_worklist_service.py`, `fbs_supply_service.py`.

Группа API `new` дополнительно отсеивает WB по сроку; поэтому механическое объединение `new+active` также не выполняет R11. R1 и актуальные правила проекта не разрешают вводить запрет по возрасту/сроку. Этот анализ не подтверждает обязательный запрет WB по дедлайну; старый комментарий в коде не является доказательством такого обязательства. Изменение рабочего набора ТСД не должно переписывать состав существующих веб-групп или менять бизнес-статус заказа.

13.09.2026 в браузере открыт локальный FBS `http://localhost:5197/app/ff/fbs`: видны существующие «Новые», «В работе», «В доставке», «Просрочены», «Завершённые», «Отменённые». В текущем авторизованном контексте «Анна Тестовая WMS» лента пустая; это не контекст «Виталик Хорс». Визуально просмотрены FBS и эталон «Ячейки»; новый дизайн для этого дополнения не требуется. Android в этой аналитической сессии не переключался, чтобы не прервать общую приёмку; его вывод проверен по коду, не выдан за новый проход устройства.

Read-only запросы к локальной БД `wms_tsd_20260913` по `users.full_name`, `sellers.name`, `tenants.name` с подстроками «Витал»/«Хорс» дали 0 совпадений. В доступных сохранённых XML экранов `.local-run` это имя также не найдено. База содержит 18 тестовых FBS-заказов: WB 9 `new` и 3 `in_delivery`, Ozon 5 `new` и 1 `in_delivery`; завершённых/отменённых в этом наборе нет. Это подтверждает доступность локальной подготовки, но не идентифицирует клиента или его проблемные заказы. Production tenant, роли и ID заказов не установлены; реальную причину именно у «Виталик Хорс» ещё необходимо подтвердить по C21.

### Решение D4 и точная граница исправления

Начальная лента ТСД предназначена для текущей работы склада: новые заказы и заказы незавершённых складских поставок. Сохраняем имеющиеся статусы и навигацию; R11 задаёт набор, R12 — принадлежность. Не показываем в этой ленте доставку, завершение, отмену/брак и внешнюю обработку, где оператору не предлагается заново собирать заказ. Существующий контекст активной поставки остаётся доступным через «В работе»; скрытие её отдельного нерабочего заказа из начальной ленты не удаляет состав документа и не запрещает восстановить начатую операцию.

Набор должен оставаться полным при постраничной загрузке: страница старых нерабочих строк не может изображать конец списка, пока дальше есть рабочие заказы. Исполнитель выбирает минимальный механизм запроса/фильтрации без нового пользовательского режима, новой таблицы или статуса. Изменять веб по этому уточнению не поручено. Подпись «Все заказы» означает все заказы рабочего набора и не требует нового оформления.

При неактуальном локальном статусе исправление должно опираться на существующую синхронизацию и сохранённый результат площадки. Запрещено массово выставлять `done/cancelled`, прятать заказы по произвольной дате или менять реальные заказы ради проверки. Расхождение с площадкой воспроизводится на синтетических данных через существующий процесс обновления статусов. Контекст «Виталик Хорс» проверяется по настоящим идентификаторам учётной записи, tenant и seller; совпадения имени недостаточно. Для сотрудника склада без ограничения по селлеру допустимы все селлеры своего tenant. Если конкретный заказ окажется в действительно рабочем статусе и владелец считает его неактуальным по иному бизнес-признаку, сначала зафиксировать этот факт, не придумывать новый признак.

### Сверка уточнения и заключение

Жалоба на старую неактуальную ленту покрыта R11/C16–C19; названный клиент и границы доступа — R12/C20–C21. Отказ от произвольного срока следует из R1 и правил проекта; отсутствие новой навигации/дизайна — из прямого ограничения владельца. Существующие R2–R10 и C1–C15 не ослаблены и не объявлены пройденными.

Дополнение подготовил Astra-аналитик как новая сессия для уточнения о старых заказах; это не продолжение прежней Sol-приёмки и не самостоятельная приёмка реализации. Документ передаётся Terra high. Продуктовый код, данные и APK этой сессией не изменены. **WMS-445 не принята:** к прежним незакрытым сценариям добавлены C16–C21, а реальный tenant «Виталик Хорс» ещё не установлен.
