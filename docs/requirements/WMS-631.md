### Уточнения

**У1 (WMS-630, тот же вечер, слова владельца в пересказе ведущего).** В строке заказа есть
поле КИЗ; если курсор в этом поле и отсканирован КИЗ — он сразу (без подтверждений, без
окон) заменяет КИЗ именно этого заказа, дальше тот же процесс печати; если курсор не в
поле — скан работает как обычно. Это поведение должно сохраниться в обоих местах.
Уточнение из WMS-630: клик вне поля снимает выбор заказа и возвращает обычный скан.

**У2 (данные прода, сообщены ведущим).** 01.10 все 371 скан WB шли через сборочное задание;
02.10 00:20–00:40 пять сканов одной поставки шли через обычную поставку (старый путь),
сразу после этого владелец жаловался на окно печати Chrome.

## 2. Существующий процесс (установлено чтением кода)

Оба места — один компонент `frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx`, вкладка
«Упаковка и маркировка». Переключатель: `useSequentialPacking = Boolean(assemblyFrame?.registerScanner) && marketplace === 'wb'`.

### 2.1. Обычная поставка WB (открыта из списка FBS, без рамки сборки)

Над таблицей заказов — полоса скана `fbs-kiz-scan-bar` (показывается, только если
хотя бы одному заказу нужен ЧЗ): поле «Сканируйте QR стикера заказа», три галки
«Печатать QR», «Печатать ЧЗ», «Перепечатывать ЧЗ», блок выбранного заказа с кнопкой
«Сбросить». «Печатать ЧЗ» и «Перепечатывать ЧЗ» взаимоисключающие (вторая
неактивна, пока отмечена первая). Состояние галок хранится в браузере на
пользователя/арендатора (`loadFbsScanPrintPreferences`, по умолчанию все выключены).
В шапке панели — кнопки «Выбрать всё», «Печать всего/выбранного», «Проверить в WB»,
«Очистить ЧЗ», «Перенести в другую поставку», **«Всё упаковано»** (упаковывает все
заказы и завершает задание упаковки), «Сдать без Честного знака».

Разбор скана (`acceptPackingScan` → `scanIdleCode` / `scanKizCode`), по приоритету:

1. **Заказ уже выбран и ждёт ЧЗ** → скан считается КИЗ: проверка и сохранение
   (validate + commit, отправка в WB). Если у заказа уже был КИЗ — диалог подтверждения
   замены. После сохранения печатается **только при «Перепечатывать ЧЗ»**: точная копия
   отсканированного КИЗ. Повторный скан того же стикера снимает выбор.
2. **Стикер заказа WB (QR)** — распознаётся при **любом** состоянии галок
   (`lookupFbsOrderBySticker`): выбирает заказ и ждёт его ЧЗ. Ничего не печатает.
3. **Полный КИЗ при «Перепечатывать ЧЗ»** без выбранного заказа → прямая точная копия
   этого КИЗ (без привязки, без выбора заказа).
4. **ШК товара**: при всех выключенных галках — ошибка «стикер не найден» (сервер
   отвергает выбор заказа при всех выключенных режимах: `scan_auto_print_disabled`).
   Иначе сервер выбирает заказ (`scan-auto-print`) и:
   - «Печатать QR» → печать стикера заказа WB (QR) сразу после скана товара;
   - «Печатать ЧЗ» → сервер берёт свободный КИЗ из пула селлера, привязывает его к
     заказу и печатает его этикетку; скан ЧЗ оператором не нужен; товар без ЧЗ — ЧЗ
     не печатается;
   - «Перепечатывать ЧЗ» → заказ выбран и ждёт скан ЧЗ; после привязки печатается
     точная копия отсканированного КИЗ.
5. **Курсор в поле КИЗ строки** (`fbs-kiz-row-input`, WMS-630) → выбирает этот заказ;
   при наличии прежнего КИЗ **показывается подтверждение замены** (расходится с У1).

Скан **не упаковывает** заказ; упаковка — кнопкой «Всё упаковано».
Вся печать идёт через браузер: QR — `printFbsOrderQrAsset` → `printTapeSections`;
ЧЗ — `printMarkingCodeTape`; копия ЧЗ — `printMarkingCodeLabels`; все три в итоге
`printHtmlInIframe` → `window.print()` в скрытом iframe/окне. Это окно печати Chrome из
жалобы (У2). Этикетка ЧЗ — HTML: DataMatrix (bwip-js PNG) + «Честный знак», GTIN, КМ,
код (`buildCzLabelHtml`) или готовое изображение этикетки с сервера
(`label-artifact?format=png`, если у кода есть артефакт). Размер — сохранённый размер
этикетки `loadLabelSizeId()` (по умолчанию 58×40).

### 2.2. Сборочное задание WB (`FfFbsSupplyAssembly.tsx`, рамка `assemblyFrame`)

Над строками — общая полоса `FbsPackingScanBar` (поле скана + выбор размера этикетки
`LabelSizeSelect` + имя выбранного товара), полоса `fbs-kiz-scan-bar` с галками
**скрыта**, кнопка **«Всё упаковано» скрыта**. Остальные кнопки шапки — те же.

Механизм (`fbsSequentialPacking.ts`, `createPackingScanController`):
скан ШК товара → сервер выбирает заказ (`scan-auto-print`, всегда `print_qr:true,
print_chz:false, reprint_chz:false, await_honest_sign:true`) → если товару нужен ЧЗ —
ждёт скан ЧЗ → привязка (validate + commit; при прежнем КИЗ — `window.confirm`) →
печать QR через WMS Print (`dispatchPreparedQrInKiosk` → `POST http://127.0.0.1:17843/print`,
ключ идемпотентности = `scan_id`, размер = `loadLabelSizeId()`) → упаковка одной единицы
этого заказа (+ раскладка в открытый короб). ЧЗ не печатается никогда. Стикер заказа
(QR) как скан **не распознаётся** (сервер сравнивает только ШК товара `wb_barcode`).
Поле КИЗ строки → `scanOrder`: сразу замена (без подтверждения), печать QR, упаковка
(уже упакованный заказ повторно не упаковывается). Сбой печати оставляет заказ
выбранным до повторного скана его ШК.

### 2.3. WMS Print

`tools/print-agent/wms_print_direct.py` — служба на компьютере оператора,
`127.0.0.1:17843/print`, принимает одну PNG-этикетку `{imageDataUrl, idempotencyKey,
widthMm, heightMm}`. Перед отправкой в ОС пишет строку в свой журнал
`direct-jobs.sqlite3` (ключ, хэш, receipt пустой), после приёма очередью ОС — номер
задания ОС (receipt). Повтор того же ключа с тем же содержимым возвращает прежний
receipt без новой печати; если прошлый результат неизвестен — отказ без повтора.

### 2.4. Существующие механизмы для отката (установлено по коду)

- Удаление КИЗ заказа: `DELETE /operations/fbs-orders/{order_id}/kiz`
  (`deleteFbsOrderKiz`, крестик в строке и «Очистить ЧЗ») — удаляет SGTIN из WB и
  отвязывает код локально.
- Замена КИЗ: `commitFbsKiz` с `confirmed: true` — удаляет прежний код из WB и
  привязывает новый; требует **полного** значения нового кода. На странице известен только
  хвост прежнего КИЗ (маска), полный прежний код фронту не приходит.
- Убрать заказ из короба: `DELETE /fbs-supplies/{supply_id}/boxes/{box_id}/orders/{order_id}`.
- Отмена упаковки: `POST /operations/packaging-tasks/{task_id}/undo-last` существует, но
  для задания упаковки FBS-поставки **явно отказывает** (`undo_not_supported`,
  `packaging_task_service.undo_last_pack_action`). Распаковки одного FBS-заказа нет.
- Выбор заказа сканом (`scan-auto-print`) пишет событие `wms514_scan_auto_print`;
  каждое такое событие (кроме сканов поля строки `order:…`) **навсегда** исключает заказ
  из следующих выборов (`served_order_ids`), ключ резерва один на заказ
  (`_order_reservation_key`). Освобождения резерва нет. Выбор стикером
  (`lookupFbsOrderBySticker`) ничего на сервере не резервирует.
- Escape сейчас: в обычной поставке Esc в поле скана при выбранном заказе снимает выбор
  (`dropKizScanActive`), но резерв товарного скана на сервере остаётся; в сборке Esc
  передаётся рамке (`registerEscape`), выбор контроллера `pending` им не снимается.

### 2.5. Цель

В обоих местах — одинаковая панель (галки и кнопки обычной поставки), один механизм
скана (из сборки), и любая печать при скане (QR, ЧЗ, копия ЧЗ) уходит заданием в
WMS Print без окон браузера.

## 3. Требования

Обозначения: «оба места» = вкладка «Упаковка и маркировка» обычной поставки WB и
сборочного задания WB.

**R1. Галки в сборке.** В сборочном задании WB показываются те же три галки
«Печатать QR», «Печатать ЧЗ», «Перепечатывать ЧЗ» с тем же видом, подписями,
порядком и взаимоисключением, что в обычной поставке. Основание: «все галочки и кнопки
такие же … должно приехать из поставки».

**R2. Кнопки в сборке.** В сборочном задании WB видна кнопка «Всё упаковано» с тем же
действием, что в обычной поставке (упаковать все заказы этой поставки и завершить
задание упаковки). Прочие кнопки панели уже одинаковы и не меняются. Основание: то же.

**R3. Общее состояние галок.** Галки в обоих местах читают и сохраняют одну и ту же
сохранённую настройку пользователя (как сейчас в обычной поставке); включённая в одном
месте галка видна включённой в другом после открытия. Основание: «объединить»;
решение Д2.

**R4. Один механизм скана в обоих местах.** Обычная поставка WB принимает сканы тем же
механизмом, что сборка (последовательность «выбор заказа → при необходимости скан ЧЗ →
привязка → печать → упаковка заказа»); старый обработчик обычной поставки для WB
больше не используется. Основание: «механизм бесшовной печати и логика скана должна
прийти из сборочного задания … и наоборот».

**R5. «Печатать QR» включена.** Скан ШК товара → сервер выбирает заказ → если товару
нужен ЧЗ, ожидается скан ЧЗ и он привязывается → печатается стикер заказа WB (QR) →
заказ упакован. Это ровно текущее поведение сборки. Основание: «если галка включена,
печать QR, то работает то, что у нас сейчас работает».

**R6. «Печатать QR» выключена.** Оператор сканирует стикер заказа WB (QR), затем ЧЗ:
скан стикера выбирает этот заказ, скан ЧЗ привязывает код; стикер QR не печатается;
затем заказ упакован. Стикер распознаётся при любом состоянии галок (и при включённой
QR тоже — как сейчас в обычной поставке). Основание: «если галка отключена … ты
сканируешь QR, потом этот честный знак»; решения Д3, Д4.

**R7. «Печатать ЧЗ» включена.** Скан ШК товара → сервер выбирает заказ, берёт КИЗ из
пула, привязывает → печатается этикетка этого ЧЗ (вместе с QR, если отмечена
«Печатать QR»: сначала QR, потом ЧЗ) → заказ упакован; скан ЧЗ оператором не нужен.
Товар без ЧЗ — этикетка ЧЗ не печатается. Нехватка ЧЗ в пуле — ошибка как сейчас,
заказ не упаковывается. Основание: «печать ЧЗ … должны работать, как сейчас работают»;
решение Д5.

**R8. «Перепечатывать ЧЗ» включена.** После привязки отсканированного ЧЗ печатается
его точная копия (вместе с QR, если отмечена «Печатать QR»: сначала QR, потом копия ЧЗ),
затем заказ упакован. Полный КИЗ, отсканированный без выбранного заказа, как сейчас
печатает точную копию без привязки и без упаковки. Основание: «если включен
перепечать ЧЗ и печать QR, то я сканирую QR, сканирую ЧЗ, и он у меня ровно дубль
вылазит».

**R9. Все галки выключены.** Работает только путь R6 (стикер → ЧЗ → привязка → упаковка),
ничего не печатается; скан ШК товара даёт ту же ошибку, что сейчас в обычной поставке.
Основание: «как раньше и делали»; решение Д4.

**R10. Поле КИЗ строки (У1).** В обоих местах: курсор в поле КИЗ строки + скан КИЗ →
сразу, без подтверждений и окон, КИЗ именно этого заказа заменяется (прежний удаляется
из WB и отвязывается, новый привязывается и уходит в WB) → печать по тем же галкам, что
для обычного скана ЧЗ (QR — если «Печатать QR»; копия ЧЗ — если «Перепечатывать ЧЗ»;
«Печатать ЧЗ» на этот путь не влияет, т. к. код отсканирован оператором) → упаковка;
уже упакованный заказ повторно не упаковывается. Клик вне поля снимает выбор; без
курсора в поле скан идёт по R5–R9. Основание: У1; решение Д6.

**R11. Печать только через WMS Print.** Каждая этикетка, печатаемая при скане в
обоих местах (QR, ЧЗ из пула, копия ЧЗ), уходит отдельным заданием в WMS Print
(`127.0.0.1:17843/print`) как PNG; в упаковке WB при скане не вызывается печать
браузера (`window.print`, iframe, всплывающее окно) и не появляется окно печати.
Основание: «без появления этого модального окна печати, задание сразу должно лететь на
печать … железно».

**R12. Вид этикетки ЧЗ не меняется.** Этикетка ЧЗ, отправленная в WMS Print, по
содержанию и раскладке совпадает с той, что печатается сейчас (DataMatrix + «Честный
знак», GTIN, КМ, код; либо серверное изображение этикетки, если оно есть у кода), и
имеет тот же размер — сохранённый размер этикетки (`loadLabelSizeId`), что и QR.
Основание: «не должно поменяться то, как это выглядит».

**R13. Ровно одно задание на этикетку.** Каждое задание печати имеет свой постоянный
ключ идемпотентности (QR и ЧЗ одного скана — разные ключи); повтор после сбоя связи или
перезагрузки страницы не создаёт второго задания в WMS Print. Новое задание той же
этикетки возникает только от нового действия оператора, которое по R8 печатает копию.
Основание: «железно»; правило проекта о повторном списании одним запросом.

**R14. След задания.** По каждому скану можно доказать: задание пришло в WMS Print
(строка журнала с ключом) и было передано принтеру (receipt — номер задания очереди ОС).
Новых сообщений, окон и уведомлений в WMS для этого не добавляется. Основание: «мы
должны прямо увидеть, что это задание прилетело в нашу программу, и что потом оно
долетело … к принтеру» + «никаких новых уведомлений»; решение Д7.

**R15. Сбои.** Ошибка печати или привязки показывается в существующем месте ошибок
полосы скана; заказ остаётся выбранным, повтор скана его ШК (или стикера) завершает
именно его без повторной печати уже принятых заданий — как сейчас в сборке. Ошибка
привязки в поле КИЗ строки не захватывает следующие обычные сканы (как сейчас).
Основание: «железно», «не должны сбиться никакие функции»; решение Д8.

**R16. Ozon не меняется.** Обычная поставка Ozon и Ozon в сборке работают и выглядят
как сейчас (без галок, прежний обработчик). Основание: «никуда нельзя вообще лезть
больше».

**R17. Ничего лишнего.** Не появляется новых элементов, текстов, уведомлений,
всплывашек, окон и экранов. **Единственные разрешённые новые элементы:** кнопка-стрелка
«Назад» (R19, по прямому требованию владельца) и перенос галок (R1) и кнопки
«Всё упаковано» (R2) в сборку в том же виде. Окна подтверждения замены КИЗ в упаковке WB
убираются (R18). В обычной поставке не
появляется выбор размера этикетки и полоса сборки. Все остальные функции (печать
всего/выбранного, перепечать из строки, «Проверить в WB», «Очистить ЧЗ», перенос,
«Сдать без ЧЗ», крестик КИЗ, короба, подбор, состав) работают как сейчас.
Основание: дословный запрет владельца; решение Д9.

**R18. Никаких окон подтверждения.** В упаковке WB обоих мест нет ни `window.confirm`,
ни диалога подтверждения замены КИЗ. (а) Курсор в поле КИЗ строки — отсканированный КИЗ
сразу идёт именно в этот заказ (R10). (б) Обычный скан КИЗ для заказа, выбранного ШК или
стикером, у которого уже есть КИЗ, — сразу замена тем же механизмом (прежний удаляется из
WB, новый привязывается), без окна. Основание: У3 «никакой хуйни. если чз встаём в эту
строку, то то что отсканируем пойдёт именно туда».

**R19. Кнопка «Назад».** В полосе скана обоих мест — одна иконка-стрелка «назад»
(IconButton с существующей иконкой MUI, напр. `UndoOutlined`, размер small, подсказка
«Отменить последнее действие», тот же стиль, что у иконок строк), стоящая сразу после
галки «Перепечатывать ЧЗ». Неактивна, когда откатывать нечего. Каждое нажатие откатывает
**одно последнее** ещё не откаченное действие сканом в этой поставке, нажатия можно
повторять (обратный порядок). Без окон подтверждения. Откатываемые действия:
- (а) **запись ЧЗ сканом в заказ** (обычный скан ЧЗ, поле строки, ЧЗ из пула по «Печатать
  ЧЗ») — заказ возвращается к прежнему состоянию КИЗ: был пуст → новый КИЗ удаляется из WB
  и отвязывается (существующий `DELETE …/kiz`); был другой КИЗ → новый удаляется, прежний
  снова привязывается и уходит в WB (см. Д13);
- (б) **связь ШК товара / стикера QR с заказом сканом** — снимается выбор; если по скану
  заказ был упакован — снимается упаковка этой единицы и заказ убирается из короба, куда
  его положил этот скан; резерв выбора на сервере освобождается, и этот заказ снова может
  быть выбран обычным сканом.

Шаг истории = один скан оператора (Д14). Скан ЧЗ, который привязал КИЗ и упаковал
заказ, откатывается одним нажатием: упаковка снимается, КИЗ возвращается к прежнему,
заказ снова ждёт ЧЗ (выбор остаётся). Следующее нажатие откатывает скан ШК/стикера:
снимает выбор и освобождает резерв. Скан ШК, который сам упаковал заказ (товар без ЧЗ,
«Печатать ЧЗ»), откатывается одним нажатием целиком (упаковка, КИЗ из пула, выбор).
Глубина: все действия сканом с момента открытия страницы этой поставки/сборки; история
живёт только в открытой странице и пропадает при перезагрузке или закрытии.
Не откатывается: уже напечатанная бумага (задания WMS Print не отзываются); действия
кнопками («Всё упаковано», «Очистить ЧЗ», крестик, перенос); заказы, у которых задание
упаковки завершено, поставка передана/закрыта или заказ перенесён в другую поставку, —
кнопка для таких шагов выдаёт ошибку и шаг остаётся в истории. Сбой отката (WB не
ответил, сервер отказал) — текст в существующей строке ошибок полосы скана, шаг остаётся
в истории, повторное нажатие повторяет тот же шаг. Неизвестный исход удаления в WB не
повторяется вслепую (существующее правило сверки). Основание: У3 «стрелочку назад кнопку
аккуратную которая отменяет последние действия — запись чз сканом, связь шк и куаркода
сканом».

**R20. Escape.** Если начат скан (заказ выбран ШК или стикером и ждёт ЧЗ) — Esc в любом
месте вкладки сбрасывает выбор; серверный резерв этого выбора освобождается (следующий
скан того же ШК может снова выбрать этот же заказ); ничего не печатается и не
сохраняется; можно сканировать заново. Esc в поле КИЗ строки — выход из поля, обычный
режим скана. Когда ничего не начато, Esc ведёт себя как сейчас (в сборке — рамка окна).
Основание: У3 «шк пикнул, а чз нет … просто на эскейп сбросить это выделение и сканить
дальше заново».

## 5. Инварианты «железно»

- И1. В упаковке WB обоих мест при скане нет вызовов `window.print`, печати через
  iframe или всплывающее окно и нет системного окна печати (R11).
- И2. Каждое задание печати попадает в WMS Print ровно один раз; повтор по сбою связи,
  перезагрузке или двойному Enter не даёт второго задания; неизвестный исход не
  повторяется автоматически (R13).
- И3. Копия ЧЗ возникает только по «Перепечатывать ЧЗ» (R8, F2, F4, M16, M18).
- И4. Сбой печати или привязки не теряет выбранный заказ и не печатает соседний
  заказ; поле строки при сбое не захватывает следующие сканы (R15).
- И5. Ozon не меняется (R16).
- И6. Нет новых элементов, уведомлений, всплывашек, окон; вид не меняется, кроме R1–R2
  в сборке; прочие функции экранов без изменений (R17).
- И8. Ни одного окна подтверждения (`window.confirm`, MUI-диалог) в упаковке WB (R18).
- И9. «Назад» и Esc ничего не печатают; откат не трогает другие заказы; после отката
  выбора заказ снова доступен обычному скану (R19, R20).
- И10. Откат не теряется при сбое: шаг остаётся в истории до успешного выполнения (R19).
- И7. Один заказ упаковывается не больше одного раза за скан; замена КИЗ уже
  упакованного заказа не добавляет единицу (R10).

## 7. Принятые решения (аналитик, без владельца)

- **Д1. «Кнопки из поставки»** — это кнопка «Всё упаковано», единственная кнопка панели,
  скрытая в сборке (остальные уже показаны). Выбор размера этикетки остаётся только в
  сборке; в обычную поставку не переносится (иначе новый элемент; размер всё равно берётся
  из той же сохранённой настройки).
- **Д2. Одно хранилище галок** для обоих мест — существующее сохранение обычной
  поставки. *Риск:* у операторов, никогда не включавших галки, после выпуска в сборке
  «Печатать QR» будет выключена и сборка перейдёт на путь R6. Ведущему: перед выкладкой
  предупредить владельца/операторов или проверить их сохранённое состояние.
  **Решение ведущего (02.10.2026):** чтобы сборка утром работала как вчера, при ОТСУТСТВИИ
  сохранённого выбора «Печатать QR» считается включённой, «Печатать ЧЗ» и
  «Перепечатывать ЧЗ» — выключенными. Сохранённый оператором выбор уважается. Основание:
  01.10 все 371 скан сборки печатали QR; все 5 сканов из обычной поставки 02.10 00:20–00:40
  шли с print_qr=true (данные прода, document_event kind wms514_scan_auto_print).
- **Д3. «Сканируешь QR»** при выключенной QR = скан стикера заказа WB (как сейчас в
  обычной поставке, подсказка поля «Сканируйте QR стикера заказа»). Стикер распознаётся и
  при включённой QR (сейчас так в обычной поставке).
- **Д4. Упаковка по скану в обоих местах** (логика сборки), включая путь без QR; товар без
  ЧЗ после скана стикера упаковывается сразу. Кнопка «Всё упаковано» остаётся.
- **Д5. «Печатать ЧЗ» = текущий код:** ЧЗ из пула печатается по скану ШК товара; скан
  стикера (QR) ЧЗ из пула **не** печатает. *Спорно:* владелец сказал «сосканить QR, и у меня
  печатается честный знак» — в коде так не работает ни сейчас, ни раньше; выбрано «как
  сейчас работает». Нужен ответ владельца.
- **Д6. «Печатать ЧЗ» в поле строки** не печатает ЧЗ из пула (код отсканирован оператором).
- **Д7. «Увидеть, что задание долетело»** — журнал WMS Print (строка с ключом = пришло,
  receipt = передано очереди ОС) и очередь принтера ОС; в интерфейсе WMS ничего не
  добавляется, служба WMS Print не меняется (переустановка у операторов не требуется).
- **Д8 (пересмотрено по У3).** Сбой печати — как сейчас в сборке: заказ держится до
  повторного скана его ШК (или стикера) либо до Esc (R20); уже принятые задания не
  повторяются. ~~`window.confirm` замены КИЗ сохраняется~~ — **отменено владельцем**:
  окна подтверждения убираются везде в упаковке WB (R18).
- **Д9. Вне задачи:** «Печать всего/выбранного» и перепечать из строки (иконка) остаются с
  текущим окном предпросмотра — это не печать по скану, владелец её не упоминал.
- **Д10. Порядок печати** — сначала QR, потом ЧЗ/копия ЧЗ (как в текущем уведомлении
  «QR → ЧЗ» обычной поставки).
- **Д11. Где видны галки.** В обычной поставке полоса скана с галками сейчас видна, только
  если хотя бы одному заказу нужен ЧЗ; это условие сохраняется. В сборке галки видны
  всегда, когда видна общая полоса скана (она там есть всегда, а QR печатается и для
  товаров без ЧЗ).

- **Д12. Место кнопки «Назад»** — сразу после галки «Перепечатывать ЧЗ» в той же строке
  полосы скана (в обычной поставке — `fbs-kiz-scan-bar`, в сборке — там же, куда переезжают
  галки). Иконка из существующего набора MUI, без текста, с подсказкой. Для Ozon кнопки нет
  (Ozon не меняется, R16).
- **Д13. Возврат прежнего КИЗ.** Удаление нового — существующим `DELETE …/kiz`. Повторная
  привязка прежнего полного кода существующими средствами невозможна: фронт знает только
  хвост. **Нужно минимальное серверное действие** «откатить запись КИЗ скана»: по
  scan_id/событию привязки сервер берёт у себя прежний полный код и выполняет обычную
  замену (удалить новый из WB, привязать прежний, отправить в WB). Если прежний код сервер
  не хранит после замены — откат делает только удаление нового, заказ остаётся без КИЗ, а
  в строке ошибок пишется, что прежний КИЗ нужно отсканировать заново. *Спорно*, проверить
  разработчику по коду commit.
- **Д14. Шаг истории = один скан оператора**, откат всех его последствий (кроме бумаги).
- **Д15. Серверный откат выбора и упаковки.** Существующих средств не хватает: резерв
  `wms514_scan_auto_print` не освобождается ничем, а `undo-last` для FBS отказывает.
  Минимально: одно действие поставки «отменить скан» по scan_id, которое в одной
  транзакции снимает упаковку именно этой единицы (если её сделал этот скан, задание не
  завершено), освобождает резерв (событие отмены, после которого заказ снова кандидат;
  ключ резерва `_order_reservation_key` должен допускать новый резерв после отмены) и
  идемпотентно по ключу. Тот же вызов без упаковки — для Esc (R20). Короб — существующим
  `DELETE …/boxes/{box}/orders/{order}`. Выбор стикером резерва не создаёт — откатывается
  только на странице.
- **Д16. Глубина истории** — без ограничения в пределах открытой страницы; не хранится между
  перезагрузками (нет требования, а хранение = новая сущность).
- **Д17. Не шаги истории:** прямая копия ЧЗ (M16/M18), действия кнопками. *Спорно:* владелец
  может ожидать отката и «Всё упаковано» — не упоминал, не включаю.
