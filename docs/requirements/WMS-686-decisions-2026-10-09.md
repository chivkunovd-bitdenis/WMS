канону пишет подробное ТЗ → разработку ведут дешёвые агенты параллельно → стенд к 06:00 →
ведущий лично проходит экран по каждому пункту и сравнивает с текущим фронтом пиксель в
пиксель: кроме обсуждённого в задаче ничего не добавляется, не убирается и не меняется.

## 1. Факты кода, на которых стоят решения (проверено чтением)

- F1. Перенос короба целиком уже есть: `boxes/attach` → `attach_existing_box_by_barcode`
  (`marketplace_unload_box_service.py`). Для каждой позиции проверяется «подобрано + в коробе ≤
  план» (`collect_into_box`, код `plan_limit_exceeded`); всё в одной транзакции, при отказе
  ничего не сохраняется (сессия закрывается без commit).
- F2. Короб отгрузки хранит только `warehouse_box_id` (складской короб WHB). Короб приёмки (INB)
  находится как `InboundIntakeBox`, ссылка у короба отгрузки остаётся пустой; `_box_out` берёт ШК
  только из WHB → у перенесённого INB ШК в отгрузке пустой, а выгрузка XLSX для WB на таком коробе
  отказывает целиком. Прогон контракта 08.10: «ШК короба приёмки потерян». На бою 661 короб INB
  против 13 WHB — это основной случай, а не редкий.
- F3. Второй скан выбранного короба на подборе уходит в поиск товара → «Штрихкод не найден»
  (`marketplace_unload_pick_service.pick_scan` распознаёт тару только если тара в запросе не
  передана). В FBS это уже решено (`fbs_picking_service.py`, «новая тара заменяет источник»).
- F4. «Завершить» отгрузку FBO вызывает проверку маркировки через задание упаковки
  (`packaging_task_service.assert_unload_marking_done`) и при нехватке отдаёт **500**
  (`PackagingTaskServiceError` нигде не ловится).
- F5. Выработка упаковщиков (ФОТ) в коде: FBO — только по заданиям упаковки в статусе `done`
  (`staff_packaging_billing_service.aggregate_staff_billing`), FBS — по фактам упаковки заказов.
  Начисление селлеру за упаковку и отгрузку FBO уже идёт по составу коробов при «Завершить».
  На бою начислений упаковщикам по FBO за 60 дней — 0.
- F6. Экран подбора общий с FBS: `FfUnloadPickPage` (FBS вызывает с `source="fbs"`),
  `UnloadPickScreen` (групповая сборка FBS), `FbsCellPickTable` (+ хотфикс WMS-709), `DataTable`.
- F7. При ошибке ручной правки количества `FfUnloadPickPage.load()` увеличивает `version`, экран
  перемонтируется (`key`), теряются источник, раскрытие и история отмены.
- F8. На экране подбора `normalizeLayoutPunctuation` превращает GS (Ctrl+]) в «]» при русской
  раскладке; упаковка FBS (`FbsPackingScanBar`) принимает скан сырым (`emitRaw`) — жалоб нет.
- F9. Поле `barcode` в телах скана ограничено 128 символами; колонка `cis_code` — 512.
- F10. Мобильный ТСД вызывает: список и карточку отгрузки, `boxes` (создать, размер 60_40_40),
  `boxes/{id}/close`, `boxes/{id}/scan`, `ship`.
- F11. Ozon FBO идёт через тот же код (`marketplace` = `ozon`), XLSX сейчас только для WB.

## 2. Решения

### Общие правила

- D0.1. Всё новое — **только FBO** (отгрузки «на МП»). Поведение и вид FBS, групповой сборки FBS,
  ТСД-сценариев FBS и общих компонентов для FBS не меняются ни на пиксель. Общие компоненты
  получают новое поведение только через явный параметр, который передаёт FBO.
- D0.2. Никаких новых таблиц, журналов, статусов и режимов. Допустимы только три новые
  необязательные колонки (D3.1, D4.1, D8.1) одной миграцией от текущей единственной головы.
- D0.3. Документ упаковки (`packaging_task`) для FBO — рудимент: ни один шаг FBO не читает его
  статус, не ждёт его создания и не блокируется им. Таблица и строки остаются в базе как есть
  (не удалять, не мигрировать), новая логика FBO их не использует.
- D0.4. Каждый успешный шаг сохраняется на сервере сразу. Повтор запроса не удваивает результат.
  Ошибка не стирает ввод и выбранный источник.
- D0.5. Оператора не заставлять ждать WB/Ozon/ЧЗ: ни один шаг подбора, упаковки, извлечения,
  допечатки, XLSX и пропуска не ходит во внешние API.
- D0.6. Ozon FBO работает тем же процессом (подбор, упаковка, КИЗ, извлечение, «Завершить»,
  пропуск). Выгрузка состава для Ozon — только если у Ozon есть официальный файл/формат загрузки
  состава FBO-поставки (исследование — раздел 5); иначе для Ozon кнопки выгрузки нет.

### Подбор (вкладка «Подбор» отгрузки FBO)

- D1.1. По умолчанию вид «По ячейкам» (раскладка `FbsCellPickTable` с хотфиксом WMS-709:
  «План», «Осталось», раздел «Уже подобрано»). Над таблицей переключатель «По ячейкам / По
  товарам» существующим компонентом темы. Оба вида — над одними данными; переключение не
  меняет данные и выбранный источник.
- D1.2. В виде «По ячейкам» ячейки и короба сворачиваются и раскрываются (стрелка как у строк
  `DataTable`); в виде «По товарам» работает существующее раскрытие. Состояние раскрытия, вид и
  выбранный источник не сбрасываются при ошибке, перечитывании и смене вкладок документа
  (убрать перемонтирование по `version` для FBO; хранить в рамках документа).
- D1.3. Столбец «КИЗ» с крупным числом: число КИЗ, привязанных к этому товару в этой отгрузке
  (D3). В виде «По ячейкам» показывается в строке товара рядом с «План»/«Осталось» (как и они —
  число по товару в отгрузке). Клик по числу раскрывает под товаром вертикальный список кодов,
  повторный клик скрывает. Без зелёной рамки, обычные отступы и разделители темы; номер приёмки
  у кода можно показать второстепенным текстом. У кода в списке — «Перепечатать» и ✕ (отвязать
  ошибочный код).
- D1.4. Скан: ячейка/тара выбирает источник и держится до скана другой ячейки/тары (в том числе
  при уже выбранной таре — исправить F3 по образцу FBS); ШК товара → +1 штука из источника;
  следующий КИЗ → привязка к этому товару без +1. Повтор того же КИЗ — «уже привязан», без
  изменений. Код другого товара — отказ со звуком, код не привязан. КИЗ сверх подобранных штук
  товара — отказ «Сначала отсканируйте ШК следующей штуки». КИЗ без предшествующего ШК —
  привязывается к товару, если товар однозначно определяется по коду (уже известный код или GTIN
  кода совпадает с ШК ровно одного товара отгрузки), иначе «Сначала отсканируйте ШК товара».
- D1.5. Приём КИЗ со сканера — **тем же способом, что в упаковке FBS** (`FbsPackingScanBar`:
  сырой ввод, без замены GS), нормализация кода — одной существующей функцией FBS
  (`fbs_kiz_service`), без собственных разборов. Поле `barcode` скана принимает длинные коды
  (до 512 символов, как `cis_code`).
- D1.6. Двойной скан: второй скан **того же** ШК короба (сравнивается сырая строка со сканера)
  в пределах 2000 мс от прихода первого (время прихода кода, а не окончания обработки) →
  «Забрать короб целиком». Кнопка «Забрать короб целиком» в строке источника делает то же.
  Скан другого кода между ними разрывает пару. Третий быстрый скан и повтор запроса ничего не
  переносят и не показывают ошибку.
- D1.7. Перенос короба разрешён, только если по **каждой** позиции «в коробе ≤ план − уже
  подобрано» (существующая проверка F1, `allow_over_plan=false`). Иначе отказ всему коробу,
  ничего не меняется, существующий звук ошибки и красное сообщение с товаром и числами:
  «Количество товаров в коробе больше, чем осталось подобрать: <товар> — в коробе N, осталось M.
  Откройте короб и подберите поштучно». Товар не из плана — тот же отказ.
- D1.8. После переноса строки этого короба серые (подобрано), источник сбрасывается, на
  «Упаковке» появляется **тот же** короб (тот же ШК, D3.1) с тем же составом. Полностью
  подобранные позиции — серые и читаемые; частично подобранные отличаются от полностью.
- D1.9. Поштучный ШК сверх плана — отказ со звуком и красным текстом (уже работает, сохранить).
  Отказ по штуке не мешает привязать недостающий КИЗ.
- D1.10. Надпись «состав КИЗ тары неизвестен» не появляется нигде.

### КИЗ (единое хранение и единые правила)

- D3.0. КИЗ хранится **на строке товара отгрузки**: новая колонка `marking_codes.marketplace_unload_line_id`
  (nullable FK на `marketplace_unload_lines`, ON DELETE SET NULL, индекс). Связи «КИЗ ↔ короб»
  нет: товар связан с коробом составом короба, товар связан с КИЗ этой колонкой.
- D3.1. Привязанный к отгрузке код — занятый для всех остальных процессов. Одна функция-предикат
  «код занят» используется во всех местах, где сейчас «занятость» решается по
  `packaging_task_line_id` (`is_unbound_received_code`, `is_unbound_cancelled_wb_code`, привязка
  в FBS/Ozon, удаление кода приёмки, передача владения, выбор из пула только `available`).
  Без копий условия в разных местах.
- D3.2. Статусы: отсканированный код → `applied`; выданный из пула и напечатанный → `printed`
  (как сейчас). Код из пула при привязке перестаёт быть `available`. Напечатанный код считается
  нанесённым: при извлечении из короба и при «Завершить» связь с товаром отгрузки не снимается
  и код в свободный пул не возвращается. Отвязка — только ✕ оператором (ошибочный скан).
- D3.3. K (КИЗ товара в отгрузке) — только вычисление `COUNT` кодов с этой строкой отгрузки;
  никаких независимых счётчиков. Существующие 71 код FBO, привязанные к строкам заданий
  упаковки, миграция один раз связывает со строкой отгрузки (та же отгрузка и тот же товар).
- D3.4. Если «подобрано» по товару уменьшилось ниже K (ручная правка подбора) — отвязываются
  последние привязанные коды, оператор видит, какие (без блокировки).
- D3.5. Отмена отгрузки отвязывает её КИЗ.

### Упаковка (вкладка «Упаковка» отгрузки FBO)

- D4.1. Короб, перенесённый целиком из приёмки, помнит свой короб приёмки: новая колонка
  `marketplace_unload_boxes.inbound_intake_box_id` (nullable FK, SET NULL). ШК короба в ответе,
  на экране, в печати и в XLSX = ШК складского короба или короба приёмки. Существующие тесты,
  где у INB пустой `warehouse_box_id`, остаются верными.
- D4.2. Структура сверху вниз (owner-review R15): контекст отгрузки и вкладки; компактная серая
  строка скана «ШК товара или ЧЗ» + галки «Печатать ШК», «Печатать ЧЗ» + компактная «Печать
  накладной»; общая таблица товаров (существующие колонки + «Нужно» (P) + «В коробах» (B) +
  «ЧЗ K из P» с кнопкой «Допечатать»); ниже — раздел коробов: шапка (количество, «Создать короб»,
  «Загрузить по накладной»), поле скана ШК короба, список раскрываемых коробов с составом.
- D4.3. «Завершить упаковку» на FBO нет нигде. Вкладка «Упаковка» доступна в статусах
  «Утверждено»/«Сборка» без задания упаковки. Плитка «Упаковано» в сводке = B (в коробах) из
  данных отгрузки. Таблица строится из данных отгрузки (строки, короба, КИЗ), не из задания.
- D4.4. Текст размеров «60 × 40 × 40» и выбор пресета на экране FBO не показываются; при создании
  короба уходит существующее значение по умолчанию. Данные размера не удаляются.
- D4.5. Скан ШК короба этой отгрузки (созданного, перенесённого целиком, приёмки) делает его
  текущим и раскрывает; выбор не меняет количества. Скан ШК короба из ячейки, ещё не входящего в
  отгрузку, — перенос целиком по правилу D1.7 (без «Добавить всё» сверх плана). Только что
  созданный короб становится текущим.
- D4.6. Скан ШК товара кладёт одну штуку в текущий короб тем же серверным путём, что «Наполнить»
  (`add_manual_qty_to_box`). Нет текущего короба — «Сначала отсканируйте или создайте короб».
  Товар появляется под коробом в раскрываемом составе и в «В коробах».
- D4.7. Скан КИЗ на упаковке — те же правила, что D1.4 (одна серверная функция привязки).
- D4.8. Галки печати FBO хранятся отдельно от FBS: включена — печатаем через WMS Print при скане,
  выключена — не печатаем и WMS Print не требуется. «Печатать ШК» — этикетка ШК товара.
  «Печатать ЧЗ» — на отсканированную штуку выдаётся свободный код товара из пула, привязывается
  (D3) и печатается.
- D4.9. «Допечатать» у счётчика ЧЗ: выдаёт свободные коды этого товара из пула на штуки,
  подобранные без КИЗ (`S − K`), привязывает и печатает через WMS Print. Повтор после потери
  ответа возвращает те же коды (ключ операции), а не новые. Пустой пул — понятное сообщение без
  ложного успеха. Сбой печати — коды остаются привязанными, «Перепечатать» печатает те же коды.
  Программа печати не обновляется (решение владельца 08.10): старый контракт WMS Print.
- D4.10. «Извлечь товар» у каждого короба → окно с ШК короба и составом → «Извлечь всё»:
  состав короба очищается одной транзакцией, «В коробах» уменьшается, «Подобрано» и КИЗ не
  меняются (штуки остаются подобранными на упаковке, их можно снова разложить). Окно
  закрывается. Повтор ничего не меняет. Остаток и расположение не меняются.
- D4.11. Красный ЧЗ — только информация; работа с коробами не блокируется.

### «Завершить» отгрузку

- D5.1. Проверка маркировки через задание упаковки для FBO убирается. Вместо отказа: если по
  товару с ЧЗ K < отгружаемого количества, сервер отвечает понятным отказом с перечнем
  (`marking_incomplete`), экран показывает большое красное окно: «Не на все товары привязаны КИЗ:
  <товар> — K из N… Возможно, часть товара добавлена целым коробом без сканирования КИЗ. Отгрузка
  без маркировки может привести к штрафам. Завершить отгрузку?» [Отмена] [Завершить]. Подтверждение
  повторяет запрос с флагом подтверждения (по образцу существующего `acknowledge_discrepancy`).
  500 при «Завершить» не бывает.
- D5.2. «Завершить» не зависит от задания упаковки. Списание остатка, резерв и начисления
  селлеру — как сейчас.
- D5.3. Выработка упаковщиков по FBO считается по проведённой отгрузке: отгруженные штуки
  засчитываются сотруднику, нажавшему «Завершить», задания упаковки FBO в выработку не входят
  (низкий приоритет; на бою по FBO начислений ноль).

### XLSX для WB, пропуск, селлер

- D6.1. «Скачать XLSX для WB» — сверху в контексте отгрузки (ФФ и селлер), файл прежнего формата
  (5 колонок образца WB), INB-короба со своим ШК (D4.1). Существующие метки `data-testid` кнопки
  и блока коробов сохраняются (охранный тест WMS-679 читает исходник).
- D7.1. Пропуск: одна машина на отгрузку. Поля — по исследованию раздела 5 (WB; для Ozon — его
  поля). ФФ вводит и правит до проведения отгрузки; после «Завершить» — только чтение. Селлер —
  только чтение, запись селлером запрещена сервером (403). В форме «Скачать XLSX» с теми же
  сохранёнными значениями (госномер и телефон — текстом). Кнопка «Внести пропуск» / «Пропуск»
  сверху в контексте отгрузки. Пропуск не блокирует «Завершить».
- D8.1. Хранение пропуска — новая колонка `marketplace_unload_requests.pass_details` (JSON, null).
- D8.2. Селлер в своей отгрузке видит всё (план, подбор, короба с составом, КИЗ, пропуск) только
  на чтение и скачивает оба XLSX. Права сотрудника селлера не трогаем.

### Мобильный ТСД

- D9.1. Подбор FBO в ТСД адаптируется под тот же процесс: ячейка → тара → ШК товара (+1) → КИЗ
  (привязка), двойной скан короба → перенос целиком с тем же отказом сверх плана. Те же серверные
  ручки, что веб. Существующие экраны ТСД (сборка коробов, «Завершить») не ломаются: ответы
  сервера только дополняются необязательными полями.

## 3. Что сознательно НЕ делается

«Закрыть короб» на экране; автосоздание коробов; связь КИЗ ↔ короб; модель «точно/возможно в
таре»; выбор места возврата при извлечении; поштучное «Убрать» с выбором КИЗ; пропуск-файл;
подтверждение «Добавить всё» сверх плана; статус «отгружен» у кодов и запись истории ЧЗ при
«Завершить»; любые правки FBS; удаление задания упаковки из базы.

## 4. Ответы владельцу на непонятые вопросы (простыми словами)

- Q3 (КИЗ при извлечении). Если вынуть товар из короба, наклейки ЧЗ остаются на вещах. Решение:
  коды остаются за товаром в отгрузке и не возвращаются в свободный пул, иначе один код окажется
  на двух вещах.
- Q4 (знаменатель ЧЗ). Только общая таблица: «ЧЗ K из N», N — план товара. Разбивки по коробам нет.
- Q12 (кнопка XLSX). Есть старый тест, который проверяет, что в коде экрана есть кнопка XLSX с
  определёнными метками. Переносим кнопку наверх, метки сохраняем — тест не мешает.
- Q13 (старые документы). В старой постановке и старых тестах остались отменённые вами решения;
  разработчики работают по этому документу, старое помечается устаревшим.
- Ловушка 14 (КИЗ «другого товара»). У товара нет поля GTIN; отказ «КИЗ другого товара» делаем,
  как в упаковке FBS (GTIN кода против ШК товара и пулов) — тот же подход, что работает без жалоб.
- Ловушка 21 (зачем «Извлечь всё»). Из вашего сообщения 08.10: «напротив каждого короба кнопка
  извлечь товар… модалка… извлечь всё… можно короб разупаковать, тогда он падает в неподобранное».
  Смысл: перепаковать короб — например, целиком перенесённый с подбора. Делаем ровно это (D4.10).
