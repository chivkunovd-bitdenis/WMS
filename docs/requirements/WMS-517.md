# WMS-517 · Селлер: отчёт и локально подписанный вывод FBS-КИЗ из оборота

## Уточнение боевой фазы и источники

После приёмки кликабельного прототипа WMS-517 расширена до постановки реальной
интеграции. UX последнего уточнения владельца сохраняется без новых экранов и
технических шагов, но результатом боевой фазы должны стать юридически значимый

## Уточнённый бизнес-контекст

- Для WB FBS продавец остаётся владельцем товара и выводит КИЗ из оборота после
  фактической передачи товара Wildberries с причиной «Дистанционная продажа».
- Для FBO/FBW после УПД собственником становится маркетплейс и выводит код сам. По
  последнему уточнению владельца такие строки вообще не показываются в этом реестре.
- В реестр и операцию попадают только КИЗ FBS-заказов, по которым в WMS уже нажали
  «Отгрузить» и подтверждена передача WB. Отменённые до передачи заказы, FBO/FBW и
  возвраты в этом экране не показываются.
- Способ появления КИЗ в WMS — печать из пула или сканирование внешнего кода — не
  влияет на включение: важны привязка к товару и заказу и подтверждённая передача.
- Отчёт WB используется для последующей сверки, но не является первичным триггером.
  Передача SGTIN в заказ через WB API сама по себе не означает вывод из оборота.
- Браузер подписывает через КриптоПро CSP/CAdES Browser Plug-in. Приватный ключ и PIN
  остаются в CSP/криптоносителе селлера; WMS получает публичные сведения сертификата,
  точные данные для подписи и готовые подписи.
- Целевой auth-путь — `GET /auth/key`, локальная присоединённая подпись challenge и
  `POST /auth/simpleSignIn` с `unitedToken=true`. Старый сохранённый JWT не является
  целевой боевой архитектурой: JWT поддерживается только до конца 2026 года, а UUID
  без challenge — только до 30.09.2026.
- Для FBS создаётся `LK_RECEIPT` с `action=DISTANCE`. Цена по каждому КИЗ обязательна
  в целых копейках с НДС; один документ содержит только одну товарную группу.
- Принятый React-прототип остаётся визуальным эталоном. Реальная интеграция, хранение
  операций и production-деплой в нём отсутствуют и принимаются отдельно.

## Подтверждённый текущий процесс

Селлер уже открывает раздел `/seller/honest-sign`, но сейчас это дашборд остатков
кодов: личный запас, общие корзины, напечатанные коды, загрузка КМ и лента расхода.
Отчёта по переданным КИЗ и действия вывода из оборота в нём нет. В FBS-рабочей области
сейчас прямо указано, что вывод из оборота остаётся на продавце.

WMS уже хранит полное значение FBS-маркировки, источник `pool`/внешний скан, связь с
заказом, товарной строкой и `MarkingCode`. Поставка хранит `delivered_at`; действующий
сервис проставляет это время только при подтверждённой операции передачи и переводит
поставку в `in_delivery`. Это существующая основа для периода отчёта, но её пригодность
для всех исторических заказов нужно отдельно подтвердить на данных перед боевым запуском.

Существующий клиент True API выполняет только чтение `cises/info` и `cises/check` с
уже полученным JWT. Выпуска UUID-токена через локальную УКЭП, подготовки и подписи
`LK_RECEIPT`, отправки документа и сверки его результата в продукте сейчас нет.
`SellerMarkingCredentials.cz_token_enc` умеет хранить старый зашифрованный токен, но
не хранит срок auth-сессии, ИНН/КПП/ФИАС МОД или состояние операции вывода. Приватный
ключ, контейнер сертификата и PIN в WMS не передаются и храниться не должны.

`MarkingCode` уже хранит tenant, seller, product, полный `cis_code` и источник.
`FbsOrderMarking` связывает код с FBS-заказом, а `FbsSupply.delivered_at` выставляется
после подтверждённой передачи WB. `BillingProfile` хранит ИНН/КПП селлера. Текущий
`FbsOrder.price` заполняется полем WB `price`; это не подтверждённая фактическая сумма
покупателя и для `product_cost` использоваться не должно. Товарная группа CRPT и ФИАС
зарегистрированного места деятельности в текущих моделях отсутствуют.

Текущий экран в production пытались открыть визуально, но браузерный коннектор дважды
завершил навигацию по таймауту. Поэтому существующий UI подтверждён чтением React-кода,
а не визуальной проверкой; макет нужно принять отдельно в браузере.

## Цель и граница результата

В кабинете селлера экран «Честный знак → Вывод из оборота» показывает плоский плотный
реестр только уже переданных WB FBS-КИЗ. Селлер выбирает строки, нажимает основное
действие и получает единственное компактное окно локального сертификата с действиями
«Отмена» и «Подписать и отправить». После одной пользовательской команды WMS внутри
одной сохраняемой операции получает auth-token, проверяет КИЗ, формирует и подписывает
документы, отправляет их и дожидается окончательного результата. В интерфейс не
выносятся challenge, документы, товарные группы, polling или reconciliation.

Прототип этого пути уже принят. Боевая реализация считается принятой только после
серверного хранения, sandbox end-to-end и разрешённой production-проверки по матрице
ниже; локальный макет и mock-ответы этого не доказывают.

## Требования принятого UX-прототипа

R1–R13 ниже фиксируют уже принятую пользовательскую границу. Технические упоминания
в них уточняются обязательными боевыми требованиями BR1–BR18; при расхождении точный
протокол BR имеет приоритет, а последний UX-запрет владельца сохраняется.

### R1. Экран в контексте раздела «Честный знак»

В seller-портале раздел «Честный знак» содержит переход «Вывод из оборота». Он открывает
отдельный экран отчёта внутри этого раздела, сохраняет существующий стиль кабинета и
не переносит действие в настройки или FBS-рабочую область. На экране прототипа явно
видно, что это демонстрация без реальной отправки в Честный знак.

### R2. Период и состав отчёта

По умолчанию и после выбора периода отчёт использует подтверждённую дату фактической
передачи WB, а не дату заказа, плановую отгрузку или дату получения отчёта WB. В реестре
есть только колонки «Передано WB», «Заказ WB», «Артикул», «Наименование», «КИЗ» и
«Статус». Артикул и наименование разделены. Схема работы, источник КИЗ, товарная группа
и служебные подробности обычного состояния в таблице не показываются.

### R3. Источник КИЗ не меняет результат

Два КИЗ одного селлера, товара и подтверждённой FBS-передачи показываются и выбираются
одинаково независимо от того, были они напечатаны из пула WMS или отсканированы извне.
Источник не создаёт отдельный режим, не является основанием скрыть код и вообще не
показывается пользователю в реестре.

### R4. В реестре только уже переданные FBS-КИЗ

Строка появляется только после подтверждённого действия «Отгрузить» по FBS-заказу
текущего селлера. FBO/FBW, ещё не переданные FBS-заказы, отменённые до передачи заказы
и возвраты не показываются ни как кандидаты, ни как информационные строки.

### R5. Выбор кодов и массовое действие

Доступны только фильтры периода, товара/поиска и «Только не выведенные»; отдельного
сложного фильтра статусов нет. Селлер может выбрать строки чекбоксами либо выбрать все
доступные строки только на текущей видимой странице после применения фильтров. Размер
страницы переключается между 50, 100 и 250 строками. Переход на другую страницу или
изменение фильтра не подписывает невидимые строки. Кнопка «Вывести из оборота» находится
на этом же экране и активна только при непустом допустимом выборе.

### R6. Прямое действие без промежуточного экрана

По клику «Вывести из оборота» сразу открывается единственное компактное окно выбора
сертификата. До него и внутри него нет предпросмотра состава, stepper, уведомления о
будущей отправке, причины «Дистанционная продажа», периода, числа КИЗ или документов,
списка КИЗ, товарных групп, `LK_RECEIPT`, предварительной проверки либо иных технических
стадий. Коды разных продавцов никогда не смешиваются, а разделение по товарным группам
выполняется внутри интеграции и не выносится в пользовательский путь.

### R7. Внутренняя проверка КИЗ

Будущая интеграция перед формированием документа повторно читает состояние выбранных
КИЗ через True API и допускает только коды, для которых вывод с выбранной причиной
разрешён. Проверка идёт внутри одного действия без отдельного экрана, шага или успешного
уведомления. Код с уже выведенным, заблокированным, отсутствующим или изменившимся
статусом не отправляется повторно. Если Честный знак фактически возвращает ошибку по
коду, она попадает в итоговую модалку ошибки по R9; WMS не придумывает свою причину.

### R8. Единственное окно сертификата и внутренние подписи

Единственное окно предлагает выбрать локальный сертификат текущего селлера и содержит
только действия «Отмена» и «Подписать и отправить». За этой кнопкой браузер через
КриптоПро CSP/CAdES Browser Plugin выполняет подпись авторизации True API и отдельную
отсоединённую подпись точных байтов `LK_RECEIPT`, но challenge, подпись документа и
прочие технические стадии не показываются как отдельные шаги. Приватный ключ, контейнер
и PIN не отправляются и не сохраняются в WMS. «Отмена» закрывает окно, не меняет строки
реестра и позволяет запустить действие повторно.

### R9. Только успешный результат или фактическая ошибка

В обычном реестре есть только «Не выведен», «Выведен» и «Ошибка». Для первых двух
состояний не показываются пояснения, готовность, статус WB или иной служебный текст.
Только финальный успешный статус True API переводит строки в «Выведен»; окно выбора
сертификата закрывается, допускается краткий toast об успехе. Ожидание, проверка,
разделение документов и иные технические стадии отдельными окнами или шагами не
показываются. Только при фактической ошибке Честного знака открывается отдельная простая
модалка со списком конкретных КИЗ и конкретной возвращённой причиной по каждому. Если
детализации нет, WMS её не выдумывает. Будущая рабочая реализация сохраняет результат
между открытиями; прототип показывает состояния локальными данными без серверной
сохранности.

### R10. Идемпотентность и потеря ответа

Одна подтверждённая попытка имеет устойчивый ключ и неизменяемый хэш точного payload.
Повторный клик, доставка того же запроса или два одновременных вызова не создают второй
документ. При потере ответа после отправки WMS сначала сверяет ранее начатую операцию и
её внешний идентификатор/статус и не отправляет новый документ вслепую. Это внутренний
контракт интеграции: прототип не показывает «Сверяем результат», повторную отправку,
технические стадии или отдельную модалку потери ответа.

### R11. Аудит без приватного ключа

Будущая реализация сохраняет tenant, продавца, пользователя, время, выбранные КИЗ и их
источники, связь с FBS-заказами/поставками, причину, товарную группу, payload/hash,
несекретные сведения сертификата, внешний идентификатор документа, попытки и ответы
True API. Приватный ключ, контейнер сертификата и PIN в аудит не попадают. Изоляция
продавцов остаётся обязательным backend-контрактом будущей интеграции, но переключение
seller-контекста и отдельный интерфейс аудита в прототип WMS-517 не входят.

### R12. Обязательная интеграционная проверка до боевой реализации

До реализации реального вызова необходимо по актуальной схеме True API для каждой
поддерживаемой товарной группы подтвердить точный состав `LK_RECEIPT` для причины
«Дистанционная продажа», включая требование фактической цены и других обязательных
полей, единицы и формат значений. Цена не выводится из плановой цены, карточки товара
или тарифа WMS без подтверждённого источника. Пока источник обязательного поля не
определён, интеграция не объявляется готовой и реальный документ не отправляется.

### R13. Возврат после передачи не маскируется повтором вывода

Отмена до передачи и возврат не показываются в этом реестре. Физически полученный
возврат уже переданного и выведенного товара требует отдельного обратного ввода в
оборот; WMS-517 не добавляет это действие и не меняет подтверждённый статус вывода.

## Продуктовые решения

1. Экран размещён в «Честный знак → Вывод из оборота», потому что это отчёт по КИЗ и
   юридически значимое действие над выбранными строками. Настройки нужны для интеграции,
   а FBS-рабочая область — для складской передачи, поэтому там новое массовое действие
   теряет контекст отчёта.
2. Основная временная ось — `delivered_at` подтверждённой передачи WB. WB-отчёт остаётся
   сверкой: ожидание отчёта откладывало бы обязательное действие и делало внешний отчёт
   вторым источником истины.
3. FBO/FBW, отмены до передачи и возвраты полностью исключены из экрана по последнему
   прямому уточнению владельца. Реестр отвечает на один вопрос: какие уже переданные
   FBS-КИЗ нужно вывести или уже вывели.
4. Источник, схема, товарная группа, верхние метрики и подробности штатного статуса
   убраны как служебная каша. Товарная группа остаётся только внутренним основанием
   разделить документы True API и нигде не показывается в штатном пользовательском пути.
5. Выбор действует только по текущей видимой странице отфильтрованной выборки. Так
   «Выбрать всё» предсказуемо при сотнях тысяч строк и не подписывает невидимые записи.
6. Один пользовательский запуск может создать несколько документов по товарным группам,
   но результат ведётся отдельно по каждому документу. Продавцы не смешиваются вообще.
7. Статус «Выведен» принадлежит подтверждённому результату Честного знака, а не клику,
   подписи, ответу HTTP или локальному складскому статусу. Вне ошибки статус не получает
   поясняющий текст.
8. Плотные одноуровневые строки, sticky header и страницы 50/100/250 выбраны из-за
   ожидаемых сотен тысяч записей; вложенные карточки и верхние status-карточки не нужны.
9. После основного действия пользователь видит только выбор сертификата. Внутренние
   проверки, документы и две подписи не превращаются в мастер шагов; отдельная модалка
   появляется лишь для фактической ошибки Честного знака с КИЗ и причиной по каждому.

## Обязательные боевые требования: данные и подпись

### BR1. Реестр и серверная принадлежность строк

`GET /operations/marking-codes/self/withdrawals` работает только в текущей seller-сессии
с правом «Честный знак». Он возвращает строки текущих `tenant_id` и `seller_id`, где
WB FBS-заказ связан с КИЗ и поставкой с непустым `delivered_at` после подтверждённой
передачи. FBO/FBW, ещё не переданные и отменённые до передачи заказы, а также возвраты
не возвращаются даже при подмене query-параметров. Источник `pool`/scan не влияет.

Единственный состав отчёта задаёт серверный `eligible_rows` SQL по существующей цепочке
`FbsOrderMarking → FbsOrder → FbsSupply`, где `FbsSupply.delivered_at IS NOT NULL`, с
tenant/seller и исключениями выше. Выбранные `row_ids` повторно разрешаются тем же
предикатом и тем же составом связей при создании operation; только эти строки становятся
items и затем входят в документы. Отдельный источник строк, повторная ручная сборка
списка или расширение состава между отчётом и operation запрещены.

Фильтры и пагинация соответствуют R2–R5. Клиент получает непрозрачный `row_id`, а не
право прислать произвольный CIS. Каждый mutation повторно выбирает и блокирует строки
по tenant/seller на сервере; данные из UI не считаются источником истины.

### BR2. Неизменяемый ценовой snapshot WB

Синхронизация `/api/v3/orders` сохраняет отдельно `finalPrice`, `currencyCode`,
`convertedFinalPrice`, `convertedCurrencyCode` и источник/время snapshot. Поля WB уже
выражены ×100: дополнительное умножение запрещено.

Для `product_cost` используется только:

1. `finalPrice`, когда `currencyCode=643` (RUB);
2. иначе `convertedFinalPrice`, когда `convertedCurrencyCode=643`.

Если обе RUB-суммы присутствуют и различаются, RUB-суммы нет, значение отсутствует или
выходит за диапазон CRPT `0..99999999999999999`, строка получает фактическую ошибку
данных и не попадает в документ. `FbsOrder.price`, цена карточки, тариф WMS и ручная
догадка не используются. Сумма отправляется целым числом копеек с НДС.

Существующий paginated sync с `dateFrom` используется для доступного WB периода не
более 30 дней. Более старые заказы или строки, которые WB уже не возвращает с финальной
RUB-ценой, остаются неотправляемыми; молчаливого backfill из `price` нет.

### BR3. Повторная проверка КИЗ, группы и владельца

После локальной auth и перед формированием документа backend повторно вызывает True API
`cises/info` для каждого выбранного КИЗ. Только ответ текущей auth-сессии определяет
`productGroup`/`productGroupId`, `ownerInn`, status/statusEx и GTIN. Категория WMS и
ручное сопоставление не подменяют этот ответ.

КИЗ допускается дальше, только если группа однозначна, поддерживает `LK_RECEIPT` с
`DISTANCE`, `ownerInn` совпадает с проверенным ИНН seller `BillingProfile`, а фактический
статус разрешает вывод. Для `LK_RECEIPT` статус должен быть `INTRODUCED`. Если дата
начала прослеживаемости наступила, `statusEx` должен отсутствовать либо быть
`CONNECT_TAP`/`WAIT_TRANSFER_TO_OWNER`; если не наступила — отсутствовать либо иметь
любое значение, кроме `MOVING_BY_UD`. WMS не угадывает начало прослеживаемости по
категории: если применимый режим для `pg` нельзя подтвердить, КИЗ fail-closed и в
документ не попадает.

Проверка доступности `DISTANCE` по официальному справочнику обязательна до проверки
МОД и сборки документа: причина недоступна для автозапчастей,
алкоголя, альтернативного табака, кабельной продукции, мясных изделий,
никотиносодержащей продукции, пива и слабоалкогольных напитков, пиротехники,
полимерных труб, полуфабрикатов и замороженных продуктов, радиоэлектронных систем
доставки никотина, сладостей, табака, титановой металлопродукции, товаров для дома и
интерьера и удобрений в потребительской упаковке. Null, неполный, чужой,
заблокированный, уже выведенный или противоречивый ответ превращает только этот КИЗ в
ошибку и не отправляется. Группа из ответа является `pg`; смешанные группы разделяются
на разные документы.

### BR4. ИНН, КПП и место деятельности

В inner `LK_RECEIPT.inn` используется ИНН seller `BillingProfile`, но только после
успешной auth тем же участником и совпадения с `ownerInn` всех КИЗ документа. Для auth
по МЧД этот же ИНН передаётся как `inn` в `/auth/simpleSignIn`; срок/отзыв МЧД ограничивает
жизнь token.

Для `DISTANCE` место осуществления деятельности обязательно только для следующих
официальных `pg`: `antiseptic`, `bicycle`, `perfumery`, `toys`, `conserve`, `petfood`,
`lp`, `milk`, `seafood`, `meat`, `shoes`, `radio`, `gadgets`, `vegetableoil`,
`softdrinks`, `construction`, `water`, `electronics`, `tires`. При этом `meat` не
поддерживает `DISTANCE` по BR3, поэтому документ с такой комбинацией не создаётся.
Отдельные правила матрицы для `alcohol`/`beer`, `otp`/`ncp`/`tobacco` и `vetpharma`
не расширяют доступность `DISTANCE` и не переносятся на другие группы.

Backend получает зарегистрированные МОД только через
`GET {v3}/mods/list?inns=<seller_inn>&productGroups=<pg>&limit=1000&page=<n>`; `page`
начинается с `0`, backend читает все страницы до `nextPage=false`. Ответ содержит строго
`result` — массив неудалённых записей с `inn`, `productGroups`, необязательными
`address`, `kpp`, `fiasId` и `isBlockedEgais`, — а также `total` и `nextPage`;
ключи `results` или `mods` для этого метода не принимаются. `isBlockedEgais`
относится только к ЕГАИС и не объявляется общим признаком активности.
Ручной ФИАС/КПП и категория WMS не подменяют ответ True API.

Если `pg` не входит в обязательную матрицу, `kpp` и `fias_id` в документе отсутствуют.
Если входит, backend оставляет из `result` только записи того же `seller_inn`, содержащие
точный `pg`, и требует ровно одну валидную внешнюю запись. Из неё без ручной подмены
берутся применимые идентификаторы: `kpp` — только для юридического лица в формате 9
цифр, `fias_id` — UUID; если присутствуют оба, True API ищет МОД по их сочетанию. Для
ИП `kpp` не отправляется. Ноль или несколько валидных записей — внешний data blocker:
блокируется только документ этой группы с фактической ошибкой, другие документы
операции продолжаются.

WMS не создаёт `WithdrawalModMapping`, привязку склада к МОД, экран настройки или выбор
МОД в withdrawal-модалке. `FbsSupply.warehouse_id` не участвует в поиске МОД. Первый
элемент результата не выбирается, а 0/multiple не разрешаются догадкой. **B1 закрыт
этим правилом**; технический вызов `/mods/list` и fail-closed builder приняты только
в local/emulator-границе, без live CRPT.

### BR5. Readiness браузера без чтения сертификатов

При открытии экрана загружается закреплённая локальная версия `cadesplugin_api.js`,
ожидается `window.cadesplugin`, создаётся `CAdESCOM.About`, читаются `PluginVersion` и
`CSPVersion`. На этом этапе `CAdESCOM.Store` и private key не открываются, PIN prompt не
вызывается. Отсутствие расширения/native host, timeout, отсутствие CSP (`0x80090019`) и
неподдержанная комбинация browser/OS/version показывают разные человеческие причины с
безопасным `getLastError`; автоматического цикла запросов разрешения/PIN нет.

Production работает только по HTTPS. Localhost, staging и production являются разными
origins и принимаются отдельно с учётом trusted-site и enterprise browser policy.

### BR6. Сертификаты только после действия пользователя

Только после клика «Вывести из оборота» браузер открывает
`CurrentUser/My/MaximumAllowed`, применяет `TIME_VALID`, оставляет сертификаты с
`HasPrivateKey=true` и показывает Subject, Issuer, срок и сокращённый thumbprint.
Полный thumbprint сохраняется только как идентификатор операции. Перед подписью
проверяются `IsValid` и `CPSigner.CheckCertificate=true`; guessed-фильтр по EKU/ИНН не
добавляется без требования True API.

PIN запрашивает только системный UI CSP/носителя. WMS не использует `CPSigner.KeyPin`,
не читает и не передаёт PIN, private key или container. Обычная USB-флешка не считается
криптоносителем. Отмена системного окна или неверный PIN не запускают автоповтор.

### BR7. Единая auth-сессия True API

Backend использует sandbox либо production v3 base URL из конфигурации:

1. `GET {v3}/auth/key` и сохраняет полученные `uuid` и `data` в операции;
2. браузер подписывает именно возвращённый challenge `data` присоединённой УКЭП только
   через подтверждённый browser-профиль;
3. `POST {v3}/auth/simpleSignIn` получает `uuid`, base64 присоединённой подписи в
   `data`, `unitedToken=true` и `inn` только для МЧД; `inn` валидируется как ровно 10
   или 12 цифр, `details` в MVP не отправляется, потому что это необязательные реквизиты
   аттестата соответствия объекта информатизации;
4. backend читает из успешного ответа `uuidToken` и `expireDate`, не отдаёт token
   JavaScript и хранит его зашифрованно с tenant/seller, thumbprint и сроком не более
   10 часов и не позже окончания сертификата/МЧД; `code`, `error_message` и
   `description` не превращаются в успешную сессию.

Новый sign-in создаёт новую сессию и не продлевает старую. UUID без `/auth/key` и JWT
не являются допустимым боевым shortcut. Challenge, auth-подпись и document-подпись —
разные объекты; смена сертификата инвалидирует неподанные подписи и требует новой auth.
Доступ определяется зарегистрированными товарными группами и ролью участника; 403 для
роли без права create не обходится другим endpoint и сохраняется как auth/access error.

**BLOCKER B3:** до реальной auth-подписи sandbox-фикстура либо письменное подтверждение
CRPT/CryptoPro должно однозначно закрепить, какие exact bytes подписывает browser,
нужно ли base64-декодирование challenge, значение `ContentEncoding`, CAdES subtype,
правила CRLF и нормализацию base64 результата. Java/1C-примеры этого не доказывают.
До снятия B3 production adapter работает fail-closed: readiness, выбор сертификата и
fake/test fixtures допустимы, но private-key sign auth challenge, `simpleSignIn` и любой
следующий live submit не выполняются. Подтверждённый профиль фиксируется golden fixture
«challenge bytes → attached signature → успешный sandbox simpleSignIn» и версией среды.

### BR8. Exact bytes и локальная подпись документов

После BR2–BR4 backend один раз сериализует inner `LK_RECEIPT` в UTF-8 bytes, сохраняет
immutable bytes и SHA-256 и отдаёт browser их base64 вместе с внутренним `document_id`.
Browser не парсит и не сериализует JSON. Для binary payload сначала устанавливается
`ContentEncoding=CADESCOM_BASE64_TO_BINARY`, затем `Content=payload_base64`; подпись
создаётся через CAdES/GOST по официальному примеру как отсоединённая УКЭП и возвращается
base64 без переносов строк. Тот же сертификат подписывает auth и все документы операции.

Backend принимает подпись только с тем же operation/document id, thumbprint и SHA-256,
и отправляет первоначальные bytes — повторная сериализация после подписи запрещена.
Каждый документ имеет отдельную подпись. Точные payload/signature могут храниться в
ограниченных данных операции, но не печатаются в application logs.

### BR9. Состав `LK_RECEIPT` для FBS

Inner JSON содержит `inn`, `action="DISTANCE"`, `action_date`, условные `fias_id`/`kpp`
по BR4 и `products` минимум с одним `{cis, product_cost}`. `action_date` — именно дата
вывода из оборота, а не дата передачи WB и не дата первичного документа. В MVP backend
ставит календарную дату формирования операции в `Europe/Moscow`; допустимое окно True
API — от текущей даты минус пять лет до текущей даты включительно, время допускается,
но игнорируется. `FbsSupply.delivered_at` остаётся основанием включения и периодом
реестра, но не копируется в `action_date`.

Для `DISTANCE` `document_type` и товарный `primary_document_type` необязательны. Если
любое из них заполнено, обязательны соответствующие номер и дата; допустимые типы —
`RECEIPT`, `SALES_RECEIPT`, `OTHER`, `CONSIGNMENT_NOTE`, `UTD`, а для `OTHER` обязательно
наименование. `document_date` — дата первичного документа в `dd.MM.yyyy` или
`yyyy-MM-dd`, не `action_date`; товарный `primary_document_date` имеет отдельный формат
и диапазон из официальной схемы. В MVP весь блок первичного документа не заполняется:
WB order ID не выдаётся за номер первичного документа.

Builder для MVP использует allowlist полей `inn`, `action`, `action_date`, условные
`kpp`/`fias_id` и `products[{cis, product_cost}]`. Условные либо запрещённые для
`DISTANCE` поля (`buyer_inn`, `withdrawal_type_other`, `state_contract_id`,
`partial_quantity` и другие поля иных причин) отклоняются до подписи, а не уходят как
`null` или пустая строка. `product_cost` обязателен для каждого товара при `DISTANCE`,
передаётся в копейках с НДС и в диапазоне `0..99999999999999999`.

Один документ содержит КИЗ одного seller и одного `pg`. Если группа поддерживает
`LK_RECEIPT`, но не `DISTANCE`, КИЗ получает ошибку до submit. Внутри группы документы
делятся так, чтобы каждый был не больше 30 MB и 30 000 КИЗ; пересечение КИЗ между
частями запрещено.

Outer create JSON содержит ровно `document_format="MANUAL"`,
`product_document=base64(exact inner bytes)`, `type="LK_RECEIPT"` и
`signature=base64(detached signature)`. Отправка выполняется через
`POST {v3}/lk/documents/create?pg=<group>`. HTTP 200/201 и полученный GIS document ID
означают только приём документа, не окончательный вывод КИЗ.

## Обязательные боевые требования: API, состояние и восстановление

### BR10. Same-origin WMS API и backend boundary

Browser обращается только к same-origin WMS API; CRPT CORS не предполагается, UUID-token
в page JavaScript не попадает. Минимальный контракт API:

- `GET /operations/marking-codes/self/withdrawals` — реестр BR1;
- `POST /operations/marking-codes/self/withdrawals/operations` — идемпотентно создать
  операцию по `row_ids` и `client_request_id`, повторно проверить локальные данные и
  вернуть operation id плюс auth challenge;
- `POST .../operations/{id}/auth-signature` — принять связанную присоединённую подпись,
  получить UUID-token, выполнить BR3–BR4 и вернуть immutable document blobs/hashes;
- `POST .../operations/{id}/document-signatures` — принять весь набор связанных
  подписей и запустить submit;
- `GET .../operations/{id}` — перечитать/возобновить состояние после reload;
- `POST .../operations/{id}/retry` — разрешён только после доказанного terminal reject
  и повторной BR2–BR4; для UNKNOWN/RECONCILING возвращает существующую операцию.

Пути могут быть вынесены в отдельный router, но семантика `self`, tenant/seller scope,
operation id и разделение стадий не меняются без обновления постановки.

### BR11. Сохраняемая модель и внутренняя идемпотентность

До внешнего вызова сохраняются:

- операция: tenant, seller, user, `client_request_id`, selection hash, состояние,
  сертификат, auth-session, timestamps;
- элементы: marking/order/supply, CIS, дата передачи, price snapshot, pg, ownerInn,
  состояние и фактическая ошибка;
- документы: pg, exact payload, SHA-256, signature, attempt, request timestamps,
  GIS document id/status, errors и `next_poll_at`;
- auth-session: CRPT uuid, зашифрованный token, expiry, certificate/MChD metadata.

Уникальность `tenant+seller+client_request_id` возвращает ту же операцию. Database
constraint/locking не допускает два активных или успешных вывода одного marking code;
два пользователя, двойной клик и повтор HTTP не создают второй документ. Terminal
reject может породить новую attempt того же элемента только через BR10 retry; история
не перезаписывается.

Внутренние состояния операции: `created`, `auth_pending`, `documents_pending_signature`,
`submitting`, `submitted`, `reconciling`, `succeeded`, `partial_failed`, `failed`,
`cancelled`. Состояния не показываются отдельными чипами в штатном seller UI.

### BR12. Ограничение запросов и частичный submit

Общий для всех workers/replicas limiter не допускает больше 50 CRPT requests/s на
участника. Process-local sleep недостаточен. Документы отправляются и фиксируются
независимо: успех одного не откатывается из-за ошибки другого. После каждого create
GIS document ID сохраняется до следующего внешнего вызова.

HTTP 400/401/403/422 сохраняет точный code/body без Authorization и переводит только
затронутый документ в отказ. HTTP 5xx, сетевой timeout или разрыв после начала POST
не считаются отказом: результат становится `reconciling` по BR14.

### BR13. Polling и окончательный результат

Для известного GIS document ID backend использует только v4
`GET {v4}/doc/{id}/info?pg=<pg>&body=true`. Старые v3 list/info и
`/doc/validator/status` для `LK_RECEIPT` запрещены. Polling выполняется сохраняемым
worker с backoff 2, 5, 10, 30, далее не чаще раза в 60 секунд и общим limiter BR12;
elapsed time сам по себе не превращает неизвестный исход в отказ.

`IN_PROGRESS` и `WAIT_FOR_CONTINUATION` продолжают polling. `CHECKED_OK` — единственный
обычный terminal success и только тогда связанные строки получают «Выведен».
`CHECKED_NOT_OK`, `PARSE_ERROR` и `PROCESSING_ERROR` — terminal failure с сохранением
`errors` и `commonErrors`. `UNDEFINED` и неожиданный статус не считаются успехом и
остаются на сверке/операторском контроле. Shipment-статус `ACCEPTED` не переносится на
`LK_RECEIPT` как доказательство вывода.

Если ошибка возвращена на документ, а не на отдельный CIS, одна и та же фактическая
причина помечается как «ошибка документа» у каждого входящего КИЗ; WMS не сочиняет
по-кодовую причину.

### BR14. Потеря create-ответа и безопасный retry

В create True API нет внешнего idempotency key, client request ID или уникального
клиентского номера. Поэтому после timeout/5xx/разрыва новый create автоматически не
выполняется.

Worker запрашивает v4 `GET {v4}/doc/list` с обязательным `pg` и узким окном
`dateFrom/dateTo`, `senderInn`, `documentType=LK_RECEIPT`, `documentFormat=MANUAL`, затем
читает кандидатов через `/doc/{id}/info?pg=<pg>&body=true`. Совпадение принимается только
по exact inner body либо одинаковым action/date/inn/MOD, множеству CIS и cost каждого
элемента. Один exact match присоединяется к операции и pollится; несколько совпадений
создают incident о возможном дубле. Отсутствие кандидата не доказывает отсутствие
документа: операция остаётся `reconciling` и повторяет только чтение.

`cises/info` может подтвердить текущий `RETIRED`, но не связывает его с нашим документом
и не закрывает audit. Новый submit после UNKNOWN разрешён только после внешнего
подтверждения CRPT/оператора, что документ не создан; публичный API не задаёт безопасный
автоматический timeout для такого решения.

После явного terminal failure новый retry повторно проверяет цену, `cises/info`, pg,
owner и MOD и формирует новые bytes/подпись. Повтор прежней подписи или payload после
изменения данных запрещён.

### BR15. UI результата и ошибки

По последнему решению владельца UI остаётся R1–R6/R9: один реестр и одно окно
сертификата. После «Подписать и отправить» все auth/document signatures выполняются
за одной командой без stepper. Системные CSP/PIN окна не копируются интерфейсом WMS.

После принятия подписей окно закрывается. Пока backend обрабатывает операцию, строка
остаётся с простым статусом «Не выведен»; повторное действие возвращает существующую
операцию и не создаёт дубль. При `CHECKED_OK` строка становится «Выведен» и допускается
краткий toast. Только при фактической local/CRPT terminal error показывается отдельная
простая модалка: конкретный КИЗ, WB order и дословная безопасная причина. `reconciling`,
pg, документ, auth, polling и служебные состояния в эту модалку не попадают.

Ошибки плагина, CSP, Store, сертификата, token/PIN и auth показываются до submit как
короткая причина и действие восстановления. Отмена пользователем не создаёт ошибку КИЗ.

### BR16. Tenant isolation, секреты и аудит

Каждый API/query/update включает tenant и seller из проверенной WMS-сессии; переданные
ID другого seller дают 404/403 без раскрытия. Сертификат одной операции нельзя применить
к другой seller/tenant. ИНН BillingProfile, ownerInn, auth participant и текущий seller
сверяются до документа.

Аудит хранит user, tenant/seller, operation/attempt, order/supply/marking ids, полный
thumbprint и безопасные сведения сертификата, payload SHA-256, CRPT document id/status,
timestamps, HTTP/status/error codes и связи per-KIZ. Exact payload/signature хранятся
как ограниченные данные операции и не пишутся в обычные логи. Authorization token,
challenge body, PIN, private key и container не логируются; token хранится только
зашифрованно и удаляется/инвалидируется по expiry.

### BR17. Контуры и release gate

Конфигурация выбирает связанные пары base URL:

- sandbox: `https://markirovka.sandbox.crptech.ru/api/v3/true-api` и `/api/v4/true-api`;
- production: `https://markirovka.crpt.ru/api/v3/true-api` и `/api/v4/true-api`.

Token, document IDs и операции разных контуров не смешиваются. Production WMS работает
по HTTPS. **BLOCKER B2:** до live-приёмки назначаются sandbox participant, УКЭП/МЧД,
зарегистрированные product groups и тестовые КИЗ/МОД; значения секретов в документ и
логи не попадают.

Поддерживаемый baseline, который нужно реально прогнать: Chrome/Chromium 104+,
Edge Chromium 104+ и Firefox на Windows 10/11 и macOS 11–14 x64/ARM64. Верхняя версия
браузера и macOS 15+ не обещаются без отдельного smoke. Найденные на одном Mac CSP
5.0.13003, CAdES 2.0.15003 и manifests доказывают только установленные артефакты, но не
enabled extension, native host, сертификат или подпись.

Выпуск требует: mock/unit, PostgreSQL concurrency, crypto integration runner с тестовым
сертификатом, ручную browser/OS/token матрицу, sandbox end-to-end и затем одну отдельно
разрешённую production-операцию с проверкой GIS document ID/status/body и повторным
открытием реестра. Commit/CI или локальный URL не заменяют ни один из этих слоёв.

### BR18. Возвраты и исторические данные

Отмены до передачи и возвраты не появляются в этом реестре. Физически полученный
возврат ранее выведенного товара требует отдельного обратного ввода в оборот и не
переводит строку WMS-517 обратно автоматически.

Исторические переданные строки без доказанной `delivered_at`, финальной RUB-цены,
однозначного owner/pg или обязательного MOD видны только как фактическая ошибка данных
и не отправляются. Исправление исходных данных и новый явный retry сохраняют историю;
подстановка фиктивного значения запрещена.

## Решения боевой фазы

1. Browser только подписывает, а CRPT вызывает same-origin backend. Так UUID-token не
   попадает в page JS, CORS не становится скрытой зависимостью, а operation survives reload.
2. Backend создаёт и замораживает exact bytes; browser не строит JSON. Иначе подпись
   могла бы относиться не к тем байтам, которые ушли в `product_document`.
3. `product_cost` берётся из подтверждённой финальной RUB-суммы WB, а не из legacy
   `price`: это единственный источник, совпадающий с фактической оплатой со скидками.
4. `pg` и owner определяются повторным `cises/info`, а не категорией карточки WMS.
   Товарная группа влияет на юридический документ, но не добавляется в видимый реестр.
5. Технические состояния сохраняются на сервере, но в seller UI остаются только три
   статуса владельца. Повтор по строке возобновляет operation и не создаёт дубль.
6. После неопределённого create-ответа WMS выбирает сохранность перед скоростью: только
   сверка v4, потому что публичный create не имеет внешней идемпотентности.
7. МОД — только внешняя техническая проверка: для обязательной группы `/mods/list`
   должен вернуть ровно одну валидную запись того же ИНН и `pg`. Ноль или несколько
   записей блокируют только этот документ; WMS не создаёт настройку, mapping или новый
   UI и не связывает МОД со складом. Этим решением B1 закрыт на уровне постановки.

## Реализационные волны

1. **Цена WB — backend/data ownership.** Добавить snapshot четырёх final/currency
   полей в import/update, backfill доступного 30-дневного окна и тесты BR2. Не менять UI.
2. **Crypto adapter — frontend ownership с gate B3.** До B3 реализовать readiness,
   certificate selection, fail-closed auth boundary, fake adapter и detached document
   fixtures по BR5–BR8. Реальную attached auth-подпись включать только после фиксации
   подтверждённого browser-профиля B3; не обращаться к CRPT и не хранить token.
3. **CRPT transport — backend integration ownership.** Изолированные v3 auth/create,
   `cises/info`, v4 list/info parsers, limits/status/error fixtures и shared limiter.
   Не подключать кнопку seller UI.
4. **Operation ledger — backend/database ownership.** Модели BR11, tenant constraints,
   API BR10, concurrency/idempotency и recovery worker BR13–BR14 на emulator fixtures.
5. **MOD verification — backend integration ownership.** Реализовать paginated
   `/mods/list`, фильтр exact seller INN+pg, требование ровно одной валидной записи,
   перенос её `fiasId`/`kpp` в builder и per-document ошибку при 0/multiple. Новых
   таблиц, mapping, настройки или UI нет; B1 постановкой закрыт. Волна реализована и
   принята в local/emulator-границе, live `/mods/list` относится к B2.
6. **Интеграция UX — frontend ownership.** Подключить принятый реестр/одну модалку к
   API, удалить demo-data и проверить BR1/BR15 без технической каши.
7. **Live acceptance/release — совместная волна после B2 и B3.** Sandbox E2E, физическая
   browser/token матрица, review, повторная аналитическая приёмка, разрешённый production
   smoke и отдельная проверка deployed SHA. Эту волну не объявлять готовой до gates.

Волны 1, 3, 4 и 5, а также ограниченная B3-безопасная часть волны 2 можно разрабатывать
независимо в отдельных файлах/ветках. B2 и B3 не блокируют emulator/internal
orchestration. Реальная auth-подпись и live submit запрещены до B3; sandbox/live
acceptance и production release — до B2/B3 и объединённой приёмки.

массовый выбор, признак вывода, фильтр невыведенных и подписание сертификатом покрыты

источника/группы/служебных статусов, раздельных артикуле и наименовании, плоских строках

исключены по R4/R13 и BR18. Немедленный выбор сертификата без предпросмотра и
технических шагов покрыт R6–R10, BR5–BR8/BR15 и C5–C9.

группа/владелец — BR3, МОД — BR4, CryptoPro и документные подписи — BR5–BR9, same-origin API и
хранение — BR10–BR11, create/limits/status — BR12–BR13, потеря ответа/retry — BR14,
tenant/audit — BR16, контуры/release — BR17. У всех BR есть BC-проверки.

B1 закрыт продуктовым решением: `/mods/list` используется только для технического
требования «ровно один внешний МОД exact seller INN+pg»; 0/multiple блокируют документ,
а WMS не хранит mapping и не добавляет выбор или настройку.
Неподтверждённые значения не превращены в требования: B2 требует назначенного sandbox
participant/cert/test data, а B3 не даёт перенести Java/1C-параметры на browser auth
signature без sandbox или письменного vendor-подтверждения. Public True API v731.0
подтверждает endpoint, поля, матрицы, create, statuses и limits, но не закрывает точный
browser encoding/profile attached auth signature.

## Заключение

**Локальный internal/emulator/browser slice WMS-517 принят по фактически реализованной
границе.** Код подтверждает одну цепочку `eligible_rows → registry → row_ids →
operation/document`; отдельной FBS warehouse→MOD модели нет. Для обязательного МОД
реализована только свежая внешняя проверка `/mods/list`: одна валидная запись даёт
`fiasId`/`kpp`, 0 или несколько блокируют документ своей группы. Business preflight,
builder, operation ledger, protected submit/reconciliation и recovery scheduler связаны.

В текущем браузере повторно проверены плотный отчёт на 317 строк, простые статусы,
выбор строки и единственная компактная модалка сертификата без stepper, preview или
технических стадий. Историческая UX-приёмка C1–C12 сохраняется. Предъявленные узкие
проверки после review: backend `70 passed, 2 skipped`, frontend `41 passed`; ruff,
mypy, ESLint и TypeScript зелёные. Две пропущенные backend-проверки требуют отдельной
PostgreSQL test DB; полный набор аналитик по прямому ограничению не перезапускал.

**Эту локальную реализацию можно сохранить отдельным commit и push как проверенный
результат разработки, но нельзя называть production-ready или работающей live-интеграцией.**
Открыты B2 — назначенный sandbox participant/УКЭП/МЧД/test data — и B3 — подтверждённый
browser-профиль присоединённой auth-подписи. До B3 реальные auth и submit остаются
fail-closed. Также не выполнены PostgreSQL-конкурентный прогон, software/physical
CryptoPro/browser/token matrix, sandbox E2E, разрешённый production smoke и проверка
deployed SHA. Секреты/сертификаты не использовались, sandbox/production вызовов и
деплоя не было.
