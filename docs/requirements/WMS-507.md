# WMS-507 · AVpack: вернуть разрешённое переключение между кабинетами селлеров

## Исходный запрос и уточнения

После разбора действующего ограничения владелец уточнил смысл исходной изоляции WMS-488:

> «я же просил сделать так чтобы ЕГО ТОВАРЫ БЛЯДЬ не были видны»

> «Бля, ты поправил проблему по Webpack, ты её реально исправил системно, но при этом ему заблокировал остальные аккаунты.»

Финальное поручение владельца 22.09.2026:

> «убирай этот запрет»

До этого владелец подтвердил целевой рабочий процесс: один менеджер управляет несколькими
юрлицами; при выборе одного из разрешённых селлеров он работает в полном кабинете именно
этого селлера — с его товарами, приёмками, отгрузками, FBS, Честным знаком и интеграциями.
Данные разных селлеров не должны смешиваться.

## Существующий процесс и цель изменения

Пользователь seller-портала имеет домашний `User.seller_id`. Право работать с несколькими
кабинетами задаётся явным `User.can_manage_seller_shops`; конкретные разрешённые кабинеты —
включёнными строками `SellerShopDelegation` того же арендатора. После переключения
`POST /auth/switch-seller` выдаёт токен с активным `seller_id`, а серверная функция
`resolve_effective_seller_id` обязана повторно проверить живое разрешение и использовать
активного селлера как область рабочих данных.

WMS-488 добавила исключение по точному slug AVpack `avpack-9uczh`: функции
`uses_home_seller_scope` и `can_manage_seller_shops` принудительно подменяют активного
селлера домашним и скрывают уже выданные делегации. В результате системная изоляция данных
сохранена, но законная работа менеджера с остальными юрлицами заблокирована.

Цель WMS-507 — удалить именно это исключение AVpack и вернуть ему общесистемную модель
явных делегаций. Область данных после переключения остаётся равной одному активному
`seller_id`; общий смешанный кабинет не появляется.

## Требования

| ID | Проверяемое поведение | Основание |
|---|---|---|
| R1 | Пользователь seller-портала AVpack с `can_manage_seller_shops=true` видит в `/auth/me` своё право управления магазинами, домашний кабинет и существующие разрешённые делегации. Включённые делегации входят в список доступных для переключения магазинов так же, как у менеджера любого другого арендатора. | Поручение «убирай этот запрет»; подтверждённая владельцем модель одного менеджера для нескольких юрлиц. |
| R2 | Такой менеджер может переключиться только на селлера своего арендатора, для которого у него есть включённая `SellerShopDelegation`. После переключения новый токен и `/auth/me` показывают выбранный кабинет как активный; домашний селлер пользователя при этом не меняется. | Действующая системная модель явных разрешений; владелец требует полноценную работу под выбранным кабинетом. |
| R3 | После переключения товары, приёмки, отгрузки, FBS, Честный знак и интеграции работают в области выбранного активного `seller_id`: видны и изменяются данные выбранного селлера, а данные домашнего и остальных селлеров не подмешиваются. Возврат в домашний кабинет снова даёт только домашнюю область. | Уточнение владельца: скрыть чужие товары, не блокируя разрешённые кабинеты; перечисленный владельцем рабочий процесс. |
| R4 | Обычный пользователь AVpack без явного флага управления магазинами остаётся в домашнем кабинете. Менеджер не может переключиться на селлера без делегации, с выключенной делегацией, из другого арендатора или на тестового селлера; подделанный либо ранее выданный токен не обходит текущую проверку разрешения. | Сохранение системной изоляции и действующих границ клиентов; задача отменяет только лишнее AVpack-исключение. |
| R5 | Удаление AVpack-исключения не меняет существующие `can_manage_seller_shops` и `SellerShopDelegation`, не создаёт новых назначений и не требует миграции данных. Существующее включение и выключение заранее разрешённых магазинов продолжает работать через текущий интерфейс и API. | Владелец просит снять запрет, а не переназначить права; исторические grants уже сохранены. |
| R6 | Поведение менеджеров других арендаторов не меняется: они по-прежнему переключаются только в явно разрешённые кабинеты, а обычные селлеры остаются в домашнем. Роль фулфилмента AVpack и её существующий доступ к селлерам не меняются. | Ограничение задачи — исправить ошибочную AVpack-заглушку без расширения прав и соседних процессов. |
| R7 | В рамках WMS-507 не добавляется административный интерфейс выдачи делегаций и не перерабатываются независимые участки системы, которые исторически используют домашний scope. Если адресная проверка обнаружит, что такой участок мешает прямо названному сценарию R3, это фиксируется как конкретное несоответствие, а не скрыто расширяется в общий рефакторинг. | Явная граница постановки ведущего: сейчас убрать запрет и защитить регресс тестами; административный UI и второстепенные home-scope участки не входят. |

## Продуктовое решение

Для AVpack применяется уже существующее общее правило: домашний кабинет доступен всегда,
дополнительный — только при явном флаге менеджера и включённой делегации тому же арендатору.
Выбор кабинета меняет один активный `seller_id`, поэтому безопасность обеспечивается
проверкой разрешения и seller-scoped запросами, а не запретом переключения для всего
арендатора.

Отдельного продуктового выбора не осталось. Специальное правило WMS-488 «любой AVpack
seller-role всегда home-only» отменено прямым уточнением владельца. Остальные исправления
WMS-488 — фильтрация по seller scope, закрытие прямых обходов и межвкладочная очистка
сессии — откатывать нельзя.

## Сверка перед передачей разработчику

- Поручение «убирай этот запрет» покрыто R1–R2: AVpack больше не принудительно home-only.
- Уточнение «его товары не были видны» покрыто R3–R4: данные определяются одним активным
  разрешённым `seller_id`, а не объединяются.
- Сценарий одного менеджера для нескольких юрлиц покрыт R1–R3 и C1–C2.
- Сохранение системного исправления WMS-488 покрыто R3–R4, R6 и C7.
- Ограничение текущей задачи без административного UI и общего рефакторинга закреплено R7
  и C8.
- Необоснованных новых ролей, сущностей, запретов или изменений данных не добавлено.

## Заключение

Приёмка не проводилась; вердикты C1–C8 заполняются после реализации и перекрёстного ревью.
