# WMS-537 · FBS: стикер WB для заказа, добавленного в поставку-черновик

Продолжение [WMS-475](WMS-475.md). Запись задачи — в [каноническом бэклоге](../KANONICHESKIY_BACKLOG.md#wms-537).

## 2. Существующий процесс и цель

### Что произошло (факты ведущего с production, только чтение, 25.09.2026; аналитик их не перепроверял)

Поставка AVpack «FBS 24.09.2026 — перенос», WB-GI-283060158, статус `draft`, 28 заказов. Четырнадцать из них добавлены одной операцией в 12:31 UTC. В WB эти заказы в поставке (`supplier_status=confirm`), но у них `sticker_status=not_requested`, код стикера и файл пустые. По поручению владельца ведущий запросил эти 14 стикеров вручную той же функцией печати: ready 14, failed 0. Данные production исправлены, задача касается только кода.

### Как это работает сейчас (прочитано аналитиком в коде ветки от `origin/etalon` 89680ae3)

Оператор добавляет WB-заказы в существующую поставку двумя путями: в рабочем месте поставки через «Состав → Добавить заказы» и со списка заказов FBS через добавление в существующую поставку. Оба экрана вызывают один серверный метод `POST /operations/fbs-supplies/{id}/orders/batch` → `add_orders_to_existing_supply` (`backend/app/services/fbs_supply_service.py`). Добавлять можно в поставки со статусами `draft`, `assembling`, а для WB ещё `packed`.

Метод подтверждает добавление у WB, связывает подтверждённые заказы с поставкой у нас и затем, по WMS-475, запрашивает стикеры только что связанных заказов через `_request_order_stickers_for_picking` → `request_supply_print_batch`. Этот запрос обёрнут условием `if supply.status != FBS_SUPPLY_STATUS_DRAFT` (коммит b22ea096, WMS-475). Поэтому в черновике стикер добавленного заказа не запрашивается. Он появится только когда оператор нажмёт «Начать работу с поставкой» (`start_supply_work` запрашивает недостающие стикеры всей поставки) или запросит печать. Постановка WMS-475 (R1) была ограничена поставкой, «по которой работа уже начата». Тест `backend/tests/test_wms475_added_order_stickers.py` в сценарии `draft` прямо проверяет, что запроса нет (`assert batch_order_ids == []`).

Остальное, что важно для задачи, тоже установлено чтением кода:

- **Черновик с заданием упаковки.** Поставка может вернуться в `draft` и при этом сохранить задание упаковки: `detach_cancelled_order_from_supply` переводит её в `draft`, когда в ней не осталось активных заказов, а `packaging_task_id` не сбрасывает. Кнопка «Начать работу с поставкой» показывается только пока у поставки нет задания упаковки. Значит, в таком черновике у добавленных заказов нет автоматического пути получить стикер, кроме печати. Попала ли поставка AVpack в это состояние именно так, аналитик не устанавливал.
- **Где оператор видит код.** Вкладка «Упаковка и маркировка» показывает крупно последние четыре знака кода стикера или прочерк. Сама вкладка открыта в любом статусе, но строки заказов в ней появляются только при наличии задания упаковки; без него там заглушка «Сначала начните работу с поставкой…». Лист подбора печатается с вкладки «Состав» в любом статусе и содержит колонку «Стикер» с кодами заказов или прочерком. Ответ добавления и `GET …/workspace` возвращают `sticker.code` у каждого заказа.
- **Ozon.** Метод добавления отказывает поставке не-WB с `409 marketplace_not_supported`. Это происходит до обращения к WB и до блока запроса стикеров, поэтому место правки к Ozon не относится.
- **Отменённые заказы.** Добавить можно только заказ в статусе `new`, иначе будет `order_bad_status` (`fbs_supply_validator_service.py`). `request_supply_print_batch` не обращается к площадке за отменёнными заказами: они получают ошибку `order_cancelled`.
- **Повторы.** `_request_order_stickers_for_picking` берёт только заказы без `sticker_code`. Повтор того же запроса добавления возвращает 409 без второго добавления в WB (закреплено тестом WMS-475). В PostgreSQL действует частичный уникальный индекс: не больше одного готового стикера на заказ. Кнопка «QR» на упаковке запрашивает печать с `retry_missing=false`, то есть заново получает стикер у WB. Это существующее поведение печати, задача его не меняет.
- **Ошибки получения.** `request_supply_print_batch` превращает ошибки WB и хранилища в `sticker_status=error` у конкретных заказов, не прерывая работу. Ошибку `FbsPrintAssetError` (например, нет токена) перехватывает и логирует `_request_order_stickers_for_picking`. Эти отказы для поставки в работе проверены приёмкой WMS-475 (C2).

Экран аналитик при постановке в браузере **не открывал**. Интерфейс в этой задаче не меняется, а показ кода уже принят в WMS-475 на тестовом экране. Визуальная проверка обязательна при приёмке (C4).

### Цель

Как только WB подтвердил добавление заказа в поставку, стикер этого заказа запрашивается у WB, сохраняется и виден оператору. Статус поставки на это не влияет: черновик ведёт себя так же, как поставка в работе.

## 4. Решения аналитика и границы

**Р-1. Запрашиваем только добавленные заказы, а не весь черновик.** Владелец говорит именно о заказах, «которые он в нее добавлял». WMS-475 сознательно ограничила запрос добавленными заказами, и её тест это закрепляет. Остальные заказы черновика получают стикеры как сейчас: при «Начать работу» или печати. Расширение на всю поставку изменило бы поведение черновиков, созданных из заказов, о чём владелец не просил. Из решения следует граница в R1.

**Р-2. Одно правило вместо особого случая для черновика.** Правка — убрать зависимость запроса от статуса. Новый путь, очередь, статус, таблицу или фоновую задачу не вводить: существующего `_request_order_stickers_for_picking` → `request_supply_print_batch` достаточно. На production тот же путь уже отдал все 14 стикеров для заказов черновика. Из решения следует R2.

**Р-3. Тест WMS-475 для черновика меняется по этой задаче.** Сценарий `draft` в `test_wms475_added_order_stickers.py` закрепляет прежнее поведение (запроса нет). Его нужно перевести на ожидание R1. Это не переписывание требований WMS-475: её R1 остаётся верным для поставки в работе, а WMS-537 распространяет то же правило на черновик.

**Р-4. Только бэк.** Показ кода на упаковке и в листе подбора уже есть, фронт не меняется (правило AGENTS.md: задача про бэк не разрешает менять фронт). Миграций не требуется.

**Р-5. Выпуск — в пакете, не хотфиксом** (уточнение владельца «В пакете»). Данные production по поставке AVpack уже исправлены ведущим; повторять ручной запрос не нужно.

**Вне задачи, только замечено.** Первое: создание поставки из заказов тоже не запрашивает стикеры в черновике. Они приходят при «Начать работу», владелец об этом не просил, требование не вводится. Второе: в черновике с сохранённым заданием упаковки кнопка «Начать работу» не показывается (см. раздел 2). Задача это не меняет. Ведущий решит, нужен ли отдельный разбор.

**Вопросов владельцу нет.** Неизвестных, от которых зависит бизнес-результат, не осталось: объект (добавленные заказы), площадка (WB) и срок выпуска (в пакете) заданы.

## 6. Сверка

**От исходных слов к требованиям.**

- «у AVPAC по последней поставке»: случай описан в разделе 2; данные production исправлены ведущим, задача про код (Р-5).
- «у заказов которые он в нее добавлял»: объект — добавленные заказы (R1, Р-1). Их поставка была черновиком, поэтому черновик приравнен к поставке в работе (R1, R2).
- «не отображаются эти QR-коды… не подтянулись… коды ВБ»: стикер запрашивается у WB, сохраняется и виден на экране (R1; C1, C3, C4); при отказе WB подтягивается позже (R3; C5).
