# WMS-710 · Печать листа подбора FBS для «Империи ФФ»: порядок и состав мест как на вкладке «Подбор»

Статус на 09.10.2026: постановка. Код не написан. Документ — требования, решения и проверки для следующих этапов (тесты до кода, разработка, ревью, приёмка). Рабочая ветка feat/wms710-imperiya-print-order построена на ветке WMS-709 (коммит 06744782a), поэтому экран подбора в ней уже в состоянии этапа 1 WMS-709. Выкатывать WMS-710 отдельно от WMS-709 нельзя: прод сейчас стоит на хотфиксе 9971abed3, а PR #418 с WMS-709 ещё не влит в etalon.

## 1. Исходный запрос и уточнения

### 1.1 Слова владельца (дословно)

«Вот ровно тот порядок, который указан сейчас на вкладке подбор, вот он должен отображаться и при печати листа подбора.
Сделай это фичер-тоглом только для империи львов. Напиши где-то крупно в проекте. Напиши коммент в коде.

Наверное, в нем, по сути, поменяется только порядок.»

### 1.2 Уточнения ведущего (не слова владельца, а объём, который ведущий подтвердил по коду)

Тенант, для которого действует изменение: «Империя ФФ», UUID 7b98a8aa-c03c-4649-9677-a645be45c622, slug imperiya-ff-3iyr4. Владелец называет его «империя львов». Это проверено чтением базы прода 09.10.2026. Отдельный арендатор «ИП Львова В.В.» (UUID 5fbf633c-3ea9-4c29-b5f5-f549b122bcae) под изменение не попадает и должен печататься как раньше.

Изменяемый документ — лист подбора FBS. Его печатают два места: карточка одной поставки и групповая сборка нескольких поставок.

## 2. Существующий процесс и цель изменения

### 2.1 Что оператор видит на вкладке «Подбор» (проверено чтением кода, ветка 06744782a)

Вкладка «Подбор» в карточке поставки FBS рисуется так: FfFbsSupplyWorkspace, этап «Подбор», затем FfUnloadPickPage с источником fbs, затем UnloadPickScreen с признаком groupByCell, затем таблица FbsCellPickTable. Групповая сборка использует ту же таблицу через FfFbsAssemblyPick (строка 736 и далее). Список мест строит функция cellPickRowsOf в pickRows.ts (строка 93).

Порядок на вкладке такой. Сначала идёт ячейка, и ячейки сравниваются не по символам, а по числам внутри кода: Intl.Collator с локалью ru и numeric (pickRows.ts, строка 87), поэтому Ж-1-7 стоит раньше Ж-1-14. Внутри ячейки сначала идёт россыпь, потом тара по названию, и тара может быть вложена в тару (палета, короб на палете). Места без ячейки и сортировочная зона «Без ячеек» стоят в самом конце. Раздел «Уже подобрано» — отдельный раскрывающийся блок в конце, по умолчанию свёрнут (FbsCellPickTable.tsx, строки 39–42).

Места для вкладки приходят с сервера из ответа pick-options (backend fbs_picking_service.get_pick_options, строка 291). Туда попадают остатки склада больше нуля (pick_option_location_service.py, строка 404), а также места, из которых уже что-то сняли, даже если сейчас там ноль (FfUnloadPickPage.tsx, строка 329). Сортировочная зона на сервере получает подпись «Без ячеек» (pick_option_location_service.py, строка 52).

### 2.2 Что печатается сейчас

Печать запускает printPickingList: в карточке поставки это FfFbsSupplyWorkspace.tsx, строка 3177, в групповой сборке это FfFbsSupplyAssembly.tsx, строка 274.

Строки листа — это товары, по одной строке на товар. Порядок строк товаров задаёт fbsBuildPickingRows (fbsUx.ts, строка 361): заказы сортируются по tape_order_index, и это тот же порядок, что у ленты «Печать всего» (комментарий WMS-580 в том же месте). Поэтому строки листа должны идти в одной последовательности с лентой.

Места внутри строки товара берутся из ответа picking-context (backend fbs_picking_print_service.py). Там места сгруппированы по приёмке (П: номер, В: возврат, И: инвентаризация, «Без привязки к документу:»). Внутри группы строки выглядят так: «Короб №3 · ШК · Ж-1-7: 5 шт.», а у сортировки без ячейки только контейнер. Порядок групп — это порядок создания приёмок. Порядок мест внутри группы — это ORDER BY по коду ячейки прямо в базе (строка 95). Приёмки попадают в групповой список, даже если по ним сейчас ничего не лежит: группа создаётся для каждой приёмки с проведённым количеством (строки 44–60), и пустые заголовки в листе печатаются.

### 2.3 Почему порядок на листе и на вкладке разный

Обход на вкладке идёт по ячейкам, а лист группирует места по приёмкам, а внутри группы сортирует по коду в базе. Пример: в базе Ж-1-14 стоит раньше Ж-1-7, потому что при сравнении символов первая разница — «1» против «7». На вкладке наоборот. Кроме того, места одного товара на листе сначала разделены по приёмкам, и приёмка, созданная раньше, выводится выше даже тогда, когда её место на обходе идёт позже. Одинаковую последовательность обхода на листе с группами по приёмкам получить нельзя, поэтому группировку придётся менять (см. решение D1 и вопрос Q1).

### 2.4 Цель

Для Империи лист должен перечислять места каждого товара в том же порядке и в том же наборе, что вкладка «Подбор» показывает для этого товара. Вся остальная вёрстка листа остаётся прежней. Для всех остальных клиентов лист не меняется ни в одном байте.

## 3. Требования

Одно требование — одно правило. Условие «для Империи» означает, что признак из R7 включён для тенанта Империи ФФ.

**R1. Порядок мест товара.** Условие: лист подбора FBS печатается для тенанта Империи. Результат: в каждой строке товара места в колонке «Поставка / ячейка / короб» идут в том же порядке, в каком вкладка «Подбор» показывает места этого товара при обходе сверху вниз. Порядок обхода: ячейки по коду (R4); внутри ячейки сначала россыпь, затем тара по названию, вложенная тара после своей родительской; места без ячейки; сортировочная зона «Без ячеек»; в самом конце места из раздела «Уже подобрано» (вопрос Q3). Основание: слова владельца «То, что они видят на подборе, точно в этой последовательности у них должно печататься в листе подбора».

**R2. Состав мест.** Условие: тот же лист. Результат: на листе есть ровно те места товара, которые вкладка показывает для этого товара, без лишних и без пропущенных. Из этого следует: (а) места с остатком больше нуля печатаются, как и сейчас; (б) места, из которых уже снято, но где сейчас ноль, попадают на лист так же, как на вкладку (вопрос Q4); (в) места, которые вкладка не показывает (например, скрытые правилом WMS-709 R4, вопрос Q5), на лист не попадают. Основание: слова владельца «то, что они видят на подборе».

**R3. Подпись документа на каждой строке.** Условие: строка места печатается на листе Империи. Результат: в начале строки стоит подпись приёмки или документа, к которому привязано место: «П: 96», «В: 12», «И: ab12cd34», «Без привязки к документу:» (те же тексты, что сейчас стоят в заголовках групп). Сам текст места остаётся прежним, например «Короб №3 · ШК · Ж-1-7: 5 шт.». Отдельных заголовков групп нет. Основание: решение D1. Слова владельца «поменяется только порядок» здесь не совсем точны, поэтому пункт зависит от вопроса Q1.

**R4. Порядок ячеек.** Условие: тот же лист. Результат: ячейки сравниваются тем же правилом, что вкладка: по числам внутри кода (Ж-1-7 раньше Ж-1-14), а не по порядку символов в базе. Основание: решение D5; вкладка сравнивает так (pickRows.ts, строка 87).

**R5. Сам лист не меняется.** Условие: лист Империи. Результат: заголовок «Лист подбора FBS», шапка с селлером, складом, маршрутом и сроком, все двенадцать колонок с их шириной и подписями, строки товара (номер, фото, товар, артикул, цвет, размер, заказы, стикер, «Взять», «Подобрано», маркировка), футер с текстом «Актуальное серверное состояние на момент печати». Меняется только содержимое колонки «Поставка / ячейка / короб»: порядок строк мест и подписи из R3. Основание: слова владельца «При этом сам лист подбора ты не меняешь, он останется прежним».

**R6. Остальные клиенты без изменений.** Условие: тенант не Империя ФФ, включая ИП Львова В.В., площадки WB и Ozon, одиночная поставка и групповая сборка. Результат: HTML листа и данные, на которых он строится, совпадают с версией до изменения байт в байт. Основание: слова владельца о том, что изменение делается только для Империи.

**R7. Признак по тенанту.** Условие: открыт лист подбора. Результат: признак «Империя» включён ровно для UUID 7b98a8aa-c03c-4649-9677-a645be45c622 и выключен для всех остальных. Признак отдаётся фронту в существующем ответе текущего пользователя, рядом с похожим признаком numbered_inbound_box_labels из WMS-565, и не смешивается с ним: у каждого признака свой набор. Основание: слова владельца «фичер-тоглом только для империи львов»; решение D4.

**R8. Групповая сборка.** Условие: лист групповой сборки из двух и более поставок для Империи. Результат: места каждого товара собираются по всем поставкам группы и идут в порядке групповой вкладки «Подбор» (план и снятое суммируются по группе, как сейчас). Одно и то же место, попавшее в две поставки группы, даёт одну строку, а не две, и два разных места с одинаковым текстом дают две строки, а не одну. Основание: «то, что они видят на подборе»; групповая вкладка тоже в ячеечном виде (FfFbsAssemblyPick.tsx, строки 736–744). Найденный риск: сейчас групповой лист склеивает строки по совпадению текста (FfFbsSupplyAssembly.tsx, строки 347 и 350–351), и два разных короба без ШК с одинаковым текстом могут схлопнуться в одну строку. Для Империи это недопустимо (решение D7).

**R9. Ozon.** Условие: поставка Ozon у тенанта Империи. Результат: R1–R5 действуют так же, как для WB. Основание: признак задан по тенанту, а не по площадке (решение D8).

**R10. Сбой данных вкладки.** Условие: сервер не отдал ответ pick-options, по которому строится порядок. Результат: лист печатается в прежнем порядке с прежним предупреждением «Не удалось получить ячейки и тару — лист подбора напечатан без них», окно печати не блокируется. Основание: уже существующее поведение печати (WMS-528, комментарий в printPickingList); решение D9.

**R11. Серверное состояние.** Условие: оператор печатает лист, когда на вкладке есть несохранённый ввод «Собрано». Результат: лист показывает состояние, сохранённое на сервере на момент печати, как и сейчас. Основание: существующий футер листа и поведение printPickingList; решение D10.

**R12. Заметно в проекте.** Условие: изменение принято. Результат: (а) создаётся реестр клиентских исключений docs/KLIENTSKIE_ISKLYUCHENIYA.md с записью о Империи ФФ: UUID, что меняется, какие места кода затронуты, как снять исключение; (б) у признака в коде стоит комментарий, что он только для Империи ФФ, со ссылкой на реестр; (в) в разделе 3 файлов AGENTS.md и CLAUDE.md добавлена одна строка, одинаковая в обоих файлах, со ссылкой на реестр. Файлы должны остаться идентичными (CI уже это проверяет). Основание: слова владельца «Напиши где-то крупно в проекте. Напиши коммент в коде.»

Основание: ведущий поручил не путать тенанты. Владелец называет Империю «империя львов», а в базе у её арендатора название «Империя ФФ», у другого арендатора — «ИП Львова В.В.». ## 4. Решения аналитика и открытые вопросы

Здесь записаны решения, которые аналитик принял сам, и вопросы, которые требуют ответа владельца. Решения отделены от слов владельца.

### 4.1 Решения аналитика

**D1. Заголовки групп по приёмкам на листе Империи не сохраняются, подпись приходит на каждую строку (R3).** Причина: обход вкладки чередует места разных приёмок, поэтому группа не может стоять одним непрерывным блоком. Владелец сказал, что порядок меняется, но подписи приёмок при этом должны остаться, иначе оператор не увидит, откуда место. Альтернатива вынесена в вопрос Q1.

**D2. Приёмки, по которым сейчас ничего не лежит, на листе Империи не печатаются (R2).** Причина: на вкладке таких приёмок нет, а состав должен совпадать. Сегодня лист печатает их пустыми заголовками (fbs_picking_print_service.py, строки 44–60 и 133). Для остальных клиентов это поведение сохраняется (R6).

**D3. Порядок строк товаров на листе остаётся порядком ленты (R14, вопрос Q2).** Причина: комментарий WMS-580 прямо требует, чтобы лист и лента шли в одной последовательности, а строки листа строятся от тех же заказов. Сама вкладка товары не упорядочивает: один товар разбросан по нескольким ячейкам, поэтому «порядок вкладки» для строки товара не определён.

**D4. Признак — набор UUID в коде, отдаётся через ответ текущего пользователя (R7).** Причина: это тот же способ, что у признака numbered_inbound_box_labels (box_barcode_service.py, строки 58–67; auth.py, строки 127 и 475; useAuth.ts, строка 50; App.tsx, строка 3844). Владелец хочет видеть такой признак в коде и в реестре (R12). Колонка в таблице арендаторов потребовала бы миграцию и была бы невидима в проекте. Признак должен быть отдельным набором, чтобы его можно было снять, не трогая другие признаки.

**D5. Ячейки сортируются по правилу вкладки, а не по порядку базы (R4).** Причина: иначе Ж-1-14 окажется раньше Ж-1-7 и лист разойдётся с вкладкой.

**D6. Источник порядка и состава — те же данные, что у вкладки; текст строки и приёмку берём из picking-context.** Порядок и состав мест вычисляются из pick-options той же функцией, что и вкладка (cellPickRowsOf). Текст строки и подпись приёмки остаются из picking-context. Сопоставление двух ответов — технический вопрос для разработчика: в picking-context сейчас нет идентификаторов мест, есть только строки текста, а в pick-options идентификаторы есть. Соединять их по тексту нельзя, потому что тексты могут совпадать (см. R8). Разработчик выбирает способ (например, аддитивное поле идентификатора в picking-context, R14).

**D7. В групповой сборке места склеиваются по идентификатору места, а не по совпадению текста (R8).** Причина: текущая склейка по тексту схлопывает разные места с одинаковым текстом. Для Империи это ошибка. Для остальных клиентов текущая склейка остаётся как есть (R6), и её исправление в этой задаче не делается.

**D8. Признак по тенанту, без различия WB и Ozon (R9).** Причина: владелец говорит о листе подбора FBS и о тенанте, о площадке он ничего не сказал. Решение мелкое, но его стоит подтвердить при приёмке.

**D9. Нет данных вкладки — прежний порядок, печать не блокируется (R10).** Причина: уже существующее правило WMS-528 (печать не блокируется, если сервер не отдал места).

**D10. Лист показывает серверное состояние на момент печати (R11).** Причина: так печать работает сейчас, и так написано в футере листа.

### 4.2 Вопросы владельцу

Для каждого вопроса указан ответ по умолчанию, с которым документ записан. Если владелец ответит иначе, требования и проверки переписываются.

**Q1. Подписи приёмок. Слова владельца «по сути поменяется только порядок» здесь не полностью точны.** Аналитик меняет две вещи: подпись приёмки на каждой строке вместо заголовка группы (D1) и исчезновение приёмок без остатка (D2). Вариант А (по умолчанию, записан в R3): подпись на каждой строке, приёмки без остатка не печатаются. Вариант Б: сохранить заголовки групп и вставлять заголовок заново каждый раз, когда обход переходит к месту другой приёмки. Тогда один документ может встретиться в листе несколько раз, но заголовки останутся похожими на сегодняшние. Нужно выбрать вариант и подтвердить, что приёмки без остатка исчезают.

**Q2. Порядок строк товаров (D3).** По умолчанию строки товаров остаются в порядке ленты (WMS-580). Альтернатива: переставлять строки товаров по первому месту на обходе. Это изменит порядок, который согласован с лентой, поэтому по умолчанию не делаем.

**Q3. Раздел «Уже подобрано».** На вкладке он свёрнут по умолчанию. По умолчанию его места печатаются в самом конце листа в том же порядке. Альтернатива: печатать только то, что видно без раскрытия. Тогда на листе пропадают места, с которых уже сняли товар, и оператор может не увидеть, где лежит уже подобранное.

**Q4. Места с нулевым остатком, но со снятым количеством.** Вкладка показывает такие места. По умолчанию они печатаются строкой вида «...: 0 шт.», как на вкладке. Альтернатива: не печатать. Уточнение по данным: на проде в таблице подборов для Империи сейчас нет ни одной записи (см. раздел 4.4), поэтому вопрос пока не проявляется на живых данных, но проявится, как только оператор начнёт подбирать.

**Q5. Зависимость от WMS-709, этап 2.** По правилу R4 из WMS-709 после его выпуска вкладка перестанет показывать места полностью собранного товара, на которых в этом подборе ничего не снято. По правилу «то, что они видят на подборе» лист Империи тоже перестанет их печатать. По умолчанию это принимается. Подтвердить, что владелец хочет именно такой лист для полностью собранного товара.
