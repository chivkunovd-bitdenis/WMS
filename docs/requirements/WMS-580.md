# WMS-580 · FBS: лист подбора и лента QR — один и тот же порядок заказов

Статус: постановка готова 29.09.2026, реализация не начиналась. Аналитик — сессия Claude (Sonnet 5) по навыку wms-product-analyst.
Связанная задача: [WMS-574](WMS-574.md) (в этой же рабочей копии, этап A) — групповая сборка нескольких поставок. Вкладка «Упаковка и маркировка» окна сборки, где по WMS-574 R12–R25 должна появиться печать ленты для каждой поставки группы, на момент этой постановки ещё не реализована (см. п. 2.4). Разработчик WMS-580 должен уточнить у ведущего актуальное состояние этой вкладки перед правкой, чтобы не столкнуться с параллельной работой над frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx и FfFbsSupplyAssembly.tsx.

## 2. Что есть сейчас (проверено по коду этой рабочей копии, ветка feat/wms580-picklist-tape-order от origin/feat/wms574-multi-supply, SHA 17cdcf37; база — etalon 3c73554d + WMS-574 этап A + WMS-575)

### 2.1 Одна поставка WB/Ozon — лист подбора и лента уже используют один порядок

Оператор в карточке поставки (frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx) на вкладках «Состав» и «Подбор» жмёт «Печать листа подбора» (data-testid="fbs-pick-list-print", строки 3001 и 3044) — печатается HTML-документ (buildFbsPickingListPrintHtml, frontend/src/screens/v2/fbsUx.ts:378–462) со строками по товару/размеру: номер позиции (сквозной диапазон «12–15» и т.п.), фото, товар и идентификаторы, размер, ячейка/тара, «Заказы WB» (список номеров), стикер (коды КИЗ/ШК по тем же заказам), «Взять», «Подобрано», маркировка.

На вкладке «Упаковка и маркировка» той же карточки кнопка «Печать всего (N)» / «Печать выбранного (N)» (строка 3102–3108) вызывает openBulkOrderMarkingPrint (2161–2214), которая отправляет на сервер `order_ids: orders.map(order => order.id)` — печатает ленту стикеров/QR в точности в том порядке, в котором эти заказы переданы.

Оба действия читают заказы поставки из одного и того же списка `fullTapeOrders = [...workspace.orders].sort((a, b) => a.tape_order_index - b.tape_order_index)` (строки 2401–2403): «Печать листа подбора» группирует эти же отсортированные заказы по товару в `pickingRows` (2405–2469, группировка через Map — первое появление товара в порядке `fullTapeOrders` определяет позицию строки, поэтому строки листа идут в том же порядке, что и tape_order_index; внутри строки массивы `wbOrders`/`stickerCodes` пополняются в этом же порядке итерации, то есть остаются параллельными); печать ленты («Печать выбранного» — filter, «Печать всего» — сам массив) без изменений передаёт этот же порядок в order_ids.

`tape_order_index` — не локальное поле фронта, а число, которое сервер вычисляет один раз на весь ответ карточки: backend/app/services/fbs_workspace_service.py:109–113 — `tape_order_index_by_id = {order.id: index for index, order in enumerate(sorted(orders, key=picking_list_order_key))}`. Функция `picking_list_order_key` (backend/app/services/fbs_picking_order_service.py:27–30, модуль называется «One deterministic order for the FBS picking list and full sticker tape») сортирует сначала по артикулу/SKU/размеру/названию товара, затем по номеру заказа WB, затем по id заказа — один и тот же ключ для всех потребителей: fbs_workspace_service.py (число для фронта), fbs_order_tape_print_service.py:39,229 (см. ниже) и fbs_scan_auto_print_service.py:262 (кому достаётся штука при печати по сканy ШК).

На сервере печать ленты (backend/app/services/fbs_order_tape_print_service.py) не переупорядочивает присланный список: `_orders_in_requested_order`/`dict.fromkeys(order_ids)` сохраняет порядок клиента (строки ~165–195). Дополнительно, только когда печатается полный набор незаотменённых заказов поставки («Печать всего» без выбора), сервер на всякий случай сам пересортировывает список тем же ключом `picking_list_order_key` (строки 218–230) — то есть даже если бы клиент прислал заказы в другом порядке, итог не разойдётся с листом подбора. Для частичной печати («Печать выбранного») сервер верит присланному порядку — это подмножество того же глобально отсортированного списка, относительный порядок внутри него не меняется при фильтрации.

Эта синхронизация — не новая: коммит 5fb9a6fc «fix(fbs): align picking list and QR tape order» (23.08.2026) уже вносил её; проверено `git merge-base --is-ancestor`, что этот коммит — предок текущих боевых версий (3e125074, a80b8991, 4d9ef2ba, f52ee419 из памяти агента). Значит, для обычной поставки (и WB, и Ozon — код не различает маркетплейс в этом месте) лист подбора и лента уже печатаются в одной последовательности в проде.

Компонент frontend/src/screens/v2/FfFbsPickList.tsx (диалог с отдельной ручкой getFbsPickingList) с этим механизмом не связан: используется только предпросмотром frontend/src/screens/v2/fbs-pick-list-preview.tsx и каталогом ui-kit, в реальном процессе оператора не участвует.

### 2.2 Порядок внутри одной строки листа (несколько заказов на один товар/размер)

Внутри строки листа подбора заказы одного товара/размера идут по возрастанию номера заказа WB (`int(order.wb_order_id)` — второй элемент `picking_list_order_key` после группового ключа товара). Ровно в этом же порядке эти заказы появляются в ленте (вставка в `wbOrders` идёт по той же итерации `fullTapeOrders`).

### 2.3 Заказы, «которых нет в листе подбора»

Проверено по коду: `pickingRows`/`fbsAssemblyPickingRows` строят строку для каждого заказа поставки без исключений — даже заказ без сопоставленного товара получает свою строку с ключом `unmapped-{order.id}` (fbsUx-подобная группировка в FfFbsSupplyWorkspace.tsx:2405–2469 и fbsSupplyAssembly.ts:278–313). Отсутствие остатка в месте хранения не убирает строку — она печатается с «Нет свободного остатка» в колонке «Ячейка/тара» (fbsUx.ts:399). Сценарий «заказ подобран/спланирован, но не попал в лист» в текущем коде не воспроизводится.

Обратная ситуация существует и не связана с листом подбора: заказ со статусом «отменён» исключается из фактической печати ленты (backend/app/services/fbs_order_tape_print_service.py:218–222, `cancelled_orders`/`ordered`), и заказ, для которого WB не вернул стикер (`qr_asset_id` отсутствует), тоже пропускается при печати с ошибкой `order_qr_missing`. Такой заказ остаётся строкой в листе подбора (с прежним «Взять»), но физически стикер на него не печатается — это не новая проблема WMS-580 и не про порядок, а про то, что лента может быть *короче* списка по причинам, не связанным с последовательностью (эта причина уже разбиралась раньше — комментарий L8 от 21.08.2026 в fbs_order_tape_print_service.py про случай, когда «лента печаталась короче листа подбора» из-за одиночных сбоев WB).

### 2.4 Групповая сборка WMS-574 — состояние на момент постановки

Групповой лист подбора (Д14 WMS-574) — `fbsAssemblyPickingRows` (frontend/src/screens/v2/fbsSupplyAssembly.ts:278–313), вызывается из `printPickingList` окна сборки (frontend/src/screens/v2/FfFbsSupplyAssembly.tsx:222–266, кнопка «Печать листа подбора», data-testid="fbs-pick-list-print", строка 363). Функция идёт по поставкам группы в порядке массива `ordered` (тот же порядок, что задаёт `supply_ids` в адресе — frontend/src/screens/v2/FfFbsSupplyAssembly.tsx:154–160), внутри каждой поставки сортирует её заказы тем же `tape_order_index`, что и одиночная карточка (строка 281). Тест frontend/src/screens/v2/fbsSupplyAssembly.test.ts (строки ~260–279) подтверждает суммирование плана и порядок `wbOrders` по группам, но не проверяет отдельно соответствие порядку ленты.

Вкладка «Упаковка и маркировка» окна сборки, где по требованиям WMS-574 (R12–R25, docs/requirements/WMS-574.md) должна появиться кнопка «Печать всего/выбранного» внутри рамки каждой поставки группы, на момент этой постановки **не реализована**: `AssemblySupplyFrame` в frontend/src/screens/v2/FfFbsSupplyAssembly.tsx рендерит для этой вкладки `{null}` (строка ~380, стадия `packing`). Требования WMS-574 R14, R21 и R26 (docs/requirements/WMS-574.md) прямо обязывают, что этот блок будет «тем же кодом», что вкладка «Упаковка и маркировка» карточки одной поставки, вынесенным в общий компонент, а печать ленты в рамке — тем же действием, что кнопка «Печать всего/выбранного» карточки, для заказов именно этой поставки (не всей группы). Значит, лента группы физически остаётся *по-прежнему поставочной* (WB не объединяет стикеры разных поставок), а не единым документом на всю группу — только лист подбора (Д14) объединяет несколько поставок для удобства сборки.

### 2.5 Печать QR по одному скану — к ленте не относится

На той же вкладке «Упаковка и маркировка» галка «Печатать QR» (data-testid="fbs-scan-print-qr-toggle", FfFbsSupplyWorkspace.tsx:3196–3213) управляет печатью по каждому отдельному скану ЧЗ/ШК (одна этикетка за раз, через тот же scan-kiz-reprint/scan-auto-print), а не пакетной лентой «Печать всего/выбранного». Порядок печати по этой галке определяется порядком сканирования оператором, а не листом подбора — этот механизм в задаче не участвует.

## 3. Цель

Печать листа подбора и печать ленты QR (кнопки «Печать всего»/«Печать выбранного») для одной и той же поставки должны выводить заказы в одинаковой последовательности: i-я позиция (заказ) в порядке ленты соответствует i-му упоминанию этого заказа в листе подбора. Это уже так в проде для обычной поставки WB и Ozon (п. 2.1) — задача превращает существующий факт в явное, проверенное тестами требование продукта и защищает его на время, пока параллельно дорабатывается групповая сборка WMS-574 (тот же файл FfFbsSupplyWorkspace.tsx, п. 2.4), а не описывает бой, которого сейчас нет.

## 4. Решения аналитика

- **Д1. Какой документ ведущий.** Последовательность задаёт сервер: `tape_order_index`/`picking_list_order_key` (артикул/SKU/размер/товар, затем номер заказа WB) — единый источник и для листа подбора, и для ленты. Ни лист, ни лента не пересчитывают порядок независимо друг от друга. Основание: слова владельца («в той же последовательности», без указания, что менять) + уже работающий на проде механизм (п. 2.1) — простейшее решение, не дублирующее вычисляемую величину (AGENTS.md, раздел 3: «Вычисляемую величину не дублируй вторым независимым источником»).
- **Д2. Порядок заказов одного товара внутри строки листа.** По возрастанию номера заказа WB — это уже действующий тай-брейк `picking_list_order_key` (п. 2.2), других сигналов от владельца о порядке внутри строки нет.
- **Д3. Заказы «не попавшие в лист».** Проверка по коду (п. 2.3) показала: в действующем механизме такого не бывает — каждый заказ поставки получает строку. Поэтому правило «класть по краю ленты» не вводится: применять его было бы новым запретом/веткой без наблюдаемого случая (AGENTS.md — не выдумывать поведение без основания). Требование R3 ниже фиксирует это как регрессионную проверку, а не как новое поведение.
- **Д4. Отменённые заказы и заказы без полученного от WB стикера.** Не входят в объём этой задачи: они не про последовательность, а про то, что лента может быть короче списка по причинам сбоя/отмены — это существующее, отдельно разобранное поведение (комментарий L8 21.08.2026, п. 2.3). Задача не меняет состав печати, только порядок уже печатаемых.
- **Д5. Групповая сборка WMS-574.** Печать ленты внутри окна сборки на момент постановки не реализована (п. 2.4) и не входит в код этой рабочей копии. Т.к. WMS-574 R14/R21/R26 уже требуют, чтобы лента в рамке поставки была тем же действием карточки для заказов именно этой поставки (используя тот же `tape_order_index`, которым уже пользуется групповой лист подбора Д14/`fbsAssemblyPickingRows`), отдельного нового правила не вводится — R4 ниже прямо привязывает регрессионную проверку синхронизации к моменту, когда эта вкладка появится, без переписывания требований WMS-574 и без блокировки этой задачи. Основание: AGENTS.md — не переносить чужие ограничения и не плодить сущности; продуктовая развилка решена в рамках существующих требований WMS-574, а не заново.
- **Д6. Что защищаем.** Поскольку раньше эта синхронизация ломалась и чинилась трижды за один день (23.08.2026, коммиты 443638a1 → 30237f3b → 5fb9a6fc), а сейчас прямого автоматического теста, сравнивающего порядок листа подбора с порядком ленты, нет ни на бэке (нет отдельного test-файла для fbs_picking_order_service.py/fbs_order_tape_print_service.py на этот счёт), ни на фронте (fbsSupplyAssembly.test.ts проверяет суммирование, не порядок печати) — задача добавляет именно такие проверки как регрессионную защиту, без изменения продуктового поведения.

## 5. Требования

- **R1.** Условие: оператор в карточке одной поставки WB печатает «Печать листа подбора», затем — «Печать всего» (без выбора) на «Упаковке и маркировке». Результат: список заказов, полученный из порядка ленты (значения order_ids, отправленные в печать), при разбиении на те же товарные строки, что лист подбора, даёт ту же последовательность заказов внутри каждой строки, что и колонка «Заказы WB»/«Стикер» листа. Основание: Д1, п. 2.1.
- **R2.** То же условие, но для поставки Ozon. Результат — тот же, что в R1, с учётом группировки листа по позициям Ozon-отправления (несколько строк на один заказ при нескольких товарах в отправлении), при этом относительный порядок отправлений в ленте и в листе совпадает. Основание: Д1 (код не различает маркетплейс в вычислении tape_order_index).
- **R3.** Условие: то же, что R1/R2, но оператор жмёт «Печать выбранного» после отметки части заказов. Результат: подмножество заказов в ленте идёт в том же относительном порядке, что и в полном листе подбора (порядок внутри выбранных не меняется фильтрацией). Основание: Д1, п. 2.1.
- **R4.** Условие: в поставке есть заказ без сопоставленного товара, заказ без остатка в местах хранения, отменённый заказ или заказ, для которого сервер печати не вернул стикер. Результат: первые два всегда получают строку в листе подбора (регрессия — Д3); последние два не печатаются в ленте (существующее поведение, не меняется — Д4), но их отсутствие в напечатанной ленте не сдвигает порядок остальных заказов. Основание: Д3, Д4.
- **R5.** Условие: групповой лист подбора (Д14 WMS-574, кнопка «Печать листа подбора» окна сборки). Результат: заказы внутри каждой поставки группы в строках листа идут в том же порядке, что и `tape_order_index` этой поставки — том же порядке, в котором эта поставка печатает свою ленту (когда вкладка «Упаковка и маркировка» окна сборки появится по WMS-574). Основание: Д5, п. 2.4.
- **R6.** Как только в этой рабочей копии или в ветке WMS-574 появится печать ленты внутри рамки поставки на вкладке «Упаковка и маркировка» окна сборки — для этой поставки должны выполняться R1–R3 так же, как для той же поставки, открытой обычной карточкой. Основание: Д5; WMS-574 R14/R21 (docs/requirements/WMS-574.md) уже требуют идентичного поведения — это требование не заменяет их, а закрепляет проверку на стыке.

## 6. Проверки

Среда: локальный стенд или стенд Railway с тестовой организацией; поставка WB с ≥2 разными товарами и ≥2 заказами на один товар/размер; поставка Ozon с многотоварным отправлением; при наличии — группа из WMS-574 (docs/requirements/WMS-574.md, C1/C3) и вкладка «Упаковка и маркировка» окна сборки, если она уже реализована на момент проверки. Рабочие поставки операторов не трогать.
