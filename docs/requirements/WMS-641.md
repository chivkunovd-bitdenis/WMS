Ну да, да, кати, понятно, что только после… клиент попробует только после моего кати. А, облегченный режим хотфикса, да, должна быть такая история. Да делай все сразу … Только не копайтесь долго, пожалуйста, по 20 раз не пере… Не пересогласовывайте требования, не 33 ревью не проводите. Давайте со скиллами, но быстро. … нужно это сделать максимально экономно, поэтому везде, где можно, разработку и всякую хуйню, пускай делают дешевые агенты, типа Sonnet, не знаю, или Haiku, если это уместно.»

> «…форма обращений, которую мы сделали. … на проде, да, которая внизу, там вот этот знак вопроса. … когда там человек пишет именно про улучшение или про баг, эта хуйня должна в точности также проходить через этот же механизм. То есть она на вход просто как из отдельного источника приходит на бэк, и с ней уже работает … вся та же самая история. То есть баг также абсолютно как бы обрабатывается.»

Решения владельца из сообщения 3, перенесённые в требования: работа на открытом маке владельца в терминале через его залогиненные CLI-сессии (не Railway, не платные ключи); «кати» — только от владельца, клиенту «пробуйте» — только после «кати»; облегчённый режим хотфикса нужен; делать всё сразу, без повторных согласований требований и множества ревью; дешёвые модели везде, где уместно; форма «?» — ещё один источник того же конвейера.

Сообщение 7 меняет R21 и решение 17 в одном узком месте: команда привязки чата принимается от owner_user_id в клиентском чате через бот приёма (до этого бот приёма не принимал от владельца никаких команд). ## 2. Существующий процесс и цель изменения

### Как это работает сегодня (проверено чтением кода и документов 02.10.2026)

**Обработка обращений.** Сегодня обращения клиентов из Telegram-чатов разбирает сам владелец: читает чат, открывает несколько сессий Claude, отправляет в одной баг, в другой другой, затем передаёт результат второй модели. Это слова владельца (сообщения 1 и 3), в проекте нет компонента, который это делает.

**Форма «?» (WMS-624, на проде).** Проверено по [docs/requirements/WMS-624.md](WMS-624.md), [backend/docs/developer-requests.md](../../backend/docs/developer-requests.md) и коду backend/app/api/developer_requests.py, backend/app/services/developer_request_*.py, backend/app/models/developer_request.py:
- Пользователь seller или фулфилмента отправляет «Ошибку» или «Улучшение / доработку». Запись сохраняется в таблице developer_requests: тип, текст полей, клиент (организация / селлер), исходный путь экрана, серверная дата, автор, tenant.
- Фоновая задача WMS (Celery, раз в 60 секунд) сама создаёт по каждой записи карточку в приватной доске Trello, в списке «На рассмотрении (Клиентские)», с цветной меткой «Клиент» и строкой WMS-REQUEST-ID с UUID записи. Это относится к обоим типам, включая «Ошибку».
- Статус записи для пользователя («На рассмотрении», «В очереди», «В работе», «Готово») определяется тем, в каком из четырёх клиентских списков находится связанная карточка: команда двигает карточку, WMS подтягивает статус.
- Пользователь видит только свои обращения (проверка автора и tenant на сервере). Обратного канала «ответить пользователю» у формы нет: переписка клиента с командой в WMS-624 прямо отнесена к незапрошенному.
- Внутренние карточки команды в WMS не импортируются: синхронизация читает только карточки, связанные с записями по сохранённому ID карточки или найденные по UUID-маркеру записи.
- Доступа к этим записям у какой-либо внешней программы нет: все ручки developer-requests работают только от имени вошедшего пользователя; общего служебного (машинного) доступа в backend/app/core и backend/app/api/deps.py не найдено (поиск по проекту 02.10.2026).
- Настройки Trello берутся из переменных TRELLO_API_KEY, TRELLO_TOKEN, TRELLO_BOARD_ID, TRELLO_REVIEW_LIST_ID, TRELLO_QUEUED_LIST_ID, TRELLO_IN_PROGRESS_LIST_ID, TRELLO_COMPLETED_LIST_ID, TRELLO_CLIENT_LABEL_ID (backend/app/core/settings.py). В WMS-624 как существующий внутренний список доски упомянут «Задачи».

**Выкладка.** Проверено по .github/workflows/deploy.yml, .github/workflows/ci.yml, scripts/deploy/prod-update.sh, scripts/railway-staging-deploy.sh:
- Прод выкатывается только вручную: workflow «Deploy Production» (запуск вручную), который на сервере выполняет prod-update.sh из origin/etalon. Скрипт отказывается выкатывать коммит, которого нет в etalon; перед миграцией делает проверенный дамп базы (ошибка дампа останавливает выкладку); затем публичная проверка адресов, ответ 200 на «/», «/seller/», «/api/health».
- CI на pull request: проверка ссылки на номер задачи из бэклога (скрипт требует, чтобы WMS-NNN нашёлся в docs/KANONICHESKIY_BACKLOG.md), ruff, mypy, полный pytest, сборка и tsc фронта.
- Стенд (Railway) выкатывается отправкой ветки в origin/staging; на прод это не влияет.

**Правила проекта (AGENTS.md).** Требуют цепочку аналитик → разработчик → ревью → приёмка, документ требований на каждую задачу, merge в основную ветку и деплой только по явному разрешению; ограничивают Astra уровнем effort не выше high; не разрешают ведущему менять код продукта; запрещают добавлять пользовательские блокировки без требования владельца; при потере ответа внешней системы велят сначала выяснить результат операции.

**Среда владельца (проверено на этом маке 02.10.2026).** Установлены claude 2.1.123 и codex 0.153.4 (оба неинтерактивные режимы: claude -p / --resume / --model / --session-id; codex exec), gh, ffmpeg. Программы локальной расшифровки речи (whisper) нет, и по сообщению 4 она не нужна: голос расшифровывается через OpenAI. Свободно на диске 6,8 ГиБ.

**Telegram (по проверенным ведущим фактам и документации Bot API, прочитанной 02.10.2026).**
- Метода расшифровки голосовых в Bot API нет; расшифровка Premium относится к аккаунту человека, не к боту. Бот может скачать голосовое файлом.
- Бот видит все сообщения группы только при выключенном privacy mode или будучи администратором; сообщения других ботов не видит никогда.
- Непрочитанные ботом обновления хранятся на серверах Telegram не дольше 24 часов (цитата документации: «they will not be kept longer than 24 hours»).
- Создать бота, добавить его в чаты и назвать их ID может только владелец.

### Цель изменения

Один постоянно работающий на маке владельца агент заменяет ручное хождение владельца по чатам: собирает обращения из клиентских Telegram-чатов и формы «?», отделяет баги от улучшений, запросов и болтовни, сам разбирает их моделями владельца, присылает владельцу короткую понятную сводку с вердиктом, по слову «кати» выпускает безопасный хотфикс в облегчённом режиме, сообщает клиенту «пробуйте»; несрочное и улучшения кладёт в Trello; в партнёрском чате по слову «Trello» согласует с автором описание задачи и заносит её в Trello. Архитектура открыта для новых источников и закладывает основу передачи утверждённых задач в разработку и вечернего релиза.

### Что входит в эту задачу и что остаётся основой

Входит (R1–R37): приём из источников, расшифровка голоса, фильтр и ворох, классификация, аналитик, вопросы клиенту, оценка и кросс-проверка, сводки владельцу, пакетная сверка, команда «кати», облегчённый хотфикс и выкладка, отчёт и «пробуйте», Trello для несрочного и партнёрских задач, макеты по запросу, устойчивая работа на маке, подключение формы «?».

Только основа (R38): вся цепочка «утверждённые задачи → разработка → вечерний отчёт → кати → релиз». В этой задаче она не реализуется; фиксируется только то, что в неё входит и что для неё должно быть сохранено.

## 3. Решения аналитика (отдельно от слов владельца)

Применены навыки постановки и продуктового решения; прочитаны owner-cases.md и failure-cases.md. Из случаев применимы: «плохой случай 2» (самодельный запрет вместо требования: поэтому агент ничего не блокирует у пользователей и не вводит ограничений, которых нет в словах владельца) и разборы B02/B09 (потеря ответа внешней системы: сначала выяснить результат, потом повторять).

1. **Форма «?» забирается с бэка опросом со стороны мака.** Мак владельца не имеет публичного адреса, поэтому агент сам периодически запрашивает новые записи формы (исходящее соединение). Основание: слова владельца «приходит на бэк, и с ней уже работает» и среда «открытый мак». Альтернатива «читать готовые карточки из Trello» отвергнута: записи сохраняются и когда Trello недоступен (R14 из WMS-624), а карточка появляется лишь через цикл доставки; нужны и структурные данные (клиент, тип, поля), а не разбор текста карточки. Следствие: требуется отдельный машинный доступ только на чтение (R4). Способ (ручка, ключ, курсор) выбирает разработчик, ограничения заданы в R4–R6.
2. **У формы нет обратного канала к автору.** Автор формы может видеть только описание и четыре статуса (WMS-624). Поэтому для обращений из формы агент не задаёт клиенту вопросов о срочности и данных; срочность он определяет сам, нехватка данных попадает владельцу в сводку (R7). Единственное, что видит автор формы, — смена статуса; она определяется вопросом 1 ниже.
3. **Хотфикс в облегчённом режиме** — отдельный раздел 4, с перечнем обязательного и отбрасываемого и явным исключением из AGENTS.md.
4. **Команды даёт только владелец.** Тексты клиентов, партнёров, форм, карточек Trello и ответов моделей — данные, а не команды. «Кати» и любое указание принимаются только из канала владельца от его Telegram-аккаунта (R21). Основание: правила проекта о границах клиентов; в чатах пишут посторонние люди.
5. **Фильтр консервативен.** При сомнении сообщение не отбрасывается как болтовня (R8): потерянный баг дороже лишнего разбора. Основание: цель владельца — не терять обращения («я теряю эти чаты, я забываю им ответить»).
6. **Ворох собирается по паузе.** Сообщения одного чата объединяются в одно обращение; разбор начинается, когда в чате наступила тишина; поздние сообщения по той же теме присоединяются к тому же обращению, а не создают второе (R9). Длину паузы и предел вороха задаёт настройка; значения по умолчанию задаёт разработчик и записывает в инструкции запуска.
7. **Сообщения клиенту — закрытый перечень** (R13): вопрос о срочности, просьба о данных, «пробуйте» после выкладки, ответ на информационный запрос по вопросу 2. Всё остальное, включая подтверждения «приняли» и любые сроки, агент клиенту не пишет. Основание: «обещания клиенту — только после кати» (сообщение 3) и правило «не добавлять ненужного».
8. **Вопрос неизвестного исхода при отправке клиенту решён «не повторять».** Бот не может надёжно выяснить, дошло ли сообщение, если ответ потерян; повторная отправка даёт клиенту дубль. Поэтому перед отправкой агент записывает намерение; при неизвестном исходе сообщение не повторяется, а владельцу в сводке сообщается «отправка клиенту не подтверждена» (R35). Если разработчик найдёт способ достоверно выяснить результат — выясняет его до повтора (правило AGENTS.md про внешние операции).
9. **Карточки агента помечаются собственным маркером** «WMS-AGENT-ID: <номер>», отличным от «WMS-REQUEST-ID» из WMS-624, и перед созданием проверяется, нет ли уже карточки с этим маркером (по тому же принципу восстановления, что R13 из WMS-624). Карточки без WMS-REQUEST-ID синхронизация WMS-624 не трогает (проверено в коде синхронизации).
10. **Список для клиентских карточек из чатов — настраиваемый параметр**, по умолчанию «На рассмотрении (Клиентские)» (TRELLO_REVIEW_LIST_ID) с меткой «Клиент» (TRELLO_CLIENT_LABEL_ID). Это существующий документированный клиентский список, а не выдуманное имя; владелец называл его «новый от клиентов, грубо говоря». Для задач партнёрского чата список настраивается отдельно, по умолчанию существующий «Задачи» (упомянут в WMS-624), метка «Клиент» не ставится. Реальные списки доски аналитик не открывал.
11. **Хотфикс с миграцией базы или затрагивающий несколько процессов — не «безопасный короткий»** (R15, R23). Основание: выкладка с миграцией требует остановки писателей и дампа (prod-update.sh), а слова владельца говорят о «безопасном коротком хотфиксе».
12. **Роли моделей** (R36, по сообщению 4): Haiku — фильтр и предварительная классификация; Sonnet — рутина (структурирование задач, формулировки сводок и вопросов) и разработчик хотфикса; Opus — разбор багов, макеты и интерфейс; Sol 5.6 (Codex, gpt-5.6-sol) — рабочая модель на стороне Codex и запасная для интерфейса, разбора и хотфикса при недоступности Claude; Astra — только ревью и перекрёстная проверка, effort не выше high. Перекрёстная проверка: работу моделей Claude (Haiku, Sonnet, Opus) проверяет Astra, работу Sol проверяет Opus. Основание: слова владельца про экономию («Haiku», «Sonnet»), «опус ↔ Астра» (сообщение 1), «правки интерфейса можно отдавать Солу … Астра чисто как ревьюер» (сообщение 4); AGENTS.md (Astra не выше high; явное указание владельца для задачи приоритетнее общего распределения).
13. **Партнёрский чат: подтверждает автор исходного сообщения** (R28). Основание: «присылает … тому человеку, который это прислал» и «если чувак отвечает».
14. **Расшифровка голоса через OpenAI по ключу владельца** (R3). Основание: сообщение 4. Следствия, записанные аналитиком: на сервис OpenAI уходит только аудиофайл голосового сообщения (без остальной переписки и данных клиентов, кроме того, что сказано голосом); при отказе OpenAI или ключа нет возврата к локальной расшифровке (владелец её отверг), действуют повторы и сообщение владельцу по R3; значение ключа хранится только в локальной конфигурации мака вне Git, не печатается в логи, сводки и документы (R37). Ключ владелец нашёл в своих проектах и разрешил взять; из каталога другого проекта его переносит ведущий или владелец в локальную конфигурацию агента — аналитик его не открывал.
15. **Интерфейс: Opus или Sol, Astra не исполнитель.** По сообщению 4 правки интерфейса в хотфиксах и макеты можно поручать Sol 5.6; по умолчанию интерфейс делает Opus, Sol — при недоступности Opus или по выбору владельца. Для макетов (R31) то же правило принято аналитиком по аналогии с интерфейсом. Основание: сообщение 4; AGENTS.md §2 (явное указание владельца для конкретной задачи). Астру исполнителем не назначать.
16. **Бэк ручки чтения формы утверждён к реализации** (R4). Основание: «доработку бэка делай». Выкладка на прод остаётся по отдельному «кати» (AGENTS.md §1; решение 4).
17. **Два Telegram-бота.** Бот приёма добавляется в клиентские и партнёрский чаты, читает сообщения, задаёт вопросы клиентам, пишет «пробуйте» и согласует задачу с партнёром; команд владельца он не принимает вообще. Бот владельца пишет сводки, предпросмотры, отчёты, уведомления о простое и принимает команды только от Telegram-аккаунта владельца (owner_user_id) в его чате (owner_chat_id) и только через этого бота; клиентские чаты он не читает. Исходящее маршрутизируется по чату. Основание: сообщения 5–6 (два бота), R2 и R21 (команды только из канала владельца). Следствие для R21 не меняется: команды по-прежнему только из канала владельца от его аккаунта. Какой токен играет какую роль, задаёт конфигурация; распределение «приёмный — @wms_korob_support_bot, владельца — @wms_korob_bot» решил ведущий, явного подтверждения владельца нет.
18. **Кого агент может вызывать.** Из сообщения 5 («кого он может вызвать, кого не может») принято как описание уже записанных границ: модели только через залогиненные CLI по ролям R36 (Haiku, Sonnet, Opus, Sol 5.6; Astra только ревью, effort не выше high); разработчик хотфикса и макетчик работают в отдельном worktree с минимальными правами; аналитик читает проект только на чтение; правка выкладки, CI и каталога агента останавливает хотфикс. Новых полномочий сообщение 5 не добавляет.
19. **Привязка чата делается словами владельца и подтверждается им** (R39, R40). Основание: сообщение 7 («только я это могу сделать»). Решение аналитика: подтверждение тем же владельцем в том же чате, потому что поиск по названию может дать несколько селлеров (в разных фулфилментах бывают одинаковые названия), а ошибочная привязка открыла бы чужие данные. Поиск кандидатов выполняет доверенный код, не модель; показываются только владельцу. Привязка относится к новым обращениям; уже заведённое обращение сохраняет селлера, с которым оно создано, чтобы смена привязки не переадресовала открытый разбор.
20. **Граница данных держится базой, а не промптом** (R41, R42). Основание: сообщение 7 («железобетонно», «агента не уговаривать»), правила проекта о границах клиентов (AGENTS.md §3). Принято: список таблиц, доступных роли селлера, задан явно (разрешающий список), всё остальное закрыто; по проверенным ведущим фактам у 24 из 120 рабочих таблиц нет ни tenant_id, ни seller_id, а у части таблиц есть только tenant_id (принадлежность селлеру из строки не следует). Такие таблицы открываются роли только если принадлежность селлеру однозначно выводится через ссылку на документ или товар этого селлера (строки документов), иначе закрыты (fail closed). Способ (роль на селлера или иной механизм), состав политик и проверку выбирает разработчик, но граница обязана держаться и против произвольного запроса модели (включая смену роли, параметры сессии, функции). Создание ролей и политик на боевой базе — отдельное действие по поручению владельца.
21. **Форма «?»: селлер берётся из записи сервера, без селлера доступа нет** (R43). Основание: сообщение 7 и решение ведущего. Решение аналитика: если у заявки нет селлера (автор — сотрудник фулфилмента), доступ к базе не даётся: открыть по тенанту значило бы показать данные всех селлеров фулфилмента, а владелец просил границу «по этому селлеру». Для этого серверная ручка чтения формы отдаёт агенту tenant_id и seller_id записи (до этого они намеренно не отдавались); название клиента из текста заявки для выбора роли не используется. Общая роль wms_agent_ro клиентским обращениям (из чата и формы) не даётся.

### Отбрасывается в этом режиме

- Отдельная цепочка «аналитик → разработчик → ревью → приёмка аналитиком» с полным документом требований R1… и таблицей проверок C1… (остаётся вердикт «кати» и сводка с оценкой самого агента-аналитика).
- Применение навыка продуктового решения и чтение библиотек случаев ревьюером на каждый хотфикс (кроме одного прохода проверки выше).
- Несколько кругов ревью без новых оснований; повторное согласование требований.
- Локальный полный прогон набора тестов и дописывание тестов «ради покрытия».
- Ожидание отдельной приёмки перед сообщением «пробуйте» клиенту (достаточно проверки версии и повтора сценария).

### Явное исключение из AGENTS.md

Для хотфиксов, выпущенных по этому режиму, не выполняется полностью AGENTS.md §2 (постановка аналитиком, перекрёстное ревью в полном порядке, приёмка аналитиком, заключение в документе) и требование «документ с заполненной таблицей проверок и заключением» заменяется короткой версией. Основание: прямые слова владельца в сообщении 3 («облегчённый режим хотфикса… не пересогласовывайте требования, не 33 ревью не проводите, давайте со скиллами, но быстро») и в сообщении 1 («с минимальным количеством тестов»). Исключение действует только для хотфиксов по «кати» владельца и не распространяется на улучшения, миграции и задачи из партнёрского чата. Выбор моделей (Sol для интерфейса, Astra только как ревьюер) исключением из AGENTS.md не является: AGENTS.md §2 даёт приоритет явному указанию владельца для конкретной задачи (сообщение 4). Остальные правила AGENTS.md (границы клиентов, секреты, merge и деплой только по разрешению, effort Astra не выше high, честные отчёты) остаются полностью. Если владелец захочет закрепить исключение в самом AGENTS.md и CLAUDE.md (оба файла должны быть одинаковы, это проверяет CI), это делается отдельным решением; аналитик эти файлы не менял.

- Привязка (R39, R40; правка ведущего от 03.10.2026: названия не публикуются в клиентском чате). Команду «@бот привяжи к ИП <название>» принимает только код, только бот приёма и только от `owner_user_id`, в любом групповом чате, где есть бот приёма, даже если чата нет в `config.json` (голосом: в уже обслуживаемом клиентском чате). В партнёрском чате, в чате владельца и в личных чатах команда не действует, у не-владельца силы не имеет. Бот приёма в самом чате не отвечает ничего ни при каком исходе (0, 1, N кандидатов, отказ, ошибка шлюза, неактуальное подтверждение). Кандидатов ищет доверенный код без модели через шлюз (`find-seller`, `tools/support_agent/support_agent/seller_directory.py`) и отправляет владельцу БОТОМ ВЛАДЕЛЬЦА в его чат: «селлер X в фулфилменте Y, чат «<название чата>»», без идентификаторов. Подтверждает владелец там же ответом на это сообщение: «да» при одном кандидате, номер при нескольких (при одинаковых названиях «да» не выбирает); подтверждение не ответом на наше сообщение, не в чате владельца или по устаревшему предложению не действует. Привязывается тот клиентский чат, из которого пришла команда: его id фиксирует код при команде и хранит предложение. После подтверждения владельцу приходит «чат … привязан к …», в клиентский чат ничего. Привязанный чат добавляется в обслуживаемые как клиентский без правки `config.json` (после перезапуска тоже); сообщения чатов вне конфига и привязок агент не сохраняет и не обрабатывает. Привязка хранится в SQLite агента (таблицы `chat_bindings`, `binding_proposals`), перепривязка заменяет прежнюю. Обращение фиксирует селлера при создании (`seller_id`, `tenant_id` в данных обращения): перепривязка уже созданные обращения не меняет.

**Решения исполнителя по техническим вопросам.**
- Приём из Telegram: long polling; позиция чтения и сообщения записываются до подтверждения Telegram, повтор обновления игнорируется (уникальный ключ); отправка клиенту записывает намерение до вызова и при неизвестном исходе не повторяется, владельцу уходит «отправка не подтверждена».
- Вызовы CLI: `claude -p --output-format json` и `codex exec --json -o`, промпт через stdin, без API-ключей Claude и Codex (платный ключ OpenAI только для голоса). Переключение между CLI при лимите или недоступности с паузой CLI; остаток лимита CLI напрямую узнать нельзя, выбор идёт по порядку и паузам.
- Аналитик читает проект из отдельного worktree `.worktrees/support-agent-etalon` (свежий origin/etalon) в режиме только чтения (`dontAsk` и список разрешённых инструментов).
- Хотфикс: отдельный worktree `.worktrees/wms<NNN>-hotfix`; диспетчер сам проверяет бэклог-заголовок, документ с таблицей вердиктов и заключением, номер в коммитах, отсутствие миграций, ruff, mypy, целевые тесты и то, что тест падает на чистом origin/etalon; одна перекрёстная проверка; PR; CI (по JSON, не по коду выхода gh); перед merge сверка `deployed..origin/etalon` (чужие невыложенные изменения останавливают выкладку); после выкладки сверка SHA и трёх адресов; отчёт и «пробуйте».
- Номер WMS-NNN: максимум из бэклога origin/etalon, веток, коммитов, PR, worktree и выданных агентом, плюс один; перед PR повторная сверка.
