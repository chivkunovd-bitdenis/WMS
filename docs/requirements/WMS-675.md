В `recovery_plan_exact.json` действительно остались прежние `execution_state=WAIT_662_SUBSTATUS_FIX_AND_ISOLATED_NO_PUBLISH_RUNNER_REVIEW_THEN_LEAD_COMMAND`, `current662_missing_delta=11`, blocked15 и `operation_sequence` с изолированным захватом публикаций/target26. Нельзя тихо переписывать raw JSON ради совпадения с новым продуктом. Исполнитель должен предъявить отдельное актуальное пояснение к перенесённому историческому bundle (набору файлов), в котором источник и граница старых полей явно названы.

Только после команды root и проверенного общего деплоя будущий оператор заново читает 31 карточку штатным seller-bound provider (подключением именно этого продавца) вне блокировок строк БД; сверяет текущий состав и отмены; перечитывает фактические ledger (журнал проведения), движения/сторно, остаток, резервы, факты/начисления. Для каждой позиции вычисляет `missing = max(0, proved_unique - already_conducted)`; неизвестный/конфликтный расход не разрешается этой формулой. Изменение состава, отмена, сторно, неизвестный ответ или расход сверх доказанного предъявляются root как конкретное расхождение, без использования старых положительных targets.

При неизвестном результате читаются checkpoint (сохранённая точка продолжения)/ledger, внешняя сдача не повторяется. Сохраняются существующие 11 facts/22 charges. Нормальная публикация остатков по активным bindings этого seller/затронутым товарам работает штатно, лимиты оператора не меняются. Нельзя обещать ровно одну публикацию строго после outer commit: прежний нюанс after_commit на savepoint здесь не исправляется.

### Уточнение замещающего аналитика 07.10.2026: минимальная защита и объём тестов

WMS-675 не создаёт новый продукт и не меняет поведение WMS-662: это
операционное восстановление через уже принятый механизм после свежего proof,
verified deploy и команды root. Следовательно, защита бизнес-поведения для
будущего repair — существующие принятые tests/review WMS-662 на точном общем
кандидате; их ожидания и постоянные guards не ослабляются. Свежий snapshot
проверяется manifest/SQL/raw CSV и аналитическим сравнением, а не новым
«продуктовым» тестом передачи handoff.

Добавленный на подготовительной ветке
`backend/tests/test_wms675_recovery_evidence_contract.py` не считается такой

handoff. В данной аналитической дорожке файл не удаляется и не исправляется.
Root решает отдельно, нужна ли его узкая техническая коррекция для интеграции;
до этого он не выдаётся за доказательство отсутствия повторного списания.

Минимальная интеграция: root включает принятую 662 и запускает её существующие

### Как доказать силу автоматических проверок без фиктивного RED

Сначала отдельный тестировщик фиксирует P1–P6 до правок исполнителя. Frozen корректные источники могут сразу проходить; это не надо называть RED. Для проверок целостности нужны реальные негативные копии файлов: чужой UUID при прежнем totals31; удалённая/повреждённая карточка; отмена с after_ship; замена одного старого fact/charge ID при прежних totals; подмена времени/источника; попытка ненужной записи или расширения SQL scope. Проверяющий код должен выявить конкретное несоответствие, а затем пройти на исходной копии. RED такого проверяющего инструмента доказывает обнаружение искусственного повреждения evidence, не новый баг продукта и не дефект живого учёта. Нельзя делать тест на наличие придуманной будущей функции, буквальную строку нового отчёта или ослаблять существующий662/параллельный тест ради зелёного.

Если перенос полностью побайтный и нового исполняемого поведения нет, тестировщик прямо фиксирует «нового product RED нет; проверен перенос и чувствительность verifier к повреждению». Это основание ограничить реализацию адресными материалами, а не сочинять продуктовую поправку ради последовательности ролей. Старые пять check_recovery_plan_offline.py остаются проверками исторической матрицы со старым WAIT/blocked15; их успешный повтор не является доказательством текущей готовности662. Изменять их ожидания для подгонки под b404 нельзя; текущую проверку P5 отделяют.
