## 1. Исходный запрос и уточнения

Слова владельца 25.09.2026, дословно.

Вопрос по скриншоту отчёта (стенд Railway, селлер Denmarcs, «Жилетка утеплённая oversize» XS: приход
30, расход 0, остаток сейчас 66):

> что за хуйня отображается у нас в отчёте блядб по товародвижениям?

> приход 30
> движерий 0
> остаток 66

Правило «остаток ≠ расположение»:

> Я тебе еще раз на всякий случай это напоминаю, просто обрати на это внимание. Значит, перемещение между ячейками не должны нахуй не создавать никакие товародвижения. Это просто виртуальная залупа. Если товар принят, как только он принят, он на остатках. Как только проведена отгрузка, он списан. Как только проведена инвентаризация, он списан. Насрать во всех местах, где есть остаток, мы смотрим на остаток. Есть понятие остаток. Есть понятие место расположения. Вот, блядь, зафиксируй. В проекте где-нибудь, что их важно не путать. Никогда критически. Остаток, сколько товара. В любых движениях с остатком, во всех документах, доступен остаток. А, расположение – это другая хуйня, это то, что там сортировка, перемещением и так далее.

Вопрос о состоянии:

> Я ничего не понял, что ты сделал. В итоге отчет сейчас работает у нас правильно, кристально. По остаткам или чего?

Основная постановка (целиком — в [WMS-530](WMS-530.md), раздел 1.4); часть про отчёт:

> … поэтому остаток, он общий в отчетах, он общий для ФБС, он общий для трансляции в кабинет. Он общий для отгрузки, он общий всегда и везде. Мне насрать на каком он складе, понимаешь? Остаток просто общий. И так должно быть. Соответственно, в отчете мы должны четко видеть все товародвижения. И причем, смотри, как должен работать отчет. Давай сразу. Первое. Все товародвижения. Все. Приемки, отгрузки ФБО, отгрузки ФБС. инвентаризации, блядь, чё угодно, те самые возвраты у нас еще есть, да, любое товародвижение по документу фиксируется обязательно строкой в в этом отчете, вот, то есть полное товародвижение там должно быть, соответственно, дальше, там же нужно сделать выгрузку этой структуры в Excel. Excel аккуратный, понятный, без всякого лишнего говна, описательного и прочего. Просто даты, движения, общая сумма, да, и все такое. Вот. Обязательно этот отчет должен отображать реальность. То есть, как только я иду в этот отчет и вижу, что у меня осталось 100 штук, это значит, что эти же 100 штук у меня по факту а, лежат, ну, по факту я их вижу в каталоге. По факту я их вижу везде. Эти цифры не должны расходиться. Вот тебе нужно проверить вообще всю систему остатков, сейчас отчетов, вот этого всего. чтобы оно было нормально и синхронно. У меня сейчас клиент, пиздец, крупный подключается, и они хотят еще по API интеграцию этих отчетов. Поэтому, блядь, никаких там не должно быть нахуй заминок, расхождений, чего-то еще.

Границы от ведущего: все движения, меняющие остаток, строками с документом (включая инвентаризацию,
сторно FBS с номером заказа, передачи между селлерами, загрузку ТЗ, корректировки; у кого документа нет —
определить подпись); движения расположения в отчёте не участвуют; остаток отчёта совпадает с каталогом;
решить через навык решения фильтр по складу, «Остаток сейчас» или «на конец периода», товары с
остатком без движений, структуру Excel и лимит 200 строк раскрытия; уравнение «было + приход − расход =
стало» по товару, селлеру и итогу для любого периода — в проверки.

## 2. Существующий процесс и цель изменения

### 2.1. Экран (проверено в браузере на локальном стенде ветки, 25.09.2026, 1440 × 900)

`FfReportsPage`. Заголовок «Остатки и движения», подпись «Текущий остаток и складские движения за
выбранный период.». Фильтры: поиск «Название, артикул продавца, SKU, ШК», период «с — по», быстрые
кнопки «Сегодня / 7 дней / 30 дней / Этот месяц / Прошлый месяц», «Склад» (варианты на стенде: «Все
склады», «Основной», «основной»; склад «FBS WB 1887957» не предлагается), «Селлер». Плитки: «Было на
начало 0», «Приход за период 30», «Расход за период 3», «Остаток сейчас 27»; строка «Данные на
25.09.2026, 11:36:09 МСК». «Группировка: По товарам / По операциям», кнопка «Скачать CSV». Таблица
селлеров «Селлер / Товаров / Приход / Расход / Остаток сейчас» (ИП Чжоу 1 / 30 / 3 / 27) раскрывается в
товары «Товар / ШК / Приход / Расход / Остаток сейчас», товар — в движения «Когда / Движение / Документ /
Штук» («FBS −3», «Приёмка 30», документ «—»). В группировке «По операциям» селлер раскрывается в виды
(«FBS 0/3», «Приёмка 30/0»). Внизу «Назад / Вперёд» по 50 селлеров.

Образец отчётов по правилам проекта — «Расчёты» (`/app/ff/billing`, открыт на том же стенде): тот же
каркас — период с быстрыми кнопками, фильтр селлера, плитки, таблица селлеров с раскрытием; догрузка
документов селлера — кнопкой «Загрузить ещё» (`FfBillingSellerDetails.tsx:614–620`). Данных там на стенде
нет, раскрытие с документами посмотрено только по коду. Демонстрационный образец на лендинге не
открывался.

### 2.2. Расчёт (проверено чтением кода, `backend/app/services/reporting_service.py` после `caa20162`)

- Приход и расход — только движения, меняющие остаток; виды расположения `stock_transfer_in/out`,
  `warehouse_map_move`, `container_reattach`, `transfer` исключены при любом фильтре; склады с
  `is_operational=false` учитываются (коммит `caa20162`).
- «Было на начало» = остаток сейчас − сумма всех движений с начала периода. «Остаток сейчас» — текущий,
  а не на конец выбранного периода: для прошлого месяца «было + приход − расход» не равно «остатку сейчас».
- Строки товаров строятся только из движений периода: товар с остатком без движений в периоде в отчёт не
  попадает, и остаток отчёта меньше суммы каталога.
- Товарные строки группируются ещё и по имени селлера движения; «было на начало» для селлера берёт
  остаток по текущему селлеру товара, а движения — по селлеру движения.
- Раскрытие селлера загружает товары без номера страницы (`FfReportsPage.tsx:loadSellerDetail`), сервер
  отдаёт первые 50 (`PAGE_SIZE = 50`), перехода к следующим нет: у селлера с 120 товарами видно 50 при
  «Товаров 120».
- Раскрытие товара — не более 200 движений (`MOVEMENT_PAGE_LIMIT`) с текстом «Показаны первые 200
  движений из большего числа. Сузьте период или фильтр, чтобы увидеть остальные.»
- Документ у строки находится только для приёмки и возврата (`inbound_intake_line_id`), отгрузки на МП
  (`marketplace_unload_request_id`) и списания FBS через журнал `FbsShipmentReversalLedger`
  (`shipment_movement_id` и позиции Ozon). Не читаются: `inventory_count_line_id` (инвентаризация),
  `outbound_shipment_line_id` (старая отгрузка), `reversal_movement_id` (сторно FBS до 05.09.2026),
  `FbsOrderPick.inventory_movement_id` (старые движения сборки FBS), пара передачи между селлерами.
- Виды в группировке «По операциям»: Приёмка, Возврат, Загрузка ТЗ, Отгрузка на МП, FBS, Отгрузка,
  Корректировка по акту расхождений; всё остальное — «Прочее», в том числе инвентаризация, передачи между
  селлерами и `correction_phantom_return`.
- Проверка неполных перемещений (`incomplete_transfer_markers`) работает только при выбранном складе.
- Выгрузка — только CSV по товарам или по операциям, без движений и документов. XLSX для отчётов нет;
  `openpyxl` в бэкенде уже используется (`inbound_marking_service.export_problems`,
  `product_tz_import_service.build_product_tz_template_xlsx`).
- Период не длиннее 366 дней (сервер и экран).
- На SQLite-стенде время движения приходит без часового пояса (`"2026-09-25T05:42:02.219270"`) и
  показывается со сдвигом; на PostgreSQL поле с поясом. Это особенность стенда; время проверять на PostgreSQL.

### 2.3. Какие движения есть в коде и на проде

По коду ветки остаток меняют: `inbound_intake` (приёмка и возврат, в том числе отмена прихода при
«Редактировать» из сортировки — `reopen_receiving`), `discrepancy_act`, `marketplace_unload` (сбор в
короб −, снятие из короба +), `fbs_shipment` (списание; до 05.09.2026 ещё и сторно «+», код сторно удалён
коммитом `8220f195`), `fbs_order_pick_undo`, `inventory_count`, `outbound_shipment`,
`ownership_transfer_out/in/receipt`. На проде по брифу ведущего есть ещё исторические `product_tz_import`
(42 строки, +10 410, стартовые остатки), `correction_phantom_return` (59, −150), `fbs_order_pick` (27, +27).

Покрытие документом на проде (бриф ведущего, мной не перепроверено): `fbs_shipment` 7580 / без документа
840 (почти все «+», сторно); `inventory_count` 521 / 0 без связи, но отчёт связь не читает;
`product_tz_import`, `correction_phantom_return`, `fbs_order_pick`, `ownership_transfer_in/out` — без
документа. По брифу строки `fbs_shipment` без документа появляются и сейчас (неделя с 21.09: «Империя» 70,
FFAdam 43). В коде ветки писателя положительных `fbs_shipment` нет (сторно удалено 05.09.2026). Проверенный
факт кода: если место списания FBS указано без тары, количество берётся по порядку — сначала россыпь,
затем тара этого места (`inventory_service.py:800–900`; для FBS система не ищет одну строку, покрывающую
всё количество), поэтому одно списание может лечь несколькими строками; такие строки получают общий номер
группы, а журнал хранит только первую (`fbs_shipment_service.py:1393`). Какие именно строки без документа
появились после 05.09, мной не установлено — это нужно посмотреть запросом к проду (раздел «Заключение»).

### 2.4. Цель

Отчёт показывает каждое движение остатка отдельной строкой с датой, видом и документом, сходится
арифметически на любом уровне и за любой период, совпадает с каталогом для текущего момента и
выгружается в аккуратный Excel той же структуры.

## 3. Требования

### R1. В отчёте только движения остатка

**Условие:** в периоде есть движения расположения: перемещение между складами или ячейками, размещение
из сортировки, перекладка тары.
**Результат:** они не входят ни в приход, ни в расход и не показываются строками при раскрытии — ни на
экране, ни в Excel, ни в плитках, ни при каком фильтре.
**Основание:** 1.2 «перемещение между ячейками не должны … создавать никакие товародвижения»; AGENTS.md §3.

### R2. Каждое движение остатка — отдельная строка

**Условие:** в периоде есть движение, меняющее остаток товара.
**Результат:** при раскрытии товара (и вида движения) оно показано отдельной строкой: дата и время по
Москве, подпись вида, документ, количество со знаком (приход «+», расход «−»). Несколько движений одного
документа — несколько строк. Подписи, документ и группа «По операциям» — по таблице:

| Вид в данных | Подпись «Движение» | «Документ» | Группа «По операциям» |
|---|---|---|---|
| `inbound_intake` приёмки (в т.ч. отмена прихода при «Редактировать») | Приёмка | «Приёмка №…», открывает документ | Приёмка |
| `inbound_intake` возврата | Возврат | «Возврат №…», открывает документ | Возврат |
| `discrepancy_act` | Корректировка по акту расхождений | приёмка, к строке которой относится акт | Корректировка |
| `marketplace_unload` | Отгрузка на МП | «Отгрузка №…», открывает документ | Отгрузка на МП |
| `fbs_shipment` «−», `fbs_order_pick_undo` | FBS | «Заказ WB №…» / «Заказ Ozon №…», открывает поставку, если заказ в ней | FBS |
| `fbs_shipment` «+» (сторно до 05.09.2026) | FBS, сторно | тот же заказ | FBS |
| `fbs_order_pick` (старые) | FBS | заказ по записи подбора | FBS |
| `inventory_count` | Инвентаризация | «ИНВ-…» — тот же номер, что в списке инвентаризаций | Инвентаризация |
| `outbound_shipment` | Отгрузка | документ старой отгрузки, как он подписан в своём списке | Отгрузка |
| `ownership_transfer_out` | Передано селлеру «…» (получатель) | без документа | Передача между селлерами |
| `ownership_transfer_in` | Получено от селлера «…» (отправитель) | без документа | Передача между селлерами |
| `ownership_transfer_receipt` | Приёмка при передаче между селлерами | служебная приёмка №… | Передача между селлерами |
| `product_tz_import` | Загрузка ТЗ | без документа | Загрузка ТЗ |
| `correction_phantom_return` | Корректировка | без документа | Корректировка |
| любой другой вид, меняющий остаток | Прочее: <код вида> | без документа | Прочее |

**Основание:** 1.4 «Все товародвижения. Все. Приемки, отгрузки ФБО, отгрузки ФБС. инвентаризации…
возвраты… любое товародвижение по документу фиксируется обязательно строкой»; граница ведущего; D6.

### R3. Документ строки — только по связям в данных

**Результат:** документ определяется по сохранённым связям: строка приёмки; отгрузка на МП; журнал
списаний FBS (исходное списание, сторно `reversal_movement_id`, позиции Ozon); для списания FBS,
разделённого на несколько строк из разных мест или тары, — общий номер группы с уже связанной строкой;
запись подбора FBS; строка инвентаризации; строка старой отгрузки; вторая строка той же передачи между
селлерами (для имени селлера). Связь по времени, товару, количеству или месту не угадывается. Если связи
нет, в колонке «Документ» написано «без документа», строка всё равно показана и учтена в сумме.
**Основание:** 1.4 «по документу»; существующий принцип отчёта «never infer links by time, product,
quantity…» (`reporting_service.list_product_movements`); граница ведущего «у кого нет документа, какая
подпись».

### R4. У заказа FBS видна площадка

**Результат:** документ списания и сторно FBS подписан «Заказ WB №<номер заказа WB>» или «Заказ Ozon
№<номер отправления Ozon>».
**Основание:** AGENTS.md «где принадлежность влияет на понимание данных или действия, явно обозначай площадку».

### R5. Нет фильтра по складу

**Результат:** в отчёте ФФ и кабинета селлера нет выбора склада; числа всегда по всей организации (с
учётом фильтров селлера, поиска и периода). Старый клиент, передавший параметр склада, получает те же
числа, что и без него.
**Основание:** 1.4 «Мне насрать на каком он складе… Остаток просто общий»; WMS-530 R1; D1.

### R6. Последняя колонка — остаток на конец периода

**Результат:** в плитке и в колонке таблиц (селлер, товар) последнее число — остаток на конец выбранного
периода. Если конец периода ещё не наступил, это остаток на момент построения отчёта, подпись «Остаток
сейчас». Если конец периода в прошлом — фактический остаток на конец последнего дня периода, подпись
«Остаток на ДД.ММ.ГГГГ». «Было на начало» — фактический остаток на начало первого дня периода.
**Основание:** 1.4 «отчет должен отображать реальность»; уравнение из границы ведущего; D2.

### R7. Уравнение сходится на каждом уровне и за любой период

**Условие:** любой период до 366 дней, любые фильтры селлера и поиска.
**Результат:** для каждой строки товара «было на начало + приход − расход = остаток на конец»; строка
селлера — сумма его товаров по каждому из четырёх чисел; плитки — сумма по селлерам. Если по товару в
периоде есть движение расположения без пары (оно изменило сумму остатка), строка товара помечается, а над
таблицей показывается уже существующее предупреждение «В истории есть неполное перемещение. Значения
показаны как записаны; отчёт ничего не достраивал.» — и без выбранного склада тоже.
**Основание:** граница ведущего; 1.4 «никаких … расхождений»; D2.

### R8. Остаток отчёта равен каталогу

**Условие:** период включает текущий момент.
**Результат:** «Остаток сейчас» товара равен его Остатку в каталоге (WMS-530 R1, WMS-532), селлера —
сумме Остатков его товаров в каталоге, плитки — сумме по всем товарам под теми же фильтрами.
**Основание:** 1.4 «вижу, что у меня осталось 100 штук… по факту я их вижу в каталоге… Эти цифры не должны
расходиться».

### R9. Товар с остатком без движений в периоде виден

**Результат:** в отчёте есть строки всех товаров, у которых в периоде были движения или ненулевой остаток
на начало или на конец; у товара без движений приход и расход 0, было = остаток на конец. Товар с нулями на
начало и конец и без движений не показывается. Селлер показывается, если у него есть хоть одна такая
строка; «Товаров» — число его строк.
**Основание:** R7, R8; 1.4 «отчет должен отображать реальность»; D3.

### R10. Товар — одна строка у своего селлера

**Результат:** строка товара и все его движения относятся к текущему селлеру товара; товар не делится на
несколько строк по селлеру движения. «Без селлера» — только для товаров без селлера.
**Основание:** R7 (сходимость по селлеру); D4.

### R11. Все товары и все движения доступны на экране

**Условие:** у селлера больше 50 товаров в отчёте или у товара (вида движения) больше 200 движений за период.
**Результат:** под списком появляется «Загрузить ещё», как в «Расчётах»; каждое нажатие добавляет
следующую часть в конец (товары по 50, движения по 200), пока не показано всё; текст «Сузьте период или
фильтр» больше не нужен. Число строк товаров равно «Товаров», сумма показанных движений равна приходу и
расходу строки.
**Основание:** 1.4 «полное товародвижение там должно быть»; образец «Расчёты»; D5.

### R12. Выгрузка в Excel

**Условие:** пользователь ФФ или селлер нажимает кнопку выгрузки отчёта.
**Результат:**
1. Кнопка «Скачать Excel» стоит на месте «Скачать CSV»; CSV в интерфейсе больше не предлагается.
2. Скачивается файл `.xlsx`, который открывается в Excel без предупреждения о формате; в имени — период,
   например «Остатки и движения 01.09.2026–30.09.2026.xlsx».
3. Один лист, первая строка — заголовки и закреплена, дальше только данные: ни шапки с описанием, ни
   пояснений, ни фильтров текстом.
4. Структура — как выбранная группировка на экране, с уровнями группировки строк Excel (сворачиваются):
   - «По товарам»: строка селлера → строки его товаров → строки движений товара;
   - «По операциям»: строка селлера → строки видов движения → строки движений вида (с товаром).
5. Колонки: Селлер · Товар · Артикул продавца · ШК · Дата · Движение · Документ · Было на начало ·
   Приход · Расход · Остаток на конец. В строке движения заполнены товар (в «По операциям»), дата,
   движение, документ и приход или расход; в строках товара и селлера — их названия и четыре итоговых
   числа; в строке вида — вид, приход и расход.
6. Последняя строка — «Итого» с четырьмя числами, равными плиткам.
7. Числа — числовые ячейки (сумма и фильтр Excel работают), даты — ячейки даты и времени по Москве.
8. В файле все строки выбранного отчёта: без ограничений 50 и 200.
9. В кабинете селлера файл без уровня и колонки «Селлер».

**Основание:** 1.4 «выгрузку этой структуры в Excel. Excel аккуратный, понятный, без всякого лишнего
говна, описательного и прочего. Просто даты, движения, общая сумма»; D6.

### R13. Файл равен экрану

**Результат:** для тех же фильтров и периода числа файла равны экрану: итог — плиткам, строки селлеров и
товаров — строкам таблиц, движения — раскрытиям.
**Основание:** 1.4 «Эти цифры не должны расходиться».

### R14. Сбой и повтор выгрузки

**Результат:** пока файл формируется, кнопка показывает «Формирование Excel…», повторное нажатие не
запускает второе формирование. При ошибке рядом с кнопкой видна причина, кнопка снова доступна, повтор
работает. Когда строк в отчёте нет, кнопка недоступна с причиной «За выбранный период нечего выгружать».
**Основание:** существующее поведение CSV (`reportCsvDisabledReason`) и сбой B05 (действие не должно
молча пропадать).

### R15. Большой период

**Условие:** период 366 дней у организации с объёмом движений не меньше реального годового у самого
крупного арендатора.
**Результат:** экран с раскрытиями и файл формируются полностью; число строк движений в файле равно числу
движений остатка за период; ошибки нет. Период длиннее 366 дней по-прежнему отклоняется с текстом «Период
не может быть длиннее 366 дней».
**Основание:** 1.4 «никаких там не должно быть нахуй заминок»; существующее ограничение периода.

## 4. Решения аналитика и вопросы

### D1. Фильтр склада убран

Владелец прямо сказал, что склад не важен, а остаток общий. После правила «расположение не является
движением» отчёт по одному складу не может сойтись: товар, пришедший перемещением, не является приходом
этого склада, а остаток склада его уже содержит. Фильтр, дающий несходящиеся числа, противоречит «цифры
не должны расходиться». Следует R5.

### D2. Остаток на конец периода вместо «остатка сейчас»

Для текущего периода число то же, что сейчас («Остаток сейчас» = каталог). Для прошлого периода «остаток
сейчас» рядом с приходом и расходом прошлого месяца не сходится с «было на начало». Поэтому последняя
колонка — остаток на конец периода с подписью, которая прямо говорит, на какой момент число. Было и стало
берутся фактическими (откат всех движений от текущего остатка), а не подгоняются: если уравнение не сходится
из-за неполного перемещения в данных, это показывается существующим предупреждением. Следуют R6, R7.

### D3. Товары без движений показываются

Иначе итог отчёта меньше суммы каталога на остаток «спящих» товаров, и владелец не увидит «100 штук» там,
где их 100. Товары с нулями и без движений не показываются, чтобы не раздувать список. Следует R9.

### D4. Селлер товара — текущий

Товар меняет селлера только при объединении карточек, а объединение разрешено лишь внутри одного селлера
(`product_merge_service`: `merge_different_sellers`); отдельного пути смены селлера в API не найдено.
Передача между селлерами идёт через разные товары. Значит, группировка по текущему селлеру не переносит
историю и даёт сходимость по селлеру. Следует R10.

### D5. Догрузка вместо обрыва

Образец отчётов «Расчёты» догружает документы кнопкой «Загрузить ещё»; тот же приём не добавляет новых
окон и оставляет полный список доступным. Порции 50 и 200 — текущие размеры страниц. Следует R11.

### D6. Структура Excel

Владелец просил выгрузить «эту структуру» и «без лишнего… описательного». Поэтому — один лист в той же
иерархии, что экран, с уровнями группировки Excel, заголовком и итогом, без текстовых шапок; период — в
имени файла. CSV убирается из интерфейса, чтобы не было двух кнопок выгрузки с разным содержимым. Подписи
и документы — таблица R2: так каждое движение, у которого нет документа, всё равно видно и понятно, что
это. Следуют R2, R12.

### Вопросы владельцу

Открытых вопросов, меняющих бизнес-результат, нет.
