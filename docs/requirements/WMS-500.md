# WMS-500 · Вернуть публичную регистрацию фулфилмента

## Исходный запрос

21.09.2026 владелец: «а где у нас ссылка пункт на регистрации для ФФ? куда он делась блядь??? срочно надо регу ФФ вернуть прям сейчас».

Уточнённая граница владельца: вернуть публичный пункт регистрации фулфилмента и саму работающую регистрацию; регистрацию селлера не добавлять.

## Подтверждённый текущий процесс и причина исчезновения

До 06.09.2026 на публичном экране входа фулфилмента `/` была ссылка «Регистрация организации (первый админ)». Она без отдельного маршрута переключала `PublicAuthScreen` на форму «Регистрация организации» с полями «Организация», «Email администратора» и «Пароль».

Регистрацию убрали намеренно в коммите `ed723aca` по WMS-383: публичный экран перестал показывать ссылку и форму, а `POST /auth/register` закрыли настройкой `WMS_ALLOW_PUBLIC_REGISTRATION`, которая по умолчанию равна `false`. При выключенной настройке API отвечает `403 registration_closed`. Причиной WMS-383 было то, что любой человек из интернета мог создать организацию.

Техническая основа регистрации не удалена. `useAuth.onRegister` по-прежнему формирует внутренний код организации, вызывает `POST /auth/register`, сохраняет полученный токен и начинает FF-сессию. Серверный `register_fulfillment` создаёт организацию, первого пользователя с ролью `fulfillment_admin`, отключённую тарифную матрицу и основной склад в одной транзакции. Сейчас `App.tsx` не передаёт `onRegister` в `PublicAuthScreen`, а тип режима экрана содержит только `login | forgot`.

Таким образом, это не случайно пропавшая ссылка, а явный разворот прежнего решения WMS-383 по новому прямому указанию владельца.

## Требования

**R1.** На публичном экране входа фулфилмента `/` без авторизации снова доступен пункт «Регистрация организации (первый админ)».

**R2.** Пункт открывает на том же публичном FF-экране форму «Регистрация организации» с полями «Организация», «Email администратора» и «Пароль», кнопкой создания аккаунта и возвратом ко входу. Отдельный маршрут регистрации не требуется.

**R3.** Валидная отправка формы действительно создаёт организацию фулфилмента через существующий `POST /auth/register`, первого FF-администратора, основной склад и отключённую тарифную матрицу, после чего пользователь входит в созданный кабинет. Частично созданная организация при ошибке недопустима.

**R4.** Публичная регистрация должна быть разрешена в том окружении, где ссылка показана: штатный запрос из формы не должен получать `registration_closed`. Способ согласования интерфейса и существующей настройки выбирается при реализации; показывать работающую кнопку перед заведомо закрытым API нельзя.

**R5.** В публичном портале селлера `/seller/` пункт и форма регистрации организации не появляются. Сценарий регистрации селлера в эту задачу не входит.

**R6.** Существующие вход, восстановление/установка пароля и переход из FF-входа в портал селлера продолжают работать. Ошибки обязательных полей и занятой почты или кода организации остаются понятными человеку и не создают дубликаты.

## Границы задачи

- Возвращается прежний публичный FF-сценарий по прямому решению владельца; приглашение, одобрение владельцем, CAPTCHA и другие новые ограничения не добавляются без отдельного требования.
- Не меняются создание сотрудников, приглашения селлеров, подписка и авторизация существующих пользователей.
- Кабинеты секретов и значения секретов для постановки не открывались и не проверялись. Фактическая настройка работающего окружения должна подтверждаться поведением регистрации, а не предположением о переменной.
