# WMS-713 · ТСД: сбой создания FBS-поставки у АртМакс

Замена аналитика: исходная сессия оборвалась при перезагрузке компьютера 10.10.2026 в 00:30 МСК.

## 3. Что установлено по данным

### 3.1 Сервер в окне не вернул ни одного отказа на создание

Журнал API прода показывает окно 15:00–17:10 UTC. Контейнер API стартовал 08.10 в 06:50 UTC, раньше окна, и в окне не перезапускался: строк запуска процесса за 14:00–23:59 UTC нет. Три ключевых файла проверки и создания поставок внутри работающего контейнера побайтно совпадают с версией 9971abed3 из репозитория. Значит, код, который я читал ниже, именно тот, что работал в окне.

Клиент ArtMaks в журнале виден под адресом 5.8.87.151. Он создал обе поставки ArtMaks и запрашивает очередь ТСД с параметрами, которые совпадают с вызовом выборки заказов в сборке 19. За окно он сделал 259 запросов: 256 с ответом 200 и 3 с ответом 201. Ответов 4xx и 5xx нет. Трассировок по поставкам в журнале нет; единственные трассировки в окне относятся к почте для приглашений другого тенанта. Уведомлений ArtMaks за 08.10 в базе нет.

Адрес 213.208.175.122 к делу не относится: он создавал поставки тенанта FFAdam (поставки 5d940ef8 в 15:32 и 6985bca9 в 15:55 UTC).

### 3.2 Что делал клиент ArtMaks и чем это закончилось

Всё ниже взято из журнала API и таблиц поставок и операций WB.

| Время UTC | Что отправил клиент | Результат |
|---|---|---|
| 15:13:54–15:14:26 | 5 запросов проверки группы (preflight) | 200; создания нет |
| 15:17:01–15:17:34 | 10 запросов проверки группы (preflight) | 200 |
| 15:17:41 и 15:17:43 | 2 создания поставки (from-orders) | 201; поставки 20f1789c и 7a7d7e4f в базе, операции WB подтверждены, код ошибки пуст |
| 15:17:53 | задание на сборку по двум поставкам | 201 |
| 15:17:55 и 15:17:56 | запуск работы по каждой поставке | 200 |
| 15:29:38–15:29:39 | 3 запроса проверки группы (preflight) | 200; создания после них нет |

Проверка группы (preflight) — это запрос, который спрашивает сервер, можно ли собрать выбранные заказы в одну поставку, ничего не создавая. Клиент вызывает её для каждой группы каждый раз, когда оператор открывает диалог «Создать поставки» или переключает склад и ПВЗ. Группа заказов — это заказы одного маркетплейса, одного селлера, одного склада WB, одного склада WMS, одного типа покупателя и одного типа груза. Создание клиент шлёт только по группам, которые получили положительный результат проверки: группа получает статус «можно создать» лишь при совместимом ответе, а кнопка создания активна только когда такая группа есть.

Из этого следует простой вывод. В пакете 15:17 было 10 групп, создано 2, значит 8 групп получили отрицательный результат. В пакете 15:29 было 3 группы, и ни одна не стала готовой: запроса создания не было, а кнопка по коду без готовой группы неактивна. Пакет 15:13 из 5 групп тоже не привёл к созданию. Это вывод из числа запросов и из кода клиента. Сам текст ответа проверки в журнал не пишется, поэтому конкретные причины отсюда не видны.

### 3.3 Совпадает ли контракт сборки 19 с сервером

Сборка 19 — это версия 0.2.0 с кодом 19 из мобильного репозитория, ветка origin/feat/wms584-585-tsd-release, коммит 41f0f33. Текущая рабочая копия ТСД имеет версию 0.2.1 с кодом 20. Сравнение показало следующее.

- Клиентский код создания (вызовы проверки и создания, модели запроса и ответа, ключ группы, порядок создания групп) в сборке 19 и в текущей рабочей копии совпадает. Различия касаются только печати этикеток.
- Бот прислал сборку 19 оператору 08.10 в 16:19 МСК (13:19 UTC) и указал совместимый сервер ac1aa840c. Этот коммит — предок прода 9971abed3. Маршруты проверки и создания и их схемы между ними не менялись. Валидатор проверки совпадает побайтно.
- Единственное изменение на пути создания на проде: после подтверждения поставки сервер дополнительно запрашивает стикеры WB (изменение WMS-666). Это не меняет проверку совместимости, а оба создания в окне прошли успешно.
- В ответе создания на проде есть поля, которых нет в клиентской модели (например, сведения о последней ошибке доставки). Клиент после 201 продолжил работу: запросил рабочее пространство и запустил сборку обеих поставок. Значит, разбор ответа создания не сломан.

Несовпадения контракта, которое объяснило бы отказ, я не нашёл.

### 3.4 По каким правилам группа получает отказ

Серверная проверка состава (файл backend/app/services/fbs_supply_validator_service.py) проверяет каждый заказ группы. Группа целиком несовместима, если хотя бы у одного заказа есть проблема. Проблемы, которые могут возникнуть у заказа, берутся из правил подбора (функция compute_selection_blockers в backend/app/services/fbs_worklist_service.py):

- срок сборки истёк, только для WB: код deadline_passed, текст «Срок сборки истёк.»;
- заказ не в статусе «новый» (код order_bad_status), в том числе заказ, уже ушедший в кабинете WB: текст «Заказ уже ушёл в кабинете WB.»;
- заказ отменён или брак: код order_cancelled;
- заказ уже в другой поставке: код already_in_supply;
- товар не сопоставлен с карточкой: код product_not_mapped;
- склад WMS не привязан: код warehouse_unmapped.

Оператор видит эти тексты строкой под группой в диалоге «Создать поставки». Клиент склеивает тексты проблем группы и не выводит номер заказа. Для кодов deadline_passed и order_bad_status в русской таблице клиента перевода нет, поэтому показывается серверный текст. Таким образом, на экране нет ни номера заказа, ни кода, по которому его можно найти. Это проверено по коду клиента (функция prepareSupplyGroups и показ group.error на экране создания).

### 3.5 Очередь ТСД показывает заказы, которые веб скрывает

Очередь ТСД (статус tsd_working) включает заказы WB независимо от срока сборки. В коде это записано как намеренное отличие от веба: веб на вкладке «Новые» для WB срок отсекает (функция _deadline_in_work_clause), ТСД — нет. Значит, оператор ТСД может выбрать заказ, у которого срок уже истёк. Тогда любая группа с таким заказом не пройдёт проверку, и повторная попытка даст тот же результат, потому что заказ остаётся в выборе.

### 3.6 Данные согласуются с этим механизмом, но не доказывают его

- Поставки, созданные в 15:17, содержат только заказы со сроком 12–13 октября. В поставке 20f1789c один заказ со сроком 12.10 07:12 UTC. В поставке 7a7d7e4f 52 заказа со сроками с 12.10 12:06 по 13.10 17:57 UTC. Ни один из них в 15:17 не был просрочен.
- В базе у ArtMaks есть заказы WB без поставки, у которых срок истёк до 15:13 UTC, и которые меняли статус уже внутри окна. Всего таких одиннадцать с последним изменением между 15:36:51 и 17:07:42 UTC. Пример: заказ 5911384333, срок 04.10 18:15 UTC, отменён на стороне WB, последнее изменение 15:36:51 UTC.
- На момент проверки в статусе «новый» у ArtMaks девять заказов. Все они созданы после 18:29 UTC 08.10 и имеют срок 13.10. Истёкших новых заказов в очереди сейчас нет, поэтому сбой на проде без новых данных не воспроизвести.

### 3.7 Что не установлено

- Тексты и коды проблем, которые вернула проверка в 15:13–15:29 UTC. Тело ответа не пишется в журнал, и бот этого не сохраняет. Поэтому нельзя назвать код для каждой из восьми групп, которые не прошли в пакете 15:17.
- Какие заказы попали в выбранные группы. Состав запросов в журнале не виден.
- Какая сборка стоит на устройстве оператора. В журнале нет идентификатора приложения. Бот отправил сборку 19 в 13:19 UTC, но её установка не подтверждена.
- Содержимое видео №627.

### 3.8 Наиболее вероятная причина, которую нужно проверить

Ниже не установленный факт, а рабочая версия, которую данные согласуют, но не доказывают. Группы не проходят проверку из-за заказов, которые попали в выбор из очереди ТСД и не могут войти в поставку. В первую очередь это WB-заказы с истёкшим сроком сборки, которые ТСД показывает, а веб нет, и заказы, отменённые или уже ушедшие в кабинете WB. Текст ошибки оператор видит без номера заказа, поэтому повтор не помогает: тот же заказ остаётся в выборе.

Минимальная проверка, которая подтвердит или опровергнет эту версию, выполняется на тестовом стенде, а не на проде:

1. Завести тестовый WB-заказ в статусе «новый» с истёкшим сроком сборки, выбрать его вместе с обычным заказом и открыть диалог создания. Ожидаемо: группа несовместима, строка под группой содержит «Срок сборки истёк.».
2. Убрать просроченный заказ из выбора и открыть диалог снова. Ожидаемо: группа из обычных заказов создаётся.
3. При следующем сбое попросить оператора прислать точный текст строки под группой. Совпадение с текстом шага 1 подтверждает версию. Текст «Заказ уже ушёл в кабинете WB.» или «Заказ отменён или брак.» означает устаревший список заказов. Пустой текст при неактивной кнопке означает, что причину надо искать в клиенте, по журналу устройства.

## 4. Требования

Аналитик выбирает форму требований внутри запроса владельца. Решения аналитика отмечены в колонке «Основание». Правило срока WB (WMS-420) аналитик не меняет: это ограничение площадки, WB не принимает сборку после срока.

| ID | Требование | Основание |
|---|---|---|
| R1 | Если все заказы группы проходят существующие правила совместимости, ТСД создаёт из неё поставку. Поставка появляется в списке поставок ТСД и открывается без ошибки. | Исходный запрос: «Исправить создание FBS-поставки в приложении». Код создания есть на клиенте и на сервере, поэтому это неисправность существующей функции, а не отсутствующая функция. |
| R2 | Если группа не создана из-за отказа проверки или сервера, экран показывает, какая группа не создана, причину текстом и номер заказа, который её блокирует. Оператор не должен угадывать, какой заказ убрать. | Задача ведущего: «понятная ошибка на экране». Основание в коде: сервер сверяет ключ повтора и хеш состава запроса и возвращает уже созданную поставку (функции создания поставок в backend/app/services/fbs_supply_service.py). |
| R4 | Исправление WMS-713 не добавляет новых блокировок сверх существующих правил и не меняет правило срока WB и остальные проверки совместимости. Блокер «Срок сборки истёк» для WB снимает отдельная задача WMS-692, которая является зависимостью выпуска WMS-713. | Правила проекта (AGENTS.md, раздел 3): без пользовательских блокировок, которых не просил владелец. Решение модератора 09.10.2026, см. раздел «Уточнения 09.10.2026». |

## 5. Вопрос владельцу

Вопрос меняет, какие заказы попадут в поставку, поэтому решение за владельцем, аналитик его не принимает.

Q1. Просроченные WB-заказы сейчас видны в очереди ТСД, но в вебе скрыты из вкладки «Новые», а правило WMS-420 не даёт включить их в поставку. Что оператор ТСД должен видеть с такими заказами: показывать их как непригодные и не давать выбирать, или скрывать, как в вебе?

## Уточнения 09.10.2026, решения модератора ночной сборки

Решение по Q1. Блокер «Срок сборки истёк» для WB снимает задача WMS-692 (решение модератора по AGENTS.md, раздел 3): предпроверка поставки больше не возвращает код deadline_passed. Поэтому на ТСД просроченные WB-заказы остаются в очереди и выбираются как сейчас, отдельной скрывающей логики в WMS-713 не делаем. Серверная часть причины закрывается WMS-692, которую ведём как зависимость выпуска WMS-713.

Объём WMS-713 на ТСД: R2 (при отказе группы показываются группа, причина текстом и номер заказа) и R3 (повтор проверки, повторное нажатие «Создать» и перезапуск приложения не создают вторую поставку той же группы; используется существующий механизм ключа повтора, новых сущностей не вводим).

R4 переформулирован, см. таблицу требований: WMS-713 не добавляет блокировок и не меняет правило срока WB, его снимает WMS-692.

Переписанные проверки. По указанию модератора C1 и C5 переписаны под это решение: просроченный WB-заказ проверяется в WMS-692, а в WMS-713 остаются текст причины с номером заказа и отсутствие дублей. Стендовый сценарий пакетов 15:13–15:29 из прежней C5 заменён автоматической проверкой выбора без блокирующего заказа.

Результаты тестировщика. Тесты лежат в мобильном репозитории WMS-TSD, коммит ac1afe9 на ветке feat/wms711-713-tsd-fbs, файл android/app/src/test/java/ru/wms/tsd/features/fbs/FbsSupplyGroupContractTest.kt (путь от корня мобильного репозитория). Проверено на изолированной копии коммита с добавленным тестовым файлом. C1, C3 и C6 падают на текущем коде: в тексте причины нет номера заказа, а одна и та же причина повторяется. C2 и C5 проходят. Охрана C2 проверена временной порчей: тест повтора падает с причиной «повтор должен идти с тем же ключом, expected 1 but was 2». Охрана C4 проверена порчей существующего теста: без вызова открытия тест падает с причиной expected [[supply-1, supply-2]] but was []. Охрана C5 порчей не проверялась.

Ограничения. Вторая половина C2, «тот же ключ с другим составом отклоняется», серверная, мобильный тест её не покрывает. На сервере поведение «тот же ключ с тем же составом возвращает одну поставку» проверяет существующий тест test_from_orders_idempotency_same_key в основном репозитории; отказ при другом составе им не проверяется. C4 закрыт существующим тестом: он проверяет создание с первого нажатия и открытие поставки, но не проверяет появление поставки в списке.

Номер заказа. Ответ проверки содержит order_id, а не номер заказа. Тест берёт номер из загруженного списка заказов по order_id, формат WB плюс номер заказа. R2 говорит «взятые из ответа сервера»; аналитику решить, достаточно ли такого источника.

Для реализации: одна и та же причина от нескольких заказов группы должна выводиться один раз, с номерами всех этих заказов.

## 6. Проверки и приёмка

Класс «навсегда» — поведение, которое должно сохраняться после выпуска. «Разово» — проверка только этого изменения. «Руками» — результат, который автомат не доказывает. Колонка «Тест WMS-TSD» заполняется тестировщиком ссылкой на тест в мобильном репозитории, вердикты заполняются при приёмке.

| Проверка | Связь | Класс проверки | Тест WMS-TSD | Вердикт |
|---|---|---|---|---|
| C1. Текст причины группы содержит номер каждого WB-заказа, которого она касается, и одна и та же причина не повторяется.
