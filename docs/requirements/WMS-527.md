Запись задачи: [канонический бэклог, WMS-527](../KANONICHESKIY_BACKLOG.md#wms-527).

## 1. Исходный запрос

В контексте предыдущего перечня «всё» означает WMS-469, WMS-514 и ещё не влитый
legacy guard WMS-476. WMS-517 — вывод КИЗ из оборота — исключена целиком.

Последующее прямое уточнение владельца: в этот же релиз включается WMS-526 —
Ozon FBS «Создать автоматически». Сохраняются все R1–R12 и границы проверки из
[требований WMS-526](WMS-526.md). Источник интеграции —
`feat/wms526-ozon-auto-boxes`, `6f76d519650b1cdb1ee8bade2e3be586ef376b85`;
отдельный PR для выпуска не создаётся.

## 3. Требования

### R1. Состав кандидата

Кандидат строится от актуального `origin/etalon`. В него входят:

1. WMS-469 — принятое распределение остатков по связкам складов, независимые
   WB/Ozon, число/процент и `min(лимит оператора, свободный остаток)`;
2. WMS-514 — три галки в существующей строке WB FBS, шесть режимов, инертный `000`,
   точный КИЗ и прежний QR→КИЗ;
3. legacy guard WMS-476 — неполный старый `/import` атомарно отвечает
   `422 manual_import_product_required` до любых записей; полностью назначенный
   ручной импорт и `/import/auto` продолжают работать.
4. WMS-526 — автоматическая раскладка каждой неразложенной позиции Ozon в отдельный
   короб, запрос этикеток по заказам существующим retry-qr, повтор после сбоя и
   постоянная красная причина у каждого короба заказа (R1–R12 WMS-526).

### R2. Сохранить уже выпущенное

WMS-519/520/523 не реализуются заново. Сохраняются исправление геометрии
сохранённого PDF/PNG, preview/manual import при нескольких пулах одного GTIN,
отдельные auto/assign-пулы и общие catalog/package counts без дублей.

### R3. WMS-517 полностью отсутствует

PR #247/#248 не сливаются и не используются как база. В diff, staging и production
не попадают WMS-517 API/UI, withdrawal ledger/models/migrations, True API,
CryptoPro/`cadesplugin_api.js`, worker/beat, Redis-limiter, Railway-конфигурация и
production-submit flags. Действия вывода из оборота и внешних withdrawal-вызовов нет.

### R4. CI исправляется по существу

Все пять известных падений закрываются без формального повышения query limit,
удаления проверок или ослабления независимого сохранения WB/Ozon. После последнего
изменения выполняются адресные тесты WMS-469/476/514/519/520/523/526 и один полный PR CI.
Неизменившиеся зелёные проверки и review без нового diff повторно не гоняются.

### R5. Staging

На staging разворачивается exact SHA с миграциями. В браузере проверяются:

- WMS-469 в FF и seller: блоки WB/Ozon, число/процент, сохранение и повторное открытие;
- WMS-514 в WB FBS: ровно три галки, `000`, выбор единицы, отсутствие новых окон,
  сохранность QR→КИЗ;
- WMS-476 на тестовых данных: старый неполный запрос не пишет ничего, полностью
  назначенный импорт проходит.

Если реально доступны настроенные принтер и сканер, дополнительно проверяются тихая
печать QR/нового ЧЗ/точной копии и считывание полного КИЗ. Если недоступны, это
остаётся явно непроверенной физической границей, а не объявляется PASS по тестам.

### R6. Merge и production

После зелёного CI, перекрёстного review и аналитической приёмки PR вливается в
`etalon`. Production разворачивается из exact merge SHA. После deploy проверяются
checkout/version, ancestry от `3c90970b` и merge SHA, миграции, `/api/health`, корень,
seller-портал и безопасный browser smoke WMS-469/WMS-514.

### R7. Интеграция WMS-526

Включается принятая на локальном стенде ветка WMS-526 вместе с требованиями,
записью бэклога и отчётами перекрёстного ревью. Проверяются стыки retry-qr и
шапки коробов с сохранённой печатью WMS-514/WMS-524, ручной путь Ozon и короба WB.
Новых миграций нет. После выкладки отдельно проверяются живой Ozon, успешная
этикетка, печать ленты и исчезновение красной причины после успешного повтора;
прежняя стендовая приёмка и тестовый провайдер не заменяют эту проверку.

## Заключение

Разработчик собрал локально проверенный кандидат от `75c1bff5`: перенёс только
legacy guard WMS-476, сохранив создание отдельных пулов WMS-523. Пять прежних
CI-падений воспроизведены и закрыты в тестовой инфраструктуре: измеритель SQL
считал фоновую публикацию fixture, а HTTP harness вызывал удалённый старый
frontend saveRule. В этой исходной дельте продуктовые stock/print/WB/Ozon потоки
не менялись. Затем по прямому уточнению владельца добавлена ветка WMS-526
с её требованиями и свидетельствами; её влияние описано отдельно в R7/C9/C10.

После последнего изменения кода прошли `ruff check .`, `mypy .` (473 файла),
`pytest -q -n auto tests/test_wms469_stock_dialog_backend.py
tests/test_wms476_auto_marking_import.py tests/test_wms514_scan_auto_print.py
tests/test_wms417_stock_http_contract.py tests/test_fbs_worklist_query_count.py
tests/test_fbs_worklist_search.py tests/test_marking*.py` (218 passed, 7 skipped —
PostgreSQL row/advisory locks и сериализация конфликтов не проверяются SQLite).
Frontend: `npx tsc --noEmit -p tsconfig.app.json`, `npm run build` и семь
адресных unit suites (fbsStockBlocks, fbsStockDialogLoader, fbsStockDialogSession,
FfFbsSupplyWorkspace.wms514, markingImportMerge, markingAvailability,
markingPrintPresets) — 92 passed.

Это технические результаты разработчика, не заключение аналитической приёмки.
Первый PR CI `36057936907` прошёл backlog/frontend, но остановился на mypy:
неограниченное `sqlalchemy>=2.0` установило SQLAlchemy 2.1.0. В отдельном чистом
Python 3.11 окружении с mypy 2.3.1 версия 2.0.54 даёт PASS (473 файла), а замена
только SQLAlchemy на 2.1.0 воспроизводит те же 63 ошибки в 22 файлах. Поэтому
зависимость ограничена `sqlalchemy>=2.0,<2.1`: совместимые патч-релизы 2.0 остаются
доступны, переход на изменившую query/result typing версию 2.1 требует отдельной
миграции типов. Проверки mypy не ослаблены, несвязанные файлы не правились.

После интеграции WMS-526 на Python 3.11.15 / SQLAlchemy 2.0.54 / mypy 2.3.1
повторены ruff и mypy — PASS. Общий backend набор выше расширен
`test_fbs_auto_assign_ozon_boxes.py`, `test_fbs_packing_box.py`,
`test_ozon_box_positions.py`, `test_ozon_box_assembly.py`: 282 passed / 7 skipped.
Frontend tsc/build PASS; восемь наборов (семь прежних плюс fbsUx) — 115 passed.
Дополнительно printMarkingCodeLabel, MarkingPrintDialog, MarkingPrintDialog.confirmOrder,
fbsScanAutoPrint, fbsKizAutoReprint — 66 passed. Продуктовый код и свидетельства
WMS-526 перенесены без изменений; единственный merge-конфликт в начале бэклога
разрешён сохранением обеих записей WMS-527 и WMS-526.

### Аналитическая приёмка exact candidate `b930a56e8184018f3c3d3a1bb2520a034bd52f92`

**Software-контракт WMS-527 и exact staging infrastructure приняты без обнаруженных
нарушений R1–R7; кандидат принят к merge и production deployment.**
Полный diff от `origin/etalon` содержит разрешённые WMS-476/WMS-526, тестовые
исправления пяти прежних CI-падений, pin `SQLAlchemy>=2.0,<2.1`, документы и
синхронизацию generated OpenAPI. Известные
WMS-517 commits не являются предками кандидата; withdrawal/True API/CryptoPro,
миграции, worker/beat и deploy-конфигурация в diff отсутствуют. Независимый Opus 4.7
high подтвердил product SHA и финальную дельту без P0–P3; полный CI exact SHA зелёный.
Staging действительно обслуживает тот же SHA обоими сервисами, public health успешен,
а runtime OpenAPI подтверждает auto-assign и отсутствие WMS-517.

Прямое поручение владельца — влить разрешённый пакет и исключить только WMS-517.
С учётом полного CI, двух независимых PASS review, неизменности принятого product-кода
между `dc8b4ab4` и `b930a56e` и exact staging infrastructure этого достаточно для
merge и контролируемого production deployment. Непройденный авторизованный staging
click-through не скрывается: login smoke доказывает только доступность web, а не работу
WMS-469/514/476 после входа. Он остаётся postdeploy browser gate вместе с C7/C10:
live Ozon, настоящая успешная этикетка и повтор, физическая печать/сканирование.
C8 закрывается только фактическим production SHA/ancestry/health после deploy.

блокируют разрешённые владельцем merge и deploy программно и инфраструктурно
принятого кандидата.
