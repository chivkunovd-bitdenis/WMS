# WMS-516. Склады WB/Ozon не являются физическими складами WMS

**Дата постановки:** 23.09.2026.

**Приоритет:** срочно.

**Статус:** техническая реализация и локальные проверки выполнены; ожидаются
перекрёстное ревью и приёмка аналитика. Разработчик production не изменял.

## 1. Исходный запрос и уточнения

Исходное требование владельца, дословно:

> «FBS-ный склад — это просто сраная фикция, это просто карточка, это просто список,
> по которому мы получаем заказы. Это просто куда мы отправляем остатки. Это не наш
> склад. Он не должен быть нашим складом. Перенеси всё на основной и убери вообще
> эту залупу. Не должны быть склады вообще нашим складам. Они нужны только для двух
> вещей. Первое: подключаем этот склад — с него получаем заказы. Второе: когда
> передаём остаток, по этому складу кидаем остатки. Всё, он больше нигде не должен
> фигурировать».

Предшествующее обязательное уточнение владельца:

> «Все остатки смотрятся по остатку. Насрать, на какой он зоне, если он не в резерве».

Оперативное поручение владельца, переданное ведущим отдельно от системной разработки:

> Прямо сейчас весь остаток ИП Фадина перенести на физический склад «основной».
> Это отдельная production data repair; системная задача должна исключить повторение.

Уточнение, полученное при разработке 23.09.2026: в WMS уже есть отдельный штатный
`defect_warehouse_service`. Он создаёт физический внутренний `Склад брака` /
`__DEFECT__` с `is_operational=false` и хранит там брак возвратов. Исходный запрос
касается marketplace FBS WB/Ozon pseudo-warehouses и не разрешает ломать или
переделывать defect-контур. Поэтому один признак `is_operational=false` недостаточен
для классификации FBS legacy warehouse.

Контекст уже заданной публикации остатков:

- изменяются только товары сегодняшней приёмки №000069, а не весь каталог селлера;
- для этих товаров включено 100% только на склад WB **Лыткарино**, ID `2067199`;
- перенос физического остатка не должен включать публикацию для других товаров,
  площадок или складов.

## 2. Проверенный существующий процесс

Анализ выполнен на `origin/etalon` `e0f0c0b98076ae11f43628239a9bf5259e0c92f0` и
read-only запросах к production 23.09.2026. Кабинеты секретов не открывались,
production-код и данные не менялись.

### 2.1. Правильные сущности уже существуют, но legacy-данные нарушают границу

- `Warehouse` сейчас является физическим складом WMS: на него ссылаются ячейки,
  документы, остатки, движения, резервы, тара и инвентаризации.
- `FbsWarehouseBinding` уже хранит нужное сопоставление: внешний склад продавца WB/Ozon
  → выбранный физический склад WMS. Внешний номер и физический `warehouse_id` — разные
  измерения.
- Исторический код создавал в `warehouses` строки `FBS WB <id>` с кодом
  `fbs-wb-...`. Нынешний код больше не создаёт их при обычном импорте WB, но сохраняет
  распознавание legacy-строк и допускает, что старые документы и остатки продолжают
  ссылаться на них.
- Обычный список складов показывает только `is_operational=true`. При этом общий
  `get_warehouse` принимает и неоперационный склад, поэтому известный UUID старого
  marketplace-склада всё ещё можно передать в создание приёмки, отгрузки, поставки,
  ячейки или привязки.
- Настройка binding WB частично отказывается использовать legacy-склад, однако ремонт
  прекращается, если по нему уже началась работа. Ozon-заказ прямо получает физический
  `warehouse_id` из binding; общий запрет привязать Ozon к marketplace legacy-складу
  отсутствует.
- `is_operational=false` само по себе не означает marketplace-заглушку. Штатный
  `defect_warehouse_service` создаёт внутренний физический `Склад брака` с кодом
  `__DEFECT__` и пишет туда брак возвратов. Это отдельный сервисный контур, который
  пользователь не просил менять. Запрет должен отличать legacy/virtual FBS warehouse
  по его marketplace-идентичности, а не запрещать все внутренние склады одним флагом.

### 2.2. Почему остаток пропал из правильного складского контекста

- Приёмка пишет принятые единицы в системную ячейку `__SORTING__` склада, указанного
  в документе. Если документ ссылается на `FBS WB ...`, физический баланс оказывается
  у скрытого технического склада.
- Публикация FBS читает свободный остаток только физического склада, указанного в
  binding. Когда binding уже направлен на «основной», остаток на старом `FBS WB ...`
  в публикацию не входит.
- Инвентаризация и складские документы ограничиваются выбранным `warehouse_id`, поэтому
  остаток скрытого склада не появляется в инвентаризации «основного».
- FBS-расчёт уже складывает хранение и `__SORTING__` одного физического склада и вычитает
  резервы. Однако общая сводка при включённом адресном хранении всё ещё вычитает
  сортировку из `available`, а выдача конкретной sorting-ячейки выставляет `available=0`.
  Это отдельно нарушает прямое правило владельца даже после переноса данных.

## 3. Цель изменения

Для обычного товарного потока оператора существует только реальный физический склад
фулфилмента. Принятый товар сразу учитывается на нём; sorting — обычная зона этого же
склада. Внешний склад WB/Ozon остаётся в карточке селлера только как адрес получения
заказов и публикации остатка. Ни подключение внешнего склада, ни импорт заказа никогда
не создают `Warehouse`, ячейку, остаток или движение с marketplace-идентичностью.
Внутренний физический `Склад брака` остаётся отдельным штатным исключением только для
дефектного товара возвратов и не становится складом WB/Ozon или источником продаваемого
остатка.

Существующие legacy-данные исправляются один раз с доказанным назначением на реальный
склад, без нового оприходования, потери коробов, повторного остатка или смешивания
арендаторов/селлеров. После исправления legacy-строки `FBS WB ...` не остаются участниками
физического учёта.

## 4. Продуктовые решения

1. **Две разные сущности.** Внешний склад площадки остаётся в справочнике площадки и
   binding. `Warehouse` означает только физический склад ФФ.
2. **Binding сохраняется.** Он отвечает на два вопроса владельца: обслуживаем ли внешний
   склад (получаем его заказы) и публикуем ли на него остаток. Для вычисления физического
   остатка binding указывает настоящий склад WMS, а не создаёт его копию.
3. **Sorting не является отдельным складом или резервом.** Это зона настоящего склада.
   Нахождение в ней меняет местоположение, но не уменьшает on-hand/free само по себе.
4. **Исправление legacy-данных — переклассификация ошибочного измерения.** Не создаётся
   повторная приёмка и не рисуется вымышленное физическое перемещение. Существующие
   документы, движения и тара сохраняют идентичность и историю, а ошибочная складская
   размерность заменяется доказанной физической; отдельный durable-аудит ремонта хранит
   source, target, run/idempotency key и сверенные количества.
5. **Несколько реальных складов не объединяются догадкой.** Единственный физический склад
   арендатора — достаточное доказательство только для его legacy-данных. При двух и более
   складах нужен однозначный существующий binding/документный источник или явная карта
   миграции. Неоднозначная строка блокируется отчётом, а не переносится в «первый» или
   склад с названием «основной».
6. **Новой пользовательской страницы не требуется.** Результат виден в существующих
   складе, каталоге, инвентаризации и настройке остатков. Для операционной миграции нужен
   проверяемый dry-run/apply/verify механизм, а не постоянный интерфейс.
7. **Неоперационный не равен виртуальному.** Marketplace legacy warehouse определяется
   зарезервированной FBS-идентичностью (`fbs-wb-*` и точным реестром legacy-строк для
   миграции), а не одним `is_operational=false`. Внутренний `__DEFECT__` — физическое
   сервисное место брака: его разрешено создавать и использовать только штатным
   defect/return-контуром. Оно не выбирается для binding, обычной приёмки или публикации.

## 5. Требования

### R1. Внешний склад площадки не создаёт физический Warehouse

При подключении, синхронизации справочника, импорте заказа WB/Ozon и повторном обмене
система хранит внешний ID/название только в marketplace-справочнике и binding. Новая
строка `Warehouse`, `StorageLocation`, баланс, тара или движение для внешнего склада не
создаётся. Повтор события не создаёт дубль.

**Основание:** прямое требование владельца о двух назначениях внешнего склада.

### R2. Binding может ссылаться только на склад обычного товарного потока ФФ

Создание и изменение WB/Ozon binding принимает только операторский физический склад
того же tenant, доступный обычному товарному потоку (`is_operational=true`). Marketplace
legacy/virtual warehouse, внутренний `__DEFECT__`, чужой tenant или отсутствующий склад
отклоняется. Один настоящий склад может кормить несколько внешних складов и обе площадки
без дублирования своего физического остатка. Это ограничение относится к binding и не
является общим запретом всех `is_operational=false`: defect-сервис продолжает хранить
физический брак на своём специально зарезервированном внутреннем складе.

**Основание:** внешние адреса не являются физическими складами; границы клиентов.

### R3. Marketplace legacy warehouse закрыт для всех новых физических записей

Создание приёмки, отгрузки, FBO-разгрузки, FBS-поставки/заказа, инвентаризации, ячейки,
тары, резерва и движения не может выбрать или унаследовать marketplace legacy/virtual
warehouse, в том числе по известному UUID. Историческое чтение до миграции остаётся
доступным для ремонта, но новые физические записи туда не пишутся.

Правило не является общим запретом `is_operational=false`: существующий возвратный
defect-контур продолжает через `defect_warehouse_service` создавать/находить
`__DEFECT__` и записывать туда только подтверждённое количество брака. Этот склад нельзя
использовать как обход для обычной приёмки, binding, FBS/FBO или публикации.

**Основание:** сейчас скрытие склада в списке не защищает серверные write-paths.

### R4. Заказы продолжают приходить с обслуживаемых складов WB и Ozon

Активный `served` binding по-прежнему определяет, с каких внешних складов импортируются
заказы. Импортированный заказ получает доказанный реальный `warehouse_id` из binding и
резервирует товар на нём. Необслуживаемый или не сопоставленный внешний склад не создаёт
технический Warehouse; заказ обрабатывается по существующему контракту unmapped/skip,
без выдуманного физического места.

**Основание:** первое разрешённое назначение внешнего склада.

### R5. Публикация использует общий физический остаток настоящего склада

Для WB и Ozon публикуемое количество считается из on-hand настоящего склада, включая
его sorting, минус действующие резервы и другие штатные вычеты, затем ограничивается
правилом оператора. Несколько внешних адресов не порождают несколько копий on-hand.
Выключение/сбой одной площадки не меняет физический баланс и правило другой.

**Основание:** второе разрешённое назначение внешнего склада и действующее правило
`min(лимит оператора, свободный остаток)`.

### R6. Sorting входит в остаток независимо от режима хранения

При адресном и безадресном хранении единицы в `__SORTING__`, россыпью или в таре входят
в on-hand. Если они не заняты резервом/отгрузкой, они входят и в free. Размещение в
ячейку меняет только местоположение. Общая сводка, конкретная sorting-зона, каталог ФФ,
кабинет селлера, FBS-расчёт и инвентаризация используют одну арифметику и не вычитают
sorting повторно.

**Основание:** прямое уточнение владельца «если он не в резерве».

### R7. Срочный production repair ИП Фадина

Отдельный контролируемый apply-run переносит весь ненулевой физический остаток товаров
ИП Фадина с `FBS WB 1887957` на «основной». На подтверждённом исходном снимке это ровно
627 единиц. Ни остаток других селлеров, ни основной остаток ИП Фадина не перезаписывается
абсолютным значением. До apply сохраняется dry-run manifest; после — сверка source=0,
target delta=+627 и tenant/seller/product totals unchanged.

**Основание:** отдельное оперативное поручение владельца.

### R8. Приёмка №000069 и тара сохраняются без дубля

После repair №000069 относится к «основному», остаётся тем же документом и содержит те
же 159 товаров/627 actual. В sorting «основного» находятся 619 единиц в тех же 208
непустых коробах и 8 россыпью; пустой 209-й короб сохраняётся как объект документа,
если он ещё существует на атомарном снимке. Product, seller, tenant, КИЗ, строки,
времена, события и идентификаторы контейнеров не меняются. Новая приёмка и второй
комплект 627 единиц не создаются.

**Основание:** подтверждённый состав production и требование сохранить историю.

### R9. Публикация №000069 остаётся адресной

Правило 100% остаётся только у 159 товаров №000069 и только для WB Лыткарино
`2067199`. Перенос всех 627 физических единиц ИП Фадина не включает публикацию для
остальных товаров ИП Фадина, Ozon или других WB-складов. На зафиксированном снимке
392 + 627 − 3 даёт публикацию 1016; на живом apply-снимке проверяется та же формула с
актуальными законными движениями и резервами, а не константа.

**Основание:** отдельное уточнение владельца «только для товаров из приёмки».

### R10. Существующие legacy-ссылки мигрируются согласованно

Для каждого legacy-склада dry-run перечисляет все ссылки: bindings, документы, заказы,
поставки, резервы, ячейки, балансы, движения, тару, инвентаризации, FBO, карты,
operation facts, биллинг и отчёты. Apply обновляет все относящиеся к доказанному target
ссылки в одной транзакции либо не меняет ничего. Исторические ID/время/тип движения
сохраняются; аудит repair позволяет восстановить source → target и количества.

**Основание:** production FK-граф показывает, что переноса одного balance недостаточно.

### R11. Несколько складов, селлеров и tenants не смешиваются

Миграция группирует и блокирует данные по tenant, seller, product, warehouse и container.
При нескольких физических складах без доказанного target apply для этой группы не
выполняется. Нулевые строки/старые документы ИП Комаровой, ИП Чжоу или другого селлера
не становятся данными ИП Фадина. Одинаковые внешние IDs WB/Ozon у разных площадок или
селлеров не объединяются.

**Основание:** фактический legacy-склад содержит историю нескольких селлеров, а у двух
production tenants есть несколько физических складов.

### R12. Резервы и параллельная работа сохраняют количество

Apply блокирует либо версионирует затронутые склады, товары, балансы, контейнеры,
документы и резервы так, чтобы параллельная приёмка, заказ, подбор, инвентаризация или
публикация не увидела половину переноса. Резерв переезжает вместе со своим заказом на
тот же реальный склад и не создаётся повторно. Если состояние изменилось после dry-run,
apply останавливается с новым manifest вместо применения устаревших чисел.

**Основание:** техническая защита от частичного сохранения и двойного расхода.

### R13. Повтор, сбой и потеря ответа безопасны

У repair есть стабильный run/idempotency key и durable status. Повтор до выполнения,
после commit или после потери ответа находит тот же результат: 627 не добавляются второй
раз, контейнеры не дублируются, ссылки не остаются наполовину. Ошибка сообщает точный
blocker и позволяет повторить после его устранения. Откат до commit оставляет исходное
состояние целиком; после commit используется обратимый manifest, а не ручное вычитание.

**Основание:** правила восстановления после неизвестного результата.

### R14. Публикация после repair подтверждается, но не входит в транзакцию данных

После успешного commit система планирует штатную публикацию затронутых товаров. Потеря
ответа WB/Ozon не откатывает физические данные и не вызывает второй repair; внешний
результат выясняется/readback и повторяется штатным идемпотентным механизмом. Для
№000069 проверяется Лыткарино `2067199`, остальные адреса и товары не меняются.

**Основание:** внешняя операция не должна разрывать атомарность локальной миграции.

### R15. Legacy Warehouse удаляется после полной миграции

После того как у legacy-склада нет балансов и ни одной физической/исторической ссылки,
его locations и строка `Warehouse` удаляются. Пустые legacy-склады удаляются тем же
проверяемым процессом. Системный код больше не определяет бизнес-поведение по имени
`FBS WB ...`; создание зарезервированного legacy-кода блокируется. Marketplace bindings
и справочники сохраняются и продолжают работать без такой строки.

**Основание:** прямое требование «больше нигде не должен фигурировать».

### R16. Проверяемый отчёт до и после

Dry-run и verify выдают без секретов: run ID, source/target, tenant/seller, количество
документов/ссылок, product/container rows, on-hand/reserved/free до и после, blockers и
статус публикации. Проверка не печатает КИЗ, токены или персональные данные заказов.

**Основание:** production repair должна быть доказуема и безопасна.

- Нельзя суммировать все склады tenant без target mapping: несколько реальных складов

## 10. Техническая реализация и проверка разработчиком, 23.09.2026

Сервисный выбор обычного склада допускает только физический operational Warehouse;
историческое чтение доступно через `include_non_operational=True`. Marketplace legacy
распознаётся по зарезервированному коду `fbs-wb`, а не по отображаемому имени.
PostgreSQL migration `20260923_0516` защищает прямые FK на warehouse/location и
наследование склада через документ. Составные FK выбирают именно ссылку на `id`,
а tenant строки без своего tenant_id определяется через родительский документ.
Штатный `__DEFECT__` сохранён; обычные selectors и WB/Ozon bindings его не принимают.
Сортировка больше не уменьшает available в summary и location endpoint сама по себе.

Repair хранит durable manifest и статус в существующей `background_jobs` с типом
`physical_warehouse_repair`. Новых таблиц учёта остатков нет. CLI исполняет один
source → physical target за run. Единственный physical target определяется
автоматически; при нескольких требуется явный `--target` для всего source.
Неоднозначные группы, коллизии исторических unique keys, чужой tenant/product и
неизвестные deployed physical FK блокируются до изменения данных. Частичного
разделения одного source между несколькими физическими targets нет: такой случай
требует отдельно подготовленной согласованной карты, а не выбора первого склада.

Apply берёт короткие PostgreSQL `SHARE ROW EXCLUSIVE` locks на затронутые таблицы,
проверяет fingerprint подготовленного source/target-графа и сохраняет весь результат
в одной транзакции. Чтения видят предыдущий committed snapshot; записи ожидают.
Если ожидание lock превышает 10 секунд, транзакция завершается ошибкой без переноса.
Это операционная maintenance-команда, которую запускают в согласованное окно.
Баланс merging использует tenant/product/container, сохраняет unpacked/packed и
проверяет количества по каждому product/container. FK, IDs и времена исторических
движений/документов сохраняются; sorting collisions сводятся в существующую sorting.
Старые warehouse/location удаляются только после переноса ссылок.

Повтор committed run возвращает прежний результат. `stale` требует нового run UUID
и нового manifest; сменить scope старого UUID нельзя. `rollback` восстанавливает
изменённые поля и удалённые строки из manifest только при неизменённом after-snapshot.
Позднейшие движения, изменения документов или публикационных metadata блокируют
автоматический rollback; ручное вычитание остатков не используется. С начала первой
попытки внешней публикации rollback запрещён независимо от её исхода: разрешено
только восстановление публикации актуального физического остатка через `publish`.

CLI `apply` после commit вызывает отдельную публикацию только affected product IDs
на активные existing bindings target-склада, не меняя настройки оператора. Повтор
после потери ответа запускает штатный absolute-stock sync/readback. Ошибка провайдера
оставляет repair completed, publication pending; восстановление — `publish --run`.
Пустой legacy после уже выполненного emergency repair не публикует и не добавляет
единицы повторно. Отчёт CLI не выводит содержимое исходных заказов, КИЗ или ключи.

### Команды rollout и recovery

Из `backend`, с обычной настроенной средой целевого стенда:

```sh
alembic upgrade head
python -m app.cli.repair_physical_warehouses prepare --run <UUID> --tenant <UUID> --source <UUID> --target <UUID>
python -m app.cli.repair_physical_warehouses apply --run <UUID>
python -m app.cli.repair_physical_warehouses verify --run <UUID>
python -m app.cli.repair_physical_warehouses publish --run <UUID>
python -m app.cli.repair_physical_warehouses rollback --run <UUID>
```

Последние две команды — восстановление при pending publication либо отмена переноса
по неизменённому manifest ДО первой попытки публикации соответственно, а не
обязательная последовательность. CLI `apply` автоматически начинает публикацию
после commit, поэтому после него нельзя обещать доступность data rollback.
Schema downgrade до `20260921_0490` снимает guards и не откатывает физические данные;
данные откатываются только командой manifest rollback. Перед production apply нужно
прочитать dry-run каждого source и обеспечить доказанный target. Разработчик эти
команды на production/staging не выполнял.

   PostgreSQL запрещает изменение кода или operational-флага существующего
   `fbs-wb-*`. Обычные selectors/bindings не принимают также `__DEFECT__`, даже
   с ошибочным operational-флагом. Прямая запись физического остатка в defect
   отклоняется. Только штатные функции создания defect location и размещения
   возвратного брака устанавливают tenant-scoped DB context внутри savepoint,
   предварительно flush-ят чужие ожидающие записи и снимают context до возврата.
2. Guard рекурсивно проходит весь развёрнутый FK-граф до warehouse, включая
   box line → box → request, cargo/document lines и циклы (visited record set).
   Repair snapshot рекурсивно включает потомков source/target и метаданные
   stock rules/sync. Неизвестная deployed таблица или physical FK останавливает
   repair. Новая строка короба и изменение quantity после apply блокируют rollback.
3. Dry-run проверяет не только UniqueConstraint, но и unique Index: строит
   проекцию будущих строк и выполняет SQL с исходным partial predicate,
   expression и NULL-семантикой. Коллизии default print connection, обоих
   warehouse tariff scopes и coalesce(container_id) у pick allocations дают
   точный blocker с именем индекса до apply. Неизвестный unique index тоже blocker.
4. До первого внешнего вызова durable `publication_started` сохраняется отдельно.
   После него rollback сообщает `rollback_blocked_after_publication`, включая
   потерянный ответ; binding не возвращается на legacy, внешнее состояние не
   объявляется отменённым. Recovery выполняет scoped публикацию актуального
   остатка вперёд. До публикации rollback доступен только без любого graph drift.

## 12. Исправление ownership preflight по повторному ревью

На commit `9be19d35` воспроизведён дополнительный P1: `prepare` ошибочно возвращал
`prepared` для legacy movement с seller другого tenant, legacy WarehouseBox с
палетой чужого tenant и legacy balance с полиморфным `container_id` чужого короба.
Причина: descendant snapshot не включает родителей вне source/target, а apply
включает repair context и потому не может полагаться только на обычные DB guards.

Repair теперь отдельно собирает ownership/FK-поля родителей, рекурсивно проверяет
tenant, все компоненты composite FK и согласованность product/seller. Полиморфные
box/cargo_place/pallet IDs разрешаются через реальные таблицы; чужая, отсутствующая
или неоднозначная тара блокирует prepare. Тара живого balance должна принадлежать
source/target группе; та же тара на третьем физическом складе не переносится по
догадке. Текущая позиция тары исторического движения не переписывается: там
проверяется идентичность/tenant, а не требование навсегда остаться в старом складе.

Внешние родители не добавляются в изменяемые строки manifest. Их ownership/FK-поля
включаются в fingerprint; seller credentials и прочие сторонние поля не читаются.
Apply повторяет снимок под maintenance locks и shared row locks родителей, так
что смена tenant владельца после prepare даёт `stale`, без переноса остатков.
Новые поля fingerprint делают старые подготовленные manifests устаревшими:
для них требуется новый run UUID и новый dry-run.

Проверки разработчика: три исходных воспроизведения сначала дали 3 failed, после
исправления — green. Полный целевой файл на SQLite in-memory: **28 passed, 2 skipped**
(PostgreSQL-only), включая третьего physical warehouse, parent drift между
prepare/apply и defensive проверку legacy composite FK. `ruff check .` и `mypy .`
— passed, 473 source files. PostgreSQL-повтор не выполнен: локальный Docker API
по-прежнему недоступен после описанного выше ENOSPC. Production/staging не тронуты.
Это исправление разработчика для повторного ревью, а не заключение о приёмке.
