# WMS-520 — Убрать 500 при preview и импорте готовых КИЗ

Задача зарегистрирована 24.09.2026 по production-инциденту. Постановка
подготовлена в `codex/wms520-requirements` от production SHA
`270215a5c065e4f45293efba45b0a018311840ad`.

Запись: [канонический бэклог, WMS-520](../KANONICHESKIY_BACKLOG.md#wms-520).

## 1. Исходный запрос и уточнение владельца

> у нас 500 сисиема висит
>
> чё за хуйня

Диагностика:

> Production `POST /operations/marking-codes/import/preview` отвечает 500.
> Трейс: `preview_marking_import` → `scalar_one_or_none()` →
> `sqlalchemy.exc.MultipleResultsFound`. То же ожидание одного пула
> есть в `get_or_create_marking_pool` фактического импорта.

Авторитетное бизнес-уточнение владельца:

> Селлер загружает готовые КИЗ и привязывает их к товару. Искать
> существующий набор по GTIN не нужно. Несколько пулов одного
> tenant/seller/GTIN могут быть нормальными отдельными загрузками.

## 2. Существующий процесс и причина

Оператор ФФ или селлер открывает «Честный знак» → «Загрузить КМ»,
выбирает CSV/PDF/TXT, а диалог вызывает `POST
/operations/marking-codes/import/preview`. Preview парсит файл и группирует
КИЗ по GTIN. После выбора товаров ручной `POST
/operations/marking-codes/import` создаёт batch, пулы, коды и события.

Сбой вызван не дублями данных, а ошибочным старым допущением кода:

- preview ищет `MarkingPool` по `tenant_id + seller_id + gtin`, хотя ему
  не нужно искать старую загрузку;
- на двух законных пулах того же GTIN `scalar_one_or_none()` даёт
  `MultipleResultsFound` и 500;
- фактический import повторяет ту же ошибку в
  `get_or_create_marking_pool`, поэтому исправляются оба шага.

## 3. Продуктовое решение

Preview — только проверка текущих файлов. Он не читает `marking_pools`, не выбирает
старую загрузку и ничего не меняет. Для каждой GTIN-группы `suggested_title`
формируется нейтрально из самой группы, например
`GTIN …<последние 4 цифры>`.

Ручной import не ищет и не переиспользует пул по GTIN. Каждая GTIN-группа
текущей успешной загрузки создаёт новый пул с title текущей `pool_spec`
и связями на все выбранные `product_ids`. Один выбранный товар — один новый
пул на GTIN-группу; несколько выбранных товаров связываются с этим же
новым пулом по текущему M2M-контракту UI. Ранее загруженные пулы того же
GTIN и всё их содержимое остаются без изменений.

Дедупликация CIS остаётся tenant-wide. Если в GTIN-группе нет ни одного
нового CIS, пустой пул не создаётся. Batch попытки с `accepted_count=0`
и `skipped_count` может сохраниться по прежнему API-контракту: это история
попытки, но не пустой расходный пул.

## 4. Требования

| ID | Правило | Основание |
|---|---|---|
| R1 | `POST /operations/marking-codes/import/preview` при любом числе старых пулов того же GTIN возвращает preview, а не `MultipleResultsFound`/500. | Production-инцидент. |
| R2 | Preview не читает и не изменяет `marking_pools`, коды, связи, события и документы; `suggested_title` формируется из GTIN-группы. | Явное бизнес-уточнение. |
| R3 | Каждая GTIN-группа manual import, в которой есть новый CIS, создаёт новый `MarkingPool` и не переиспользует прежние пулы того же GTIN. | Пул — итерация загрузки готовых КИЗ. |
| R4 | Новый пул получает GTIN/title текущей группы и связывается со всеми переданными для неё `product_ids`; новые CIS и события `imported` относятся к этому пулу. | Текущий M2M-контракт UI. |
| R5 | Все ранее созданные пулы, их title, КИЗ, товарные связи и история не меняются. | Жёсткая граница владельца. |
| R6 | Повторный CIS по-прежнему считается `duplicate`/`skipped` и не создаётся второй раз; один CIS не попадает в несколько пулов. | Существующая tenant-wide дедупликация. |
| R7 | Если все CIS GTIN-группы уже существуют, import не оставляет для этой группы пустой `MarkingPool`; batch попытки и accepted/skipped сохраняются по API-контракту. | Не плодить пустые пулы. |
| R8 | Валидация `product_ids`, пулы, коды и события строго соблюдают tenant/seller boundaries; чужой товар не затрагивается. | Инвариант изоляции. |
| R9 | Сохраняются batch, `document_number`, accepted/skipped, skip reasons, события `imported` и форматы API. | Минимальная правка. |
| R10 | Фронт, API-схемы, маршруты, кнопки, тексты, права, WMS-476 auto import, печать/перепечать и другие процессы не меняются. | Граница владельца и AGENTS.md. |
| R11 | DB UNIQUE по tenant/seller/GTIN, data cleanup, слияние или удаление пулов запрещены: несколько пулов одного GTIN разрешены. | Явное уточнение владельца. |

### Production deployment от 24.09.2026

PR [#245](https://github.com/chivkunovd-bitdenis/WMS/pull/245) смержен в
`etalon`; точный merge и production SHA —
`ba75fe0bca7fee9716bed833fc13edece02740c5`. После выкладки на сервере
подтверждены ветка `etalon`, успешный `/api/health`, HTTP 200 для корня и
`/seller/`. Readback запущенного API подтвердил, что
`preview_marking_import` не содержит обращения к `MarkingPool`, а прежняя
функция `get_or_create_marking_pool` отсутствует. Число недавних 500 на
preview после этой выкладки — 0.

Реальный авторизованный preview/import с файлом оператора намеренно не
запускался, чтобы при документальной post-deploy проверке не создавать и не
привязывать КИЗ в production. Поэтому **операторская live-приёмка остаётся
открытой**: оператору нужно повторить исходный preview и штатный import своего
файла. До этого доказаны выкладка и отсутствие новых preview 500 в наблюдаемом
интервале, но не полный бизнес-сценарий с реальными production-данными.

Итоговый статус: **развёрнуто в production; операторский live import ожидается**.
