# WMS-613 · Восстановить печать QR и ШК без пустых этикеток

## Запрос

01.10.2026 владелец: «так же через 1 печатается», «убери аналитиков», «срочно на проде правь», «и он шк теперь вообще не печатает». Предыдущее исправление f512103b не подтвердилось на физическом принтере. Аналитический цикл по указанию владельца не проводится.

## Требования

- R1. При ШК=1 и ЧЗ=0 сохранить последовательность QR заказа → товарный штрихкод для каждого заказа.
- R2. Не создавать пустую страницу между этикетками и после последней, в том числе при печатной области на 1 мм короче номинального размера.
- R3. Не менять выдачу ЧЗ, данные заказов, состав выбранного макета и API.
- R4. Проверить короткую страницу в Chromium PDF и присутствие изображения штрихкода на каждой товарной странице. Сохранить изменение в Git и передать в релиз; физическую проверку отличать от программной.

## Реализация

В печатном CSS убрана зависимость высоты и отступа от 100vh. Каждая секция на 1,5 мм ниже номинальной высоты бумаги, разрыв стоит после каждой секции кроме последней. У товарной этикетки этот запас взят из внешних вертикальных отступов: область штрихкода и текста сохранена.

| TypeScript и production build | R1–R3 | Подтверждено: обе проверки прошли |
| Физический принтер оператора | R4 | Не проверено: устройство недоступно исполнителю |

## Заключение

Программные проверки пройдены. Проверка реальной пагинации сохранена в `frontend/src/utils/printMarkingCodeLabel.pagination.test.ts`; запуск из frontend: `WMS_PRINT_CHROMIUM="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" npm run test:unit -- src/utils/printMarkingCodeLabel.pagination.test.ts` (нужен Poppler pdfimages). Тест проверяет изображения, фактически нарисованные на каждой PDF-странице, а не только цифры штрихкода или число HTML-секций.

Причина именно физического сбоя не объявляется доказанной; требуется проверка результата на принтере после выпуска. Продовый деплой и физическая приёмка этим заключением не подтверждаются.
