# WMS-578 — Сортировка сканом не находит товар по индексу приёмки (P2-4)

## Исходная находка

Независимое ревью 28.09.2026, `docs/reviews/artifacts/release-audit-20260928/review-opus-all.md`,
раздел P2-4 («Сортировка сканом не узнаёт штрихкоды, которые принимает приёмка: товар Ozon сканом
не разложить»).

## Нарушенные требования

WMS-550/WMS-559 (сортировка сканом) и WMS-473 (единый поиск ШК приёмки) — сортировка должна
находить товар документа тем же способом, что и приёмка. WMS-535 (все ШК товара в
`product_barcodes`) — эти дополнительные штрихкоды должны участвовать в сканах. Фактически
`sorting_scan_service.matching_scan_lines` искала товар только по точному совпадению с
`product.wb_barcode` и по `sizes[].skus` карточки WB (для варианта того же `nm_id`), без учёта
регистра, без `product_barcodes`, без штрихкодов Ozon и без артикула WMS. Товар, продающийся
только на Ozon (нет `wb_barcode`/`wb_nm_id`), не находился вовсе.

## R (требования этого исправления)

R1. Сортировка ищет товар документа тем же индексом, что и приёмка
    (`inbound_intake_service._request_barcode_index`/`_index_lookup`), ограниченным строками
    этого документа (`include_seller_catalog=False`), как и требует приёмка.
R2. Раскладываются сканом: дополнительный ШК из `product_barcodes`, артикул WMS (`sku_code`),
    товар, продающийся только на Ozon (по его штрихкоду), прежний основной ШК WB — без учёта
    регистра.
R3. Неоднозначность — тот же штрихкод у двух товаров документа — обрабатывается как у приёмки:
    отдельная ошибка (`ambiguous_product`), а не молчаливый выбор одного из них.
R4. Ничего из уже работающего не ломается: WB-карточный механизм альтернативных ШК по размеру
    (`sizes[].skus`, WMS-556/WMS-559) для штрихкода, ещё не попавшего в `product_barcodes`,
    остаётся рабочим — это не заменяется, а дополняется.

## Реализация

`backend/app/services/sorting_scan_service.py`, `matching_scan_lines`:

- Прямая проверка (без обращения к БД, не зависит от `seller_id` документа): совпадение
  штрихкода без учёта регистра с `product.wb_barcode` или `product.sku_code` каждой строки
  документа. Это сохраняет прежнее поведение для основного ШК WB даже в редком случае, когда у
  строки ещё не выставлен `seller_id` документа (ровно сценарий существующего теста
  `test_saved_variant_alternative_and_primary_share_stock`).
- Тот же индекс, что у приёмки: `inbound_intake_service._request_barcode_index`/`_index_lookup`
  — покрывает дополнительные ШК из `product_barcodes`, штрихкоды Ozon и повторно артикул/основной
  ШК, ограничено строками документа.
- Неоднозначность: если индекс сам нашёл два разных товара документа с одним штрихкодом либо
  прямая проверка и индекс разошлись на разные товары — `WarehouseMapError("ambiguous_product")`,
  как у `scan_product`.
- Если ни прямая проверка, ни индекс ничего не нашли — старый (не изменённый) откат на
  WB-карточный механизм `sizes[].skus` по `chrtID`, вынесенный в отдельную функцию
  `_wb_card_variant_scan_lines` без изменения логики.
