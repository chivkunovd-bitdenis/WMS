# WMS-550 · Сортировка сканами: ячейка → тара → товар по одной штуке

Запись задачи: [канонический бэклог, WMS-550](../KANONICHESKIY_BACKLOG.md#wms-550).

## 1. Исходный запрос

27.09.2026 ArtMax начал сортировать принятую поставку. Владелец потребовал срочно
сделать рабочим операторский порядок: скан ячейки активирует ячейку; скан тары
открывает тару; каждый следующий скан товара кладёт одну существующую единицу в
открытую тару, а без тары — прямо в ячейку. Тара при этом должна быть закреплена за
выбранной ячейкой. Повторный скан активной тары закрывает её, повторный скан активной
ячейки закрывает ячейку. При закрытии или смене ячейки прежняя тара обязательно
сбрасывается, чтобы следующий товар не попал в старую цель.

Технический вывод из проверки текущего процесса: товар уже существует в данных этой
приёмки, в том числе внутри входных коробов, а одинаковый товар может иметь несколько
источников. Поэтому реализация должна перемещать существующее количество, а не создавать
новое, и не может молча выбирать один из нескольких возможных источников. Это защита
сохранности учёта, а не отдельное пользовательское требование.

## 2. Текущий процесс и опасность

Экран сортировки получает ячейки, тару и товарные строки конкретной приёмки через
`GET /warehouses/{warehouse_id}/sorting-objects?inbound_request_id=...`.
Сейчас обработчик сканера распознаёт только ячейку и тару: скан ячейки выбирает цель,
а скан тары сразу переносит всю тару с содержимым в эту ячейку. Штрихкод товара
обработчик не ищет.

Сервер переносит товар не по `product_id`, а по идентификатору конкретной строки
остатка `InventoryBalance.id`. Поэтому одинаковый товар в двух исходных коробах — это
два разных возможных источника. Выбор первой найденной строки был бы скрытым списанием
не из того физического места. При неоднозначности операция должна быть отклонена без
изменения остатков.

## 3. Требования

| № | Требование |
|---|---|
| R1 | Скан ячейки по её системному штрихкоду `LOC-…` или видимому коду делает ячейку активной и явно показывает её оператору. Тип символа не важен: один и тот же текст распознаётся из Code128 и QR. Используется общая нормализация клавиатурного сканера, включая `LOC-…`, введённый при русской раскладке как `ДЩС-…`. Сам выбор ячейки остатков не меняет. |
| R2 | Если оператор повторно сканирует активную ячейку, ячейка закрывается: активная ячейка и активная тара очищаются. Скан другой ячейки переключает активную ячейку и также очищает прежнюю активную тару. |
| R3 | Скан тары при активной ячейке делает эту тару активной и размещает её целиком в активной ячейке штатной серверной операцией. Тара — короб, палета или грузоместо из текущей приёмки. Скан другой тары переключает активную тару на неё. Без активной ячейки скан тары показывает ошибку и ничего не меняет. |
| R4 | Повторный скан активной тары закрывает тару: активная тара очищается, но сама тара и уже вложенный товар остаются в ячейке. Активная ячейка сохраняется, поэтому следующие товары идут прямо в неё. Закрытие тары само по себе не вызывает повторного перемещения. |
| R5 | При активных ячейке и таре каждый новый скан товарного штрихкода переносит ровно одну существующую единицу из единственного внешнего источника этой приёмки в активную тару. Сама активная тара полностью исключается из источников, но наличие этого SKU внутри неё не мешает добавить следующую единицу из единственного внешнего источника. Если внешнего источника уже нет, но товар есть в активной таре, сервер отвечает `already_in_target` без изменения количества; он не создаёт дубль и не изымает единицу из случайной чужой тары. Тара остаётся связанной с активной ячейкой. |
| R6 | При активной ячейке без активной тары каждый новый скан товарного штрихкода переносит ровно одну существующую единицу товара из остатка текущей приёмки прямо в активную ячейку. Без активной ячейки товарный скан показывает ошибку и ничего не меняет. |
| R7 | Источник единицы ограничен текущими `tenant`, складом и `inbound_request_id`, должен иметь положительное доступное количество и не быть уже целевой тарой/ячейкой. Источником может быть ещё не проведённая строка входной тары либо уже созданный физический `InventoryBalance`; сервер различает эти типы явно. Если после ограничений есть ровно один источник, перенос выполняется из него. Если источников нет либо их больше одного, сервер возвращает понятную ошибку и не меняет экран или остатки. Оператор разрешает неоднозначность существующим ручным выбором строки/источника; первая найденная строка никогда не выбирается автоматически. |
| R8 | Штрихкод товара должен однозначно соответствовать одному товару этой приёмки. Если один код соответствует нескольким товарам либо товар отсутствует в текущей приёмке, система показывает ошибку и ничего не меняет. |
| R9 | Скан не создаёт новое количество и не увеличивает общий остаток товара: используется штатный перенос количества `qty=1` между существующим источником и целью. Допустимо технически создать или объединить строку остатка в цели, но сумма источника и цели до и после успешной операции одинакова. Товар, уже находящийся только в активной цели, повторно не добавляется. |
| R10 | Каждый физический товарный скан получает отдельный идентификатор операции; повтор того же запроса после потери ответа не переносит вторую единицу. После успешного ответа экран перечитывает серверное состояние. При ошибке или неизвестном результате экран не показывает неподтверждённый перенос как сохранённый. |
| R11 | Существующие ручные действия сортировки, перенос тары целиком, права доступа, границы арендатора и других приёмок не меняются. Новые экраны, сущности, режимы и ручное создание остатка не добавляются. |
| R12 | Товарный скан выполняется серверным `POST /warehouses/{warehouse_id}/sorting-objects/scan`, который всегда переносит одну единицу. Запрос содержит `barcode`, `inbound_request_id`, уникальный `operation_id`, `cell_id` активной ячейки и необязательный `to_id` активной тары. Фронт не вычисляет и не подставляет «первый» источник. Ответ различает выполненный перенос, безопасное `already_in_target` без мутации и явный отказ/неоднозначность. |
| R13 | Если тара уже размещена в активной ячейке — непосредственно либо через палету, — её скан только открывает тару и не повторяет серверное размещение. Следующий скан этой активной тары закрывает её, ещё один снова открывает без `POST /sorting-objects/place`. Первичное размещение заполненной тары переносит её целиком со всем уже учтённым содержимым до последующих товарных сканов. Товарный скан сверх принятого и ещё не размещённого количества не создаёт новую единицу: сервер возвращает отсутствие движения. |

## 5. Заключение

Первичная focused-приёмка прошла, но после первой выкладки обнаружен конкретный
регрессионный дефект: повторное открытие уже размещённой тары снова вызывало
`POST /sorting-objects/place`. Backend корректно отвечал `nothing_to_move`, после
чего frontend сбрасывал контекст. Узкий patch теперь определяет фактическую ячейку
тары по цепочке держателей и, если она уже совпадает с активной, открывает тару без
повторного размещения. После подтверждённого первичного `place` frontend синхронно
обновляет данные сканерной очереди, поэтому быстрые последовательные сканы видят
уже размещённый короб, не устаревшее состояние React.

Focused review patch и адресная приёмка C14 — **PASS, новых блокирующих дефектов
в изменённом сценарии не найдено**. Проверен ровно сценарий уже размещённого короба:
первичное открытие, быстрые закрытие и повторное открытие, затем открытие короба на
палете той же ячейки; повторный `place` не вызван. Patch ещё не выложен.

Остальной код следует явному контракту: контекст сканов меняется только
после подтверждённого сервером размещения; товар переносится по одной существующей
единице; активная цель исключена из источников; единственный источник используется,
несколько источников дают явную ошибку; повтор потерянного ответа не переносит вторую
единицу. Заполненный короб при первом размещении переносится целиком со всем уже
учтённым содержимым. Последующие товарные сканы могут перемещать только ещё не
размещённые принятые единицы; скан сверх принятого количества не создаёт остаток.

Read-only срез ArtMax подтвердил применимость: 321 SKU имеют pending-остаток и
физические balances; у 319 SKU источник единственный, у двух SKU по два источника —
они ожидаемо получат `ambiguous_source`, а не скрытый выбор первого короба.

Браузерно проверен только локальный демонстрационный компонент без backend: открытие
и закрытие ячейки/тары работает. Первичная production-выкладка выполнена и версия проверена;
узкий C14-patch повторного открытия тары ещё не выложен;
реальный сканер и операторский проход ArtMax не проверены. Opus-review провести не
удалось из-за недоступной квоты; focused review Astra не выдаётся за Opus-review.
