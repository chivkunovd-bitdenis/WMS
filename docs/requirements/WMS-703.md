## Требования

**R1.** Исправить только исходные 166 Ruff diagnostics и десять E2E случаев ниже. До правки сохранить воспроизводимый baseline: exact SHA, версии инструментов, полный `path:line:column/code`. Расхождение нового baseline объяснить по исходному diff; не расширять задачу в общую чистку, не удалять пути/тесты из discovery/CI.

**R2.** Ruff исправляется без изменения результата бизнес-операций. Сохранить русские строки, коды ошибок, значения fixtures и побочные эффекты импортов/вызовов. E712 требует эквивалентного SQLAlchemy predicate, не Python truthiness столбца; F841/RUF059 не разрешают удалить выполнявшийся вызов вместе с неиспользуемым результатом. Не применять массовый unsafe fix, глобальные ignore/exclude или отключение Ruff. Адресное подавление неоднозначных русских букв допустимо только с обоснованием конкретного исходного русского текста, без общего waiver.

**R3.** Отказы в `auth-dual-portal-sessions` и `ff-staff-users` защищают отсутствие доступа/данных/действий чужого портала и разделение FF/seller сессий. Если есть только FF сессия, действующий экран показывает «Нет доступа», объяснение отсутствия seller сессии и «Войти как селлер»; старое буквальное предложение не требует вернуть тупик. Отказ при существующей seller сессии без права остаётся отдельным случаем. Нельзя заменить все проверки отказов одним общим locator.

**R4.** Сопоставление склада и включение публикации — разные действия. После выбора WMS-склада при выключенной передаче ожидается «публикация выключена», до toggle внешний sync не запускается. Затем проверить связь, включение, sync/status и изоляцию выбранного склада; не включать публикацию автоматически ради старого «готов к публикации».

**R5.** Каталог/приёмка используют действующие «Артикул продавца», SKU, ШК, размер, фактический остаток и действия. Старые обязательные `WB/nmId`, «Артикул WB», `FBS-пул`, «Публикация WB» и запреты остатков/фильтров трассируются отдельно от проверки значений. NmId `123456789` из XLSX должен сохраниться в настоящем продукте/API/карточке: отсутствие в основной строке не доказывает потерю импорта. Коррекция теста сохраняет проверку imported nmId, упаковки, вариантов/ШК и числа строк через действующий источник; удалить assertion без замены нельзя.

**R6.** `seller-available-stock` и `seller-stock-directions` сохраняют проверки остатка после плана, количества/резерва, действия над пулом и запрета лишнего расхода. Если действие перенесено в FF-контекст, fixture/маршрут отражает действующие права и UI. Перед коррекцией больших сценариев тестировщик составляет построчную карту: прежнее ожидание → сохранённая проверка/новый источник/selector либо точный принятый заменяющий контракт. Первая упавшая строка не подтверждает остальные шаги.

**R7.** Семантика отдельного chip «ЧЗ» (метка обязательной маркировки) **OPEN**. Main выводит его при `requires_honest_sign`, отдельно выводит `ff-catalog-marking-link-*` с количеством кодов; E2E ожидает отсутствия chip при двух кодах. Нужно сверить значение признака в fixture и действующий источник требования. Обязательны две привязанные строки кодов, count=2, переход конкретного товара, права и границы клиента. До выяснения нельзя удалить chip из продукта или отрицательное assertion из теста ради GREEN.

**R8.** `ff-reports` упал на `POST /operations/inbound-intake/{rid}/post` до открытия отчёта. Нужны exact status/body и состояния документа/строк/коробов до/после verify. Main API различает `not_verified`, `already_posted`, `lines_missing_storage`, `actual_missing`, `nothing_to_receive`; `post.ok() == false` не выбирает причину. Main `post_all_remaining` требует сортировку, непринятый остаток строк и назначенное место, отличное от сортировки. Это основание проверить fixture, не доказанная причина конкретного run. Причина и допустимая коррекция **OPEN**. Корректная приёмка даёт ровно один приход 6 по реальному документу и согласованный отчёт/остаток; повтор не создаёт второе движение. Нельзя принимать любой не-2xx, пропускать post или искусственно вписать движение вместо проведения.

**R9.** Коррекция тестов/fixtures оформляется отдельным контрактом до реализации: исходный отказ и отрицательные контроли потери прав, данных, количества или действия. Бизнес-assertions сохраняются либо явно трассируются к принятому заменяющему контракту. Protected exact pairs, SOURCE/validator hash и process proof обновляются по WMS-652; эта задача не даёт исключения для будущих произвольных тестовых/guard edits.

**R10.** После целевых локальных проверок обязательны независимое ревью, аналитическая приёмка и полный CI exact итогового SHA. SOURCE/pin/process proof проверяются отдельно. Ruff PASS и десять локальных E2E PASS не разрешают merge #408, не закрывают proof #405, успешную цель WMS-652 10–15 минут, deploy или операторскую приёмку.

Полный CI, успешная длительность WMS-652, protected SOURCE/validator hash/process proof, deploy и операторские проверки остаются OPEN.
