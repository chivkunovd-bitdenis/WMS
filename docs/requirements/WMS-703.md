## Требования

**R1.** Исправить только исходные 166 Ruff diagnostics и десять E2E случаев ниже. До правки сохранить воспроизводимый baseline: exact SHA, версии инструментов, полный `path:line:column/code`. Расхождение нового baseline объяснить по исходному diff; не расширять задачу в общую чистку, не удалять пути/тесты из discovery/CI.

**R2.** Ruff исправляется без изменения результата бизнес-операций. Сохранить русские строки, коды ошибок, значения fixtures и побочные эффекты импортов/вызовов. E712 требует эквивалентного SQLAlchemy predicate, не Python truthiness столбца; F841/RUF059 не разрешают удалить выполнявшийся вызов вместе с неиспользуемым результатом. Не применять массовый unsafe fix, глобальные ignore/exclude или отключение Ruff. Адресное подавление неоднозначных русских букв допустимо только с обоснованием конкретного исходного русского текста, без общего waiver.

**R3.** Отказы в `auth-dual-portal-sessions` и `ff-staff-users` защищают отсутствие доступа/данных/действий чужого портала и разделение FF/seller сессий. Если есть только FF сессия, действующий экран показывает «Нет доступа», объяснение отсутствия seller сессии и «Войти как селлер»; старое буквальное предложение не требует вернуть тупик. Отказ при существующей seller сессии без права остаётся отдельным случаем. Нельзя заменить все проверки отказов одним общим locator.

**R4.** Сопоставление склада и включение публикации — разные действия. После выбора WMS-склада при выключенной передаче ожидается «публикация выключена», до toggle внешний sync не запускается. Затем проверить связь, включение, sync/status и изоляцию выбранного склада; не включать публикацию автоматически ради старого «готов к публикации».

**R5.** Каталог/приёмка используют действующие «Артикул продавца», SKU, ШК, размер, фактический остаток и действия. Старые обязательные `WB/nmId`, «Артикул WB», `FBS-пул`, «Публикация WB» и запреты остатков/фильтров трассируются отдельно от проверки значений. NmId `123456789` из XLSX должен сохраниться в настоящем продукте/API/карточке: отсутствие в основной строке не доказывает потерю импорта. Коррекция теста сохраняет проверку imported nmId, упаковки, вариантов/ШК и числа строк через действующий источник; удалить assertion без замены нельзя.

**R6.** Для проверенного baseline PR408 main `ac6c92bb5c8bd346a748690d868185c3eab397ed` E9 использует seller-catalog selectors: после приёмки сверяет `На ФФ=10`, `В ячейках=10`, `Свободный FBO=10`, а после MP-плана следующий picker показывает `6`. `wb_nm_id=424242` проверяется отдельно по авторизованному `GET /products` для того же `productId`; seller-строка его не обязана показывать. Экран селлера показывает остаток и резервы только для чтения. E10 выполняет CRUD только для поддерживаемых reserve directions пользователем FF на `/app/ff/products`; payload сохраняет `is_fbs=false`, отдельный редактор/checkbox `is_fbs` не вводится. После FF CRUD сценарий входит в seller account, открывает read-only reserve panel и сверяет остаток направления 4/free FBO 6; кнопок редактирования/удаления у селлера нет. Старые seller publication/status/toggle assertions не относятся к текущему main baseline; это покрытие сверяется отдельно по WMS-670/PR405. E2 проверяет текущую привязку склада и ручную синхронизацию; считать E2 эквивалентом WMS-670 нельзя. Для обеих проверок тестировщик связывает каждое прежнее ожидание с действующим источником/selector или принятым заменяющим контрактом; первая упавшая строка не подтверждает остальные шаги.

**R7.** Решение закрыто аналитиком 08.10.2026 по принятому WMS-669 R5: `requires_honest_sign=true` означает, что в строке товара должен быть виден отдельный статус «ЧЗ» и действие; отдельная иконка показывает число привязанных кодов. E4 должен проверять ровно один видимый `ff-honest-sign-status-${productId}`, две реальные строки кодов, count=2, переход в карточку именно этого товара, а также тестовый контекст доступа/клиента. Нельзя слить chip и счётчик в одну проверку.

**R8.** В исходном E2E CI упало `post.ok()` на `POST /operations/inbound-intake/{rid}/post`; run не содержит status/body и состояний документа/строк/коробов, поэтому историческая причина **OPEN**. Read-only source audit выявил вероятное предусловие: исходный helper не назначает строке ячейку, а `post_all_remaining` по коду требует назначенное место того же склада, не являющееся сортировкой; ожидаемый source-path — `422 lines_missing_storage`, но это не результат исходного run. Для test-first корректная положительная приёмка должна назначить строке реальную non-sorting ячейку этого же склада через действующий PATCH API до проведения, проверить пустые движения до verify, один приход `inbound_intake +6` после verify, завершённое состояние/posted_qty после putaway, отчёт `Приёмка=6/net=6` и повтор `POST` без второго прихода. В тесте фиксируется ожидаемый повторный ответ `409 already_posted` по действующему API-контракту; этот новый позитивный сценарий не переписывает исторический ответ исходного CI.

**R9.** Коррекция тестов/fixtures оформляется отдельным контрактом до реализации: исходный отказ и отрицательные контроли потери прав, данных, количества или действия. Бизнес-assertions сохраняются либо явно трассируются к принятому заменяющему контракту. Protected exact pairs, SOURCE/validator hash и process proof обновляются по WMS-652; эта задача не даёт исключения для будущих произвольных тестовых/guard edits.

**R10.** После целевых локальных проверок обязательны независимое ревью, аналитическая приёмка и полный CI exact итогового SHA. SOURCE/pin/process proof проверяются отдельно. Ruff PASS и десять локальных E2E PASS не разрешают merge #408, не закрывают proof #405, успешную цель WMS-652 10–15 минут, deploy или операторскую приёмку.

## Заключение

WMS-703 зарегистрирована как ограниченная коррекция baseline CI: 166 Ruff diagnostics и десять E2E failures привязаны к точным источникам. Test-first guard и уточнённые E9/E10 E2E assertions фиксируются до продуктовых исправлений: E9 отделяет API-проверку nmId от seller-catalog строки, E10 оставляет FF reserve CRUD в поддерживаемом FF-контексте и отдельно доказывает read-only seller view. Mutation controls, Ruff и py_compile проходят; основной audit остаётся ожидаемо RED по невыполненным маркерам E1–E8, E9/E10 проходят контракт. Семантика chip закрыта аналитиком по WMS-669 R5.
