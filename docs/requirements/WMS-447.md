# WMS-447 — Количество коробов FBS в отчёте «Расчёты»

## 1. Исходный запрос и уточнения

Поручение владельца 14.09.2026, дословно:

> и возьми новую задачу - надо считать ещё кол-во коробов при отгрузках по ФБС
> ьез лишнего говна и лишних сушностей, минималичтисчно
> сколько в проведённых отгрзках короболв, столько и считаем
> эту цифру выводим в отчёт расчёты - там делаем отлельный квалртаи точно такой же как и кол-во заказов фбс отгруженных и в нём кол-во коробов по фбс за период будет указано
> ну и задним числом надо прогрузить все эти кол-ва

**Повод** (тот же день, тот же чат). Владелец спросил: «кол-во коробов по фбс: ИП Фадин с 5.09.26 по 13.09.26, ИП Машнин с начала работы фбс по 13.09». Ведущий агент посчитал по боевой базе (только чтение, 14.09.2026): ИП Фадин — 55 проведённых поставок, 63 короба; ИП Машнин — 30 поставок (первая проведена 25.08.2026), 31 короб. Эти цифры — ориентир для приёмки: после реализации отчёт за те же периоды должен показывать те же числа (см. C11). Аналитик эти цифры на бою не перепроверял — они приведены как сообщённые ведущим.

**Уточнения ведущего при передаче задачи аналитику (14.09.2026):** правило владельца «не плодить сущностей; одно число — один источник» действует; «задним числом прогрузить» — требование к результату (история должна быть видна за прошлые периоды), а не обязательно к механизму; выбор реализационного подхода — за аналитиком по навыку принятия решения. Уточнений от самого владельца после исходной реплики не было.

### 2.2. Откуда берётся «Отгружено FBS» сейчас

Карточка «Отгружено FBS» рисуется из ответа `GET /api/billing/seller-report/summary` (параметры `date_from`, `date_to`, `include_finance`, необязательный `seller_id`; роут `backend/app/api/billing.py`, права `require_fulfillment_admin`), поле `totals.fbs_items` (схема `backend/app/api/billing_seller_report_schemas.py`, класс `SellerReportPhysicalTotals`, значение по умолчанию 0). Считает его `backend/app/services/billing_seller_report_service.py`: `_natural_totals` суммирует `item_quantity` строк отчёта с `service_code == "fbs_order"`. Строки для WB строит `_fbs_handed_entries` — по заказам `FbsOrder`, у которых есть подтверждённая передача (`confirmed_order_handover_dates` в `backend/app/services/fbs_order_billing_service.py`: момент — `FbsSupply.delivered_at` поставки заказа либо `confirmed_at` подтверждённой операции `supply_deliver`); импортированный из WB статус заказа передачей не считается (правило WMS-406). Строки для Ozon приходят из `_operation_entries` — факты `OperationFact` с `document_type == "fbs_order"` и `marketplace == "ozon"`, которые пишет `record_fbs_order_confirmed` в момент проведения. Период — московские сутки через `moscow_interval` (не больше 365 дней, не позже сегодняшнего дня).

То есть «Отгружено FBS» — это штуки заказов, отнесённые к периоду по моменту проведения поставки. Число коробов должно ложиться в тот же период тем же способом (см. D3).

### 2.3. Что такое короб FBS и проведённая поставка — по коду

**Короб** — строка таблицы `fbs_packing_boxes` (модель `backend/app/models/fbs_packing_box.py`: `tenant_id`, `supply_id`, `warehouse_box_id`, `trbx_id` nullable, `box_number`, `created_without_distribution`). Оператор создаёт короба во вкладке «Короба» рабочего пространства поставки (`frontend/src/screens/v2/FfFbsSupplyWorkspace.tsx` → `createFbsPackingBoxes` → `POST /operations/fbs-supplies/{id}/boxes`), сервис `backend/app/services/fbs_packing_box_service.py::create_boxes`. Для WB под каждый короб дополнительно регистрируется грузоместо WB — строка `fbs_trbxes` (`_link_or_create_cargo_places`), для Ozon короб только локальный. Веб-интерфейс сейчас создаёт короба только этим путём; старый API грузомест `POST/DELETE /operations/fbs-supplies/{id}/cargo-places` во фронте вызывается только на чтение (`fetchFbsCargoPlaces` в `FfFbsOrdersScreen.tsx`).

После проведения поставки короба неизменяемы: `create_boxes`, `delete_box`, `assign_orders`, `remove_order`, `clear_box`, `set_boxes_without_distribution` вызывают `_assert_supply_mutable`, который отвергает статусы `in_delivery` и `done` ошибкой `supply_not_editable`. Эндпоинта удаления поставки нет (`backend/app/api/fbs_supplies.py` содержит только удаление короба и заказа из короба). Значит, состав коробов проведённой поставки стабилен и его можно считать по факту в любой момент.

Отсутствие коробов передачу не запрещает: в preflight передачи проверка `physical_boxes_required` («В поставке пока нет коробов») — мягкая (`backend/app/services/fbs_shipment_service.py`, ~строка 830). Поставку можно провести и с нулём коробов.

**Проведённая поставка** — `FbsSupply` (`backend/app/models/fbs_supply.py`) с заполненным `delivered_at`. Во всём коде приложения это поле присваивается в одном месте — `fbs_shipment_service._apply_local_delivered` (строки 1209–1211): `supply.status = in_delivery`, `supply.delivered_at = now`, затем начисление по заказам. Через эту функцию проходят и WB, и Ozon (`_persist_confirmed_delivery`). Статус `done` сам по себе передачей не является: `fbs_tracking_service` ставит `done` по флагу WB `supply.done` при синхронизации, `delivered_at` при этом не трогает — так выглядит поставка, проведённая в кабинете WB мимо WMS. Другие сервисы уже трактуют «проведена» именно как `delivered_at is not None` (`fbs_assembly_time_service.py`, `fbs_cancelled_after_pack_service.py`, `cli/reconcile_fbs_unlinked_shipments.py`).

### 2.4. Границы данных (по коду и по сообщённым ведущим фактам боя)

Таблица `fbs_packing_boxes` появилась миграцией `backend/alembic/versions/20260806_0073_fbs_local_packing_boxes.py`; переноса данных в старые поставки в миграции нет (проверено чтением). Грузоместа `fbs_trbxes` — миграция `20260730_0066_fbs_trbx.py`. Поставки, проведённые до появления таблицы коробов, коробов не имеют — для них число будет 0, и это отсутствие данных, а не ошибка расчёта.

Ведущий сообщил по бою (только чтение, 14.09): у ИП Фадин за 05.09–13.09 все 55 проведённых поставок с коробами; отдельно есть поставка `source=wb`, `status=done` без `delivered_at` и без коробов (проведена в кабинете WB, не через WMS); две поставки от 29.08 (`WB-GI-270967044`, `WB-GI-270968333`) имеют по 1 коробу при 2 грузоместах WB — вне периода вопроса, но показывает, что `fbs_packing_boxes` и `fbs_trbxes` могут расходиться. У ИП Машнин все 31 поставка проведены через WMS, короба равны грузоместам. Второй селлер с именем «ИП Фадин» (tenant «ИП Львова В.В.») поставок не имеет.

### 2.5. Цель изменения

После изменения администратор на той же вкладке «Селлеры» видит ещё одну карточку — число коробов FBS, проведённых за выбранный период по выбранному селлеру, — рядом с «Отгружено FBS» и в том же виде. Число верно за любой прошлый период, за который в системе есть короба. Ничего другого на экране не меняется.

## 3. Решения аналитика

Развилок с разным бизнес-результатом, требующих вопроса владельцу, не найдено; решения ниже приняты по навыку принятия решения в границах запроса. Они отделены от слов владельца.

**D1. Что считается коробом.** Короб — строка `fbs_packing_boxes`. Это единый источник для WB и Ozon, именно эти короба оператор создаёт и наполняет в WMS, и именно их состав фиксируется при проведении. Грузоместа WB (`fbs_trbxes`) вторым источником не используются: их нет у Ozon, а на бою уже есть поставки, где грузомест больше, чем коробов, — считать «по коробам, а если разошлось, то по грузоместам» значило бы завести второй источник одной величины. Следствие: у двух поставок ИП Фадин от 29.08 отчёт покажет по одному коробу. Признак «короба созданы без распределения» на счёт не влияет — короб есть короб.

**D2. Что считается проведённой отгрузкой.** Поставка с заполненным `delivered_at`. Это единственный след передачи через WMS, он один и тот же для WB и Ozon и уже используется соседними сервисами в этом смысле. Статус отдельно не проверяется: `delivered_at` появляется только при проведении, а `done` из синхронизации WB без `delivered_at` передачей через WMS не является (у такой поставки в WMS и коробов нет). Это согласуется с тем, как «Отгружено FBS» отбрасывает импортированные статусы.

**D3. По какой дате поставка попадает в период.** По `delivered_at`, в московских сутках того же `moscow_interval`, что и вся сводка. Так число коробов ложится в тот же период, что и штуки «Отгружено FBS» по тем же поставкам: в `_apply_local_delivered` одно и то же значение `now` записывается в `delivered_at` поставки и передаётся как момент передачи в начисление по заказам (`charge_handed_over_orders` → `record_fbs_order_confirmed`), а `confirmed_order_handover_dates` для WB читает именно `delivered_at` поставки (либо `confirmed_at` подтверждённой операции, которое в штатном пути равно тому же значению). Дата создания короба и даты заказов не используются: короб может быть создан накануне отгрузки, а заказ — за несколько дней до неё.

**D4. Маркетплейс.** Одно число по WB и Ozon вместе, без разреза по площадкам. Владелец просит карточку «точно такую же», как «Отгружено FBS», а та суммирует обе площадки; короб — физический предмет, одинаковый для площадок. Правило AGENTS.md о явном обозначении площадки касается данных товаров и заказов, где принадлежность меняет понимание; у итогового числа коробов за период такой зависимости нет. Разрез по площадкам не вводится.

**D5. «Задним числом прогрузить».** Трактуется как требование к результату: отчёт показывает верное число коробов за любой прошлый период по уже хранимым `fbs_supplies` и `fbs_packing_boxes`. Отдельная разовая прогрузка (миграция данных, скрипт, новая колонка-счётчик, журнал) не нужна и запрещена правилом «одно число — один источник»: число вычисляется из существующих таблиц при каждом запросе, как и остальные показатели полосы. Граница: поставки, проведённые до миграции `20260806_0073`, дадут 0 коробов — это зафиксированная граница данных, а не дефект реализации.

**D6. Где и как показать.** Одна карточка «Коробов FBS» в существующей полосе `ReportMetricStrip`, сразу после «Отгружено FBS» и перед «Хранение», тем же компонентом и с той же единицей «шт.» (подпись построена по образцу «Селлеров»: капитель, родительный падеж). Никаких новых экранов, окон, чипов, подсказок и колонок в таблице селлеров. Значение приходит в том же ответе сводки `GET /billing/seller-report/summary` (в `totals`), чтобы карточка грузилась и показывала скелет вместе с соседями; отдельный запрос, как у «Хранения», не нужен — расчёт лёгкий (один агрегат по двум таблицам).

**D7. Фильтр селлера и ноль.** Карточка подчиняется тому же фильтру селлера и периода, что и вся сводка. Ноль показывается как «0 шт.», как у соседних карточек; никаких «—», подсказок и объяснений. Ошибка загрузки сводки обрабатывается существующим уведомлением экрана, отдельного поведения у карточки нет.

**D8. Что не входит в задачу.** Не меняются: расчёт «Отгружено FBS» и других карточек, таблица селлеров и её раскрытие, счета, права доступа, процесс создания и проведения поставок, экраны FBS. Не вводятся новые таблицы, колонки, статусы, журналы, фоновые задачи, миграции. Разрез коробов по селлерам в таблице, по площадкам и по дням — не просили, не делаем.
