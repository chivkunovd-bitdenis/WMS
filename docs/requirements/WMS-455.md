# WMS-455 — «Общая корзинка»: весь свободный остаток в оба кабинета у товара на двух площадках

Ветка feat/wms453-455-boxes-shared-pool от origin/etalon 388f389b (то, что стоит на проде
после ночного выпуска WMS-454/456/457). Документ подготовлен аналитиком 17.09.2026 по навыку
постановки и приёмки. Соседняя задача той же ветки — WMS-453 (деление позиции Ozon по коробам),
она этого окна и расчёта не касается.

## 1. Исходный запрос и уточнения

Владелец, 17.09.2026, дословно (опечатки сохранены):

> WMS-455 — «общая корзинка» ждёт вашего решения; сейчас сумма долей ≤ 100%.
> тут просто нужна кнпока котоорая будет делать так:
> текущий остаток публикуется сразу и в озон и в вб
> и у них просто одна корзинка
> пришли 100 заказов озон - ушли в озон, пришли 200 на вб - ушли на вб
> то есть каждое движение товара моментально обновляет  остаток товар и в озон и в вб
> актуально только  для тех товаров которые по 2 маркетам
> то есть вообще ты на фронре не выставляешь пулы, просто все ебашит из одной корзинки

Контекст запроса — вопрос владельца от 16.09.2026 из карточки WMS-455:

> что будет, если мы поставим сотку и там, и там? Есть ли у нас возможность вообще расходовать
> неравномерно этот лимит, и у нас есть тысячи товаров. Пускай сыпятся заказы по WB: пришло
> 700 — взяли оттуда. Пришло по Ozon 200 — взяли оттуда. То есть не задавая этот лимит
> использовать их в общую корзинку

Что этим запросом отменяется. Постановка WMS-350 от 05.09.2026 говорила: «сумма по всем
складам и всем маркетплейсам не больше ста процентов». Для товаров на двух площадках владелец
этим запросом вводит другой режим — без долей, всё из одной корзинки. Для остальных товаров
и для товаров, у которых этот режим не включён, правило WMS-350 остаётся как есть: владелец
говорит «актуально только для тех товаров которые по 2 маркетам» и «кнопка», то есть
включаемый режим, а не замена формулы всем.

Владелец недоступен для вопросов до конца работы. Одна развилка, где варианты дают разный
бизнес-результат (несколько складов одной площадки у продавца), зафиксирована вопросом в
разделе 4; выбран вариант, наиболее буквально следующий словам «одна корзинка… не выставляешь
пулы», и это явно помечено как решение аналитика.

## 2. Существующий процесс и цель изменения

Кто и где. Администратор фулфилмента в «Каталоге» (/app/ff/products) нажимает в строке товара
значок «Остаток для FBS <SKU>» либо выделяет несколько товаров одного продавца и нажимает
«Задать остаток · N». Открывается окно «Остаток для FBS» (компонент
frontend/src/screens/ff/products-fbs/FbsStockDialog.tsx, данные для него собирает
fbsStockDialogLoader.ts, сохраняет FfProductsCatalogScreen.tsx через PUT /products/fbs-rule).
Второй путь к тому же окну — маршрут /app/ff/fbs-stock (FfProductsFbsPage → ProductsScreen), в
меню его нет. Объект окна — правило публикации остатка товара (или пачки товаров одного
продавца).

Как правило устроено сейчас (проверено чтением кода ветки 17.09.2026):

- Правило товара — поля products.fbs_stock_sync_enabled (галка WB), fbs_ozon_stock_sync_enabled
  (галка Ozon, NULL наследует WB), fbs_same_everywhere, fbs_percent, fbs_units_mode и пулы
  fbs_binding_stock_pools (percent и quantity по каждой привязке продавца). В сервисе
  backend/app/services/fbs_stock_rule_service.py это класс FbsRule (publish, publish_ozon,
  same_everywhere, percent, by_warehouse, units_mode, units_by_warehouse). Все эти поля
  описывают одно: как разделить ОДНИ сто процентов свободного остатка между направлениями.
  Поля «не делить, отдать всем всё» нет.
- validate_rule считает сумму долей по всем обслуживаемым публикующим привязкам ОБЕИХ площадок
  (при «одинаково» — доля умножается на число привязок) и отказывает выше 100 с текстом
  «В сумме по складам получается N% свободного остатка, а он у складов общий — больше 100%
  отдать нельзя». В режиме штук _validate_units отказывает, если сумма штук больше свободного.
- split_amounts идёт по привязкам обеих площадок подряд (сортировка по номеру склада) и
  вычитает выданное из общего remaining: вторая площадка получает то, что осталось. Функция
  _seller_bindings специально не фильтрует по площадке, и в её описании сказано, зачем:
  чтобы одну физическую единицу не пообещали двум покупателям. Тест
  test_one_physical_unit_is_never_promised_to_both_marketplaces закрепляет это для обычных
  правил.
- set_rule_for_products берёт замок продавца по обеим площадкам, читает старые правила,
  подставляет нетронутые галки, считает «изменённые площадки» по сигнатуре правила, проверяет
  потолок, обнуляет выключенную площадку, включает stock_sync_enabled у обслуживаемых привязок,
  названных правилом (при «одинаково» — у всех обслуживаемых), пишет поля товара и пулы и
  планирует публикацию по изменённым площадкам (schedule_seller_stock_publish).
- publish_amounts_for_binding — единственный источник числа для кабинета: берёт публикующие
  привязки продавца на том же складе WMS, отбирает товары с правилом (_has_rule: в режиме
  долей доля должна быть больше нуля) и раздаёт split_amounts. Его вызывают и WB-публикация
  (fbs_stock_sync_service), и Ozon-публикация (ozon_fbs_sync_service.sync_ozon_stocks).
  Отбор товаров для WB идёт через SQL-предикат product_has_rule_predicate (fbs_percent не
  NULL или режим штук). get_rule_views считает published_now для окна тем же split_amounts
  и складывает по всем публикующим привязкам.
- Эффективная галка Ozon (WMS-456): без активной связки ProductMarketplaceLink с
  marketplace="ozon" товар в Ozon не публикуется, publish_ozon в ответах false, явный true в
  запросе в базу не попадает. Признак связки — тот же, что у значка площадки в строке
  каталога (_marketplaces_by_product в backend/app/api/products.py: «wb» — есть nmID,
  артикул продавца или связка WB; «ozon» — есть активная связка Ozon).

Как публикация запускается после движения товара (проверено кодом):

- backend/app/services/inventory_service.py: update_fbs_order_reservation (резерв и снятие
  резерва заказа WB и Ozon — его вызывают импорт заказов WB и Ozon через _try_reserve_order и
  отмены через _release_reservation) заканчивается вызовом schedule_seller_stock_publish без
  указания площадки; record_movement_and_adjust_balance (единственная точка изменения
  остатка: приёмка, списание, инвентаризация, перемещение, отгрузка) — тоже. Аналогично
  stock_direction_service (направления) и marketplace_unload_service (отгрузка на
  маркетплейс).
- backend/app/services/fbs_stock_publish_service.py: намерение копится в сессии и уходит после
  коммита; publish_seller_stocks_now без площадки берёт все цели продавца из
  list_marketplace_poll_targets — WB (продавец с ключом WB и хотя бы одной активной
  обслуживаемой WB-привязкой) и Ozon (активный MarketplaceAccount с ключом) — и публикует по
  каждой независимо, под замком продавца по площадке. То есть после резерва заказа любой площадки публикация
  уже сейчас планируется по обеим площадкам.
- Автоопрос заказов — раз в fbs_poll_interval_sec (180 с по умолчанию), сверка стоков — раз
  в fbs_stock_reconcile_interval_sec (300 с) (backend/app/core/settings.py). Заказ на
  площадке становится известен WMS только в момент импорта; до него другая площадка видит
  прежнее число. Это и есть «хвост» из карточки задачи.
- Резерв заказа (update_fbs_order_reservation) проверяет доступность по физическому
  свободному остатку (fbs_available_qty_for_product: на складе минус резервы), от долей она
  не зависит. Но статус not_published выставляется, если у WB-заказа товар без галки WB или
  без fbs_percent, а в режиме штук — если у товара нет пула на складе заказа.

ползунков долей нет, в каждый кабинет уходит весь свободный остаток, каждое движение товара
(резерв заказа любой площадки, приёмка, списание, отмена) сразу даёт обеим площадкам новое
число. Товары без этого режима работают по прежним долям и потолку 100 %.

## 3. Требования

Термины. «Товар на двух площадках» в окне — строка каталога, у которой в поле marketplaces
есть и «wb», и «ozon» (оба значка площадок в строке). На сервере признак режима — «есть
активная связка Ozon» (ProductMarketplaceLink с marketplace="ozon", is_active), тот же, что
решает эффективную галку Ozon в WMS-456. «Публикующее направление» — активная привязка
продавца (склад кабинета WB или Ozon, сопоставленный со складом WMS) с включённой
трансляцией stock_sync_enabled. «Режим» ниже — режим общей корзинки.

R1. Хранение и API. Условие: правило товара читается или сохраняется. Результат: у правила
есть булев признак режима — поле shared_pool в теле PUT /products/{id}/fbs-rule и в rule
для PUT /products/fbs-rule (по умолчанию false, если поле не прислано) и в ответах
GET /products/{id}/fbs-rule и POST /products/fbs-rule/bulk. В базе — одна новая булева
колонка у products (NOT NULL, по умолчанию false, миграция alembic). У всех существующих
товаров после выкладки режим выключен, их правила, published_now и публикация не меняются.
Основание: запрос («кнопка… одна корзинка»); решение аналитика 1 (почему существующих полей
недостаточно).

R2. Кому доступен режим. Условие: в запросе shared_pool=true. Результат: режим сохраняется
включённым только у товара с активной связкой Ozon; у товара без связки в базу пишется
false и в ответах shared_pool=false (тот же приём, что у publish_ozon в WMS-456), остальное
правило такого товара не меняется (см. R4). Если связка Ozon пропала у товара с сохранённым
режимом, режим не действует: в ответах shared_pool=false, товар публикуется по сохранённым
долям или штукам, при следующем сохранении в базу пишется false; если связка появилась
снова до пересохранения — режим действует опять. Основание: «актуально только для тех
товаров которые по 2 маркетам»; решение 3.

R3. Расчёт публикации. Условие: у товара действует режим (R2). Результат: каждое
публикующее направление продавца, чья площадка у товара включена галкой «Передавать
остаток…», получает весь свободный остаток товара на своём складе WMS — то есть публикуемое
число равно min(100 % свободного, свободный) = свободный остаток; доли, штуки и вычитание
«остатка после предыдущего направления» (remaining в split_amounts) не применяются;
направления площадки с выключенной галкой получают 0, как сейчас. Это относится к каждому
складу каждой площадки, в том числе если у продавца несколько складов WB (см. решение 5 и
вопрос владельцу). Товар с действующим режимом считается имеющим правило и попадает в
публикацию, даже если fbs_percent NULL или 0 и штуки не заданы. В ответах API published_now
равен числу, которое уходит в каждое направление: при одном складе WMS — свободному остатку
товара (free_stock); при выключенных обеих галках или отсутствии публикующих направлений —
0. Основание: «текущий остаток публикуется сразу и в озон и в вб… у них просто одна
корзинка»; AGENTS.md — публикуемый остаток min(лимит оператора, свободный остаток), лимит
здесь равен всему свободному; решение 6 (published_now).

R4. Сохранение с включённым режимом. Условие: запрос с shared_pool=true (одиночный или
массовый). Результат: сервер отвечает 200 без проверки потолка «сумма долей ≤ 100 %» и
«сумма штук ≤ свободному» — для товара на двух площадках у любого продавца с любым числом
привязок; поля same_everywhere, percent, by_warehouse, units_mode, units_by_warehouse из
такого запроса НЕ записываются — у каждого товара запроса остаются его прежние доли, режим
штук и пулы; галки publish и publish_ozon обрабатываются как сейчас (прислали — записали,
не прислали — прежние). У товара без связки Ozon в таком запросе меняются только галки
площадок, если присланы. Основание: «на фронте не выставляешь пулы»; решение 4 (массовое
включение не должно затирать индивидуальные доли тысяч товаров).

R5. Включение и выключение → публикация и привязки. Условие: сохранение меняет режим хотя
бы у одного товара запроса (в любую сторону). Результат: сервер планирует публикацию
продавца по каждой площадке, которую хотя бы один товар запроса публикует, и включает
трансляцию (stock_sync_enabled=true) у всех обслуживаемых привязок продавца этих площадок
— как это делает «одинаково по всем складам»; после ответа GET показывает shared_pool=true
и published_now по R3 (для HD-GRY-L на стенде — 100 при 100 свободных вместо 60+40). Если
режим и остальное правило не изменились (повторное сохранение того же), публикация не
планируется и обращений к кабинетам нет (существующее поведение по сигнатуре правила).
Основание: «моментально обновляет остаток и в озон и в вб»; существующий механизм
schedule_seller_stock_publish; failure-cases B10 (повторное сохранение выключенного не
шлёт нули).

R6. Выключение → возврат к долям. Условие: запрос с shared_pool=false у товара, у которого
режим был включён. Результат: режим снимается, поля долей и штук из запроса записываются и
проверяются как при обычном сохранении (потолок 100 % снова действует: 100 %+100 % → 422 с
прежним текстом); published_now снова считается по долям. Окно при выключении галки
показывает те доли и штуки, которые были сохранены у товара до включения режима (они не
затирались, R4), и оператор сохраняет их или правит осознанно. Основание: правило WMS-350
остаётся для товаров без режима; решение 4.

R7. Движения товара. Условие: у товара действует режим; происходит движение, меняющее его
свободный остаток: резерв заказа WB или Ozon при импорте или автоопросе, снятие резерва при
отмене, приёмка, списание, инвентаризация, перемещение, отгрузка, направление. Результат:
как и сейчас, планируется публикация продавца по обеим площадкам, и в каждое публикующее
направление уходит новый свободный остаток (например, 100 свободных, резерв заказа Ozon на
6 → WB и Ozon получают 94; отмена → 100). Набор триггеров, интервалы автоопроса (180 с) и
сверки (300 с) и порядок публикации не меняются. Основание: «каждое движение товара
моментально обновляет остаток товар и в озон и в вб»; проверено кодом (раздел 2).

R8. Резерв заказа в режиме. Условие: у товара действует режим, приходит заказ любой
площадки. Результат: резерв проходит по физическому свободному остатку (reserve_status
reserved при наличии, no_stock при нехватке) независимо от сохранённых долей и штук: статус
not_published для такого товара не выставляется ни из-за fbs_percent NULL, ни из-за режима
штук без пула на складе заказа. Основание: «пришли 100 заказов озон — ушли в озон, пришли
200 на вб — ушли на вб»; AGENTS.md — не добавлять блокировок, которых не просил владелец.

R9. Окно — видимость галки режима. Условие: открыто окно «Остаток для FBS» (каталог, в том
числе массовое «Задать остаток · N», и маршрут /app/ff/fbs-stock). Результат: если хотя бы
у одного выбранного товара обе площадки (marketplaces содержит «wb» и «ozon»), под галками
«Передавать остаток в Wildberries» и «Передавать остаток в Ozon» и над «Остаток по штукам»
показывается галка «Весь свободный остаток в Wildberries и Ozon» (CheckboxInput того же
вида, что «Остаток по штукам»); начальное положение — из shared_pool правила первого товара
(одиночное окно — самого товара). Если таких товаров среди выбранных нет (товар только WB,
только Ozon, пачка без товара на двух площадках), галки нет и окно не отличается от
нынешнего. Основание: «кнопка… актуально только для тех товаров которые по 2 маркетам»;
решение 2 и 3.

R10. Окно — включённый режим. Условие: галка режима включена (в черновике окна). Результат:
под галкой подпись «Доли отключены: в каждый кабинет уходит весь свободный остаток,
продажа на любой площадке уменьшает его на обеих»; галка «Остаток по штукам», ползунок
«Доля свободного остатка» и галка «Одинаково по всем складам» заперты с подписью «Включён
весь свободный остаток в оба кабинета» (существующий приём disabledReason, как при
«Остаток по штукам»); ползунки «Доля на этот склад» и поля «Потолок публикации, шт» под
складами не показываются; текст «Общий лимит долей для обеих площадок — 100%…» заменён
строкой «На каждый склад ниже уходит весь свободный остаток товара»; строка
«Нераспределено…», строка «Задано по складам … шт», красная плашка про 200 % и запрет кнопки
«Сохранить» не появляются ни при каких прежних значениях долей и штук. Галки площадок,
заголовки «Wildberries»/«Ozon», строки складов с галкой «Принимаем заказы продавца со
склада…», чипами и выбором «Склад WMS», блок «N шт» с пояснением, кнопки «Отмена» и
«Сохранить» — как сейчас. При выключенной галке режима под ней подпись «Включите, чтобы
отдавать весь свободный остаток в оба кабинета без долей», остальное окно без изменений.
Новых окон, шагов подтверждения, чипов и других элементов нет. Основание: «вообще ты на
фронте не выставляешь пулы»; AGENTS.md — существующие компоненты и дизайн, без лишних
элементов; решение 2.

R11. Окно — сохранение и повторное открытие. Условие: оператор нажимает «Сохранить». Результат:
в теле правила уходит shared_pool (true или false по галке) вместе с остальными полями;
publish и publish_ozon — по прежнему правилу «только если трогали в этом открытии». При
ответе 200 окно закрывается, каталог перечитывается; повторное открытие показывает галку
режима включённой, запертые ползунки, строки складов и блок «N шт», равный свободному
остатку (100 для HD-GRY-L). При отказе сервера (4xx/5xx) или обрыве ответа ошибка
показывается плашкой внутри окна, окно остаётся открытым, положение галки и остальное
введённое не теряются; повтор после восстановления проходит. Основание: существующее
поведение окна; failure-cases B05 (ошибка видна в самом окне), B10 (потеря ответа не
считается успехом).

R12. Массовое применение. Условие: оператор выделил несколько товаров одного продавца
(например, фильтром «Маркетплейс: Ozon» и галкой «выбрать все»), нажал «Задать остаток · N»,
включил галку режима, «Сохранить». Результат: один PUT /products/fbs-rule с product_ids
пачки и rule.shared_pool=true; у всех товаров пачки со связкой Ozon режим включён (R2), их
доли, штуки и пулы не затронуты (R4); у товаров пачки без связки Ozon (если попали) режим
false и правило не изменилось, кроме тронутых галок площадок; ответ 200, публикация
запланирована по R5. Массовое выключение — тем же окном с выключенной галкой: у всех
товаров пачки записываются присланные доли (существующее поведение пачки) и проверяется
потолок. Основание: «у нас тысячи товаров» (16.09.2026); существующее массовое окно, новых
экранов нет.

R13. Соседние процессы. Условие: изменения выпущены. Результат: у товаров без режима (в том
числе того же продавца и в той же пачке) validate_rule, split_amounts, published_now,
публикация и резерв работают как раньше; товар только WB и товар только Ozon, второй
продавец, режим «по штукам», обычные доли, галки площадок (WMS-351), скрытие Ozon у
WB-товара (WMS-454), эффективная галка Ozon (WMS-456), подписи складов (WMS-457) не
меняются; тест test_one_physical_unit_is_never_promised_to_both_marketplaces остаётся
зелёным для обычных правил. Основание: AGENTS.md, раздел 3 (сохранять дизайн и соседние
процессы, менять только в объёме задачи).

## 4. Решения аналитика и оставшиеся вопросы

Решение 1 — новое поле правила, а не комбинация существующих. Все существующие поля (доля,
«одинаково», доли по складам, режим штук, штуки по складам) отвечают на вопрос «как
разделить одни сто процентов». Единственная комбинация, похожая на «всем всё» —
«одинаково» + 100 % — сегодня сервером отвергается при двух и более привязках, а при одной
привязке означает обычные 100 % на неё. Если сделать эту комбинацию режимом, то (а) её
нельзя будет отличить от обычных 100 % у товара только WB с двумя складами WB, чего владелец
не просил, и (б) товар со 100 % «одинаково» на одной привязке начал бы отдавать всё и на
вторую привязку в тот момент, когда её включат по другому товару, — молча. Поэтому признак
хранится отдельной булевой колонкой у товара. Это не дублирование вычисляемой величины
(AGENTS.md, раздел 3): режим — выбор оператора, а не производное от других полей. Имя поля
в API — shared_pool (совпадает с названием ветки), имя колонки — на усмотрение
исполнителя.

Решение 2 — где живёт «кнопка» и как выглядит. Владелец говорит «кнопка», но в этом окне
режимы уже представлены галками CheckboxInput с подписью-подсказкой («Остаток по штукам»,
«Одинаково по всем складам»), и соседние настройки при включённом режиме запираются с
причиной. По плохому случаю 1 из библиотеки (действие вынесли из контекста документа)
режим должен жить там, где оператор настраивает остаток этого товара — в окне «Остаток для
FBS», а не отдельной кнопкой в строке каталога или в новом экране. Отдельная кнопка «в
строке» дала бы второй путь к тому же правилу и разошлась бы с окном (failure-cases B08:
множество затронутых площадок разошлось между путями). Поэтому — галка в окне, сразу под
галками площадок: она относится к обеим и логически читается после них («передавать в WB,
передавать в Ozon, весь остаток в оба»). Подписи взяты в стиле соседних; повествовательных
подсказок сверх того, что уже есть у «Остаток по штукам», не добавляется; строка «Общий
лимит долей…» не дублируется, а заменяется. Эталоны «Ячейки» и «Инвентаризация» просмотрены
— те же компоненты и тон.

Решение 3 — только товары на двух площадках. В окне признак берётся из marketplaces строки
каталога (оба значка), чтобы окно и значок не разошлись. На сервере такого предиката «WB и
Ozon вместе» в сервисе правил нет, а есть готовый признак связки Ozon из WMS-456; он и
используется: без связки Ozon режим в базу не попадает, со связкой — сохраняется. Отсюда
маленькая асимметрия: товар только с картой Ozon (без WB), попавший в пачку вместе с
товаром на двух площадках, тоже получит режим — для него это означает «весь свободный
остаток в Ozon», WB-публикация такой товар и так пропускает (нет wb_chrt_id,
_build_publish_plan → skipped_missing). Вреда нет, отдельного запрета не вводится. Пропажа
связки Ozon (разъединение карточек) переводит товар на сохранённые доли — тот же принцип,
что у эффективной галки Ozon в WMS-456; оператор увидит обычное окно с прежними долями.

Решение 4 — включение режима не трогает доли и штуки. Главный сценарий владельца —
массовый («тысячи товаров»). Массовое окно сегодня применяет черновик первого товара ко
всей пачке; если при включении режима записывать ещё и доли, тысячи индивидуальных
раскладок затёрлись бы долями первого товара, и выключение режима стало бы разрушительным.
Поэтому при shared_pool=true сервер записывает только сам режим и тронутые галки площадок, а
при выключении доли из запроса записываются как обычно — оператор их в этот момент видит.
Следствие для исполнителя: признак «у товара есть правило» (_has_rule и
product_has_rule_predicate) должен учитывать режим, иначе товар без прежней доли (fbs_percent
NULL, как TS-WHT-M-OZ на стенде) не попадёт в публикацию.

Решение 5 — несколько складов одной площадки (вопрос владельцу). Слова «одна корзинка…
не выставляешь пулы, просто всё из одной корзинки» прочитаны буквально: долей нет вообще,
и каждое направление каждой площадки видит всю корзинку. У продавца с двумя складами WB и
одним Ozon все три получают весь свободный остаток; после любой продажи все три получают
новое число. Альтернатива — считать 100 % на площадку, но внутри площадки делить по
прежним долям складов — сохранила бы ползунки внутри WB, то есть «пулы» остались бы, и
противоречит «не выставляешь пулы». Бизнес-результат вариантов различается только у
продавцов с несколькими складами одной площадки, поэтому это вынесено в вопрос владельцу
(В1), а до ответа действует буквальное прочтение.

Решение 6 — что показывает «N шт». published_now по сложению амплитуд направлений дал бы
«200 шт» при 100 свободных и был бы ложью про остаток. В режиме число окна — то, что
уходит в каждый кабинет, то есть свободный остаток. Подпись под числом («Расчёт публикации
по сохранённому правилу…») остаётся.

Решение 7 — галки площадок режим не трогает. Режим говорит «без долей», а куда публиковать
— по-прежнему решают галки «Передавать остаток в Wildberries/Ozon» (WMS-351: изменение
одной площадки не включает другую). Если у товара выключена одна из галок, режим даёт
100 % только включённой площадке; галки стоят прямо над режимом, оператор их видит.

Решение 8 — хвостовой риск принят, блокировок нет. Заказ на одной площадке становится
известен WMS при импорте (автоопрос до 180 с), до этого вторая площадка видит прежнее число
и на последних единицах возможна перепродажа. Владелец описал именно такую работу («пришли
100 заказов озон — ушли в озон…») и знал про ограничение из карточки задачи; никаких
проверок «а вдруг продадут дважды», задержек и подтверждений не вводится (плохой случай 2
— самодельный запрет).

Вопрос владельцу В1 (не блокирует реализацию, действует решение 5): у продавца с
несколькими складами одной площадки (например, два склада WB и один Ozon) в режиме
«общая корзинка» каждый склад WB должен видеть весь свободный остаток (как выбрано), или
внутри WB остаток по-прежнему делится долями складов, а 100 % считаются на площадку?

Других вопросов нет.

## 6. Сверка запроса с требованиями

«нужна кнопка которая будет делать так» → R9 (галка режима в окне остатка), R11 (сохранение
одной галкой), решение 2 (почему галка, а не кнопка в строке). «текущий остаток публикуется
сразу и в озон и в вб / у них просто одна корзинка» → R3 (каждое направление получает весь
свободный остаток), R5 (после включения публикация по обеим площадкам). «пришли 100 заказов
озон — ушли в озон, пришли 200 на вб — ушли на вб» → R8 (резерв по свободному остатку без
статуса not_published), R7 (после резерва обе площадки получают новое число). «каждое
движение товара моментально обновляет остаток и в озон и в вб» → R7 (триггеры и публикация
по обеим площадкам; интервалы не меняются). «актуально только для тех товаров которые по 2
маркетам» → R2 (сервер: связка Ozon), R9 (окно: оба значка), решение 3. «вообще ты на фронте
не выставляешь пулы, просто всё из одной корзинки» → R10 (ползунки долей и штук не
показываются, потолок не считается), R4 (сервер не проверяет и не записывает доли). Вопрос
16.09 «сотку и там, и там… у нас тысячи товаров» → R4/R12 (массовое включение существующим
окном без затирания долей). Карточка задачи (хвостовой риск) → решение 8, без блокировок.

Обратная сверка: R1 — основание в самом запросе (нужен признак режима) и решении 1; R6 —
постановка WMS-350 остаётся для товаров без режима (владелец её не отменял целиком); R13 —
AGENTS.md, раздел 3. Ни одно требование не добавляет запретов, подтверждений или задержек,
которых владелец не просил; единственная «проверка» (R2: без связки Ozon режим не пишется)
не запрещает оператору ничего — окно у такого товара галку и не показывает, а API
возвращает 200.

Что не входит в задачу: изменение формулы для товаров без режима, автоматическое
включение режима у новых объединённых карточек, новые фильтры каталога (например «на двух
площадках»), изменение интервалов автоопроса и сверки, поведение при нескольких складах
WMS у продавца сверх описанного в R3, WMS-453.
