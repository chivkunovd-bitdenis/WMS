## Существующий процесс и цель

Оператор создал поставку в WMS, завершил внешний шаг в кабинете, а WMS получает
статусы. Сейчас WB `link_confirmed_orders_to_wb_supplies` может выставить `done`,
а `_apply_wb_status_to_order` — снять резерв по sold без списания. Ozon `_apply_status`
также снимает резерв в терминальных состояниях, но не проводит отгрузку.
`sync_ozon_order_statuses` вообще исключает локально завершённые заказы из опроса.
Поэтому одного вызова в ветке «статус изменился» недостаточно для восстановления.

Штатная локальная сдача использует `_write_off_delivered_orders_once`, журнал
`FbsShipmentReversalLedger` (далее ledger — существующая запись списания заказа),
движения склада и снятие резерва. Цель — выполнить ту же локальную часть для
точно подтверждённого состава, без второй внешней сдачи и без нового документа.

## Решения аналитика и технические границы

1. Регистрация новой WMS-662 обоснована отменой прежнего поведения и новым точным
   предметом; чужие действующие требования не меняются. Это не разрешение на
   адресный ремонт Бамбука: его актуальная область пока недоступна.
2. Частичная поставка использует существующий документ и результаты заказов.
   Для Ozon разделённого заказа сохраняются реальные posting_number и связи
   существующих FbsOrderProduct; ledger.ozon_positions_json уже хранит количество
   и movement_id по источникам. Частичная запись должна различать проведённые
   количества по этим существующим связям. Новая таблица не требуется.
3. Нынешние `write_off_order` и `_finish_ozon_delivery` **не готовы к частичному
   составу**: первый считает ненулевой shipment_movement_id завершением целого
   заказа, второй заново загружает все заказы поставки. Нельзя просто передать
   подсписок в них и объявить R3/R4 выполненными. Тестировщик фиксирует это до кода.
4. Выбор источника по всему остатку нельзя повторять для уже проведённой части.
   При concurrent callbacks блокируются supply → orders → ledger/stock по
   существующему порядку; HTTP выполняется вне этих DB-блокировок, затем состояние
   перечитывается. Полнота проведения выводится из движений и количеств, не из
   нового независимого флага.
5. Восстановление не вызывает упаковочный preflight как разрешение заново отправить
   груз. Подтверждённая передача уже произошла; недостающий локальный учёт чинится
   существующим процессом, а ошибки источника сохраняются для продолжения.
6. G1 остаётся технической границей: автоматическое признание внешнего formed
   без checkpoint не определено доступной официальной response-схемой. До
   подтверждения оно имеет результат «не установлено», не автоматический отказ
   оператора и не успех. Положительные строки по карточкам заказов уже пригодны для тестов.
7. G4: `/v2/posting/fbs/act/get-postings` упомянут в официальном описании create,
   однако его path и схемы отсутствуют в сохранённом OpenAPI; текущую документацию
   получить не удалось. Кроме того, не подтверждён read-only поиск carriage_id
   для внешней перевозки, чей номер WMS ещё не сохранила. Не придумывать
   pagination/body/ID по дате и продавцу. До закрытия G4 опираться на точные
   карточки posting, либо на ранее сохранённые реальные carriage_id/состав и
   подтверждённый checkpoint. Позитивный wire-тест ветви только по carriage
   требует сначала официальной схемы; существующий источник не даёт её.
