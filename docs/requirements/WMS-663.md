## Поиск дублей и новое основание

WMS-638 уже нормализует числовые SKU в requirements.products_requiring_*;
это исправление сохраняется без дублирования. Её R2 запрещала автоматически
передавать ГТД/отсутствие документа. Источник 154 и текущее уточнение дают новый
предмет: **явное действие оператора**, только по подтверждённым полям API.
WMS-663 меняет прежний запрет ровно в этом объёме; фоновая постановка «нет ГТД»
без выбора по-прежнему запрещена. Историческая WMS-638 не переписывается.
Проверка номеров, refs и registry-предметов описана в analysis.md; 663 свободен.

## Существующий процесс, экран и цель

Заказ Ozon находится в существующем рабочем пространстве FBS. В коде
`FfFbsSupplyWorkspace.tsx` уже выводятся позиции Ozon, SKU, метаданные/ошибки
маркировки и действия заказа. `prepare_order_assembly` готовит ограничения и
страны, но выбора ГТД/РНПТ нет. `_full_exemplar_products` собирает маркировки
из локальных строк; для документов этого недостаточно: можно затереть сведения
других экземпляров и сведения, введённые в кабинете.

В отдельной браузерной вкладке 05.10 открыты список FBS и образец `WMS617 ozon`
на `web-production-9e7c1.up.railway.app`, склад «Тестовый». Видны вкладки «Состав»,
«Подбор», «Упаковка и маркировка», «Короба», Ozon-контекст. Во вкладке упаковки
у образца нет созданного задания: показано предложение начать работу. Такое
действие не выполнялось, чтобы не менять данные. Это просмотр оболочки образца,
не проверка фактической строки документов и не чтение Бамбука.

**Решение аналитика по UI:** в существующей строке Ozon-заказа/его позиции на
«Упаковка и маркировка» дать действие «ГТД / РНПТ», раскрывающее компактный блок
в контексте заказа. Использовать имеющиеся MUI `Collapse`, `TextField`,
`Checkbox`/`FormControlLabel`, `Button`, `Typography` и тему. По документу — поле
номера и отдельная явная галка «Номера ГТД нет» / «Номера РНПТ нет»; изначально
галки не выбраны. В блоке видны SKU/товар и номер экземпляра, когда их несколько.
Одна галка на весь заказ/все документы недопустима. Не создавать отдельный
глобальный экран или новое обязательное модальное подтверждение.

**Макет нужен** для нескольких позиций/экземпляров и длинных названий: текущий
просмотр не подтвердил геометрию этой строки. Последующий макет и UI-код делает
Sonnet через Claude CLI, при недоступности — только gpt-5.6-sol; ревью Astra high.
Этот аналитик другие модели не вызывает. Макет уточняет расположение, не ставит
под вопрос уже заданный выбор оператора и не добавляет отдельный запрос владельцу.

## Официальный контракт и границы знания

Сохранённый официальный источник: `tasks/ozon-integration-20260825/OZON_FBS_OPENAPI.json`.
На 05.10 актуальная публичная страница через web возвращает redirect loop,
поиск на docs.ozon.ru не дал доступных карточек методов; локальный предшествующий
запрос столкнулся с TLS-ошибкой. Свежесть спецификации онлайн не подтверждена.
Вызовы Seller API с учётными данными не выполнялись.

| Метод / поле | Подтверждённое поведение |
|---|---|
| `/v3/posting/fbs/get` requirements | products_requiring_gtd/rnpt относятся к конкретным SKU; числовые/строковые SKU уже принимает WMS-638. |
| `/v6/fbs/posting/product/exemplar/create-or-get` | Получить существующие exemplar_id и сведения экземпляров, признаки is_gtd_needed/is_rnpt_needed. Не объявлять метод немутирующим по имени; не вызывать фоном при простом показе списка. |
| `/v6/fbs/posting/product/exemplar/set` | posting_number + полный products/exemplars; по экземпляру gtd/rnpt, is_gtd_absent/is_rnpt_absent, marks, weight; multi_box_qty на отправлении. 200 — создана задача, не принятие данных. |
| `/v5/fbs/posting/product/exemplar/status` | posting_number, общий status, полный список экземпляров, gtd/rnpt, absent-флаги, check_status/error_codes. Сверять результат с сохранённым выбором конкретного запроса. |
| `ship_available` | Сборка доступна; для «принято» дополнительно нужны совпадающие целевые данные и отсутствие ошибок этих документов; незнакомый непустой document check_status оставляет результат неустановленным. Пустой products не подтверждает именно наш выбор. |
| `validation_in_process` | Проверяется; продолжать чтение, не отправлять set заново. |
| `ship_not_available` | Сборка недоступна; показать фактические ошибки, не выдавать сохранение за успех. |
| `update_available` / `update_not_available` | Разрешено/запрещено редактирование сведений. Это не синоним accepted/rejected документа. Отображать возможность редактирования и отдельный результат документов. |
| gtd_check_status/rnpt_check_status | В сохранённой схеме просто string, перечня значений нет. Не копировать значения `passed/failed/processing` из соседней marks.check_status. Неизвестное значение не объявлять успешной проверкой. |

ГТД и РНПТ имеют самостоятельные поля отсутствия. Для УИН, IMEI, маркировки,
страны, сертификатов универсальное «нет документа» спецификацией не доказано;
добавлять их сюда нельзя. API-способность принять absent-флаг не означает
универсальной допустимости для любого товара: окончательный отказ Ozon
отображается для конкретного документа/экземпляра.

## Решения аналитика и незакрытые технические сведения

Три состояния выбора — не заполнено / номер / явно нет номера — выводятся из
значений и флагов, а не из новой независимой таблицы. Отдельно отображается
состояние внешней обработки. Для сохранённого намерения подходят существующие
`FbsOrder.meta_details_json` и provider-данные позиций, с сохранением чужих ключей;
параллельные marking writers обязаны использовать тот же полный набор. Конкретный
JSON-ключ определит разработчик, это не новый пользовательский идентификатор.

После timeout не создавать автоматическую очередь повторных set. Штатный
повтор чтения допустим; периодический статус по незавершённым документам должен
работать и у заказа без строк FbsOrderMarking, иначе ГТД-only случай зависнет.
Старые данные в `/status` не доказывают, что предыдущая задача завершена.

G2: актуальность публичного Ozon-контракта и допустимые значения gtd/rnpt_check_status
онлайн не подтверждены. Без них нельзя придумывать частное «passed=принято».
Зафиксированный здесь строгий успех через ship_available + совпадение данных +
отсутствие ошибок пригоден для тестов; другие результаты остаются различимыми
и не объявляются успехом. Перед внешней приёмкой требуется доступная официальная
версия/ответ разрешённого тестового Seller API; это техническое доказательство,
не повторный вопрос владельцу о поведении.

G3: нужна визуальная проверка реальной строки заказа с активным заданием упаковки
на тестовом стенде и макет Sonnet. Просмотр оболочки браузера и чтение кода не
выдаются за эту проверку. R1–R15 по смыслу определены, геометрия до UI-кода проверяется.
