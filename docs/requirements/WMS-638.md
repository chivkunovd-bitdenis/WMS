# WMS-638 · Ozon: сборка падала на «ответ неизвестного формата», если Ozon требует ГТД

## Исходный запрос

> «Блять, срочно напротив бери это нахуй все эти ГТДшки, блять, пускай просто читает и не блокирует. Прям сейчас, ход фиксом, быстро, блять, чтобы они передали через ВМС заказы» (владелец, 02.10.2026)

Без аналитика и ревью — срочный хотфикс по прямому указанию владельца.

## Причина (проверено на бою 02.10.2026)

ФФ «Бамбук», селлер Мовсесян: заказы 0148656673-0134-1, 0181745532-0045-3, 0282817049-0013-1 не собирались по QR (`ozon_label_error = ozon_invalid_response`). Живой ответ `/v3/posting/fbs/get` содержит `result.requirements.products_requiring_gtd: [1695134284]` — SKU числом, а сгенерированная схема `ozon_fbs_api.py` объявляет все `products_requiring_*` как `list[str]`; pydantic не приводит число к строке → `ValidationError` → «Ozon вернул ответ неизвестного формата». Несобранный заказ блокирует передачу всей поставки (`ozon_order_not_assembled`).

## Требования

### R1. Списки `products_requiring_*` принимают SKU числом и строкой

В базовой модели Ozon до валидации числа в списках `products_requiring_*` приводятся к строкам. Остальные поля не меняются. Правка в генераторе `scripts/generate_ozon_fbs_models.py`, схема перегенерирована.

### R2. ГТД не передаётся

По указанию владельца номер ГТД и отметка «номера нет» не передаются; задача — только перестать падать при чтении.

## Заключение

Хотфикс принят локально без аналитика и ревью по указанию владельца. Если Ozon при сборке откажет из-за отсутствия ГТД, его ошибка теперь будет показана как есть, а не как «ответ неизвестного формата»; передача ГТД — отдельное решение владельца.
