Владелец должен выбрать ожидание или замену модели; требований к фронту и критериев его приёмки этот лимит не меняет. Работа не включает merge или деплой без отдельного поручения. Пользователи работают с обращениями в WMS; команда разработчиков работает с карточками в Trello. Отдельная собственная админка условна в запросе и не нужна при подходящей бесплатной интеграции.

## Существующий процесс и цель изменения

Проверено по коду: общая оболочка авторизованного приложения — `frontend/src/layouts/AuthedAppLayout.tsx`, с ветками seller и ff. В ней шапка, боковая навигация, основной экран и уведомления; глобального обращения разработчикам сейчас нет. Новая кнопка должна быть единой для оболочки, а не дублироваться в каждом рабочем экране.

`backend/app/api/deps.py:get_current_user` извлекает пользователя и проверяет организацию (tenant) из авторизованной сессии. Делегированный магазин определяется `resolve_effective_seller_id`, а не данными произвольного запроса. `/auth/me` уже возвращает `id`, `tenant_id`, `active_seller_id`, `organization_name` и имя селлера; на актуальной базе `origin/etalon` тип `Me` в `frontend/src/hooks/useAuth.ts` уже объявляет `id`, но пока не объявляет `tenant_id`. Оба значения нужно использовать для привязки черновика к человеку, без обращения к хранилищам ключей.

В браузере 01.10.2026 открыт текущий production `https://wms.sellerfocus.pro/`: доступен только экран входа, авторизованная сессия отсутствует. Поэтому текущие «Ячейки» и «Расчёты» визуально не подтверждены. Просмотрен доступный образец из библиотеки продуктовых случаев `https://sellerfocus.pro/wms/app/raschety-razdely.html`, раскрыта «Приёмка» до документов и просмотрен снимок: светлая тема, фиолетовый основной цвет, компактные строки, округлые элементы, действия в контексте. Это образец темы и поведения, не доказательство состояния рабочего стенда. После реализации авторизованный экран необходимо проверить локально с тестовым пользователем или на разрешённом тестовом стенде и сравнить с действующей темой приложения.

Цель: человек, столкнувшийся с ошибкой или предложением по процессу, может отправить обращение из текущего экрана, продолжить складскую работу, затем вернуться к описанию и текущему статусу. Команда получает одну карточку на обращение в общей доске Trello.

## Продуктовые решения аналитика

1. Применены навыки постановки/приёмки и продуктового решения; прочитаны библиотеки `owner-cases.md` и `failure-cases.md`. Из случаев применимы сохранение контекста действия, видимая ошибка внутри модалки, восстановление после потери ответа и защита от повторного внешнего создания.
2. Два типа в одном выпадающем списке: «Ошибка» и «Улучшение / доработка». Для ошибки — одно обязательное большое текстовое поле «Описание ошибки». Для улучшения — обязательные «Экран / процесс», «В чём сейчас проблема» и «Как можно улучшить». Пример первого поля: «Шаг упаковки при отгрузке FBS заказов». Отдельное обязательное название заявки не добавляется: краткое название получается из текста автоматически.
3. Одна модалка «Задача разработчикам» с разделами «Новая заявка» и «Мои заявки». Открытие кнопки ведёт к сохранённому черновику нового обращения; список и описание заявки открываются в этом же окне. Чат здесь — только аналогия навигации. Переписка клиента, вложения, голосование и редактор отправленного обращения не запрошены.
4. Черновик автоматически сохраняется в этом браузере для user + tenant + текущего/effective seller (если есть). Удобство восстановления между устройствами не запрошено. Смена типа не уничтожает уже набранный текст; отправляется только выбранная форма. «Отменить», крестик и Escape закрывают окно, сохраняя черновик. «Очистить черновик» очищает только текущий черновик.
5. Единые четыре статуса: «На рассмотрении» → «В очереди» (утверждена) → «В работе» → «Завершена». «В очереди» обозначает принятую командой заявку и снимает разницу формулировок из исходной речи. Команда управляет стадиями перемещением карточки между соответствующими списками Trello; WMS показывает синхронизированный статус, а не независимый редактируемый процесс.
6. Ведущий проверил официальные условия: Trello Free допускает неограниченные карточки, до 10 досок на Workspace и до 10 участников Workspace; REST API позволяет создавать карточки, читать карточки/списки и назначать labels. Поэтому выбран Trello, условие собственной админки не наступило. Источники: [тарифы Trello](https://trello.com/pricing), [REST API cards](https://developer.atlassian.com/cloud/trello/rest/api-group-cards/). Бесплатность относится к этим пределам; реальный состав Workspace пока не проверен.
7. Новая сохранённая сущность обращения нужна для заявленного списка «Мои заявки», изоляции авторов, приёма без доступного Trello и восстановления повторной отправки. Черновики остаются локальными; отдельные журналы, счётчики и админские экраны не вводятся. Доставка и опрос Trello используют существующий контур фоновых задач; обычное чтение моих заявок не создаёт внешних карточек.
8. «Спасибо, ваше обращение зафиксировано» подтверждает сохранение в базе WMS. Недоступность или отсутствие настройки Trello не стирает принятое обращение и не вынуждает пользователя повторно создавать заявку. Пока реальная интеграция не включена, в итоговом отчёте нельзя объявлять её рабочей на живой доске.

## Согласованный контракт frontend/backend

Маршруты указаны относительно существующего API base приложения. Префикс развёртывания использует `apiUrl`, без отдельного адреса в компоненте.

- `POST /developer-requests`: `{ idempotency_key: UUID, type: "bug" | "improvement", description?: string | null, screen?: string | null, problem?: string | null, proposal?: string | null, page_url?: string | null }`. `page_url` означает только pathname без query/hash. Поля user/tenant/seller/status не принимаются от клиента. Backend проверяет непустые поля выбранного типа; сохраняет только поля активной формы.
- Ответ создания и `GET /developer-requests/{id}`: `{ id, type, title, description, screen, problem, proposal, status: "review" | "queued" | "in_progress" | "completed", created_at, updated_at }`. Поля другого типа равны null; `title` формируется из текста. Серверное время хранится с timezone. На UI подписи статусов из решения 5.
- `GET /developer-requests` возвращает массив таких объектов, только author+tenant, новые первые. Чужой/отсутствующий ID — 404, нет авторизации — штатный 401. Дополнительная WMS админская ручка не нужна.
- Один `idempotency_key` связан с текущей попыткой в черновике до подтверждённого сохранения. Повтор того же содержимого возвращает ту же заявку. Изменённое содержимое с уже использованным ключом — 409; UI сохраняет текст и сообщает, что предыдущая попытка уже сохранена, не повторяет создание вслепую. Для нового намеренного отправления используется новый UUID.
- `/auth/me` уже возвращает id+tenant_id. Дополнить тип frontend `Me` полем tenant_id (id уже есть на актуальной базе) и передать идентичность кнопке. Ключ черновика включает tenant/user/effective seller. Магазин берётся из `active_seller_id`/сессионного seller; не из текстового имени клиента.
- Фоновая синхронизация использует существующий Celery: доставляет заявки, восстанавливает неопределённое внешнее создание по UUID-маркеру, опрашивает списки связанной карточки и сохраняет соответствующий статус. GET не создаёт внешнюю карточку. Неизвестная стадия не становится автоматически `review`.
- Конфигурация поддерживает доску, четыре списка и credentials из существующего серверного окружения. В этой задаче создаётся контракт конфигурации и тестовый провайдер; существующие секреты не читаются и реальные не выпускаются/не меняются.

## Настройка и запуск серверной части

Подробная техническая инструкция исполнителя — [backend/docs/developer-requests.md](../../backend/docs/developer-requests.md). Здесь сохранён необходимый контракт подключения без значений секретов.

| Переменная окружения | Назначение |
|---|---|
| TRELLO_API_KEY / TRELLO_TOKEN | Разрешённые владельцем серверные credentials выбранной доски; фронт их не получает. |
| TRELLO_BOARD_ID | ID приватной незакрытой доски команды. |
| TRELLO_REVIEW_LIST_ID | Открытый список «На рассмотрении». |
| TRELLO_QUEUED_LIST_ID | Открытый список «В очереди». |
| TRELLO_IN_PROGRESS_LIST_ID | Открытый список «В работе». |
| TRELLO_COMPLETED_LIST_ID | Открытый список «Завершена». |
| TRELLO_CLIENT_LABEL_ID | ID существующей цветной метки «Клиент»; необходим для полного выполнения R12. |
| TRELLO_SYNC_INTERVAL_SEC | Интервал планировщика: 60 секунд по умолчанию, минимум 30. |

Без полного набора credentials/доски/четырёх разных списков задача ничего не отправляет, но локальный приём заявок работает. Если метка не задана, карточка может доставиться с текстом «Клиент», однако требование о цветном различии ещё не выполнено. Для завершения подключения нужно настроить метку и проверить её фактический вид, внутреннюю карточку и клиентскую карточку на выбранной доске. Это не основание блокировать отправку обращения пользователем WMS.

Сервер и миграцию `20261001_2301_developer_requests.py` необходимо выпускать вместе штатным путём; отдельное накатывание миграции на стенд в обход соответствующего кода запрещено. Для автоматической доставки нужны существующий `CELERY_BROKER_URL`, работник `celery -A app.celery_app worker` и планировщик `celery -A app.celery_app beat`. Имя задачи — `wms.developer_requests_sync`; один проход выбирает до 50 ожидающих записей. Production Compose передаёт TRELLO настройки worker, а интервал также beat. В Railway эти переменные нужны в окружении worker и интервал в beat. Запуск одного API карточки не доставляет; обычный GET заявок внешнего создания не выполняет.

HTTP 4xx сохраняет pending и повторяется с растущей задержкой, максимум час, без окончательного запрета после серии отказов. Неопределённый исход POST хранится как outcome_unknown до внешнего вызова: следующие циклы только ищут точную строку `WMS-REQUEST-ID: <UUID>` в той же доске, включая архивные карточки. Найденная карточка связывается; отсутствие/несколько совпадений или ошибка чтения не разрешают новый POST. При устойчивом outcome_unknown команда выясняет результат исходного действия на доске; нельзя обнулять состояние только из-за отсутствия результата поиска. Ручная production коррекция требует отдельного разрешения и подтверждённого внешнего результата. Аренда записи действует пять минут и защищена уникальным токеном от позднего ответа другого работника.

В этой работе не создавались реальные credentials/карточки и не менялись реальные окружения. Этот runbook описывает способ подключения и не предоставляет разрешения на конкретные действия с секретами или production.

## Заключение

**WMS-624 не принята. Серверная часть реализована и сохранена на актуальной базе; фронт и перекрёстное ревью ожидают Opus.**

Фронт/дизайн и локальный черновик ещё не реализованы из-за ограничения доступности Opus. Перекрёстное ревью серверной реализации требуемой моделью Opus не проведено; собственное чтение аналитика и тесты разработчика его не заменяют. Авторизованные браузерные сценарии, визуальная/клавиатурная приёмка и фактическое подтверждение полного пользовательского пути не выполнены. Живая Trello доска не подключена; реальные перемещения статусов, цветовая метка и штатные внутренние карточки команды не проверены. Merge и деплой не выполнялись.

Оставшиеся требования сохраняются без смягчения: необходимо реализовать фронт порученной владельцем моделью (или получить прямое уточнение о её замене), провести Opus cross-review backend и соответствующее ревью фронта, выполнить обязательные проверки в браузере и после разрешённого подключения проверить живую интеграцию. Только после подтверждения всех обязательных сценариев можно записать итог «принято».
