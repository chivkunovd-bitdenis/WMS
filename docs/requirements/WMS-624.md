## Существующий процесс и цель изменения

Уточнено по актуальному коду: фулфилмент использует `frontend/src/layouts/AuthedAppLayout.tsx`; фактический отдельный seller SPA использует `frontend/src/apps/seller/SellerLayout.tsx`. Наличие ветки seller в AuthedAppLayout не означает, что основной seller портал построен на ней. В обеих реальных оболочках есть навигация и рабочий экран. Реализация использует один общий компонент DeveloperRequests в обеих реальных оболочках; кнопка не дублируется по каждому рабочему экрану. Это подтверждено чтением кода и локальным браузером после реализации.

`backend/app/api/deps.py:get_current_user` извлекает пользователя и проверяет организацию (tenant) из авторизованной сессии. Делегированный магазин определяется `resolve_effective_seller_id`, а не данными произвольного запроса. `/auth/me` уже возвращает `id`, `tenant_id`, `active_seller_id`, `organization_name` и имя селлера; на актуальной базе `origin/etalon` тип `Me` в `frontend/src/hooks/useAuth.ts` уже объявляет `id`, до WMS-624 не объявлял `tenant_id`; реализация добавляет его. Оба значения нужно использовать для привязки черновика к человеку, без обращения к хранилищам ключей.

В браузере 01.10.2026 открыт текущий production `https://wms.sellerfocus.pro/`: доступен только экран входа, авторизованная сессия отсутствует. Поэтому текущие «Ячейки» и «Расчёты» визуально не подтверждены. Просмотрен доступный образец из библиотеки продуктовых случаев `https://sellerfocus.pro/wms/app/raschety-razdely.html`, раскрыта «Приёмка» до документов и просмотрен снимок: светлая тема, фиолетовый основной цвет, компактные строки, округлые элементы, действия в контексте. Это образец темы и поведения, не доказательство состояния рабочего стенда. После реализации авторизованный экран необходимо проверить локально с тестовым пользователем или на разрешённом тестовом стенде и сравнить с действующей темой приложения.

Цель: человек, столкнувшийся с ошибкой или предложением по процессу, может отправить обращение из текущего экрана, продолжить складскую работу, затем вернуться к описанию и текущему статусу. Команда получает одну карточку на обращение в общей доске Trello.

## Продуктовые решения аналитика

1. Применены навыки постановки/приёмки и продуктового решения; прочитаны библиотеки `owner-cases.md` и `failure-cases.md`. Из случаев применимы сохранение контекста действия, видимая ошибка внутри модалки, восстановление после потери ответа и защита от повторного внешнего создания.
2. Два типа в одном выпадающем списке: «Ошибка» и «Улучшение / доработка». Для ошибки — одно обязательное большое текстовое поле «Описание ошибки». Для улучшения — обязательные «Экран / процесс», «В чём сейчас проблема» и «Как можно улучшить». Пример первого поля: «Шаг упаковки при отгрузке FBS заказов». Отдельное обязательное название заявки не добавляется: краткое название получается из текста автоматически.
3. Одна модалка «Задача разработчикам» с разделами «Новая заявка» и «Мои заявки». Открытие кнопки ведёт к сохранённому черновику нового обращения; список и описание заявки открываются в этом же окне. Чат здесь — только аналогия навигации. Переписка клиента, вложения, голосование и редактор отправленного обращения не запрошены.
4. Черновик автоматически сохраняется в этом браузере для user + tenant + текущего/effective seller (если есть). Удобство восстановления между устройствами не запрошено. Смена типа не уничтожает уже набранный текст; отправляется только выбранная форма. «Отменить», крестик и Escape закрывают окно, сохраняя черновик. «Очистить черновик» очищает только текущий черновик.
5. Единые четыре статуса: «На рассмотрении» → «В очереди» (утверждена) → «В работе» → «Готово» (последующее уточнение по клиентской доске). «В очереди» обозначает принятую командой заявку и снимает разницу формулировок из исходной речи. Команда управляет стадиями перемещением карточки между соответствующими списками Trello; WMS показывает синхронизированный статус, а не независимый редактируемый процесс.
6. Ведущий проверил официальные условия: Trello Free допускает неограниченные карточки, до 10 досок на Workspace и до 10 участников Workspace; REST API позволяет создавать карточки, читать карточки/списки и назначать labels. Поэтому выбран Trello, условие собственной админки не наступило. Источники: [тарифы Trello](https://trello.com/pricing), [REST API cards](https://developer.atlassian.com/cloud/trello/rest/api-group-cards/). Бесплатность относится к этим пределам; реальный состав Workspace пока не проверен.
7. Новая сохранённая сущность обращения нужна для заявленного списка «Мои заявки», изоляции авторов, приёма без доступного Trello и восстановления повторной отправки. Черновики остаются локальными; отдельные журналы, счётчики и админские экраны не вводятся. Доставка и опрос Trello используют существующий контур фоновых задач; обычное чтение моих заявок не создаёт внешних карточек.
8. «Спасибо, ваше обращение зафиксировано» подтверждает сохранение в базе WMS. Недоступность или отсутствие настройки Trello не стирает принятое обращение и не вынуждает пользователя повторно создавать заявку. Пока реальная интеграция не включена, в итоговом отчёте нельзя объявлять её рабочей на живой доске.

9. Независимое ревью выявило обязательное ограничение провайдера: [официальный Card object Trello](https://developer.atlassian.com/cloud/trello/guides/rest-api/object-definitions/) допускает описание карточки не длиннее 16 384 символов; аналитик отдельно проверил источник 01.10.2026. Выбрана проверка общего **полного сформированного описания** до сохранения WMS, включая все поля, клиента, дату, исходный pathname и UUID-маркер. Произвольные лимиты отдельных полей не вводятся. При превышении пользователь получает понятную ошибку в прежнем окне и может сократить текст; черновик сохраняется, благодарность не показывается, запись и внешняя карточка не создаются. Молчаливое обрезание нарушило бы требование полного описания; вложение добавило бы отдельное внешнее создание и его восстановление без необходимости из запроса. Это подтверждённое обязательное условие платформы по AGENTS.md, а не новое бизнес ограничение. Параметры реально настроенной доски и секреты для проверки длины не нужны. Техническое решение счётчика: использовать единицы UTF-16 (обычная кириллица/ASCII — одна, emoji вне базового диапазона — две), что совпадает с JavaScript length и консервативно допускает описание. Официальный источник говорит chars и не уточняет способ счёта Unicode; считать UTF-16 подтверждённым измерителем самого Trello нельзя. actual_length и max_length используют одни единицы; проверка граничных emoji обязательна.

10. Независимое ревью воспроизвело технический тупик 409: две вкладки открыли один черновик, A сохранила исходное содержимое, B с изменённым содержимым получила постоянный отказ для того же UUID. Решение восстановления в рамках R7: только после доказанного 409 показать «Продолжить как новый черновик». Явное нажатие сохраняет текущий тип и все поля, меняет UUID, снимает состояние отвергнутой попытки и ничего не отправляет. Затем пользователь намеренно нажимает «Отправить». Автоматическая смена UUID была бы риском дубля при неизвестном результате; при потере ответа сохраняется прежний путь «Проверить отправку» исходного payload. Восстановление старой заявки сохраняет новые правки как отдельный черновик. Решение определяет действие человека; технический дефект закрывается исправлением, повторным независимым ревью и C16, а не одобрением аналитика.
11. Последнее поручение о клиентских списках заменяет первоначальное предложение использовать общие колонки команды. Интеграция связывается только с четырьмя явно выбранными клиентскими списками. Внутренние карточки/комментарии и прежние колонки остаются команде; создание новых обращений и просмотр «Моих» не требуют удаления/перемещения старых задач. Название последней стадии в UI — «Готово», API enum completed сохранён.

## Согласованный контракт frontend/backend

Маршруты указаны относительно существующего API base приложения. Префикс развёртывания использует `apiUrl`, без отдельного адреса в компоненте.

- `POST /developer-requests`: `{ idempotency_key: UUID, type: "bug" | "improvement", description?: string | null, screen?: string | null, problem?: string | null, proposal?: string | null, page_url?: string | null }`. `page_url` означает полный pathname с префиксом портала, без query/hash. Поля user/tenant/seller/status не принимаются от клиента. Backend проверяет непустые поля выбранного типа и полное сформированное описание по R17; сохраняет только поля активной формы.
- При превышении полного описания: HTTP 422, `detail: { code: "developer_request_description_too_long", message: "Обращение слишком длинное для передачи разработчикам. Сократите текст и отправьте ещё раз.", max_length: 16384, actual_length: N }`. Это доказанный отказ до сохранения: фронт сохраняет текущий текст, даёт исправить его, а снимок отвергнутой попытки не использует для последующего восстановления. Сервер использует одно форматирование описания для проверки и доставки со стабильными метаданными записи.
- Ответ создания и `GET /developer-requests/{id}`: `{ id, type, title, description, screen, problem, proposal, status: "review" | "queued" | "in_progress" | "completed", created_at, updated_at }`. Поля другого типа равны null; `title` формируется из текста. Серверное время хранится с timezone. На UI подписи статусов из решения 5.
- `GET /developer-requests` возвращает массив таких объектов, только author+tenant, новые первые. Чужой/отсутствующий ID — 404, нет авторизации — штатный 401. Дополнительная WMS админская ручка не нужна.
- Один `idempotency_key` связан с текущей попыткой в черновике до подтверждённого сохранения. Повтор того же содержимого возвращает ту же заявку. Изменённое содержимое с уже использованным ключом — 409; UI сохраняет текст и сообщает, что предыдущая попытка уже сохранена, не повторяет создание вслепую. Для нового намеренного отправления используется новый UUID только после явного действия «Продолжить как новый черновик» по R18; действие ничего не отправляет.
- `/auth/me` уже возвращает id+tenant_id. Дополнить тип frontend `Me` полем tenant_id (id уже есть на актуальной базе) и передать идентичность кнопке. Ключ черновика включает tenant/user/effective seller. Магазин берётся из `active_seller_id`/сессионного seller; не из текстового имени клиента.
- Фоновая синхронизация использует существующий Celery: доставляет заявки, восстанавливает неопределённое внешнее создание по UUID-маркеру, опрашивает списки связанной карточки и сохраняет соответствующий статус. GET не создаёт внешнюю карточку. Неизвестная стадия не становится автоматически `review`.
- Конфигурация поддерживает доску, четыре списка и credentials из существующего серверного окружения. Первоначальная разработка выполнялась с тестовым провайдером без чтения/выпуска реальных секретов. Последующее поручение подключения фиксируется отдельно; доступ к конкретным credentials и живые действия не подразумеваются контрактом.

HTTP 4xx сохраняет pending и повторяется с растущей задержкой, максимум час, без окончательного запрета после серии отказов. Неопределённый исход POST хранится как outcome_unknown до внешнего вызова: следующие циклы только ищут точную строку `WMS-REQUEST-ID: <UUID>` в той же доске, включая архивные карточки.
