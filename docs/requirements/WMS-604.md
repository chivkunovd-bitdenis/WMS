## Существующий процесс и цель изменения

В `FfFbsSupplyAssembly` общая сборка уже содержит поставки разных селлеров/складов. На вкладке упаковки каждая поставка сейчас отображается отдельной рамкой; только одна рамка активна, без активной поставки скан не отправляется. Каждая рамка использует существующее рабочее место `FfFbsSupplyWorkspace`. Оно уже содержит товарный скан `scanFbsProductForAutoPrint`, выбор заказа, ожидание ЧЗ, сохранение ЧЗ и печать, но последовательность зависит от плана печати, а обработка ограничена одной поставкой. Это установлено чтением кода; само по себе не доказывает текущую работу сканера/принтера.

Цель: оператор работает со всеми товарами выбранной сборки непрерывно, без выбора поставки для каждого скана. Данные поставок, селлеров, складов, коробов и отгрузки остаются существующими; меняется представление упаковки и последовательность сканов.

## Решения аналитика и вопросы

1. Единый список относится к текущей выбранной общей сборке, а не ко всем заказам организации. Это сохраняет явно заданный пользователем первый шаг выбора заказов и существующий контекст.
2. «Любой заказ» означает детерминированный выбор первого доступного подходящего неупакованного заказа текущего списка; селлер и склад не являются переключателями упаковки. Связи конкретного заказа с его поставкой и коробами сохраняются.
3. Требование QR реализуется через существующую печать стикера заказа; новый экран или формат не вводится. Пользователь исправил свою промежуточную фразу, поэтому для маркируемого товара момент QR — после успешного ЧЗ.
4. Удаление «Всё упаковано» требует подтверждать фактическую упаковку по завершённому скану, иначе исчезнет единственный путь продолжения. Это следствие R7 и R11, не новый этап оператора.
5. Поддержка последовательности в отдельной карточке поставки не должна расходиться с общей сборкой, поскольку используется общий механизм; изменения других экранов вне упаковки не требуются.
6. Для массовой операции неоднозначные категории нельзя угадывать по случайному слову: агент проверяет категорию и название вместе с принадлежностью принятой поставке и сообщает исключённые неоднозначные позиции. Новый глобальный автоматический классификатор не требуется.

7. Единый список сохраняет существующие действия строки (QR, ТЗ, ручная печать, снятие ЧЗ). Короба и передача поставок могут оставаться ниже общего списка: они не разрывают строки упаковки и сохраняют объект операции. Реализация через существующие контроллеры поставок допустима без пользовательского выбора активной поставки и без нескольких обработчиков одного скана.

8. Массовая операция охватывает все склады/селлеры заданного множества. Подтверждённый preview: 551 карточка, из них 524 false → true и 27 уже true. Критерий принятого входящего документа: `operation_type=inbound`, статус `sorting/done/verified/posted`, `verified_at IS NOT NULL`, `actual_qty>0`. Явные категории одежды, включая палантины, включены; возвраты, непринятые документы, обувь/сумки и пустые категории исключены. Один `[OLD] Костюм…` AVpack без категории остаётся явно отмеченным исключением. Итог операции проверяется отдельно.

Визуальный просмотр исходного экрана: браузером открыт `http://localhost:5177/`, доступен только экран входа. Упаковка пока не просмотрена; разработчику запрошен локальный тестовый экран с двумя поставками. Это ограничение постановки, не визуальная приёмка. Процесс по коду определён достаточно для начала реализации.

## Заключение

**Текущий статус: основная упаковка реализована в именованной ветке; технологическое условие «без дополнительной программы и без настроек браузера» не выполнено; основная WMS в production не выложена. Полной приёмки нет.**

Основная реализация сохранена в `af813adc`. По результатам исполнителя/ведущего пройдены backend ruff, mypy, 532 + 19 целевых pytest; frontend TypeScript, сборка и 56 тестов. Перекрёстное ревью Opus ещё выполняется, заключение не получено. Аналитик ранее проверил настоящие React-компоненты на подменённых API/квитанции: единый список четырёх заказов двух селлеров/складов, ШК → ожидание ЧЗ → печать, ветвь без ЧЗ, сохранение выбранного заказа при ошибке, восстановление с тем же job_id, отсутствие повторной упаковки и кнопки «Всё упаковано». Это браузерная проверка с mock API, а не проверка production/физического принтера.

На https://sellerfocus.pro/packing-scan-check/ ранее опубликован native-прототип, требующий bridge; по последнему запросу владельца ведущий запустил замену на Chrome-вариант без bridge. Факт завершения публикации/внешняя версия подтверждаются ведущим отдельно, аналитик повторно страницу не открывал. Его успешный тест CUPS/виртуального IPP не выполняет последний запрет владельца на дополнительные программы. Локальный Chrome-вариант сохранён в `fb4fb720`/`c4e0332b`; он не требует bridge, но требует `--kiosk-printing` либо политику `SilentPrintingEnabled`, поэтому публикуется только как тест с этим явно указанным условием, а не как решение без настройки. Ведущий прогнал настоящий Chrome 147 с этим флагом: 10 этикеток 40×58 мм дошли через CUPS до виртуального IPP-принтера и независимо декодированы ZXing в точные 10 тестовых значений; afterprint приходил через 0,94–1,38 с. afterprint не доказывает выход бумаги. Внутренний target `chrome://print` существовал около 0,5 с, а заблокированный macOS не позволил подтвердить отсутствие визуального мелькания. Доказательства текущего эксперимента сохраняются ведущим отдельно.

Массовая операция товарного признака подтверждена evidence исполнителя (C6). Рабочую упаковку, экспериментальные варианты печати, результат ревью и deployment нельзя объединять в заявление о готовности: обязательное условие печати без программ/настроек остаётся невыполненным.
