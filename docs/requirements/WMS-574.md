### 2.2 Создание поставки сейчас

- Окно создаёт одну поставку: сначала проверка POST /operations/fbs-supplies/preflight, затем создание POST /operations/fbs-supplies/from-orders с телом name, order_ids, planned_delivery_type, planned_destination, idempotency_key (FbsSupplyCreateDialog.tsx:98–131; fbsApi.ts:659–685). «Создать поставку» доступна только при compatible=true.
- Сервер (fbs_supply_validator_service.py:183–244) сравнивает каждый заказ с первым по шести признакам и отказывает при расхождении: площадка (different_marketplace), селлер (different_seller), склад WB — поле заказа wb_warehouse_id, то есть склад продавца в WB (different_wb_warehouse), склад WMS (different_wms_warehouse), тип покупателя B2C/B2B (legal_type_mismatch), грузовой тип (different_cargo_type). Создание: поставка у WB → строка FbsSupply → добавление заказов в WB → привязка (fbs_supply_service.py:576–1046); несовместимый состав — 409 order_incompatible.
- Все шесть признаков есть у заказа на клиенте (тип FbsWorklistOrder, fbsApi.ts:204–262: marketplace, seller.id, wb_warehouse.id, wms_warehouse.id, buyer_type, cargo_type).
- Сейчас выбор заказов двух селлеров или двух складов WB нельзя превратить в поставку: preflight вернёт несовместимость, кнопка создания неактивна.

### 2.3 Как открывается карточка и что переживает перезагрузку

- После создания карточка открывается через адрес: openWorkspace пишет параметр supply_id (FfFbsOrdersScreen.tsx:1053–1063), при загрузке страницы параметр читается и окно открывается снова (1176–1192), при закрытии параметр удаляется (2058).
- Выбранная вкладка хранится в sessionStorage под ключом wms:fbs:<id поставки>:stage (fbsWorkspaceStage.ts). Ключи повторяемых операций (создание/удаление короба, передача) — тоже в sessionStorage по поставке (FfFbsSupplyWorkspace.tsx:172–192).
- Сущности, объединяющей несколько поставок FBS, нет: в модели FbsSupply нет group/batch/wave, документ «Отгрузка на маркетплейс» (MarketplaceUnloadRequest) поставки FBS не объединяет.

### 2.4 Подбор сейчас

- Вкладка «Подбор» карточки встраивает общий экран подбора FfUnloadPickPage с requestId = id поставки и source="fbs" (FfFbsSupplyWorkspace.tsx:2933–2942). Тот же экран подбирает «Отгрузку на маркетплейс».
- Экран читает GET /operations/fbs-supplies/{id} и GET /{id}/pick-options (FfUnloadPickPage.tsx:196–199); план по товару — planned_qty из pick-options. Скан товара — POST /{id}/pick/scan, ручное число в поле «Снять» — POST /{id}/pick/set. Все ручки принимают один supply_id в пути; нескольких поставок ни одна ручка не принимает.
- Кому достаётся снятая штука: сервер выбирает заказ этой поставки с этим товаром, ещё не подобранный, — самый ранний по дате создания в WB, затем по сроку (fbs_picking_service.py:968–973, 1124). Ручное число раздаётся по сроку, уменьшение снимает самые поздние подборы (там же, 469–607).
- Для WB подбор товар не перемещает и не списывает (fbs_picking_service.py:1139 — перемещение только для не-WB). Пишется только связь «штука → заказ» с местом, откуда сняли (fbs_order_picks), статус заказа «подобран» и факт операции. Списание — при передаче поставки (fbs_shipment_service.py:1222–1398) из места, записанного при подборе.
- Сколько можно снять из места, сервер считает по всей организации: остаток места минус активные подборы всех незакрытых поставок (pick_option_location_service.py:57–79, 143–193). Значит, у разных поставок одной группы «доступно в месте» одинаковое.
- Проверено в браузере: сцена http://localhost:5610/kb-scenes.html?scene=fbs-pick — вкладка «Подбор» настоящей карточки на подставных данных, план, «Где лежит», раскрытие места.

Если хоть одна галка включена — прямой ЧЗ (POST …/scan-kiz-reprint) или ШК товара (POST …/scan-auto-print, сервер сам выбирает единицу и заказ). - Короба (вкладка «Короба», 3442–3690): «Печать всех QR (N)», «Без распределения», поле «Коробов» и «Добавить короба» — POST /operations/fbs-supplies/{id}/boxes с count и ключом повтора. На сервере каждый короб сразу регистрируется у WB как грузоместо (fbs_packing_box_service.py:172–260, 750–796), QR грузоместа запрашивается у WB. У короба: «QR» (готовый QR WB или повторный запрос POST …/boxes/{box}/retry-qr), «Добавить товары» (окно ручного выбора заказов, POST назначения в короб, сервер отказывает, если заказ уже в другом коробе — order_already_in_box, или если поставка «Без распределения» — box_without_distribution; fbs_packing_box_service.py:364–420), меню ⋮ (очистить, удалить), раскрытие состава с удалением строки. «Передать в WB» — предварительная проверка и подтверждение.
- «Создать короб» как отдельной кнопки в карточке поставки нет — есть «Добавить короба» с числом. Понятия «открытый короб, куда идут сканы» в продукте нет: товары раскладываются по коробам вручную.
- Проверено в браузере: сцена http://localhost:5610/kb-scenes.html?scene=fbs-marking — вкладки «Упаковка и маркировка» и «Короба» настоящей карточки (кнопки, галки, строки, «Печать всех QR (0)», «Без распределения», «Добавить короба», «Передать в WB»).

### 2.6 Макет (ветка mockup/fbs-multi-supply-pack, 4812f2aa)

Открыт и прокликан в браузере 28.09 (http://localhost:5610/fbs-multi-supply-mockup.html, окно 1440×900): выбор всех 20 заказов → «Сформировать поставку» → окно «Новые поставки FBS» с таблицей «Селлер / Склад WB / Грузовой тип / Заказов», чип «Разделено на 4 поставки», радио «Склад или сортировочный центр / Пункт выдачи», «Создать поставки (4)» → окно «Сборка · 4 поставки» размера карточки поставки со вкладками «Состав», «Подбор», «Упаковка и маркировка». «Состав» — таблица состава с подзаголовками по поставкам. «Подбор» — настоящий экран подбора с суммарным планом (20 штук), скан ШК товара уменьшил «осталось» до 19. «Упаковка и маркировка» — четыре рамки «Поставка 000321 · WB № WB-GI-… · ИП … · Склад WB … · Склад / СЦ», «Упаковано 0 из 5», «Начать работу с поставкой»; после нажатия рамка с зелёной обводкой и светло-зелёной шапкой, «Завершить работу с поставкой», блок упаковки как в продукте, подпись «Сканы принимает только активная поставка», внизу «Короба · Склад / СЦ» с «Создать короб» и «Короб 1 · 0 шт · открыт — сканы идут сюда · Грузоместо WB …», кнопки «Закрыть короб», «QR», ⋮, уведомление «Отправлено на печать: QR грузоместа WB · Короб 1». Скан ШК товара чужой поставки дал красное «Этого товара нет в поставке 000321».

Что макет упростил (README макета, раздел «Что упрощено», и код): окно шага 2 не делает preflight и не проверяет остатки; «Доступно ЧЗ» — постоянное 50; печать (QR, ЧЗ и ШК, «Перепечатать», QR короба) и «Проверить в WB» только показывают уведомление; QR короба появляется мгновенно; убраны ветки Ozon и «Перенести в другую поставку»; скан ШК товара в макете упаковывает заказ без учёта галок печати; «Всё упаковано» и «Сдать без Честного знака» в макете сами кладут заказы в открытый короб. По слову владельца (раздел C) везде, где макет упростил, в продукте будет как в продукте.

## 3. Цель

Оператор выбирает на «Новых» заказы разных селлеров и складов, одним действием получает несколько поставок WB (по одной на каждый набор, который WB и сервер разрешают объединить) и собирает их в одном окне: общий подбор по суммарному плану, затем упаковка поставка за поставкой в её рамке, со сканом прямо в открытый короб этой поставки. Всё, что делается с заказами, ЧЗ, стикерами, коробами и WB, — те же действия и те же запросы, что в карточке одной поставки. Карточка одной поставки и обычная сборка не меняются ни в одном месте.

## 4. Решения аналитика

Владелец попросил не задавать ему вопросов в этом чате (раздел D). Развилки ниже решены по навыку wms-product-decision в границах его слов; каждое решение помечено основанием.

- **Д1. По каким признакам делить.** По тем же шести признакам, по которым сервер сейчас отказывает в объединении (п. 2.2): площадка, селлер, склад WB, склад WMS, тип покупателя, грузовой тип. Основание: A — «сформировали поставки по направлениям … направление селлер ну есть какие-то еще есть признаки»; делить по меньшему числу признаков — получить отказ сервера на создании. В окне показываются колонки макета «Селлер», «Склад WB», «Грузовой тип», «Заказов».
- **Д2. Обычный путь не трогаем.** Если выбранные заказы помещаются в одну поставку (все шесть признаков совпадают), «Сформировать поставку» открывает прежнее окно FbsSupplyCreateDialog без единого изменения, и дальше открывается прежняя карточка поставки. Новое окно «Новые поставки FBS» появляется, только когда выбор делится на две и больше групп. Смешение WB и Ozon в одном выборе остаётся под прежним запретом (не новый запрет — существующий). Групповая сборка — только для WB (весь макет и слова владельца — про WB; C: «в новом процессе»). Основание: B — «обычная сборка заказов не должна вообще никак ломаться»; AGENTS.md — не менять фронт сверх задачи.
- **Д3. Как создаются поставки.** Для каждой группы по очереди — тот же preflight и тот же POST from-orders с тем же телом, что у сегодняшнего окна; способ сдачи из единственной радиогруппы применяется ко всем группам. У каждой группы свой ключ повтора, который живёт до подтверждённого успеха: повтор после потерянного ответа не создаёт вторую поставку (сервер уже держит идемпотентность from-orders). Нового серверного механизма не нужно. Основание: C — «логика не переписывается»; AGENTS.md — при потере ответа выяснить результат до повторного внешнего действия.
- **Д4. Как хранится группа и как к ней вернуться.** Группа — это только список id поставок. Он пишется в адрес страницы параметром supply_ids (по образцу существующего supply_id), при перезагрузке окно сборки открывается с теми же поставками, при закрытии параметр удаляется. Новой таблицы, сущности или статуса нет, потому что вся работа (подборы, ЧЗ, стикеры, короба, назначения в короба) уже хранится у каждой поставки на сервере, а сама группа никаких данных, кроме перечня, не несёт. Если адрес потерян (закрыли вкладку), каждая поставка открывается обычной карточкой из списка поставок или из строки заказа, как сейчас, и ничего не теряется. Выбранная вкладка окна сборки — в sessionStorage, как у карточки. «Активная поставка» и «открытый короб» — состояние экрана, не сохраняется: после перезагрузки оператор снова жмёт «Начать работу с поставкой», и открывается последний короб этой поставки без создания нового (R17). Основание: AGENTS.md — «Новую таблицу … вводи только при конкретной необходимости», «позволяет продолжить работу после сбоя».
- **Д5. Кому достаётся штука на общем подборе.** Поставки группы стоят в том порядке, в каком показаны (порядок создания). Снятая сканом штука уходит первой по порядку поставке, у которой по этому товару ещё есть неподобранные заказы; внутри поставки заказ выбирает сервер своим прежним правилом. Ручное увеличение числа в поле «Снять» раздаётся по поставкам в том же порядке, уменьшение снимает с поставок в обратном порядке; отмена последнего снятия возвращает штуку в той поставке, которой она досталась. Вызовы — прежние pick/scan и pick/set конкретной поставки. Почему так можно: подбор WB не меняет остаток, только связывает штуку с заказом (п. 2.4), доступность места общая для организации, а к концу подбора все штуки всё равно распределены. Основание: A — «экран подбора. В точности … Один в один»; C — «план суммарный по всем поставкам».
- **Д6. Где кнопки «Начать/Завершить работу».** В шапке рамки поставки, как в макете. «Начать работу с поставкой» делает то же, что одноимённая кнопка продукта (start-work), если у поставки ещё нет задания упаковки; если задание есть — запрос не отправляется. Основание: A, макет; п. 2.5. Кнопка у переданной в WB поставки не выключается (Д17).
- **Д7. Что показывается в рамке.** В активной рамке — весь блок упаковки продукта для этой поставки: те же кнопки, галки, поле, строки, окна и меню, включая то, что макет убрал («Очистить ЧЗ», «Перенести в другую поставку»). Короба поставки — внутри рамки, под строками (как в макете), без отдельной вкладки «Короба». У короба — действия продукта («QR», «Добавить товары», меню ⋮ с очисткой и удалением, раскрытие состава с удалением строки) плюс «Открыть короб / Закрыть короб» из макета. «Добавить короба» с числом и «Без распределения» в рамке не показываются: их заменяет «Создать короб» макета; в карточке поставки они остаются как есть. Основание: C — «где макет упростил … будет как в продукте»; B — «Макет использовать строго тот».
- **Д8. Когда заказ кладётся в открытый короб.** Как только скан в активной поставке нашёл заказ по существующей логике: нашёлся стикер (lookup) или сервер выбрал заказ по ШК товара (scan-auto-print при включённой галке). Назначение — тем же запросом, что «Добавить товары» (POST назначения в короб этой поставки), только если заказ ещё не лежит ни в каком коробе. Скан ЧЗ после стикера продолжает прежний путь привязки ЧЗ и короб не меняет. Основание: A — «ШК, этого QR-кода, ЧЗ, ШК, все это привязывается только сразу условно к коробке».
- **Д9. Заказ без обязательного ЧЗ.** В продукте найденный по стикеру заказ всегда ждёт ЧЗ, и следующий скан другого стикера уходит как ЧЗ предыдущего заказа (ошибка). В окне сборки для заказа, которому ЧЗ не нужен (то же правило продукта requiresOrderHonestSign: задание упаковки не требует ЧЗ и WB не требует sgtin), после того как заказ положен в короб, ожидание ЧЗ снимается тем же сбросом, что по повторному скану стикера, — следующий скан сразу ищет следующий заказ. Для заказа, которому ЧЗ нужен, — прежнее ожидание ЧЗ. В карточке одной поставки ничего не меняется. Основание: A — «я такой пик пик пик лишнее у меня не сканится я дальше пик пик пик»; макет — «у товаров без обязательной маркировки один скан сразу упаковывает заказ». Риск: если у товара ЧЗ физически есть, а признака маркировки нет, ЧЗ сканом в окне сборки не внесётся — его вносят в карточке поставки, как сейчас.
- **Д10. ШК товара при выключенных галках.** Как в продукте (WMS-514 R3): при трёх выключенных галках ШК товара заказ не выбирает, оператор видит ошибку. Макет это упростил. Основание: C — «где макет упростил … будет как в продукте».
- **Д11. Нет открытого короба.** Скан не блокируется: вся логика продукта (поиск заказа, ЧЗ, печать) выполняется, заказ просто не кладётся в короб, и под полем скана показывается текст макета «Откройте или создайте короб.». Основание: AGENTS.md — не добавлять блокировок, которых не просил владелец; «Товар ещё не упакован» не основание блокировать.
- **Д12. Печать QR короба при создании.** Сразу после создания короба его QR грузоместа WB отправляется в печать тем же способом, каким «Печатать QR» (WMS-514) печатает стикер заказа — без окна предпросмотра. Если WB ещё не вернул QR, выполняется тот же запрос, что у кнопки «QR» короба (retry-qr), и после ответа QR печатается; если QR так и не готов — сообщение продукта «QR грузомест ещё не получены от WB — откройте QR любого короба, чтобы запросить.» и короб остаётся рабочим. Основание: A — «сразу вылазит из принтера ШК этого короба», «QR-код, потом должен быть запрашиваться».
- **Д13. «Передать в WB».** Кнопка в шапке рамки, как в макете, и работает как «Передать в WB» на вкладке «Короба» (та же проверка и то же подтверждение). Доступна так же, как в продукте, — до передачи, без условия «всё упаковано» (в макете она появлялась только после полной упаковки; такое условие было бы новой блокировкой). Основание: AGENTS.md; C.
- **Д15. Прогресс в шапке окна сборки (уточнение 29.09.2026).** Исполнитель этапа A нашёл, что карточка WB показывает в шапке «M из M подготовлено к отгрузке» (FfFbsSupplyWorkspace.tsx:2284–2296: для WB ready = total; «0 из 20» было только в макете). R5 остаётся как есть — числа как в продукте, сумма по поставкам; исправлено ожидание C3 на «10 из 10». Основание: C — «где макет упростил … будет как в продукте»; B — «Абсолютно все идентично с тем, что работает у нас».
- **Д16. Как называть поставку (уточнение 29.09.2026).** Своего номера документа у поставки WB нет: окно создания даёт имя «FBS {дата}» (FbsSupplyCreateDialog.tsx:124–131), у всех поставок группы оно одинаковое; различает их номер WB, который карточка показывает как «№ WB {wb_supply_id}» (FfFbsSupplyWorkspace.tsx:2711–2717). В шапке рамки и подзаголовке «Состава» — «Поставка {имя, как в заголовке карточки} · WB № {номер WB}»; в ошибке чужого кода — «Этого товара нет в поставке {номер WB}», потому что только он однозначно называет поставку. Основание: A — ошибка должна сказать, в какой поставке оператор работает; C — как в продукте.
- **Д17. «Начать работу с поставкой» у переданной поставки (уточнение 29.09.2026).** Макет выключал кнопку у переданной поставки; в требованиях такого условия нет, и вводить его не нужно: AGENTS.md запрещает пользовательские блокировки, которых не просил владелец. Кнопка у переданной поставки доступна; внутри рамки действуют только существующие правила продукта для переданной поставки (вкладка упаковки показывает «Поставка уже передана в WB. Состав менять нельзя, печать этикеток и стикеров доступна.», изменение коробов выключено тем же правилом fbsBoxEditingDisabled, печать доступна). Реализация этапа A (кнопка не выключается) этому соответствует. Основание: AGENTS.md, раздел 3; C — «как в продукте».
- **Д18. Рамка поставки — режим карточки, а не вынесенный компонент (уточнение 29.09.2026, этап B).** Исходная R26 разрешала менять карточку только выносом блока упаковки и коробов в общий компонент. Исполнитель вместо выноса сделал рамку самой карточкой FfFbsSupplyWorkspace с новым необязательным параметром assemblyFrame. Причины, которые он назвал: шесть файлов тестов карточки читают её файл по пути и вызывают функции по именам — вынос сломал бы их; при выносе ожидание ЧЗ и выбор строк сбрасывались бы при смене вкладок. Решение: принять. Цель R26 — не изменить обычный путь ни в одном месте; режим, который включается только параметром окна сборки, меняет обычный путь меньше, чем перенос всего блока в новый файл: прежний код карточки остаётся на месте, существующие тесты проходят без правки ожиданий. Условие решения: карточка без параметра неотличима от прежней — проверяется G11 и G1–G10, а при ревью — что каждая новая ветка кода выполняется только при assemblyFrame. Аналитик 29.09 сверил попиксельно снимки docs/reviews/artifacts/wms-574/card-packing-before/after.png и card-boxes-before/after.png: окно карточки совпадает, отличия только в полосе 4–7 px у левого края затемнённого бокового меню за окном. Основание: B — «не сломать, не затронуть, не помешать ни в одном месте … при написании каждой строчки кода задавать себе вопрос, а что будет здесь с нашим обычным путем»; AGENTS.md — простейшее решение, меняющее существующий фронт только в объёме задачи.
- **Д19. Когда говорить «Этого товара нет в поставке» (уточнение 29.09.2026, итоговое ревью P2-1).** Первая редакция R16 связывала этот текст с ответом «стикер не найден в этой поставке». Но при трёх выключенных галках ШК товара заказ не выбирает (WMS-514 R3) и получает тот же ответ, поэтому на ШК товара, который в поставке есть, рамка говорила «Этого товара нет в поставке» — неправду. Решение: текст «Этого товара нет в поставке {номер WB}» — только когда код действительно не относится к активной поставке: не стикер её заказа, не ШК товара её заказа (штрихкоды товаров заказов из снимка поставки: товар заказа, позиции, штрихкоды привязок маркетплейса) и не ЧЗ товара её заказа (GTIN из ЧЗ совпадает с ШК товара её заказа). Во всех остальных отказах, включая ШК товара этой поставки при выключенных галках, — прежний текст карточки. Сигнал ошибки звучит в обоих случаях. Логика скана и запросы не меняются, меняется только выбор текста ошибки. Основание: A — «если я в эту поставку попробую сканировать а, qr или шика товара который в ней здесь нет мне вот этот негативный сигнал»; C — как в продукте; WMS-514 R3.
- **Д14. «Печать листа подбора» на вкладке «Подбор».** Печатает лист по всей группе тем же шаблоном, что buildFbsPickingListPrintHtml, строки — суммарный план; в шапке листа — номера поставок группы. Основание: макет (кнопка есть), A — подбор «один в один».

## 5. Требования

Общий принцип для всех требований: любое действие над заказом, ЧЗ, стикером, коробом или WB в окне сборки выполняется теми же функциями фронта и теми же запросами, что в карточке одной поставки, с id конкретной поставки. Карточка одной поставки, экран «Заказы FBS» при выборе, укладывающемся в одну поставку, подбор «Отгрузки на маркетплейс» и все сценарии Ozon ведут себя ровно как в etalon 312a1748.

### Создание

- **R1.** Условие: на «Заказы FBS» → «Новые» выбраны заказы WB, которые по шести признакам Д1 делятся на две и больше групп. Действие: «Сформировать поставку». Результат: окно «Новые поставки FBS» как в макете — подзаголовок «WMS разделит N заказов на поставки по продавцу и складу WB и создаст каждую отдельно.», радиогруппа «Планируемый способ сдачи» (по умолчанию «Склад или сортировочный центр»), чип «Разделено на K поставок», таблица групп (Селлер, Склад WB, Грузовой тип, Заказов), «Отмена», «Создать поставки (K)». Для каждой группы выполнен тот же preflight, что у окна одной поставки; несовместимость группы (issues сервера) показана в её строке тем же текстом, что сейчас. Основание: A, C, Д1, Д3.
- **R2.** Условие: выбор укладывается в одну поставку, или выбраны заказы Ozon, или смешаны WB и Ozon. Результат: всё как сейчас — прежнее окно одной поставки или прежний запрет смешения; нового окна нет. Основание: B, Д2.
- **R3.** Действие: «Создать поставки (K)». Результат: для каждой совместимой группы по очереди выполнен тот же POST from-orders, что сейчас (тело, способ сдачи, ключ повтора группы). После успеха всех групп открывается окно «Сборка · K поставок» с созданными поставками, в адресе — supply_ids. Каждая созданная поставка — обычная поставка: видна в списке поставок и открывается обычной карточкой. Основание: A, C, Д3, Д4.
- **R4.** Условие: создание части групп не удалось (ошибка сервера или WB, потерянный ответ). Результат: окно не закрывается; у каждой группы виден её итог — создана (номер) или текст ошибки; кнопка повтора отправляет только несозданные группы с их прежними ключами, так что уже созданная у WB поставка не дублируется; кнопка «Открыть сборку» открывает окно сборки с уже созданными поставками. Заказы несозданных групп остаются на «Новых». Основание: AGENTS.md (потеря ответа внешней системы, продолжение после сбоя), Д3.

### Окно сборки

- **R5.** Окно «Сборка · K поставок» — того же размера и оформления, что карточка поставки (Dialog min(1500px, 98vw) × 94vh, иконка грузовика): заголовок «Сборка · K поставок», под ним селлеры через запятую, полоса прогресса и «N из M подготовлено к отгрузке», где N и M — суммы тех же чисел, что шапка карточки показывает для каждой поставки (у WB карточка показывает «M из M»: ready = total, FfFbsSupplyWorkspace.tsx:2284–2296, поэтому у группы WB — «M из M», где M — число заказов группы; уточнение 29.09, Д15). Вкладки «Состав», «Подбор», «Упаковка и маркировка». Закрытие — крестиком. Основание: A, макет.
- **R6.** Перезагрузка страницы с открытым окном сборки открывает его снова с теми же поставками и последней выбранной вкладкой; закрытие окна убирает supply_ids из адреса. Все сделанные подборы, ЧЗ, стикеры, короба и назначения в короба после перезагрузки видны, потому что читаются с сервера. Основание: AGENTS.md, Д4.
- **R7.** «Состав» — таблица состава карточки поставки (колонки «Фото», «Заказ WB», «Товар и идентификаторы», «Количество», «Маркировка», «Подбор»), строки сгруппированы по поставкам с подзаголовком «Поставка {название поставки} · WB № {номер WB} · {селлер} · Склад WB {склад}» (Д16). Основание: макет.

### Подбор

- **R8.** «Подбор» — тот же экран подбора (FfUnloadPickPage/UnloadPickScreen, те же колонки, «Где лежит», раскрытие мест, поле «Снять», отмена последнего снятия), где план по товару — сумма планов всех поставок группы, «снято» — сумма снятого, а «доступно в месте» — значение сервера, взятое один раз, не суммированное. Основание: A («Один в один»), C, п. 2.4.
- **R9.** Скан ячейки или тары выбирает место так же, как сейчас. Скан ШК товара (с выбранным местом или без) снимает одну штуку: запрос pick/scan уходит в поставку по правилу Д5, счётчики товара и «штук осталось снять» уменьшаются на 1. Если ни одной поставке группы этот товар больше не нужен — та же ошибка, что сейчас «по плану уже всё снято» / «нет в плане». Основание: B («скан ячейки, скан товара … переносить счетчик съема»), Д5.
- **R10.** Ручное изменение числа в поле «Снять» у места раздаётся по поставкам по Д5 теми же вызовами pick/set; после ответа показанное число равно сумме по поставкам. Отмена последнего снятия отменяет его в той поставке, которой досталась штука. Основание: Д5.
- **R11.** «Печать листа подбора» печатает лист по всей группе (Д14). Основание: макет.

### Упаковка и маркировка

- **R12.** Вкладка — рамки поставок группы в порядке Д5. Шапка рамки: «Поставка {название поставки} · WB № {номер WB} · {селлер} · Склад WB {склад} · {Склад / СЦ | ПВЗ}», где название — то, что заголовок карточки показывает как имя поставки (workspace.supply.name), номер WB — wb_supply_id (Д16), под ней «Упаковано X из Y» (X, Y — те же числа упаковки, что в карточке), чипы «Сдаём без Честного знака» и «Передана в WB» по фактам поставки. Длинная шапка переносится на вторую строку целиком, без многоточия. Неактивная рамка свёрнута, её можно развернуть стрелкой — тогда видны её короба. Основание: A, макет.
- **R13.** «Начать работу с поставкой» в шапке рамки: если у поставки нет задания упаковки — тот же запрос start-work, что у одноимённой кнопки карточки; рамка становится активной — обводка success.main 2px, шапка alpha(success.main, 0.12), кнопка меняется на «Завершить работу с поставкой»; если до этого активной была другая рамка, её работа завершается (R15). Активной может быть только одна рамка. Короб — по R17. Основание: A («как только начать работу она светло-зелёным … шапка гореть»), Д6.
- **R14.** Активная рамка содержит весь блок упаковки продукта для этой поставки (п. 2.5, Д7): те же кнопки с теми же условиями доступности, те же галки (сохраняются там же, где сейчас), то же поле скана, те же строки и кнопки строк, те же окна подтверждений и печати, и каждое действие вызывает ту же функцию с тем же запросом для этой поставки. Над полем — подпись макета «Сканы принимает только активная поставка». Основание: A («внутри этой поставки уже применяются все те правила … то же самое сканирование те же самые кнопки»), B («Все кнопки, все там запросы QR, проверки ЧЗ … Абсолютно все идентично»), C.
- **R15.** «Завершить работу с поставкой»: открытый короб поставки закрывается, подсветка снимается, рамка сворачивается; запросов к серверу нет, данные поставки не меняются. Основание: A, макет.
- **R16.** Скан при активной поставке обрабатывается существующей логикой скана только этой поставки (lookup по её supply_id, scan-auto-print / scan-kiz-reprint по её id, ЧЗ — для её активного заказа). Код, который не относится к активной поставке (Д19: не стикер её заказа, не ШК товара её заказа, не ЧЗ товара её заказа), даёт красное «Этого товара нет в поставке {номер WB}» (номер WB активной поставки, например WB-GI-283060158; Д16) и сигнал ошибки (звук — WMS-575); ни в какой другой поставке он ничего не меняет. Код, который к поставке относится, но существующая логика его не принимает (например ШК товара этой поставки при трёх выключенных галках, WMS-514 R3), даёт прежний текст карточки («Номер или стикер заказа не найден в этой поставке») с тем же сигналом ошибки. Остальные ошибки — прежними текстами продукта с тем же сигналом ошибки. Скан без активной поставки ничего не отправляет на сервер и показывает «Нет активной поставки.» с сигналом ошибки. Основание: A («если я в эту поставку попробую сканировать а, qr или шика товара который в ней здесь нет мне вот этот негативный сигнал»; «сканы которые просто в холостую они вообще ничего не делают»), C.

### Короба в рамке

- **R17.** При «Начать работу с поставкой»: если у поставки ещё нет коробов — создаётся один короб тем же запросом, что «Добавить короба» при числе 1 (с ключом повтора, сохраняемым так же, как сейчас), он становится открытым, и его QR сразу уходит в печать по Д12; если короба есть — открытым становится последний по номеру, новый не создаётся. Основание: A («Я начал работать с поставкой, у меня сразу открывается как бы типа короб … И сразу вылазит из принтера ШК этого короба»), макет.
- **R18.** В рамке под строками — «Короба · {Склад / СЦ | ПВЗ}», справа «Печать всех QR (N)» и «Создать короб» (обе видны в активной рамке). Список коробов этой поставки: «Короб {номер} · {K} шт», у открытого — « · открыт — сканы идут сюда», строкой ниже «Грузоместо WB {номер}». Кнопки короба: «Открыть короб» / «Закрыть короб», «QR», «Добавить товары», ⋮ (пункты меню короба продукта). Раскрытие ▸ показывает состав, как на вкладке «Короба». Основание: A, B, макет, Д7.
- **R19.** «Создать короб»: открытый короб поставки закрывается, создаётся новый тем же запросом (число 1), он становится открытым, его QR печатается по Д12. Основание: A («Я нажал закрыть короб, создать короб. Туда ебашу дальше»).
- **R20.** «Закрыть короб» делает короб не открытым; «Открыть короб» делает его открытым, а другой открытый короб этой поставки — закрытым. Эти кнопки работают всегда — в любом состоянии поставки до передачи, без условий заполненности; запросов к серверу нет. Основание: A («Кнопка закрыть и открыть всегда должна работать … это просто активность, куда я сканирую»).
- **R21.** «Печать всех QR (N)» в рамке — то же действие, что «Печать всех QR (N)» вкладки «Короба» карточки (openAllBoxQrPreview) для коробов этой поставки: тот же текст, то же окно печати, то же сообщение, когда QR ещё не получены, выключена при отсутствии коробов. Основание: B («аккуратную кнопочку … рядом создать короб … печать всех QR-кодов коробов»), C.
- **R22.** Заказ кладётся в открытый короб по Д8: сразу после того, как скан нашёл заказ активной поставки; тем же запросом назначения в короб; только если заказ ещё ни в каком коробе. После ответа строка короба показывает новое число штук. Заказ, уже лежащий в коробе, не перекладывается. Основание: A, Д8.
- **R23.** После того как заказ без обязательного ЧЗ положен в короб, ожидание ЧЗ по нему снимается (Д9); для заказа с обязательным ЧЗ поле ждёт ЧЗ, как сейчас. Основание: A, Д9.
- **R24.** Нет открытого короба: скан выполняет всё, что делает сейчас, заказ не кладётся в короб, под полем — «Откройте или создайте короб.». То же после «Всё упаковано»: упаковка выполняется, а заказы поставки без короба кладутся в открытый короб, если он есть. Основание: Д11, макет.
- **R25.** «Передать в WB» в шапке рамки — то же действие и то же окно подтверждения, что на вкладке «Короба» карточки, доступно так же, как там (Д13). Основание: макет, AGENTS.md.

### Невмешательство в обычную сборку

- **R26.** Не меняются: карточка одной поставки (все вкладки, кнопки, тексты, запросы, порядок и условия), окно создания одной поставки, «Добавить в существующую поставку», подбор «Отгрузки на маркетплейс», все сценарии Ozon, серверные ручки и их ответы. Новый серверный код в задаче не нужен; если исполнитель посчитает иначе — это вопрос к аналитику до реализации. Изменения фронта карточки допускаются только как режим рамки (Д18): один необязательный параметр карточки FfFbsSupplyWorkspace (assemblyFrame), который передаёт только окно сборки. Без него карточка выглядит и работает ровно как раньше; всё новое поведение (назначение в открытый короб, снятие ожидания ЧЗ у заказа без ЧЗ, «Этого товара нет в поставке …», «Всё упаковано» в открытый короб, подпись над полем, приём скана только активной рамкой) выполняется только при переданном параметре. Изменения карточки по WMS-575 регулируются WMS-575. Основание: B («Критически важно не сломать, не затронуть, не помешать ни в одном месте … обычная сборка заказов не должна вообще никак ломаться»).
