## Исходный запрос

«селлер ИП Бугаев продает через озон. Почему все эти поставки на скрине еще в статусе доставка? Мы ведь отвозили и сдавали на озон почему не меняется статус? Можно ли узнать по апи принял ли озон в итоге эти поставки?»

## Ожидаемый результат разбора

R1. Сопоставить конкретные поставки на вложениях с точным продавцом, документами WMS и отправлениями Ozon, включая дочерние отправления. Девять найденных в БД поставок нельзя без сопоставления объявить именно теми, которые показывает клиент.

R2. Установить актуальные ответы Ozon о принятии и дальнейшем движении конкретных отправлений. Различать складскую сдачу, принятие Ozon и получение покупателем. Время локального опроса само по себе не доказывает успешный ответ площадки для каждой строки.

R3. Объяснить связь статусов отправлений со статусом всей поставки и вкладкой «Завершённые», сверив код с фактически обслуживаемой production-версией. Не объяснять отсутствие поставки только ожиданием получения всех заказов покупателями без подтверждения существующего перехода статуса Ozon-поставки.

R4. Сохранить одну каноническую карточку обращения. Диагностика не разрешает менять правила завершения, интерфейс, настройки, остаток, резерв, данные или повторно сдавать отправления. Если обнаружен дефект, его конкретное ожидаемое поведение определяется отдельно до реализации.

## Наблюдения из сохранённого разбора

Проверено чтением доступного кода: frontend/src/screens/v2/FfFbsOrdersScreen.tsx использует список поставок для вкладок «В работе», «В доставке», «Завершённые», а не список отдельных заказов. backend/app/services/fbs_supply_service.py::list_supply_worklist выбирает для done только FbsSupply.status=done. fbs_autopoll_service.py вызывает обновление поставок через fbs_tracking_service только для WB; Ozon направляется в ozon_fbs_sync_service.py::sync_ozon_order_statuses, который обновляет статусы отдельных отправлений и не завершает поставку. Поиск присвоений статуса done поставкам выявил их в WB-путях; это признак отсутствующего перехода Ozon-поставки, но соответствие кода текущему production не проверено. Нельзя объяснять отсутствие поставок только ожиданием получения всех заказов покупателями.

Текущая проверка БД для ИП Бугаев А., seller_id 115c765e-bafa-4909-8dfd-0681f15cc620: девять Ozon FBS-поставок 28.09–06.10.2026, все in_delivery, last_wb_sync_at у поставок пуст. Последний сохранённый опрос нетерминальных отправлений: 06.10.2026 06:54:39 UTC. В коде эта отметка ставится и при отсутствии строки ответа Ozon, поэтому сама отметка не доказывает новый успешный ответ для каждого отправления. Данные delivering и delivered указывают на дальнейшее движение/получение этих отправлений; awaiting_deliver/posting_in_carriage само по себе не подтверждает физическое принятие Ozon. Отдельного запроса API в этом ходе не было.


Эти сведения прочитаны из текущего журнала существующей интеграции. Автоматизация Trello не повторяла запрос БД или Ozon API. Вложения source315/source316 пока не прочитаны, совпадение с девятью поставками не установлено. Соответствие прочитанного кода production ещё не подтверждено.

## Прямое поручение владельца 06.10.2026 и адресное обновление

В текущем чате владелец поручил прямо запросить Ozon API на production и прогрузить актуальные статусы поставок ИП Бугаева; отдельно проверить, исправляет ли причину ночная WMS-662. Это новое разрешение на адресное обновление, отменяющее прежнее ограничение «только диагностика» в объёме статусов.

Свежий preflight: tenant7b98a8aa-c03c-4649-9677-a645be45c622, seller115c765e-bafa-4909-8dfd-0681f15cc620, имя ИП Бугаев А. Семь числовых перевозок прочитаны через /v1/carriage/get: шесть closed, одна formed; ещё две поставки имеют PENDING-ID. Сохранённая официальная API-схема определяет closed как «завершена после приёмки».

Разрешённая операция: только шесть уже переданных поставок с точным external ID, closed, is_partial=false, has_postings_for_next_carriage=false переводятся из in_delivery в done. Не утверждается доставка покупателям. Заказы, остатки, резервы, начисления и фактическая передача не меняются. Триггеры БД просмотрены: журналируют статус и проверяют согласованность склада, нового расхода не создают.

Операционный скрипт [refresh_bugaev.py](../reviews/wms678-20261006/refresh_bugaev.py) по умолчанию читает; запись требует --apply, после внешних чтений блокирует точный scope, повторно сверяет идентичность/предыдущее состояние, затем перечитывает commit. formed и PENDING не закрываются.

Ночная WMS-662 на 245b09e27/a7c74830f проводит подтверждённый недостающий расход по отправлениям; код fbs_observed_handoff_service выставляет supply.in_delivery, не агрегирует closed перевозки в supply.done. raw carriage ветвь G4 в документе остаётся условной. Поэтому это разовое обновление устраняет зависшие статусы подтверждённых перевозок; ночная задача сама по себе не доказывает автоматическое исправление WMS-678.
