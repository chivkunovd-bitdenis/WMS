# WMS-564 · Империя ФФ: вернуть подпись «Короб № N» на коробах с системным кодом

Запись задачи: [канонический бэклог, WMS-564](../KANONICHESKIY_BACKLOG.md#wms-564).

Задача срочная, поставлена владельцем напрямую, без отдельного аналитика («быстро,
без аналитиков»). Документ и приёмка по нему в этом режиме всё равно ведутся, как
требует `CLAUDE.md`, раздел 4.

## 1. Исходный запрос владельца (дословно)

«мы вчера меняли название коробов на технические… фулфилмента империя львов, они не
понимают эти технические названия, у них расклеены уже были короб 1, короб 2… нужно
именно для империи львов вернуть ровно так, как у них было».

## 2. Контекст и подтверждённые данные

27.09.2026 задача WMS-551 (commit `7ae7d29b160859a4cfc254eaa3f0d791156f78ac`) заменила
во всех подписях входного короба приёмки (`InboundIntakeBox`) технический номер на
`internal_barcode`: на бэкенде в `backend/app/services/warehouse_map_service.py` было
`f"КР-{box_number:06d}"`, стало `internal_barcode` (объект карты/сортировки, путь
контейнера, formatter `_container_code`); на фронте в
`frontend/src/screens/ff/FfInboundRequestView.tsx` было «Короб № {box_number}»
(заголовок печатной этикетки, строка короба, чекбокс выбора, диалог наполнения,
список «На палету встанут короба: № 1, № 2»), стало показывать штрихкод. Правка
делалась ради ArtMaks — у него `internal_barcode` содержит настоящие коды клиента из
файла поставки (`WB_1627473060` и т. п.), и подмена их на порядковый номер прятала
нужную операторам информацию.

У фулфилмента «Империя ФФ» (tenant `7b98a8aa-c03c-4649-9677-a645be45c622`) таких
клиентских кодов нет: `internal_barcode` — это техническая метка, которую генерирует
сама система, а на физических коробах уже наклеены бумажные стикеры «Короб 1»,
«Короб 2»… После WMS-551 такие короба стали подписываться нечитаемым техническим
кодом вместо привычного номера.

Live read-only запрос к боевой базе (28.09.2026, `ssh root@sellerfocus.pro`,
`docker exec wms_prod-db-1 psql -U postgres -d wms`) по таблице
`inbound_intake_boxes`, сгруппированный по префиксу/длине `internal_barcode`, дал:

| Арендатор | Всего коробов | `INB-`, 18 симв. (текущий `generate_box_barcode`) | `INB-`, 16 симв. (старый генератор) | Внешние коды |
|---|---|---|---|---|
| Империя ФФ | 408 | 295 | 113 | 0 |
| ArtMaks | 66 | 6 | 0 | 60 (`WB_…`) |
| ИП Тестовый | 33 | 0 | 33 | 0 |
| AVpack | 25 | 0 | 25 | 0 |
| ПакХаб | 3 | 0 | 3 | 0 |

Важное уточнение, которое не было известно на старте задачи и обнаружено только этой
проверкой: у «Империя ФФ» технический код существует в **двух** исторических форматах,
а не в одном. Текущий генератор — `generate_box_barcode("INB")` из
`backend/app/services/box_barcode_service.py`: `INB-` + 14 символов Crockford
Base32 (`_SUFFIX_LENGTH = 14`), например `INB-41GF45KH10EK6P`. Но 113 из 408 коробов
«Империя ФФ» созданы раньше, чем `inbound_intake_box_service.py` начал использовать
этот сервис (коммит `fe4d83dc`, 26.08.2026), и несут код старого генератора
`f"INB-{uuid.uuid4().hex[:12].upper()}"` (коммит `a9cebe6b`) — `INB-` + 12
шестнадцатеричных символов, например `INB-27B9C9171F5E`. Оба формата на живых данных
чистые (100% совпадение с соответствующим регулярным выражением, проверено запросом),
третьих форматов (например промежуточного 26-символьного из `fe4d83dc`/`a053f5a6`) в
проде не осталось. Правило «проверять только текущий формат `generate_box_barcode`»,
которое было в исходной постановке, оставило бы 113 коробов «Империя ФФ» (28% из 408)
с нечитаемым техническим кодом — то есть не решило бы обращение владельца полностью.
Поэтому решающая функция распознаёт оба формата.

## 3. Принятое правило

Правило по данным, без настроек, тумблеров и признаков по арендатору: если
`internal_barcode` входного короба — это код, сгенерированный системой (совпадает
с форматом `generate_box_barcode("INB")` **или** с форматом старого генератора
`inbound_intake_box_service._new_barcode()`, который он заменил), то все подписи
короба — точно такие же, как до `7ae7d29b` (`КР-{box_number:06d}` на бэкенде,
«Короб № N» / «№ N» на фронте, включая заголовок печатной этикетки). Если код
внешний (например `WB_…`, как у ArtMaks) — остаётся поведение WMS-551 (показываем
сам код). Поле `barcode`, сканирование, идентификаторы, остатки и другие данные
не меняются нигде.

## 4. Требования

| № | Требование |
|---|---|
| R1 | Введена одна решающая функция на бэкенде (`is_generated_box_barcode` в `backend/app/services/box_barcode_service.py`) и одна на фронтенде (`isGeneratedInboundBoxBarcode` в `frontend/src/screens/ff/FfInboundRequestView.tsx`), которые по строгому формату (не `startswith`) определяют, что `internal_barcode` — код, сгенерированный системой: текущий формат `generate_box_barcode("INB")` (`INB-` + 14 символов Crockford Base32) и старый формат `inbound_intake_box_service._new_barcode()` (`INB-` + 12 hex-символов). |
| R2 | Для короба со сгенерированным кодом все места, которые менял `7ae7d29b`, показывают то же самое, что показывали до него: `code = КР-{box_number:06d}` в объекте карты/сортировки, в пути контейнера (`resolve_container_paths`) и в formatter’е `_container_code`; на фронте — заголовок печатной этикетки «Короб № {box_number}», текст строки короба «Короб № {box_number}» (код в отдельном чипе рядом не убирается — он не менялся WMS-551), скрытая подпись чекбокса «Выбрать короб № {box_number}», `boxLabel` диалога наполнения «Короб № {box_number}», элемент списка «№ {box_number}» в диалоге сборки палеты. |
| R3 | Для короба с внешним кодом (не совпадает ни с одним сгенерированным форматом, например `WB_…`) все перечисленные в R2 места ведут себя так же, как после WMS-551: показывают сам `internal_barcode`, без изменений. |
| R4 | Поле `barcode` в API карты склада для входного короба остаётся равным `internal_barcode` всегда, независимо от того, сгенерирован код или внешний — WMS-551 это уже устанавливало, WMS-564 не трогает. Идентификаторы, сканирование, размещение, остатки, состав коробов и серверные операции не меняются. |
| R5 | Правка ограничена ровно теми местами, которые менял `7ae7d29b`: три backend-формата в `warehouse_map_service.py` и четыре frontend-контекста в `FfInboundRequestView.tsx`. Никакой новой настройки, признака арендатора, флага или отдельной таблицы не вводится. Другой фронт, дизайн, текст сверх возврата прежних подписей не меняются. |
| R6 | Решающая функция — не эвристика по префиксу, а строгая проверка формата (регулярное выражение на всю строку), чтобы не принять случайный внешний код клиента, который просто начинается с `INB-`, за системный. |

## 6. Заключение

Задача решена точечно, ровно в тех местах, которые правил `7ae7d29b`: три
backend-формата подписи входного короба в `warehouse_map_service.py` и четыре
frontend-контекста документа приёмки в `FfInboundRequestView.tsx`. В обоих местах
добавлена одна небольшая решающая функция рядом с использованием, без новых
таблиц, флагов, настроек или признаков арендатора — правило работает по формату
самого `internal_barcode`, а не по тому, кто владелец короба.

Ключевая находка проверки, изменившая объём решения по сравнению с исходной
постановкой: 113 из 408 коробов «Империя ФФ» несут код не текущего, а старого
(до 26.08.2026) генератора `internal_barcode`, и правило «проверять только формат
`generate_box_barcode`» оставило бы почти треть их коробов с нечитаемой технической
строкой — то есть не выполнило бы обращение владельца целиком. Это установлено
прямым read-only запросом к продовой базе и сверкой с историей `git` двух версий
генератора, а не предположением; решающая функция поэтому распознаёт оба формата.

Backend и frontend целевые проверки (`pytest`, `ruff`, `mypy`, `tsc`, `build`) зелёные.
Дополнительно — и это не входило в обязательный список локальной проверки, но было
сделано, потому что решение видимо в интерфейсе, — правка проверена вручную в
браузере на локальном стенде (не в проде): для всех трёх категорий кода (текущий
сгенерированный, старый сгенерированный, внешний `WB_…`) визуально подтверждены
строка короба, скрытый чекбокс, диалог наполнения, диалог сборки палеты и заголовок
печатной этикетки — везде подпись совпадает с ожидаемой по требованиям.

Не выполнено: сама выкладка на прод (ждёт отдельной команды владельца «кати»),
физическая сверка на складе «Империя ФФ» с уже наклеенными стикерами и
production-проверка после выкладки. Два известных старых падения source-теста
(`data-testid`-мультисет и лимит 600 строк на файл) воспроизводятся на
`origin/etalon` без моих изменений и не являются дефектом этой задачи.
