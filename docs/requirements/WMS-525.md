# WMS-525 — одинаковый email для seller и fulfillment

## Исходный запрос и уточнения

Владелец: «у нас есть seller, и он же, по сути, fulfillment… Нужно дать возможность регистрировать с одной почтой, но входить они будут, соответственно, на разных порталах… даже если у меня отдельная вкладка открыта». Срочный клиент: Денис Веденеев, Gmail. Затем владелец уточнил: «без аналитиков… сам быстро сделай» и «только это надо сделать быстрым фиксом». Предыдущая задача про модерацию переносится за границу этого хотфикса.

## Проверенный процесс

В production уже есть `denisvideneev@gmail.com` как `fulfillment_admin` организации «ООО ФАБРИКА». В `users.email` действует одна глобальная уникальность, поэтому второй seller-аккаунт с той же почтой создать нельзя. Оба портала посылают `/auth/login`, который раньше искал одного пользователя только по email. Браузерные токены уже хранятся под разными ключами для FF и seller.

## Требования

- R1. Один email допускается в двух отдельных аккаунтах: один seller и один FF. Внутри одного портала email остаётся уникальным.
- R2. Вход на FF и `/seller/` выбирает пользователя соответствующего портала, включая случай одинакового пароля у обоих.
- R3. Восстановление пароля выбирает аккаунт текущего портала и не меняет пароль второго.
- R4. Уже открытые вкладки разных порталов сохраняют свои отдельные сессии. Существующие записи и вход без нового параметра не теряются.
- R5. После выкладки можно добавить seller-аккаунт Дениса на его существующий email. Создание конкретного seller-аккаунта требует назвать seller и его FF-арендатора; хотфикс схемы сам его не создаёт.

## Проверки

| Проверка | Требование | Вердикт |
|---|---|---|
| Один email для FF и seller; повтор в каждом портале запрещён | R1 | Подтверждено целевым API-тестом и миграцией на копии production; на production проверены ревизия `20260924_0525` и оба раздельных индекса |
| Вход в оба портала при одинаковом email и пароле; чужая роль не выбирается | R2 | Подтверждено API-тестом с `/auth/me`; legacy вызов без портала остаётся FF |
| Сброс пароля направлен на роль текущего портала | R3 | Код передаёт portal с формы в API и фильтрует по роли; отдельный тест ещё не выполнен |
| Хранение двух вкладок под разными ключами | R4 | Кодовая проверка: `wms_token_ff`, `wms_token_seller` |
| Существующий FF Дениса и возможность seller-аккаунта после миграции | R5 | Production FF-запись подтверждена; seller не создавался, поскольку не указан конкретный кабинет seller |

## Заключение

Целевые API-тесты, ruff, mypy и сборка frontend пройдены локально. Узкий хотфикс с SHA `3c90970b132144f9b375b5967b40f857c9af38a3` проверен миграцией на копии production и выложен на production 24.09.2026. После выкладки подтверждены SHA сервера, ревизия БД `20260924_0525`, индексы `ix_users_ff_email` и `ix_users_seller_email`, ответы 200 главного портала, `/seller/` и `/api/health`. Реальный вход клиента не проверялся без его пароля; seller-аккаунт ему автоматически не создавался. Схема будущей общей ветки сведена отдельной no-op миграцией `20260924_0526`, которая в текущий хотфикс на production не входила. Модерация новых FF в эту задачу не включена по последнему уточнению владельца.
