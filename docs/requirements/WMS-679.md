## Ожидаемое поведение

R1. В существующем процессе отгрузки WB FBO (у WB — FBW, «Склад WB») оператор собирает товары по накладной, затем распределяет их по существующим коробам WMS. Использовать уже имеющиеся создание, наполнение, привязку и печать коробов, дополняя только недостающую часть сценария.

R2. Сохранить существующие идентификаторы коробов, `WarehouseBox.internal_barcode`, связь с отгрузкой и селлером и действующий механизм генерации. Исходное пожелание автора — один код в WMS и WB — сохраняется. Не заменять уникальный код комбинацией полей и не создавать второй независимый внутренний код. Возможность загрузить текущие значения `WHB-…`/`INB-…` в WB должна быть подтверждена контрактом либо проверкой согласованного примера: название функции `is_wb_compatible_box_barcode` само по себе этого не доказывает.

R3. После распределения товаров нужна выгрузка XLSX для загрузки в соответствующую поставку кабинета WB. По официальной инструкции «Этап 2. Наполнение упаковки» (обновлена 05.10.2026) и её изображению шаблона поля: «Баркод товара», «Кол-во товаров», «ШК короба», «Срок годности». Строка соответствует баркоду товара в коробе и количеству; для разных баркодов одного короба повторяется его ШК. Баркод выбирается для соответствующего товара/размера WB из существующих данных, без подмены внутренним SKU. Срок годности заполняется для товаров, у которых он есть. Сохранять строковые коды без изменения ведущих нулей. Перед реализацией подтвердить точную структуру на реальном официальном XLSX-шаблоне: сам файл в этом разборе не получен, проверено официальное изображение и описание.

R4. Печать для приёмки WB должна соответствовать текущему официальному способу сдачи. Инструкция отдельно различает «ШК короба» для загрузки упаковки и «ШК короба для печати в стороннем сервисе» для этикетки. Для сдачи через ПВЗ WB требует ШК, созданные и распечатанные в WB Partners. Для других пунктов сторонняя печать использует только данные из специального столбца шаблона WB; произвольная этикетка с внутренним Code 128 не доказана как допустимая. Существующую печать внутреннего кода не объявлять печатью для приёмки WB. До разработки установить маршрут конкретной поставки и способ получения требуемых WB данных в контексте существующего короба, сохраняя его идентичность. Новые сущности, замена внутренних кодов или отдельное переименование коробов этой редакцией не согласованы.

R5. Исходное пожелание прямой передачи состава из WMS в поставку WB остаётся условной частью задачи: реализовывать её только после подтверждения официального метода **записи FBW** с составом «код короба — товарный баркод/размер — количество». На 06.10.2026 такой метод в этом разборе не установлен: текущая документация FBW недоступна (HTTP 498), сохранённая официальная спецификация не найдена. Если запись не подтвердится, описанный доступный путь — XLSX для кабинета WB; завершение проверки зависимости фиксируется отдельно в этой же задаче.

R6. В XLSX и, при доказанном API, в прямой передаче должны совпадать фактический состав коробов WMS, товары/размеры и количества в границах соответствующей отгрузки, селлера и тенанта. Чтением кода подтверждён актуальный путь `/app/ff/mp-shipments` (родительский маршрут `/app/*`, дочерний `ff/mp-shipments`); старый `ff/supplies-shipments` перенаправляет в приёмку. Экран `FfSuppliesShipmentsPage`, вариант `mp-shipments`: открыть отгрузку `marketplace_unload`, затем её подбор/короба. Новое действие выгрузки относится к этой отгрузке и её коробам. Путь API: `/operations/marketplace-unload-requests/{request_id}`.

В `MarketplaceUnloadRequest` уже есть marketplace, seller_id, external_supply_id, wb_mp_warehouse_id и плановая дата; фактического типа точки сдачи ПВЗ/СЦ эта модель не устанавливает. `MarketplaceUnloadBox` связывает отгрузку с `WarehouseBox`; `MarketplaceUnloadBoxLine` хранит product_id и quantity. Сервисы уже создают, наполняют и привязывают короба. «Загрузить по накладной» сейчас импортирует формат «Штрих-код комбайн», а не официальный шаблон WB. Это действие не следует менять на экспорт и не следует называть новой возможностью.

Текущая печать `confirmPrintBoxBarcode` берёт internal_barcode, рисует Code128 и печатает `layout: internalBox`. Это внутренний складской код. Название `is_wb_compatible_box_barcode` не подтверждает приём этикетки площадкой. Экспорту нужен WB-баркод конкретного варианта товара: в проекте есть Product.wb_barcode, wb_chrt_id/wb_size, ProductBarcode и существующий каталог селлера; SKU и Ozon-код заменой не являются. `Product.wb_shelf_life` импортируется из характеристики карточки «Срок годности», а не хранит дату окончания партии; её нельзя превращать в дату произвольно.

Живой экран в браузере в этом аналитическом ходе **не открыт**: callable браузерного инструмента нет, и локальная авторизованная тестовая сцена координатором не предъявлена. Пути и действия установлены чтением кода, внешний вид не засвидетельствован. Перед реализацией UI разработчик обязан открыть тестовый экран и сравнить с «Ячейками»/«Расчётами»; это явно переданная незавершённая проверка, не основание менять дизайн вслепую.

### Решения аналитика и первичные основания

Используется уже существующая модель коробов; новый экспорт — чтение состава. Подтверждённый первичный источник: [инструкция WB «Этап 2. Наполнение упаковки»](https://seller.wildberries.ru/instructions/ru/ru/material/step-two-fbw-package-filling), актуальная отметка 05.10.2026. Она разрешает собственный ШК в загрузке, различает его и QR для сдачи, указывает отдельные правила ПВЗ. 07.10 получен подлинный бинарный шаблон; его обезличенная фикстура и точная трансформация сохранены в `docs/evidence/WMS-679/`, а факты структуры — в `TEMPLATE-RESOLUTION.md`. Реальные коды и идентификатор поставки не публикуются.

Обнаружен точный путь получения шаблона в **публичном официальном коде** WB Partners: `supply-detail-packaging-nano/v1.0.66`, `645.chunk.fa4c5ad064581d15d891.js`; конфигурация `vol20/menu/v0.0.1/config.json` задаёт `ENDPOINT_SHK_DOWNLOAD_EXCEL = https://seller-supply.wildberries.ru/ns/sm-box/supply-manager/api/v1/box/getTemplateXLS`. Клиент делает JSONRPCRequest с `{params:{incomeID: ID поставки}}`, `credentials: include`; получает `{file,mime}`, декодирует base64 и сохраняет `shk-excel.xlsx`. Полученный через этот путь файл подтверждает лист `Sheet1`, A1:E3 и пять точных заголовков, включая колонку внешней печати. В публичном модуле также найдена обработка ошибки о запрете самостоятельно задаваемого префикса WB_; точный алфавит/длина и принятие WHB/INB всё ещё не подтверждены. Это основания для исследования, а не публичный API-контракт автоматизации кабинета.

[Официальная страница API FBW](https://dev.wildberries.ru/openapi/orders-fbw) и кандидаты YAML RU/EN снова вернули 498; первичное поисковое представление официальной страницы описывает чтение supplies/package, но снимок старый и полноту актуального API не доказывает. В стороннем поисковом результате видны методы добавления товаров в черновик: это полезная подсказка поиска, не допустимое доказательство контракта упаковки. Нельзя сделать вывод «у WB вообще нет записи FBW», нельзя подменить передачу коробов записью товаров черновика или внутренними endpoint кабинета. Координатор добавляет независимое исследование официальной спецификации и шаблона. Новый узкий отчёт: [ANALYST-RECOVERY.md](../research/wms679-20261006/ANALYST-RECOVERY.md).

### Требования действующей редакции

**R1. Сборка существующей отгрузки.** Оператор открывает WB FBO/FBW отгрузку на `ff/mp-shipments`, собирает по её накладной и распределяет товары существующими действиями в существующие короба. Повторное открытие показывает тот же сохранённый состав и связи. Новый экспорт не требует второго документа, новой поставки, отдельного резерва или пересборки коробов. Основание: исходное описание и правило проекта об использовании существующего процесса.

**R2. Идентичность короба.** Получение файла и внутренняя печать используют существующий WarehouseBox/internal_barcode связанного короба, не генерируют замену, не меняют legacy INB-код и не создают вторую складскую сущность. Один и тот же код WMS записывается строкой в подтверждённую колонку «ШК короба». Допустимость загрузки конкретных WHB/INB и допустимость печатной этикетки WB проверяются раздельно; локальная выгрузка не выдаёт их за внешне принятые. Основание: исходное пожелание одного кода, подлинный шаблон и прямое уточнение владельца.

**R3. Точный XLSX.** В контексте коробов WB-отгрузки оператор скачивает XLSX с официальной структурой: видимый `Sheet1`, строка заголовков A1:E1 и ровно пять колонок «Баркод товара», «Кол-во товаров», «ШК короба», «Срок годности», «ШК короба для печати в стороннем сервисе». В подлинном образце A2/A3 — пустая строка, B2/B3 — числовой `0`, C/E — строки, D пуста; обезличенная фикстура воспроизводит это без приватных кодов. Товарный и коробочный коды выгрузка пишет строками, количество — целым числом. В образце нет заполненной даты, поэтому её формат не назначается догадкой. Поле внешней печати не заполняется самодельным QR или копией internal_barcode. Основание: инструкция, подлинный шаблон и требование владельца о точном XLSX.

**R4. Источник и строки состава.** На каждую непустую строку «короб — конкретный товар/вариант WB» выгрузка передаёт фактическое quantity из MarketplaceUnloadBoxLine; разные баркоды одного короба повторяют его ШК. Пустые короба не создают товарных строк. План отгрузки, подобранное количество и ProductBarcodes не становятся независимыми источниками количества. Итоговая сумма экспортированных штук равна сумме фактического состава отгрузки, данные второго документа не примешиваются. Основание: запрос о совпадении состава и инструкция WB.

**R5. Баркоды и ошибки данных.** Выгрузка выбирает существующий основной WB-баркод именно product_id/размера из отгрузки; при отсутствии основного допустим единственный однозначный WB-баркод этого варианта. Не брать случайный баркод из общей карточки с несколькими размерами. Все товарные и коробочные коды — строковые ячейки, ведущие нули/символы сохраняются, код с `=` не превращается в Excel-формулу. При отсутствии/неоднозначности WB-баркода или связи с WarehouseBox файл не выдаётся как полный: в том же документе указаны конкретный товар/короб и причина. Состав остаётся сохранённым, складские действия продолжаются; после исправления исходных данных можно повторить экспорт. Это техническое условие достоверного файла, не запрет отгрузки/подбора. Основание: состав WB и запрет подмены данных.

**R6. Сроки годности.** Официальная инструкция WB прямо говорит: «Поле “Срок годности” обязательно нужно заполнить для товаров, у которых он есть»; при нескольких партиях указывается минимальная дата. Для товара без срока D остаётся пустой. В WMS нет даты окончания партии: `Product.wb_shelf_life` — только текстовая длительность и не преобразуется в дату. Поэтому при непустом `wb_shelf_life` экспорт также оставляет D пустой, но в контексте документа честно предупреждает, что перед загрузкой в WB оператор должен вне WMS внести фактическую дату партии; скачивание не блокируется и не называется полностью готовым для WB. Это использует существующий ручной шаг WB «указать дату окончания срока годности самостоятельно», не вводит новую таблицу/поле или выдуманную дату. Основание: официальный текст `evidence/seller-package-filling-text.txt`, «Шаг 2. Укажите сроки годности», и правило проекта не создавать лишнюю блокировку.

**R7. Чистое чтение и восстановление выгрузки.** Экспорт, повторная выгрузка после потери ответа и два параллельных скачивания не меняют состав, статус, резерв, остаток, расположение либо внешний WB. Каждый успешный файл соответствует одному согласованному снимку состава, без смеси старой и новой половины одновременной правки. Сбой формирования/скачивания виден в контексте документа, после него доступны повтор и работа с другой отгрузкой. Основание: правила проекта и повторяемая выгрузка.

**R8. Правдивая внутренняя печать.** Печать существующего internal_barcode сохраняет складское назначение и обозначается как «Внутренний ШК WMS», если её текущее нейтральное название в WB-контексте смешивает назначения. Не заявлять, что такой Code128 — этикетка приёмки WB. Локально проверяется содержимое макета/число страниц и отсутствие побочных записей; бумага отдельно. Основание: прямое уточнение владельца и подтверждённый текущий путь печати.

**R9. Этикетка WB и маршрут.** Для ПВЗ допустим только документ печати, созданный WB Partners. Для иных точек допустима печать в WB Partners либо QR, кодирующий **точную** строку «ШК короба для печати в стороннем сервисе», полученную WB для этого короба/поставки. Внутренний WHB/INB и вручную собранный набор полей эту строку не заменяют. По неизвестному типу точки не выбирать маршрут сторонней печати автоматически. Пока подтверждённого получения печатных данных/связи с коробом нет, WMS не предоставляет ложную кнопку «Этикетка WB готова»; существующая внутренняя печать и экспорт не запираются. Для локального релиза разрешён честный путь загрузки состава XLSX с последующей печатью в WB Partners; печать WB из WMS остаётся не выполненной частью исходного пожелания, а не засчитывается этим обходным путём. Основание: официальное правило WB и исходный запрос. Точная зависимость B2 ниже.

**R10. Прямая передача только по доказанному контракту.** API-передача состава коробов не входит в исполняемый интерфейс до подтверждения официального публичного метода записи упаковки FBW с кодом короба, баркодом/размером и количеством. При неподтверждённом методе текущая реализация предоставляет XLSX, не вызывает FBS/trbx, не использует cookie-методы WB Partners и не показывает сообщение об отправке состава в WB. Наименование POST supplies как чтения сохраняется. Если координатор подтвердит нужный метод, до тестов дописываются точные тело, идентификатор, права, восстановление неизвестного результата и проверки повторов; нынешний раздел не даёт разработчику догадаться самому. Основание: прямое решение владельца о честном XLSX fallback (резервном пути).

**R11. Изоляция и существующие права.** Скачивание разрешено пользователю с существующим доступом к конкретной WB-отгрузке в своём тенанте (клиентском контуре); чужая отгрузка/селлер не выдаёт данные в XLSX или печати. Новый экспорт WB не появляется у Ozon и FBS; соседние операции, импорт по накладной и внутренние коды сохраняют поведение. Основание: границы клиента и WB-охват запроса.

**R12. UI в контексте документа.** Действие скачивания размещается рядом с существующими коробами открытой WB-отгрузки, использует тему/компоненты текущего приложения. Существующая «Загрузить по накладной» остаётся импортом. После скачивания оператор остаётся в той же отгрузке. Ошибка не сбрасывает документ/выбор и не ломает весь экран; устаревший ответ документа A не заменяет состояние открытого B. Длинные названия и ошибки читаются без наложения кнопок. Основание: правила проекта; применимые случаи B01, B20 из библиотеки сбоев.

### Точные оставшиеся зависимости, а не выдуманное продуктовое решение

**B1 — принятие загрузочного кода WB.** Структурная часть закрыта: подлинный `shk-excel.xlsx` сохранён локально, а его обезличенная фикстура — в Git. Реальные строки образца не являются WHB/INB; полный валидатор, уникальность в поставке и фактическое принятие existing WHB/INB не доказаны. Это не блокирует локальную реализацию и её контрактные тесты, но остаётся ручной внешней проверкой по отдельному разрешению.

**B2 — внешний QR и маршрут.** Подлинный шаблон подтверждает отдельную колонку «ШК короба для печати в стороннем сервисе», но не источник её значения: в двух строках образца оно совпадает с загрузочным кодом, что не является общим правилом. В существующей модели не подтверждён тип точки сдачи. Из этого не следует создать новую таблицу маршрутов, скопировать internal_barcode или заменить внутренний код. Локальные R8 и честный XLSX-путь определены; интегрированная WB-печать не готова к реализации без данных WB и связи с коробом.

**B3 — дата окончания срока товара.** Официальная обязательность подтверждена, но в просмотренных моделях нет даты партии: есть лишь характеристика длительности в карточке. Это не блокирует скачивание и не разрешает преобразовать длительность в дату. До появления подтверждённого источника WMS оставляет D пустой и предупреждает о ручном завершении по фактической партии перед загрузкой в WB; будущая автоматизация даты потребует отдельного источника, а не нового вычисления.

**B4 — актуальный официальный API упаковки.** 498 — недоступность чтения сайта из этого окружения. Старый поисковый снимок и наличие внутренних методов кабинета не доказывают наличие либо отсутствие публичной записи упаковки. Обязательная локальная реализация без подтверждения записи — XLSX; реализация API по неподтверждённому контракту запрещена новым поручением. Координатор дополняет исследование до фиксации контрактов.

### Сверка с исходным запросом

Сборка по накладной и имеющиеся короба → R1; один внутренний код и совпадение кода загрузки → R2; файл WB → R3–R7; генерация/печать кода → R8–R9 с явной внешней зависимостью, без скрытой отмены пожелания; второй способ передачи → R10 с разрешённым XLSX-путём при неподтверждённом API; совпадение отгрузки/селлера → R4–R5/R11. R7/R12 следуют правилам проекта и обеспечивают проверяемое продолжение после ошибки. Новые учёт количества, резервы, маршруты и производственные проверки не добавлены. WMS-680, бэклог и progress не изменялись этим аналитиком.

### Handoff тестировщику и root

Заменяющий аналитик передаёт тестировщику все R1–R12 и C1–C14: шаблон больше не нужно воспроизводить по догадке, используется `docs/evidence/WMS-679/wb-fbw-shk-excel-template-anonymized.xlsx`. В тестах нельзя публиковать или восстанавливать реальные коды, приписывать принятие WB WHB/INB, создавать QR, вызывать кабинетные/cookie/FBS методы либо заполнять E копией C. C6 обязан охранять одновременно пустую D, отсутствие превращения `wb_shelf_life` в дату и неблокирующее предупреждение для товара со сроком.

Для начала контрактных тестов новых разрешений не нужно. Фактическая загрузка XLSX и приём WHB/INB WB остаются честно непроверенными, потому что потребовали бы изменения живой поставки. Прямая передача и WB-печать остаются отложенными до официального контракта/данных WB; это не повод подменять их FBS или кабинетными методами.

### Заключение по актуальной постановке
