## Ожидаемое поведение

R1. В существующем процессе отгрузки WB FBO (у WB — FBW, «Склад WB») оператор собирает товары по накладной, затем распределяет их по существующим коробам WMS. Использовать уже имеющиеся создание, наполнение, привязку и печать коробов, дополняя только недостающую часть сценария.

R2. Сохранить существующие идентификаторы коробов, `WarehouseBox.internal_barcode`, связь с отгрузкой и селлером и действующий механизм генерации. Исходное пожелание автора — один код в WMS и WB — сохраняется. Не заменять уникальный код комбинацией полей и не создавать второй независимый внутренний код. Возможность загрузить текущие значения `WHB-…`/`INB-…` в WB должна быть подтверждена контрактом либо проверкой согласованного примера: название функции `is_wb_compatible_box_barcode` само по себе этого не доказывает.

R3. После распределения товаров нужна выгрузка XLSX для загрузки в соответствующую поставку кабинета WB. По официальной инструкции «Этап 2. Наполнение упаковки» (обновлена 05.10.2026) и её изображению шаблона поля: «Баркод товара», «Кол-во товаров», «ШК короба», «Срок годности». Строка соответствует баркоду товара в коробе и количеству; для разных баркодов одного короба повторяется его ШК. Баркод выбирается для соответствующего товара/размера WB из существующих данных, без подмены внутренним SKU. Срок годности заполняется для товаров, у которых он есть. Сохранять строковые коды без изменения ведущих нулей. Перед реализацией подтвердить точную структуру на реальном официальном XLSX-шаблоне: сам файл в этом разборе не получен, проверено официальное изображение и описание.

R4. Печать для приёмки WB должна соответствовать текущему официальному способу сдачи. Инструкция отдельно различает «ШК короба» для загрузки упаковки и «ШК короба для печати в стороннем сервисе» для этикетки. Для сдачи через ПВЗ WB требует ШК, созданные и распечатанные в WB Partners. Для других пунктов сторонняя печать использует только данные из специального столбца шаблона WB; произвольная этикетка с внутренним Code 128 не доказана как допустимая. Существующую печать внутреннего кода не объявлять печатью для приёмки WB. До разработки установить маршрут конкретной поставки и способ получения требуемых WB данных в контексте существующего короба, сохраняя его идентичность. Новые сущности, замена внутренних кодов или отдельное переименование коробов этой редакцией не согласованы.

R5. Исходное пожелание прямой передачи состава из WMS в поставку WB остаётся условной частью задачи: реализовывать её только после подтверждения официального метода **записи FBW** с составом «код короба — товарный баркод/размер — количество». На 06.10.2026 такой метод в этом разборе не установлен: текущая документация FBW недоступна (HTTP 498), сохранённая официальная спецификация не найдена. Поэтому нельзя обещать API-передачу или утверждать, что API отсутствует. Не подменять её FBS supplies/trbx/стикерами или чтением FBW-поставок. Если запись не подтвердится, описанный доступный путь — XLSX для кабинета WB; завершение проверки зависимости фиксируется отдельно в этой же задаче.

R6. В XLSX и, при доказанном API, в прямой передаче должны совпадать фактический состав коробов WMS, товары/размеры и количества в границах соответствующей отгрузки, селлера и тенанта. Использовать существующий состав, не заводить второй источник количества. Экспорт, распределение и печать не меняют остаток; это не проведение отгрузки.

## Доказательства и зависимости

- [Официальная инструкция WB, обновлена 05.10.2026](https://seller.wildberries.ru/instructions/ru/ru/material/step-two-fbw-package-filling): XLSX и правила печати; снимок, извлечённый текст, изображения и контрольные суммы сохранены в отчёте.
- [Официальная документация FBW](https://dev.wildberries.ru/openapi/orders-fbw): получен HTTP 498 и экран проверки браузера, содержание контракта сегодня не прочитано. Точный метод записи и его ограничения остаются неизвестными.
- В коде `fetch_supplies_list` использует `POST /api/v1/supplies` как **чтение** списка FBW для импорта. Метод POST не означает запись. Это факт кода, не доказательство полноты API WB.
- Не установлен контракт допустимого алфавита и длины самостоятельно загружаемого ШК. Проверка WMS «6–30, латиница/цифры/_/-, без WB_» остаётся локальным правилом кода, не подтверждённым в этом разборе актуальным требованием WB.
- До реализации нужны реальный официальный XLSX и подтверждение совместимости текущих кодов; маршрут сдачи определяет допустимую печать. Это зависимости, не новые блокировки текущей складской работы.

## Заключение

Аналитический проект существующей WMS-679 уточнён по актуальной официальной инструкции WB и текущему коду. XLSX подтверждён как доступный способ загрузки состава в кабинет, API записи FBW остаётся непроверенной зависимостью. Важное несоответствие исходного пожелания: внутренний ШК WMS и содержимое этикетки для приёмки WB нельзя автоматически считать одним значением.
