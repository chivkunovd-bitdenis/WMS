# WMS-577 — Окно «Остаток для FBS» не сохраняет лимит при отрицательном «Доступно» (P2-2)

## Исходная находка

Независимое ревью 28.09.2026, `docs/reviews/artifacts/release-audit-20260928/review-opus-all.md`,
раздел P2-2 («Окно «Остаток для FBS» не даёт сохранить лимит у товара с отрицательным «Доступно»»).

## Нарушенные требования

WMS-469 R12 — ручной ввод числа больше остатка обрезается до максимума без блокировки сохранения.
WMS-530 review F2 — сервер намеренно отдаёт окну «Доступно» как есть, включая отрицательное
(перебронирование). Фронт (`fbsStockBlocks.ts`: `unitsCap`/`clampUnits`) строил потолок ручного
числа по этому же (потенциально отрицательному) значению вместо `max(0, …)`, поэтому при
отрицательном «Доступно» поле принимало отрицательное число, а сервер (`ProductFbsBindingRuleBody`,
требует `value ≥ 0`) отвечал 422 — не сохранялся даже явный ноль.

## R (требования этого исправления)

R1. Потолок ручного числа не может быть отрицательным: при отрицательном «Доступно» поле
    встаёт на 0 (максимум), как и предусмотрено WMS-469 R12, а не на отрицательное число.
R2. Явный ноль при отрицательном «Доступно» тоже сохраняется без 422.
R3. Отрицательное «Доступно» само по себе никуда не пропадает — его по-прежнему показывает
    строка трёх чисел (`blockTotals`), это не менялось и менять не требовалось.
R4. При обычном (неотрицательном) «Доступно» поведение поля не меняется.
R5. Сервер не трогать: F2 (WMS-530) с осознанным решением «не обрезать» — единственное, что
    менялось на сервере, это поведение фронта.

## Реализация

`frontend/src/screens/ff/products-fbs/fbsStockBlocks.ts`, функция `unitsCap`: потолок ручного
числа теперь `Math.max(0, picked.free)` — товар-ограничитель по-прежнему выбирается по настоящему
(не обрезанному) остатку, чтобы подпись называла правильный товар, а обрезается только
возвращаемое наружу число. `clampUnits` и `useEffect`-переклэмп при смене склада ФФ в
`FbsStockDialog.tsx` (line 254-257) используют `unitsCap` и получили исправление автоматически —
отдельно их трогать не пришлось. Попутно поправлен комментарий у `blockTotals`, который до сих пор
утверждал, что сервер обрезает `free_stock` нулём (это уже не так после F2 — проверено чтением
`backend/app/services/fbs_stock_rule_service.py:638-643`: `free_stock` = `total.available`
неотрезанным, отрезана только отдельная база публикации `available_for_checks`).
