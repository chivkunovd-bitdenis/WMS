# WMS-483 · WB FBS: повторно передавать нулевой остаток каждые 10 минут

## Исходный запрос и уточнения

Владелец, 20.09.2026, дословно:

> Здесь вот эту задачу, короче. Есть проблема в том, что WB иногда сам в плюс корректирует остатки по FBS. Соответственно, если товар на полке закончился, в кабинете он может всё равно приплюсовать и упадет заказ на то, чего нет. Поэтому если на товаре стоит ноль на остатке, соответственно нужно... да даже не так. Мы... ну да, вообще-то да. Короче, если ставить ноль на остатке, то мы транслируем каждые 30 минут, каждые 10 минут давай, этот ноль в кабинет селлера. То есть мы их на всякий случай обнуляем.

Последующих уточнений владельца пока нет. Внутри исходного сообщения 30 минут заменены окончательным выбором **10 минут**.

## Существующий процесс и цель

Оператор ведёт физический товар и его остаток в WMS; система рассчитывает свободное количество с учётом резерва и публикует FBS-остаток по привязке склада селлера к WB. Управление публикацией остаётся у существующих галок склада и товара и действующего правила распределения; новое действие на экране не запрошено.

До реализации компонент `frontend/src/screens/ff/products-fbs/FbsStockDialog.tsx` в окне «Остаток для FBS» показывал поштучное поле под каждым складом и подставлял число 0, если ключа склада не было в `unitsByWarehouse`. `NumberInput` уже умел показывать пустое значение. При подготовке уточнения после первого ревью попытка открыть существующую production-вкладку WMS в браузере дважды завершилась таймаутом средства компьютерного управления. Позднее изолированный preview этой ветки на `http://127.0.0.1:15183/products.html` удалось открыть: на выдуманных данных пустое поле, явный 0 и очистка читаемо различаются в том же окне. Preview не подключён к реальному API и не подтверждает состояние production.

По проверенному коду `backend/app/services/fbs_stock_rule_service.py` (`publish_amounts_for_binding`, `_has_rule`) к публикации допускаются только активные привязки с `stock_sync_enabled` и товар с заданным правилом. Количество рассчитывается из `fbs_stock_breakdown_by_product(...).free`. `backend/app/services/fbs_stock_sync_service.py` (`_build_publish_plan`) после подтверждённого нуля не включает его в следующий план отправки. `backend/app/services/fbs_autopoll_service.py` (`reconcile_fbs_stocks_all_sellers`) регулярно запускает общую сверку; расписание `fbs-stock-reconcile` в `backend/app/celery_app.py` берёт интервал из `backend/app/core/settings.py`, где значение по умолчанию — 300 секунд. Это описание исходного кода, а не подтверждение текущего расписания production.

Цель: если свободных единиц управляемого товара для WB больше нет, очередная самовольная прибавка в кабинете WB не должна оставаться без ответа WMS дольше следующего десятиминутного цикла отправки нуля. Передача означает реальный запрос изменения остатка в WB, а не только чтение его кабинета или запись локального статуса.

## Требования

**R1. Область действия.** Для каждой активной WB-привязки с включённой трансляцией и товара этого селлера с включённой товарной публикацией система определяет свободный остаток и применяет существующее правило расчёта. Десятиминутное обнуление действует, когда (а) свободный остаток для этой привязки равен нулю и для товара задано действующее правило публикации по ней либо (б) оператор явно установил для неё лимит `0 шт.` в поштучном режиме при включённой публикации, даже если физически товар ещё есть. Отсутствующее распределение по привязке не считается явно установленным нулевым лимитом. Основание: «если ... ноль на остатке» и защита от заказа, который нечем обеспечить; существующий расчёт свободного остатка и правило WMS-376.

**R2. Первая и повторные отправки.** Когда остаток управляемой карточки достигает нуля по R1 после движения, резерва или сохранения лимита оператором, существующий событийный путь отправляет первый ноль после сохранения изменения, не дожидаясь планового цикла. Пока условия R1 сохраняются, система повторно отправляет ноль в кабинет WB каждые 10 минут, даже если ноль уже был подтверждён ранее или локальная запись последней отправки содержит ноль. Это действует и для управляемого товара, по которому ранее не было подтверждённой публикации: отсутствие предыдущего положительного числа не подавляет отправку нуля. Интервал относится к повтору нулей и не требует замедлить существующую общую сверку остальных остатков. Основание: окончательное «каждые 10 минут ... этот ноль в кабинет селлера», описанная владельцем самовольная прибавка WB и существующий событийный путь публикации.

**R3. Сохранение границы управления.** Товар без действующего правила публикации по данной привязке, с выключенной товарной публикацией, привязка WB с выключенной трансляцией или неактивная привязка не становятся объектом периодического обнуления. `0%` в процентном режиме остаётся отсутствием правила по WMS-376; WMS-483 не решает открытый вопрос WMS-385 о поведении при установке `0%`. В поштучном режиме явно установленный оператором лимит `0 шт.` отличается от отсутствующего распределения для привязки. Остаточная строка старого долевого правила с `quantity=0` не считается доказательством такого указания: если при переходе на штуки оператор не выбрал данную привязку для поштучной публикации, периодический ноль на неё не идёт. При выключении публикации сохраняется существующее отдельное правило переходного нуля, но после перехода новые десятиминутные отправки не идут. Признак «склад обслуживается» относится к приёму заказов и сам по себе не включает и не исключает публикацию. Основание: зафиксированные правила WMS-376 и WMS-385, защита чужих или неуправляемых карточек.

**R4. Изменение количества.** Если свободный остаток стал положительным и оператор не задал явный лимит `0 шт.` для данной WB-привязки, повторная отправка нуля по R2 прекращается; далее действует обычный расчёт публикуемого количества по текущему правилу распределения. Если рассчитанное количество равно нулю при положительном свободном остатке только из-за доли, округления или распределения между складами, новый десятиминутный режим к такому нулю не применяется. Если оператор меняет явный лимит `0 шт.` на положительный, также возобновляется обычная публикация. Основание: запрос о нулевом остатке, существующее управление лимитом и обычное распределение.

**R5. Подтверждение и сбои.** Для каждого планового нуля сохраняется существующая схема отправки WB и проверки ответа чтением из WB. Успешным считается только подтверждённый ноль; при отказе отправки, несовпадении прочитанного количества либо потере ответа состояние не обозначается подтверждённым без проверки. Если срок повтора пропущен из-за отказа WB, занятой синхронизации, сбоя worker или потери отложенной задачи, обязательство отправить ноль остаётся просроченным: после восстановления доступности система повторяет попытку при первой доступной обработке, не ждёт ещё один полный десятиминутный интервал от неудачи и не теряет дальнейшие повторы, пока действует R1. Отдельная ошибка одного товара, склада или селлера не прекращает обработку остальных. Гарантия R2 «не позже 10 минут» относится к штатной работе с доступными WB, worker и синхронизацией; при реальном отказе внешней системы подтвердить её выполнение невозможно, и такой сбой должен быть виден как сбой, а не как успешная десятиминутная отправка. Основание: существующий контракт `sync_binding_stocks` и необходимость реально обнулить WB после его корректировки.

**R6. Остальные направления и состояние публикации.** Десятиминутное повторение нуля относится к WB FBS. Оно не меняет публикацию положительного количества, расчёт общего свободного остатка, сохранённые доли по складам WB/Ozon при переключении режима и правила Ozon. Узкий проход повторного нуля обновляет результат своих позиций, но не объявляет всю привязку успешно синхронизированной и не стирает сводную ошибку другого товара. По одинаковому товару разных селлеров и привязок отправка адресуется только соответствующему кабинету и складу WB. Основание: запрос владельца относится к WB FBS; существующие границы арендатора, селлера и привязки и запрет побочных изменений соседнего процесса.

**R7. Нулевой лимит в существующем окне остатков.** В окне «Остаток для FBS» в режиме «Остаток по штукам» поле склада, для которого лимит не задан, остаётся пустым и не превращается в заданный ноль при простом открытии, переключении режима или сохранении другого склада. Если оператор вводит `0`, окно показывает `0`, а сохранение передаёт в правило ключ этого склада со значением 0 и режим штук. Если оператор очищает поле, ключ удаляется из правила. После закрытия и повторного открытия окна пустое поле остаётся пустым, явный 0 остаётся 0; результат обычной публикации и периодического нуля соответствует R1–R3. Поведение одинаково при открытии общего окна из каталога товаров и из `/ff/fbs-stock`: оба пути используют одно окно, а сохранение с любого из них должно передавать `units_mode` и `units_by_warehouse` без подмены долевым правилом. Отдельный экран и новое действие не требуются. Основание: различие между «не задавали» и «оператор поставил ноль» в запросе и защита от публикации по чужой карточке по WMS-376.

## Решения аналитика и вопросы

**Решение.** Под «ноль на остатке» для публикации понимаются два управляемых состояния: отсутствие **свободной** единицы по действующему расчёту WB либо явное указание оператором `0 шт.` для конкретной WB-привязки в поштучном режиме. Первое охватывает физический ноль и ситуацию, когда весь физический остаток уже зарезервирован: в обоих случаях новый WB-заказ нечем обеспечить. Второе отражает прямой нулевой лимит оператора даже при положительном физическом остатке. Код `split_amounts` в обоих случаях рассчитывает ноль, но для отсутствующего распределения тоже подставляет ноль; это не доказательство намерения управлять данной карточкой, поэтому повторная отправка там не вводится. Признак явного поштучного нуля — сохранённое указание оператора именно для этой привязки, а не само наличие строки `FbsBindingStockPool`: строка может сохраниться после долевого режима, где `quantity` автоматически становится 0. В существующей таблице пула оправдан один признак `units_configured`: он хранит присутствие ключа поштучного правила независимо от значения `quantity`, не создавая второй журнал остатка. Новый явно сохранённый ключ, включая 0, помечается как заданный; неуказанный ключ снимает этот признак. Для исторических строк положительный лимит сохраняется как заданный, а исторический 0 без доказанного действия оператора остаётся не заданным. Следствие: если исторический ноль действительно был намеренным лимитом, его нужно явно снова указать в окне, поскольку по старым данным это намерение не восстановить; до этого он не включает периодическое обнуление. При чтении правила в окно и при сохранении через API `units_by_warehouse`/`units_remaining_by_warehouse` содержат только явно заданные и сохранённые исторические положительные ключи. `0%` в процентном режиме остаётся отдельной неразрешённой развилкой WMS-385. Применён подход из хорошего случая 1 `owner-cases.md`: резерв уменьшает общий свободный остаток, видимый WB и Ozon, при раздельном управлении публикацией площадок.

**Решение по времени.** Ожидание 10–15 минут после первого событийного нуля при штатной работе не выполняет окончательный выбор владельца «каждые 10 минут». Если первый ноль ушёл между тактами существующего общего пятиминутного прохода, подтверждённый ноль не должен отложить следующий реальный запрос WB за отметку `+10 минут`. Новое правило задаёт срок повторной отправки нуля; оно не требует замедлять общий проход для других остатков. Реальный сбой worker, замка или WB отделяется от штатного опоздания: нельзя считать неудачу подтверждённым нулём, обрывать расписание после неё или начинать новый десятиминутный отсчёт от отказа. После восстановления просроченный ноль отправляется при первой доступной обработке, а общий проход страхует потерянный таймер.

**Вопросов, препятствующих постановке, нет.** Точное техническое расписание может использовать существующий цикл или иной способ, но наблюдаемый контракт R1–R6 обязателен. Открытое решение по `0%` остаётся в WMS-385 и не подменяется этой задачей.

Проверки проводить в тестовой среде с подставным WB, который фиксирует отправку и возвращает заданный остаток при чтении. Сокращение времени циклов допустимо только в тесте; проверка должна различать **фактический запрос отправки** и одну лишь локальную запись. Ниже раздельно отражены адресные автотесты с управляемыми часами и кликовая проверка изолированного frontend → API → SQLite → синтетический WB.

## Заключение

Локальная приёмка основного сценария **пройдена с указанными в C3, C8 и C11 границами проверки**. После независимых ревью кода локальный браузер прошёл оба входа в существующее окно на изолированном синтетическом контуре `frontend → API → SQLite → подставной WB`: у товара с 50 свободными штуками сохранён явный ноль только для WB-склада 501001, ответ API содержал `units_mode=true` и `units_by_warehouse={"wb:501001":0}`, подставной WB зафиксировал `PUT amount=0` и подтверждающий `POST` чтения. Повторное открытие показывало 0 на WB 501001 и пустые поля на WB 501002 и Ozon 501001; очистка через второй вход удаляла ключ из API и оставалась пустой после открытия.

Первый прогон обнаружил, что после очистки явного нуля и повторного ввода 0 прежнее подтверждение подавляло событийный PUT. Исправление backend в коммите `03870a73` прошло адресный тест и независимое ревью. При повторной кликовой проверке через `/ff/fbs-stock` последовательность 0 → пусто → 0 в пределах десяти минут дала **два новых PUT нуля и два подтверждающих POST** в журнале подставного WB; API вновь хранит ровно `{"wb:501001":0}`, окно показывает 0 у первого WB и пустое поле у второго. Остальные вердикты в таблице относятся к адресным автотестам и указанным частям браузерной проверки. Живой Celery worker в течение десяти минут, реальный кабинет WB и production не проверялись; C3, C8 и C11 не воспроизводились целиком кликовым либо отказным сценарием.
