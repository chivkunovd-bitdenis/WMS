# WMS-616 · Раздел FBS в кабинете селлера

Запись задачи: [канонический бэклог, WMS-616](../KANONICHESKIY_BACKLOG.md#wms-616).

## 1. Исходный запрос и уточнения

То есть новый — это новый, то, что у нас в работе у фулфилмента — это в работе, значит собрано, да, в поставку. Дальше там дальше статусы должны быть с VB, типа передано, там отгружено. Ой, как это, блядь, там, в сортировке, да, ну вот это всё. Вот, либо там отменён, например. Соответственно, там должно синхронно с VB, так же как у VB, на экране отображаться, типа время, когда заказ пришёл и когда он, ну сколько часов он уже в сборке. Вот. На Ozon-овском заказе, смотри, Ozon-овский заказ будет в столбце типа количество товаров, сколько там товаров. Там будет, типа, написано 3 штуки. Вот. Также... Также там должен быть фильтр тоже по статусам, фильтр по маркетплейсу. Соответственно, что важно: селлер видит только свои заказы. Дизайн Opusu отдай.

`VB` в запросе трактуется как `WB` (Wildberries) по контексту продукта. В интерфейсе используется
принятое название `Wildberries`/`WB`.

## 2. Существующий процесс и цель изменения

В seller-портале сейчас есть «Документы», «Товары», «Отчёты», «Расчёты», «Честный знак» и «Настройки»;
маршрута и пункта «FBS» нет. Складской экран ФФ сложнее требуемого seller-представления: «Новые» — строки
заказов, а «В работе», «В доставке» и «Завершённые» — поставки с действиями подбора, упаковки, печати и
передачи. Эти действия принадлежат оператору фулфилмента и не должны переезжать в кабинет селлера.

В базе уже есть единый `FbsOrder` для WB и Ozon: seller/tenant, площадка, внешний номер, локальный статус,
статусы площадки, время появления у площадки (`created_at_wb` — историческое имя, используется и для Ozon),
позиции Ozon и их количества. Текущий складской `/operations/fbs-orders/worklist` уже умеет фильтровать
по площадке и группам, но требует складского права «Упаковка» и скрывает часть WB-заказов по обслуживаемой
привязке; расширять его на селлера опасно, потому что рядом находятся операторские действия.

В браузере 01.10 открыт обязательный образец «Расчёты»: проверены боковое меню, фильтры над таблицей,
компактная таблица и прокрутка. Production seller-портал был доступен только на форме входа после
неуспешной авторизации, поэтому авторизованный экран не выдаётся за просмотренный. Текущая структура
seller-меню и FBS-экрана подтверждена чтением актуального frontend.

Цель — отдельный read-only раздел селлера: один постраничный список всех его FBS-заказов с понятным
статусом, временем и фильтрами, без копирования складского рабочего места.

## 3. Решения аналитика

**D1. Отдельный пункт «FBS», но не новый контур прав.** Пункт размещается в основном seller-меню после
«Документы» и перед «Товары». Он доступен по существующему seller-праву «Документы»: FBS-заказы — документы
селлера, а новое отдельное право владелец не просил. Владелец магазина с полными правами видит его всегда;
сотрудник без «Документов» — нет.

**D2. Только чтение.** Экран — одна таблица заказов. На нём нет создания/изменения поставки, подбора,
упаковки, ЧЗ, коробов, печати, отмены или ручной синхронизации площадки. Эти операции остаются у
фулфилмента; seller-экран читает уже синхронизированные факты.

**D3. Один отображаемый статус, вычисленный из существующих полей.** Новая колонка/таблица статусов в БД
не создаётся. Read model выводит один понятный этап с приоритетом отмены/дефекта, затем локальной работы,
затем подтверждённого состояния площадки. Группы:

- `new` → «Новый»;
- `in_supply`, `assembling`, `packed` → «В работе»;
- `in_delivery` и подтверждённые статусы передачи → «Передан площадке»;
- `sorted` / подтверждённая приёмка площадкой → «Принят площадкой»;
- `external_processing`, если более точное известное состояние не сопоставлено → «Обрабатывается площадкой»;
- `done` → «Завершён»;
- `cancelled` → «Отменён»;
- `defect` → «Дефект».

Известные WB/Ozon-статусы переводятся на человекочитаемый этап; неизвестный код не показывается как
необъяснённая основная подпись и не считается успехом — строка остаётся «Обрабатывается площадкой».

**D4. Время без выдуманного события.** Экран показывает точное «Поступил» из `created_at_wb` и
«Возраст» — целые часы от этого времени до `server_now`. Отдельного надёжного `assembly_started_at`
сейчас нет, поэтому подписывать возраст как точное время «в сборке» было бы ложью. Возраст продолжает
обновляться от серверной отметки времени, чтобы часы компьютера селлера не искажали значение.

**D5. Количество — товарные единицы.** Единая колонка «Товаров» показывает WB `1 шт.`, а для Ozon сумму
`quantity` всех позиций отправления. Три единицы одного SKU и три разных SKU обе дают «3 шт.»; число
позиций не подменяет число товаров.

**D6. Все существующие заказы, но постранично.** В список входят все строки FBS текущего селлера,
включая завершённые, отменённые, дефектные и заказ с несопоставленным товаром; локальная обслуживаемость
склада и просрочка не скрывают историю селлера. Порядок — новые по времени поступления первыми,
с устойчивым вторичным ключом id. Полный массив не грузится в браузер.

## 4. Требования

- **R1.** В seller-портале у пользователя с правом «Документы» виден пункт «FBS» после «Документы»;
  он открывает самостоятельный экран FBS. Без права «Документы» пункт и маршрут недоступны. Новое право
  доступа не создаётся. Основание: прямой запрос; D1.
- **R2.** Экран получает заказы только из текущих tenant и seller/shop токена. Селлер видит все свои
  существующие FBS-заказы и ни одного заказа другого селлера; query-параметром scope расширить нельзя.
  После штатного переключения магазина старые строки очищаются до ответа нового. Основание: прямое
  «селлер видит только свои заказы»; правила изоляции; D6.
- **R3.** Один заказ — одна строка. Без дополнительного раскрытия видны: площадка и внешний номер заказа,
  «Товаров», «Статус», «Поступил», «Возраст». Длинный внешний номер не перекрывает соседние колонки.
  Основание: «просто список всех FBS-ных заказов»; D2.
- **R4.** Колонка «Товаров» показывает количество товарных единиц: WB — `1 шт.`, Ozon — сумму количеств
  всех позиций заказа. Нулевой/повреждённый состав не превращается в выдуманную единицу: показывается `—`
  и факт остаётся проверяемым на backend. Основание: прямой пример «3 штуки»; D5.
- **R5.** Колонка «Статус» использует группы D3 и обновляется из тех же локальных и площадочных полей,
  которые уже пишет действующая синхронизация WB/Ozon. Новый, локально взятый в работу, переданный,
  принятый/отсортированный, завершённый, отменённый и дефектный заказы различимы. Статус seller-экрана
  не становится вторым источником и сам ничего не записывает. Основание: прямое описание этапов;
  правила о вычисляемом значении.
- **R6.** Над таблицей есть фильтр «Маркетплейс» (`Все`, `Wildberries`, `Ozon`) и фильтр «Статус»
  (`Все`, группы D3). Фильтры работают совместно, применяются сервером до пагинации и счётчика; изменение
  фильтра возвращает на первую страницу. Пустой срез показывает спокойное пустое состояние, а не ошибку.
  Основание: прямой запрос фильтров; D3/D6.
- **R7.** «Поступил» показывает дату и время площадки в локальном формате интерфейса. «Возраст» показывает
  неотрицательное число полных часов от поступления до `server_now` (`N ч`; меньше часа — `< 1 ч`) и
  обновляется без перезагрузки. Будущая/битая дата не даёт отрицательное или сегодняшнее выдуманное время:
  выводится `—`. Основание: прямой запрос времени; D4.
- **R8.** Обновление существующей синхронизацией статуса WB/Ozon видно после очередного чтения экрана без
  ручной правки заказа. При отказе API список не заменяется ложным пустым успехом; видна ошибка и доступен
  повтор/обновление. Запоздалый ответ прежнего seller scope не применяется. Основание: «синхронно с WB»;
  восстановление после сбоя.
- **R9.** Seller FBS остаётся read-only: экран не вызывает provider-write, не меняет локальный заказ,
  поставку, резерв, остаток, подбор, упаковку, ЧЗ, короб или печать. Складской FBS фулфилмента не меняется.
  Основание: запрос на представление, не на действие; D2.
- **R10.** API списка постраничный, с устойчивой сортировкой «новые сначала», и не строит N+1 запросов
  по позициям Ozon. На крупной истории фильтры и следующая страница не грузят весь набор в память.
  Основание: известные крупные каталоги/заказы; D6; WMS-538.
- **R11.** Экран собран из текущих компонентов и темы: фильтры в одной панели над таблицей, без новых
  пояснительных карточек, складских вкладок и лишних чипов. Он читаем при 1440 и 1280 px, а на узкой
  ширине допускает штатный горизонтальный скролл без наложения. Frontend и дизайн выполняет Opus Extra
  по прямому указанию владельца. Основание: запрос; UI-правила; просмотренный образец «Расчёты».

## 5. Проверки

| Проверка | Требования | Ожидаемый результат | Вердикт |
|---|---|---|---|
| C1. Навигация и право | R1 | Владелец seller-аккаунта и сотрудник с «Документы» видят «FBS» после «Документы» и открывают экран. Сотрудник без права не видит пункт; прямой URL/API получает 403. Другие пункты сохраняют порядок. | |
| C2. Seller/tenant isolation | R2 | У A и B одного tenant и C другого tenant есть различимые заказы. A видит только A; подмена seller_id не расширяет список. При задержанном ответе A переключить разрешённый магазин на B: строки A исчезают и поздний ответ не возвращает их. | |
| C3. Все этапы | R2, R3, R5 | Подготовить по одному заказу каждого локального этапа D3 и известные WB/Ozon provider-статусы. В таблице одна строка на заказ, понятные подписи и правильный приоритет отмены/дефекта. Завершённые и отменённые не скрыты. | |

| C8. Только чтение | R9 | Снять backend-запросы при открытии, фильтрах, пагинации и обновлении: только чтение. Сравнить до/после заказы, поставки, резервы, остатки, pick/pack/ЧЗ/print — изменений нет. Складской экран ФФ и его действия работают как раньше. | |

## 6. Сверка с исходным запросом

- «у селлера должен появиться раздел FBS» → R1;
- «просто список всех FBS-ных заказов» → R2-R3 и D2/D6;
- «новый ... в работе ... собрано в поставку ... передано ... в сортировке ... отменён» → R5 и D3;
- «синхронно с WB» → R5/R8 без второго источника статуса;
- «время, когда заказ пришёл ... сколько часов» → R7 и честная граница D4;
- «Ozon ... количество товаров ... 3 штуки» → R4/D5;
- «фильтр по статусам, фильтр по маркетплейсу» → R6;
- «селлер видит только свои заказы» → R2;
- «Дизайн Opusu отдай» → R11/C10.

Обратная сверка: read-only, существующее право «Документы», постраничность и серверное время не добавляют
новых бизнес-действий; они защищают заявленный список от лишних прав, ложного времени и утечки данных.
Новых таблиц, хранимых seller-статусов и пользовательских блокировок нет.

## 7. Заключение

Будет заполнено после реализации, перекрёстного ревью и приёмки по проверкам выше.
