## Коротко

«Сегодняшняя» история — это WMS-627: четыре WB-поставки ArtMaks 01.10 закрылись
в WB (статус «Завершена» пришёл автоопросом), а остаток в WMS не списался; вечером
его списали вручную, и в прод был выложен код 660bc5c7, который списывает остаток
в момент, когда автоопрос видит закрытую поставку. **Ночная выкладка WMS-624
(`b726e44a`, 22:19 UTC) этот код с прода убрала**: коммиты WMS-627 не входят в
`b726e44a`, модуля `fbs_observed_delivery_service.py` в контейнере api нет.
Значит, дыра «поставка закрыта в WB — остаток не списан» снова открыта на проде.

Подбор FBS по расположению теперь работает так, как сказал владелец: с 30.09 (WMS-584)
подбор WB-заказа сразу переносит штуку из ячейки на сортировку, отмена подбора
возвращает её в ту же ячейку/короб, общий остаток при этом не меняется. Но **отмена
самого заказа** подобранную штуку обратно в ячейку не возвращает — она остаётся на
сортировке. До 30.09 это было неважно (WB-подбор вообще не двигал товар), теперь —
дефект.

## Установленная механика (по коду `b726e44a`)

Остаток хранится построчно по месту: `inventory_balances` (место × товар × тара),
каждое изменение — строка `inventory_movements`. Остаток товара = сумма по местам.
Единственная точка изменения — `record_movement_and_adjust_balance`
(backend/app/services/inventory_service.py:665); минус по умолчанию запрещён,
разрешается явно только для подтверждённой отгрузки FBS (комментарий в
backend/app/models/inventory_balance.py:36–54).

1. **Подбор FBS (WB и Ozon).** `scan_pick_product`
   (backend/app/services/fbs_picking_service.py:1453); все остальные пути подбора
   (скан, ручной, «задать количество» — `set_pick_quantity`:732) идут через него.
   При наличии товара в выбранном месте вызывается `transfer_on_hand_between_locations`
   (fbs_picking_service.py:1613–1625) — пара движений `stock_transfer_out` (ячейка/короб)
   и `stock_transfer_in` (`__SORTING__`). Это смена расположения, общий остаток не меняется.
   До коммита 35eb3457 (WMS-584/585, 30.09 01:48) условие было
   `supply.marketplace != "wb" and …` — WB-подбор товар **не двигал**, и при отгрузке
   списание шло прямо из исходной ячейки (режим `manual_pick`).
2. **Отмена подбора.** `undo_pick` (fbs_picking_service.py:1798): для подбора с движением
   — обратный перенос сортировка → исходная ячейка в ту же тару (1960–1997, для Ozon 1874–1895).
3. **Отмена заказа.** `_finish_local_cancellation`
   (backend/app/services/fbs_cancellation_service.py:178–211): статус, сторно биллинга,
   отцепление от поставки (`detach_cancelled_order_from_supply`,
   backend/app/services/fbs_packaging_integration_service.py:259–318), снятие резерва.
   `reverse_fbs_shipment_if_needed` (fbs_cancellation_service.py:98–111) ничего не делает.
   **Активный подбор не отменяется, штука с сортировки в ячейку не возвращается.**
4. **Проведение отгрузки FBS в WMS.** `deliver_supply` (backend/app/services/fbs_shipment_service.py:2182)
   → `_apply_local_delivered` → `_write_off_delivered_orders_once` (1222–1398): по каждому
   заказу одна строка `fbs_shipment_reversal_ledger` (уникальна на заказ) и движение
   `fbs_shipment`. Источник выбирает `resolve_fbs_shipment_sources`
   (backend/app/services/fbs_shipment_source_service.py:276): подобран с переносом →
   сортировка (`legacy_sorting`); подобран без переноса → исходная ячейка (`manual_pick`);
   не подобран → сначала сортировка, потом ячейки (`sorting_*`/`storage_*`); товара нет
   нигде → минус на сортировке (`forced_negative`). Ozon — тот же принцип через
   `fbs_ozon_packaging_service.write_off_order` (:349).
5. **Закрытие поставки на стороне WB без проведения в WMS.** Автоопрос ставит `done`:
   backend/app/services/fbs_tracking_service.py:261, 269, 284, 316, 327 и
   backend/app/services/wb_marketplace_orders_service.py:1280. **Ни одна из этих веток
   остаток не списывает и `delivered_at` не ставит.** Исправление WMS-627 (660bc5c7)
   добавляло перед этими местами `reconcile_observed_wb_delivery`; в `b726e44a` его нет.
6. **FBO («Отгрузка на МП»).** Остаток списывается не при «Отгрузить», а при укладке в
   короб сборки: `apply_marketplace_unload_pick` (inventory_service.py:1629) из
   backend/app/services/marketplace_unload_collect_service.py:355 и :538; при выемке из
   короба — возврат (`reverse_marketplace_unload_pick`, «DEC-016»). `ship_request`
   (marketplace_unload_pick_service.py:507) остаток не трогает. Так устроено с мая
   (a9cebe6b, e6913ecd), это не свежая поломка. Старый документ `outbound_shipment`
   на проде не используется (0 документов).
7. **Прочие изменения остатка.** Приёмка (`inbound_intake`), инвентаризация
   (`inventory_count`), акт расхождений, передача владения, перемещения
   (`stock_transfer_*`, `warehouse_map_move` — нулевой итог). Фоновых задач,
   синхронизации с маркетплейсом, упаковки, сортировки, меняющих сумму остатка, в
   коде не найдено (поиск всех вызовов `record_movement_and_adjust_balance`).

Свежие изменения с 25.09: WMS-584/585 (35eb3457, 21abf815) — включили перенос при WB-подборе
и точную отмену; WMS-602/603 (88a2e368, d571fcf3) — только распознавание скана ячейки/короба;
WMS-600 (3cbabfe5) — только фронт (группировка подбора по ячейкам); WMS-576/578 —
инвентаризация брака и скан сортировки; WMS-588 — сборочное задание и метка «Подобрано»,
остаток не трогает. WMS-628 в истории этой ветки не найден (не проверялся).

## Найденные дефекты

**Д1. Снят фикс WMS-627: закрытая в WB поставка снова не списывает остаток.**
Причина: ночная выкладка WMS-624 собрана из `b726e44a`, куда коммиты 14fddaec / 660bc5c7 /
ab01d1b2 (ветка `codex/wms627-artmaks-stock-reconcile`) не влиты. Проверено: `git merge-base`,
на сервере `/opt/wms` HEAD = `b726e44a`, файла `fbs_observed_delivery_service.py` в контейнере
api нет. Это то же место, что сломалось «сегодня» у ArtMaks; любая следующая поставка, которую
закроют в кабинете WB, а не кнопкой WMS, опять не спишется.

**Д2. Отмена заказа не возвращает подобранную штуку в ячейку.** С 30.09 WB-подбор переносит
штуку на сортировку, а `_finish_local_cancellation` подбор не отменяет. Итог: в системе штука
числится на сортировке, физически её вернут на полку — расположение расходится, ячейка
показывает на 1 меньше. Общий остаток не страдает. Причина — 35eb3457 изменил поведение подбора,
а путь отмены заказа под него не доработан.

**Д3. Не устранённые пропуски списаний прошлых дней (данные).**
- AVpack, WB-GI-284256770 «FBS 27.09.2026», `done` 28.09 18:42, `delivered_at` пуст: 40 заказов
  (в WB `sorted`/`ready_for_pickup`/`sold`), **списаний 0**. В аудите WMS-627 AVpack был найден
  (47 заказов без ledger), но в ремонт вошли только ArtMaks/FFAdam/Империя — почему AVpack
  исключён, не установлено.
- AVpack «Перенос be4ce318…» (WB-GI-284967126): 1 заказ, списаний 0.
- Бамбук, две Ozon-поставки от 24.09 (`PENDING-…`), `in_delivery`/`done` с 30.09 12:44 без
  `delivered_at`: 30 заказов, списаний 0. Путь, которым они получили статус, не установлен.

**Д4 (расхождение с правилом, не регрессия). FBO списывает остаток при укладке в короб, а не
при проведении отгрузки.** Решение DEC-016 действует с мая. По словам владельца и AGENTS.md
отгрузка списывает при проведении. Пока отгрузка не отгружена, товар физически на складе,
а остаток уже уменьшен. Нужен ли перенос списания на «Отгрузить», должен подтвердить владелец:
это меняет давно работающий процесс. Без его решения правка не делается.

**Наблюдение (не дефект кода).** Отрицательный остаток на `__SORTING__`: Империя ФФ −216 (7 строк),
FFAdam −134 (27), AVpack −25 (5), ArtMaks −8 (2), Руспро −1. Это `forced_negative`: заказ отгружен,
а товара в WMS нигде не было (с 29.09 — AVpack 161, Империя 57 WB + 34 Ozon, ArtMaks 8 заказов).
Так задумано (решение владельца в inventory_balance.py), но это значит, что приход части товара
в WMS не оформлен.

## Требования к исправлению

- **R1.** Вернуть на прод исправление WMS-627 (660bc5c7: `fbs_observed_delivery_service` и вызовы
  в fbs_tracking_service.py / wb_marketplace_orders_service.py) поверх текущего `b726e44a`, не
  откатывая WMS-624/630. Поставка, которую автоопрос видит закрытой в WB, получает списание
  тем же механизмом ledger, что и кнопка WMS, ровно один раз; при сбое статус `done` без
  списания не сохраняется.
- **R2.** Отмена заказа (WB и Ozon, любой путь: автоопрос, кнопка, Ozon) при активном подборе
  с переносом выполняет то же, что отмена подбора: штука возвращается в исходную ячейку и тару,
  подбор помечается отменённым. Подбор без переноса (до 30.09) — только отметка. Повтор отмены не
  возвращает штуку второй раз. Если исходная ячейка удалена — возврат на сортировку не нужен
  (штука уже там), подбор просто снимается.
- **R3.** Перед любой следующей выкладкой проверять, что коммиты, уже выложенные на прод
  (сейчас — WMS-627), входят в выкладываемый SHA (`git merge-base --is-ancestor`).
- **R4 (только после решения владельца по Д4).** Если владелец подтвердит, перенести списание
  FBO на проведение отгрузки, а укладку в короб считать расположением.

### Требования (дополнение)

- **R5. FBO: подбор и укладка — только расположение.** Подбор с ячейки переносит штуку на
  сортировку тем же переносом, что подбор FBS (`transfer_on_hand_between_locations`), а не
  `apply_marketplace_unload_pick`. Укладка в короб остаток не меняет. Резерв документа
  не уменьшается до проведения. Выемка из короба / уменьшение подбора / «Отменить отгрузку»
  возвращают штуку переносом в исходную ячейку/тару и снимают резерв (при отмене).
- **R6. FBO: списание при «Завершить».** `complete_unload` в одной транзакции списывает
  распределённый по коробам факт с мест, где штуки лежат (сортировка; для старых
  документов — см. R8), движением `marketplace_unload`, привязанным к документу, и снимает резерв.
  Повторный вызов ничего не списывает: списывается только «факт минус уже списанное этим
  документом» (сумма его движений `marketplace_unload`).
- **R7. FBS: резерв при поступлении заказа не зависит от публикации остатка.** Убрать условие
  `not_published` для WB (inventory_service.py:216–222): заказ резервируется, если товар
  сопоставлен и свободный остаток есть. `no_stock` и `warehouse_unmapped` — оставить (спорно,
  см. ниже). Публикуемое в WB число по-прежнему `min(лимит, свободный)`.
- **R8. Переход FBO без двойного списания.** Документы, у которых до выкладки R5–R6 уже есть
  списание при подборе/укладке, проводятся по правилу R6: списывается только недостающая разница.
  Если данные исправлены по п. Д-FBO ниже (списание возвращено), правило даёт полное списание
  при «Завершить» — тоже ровно один раз.
- **R9. Кнопка «Отменить отгрузку» FBO** уже есть. Новую не добавлять; после R5 проверить, что
  она возвращает товар переносом и снимает резерв.
- Связанное: R1 (вернуть WMS-627 на прод) закрывает М10; R2 (у разработчика) — отмену заказа
  после подбора.
