# WMS-506 · Подключение Ozon без лишнего требования роли seller/info

## Исходный запрос и уточнения

22.09.2026. Ведущий передал обращение: клиент не может подключить Ozon. После диагностики владелец потребовал дословно:

> убирай нахуй это из вмс

Контекст приказа — убрать препятствие подключения, связанное с проверкой через `/v1/seller/info`. Это не поручение удалить интеграцию Ozon, отключить проверку действительности ключа или менять ключ в кабинете Ozon.

Ведущий передал установленные диагностикой факты: исходная пара Client-Id/Api-Key действительна; `POST /v1/roles` отвечает200, доступны роли Returns/Warehouse/Product/Supply order/Posting FBS, expires_at —2026-12-21. Нужные текущим операциям read-only методы складов, товаров и FBS postings отвечают200. `POST /v1/seller/info` отвечает403, code7, `Api-Key is missing a required role for a method`. Значения Client-Id и Api-Key в документ не включаются. Аналитик не повторял внешние запросы с клиентским ключом; эти факты — результат диагностики ведущего.

Уточнение ведущего при постановке: сохранить существующий публичный контракт ошибок. Недействительная пара отличается от временной недоступности; transport/429/5xx могут оставаться одной публичной категорией. Новый UI-код/текст не нужен. Проверка полного списка ролей как условие подключения запрещена: владелец потребовал убрать лишний барьер, а не заменить его другим.

## Существующий процесс и цель

База ветки `codex/wms506-ozon-role-validation` — `origin/etalon`, продуктовый SHA `3e125074`. Селлер вводит два значения в существующем разделе настроек Ozon. `SellerSettingsScreen.tsx` отправляет `PUT /integrations/ozon/self/account`; повторная проверка сохранённого подключения использует `POST /integrations/ozon/self/account/test-connection`.

По прочитанному `backend/app/services/ozon_client.py` обе операции вызывают `validate_ozon_credentials`, которая делает один read-only POST к фиксированному Ozon host, сейчас `/v1/seller/info`, с пустым JSON и запретом redirect. API в `backend/app/api/ozon_integration.py` превращает401/403 в `ozon_credentials_invalid` и прекращает сохранение. Отсюда действующий ключ с правами рабочих операций ошибочно выглядит недействительным. После успешной проверки кандидат сохраняется существующим `MarketplaceAccountService`, затем запускается существующий импорт каталога; неудача этого импорта не должна отменять уже подтверждённое подключение.

Цель — действующая пара подключается и повторно проверяется через `/v1/roles`, не требуя роли для seller/info. Сохраняются существующие данные, права, границы селлеров и понятное различие между отказом аутентификации и временной проблемой проверки.

## Решения аналитика

D1. Меняется read-only метод общей валидации, а не набор разрешённых действий пользователя. Это устранение подтверждённого технического дефекта. Нет оснований требовать выдачу новой роли, выпуск другого ключа или весь каталог ролей.

D2. Сохраняется проверка по успешному HTTP-статусу, как в исходной границе транспорта. В этой задаче не вводится анализ тела roles, локальное толкование срока действия или обязательных полей ролей. Поэтому отсутствующее необязательное поле в успешном ответе не становится новым запретом. Неуспешный статус не принимается за успех.

D3. Нового интерфейсного решения нет. Прочитан существующий экран настроек и его error mapping; визуальный просмотр на этапе постановки не выполнялся. Приёмка пользовательского пути должна отличать наблюдение экрана от проверки API. Искусственные ошибки выполняются только на изолированной среде с синтетическими ключами.

D4. Навыки аналитика и продуктового решения, owner-cases/failure-cases прочитаны из основного checkout по `/Users/deniscivkunov/Projects/WMS/docs/reviews/2026-09-11-analyst-draft/`: их нет в baseline этой ветки, копии не добавляются. Применимы запрет самодельного барьера, B03 о границе ошибки/успеха, B04 о всех путях общей функции, B05 о повторе после ошибки и B08 о соседнем scope. Актуальное прямое правило владельца о продолжении работы при обнаружении секретов имеет приоритет над старой stop-формулировкой baseline AGENTS.

## Сверка исходного запроса

«Клиент не может подключить Ozon» → R1/R2 и сохранённый результат C1/C2/C7. «Убирай ... это» в установленном контексте → удаление зависимости seller/info, R1/R5, без удаления интеграции и без обхода аутентификации. Сохранность ключа и честная ошибка → R3/R4/R6. Соседние селлеры/площадки и повторы → существующие гарантии R7, а не новый объём функциональности. У каждого требования есть основание в запросе, уточнении или действующем контракте. Новый blocker и новая схема ролей не добавлены.

## Заключение

**Минимальное исправление WMS-506 принято локально.** Подтверждённый лишний барьер seller/info удалён из общей проверки сохранения и повторного теста подключения; подлинность пары по-прежнему проверяется до сохранения через roles. Новых пользовательских ограничений, UI-изменений и изменения политики импорта нет. Технических несоответствий исходному запросу не выявлено. Степень проверки соседних неизменных гарантий отдельно раскрыта в C6: это не новый полный аудит изоляции и PostgreSQL-конкуренции.

Реализация, повтор целевых тестов, независимое review и локальный браузер завершены; публикация ветки, CI и деплой относятся к следующему этапу ведущего. Успешное подключение клиента через production после выкладки пока не заявлено.
