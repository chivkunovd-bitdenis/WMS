## 2. Существующий процесс и цель изменения

Кто и что. Оператор фулфилмента на экране «Заказы FBS» выбирает подтверждённые заказы и в окне
«Новая поставка FBS» нажимает «Создать»; так же он добавляет заказы в уже открытую поставку.
Сервер сериализует записи по одному продавцу и одной площадке «замком продавца» — advisory-замком
PostgreSQL (замок, который база держит по числовому ключу без привязки к строкам таблиц) с
ключом marketplace_seller_lock_key(seller_id, marketplace). Тот же ключ берут фоновые процессы:
автоопрос заказов, статусов и остатков, публикация остатков, ручная синхронизация заказов и
остатков, правила остатков, привязки складов, каталог.

Как это устроено сейчас (проверено чтением кода в ветке, строки по etalon 388f389b):

- backend/app/services/marketplace_seller_lock_service.py: замок берётся на переданной AsyncSession
  либо в сессионном режиме (pg_try_advisory_lock — держится до явного pg_advisory_unlock или до
  закрытия соединения; transaction_scoped=False), либо в транзакционном (pg_try_advisory_xact_lock —
  отпускается при commit/rollback транзакции; transaction_scoped=True). Не на PostgreSQL (SQLite в
  тестах) замок считается всегда взятым. Обёртка marketplace_seller_lock в finally вызывает
  pg_advisory_unlock на той же сессии.
- backend/app/services/fbs_wb_seller_lock_service.py: wb_seller_lock(session, seller_id, wait_timeout_sec)
  — та же схема, всегда сессионный режим, без release_connection_while_waiting.
- Создание поставки (backend/app/services/fbs_supply_service.py:693): для WB — транзакционный замок
  с ожиданием WB_LOCK_WAIT_FOR_OPERATOR_SEC = 90 с (release_connection_while_waiting=True), для
  Ozon — сессионный на рабочей сессии; внутри блока только flush, commit нет. При неудаче —
  FbsSupplyError("operation_in_progress", 503, retryable=True) с текстом «Синхронизация WB по селлеру
  ещё идёт — повторите через несколько секунд.» (строки 705–706). Черновик поставки в WB создаётся
  до замка (строка 677), локальная операция — внутри блока, поэтому отказ не оставляет записей
  в fbs_wb_operations.
- Добавление заказов (fbs_supply_service.py:1968, add_orders_to_existing_supply, маршрут
  POST /operations/fbs-supplies/{id}/orders/batch): wb_seller_lock на рабочей сессии с ожиданием 90 с;
  внутри блока — PATCH в WB и сверка состава, commit нет; текст отказа «WB-синхронизация по селлеру
  ещё идёт — повторите через несколько секунд.» (строка 1974).
- Связывание заказов с поставками WB (backend/app/services/wb_marketplace_orders_service.py:1273,
  link_confirmed_orders_to_wb_supplies): wb_seller_lock на рабочей сессии, а на строке 1384 внутри
  блока — await session.commit(). Вызывается из sync_seller_orders (строка 1515) только при
  include_history=True.
- Ремонт состава поставок (fbs_supply_service.py:1712, repair_pending_supplies_for_seller):
  wb_seller_lock на рабочей сессии, commit внутри блока на строке 1734. Вызывается только из
  автоопроса статусов (fbs_autopoll_service.py:445).
- Ручная синхронизация заказов: экран «Заказы FBS», кнопка «Синхронизировать заказы»
  (frontend/src/screens/v2/FfFbsOrdersScreen.tsx:1245) → POST /operations/fbs-orders/sync
  (backend/app/api/fbs_orders.py:488) → задача wms.wildberries_marketplace_orders_sync →
  background_job_service.run_wildberries_marketplace_orders_sync_job → sync_seller_orders(session, …)
  с include_history=True и без внешнего замка → link_confirmed_orders_to_wb_supplies → wb_seller_lock
  на той же рабочей сессии.
- Автоопрос (fbs_autopoll_service.py:566, 683, 786; публикация остатков fbs_stock_publish_service.py:61;
  ручная синхронизация остатков background_job_service.py:362 и api/fbs_sellers.py:699; правила
  остатков fbs_stock_rule_service.py:696; привязки складов fbs_warehouse_binding_service.py:273/509;
  каталог catalog_service.py:1261; передача Ozon fbs_shipment_service.py:1899): замок берётся на
  отдельной сессии AsyncSession(bind=session.bind) — commit рабочей сессии его не трогает. Комментарий
  в fbs_shipment_service.py:1894 прямо описывает этот образец: замок на собственном соединении,
  потому что чекпойнты коммитят бизнес-сессию и отдают её соединение.
- backend/app/db/session.py: SessionLocal — обычная async_sessionmaker(engine, expire_on_commit=False).
  После commit SQLAlchemy возвращает соединение в пул (с ROLLBACK при возврате), следующий запрос
  сессии берёт из пула соединение в порядке очереди — при двух и более свободных это другое соединение.
- Ответ оператору: API отдаёт 503 с конвертом {code, message, retryable} (api/fbs_supplies.py,
  _raise_from_service и envelope_from_exc); фронт показывает серверный message как есть
  (frontend/src/screens/v2/fbsUx.ts, fbsErrorText: «подробный текст сервера сохраняем целиком»),
  окно «Новая поставка FBS» выводит его в Alert, обновляет idempotency-ключ, выбор заказов не теряет,
  кнопка «Создать» снова доступна (FbsSupplyCreateDialog.tsx:140–147). Таймаута на запрос создания у
  фронта нет — браузер ждёт серверные 90 с.

Механика утечки (диагноз ведущего, перепроверен аналитиком). wb_seller_lock берёт сессионный замок
на соединении рабочей сессии. Commit внутри блока возвращает это соединение в пул. pg_advisory_unlock
в finally выполняется уже на другом соединении, взятом из пула, и возвращает false (замка на нём нет).
Замок остаётся на первом соединении и живёт, пока живёт пул процесса — у celery-воркера часами.
Оператор из процесса API получает «занято» на каждой попытке. Ошибка БД внутри блока даёт ту же
утечку другим путём: транзакция рабочей сессии испорчена, unlock в finally падает с
InFailedSqlTransaction (и подменяет исходное исключение), после rollback соединение уходит в пул
с замком.

Воспроизведено аналитиком 17.09.2026 на локальном PostgreSQL 17 с кодом ветки (скрипт вне проекта,
отдельная база, затем удалена):

- сценарий «commit внутри блока wb_seller_lock»: взят на pid 19986; после commit сессия работает на
  pid 19985; после выхода из блока pg_locks: [(19986, True)] — утечка; оператор из другого пула
  (как API на бою) с транзакционным try-lock: acquired=False; оператор из того же пула случайно
  получил утёкшее соединение: acquired=True — то есть проверка «конкурент взял замок» из того же пула
  не доказывает отсутствие утечки, доказывает только pg_locks;
- сценарий «ошибка БД внутри блока» (select 1/0): наружу вышло InternalError InFailedSqlTransaction
  из unlock, после rollback pg_locks: [(19988, True)] — утечка;
- сценарий «вложенный try-lock при внешнем замке на отдельной lock_session»: acquired=False, после
  выхода замков нет — утечки нет;
- реальный путь link_confirmed_orders_to_wb_supplies на заготовке test_adoption_with_supplies_list_done_true
  с пулом из двух соединений: результат {'supply_linked_orders': 1, 'supply_links_created': 1, …},
  после вызова pg_locks держит pid 20819 — утечка на настоящем коде связывания.

Бой (только чтение): по карточке задачи 17.09 ~09:00 UTC единственный advisory-замок Фадин/wb держал
pid 932703 воркера — соединение открыто 05:54:06 UTC, idle, последний запрос ROLLBACK, три часа; снят
ведущим через pg_terminate_backend. Аналитик 17.09 09:17 UTC проверил: advisory-замков в боевой базе 0;
idle_in_transaction_session_timeout = 0 и statement_timeout = 0 — сервер не убивает соединения с
открытой транзакцией, поэтому образец «замок на отдельной сессии» безопасен на бою (образец автоопроса
так и живёт).

Что видит автоопрос. Внешний замок на отдельной lock_session держится на весь цикл по продавцу, поэтому
вложенный wb_seller_lock(session) внутри repair_pending_supplies_for_seller (цикл статусов) и внутри
link_confirmed_orders_to_wb_supplies (полная сверка раз в 6 часов, include_history=True) всегда отвечает
«занято» и шаг пропускается — «fbs supply repair skipped … reason=lock_busy», «wb supply link skipped …
reason=lock_busy». В частом автоопросе заказов include_history=False, и связывание не вызывается вовсе.
Утечки в автоопросе нет; единственный путь, где вложенный замок реально берётся, — ручная синхронизация
из интерфейса. Это наблюдение, решение по нему в задачу не входит (раздел 8).

Цель изменения. Замок продавца, взятый в сессионном режиме на рабочей сессии, не может пережить блок:
после выхода из блока — обычного, через return, через исключение — в pg_locks нет ключа продавца, а
во время блока замок держится независимо от commit/rollback рабочей сессии. Оператор, попавший на
законно занятый замок, получает тот же отказ 503, но честный текст. Ничего нового в данных и на экране.

## 3. Требования

Термины: «замок продавца» — advisory-замок с ключом marketplace_seller_lock_key(seller_id, marketplace);
«сессионный режим» — wb_seller_lock(session, …) и marketplace_seller_lock(session, …, transaction_scoped=False);
«транзакционный режим» — marketplace_seller_lock(…, transaction_scoped=True); «ключ свободен» — в pg_locks
нет строки locktype='advisory' с classid/objid этого ключа (classid — старшие 32 бита беззнакового
представления ключа, objid — младшие 32 бита).

R1. Замок в сессионном режиме держится весь блок и отпускается на выходе. Условие: код взял замок
продавца в сессионном режиме на рабочей сессии и внутри блока делает с этой сессией что угодно —
запросы, flush, commit, rollback, — а также выходит из блока обычным путём или через return из
середины. Результат: (а) пока блок не завершён, замок удерживается — в том числе после commit
рабочей сессии: конкурент из другого пула (другой процесс) получает «занято» и в сессионном, и в
транзакционном режиме; (б) сразу после выхода из блока ключ свободен, и конкурент из другого пула
берёт замок; (в) ни одно соединение не возвращается в пул с невыпущенным замком — обёртка отпускает
замок на том соединении, на котором он взят, независимо от того, что вызывающий код сделал со своей
сессией. Транзакционный режим не меняется: замок остаётся на рабочей сессии и отпускается commit'ом,
который сохраняет локальную операцию (создание поставки WB). Не на PostgreSQL поведение прежнее —
замок считается взятым. Основание: диагноз с боевой базы 17.09; воспроизведение аналитика (раздел 2);
поручение ведущего, пункт (1).

R2. Исключение внутри блока не оставляет замка и не подменяется. Условие: внутри блока в сессионном
режиме возникает исключение — бизнес-ошибка (FbsSupplyError и подобные), ошибка WB-клиента или
ошибка БД на рабочей сессии, после которой транзакция рабочей сессии испорчена (сейчас — сценарий
InFailedSqlTransaction). Результат: наружу выходит исходное исключение того же типа, а не ошибка
pg_advisory_unlock; после выхода из блока ключ свободен, включая случай, когда вызывающий код
делает rollback рабочей сессии уже после блока (как в sync_seller_orders и repair_pending_supplies);
состояние рабочей сессии обёртка не меняет — её rollback остаётся за вызывающим кодом, как сейчас.
Основание: воспроизведение аналитика, сценарий 2; правило проекта «решение позволяет продолжить
работу после сбоя» (AGENTS.md, раздел 3); поручение ведущего, пункт (2).

R3. Отказ оператору при законно занятом замке — с честным текстом. Условие: оператор создаёт
поставку из заказов (окно «Новая поставка FBS», «Создать» → POST /operations/fbs-supplies/from-orders)
или добавляет заказы в поставку (POST /operations/fbs-supplies/{id}/orders/batch), а замок продавца
по этой площадке удерживается другим процессом всё время ожидания WB_LOCK_WAIT_FOR_OPERATOR_SEC.
Результат: как сейчас — ожидание до WB_LOCK_WAIT_FOR_OPERATOR_SEC (90 с), затем HTTP 503,
code=operation_in_progress, retryable=true, записи в fbs_wb_operations нет, PATCH добавления заказов в
WB не отправлялся; message —

- для создания: «По этому селлеру идёт фоновый обмен с WB — создание поставки ждало его 90 с и не
  дождалось. Повторите попытку позже.»
- для добавления заказов: «По этому селлеру идёт фоновый обмен с WB — добавление заказов ждало его
  90 с и не дождалось. Повторите попытку позже.»

где «90» — фактическое значение WB_LOCK_WAIT_FOR_OPERATOR_SEC в целых секундах (текст берёт число из
константы, а не хранит его отдельно), «WB» — площадка поставки (для поставки Ozon — «Ozon», как
сейчас подставляется marketplace). В тексте нет обещания «через несколько секунд» и нет внутренних
идентификаторов (pid, ключ). Если замок освободился в пределах ожидания, создание и добавление
проходят без ошибки, как сейчас. Экран не меняется: серверный текст доходит до Alert окна как есть,
код и retryable прежние, поэтому обработка на фронте (новый idempotency-ключ, сохранённый выбор,
доступная кнопка) остаётся прежней. Основание: слова владельца 11.09 и 17.09 (ждать пришлось не
секунды); поручение ведущего, пункт (3); решение аналитика 2.

R4. Затронутые пути работают как раньше. Условие: изменение выпущено. Результат:

- (а) ручная синхронизация заказов («Заказы FBS» → «Синхронизировать заказы» → задача
  wildberries_marketplace_orders_sync → sync_seller_orders → link_confirmed_orders_to_wb_supplies):
  заказы импортируются, поставки WB подхватываются, заказы связываются, сводка (supply_linked_orders,
  supply_links_created и остальные ключи) прежняя; после завершения задачи ключ продавца свободен;
  создание поставки этим продавцом сразу после — успешно. То же для repair_pending_supplies_for_seller:
  результат прежний, ключ свободен;
- (б) автоопрос: внешние замки fbs_autopoll_service на отдельной lock_session прежние; вложенный
  wb_seller_lock из repair_pending_supplies_for_seller и link_confirmed_orders_to_wb_supplies при
  удерживаемом внешнем замке по-прежнему отвечает «занято» без ожидания и шаг пропускается с той же
  записью в логе; реентерабельность замка (повторный вход того же процесса) не вводится;
- (в) создание поставки WB: транзакционный замок с release_connection_while_waiting прежний,
  существующие проверки test_fbs_create_lock_connection.py и test_fbs_create_http_connection.py
  на PostgreSQL зелёные (на etalon аналитик прогнал их вместе с test_wb_marketplace_orders_service.py:
  19 passed);
- (г) добавление заказов в поставку: замок берётся на время PATCH в WB и сверки состава, отпускается
  на выходе; во время ожидания замка оператор не удерживает второе соединение пула сверх нынешнего
  (сейчас — одно, рабочей сессии): между попытками ожидания соединение замка в пул возвращается,
  и параллельная работа с двухслотовым пулом не блокируется;
- (д) остальные пользователи замка со своей lock_session (публикация остатков, ручная синхронизация
  остатков, правила остатков, привязки складов, каталог, передача Ozon) ведут себя как сейчас;
- (е) на SQLite (обычный прогон pytest и CI) поведение прежнее.

Основание: поручение ведущего, пункт (4); AGENTS.md, раздел 2 — побочные изменения соседних
процессов недопустимы; случай B01 библиотеки сбоев (два оператора и один заказ — единственность
поставки сохраняется, это уже держит транзакционный замок).

R5. Без новых сущностей и без фронта. Условие: изменение выпущено. Результат: нет миграций, новых
таблиц, колонок, журналов, настроек и фоновых «сторожей» утёкших замков (никакого

## 4. Решения аналитика и оставшиеся вопросы

Решение 1 — чинить обёртку, а не три места вызова. Вариант «в link, repair и add-orders передать
отдельную lock_session, как в автоопросе» убирает сегодняшние три утечки, но оставляет ловушку:
wb_seller_lock(session) и marketplace_seller_lock(session) по-прежнему можно вызвать с рабочей
сессией, и следующий commit внутри блока снова уронит операторов. Ловушка уже была описана
комментарием в fbs_shipment_service.py и всё равно сработала в трёх местах. Поэтому инвариант R1/R2
задан для самой обёртки в сессионном режиме: какой бы ни была переданная сессия и что бы с ней ни
делал вызывающий код, замок отпускается на выходе. Рекомендуемый способ — обёртка держит замок на
собственном соединении (своя AsyncSession(bind=session.bind) или соединение движка на время блока),
переданная сессия для сессионного режима служит только источником движка; между неудачными
попытками ожидания соединение замка отдаётся в пул (R4г); если unlock всё же не удался, соединение
замка не должно вернуться в пул живым (invalidate). Конкретная техника — за исполнителем.
Транзакционный режим остаётся на рабочей сессии: там отпускание замка вместе с commit локальной
операции — суть конструкции создания поставки. Существующие вызовы, которые уже передают свою
lock_session, менять не требуется (это не рефактор в объёме задачи); их поведение — R4д.

Решение 2 — формулировка отказа. Оператор уже прождал 90 секунд, а прежний текст обещал «несколько
секунд» — 11.09 и 17.09 это звучало как ложь. Новый текст говорит три вещи, которые сервер знает
точно: причина (по продавцу идёт фоновый обмен с площадкой), что запрос ждал и сколько (число из
константы, чтобы текст не разошёлся с кодом при её изменении) и что делать (повторить позже, без
обещания срока). Ничего сверх этого — ни идентификаторов, ни советов «обратитесь к администратору»:
по правилам проекта не добавляем повествовательных подсказок. Отдельная формулировка для добавления
заказов — тот же шаблон с названием действия. Код ошибки, статус 503 и retryable не меняются, чтобы
не задеть обработку на фронте.

Решение 3 — не трогать длительность фоновых замков и ожидание оператора. Ведущий задал границу:
пока фон держит замок законно, отказ остаётся. После устранения утечки фоновые держатели — это
реальные циклы автоопроса, публикации и ручных синхронизаций по продавцу, которые обычно короче
90 секунд ожидания. Разбивать фоновые блоки на короткие участки или разносить ключи (варианты из
старой части карточки) — отдельная задача, если после выпуска ожидание всё ещё будет мешать.

Решение 4 — проверки на PostgreSQL. SQLite advisory-замок не эмулирует (в сервисе замок там всегда
«взят»), поэтому все проверки R1, R2, R4а–г идут на локальном PostgreSQL через WMS_TEST_DATABASE_URL
в один процесс (все воркеры xdist делили бы одну базу, а conftest чистит её DELETE'ами между
тестами). В CI PostgreSQL нет — эти тесты там пропускаются (маркер postgresql_concurrency,
существующий образец test_fbs_create_lock_connection.py); прогон на PostgreSQL — обязанность
исполнителя, ревьюера и аналитика на приёмке, результат фиксируется в этом документе.

Вопросов владельцу нет.

Оракул утечки — только pg_locks (select pid from pg_locks where locktype='advisory' and classid=… and

## 6. Сверка запроса с требованиями

«Уже 30 минут не дает взять» и семь 503 подряд 11.09 → R1, R2 (причина: утечка сессионного замка через
commit и через испорченную транзакцию), R4а (ручная синхронизация — единственный путь, где замок
реально берётся на рабочей сессии, — больше не оставляет ключа). Ведущий, «чинить причину, не
симптом» → R1, R2, R5 (никаких сторожей). Поручение (1) → R1; (2) → R2; (3) «отказ остаётся, текст
честный, без новых элементов» → R3; (4) → R4а–е; (5) pytest на PostgreSQL с тремя обязательными
тестами → C1, C3, C5 плюс C6–C10. Обратная сверка: R5 опирается на AGENTS.md и поручение; новых
ограничений для оператора ни одно требование не вводит (ожидание и отказ существовали до задачи,
меняется только текст). Не входит: длительность фоновых замков и разнос ключей (решение 3), пустые
