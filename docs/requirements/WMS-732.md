# WMS-732 · Склады WB: ежедневно загружать новые склады

Статус: постановка уточнена 09.10.2026 для тестов целевого и временного поведения.
Свежая загрузка из WB внешне заблокирована отключением метода. Реализация,
тесты, независимое ревью и приёмка не выполнены. Пакет поручений владельца:
WMS-716…WMS-734. Документ изменён локально; сохранение в Git выполняет ведущий.

## 1. Исходный запрос и уточнения

09.10.2026, первое сообщение владельца (дословно): «автоматом тянуть список складов по расписанию».

09.10.2026, второе сообщение владельца (голосом, дословно по расшифровке): «По складам ежедневная
загрузка должна быть и загружать эти склады, актуализировать. Не актуализировать, а просто новые
загружать.»


## 2. Существующий процесс и цель изменения

WMS хранит справочник складов маркетплейса WB отдельно для каждого фулфилмента.
Оператор выбирает склад в отгрузке FBO; селлер использует тот же справочник в
существующей форме отгрузки на маркетплейс. Пользователь должен получать новые
склады автоматически раз в сутки, сохраняя прежние записи и выбор в документах.
Уточнение владельца отменяет замену/актуализацию уже сохранённых складов.

### Что сверено чтением текущего кода

Исходная ревизия: `159f6a9a9ab4a1a1254c31f8b48f59ba641863e2`.

- `wb_mp_warehouse_service.py`: `run_daily_wb_mp_warehouses_sync_for_tenant`
  выбирает только первого селлера по `created_at`. Если у него нет пары ключей,
  сразу выходит. `fetch_mp_warehouses_try_tokens` пробует разные непустые ключи
  карточек и поставок этого селлера, исключая одинаковые значения; ошибки клиента
  WB/транспорта переходят к следующему ключу, но не к следующему селлеру.
- `replace_tenant_mp_warehouses` удаляет все строки своего фулфилмента и вставляет
  полученные, фильтруя отсутствие целого `ID` и непустого имени. Сохраняются имя,
  адрес, время работы, признаки активности/транзита и `fetched_at` (время загрузки).
  Это расходится с «просто новые загружать». Пустой результат в вызывающем сервисе
  сейчас сохраняет кэш, но не объясняет, почему данные не получены.
- `run_daily_wb_mp_warehouses_sync_all_tenants` получает разные `tenant_id` из
  селлеров и обходит их последовательно; отдельной изоляции непредусмотренного
  исключения одного фулфилмента в этом цикле нет.
- `celery_app.py`: `wb-mp-warehouses-daily` вызывает
  `wms.wb_mp_warehouses_daily_sync` по `crontab(hour=3, minute=0)`;
  `background_jobs.py` связывает эту задачу с обходом фулфилментов. Это наличие
  расписания в коде, не доказательство успешного исполнения на production.
  Специальный часовой пояс этому расписанию в файле не задан.
- `wildberries_client.py`, `fetch_mp_warehouses_list`: GET по текущему базовому
  адресу поставок и `/api/v1/warehouses`; результат ожидается списком. Ответ с
  HTTP-ошибкой превращается в ошибку клиента, транспортный сбой тоже. Сообщённый
  ведущим 404 в этой сессии не воспроизводился.
- `TenantWbMpWarehouse`: существующие `tenant_id` и `wb_warehouse_id` позволяют
  определить принадлежность и идентичность склада; номер хранится как `BigInteger`,
  то есть большое целое число. Не вводить второй справочник.
- `backend/app/api/wb_mp_warehouses.py`: `/operations/wb-mp-warehouses` возвращает
  кэш только текущего фулфилмента, с прежними правами. При пустом кэше сервис
  `list_mp_warehouses_for_tenant` лениво пытается загрузить список. Фоновая
  `run_wb_mp_warehouses_sync_task` при заведении ключей также заполняет пустой кэш.
- Фактические файлы UI: `frontend/src/screens/ff/FfSuppliesShipmentsPage.tsx`
  и `frontend/src/components/SellerMarketplaceUnloadDialog.tsx`. Первый читает
  этот API и показывает «Склад маркетплейса», второй выбирает номер WB в
  существующей форме. Прежний выбор хранится как `wb_mp_warehouse_id` и должен
  находить прежнее имя в справочнике.

Формы, доступность выбора и отображение после загрузки **на экране не проверено**:
у аналитика нет браузера. Работа расписания на production и результат у названных
фулфилментов в этой сессии не проверены. Они выделены в ручные C10–C11.

## 3. Требования

**R1. Ежедневная автоматическая загрузка.** Условие целевого поведения: метод
списка FBW доступен, у фулфилмента есть хотя бы один селлер с рабочим существующим
ключом WB для этого метода.
Событие: ежедневное расписание WMS. Результат: без открытия экрана и действий
оператора WMS получает список складов WB и сохраняет новые склады в справочнике
этого фулфилмента; непустой кэш не является причиной пропуска дня. После повторного
открытия отгрузки новые записи доступны через существующий список выбора.
При отключённом методе сохраняется ежедневная попытка и применяется R7, без
заявления об успешном получении свежих данных WB. Основание: «автоматом … по
расписанию», «ежедневная загрузка», новые факты ведущего, решения A1/A6.

**R2. Только добавление новых складов.** Условие: WB успешно вернул список либо
использован подтверждённый последний известный список по R7, содержащий уже
известные и отсутствующие в справочнике фулфилмента номера.
Событие: сохранение загрузки. Результат:
каждый отсутствующий номер добавляется один раз в пределах своего фулфилмента;
существующие записи не удаляются и не перезаписываются, даже если WB изменил
их поля или не включил их в текущий ответ. Сохраняются их внутренний идентификатор,
имя, адрес, время работы, признаки активности и исходное время загрузки.
Повтор списка/дубли в одном ответе не создают дублей. Основание: последнее уточнение
«Не актуализировать, а просто новые загружать», решение A2.

**R3. Прежние отгрузки и общие пути справочника сохраняются.** Условие: отгрузка
FBO уже содержит выбранный склад либо справочник загружается при открытии/из
фонового заполнения пустого кэша. Событие: дневная или такая начальная загрузка,
затем чтение отгрузки и списка. Результат: прежний номер и прежнее имя доступны,
отгрузка не получает другой склад, новые склады видны в существующем выборе.
Во всех затронутых путях записи сохраняются по R2, а не заменяются целиком.
Основание: уточнение о сохранении старых записей, действующие потребители данных,
AGENTS.md §3; решение A3, случаи B04, B09.

**R4. Рабочий ключ не зависит от первого селлера.** Условие: метод WB доступен,
но ключи первого селлера отсутствуют, не подходят либо запрос по ним не дал пригодного списка,
но другой селлер того же фулфилмента располагает рабочим ключом. Событие: загрузка.
Результат: WMS пробует существующие доступные ключи внутри этого фулфилмента,
доходит до рабочего и добавляет новые склады; успешный список завершает поиск
для этого фулфилмента. Явное общее отключение метода WB обрабатывается по A4/A6
и не требует перебора всех ключей ради поиска несуществующего рабочего метода.
Ключ другого фулфилмента не используется. Если рабочих
ключей нет, старые данные сохраняются и следующий дневной запуск снова пробует.
Основание: R1 и проверенная проблема выбора только первого селлера; решение A4.

**R5. Отказ и восстановление без потери справочника.** Условие: WB вернул
404/401/403/429/500, произошёл тайм-аут, ответ пустой/непригодный либо локальное
сохранение текущей загрузки отказало. Событие: ежедневный обход. Результат:
старые записи не меняются; ошибка одного фулфилмента не прерывает обработку
следующего. Следующий запуск штатно повторяет попытку, а полученные позднее
новые склады добавляются. Непригодный ответ не считается успешной загрузкой.
Для локального отказа сохранение принятого набора новых строк одной загрузки
либо завершается целиком, либо откатывается; повтор не создаёт дублей.
Основание: AGENTS.md §3 о связанных изменениях и восстановлении, R1–R2;
решения A4–A5, B03, B09.

**R6. Повторы, конкуренция и границы.** Условие: одинаковый список приходит
повторно или одновременно через дневную и начальную загрузку; разные фулфилменты
имеют склад с одинаковым номером. Событие: сохранение и чтение. Результат:
в рамках одного фулфилмента у каждого нового номера одна добавленная запись,
записи разных фулфилментов независимы. Только общий справочник WB допускает
внутреннее использование подтверждённых данных по R7; API по-прежнему возвращает
записи своего фулфилмента, без сведений о других клиентах. Не меняются права, документы FBO,
остаток, резерв, справочник Ozon, глобальные расписания и дизайн форм.
Не появляются новые экраны, пользовательские действия и требования сменить ключ.
Основание: AGENTS.md §3, существующая принадлежность справочника; A2–A6, B08.

**R7. Использование последнего известного списка при отключении WB.** Условие:
метод FBW временно отключён, у фулфилмента есть настроенный WB, а в WMS сохранён
подтверждённый общий список FBW. Событие: ежедневная загрузка либо существующее
начальное заполнение справочника. Результат: отсутствующие у этого фулфилмента
номера добавлены из последнего известного списка по R2; прежде пустые справочники
ArtMaks, «Бамбука», «Руспро» доступны в прежнем выборе склада. Время получения
данных от WB сохраняется из источника, не заменяется сегодняшней датой; строки
источника не меняются. Повтор ничего не дублирует. Склад в документе выбирает
оператор, автоматически выбирать его по черновику или разрешать утверждение без
выбора нельзя. При отсутствии подтверждённого списка данные не выдумываются;
после восстановления метода новые номера добавляются обычным путём R1/R2.
Основание: новые факты ведущего об общем справочнике и пустых кэшах, исходная
просьба добавлять новые записи, сохранение действующего бизнес-процесса; A6.

## 4. Решения аналитика и оставшиеся вопросы

**A1.** Использовать имеющуюся ежедневную задачу и её время 03:00 по действующему
часовому поясу планировщика. Владелец задал периодичность, а не новое время;
вводить второе расписание или менять глобальный часовой пояс не требуется.
Наличие задачи в коде недостаточно: исполнение по расписанию подтверждается
отдельно на приёмке. Успешная загрузка нужна и при непустом справочнике.

**A2.** «Новый склад» определяется парой «фулфилмент + номер склада WB», а не
названием: переименование того же номера не создаёт новый склад и не обновляет
старый. Если WB больше не возвращает номер или меняет его активность, прежняя
запись сохраняется. Для нового номера заполнить существующие поля справочника
из пригодного ответа или подтверждённого списка A6, с сохранением точного номера
и существующей обработки необязательных полей. У старой записи `fetched_at` не обновлять: это было бы
перезаписью, прямо отвергнутой владельцем. Исторические дубли, если обнаружатся,
не удалять в рамках этой задачи; правило предотвращает новые дубли.

**A3.** Общая функция записи не может оставаться разрушительной для другого
потребителя: ежедневный, ленивый и фоновый первоначальный пути должны соблюдать
добавление R2. Сами формы и документы не переделывать. Старый выбранный склад
сохраняется в отгрузке и остаётся в справочнике даже при отсутствии в новом ответе.

**A4.** Перебирать селлеров своего фулфилмента в существующем порядке регистрации;
внутри селлера пробовать доступные виды ключей, допускаемые выбранным рабочим
методом WB. Не использовать одинаковый ключ повторно в рамках этого поиска.
Нет ключа/неудача первого — перейти к следующему; после первого пригодного
непустого списка прекратить поиск. Это общий справочник, объединять несколько
успешных ответов от селлеров без основания не нужно. При явном сообщении WB
об общем временном отключении прекратить дальнейший перебор этого метода
в текущем дневном обходе, применить R7 для фулфилментов и повторить запрос на
следующем ежедневном запуске. Обычные 401/403, неизвестный 404 или ошибка одного
ключа не считаются общим отключением и не останавливают остальные фулфилменты.
Перебор не означает выпуск, замену или управление секретами. Идентичность
владельца ключа по значению ключа не определять. Ключи и клиентские данные
чужого фулфилмента не привлекать; исключение касается только общего справочного
списка WB по A6, без переноса принадлежности и прав клиента.

**A5.** Новая диагностика отменяет прежнюю гипотезу «разработчик найдёт другой
рабочий метод вместо 404». Причина подтверждена: WB временно отключил FBW-метод.
Не требовать от разработчика невозможного успешного ответа сейчас и не считать
200 от `/ping` или FBS-метода `/api/v3/offices` выполнением R1. Для будущего
восстановления сохраняется клиент официального FBW-метода; если WB объявит
другой метод, разработчик сверит официальный контракт и фактический ответ.
Принадлежность склада к FBW обязательна, общий «Склад WB РФ» из отчёта не
становится выбираемым складом без реального номера.

**A6. Решение аналитика по существующим данным.** Пока WB отключён, использовать
подтверждённый последний известный список FBW из имеющихся кэшей WMS как общий
источник для добавления отсутствующих номеров в справочники фулфилментов с WB.
«Новый» здесь означает отсутствующий в справочнике получателя, а не впервые
открытый WB после 14.08. Это позволяет заполнить пустой список без изменения
бизнес-поведения: остаются прежние форма, выбор оператором и обязательность склада.
Свежие склады, о которых WB больше не сообщает, таким способом обнаружить нельзя.

Использовать именно проверенные данные прежней загрузки FBW, не произвольные
строки другого клиента, не склады Ozon или FBS. На одинаковый номер выбрать
данные с самой поздней исходной датой получения от WB; при одинаковой дате
использовать стабильный порядок источников, не менять существующую строку
получателя. Добавленные строки принадлежат получателю с собственными внутренними
идентификаторами, исходная дата WB сохраняется. Не копировать ключи, идентификаторы
внутренних строк источника, документы, настройки селлера или другие клиентские
данные. API и права остаются в границах своего фулфилмента.

Новая сущность общего каталога, журнал или пользовательский режим не нужны:
использовать текущий справочник и общий внутренний путь добавления. Ежедневная
попытка официального запроса сохраняется; при отключении — пополнение известными
номерами, при восстановлении — добавление новых из WB. Само копирование кэша
не выдавать за свежую загрузку WB, проверку доступности приёмки склада или
разрешение автоматически выбрать склад в черновике. Основание A6 — проверенная
общность справочника, наличие последнего списка и AGENTS.md о простом решении
через существующие данные. Вопрос владельцу о смене процесса не требуется.

Непригодные строки без номера/имени не добавлять, как и сейчас; пригодные новые
строки того же корректного списка можно сохранить. Пустой ответ не очищает
справочник; полностью непригодный результат позволяет перейти к следующему ключу.
Ошибку фиксировать существующим техническим журналом без значений секретов;
нового экрана/статуса/журнала для пользователя не вводить. На следующем ежедневном
запуске попытка повторяется; дополнительный частый цикл повторов не требуется.

Вопросов владельцу нет: временное решение A6 сохраняет бизнес-поведение.
Полная загрузка новых складов из WB внешне заблокирована до восстановления
метода; это ограничение источника, не скрытый выбор владельца и не замена R1.

## 5. Проверки

Сценарии с искусственными сбоями и конкуренцией выполняются только в тестовой среде.
После сохранения читать справочник/отгрузку новой сессией. Столбцы «Тест» и
«Вердикт» пока пусты; наличие расписания и успешный ручной вызов не доказывают
фактический ежедневный запуск.

текущего отключения, C9c — реальную успешную загрузку после восстановления WB.

## 6. Сверка исходного запроса и требований

Запрос → требования: «автоматом тянуть … по расписанию» — R1/A1; «ежедневная
загрузка» — R1 и C1/C11; «загружать эти склады» — новые строки R2, доступность R3;
позднейшее «Не актуализировать, а просто новые загружать» — R2/A2, имеет приоритет
над предыдущим словом «актуализировать» в том же сообщении.

Требования → основания: R1 — обе реплики владельца; R2 — прямое уточнение;
R3 — сохранение существующих строк и действующих отгрузок, без нового UI;
R4 — достижение R1 при проверенном недостатке выбора первого селлера;
R5 — восстановление ежедневной загрузки без разрушения данных по AGENTS.md;
R6 — отсутствие дублей при повторном добавлении, границы фулфилментов и сохранение
соседних процессов из правил проекта; R7 — решение аналитика по новым фактам
об общем историческом справочнике. A1–A6 отделены от слов владельца.
Каждое R покрыто C; технический выбор метода не переложен на владельца.
R1/R3 проверяются раздельно: C9a — разбор формата, C9b — живая диагностика
отключения, C9c — реальный успех после восстановления. Временное добавление
из существующего списка проверяют C12–C15; оно сохраняет просьбу «просто новые
загружать» для отсутствующих записей, но не обнаруживает неизвестные WB склады
после августа. Полнота свежего внешнего списка до восстановления не заявляется.

## Заключение

Постановка уточнена по фактам ведущего от 09.10.2026 и определяет целевое
поведение после восстановления WB и временное использование существующего
общего FBW-списка. Она подготовлена к автоматическим тестам обоих путей;
вопросов владельцу нет, поскольку выбор склада, утверждение и учёт не меняются.
Требование получить свежие склады из WB полностью не выполнено и не может быть
принято до восстановления источника: C9c внешне заблокирована. C9b подтверждает
диагностику, C12–C15 — исторические данные и сохранение прежнего процесса.
Не выдавать успешное заполнение пустых кэшей за успешный ответ метода WB.

Слова владельца и уточнения сохранены дословно. Новые production-факты и выписка
WB переданы ведущим; здесь код прочитан, экран и production не проверены,
независимое открытие release notes не удалось. Вердикты всех проверок и ссылки
на тесты пусты до соответствующих этапов. Изменён только этот документ локально;
сохранение в Git и публикацию выполняет ведущий.
