## 3. Требования

- **R1. Компактная карточка заказа.** Фото слева, справа: номер заказа, название товара (до 2 строк), ШК/артикул, селлер, «Отгрузить до». Строку маршрута и строку «Поступил» убрать; статус не выводить отдельной строкой. На экране 1080×2280 видно не меньше 4 карточек. Близкий срок по-прежнему выделен (WMS-401).
- **R2. «Выбрать все» и «Снять выделение»** для заказов, доступных к выбору в текущем списке (с учётом фильтра R3).
- **R3. Фильтр по селлеру** над списком: «Все селлеры» + селлеры из загруженных заказов текущей площадки.
- **R4. Общий список — только новые заказы для выбора.** Заказы, уже находящиеся в поставке, в общем списке не показываются (к ним ведёт «В работе»); зелёной подсветки подбора в общем списке нет. *(Решение ведущего по словам «как будто я их не взял в работу»; владельцу сообщено.)*
- **R5. Массовое создание поставок как в вебе.** Кнопка «Создать поставки (N)» делит выбранные заказы на группы тем же ключом, что веб (`fbsSupplyGroupKey`: селлер, склад WB, тип груза, склад WMS, тип покупателя), показывает группы (селлер · кол-во заказов), для WB — выбор «Склад / СЦ» или «ПВЗ». Название вводить не обязательно: имя как в вебе — `FBS <дата dd.MM.yyyy>`. По каждой группе — `preflight`, несовместимая группа показывается с причиной и не создаётся; совместимые создаются `from-orders` по одной с ключом повтора на группу (частичный успех виден по группам). Разные селлеры больше не дают общий отказ.
- **R6. Общий подбор созданных поставок.** После создания открывается один экран подбора по всем созданным поставкам (как «едины на подборе» в вебе): общий список товаров по R8, скан товара подбирает для самого старого неподобранного подходящего заказа среди всех поставок группы (в ту поставку, где этот заказ). Для одной поставки — тот же экран.
- **R7. Отказ сервера не застревает.** Если сервер окончательно отказал (HTTP 4xx или `retryable:false`), сохранённая попытка создания/добавления стирается, повторно не отправляется и окно само не открывается; оператор видит причину по-русски применительно к заказам (`different_seller` → «разные селлеры» и т. п., номера заказов). Сохранённая попытка остаётся и восстанавливается только при потере связи / 5xx / неизвестном результате (защита WMS-445 от дубля сохраняется).
- **R8. Экран поставки — как был, без селлера/маршрута/склада.** Исходный вид (cef944b) сохраняется: название, «площадка · статус», строка счётчиков, «Состав», три вертикальные кнопки во всю ширину «Подбор», «Упаковка и этикетки», «Короба», ниже передача. Убираются только строки «Селлер», «Маршрут», «Склад». Состав — карточками товаров с фото (решение владельца 29.09). Карточка поставки в «В работе» — исходная. *(Исправление ведущего: прежняя редакция R8 с «кнопками наверху» была дописана ведущим от себя, владелец её отклонил: «зачем остальные экраны поменяли… он же был нормальный».)*
- **R9. Компактный подбор по товарам.** Список товаров поставки (или группы), одна строка на товар: фото, название, ШК, «подобрано X из Y»; под строкой — ячейки, где товар есть, с доступным количеством (из `pick-options`), подобранные — зелёным. Карточки заказов, селлер, маршрут, «Поступил», «Отгрузить» на подборе не выводятся. Сканирование ячейки/товара — как сейчас (работает).
- **R9a. Карточки подбора по образцу владельца.** Сверху полоса текущей ячейки (зелёная — ячейка отсканирована, серая — нет), заголовок «Товары»; карточка товара: крупное фото ~1/3 ширины, название, артикул, ШК, крупно красным «N шт.» к подбору, «Подобрано» зелёным; ячейки с остатком под карточкой. Состав поставки — те же карточки без красного.
- **R14. Без отдельного шага «Короба».** На экране поставки остаются «Подбор», «Упаковка и этикетки» и передача (вид R8); кнопка «Короба» убирается. В подборе коробов нет (решение владельца: «2. Не надо»).
- **R15. Короба в упаковке.** Экран «Упаковка и этикетки» поставки содержит всё, что было на шаге «Короба»: создать короб, открыть/закрыть, положить в открытый короб сканом (товар/QR заказа) или изменить количество, этикетка короба (QR от WB), «Все этикетки»; для Ozon — позиции и подтверждение сборки, как было. Прежние функции упаковки (отметка упаковки, печать этикеток, QR заказа → ЧЗ) не меняются. Поведение сканов при открытом коробе — как в упаковке веба с коробами (групповая сборка WMS-574, `FbsAssemblySupplyFrame.tsx`).
- **R16. Упаковка массовой сборки — по поставкам.** После массового подбора из экрана общего подбора есть переход к упаковке группы: список поставок группы (название, селлер, прогресс упаковки); оператор заходит в поставку → экран упаковки этой поставки по R15; сканы применяются только к поставке, в которую зашёл; «назад» — к списку поставок группы, откуда заходит в следующую. Передача — у каждой поставки, как сейчас.
- **R17. Ручной подбор.** Тап по карточке товара в подборе (одной поставки и общем) → выбрать ячейку из тех, где товар есть (с доступным количеством) → ввести, сколько взято → сохраняется существующим серверным действием, как ручной подбор в вебе; заказы — самые старые неподобранные, как при скане; повтор нажатия не удваивает.
- **R18. Два действия после полного подбора, без нового статуса и блокировок.** На экране подбора одной поставки и общего подбора сборочного задания две крупные нижние кнопки «К упаковке» и «Завершить подбор» отсутствуют, пока не подобраны все единицы всех открытых поставок (`total > 0`, `picked == total`), и появляются вместе только после полного подбора. В общем подборе прежняя верхняя «К упаковке» убирается. «К упаковке» открывает упаковку этой поставки, а для сборочного задания — список входящих поставок для последовательной упаковки. «Завершить подбор» не создаёт статус, поле или отдельную серверную операцию: сервер уже вычисляет пройденный подбор по фактам `pick`; кнопка возвращает в FBS с **открытой вкладкой «В работе»**, где видна завершённая поставка/задание и откуда упаковщик может их снова открыть. Возврат на вкладку новых заказов не выполняет запрос. Вкладки и дальнейшие действия не блокировать.
- **R20. Сохранение ручного подбора с клавиатуры.** В окне ручного подбора после выбора товара и ячейки ввод положительного количества и нажатие клавиатурной галочки/Done запускает то же сохранение, что видимая кнопка подтверждения. Действуют одинаковые ограничения по доступному количеству и одинаковая обработка ошибки; двойной сигнал «галочка + кнопка» в ходе одной занятой операции не создаёт два подбора. При отмене окна количество не сохраняется. Поведение должно соответствовать уже сделанному сохранению количества галочкой в приёмке WMS-585.
- **R19. Моментальное отражение действий ТСД в БД и вебе.** После успешного ответа на каждое действие ТСД новый факт уже зафиксирован в PostgreSQL и виден при немедленном повторном чтении теми API, которыми пользуется веб; закрывать экран или ждать фонового задания не требуется. Проверяются: FBS-подбор сканом, ручной FBS-подбор, отмена подбора, приёмка товара, размещение из сортировки в ячейку, сборка и отгрузка обычной отгрузки, передача FBS-поставки. Семантика учёта: FBS-подбор должен сразу перемещать единицу из исходной ячейки в место подбора/сортировки, не уменьшая общий складской остаток; отмена возвращает её обратно. Приёмка сначала фиксирует факт в строке документа, а остаток возникает при предусмотренном учётном шаге; размещение даёт парные движения между сортировкой и ячейкой. Обычная отгрузка не должна списывать одну единицу дважды между сборкой и финальным `ship`. Клиент после мутации перечитывает сервер и не показывает устаревший кэш.
- **R10. Отменить последний подбор.** Кнопка «Отменить последний» возвращает последнюю успешно подобранную единицу (через `pick/set` товара в той же ячейке/контейнере на количество −1 от текущего, с защитой от повторного нажатия), после чего данные перечитываются с сервера. Если отменять нечего — кнопка неактивна.
- **R11. «Сменить ячейку».** Кнопка видна только когда ячейка отсканирована и называется «Сменить ячейку».
- **R12. Без ложных сигналов.** Звук/вибрация/зелёная вспышка успеха — только на результат скана или действия оператора (подбор, упаковка, короб, ЧЗ, создание), не на загрузку и обновление экранов.
- **R13. Остальное не меняется:** упаковка и этикетки, ЧЗ, короба («открыть/закрыть короб»), передача, Ozon-позиции, восстановление после потери ответа там, где сервер не ответил. Серверный код не меняется.

**Находка C16-FBS-1.** FBS-подбор в текущем сервере — только запись факта pick. Он не меняет расположение и не резервирует/уменьшает видимое количество исходной ячейки. Фактическое `fbs_shipment -1` создаётся лишь при передаче поставки маркетплейсу. Поэтому требование владельца «подобрал на ТСД → обновил веб → на ячейке уже нет одной единицы» сейчас нарушено и одновременно нарушено проектное правило «подбор меняет расположение, а не остаток». Серверное правило не исправлялось в рамках этой проверки по прямому ограничению владельца; требуется отдельное согласованное исправление учёта FBS.

**Кэш ТСД.** Очевидного клиентского дефекта перечитывания не найдено: FBS после скана/ручного подбора/отмены обновляет workspace и `pick-options`, приёмка, сортировка и обычная отгрузка перечитывают документ после мутации. Расхождение FBS воспроизводится свежими веб-GET и прямым чтением PostgreSQL, то есть находится на серверной стороне, а не в кэше ТСД.

**Как открывает этап веб.** `FfFbsSupplyWorkspace` при новом открытии берёт вычисленный сервером stage (`packing` после полного подбора), но сохранённый в `sessionStorage` выбор вкладки имеет приоритет. `FfFbsSupplyAssembly` не имеет отдельного серверного статуса задания и при новом открытии выбирает сохранённую вкладку либо `composition`; автоматически выводить веб-группу на упаковку эта задача не меняла. На ТСД полностью подобранное задание теперь определяется по уже существующим `picked_count/orders_count` его поставок и открывается в списке упаковки без нового поля. Если владелец ожидает такое же автоматическое открытие именно веб-группы, это остаётся отдельной фронтовой правкой, а не основанием добавлять статус в сервер.
