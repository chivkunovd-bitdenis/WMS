# WMS-488 · AVpack: товары каждого селлера видны только ему и фулфилменту

## Исходный запрос

Формулировка владельца, переданная ведущим 21.09.2026: подключённые к AVpack селлеры видят в своём каталоге чужие товары друг друга. Нужен глубокий разбор и закрытие всех путей утечки. AVpack как фулфилмент должен видеть товары подключённых селлеров; каждый селлер — только свои. Требование не ограничено скрытием строк на экране.

Это **новая WMS-488**. Историческая WMS-481 от 19.09 касалась удаления копии селлера AVpack из другого, тестового арендатора. Тогдашний вывод о доступе не доказывает состояние текущего AVpack и не закрывает этот запрос.

## Проверенный процесс и границы расследования

В текущем коде селлерский экран `/seller/products` загружает `GET /products/wb-catalog`. Сервер берёт `effective_seller_id` из активного магазина в токене; для пользователя с правом управления магазинами это может быть не домашний селлер. `seller_shop_service.py` даёт это право по признаку пользователя, списку email и встроенным фрагментам email; затем включённая делегация разрешает другой магазин того же арендатора. Поэтому один только фильтр списка по `effective_seller_id` не обеспечивает правило владельца «каждый селлер — только свои». Также существуют `GET /products`, `/products/categories`, прямые маршруты по ID, массовые изменения, связанные списки и выгрузки; каждый путь требуется проверить по фактическим правам и данным.

Ведущий исследователь сообщил о свежей проверке production на чтение: в AVpack есть пользователь селлера с включённым управлением магазинами и делегациями на других селлеров. Это подтверждает существование конкретного **разрешённого текущим кодом** пути к чужому каталогу; не доказывает, что любой селлер AVpack видит всё, и не доказывает отсутствия иных путей. Конкретные результаты API/данных и корневая причина должны быть приложены к приёмке. Боевые данные менять ради воспроизведения нельзя.

Позднее исследование на опубликованном frontend bundle подтвердило отдельный клиентский дефект: первая вкладка показывала 38 товаров одного селлера; во второй вкладке вошли другим селлером с 19 товарами и затем вышли. Первая вкладка получила события `storage`, но продолжила показывать старый каталог и пользоваться старой сессией. `useAuth` не синхронизировал состояние React с изменением общего хранилища. Источник и границы воспроизведения — [AUDIT.md](../evidence/WMS-488/AUDIT.md). Связь этого механизма с конкретным наблюдением владельца не доказана, но раскрытие прежних карточек после смены общего пользователя подтверждено.

Первичная постановка готовилась до браузерной проверки. После реализации ведущий исследователь прошёл селлерский и FF-каталог в настоящем Chrome на локальном production build с обезличенными API fixtures; реальные серверные границы проверены отдельно на тестовой БД. Полное доказательство и ограничения — [ACCEPTANCE.md](../evidence/WMS-488/ACCEPTANCE.md). Финальная приёмка исходного аналитика следует после общего перекрёстного ревью.

Пустой результат поиска и метаданные страницы не раскрывают наличие чужих товаров. | Запрос о всех путях утечки; экспорты и агрегаты обходят экранный фильтр. |
| R6 | Смена активного магазина, старый токен с чужим `seller_id`, обновление страницы, повторный вход и клиентский кэш не открывают чужой каталог AVpack-селлеру. Для старого подписанного токена с чужим активным магазином сервер **игнорирует этот выбор и применяет домашний `User.seller_id`** во всех чтениях и действиях; `/auth/me` показывает домашний магазин. Новый запрос переключиться на чужой магазин не создаёт токен для него. Когда в другой вкладке браузера происходит вход под другим пользователем или выход, открытая вкладка сразу прекращает использовать прежнюю сессию и убирает старые карточки, счётчики и детали со своего экрана; при новом входе показывает данные только после проверки нового пользователя и его области. Запоздалый ответ чтения каталога или `/auth/me`, начатого до смены/выхода, не может снова показать прежнего пользователя и его товары. Сервер независимо проверяет принадлежность товара на каждом пути. Менеджер другого арендатора сохраняет существующие разрешённые делегации. | Прямое правило владельца для AVpack и подтверждённый межвкладочный дефект; нормализация старого токена не прерывает собственную работу селлера. |
| R7 | Товары другого арендатора не видны и не изменяемы ни AVpack-ФФ, ни его селлерами; товар селлера AVpack сохраняет правильного владельца после синхронизации WB/Ozon, импорта, создания и объединения. Ошибочно принадлежащие другому селлеру данные не маскируются одной только правкой интерфейса: первопричина и затронутые записи устанавливаются отдельно перед исправлением данных. | Изоляция клиентов проекта и глубокий анализ причины, а не косметический фильтр. |

## Продуктовое решение

**Решение 21.09 после повторной проверки роли.** Прямой запрос владельца «каждый подключённый селлер — только свои товары, AVpack как ФФ — всех» задаёт границу и для Геруса: в production его роль `fulfillment_seller`, есть явный флаг менеджера и пять активных делегаций, но нет роли или прав сотрудника ФФ. Происхождение личного назначения менеджером неизвестно; это не даёт основания объявить старые записи ошибкой, но не создаёт исключения из нового правила владельца. Поэтому на сервере для всех пользователей с ролью селлера **именно арендатора AVpack** область товаров и связанных действий равна домашнему `User.seller_id` независимо от флага, делегаций и `seller_id` в токене. FF admin/staff с действующими правами продолжают видеть всех селлеров своего арендатора. Делегации других арендаторов работают как прежде. Исторические флаг и пять grants Геруса в production не меняются; безопасность не должна зависеть от их ручного отзыва.

Арендатора определяют по **уникальному `Tenant.slug == "avpack-9uczh"` из БД**, проверенному для AVpack в production запросом `READ ONLY` (одна строка), а не по email Геруса, имени организации/селлера или вшитому UUID. В тестах должны быть AVpack и другой tenant с одинаково выданным флагом/делегацией: правило home-only действует только для первого. Для старого токена с чужим выбранным магазином сервер возвращает домашний scope и домашний active shop в `/auth/me`; запрос создать новый токен на чужой магазин отклоняет до выдачи токена. Существующий селлерский экран показывает только домашний магазин без нового UI-режима. Это сохраняет собственную работу селлера и не вводит блокировку его обычных операций.

Исследование установило scan-обход, сохранение прежней сессии между вкладками, runtime-право менеджера по email и пропуск Products permission в массовом признаке ЧЗ. Карта маршрутов и production read-only результаты сохранены в [AUDIT.md](../evidence/WMS-488/AUDIT.md); ошибочных владельцев товаров не найдено. Точная причина каждого сообщения владельца о массовом показе всех чужих товаров и назначение особого менеджера остаются неустановленными.

## Заключение

**Обновление 21.09 после решения по Герусу: к выпуску не принято.** Помимо нарушенной C6, проверки C1/C3–C5/C8/C10 не покрывают новое требование home-only для AVpack-менеджера с активными делегациями.
