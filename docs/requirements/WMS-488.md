# WMS-488 · AVpack: товары каждого селлера видны только ему и фулфилменту

## Исходный запрос

Формулировка владельца, переданная ведущим 21.09.2026: подключённые к AVpack селлеры видят в своём каталоге чужие товары друг друга. Нужен глубокий разбор и закрытие всех путей утечки. AVpack как фулфилмент должен видеть товары подключённых селлеров; каждый селлер — только свои. Требование не ограничено скрытием строк на экране.

Это **новая WMS-488**. Историческая WMS-481 от 19.09 касалась удаления копии селлера AVpack из другого, тестового арендатора. Тогдашний вывод о доступе не доказывает состояние текущего AVpack и не закрывает этот запрос.

## Проверенный процесс и границы расследования

В текущем коде селлерский экран `/seller/products` загружает `GET /products/wb-catalog`. Сервер берёт `effective_seller_id` из активного магазина в токене; для пользователя с правом управления магазинами это может быть не домашний селлер. `seller_shop_service.py` даёт это право по признаку пользователя, списку email и встроенным фрагментам email; затем включённая делегация разрешает другой магазин того же арендатора. Поэтому один только фильтр списка по `effective_seller_id` не обеспечивает правило владельца «каждый селлер — только свои». Также существуют `GET /products`, `/products/categories`, прямые маршруты по ID, массовые изменения, связанные списки и выгрузки; каждый путь требуется проверить по фактическим правам и данным.

Ведущий исследователь сообщил о свежей проверке production на чтение: в AVpack есть пользователь селлера с включённым управлением магазинами и делегациями на других селлеров. Это подтверждает существование конкретного **разрешённого текущим кодом** пути к чужому каталогу; не доказывает, что любой селлер AVpack видит всё, и не доказывает отсутствия иных путей. Конкретные результаты API/данных и корневая причина должны быть приложены к приёмке. Боевые данные менять ради воспроизведения нельзя.

Позднее исследование на опубликованном frontend bundle подтвердило отдельный клиентский дефект: первая вкладка показывала 38 товаров одного селлера; во второй вкладке вошли другим селлером с 19 товарами и затем вышли. Первая вкладка получила события `storage`, но продолжила показывать старый каталог и пользоваться старой сессией. `useAuth` не синхронизировал состояние React с изменением общего хранилища. Источник и границы воспроизведения — [AUDIT.md](../evidence/WMS-488/AUDIT.md). Связь этого механизма с конкретным наблюдением владельца не доказана, но раскрытие прежних карточек после смены общего пользователя подтверждено.

Первичная постановка готовилась до браузерной проверки. После реализации ведущий исследователь прошёл селлерский и FF-каталог в настоящем Chrome на локальном production build с обезличенными API fixtures; реальные серверные границы проверены отдельно на тестовой БД. Полное доказательство и ограничения — [ACCEPTANCE.md](../evidence/WMS-488/ACCEPTANCE.md). Финальная приёмка исходного аналитика следует после общего перекрёстного ревью.

## Требования

| ID | Проверяемое поведение | Основание |
|---|---|---|
| R1 | **Любой пользователь с ролью `fulfillment_seller` в AVpack**, включая Геруса с явным флагом менеджера и пятью активными делегациями, видит в каталоге только товары своего домашнего `User.seller_id`. Список, карточка, поиск, фильтры, категории, счётчики, подсказки и пагинация считают данные в той же границе; наличие чужого артикула, ШК, SKU или названия не выдаёт чужой товар. | Прямое правило владельца «каждый селлер — только свои»; подтверждённая роль Геруса — селлер, а не ФФ. |
| R2 | AVpack под ролью фулфилмента с существующим правом чтения каталога продолжает видеть товары всех подключённых к **этому** фулфилменту селлеров, в том числе через выбор нужного селлера. Селлерский вход и вход ФФ различаются по серверному праву, а не по видимости кнопки. | Прямое правило владельца «AVpack как ФФ должен видеть товары подключённых селлеров». |
| R3 | Прямой запрос **любого AVpack-селлера, включая менеджера с делегациями**, к чужому товару по ID или через скан кода и связанные с ним чтения (карточка, остатки, направления, правила публикации, упаковочные инструкции, история размеров, маркировка, изображения/печатные данные, если доступны из кабинета) не возвращает сведения о чужом товаре. Даже ответ о нескольких совпадениях кода не раскрывает чужие товары или заказы. Известный ID фоновой задачи другого магазина также не открывает её результат. Обращение к собственному товару и доказанно своей задаче продолжает работать. | Требование закрыть все пути утечки, не только таблицу; найденные обходы `GET /operations/scan/resolve` и `GET /operations/background-jobs/{job_id}`. |
| R4 | Любой AVpack-селлер, включая менеджера с делегациями, не может создать, изменить, импортировать, объединить, привязать, напечатать или массово изменить чужой товар через прямой ID, подменённый `seller_id`, активный магазин в токене, смешанный список ID либо экспорт/импорт. Отказ происходит до изменения чужих данных; собственные операции сохраняются. | Та же граница владения должна действовать на записи и действия, иначе обход экрана остаётся. |
| R5 | Любая выгрузка, отчёт, файл, печать, вспомогательный список товаров или ответ о фоновой задаче, доступные **любому AVpack-селлеру, включая менеджера**, включают только товары его домашнего селлера и производные данные. `payload_json`, `result_json` и `error_message` задачи другого магазина либо общей задачи арендатора без доказанной домашней области не выдаются даже по известному `job_id`, независимо от того, кто когда-то запустил задачу. Домашняя задача одного из пяти проверенных типов — `wildberries_cards_sync`, `storage_measurement_rebuild`, `wildberries_supplies_sync`, `wildberries_marketplace_orders_sync`, `fbs_stock_sync` — доступна независимо от того, запущена селлером или ФФ; её payload/result относятся только к домашнему селлеру. Произвольный сохранённый `str(exc)` в `error_message` для селлера заменяется точным общим сообщением «Не удалось выполнить задачу», сохраняя статус и доступ к задаче. Неизвестный тип, неверный/чужой `seller_id`, задача без домашней области и отдельно защищённая FF-печать не становятся доступными из-за одного поля `seller_id`. Пустой результат поиска и метаданные страницы не раскрывают наличие чужих товаров. Задачи ФФ и системный обход всех подключённых магазинов сохраняются. | Запрос о всех путях утечки; экспорты, агрегаты и `GET /operations/background-jobs/{job_id}` обходят экранный фильтр. Проверены producer/result восьми типов: пять содержат данные одного селлера, включая три из FF-процесса; сырой текст ошибки произволен. |
| R6 | Смена активного магазина, старый токен с чужим `seller_id`, обновление страницы, повторный вход и клиентский кэш не открывают чужой каталог AVpack-селлеру. Для старого подписанного токена с чужим активным магазином сервер **игнорирует этот выбор и применяет домашний `User.seller_id`** во всех чтениях и действиях; `/auth/me` показывает домашние `seller_id`/`active_seller_id`, только домашний магазин в `switchable_shops`, пустой `delegatable_shops` и вычисляемое `can_manage_seller_shops=false` без изменения флага в БД. Новый запрос переключиться на чужой магазин не создаёт токен для него; `PUT /auth/seller-shops` не изменяет делегации, в том числе при пустом списке. Когда в другой вкладке браузера происходит вход под другим пользователем или выход, открытая вкладка сразу прекращает использовать прежнюю сессию и убирает старые карточки, счётчики и детали со своего экрана; при новом входе показывает данные только после проверки нового пользователя и его области. Запоздалый ответ чтения каталога или `/auth/me`, начатого до смены/выхода, не может снова показать прежнего пользователя и его товары. Сервер независимо проверяет принадлежность товара на каждом пути. Менеджер другого арендатора сохраняет существующие разрешённые делегации. | Прямое правило владельца для AVpack и подтверждённый межвкладочный дефект; нормализация старого токена не прерывает собственную работу селлера. |
| R7 | Товары другого арендатора не видны и не изменяемы ни AVpack-ФФ, ни его селлерами; товар селлера AVpack сохраняет правильного владельца после синхронизации WB/Ozon, импорта, создания и объединения. Ошибочно принадлежащие другому селлеру данные не маскируются одной только правкой интерфейса: первопричина и затронутые записи устанавливаются отдельно перед исправлением данных. | Изоляция клиентов проекта и глубокий анализ причины, а не косметический фильтр. |

## Продуктовое решение

**Решение 21.09 после повторной проверки роли.** Прямой запрос владельца «каждый подключённый селлер — только свои товары, AVpack как ФФ — всех» задаёт границу и для Геруса: в production его роль `fulfillment_seller`, есть явный флаг менеджера и пять активных делегаций, но нет роли или прав сотрудника ФФ. Происхождение личного назначения менеджером неизвестно; это не даёт основания объявить старые записи ошибкой, но не создаёт исключения из нового правила владельца. Поэтому на сервере для всех пользователей с ролью селлера **именно арендатора AVpack** область товаров и связанных действий равна домашнему `User.seller_id` независимо от флага, делегаций и `seller_id` в токене. FF admin/staff с действующими правами продолжают видеть всех селлеров своего арендатора. Делегации других арендаторов работают как прежде. Исторические флаг и пять grants Геруса в production не меняются; безопасность не должна зависеть от их ручного отзыва.

Арендатора определяют по **уникальному `Tenant.slug == "avpack-9uczh"` из БД**, проверенному для AVpack в production запросом `READ ONLY` (одна строка), а не по email Геруса, имени организации/селлера или вшитому UUID. В тестах должны быть AVpack и другой tenant с одинаково выданным флагом/делегацией: правило home-only действует только для первого. Для старого токена с чужим выбранным магазином сервер возвращает домашний scope и домашний active shop в `/auth/me`; запрос создать новый токен на чужой магазин отклоняет до выдачи токена. Существующий селлерский экран показывает только домашний магазин без нового UI-режима. Это сохраняет собственную работу селлера и не вводит блокировку его обычных операций.

Исследование установило scan-обход, сохранение прежней сессии между вкладками, runtime-право менеджера по email и пропуск Products permission в массовом признаке ЧЗ. Карта маршрутов и production read-only результаты сохранены в [AUDIT.md](../evidence/WMS-488/AUDIT.md); ошибочных владельцев товаров не найдено. Точная причина каждого сообщения владельца о массовом показе всех чужих товаров и назначение особого менеджера остаются неустановленными.

Адресное ревью объединённого SHA `69b3f2c` дополнительно нашло чтение фоновых задач только по арендатору. Это входит в исходное требование закрыть прямые пути к чужим товарным и производным данным: ответ по известному `job_id` содержит параметры и результат задачи, в том числе общие складские агрегаты. Даже обычный AVpack-селлер без флага менеджера может прочитать чужую задачу. Подробности и граница соседней находки по пустому документу отгрузки — в [дополнении к расследованию](../evidence/WMS-488/FOLLOWUP-ROLE-AND-STORAGE.md).

## Заключение

**WMS-488 принята к релизу по C1–C8, C10 и C11 в изолированном контуре на `22108eea6137eaaf192c03d53909db22e652c545`.** Исторические нарушения SHA `69b3f2c` закрыты в текущем backend/frontend и повторены адресными API-тестами и Chrome-сценариями. Я самостоятельно пересобрал frontend, прошёл 8 сценариев смены/выхода и два порядка старого ответа до `storage` на настоящем интерфейсе с синтетическими API; осмотрел снимки seller B и FF. Продуктовые ограничения совпадают со словами владельца: каждый AVpack seller-role, включая обладателя прежних grants, получает только домашний товар; AVpack как ФФ видит товары своих подключённых селлеров. Исторические grants и flag не переписываются ради изоляции, другие арендаторы сохраняют разрешённое делегирование.

Серверные факты подтверждены чтением текущего кода и адресных тестов для signed test JWT, прямых ID/scan/CSV/мутаций, миграции и фоновых задач. Общий backend прогон на интеграции сообщил 281 passed PostgreSQL; этот прогон не заменяет браузер и production. Новых блокировок собственных товарных действий в проверенной матрице не найдено. **C9 остаётся обязательной проверкой после выкладки**, когда можно установить работающий SHA и безопасно прочитать реальные данные на новом коде. Реальный вход по production JWT, внешние WB/Ozon вызовы и физическую печать здесь не проводили. Массовый показ чужого каталога из исходного сообщения не был повторён на старом production; обнаруженные пути утечки и сессии объясняют возможное раскрытие, но не доказывают единственную причину каждого наблюдения.
