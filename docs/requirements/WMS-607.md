# WMS-607 — запуск и прямая печать QR без настройки подключения

## Исходный запрос
30.09.2026: срочно исправить WMS Print. Windows и Mac: запустить программу,
сканировать из Chrome, сразу печатать QR системным принтером по умолчанию.
Без адресов, кодов сопряжения, выбора очереди, навыков, агентов и большого набора тестов.
Последнее указание владельца отменяет агентную цепочку для этой задачи.

## Требования
R1. Запуск отдельной программы без вопросов о сервере/складе/коде/принтере.
R2. Прямой приём подготовленной QR-этикетки из Chrome без window.print.
R3. Использовать текущий принтер ОС по умолчанию для каждого нового задания.
R4. Сохранить последовательность и не дублировать задание после потери ответа/перезапуска.
R5. Самостоятельные пакеты Windows x64 и macOS; исходники и SHA сохранены в Git.
R6. Программа открывает готовую локальную страницу проверки в Chrome.
R8. Уточнение владельца: «важно работать должно мгновенно прям за секунду».
Цель — скан → квитанция ОС менее 1000 мс; механика физического принтера измеряется отдельно.
R7. Не менять настройки безопасности ОС/Chrome. Первое системное разрешение
для загруженного приложения или обращения сайта к localhost нельзя обещать устранить.

## Ошибка ЧЗ в объединённой сборке — 30.09.2026

Владелец уточнил: скорость сканов восстановилась; в обычном FBS ежедневный
сценарий QR заказа → КИЗ работает. Требуется устранить регрессию нового
объединённого экрана, не переписывать архитектуру упаковки.

R9. Сохранить существующий серверный путь обычного FBS: перед commit ЧЗ
выполнить start-work только для ещё не подготовленной поставки. Новых кнопок
и ручной настройки нет. Повторное сохранение упаковки использует уже полученный
результат, даже если фоновое обновление экрана ещё не пришло.

Сравнение кода: обычная карточка вызывает startFbsSupplyWork до сканирования;
новый fbsSequentialPacking вызывал его лишь в pack, после bind и print.
В объединённом списке WMS-604 ручной старт скрыт. На staging у поставки
fa0f4b00-3cd3-423a-b88a-b809d6b60434 packaging_task_id=null, у второй поставки
подготовка есть. Чтение существующей серверной функции для заказа 500051
(транзакция завершена rollback, без записи) вернуло packaging_line_not_found.
Историческое требование о фактах вместо отдельного документа найдено в
CHAT_FBS_2026-08-31_RU.md и WMS-392; полное удаление старой сущности не выполнено
в прежнем коде и не входит в эту срочную коррекцию по последнему уточнению владельца.

## Уточнение о неизменности обычного FBS и эмуляторе

Владелец требует точную копию существующего сканирования: все селлеры и
поставки в одном списке плюс мгновенная печать, без новых ожиданий WB.
После fetch origin/etalon сравнение fbs_kiz.py, fbs_kiz_service.py и
fbs_marking_service.py не показало отличий от staging. Оба экрана используют
validate/commit; эти серверные функции в данной задаче не изменены.

На живом новом экране acf6940e исчезла packaging_line_not_found: код записан
за заказом 500060. Следом существующая защита сообщила wb_pending_confirmation.
Подтверждено, что staging обращается к wb-emulator.railway.internal, mock=false.
В его batch meta endpoint metaDetails всегда был пустым, хотя PUT сохранял
код и вердикт. Исправлен исключительно ответ эмулятора: точное сохранённое
значение и accepted/rejected по его существующему checkStatus. Пустой ответ
без предварительного PUT остаётся пустым; реальный сервер WB не меняется.

R10. Тестовый эмулятор должен возвращать сохранённый КИЗ и свой фактический
вердикт в текущем контракте metaDetails. Никаких подмен результата реального WB.
