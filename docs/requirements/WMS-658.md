## Что проверено в проекте

Существующее окно называется «Загрузка КИЗ» (`MarkingImportDialog`). Оно использует три пути сохранения:

1. `POST /operations/marking-codes/import/auto` автоматически сопоставляет строки загруженного файла с товаром. Сейчас сервер заранее выбирает только товары с `Product.requires_honest_sign=true`.
2. `POST /operations/marking-codes/import` сохраняет КИЗы на товары, заранее выбранные оператором. Сервер допускает товар с выключенным признаком, но после успешной загрузки его не включает.
3. `POST /operations/marking-codes/import/assign` назначает выбранному товару строки, оставшиеся после автоматического разбора. Сейчас сервер отвергает товар без признака ЧЗ.

Фронтенд предварительного ручного выбора и назначения остатка дополнительно скрывает товары без `requires_honest_sign`. При этом границы каталогов в существующих путях различаются: автоматический серверный поиск работает по точному `tenant_id + seller_id`, а ручной каталог сохраняет действующий допуск строк выбранного селлера и уже доступных в нём общих строк с `seller_id=null`. Эта задача снимает фильтр ЧЗ, но не расширяет остальные границы каждого пути.

Для PDF WMS декодирует DataMatrix, сохраняет полный декодированный payload в `MarkingCode.cis_code`, вырезанную этикетку — в `label_artifact_pdf`, а исходный PDF — через `MarkingCodeImportFile` в объектном хранилище. Исходный файл сохраняется best-effort: ошибка хранилища сейчас не откатывает импорт. При печати сохранённая этикетка может масштабироваться/объединяться в ленту; сам payload не должен подменяться сокращённым представлением, товарным штрихкодом или другим КИЗом.

Товар WMS хранит `Product.category` как `subjectName` WB, например «Футболки» или «Брюки». Это предмет, а не надкатегория. Полная карточка WB сохраняется в `SellerWildberriesImportedCard.raw_json`, однако текущий код извлекает для Product только `subjectName` и не использует иерархию для `requires_honest_sign`.

## Что подтверждено официальной документацией Wildberries 05.10.2026

Проверены официальные страницы [«Работа с товарами»](https://dev.wildberries.ru/openapi/work-with-products) и [журнал изменений WB API о маркировке](https://dev.wildberries.ru/release-notes?id=198):

- `POST /content/v2/get/cards/list` возвращает для карточки `subjectID`, `subjectName`, `needKiz` и `kizMarked`;
- `needKiz=true` документированно означает, что товару требуется код маркировки;
- `kizMarked` означает подтверждение продавца, что обязательный код нанесён, и не заменяет признак необходимости `needKiz`;
- `GET /content/v2/object/all` возвращает `subjectID`, `parentID`, `subjectName`, `parentName`;
- `GET /content/v2/object/parent/all` возвращает родительские категории с устойчивым ID и названием.

Следовательно, надкатегорию нельзя определять по названию товара или по `Product.category='Одежда'`. Проверяемые источники — `needKiz` конкретной карточки и связь её `subjectID` с родительской категорией «Одежда» из официального справочника WB.

## Решение аналитика

Три API-сценария остаются разными, потому что у них разные входы и пользовательские результаты. Общим становится внутренний серверный механизм: проверить допустимость товара для текущего пути, атомарно сохранить точные КИЗы и включить `requires_honest_sign`, если хотя бы один КИЗ действительно сохранён.

Для текущих и новых WB-товаров признак включается монотонно: WMS может автоматически изменить `false → true`, когда это доказано загрузкой КИЗа, `needKiz=true` или принадлежностью предмета родительской категории «Одежда». Автоматически менять `true → false` нельзя: существующий признак мог быть включён оператором или подтверждён уже загруженными КИЗами.

Разовая операция по текущим товарам проектируется как `dry-run → зафиксированный точный список product_id → отдельный apply → контрольное чтение`. В этой задаче готовится код и проверяемый способ; выполнение apply на production требует отдельного прямого разрешения.

## Требования

### R1. Искать не только товары с уже включённым ЧЗ

Во всех трёх существующих путях загрузки КИЗ кандидаты не фильтруются по текущему `requires_honest_sign`. Сохраняются прежние границы каждого пути: текущая организация, выбранный селлер и уже действующий допуск общих строк ручного каталога. Товары другой организации или другого селлера не появляются.

### R2. Не менять правила сопоставления

Автоматическое сопоставление продолжает использовать существующие артикулы/SKU, артикул WB, размер и GTIN/штрихкод. При отсутствии или нескольких допустимых совпадениях товар не выбирается догадкой, КИЗ не связывается и признак не включается.

### R3. Единый серверный механизм трёх путей

`/import/auto`, `/import` и `/import/assign` используют один внутренний механизм проверки товара, сохранения кода/пула и включения признака. Разные входные данные, ответы и пользовательские шаги API не объединяются. Фронтенд убирает только фильтр ЧЗ и не становится источником проверки границ.

### R4. Атомарное автоматическое включение признака

Если в текущей операции хотя бы один новый КИЗ успешно сохранён и связан с допустимым товаром с `requires_honest_sign=false`, в той же транзакции товар получает `true`. Ошибка до фиксации, откат, не найденный/неоднозначный товар и полностью дублирующий файл не оставляют отдельно включённый признак. Повтор и два параллельных запроса не создают дубликаты КИЗов, пулов или повторные побочные изменения.

### R5. Полный исходный payload загруженного КИЗа

Для каждого принятого КИЗа WMS сохраняет полный исходный payload DataMatrix, включая допустимые разделители и криптографическую часть. Нормализованное значение может использоваться только для проверки/поиска; оно не заменяет сохранённый и печатаемый payload. Сокращённая подпись, GTIN, товарный ШК или префикс полного КИЗа не считаются самим КИЗом.

### R6. Печатать именно загруженные КИЗы

При печати результата конкретной загрузки источником служат принятые `MarkingCode` этой загрузки (`import_batch_id` и точные идентификаторы кодов), а не произвольный код из общего пула. PDF-загрузка печатает сохранённый `label_artifact_pdf` с DataMatrix, декодирующимся в тот же полный payload. CSV/TXT-загрузка генерирует DataMatrix из полного сохранённого payload. Если точный загруженный код или его обязательный исходный артефакт нельзя получить, WMS сообщает ошибку и не подменяет его другим или сокращённым кодом.

Допускаются только изменения носителя, не значения: объединение страниц, выбранное число копий и пропорциональное масштабирование. После подготовки к печати DataMatrix должен декодироваться в исходный полный payload.

### R7. Документированные источники автоматического ЧЗ для WB-карточки

При синхронизации WB-карточки WMS включает `requires_honest_sign=true`, если выполняется хотя бы одно доказанное условие:

- в текущем ответе карточки `needKiz=true`; или
- `subjectID` карточки по актуальному справочнику `GET /content/v2/object/all` связан с родительской категорией, идентифицированной через `GET /content/v2/object/parent/all` как «Одежда».

`kizMarked` не используется вместо `needKiz`: это подтверждение нанесения кода, а не признак обязательности. Название товара, совпадение по тексту `Product.category`, ручной список названий предметов и догадка по артикулу источником не являются.

### R8. Новые и повторно синхронизированные карточки

Новая карточка и новый размерный вариант, доказанно попавшие под R7, создаются с `requires_honest_sign=true`. При повторной синхронизации существующий `false` меняется на `true`; существующий `true` не сбрасывается, если WB позже не прислал поле, справочник временно недоступен или условие больше не доказано. Сбой получения справочника не должен ломать весь импорт карточек: недоказанное автоматическое включение откладывается и фиксируется диагностикой.

### R9. Безопасная разовая операция для текущих товаров

Перед любой записью операция строит dry-run по текущим `SellerWildberriesImportedCard.raw_json` и официальному справочнику WB: `product_id`, tenant, seller, `nmID`, `subjectID`, основание (`needKiz` или родитель «Одежда»), исходный флаг. Строка без доказанного `subjectID`/`needKiz` в apply не входит.

Apply принимает именно зафиксированный список `product_id`, меняет только `false → true`, не трогает другие поля, остатки, резервы, пулы и КИЗы, допускает безопасный повтор и после записи перечитывает тот же список. Расхождение состава между dry-run и apply останавливает операцию до записи. Production apply в рамках ночной проработки запрещён.

### R10. Проверка текущих данных до backfill

До apply необходимо read-only подтвердить, какие текущие raw-карточки реально содержат `subjectID`, `needKiz` и соответствующий `nmID`, а также получить актуальную связь `subjectID → parentID/parentName` штатным read-only клиентом WB. Если этих данных нет или смысл поля расходится с официальной документацией, изменять такие товары нельзя; возвращается точный список недостающих данных.

### R11. Расследование инцидента 04.10.2026

Для конкретного импорта сравнить исходный PDF из `MarkingCodeImportFile`, декодированные DataMatrix по страницам, сохранённый полный `cis_code`, `label_artifact_pdf`, привязку к продукту/пулу и конечный PDF/PNG задания печати. Сравнение должно установить, на каком шаге значение или этикетка изменились. Не считать фильтр ЧЗ причиной без доказательств, не запрещать все короткие форматы и не повторять внешнюю загрузку с неизвестным результатом.

Если исходный файл не сохранился, это фиксируется как конкретный пробел доказательств; недостающий артефакт не восстанавливается повторным вызовом WB. Если причина относится к независимому процессу, вывод сохраняется здесь, а исправление оформляется отдельным связанным продолжением.

### R12. Соседние процессы не меняются

Не менять упаковку и передачу FBS, правила остатков/резервов, существующие корректные общие пулы, число копий, товарные QR/ШК и печать ранее корректных КИЗов. Новые таблицы, категории, статусы и пользовательские блокировки не добавляются без отдельного доказанного требования.
