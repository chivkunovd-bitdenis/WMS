# WMS-745 · GET заявки приёмки после скана не должен выполнять N+1 чтений

## Исходное поручение

На складе ArtMaks десять сотрудников сканируют товары в короба приёмки с ТСД. Владелец требует, чтобы оператор мог принимать следующий скан примерно через секунду. Нагрузочный отчёт `/Users/deniscivkunov/Projects/WMS/.worktrees/_night-20261010/lanes/concurrency.md` показывает, что мобильный экран после успешного скана товара в коробе вызывает GET заявки и ждёт его.

Мобильный клиент выполняет POST `operations/inbound-intake-requests/{requestId}/boxes/{boxId}/scan` из `core/api/ScanMutations.kt`, затем `InboundReceivingViewModel.processScan` вызывает `refresh()`. `refresh()` вызывает GET `operations/inbound-intake-requests/{requestId}`. Серверный обработчик — `backend/app/api/inbound_intake.py:get_inbound_request`.

## Подтверждённая причина

В исходном коде `get_inbound_request` проходит по всем строкам заявки и для каждой вызывает `_line_out_for_request`. Для строки в статусе «в приёмке» `effective_actual_qty` отдельно запрашивает сумму количества в коробах и грузоместах, а `_line_out_for_request` отдельно читает у арендатора настройку адресного хранения. Отчёт зафиксировал 414 запросов для заявки на 200 позиций и 2416 для 1200 позиций; при самом скане было 27 и 29 запросов соответственно. Полный GET занимал до 6,87 секунды в приведённых одиночных замерах и до 6,28 секунды в цикле десяти сотрудников.

## Требования

R1. Для существующих данных и того же GET сохраняются все поля, порядок элементов и значения JSON. Мобильный клиент и контракт API не меняются.

R2. Суммы принятого количества по коробам и грузоместам для строк одной заявки загружаются пакетно, а настройка адресного хранения читается не более одного раза на GET. Число SQL-запросов чтения не должно расти пропорционально числу строк заявки.

R3. Для заявки приёмки с 200 позициями и коробами чтение выполняет не более 30 SQL-запросов. Контрольная заявка с 20 позициями отличается по числу запросов не более чем на 5.

R4. Проверка побайтно сравнивает тело ответа GET старого кода и исправленного кода на одной детерминированной заявке с 200 позициями и коробами. Снимок старого ответа создаётся и фиксируется до изменения серверного кода.

R5. Изменение ограничено чтением полной заявки приёмки. Маршруты скана, мобильный клиент, значения и форма API-ответа не меняются.

## Заключение

Тест и снимок старого ответа зафиксированы до изменения серверного кода. На исходной ревизии тест подтверждает совпадение ответа со снимком и воспроизводит превышение числа запросов: 54 для 20 строк и 414 для 200 строк. Исправление, повторные проверки, независимое ревью и приёмка ожидаются.
