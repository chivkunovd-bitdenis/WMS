## 2. Существующий процесс и цель изменения

### 2.1. Где живут реквизиты селлера (проверено по коду ветки от `origin/etalon` 141c9fb9)

- Таблица `billing_profiles` (`backend/app/models/billing.py`, `BillingProfile`): одна запись на
  селлера (уникальность `tenant_id + seller_id`). Поля: `legal_name` и `inn` — обязательные,
  `kpp`, `bank_name`, `bik`, `settlement_account`, `correspondent_account` — необязательные.
- Запись/чтение: `PUT/GET /api/billing/profiles/sellers/{seller_id}` (`backend/app/api/billing.py`,
  только админ ФФ своего тенанта); сохранение — `save_profile` в
  `backend/app/services/billing_configuration_service.py`: проверяет ИНН (10/12 цифр и контрольное
  число), пишет изменение в журнал документа. При выставлении счёта реквизиты копируются в счёт.
- Окно «Реквизиты» (`frontend/src/screens/ff/FfBillingProfilesDialog.tsx`): ИНН + «Заполнить по ИНН»,
  Наименование, КПП, Банк, БИК, Расчётный счёт, Корреспондентский счёт, «Сохранить». По WMS-491
  окно открывается кнопкой «Реквизиты» из карточки селлера; в «Расчётах» остаётся своё окно
  с выбором «Чьи реквизиты».
- Уже есть подстановка по ИНН: `GET /api/billing/profiles/lookup-inn` → DaData
  (`backend/app/services/dadata_party_service.py`) отдаёт наименование (сокращённое с ОПФ), КПП,
  ОГРН, адрес, руководителя. Нужен ключ `DADATA_TOKEN`; без него — ошибка `dadata_not_configured`.
  Кнопка подставляет наименование, ИНН, КПП **в форму**, сохраняет человек кнопкой «Сохранить».
  Расчётный счёт и банк не подставляются ничем.

### 2.2. Где подключаются ключи площадок

- WB, селлер в своём кабинете: `POST /api/integrations/wildberries/self/content-token`
  (`backend/app/api/wildberries_integration.py`): проверка ключа, сохранение, импорт карточек,
  фоновая синхронизация складов.
- WB, админ ФФ за селлера: `PATCH /api/integrations/wildberries/sellers/{seller_id}/tokens`.
- Ozon, селлер: `PUT /api/ozon/self/account` (`backend/app/api/ozon_integration.py`): проверка
  пары Client-Id/Api-Key, сохранение в `marketplace_accounts`, импорт каталога; сбой импорта
  не отменяет сохранение ключа.
- Признаки для экрана уже есть в `GET /api/sellers`: `wb_has_key` (есть любой токен WB) и
  `ozon_connected` (активный основной аккаунт Ozon).
- Сейчас ни один код WMS не запрашивает у площадок сведения о продавце (поиск по `seller-info`,
  `seller/info` в `backend/app` пуст).

### 2.3. Что реально отдают площадки (официальная документация, прочитана 27.09.2026)

**Wildberries — «Получить информацию о продавце»**, `GET https://common-api.wildberries.ru/api/v1/seller-info`
(dev.wildberries.ru, раздел «Общее → Информация о продавце», operationId `getV1SellerInfo`,
прочитан в браузере; схема ответа из встроенной спецификации страницы):

| Поле | Описание в документации | Используем |
|---|---|---|
| `name` | «Наименование продавца» (пример «ИП Кружинин В. Р.») | да → наименование |
| `tin` | «ИНН» | да → ИНН |
| `sid` | уникальный ID продавца на WB | нет |
| `tradeMark` | «Торговое наименование продавца» (бренд, не реквизит) | нет |

Токен — **любой категории**. Лимит на аккаунт продавца: персональный и сервисный токен — 1 запрос
в минуту (всплеск 10), базовый с секретом — 1 в минуту, **базовый — 1 запрос в 24 часа**. Ответы:
200, 401 (не авторизован), 402 (требуется платёж — только для сервисов каталога), 429 (слишком
много запросов). КПП и банковских реквизитов в ответе нет.

**Ozon — «Информация о кабинете продавца»**, `POST https://api-seller.ozon.ru/v1/seller/info`, тело `{}`
(docs.ozon.ru/api/seller, operationId `SellerAPI_SellerInfo`, схема `v1SellerInfoResponse` из
официального `swagger.json` Seller API 2.1, прочитан 27.09.2026). Объект `company`:

| Поле | Описание | Используем |
|---|---|---|
| `inn` | «ИНН.» | да → ИНН |
| `legal_name` | «Название юридического лица.» | да → наименование |
| `name` | «Название компании на Ozon.» | только если `legal_name` пуст |
| `ogrn`, `ownership_form`, `tax_system`, `country`, `currency` | ОГРН, форма собственности, налоговый режим, страна, валюта | нет (в реквизитах WMS таких полей нет) |

Плюс `ratings` и `subscription` — не реквизиты. КПП и банковских реквизитов в ответе нет. Поиск
по всей спецификации: КПП продавца встречается только в отчётах за период (шапка отчёта о реализации
`/v2/finance/realization` — `payer_kpp`/`receiver_kpp`; сведения о продавце в JSON-отчёте о продажах
юрлицам — схема `CreateDocumentB2BSalesJSONReportResponseSellerInfo`); это документы за период,
для подстановки реквизитов не используются. Полей банка, БИК, расчётного и корреспондентского
счёта продавца в спецификации нет.

**Вывод.** По API площадок достоверно приходят только **ИНН и наименование**. **КПП** можно получить
по ИНН уже существующей в проекте подстановкой DaData. **Банк, БИК, расчётный и корреспондентский
счёт** не отдаёт никто — они остаются ручными.

### 2.4. Цель

Админу ФФ не нужно вручную набивать реквизиты селлера, у которого подключён ключ WB или Ozon:
ИНН и наименование (и КПП, если настроена DaData) появляются в карточке селлера сами после
подключения ключа, а для уже подключённых селлеров и для обновления — одной кнопкой в окне
реквизитов. Введённое руками система сама не перезаписывает.

## 3. Решения аналитика (навык принятия решения)

Прочитаны [owner-cases.md](../reviews/2026-09-11-analyst-draft/owner-cases.md) и
[failure-cases.md](../reviews/2026-09-11-analyst-draft/failure-cases.md): для этой задачи важны B03
(отсутствующее и `null`-поле во внешнем ответе не роняют путь), B09/«при потере ответа выясни
результат» (здесь внешний вызов только читает, повтор безопасен), B05 (ошибка видна в окне,
введённое не теряется) и «Плохой случай 1» (действие — в контексте документа: в окне реквизитов).

**РА1. Какие поля.** ИНН и наименование — из площадки (WB `tin`/`name`; Ozon `company.inn`/
`company.legal_name`, при пустом — `company.name`). КПП — по полученному ИНН через существующую
подстановку DaData (та же, что кнопка «Заполнить по ИНН»); если DaData ответила, наименование тоже
берётся из неё — тот же источник и тот же вид, что уже даёт «Заполнить по ИНН» (иначе одно и то же
поле заполнялось бы в двух разных видах). Если DaData не настроена или не ответила — наименование
из площадки, КПП пустой. Банковские поля не трогаются никогда. Почему DaData: без КПП реквизиты
ООО для счёта неполные, а у площадок КПП нет; механизм уже есть в проекте, новой сущности нет.

**РА2. Когда — и при подключении ключа, и по кнопке.** Автоматически — сразу после успешного
подключения ключа WB или Ozon: владелец сказал «по API мы должны подтянуть», то есть без ручного
набора. Но у всех нынешних селлеров ключи уже подключены, и автоматическое заполнение при подключении
до них не дойдёт; кроме того, WB ограничивает запрос (базовый токен — раз в сутки), и первый
вызов может не пройти. Поэтому в окне «Реквизиты» селлера есть кнопка «Заполнить из WB» /
«Заполнить из Ozon» — по образцу существующей «Заполнить по ИНН». Периодического опроса и
запроса при каждом открытии карточки нет: это расходовало бы лимит WB и молча меняло данные.

**РА3. Как не затереть введённое руками.**
- Автоматически система создаёт реквизиты **только если у селлера их ещё нет совсем**. Если запись
  реквизитов есть (любая), автоматическое заполнение ничего не меняет — ни одного поля.
- Кнопка ничего не сохраняет сама: она подставляет ИНН, наименование и КПП **в форму** окна,
  как «Заполнить по ИНН». Человек видит значения и сам нажимает «Сохранить» или закрывает окно
  без сохранения. Банковские поля формы кнопка не трогает.

**РА4. Отказ API.**
- При подключении ключа: реквизиты запрашиваются после того, как ключ сохранён, и их неудача
  ни на что не влияет — ключ сохранён, проверка и импорт каталога идут как сейчас, пользователю
  ничего не показывается. Реквизиты можно дотянуть кнопкой позже.
- По кнопке: короткая строка ошибки в окне, форма не меняется. Повтор кнопкой безопасен —
  вызов только читает данные площадки.

**РА5. Где кнопки.** Только в окне реквизитов, открытом из карточки селлера (WMS-491), и только для
подключённых у этого селлера площадок (`wb_has_key`, `ozon_connected`). В окне «Реквизиты»
«Расчётов» (выбор «Чьи реквизиты») кнопок нет — реквизиты селлера по WMS-491 живут в его карточке,
«Расчёты» не меняем. Подпись с названием площадки обязательна (AGENTS §3: где принадлежность
влияет на понимание действия, обозначать площадку). Никаких подписей «источник: WB» и прочих
пометок в карточке и окне не добавляется.

## 6. Проверки

Внешние площадки на стенде и в тестах — только подставные ответы (как существующие
`E2E_MOCK_WB_*` и `FakeMarketplaceTransport`); живые ключи и прод не трогать. Тестовые данные —
с префиксом `WMS-547`. Вердикты заполняет аналитик на приёмке.

В колонке «Проверка»: подготовка → действие → ожидаемый результат.
