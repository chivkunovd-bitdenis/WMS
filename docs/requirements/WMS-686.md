## 3. Общие правила (основание: D0.1–D0.6)

- G1. Всё новое — только для отгрузок FBO («на МП»). FBS, групповая сборка FBS, сценарии ТСД по FBS и общие компоненты для FBS не меняются ни на пиксель; общие компоненты получают новое поведение только через явный параметр, который передаёт FBO (D0.1). Для подбора параметр называется fboMode (по умолчанию false; FfUnloadPickPage передаёт fboMode при source ≠ 'fbs').
- G2. Новых таблиц, журналов, статусов и режимов нет. Допустимы только три необязательные колонки одной миграцией от головы 20261007_2303: marking_codes.marketplace_unload_line_id, marketplace_unload_boxes.inbound_intake_box_id, marketplace_unload_requests.pass_details (D0.2). Миграция уже заведена в рабочем каталоге: backend/alembic/versions/20261009_0686_wms686_fbo_kiz_inb_pass.py (три колонки, FK с ON DELETE SET NULL, индексы и однократный перенос 71 кода) — вторая миграция не создаётся.
- G3. Документ упаковки (packaging_task) для FBO — рудимент: ни один шаг FBO не читает его статус, не ждёт его создания и не блокируется им. Таблицы и строки остаются как есть; новая логика FBO их не использует (D0.3).
- G4. Каждый успешный шаг сохраняется на сервере сразу; повтор запроса не удваивает результат; ошибка не стирает ввод и выбранный источник (D0.4).
- G5. Ни один шаг подбора, упаковки, извлечения, допечатки, XLSX и пропуска не ходит во внешние API WB/Ozon/ЧЗ (D0.5).
- G6. Остаток и расположение: подбор, упаковка, извлечение, перенос короба меняют только расположение/состав; остаток списывается только при «Завершить» (AGENTS.md, D4.10).
- G7. Не добавлять блокировок, которых не просил владелец (AGENTS.md раздел 3): красный ЧЗ, пустой пропуск, неполная упаковка не блокируют «Завершить» и работу с коробами; единственное, что стопорит переход, — подтверждаемое красное окно R40.
- G8. Ничто в интерфейсе не добавляется, не убирается и не меняется, кроме перечисленного в разделе 5. Ведущий сверяет экраны с текущим фронтом.

## 4. Требования

Формат: условие → действие → результат на экране и в данных → основание. D — decisions 09.10, Ow — owner-review 08.10 (R-номер владельца).

### 4.1. Подбор (вкладка «Подбор» отгрузки FBO)

**R1. Вид по умолчанию и переключатель.** Условие: открыта вкладка «Подбор» отгрузки FBO. Действие: открытие; переключение. Результат: по умолчанию вид «По ячейкам» (раскладка FbsCellPickTable с хотфиксом WMS-709: столбцы «План», «Осталось», раздел «Уже подобрано»); над таблицей переключатель «По ячейкам / По товарам» (MUI ToggleButtonGroup, как в FfSortingObjectsPage). Оба вида показывают одни данные; переключение не меняет подобранное, КИЗ и выбранный источник. Основание: D1.1, Ow R02.

**R2. Сворачивание и раскрытие.** Условие: вид «По ячейкам». Действие: нажатие на ячейку, тару (короб, палету, грузоместо) или раздел «Уже подобрано». Результат: вложенные строки скрываются/показываются стрелкой того же вида, что у раскрываемых строк DataTable; данные, количества и источник не меняются. В виде «По товарам» работает существующее раскрытие мест. Вид, раскрытые строки и выбранный источник не сбрасываются при ошибке, перечитывании и смене вкладок документа: для FBO убирается перемонтирование экрана по version (key); состояние хранится на уровне документа (решение аналитика: в памяти приложения по id отгрузки, без localStorage). Основание: D1.2, Ow R01, F7.

**R3. Столбец «КИЗ».** Условие: FBO, оба вида. Результат: столбец «КИЗ» с крупным числом K — число КИЗ, привязанных к этому товару в этой отгрузке (R14). В виде «По ячейкам» число стоит в строке товара сразу после «Осталось»; в виде «По товарам» — в строке товара на том же относительном месте. Число показывается, если у товара включён Честный знак (requires_honest_sign) или K > 0; иначе ячейка пуста. Число одинаково во всех строках одного товара (это число по товару в отгрузке, как «План»). Нажатие на число раскрывает под строкой товара вертикальный список кодов; повторное нажатие скрывает. Один раскрытый список на товар (в виде «По ячейкам» — под первой строкой товара, переключатель общий для строк товара). Список без зелёной рамки, с обычными отступами и разделителями темы; строка кода: значение (длинный код переносится/усекается с подсказкой полного значения), второстепенным текстом «приёмка №…» (intake_document_number), если известен, кнопка «Перепечатать» и крестик (aria-label «Отвязать код»). Скан нового КИЗ обновляет число сразу, не закрывая уже раскрытый список. Основание: D1.3, Ow R03–R05.

**R4. Скан ячейки или тары — выбор источника.** Условие: вкладка «Подбор», сканер активен. Действие: скан ШК ячейки, короба, палеты, грузоместа. Результат: источник выбирается и держится до скана другой ячейки/тары или до явного «Забыть место», в том числе при уже выбранной таре: сервер на скан ШК другой или той же тары при выбранной таре отвечает kind=container (по образцу FBS, «новая тара заменяет источник»), а не «Штрихкод не найден»; ШК ячейки отвечает kind=location. Раскрытие, сворачивание, смена вида не меняют источник. Основание: D1.4, Ow R07, F3.

**R5. Скан ШК товара.** Условие: источник выбран или нет. Действие: скан ШК товара. Результат: +1 штука из источника (существующий POST …/pick/scan); без выбранного места товар ищется по доступному остатку, как сейчас. Сверх плана товара — отказ существующим звуком ошибки и красным текстом, число и источник сохраняются; такой отказ не мешает привязать недостающий КИЗ (R6). Основание: D1.4, D1.9, Ow R12.

**R6. Скан КИЗ на подборе.** Условие: вкладка «Подбор», у товара подобрана хотя бы одна штука. Действие: скан КИЗ. Результат: КИЗ привязывается (POST …/marking-codes/scan, R14) к товару последнего отсканированного ШК без +1 штуки; K растёт на 1 и показывается сразу. Повтор того же КИЗ — нейтральное «Этот КИЗ уже привязан к товару», без изменений и без красного. Код другого товара — отказ со звуком, код не привязан. КИЗ сверх подобранных штук (K+1 > подобрано) — отказ «Сначала отсканируйте ШК следующей штуки». КИЗ без предшествующего ШК привязывается, только если товар определяется однозначно (код уже известен в системе с товаром, либо GTIN кода совпадает с ШК ровно одного товара отгрузки), иначе «Сначала отсканируйте ШК товара». Работа без КИЗ возможна: КИЗ необязателен. Основание: D1.4, Ow R06.

**R7. Приём кода со сканера.** Условие: любой скан на подборе FBO и на упаковке FBO. Результат: сканер принимается тем же способом, что в упаковке FBS (FbsPackingScanBar): useScanIntake с emitRaw — сырой ввод, GS (Ctrl+]) не заменяется на «]» (на подборе FBO normalizeLayoutPunctuation для скана не применяется); нормализация кода на сервере — одной существующей функцией normalize_scanned_cis (services/fbs_kiz_service.py), без собственных разборов. Поле barcode тела скана принимает до 512 символов (как cis_code): MarketplaceUnloadPickScanBody и MarketplaceUnloadScanBody. Правило распознавания скана на клиенте (решение аналитика): сначала совпадение с ШК/SKU товара отгрузки (как в FfUnloadPickPage.scan), затем ШК ячейки/тары через сервер, иначе — КИЗ. Основание: D1.5, F8, F9.

**R8. Двойной скан короба и кнопка «Забрать короб целиком».** Условие: подбор FBO. Действие: второй скан того же ШК короба (сравнивается сырая строка со сканера) в пределах 2000 мс после прихода первого (время прихода кода со сканера, а не окончания обработки; сканы обрабатываются по очереди приёма) либо нажатие «Забрать короб целиком» в строке источника-короба. Результат: выполняется перенос короба целиком (POST …/boxes/attach, allow_over_plan=false). Скан любого другого кода между двумя сканами разрывает пару. Третий быстрый скан и повтор запроса ничего не переносят и не показывают ошибку: после переноса одинаковые сканы того же ШК игнорируются без запроса, звука и сообщения, пока не придёт другой код или не пройдёт 2000 мс; ответ сервера box_already_attached/box_empty на повтор экран показывает нейтрально (без красного). Основание: D1.6, Ow R09.

**R9. Отказ переноса сверх остатка плана.** Условие: перенос короба целиком. Правило: короб принимается, только если по каждой позиции «в коробе ≤ план − уже подобрано» (существующая проверка collect_into_box, allow_over_plan=false); товар, которого нет в плане, — отказ (remaining 0). Результат отказа: ничего не меняется (одна транзакция, сессия закрывается без commit), существующий звук ошибки, красное сообщение с товаром и числами: «Количество товаров в коробе больше, чем осталось подобрать: <товар> — в коробе N, осталось M. Откройте короб и подберите поштучно» (позиций несколько — все перечислены через «; »). Окно «Больше, чем в плане» с «Добавить всё» для FBO удаляется. Основание: D1.7, F1, Ow R10–R11.

**R10. После успешного переноса.** Результат: строки этого короба серые (подобрано), источник сбрасывается, на вкладке «Упаковка» появляется тот же короб — тот же ШК (R36) и тот же состав. Основание: D1.8, Ow R14.

**R11. Подобранные позиции.** Полностью подобранные позиции серые и читаемые, частично подобранные визуально отличаются от полностью; серый не скрывает КИЗ и не отключает правку количества (уменьшить/очистить число можно, как сейчас; последствия для КИЗ — R19). Основание: D1.8, Ow R13.

**R12. Надпись о неизвестном составе.** «Состав КИЗ тары неизвестен» и подобные формулировки не появляются нигде в FBO. Основание: D1.10, Ow R08.

### 4.2. КИЗ (единое хранение и правила)

**R13. Хранение.** КИЗ хранится на строке товара отгрузки: marking_codes.marketplace_unload_line_id (nullable FK на marketplace_unload_lines, ON DELETE SET NULL, индекс). Связи «КИЗ ↔ короб» нет: товар связан с коробом составом короба, товар связан с КИЗ этой колонкой. Основание: D3.0.

**R14. Привязка кода к отгрузке.** Условие: статус отгрузки «Утверждено» или «Сборка»; пользователь ФФ. Действие: POST …/marking-codes/scan {code, product_id?, mutation_id?}. Результат: код нормализуется (R7); если он есть в базе — проверяются принадлежность селлеру, товар, занятость; нет в базе — создаётся принятый внешний код (по образцу FBS _create_or_apply_external_code: source external_fbs, status applied, seller из отгрузки, product, gtin); код привязывается к строке товара отгрузки. Ответ: marking_code_id, cis_code, product_id, line_id, already_linked, kiz_count (K), picked_qty (S). Отказы и их коды — раздел 6. Статус: отсканированный код → applied (available → applied; printed остаётся printed), applied_at = время привязки. Повтор того же кода на ту же строку → already_linked=true без изменений. Привязка КИЗ сверх подобранного (K+1 > S) → marking_quantity_exceeded. Основание: D1.4, D3.2, F9.

**R15. Единый предикат «код занят».** Привязанный к отгрузке код занят для всех остальных процессов. Создаётся одна функция-предикат в marking_code_service (код занят, если packaging_task_line_id или marketplace_unload_line_id не пусты) и используется во всех местах, где занятость решается по packaging_task_line_id: is_unbound_received_code, is_unbound_cancelled_wb_code, привязка FBS/Ozon (fbs_kiz_service, ozon_kiz_service), удаление кода приёмки (inbound_marking_service), передача владения (ownership_transfer_service), выбор из пула (только status = available и не занят). Копий условия в разных местах нет. Исполнитель перед правкой ищет все вхождения packaging_task_line_id в backend/app (список известных файлов — раздел 8) и перечисляет заменённые места в отчёте. Основание: D3.1.

**R16. Счётчик K — вычисление.** K товара в отгрузке = COUNT кодов с marketplace_unload_line_id этой строки. Независимых счётчиков нет. Существующие 71 код FBO, привязанные к строкам заданий упаковки, миграция один раз связывает со строкой той же отгрузки и того же товара (packaging_task_line_id у них не обнуляется). В ответе детали строка отгрузки получает необязательные поля kiz_count и requires_honest_sign. Основание: D3.3.

**R17. Напечатанный код остаётся за товаром.** Код, выданный из пула и напечатанный, имеет статус printed (как сейчас) и считается нанесённым: при извлечении из короба (R35) и при «Завершить» связь с товаром отгрузки не снимается, в свободный пул код не возвращается, статус shipped и запись истории ЧЗ при «Завершить» не пишутся. Отвязка — только крестиком оператора (R18). Основание: D3.2, §3 decisions, ответ на Q3.

**R18. Отвязка ошибочного кода.** Действие: крестик у кода в списке (DELETE …/marking-codes/{marking_code_id}). Результат: marketplace_unload_line_id очищается, K уменьшается; статус кода не меняется (печатный остаётся printed и в пул не возвращается, принятый остаётся applied и может быть привязан заново); {removed: true}. Повтор — {removed: false}. Только ФФ, только в статусах «Утверждено»/«Сборка». Основание: D1.3, D3.2 (решение аналитика о статусе после отвязки: ничего не менять).

**R19. Уменьшение подбора.** Условие: оператор уменьшил «подобрано» по товару (pick/set, remove_from_box) так, что K > S, при этом до уменьшения K ≤ S (коды, выданные заранее под план при S < P — R21, R51 — не отвязываются: напечатанный до подбора код не теряется при правке подбора; решение аналитика). Результат: отвязываются последние привязанные коды (порядок по applied_at, затем id, от новых к старым), K = S; ответ pick/set дополняется необязательным полем unlinked_marking_codes (список значений); экран показывает неблокирующее сообщение «Отвязаны КИЗ: …». Нет блокировки уменьшения. Основание: D3.4.

**R20. Отмена отгрузки.** При отмене отгрузки (cancel → rollback_all_collected_for_cancel) все её КИЗ отвязываются (marketplace_unload_line_id = NULL; статусы не меняются). Основание: D3.5.

**R21. Выдача свободных кодов из пула (кнопка «ШК + ЧЗ», R51).** Условие: у товара есть строка в отгрузке и P − K > 0 (P — план строки). Действие: POST …/marking-codes/issue {product_id, quantity?, mutation_id}. Результат: сервер берёт свободные (available, не занятые) коды пула этого товара в порядке создания, привязывает к строке отгрузки, ставит printed (printed_at, applied_at = сейчас, printed_by_user), возвращает items и shortage (сколько не хватило). quantity по умолчанию: S − K, если S > 0, иначе P − K (печать до подбора); максимум (потолок) при любом S: P − K; явный quantity выше потолка уменьшается до потолка. Привязка КИЗ сканом (R14) по-прежнему ограничена S — потолок P относится только к выдаче из пула. Повтор с тем же mutation_id возвращает те же коды (квитанция операции по образцу box-scan receipts), а не новые; повтор с другим payload — 409 mutation_payload_mismatch. Пул пуст — 422 marking_pool_empty, ложного успеха нет; P − K ≤ 0 (а также quantity не передан и значение по умолчанию равно 0, т. е. S > 0 и S = K) — 422 nothing_to_issue. Печать выданных кодов выполняет экран через WMS Print (старый контракт программы печати, программа не обновляется); сбой печати не отвязывает коды, «Перепечатать» печатает те же коды. Основание: D4.9, Ow R27.

**R22. Права на КИЗ.** Чтение списка (GET …/marking-codes) — ФФ и селлер своей отгрузки; scan, issue, delete — только ФФ (селлер получает 403 forbidden). Основание: D8.2.

### 4.3. Упаковка (вкладка «Упаковка» отгрузки FBO)

**R23. Доступность вкладки.** Вкладка «Упаковка» доступна в статусах «Утверждено», «Сборка» и (только чтение результата) «Отгружено» без задания упаковки; условие mpStepEnabled('packaging') = Boolean(linked_packaging_task) заменяется на статус. Подсказка заблокированной вкладки при статусе до утверждения: «Утвердите план поставки, чтобы открыть упаковку.» Галочка «Упаковка ✓» (mpStepDone) — когда по всем строкам «В коробах» ≥ «Нужно» (решение аналитика). Плитка «Упаковано (из подобранного)» в сводке показывает «B/N» (формат прежний): B — сумма в коробах из данных отгрузки, N — подобрано, а при нулевом подборе — план (уточнение ведущего после редакции 4; подпись не меняется). Таблица строится из данных отгрузки (строки, короба, КИЗ), а не из задания упаковки. Основание: D4.3, D0.3, Ow R17.

**R24. Структура сверху вниз.** (1) контекст отгрузки и вкладки (как сейчас); (2) компактная серая строка скана «ШК товара или ЧЗ» + галки «Печатать ШК», «Печатать ЧЗ» + компактная кнопка «Печать накладной» в этой же строке; (3) общая таблица товаров; (4) раздел коробов (существующий Accordion «Короба», он раскрыт по умолчанию — решение аналитика): шапка с полем «Кол-во коробов», «Загрузить по накладной», «Создать короб/короба»; (5) поле скана ШК короба «Штрихкод готового короба (WHB-…)» + «Привязать» ниже шапки; (6) список коробов с раскрываемым составом. Управление созданием и загрузкой стоит над списком коробов, а не под ним. Кнопки «Скачать XLSX для WB» в разделе коробов больше нет (переносится вверх, R41). Основание: D4.2, Ow R15, R18, R20.

**R25. Серая строка скана и галки печати.** Строка: поле скана (компактнее нынешней панели FfPackagingPage; по образцу FbsPackingScanBar: подложка action.hover, поле размера small), галки «Печатать ШК» и «Печатать ЧЗ» (компонент FbsScanPrintToggles не используется как есть: в нём «Печатать QR»/«Печатать ЧЗ»/«Перепечатывать ЧЗ»; для FBO нужны ровно две галки — решение аналитика: отдельный маленький компонент в папке упаковки FBO на тех же MUI-элементах), кнопка «Печать накладной» (существующая printPackagingSheet) компактнее прежней и в этой строке. Выбор галок хранится в localStorage под ключом, отличным от FBS (например wms:fbo:scan-auto-print:<tenant/user>), и не влияет на FBS и наоборот. Галка выключена — не печатаем и WMS Print не требуется; включена — печатаем. «Печатать ШК» — этикетка ШК товара (существующая печать этикетки товара). «Печатать ЧЗ» — на отсканированную штуку выдаётся свободный код товара из пула (R21, quantity=1, свой mutation_id на каждый скан), привязывается и печатается. Основание: D4.2, D4.8, Ow R15, R18.

**R26. Общая таблица товаров.** Строки — товары отгрузки. Столбцы: существующие («Товар», «Артикул продавца», «Артикул WB», «Размер», «ШК», «ТЗ») плюс «Нужно» (P — план строки), «В коробах» (B — сумма количества товара во всех коробах отгрузки), «ЧЗ» в виде «K из P» (K — число КИЗ, P — план товара; Q4 decisions: знаменателя по коробам нет). Если у товара ЧЗ не включён — вместо «ЧЗ» прежнее «не требуется» (без красного). Если K < P — счётчик красный, при K = P — обычный. Красный — только информация (R37). Число K — кнопка: нажатие раскрывает под товаром вертикальный список кодов (как R3), повторное скрывает. Печать — кнопкой «ШК + ЧЗ» в столбце «Действия» (R51); отдельной кнопки «Допечатать» нет (R32). Иконка «ТЗ» показывает packaging_instructions товара, как сейчас (сервер дополняет строки отгрузки необязательным полем packaging_instructions, раздел 6.4); артикулы, размер и ШК берутся из каталога товаров селлера тем же хуком, что на подборе (useMarketplaceProductCatalog). Последний столбец «Действия» с кнопкой «ШК + ЧЗ» остаётся таким же по виду (contained, size large, значок принтера, подпись «ШК + ЧЗ», aria-label «Печать товара <название>», data-testid ff-packaging-line-print-<id строки>, кнопка прижата к правому краю колонки); меняется только источник данных печати (R51). Основание: D4.2, Q4, Ow R19, R24–R25, запрет владельца убирать необсуждённые элементы.

**R27. Пояснение при нехватке КИЗ.** Рядом с красным счётчиком — значок «!» с подсказкой по наведению: «Не все КИЗ привязаны. Если товар перенесён целым коробом, КИЗ этих единиц не сканировали; привязаны только показанные коды». Значок виден при любой нехватке K < P (решение аналитика: признака «перенесён целым коробом» в данных нет, вводить его запрещено G2; текст не утверждает причину, а называет возможную). Подсказка пропадает вместе с красным счётчиком. Основание: Ow R26 (текст предложен владельцем), D5.1.

**R28. Создание коробов.** Поле «Кол-во коробов» (1–50) и «Создать короб/короба» → POST …/boxes/batch; «Загрузить по накладной» → существующее окно импорта. Созданный короб получает свой ШК WHB, его можно распечатать существующим меню короба. Размер/пресет на экране FBO не показываются: выбор «Пресет» и текст «60×40×40 см» в карточке короба убираются; при создании уходит существующее значение по умолчанию 60_40_40. Данные размера в базе не удаляются. Только что созданный (один) короб становится текущим; при создании нескольких текущим становится первый. Основание: D4.2, D4.4, Ow R20–R21.

**R29. Скан ШК короба.** Условие: вкладка «Упаковка», сканер активен. Действие: скан сырой строки, равной internal_barcode одного из коробов этой отгрузки (созданного, перенесённого целиком, приёмки). Результат: короб становится текущим (подсвечен) и раскрывается; количества не меняются; новых коробов не создаётся. Скан ШК короба WHB-/INB-…, ещё не входящего в отгрузку — перенос целиком по правилу R9 (окно «Добавить готовый короб?» сохраняется как сейчас; окно «Больше, чем в плане» для FBO убрано). Основание: D4.5, Ow R22.

**R30. Скан ШК товара.** Условие: есть текущий короб. Действие: скан ШК товара. Результат: +1 штука в текущий короб тем же серверным путём, что «Наполнить» (POST …/boxes/{box_id}/scan → add_manual_qty_to_box: сначала уже подобранное и не разложенное, недостающее добирается подбором); товар появляется под коробом в раскрываемом составе и в «В коробах». При включённых галках печати выполняются R25. Нет текущего короба — сообщение «Сначала отсканируйте или создайте короб», запросов нет. Основание: D4.6, Ow R23.

**R31. Скан КИЗ на упаковке.** Те же правила, что R6 (одна серверная функция привязки, POST …/marking-codes/scan). Товар для кода определяется ШК последнего отсканированного товара либо однозначно по коду. Основание: D4.7.

**R32. Кнопки «Допечатать» нет (отменена владельцем 09.10, по словам ведущего).** Её работу выполняет единственная кнопка строки «ШК + ЧЗ» (R51). Перепечатка уже привязанного кода — кнопка «Перепечатать» в списке кодов, который раскрывается по клику на «K из N» (R3, R26). Правила выдачи (D4.9: ключ операции при потере ответа, пустой пул без ложного успеха, сбой печати не отвязывает коды) сохраняются за «ШК + ЧЗ». Основание: прямое решение владельца 09.10 (передано ведущим), D4.9, Ow R27.

**R51. Кнопка «ШК + ЧЗ» в строке таблицы упаковки.** Условие: вкладка «Упаковка» FBO, любая строка товара; кнопка всегда активна и не зависит от S (как сейчас — печать возможна до подбора), блокируется только на время выполнения запроса и после проведения отгрузки (только чтение). Действие: нажатие «ШК + ЧЗ» в столбце «Действия». Результат: через WMS Print (старый контракт программы печати) печатаются N этикеток ШК товара, где N = S при S > 0, иначе план P; если у товара включён ЧЗ — печатаются ТОЛЬКО недостающие коды: сервер выдаёт quantity = N − K из пула через POST …/marking-codes/issue {product_id, quantity, mutation_id} (R21), привязывает их к строке отгрузки, экран печатает выданные. Уже привязанные коды не перепечатываются: перепечатка — «Перепечатать» в списке кодов по клику на «K из N». Если N − K ≤ 0 или ответ nothing_to_issue — печатаются одни ШК, ошибки нет. Повтор нажатия после потери ответа использует тот же mutation_id и получает те же коды, новые не выдаются; выданные, но не напечатанные из-за сбоя печати коды при следующем нажатии печатаются повторно (те же, не новые). Пустой пул — сообщение «В пуле нет свободных КИЗ этого товара» (ШК к этому моменту уже напечатаны, ложного успеха по ЧЗ нет); при shortage > 0 — «Выдано N из M: в пуле не хватает КИЗ». Сбой печати не отвязывает коды. Товар без ЧЗ — печатаются только ШК. Печать по строке задания упаковки (ручки packaging-tasks, markProductLabelPrinted, refreshTask) для FBO не используется (D0.3). Основание: уточнение ведущего 09.10 (владелец запретил убирать необсуждённые элементы и кнопку «Допечатать»), D4.8–D4.9, D0.3.

**R33. Раскрываемые короба и «Наполнить».** Каждый короб — раскрываемая карточка (существующая renderMpBoxCard): ШК (внутренний ШК WHB или INB), состав «товар — количество». «Наполнить» (существующее окно FfMarketplaceUnloadBoxAddDialog) работает как раньше; результат сканом и «Наполнить» одинаков (состав и «В коробах» обновляются). Меню короба (печать ШК, копирование, удаление) сохраняется как сейчас; кнопки «Закрыть короб» нет. Основание: D4.2, Ow R22–R23, §3 decisions.

**R34. «Извлечь товар» → «Извлечь всё».** Условие: статус «Утверждено»/«Сборка». Действие: у каждого короба кнопка «Извлечь товар» → окно с ШК короба и составом → «Извлечь всё». Результат: состав короба очищается одной транзакцией (POST …/boxes/{box_id}/extract-all), «В коробах» уменьшается, «Подобрано» и КИЗ не меняются (штуки остаются подобранными, их можно снова разложить по коробам), остаток и расположение не меняются, короб остаётся пустым и не закрывается; окно закрывается. Закрытие окна без «Извлечь всё» ничего не меняет. Повтор запроса ничего не меняет (пустой короб остаётся пустым). Извлечение из одного короба не затрагивает остальные. Основание: D4.10, Ow R28–R30.

**R35. Извлечение и КИЗ.** КИЗ при извлечении не снимаются и в пул не возвращаются (R17); K не меняется. Основание: D4.10, D3.2, ответ на Q3.

**R36. ШК перенесённого INB-короба.** Короб, перенесённый целиком из приёмки, помнит короб приёмки: marketplace_unload_boxes.inbound_intake_box_id (nullable FK, SET NULL). ШК короба в ответе (internal_barcode), на экране, в печати и в XLSX = ШК складского короба (WHB) либо короба приёмки (INB). Повторный перенос того же INB-короба в ту же отгрузку — 409 box_already_attached (как для WHB). Существующие тесты, где у INB пустой warehouse_box_id, остаются верными. Основание: D4.1, F2.

**R37. Красный ЧЗ не блокирует.** Красный счётчик ЧЗ — только информация; работа с коробами, сканы, «Завершить» от него не зависят. Основание: D4.11.

**R38. Нет «Завершить упаковку».** Кнопки «Завершить упаковку» нет нигде в FBO (серая строка, панель, нижняя часть). Остаётся общая кнопка «Завершить» отгрузки (R40). Основание: D4.3, Ow R16.

### 4.4. «Завершить» отгрузку

**R39. Независимость от задания упаковки.** Проверка маркировки через задание упаковки для FBO (assert_unload_marking_done) убирается. «Завершить» не зависит от задания; списание остатка, резерв, начисления селлеру — как сейчас. Основание: D5.2, F4.

**R40. Красное окно при нехватке КИЗ.** Условие: «Завершить», по товару с ЧЗ (requires_honest_sign) K < отгружаемого количества N (N — сумма товара в коробах). Результат: сервер отвечает 422 marking_incomplete с перечнем (товар, linked, quantity); экран показывает большое красное окно (AppDialog, красный заголовок/акцент): «Не на все товары привязаны КИЗ: <товар> — K из N. Возможно, часть товара добавлена целым коробом без сканирования КИЗ. Отгрузка без маркировки может привести к штрафам. Завершить отгрузку?» кнопки «Отмена» и «Завершить» (красная). Подтверждение повторяет запрос с acknowledge_marking=true (флаг расхождения acknowledge_discrepancy передаётся как раньше). Отказ любого вида при «Завершить» — это 4xx с понятным кодом; 500 при «Завершить» не бывает. Порядок проверок на сервере: существующие (статус, строки, дата, склад WB) → есть ли подобранное/расхождение (distribution_incomplete, acknowledge_discrepancy, как сейчас) → маркировка (marking_incomplete). Основание: D5.1, ответ владельца на вопрос 1.

**R41. Выработка упаковщиков.** Низкий приоритет. Выработка по FBO считается по проведённой отгрузке: отгруженные штуки засчитываются сотруднику, нажавшему «Завершить» (completed_by_user_id) в месяце проведения; задания упаковки FBO в выработку не входят (чтобы не считать дважды, задание отгрузки FBO исключается из задачного блока aggregate_staff_billing). FBS не меняется. Основание: D5.3, F5, ответ владельца 6.

### 4.5. XLSX для WB, пропуск

**R42. «Скачать XLSX для WB» сверху.** Кнопка стоит сверху в контексте отгрузки (в строке вкладок документа справа, раздел 5.2), видна ФФ и селлеру для отгрузок WB в статусах «Утверждено», «Сборка», «Отгружено»; файл прежнего формата (5 колонок образца WB, лист Sheet1), INB-короба со своим ШК (R36). Ручка GET …/wb-fbw-packaging.xlsx остаётся; ошибка и предупреждение выгрузки показываются в контексте документа (wbFbwExportRequests, ff-mp-wb-fbw-export-error сохраняются). Существующие метки data-testid кнопки (ff-mp-wb-fbw-export) и блока коробов (ff-mp-boxes, ff-mp-boxes-accordion, ff-mp-import-boxes) сохраняются — охранный тест WMS-679 читает исходник FfSuppliesShipmentsPage.tsx. Для Ozon кнопки нет (R48). Основание: D6.1, Q12, Ow R31–R34.

**R43. Пропуск — форма.** Одна машина на отгрузку. Кнопка сверху рядом с XLSX: «Внести пропуск», после сохранения — «Пропуск». Открывает модальное окно с полями (общие WB/Ozon, исследование ведущего 09.10; * — обязательные для сохранения): Фамилия водителя* (driver_last_name), Имя водителя* (driver_first_name), Телефон водителя (driver_phone; обязателен для Ozon, необязателен для WB), Марка и модель автомобиля* (car_brand), Госномер* (car_number, подсказка в поле «А111АА111»), Тип грузомест (cargo_type: Короб | Паллета, необязательно), Количество грузомест (cargo_places_count, необязательно, целое ≥ 1), Плановая дата приезда (arrival_date, необязательно, дата). Кнопки: «Сохранить», «Скачать XLSX», «Закрыть». ФФ вводит и правит до проведения отгрузки; после «Завершить» и при отмене — только чтение (409 pass_not_editable). Пропуск не блокирует «Завершить»; пустой пропуск не показывает вымышленных значений. Для отгрузки Ozon без телефона сервер отвечает 422 pass_phone_required. Источники исследования: инструкция WB «Как заказать пропуск в пункт отгрузки» (обновлена 29.09.2026) и Ozon Seller API /v1/supply-order/pass/create. Основание: D7.1, Ow R35–R36, ответ владельца 8.

**R44. Права пропуска.** PUT …/pass — только ФФ и только до проведения; селлер получает 403 на запись (сервером, а не только скрытием кнопки). GET …/pass — ФФ и селлер своей отгрузки. Селлер открывает ту же форму с сохранёнными значениями, поля не редактируются, «Сохранить» нет, есть «Скачать XLSX». Если пропуск не внесён, селлер видит «Фулфилмент ещё не внёс данные пропуска». Основание: D7.1, D8.2, Ow R37, R39.

**R45. XLSX пропуска.** GET …/pass.xlsx — отдельный файл от XLSX для WB (не официальный импорт WB, формат WMS): один лист «Пропуск», шапка и одна строка значений: «Отгрузка» (номер документа), «Фамилия водителя», «Имя водителя», «Телефон», «Марка и модель автомобиля», «Госномер», «Тип грузомест», «Количество грузомест», «Плановая дата приезда». Госномер и телефон записываются текстом (ведущие нули и знаки сохраняются). Значения — сохранённые в базе, а не несохранённые правки в форме; пока пропуск не сохранён, кнопка «Скачать XLSX» неактивна, сервер отвечает 404 pass_not_filled. Основание: D7.1, Ow R38 (формат листа — решение аналитика по рабочему предложению владельца-разбора).

**R46. Хранение пропуска.** marketplace_unload_requests.pass_details (JSON, null). Детальный ответ отгрузки дополняется необязательным полем pass_details (для ФФ и селлера) — по нему кнопка меняет надпись. Основание: D8.1.

### 4.6. Селлер

**R47. Селлер видит всё, только на чтение.** В своей отгрузке селлер видит план, подбор, короба с составом, КИЗ, пропуск и скачивает оба XLSX. Сервер в GET /{id} перестаёт обнулять boxes, pick_allocations и picked_qty для селлера (linked_packaging_task для селлера по-прежнему не отдаётся — рудимент). Запись остаётся запрещённой (все операции подбора/коробов/«Завершить» — 403 forbidden, как сейчас). Права сотрудника селлера не трогаются. В SellerMarketplaceUnloadDialog для отгрузок вне черновика под таблицей строк добавляются только чтение: столбцы «Подобрано», «В коробах», «КИЗ» (счётчик с раскрытием списка), блок «Короба» (ШК и состав), кнопки «Скачать XLSX для WB» (WB) и «Пропуск». Основание: D8.2, ответ владельца 7, Ow R32, R37.

### 4.7. Ozon

**R48. Ozon FBO.** Подбор, упаковка, КИЗ, извлечение, «Завершить» и пропуск работают тем же процессом (marketplace = ozon, тот же код). Выгрузки состава для Ozon нет и кнопки «Скачать XLSX для WB» у Ozon нет: Ozon принимает состав грузомест только в XLS-шаблоне из своего кабинета с ID грузомест (колонки не опубликованы) или через Seller API /v1/cargoes/create; отдельный файл WMS для Ozon не делается, интеграция — отдельная задача. Поля пропуска общие (R43), телефон для Ozon обязателен. Основание: D0.6, ответ владельца 8, исследование ведущего 09.10.

### 4.8. Мобильный ТСД

**R49. Подбор FBO в ТСД.** Подбор FBO в приложении ТСД (каталог mobile/, features/outbound) адаптируется под тот же процесс на тех же серверных ручках: ячейка → тара → ШК товара (+1) → КИЗ (привязка), двойной скан короба в 2000 мс → перенос целиком с тем же отказом сверх остатка (показывается message ответа, красным, с вибрацией/звуком ТСД); поле скана принимает до 512 символов. «Завершить» (ship) в ТСД при ответе marking_incomplete показывает то же красное подтверждение и повторяет запрос с acknowledge_marking=true. Основание: D9.1, «под мобилку тоже надо обязательно адаптировать подбор».

**R50. Обратная совместимость ТСД.** Существующие экраны ТСД (сборка коробов, boxes create/close/scan с size 60_40_40, карточка и список, ship, задание упаковки перед ship) не ломаются: ответы существующих ручек только дополняются необязательными полями, ничего не переименовывается и не удаляется; ТСД-сценарии FBS не меняются. Основание: D9.1, F10.

## 6. Контракт API

Префикс всех путей: /operations/marketplace-unload-requests. Права: «ФФ» — любой пользователь без роли селлера с require_mp_shipments_access (как _require_ff_execution); «видимость» — _get_visible_request (ФФ видит все отгрузки тенанта, селлер — свои). Статусы выполнения: «Утверждено» (confirmed) и «Сборка» (collecting); вне их записи отвечают 409 bad_status (или not_editable, как у соседних ручек). Все существующие ручки сохраняют пути и поля; добавляются только необязательные поля.

### 6.1. КИЗ отгрузки (новый роутер, файл api/marketplace_unload_marking.py, подключается в main.py рядом с marketplace_unload_requests_router; префикс /{request_id})

**POST /{request_id}/marking-codes/scan** — ФФ.
Тело: {code: str 1..512, product_id?: uuid, mutation_id?: uuid}.
200: {marking_code_id: str, cis_code: str, product_id: str, line_id: str, already_linked: bool, kiz_count: int, picked_qty: int}.
422 (detail — строка): marking_code_invalid (не прошёл normalize_scanned_cis/is_probably_cis), marking_product_unknown (product_id не из отгрузки либо товар не определён однозначно), marking_code_other_product (код записан за другим товаром), marking_code_other_shipment (код привязан к строке другой отгрузки), marking_code_used_elsewhere (занят предикатом R15 вне этой отгрузки или принадлежит другому селлеру), marking_quantity_exceeded (K+1 > подобрано). 404 not_found; 409 bad_status; 403 forbidden.
Повтор того же кода на ту же строку → 200 с already_linked=true, данные не меняются. mutation_id принимается для единообразия и не меняет результата (повтор и так идемпотентен).

**GET /{request_id}/marking-codes** — ФФ и селлер (видимость).
200: {items: [{marking_code_id, cis_code, product_id, line_id, status, intake_document_number: str|null, linked_at: str|null, has_label_artifact: bool}]}. intake_document_number — номер документа приёмки, если связь известна (import_batch.document_number либо событие imported с source_process=reception), иначе null (неизвестное не выдумывается); linked_at — applied_at (время привязки). Порядок: по товару, затем linked_at, id.

**DELETE /{request_id}/marking-codes/{marking_code_id}** — ФФ, статусы выполнения.
200: {removed: bool}. Код этой отгрузки → отвязка (R18) и removed=true; код есть, но не привязан к этой отгрузке → removed=false; код не найден в тенанте/отгрузке → 404 marking_code_not_found.

**POST /{request_id}/marking-codes/issue** — ФФ, статусы выполнения.
Тело: {product_id: uuid, quantity?: int ≥ 1, mutation_id: uuid}.
200: {items: [как в GET], shortage: int}. Выдача по R21; повтор с тем же mutation_id и тем же телом возвращает те же items и shortage; другое тело → 409 mutation_payload_mismatch.
422: marking_pool_empty (в пуле нет ни одного свободного кода), nothing_to_issue (P − K ≤ 0 либо значение по умолчанию равно 0), marking_product_unknown, product_not_in_shipment.

### 6.2. Подбор
- POST /{request_id}/pick/scan — тело как сейчас, barcode теперь 1..512; при заданных container_kind/container_id сервер сначала проверяет скан как ячейку и как тару (ШК другой или той же тары → kind=container, новый источник), и только затем ищет товар. Форма ответа не меняется.
- POST /{request_id}/pick/set — ответ MarketplaceUnloadPickAllocationOut дополняется необязательным unlinked_marking_codes: list[str] = [] (R19). Внутренний интерфейс: SetPickAllocationResult получает необязательное поле unlinked_marking_codes (tuple[str, ...] = ()), его заполняет BE-A в collect_service, а в ответ API маппит BE-B.
- POST /{request_id}/boxes/{box_id}/scan — barcode 1..512; остальное без изменений (используется ТСД и упаковкой).

### 6.3. Короба
- POST /{request_id}/boxes/attach (существующая) — тело {barcode (1..512), box_preset="60_40_40", allow_over_plan=false}: поле allow_over_plan остаётся для совместимости; клиент FBO всегда шлёт false. 201 → MarketplaceUnloadBoxOut. Отказ сверх остатка: 422 с detail-объектом {code: "plan_limit_exceeded", message: "Количество товаров в коробе больше, чем осталось подобрать: …", items: [{product_id, product_name, in_box, remaining}]} (товар вне плана — remaining 0; все превышающие позиции в items и в message; ничего не сохраняется). Только для attach форма detail меняется (остальные ручки с plan_limit_exceeded отвечают строкой, как раньше). Повтор того же INB/WHB-короба → 409 box_already_attached. Остальные коды: box_barcode_unknown, warehouse_mismatch, box_empty, invalid_container_reference — как сейчас.
- POST /{request_id}/boxes/{box_id}/extract-all — ФФ, статусы выполнения. Тело пустое. 200 → MarketplaceUnloadBoxOut с lines = []. Очищает MarketplaceUnloadBoxLine короба в одной транзакции; записи подбора (pick_allocations), КИЗ, резерв, остаток и расположение не меняются; запись аудита короба как у других операций короба (record_box_mutation); повтор — 200 с пустым составом без изменений. Нет короба → 404 box_not_found; чужая отгрузка → 404.
- MarketplaceUnloadBoxOut: internal_barcode = ШК WHB, при его отсутствии — ШК INB (inbound_intake_box_id). Прочие поля без изменений; допускается необязательное inbound_intake_box_id: str|null.

### 6.4. Детальный ответ GET /{request_id}
Дополняется: lines[].kiz_count: int = 0, lines[].requires_honest_sign: bool = false, lines[].packaging_instructions: str|null, pass_details: object|null. Для селлера boxes, pick_allocations, lines[].picked_qty и has_discrepancy отдаются как для ФФ (R47); linked_packaging_task для селлера не отдаётся. Поведение для ФФ и ТСД: существующие поля неизменны.

### 6.5. «Завершить»
**POST /{request_id}/ship** — ФФ. Тело (необязательное): {acknowledge_discrepancy?: bool = false, acknowledge_marking?: bool = false}.
200 → детальный ответ. Отказы: как раньше (not_found, bad_status, no_lines, planned_shipment_date_required, wb_mp_warehouse_required, distribution_incomplete) плюс 422 с detail-объектом {code: "marking_incomplete", items: [{product_id, product_name, linked, quantity}]} — для каждого товара с requires_honest_sign, у которого linked (K) < quantity (N — отгружаемое количество, сумма по коробам). С acknowledge_marking=true проверка пропускается. Любая ошибка проверки маркировки — 4xx, не 500. assert_unload_marking_done для FBO не вызывается.

### 6.6. Пропуск
- GET /{request_id}/pass — видимость (ФФ и селлер). 200: {pass_details: object|null, editable: bool}; editable=true только для ФФ в статусах до проведения.
- PUT /{request_id}/pass — только ФФ. Тело: {pass_details: {driver_last_name: str, driver_first_name: str, driver_phone?: str|null, car_brand: str, car_number: str, cargo_type?: "box"|"pallet"|null, cargo_places_count?: int|null, arrival_date?: "YYYY-MM-DD"|null}}; строки обрезаются по краям; длины: фамилия/имя ≤ 100, телефон ≤ 32, марка ≤ 100, госномер ≤ 16, cargo_places_count 1..100000. 200: {pass_details, editable}. Отказы: 403 forbidden (селлер); 409 pass_not_editable (отгружена или отменена); 404 not_found; 422 pass_field_required (нет обязательного поля, в detail поле), 422 pass_phone_required (marketplace = ozon и телефон пуст), стандартная 422 валидации. PUT заменяет объект целиком.
- GET /{request_id}/pass.xlsx — видимость. 200 файл по R45 (media type xlsx, Content-Disposition attachment; filename="pass.xlsx"); 404 pass_not_filled.

### 6.7. XLSX для WB
GET /{request_id}/wb-fbw-packaging.xlsx — путь и права без изменений (ФФ и селлер по видимости); меняется источник ШК короба: WHB либо INB (R36), проверка принадлежности короба тенанту сохраняется, проверка склада WHB — только для WHB.

### 6.8. Совместимость
Мобильный ТСД использует: список, карточку, boxes (создать), boxes/{id}/close, boxes/{id}/scan, ship. Изменения этих ручек — только необязательные поля ответов и новое тело/ответ 422 marking_incomplete у ship. Имена, пути и обязательные поля не меняются. mobile/openapi.json перегенерируется после слияния серверной части.

## 9. Решения аналитика (сводка)

Принятые без вопросов владельцу, совместимые с решениями D0–D9:
1. Состояние вида «По ячейкам/По товарам», раскрытий и источника хранится в памяти приложения по id отгрузки, без localStorage (R2).
2. Число КИЗ показывается при requires_honest_sign или K > 0; один раскрываемый список на товар (R3).
3. Распознавание скана на клиенте: товар → ячейка/тара → КИЗ (R7).
4. Логика «пара сканов» и игнорирование дублей после переноса (R8).
5. Отвязка крестиком не меняет статус кода (R18); порядок «последних» по applied_at (R19).
6. Привязываемый КИЗ ставит applied_at = момент привязки; неизвестный код создаётся как принятый внешний (R14).
7. Знаменатель «ЧЗ K из P»; красный при K < P; кнопки «Допечатать» нет, «ШК + ЧЗ» печатает N этикеток ШК и только недостающие ЧЗ (N − K) (R26, R32, R51).

9. Две галки печати FBO — отдельный компонент, хранение в localStorage с ключом, отличным от FBS (R25).
10. Accordion «Короба» раскрыт по умолчанию; кнопка XLSX и пропуск — в строке вкладок документа справа (R24, R42).
11. Вкладка «Упаковка» доступна и в статусе «Отгружено» (только чтение); галочка вкладки — B ≥ P по всем строкам (R23).

17. Для селлера отдаются boxes/pick_allocations/picked_qty/has_discrepancy как ФФ, linked_packaging_task не отдаётся (R47).
18. Дополнительные необязательные поля ответов: kiz_count, requires_honest_sign, packaging_instructions, pass_details, unlinked_marking_codes, inbound_intake_box_id (раздел 6).

Решение аналитика «убрать столбец «Действия» с кнопкой «ШК + ЧЗ»» отменено ведущим 09.10 (владелец запретил убирать необсуждённые элементы): кнопка остаётся, источник печати — новые ручки (R51); кнопка «ШК + ЧЗ» всегда активна (уточнение ведущего 09.10: блокировка при S = 0 не вводится), число ШК N = S при S > 0, иначе плану P.
