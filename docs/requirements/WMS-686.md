## 2. Существующий процесс (проверено чтением кода)

Факты ниже подтверждены чтением файлов на базе `a5df04f`. Работа на стенде и на
складе ArtMaks этим не подтверждается.

**Кто и где.** Сотрудник ФФ открывает отгрузку FBO на маркетплейс
(«Отгрузки на МП» → документ во весь экран). Вкладки документа: «Товары»,
«Подбор», «Упаковка» (`frontend/src/screens/ff/FfSuppliesShipmentsPage.tsx:224-231`,
`:2645-2683`). Над вкладками — сводка «План / Подобрано / Осталось подобрать /
Упаковано (из подобранного)» (`:2572-2642`).

**Подбор** (`FfUnloadPickPage` → `UnloadPickScreen`, `FfSuppliesShipmentsPage.tsx:2847-2861`):

- Скан ячейки или тары выбирает источник; он хранится в состоянии экрана и
  используется для всех следующих сканов товара, пока не отсканирована другая
  ячейка/тара или не нажат ✕ (`unload-pick/UnloadPickScreen.tsx:180`, `:366-390`, `:665-684`).
- Скан ШК товара сразу снимает 1 шт. из выбранного источника
  (`pick/scan` → `record_pick_allocation(quantity=1)`,
  `backend/app/services/marketplace_unload_pick_service.py:333-455`).
  Повторный скан того же ШК — следующая штука.
- Подбор меняет только расположение: товар переносится из ячейки/тары на
  «Сортировку», остаток и резерв не меняются (`marketplace_unload_collect_service.py:555-571`,
  `inventory_service.py:1619-1679`). Остаток списывается только в «Завершить»
  (`marketplace_unload_service.py:964-1122`).
- Ручное количество по каждому источнику — поле «Снять» в раскрывашке товара
  (`unload-pick/PickPlacesTree.tsx:200-232`, `pick/set`). Уменьшение возвращает
  товар именно в ту же тару (`marketplace_unload_collect_service.py:725-768`).
- Один короб можно делить между отгрузками: доступное количество источника
  учитывает уже снятое другими документами (`pick_option_location_service.py:299-353`).
- Отмена последнего снятия — только в памяти экрана (`UnloadPickScreen.tsx:321-334`).
- Скан идёт через общую очередь: следующий код обрабатывается после предыдущего
  (`frontend/src/hooks/useScanIntake.ts:121-145`).
- **КИЗ в подборе отсутствует.** Код Честного знака уходит в `pick/scan` как
  обычный штрихкод и получает отказ `barcode_unknown`
  (`marketplace_unload_pick_service.py:425-429`).
- **Целый короб в «Подборе» отсутствует**: скан короба только выбирает источник.

**Упаковка** (`FfPackagingTaskPanel` для задания отгрузки, `FfSuppliesShipmentsPage.tsx:2862-2904`):

- Таблица строк задания: Товар, артикулы, размер, ШК, ТЗ, ЧЗ (напечатано/нужно),
  кнопка «ШК + ЧЗ» (`FfPackagingPage.tsx:923-1087`). Кнопка открывает
  `MarkingPrintDialog` и печатает через браузер, не через WMS Print (`:380-407`).
- **Поле скана товара для FBO скрыто** (`FfPackagingPage.tsx:842`,
  условие `!isMpUnloadTask`). Сканер страницы на этой вкладке принимает только
  ШК готового короба `WHB-`/`INB-`; ШК товара даёт ошибку «На этой строке
  сканируют только готовый короб» (`FfSuppliesShipmentsPage.tsx:988-1002`, `:2111-2127`).
- Прогресс упаковки FBO вычисляется из состава коробов отгрузки
  (`packaging_task_service.py:676-770`).
- Блок «Короба» (свёрнут): создать короб(а), привязать готовый короб по ШК
  целиком (с подтверждением и превышением плана), «Наполнить» (диалог со
  сканом ячейка → тара → товар), печать ШК короба через браузер,
  «Скачать XLSX для WB» (`FfSuppliesShipmentsPage.tsx:2905-3079`).
- Наполнение короба сначала берёт уже подобранные, но не уложенные штуки, и
  только недостающее снимает со склада (`marketplace_unload_box_service.py:834-867`).
- «Убрать из короба» в интерфейсе показан только в черновике
  (`FfSuppliesShipmentsPage.tsx:1236-1240`, `:1441-1455`), хотя сервер разрешает
  и в статусе «Сборка» (`marketplace_unload_box_service.py:1006`).
- Завершение упаковки и «Завершить» отгрузку требуют для товаров с ЧЗ
  «напечатано + внешние ≥ количество» (`FfPackagingPage.tsx:253-261`, `:707-739`;
  `packaging_task_service.py:1283-1295`, `:1533-1543`).

**FBS как образец печати** (`frontend/src/screens/v2/FbsPackingScanBar.tsx:33-174`,
`FbsScanPrintToggles.tsx:40-107`): поле скана, галки «Печатать QR», «Печатать ЧЗ
− N +», «Перепечатывать ЧЗ − N +» (две последние взаимоисключают друг друга),
«Отменить последний скан», размер этикетки. Печать при скане идёт в локальную
программу WMS Print Direct `http://127.0.0.1:17843/print` с ключом операции
(`frontend/src/utils/printDirectQr.ts`); повтор с тем же ключом не печатает
второй раз, отказ программы показывается, браузерной подмены нет.

**КИЗ и история** (`backend/app/models/marking_code.py:222-435`):
коды приёмки привязаны к документу приёмки и товару (не к коробу)
(`inbound_marking_service.py:198-313`); у отгрузок FBO, их коробов и строк
подбора нет никакой связи с КИЗ; событие `shipped` объявлено, но нигде не
пишется. «История ЧЗ» и её CSV существуют (`api/marking_codes.py:1202-1300`).
Срок годности и QR маркетплейса для КИЗ не хранятся.

**Финал.** «Скачать XLSX для WB» формирует файл с колонками «Баркод товара /
Кол-во товаров / ШК короба / Срок годности / ШК короба для печати в стороннем
сервисе»; заполняются первые три (`marketplace_unload_wb_fbw_export_service.py:29-35`,
`:110-119`). Сервер отдаёт файл и селлеру, но в кабинете селлера кнопки нет.
Пропуска, слота и вложений у отгрузки нет (`marketplace_unload_service.py:1005-1008`).

## 4. Итоговое видение и экраны

Принцип: обычные вкладки, таблицы, тема и компоненты WMS остаются. Новое —
только там, где без него требование не выполняется. Никаких новых панелей,
услуг, дат и режимов.

### 4.1. «Товары» — без изменений

Первая вкладка, шапка документа, сводка и таблица плана не меняются.

### 4.2. «Подбор» — существующий экран + КИЗ в строке источника + «Забрать целиком»

```
[ Сканер: место, товар или КИЗ ........................ ]  (существующее поле)
Снимаем с: Короб INB-000123 · А-1-1   [Забрать целиком]  [✕]
12 штук осталось снять из 20 по плану отгрузки   ▓▓▓▓░░░░
┌ Товар ───────────── Артикул ── SKU ── ШК ── Где лежит ── План ─ Снято ─ Осталось ┐
│ ▾ Футболка 48       DEMO-TS   …                В 2 местах   8      3       5       │
│     А-1-1                                                                           │
│       Короб INB-000123        внутри 6 шт                                           │
│         Футболка 48   ШК…   Лежит 3   Снять [3]                                     │
│           КИЗ 0104…21AbC…  ← светло-зелёная (новая)                ✕               │
│           КИЗ 0104…21XyZ…                                           ✕               │
└─────────────────────────────────────────────────────────────────────────────────────┘
```

- Последовательность: ячейка → короб → ШК (+1 сразу) → КИЗ (необязательно) →
  ШК → КИЗ → … Источник не нужно сканировать заново, пока не отсканирована
  другая ячейка/тара.
- КИЗ показывается строкой под товаром внутри того источника, из которого
  снята единица. Новая строка подсвечена светло-зелёным (как строка последнего
  скана в приёмке). Под строкой КИЗ — номер приёмки, если он известен.
- «Забрать целиком» появляется только когда источник — тара (короб/палета).
  Одно нажатие переносит всё содержимое тары в отгрузку как короб отгрузки
  с собственным ШК, без вскрытия. Превышение плана — существующее
  подтверждение «Больше, чем в плане».
- Поле «Снять», раскрывашка мест, отмена последнего снятия, прогресс и нижние
  кнопки остаются прежними.

### 4.3. «Упаковка» — существующая таблица + поле скана FBS-вида + вложенность КИЗ

```
[ Сканируйте ШК товара или ЧЗ ...... ] ☑Печатать ШК ☑Печатать ЧЗ −1+ ☐Перепечатывать ЧЗ ↶  [58×40]  Короб 2 · WHB-…
                                                                                         [Печать накладной]
┌ Товар ──── Артикул ─ Артикул WB ─ Размер ─ ШК ─ ТЗ ─ ЧЗ ─ Действия ┐
│ ▾ Футболка 48 (подсветка последнего скана)        1/8   [ШК + ЧЗ]  │
│     Упаковано 3 из 8 · с КИЗ 2                                     │
│     КИЗ 0104…21AbC  · Короб 2 · Приёмка 000041   [Перепечатать] ✕  │  ← светло-зелёная
│     КИЗ 0104…21XyZ  · Короб 1 · Приёмка не указана [Перепечатать] ✕ │
│ ▸ Футболка 50                                       0/4   [ШК + ЧЗ]  │
└─────────────────────────────────────────────────────────────────────┘
▸ Короба  [Коробов: 2] [Единиц: 3]   (существующий блок; текущий короб отмечен)
   [Скачать XLSX для WB]  [Пропуск: прикрепить / pass.pdf]
```

- Поле скана и галки — тот же вид и поведение, что в FBS, только первая галка
  «Печатать ШК» вместо «Печатать QR» (QR заказа FBS в FBO нет).
- Скан ШК: сразу +1 упакованная единица этого товара — подобранная, ещё не
  уложенная штука кладётся в текущий короб. Строка товара раскрывается.
- Следующий КИЗ (необязательно) — строка под этим товаром, светло-зелёная.
  Повтор ШК того же товара → следующая единица; КИЗ → вторая строка. Скан
  другого товара — то же у другого товара.
- Текущий короб показан справа в поле скана; меняется сканом ШК короба этой
  отгрузки (в том числе ранее закрытого или взятого целиком — короб снова
  изменяемый). Рядом — «Закрыть короб»: текущим становится следующий открытый
  короб; если открытых нет — подсказка и существующая «Создать короб» (R32).
  Скан готового короба склада/приёмки, не входящего в отгрузку, — прежнее
  присоединение целиком.
- КИЗ всегда относится к текущему коробу и к товару по своему GTIN; если в
  текущем коробе нет непомеченной единицы этого товара — отказ с подсказкой
  отсканировать нужный короб; в другой короб код молча не уходит (R14).
- В строке КИЗ: «Перепечатать» (N экземпляров через WMS Print) и ✕ «Убрать КИЗ».
- Блок «Короба», «Наполнить», XLSX и печать накладной не перестраиваются.
  В карточке короба у строки товара — действие «Убрать» (R28): выбор конкретной
  единицы — с КИЗ (код виден) или без КИЗ — и показ, куда она вернётся
  («в Короб INB-…/ячейку А-1-1»). Рядом с «Скачать XLSX для WB» — поле пропуска (R25).

### 4.4. История КИЗ

Существующая «История ЧЗ» и её CSV после «Завершить» показывают для кода
событие «Отгрузка» с номером отгрузки FBO; если код был в приёмке — событие
приёмки уже есть. Новые экраны не вводятся.

## 5. Требования

Каждое требование: условие → действие → результат на экране и в данных → основание.

### Подбор

**R1. Источник держится до следующей ячейки/тары.**
Условие: открыта вкладка «Подбор» отгрузки FBO в статусе «Утверждено/Сборка».
Действие: сотрудник сканирует ячейку или тару, затем любое число ШК товара и КИЗ.
Результат: все сканы товара и КИЗ относятся к этому источнику; строка «Снимаем с:»
показывает его. Источник меняется только сканом другой ячейки/тары или ✕; скан
другой тары при уже выбранной таре сразу выбирает новую тару (сейчас это не
работает, риск K23). Он
сохраняется после ошибки сервера при снятии или ручной правке количества, после
переключения вкладок этого же документа и после перезагрузки страницы этого
документа. Если тара за это время исчезла из ячейки, следующий скан товара
получает понятный отказ и источник сбрасывается.
Основание: сообщение 7 («пока я не пифну другой короб либо другую ячейку»), 784.

**R2. Скан ШК товара — сразу одна единица.**
Условие: выбран источник (или товар лежит в одном месте).
Действие: скан ШК товара.
Результат: «Снято» +1 сразу, без ожидания КИЗ; товар переносится из источника на
«Сортировку»; остаток не меняется. Повторный скан того же ШК — следующая
физическая единица (+1). Основание: сообщения 7, 8; брифинг ведущего; AGENTS.md
«Остаток и расположение».

**R3. Необязательный КИЗ после товара относится к этой единице.**
Условие: непосредственно перед КИЗ отсканирован ШК товара этой отгрузки
(контекст единицы, D16).
Действие: скан КИЗ (формат GS1: `01` + 14 цифр + `21…`, со скобками или с GS).
Результат: КИЗ сохраняется за единицей, только что посчитанной этим ШК (в данных —
за одной ещё не помеченной единицей этого товара из текущего источника в этой
отгрузке, D2). Один ШК — не больше одного КИЗ. Количество «Снято»/«Осталось» не меняется.
Раскрывается строка товара, под строкой источника появляется строка КИЗ,
подсвеченная светло-зелёным как новая. После перезагрузки строка КИЗ остаётся
(без подсветки). Основание: сообщения 3, 7; 774, 789.

**R4. КИЗ необязателен.**
Действие: подбор и упаковка без единого скана КИЗ.
Результат: подбор, упаковка и «Завершить» работают как сейчас; новых условий,
связанных со сканом КИЗ, нет. Основание: сообщения 3 («можно не вносить»), 8
(«это не обязательно»); 768.

**R5. КИЗ не создаёт единиц и не дублируется.**
Результат:
(а) повтор того же КИЗ в этой отгрузке — сообщение «КИЗ уже привязан», ни
единицы, ни второй связи;
(б) КИЗ сверх количества единиц товара (из источника) — отказ «Коды уже есть для
всех снятых единиц. Сначала отсканируйте ШК следующей единицы», количество не меняется;
(в) КИЗ уже числится в другой незавершённой или завершённой отгрузке, в заказе
FBS или использован иначе — отказ с указанием, где он числится; первая связь
не меняется; единица остаётся посчитанной.
Основание: 771 («увидели либо дубль»); брифинг («повтор same KIZ не должен её создавать»).

**R6. Цель КИЗ однозначна и задаётся последним сканом (D16).**
(а) Контекст единицы: последним был ШК товара P. КИЗ относится к этой единице P.
Если GTIN кода указывает другой товар — отказ «КИЗ относится к товару A, а
последним отсканирован B. Код не привязан», связи нет; цель на ранее снятый A
не меняется. Если GTIN не найден в карточках — код относится к P. Второй КИЗ
после того же ШК — отказ «Код уже есть у этой единицы: отсканируйте ШК
следующей единицы».
(б) Контекст проверки: последним был скан ячейки/тары («Подбор») или ШК короба
отгрузки («Упаковка»). КИЗ без ШК относится к непомеченной уже посчитанной
единице своего товара (по GTIN) именно в этом источнике/коробе, без +1; можно
сканировать несколько кодов подряд (проверка готового короба). GTIN не найден —
«Сначала отсканируйте ШК товара». Нет непомеченной единицы этого товара в
источнике/коробе — отказ, код в другой источник/короб не уходит.
(в) Последовательность ШК A → ШК B → КИЗ(A) — отказ по (а); чтобы привязать код
к A, оператор сканирует источник/короб (контекст проверки) и затем КИЗ(A).
Основание: сообщение 8 («отсканировал… и к нему сканишь КИЗ»); 771; аналог приёмки
`product_gtin_mismatch`; замечания ведущего 2 и 1 (вторая серия).

**R7. Целый короб/палета без вскрытия.**
Условие: источник — тара (короб или палета) в ячейке.
Действие: «Забрать целиком» в строке «Снимаем с:».
Результат: всё текущее содержимое тары (все товары, смешанный состав; для
палеты — все короба и россыпь на ней) переносится в отгрузку одним коробом
отгрузки на каждый короб, с его собственным ШК, без пересканирования единиц.
Повтор не удваивает состав. Остаток не меняется. Если состав больше плана —
существующее подтверждение «Больше, чем в плане». Основание: 758, 762, 763, 779,
784, 788; сообщение 7 («сканю ячейку и сканю короб, и он уходит»).

**R8. Ручное количество и деление по направлениям сохраняются.**
Поле «Снять» по каждому источнику, отмена последнего снятия и прогресс остаются.
Один короб можно разделить между несколькими отгрузками (разные склады WB):
каждая отгрузка снимает своё количество, доступное количество тары уменьшается
для всех. КИЗ, отсканированные в отгрузке, относятся только к ней. Основание:
788, 789, 778.

**R9. Коррекции и возврат — с точными кодами.**
(а) Уменьшение количества по источнику сначала возвращает в источник единицы без
КИЗ. (б) Если все оставшиеся единицы источника с КИЗ, система не выбирает код
сама: показывает «Верните конкретную единицу (действие у кода) или отвяжите
ошибочный код» и ничего не меняет.
(в) У строки КИЗ два действия: «Вернуть эту единицу в {источник}» — одно
атомарное действие: −1 из источника этого кода, единица в свой источник, код
свободен и становится точно известным содержимым этой тары (R30); и «Отвязать
код» — только для ошибочного скана: связь снимается, количество не меняется,
местонахождение кода неизвестно. Отвязка + последующее уменьшение количества не
доказывают, какой код вернулся, и состав тары не меняют. Повтор — без изменений.
(г) «Отменить последнее снятие» отменяет последний скан: если это КИЗ — отвязывает
код; если ШК — возвращает единицу без КИЗ.
Основание: 774 («либо же их сканить при изменении короба»), 763 («убрать»).

**R10. Повтор доставки скана не равен новому скану.**
Каждый физический скан несёт свой ключ операции. Повтор запроса с тем же ключом
(потеря ответа, ретрай сети) возвращает исходный результат без второй единицы и
без второго перемещения. Новый скан того же ШК — новая единица.
Основание: failure-cases B07, навык аналитика.

**R11. Быстрый поток сканов — в порядке прихода.**
ШК → КИЗ → ШК → КИЗ, считанные подряд быстрее ответа сервера, обрабатываются по
очереди; каждый КИЗ относится к единице, отсканированной непосредственно перед
ним (контекст единицы, R6а). Основание: сообщение 8; существующая очередь `useScanIntake`.

### Упаковка

**R12. Поле скана и панель печати FBS-вида на «Упаковке» FBO.**
Над таблицей строк задания — поле «Сканируйте ШК товара или ЧЗ», галки
«Печатать ШК», «Печатать ЧЗ» с «− N +», «Перепечатывать ЧЗ» с «− N +»
(взаимоисключают друг друга, как в FBS), «Отменить последний скан», размер
этикетки, справа — текущий короб. Галки «Печатать QR» нет. Настройки FBO
сохраняются отдельно от FBS. Основание: сообщение 8 («в точности такие же
кнопки… всё то же самое, что с FBS»).

**R13. Скан ШК на упаковке — сразу +1 упакованная единица.**
Действие: скан ШК товара отгрузки.
Результат: одна подобранная и ещё не уложенная единица кладётся в текущий короб;
«Упаковано» по товару и в сводке +1; строка товара раскрывается и подсвечивается
как последний скан. Упаковка не снимает товар со склада и не переподбирает уже
подобранное: если все подобранные единицы товара уже в коробах, +1 не происходит,
показывается «Все подобранные единицы уже упакованы — подберите ещё на вкладке
«Подбор» или используйте «Наполнить»», ничего не меняется; ШК при этом выбирает
товар для следующего КИЗ. Остаток не меняется. Основание: сообщение 8; брифинг.

**R14. Следующий КИЗ на упаковке — строка под товаром, цель — текущий короб.**
Результат: после ШК товара P КИЗ относится к только что уложенной единице P в
текущем коробе (контекст единицы, R6а; несовместимый GTIN — отказ); под товаром
появляется строка КИЗ, светло-зелёная как новая; повтор ШК+КИЗ того же товара —
вторая строка; для другого товара — в его вложенности. Если ШК не уложил единицу
(все подобранные уже в коробах), КИЗ после него относится к непомеченной
единице P в текущем коробе без +1. Проверка готового (взятого целиком) короба
без переупаковки: скан ШК этого короба делает его текущим без изменения
количества (контекст проверки, R6б), затем КИЗ его единиц подряд. Если в текущем
коробе нет непомеченной единицы товара кода — отказ с подсказкой «отсканируйте
ШК короба, в котором лежит эта единица»; в другой короб код молча не уходит.
Два короба одного товара: код идёт только в текущий; переключение — сканом ШК короба.
Основание: сообщение 8; 779; замечания ведущего 2 (обе серии).

**R15. Текущий короб упаковки.**
Текущий — выбранный оператором (сканом ШК короба этой отгрузки) или, если не
выбран, последний созданный открытый короб отгрузки. Скан ШК любого короба этой
отгрузки, включая закрытый и взятый целиком, делает его текущим и не меняет
количество. Скан готового короба склада/приёмки, ещё не входящего в отгрузку, —
прежнее присоединение целиком. Если текущего короба нет, скан ШК не теряется
молча: «Нет открытого короба — создайте короб» и рядом существующая кнопка
«Создать короб» (D10: автосоздания нет). Основание: 765; существующий блок «Короба».

**R16. Печать при скане через WMS Print.**
(а) «Печатать ШК»: на каждую упакованную единицу — этикетка ШК товара.
(б) «Печатать ЧЗ» × N: на упакованную единицу берётся один код из пула товара,
печатается N экземпляров, код сразу привязывается к этой единице в текущем коробе
и появляется строкой КИЗ. Новый код **не выдаётся**, если единица может уже
нести КИЗ: у товара в отгрузке есть коды, отсканированные при подборе и ещё не
подтверждённые в коробе (R29), или в текущем коробе нет непомеченной единицы.
Тогда — сообщение «Единица может быть уже с КИЗ: отсканируйте её КИЗ»;
упаковка единицы не отменяется. Нет кода в пуле — сообщение «В пуле нет кодов
для {товар}», единица остаётся упакованной, печати нет.
(в) «Перепечатывать ЧЗ» × N: при скане существующего КИЗ печатаются N экземпляров
этого же кода; код из пула не берётся.
(г) Печать идёт в WMS Print с ключом операции на единицу и экземпляр
(`…:c2`, `…:c3` для копий); повтор того же задания использует тот же ключ и не
даёт второй этикетки. Ошибка WMS Print или потерянный ответ показываются в поле
скана с «Повторить печать» (тот же ключ); упаковка единицы не отменяется;
следующие сканы не блокируются (D15). Escape/«Отменить печать» снимает
ожидающее задание. Снятая после сбоя галка больше не печатает и не требует
WMS Print (как WMS-643).
Основание: сообщение 8; FBS-образец; замечание ведущего 3, 5.

**R17. Действия строки КИЗ.** «Перепечатать» (N экземпляров через WMS Print) и
✕ «Убрать КИЗ» (связь снимается, единица остаётся упакованной). Основание:
сообщение 8 («перепечать КИЗа»); 763.

**R18. Отсканированный КИЗ засчитывается в маркировку строки.**
Для товара с ЧЗ привязанный (отсканированный или напечатанный при скане) код
засчитывается в «ЧЗ» строки упаковки и в проверку маркировки при «Завершить»,
как внешний код в FBS. Один и тот же код (напечатан и затем отсканирован)
считается один раз. Скан КИЗ при этом не становится обязательным.
Основание: FBS (`fbs_kiz_service.py:1361`, `:1660`); существующий гейт
`packaging_task_service.py:1283-1295`; R4.

**R19. Упаковка и печать не меняют остаток.** Укладка в короб, печать,
привязка и отвязка КИЗ не создают движений остатка; «Завершить» списывает
как сейчас. Основание: AGENTS.md.

### История и финал

**R20. История КИЗ с реально известными связями.**
Для каждого привязанного КИЗ видно: номер приёмки (если код был отсканирован в
приёмке), номер отгрузки FBO, источник подбора (если КИЗ сканирован при подборе),
короб отгрузки (если известен). Неизвестное показывается как «не указано» и не
выдумывается. Для внешнего кода, впервые встреченного в отгрузке, приёмка пустая.
Основание: 776, 779, 789; сообщение 3.

**R21. «Завершить» фиксирует отгрузку КИЗ; отмена освобождает.**
После «Завершить» в истории каждого привязанного кода — событие «Отгрузка» с
номером отгрузки. Отмена неотгруженной отгрузки снимает её связи КИЗ; коды можно
использовать снова. Основание: 776, 789.

**R22. Выгрузка КИЗ по отгрузкам.** Существующая выгрузка «Истории ЧЗ» (CSV)
содержит строки отгрузки FBO с номером документа и кодом. Основание: 776
(«клиенты просят выгрузку по честному знаку, по нашим отгрузкам»).

**R23. Целый короб сохраняет свой ШК.** Короб склада или приёмки, присоединённый
целиком, показывается в отгрузке и в XLSX для WB со своим ШК. Основание: 763,
766.

**R24. XLSX для WB не меняется по составу колонок.** КИЗ, QR маркетплейса и срок
годности в файл не добавляются и не выдумываются. Основание: 756; брифинг.

**R25. Пропуск к отгрузке.** Селлер или ФФ прикрепляет файл пропуска к отгрузке
(PDF/изображение); обе стороны видят имя файла и могут скачать или заменить.
Пропуск не блокирует подбор, упаковку и «Завершить». На экране ФФ — рядом с
«Скачать XLSX для WB». Основание: 756 («закрепить в WMS пропуск»), сообщение 8.

**R26. Селлер скачивает XLSX для WB.** В карточке отгрузки селлера доступна та же
кнопка «Скачать XLSX для WB». Основание: 756 («подгрузить… Excel в кабинет ВБ»).

### Интерфейс

**R27. Ничего лишнего.** Первая вкладка «Товары», заголовок, сводка, вкладки,
таблицы, тема и компоненты не меняются. Новое на экране только: строки КИЗ во
вложенности «Подбора» и «Упаковки», кнопка «Забрать целиком» в строке источника,
поле скана с галками на «Упаковке», поле пропуска у XLSX. Нет услуг, тарифов,
калькулятора, новых дат, отдельных панелей и режимов подбора.
Основание: сообщения 4, 7.

### Добавлено по замечаниям ведущего к `0ed8315`

**R28. Убрать конкретную единицу из короба отгрузки.**
Условие: отгрузка в статусе «Утверждено»/«Сборка»; короб открыт, закрыт или взят
целиком (запрета менять закрытый короб нет — 763).
Действие: в существующей карточке короба (блок «Короба») у строки товара —
«Убрать», затем выбор единицы: «КИЗ {код}» для каждой единицы с КИЗ в этом
коробе или «Без КИЗ», если такие есть. В каждом пункте видно, куда вернётся
единица: тара/ячейка, из которой её сняли.
Результат: в коробе −1, «Подобрано» −1; единица возвращается в источник подбора
(остаток не меняется, меняется расположение); связь КИЗ снимается, код свободен.
Место возврата различается явно:
- **источник известен** — у кода, отсканированного при подборе: пункт «КИЗ {код} →
  вернуть в {источник} (источник известен)»; код становится точно известным
  содержимым этой тары (R30);
- **источник неизвестен** — у кода, впервые отсканированного на упаковке (или
  напечатанного там): пункт «КИЗ {код} — источник неизвестен» раскрывает выбор места
  из существующего контекста — источников, из которых этот товар подбирался в этой
  отгрузке; оператор выбирает, куда кладёт единицу; без выбора сервер отказывает
  `return_place_required`; выбранное место записывается как место возврата, а не
  как доказанный исходный источник;
- **без КИЗ** — тот же выбор места; предложенное по умолчанию (последний источник
  подбора с непомеченными единицами, D14) подписано «предложено».
Если исходной тары уже нет — возврат в её ячейку россыпью с прямым сообщением (не
ошибка 500, риск K22). Если у строки все единицы с КИЗ, «Без КИЗ» не
предлагается. Повтор того же запроса не убирает вторую единицу.
Основание: 763 («открыть и… убрать»), сообщение 2 («Как убрать единицу из
короба?»), 774; замечание ведущего 1.

**R29. Сквозной путь: КИЗ, отсканированный при подборе, → короб на упаковке.**
(а) Код, привязанный при подборе, знает источник, но не короб. Скан ШК на
упаковке кладёт в текущий короб одну подобранную единицу товара; какая именно
физическая штука — WMS не знает (D2), поэтому код подборa не переносится в
короб автоматически: в истории у него «короб не указан».
(б) Скан этого же кода на упаковке (после ШК или отдельно) подтверждает его
единицу в текущем коробе: код получает короб, количество не меняется, новой
связи нет; сообщение «КИЗ подтверждён в коробе X».
(в) Повтор того же кода в том же коробе — «КИЗ уже в этом коробе», без
изменений. Тот же код в другом коробе отгрузки — отказ «КИЗ числится в коробе
Y»; молча код не переносится.
(г) «Печатать ЧЗ» не выдаёт новый код единице, которая может уже нести КИЗ
(R16б): пока у товара есть коды подбора, не подтверждённые в коробах, новый код
из пула не берётся.
(д) Точность: WMS точно знает, какие коды в отгрузке; короб кода — только если
код отсканирован/напечатан в контексте короба; источник кода — только если код
отсканирован при подборе. Для неотсканированных единиц коды не выводятся;
источник кода, впервые появившегося на упаковке, не выводится (R28 — выбор места
возврата оператором).
Основание: сообщения 3, 8; 779; замечание ведущего 3.

**R30. Известный и неизвестный состав КИЗ тары (частичная достоверность).**
«Известный код тары» — код, про который WMS знает, что он лежит в этой таре
хранения. Сегодня он появляется только атомарным возвратом единицы с кодом:
R28 (из короба отгрузки) или R9в «Вернуть эту единицу» (из подбора). Отвязка
кода и последующее уменьшение количества известным кодом не делают. Коды
приёмки известны только на уровне документа и товара, не короба
(`inbound_marking_service.py:198-313`), поэтому состав коробов приёмки —
**неизвестный**. Известные коды — почти всегда **часть** состава тары, а не весь.
Каждый известный код имеет одно из двух состояний по товару и таре:
- **точно в таре** — после атомарного возврата и пока из этой тары не снимали
  единицы этого товара без кода;
- **возможно в таре** — после снятия из этой тары хотя бы одной единицы этого
  товара без кода (ШК без КИЗ, ручное количество, «Забрать целиком» в другой
  документ без известного кода): оператор мог забрать именно эту единицу;
  конкретный код никому автоматически не назначается.
(а) Снятие со сканом кода (из точных или возможных) убирает этот код из тары.
(б) Возврат без кода (уменьшение количества) состояния не меняет.
(в) Когда единиц товара в таре не осталось, известные коды этого товара
перестают числиться в таре (куда ушли — неизвестно, если не сканировали).
(г) «Забрать целиком»: коды «точно в таре» переносятся конкретными кодами в
короб отгрузки; коды «возможно в таре» не переносятся и не назначаются.
(д) В строке «Снимаем с» — «КИЗ в таре: точно N, возможно M» с раскрываемым
списком, либо «состав КИЗ тары неизвестен». Обычный подбор без КИЗ не блокируется.
(е) Скан кода, который числится в другой таре, при снятии из текущей —
принимается (физический факт важнее записи), запись исправляется, показывается
предупреждение «КИЗ числился в таре Y».
Ограничение: центральная цель сообщения 3 для коробов приёмки не закрыта до
появления связи из раздела 7.1. Основание: сообщение 3; 774; замечание ведущего 4.

**R31. Граница печати: сбои и повторы.** Детализация R16г для проверки:
задание WMS Print с ошибкой, с потерянным ответом и без кода в пуле не меняет
упаковку и связи; повтор берёт тот же ключ; второй этикетки при успешном
первом ответе нет; при снятой галке повтор не печатает. В макете и тестах
настоящий принтер и `127.0.0.1:17843` не вызываются — запрос перехватывается.
Основание: сообщение 8; WMS-643; замечание ведущего 5.

**R32. Закрыть короб и перейти к следующему.**
У текущего короба в поле скана упаковки — «Закрыть короб» (существующая
серверная операция `close`). После закрытия текущим становится следующий
открытый короб (самый ранний созданный); если открытых нет — «Нет открытого
короба» и существующая «Создать короб». Закрытый короб можно снова сделать
текущим сканом его ШК и изменить (R15, R28). Основание: 765; 763.

**R33. Доступ и конкуренция.**
(а) Связи КИЗ отгрузки видит и меняет только ФФ этой организации; селлер — только
читает свои отгрузки; чужая организация получает 404.
(б) Два одновременных скана одного КИЗ в двух отгрузках: побеждает один, второй
получает «КИЗ уже числится в отгрузке N»; связь одна.
(в) Два одновременных снятия последней единицы источника для двух отгрузок:
снимается одна, вторая получает отказ доступности (существующие блокировки).
(г) Быстрые сканы при задержанном ответе сервера обрабатываются по порядку:
КИЗ, считанный до ответа на предыдущий ШК, уходит после него и с тем же товаром.
Основание: навык аналитика; failure-cases B01, B07; замечание ведущего 5.

## 6. Решения аналитика (не слова владельца)

- **D1. Как распознаётся КИЗ.** По формату GS1, как в приёмке
  (`inboundMarkingCodes.ts:15-18`). Иначе код — место/тара/товар как сейчас.
- **D2. Единица без собственного номера.** У физической штуки нет ID; КИЗ
  хранится за парой «отгрузка + товар + источник + короб (если известен)».
  Правило «кодов не больше единиц» (по товару, по источнику, по коробу) заменяет
  «привязку к штуке». Поэтому повторный ШК — новая штука, а КИЗ лишь помечает уже
  посчитанную.
- **D3. Новая связь КИЗ ↔ отгрузка нужна.** Существующие связи не подходят:
  `MarkingCode.packaging_task_line_id` означает «напечатан для строки» и
  стирается при слиянии строк (`packaging_task_service.py:626-632`);
  `FbsOrderMarking` — только FBS. Новая связь хранит отгрузку, товар, источник,
  короб; один код — одна активная связь.
- **D4. Упаковка не снимает со склада.** Поле скана упаковки кладёт только уже
  подобранные единицы. Снять и уложить одним движением — существующее
  «Наполнить» с выбором источника.
- **D5. «Забрать целиком» — кнопка после скана тары**, а не автоматический
  перенос при скане: один и тот же скан «ячейка → короб» начинает и частичный
  подбор (сообщение 7 описывает оба). Вопрос Q1.
- **D6. Источник хранится в пределах документа** (вкладка браузера), чтобы
  ошибка/перезагрузка не сбрасывала его (R1).
- **D7. Настройки печати FBO отдельно от FBS**, иначе включённая в FBS печать QR
  и количества переходят в FBO (`fbsScanAutoPrint.ts:41`).
- **D8. Ошибки скана КИЗ не блокируют работу.** Отказ касается только связи кода;
  единица уже посчитана, следующий скан принимается.
- **D9. Интерфейс контракта тестов** — раздел 9. Это решение аналитика и
  тестировщика; меняется только через аналитика.
- **D10. Короб не создаётся автоматически** (бывш. Q4): ни при первом скане
  упаковки, ни при закрытии. Основание по контексту: решение заказчика 16.08
  против самопроизвольных коробов (`marketplace_unload_collect_service.py:478-486`);
  физический короб всё равно нужно взять и оклеить. Цена — один клик «Создать короб».
- **D11. Пропуск** (бывш. Q6): прикрепляют обе стороны, не обязателен для
  «Завершить» — AGENTS.md запрещает пользовательские блокировки без указания владельца.
- **D12. Статус кода в ЧЗ при отгрузке не проверяется** (бывш. Q5): не просили;
  проверка уже есть при приёмке (773); дополнительная внешняя зависимость на
  каждом скане отгрузки не нужна для R1–R33.
- **D13. Прежний контракт макета сохраняется** (бывш. Q8): `docs/mockups/WMS-686/model.test.ts`
  (11 кейсов отклонённого расширенного макета) закреплён хешем в
  `guards/PROCESS_CONTRACTS.json:228` и требуется задачей `wms686-mockup` в
  `ci.yml` для `process-proof`. Он остаётся зелёным на `model.ts` из etalon и
  **не является** контрактом этой постановки: новый макет его не использует,
  новый контракт — раздел 10. Снятие закрепления — проверенное обновление процесса,
  решение ведущего.
- **D14. Место возврата единицы без КИЗ** (R28): последний источник подбора
  товара, где есть единицы без КИЗ; показывается до нажатия.
- **D15. Сбой печати не блокирует сканирование** (R16г): задание остаётся с
  «Повторить печать» (тот же ключ) или снимается Escape. В FBS заказ остаётся
  выбранным до повтора; в FBO единица не выбирается, поэтому следующий ШК —
  следующая единица, а не повтор печати.
- **D16. Цель КИЗ задаёт последний скан** (R3, R6, R11, R14): после ШК товара —
  эта единица этого товара (несовместимый GTIN — отказ, не смена цели); после
  скана источника/короба — проверка единиц этого источника/короба без +1; код
  никогда не уходит молча в соседний источник/короб. Клиент передаёт `product_id`
  последнего ШК только в контексте единицы и не отправляет второй КИЗ после того
  же ШК; без `product_id` сервер работает в контексте проверки.
- **D17. Известный состав тары** (R30) появляется только из атомарных возвратов с
  кодом (R28, R9в); достоверность понижается до «возможно» при снятии без кода;
  из приёмки — только после связи раздела 7.1.

## 9. Интерфейс контракта для тестов (D9)

Пути без префикса `/api`, как в тестах бэкенда.

1. `POST /operations/marketplace-unload-requests/{id}/pick/scan` — тело как сейчас
   плюс необязательный `mutation_id` (UUID). Повтор с тем же `mutation_id` и тем же
   телом возвращает исходный результат без второго снятия. Если `barcode` — КИЗ
   (D1): ответ `200 {"kind": "marking", "product_id", "marking_code_id", "cis_code",
   "already_linked", "picked_qty", "allocation_quantity"}` без изменения количеств;
   `product_id` в теле — товар последнего ШК (контекст единицы, D16; GTIN другого
   товара → `marking_code_other_product`); без `product_id` — контекст проверки
   выбранного источника. Источник — как у товара. Отказы `422 {"detail": …}`: `marking_quantity_exceeded`,
   `marking_code_other_shipment`, `marking_code_other_product`,
   `marking_code_already_used`, `marking_product_unknown`.
2. `GET /operations/marketplace-unload-requests/{id}/marking-codes` → список
   `{"marking_code_id", "cis_code", "product_id", "storage_location_id",
   "container_id", "box_id", "intake_document_number"}`; неизвестное — `null`.
3. `DELETE /operations/marketplace-unload-requests/{id}/marking-codes/{marking_code_id}`
   → `200 {"removed": true}`; повтор → `200 {"removed": false}`; количество не меняется.
4. `POST …/pick/set` при уменьшении: сначала единицы без КИЗ; если нужно убрать
   единицу с КИЗ — `422 marking_unit_ambiguous`, ничего не меняется.
5. `POST …/boxes/{box_id}/scan` плюс необязательный `pick_from_storage` (по
   умолчанию `true`, как сейчас). С `false`: только уже подобранные, ещё не
   уложенные единицы; если их нет — `422 nothing_picked_to_pack` без движений.
   КИЗ (D1) → `200 {"kind": "marking", …}` со связью на этот короб.
6. `POST …/ship` пишет событие истории `shipped` с номером документа отгрузки для
   каждого привязанного кода (`GET /operations/marking-codes/codes/{id}/history`).
   `POST …/cancel` снимает связи (список п.2 пуст).
7. `PUT /operations/marketplace-unload-requests/{id}/pass` (multipart, поле `file`)
   → `200 {"filename", "content_type", "size"}`; `GET …/pass` → файл; доступно ФФ и
   селлеру этой отгрузки; отсутствие пропуска не мешает `ship`.
8. Веб: строки КИЗ — `data-testid="pick-kiz-row"` (подбор) и
   `data-testid="fbo-pack-kiz-row"` (упаковка); новая строка —
   `data-kiz-state="new"`; кнопка «Забрать целиком» —
   `data-testid="pick-source-take-whole"`; поле скана упаковки — внутри
   `data-testid="fbo-pack-scan"`; печать при скане — запрос в WMS Print
   `http://127.0.0.1:17843/print` с `idempotencyKey`; «Повторить печать» —
   кнопка с этим текстом внутри `fbo-pack-scan`; «Закрыть короб» — кнопка с этим
   текстом внутри `fbo-pack-scan`; «Убрать» в карточке короба —
   `data-testid="fbo-box-line-remove-{line_id}"`, пункты выбора — роль `menuitem`
   с текстом кода/«Без КИЗ» и места возврата.

Добавлено по замечаниям ведущего:

9. `POST …/boxes/{box_id}/scan`, КИЗ: если код уже привязан в этой отгрузке без
   короба (подбор) — получает этот короб, `already_linked=true` для связи, количество
   не меняется; если код в другом коробе отгрузки — `422 marking_code_other_box`;
   если в коробе нет непомеченной единицы товара кода — `422 marking_unit_not_in_box`;
   `product_id` в теле — товар последнего ШК (контекст единицы; GTIN другого товара
   → `422 marking_code_other_product`); без `product_id` — контекст проверки короба.
   `pick/scan`, КИЗ: нет непомеченной снятой единицы товара в текущем источнике —
   `422 marking_unit_not_in_source`.
10. `POST …/boxes/{box_id}/lines/{line_id}/remove` — существующий маршрут плюс
    необязательные `marking_code_id`, `return_to` `{"storage_location_id",
    "container_id"}` и `mutation_id`; убирает одну единицу (с этим кодом или без
    КИЗ); ответ содержит `returned_to` и `source_known` (`true` только для кода с
    источником подбора); для кода с неизвестным источником без `return_to` —
    `422 return_place_required`; `return_to` должен быть источником подбора этого
    товара в этой отгрузке, иначе `422 invalid_return_place`; без кода, когда все
    единицы строки с КИЗ, — `422 marking_unit_ambiguous`; повтор с тем же
    `mutation_id` не убирает вторую единицу. Разрешено в «Сборке» для открытых и
    закрытых коробов.
11. `POST …/boxes/{box_id}/print-marking` `{"product_id", "mutation_id"}` — один код
    из пула на единицу этого товара в коробе: `200 {"marking_code_id", "cis_code"}`,
    код связан с коробом; повтор с тем же `mutation_id` возвращает тот же код без
    второго списания из пула; `422 unit_may_be_marked` (R16б/R29г),
    `422 marking_pool_empty`.
12. `GET …/pick-options`: у источника-тары — `known_marking_codes` (коды «точно в
    таре») и `uncertain_marking_codes` (коды «возможно в таре»), R30; пустые
    списки, если известных нет.
14. `POST …/marking-codes/{marking_code_id}/return` `{"mutation_id"}` — атомарный
    возврат единицы с этим кодом из подбора (R9в): −1 из источника кода, единица в
    этот источник, код свободен и «точно в таре»; ответ `{"returned_to"}`; код без
    источника подбора — `422 return_place_required`; повтор с тем же ключом — без
    второго возврата. `DELETE …/marking-codes/{id}` (п.3) остаётся «Отвязать код»
    и состав тары не меняет.
13. Другая организация: `GET/DELETE …/marking-codes` чужой отгрузки → `404`.
