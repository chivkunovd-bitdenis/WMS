## 2. Существующий процесс и цель изменения

Термины: «приёмка» — движение товара от селлера на склад фулфилмента (ФФ); «россыпь» / «общая область» —
принятые штуки, не разложенные в тару; «тара» — короба и грузоместа документа приёмки; ТСД — Android-терминал
склада, который работает с теми же серверными ручками.

### 2.1. Что такое «документ ФФ» и «документ селлера» (проверено по коду)

Сервер уже различает автора документа полем `created_by_seller_id` в `backend/app/models/inbound_intake.py`:
при создании ручкой `POST /operations/inbound-intake-requests` (`backend/app/api/inbound_intake.py`,
`create_inbound_request`) оно заполняется только для роли `fulfillment_seller`, у сотрудника ФФ остаётся пустым.
Функция `is_ff_inbound(req)` в `backend/app/services/inbound_intake_service.py` считает документом ФФ обычную
приёмку (`operation_type = inbound`) с пустым `created_by_seller_id`. Поле `seller_id` при этом — владелец
товара, оно есть у обоих видов документов. Экран `FfInboundRequestView.tsx` использует тот же признак
(`ffInbound = operation_type === 'inbound' && created_by_seller_id == null`). Нового поля не нужно.

Статусы: `draft` («Черновик») → `submitted` («Передано на склад», только у документа селлера) → `receiving`
(«Приёмка») → `sorting` («В сортировке») → `done` («Оприходовано»). Документ ФФ по вебу идёт короче:
черновик ФФ наполняется и завершается кнопкой «Завершить приёмку» сразу в `sorting` (WMS-440);
в статус «Приёмка» документ ФФ попадает из сортировки кнопкой «Редактировать» (`reopen_receiving`)
или устаревшей ручкой `begin-receiving` (в вебе для ФФ-приёмки не используется).

### 2.2. Три области сканирования и как они ищут товар (проверено по коду)

| Область | Ручка | Где ищет штрихкод | Что требует от строки | Отказ, если товара нет в документе |
|---|---|---|---|---|
| Общая область, черновик ФФ | клиент сам ищет в каталоге селлера и шлёт `POST …/lines` (`product_id`, `expected_qty: 1`, `increment`) | весь каталог селлера на клиенте (`resolveProductIdByBarcode`) | строка создаётся сама | «Товар не найден в каталоге селлера. Добавление нового товара будет отдельной задачей.» |
| Общая область, статус «Приёмка» | `POST …/receiving/scan` → `scan_barcode_to_loose_intake` | только строки документа (`_request_barcode_index(include_seller_catalog=False)`) | нужна строка | 422 `product_not_on_request` → тост «Товар не найден в документе. Нажмите «Добавить товар» и выберите его из каталога селлера.» с кнопкой «Добавить товар» |
| Короб | `POST …/boxes/{box_id}/scan` → `scan_product_into_box` (`inbound_intake_box_service.py`) | только строки документа (`_barcode_index_for_request`; каталог читается только по товарам этих строк) | нужна строка **и** `expected_qty > 0` | 404 `barcode_unknown` (нет строки) или 422 `product_not_on_request` (строка есть, ожидаемое 0) |
| Грузоместо | `POST …/cargo-places/{place_id}/scan` → `scan_product` (`inbound_cargo_place_service.py`) | только строки документа | нужна строка (ожидаемое 0 допускается) | 404 `barcode_unknown` или 422 `product_not_on_request` |

Функция `_seller_catalog_barcode_index` (поиск по всему каталогу селлера) в сервисе есть, но нигде не
вызывается; код отказа `product_not_in_seller_catalog` есть в карте ошибок API и в тексте фронта, но сервер
его не выбрасывает. Ручка «Добавить товар» (`POST …/receiving/lines` → `add_or_increment_received_product`)
создаёт строку с `expected_qty = 0`, `actual_qty = n`, `added_by_fulfillment = true`.

### 2.3. Как считаются количества сегодня (проверено по коду и на стенде)

У строки документа три числа: `expected_qty` (план), `actual_qty` и `posted_qty` (уже разложено). Пока документ
в черновике / передан / в приёмке, `actual_qty` — это **только россыпь**; принятое по строке считает
`effective_actual_qty` = россыпь + сумма по коробам + сумма по грузоместам (`container_total_for_product`,
`inbound_intake_quantity_service.py`). API отдаёт это число полем `effective_actual_qty`, экран показывает его в
колонке «Принято» и суммирует в шапке «Принято: N». При завершении приёмки (`complete_receiving`) в
`actual_qty` записывается итог (россыпь + тара), и если итог ≠ `expected_qty` хотя бы у одной строки, документ
получает `has_discrepancy = true`; приход в зону сортировки делается по коробам, грузоместам и остатку россыпью —
ровно на это число, без удвоения. Список «Приёмка на FF» показывает «N ед.» как **сумму `expected_qty`**
(`goods_qty_total` в `list_inbound_requests`), а красным — `has_discrepancy`.

Документ ФФ по WMS-440 живёт по правилу «одно число»: в черновике `add_line` и `update_line_expected_qty`
держат `expected_qty` равным принятому итогу (`actual_qty = expected − тара`), а скан/правка тары через
`redistribute_ff_draft_container` сначала переносит уже учтённые штуки россыпи в тару и лишь потом увеличивает
итог; колонка «План» у документа ФФ скрыта, шапка показывает «Принято: N» без «из». Это подтверждено на стенде:
скан 2051083009112 в черновик → строка `expected 1 / actual 1`; два скана этого же товара в короб → в базе
`expected 2 / actual 0 / в коробе 2`, на экране «Принято: 2», в коробе 2; «Завершить приёмку» → `sorting`,
`has_discrepancy = false`, одно движение 2 шт. из короба.

Где «считаем по-разному» (воспроизведено на стенде 18.09.2026, документ №000001 арендатора «Империя ФФ
(стенд WMS-469)»):

- после «Редактировать» документ ФФ оказывается в статусе «Приёмка»; скан незнакомого документу FAD-BLACK-46
  даёт тост с кнопкой «Добавить товар»; после добавления через неё строка создаётся с `expected 0`, и та же
  строка на экране документа ФФ подсвечена красным с подписью «Излишек 1» — при том, что колонки «План» у ФФ нет;
- второй скан этого товара россыпью — «Излишек 2»; «Завершить приёмку» открывает окно «Есть расхождения,
  провести приёмку?» с таблицей «Ожидалось 0 / Принято 2 / Излишек 2»; после подтверждения в базе
  `has_discrepancy = true`, в списке «Приёмка на FF» строка «1 короб — 2 ед.» красным, хотя принято 4
  (`goods_qty_total` = Σ expected = 2, `sorting_remaining_qty` = 4). Три числа одного документа не сходятся;
- скан той же добавленной строки (ожидаемое 0) в короб отвечает 422 `product_not_on_request`, а диалог короба
  показывает «Товар не найден в документе. Нажмите «Добавить товар»…», хотя кнопки «Добавить товар» в диалоге
  нет — оператор ходит по кругу. То же в документе селлера: строка «Добавлено ФФ» не принимается в короб.

### 2.6. Цель изменения

Сотрудник ФФ в документе приёмки — своём или присланном селлером — сканирует штрихкод товара селлера туда,
куда кладёт вещь: в общую область, в короб или в грузоместо. Если такого товара в документе ещё нет, строка
появляется сама и штука засчитывается сразу, без кнопки «Добавить товар». Количества в документе, в диалоге тары,
в шапке, в списке приёмок и в сортировке сходятся: принято = россыпь + тара, а у документа ФФ нет никакого
«плана», с которым это число могло бы разойтись.

## 3. Требования

| ID | Условие, действие и наблюдаемый результат | Основание |
|---|---|---|
| R1 | Признак «документ ФФ» — существующее авторство: обычная приёмка, у которой `created_by_seller_id` пустой (создана сотрудником ФФ в вебе или на ТСД). Состав строк, наличие селлера в шапке и роль того, кто открыл документ, признак не меняют. Новое поле, статус или режим не вводятся. | «если создаёт ФФ — значит документ ФФ»; существующее `is_ff_inbound`; правило «не плоди сущностей». |
| R2 | Сотрудник ФФ с правом приёмки сканирует в **общую область** документа (черновик ФФ; статус «Приёмка» у документа ФФ и у документа селлера) штрихкод товара, которого в документе ещё нет строкой, но который есть в каталоге селлера документа. Результат без дополнительных действий: строка этого товара появляется в таблице «Состав» с «Принято 1», строка подсвечена как последняя отсканированная, шапка «Принято» увеличилась на 1; тост «Товар не найден в документе. Нажмите «Добавить товар»…» для такого товара не показывается. Повторный скан того же товара увеличивает «Принято» этой же строки на 1, вторая строка не создаётся. После обновления страницы результат тот же. | «принимать товар от селлера — что тот который есть в приёмке, что тот которого нет»; название задачи; боевой случай №000066; сегодняшнее поведение черновика ФФ (уже так). |
| R3 | То же для **короба и грузоместа**: в диалоге «Наполнить короб» / «Наполнить грузоместо» скан штрихкода товара из каталога селлера, которого в документе нет, сам создаёт строку документа и кладёт штуку в эту тару. Результат: в диалоге строка товара появляется сразу с «В коробе 1» и подсвечивается, в таблице документа — «Принято 1», в карточке короба/грузоместа под панелью «Короба и грузоместа» товар виден с количеством 1. Работает в черновике ФФ и в статусе «Приёмка» (документ ФФ после «Редактировать», документ селлера). Второй скан того же товара в ту же тару — «В коробе 2»; в другую тару — по 1 в каждой; россыпью после этого — плюс 1 к россыпи. Все три области дают одну и ту же строку документа. | «принимать сразу в коробки»; «наполнять её сканированием — что в общую область, что сразу в короба»; «другую тару» → грузоместа. |
| R4 | Распознавание штрихкода одинаково во всех трёх областях и делается на сервере: сначала по строкам документа (быстрый путь, каталог не читается — как сейчас с подсказкой `product_id`), при промахе — по каталогу селлера документа (артикул, основной ШК WB, все ШК WB, внешние ШК привязок площадок — тот же набор, что в `list_seller_wb_catalog_rows`). Клиентская карта штрихкодов остаётся ускорителем, а не источником отказа: если клиент не нашёл товар в своей карте, сервер всё равно ищет в каталоге. Черновик ФФ, где клиент сегодня ищет по каталогу сам, признаёт тот же набор штрихкодов, что и сервер. Если у документа нет селлера, скан незнакомого штрихкода отвечает отказом «не найден в каталоге селлера» (искать негде); веб при создании приёмки селлера выбирает всегда. | «по нашему флоу» — один процесс для всех областей; существующий тест «product_id fast path must not rebuild the WB catalog» и комментарий диалога о 15–20 с на скан при 300 строках; существующий индекс `_seller_catalog_barcode_index`. |

## 4. Решения аналитика и оставшиеся вопросы

Решения приняты по навыку принятия решения: развилки продукта разобраны по библиотеке случаев владельца
(хороший случай 1 — один физический остаток без второго счётчика; плохой случай 1 — действие в контексте своего
объекта; плохой случай 2 — самодельный запрет без основания) и по библиотеке сбоев (B05, B07). Экраны задачи
открыты и пройдены (раздел 2.5); эталон «Ячейки» (`/app/ff/warehouse-map`, экран «Карта склада») открыт на
стенде после прогона: сверху поле сканера с зелёной подписью «Сканер активен…», ниже таблица-дерево
«Содержимое / Селлер / Артикул…» с чипами («Пустое») и раскрытием короба до товаров — те же компоненты MUI
(таблица, чипы, Alert), что в таблице «Состав» и в диалоге тары. Задача новых элементов не добавляет; при
правке диалога (текст ошибки, подпись колонки, новая строка) разработчик сравнивает результат с этим экраном
и с текущим диалогом (R13).

**D1. Автодобавление действует и в документе селлера, а не только в документе ФФ.** Слова владельца
«принимать товар от селлера — что тот который есть в приёмке, что тот которого нет» относятся к товару,
который есть или нет строкой в документе; в документе селлера сегодня тот же результат даёт кнопка «Добавить
товар» (строка `expected 0`, «Добавлено ФФ», «Излишек»), и владелец 18.09 назвал лишний клик проблемой. Бизнес-
результат для селлера не меняется: план селлера не переписывается, добавленная строка остаётся отличимой в
таблице, в окне расхождений и в признаке `has_discrepancy` (R9). Вопрос владельцу не нужен: оба прочтения дают
одно и то же поведение для документа ФФ, а для документа селлера — тот же документ, что и сегодня, минус клик.

**D2. Ожидаемое количество строки документа ФФ равно принятому итогу (а не нулю с особыми случаями).**
Разобраны два варианта: (а) держать `expected_qty` = россыпь + тара, как уже делает WMS-440 в черновике, и
распространить это на статус «Приёмка» и на строки, добавленные сканом; (б) считать `expected_qty` у документа
ФФ неважным и учить каждую точку чтения (завершение, список, подписи строк, диалог тары, проверка короба, ТСД)
пропускать его для документов ФФ. Выбран (а): это уже принятая модель WMS-440 («число, которое внесли, — правда»),
её понимает ТСД, список и диалоги читают `expected_qty` без особых случаев, а единственный источник числа —
факт (россыпь + тара), `expected_qty` лишь его сохранённая копия, которая выравнивается при каждом изменении и
ещё раз при завершении. Ни нового поля, ни нового статуса. Устаревший путь `begin-receiving` для черновика ФФ
(сброс россыпи в «пересчёт с нуля», оставлен WMS-440 для старых клиентов) задача не трогает; R7 требует лишь,
чтобы завершение документа ФФ не рисовало расхождение по строкам, каким бы путём документ ни пришёл.

**D3. Правило «сначала перенос учтённых штук в тару» распространяется на документ ФФ в статусе «Приёмка».**
Слова владельца «скан в короба или другую тару наполняет общее кол-во приёмки» в его же случае — пустой документ
ФФ, вещи кладутся сразу в короба — означают ровно то, что делает R8: каждый скан в тару даёт +1 к итогу, потому
что россыпи у товара нет. Перенос касается только другого случая: сотрудник сначала внёс количество россыпью
(или отсканировал в общую область), а потом раскладывает те же вещи по коробам — тогда вещь одна, и второй раз её
считать нельзя (WMS-440 R11, хороший случай 1 — одна физическая единица не превращается в две). Сегодня перенос
действует только в черновике (`redistribute_ff_draft_container`); после «Редактировать» документ ФФ хранит ту же
россыпь, посчитанную самим ФФ, поэтому правило должно действовать и там. Для документа селлера правило не
переносится: там россыпь — факт приёмки, и каждый скан в тару остаётся новой штукой, как сейчас (перенос чужих
правил запрещён навыком принятия решения).

**D4. Ограничение «в короб только строку с ожидаемым > 0» снимается.** У него нет основания в словах владельца,
у грузомест его нет, а на стенде оно замыкает круг «Добавить товар → отказ → «Нажмите «Добавить товар»» (2.3).
По плохому случаю 2 запрет без точного требования удаляется, а не обходится.

**D5. Новых механизмов повтора не вводится.** Защита от повтора одного запроса уже есть (`mutation_id` +
`document_events`) у скана в короб/грузоместо и у всех запросов черновика ФФ; общий скан в статусе «Приёмка»
`mutation_id` не принимает, и веб его не повторяет автоматически (после ошибки оператор видит состояние и
сканирует осознанно — B07). Оставшийся риск вне задачи, который ведущему стоит знать: при потере ответа в статусе
«Приёмка» неосознанный повторный скан россыпью засчитает вторую штуку — это сегодняшнее поведение всех сканов
приёмки, задача его не ухудшает и не чинит; R12 требует, чтобы сохранённая штука была видна до повтора.

**D6. Тексты отказов не придумываются заново** — используются существующие «Товар не найден в каталоге
селлера…», «другой селлер», «неоднозначный штрихкод»; текст с кнопкой «Добавить товар» остаётся только для
ситуаций, где кнопка действительно нужна (товар не распознан по штрихкоду и оператор хочет выбрать его руками),
а для распознанного товара из каталога не показывается вовсе (R2, R5).

**Вопросов владельцу нет.** Неизвестных, от которых зависит бизнес-результат, после проверки кода, стенда и
боевого документа не осталось.
