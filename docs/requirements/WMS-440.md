## Существующий процесс и цель изменения

ФФ — сотрудник фулфилмента, ТСД — Android-приложение складского терминала. Предмет задачи — обычная приёмка товара от селлера на склад (`operation_type=inbound`).

По прочитанному коду веба сотрудник в `/app/ff/reception` нажимает «Создать приёмку», выбирает селлера. Склад берётся из выбранного склада, иначе первого доступного. Создаётся серверный черновик и открывается его карточка; товары добавляются из каталога селлера или сканом. Документ можно сохранить, закрыть и снова открыть. Веб также имеет отдельное создание возврата с выбором площадки; это соседний существующий процесс, а не основание строить в этой задаче новый процесс возвратов на ТСД.

Сервер уже отличает автора: `created_by_seller_id` назначается по авторизованной роли, у ФФ поле пустое; `seller_id` при этом обозначает владельца товара. Выбранный селлер сам по себе не делает документ селлерским. Новое поле происхождения не требуется.

Сейчас у обычной приёмки `add_line` пишет количество только в `expected_qty`, `actual_qty=None`; изменение количества также меняет только план. Поэтому ФФ после «Начать приёмку» должен вносить факт повторно. Для возврата WB/без площадки существует особая ветка: факт заполняется при добавлении, а `begin_receiving` завершает пересчёт автоматически. Эту ветку нельзя без анализа распространять по одному признаку площадки на обычную приёмку: новое правило относится к авторству.

В Android `InboundListScreen` показывает только `submitted` и статусы пересчёта; черновиков и действия создания нет. `Navigation.kt` открывает submitted через экран коробов, остальные — через `InboundReceivingScreen`. В последнем скан увеличивает факт, ручной ввод устанавливает абсолютное количество, после `complete-receiving` выполняется возврат к очереди. Используется тот же API, отдельного мобильного складского учёта нет.

Серверный путь: `draft → submitted` для селлера, `begin-receiving → receiving`, `complete-receiving → sorting`, размещение → `done`. Завершение пересчёта получает фактическое количество, приходует его в зону сортировки и сохраняет автора движения. Завершение размещения вызывает `_record_charge_if_done`: начисление услуги `inbound` по `posted_qty` и факт выполнения через `record_inbound_completion`. Нажатие «Создать» не должно сразу создавать остаток или начисление. Возврат к редактированию из sorting уже есть, он отменяет приход в зону сортировки до частичного размещения; это существующее техническое ограничение, которое задача не расширяет.

## Решения аналитика и оставшиеся вопросы

D1. Выбран короткий путь ФФ: создать черновик → заполнить фактический состав → явно завершить приёмку → существующая сортировка. Это убирает повторную работу, но сохраняет необходимый момент подтверждённого прихода. Само добавление товара в черновик ещё не приходует его. Разрешённые исправления не запрещаются: «не должен уже вносить» трактуется как отсутствие обязательного повторного ввода, а не запрет исправить ошибку.

D2. Использовать существующее серверное происхождение `created_by_seller_id`. Клиент не выбирает «считать план фактом» переключателем. Существующее техническое поле `expected_qty` можно оставить для совместимости в ФФ-черновике, но оно не становится второй независимой правдой. После начала физического процесса нельзя глобально подставлять план вместо отсутствующего факта.

D3. В ТСД расширяется текущая очередь приёмки доступными черновиками ФФ и вводится карточка создания/редактирования по привычным компонентам приложения. Селлерские неотправленные черновики не превращаются в складские заявки. Выбор/скан товара работает в контексте выбранного селлера. Отдельная мобильная сущность, назначение исполнителя через диспетчера, офлайн-очередь, новый журнал количеств и новые режимы не нужны.

D4. Предмет новой кнопки — обычная приёмка. Отдельный сценарий возврата с внешней площадки и его расширение на ТСД не добавлены к словам владельца. Обязательная регрессия существующих возвратов нужна, потому что общий сервис уже содержит особую обработку WB и Ozon. Если реализация затрагивает эту обработку, сохраняются её существующие явные бизнес-условия, внешние операции не выполняются в production ради теста.

Применён `wms-product-decision`: прочитаны owner-cases целиком. Использованы правило одного физического количества (хороший случай 1), сохранение контекста действия (плохой случай 1), отсутствие выдуманных блокировок (плохой случай 2). Границы фактического визуального осмотра зафиксированы выше; код не заменяет проверку заполненной карточки. Существенных вопросов о намерении владельца для этой постановки не осталось; недостаёт заполненных тестовых данных для сравнения самой карточки, базовые формы и Android-очередь уже осмотрены.

Разработчик проверяет реальный каталог для товаров обеих площадок, не принимает `wb` в историческом названии за разрешение скрыть Ozon-товар. Состав и семантику уже работающих ответов нужно сохранить для выпущенного APK 11; generated-клиент мобильного Git не является источником серверного контракта.

Веб: `frontend/src/App.tsx` (onCreateFfInboundDraft и открытие документа), `frontend/src/screens/ff/FfInboundQueuePage.tsx`, `FfInboundRequestView.tsx`, при необходимости общие helpers и селлерское отображение. Android (отдельный Git): `Navigation.kt`, `features/inbound/InboundListScreen.kt`, `InboundReceivingScreen.kt`, `InboundReceivingViewModel.kt`, `InboundUi.kt`, API-клиенты. Новые файлы формы/модели состояния вводит разработчик в этом разделе.

WMS-441 владеет сортировкой после `sorting`, списком размещения и автозавершением. Общий файл сервиса надо изменять последовательно или согласовать конкретные функции: WMS-440 не переписывает distribution/putaway и `_maybe_complete_request`. Совместный контрольный пример: ФФ ввёл A=3 → в зоне сортировки ровно 3 → WMS-441 размещает 3 → документ done, в остатке 3.

WMS-444 проверяет расчёты во всех мобильных операциях. WMS-440 не создаёт новую систему начислений; передаёт ему документ этого примера, автора, `source_type=inbound_intake`, код `inbound` и фактическое `posted_qty=3` для проверки в расчётах. Идентификацию/отображение ФИО не решает внутри этой карточки отдельным механизмом.

## Сверка с исходными словами

«Создание ... внутри ТСД ... с нуля» → R1/R2, C1/C2. «Так же ... в системе в точности» → тот же документ/каталог/складской путь R1/R2/R8/R10, C1/C4/C12. «И в основной приёмке ... и в ТСД» → R3/R4 и симметричные C3/C4. «Если ... ФФ ... не должен ... вносить фактические числа» → R3/R4, C1/C3/C4. «Селлер ... две правды» → R5, C5. «Число ... и есть ... правда» → R3/R6, C3/C8/C9. ## Заключение

Постановка подготовлена по исходному запросу и проверенному коду. Реализация, перекрёстное ревью и приёмка ещё не выполнены, задача не принята. На согласованном baseline-стенде осмотрены авторизованные пустые «Приёмка»/«Ячейки» и форма создания. До изменения карточки нужен осмотр заполненного документа; production открыт только до формы входа. После предъявления реализации этот же аналитик выполняет C1–C12 и дописывает заключение без подгонки требований под код.
