# ФБС: пять задач в редакции владельца, 31.08.2026

Переписано после разбора с владельцем. Заменяет формулировки T-14…T-18 из
`FBS_OWNER_TASKS_2026-08-31_RU.md` — там часть диагнозов оказалась неточной,
а часть решений сложнее, чем нужно.

## Принципы, из которых собраны задачи

Владелец сформулировал их прямо, и они важнее конкретных правок.

**Не заводить сущность там, где хватает записи факта.** Как только появляется
документ, на него налипают правила: нельзя закрыть, пока; нельзя перейти, если.
Каждое по отдельности осмысленно, вместе они останавливают работу. На строку в
таблице навесить нечего — упаковал, записали кто и сколько, пошли дальше.

**Ничего не должно блокировать друг друга.** Процесс линейный: подобрал,
упаковал, отгрузил. Взаимных ворот между этапами быть не должно.

**Не предсказывать.** Сколько упаковали — столько и записали. Заранее посчитанное
количество всегда устареет, потому что состав поставки меняется извне.

**Экран не отправляет человека назад против его воли.** Дошёл до упаковки —
открывается на упаковке. Вернуться назад самому можно и нужно: на подборе
меняется только ячейка, количество там уже не тронуть.

**Упаковка — экран печати кодов и отметка «сделано».** Не ворота.

## T-14 · Состав поставки меняется — задание обязано это проглотить

**Что на самом деле происходит.** Досинхронизация задания уже написана и работает
правильно: `_sync_existing_packaging_task_for_added_orders` в
`backend/app/services/fbs_supply_service.py:331` находит строку по товару и
**поднимает количество**, а новую строку заводит только для нового товара.

Но зовут её из одного места — из нашей кнопки «добавить заказы»
(`add_orders_to_existing_supply`, строка 1764). **Два других пути её обходят:**

1. привязка заказа при импорте — когда селлер добавил заказ в кабинете WB, и он
   приезжает уже с номером нашей поставки (`wb_marketplace_orders_service.py`,
   около строки 1666);
2. `repair_supply_composition_from_wb` (`fbs_supply_service.py:1312`) — тянет
   состав от WB и про задание не знает.

Поставка Чжоу `WB-GI-271834606` разъехалась (100 в задании против 199 в поставке)
именно по одному из этих двух путей — через нашу кнопку это невозможно.

**Что делать.**

| | |
|---|---|
| Позвать существующую досинхронизацию из обоих обходных путей | Ничего нового писать не надо, функция готова |
| Запретить привязку заказа к поставке, которая прошла подбор | И в нашей кнопке, и в импорте. Селлер может докинуть из кабинета, поэтому одной кнопкой не обойтись |
| Сказать вслух, когда отказали | Заказ, который не пустили в поставку, должен быть виден оператору с причиной, а не потеряться |

**Почему запрет после подбора обязателен, а не желателен.** Заказ, упавший после
подбора, никто не подбирал — привязки к ячейке нет, списывать неоткуда. Учёт
разъезжается.

**Как проверить:** довести поставку до подбора, добавить заказ из кабинета WB —
система должна отказать и показать причину. Добавить до подбора — задание должно
покрыть новые заказы само.

## T-15 · Экран перестаёт швырять оператора в начало

**Что происходит.** Этап нигде не хранится, он каждый раз вычисляется заново и
последним делом смотрит на статус поставки (`fbs_workspace_service.py:414`). Статус
отстал — человека отбрасывает на подбор. Молча: список претензий считается только
для поздних этапов, на подборе он пустой по построению. Круг замкнулся — статус
устарел, этап «подбор», претензий ноль, экран выглядит чистым.

**Что делать.**

| | |
|---|---|
| Хранить достигнутый этап | Дошёл до упаковки — открылся на упаковке, что бы ни думал статус |
| Назад не отправлять никогда | Вернуться самому можно, это нормально: на подборе меняется только ячейка |
| Задание закрыто по факту, а не по плану | Сейчас «сделано ≥ запланировано». Планировать нечего — состав приходит от WB |
| Начисление упаковщику — из факта | Сколько единиц записано за человеком, столько и оплачено. Сейчас сумма фиксируется один раз и при дополнении задания не пересчитывается |

**Как проверить:** довести поставку до готовности, оставив статус несинхронным —
экран должен остаться на достигнутом этапе, а не отправить на подбор.

## T-16 · Картинки едут вместе с лентой

**Что происходит.** Сервер отдаёт ленту одним запросом мгновенно, но кладёт в неё
только ссылки на QR-коды. Браузер потом идёт за каждой картинкой отдельно — 134
запроса подряд на поставке Loviana `WB-GI-271927501`. Экран замирает, выглядит как
зависший.

QR-коды — обычные PNG, **уже лежащие файлами на сервере**. Ничего не генерируется.

**Что делать.** Положить картинки в тот же ответ, которым сервер отдаёт ленту.
Один запрос вместо ста тридцати пяти. Никаких волн и параллельных загрузок в
браузере не требуется.

**Как проверить:** лента на 134 заказа собирается без видимой паузы.

| | |
|---|---|
| Перенести коммит на эталон | Ветка отходит от `85c64240`, брать сам коммит |
| Свести руками `fbs_packing_box_service.py` | С точки ветвления файл вырос на +81/−22, автоматом не ляжет |

## T-18 · Один ключ у селлера, товар привязан к ключу

**Что произошло.** 10.08 у ИП Горячкина заменили ключ WB. На следующий день загрузка
молча притянула 100 карточек чужого кабинета — лампочки и удобрения — и смешала с её
30 карточками очков и сумок. Заметили через три недели. 12.08 тот же кабинет завели
вторым именем у другого арендатора, с 25.08 по нему приехал 71 заказ под обоими.

**Механика.** `wildberries_import_cards_service.py` умеет **только добавлять**: там
есть `upsert_imported_cards` и `list_imported_cards_for_seller`, и всё. Ни сверки, ни
удаления, ни сравнения. Подмешивание чужого кабинета — единственное возможное
поведение, а не сбой.

**Что делать.**

| | |
|---|---|
| Запретить повторное использование ключа | При попытке завести уже используемый ключ — отказ с текстом «этот API-ключ уже используется» |
| Товары, не приходящие по текущему ключу, — **помечать** | Не удалять. У товара может быть остаток на полке, история движений, незакрытые заказы |
| Остатки по помеченным товарам показывать как есть | Склад цел, каталог понятен |

**Как проверить:** заменить ключ на кабинет с другим составом — старые товары
помечаются, остатки видны, ничего не пропадает.

## T-19 · Выкинуть заказ из поставки — заблокировано на стороне WB

Нужно на подборе и на упаковке: выяснили, что товара физически нет — убрать заказ и
работать дальше.

**Проверено по документации WB.** Метода «убрать одно сборочное задание из поставки»
нет. Есть: получить список поставок, создать, посмотреть, **удалить поставку целиком**,
передать в доставку, работа с грузоместами, получить список заданий, **добавить**
задания. Убрать одно — нельзя.

Возможный обходной путь: добавление задания в другую поставку, судя по всему, его
туда переносит — заказ не может лежать в двух поставках сразу. **По документации не
подтверждено.**

**Первый шаг:** проверить перенос на живом кабинете. Работает — делаем через перенос
в отдельную поставку. Не работает — задача закрывается как невозможная, и надо решать
на уровне процесса.
