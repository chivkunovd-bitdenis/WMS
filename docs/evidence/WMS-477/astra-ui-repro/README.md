# WMS-477 — Chrome reproduction of Astra findings 1, 2 and 4

21.09.2026, проверяемый продуктовый код:
`69b3f2ccc119e7a9ec67eeb629d4e96e69a6b414`.
Изолированная ветка `codex/wms477-astra-ui-repro`; release branch не менялась.

Использован настоящий установленный Google Chrome, headless, 1440 × 1000.
Оснастка импортирует настоящий `FfFbsSupplyWorkspace` и `ErrorBoundary` WMS-484;
продуктовые файлы не подменяются. Только ответы `window.fetch` создаются из
синтетических данных и удерживаются до явно заданного события. Часы Playwright
ускоряют ожидание, исполняя неизменённые продуктовые `setInterval`/`setTimeout`.
Ни production, ни backend, ни WB не вызывались. Это наблюдение React-компонента
в браузере, не только исполнение извлечённых функций в памяти.

## Запуск

Нужны Python с Playwright, установленный Chrome и frontend/node_modules проекта.
Из корня этого checkout:

```bash
python3 docs/evidence/WMS-477/astra-ui-repro/reproduce.py
```

Скрипт копирует оснастку в игнорируемый `frontend/tmp/wms477-astra-repro`, поднимает
свой Vite на `127.0.0.1:5577` с `--strictPort` и завершает только свой процесс.
Другой свободный порт: `WMS_QA_PORT=5578 python3 .../reproduce.py`.
Результат и скриншоты — `local/result.json` и `local/*.png` рядом со скриптом.
`baseline-result.json` сохраняет точные события и DOM-текст успешного
воспроизведения на исходном SHA. Все четыре `bug_reproduced=true`, pageerror — 0.
Скрипт намеренно проверяет наличие исходных дефектов; после исправления его
старые bug-assertions должны перестать выполняться.

## Дополнительная C23: WMS-484, клиентская ошибка и физическое изменение DOM

Запуск на том же продуктовом SHA:

```bash
python3 docs/evidence/WMS-477/astra-ui-repro/boundary.py
```

21.09.2026 выполнены три сценария в Google Chrome 153.0.0.0. Скрипт завершился
с кодом 0. `boundary-result.json` содержит фактическое состояние DOM до/после,
а также перехваченные сообщения `/client-errors`. `boundary-fallback.png`
осмотрен: видны панель изолированной оснастки, текст ошибки и кнопка «Обновить»;
страница не превращается в пустой экран или стандартную ошибку React Router.
Локальные повторные прогоны пишут в игнорируемый `local-boundary/`.

| Сценарий | Наблюдение и вердикт |
|---|---|
| Одно клиентское исключение внутри настоящего ErrorBoundary | Синтетический сосед FBS выбрасывает исключение в layout effect. Ошибка отправляется в mock client-errors с component=FfFbsSupplyWorkspace; после автоматической повторной отрисовки FBS доступен. Пройдено. |
| Три повторных исключения при попытках восстановления | После предусмотренных повторов появляется настоящий fallback с текстом «Не удалось показать этот раздел. Обновите страницу.» и кнопкой. Нажатие настоящей кнопки перезагружает страницу, FBS снова доступен. Пройдено. |
| Физическое удаление DOM-узла FBS | В Chrome удалён настоящий React-owned узел размера A1 через element.remove(). Следующий mock workspace убирает столбец размера. React пытается удалить уже отсутствующий узел и выбрасывает реальный NotFoundError/removeChild; методы DOM не подменялись. ErrorBoundary перехватывает ошибку, client-errors получает stack, FBS автоматически восстанавливается. Пройдено. |
| Опрос до ошибки и после возвращения к работе во всех трёх сценариях | Выбрана A1, скан стикера активирует её, оставлен фрагмент следующего скана 010460PARTIAL. После 15000 ms приходит новый accepted. Ввод, выделение checkbox, активная строка и фокус сохранены, вердикт обновлён. Пройдено. |

**Граница сохранения состояния:** само восстановление после исключения пересоздаёт
дочерний компонент. В двух сценариях автоматического восстановления наблюдались
пустой ввод, отсутствие выбранного checkbox и активной строки. Доказательство
сохранности относится к обычному 15-секундному опросу после повторного ввода и
выбора оператором, а не к переносу несохранённого ввода через падение или reload.
JSON сохраняет эти сбросы явно; проверка их не скрывает.

Искусственная ошибка вводится только в оснастке; физическое удаление выполняется
только в изолированном браузере с синтетическими данными. Полная оболочка портала,
историческая причина production-инцидента, расширения браузера и живой WB здесь
не проверялись. Проверены настоящий FBS-компонент, ErrorBoundary и клиентский
репортёр из SHA 69b3f2. Production не вызывался. Release branch не менялась.


## Проверка будущего исправления: --expect-fixed

Прежний запуск без аргументов остаётся baseline-режимом: код 0 означает, что
четыре исходных дефекта воспроизведены. Для проверки исправленного продукта
используется отдельный режим:

```bash
python3 docs/evidence/WMS-477/astra-ui-repro/reproduce.py --expect-fixed
```

Запускайте его из отдельного QA-worktree, основанного на проверяемом merged SHA,
куда перенесён каталог этой оснастки. Скрипт импортирует продуктовые компоненты
из `frontend/src` именно этого worktree, а не загружает опубликованный сайт.
Не запускайте старый QA checkout в качестве доказательства исправления нового SHA.
В `local-fixed/result.json` записываются HEAD запуска, режим, снимки всех четырёх
сценариев и список `failed_assertions`; скриншоты также лежат в `local-fixed/`.
SHA оснастки и SHA продукта следует указать в итоговом evidence отдельно, если
оснастка переносилась незакоммиченным изменением. Все данные локальные и синтетические.

Код 0 в режиме `--expect-fixed` требует одновременно:

- актуальный rejected остаётся после отпускания старого accepted POST;
- компонент с props B сохраняет строку B1 и её прежнее состояние после ответа A;
- после старого GET остаются order6, стикер с окончанием 0006 и размер L именно
  в строке добавленного заказа;
- первый успешный ответ с задержкой 16 секунд уже отображает accepted, последующие
  снимки сохраняют его, а журнал запросов показывает максимум один незавершённый GET.

Для первых трёх сценариев после отпускания ответа даётся 200 ms на обработку
Promise и отрисовку; все режимы используют один и тот же порядок mock API событий.
Последний сценарий считает незавершённые GET по парам request/response их ID,
а не только по итоговому цвету строки. Ошибка любой проверки даёт ненулевой код;
все четыре результата сохраняются, если установка сценариев прошла успешно.
Необработанные browser pageerror также приводят к ненулевому коду.

Проверка самого режима на неизменённом продукте 69b3f2: baseline завершился 0,
все четыре bug_reproduced=true; --expect-fixed завершился 1, перечислив все четыре
нарушения. В обоих прогонах page_errors пуст. Наблюдались два одновременно
незавершённых GET и неприменённый первый ответ. Краткий сохранённый результат —
`mode-validation.json`. Положительный прогон нового режима на исправленном
продукте ещё требуется после frontend-патча; эта проверка его не заменяет.

Этот недостающий прогон выполнен на `0e0406691c11545f215a344f6db6cdc98f65decb`:
`--expect-fixed` завершился 0, все четыре `expectation_met=true`, page_errors пуст.


## Три дефекта последнего ревью: supply_switch.py

Четыре сценария выше — исходные находки Astra. Последнее ревью нашло ещё три
дефекта, которых они не касаются, и на них заведена отдельная оснастка в том же
настоящем Chrome:

```bash
python3 docs/evidence/WMS-477/astra-ui-repro/supply_switch.py                     # требует исправленного поведения
python3 docs/evidence/WMS-477/astra-ui-repro/supply_switch.py --expect-vulnerable # требует исходных дефектов
```

Скрипт берёт `main.tsx` из этого же каталога и дописывает к нему три умения,
которых у общей оснастки не было: перехват запроса снятия требования Честного
знака, ответ ошибкой с признаком `retryable` и собственное задание упаковки
у каждой поставки, чтение которого можно сорвать. Последнее существенно: ошибка
чтения задания приходит мимо `run()`, и именно она в разборе Astra оставляла
оператору чужую кнопку «Повторить». Каждая правка оснастки проверяется assert'ом,
поэтому переименование в `main.tsx` обрушит запуск, а не тихо обесценит сценарий.
Свой Vite поднимается на `127.0.0.1:5579` (`WMS_QA_PORT` меняет порт), выдача —
в игнорируемом `local-switch/`.

| Сценарий | Последовательность в Chrome | Исходное поведение | После исправления |
| --- | --- | --- | --- |
| `saved_retry_does_not_survive_supply_switch` | В A ручная проверка отвечает ошибкой с повтором. Оператор уходит в B, где срывается чтение задания упаковки. Нажать «Повторить» рядом с ошибкой B | кнопка есть (`retry_beside_b_error=1`), нажатие отправляет операцию A (`sent_a_operation=true`), и на экране B появляется «Товар поставки A» | кнопки рядом с чужой ошибкой нет, текст ошибки B сохранён, строки остаются «Товар поставки B» |
| `lost_race_is_repaired_by_a_read_started_after_the_write` | Ручная проверка идёт; тик запускает тихое чтение, которое читает базу до записи и отвечает `pending`; затем приходит успешный `accepted` операции | `recovery_started=false`, строка навсегда остаётся «WB ещё не подтвердил ЧЗ» | свой снимок по-прежнему не применяется, но запускается новое чтение (запрос 3 в журнале), и строка доходит до «ЧЗ принят WB» |
| `skip_honest_sign_dialog_is_not_stuck_after_a_supply_switch` | В A подтверждено «Сдать без Честного знака», ответ задержан, оператор уходит в B, ответ A отпускается | `stuck_without_exit=true`: окно открыто, обе кнопки и закрытие отключены | окно закрыто, кнопка снова доступна, диалог открывается и закрывается обычным способом |

Второй режим получен подменой самого экрана на версию `c2371648` в рабочем дереве,
поэтому `head_sha` в отчёте одинаковый в обоих прогонах — что на самом деле
исполнялось, говорит `component_blob`: `dc555a0d` — экран до правки, `1610fb3d` —
исправленный. Оба прогона завершились 0 с пустым `page_errors`; сводка —
`supply-switch-validation.json`.
