# WMS-477 — Chrome reproduction of Astra findings 1, 2 and 4

21.09.2026, проверяемый продуктовый код:
`69b3f2ccc119e7a9ec67eeb629d4e96e69a6b414`.
Изолированная ветка `codex/wms477-astra-ui-repro`; release branch не менялась.

Использован настоящий установленный Google Chrome, headless, 1440 × 1000.
Оснастка импортирует настоящий `FfFbsSupplyWorkspace` и `ErrorBoundary` WMS-484;
продуктовые файлы не подменяются. Только ответы `window.fetch` создаются из
синтетических данных и удерживаются до явно заданного события. Часы Playwright
ускоряют ожидание, исполняя неизменённые продуктовые `setInterval`/`setTimeout`.
Ни production, ни backend, ни WB не вызывались. Это наблюдение React-компонента
в браузере, не только исполнение извлечённых функций в памяти.

## Запуск

Нужны Python с Playwright, установленный Chrome и frontend/node_modules проекта.
Из корня этого checkout:

```bash
python3 docs/evidence/WMS-477/astra-ui-repro/reproduce.py
```

Скрипт копирует оснастку в игнорируемый `frontend/tmp/wms477-astra-repro`, поднимает
свой Vite на `127.0.0.1:5577` с `--strictPort` и завершает только свой процесс.
Другой свободный порт: `WMS_QA_PORT=5578 python3 .../reproduce.py`.
Результат и скриншоты — `local/result.json` и `local/*.png` рядом со скриптом.
`baseline-result.json` сохраняет точные события и DOM-текст успешного
воспроизведения на исходном SHA. Все четыре `bug_reproduced=true`, pageerror — 0.
Скрипт намеренно проверяет наличие исходных дефектов; после исправления его
старые bug-assertions должны перестать выполняться.

## Подтверждённые результаты и проверки исправления

| Проверка | Последовательность в Chrome и исходный результат | Ожидание после исправления |
|---|---|---|
| Finding 1a · старый ручной ответ | Нажата настоящая кнопка «Проверить в WB», POST удержан. Через 15 с авто-GET вернул rejected: экран показал «WB не принял ЧЗ». После отпускания старого POST с accepted строка стала зелёной «ЧЗ принят WB». | Последний актуальный rejected сохраняется; старый ручной ответ не откатывает вердикт. Допустима свежая проверка после операции, но не принятие старого снимка. |
| Finding 1b · другая поставка | Начат POST A; тестовый host передал тому же компоненту props B без remount, воспроизводя изменение открытой поставки. На экране появилась B. Поздний POST A вернул экран и строку A, хотя `requested: B` остался. Сам переход полного React Router/history здесь не тестировался. | Остаются заголовок B, строка B1 и её состояние; ответ/ошибка/notice/retry/finally от A не меняют B. |
| Finding 2 · GET до добавления | Удержан старый авто-GET. Через реальные «Состав → Добавить заказы» добавлен order6: на упаковке видны строка, стикер 0006 и размер L. Отпущен старый GET: order6 и размер исчезли, осталась A1. | После подтверждённого add сохраняются order6, стикер 0006, размер L; чтения, начатые до мутации, не откатывают состав. |
| Finding 4 · 16 с при polling 15 с | Каждый mock GET успешно вернул accepted ровно через 16000 ms. Реальный интервал компонента запустил запросы с шагом 15000 ms. Три последовательных успешных ответа проигнорированы: строка осталась «WB ещё не подтвердил ЧЗ». | Первый успешный ответ обновляет строку; длительный запрос не порождает бесконечное отбрасывание всех ответов. При single-flight не более одного GET в работе. |

Скрин `local/manual_cross_supply.png` осмотрен: верхняя панель оснастки показывает
`requested: B`, продуктовый заголовок — «Поставка A», зелёная строка — «Товар поставки A».
Другие события подтверждены DOM-текстом и журналом порядка запросов/ответов.
Finding 3 (старый auth 401) по поручению ведущего не дублировался.

Это доказательства дефектов и воспроизводимая оснастка, а не продуктовое исправление,
не приёмка релиза и не установление причины прежнего production DOM-инцидента.
