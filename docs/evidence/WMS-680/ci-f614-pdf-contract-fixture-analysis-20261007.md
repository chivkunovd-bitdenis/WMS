# WMS-680: разбор двух сбоев PDF-контракта в CI f614

Проверен полный Linux-лог `frontend-f614.log` для коммита
`f61468b0c`. Два падения `wms680PrintGeometry.test.ts` не показывают
отсутствие продуктовых данных или нарушение согласованной раскладки.

Первое падение относилось к FBO: старый тест искал
`PACKAGING-LONG-NAME-01-680` в строке XML после удаления пробелов. В реальном
`pdftotext -bbox-layout` Chrome записал два слова одной ячейки: сначала
`PACKAGING-LONG-NAME-01-`, затем `680`; XML-теги между ними не удаляются
функцией `compact`. Поэтому это была ошибка парсера теста, а не усечение
названия в PDF.

Второе падение (`ENOTEMPTY` в `profile/Default`) возникло после готового PDF:
тест отправлял Chrome `SIGTERM` и сразу удалял его собственный временный
профиль. В CI дочерний процесс ещё создавал файл профиля. Исправленный fixture
ждёт завершения запущенного им Chrome (с контролируемым `SIGKILL` только после
таймаута) и удаляет только каталог `mkdtemp` этого запуска, с короткой повторной
попыткой для файловой гонки.

Контрактный commit: `4ed0c391135c95b67879c954195034b9c43d4980`.
Он заменяет XML-поиск на сбор последовательных PDF-слов с одинаковой левой
границей и неубывающей вертикальной координатой. Полное имя должно быть в одной
физической ячейке и закончиться до заголовка «Артикул»; остаются проверки
порядка колонок, границ страниц, полного текста, строк подбора, количеств и
компактности числовой колонки.

всех шести шаблонов. Канарейка использует полученные PDF-слова и подтверждает,
что после удаления последнего фрагмента имя перестаёт находиться целиком.
