# WMS-501 — оперативная проверка общего торможения 21.09.2026

Исходный вопрос владельца: «у нас прямо сейчас пиздец долго работает система почему?» Уточнение: «вообще всё в том числе печать у виталик хорс». Проверка выполнялась только чтением установленного production хоста194.87.96.144; никаких перезапусков, очистки диска, настройки лимитов или изменений данных не было. Это оперативное дополнение к аудиту, а не исправление или новая приёмка продукта.

PSI full означает долю времени, когда все активные задачи одновременно простаивали по соответствующему ресурсу; avg10 — сглаженный10секундный показатель. Это реальное наблюдение давления памяти, а не вывод только из занятого swap. Само заполнение диска не доказывает причину каждой задержки, но свободный запас крайне мал.

**У WMS и другого проекта wb-finance общий сервер без отдельных hard memory limits у проверенных обработчиков.** Большой RSS принадлежит главному процессу Celery wb-finance, а не WMS и не его трём дочерним рабочим процессам. Дочерние процессы в повторном снимке занимали примерно3/15/3MB. Перезапуск WMS поэтому не устраняет основной обнаруженный соседний объём памяти.

[Срез логов соседнего обработчика](live-incident-neighbor-worker.txt) и [повтор с distinctID](live-incident-final-snapshot.txt): в ограниченной выборке последних4000строк обнаружены **1999различных wb_orchestrator_tick received за3.505секунды,18:12:38.354–18:12:41.859UTC**. Это сильный кандидат на источник дополнительного давления вблизи инцидента. Однако причины всплеска, размер внутреннего расписания Celery и причинная доля этого всплеска в расходе RAM не установлены; это не доказанный memory leak. LLEN/HLEN соседнего Redis вернули NOAUTH, счётчики очереди не получены; для диагностики общего давления этого доступа не потребовалось.

Повторный [SQL и результат](live-incident-db.txt) также дал blocked_sessions0,12idle и1idle-in-transaction0.004s. Исторические deadlocks7/tempfiles206/tempbytes1795956736 не выросли относительно предыдущего аудита. Это не подтверждает гипотезу, что сейчас одна зависшая транзакция блокирует всю WMS; короткие срезы не исключают ранее завершившихся медленных запросов.

Локальный HTTP `/api/health` через web дал200 за137мс в18:20:56 и200 за160мс в18:22. Health не равен скорости каталогов/PDF и не проверяет сеть пользователя.

[Ограниченный журнал API](live-incident-print-logs.txt), последние20мин/2000строк: order-print-tape200×1, content готовых print-assets200×10, label-artifact200×10, applied200×10. За30минут background_jobs с типом print не найдены; веб-печать может идти синхронным путём без такой записи. Название «Хорс/Hors» по ограниченному поиску в имени tenant/seller не сопоставилось с организацией. Следовательно, конкретная пользовательская сессия/задание Виталика пока не идентифицированы: общий инцидент подтверждён, отдельная причина его принтера не установлена.

## Вывод

Наиболее убедительная подтверждённая причина общего замедления в наблюдавшийся момент — общий дефицит RAM и ожидание диска на хосте. Существенный потребитель — соседний wb-finance worker с~1.35GiB; одновременно обнаружен массовый приём его задач. Ошибка этого обработчика как первопричина ещё требует разбора. Доказательств текущей общей DB-блокировки нет. Связь с конкретной печатью не завершена.

Оперативное восстановление следует направить на ресурсный запас всего хоста и соседнюю очередь, учитывая выполняющиеся задания. Долговременные меры — изоляция ресурсов двух проектов, устранение причины массового накопления задач и контролируемый запас RAM/диска. Рестарты, удаление файлов и изменение другого проекта этим диагностическим вопросом не выполнялись.
