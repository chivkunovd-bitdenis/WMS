Проверка дополнения WMS-501 закончена. Ниже — вердикт качества доказательств, ссылки на источники и границы моей собственной сверки.

## Вердикт по качеству дополнения

Дополнение (`production-audit.md`, `socket-load-audit.md`, `mobile-audit.md`, `isolation-completion.md`, `browser-completion.md`) — читаю как честный, воспроизводимый read-only аудит. Ложных cross-tenant утверждений, замалчивания провалов и «мгновенности всех сканов» я не нашёл. Границы (macOS-хост, одноразовые БД, closed-loop, single-process API, аппаратный ТСД не подключён, production не нагружали) явно проговорены. Все крупные числа подтверждаются исходниками, SQL-агрегатами и сохранёнными JSON. Продукт при этом действительно не меняли: правки только в документах постановки/отчётов, `AGENTS.md`/`CLAUDE.md` и новые файлы в `docs/evidence/WMS-501/`.

Приёмку это дополнение не заменяет — новая приёмка аналитиком по правилам конвейера ещё не завершена. Это ожидаемо, не дефект.

## Что я перепроверил на месте

- **Source fingerprint deployed vs baseline.** `docs/evidence/WMS-501/production-source-fingerprint.json` показывает три одинаковых SHA256 для 284 Python-файлов бэкенда локально, в контейнере `wms_prod-api-1` и в `wms_prod-celery_worker-1`. Утверждение `production-audit.md:5–7` про совпадение файлов с baseline `3e125074` формально соответствует именно диску контейнеров; оговорка «уже загруженная память процессов этим хешем не проверяется» стоит на месте.
- **DB timeouts: defaults vs local SET LOCAL.** В `production-metadata.sql` действительно стоит `SET LOCAL statement_timeout='5s'` и `SET LOCAL lock_timeout='1s'` до самого `SELECT ... pg_settings`, поэтому `production-metadata.txt` показывает 5000/1000. `production-timeout-defaults.txt` отдельно даёт `statement_timeout=0`, `lock_timeout=0`, `idle_in_transaction_session_timeout=0` (source=default). В `production-audit.md:21` этот подводный камень прямо разъяснён — «Значения 5000/1000 в metadata относятся только к защитным SET LOCAL самого аудита». Ошибки нет.
- **Footprint PDF с корректным pool-фильтром.** В `backend/app/services/marking_code_service.py:1248–1264` `_code_filter_for_product` возвращает `pool_id IN pool_ids AND (product_id IS NULL OR product_id = product.id)`, если у товара есть пулы, иначе `product_id = product.id`. Внешний `list_product_codes` (1537–1572) добавляет `tenant_id`/`seller_id`/`source='pool'`. SQL в `production-marking-list-aggregate.sql` этот же фильтр эмулирует UNION'ом (первый — по пулам, второй — прямые коды без записи в `marking_pool_products`), поэтому агрегат «71 товарный список, 646 кодов, 130 601 301 B = 124.55 MiB в самом тяжёлом» получен правильно. `production-audit.md:30–33` явно оговаривает, что 552 MiB из `production-pdf-groups.txt` — это сумма кодов с `product_id IS NULL`, разложенная по пулам и товарам, а не один товар с 527 MiB PDF. `label_artifact_pdf` в модели (`backend/app/models/marking_code.py:262`) действительно нe deferred, поэтому `select(MarkingCode).scalars().all()` затянет бинарные данные в память — риск памяти воспроизведён по коду, HTTP на бой не отправляли.
- **Память и OOM.** `production-memory-queue.txt` фиксирует total 3886 MiB, available 285 MiB, swap used 1153 MiB, PSI memory `avg10/60/300 = 0`. `production-resource-snapshot.txt` даёт OOM=false, restarts=0 у API/DB/worker и правильно оговаривает, что первая строка `vmstat` — статистика с запуска. `production-audit.md:15–16` не делает из этого «сервер уже упал»: «запас памяти небольшой, но текущая непрерывная нехватка памяти/активный swap storm не доказаны». Формулировка соответствует источнику.
- **Socket-load contract.** `socket-load-probe.py` действительно использует один локальный uvicorn (127.0.0.1:18452), реальный PG `wms501_load2`, closed-loop coroutine workers, 200 мс think time; hosts: «Native macOS hardware; not a production capacity certification». `socket-load-results.json` для `multi100` даёт `scan_write` p50 629.6 / p95 1537.0 / p99 2118.94 мс — совпадает с REPORT «p95 1.537 с при 100 операторов». `socket-load-readback.py` считает сумму `InboundIntakeLine.actual_qty` по 130 seed'нутым документам: 4356 успешных `receiving/scan` POST = 4356 в сумме БД, `supplement` +314 → +314. Оговорка про «aggregate quantity equality only; no per-attempt idempotency contract or per-document event matching» стоит явно в JSON и в тексте.
- **Большой документ.** `socket-load-readback.py` добавляет 499 доп. строк в один документ и запускает 25 воркеров под одним JWT в режиме `barcode_only=True` (без подсказки `product_id`). Результат `scan_write` p95 1180.6 мс — воспроизводится. Признак «13 разных FFadmin, но операторы — coroutine workers, а не аккаунты» указан в шапке отчёта; не подменяется утверждением про 100 живых людей.
- **Mobile 70 тестов.** `mobile-junit-summary.txt` даёт 18 классов, 63 сущуствующих + 7 новых из `MobileAuditReproTest` = 70 tests, 0 failures/errors. `mobile-repro-results.txt` печатает результат каждого repro-теста человеческим языком (например `wedgeSingleEightyMillisecondGapEmitsTruncatedBarcode → 4630452635503 with one 80ms gap → 0452635503`). `mobile-audit.md` не выдаёт JVM-репро за device-приёмку: «Один новый тест использует настоящий Retrofit/OkHttp HTTP на localhost MockWebServer; остальные — реальные компоненты с управляемым расписанием корутин и подменённым API. Это не измерение Android UI, production DB или сети склада». Формулировка соответствует протоколу.
- **Tenant vs seller и 93/226.** ISO-01 подтверждён в коде: `backend/app/services/seller_shop_service.py:42–47` привязывает `uses_home_seller_scope` к точному `Tenant.slug == "avpack-9uczh"`; `backend/app/api/background_jobs.py:225–280` вызывает seller-проверку только внутри этой ветки, для всех прочих tenants путь падает в `return _job_out(job)`. ISO-02 — `backend/app/api/inventory_movements.py:44–72` действительно берёт только `get_current_user` и `seller_line_product_scope`, без `assert_inventory_read_access` (в `/summary` он есть, `:113`). По цифрам: `isolation-completion-root-results.json` содержит ровно 59 case-элементов, `isolation-completion-nested-results.json` — 34, `isolation-completion-controls-results.json` — 12; итого 59+34 = 93 отрицательных HTTP-сценария. `isolation-completion-production-summary.json`: `check_count=226`, `nonempty_relationships=155`, `mismatched_relationships=0` — совпадает со сводкой отчёта. Дополнение честно отмечает, что 226 включают 214 одноколоночных FK + 12 цепочек «документ→строка→продукт/локация» и что NULL FK в inner join не участвуют, поэтому это не сертификат безопасности всех связей.
- **Rate-limiter reset (замечание Z4 из ревью).** `docs/evidence/WMS-501/scan_api_probe.py:39` действительно вызывает `reset_rate_limit_state()` перед смешанным опытом, но сама функция в `backend/app/services/login_rate_limit.py:95–98` только очищает `_attempts`. Route `POST /auth/login` (`backend/app/api/auth.py:267–289`) в живой цепочке всё равно проходит через `check_login_rate_limit(request=request, email=…)`. Пять реальных 401 при пустом окне — не обход. Отклонение Z4 в `review-resolution.md` обосновано.
- **Browser-completion (файл есть).** `browser-completion.md` присутствует; scenarios B1–B6 сверены со `browser-state-after-close-queue.json` (actual_qty=1 после закрытия очереди с задержанным POST), `browser-state-after-outbound-failure.json` (после DELETE+503-POST строка ушла из БД), `browser-http-relevant.json` (реальные POST-события с идентификаторами и статусами). Уточнение по сортировке — «в текущем `/app/ff/sorting` открыт `SortingObjectsScreen`, а не `FfInboundSortingPanel`; старый `distribution-scan` не выдаётся за браузерный вывод» — читается как правильная поправка охвата, а не расширение позитивного утверждения.

## Что я бы попросил уточнить в тексте (нитпики, не блокеры)

- В `production-audit.md:9` фраза «В API один процесс uvicorn» опирается на один снимок `docker top`/`ps`; стоит добавить «в проверенный момент», потому что worker preload/multiple procfile-инстансы теоретически возможны — сейчас без хеджа это чуть жёстче, чем источник.
- Там же — «Runtime-пул SQLAlchemy действительно 5 постоянных + 10 дополнительных соединений» опирается на `production-pool.json`, где значения совпадают с SQLAlchemy defaults для `create_async_engine(..., pool_pre_ping=True)` (см. `backend/app/db/session.py:14`). Это надёжно как statement про код, но JSON не помечен как чтение engine.pool именно на бою. Стоит пометить: «читаем attributes engine, созданного из того же кода, что верифицирован fingerprint'ом; отдельного HTTP-запроса на бой не выполняли».
- В сводке REPORT есть строка «226 проверенных типах фактических связей production несовпадений tenant 0». Формулировка формально верна, но без ссылки на `isolation-completion.md` абзац про NULL FK/polymorphic/составные FK/произвольные seller-комбинации внутри одного tenant. В теле report'а это уточнение есть; сводке достаточно короткой отсылки.
- В `socket-load-audit.md` таблица p50/p95 корректная, но при чтении быстро проглядывается, что `multi100` throughput (97.91 rps) уже ниже `multi50` (103.8 rps). В тексте это отражено «throughput перестал расти относительно 50». Просто отмечу: замер это по существу point-of-saturation, а не потолок вместимости — так и написано.
- В `mobile-audit.md` из 63 «existing» тестов часть лежит в тех же файлах, что новый `MobileAuditReproTest`; при этом только 7 из 70 — новые. Стоит явно связать «Один новый тест использует настоящий Retrofit/OkHttp HTTP» с конкретным именем `delayedHttp401FromAInvalidatesNewSessionB` (в `mobile-repro-results.txt:38–41` он и есть), чтобы читателю не пришлось ловить это из общего текста.
