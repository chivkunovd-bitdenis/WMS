Baseline: `3e125074d5cb4c38e9107f864c3075f4f1f224cd`, свежий origin/etalon на начало 21.09.2026. Это аудит исходного кода и выделенного локального PostgreSQL, не измерение production. Ни тариф сервера, ни число работающих API/worker процессов, ни размер production БД, ни deployment SHA в этой работе не проверялись.

- `api_performance_probe.py` — настоящая авторизация JWT и настоящий PostgreSQL, HTTP через ASGITransport в одном процессе. Нет сетевого соединения, reverse proxy, браузерного рендера, физического сканера и внешних API. В нём 10 tenants, 19 000 товаров: 10 000 у первого, по 1 000 у остальных. Никаких реальных ключей, клиентов или данных.
- Это короткие диагностические опыты, не sustained load / soak test. Значения применимы к этой машине, этому запуску и искусственному набору. Конкурирующая активность других локальных задач могла влиять на время.

## Подтверждённые узкие места

### BE-01 · P1 · синхронный bcrypt останавливает обработку других coroutine в API

`backend/app/api/auth.py:268` → `services/auth_service.py:91–116` → `services/passwords.py:5–16`. Async обработчик прямо вызывает CPU-затратную синхронную проверку пароля; регистрации и установка паролей используют такой же hash. В `backend/Dockerfile:21` и `backend/Dockerfile.railway:18` команда запуска не задаёт несколько workers. Фактическое число процессов production неизвестно.

В опыте heartbeat, который должен получать управление каждые 5 мс, при пяти одновременных реальных вызовах login с несуществующим синтетическим пользователем не выполнялся **1208,84 мс**; пять отказов заняли 1211,74 мс. Один login дал максимальную паузу 245,17 мс. Речь не только о медленном входе: в том же процессе задерживаются другие запросы, в том числе сканирование. В опыте обойдён route rate limiter (вызван реальный service); это не доказательство, что пять попыток всегда проходят route limiter. По коду успешные и in-flight проверки разных клиентов используют тот же event loop.

Дополнительный опыт через **настоящие HTTP route/auth guards** подтвердил влияние именно на поиск скана: `scan_api_probe.py` в том же ASGI процессе вызывает `/operations/scan/resolve` и пять `/auth/login`. На синтетическом tenant с 10 000 товаров 50 последовательных поисков имели p50 8,34 мс / p95 9,29 мс / max 10,09 мс; одиночный запрос выполнял 12 SQL. 20 одновременных поисков завершились за 69–94 мс. Тот же поиск параллельно с пятью допустимыми по форме попытками входа занял **1234,45 мс**, перед серией `reset_rate_limit_state()` очищает состояние ограничителя для нового изолированного опыта, **не отключает и не обходит** сам route limiter (пять разрешённых попыток для пустого окна); все пять login действительно вернули 401 после проверки пароля (не 422/429). Результат — `scan-api-results.json`. Это только поиск товара по коду, без записи количества/DOM/сети; не время полного физического скана и не норматив нагрузки. Первый пробный запуск имел невалидный email и вернул 422; он не использован как свидетельство блокировки, в окончательном скрипте добавлен assert 401.

Направление исправления: вынести password hashing/checking в ограниченный thread executor, сохранив выравнивание времени ошибок и действующий rate limit. Не снижать криптографическую сложность ради скорости. Замерить одновременно login + scan на реальном API после исправления.

### BE-02 · P2 · полные каталоги на старте сессии

`api/products.py:641–665` и `:772–785` возвращают полные списки, у `/products` нет параметра limit. `services/catalog_service.py:574–635` поддерживает limit, но этот маршрут его не передаёт. Полный FF каталог дополнительно обогащается данными маркетплейсов/маркировки. Реальный вызов этих маршрутов при входе подтверждён фронтовым аудитом FE-01; существующая `/products/ff-catalog-page` проблему глобального preload сама по себе не снимает.

На 10 000 искусственных товаров, после прогрева:

| Действие | HTTP | Время API в процессе | JSON, байты |
|---|---:|---:|---:|
| `/products` | 200 | 254,79 мс | 6 468 891 |
| `/products/ff-catalog` | 200 | 527,25 мс | 7 608 891 |
| `/products/ff-catalog-page?limit=100` | 200 | 14,78 мс | 75 974 |
| `/auth/me` | 200 | 2,63 мс | 830 |

Два полных каталога дают суммарно **14 077 782 байта JSON до HTTP-сжатия**, ещё до учёта прочих стартовых запросов. Нельзя складывать время двух параллельных запросов в пользовательское время входа. Пять одновременных `/products` под одним аккаунтом завершились с 200 за 460–1381 мс; пять страниц по 100 — за 46–49 мс. При десяти tenants параллельно все ответы были 200, время 49–557 мс. Это не предел вместимости, но воспроизводимый источник избыточной работы.

Направление исправления: убрать ненужный глобальный preload, загружать нужные экрану страницы/результаты поиска, не вводя запрет на обработку больших каталогов. Сохранить возможность законного сканирования товара вне загруженной страницы.

### BE-03 · P1 при реальной насыщенности · очередь подключения к БД общая для всех клиентов процесса

`backend/app/db/session.py:15` задаёт только `pool_pre_ping=True`; действующие в проверенном runtime значения: 5 постоянных соединений + 10 дополнительных, ожидание свободного соединения до 30 с. Это **15 одновременных подключений одного engine**, а не лимит 15 клиентов: короткие запросы многократно переиспользуют соединения. У каждого API процесса и Celery дочернего процесса свой engine; суммарный бюджет соединений нельзя увеличивать без проверки `max_connections` PostgreSQL.

Когда 15 соединений удерживались полсекунды в контролируемом опыте, простой `SELECT 1` завершился за **507,55 мс**. При запросе с искусственной серверной задержкой 50 мс медиана/максимум составили: 15 запросов — 68/72 мс, 30 — 86/115 мс, 60 — 140/229 мс. Это проверка механизма очереди, не бизнес-нагрузочный тест.

Сессия запроса открыта до выхода из dependency; после первого SQL транзакция может держать соединение до commit/rollback/close. Сетевые ожидания внутри такой транзакции, длительные выборки и скачивания усиливают влияние одного tenant на остальных. Автоматических per-tenant квот/отдельных пулов в просмотренной конфигурации нет; это отсутствие изоляции ресурсов, **не утечка данных**.

Направление исправления: измерить время ожидания пула и возраст транзакций, затем сократить удержание подключений; только после этого согласовать пул с числом процессов и бюджетом БД. Не назначать произвольные большие значения.

### BE-04 · P2 · последовательная синхронизация всех клиентов и общий backoff площадки

`services/fbs_autopoll_service.py:586–629`, `:711+`, `:806+`: перебор всех пар seller/marketplace последовательный. Медленный клиент задерживает клиентов после него. Интервалы по умолчанию: orders 180 с, statuses 600 с, stock reconciliation 300 с (`core/settings.py:306+`; реальные env неизвестны). `wildberries_client.py` содержит вызовы с timeout 60 с. При росте числа клиентов полный цикл может превысить интервал расписания. Это кодовый риск, длительность production циклов не измерена.

`marketplace_provider.py:66–82` и `_MARKETPLACE_BACKOFF` в autopoll используют ключ площадки (`wb`/`ozon`), без tenant/seller. Ошибка 429 одного кабинета может временно пропустить следующие кабинеты той же площадки в этом процессе. Backoff process-local: разные Celery процессы имеют разные состояния. Контекст лимита провайдера (на весь сервис, IP или конкретный кабинет) нужно установить по соответствующим ответам/контракту прежде, чем менять ключ. Не объявляется безусловным багом внешнего лимита.

`celery_app.py` не задаёт отдельных очередей, time limits, prefetch и fairness по tenant; production compose запускает worker без явного concurrency. Длительные импорты и периодические задачи могут конкурировать за одни worker slots. Existing per-seller advisory locks предотвращают часть одновременной работы, но не являются планировщиком справедливой очереди; некоторые операции используют отдельное подключение под lock (`marketplace_seller_lock_service.py:96+`).

Направление: замерять возраст задачи в очереди и длительность цикла по tenant/marketplace; делать ограниченную параллельность и разделение классов работ после подтверждения лимитов. Нельзя просто параллелить всё или удалять блокировки.

### BE-05 · P2 · нужны планы запросов на реальной структуре данных

Фильтры tenant имеются, но наличие фильтра не делает любой SQL дешёвым. Поиск каталога использует `ILIKE '%...%'`, OR по нескольким полям и приведение JSON баркодов к строке (`catalog_service.py:607–630`). Отдельный B-tree по tenant/артикулу не гарантирует быстрый поиск подстроки. Конкретные дорогие планы, селективность, bloat, статистика и индексы production не проверялись; **предложение добавить индекс без EXPLAIN не выносится как готовое исправление**.

В локальном наборе list_products на 10 000 строк без limit занял 162,68 мс, из них heartbeat не получал управление до 122,84 мс при материализации ORM. При limit=50 запрос занял 4,90 мс. Поиск редкого значения на этом наборе занял 9–12 мс. Это подтверждает цену объёма выдачи, а не доказывает медленный индексный план.

## Что нужно для численного ответа «сколько клиентов выдержит»

На безопасном стенде той же конфигурации зафиксировать API/web/worker SHA, число процессов, CPU/RAM/IO, max_connections, размеры таблиц и индексы. Подготовить обезличенные объёмы small/medium/large tenant; смесь клиентов с большими и малыми каталогами. Измерить 1/10/25/50/100 одновременных операторов как **сценарии испытаний, не заявленную вместимость**. Отдельно 1/5/10 устройств с одним аккаунтом и с разными аккаунтами. В нагрузке сочетать сканирование, вход, стартовые каталоги, отчёты и фоновые синхронизации; ступень выдерживать достаточно долго для полного фонового цикла и прогрева.

Собирать p50/p95/p99 каждого маршрута, event-loop lag, pool wait/checked-out, DB query time/locks, CPU/RAM/IO, длину/возраст очереди, число HTTP ошибок, **сколько сканов принято/сохранено/потеряно/повторено**. Сравнивать счётчики с durable read-back после перезагрузки. В браузере измерять отдельно scan→видимое принятие и scan→durable save; на физическом ТСД — отдельно устройство/декодер/сеть. Искусственную успешную индикацию до надёжного сохранения нельзя выдавать за мгновенность.

Численную цель задержки владелец пока не задал. Можно предложить ориентир реакции UI до 100 мс, но это **предложение для согласования**, не принятое требование и не текущий результат. Требование отсутствия потери/дублирования корректных действий уже следует из рабочего процесса.
