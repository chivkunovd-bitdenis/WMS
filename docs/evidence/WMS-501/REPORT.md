# WMS-501 · Аудит скорости, сканирования и изоляции клиентов

Дата: 21.09.2026, обновлено после продолжения аудита по прямому уточнению владельца. Проверенный продуктовый срез: `3e125074d5cb4c38e9107f864c3075f4f1f224cd` (origin/etalon на начало работы). Ветка аудита: `codex/wms501-performance-isolation-audit`. [Постановка и приёмка](../../requirements/WMS-501.md).

## Вывод для владельца

В системе есть конкретные места, где рост числа работающих людей создаёт лишнюю нагрузку, и воспроизведённые сценарии потери изменений при работе с одним документом. Прежние ускорения сканирования сохранились, но не охватывают все экраны. Считать сейчас все сканирования мгновенными нельзя.

Между разными фулфилментами доступ в выполненных отрицательных проверках блокируется. Но это не доказательство отсутствия всех утечек: обнаружено раскрытие данных фоновых заданий другого селлера **внутри одного фулфилмента** и обход отдельных прав сотрудника. Защита фоновых заданий из WMS-488 применяется только к конкретному tenant AVpack, а не ко всем организациям.

Дополнение завершило мобильные тесты, шесть браузерных сценариев, отрицательные проверки вложенных ID, read-only обследование production и смешанную нагрузку через настоящие HTTP-соединения. В production-снимке один API-процесс; файлы API и фонового обработчика совпали с284проверенными Python-файлами baseline. На13синтетических организациях/27 275товарах задержка95%записей скана выросла с~200мс при25операторах до1.537с при100. Все4356успешных увеличений подтверждены суммой в БД. Это локальная диагностическая нагрузка, **не установленная вместимость production**. Продукт, данные и настройки production не менялись. По требованию владельца удалено правило остановки из-за обнаружения пароля: в глобальном AGENTS и синхронно в проектных AGENTS/CLAUDE; значения секретов не публикуются.

Рекомендации — направления последующих задач, здесь они не реализованы. Сохранение сканирования товара вне загруженной страницы — условие, которое будущий аналитик должен связать с конкретными действующими сценариями. Идентичность повторной попытки следует по возможности опереть на существующие механизмы draft mutation_id; новая таблица или журнал автоматически не требуются. Межвкладочный риск восстановления FE-05 и отсутствие серверной идентичности попытки S4 разбираются отдельно.

Приоритеты — оценка аудиторов для планирования исправлений; они не означают, что исправления уже сделаны. Точные условия и ограничения доказательств находятся в тематических отчётах ниже. Нет основания отключать всем сотрудникам параллельную работу или вводить новые бизнес-запреты.

## Ответы на вопросы

**Будет ли база тормозить при большом числе клиентов?** Риск реален, но причина не в самом факте мультитенантности. Сейчас API делает лишние полные выдачи, использует общий для процесса пул и обслуживает CPU-задачи в основном потоке; фоновые циклы проходят клиентов последовательно. На локальном наборе 10 tenants/19 000 товаров все диагностические запросы прошли, но это короткий опыт без внешних площадок и сетевой задержки. В продолжении измерены production настройки и короткие CPU/память/очередь снимки, реальные размеры и один план поиска; см. production report. На сервере3CPU/3.8GiBRAM, available285MiB; текущий активный swap не выявлен. Полные каталоги, синхронный password hash и большие PDF-выборки конкурируют с рабочими операциями. Предельное число клиентов из этих коротких опытов вывести нельзя.

**Несколько сотрудников под одной учёткой.** Сам логин не создаёт отдельной глобальной очереди SQL. В тесте 20 одновременных увеличений количества от одного пользователя сохранили 20 штук. Однако операции с абсолютным значением или полным снимком документа могут затирать работу второго устройства. Общая учётка также объединяет запись автора действия; в одном browser origin вкладки делят localStorage, а на разных устройствах — нет. Раздельные логины улучшат атрибуцию, но сами по себе не исправят потерю обновления одного документа.

**Сканирование.** Очереди и частичное обновление уже есть в отдельных сценариях приёмки/коробов, а FBS-оптимизация списка 500 заказов присутствует. В части обработчиков ввод отключается на время сети. При этом браузер уточнил охват: текущая сортировка использует SortingObjectsScreen, и два размещения объектов с задержанным первым ответом успешно перекрылись; старый FfInboundSortingPanel нельзя считать доказательством блокировки нынешнего экрана. Видимое принятие скана, готовность принять следующий и подтверждённая запись в БД — разные измерения. Нельзя показывать фиктивный успех, чтобы визуально скрыть ожидание. Браузером воспроизведены конкретные ошибки очереди, отказа и неизвестного исхода; HTTP p50/p95/p99 измерены отдельно. Mobile JVM-тесты выявили дополнительные потери. Физическая задержка ТСД/камеры и browser-p95 от аппаратного сканера до отображения не измерены.

**Изоляция данных.** Уровни tenant, seller и разрешения сотрудника проверялись отдельно. HTTP/JWT проверки подтверждают ряд защит и два конкретных нарушения внутри tenant. Проверка 401 без токена говорит об обязательности входа, а не о корректности всех вложенных ID. Отсутствие автоматического DB/RLS-фильтра — дополнительная зависимость от точности прикладных guards; само по себе это не HTTP-уязвимость. Дополнение добавило93отрицательных HTTP-сценария с чужими документами/вложеннымиID, положительные контроли и матрицу414методов. В226проверенных типах фактических связей production несовпаденийtenant0 ([ограничения FK-проверки](isolation-completion.md#фактическая-сверка-production-только-чтение): NULL, JSON/polymorphic и произвольные seller-связи этим не покрыты). Нельзя делать вывод «другие фулфилменты точно никогда ничего не увидят» по ограниченным тестам; конкретные дефекты внутри tenant остаются открытыми.

## Как закрывать оставшиеся вопросы

Сначала исправить конкретные обходы доступа и потерю обновлений с отдельными требованиями и regression tests. Затем убрать доказанные общие источники нагрузки — стартовые полные каталоги и блокировку event loop. При исправлениях расширять уже выполненные шесть браузерных сценариев по карте каждого рабочего экрана: быстрая серия одинаковых/разных кодов, медленный ответ, отказ, потеря ответа после записи, закрытие/смена документа, два устройства; после каждого сценария сверить итог в БД и после перезагрузки.

Для окончательного ответа о вместимости развить выполненный socket-load опыт: безопасный стенд с зафиксированным SHA/конфигурацией и размерами данных, ступени 1/10/25/50/100 операторов, фоновые задачи, метрики p50/p95/p99, pool/DB/CPU/queue и нулевой потери/дублирования сканов. Эти числа — сетка испытаний, не обещание вместимости. Числовой норматив «мгновенно» ещё предстоит выбрать; можно предложить реакцию UI до 100 мс, отдельно от надёжного сохранения.
