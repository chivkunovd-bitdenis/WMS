# WMS-501. Сканирование и несколько сотрудников одного аккаунта

> Первичный этап. Ограничения охвата и уровня доказательств ниже уточнены продолжением от21.09.2026: [mobile](mobile-audit.md) и [browser](browser-completion.md). Актуальный сводный вывод — [REPORT](REPORT.md). Старое правило остановки из-за обнаружения пароля отменено.

Аудит исходников baseline `3e125074` и изолированные проверки выполнены 21.09.2026 в постоянном worktree `.worktrees/wms501-performance-isolation-audit`. Продуктовый код не изменялся. Постановка: `docs/requirements/WMS-501.md`, R3–R5, часть R1/R7. Это технические доказательства для общего отчёта, а не приёмка физических сканеров или production.

Главный вывод: прежние исправления существуют, но общая гарантия «любой экран принимает следующий скан немедленно» отсутствует. Приёмка и добавление товара в короб используют последовательные очереди; сортировка, подбор, упаковка, КИЗ и каталог мест по-прежнему выключают ввод на время запросов. Очередь сохраняет порядок, но сама по себе не гарантирует сохранность хвоста при закрытии экрана. Один логин не создаёт общего серверного mutex (замка на пользователя), однако сотрудники сталкиваются на одном документе, могут перезаписать устаревшее количество и будут записаны в историю одним и тем же человеком.

## Находки и подтверждённые сценарии

### S1. P1 — устаревший ручной факт стирает уже сохранённый скан

**Воспроизведено через HTTP на PostgreSQL.** На двух устройствах одного user открыт один документ с фактом 5. A сканирует товар: `POST .../receiving/scan` возвращает факт 6. B отправляет ранее открытое абсолютное значение: `PATCH .../lines/{id}/actual {actual_qty:5}`. Сервер отвечает 200 с фактом 5, без проверки исходной версии. `api/inbound_intake.py:1638`, `inbound_intake_service.py:1554–1580`: row lock защищает транзакцию, но не проверяет устарелость намерения клиента. Тест `test_stale_absolute_quantity_overwrites_committed_scan` в `scanning-repros.py`; лог — 5→6→5. Источник ожидания одинакового/разного login здесь не существенен: конфликт по одному документу, а не по имени пользователя. Рекомендация: отдельная версия/expected value для абсолютной правки либо атомарная дельта для скана; не запрещать совместную работу целиком.

### S2. P1 — последний снимок распределения стирает работу другого сотрудника

**Воспроизведено сервисом на PostgreSQL.** A и B открыли пустую незавершённую раскладку. A сохраняет товар в ячейку A, затем B сохраняет собственный снимок с ячейкой B. После второго вызова строки A нет. `inbound_intake_service.replace_distribution_lines:2412` загружает lock документа, затем удаляет все не проведённые строки, отсутствующие в новом снимке; expected version не принимает. Уже проведённые строки сохраняются — их потерю тест не утверждает. API семейство `PUT .../distribution-lines` используется web и описано в истории mobile, однако mobile-код в этом аудите не проверялся. Рекомендация: проверка версии снимка или отдельные операции изменения строк.

### S3. P1 — очередь приняла сканы, но закрытие экрана может отбросить её хвост

**Подтверждено ветвлением кода, browser-runtime не выполнен.** Приёмка: `FfInboundRequestView.tsx:533–538` меняет scanDocument на cleanup, `:1721` игнорирует задание старого документа, `:2171` закрывает без ожидания receivingScanQueue; операция завершения приёмки `:1976` очередь ждёт, обычное закрытие — нет. MP-короб: `FfMarketplaceUnloadBoxAddDialog.tsx:346` ставит `scanOpen=false`, увеличивает session и закрывает; queued `runScan:425–427` возвращается для старой session, `enqueueScan:595–599` не сохраняет задание вне памяти. Условие: API первого скана медленный, в очередь уже вошли B/C, оператор закрыл окно до окончания первого. B/C не отправятся; первый мог сохраниться, а обновление parent зависит от флага, который ещё не успел выставиться. В inbound box `handleDismiss:344–353` уже реализован drain: использовать как проверенный по исходнику образец, не объявляя перенос исправленным.

### S4. P1 — неоднозначный исход обычного receiving scan при обрыве ответа

**Свойство API воспроизведено; обрыв сети/поведение оператора моделируется, не измерялось.** Две доставки одного HTTP payload `receiving/scan` дают 1→2 даже с одинаковым произвольным `Idempotency-Key`. Это **не нарушение заявленного контракта заголовка**: модель `InboundReceivingScanBody` его не поддерживает, а UI его не посылает. `FfInboundRequestView.tsx:1733–1740` отправляет barcode/product_id, при исключении `:1771` показывает ошибку, не имеет receipt-запроса или автоматического retry. Если первый POST commit произошёл, а ответ потерян, ручной повтор скана неотличим от второй физической штуки. Новый физический скан действительно должен дать +1, и дедупликация по самому barcode была бы ошибкой. Рекомендация: UUID физического события с повтором **того же UUID для повторной доставки**, отдельно от нового физического скана; показывать неизвестный исход/проверку результата. Аналогичный кодовый риск имеется в недрафтовом box scan, packaging scan и shared FBS pick UI (API FBS поддерживает ключ, но клиент его не посылает).

### S5. P1 — часть обработчиков прекращает приём на время сети/провайдера

**Уточнение продолжения:** `FfInboundSortingPanel` не является текущим экраном `/app/ff/sorting`; там используется `SortingObjectsScreen`. Браузерный B5 подтвердил перекрытие двух размещений объектов без потери второго. Упоминание старой сортировки ниже относится к legacy-обработчику, а достижимость каждого такого обработчика требуется проверять отдельно. См. [browser-completion](browser-completion.md).

**Подтверждено кодом**, частота реальных пропусков не измерена. Сортировка `FfInboundSortingPanel.tsx:801,989`, подбор `UnloadPickScreen.tsx:569` + `FfUnloadPickPage.tsx:451,506`, упаковка `FfPackagingPage.tsx:852`, FBS КИЗ `FfFbsSupplyWorkspace.tsx:2282`, reprint `KizReprintDialog.tsx:122`, каталог мест `FfCatalogInboundPackages` используют busy/disabled без очереди. Поэтому «следующий скан через 100 мс» зависит от завершения предыдущего запроса; сигнал аппаратного сканера не доказывает, что приложение приняло ввод. КИЗ ждёт validate + commit/marketplace + reload. Рекомендация: сначала единый честный контракт принятия и pending/ошибки; затем локальное подтверждение принятия и очередь с сохранностью, не оптимистичное сообщение «сохранено».

### S6. P1 — скан существующего товара в draft отгрузки использует DELETE + POST

**Кодовый дефект атомарности, отказ между HTTP не воспроизводился.** `FfSuppliesShipmentsPage.tsx:2005–2018` сначала удаляет строку, затем создаёт её с `existing.quantity+1`. Если DELETE успешен, а POST отказал/не дошёл, строка уже удалена; интерфейс показывает ошибку, восстановительного единого action/receipt здесь нет. Если два устройства загрузили одинаковый исходный quantity, вычисление +1 сделано по устаревшему снимку. Дополнительно это минимум две записи и два перечитывания (`:2024–2025`) на один скан. Рекомендация: одна атомарная серверная операция increment для строки документа с идентичностью попытки.

### S7. P2 — локальное «+1» инвентаризации не равно сохранению; повтор/восстановление зависит от потока

`FfInventoryPage.tsx:325` прямо сохраняет факт обычных сканов только по Save либо перед находкой. Найденные новые позиции проходят отдельную serial queue с scanId и retry (наиболее полная защита среди просмотренных потоков), но queue и parked хранятся в памяти (`foundQueue.ts:60–63`). После исчерпания пяти попыток элемент удаляется из очереди и выдаётся onRejected (`:91–95`), не сохраняется для последующего ручного resume. По коду важно различать «человек видит число», «попытка ожидает», «есть commit». Потеря вкладки с несохранённым локальным фактом — ожидаемый риск контракта, не утверждение о повреждении БД. Сам `save_actuals` проверяет expected_comment, но абсолютным quantities не передаётся expected value (`inventory_count_service.py:486–535`); общий login не устраняет last-writer-wins одного счётного ряда.

### S8. P2 — разный ввод сохраняет старые причины видимого зависания

Uncontrolled ScannerField и global hook исправляют известных виновников (потерю символов при тяжёлом render, русскую раскладку, отсутствие фокуса, Tab). Но FfCatalogInboundPackages, FfInboundSortingPanel, FfPackagingPage, FBS КИЗ остаются на controlled value и Enter/form-submit. Для них нельзя автоматически утверждать перенос общего исправления. Некоторые сканеры с Tab и без суффикса не получают единое поведение. Поле ScannerField само честно поддерживает таймер 900 мс, но плашка `active={listening || busy}` отображает активность и при disabled — человеческий сигнал может противоречить фактической готовности. Обрыв/потеря символов на конкретном устройстве здесь не воспроизведены; нужен browser/device тест.

## Общий логин: что доказано

`auth_service.login:90–115` создаёт JWT (подписанный токен); `services/tokens.py:12–32` не содержит session/device id и не хранит один «активный токен пользователя». `api/deps.py:98–136` проверяет JWT и заново читает user/tenant, не блокирует пользователя на время работы. Поэтому второй вход сам по себе не образует очередь всех действий первого. На disposable PostgreSQL **20 одновременных HTTP receiving scans с одним bearer/user сохранили ровно 20**; тест включает реальные guards/маршрут/commit. Он подтверждает этот сценарий, не максимальную нагрузку и не остальные операции.

Сканирование одного inbound документа сериализуется `get_request_for_receiving_scan:650–668` на строке документа, даже если сотрудники сканируют разные товары. Это защищает создание строки WMS-473 и потерю increments, но объединяет пропускную способность на один lock. Разные документы не делят этот конкретный lock, хотя используют общий DB pool/CPU/IO. Для распределения, упаковки, остатков действуют свои locks; их ожидание зависит от данных, не от совпадения login.

История/оплата: request actor связан с user.id (`api/deps.py:134–136`), упаковка передаёт acting_user_id (`api/packaging_tasks.py:571–576`), billing группирует по completed/fulfilled user (`staff_packaging_billing_service.py:135–167`). Разные сотрудники под одним логином неразличимы в этих данных. Это предсказуемая граница учётной модели, не изолированная неисправность скорости.

Две вкладки одного браузера делят localStorage. `hooks/useAuth.ts:155–157,275–293` уже синхронизирует смену сессии между вкладками (WMS-488). `inboundDraftPersistence.ts:15–24` ключует pending draft по server+tenant+sub+document; два устройства хранят отдельные pending, две вкладки — общий ключ. `active` Set `:13,55` существует только внутри одного JS-модуля и не является межвкладочным lock. Это область обязательной проверки interleaving/recovery, а не доказанная утечка tenant. В `pendingPlacement.ts:10` ключ также связан с endpoint+user+document.

## Следующие обязательные замеры

На тестовом браузере и реальном сканере измерить T0 — suffix/полный код, T1 — видимое принятие, T2 — HTTP start, T3 — commit-confirmed response, T4 — результат render. Отдельно измерить глубину очереди и пропуски. Для каждого активного ряда реестра: 1/2/5/10 сканов в секунду, 50/500/5000 строк, два разных документа и один общий документ, одинаковый SKU как две штуки, retry того же события, искусственный RTT 50/300/1500 мс, lost response после commit, Enter/Tab/без suffix/русская раскладка/GS, закрытие во время очереди, смена сессии. Эти числа — предложенная матрица испытаний, не разрешённая production нагрузка и не утверждённая SLA. Для FBS отделить local accepted/durable от marketplace accepted, для печати — от физического выхода этикетки.

Неисполненное явно: физический scanner/TSD/camera; browser dropped-character и close-queue repro; multi-tab renderer race; network loss injection; полномасштабный concurrent-user benchmark; mobile после остановки. Точный аудит не может назвать эти поверхности проверенными лишь потому, что backend unit tests зелёные.
