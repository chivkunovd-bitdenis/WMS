## Подтверждённый механизм всплеска

**Всплеск `received` означает повторную доставку уже существующих отложенных задач из Redis. Это не 1999 новых вызовов Wildberries и не 1999 задач, впервые созданных beat в эту секунду.** Число1999 было ограничено первоначальным хвостом журнала. Полное окно 18:10–18:16 UTC содержит 4788 `wb_orchestrator_tick received`, ни одного `succeeded` для tick. Внутри 18:12:30–18:13:00 —3758 receipts с3758 уникальными ID. Каждой строке соответствует предупреждение `QoS: Disabled: prefetch_count exceeds 65535`.

Ограниченный хвост80000строк покрывает16:27:17–18:30:00 UTC:39987 receipts,19104 различных taskID, **все19104 ID повторяются**, максимум3 доставки одного ID. Один из примеров без публикации ID:16:27:17.189710→17:27:47.285402→18:29:24.488550. Ещё четыре независимо проверенных ID имеют практически те же интервалы. В этом хвосте не было lifecycle markers `Connected to`, `ready.`, `Connection to broker lost`, `Restoring`, `consumer:`. Отсутствие сообщения само по себе не доказывает отсутствия любого reconnect; повторные ID, период около часа и брокерные заголовки подтверждают конкретный redelivery механизм.

В18:38:57 UTC штатное подключение Celery к Redis использовано только для LLEN/HLEN/ZCARD и трёх HSCAN COUNT200. `celery` list=0, `unacked` hash=19104, `unacked_index`=19104. Выборка602 сообщений: все `wb_orchestrator_tick`, все `delivery_info.redelivered=True`, все `retries=0`, все имеют будущий ETA19:15:04–19:19:24 UTC (заголовки22:15–22:19 +03:00). Первые аргументы относятся всего к двум различным пользователям; идентификаторы не сохранены. `origin` принадлежит трём дочерним процессам worker: gen8=198, gen9=203, gen10=201 в этой выборке. Размер всей очереди нельзя оценивать только по LLEN=0: задачи уже зарезервированы и ожидают в памяти.

Фактически установлены Celery5.6.3 и Kombu5.6.2. Прочитан исходник внутри рабочего контейнера:

- `/usr/local/lib/python3.12/site-packages/celery/worker/strategy.py:198–200`: будущий ETA увеличивает QoS-счётчик и помещает request в timer через `call_at`, не передавая сразу на исполнение.
- `celery/worker/consumer/consumer.py:578–582`: по наступлении ETA request передаётся на исполнение, счётчик уменьшается.
- `kombu/transport/redis.py:410–423,644`: `restore_visible` выбирает unacked старше `visibility_timeout`, затем возвращает их в очередь. Значение по умолчанию3600с, override в конфигурации отсутствует.
- `kombu/common.py:441–449`: при счётчике выше65535 выводится наблюдаемое предупреждение и callback получает prefetch_count=0. Это не отменяет уже удерживаемые requests в памяти.

Конфигурация прочитана выборочно через уже установленный Celery app, без вывода broker URL: worker_prefetch_multiplier=4, worker_concurrency=None (автоматический выбор), task_acks_late=False, worker_eta_task_limit=None. Команда compose — `celery -A celery_app.celery worker --loglevel=info`, явных concurrency/max-memory/max-tasks ограничений нет. Это чтение текущей конфигурации новым Python-процессом контейнера, не инспекция timer heap в памяти работающего worker.

Причинная цепочка подтверждена совокупностью: длительные ETA удерживаются без завершения → часовой срок видимости Redis истекает → те же ID возвращаются → consumer повторно принимает их и увеличивает ETA/QoS накопление. Эта повторная доставка непосредственно объясняет наблюдаемые burst-строки. Она согласуется с большим RSS worker и давлением памяти всего хоста, но точный объём RAM, занятый именно копиями ETA, без heap-профиля не измерен.

## Кто создаёт будущие tick и что ещё неизвестно

Прочитан production `backend/celery_app/tasks.py`:

- `wb_orchestrator_kick:927–957` обновляет intents и ставит tick при idle/истёкшем cooldown/устаревшем running. Проверка и изменение состояния не используют compare-and-set или row lock в этой функции.
- `wb_orchestrator_tick:1105–1111` ограничивает только недавно установленный `running` (30с).
- Если cooldown ещё действует, `1115–1121` **каждый исполненный tick создаёт новый tick с оставшимся countdown**; отдельного уникального ключа уже ожидающей ETA здесь нет.
- `1262–1267` ставит ETA до ближайшего окна blocked operation. `1276–1307` на retryable HTTP-коды сохраняет block/cooldown и создаёт новый `apply_async`, а не Celery `retry` (поэтому header retries=0 не исключает прикладное перепланирование).
- Рабочие шаги ставят продолжение с20с. `ORCH_RUNNING_STALE_WAKE_SEC=300с`.
- `archive_backfill_manager` выбирает ограниченный batch пользователей и отправляет `kick`, а не тысячи tick напрямую. В конкретном окне beat отправил один manager; он завершился за0.0457с. Текущий beat schedule не содержит прямого `wb_orchestrator_tick`.
- `app/routers/dashboard.py:267–270` может отправлять прямой tick при pending funnel_tail и статусе idle/scheduled. Это ещё один вход; принадлежность исходного накопления именно dashboard по имеющимся логам не установлена.

**Механизм размножения исходных сообщений также подтверждён.** Полный read-only HSCAN всех19104 сообщений в18:42:36 UTC дал6 цепочек root_id; размеры цепочек —18945,155,1,1,1,1. У всех сообщений retries=0, redelivered=True; отсутствующих root/parent/ETA нет. Они созданы1811 различными parentID. Распределение числа детей одного parent:354 родителя имеют13 детей каждый,1185 имеют12,270 имеют1, один имеет10, один имеет2. Текущий tick в каждой завершающей ветке ставит максимум один следующий tick; множество разных children с одним parent доказывает повторное исполнение этого parent с созданием новых ID, а не только повторный receive одного неизменного сообщения. [Полная агрегированная lineage](live-incident-wb-lineage.json), [воспроизводитель](live-incident-wb-lineage-probe.py).

Дополнительное чтение сохранённых результатов всех1811 parentID нашло1811 SUCCESS. У1810 последний result.message=`cooldown`, у одного —`already_running`. Последний результат перезаписывает предыдущие исполнения того же taskID; `already_running` одной последней копии не отменяет наличие ранее созданных детей.1808 родителей имеют задержку не менее часа, большинство около43123–43220 секунд, то есть почти12 часов; два имеют задержку менее часа, у одного нет delay_sec.1807 последних завершений пришлись на07:xx UTC, ещё4 —10:xx UTC, до старта нынешнего worker в10:05. [Результаты родителей](live-incident-wb-result-parents.json), [результаты корней и задержки](live-incident-wb-roots.json).

Полный доступный журнал текущего контейнера (297599 строк,10:05–18:40 UTC) не содержит завершений этих1811 родителей или6 корней. Это согласуется с сохранёнными date_done: размножение случилось до текущего контейнера, а его нынешние bursts — повторная доставка уже накопленного результата. [Корреляция журнала](live-incident-wb-parent-correlation.json) явно сохраняет нулевое число найденных parent-successes, а не подменяет отсутствие исходных логов предположением.

Причина цепочки теперь установлена: **длинный cooldown около12 часов помещён в Celery ETA при Redis visibility_timeout1час → один ID повторно резервируется и остаётся несколькими ожидающими экземплярами в worker → при исполнении cooldown-ветка каждого экземпляра создаёт новую задачу → один parent даёт12–13 новых ID → новая партия снова ждёт много часов и повторно доставляется каждый час.** Защита `running <30с` не защищает ветку `cooldown`; в ней отсутствует уникальность уже запланированного продолжения. Установленный код позволяет это поведение, а parent/child граф и retained results подтверждают фактическое размножение.

Начальный триггер **двух больших корней** остаётся отдельной исторической неизвестной: их result metadata уже не сохранены; текущие container logs начинаются позднее. У четырёх малых roots metadata есть, но ими нельзя объяснить большие цепочки. В частности, нельзя достоверно назвать конкретного пользователя, первоначальный dashboard запрос или исходный HTTP429, создавший самые ранние корни. Неизвестность первого trigger не отменяет доказанного механизма размножения. В коде `_retry_http_delay_with_headers:621–634` допускается длительный Retry-After с jitter; наличие именно соответствующего исходного ответа WB для больших корней не восстановлено.

**Ближайший ETA всей текущей партии —19:15:04–19:19:25 UTC 21сентября** (22:15–22:19 по Москве). На момент последнего чтения18:44 UTC он ещё впереди. Это не просто прошлый spike: текущие19104 уникальные сообщения имеют этот диапазон времени запуска, а в памяти worker могут оставаться дополнительные повторно зарезервированные экземпляры. Heap не инспектировался, поэтому точное число таких экземпляров и их байтов не установлено. RSS около1.4GB и давление памяти всего хоста подтверждены отдельными снимками; утверждать, что все1.4GB принадлежат только ETA, нельзя. Задачи не удалялись и не отзывались, worker не перезапускался; никакого исправления эта диагностика не выполнила.
