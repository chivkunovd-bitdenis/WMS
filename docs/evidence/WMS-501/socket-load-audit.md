# WMS-501 — нагрузка через настоящие HTTP-соединения

21.09.2026. Изолированный uvicorn на `127.0.0.1:18452`, disposable PostgreSQL16.14 `wms501_load2`. Продуктовый baseline3e125074, без правок приложения. Тестовые данные:13tenants,13различных FFadmin аккаунтов,27 275товаров (24 875у самого крупного),130документов приёмки. Основной прогон: один товар/строка в документе, статусreceiving, факт0. Прямой seed не включает всю историю production, миграции заменены create_all.

Хост AppleM1/8логическихCPU/16GiBRAM/macOS, API один процесс, SQL pool5+10. CPU API в выборочных ps-снимках доходил100%, RSS455824KiB (~445MiB). Это локальные значения, не ресурсы production. Параллельно выполнялись другие изолированные аудиторские проверки; на диске оставалось около200MiB. Ранее browser wrapper один раз получил ENOSPC до начала этого прогона, но все HTTP запросы этого прогона завершились200; контролируемого выделенного hardware benchmark нет.

Операторы — параллельные coroutine workers, не такое же число отдельных аккаунтов. После каждого ответа пауза200мс; 60%запись receiving scan,20%поиск scan/resolve,20%страница каталога100товаров. Каждая ступень15секунд плюс завершение текущих запросов. Это closed-loop: с ростом задержки входящий поток сам снижается. Поэтому отсутствие ошибок не означает отсутствие насыщения, а результат не устанавливает предел допустимых клиентов. Серии без разогрева отдельного tier; первый единичный запрос включает холодные издержки.

`multiN`: Nработников распределены по13tenant/users и разным документам; приN<13 участвуетNtenants. `shared25`:25работников под одним JWT, один документ. `multi25_catalog`: тот же mixed workload25 плюс отдельный запрос полного каталога крупнейшего клиента, затем пауза2с (всего5полных запросов). Это не замер входа в браузере; он воспроизводит конкуренцию уже выявленной стартовой выдачи с рабочими операциями.

Основные сканы передают известный product_id — быстрый путь веба. Дополнение `barcode_only_500lines_shared25` убирает подсказку product_id, добавляет499строк к одному документу и повторяет25работников под одним JWT. Его p95=1180.6мс относится только scan POST; мобильный последующий GET всего документа сюда не включён.

**Сверка сохранности:** основной прогон4356scan POST200, сумма actual_qty по ровно130созданным документам4356 (начальная0). Дополнение314успешных POST, прирост суммы314. Все запросы всех типов имеютHTTP200, timeout/5xxнет. Это проверка общей суммы; отдельный журнал событий и сопоставление каждого физического скана с конкретной строкой не построены. Дубли при повторе после неизвестного исхода этим тестом не исключаются.

**Вывод:** простые серверные увеличения количества выдержали эту серию без потери общей суммы, включая один общий аккаунт/документ. При100исполнителях p95записи вырос до1.537с, throughput перестал расти относительно50. Полная выдача каталога при25исполнителях сопровождается p95~0.993с вместо~0.200с в предыдущем mixed tier; это последовательные короткие диагностические опыты, не рандомизированная статистическая оценка эффекта. Большой документ без product_id также значительно медленнее. Назвать такие пути мгновенными нельзя.

В нагрузку не включены WB/Ozon, Celery задачи, PDF-печать, реальные сеть/ТСД/браузер, proxy/TLS. Длительное накопление очередей, суточная нагрузка и recovery после restart требуют отдельного стендового прогона; активную систему ради теста не нагружали.
