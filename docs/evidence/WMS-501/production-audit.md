21 сентября 2026, агрегаты и короткие снимки состояния. Проверка выполнена через существующий SSH-доступ; настройки, секреты, код и пользовательские данные не менялись. Значения товаров, имена клиентов, токены и PDF не выгружались.

## Какая версия проверена

Более сильная проверка: совокупная SHA256 всех **284 Python-файлов `backend/app`** равна `0d876f9691dde92c6db04ac80bf17e9e74fb979d9084d382f016616df240c521` локально, в контейнере API и в контейнере Celery worker. См. [fingerprint](production-source-fingerprint.json). Это подтверждение файлов серверного приложения на диске контейнеров; frontend bundle, установленные зависимости и уже загруженная память процессов этим хешем не проверяются.

В проверенный момент в контейнере API наблюдался один процесс uvicorn (один снимок docker top). У фонового Celery обработчика три дочерних процесса; API, PostgreSQL, Redis, worker, scheduler и web делят один сервер. Параметры SQLAlchemy **5 постоянных + 10 дополнительных соединений, ожидание до30секунд** прочитаны из `engine.pool` отдельным Python-процессом внутри работающего API-контейнера: импорт `app.db.session.engine` из проверенных файлов с окружением контейнера. Это подтверждает конфигурацию создаваемого engine, но не читает объект pool из памяти уже работающего uvicorn и не измеряет его текущую занятость. [Значения](production-pool.json). Это соединения на процесс, не допустимое количество пользователей.

## Проверенный план поиска

На реальном наборе крупнейшего tenant выполнен один EXPLAIN ANALYZE репрезентативного фильтра поиска каталога (несуществующая строка, sku/name/barcode/vendor/nmId + Ozon links, LIMIT50). План использовал tenant index и отфильтровал **24 875 строк**, исполнение **195.571мс**, planning8.591мс; чтений с диска0, sharedhits2258. Включён поиск tenant с максимальным каталогом — около9.9мс из исполнения. Это один тёплый SQL-опыт, без ORM-сериализации и сети, не p95 API. Exact barcode resolver имеет другой путь; эти195мс нельзя приписывать каждому скану.

Сохранены [SQL](production-plan-probe.sql), [сырой вывод](production-plan-probe.txt) и [план JSON](production-plan-probe.json). Вывод: ограничение выдачи50строк не ограничивает работу фильтра50строками. Оптимизацию поиска надо проверять отдельным планом, сохраняя поиск товаров вне загруженной страницы.

## PDF маркировки

`marking_code_service.py:1538` читает список всех ORM MarkingCode вместе с `label_artifact_pdf`, а затем проверяет PDF в отдельном потоке. Перенос проверки в thread уже есть; чтение всех бинарных данных и удержание списка в памяти остаются. Сервис `_code_filter_for_product` учитывает не только прямой product_id, но и общие pools; простой GROUP BY product_id недостаточен для размера такого ответа.

[Агрегаты](production-pdf-groups.txt) показывают4184кода,3999PDF,555573903байта несжатых PDF. Из них552991881байт относятся3944кодам с product_id=NULL: **это не один товар с527MB PDF**. Среди непосредственно привязанных кодов максимум64на товар и703271байт на группу. **BE-05, P1, подтверждённый риск больших выделений памяти:** [точный pool/product фильтр](production-marking-list-aggregate.sql) на текущих данных даёт71товарный список с кодами, максимум646кодов в одном списке и **130601301байт (124.55MiB) PDF в самом тяжёлом списке**. Максимумы количества и байтов вычислены независимо. [Результат](production-marking-list-aggregate.txt) получен SQL-агрегатом без выгрузки PDF. По коду такой список полностью загружается в память запроса, прежде чем формируется компактный ответ. На сервере с available285MiB даже несколько подобных одновременных операций существенно конкурируют за память. Сам HTTP запрос с этим объёмом на production намеренно не выполнялся, OOM/конкретное время его исполнения не доказаны. Следующее исправление должно разделить список метаданных и нужные бинарные артефакты либо иначе ограничить объём чтения, сохраняя достоверную проверку печати.

## Практический вывод

По размеру таблицы товаров база ещё не выглядит огромной. Однако один API-процесс обслуживает синхронный password hash, полные выдачи каталогов и рабочие операции, а сервер имеет небольшой запас доступной RAM. Увеличение количества клиентов и устройств усиливает общую конкуренцию. Начинать следует с доказанных лишних выдач, блокирующей работы API, сохранности сканов и наблюдаемости pool/queue/transaction age; число процессов и память рассчитывать по замерам после этих изменений. Этот аудит не устанавливает максимально безопасное число клиентов и не меняет инфраструктуру.
