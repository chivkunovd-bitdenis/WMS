## Exact scope of the 33 cases

The original six cases remain: three true technical-QR entry forms plus single creation, grouped partial-refusal retry and add-existing refusal retry. The added 27 cases are the Cartesian product of three entry forms (`supply_id=A`, `supply_ids=A`, `supply_ids=A,B`) and nine variants:

- Six persisted WB settings: all off, QR, reprint CIS, QR+reprint, pool CIS, QR+pool. Settings are seeded in localStorage; these cases do not click the flag controls. Every case uses technical order-sticker QR, not product barcode. Explicit stickers must not allocate a pool CIS, even under the pool settings. Alloff/pool use local selection and local pack keys; QR/reprint modes use server selection. Assertions require exact full CIS commit, correct print intent set, correct label dimensions/content, correct pack quantity/order/task/line and FIFO.
- Held receipt: under **QR-only** settings, first accepted print response is held while next QR/CIS are already queued. Before release, neither first pack nor second lookup may occur; after release both complete in order.
- Lost accepted acknowledgement: under **QR-only** settings, synthetic print boundary records acceptance and then closes the response. No pack may happen before explicit recovery. Rescanning the first QR dispatches the same print key twice in total; the synthetic accepted ledger returns the existing receipt, then the flow packs and advances.
- Remount after lost acknowledgement: the same QR-only loss, localStorage preserved across page navigation, fixture reports the existing bound CIS, same print key dispatched again, exactly one CIS commit per order, correct pack and next QR.

Thus the nine recovery cases are three recovery modes × three entries, **not** recovery under every combination of QR/pool/reprint. The synthetic ledger proves browser transport behavior against a stated native-service contract; it does not implement or prove the actual native agent's durable deduplication. Existing native/backend tests remain necessary. Final packed UI state, marketplace behavior and physical paper remain outside this contract.

The extended mutation evidence is causally relevant: wrong full CIS → nine copy-content RED; actual repeated groups → six-vs-four POST RED; quantity two → all 27 extended cases RED; new print key → all nine recovery cases RED among 24 total failures; pool allocation for explicit QR → three QR+pool RED. ## Remaining narrow finding: remount selection key can be masked

`browser.mjs:107–112` returns `scan_id: scan-${one.id}` regardless of the request's `idempotency_key`, with `replayed: restored`. Recovery availability is also controlled by that global remount flag. The remount assertions compare order IDs, print keys and commit counts, but `390–394` never checks the `idempotency_key` of the two explicit selection POSTs.

Causal gap: if the product accidentally changes the explicit `/scan-auto-print` request key after remount, this fixture still returns the old synthetic scan ID and bound CIS. The downstream print key then remains the expected `scan-wb-a-order`, so the print-key assertion does not detect that upstream request-identity regression. This is a **static coverage gap**, not a product bug reproduced in this review and not a claimed executed survivor mutant.

The final saved trace is correct: in `browser-final-green/WMS652-realQrFlags-remount-after-lost-ack-supply_id-A-.json`, the explicit selection before and after remount both use `5de2a417-b731-4e2d-adb0-cf3b34371547`. The first product-lookup miss has another key, as expected, and must not be mistakenly compared to the explicit selection. The missing invariant therefore needs no changed product behavior or baseline business expectation.

Minimal fix: for each remount entry, require the initial and restored **explicit order selection** requests to carry the same nonempty `idempotency_key`, and preserve the request's actual order/barcode identity. Add a bounded product negative control that changes only that restored selection-request key while leaving native print dispatch unchanged; expect failure on the selection-key invariant in all three remount entries. A stateful synthetic scan registry rejecting changed keys could also strengthen the boundary, but a broad fixture rewrite is unnecessary for this finding.
