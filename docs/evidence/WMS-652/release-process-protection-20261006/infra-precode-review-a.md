# WMS-652: короткое инфраструктурное ревью до кода

**Направление parser + immutable registry обосновано, но само по себе не закрывает удаление проверяющей команды.** Минимальная первая реализация должна проверять конкретно выполненные сценарии и неизменность их источников. Независимый обязательный запуск проверки остаётся отдельным bootstrap-барьером; до его фактического включения нельзя утверждать автоматический запрет merge с удалённой командой. Это read-only proposal, не выполненное изменение настроек или кода.

## Проверенные исходные факты

Read-only GitHub API вернул repository `chivkunovd-bitdenis/WMS`, **defaultBranchRef=main**. Active ruleset **24431521** относится к `refs/heads/etalon`, требует PR и пять GitHubActions contexts (`baseline`, `backlog`, `backend`, `frontend-build`, `охрана`, integration15368), запрещает deletion/non_fast_forward; `bypass_actors=[]`, `strict_required_status_checks_policy=false`. Это реальная защита ветки;404 старого branch-protection endpoint не означает её отсутствия. Но required job name не фиксирует workflow path и состав commands.

Проверены нынешние `check_regression_guards.py`, `resolve_ci_base.py`, `verify_ci.py`, candidate и origin/etalon `ci.yml`. Existing checker правильно читает manifest/собственную версию из trustedBASE и запрещает подмену хеша вместе с guardbytes, **если вызван**. Внешний job `охрана` в candidate workflow сам может быть изменён; registry checksum внутри удаляемого job не обеспечивает собственную неизбежность.

В текущей GitHub семантике `pull_request` исполняет workflow из PR merge commit; `pull_request_target` использует defaultbranch независимо от basebranch PR. Это изменение вступило в силу08.12.2025. Следовательно PR→etalon не делает etalon источником PRT workflow: здесь им будет **main**. [Официальное изменение GitHub](https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/). Candidate в privileged-trigger workflow допустимо только читать как данные; build/npm/pytest из него запускать нельзя. [GitHub security guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).

## Минимальное усиление в порядке зависимостей

1. **Расширить доверенный registry.** Сохранить механизм trustedBASE, отдельно включив исходные critical businesscontracts, helpers, conftest, pytest/vitestconfigs, runner и producer receipts. Existing paths/hash/обязательные IDs не удаляются и не перехэшируются candidate-манифестом; новые добавления разрешены в отдельном reviewed contract. Не ограничиваться названием test-файла: изменение общего helper/collection hook способно сделать неизменённый assertion пустым. Переименование старого node трактуется как удаление старого+добавление нового и требует явной миграции контракта.
2. **Receipt должен доказывать исполнение, а не collection/count.** Стабильный полный nodeID, включая параметры, suite/environment, исход call+setup+teardown; required ID set должен целиком содержаться в фактически исполненном PASSset. Отсутствие/дубли/skip/xfail/xpass/error, пустой/повреждённый файл — отказ. Для frontend — file+полное testname/параметр; для PG — реальное выполнение нужной DBfixture, а не словоpostgres в произвольном поле. Не склеивать одних и тех же IDs между альтернативными средами, если контракт требует именноPG. Общий счёт25 можно сохранить как дополнительный assert, но он не заменяет точные IDs.
3. **Привязать receipt к GitHub фактам.** Репозиторий, workflowID/path, event, runID, runAttempt, headSHA, baseSHA, testedSHA (PR mergeSHA отдельно), digest trustedregistry/producer. Скачивать артефакт из конкретного проверяемого run/attempt; сверять API provenance и metadata, не верить одним полямJSON. Latestattempt only: нельзя дополнить неполный rerun зелёным артефактом первой попытки. Указать attempt в имени артефакта и ещё проверить metadata. Отказ при missing/ambiguous/expired artifact; downloaded file только data, без выполнения кода и небезопасного извлечения путей.
4. **Усилить verify_ci до SSH.** Сохранить существующий exact etalon pushSHA/latestattempt/requiredjobs gate, добавить registry и receipt verification того же run/attempt. Для PR проверять current head/base и соответствующий testmerge; после merge нужен новый pushreceipt точного etalonSHA. Старый PRreceipt нельзя объявить доказательством merged tree. Изменениеbase во время/после проверки требует нового результата; ruleset strictfalse сам не обещает перепроверку обновившейся базы, поэтому минимум текущий release driver перечитывает head/base непосредственно передmerge. Полная автоматическая политика для будущих concurrentPR потребует отдельно согласованной активации.
5. **Закрыть источник самой команды отдельно.** Минимальный независимый механизм — маленький metadata-only trusted workflow/checker из **defaultmain**, запускаемый для PR→etalon, читающий candidateworkflow/registry/receipts как данные и выдающий обязательный результат. Он не устанавливает зависимости и не запускает candidateкод. Его workflow/script не должны заменяться bytes из PR; policies берутся из pinnedtrustedBASE/approvedanchor. Удалённая candidateкоманда/step/runner, изменённый if/continue-on-error/permissions/needs должны давать fail доmerge. Не изобретать сложную «семантическую эквивалентность shell»: для узкого protected execution surface безопаснее explicit immutable bytes, а легитимные инфраструктурные изменения проводить отдельным reviewed upgrade anchor.

Последний пункт не требует нового сервиса или отдельного секрета, но требует доверенного anchor и его обязательности в GitHub. Возможные names/разделение existing `охрана` и executor должен выбрать ведущий; нельзя просто получить ещё один зелёный job с тем же именем и предположить правильную привязку. Для required checks GitHub различает head и testmerge и допускает лишь определённые trigger events; `workflow_dispatch` jobcheck наhead сам по себе PRrequirement не удовлетворяет. Если check и commitstatus имеют одинаковое имя, требуются оба. [Официальная семантика required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks). Поэтому перед включением необходим реальный canaryPR/mergeability readback, не только YAMLunit test. Settings/main в этом проходе не менялись.

## Обязательные отрицательные проверки реализации

- Не меняя businessassertions, выключить producteffect → конкретный requiredtestFAIL → receiptrejected → verify_ci отказывает передSSH.
- Удалить один testcase/parameter или сделатьskip; сохранить прежний total добавлением другого testcase → receiptrejected.
- Ослабить assertion и пересчитать candidatehash; изменить helper/collectionconfig → trustedBASE integrity отказ.
- Оставить jobname `охрана`, удалить его command либо весь requiredteststep, добавить `continue-on-error`, передать ложный env/не тот runner → независимый trustedgateFAIL. Именно этот опыт проверяет устранение исходного механического пробела.
- Передать правильныйreceipt отдругогоSHA/run/attempt/PGsuite, пустой artifact, частичныйrerun либо PRreceipt для etalonpush → отказ.
- Полностью удалить candidateworkflow при сохранённом доверенном anchor → requiredgate не становится success; фактическую невозможность merge проверить через GitHub, не выполнять merge ради опыта.

## Bootstrap и граница обещания

Новый registry/parser, отсутствующий в старомetalon, не становится trusted только потому, что проверил собственныйcandidate и совпали егохеши. Первый checkpoint требует отдельного рассмотрения exactdiff/negativecontrols и публикации trusted baseline. Одного добавления PRT вetalon здесь недостаточно: defaultmain остаётся источником. До отдельно разрешённого включения anchor/main/requiredcheck путь **premerge inevitability BLOCKED**; можно честно сообщать лишь выполненный parser/integrity/deploy-driver proof в границах нового reviewedкода. Main/defaultbranch/ruleset менять без отдельного поручения нельзя.

Защита предназначена против регрессий, случайного удаления/ослабления тестов и обычного обхода через изменённыйCI. Математическая защита от администратора, способного заменить trustedbranch, правилаGitHub иправа, не заявляется и не нужна этой задаче.
