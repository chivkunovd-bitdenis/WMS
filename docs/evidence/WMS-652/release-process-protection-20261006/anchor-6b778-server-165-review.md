## Anchor: verified fix and remaining pending-loss P1

It checks repository, target, exact head and PR identity; workflow_run additionally checks CI path, completed pull_request event and matching run/head. Fresh strict verification remains the only route to success. The five new tests were committed before implementation in `9646bef50`; the original three frozen test modules are unchanged from the prior checkpoint. Independently executed all four modules: **27 PASS**. No live check-runs were published.

The constant concurrency group correctly prevents two publishers from executing simultaneously. But `docs/evidence/WMS-652/trusted-anchor-20261006/process-integrity.yml:18–22` omits `queue`, so GitHub uses its default `single` behavior: one running plus one pending, with a new pending run replacing the previous pending run even when `cancel-in-progress` is false. Current official [GitHub workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#concurrency) documents `queue: max` to retain up to 100 pending runs; it is compatible with the existing false cancellation setting.

Concrete three-event sequence: A-old finishes a delayed success POST; A-new, which should reject a newer failed CI for the same head, waits pending; unrelated PR B arrives and replaces pending A-new. A-old publishes success and finishes, then B verifies only B. No invocation remains to publish A's required failure. The new `threading.Lock` contract accurately tests serialization but implicitly supplies an unlimited wait queue, so it cannot catch GitHub's pending replacement. My earlier two-event proposal likewise did not test this third-event boundary; this follow-up corrects that omission.

The saved `anchor-6b778-pending-probe.py/.txt` reads the frozen YAML and models these documented scheduler semantics. It shows A-new cancelled and A remaining success. Its in-memory `max` control preserves A-new and ends A at failure. This is a deterministic scheduler model supported by official platform documentation, **not a live GitHub execution reproduction**. The older actual-CLI race proof and new 27 actual-CLI/unit tests remain separate evidence.

Minimal addition: freeze a three-event pending-retention contract before adding `queue: max` to the prepared YAML. Preserve constant group and false cancel. Test the actual configured queue mode, not only a mutex. The 100-pending maximum, GitHub publication outage, and the non-atomic interval between verification/CI change/POST remain explicit external boundaries; required current pipeline proof and strict current base must still be activated. No broad code redesign or new service is required for this correction.
