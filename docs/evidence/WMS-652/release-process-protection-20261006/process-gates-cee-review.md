## P1 — обязательный Windows-набор невозможно выполнить без skipped

В cee `guards/PROCESS_CONTRACTS.json` suite `native-windows` требует exact31: все30 Linux cases плюс Windows-only `test_windows_cmd_synthetic_queue_receipt`. Но существующие `tools/print-agent/test_wms_print_runtime.py:185–188` (`test_safe_synthetic_queue_runs_real_child_process_once`) и `:224–227` (`test_actual_process_exit_after_spool_acceptance_recovers_without_second_submit`) вызывают `skipTest` при `os.name == 'nt'`. CI `.github/workflows/ci.yml:337` запускает оба файла целиком. Поэтому при исправном Windows-прогоне эти два **обязательных** случая skipped, и `verify_reports` закономерно отклонит их; process-proof не может стать зелёным.

Это обратная сторона уже учтённого Windows-only пропуска на Linux, а не отсутствие Windows runner. [Изолированный read-only probe](process-gates-cee-probe.py) читает frozen policy/AST и строит ровно ожидаемый Windows JUnit со skipped для двух известных Unix-only случаев. Настоящий frozen parser отклоняет его: [вывод](process-gates-cee-probe.txt). Нативный Windows runner аудитор не запускал; вывод об этих двух ранних skip ветках непосредственно следует из неизменённых тестов, а реакция parser воспроизведена.

Минимальное исправление: разнести OS-specific обязательности, сохранив все31 уникальных сценария. Например Linux запускает30 без Windows-only node, Windows29 без двух Unix-only nodes, оба suite exacttrue/0skip. Не удалять и не ослаблять сами тестовые проверки; два реальных Unix subprocess случая остаются обязательными на Linux. Ведущий сообщил именно такой план, следующая дельта пока не принята этим отчётом.

## P2 — попытка указана только на финальном пакете, исходные отчёты её не различают

В cee `.github/workflows/ci.yml:174,260,341` и release-print upload имя состоит из prefix+`github.sha`. Downloads в `process-proof:359–376` используют те же имена. Только финальный artifact содержит sha/runID/attempt. `build_process_proof.py:35–47` читает скачанные исходные отчёты и проставляет текущие `GITHUB_RUN_ID/GITHUB_RUN_ATTEMPT`; происхождение исходных файлов по attempt не проверяет.

У повторного запуска того жеrun два следствия. Повторный producer пытается создать artifact с прежним именем; upload-artifact@v4 по умолчанию не перезаписывает existing artifact, поэтому загрузка конфликтует. Повтор только collector может получить старые исходные отчёты и обернуть их metadata новой попытки. [Документация actions/upload-artifact: overwrite по умолчанию false; existing name вызывает отказ](https://github.com/actions/upload-artifact#inputs).

Первое — ошибка штатного восстановления CI после сбоя, второе — разрыв цепочки происхождения receipt. **Успешный обход deployment этим не воспроизведён и не утверждается:** действующий `verify_ci` отдельно требует полный набор jobs конкретной попытки и может отказать partial rerun раньше. Но правильный final artifact name не доказывает attempt его upstream reports. Это чтение конкретного wiring и семантики artifact action, а не проведённый реальный GitHub rerun.

Минимальное исправление: все producer upload и collector download names должны включать immutable sha+runID+runAttempt; при отсутствии текущего источника — fail без fallback на предыдущую попытку. Требовать повтор всех обязательных producer jobs либо отдельно реализовать и доказать явную модель provenance per-job attempt. Простое overwrite уничтожает исторический источник и само по себе не связывает файлы с попыткой.

## Проверенное положительное и пределы

- Независимо выполнены **18 новых infrastructure unittest, PASS** (`test_process_contracts`, `test_process_deploy_gate`,0.931s), без GitHub/network/deploy. Прочитан ведущий59PASS log;59 не выдаются за новый собственный прогон. Тесты реально проверяют same-count replacement, skip/ошибку, duplicate, отсутствие evidence, чужой SHA/run/attempt, архивные traversal/duplicates и ноль fake external actions до отказа.
- Immutable checker сравнивает existing hashes и suite properties/cases с trustedBASE, затем actual bytes. Одновременная замена candidate file+its hash не самоодобряется. Защищены85files. Статический просмотр прямых test-helper imports защищённых файлов не нашёл незарегистрированного `tests.*` helper. Это не формальное доказательство всех возможных динамических импортов.
- Parsers используют точные classname/name или file/fullName, не одну сумму. Required skipped/failure/error/missing запрещены; exact suites отклоняют extras. Subset suites намеренно допускают unrelated skipped. JUnit collection/error не теряется при subset. Это лучше прежних count-only gates; новые реальные browser/selection сценарии ещё отдельно в работе.
- Archive verifier ограничивает размер/число/распакованный размер, запрещает symlink/traversal/duplicate, извлекает только требуемые файлы через безопасные пути и читает их как данные. Просмотр не выявил write-outside/archive execution дефекта. CLI сначала проверяет immutableSHA/run, policy получает по exactSHA, после report download ещё раз проверяет latestrun. Дельта deploy вызывает `verify_process_ci.py` в существующем `set -euo pipefail` шаге **до SSH**.
- `run_isolated_pytest` ставит socket audit hook до импорта pytest, допускает только заданный loopback port. Это разумная защита от случайного marketplace/network вызова в выбранных asyncpg тестах; текущая заявленная область не включает libpq native sockets или произвольные дочерние процессы. Шесть realPG сценариев в этом review не повторялись.

**Advisory: base_sha пока информационное поле.** `verify_process_ci.py:77–80` сравнивает sha/head_sha/runID/attempt/policydigest, но не base_sha. На существующем synthetic EvidenceFixture `metadata.base_sha='not-a-sha'` всё ещё даёт успешный verify_execution. Это не самостоятельный доказанный обход: workflow resolver формирует base, trusted integrity и внешний anchor рассматриваются отдельно. Но нельзя утверждать, что deploy verifier удостоверяет base identity. Минимум нужна структурная проверка nonzero40hex/base!=target; полноценную доверенную связь — из выбранного event/anchor proof, не из произвольного поля самого JSON. Ведущий получил этот advisory.
