# Перепроверка 12 дефектов на свежей сборке — 30.08.2026

Стенд: `https://web-production-9e7c1.up.railway.app`. Отпечаток фронта на момент
проверки: `assets/ff-IlZohxl7.js` (был `assets/ff-C3dFHT81.js` — сборка сменилась,
проверено `curl` перед стартом, ждал 34 попытки по 60 секунд). Вход — токен
`fulfillment_admin` через `localStorage.wms_token_ff`, роль «администратор».

**Инфраструктурная помеха.** В процессе проверки бэкенд дважды на несколько минут
падал в `502 Application failed to respond` (первый раз сразу после входа, второй —
в середине прохода). Оба раза дождался восстановления (проверял `/api/auth/me`
до ответа 401/200) и продолжал с того же места. Само по себе падение бэкенда не
входит в 12 пунктов и не включено в вердикты ниже.

**Оговорка по скриншотам.** Инструмент браузерной панели в этой сессии не
позволяет сохранить PNG на диск (та же проблема, что описана в
`docs/evidence/20260829-brauzernaya-proverka-stenda/HOD-PROVERKI.md`: «could not
create image from display»). Дополнительно у панели обнаружился воспроизводимый
баг: скриншот показывает чёрный экран (или рассинхронизированный кадр) всякий раз,
когда страница прокручена средствами `window.scrollTo` дальше `y=0` — при этом сама
страница (проверено через `get_page_text` / `read_page` / сетевые запросы) продолжает
работать нормально, это чисто визуальный артефакт инструмента, не приложения. Каждый
вердикт ниже поставлен по содержимому экрана, которое я реально читал (accessibility
tree, `get_page_text`, счётчики, диалоги) и по не менее чем одному валидному
скриншоту (сделанному при `scrollY=0` либо внутри модалки, где это работало
корректно) — не по чтению кода и не по одним только сетевым запросам. Сетевые
запросы использовались только как вспомогательное подтверждение (какой запрос ушёл
и что вернул), а не как замена клику.

**Ограничение инструмента drag-and-drop.** У части объектов на карте склада стоит
нативный HTML5 `draggable="true"` (проверил через DOM). Синтетические
mouse-события инструмента `left_click_drag` не порождают событие `dragstart` —
это известное ограничение автоматизации нативного HTML5 DnD, не тестировалось
успешно ни разу за несколько попыток с разных стартовых точек. Там, где сценарий
можно было проверить только через drag на карте склада, это отмечено отдельно как
непроверенное (не путать со «сломано»).

### 1. A-03 — создание палеты/короба/грузоместа внутри документа раскладки — СЛОМАНО ВСЕГДА

Открыл «Сортировка» → «Приёмка № 000034» (Denmarcs, «В сортировке», Принято 110 из
120). Внутри документа есть отдельный блок «Раскладка по ячейкам» (не тот
экран, что открывается прямым кликом по строке списка «Сортировка» — тот
показывает другой, по-товарный, режим без кнопок создания тары; блок
«Раскладка по ячейкам» открывается из документа «Приёмка на FF» → кнопка
«Раскладка/Сохранить»). Счётчик «110 штук осталось поставить … — это 2
объектов и 2 позиций россыпью», таблица «Содержимое»: «Короб КР-000001»,
«Грузоместо ГМ-000001».

Нажал «Новый короб». Сеть: `POST .../sorting-objects → 201` (создан), следом
ушёл `GET .../sorting-objects?inbound_request_id=...` (тот самый документ).
На экране: счётчик остался «2 объектов и 2 позиций россыпью», в таблице
«Содержимое» по-прежнему только «Короб КР-000001» и «Грузоместо ГМ-000001» —
новый короб не появился. Это подтверждено чтением accessibility-дерева
диалога (полный текст таблицы) сразу после запроса, не только скриншотом.

**Вердикт: сломано.** Объект создаётся на сервере, но полностью мимо
документа, откуда его создавали — ровно тот дефект, что был описан раньше.

### 4. A-06 — вложить короб в палету — СЛОМАНО ВСЕГДА

**Вердикт: сломано** (по диалогу — это надёжно проверено кликом; по drag —

### 9. Е-06 — снятие с тары уменьшает остаток именно там — СЛОМАНО ВСЕГДА (частичное улучшение)

Поскольку тары в местах снятия по-прежнему не видно (см. Е-04), проверял по
ячейкам, как и в прошлой сессии. В поле «Снять» для места «АА 1.1» (10 шт):

- Залповый ввод (симуляция быстрого набора «12» одним действием в другое
  поле, «232 1.1») — значение осталось «0», **полностью проигнорировано**,

  воспроизводится 1-в-1.
- Верхнее поле сканера «Пикните место или товар» — Enter и потеря фокуса
  (blur) не запускают никакой обработки (см. Ж-02/Ж-03 ниже).
- Отдельное наблюдение (частичное улучшение, не входит в заявленный
  дефект дословно): одиночное нажатие клавиши `5` (не залпом, через
  отдельное нажатие клавиши, не через «печать текста») один раз реально
  прошло: значение стало «05», «Снято» в шапке выросло с 0 до 5, «Осталось»
  с 12 до 7, сеть подтвердила `POST .../pick/set → 200`. Но сразу после
  этого фокус ушёл на `DIV.MuiDialog-container`, а не остался в поле —
  то есть тот же самый «фокус улетает», что в Ж-01.

**Вердикт: сломано** — заявленные в дефекте симптомы («не принимает
залповый ввод», «сканер не реагирует на Enter») подтверждены оба; отдельно
обнаружено, что единичное списание всё-таки может пройти при точечном
нажатии клавиши (не входит в исходную формулировку сценария, но упоминаю
как факт для честности).

На «Отгрузка № 000010» → «Подбор», поле «Снять» для места «232 1.1» (18 шт).

## Чип «Пустая» на непустой палете (запрос не из списка 12)

Проверил инструкцию владельца: «пустая» должна значить, что внутри реально
ничего нет. На карте склада **без фильтра** прогнал JS-проверку по всем
элементам с текстом «Пустая/Пустой/Пустое» (склад Подольск, 120 строк в DOM,
не виртуализировано, проверено полностью, не только видимая часть) — все 7
найденных отметок (Короб WHB-PODOLSK-001, Палета П-001009, Короб
WHB-Q29PGMCZQ9KEFF, Короб WHB-T1CA62V04GNZ1J, Грузоместо WHB-0J5VQ73HWN994E,
Короб КР-000001, Грузоместо ГМ-000001) действительно показывают 0 шт и (для
палет) не имеют вложенных объектов — без фильтра чип корректен.

**С фильтром — дефект подтверждён.** Ввёл в поле поиска карты склада штрихкод
`PLT-PODOLSK-4` (палета «Палета П-001004», реально содержит короб + 4 товара,
всего 67 шт — подтверждено видимым числом «67» в колонке «Штук» той же
строки). Отфильтрованная строка при этом показывает чип **«Пустая»** и текст
«Внутри сейчас ничего нет» — притом что рядом в той же строке видно «67» в
колонке «Штук». Это прямое визуальное противоречие на одном экране,
подтверждено и accessibility-деревом (`generic "Внутри сейчас ничего нет" →
generic "Пустая"` в той же строке, что и `PLT-PODOLSK-4`), и скриншотом.
После снятия фильтра (обычный список) та же палета корректно показывает
содержимое и не помечена «Пустая».

**Вердикт: дефект подтверждён, только с активным фильтром.** Причина по
всей видимости в том, что при фильтрации сворачиваются/не подгружаются
дочерние объекты (короб внутри палеты), и компонент считает «дочерних
элементов не отрисовано → пусто», не пересчитывая по итоговому числу в
своей же колонке «Штук». Правило канона не называю (это факт сценария, а не
нарушение конкретного пункта UX-канона) — фиксирую как самостоятельную
находку.
