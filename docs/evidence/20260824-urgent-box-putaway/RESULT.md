# Аварийное размещение короба и крупная этикетка ячейки

Проверяемый кандидат основан на `origin/etalon` `269ed6cf5e9807102602927a129a0854a2f57271`.

## Что проверено

- скан внутреннего ШК закрытого короба выбирает короб, но сам по себе не меняет остатки;
- следующий свежий скан ячейки одной операцией размещает весь остаток всех товарных позиций короба;
- ручной выбор ячейки и кнопка «Разместить» выполняют ту же серверную операцию;
- существующий сценарий «ячейка → отдельный товар» продолжает работать;
- превью ШК ячейки использует крупный CODE128: живой размер источника 1103×288 px, на экране 518×136,7 px;
- печатная версия ячейки использует 96% ширины и высоту ШК 48 мм;
- товарные, FBS- и ЧЗ-этикетки не изменены.

## Автоматические проверки

- `backend/tests/test_inbound_distribution.py`: 8 passed, включая два конкурентных POST одного короба — ровно один применяется, остаток второго короба сохраняется;
- `frontend/src/hooks/useBarcodeScanner.test.ts`: 26 passed;
- production build: green;
- Chromium production preview: целевые сценарии зелёные — крупная этикетка, прежний скан ячейка→товар, новый короб→ячейка, блокировка повторного ручного действия.

## Живая проверка

В живом встроенном Chromium на локальном стенде из кандидата пройдено:

1. открыт документ сортировки с одним коробом, двумя товарами и остатком 4 шт.;
2. скан короба только выбрал строку и запросил свежую ячейку;
3. скан ячейки перевёл обе позиции по 2 шт. в размещённые, остаток документа стал 0, документ — «Оприходовано»;
4. открыто превью крупной этикетки ячейки и измерена фактическая геометрия.

Скриншоты: `box-putaway-before-live.png`, `box-putaway-after-live.png`, `large-cell-barcode-live.png`.

Финальный SHA, независимое ревью и результат выкладки дописываются после соответствующих стадий.
