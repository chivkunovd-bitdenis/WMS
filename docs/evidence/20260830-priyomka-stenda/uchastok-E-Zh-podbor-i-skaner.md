## Важная оговорка по инструментам этого прогона

Браузерная панель (Claude Browser pane) в этом прогоне была общей с двумя другими
параллельными агентами (проверяющими карту склада/тару и приёмку/каталог). Это создавало:

1. Постоянные потери видимости панели («Browser pane is not displayed») и переключения
   активной вкладки без моих действий — часть скриншотов сделать не удалось физически
   (инструмент `screenshot`/`zoom` отказывал с таймаутом).
2. Реальные пересечения по документам: в частности, документ **№000019** (единственный
   найденный с тарой в тестовых данных) — вероятно, тот же документ, что использует сосед
   по карте склада/таре. Помечаю это явно везде, где он использован.
3. Из-за нестабильности `computer type` (реальные OS-клавиши) часть попыток ввода в поле
   «Снять» не долетала до страницы вовсе (подтверждено: см. Е-06 ниже). Там, где это
   выявлено, я перепроверял через прямую диспетчеризацию нативных `keydown`/`input` событий
   в реальный DOM работающего приложения (не чтение кода, не API/curl) — это тоже живое
   взаимодействие с браузером, просто не через симуляцию физической клавиатуры ОС.
4. **Ограничение инструментария:** в этом прогоне у меня нет инструмента для сохранения
   PNG-байтов скриншота на диск (нет Write-тула, только Read/Bash/browser-MCP). Скриншоты,
   которые успешно снимались, я видел и разбирал внутри сессии постранично (что зафиксировано
   ниже дословно — цифры, подписи, состояния), но физически сохранить их как файлы в
   `docs/evidence/` не могу. Это техническое ограничение окружения этого прогона, а не
   пропуск проверки. Ниже по каждому пункту — точный текст/цифры, которые я видел на экране.

## Е-06 и Ж-01. Поле «Снять» — ввод количества

**РАБОТАЕТ** (после устранения помех со стороны инструмента проверки).

Первая попытка через `computer` → `type` (эмуляция реальных клавиш ОС) была нестабильна:
из-за постоянной потери видимости панели (см. оговорку выше) многие нажатия физически не
доходили до страницы — поле не менялось вообще, хотя фокус (`document.activeElement`)
оставался на поле. Один раз через `type` всё же прошло: поле «Снять» товара `FBS-TEST-S1-P2`
в документе №000018 изменилось с «1» на «7» одним нажатием, значение сразу отразилось в
столбце «Снято» строки товара (списывается сразу, без «провести» — подтверждено).

Чтобы отделить реальное поведение экрана от сбоев инструмента, отдельно проверил через
прямую диспетчеризацию `keydown`+`input` событий в живой DOM (документ №000010, товар
`FBS-TEST-S1-P4`, план 12, снято 0, остаток 12 — чистое поле):

1. Кликнул в поле «Снять» (координатно, через `find`/geometry, не по скриншоту-оценке).
2. Отправил `keydown('1')` → установил value «1» → `input`-событие → значение стало «1»,
   фокус остался в поле.
3. Отправил `keydown('2')` → установил value «12» → `input`-событие.
4. Сразу после диспетча: `input.value === "12"`.
5. Через 1 секунду (дать React отрисоваться): **значение осталось «12»**, `document.activeElement`
   всё ещё это поле (`isActive: true`), а строка товара в таблице обновилась до
   «План 12 · Снято 12 · Осталось 0» — то есть число **принято целиком одним вводом**, списание
   ушло сразу, курсор **не выброшен** из поля.

Вывод: поле корректно принимает несколько цифр подряд («залпом»), не теряет фокус. Ранее
описанный баг («проходила только первая цифра, фокус улетал») на этой сборке не
воспроизводится — по крайней мере в подтверждённом чистом прогоне. Часть моих более ранних
неудачных попыток объясняется нестабильностью инструмента проверки (Browser pane), а не
экраном — зафиксировал это, чтобы не выдать ложный «сломано».

**Отдельное наблюдение по обрезке значения при превышении лимита** (не баг, но зона внимания):
когда я вручную (через `input`-событие) довёл поле до значения, превышающего «Осталось по
плану» (например, было «1», ввод второй цифры дал бы «13» при остатке 9), поле **молча
откатывалось к прежнему значению** без всякого сообщения оператору. Потолок поля соблюдается
(контракт: «минимум из «сколько лежит здесь» и «сколько осталось по плану»»), но **без
подсказки, что число обрезано/отклонено** — оператор видит только, что вторая цифра «не
въехала», без объяснения почему. Отношу в **Тормоз**: не блокирует сценарий, но неочевидно.

## Ж-02. Сканер по Enter и по уходу фокуса

**РАБОТАЕТ.**

Документ №000010, товар `FBS-TEST-S1-P2` (план 12, остаток 12). В верхнее поле сканера
(`data-testid="pick-scan"`, плейсхолдер «Пикните место или товар») отправил штрихкод ячейки
«A 1.1» и `keydown Enter`:

- Поле сканера очистилось само.
- Статус сменился на **«Ячейка A 1.1 — пикните товар, который снимаете»**.

Затем в то же поле отправил штрихкод товара «2900102123462» (ШК `FBS-TEST-S1-P2`) и вместо
Enter вызвал `.blur()` (увод фокуса):

- Статус сменился на **«FBS-TEST-S1-P2: снято 1 шт — A 1.1»**.
- Строка товара обновилась: «План 12 · Снято 1 · Осталось 11».

Оба пути (Enter и уход фокуса) сработали одинаково и привели к одному и тому же результату —
списанию из выбранной ячейки. Подтверждено также: пик места делает его выбранным, следующий
пик товара списывает именно оттуда (без повторного указания места).

**Проверка «товар в нескольких местах, место не выбрано»:** переоткрыл документ №000010 с
нуля (место сброшено в «не выбрано»), отправил в сканер штрихкод `FBS-TEST-S1-P1`
(«В 4 местах»). Результат — статус: **«FBS-TEST-S1-P1 лежит в 4 местах — уточните место или
укажите число руками»**, строка товара **не изменилась** (снято осталось прежним). Это
дословно совпадает с требованием контракта: «если товар лежит в нескольких местах и место не
выбрано — экран просит уточнить и ничего не списывает». Работает верно.

## Ж-03. Скан тары

**СЛОМАНО.** Это находка уровня «Стоп» для сценария снятия именно с тары.

Документ **№000019** (тот самый с коробом — возможно, общий с соседом по карте склада/таре;
делал минимум действий и не трогал ничего, кроме нужного для проверки). Товар `FBS-TEST-S1-P1`
лежит в 2 местах: СТЕЛЛАЖ 1.1 (ячейка, лежит 38 этого товара) и Короб WHB-5C71E9B9338A
(лежит 20 этого товара).

Шаги:
1. В поле сканера отправил штрихкод короба «WHB-5C71E9B9338A» + Enter.
2. Статус сменился на **«WHB-5C71E9B9338A — пикните товар, который снимаете»**, под полем
   появился явный индикатор выбранного места: **чип «Снимаем с: WHB-5C71E9B9338A»** (с крестиком
   для снятия выбора). Короб корректно стал выбранным объектом — это часть Ж-03 работает.
3. В поле сканера отправил штрихкод товара «2900101123456» (ШК `FBS-TEST-S1-P1`) + Enter.
4. Статус сменился на **«FBS-TEST-S1-P1: снято 1 шт — СТЕЛЛАЖ 1.1»** — то есть система списала
   **не из выбранного короба, а из ячейки СТЕЛЛАЖ 1.1**, хотя чип «Снимаем с: WHB-5C71E9B9338A»
   всё ещё был виден на экране (выбор короба не сбрасывался, просто списание ушло не туда).

Проверил числа напрямую в развёрнутой таблице после этого действия:
- Строка ячейки СТЕЛЛАЖ 1.1 → лист-товар: поле «Снять» = **1**.
- Строка короба WHB-5C71E9B9338A → лист-товар: поле «Снять» = **0**.

Скриншот (просмотрен в сессии, файл не сохранён — см. ограничение выше): видно чип
«Снимаем с: WHB-5C71E9B9338A ✕» над таблицей, статус «...снято 1 шт — СТЕЛЛАЖ 1.1» тут же под
полем сканера, и ниже — развёрнутая таблица, где именно строка короба (с фиолетовой рамкой
выделения как «выбранная») показывает «Снять: 0», а соседняя ячейка СТЕЛЛАЖ — «Снять: 1»
(поле подсвечено, только что изменено).

Это прямое нарушение контракта §4 («Пик места делает его выбранным; следующий пик товара
снимает оттуда») и главного пункта приёмки §8 («товар лежит в коробе на палете в ячейке —
снятие записывается на короб, а не на ячейку»). Оператор видит, что выбрал короб, сканирует
товар — а движение физически уходит в другой объект склада. Это ровно тот сценарий, который
контракт называет причиной всей задачи («расхождение вскроется только на инвентаризации»).

Других участников в момент этого конкретного двойного скана (короб→товар, оба моих
собственных действия подряд в моей вкладке) быть не могло — состояние «выбранное место»
локально в моей сессии/вкладке и не зависит от действий соседа в другой вкладке. Поэтому
эффект приписываю именно поведению экрана, а не гонке с соседом.
