## A-05. Снять тару с ячейки — СТОП (найден блокирующий баг)

Нашёл короб КР-000001 в ячейке «А 1.1» (см. A-04), нажал «Снять с ячейки», подтвердил в диалоге «Снять».

**Результат: запрос падает.** `POST /api/warehouses/.../map/move → 422`, в интерфейсе всплывает текст ошибки: **«qty: Input should be greater than 0»**. Короб остаётся в ячейке «А 1.1», операция не проходит.

Проверил ОБА варианта, как просил владелец:
- **С фильтром поиска** (по коду тары `INB-BY1Q55GV8YTWSS`) — тот же результат: 422, «qty: Input should be greater than 0».
- **Без фильтра** (полный список ячеек, только развернул «А 1.1» кнопкой-шевроном) — тот же результат: 422, «qty: Input should be greater than 0».

Похоже на прямое следствие соседнего бага (см. ниже «Чип Пустая»): раз бэкенд/фронт считают короб «пустым» (qty=0), запрос на снятие с ячейки пытается переместить 0 штук и падает на валидации `qty > 0`. То есть сценарий «снять тару с ячейки» для непустого короба **физически невозможно пройти**, если он показан как «Пустой» — а он показан так почти всегда (см. ниже баг воспроизводится даже без фильтра).

Скриншот: сообщение об ошибке зафиксировано текстом через `get_page_text` («qty: Input should be greater than 0»); визуальный скриншот не удалось сохранить из-за нестабильности пейна в этот момент (см. оговорку по инструменту) — но сетевой лог (`POST .../map/move → 422`) снят дважды, воспроизводимо.

В документе №000035 (Северный ветер, ещё одна своя приёмка) создал «Новая палета» (Палета П-001010, `PLT-7CF3A0C1248A`) и «Новый короб» (`WHB-AF7JPERE4CA5SP`). У короба нажал «Положить в место» → в выпадающем списке `Выберите место` рядом со всеми ячейками (А1.1…В2.5) в самом конце списка присутствует опция **«Палета П-001010»** (`value="obj:dbe930e9-6bac-4629-99ab-13087005ac19"`). Выбрал её, нажал «Положить» → `POST /api/warehouses/.../sorting-objects/place → 200`, короб успешно вложен в палету.

**Перетаскивание короба на строку палеты (drag-and-drop) не проверено** — при попытке проверить в конце сессии браузерный пейн перестал отдавать скриншоты (устойчивая ошибка «Browser pane is not displayed»), а без визуального скриншота нельзя достоверно подтвердить, куда именно приземлился drag. Это ограничение инструмента в сессии, не выдаю его за дефект интерфейса.

## Чип «Пустая» — СТОП (враньё подтверждено, воспроизводится без фильтра тоже)

Владелец просил проверить короб/палету, где внутри реально что-то есть, особенно с фильтром поиска по коду тары. Взял короб КР-000001 (`INB-BY1Q55GV8YTWSS`), который на момент проверки лежал в ячейке «А 1.1» и достоверно содержал 1 шт товара «Футболка хлопковая M» (это подтверждено в самом документе приёмки №000036: «Короб № 1, внутри 1», и в неотфильтрованной карте склада — дочерняя строка товара видна прямо под строкой короба).

**С фильтром** (поиск по `INB-BY1Q55GV8YTWSS`, склад «Подольск»): строка «Короб КР-000001» помечена чипом **«Пустой»**, «Штук: 0», тултип «Внутри сейчас ничего нет». Дочерняя строка товара в этом отфильтрованном виде вообще не показывается.

**Без фильтра** (полный список, только раскрыл ячейку «А 1.1»): та же строка «Короб КР-000001» снова помечена чипом **«Пустой»**, «Штук: 0», тултип «Внутри сейчас ничего нет» — при этом прямо под ней в том же дереве видна дочерняя строка «Футболка хлопковая M … 1». То есть баг не специфичен для фильтра — он воспроизводится и в базовом виде карты склада. Подтверждено через `read_page` (полное дерево доступности, не плоский текст) — короб `ref_1403/1404/1405` = «Пустой», его дочерняя строка товара `ref_1411` = «Футболка хлопковая M … 1» лежит в той же таблице на том же уровне вложенности.

Скриншот сохранён визуально в сессии (см. оговорку по инструменту): карта склада, фильтр `INB-BY1Q55GV8YTWSS`, склад «Подольск», строка «А 1.1» → «Короб КР-000001 [Пустой]» / ШК `INB-BY1Q55GV8YTWSS` / Штук `0`.

Эта же метка «Пустой» напрямую ломает A-05 (см. выше): раз система считает короб пустым, операция «снять с ячейки» падает с ошибкой валидации количества.
