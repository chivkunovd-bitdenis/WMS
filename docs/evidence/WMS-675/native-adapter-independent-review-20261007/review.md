## Что подтверждено чтением исходника

Входной барьер `adapter.py:228–251` связывает явные CLI-аргументы с пятью exact IDs,
SHA адаптера, bindings и всех14 входов; при `--execute` требует штатный `/app`
и17 хешей установленных файлов4c. Критические импортированные функции дополнительно
проверяются по реальным путям пакета. README-команда содержит правильные IDs и хеши:
адаптер `5d290b28419c72389a85a2f518efcdbf612c43c49d43f62e048dd5c3bf427535`,
bindings `a4e59a459c92c9fadf93455be1669d8cdd0a7be9028d397fd902766b49885e6d`.
Самостоятельно живую установку/копию в этом ревью не проверял: это проверки
исполняемого адаптера и уже сохранённый producer proof, а не новый production read.

Штатный неизменённый Ozon reader выполняется до складских блокировок. Его единственная
внешняя операция — семантическое чтение `/v3/posting/fbs/get`, без отправки/подписи/
печати/повторов и управления credentials/ролями. Адаптер допускает только31 успешный
proof без children/unknown, с прежним posting/SKU/offer/quantity, статусом и локальным
составом свежей416 матрицы. Изменение этих полей останавливает проход; старый
положительный статус не заменяет новое чтение. `NoAdditionalNetwork` только запрещает
неожиданный дополнительный запрос на стадии вычисления; настоящие `ozon_targets`
и `make_observation` не заменены и искусственные targets не присваиваются.

`adapter.py:113–124` использует настоящий `save_observations`, который в4c отдельно
фиксирует существующий checkpoint. До вызова записан неизвестный исход, после —
возврат commit. Запись proof не выдаётся за складской расход. Под штатными parent/order
locks повторно проверяется состав31, затем вызываются реальные product locks и
ledger locks (`128–190`). Сигнатуры, столбцы и fixed SELECTs сопоставлены с4c;
девять файлов запросов побайтно совпадают с опубликованными SELECTs. Дополнительный
запрос linked movements также только SELECT. Прямых SQL-мутаций нет.

Текущий расход считается настоящим `completed_quantities` по непогашенным рецептам,
с сохранением всех12 исходных ссылок, header movement IDs и отказом при сторно,
неизвестном/дублированном движении, превышении proof или смене источника. Сумма missing
пересчитывается под блокировками в пределах0..14 (`148–193`). Все пять отмен исключены;
в матрице26 подтверждённых единиц по пяти товарам и12 уже проведённых. Более новый
согласованный native расход уменьшает missing; матрица14 не используется как команда
безусловно списать14. Статические ограничения соответствуют текущим done/in_delivery/
cancelled строкам, а штатный conduct не меняет их в этом составе; новый несовместимый
статус требует обновлённого плана и не обходится.

Вызов `conduct_supply` (`194–214`) штатный, только при missing>0, без подмены Session,
publisher или ручного изменения reserves/status/date. До outer commit проверяются
missing0, число новых единичных расходов ровно current missing, сохранение прежних
ссылок, точный decrement балансов каждого товара, нулевые position reserves и прежние
52 charges/26 facts по IDs/quantity/amount. Native billing использует прежние source
keys и cumulative quantities; добавление повторного начисления здесь не разрешено.
Все52 суммы в сохранённом baseline null; денежная успешность этим не подтверждается.
Ошибки штатного conduct не превращаются в успешный результат.

До commit штатный Session context откатывает незавершённую stock-транзакцию; после
начала попытки commit ошибка обозначается `COMMIT_UNKNOWN_REQUIRES_READBACK`
(`211–218`), без автоматического повтора и без утверждения отката. Pending-фазы также
сохраняют необходимость выяснить результат после обрыва процесса. Отдельно сохранённый
checkpoint может остаться: повторное действие должно опираться на него и актуальный
ledger, а не на новый внешний handoff. Это соответствует утверждённому плану.

Обычное намерение публикации остатков сохранено. Реальный4c hook откладывает dispatch
на root commit; адаптер в finally ждёт настоящий
`drain_background_stock_publish_tasks` (`219–225`), включая исключение после попытки
commit. Helper ждёт in-process tasks с `return_exceptions=True`; Celery broker/provider
и его подавленные/залогированные ошибки не дают внешнего success receipt.
Адаптер прямо сохраняет эту границу и необходимость независимого SQL readback
интегратора. Подавления публикаций, новых runtime flags или ручного publish нет.
