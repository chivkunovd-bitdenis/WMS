## Первая ошибка: все места возникновения

В проверенном production коде точный текст есть только в
`tools/print-agent/wms_print_direct_macos.swift` (две проверки defaultPrinter)
и `tools/print-agent/wms_print_direct.py` (lpstat health и cupsGetDefault POST).
`frontend/src/utils/printDirectQr.ts` передаёт error из ответа localhost оператору.
Сетевой отказ, запрет Chrome, выключенная программа дают другой текст.

| Путь | Условие исходной программы | Проверка |
|---|---|---|
| Swift | lpstat -d не завершился за 10 секунд | Настоящий дочерний процесс с задержкой: точная ошибка |
| Swift | Ненулевой exit status | fault injection: точная ошибка |
| Swift | Нет двоеточия, пустое имя, имя >127, перевод строки | fault injection: точная ошибка |
| Swift | Валидный stdout плюс предупреждение stderr | Воспроизведён ложный отказ: потоки смешивались |
| Swift + CUPS | CUPS_SERVER указывает на недоступный endpoint | Настоящий lpstat -d возвращает rc0/no default; точная ошибка, эмулятор продолжает работать |
| Swift + CUPS | LPDEST указывает на отсутствующую очередь | Настоящий lpstat выдаёт ошибку в stdout при rc0. Короткий текст ошибочно принят за queue; длинный вызывает точную ошибку |
| Swift + CUPS | Устаревший пользовательский default перекрывает серверный | Opus воспроизвёл в отдельном Linux CUPS: есть рабочая очередь, lpstat -d сообщает no default |
| Python | cupsGetDefault() возвращает NULL | Найдено в коде; установленная версия ArtMaks неизвестна. Совпадение с lpstat на нашем Mac не исключает расхождение на клиенте |

Питание принтера не проверяется в этих ветках. Поэтому «принтер включён»
совместимо с ошибкой разрешения системного имени. Без вывода с Mac клиента
нельзя выбрать один из перечисленных триггеров и честно объявить его причиной.

## Вторая ошибка и воспроизведение

`createPackingScanController.scan`: после сохранения ЧЗ и отказа print выбранный
заказ остаётся pending с needsKiz=false. Другой штрихкод вызывает «Не завершена
упаковка … Повторите его штрихкод …». До печати другого товара код не доходит.
Повтор исходного штрихкода вызывает finish с прежним намерением QR; pack идёт
только после успешной печати. Это одна цепочка, а не доказательство второго сбоя WB.

Проверка `wms607_scan_emulator.py` использует настоящий контроллер и printDirectQr,
настоящий HTTP /print и собранный исходный Swift, затем настоящий macOS CUPS и
существующий IPP-эмулятор WMS604_Proof → localhost:18631. Только зависимости API
WMS заменены фикстурой, журнал помощника изолирован. Экраны браузера и настоящая
БД не входят в эту проверку. Глобальные настройки принтеров не менялись.

До правки: обе ошибки воспроизведены подряд. После восстановления CUPS исходный
ШК завершает упаковку, bind/select/pack по одному, квитанция WMS604_Proof-312,
ровно один PDF. Повтор HTTP задания возвращает ту же квитанцию.
После правки: аналогично WMS604_Proof-314; выходной QR декодирован и совпадает
с входным идентификатором. Никакая физическая печать на складе не выполнялась.

## Что изменено

Swift defaultPrinter отделяет stderr от данных stdout, проверяет существование
распознанного назначения до записи задания и даёт разные сообщения при таймауте,
недоступном списке принтеров и неопределённом default. Проверки ограничены 5 секундами
каждая. Ненулевой lpstat -p не позволяет уверенно отличить остановленную службу
от отсутствия всех очередей, поэтому сообщение честно упоминает оба варианта.
Ошибки stderr сохраняются в терминале помощника. Не выбирается первый/единственный
принтер, не меняется default ОС, не сбрасываются задания с неизвестным исходом.

Пять регрессионных тестов: исходный код 1 pass/4 fail, исправленный 5 pass.
Существующие frontend sequential/recovery тесты: 40 pass. Сценарии и результаты
эмулятора сохранены рядом; old/fixed source_sha256 различают проверенные версии.

Облачный Opus 5.5: https://claude.ai/code/session_01G6HXiBz2kzyq9v39nD6Ejv .
Он независимо поднял CUPS, подтвердил дефект и проверил план исправления.
Замечания о rc1 при пустом CUPS и бюджете таймаутов учтены. Полного ревью финального
кода, полного CI и приёмки клиентом нет.

## Что остаётся для восстановления клиента

Нужно проверить именно процесс WMS Print на Mac Артмакс: версию, его /health,
вывод lpstat -d и реальные назначения, а при расхождении — источник default
(пользовательская настройка, последний использованный принтер или окружение).
Если рабочая очередь существует, явный выбор её системным принтером по умолчанию
устраняет ветку отсутствующего выбора; после этого исходный ШК продолжает тот же
заказ. Если недоступна сама служба CUPS, нужен её разбор на том Mac. Серверный
деплой не заменяет локальную программу и не восстанавливает системную настройку.
