# WMS-475 · обезличенная проверка уже существующего заказа в production GET

21.09.2026 на работающем API из checkout `9f6f15211b55ea9914c9e12778ba0b6cb3e69b09` выполнен только локальный ASGI `GET /operations/fbs-supplies/{supply_id}/workspace`. Перед и после проверки контейнер имел один и тот же image digest и время запуска; ведущий ранее побайтово сопоставил его исходники с этим checkout (798/798 файлов). Обезличенный результат — [production-workspace-readonly-result.json](production-workspace-readonly-result.json), воспроизводимый код — [production_workspace_readonly.py](production_workspace_readonly.py). В результате и в тексте нет ID заказа/поставки, артикула, полного кода стикера или значения размера.

Сначала SQL по журналу `document_event` нашёл девять связей заказа с WB-поставкой, где пользовательское событие `line_added` произошло **после** события перехода той же поставки в `assembling` или `packed`. Все эти поставки на момент проверки уже имели статус `done`. Из них выбран один существующий заказ с сохранённым стикером и размером. Это подтверждает позднюю связь от пользователя по журналу, но не определяет конкретную кнопку и не измеряет задержку получения стикера при исходном добавлении.

GET вернул HTTP 200 и 15 строк рабочего места. Выбранный заказ присутствовал ровно один раз; `sticker.code` совпал с сохранённым в БД кодом, его часть после последнего пробела состояла ровно из четырёх цифр; `product.size` совпал с сохранённым размером товара. Хотя бы у одной строки рабочего места размер заполнен, то есть данные для условной колонки есть. Текущий этап ответа — `tracking`. Само событие добавления выбранного заказа произошло **до** выкладки `9f6f1521`, поэтому это проверка того, что нынешний API читает и отдаёт исторические данные, а не проверка немедленного запроса нового стикера у живого WB.

Каждая SQL-сессия начиналась с `SET TRANSACTION READ ONLY`, проверяла `SHOW transaction_read_only = on`, устанавливала лимит 15 секунд и завершалась `rollback`. Дополнительный guard останавливал ORM flush, а неожиданный внешний запрос через `httpx.AsyncHTTPTransport` отклонялся до сети. Рабочий обработчик GET и его SQL-проекция выполнялись из API-контейнера; роль существующего администратора ФФ подставлялась как несекретные поля через dependency override. Настоящий JWT-вход, браузерный экран оператора, живой WB и печать не вызывались. GET имеет путь, который может попытаться создать служебную ячейку при отсутствии её в БД; указанная защита сделала бы такую попытку ошибкой без записи. Проверка завершилась успешно.

Повтор выполняется только после отдельной сверки production-образа с ожидаемым checkout. Скрипт передают на stdin Python-процесса **проверенного** API-контейнера; он не требует токена оператора и не пишет входные данные в рабочий каталог контейнера. Например, через уже согласованный SSH-доступ: `ssh <host> 'docker exec -i <api-container> python -' < docs/evidence/WMS-475/production_workspace_readonly.py`. Не запускать скрипт через публичный HTTP и не подменять его POST-маршрутом добавления заказа.
