# WMS-488 · безопасная проверка C9/C11 после выкладки

Это инструкция и проверенный инструмент, **не свидетельство выкладки и не финальная приёмка продукта**. До выпуска нового кода production этим обновлённым скриптом не проверялся. Исходная проблема C11 остаётся открытой до реализации и адресных тестов исполнителя.

## Что выполняет скрипт

`production_readonly_audit.py` запускается отдельным процессом внутри выбранного API-контейнера. Он вызывает только GET через локальный ASGI transport (серверный обработчик внутри процесса), не выполняет вход, не выпускает токены, не запускает Celery/BackgroundTasks и не вызывает внешний HTTP API. В качестве текущего пользователя подставляются существующие записи с пятью несекретными полями: ID, tenant, домашний seller, роль и флаг менеджера. Email, ФИО и пароль не выбираются. Все реальные зависимости авторизации и SQL-запросы обработчиков остаются. Это проверка опубликованного кода и данных; проверку JWT, входа и межвкладочной гонки она не заменяет.

Каждая сессия PostgreSQL начинает `SET TRANSACTION READ ONLY`, задаёт локальный лимит запроса 15 секунд и подтверждает `SHOW transaction_read_only = on`. После чтения выполняется rollback. Неподдерживаемая СУБД останавливает проверку. Для изолированных тестов SQLite используется и проверяется `PRAGMA query_only=ON`.

Tenant выбирается по проверенному уникальному slug `avpack-9uczh`. По существующим заданиям выбираются только ID, тип и поля области доступа: seller ID, наличие request ID и ID инициатора печати. Полные payload/result/error не извлекаются подготовительным SQL. Обработчик GET формирует свой обычный ответ в памяти; в отчёт его содержимое не попадает. Инструмент проверяет домашний seller ID в payload и, когда он присутствует, в result; текст `error_message` допускает только отсутствие либо точное общее сообщение. Это не доказывает безопасность произвольных вложенных полей result — её подтверждают адресные тесты каждого producer/result и ревью кода.

Для каждого обычного селлера и менеджера AVpack проверяются:

- `home`: собственное задание одного из пяти доказанно домашних типов — ожидается 200, домашний seller в payload и безопасный общий текст ошибки, если она есть;
- `foreign`: такой же тип, но другой seller — ожидается 403/404 без полей payload/result/error;
- `tenant-wide`: нет корректного seller в старом payload — ожидается закрытый доступ;
- `ff-only`: прочие типы, в том числе печать, проверка маркировки, общий digest и неизвестный тип, — ожидается закрытый доступ даже с домашним seller ID.

Домашнее чтение разрешено для пяти проверенных по producer/result типов: `wildberries_cards_sync`, `storage_measurement_rebuild`, `wildberries_supplies_sync`, `wildberries_marketplace_orders_sync`, `fbs_stock_sync`. Последние три запускаются ФФ, но их payload/result относятся к одному селлеру; инициатор ФФ сам по себе не делает их общими. У `storage_measurement_rebuild` FF-запуск без seller ID остаётся общей задачей и закрыт селлеру. `movements_digest`, `inbound_marking_check`, `fbs_label_print` и неизвестные типы не становятся селлерскими из-за одного seller ID. Общая служебная задача без seller попадает в оба отрицательных сценария намеренно. Для домашней задачи произвольный сохранённый `str(exc)` не выдаётся: seller-ответ содержит точное общее `error_message` «Не удалось выполнить задачу», а статус и сама задача остаются доступными.

Для существующего администратора ФФ проверяется чтение доступных ему заданий. Задания сортировочной печати другого оператора исключаются из положительного контроля: там уже существует отдельная проверка инициатора. Для каждого типа и сценария берутся до трёх записей, включая самую новую и самую старую. Если нужного типа, класса или роли нет в данных, результат — `not-covered`, а не успешная приёмка. Искусственные записи в production не создаются.

Вывод содержит только обезличенные `seller-1`/`account-1`, роль, логический флаг менеджера, название сценария, количества, HTTP-статус, вердикт и безопасное имя класса исключения. UUID, email, SKU, URL, payload, result, error и текст исключений не выводятся; логи HTTP/SQL отключаются в CLI. Также обезличен прежний каталоговый блок C9. Коды завершения: 0 — выполненные проверки прошли; 1 — нарушение или ошибка; 2 — нет данных для обязательного класса. Каталоговая часть сохраняет прежний ограниченный набор маршрутов и временной диапазон отчёта; она не является полной проверкой всех исторических товаров.

## Как связать проверку с конкретной версией

Текущий `/health` возвращает лишь `status=ok`. В `backend/Dockerfile` нет автоматической записи Git SHA; SHA checkout на хосте отдельно не доказывает версию работающего контейнера.

1. До запуска зафиксировать только имя выбранного API-контейнера, `.Image` и `StartedAt` через узкий `docker inspect --format`. Не выводить `Env` и полный inspect.
2. Прочитать только метку образа `org.opencontainers.image.revision`, если она есть, и сверить с принятой полной release SHA.
3. Если метки нет, составить manifest SHA-256 файлов из принятого Git SHA и сравнить с байтами соответствующих файлов `/app/app`, `/app/alembic`, `/app/pyproject.toml`, `/app/alembic.ini` внутри контейнера. Проверить полный набор исходников, в том числе отсутствие лишних исполняемых файлов, а не только один исправленный модуль. В доказательство сохранить release SHA, image digest, количество файлов и несовпадений; не содержимое файлов. Такое сравнение подтверждает соответствие исполняемых исходников; несуществующую SHA-метку образа оно не создаёт.
4. Для worker, если он входит в выпуск, выполнить ту же проверку версии. C9 GET не запускает worker и не заменяет его тесты.
5. Передать опубликованный файл аудита на stdin Python-процесса **этого же** контейнера, без копирования продуктового кода и без перезапуска. Например, локальный файл можно передать через `ssh ... docker exec -i <проверенный API-контейнер> python -`; рабочий каталог API должен оставаться `/app`. Конкретный контейнер и SHA выбирает ведущий после deployment.
6. После завершения снова сравнить `.Image` и `StartedAt`; если контейнер менялся во время проверки, результат нельзя приписывать одной версии.

Пробелы production-данных дополняются изолированными тестами: отсутствующий/невалидный seller ID, исторический foreign-token, попытка чтения старой foreign-задачи прежним инициатором, FF-only job с домашним seller ID. Для этого не нужны production-записи или доступ к токенам.

## Локальная проверка инструмента

`test_production_readonly_audit.py` использует только SQLite в памяти и синтетические записи. Девять синтетических проверок прошли (сценарий утечки проверяется в четырёх вариантах):

1. Проверяющий код принимает правильный контракт для обычного селлера, менеджера и ФФ; все четыре seller-класса и пять разрешённых домашних типов представлены.
2. Ответ 404 с чужим result внутри detail, ошибочный 200 с чужим содержимым и 200 с сырым `error_message` и подмена seller в result отклоняются; содержимое не печатается во всех четырёх вариантах.
3. Отсутствующие задания дают `not-covered`.
4. Случайная попытка DELETE внутри read-only сессии отклоняется, записи сохраняются.
5. Настоящий текущий product-handler выполняется отдельно от эталонного тестового обработчика; вывод обезличен. Эта проверка не требует сохранения дефекта в будущем и не объявляет продукт принятым.
6. Выборка сохраняет старейшую/новейшую запись и представителя каждого типа.

Команда из корня worktree:

```sh
PYTHONPATH=backend /Users/deniscivkunov/Projects/WMS/backend/.venv/bin/python -m pytest -q docs/evidence/WMS-488/test_production_readonly_audit.py
```

На исследованном продукте `6c586380` отдельный повтор настоящего API уже показал 200 для чужой `wildberries_cards_sync` и общей `movements_digest` как под обычным селлером, так и под флагом менеджера. Прямой доступ к иному tenant закрыт 404, а FF-печать селлеру закрыта 403. Это локальное воспроизведение C11; production-данные не изменялись.
