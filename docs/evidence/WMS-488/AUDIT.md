# WMS-488 — каталог AVpack и границы доступа

Дата исследования: 21.09.2026. Исходный кодовый срез — `origin/etalon` `74665f910b07fed0425caa203f8d3537b912c9e3`; production API — `b1b6909659b02e35b62901646896d2f516fe37b1`. Браузерный повтор использовал опубликованный bundle `/assets/seller-Dgi-BWAP.js`, web image `sha256:ced71f39986f4cef05327c55019767c2f7ed5668c930e1530dc4323bf5fc8d9b`.

## Что подтверждено

1. **Обычный селлер мог узнать чужой товар сканированием.** `GET /operations/scan/resolve` проверял только вход и арендатора. Он возвращал ID и название чужого товара того же фулфилмента по SKU/штрихкоду; те же недостаточные границы применялись к заказам и результатам неоднозначного поиска. На существующих данных AVpack пять селлеров получили HTTP 200 с товаром шестого. Это отдельный путь раскрытия данных, даже если списочный каталог ограничен правильно.
2. **Открытая вкладка сохраняла прежнего селлера после входа или выхода в другой вкладке.** На опубликованном bundle первая вкладка показывала 38 товаров магазина A. Во второй вкладке общая сохранённая сессия сменилась на магазин B, который показывал 19 товаров. Первая вкладка получила событие `storage`, но продолжила показывать 38 товаров A. После выхода во второй вкладке первая снова получила событие, но прежний каталог остался. `useAuth` сохранял старую сессию в React и не слушал изменение общего хранилища. Это воспроизведённый дефект сессии; связь именно с наблюдением владельца пока не доказана.
3. **Право управления магазинами зависело от email.** Помимо явного флага в БД, право выдавалось по фрагментам `vitalik`, `vitaliy`, `denmark` и точному списку из настройки. Само действие над другим магазином дополнительно требовало записанную активную делегацию и того же арендатора. Таким образом, email не открывал произвольный каталог без делегации, но оставался неявным источником прав.
4. **Массовое изменение признака ЧЗ обходило право сотрудника на каталог.** `/products/requires-honest-sign/bulk` проверял владельца товаров, но пропускал существующую проверку `PERM_PRODUCTS`. Сотрудник селлера без этого права мог менять признак у своих товаров. Чужие строки это действие не затрагивало.

## Что проверено и не воспроизведено

Изолированный запуск существующих production API-обработчиков с 50 реальными контекстами пользователей выполнил 356 GET-вызовов. Все подключения к БД были `READ ONLY`. Подменялась только зависимость определения уже вошедшего пользователя: использовалась его настоящая запись БД. Проверки прав, разрешённого селлера, обработчики и SQL оставались настоящими. Пароли, подписи и access tokens не читались, не выпускались и не менялись. Эта проверка не подтверждает процесс входа в production.

В обычных `/products`, `/products/wb-catalog`, поиске, остатках и проверенных чтениях товара по ID чужая карточка не вернулась. FF-каталоги обычному селлеру вернули 403. Фулфилмент AVpack получил свой общий каталог из 101 товара. Поиск конкретного товара AVpack в других арендаторах его не вернул.

Опубликованный frontend затем отрисовал точные ответы только чтения для семи пользователей шести магазинов AVpack. В обычном `/seller/products` счётчики составили **38, 7, 19, 21, 1 и 15 товаров**; дополнительный сотрудник магазина с 38 товарами получил те же 38. Поиск чужого SKU у остальных пяти магазинов показал ноль. Пагинация отображала по 10 строк, что не следует путать с размером каталога. Все браузерные API-запросы перехватывались; production-запись из браузера была невозможна.

Постоянное отображение всех чужих товаров в свежем обычном каталоге этим повтором **не воспроизведено**. Это граница проверки, а не опровержение наблюдения владельца. Отдельно воспроизведены обход через сканирование и сохранение прежней сессии между вкладками.

Проверки принадлежности данных показали ноль расхождений: `Product → Seller → Tenant`, `User → Seller → Tenant`, межарендаторские делегации, владелец/арендатор движений и остатков, арендатор marketplace-связей и импортированных WB-карточек. WB nmId AVpack не пересекались с карточками других его селлеров или других арендаторов. Убедительных признаков ошибочной копии каталога в текущих данных не найдено.

## Как проходит выбор магазина

1. Пользователь загружается из БД, а его арендатор сверяется с подписанной сессией. Роль берётся из БД.
2. Для обычного селлера область товаров — его собственный `seller_id`. Чужой идентификатор магазина в старой сессии не меняет эту область.
3. Для пользователя с правом управления магазинами выбранный магазин допускается только при существующей включённой делегации к магазину того же арендатора. Отключённая делегация не даёт работать в магазине, но до изменения кода менеджер мог включить её через существующий переключатель.
4. Каталог фильтруется по `Product.tenant_id` и разрешённому `Product.seller_id`. Данные WB/Ozon обогащают уже выбранные карточки; ключ WB-обогащения содержит селлера и nmId.
5. У ФФ отсутствует seller-ограничение: он видит товары своего арендатора в рамках своих рабочих прав. Это необходимая работа фулфилмента, которую исправление сохраняет.
6. Отдельные записи делегаций однонаправленные. Право менеджера работать с селлером не выдаёт обратного права тому селлеру.

История: `b76f0f62` ввёл переключение 15.06; `dff34604` в тот же день сузил email-условие; `c5f5ef4e` 16.06 изолировал обычный каталог и вернул маркеры Виталика. WMS-481 19.09 была операцией удаления копии магазина в тестовом арендаторе; её отрицательный вывод о других утечках не использовался как доказательство нынешней безопасности.

## Граница переноса прав

На production из 50 проверенных пользователей право управления магазинами имели ровно два пользователя AVpack. Первый получал его по email, при выключенном флаге БД и пяти существующих отключённых делегациях. Второй имел явный флаг и пять активных делегаций. Других менеджеров найдено не было.

Миграция сохраняет только уже существовавшее право: подходящий по прежнему правилу пользователь с правильным домашним магазином и уже записанной делегацией того же арендатора получает явный флаг. Новых делегаций и их включения нет. В предварительном расчёте меняется только флаг первого пользователя; доступные магазины остаются прежними у всех 50. Затем точный код миграции из `65b15418c53a143f783cb4d2a8138c041a1d2c78` выполнен в изолированном production-процессе с подключением READ ONLY: SELECT выполнен, UPDATE перехвачен и только записан как кандидат. Результат совпал: **один кандидат, выполненных записей 0**. Право второго пользователя нельзя трактовать как доказанно ошибочное назначение без установления его роли.

## Карта проверенных путей

| Путь | Граница до исправления | Результат аудита |
| --- | --- | --- |
| Каталог, WB-каталог, категории | Арендатор + разрешённый селлер | Чужие строки не найдены |
| FF/linked каталог и страница | Только FF с рабочими правами, свой арендатор | Обычному селлеру 403 |
| Размеры/история, инструкции, направления, FBS-правила | Проверка существования товара в арендаторе + владельца | Чужие ID не дали карточку |
| Остатки, движения, отчёты и CSV | Серверная область селлера; query не расширяет её | По коду граница присутствует; targeted тесты входят в передачу |
| Создание/объединение/импорт | FF-действия, принадлежность селлера/товара проверяется | Нового обхода при чтении кода не найдено |
| Сканирование SKU/ШК/Ozon, 409 matches | Только арендатор | Подтверждён дефект |
| Массовый признак ЧЗ | Владелец проверяется; право Products отсутствовало | Подтверждён дефект |
| Переключение менеджера | Флаг/email + явная включённая делегация | Email как источник права устраняется |
| Смена сессии в соседней вкладке | Нет синхронизации React с storage | Подтверждён дефект |

## Доказательства и приватность

В Git сохраняются этот обезличенный отчёт и воспроизводимые скрипты. Исходные пользовательские UUID, каталоги, responses и снимки экранов остаются в игнорируемом `local/` и не публикуются. `production_readonly_audit.py` проверяет GET-обработчики, `production_ui_snapshot.py` собирает только чтение для браузерного повтора, `ui_replay.py` проверяет каталог, `ui_session_replay.py` воспроизводит межвкладочную сессию. Сырые stdout этих скриптов нужно направлять только в `local/`.

Заключение приёмки, точные коммиты исправлений и результаты общего ревью хранятся в `docs/requirements/WMS-488.md`. Данный отчёт описывает исследование причин и не объявляет исправления выложенными.
