# WMS-488 — назначение менеджера и порядок событий сессии

Повторная проверка 21.09.2026 после общего Astra CLI review. Код продукта и production-данные не изменены. Результаты дополняют [предыдущую проверку](ACCEPTANCE.md).

## Назначение аккаунта Геруса: что установлено

Свежие SELECT в production-транзакциях `READ ONLY` подтвердили: домашний аккаунт магазина «ИП Герус Д.В.» имеет роль `fulfillment_seller`, явный `can_manage_seller_shops=true` и пять включённых делегаций на остальных селлеров AVpack. Поля ФИО и должности пустые. Записи FF staff permissions нет. В AVpack сейчас один `fulfillment_admin`, семь пользователей `fulfillment_seller`, пользователей FF staff нет.

Аккаунт создан 14.06.2026. Три делегации созданы 15.06.2026, ещё две — 17.06.2026. В модели делегации записаны адресат, enabled и время создания; нет автора выдачи и основания. Таблица пользователей также не хранит автора и историю изменения менеджерского флага. Поэтому существующие строки доказывают выданный доступ, но не назначение человека сотрудником ФФ.

История разработки подтверждает отдельную функцию менеджера **в портале селлера**:

- `b76f0f62`, TASK-55 и [PR 38](https://github.com/chivkunovd-bitdenis/WMS/pull/38), 15.06: менеджер Виталика может включать чужие магазины и действовать от их имени; обычным селлерам оставлен домашний магазин, FF-администратор не затронут.
- `dff34604` и [PR 39](https://github.com/chivkunovd-bitdenis/WMS/pull/39), 15.06: доступ ограничен DB-флагом/Denmarks/email allowlist; переключатель из FF-портала удалён. Герус в описании не назван.
- `c5f5ef4e` и [PR 41](https://github.com/chivkunovd-bitdenis/WMS/pull/41), 16–17.06: обычный селлер всегда получает свой каталог; возможность менеджера переключаться по включённым делегациям явно сохранена как намеренное поведение.

Первоначальная миграция `20260615_0040` добавляла флаг с `server_default=false` и не назначала конкретных менеджеров. В просмотренной истории приложения не найдено маршрута, выдающего сам этот флаг Герусу. `PUT /auth/seller-shops` только меняет делегации уже уполномоченного менеджера. Адрес аккаунта не содержит прежних маркеров `denmark` или `vitali`; проверка действующего runtime с копией его несекретных полей и условным `can_manage_seller_shops=false` вернула **false**. Значение адреса и конфигурационных списков не выводилось.

В текущих таблицах не найдено действий этого пользователя как автора складских движений, фактов операций, истории габаритов, событий документов или подключения marketplace-аккаунтов. Отсутствие записей не доказывает отсутствие работы в прошлом: журнал выдачи доступа не существует, а часть старых селлерских документов записывает выбранного селлера, а не человека.

**Вывод по доказательствам:** технически это аккаунт селлера с отдельно выданным правом менеджера магазинов. Он не является FF-администратором или FF-сотрудником по модели ролей. Источник и бизнес-основание персонального назначения Геруса менеджером не установлены; история описывает эту возможность для менеджера вообще, но не связывает её с Герусом. Объявлять его человеком, который намеренно работает за весь FF, оснований нет. Объявлять сам исторический grant случайной ошибкой оснований тоже недостаточно.

Отключение только пяти делегаций уберёт текущие переходы, но при сохранённом флаге менеджер сможет включить их снова. Для ограничения именно этого аккаунта домашним селлером потребуются flag=false и enabled=false у его пяти существующих делегаций. FF-аккаунт AVpack и доступ FF к общему каталогу от этих строк не зависят. Возможный бизнес-ущерб — прекращение работы Геруса от лица других магазинов, если она была намеренной. В данном исследовании такие изменения не выполнялись.

## Два подтверждённых дефекта сессии

Astra CLI обнаружил промежуток между записью B в общем localStorage и обработкой события `storage` первой вкладкой. Собственный Chrome-повтор подтвердил его на frontend `90dd0044`: предикат актуальности смотрит только на `sessionTokenRef`, который в этот момент ещё равен A.

[storage_order_regression.py](storage_order_regression.py) использует настоящий локальный production bundle и синтетические API fixtures из `session_acceptance.py`. Capture-listener временно задерживает доставку настоящего события `storage` обработчику приложения; код приложения не подменён. Это управляемое воспроизведение возможного порядка задач браузера, а не утверждение, что именно такой порядок наблюдался у клиента в production.

Результат 20.09.2026 21:56:30 UTC (21.09 по локальному времени):

| Событие | Старый 401 | Старый 200 с ролью FF в seller-портале |
| --- | --- | --- |
| Запрос A удержан | 434.0 мс | 320.0 мс |
| B сохранён соседней вкладкой | 435.9 мс | 322.3 мс |
| `storage` удержан перед `useAuth` | 449.6 мс | 332.1 мс |
| Ответ A отпущен | 451.2 мс | 333.3 мс |
| После старого ответа | 805.1 мс: сохранено null | 687.0 мс: сохранено null, показана ошибка роли |
| `storage` доставлен | 832.1 мс | 700.2 мс |
| Итог | 1194.7 мс: null, каталога B нет | 1064.2 мс: null, каталога B нет |

В обоих случаях подтверждён переход **B → null**, после обработки `storage` B не восстанавливается. Browser pageerror отсутствует. Первый путь удаляет B в ветке `unauthorized`, второй — в эффекте `portalMismatch`. Предыдущие восемь сценариев по-прежнему проходят, но в них событие storage было обработано до старого ответа. Они не покрывали найденный промежуток. **C6 нарушен; выпуск до исправления этой гонки не подтверждён.**

Команда для записи уязвимого поведения: `python3 docs/evidence/WMS-488/storage_order_regression.py --expect-vulnerable`. После исправления запускать без этого флага: тогда скрипт требует сохранённый B и `Найдено: 19 из 19` после доставки storage, иначе завершается с ошибкой. Базовый URL задаётся `AUDIT_UI_BASE_URL`. Подробная временная шкала хранится только в игнорируемом `local/storage-order-race.json`.

## План узкого исправления для Opus Extra

1. Проверять актуальность ответа одновременно по локальному ref и **текущему сохранённому токену этого портала**. Проверка только ref недостаточна до события storage. Проверять после fetch и чтения body, а также непосредственно перед применением результата.
2. Выделить общий переход к фактически сохранённой сессии и использовать его как из storage-handler, так и при обнаружении устаревшего ответа. Переход снимает прежние профиль/карточки/ошибки, обновляет ref и запускает проверку нового пользователя. Простого `return stale` недостаточно: без уже обработанного storage локальная вкладка может остаться на старой загрузке.
3. Объединить автоматическое удаление недействительной сессии в действие с ожидаемым токеном запроса. Перед удалением сверить и ref, и сохранённое значение с этим токеном; если значение уже другое — принять актуальную сессию, не удалять её. Применить к 401 **и ко всем веткам portalMismatch**.
4. Связать проверку роли с токеном, которому принадлежит профиль. Предпочтительно проверять роль в том же защищённом обработчике `/auth/me`, до применения профиля, либо хранить явную связь профиля с токеном. Проверка старого `me` по текущему `token` без этой связи оставляет риск удаления B отложенным эффектом A.
5. Повторить два новых Chrome-сценария без `--expect-vulnerable` и прежние восемь. Добавить тесты, где storage уже содержит B, а ref остаётся A; отдельно убедиться, что текущие 401/неподходящая роль действительно требуют входа, обычный текущий профиль применяется, а другой портал остаётся независимым.

Backend scopes, права менеджера и production-делегации для исправления этих двух гонок менять не требуется. Патч продукта ожидает завершения общего Opus CLI review и отдельной передачи исполнителю ведущим.
