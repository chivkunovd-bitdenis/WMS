# WMS-666: native printing proof at product P

This evidence checkpoint pins product source and the served runtime to `b6d23148f1571d08d13d83c6179c385e2f6a1efc`. The runtime checkout and the approved product paths (`backend/app`, `frontend/src`, and `tools/print-agent`) matched at execution. Each completed browser/native case also records the product and runtime SHA in its own evidence directory. Earlier runs against `28a799`, `5066f1d`, and `cedb428` are historical baselines; they are not part of the results below.

The React FBS screen ran from the pinned checkout in Chrome. Its API requests reached the real test API and PostgreSQL fixture; the scan, binding validation, packing, undo, and receipt recovery routes were not HTTP stubs. React's direct print request reached the candidate's actual WMS Print Direct HTTP handler, which ran request validation, origin checks, its SQLite idempotency ledger, and its normal receipt response. The test harness replaced only `Printer.submit`: it saved the accepted PNG bytes and returned a synthetic receipt without submitting to CUPS or a physical printer. The persisted request payloads, sink PNGs, receipt ledger, PostgreSQL snapshots, and independent QR/Data Matrix decodes are kept beside each case.

The checked-in proof database and all scanned values are synthetic. The fixture uses real FBS order and supply records, real current marking-code pool records, and persisted order-sticker PNG assets whose QR values equal each order's stored `sticker_code`. No marketplace HTTP request or live Wildberries confirmation is proven here. Where the UI used the fixture's provider adapter to mark a current KIZ accepted, that readback is explicitly synthetic; it does not prove an outbound payload to WB. Physical paper is **NOT TESTED**.

## Remaining coverage for this checkpoint

This checkpoint covers the listed single-supply flags, copies, rapid scans, retries, unlink-before-validation, and scan undo/reload. The separate multi-supply/grouped (`G`) journey that prints manual HTML tapes and then routes a product scan to this real handler is still pending a coordinated seed/window with the release whole-process runner. Its earlier synthetic `/print` interception is not counted as native-handler proof. The full native matrix is not complete until that exact-P run is added.

Manual HTML tape printing remains a separate Chromium print path (`iframe` and `window.print`), not a request to WMS Print Direct. Any result from the release's manual-tape renderer must be described separately from the native Handler receipts. The known race between the final server binding validation and printer acceptance remains the narrowly accepted site-side residual; it is not atomic, and this proof does not exercise the physical-printer boundary.
