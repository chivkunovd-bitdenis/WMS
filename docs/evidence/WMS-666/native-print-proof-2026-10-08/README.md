# WMS-666 native print proof — checkpoint 28a799

This is an instrumented, synthetic end-to-end proof against candidate checkout `28a7999fefd886de41f6ffda5b05b69cd49aa496`. The five production source blobs used for the React-to-native path are pinned in `run-28a799/source-identity.json`; each matches the release candidate. No product/runtime file was modified for this proof.

The real FBS screen ran in one isolated Chrome at `127.0.0.1:16696`. Its `/api/*` calls were forwarded to the integrator's real ASGI/PostgreSQL audit fixture at `127.0.0.1:16692`; those calls were not stubbed. React `printPreparedQr`/`printDirectQr` sent actual HTTP POST requests directly to the candidate's `WMS Print Direct Handler` at `127.0.0.1:17843`. That handler's HTTP origin checks, request validation, SQLite idempotency ledger and receipt response ran unchanged. Only `Printer.submit` was injected, to save accepted PNG bytes and a synthetic receipt; there was no CUPS submission or physical printer. The exact Mac adapter method `MacPrinter.submit_default` was also run in memory with a `cupsPrintFile` file-copy stub; it preserved each PNG byte-for-byte and returned only synthetic receipts.

The synthetic PostgreSQL seed had two WB FBS orders for actual product barcode `460666AUDIT`, two persisted synthetic order QR PNGs, and a four-code marking pool. The independent QR decoder found the exact fixture payloads `*NATIVE-ORDER-666-A` and `*NATIVE-ORDER-666-B`. The independent Data Matrix decoder found full CIS values `010460043993125321KIZTAPE0000000000` and `010460043993125321KIZTAPE0000000001` in their respective CHZ PNGs.

The first real React barcode scan dispatched three unique native jobs: one order QR and two copies of the one claimed CIS. Both CHZ copies decode to the same full CIS and have distinct idempotency keys. The second order was scanned with the same product barcode. For its QR POST, the real handler accepted the PNG and committed its receipt to SQLite, then the local test handler deliberately dropped only the HTTP response. The UI showed the unknown-result error. Scanning the same barcode again retried the same native key and identical PNG payload; the handler returned the stored receipt, and the sink did not accept a duplicate. The flow then dispatched two copies of the second CIS. Across both scans there were six unique sink PNGs/receipts and six unique job keys; one QR key was requested twice but accepted once.

Post-scan PostgreSQL evidence shows both orders packed, CIS 0 and 1 bound to their respective orders and marked printed, and packaging-task `qty_marking_printed=2`, `qty_packed_in_task=2`. Stock snapshots before and after the first scan are unchanged. The UI's `Напечатано 0 из 2` is consistent with its current definition: that count requires order-sticker application/accepted required WB marking metadata; this synthetic fixture leaves sticker `applied_at=null` and WB marking state `unknown`. Native queue receipt does not claim marketplace confirmation or physical paper.

Evidence files in `run-28a799/` include both database snapshots, the real UI/API request trace, native request payloads (synthetic PNGs only), the emulated sink PNGs and receipt ledger, independently decoded input/output payloads, the SQLite idempotency database, UI screenshots, and the in-memory Mac adapter pass-through report. `run_native_scan.mjs`, `run_lost_ack_retry.mjs`, `emulated_wms_print_direct.py`, `decode_outputs.mjs`, and `exercise_mac_cups_stub.py` provide the repeatable instrumentation. The Chrome profile is deliberately disposable; it is not required for reproduction.

Physical paper and a live marketplace/WB confirmation were **not tested**. The narrowly accepted race between the last server binding validation and external printer acceptance remains outside this proof.

`run-28a799-final-matrix/` is an unfinished diagnostic stage, not a passing matrix result. Its QR-only attempt received `scan_product_exhausted` before any native PNG was accepted because both orders already had scan reservation events from earlier interrupted attempts. The order state and stock snapshot remained unchanged by the final rejected scan. The API fixture is isolated and `/idle` reported no active request when checked, but it must be reseeded and its ASGI process restarted from the final release SHA before any final-candidate matrix run. `run_qr_chz_modes.mjs` includes the same local CORS preflight response used by the successful runner; the preserved debug JSON explains why this older diagnostic did not count as proof.

A second agreed `/seed` reset was used for the flags/continuous-scan check; its fixture and redacted identities are kept separately in `run-28a799-flags/seed-public.json`. The second Chrome run first cleared both print flags and scanned the real product barcode: the UI showed “Стикер не найден в этой поставке”, no `/scan-auto-print` API claim occurred, and the native sink stayed at zero. After turning QR and CHZ on through the UI, two rapid scans of the same product barcode returned two distinct scan keys and order IDs. Six unique native jobs followed (one QR plus two identical copies for each order); the independently decoded labels match the two order QR fixtures and the two corresponding full CIS values. Both orders reached packed state and the packaging task reports two marked units. The live release checkout observed for this second run was `160640df7d811ba8f74939280b1959dcbd29a825`; the only changes from `28a799` were a backend test and the requirements document, and every frontend/backend/native production blob listed in `run-28a799-flags/source-identity.json` is identical.

## Reproduction setup

The guarded API fixture is versioned in this directory. It refuses to start unless `WMS_TEST_DATABASE_URL` names exactly the synthetic database used here, and it blocks every outbound HTTP transport. From the repository root, launch these three local services sequentially (using the existing main-checkout backend virtualenv and existing frontend dependencies):

```sh
PYTHONPATH=backend/tests:backend WMS_TEST_DATABASE_URL='postgresql+psycopg_async://deniscivkunov@127.0.0.1:5432/wms_native_print_wms_test_666_compatibility_audit' /Users/deniscivkunov/Projects/WMS/backend/.venv/bin/python docs/evidence/WMS-666/native-print-proof-2026-10-08/wms666_native_print_server.py
frontend/node_modules/.bin/vite --config frontend/tests-e2e/native-print-proof/vite.config.ts
/Users/deniscivkunov/Projects/WMS/backend/.venv/bin/python docs/evidence/WMS-666/native-print-proof-2026-10-08/emulated_wms_print_direct.py --checkout "$PWD" --output docs/evidence/WMS-666/native-print-proof-2026-10-08/run-28a799 --port 17843
```

Then run `node docs/evidence/WMS-666/native-print-proof-2026-10-08/run_native_scan.mjs`, `node docs/evidence/WMS-666/native-print-proof-2026-10-08/run_lost_ack_retry.mjs`, and `node docs/evidence/WMS-666/native-print-proof-2026-10-08/decode_outputs.mjs`. The last of these validates saved results without launching a browser. `reset_seed_flags.mjs` makes the separately recorded opaque-white synthetic sticker seed; only run it when the audit fixture is idle, because `/seed` intentionally resets that one isolated database. `run_flags_rapid.mjs` runs its no-flags and rapid-scan UI case after that reset; run it only once for that seed. The native handler script rejects a checkout that does not match its pinned candidate SHA and runtime blobs.
