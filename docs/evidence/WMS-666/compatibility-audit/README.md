# WMS-666: независимая проверка совместимости упаковки, 07.10.2026

Проверен продукт **212f19d548496fef7baf75c83204b771e304281b**. Это точный Git-срез,
названный ведущим как текущий production checkout; аудит сам не доказывает SHA
работающего контейнера. Изолированный sparse-worktree создан после чтения
`origin/etalon` a5df04f1560de0eaaf855199065936cb22a222b1. Продукт не исправлялся,
production, реальные заказы, WB/Ozon и физические принтеры не затрагивались.

**Вердикт: NO-GO для заявления о безопасной совместимости всех действий.**
Найден и дважды воспроизведён новый опасный путь: старый скан может получить
разрешение печатать пуловый КИЗ, который уже отменён у его заказа и выдан другому.
Это не означает, что остальные действия не работают; ниже указаны прошедшие
проверки и непроверенные границы. Предложенное объединение ручных действий
ещё не реализовано и не может считаться принятым по макету или этим тестам.

## 1. Воспроизведённый дефект: старый pool payload после отмены

Новый opt-in тест: `backend/tests/test_wms666_stale_pool_print_audit.py`.
Он использует реальные сервисы, API и отдельную PostgreSQL-базу; WB подменён
существующим тестовым подтверждением. Нормативное ожидание не изменено ради PASS.

1. Товарный скан A с `print_chz=true` получает единственный код пула C.
   Ответ `printed_codes` остаётся в браузере как будущий печатный payload.
2. До печати оператор отменяет КИЗ A штатным `cancel_order_kiz`.
3. Ручная лента другого заказа B получает C. База перечитана: ровно одна текущая
   связь `FbsOrderMarking`, принадлежащая B. Остаток, резерв и число движений прежние.
4. Старый scan A вызывает `/scan-auto-print/{scan_id}/print-claim` для `chz`.
   Ожидалось отсутствие разрешения старой привязке; получено **200,
   `{"claimed":true,"started":false}`**.

Полный лог с синтетическими UUID/CIS: [stale-pool-claim.txt](stale-pool-claim.txt).
Последний независимый последовательный прогон: **1 failed, 0 skipped, 3.84 s**.

Причина по коду: `fbs_scan_auto_print_service.py:877` проверяет принадлежность
scan поставке, флаги и владение print-claim, но pool-путь не проверяет текущую
привязку и записывает `marking_id: None`. `fbsSequentialPacking.ts:801`
рендерит старый `result.printed_codes[0]` после такого разрешения. Exact reprint
использует отдельный `claim_reprint_kiz_recovery` с проверкой текущей маркировки;
его защита не распространяется автоматически на выдачу из пула.

**Что фактически доказано:** база уже закрепила C за B, а сервер разрешил
старой попытке A печать. Ветвь frontend, которая после разрешения передаёт старый
C рендереру, прочитана. Сам stale C не отправлялся ни в OS queue, ни на бумагу.
Новая отдельная end-to-end проверка stale PNG ещё нужна; успешные обычные PNG
проверки из раздела 3 не подменяют её.

Для оператора это означает: другая станция/другая попытка уже отменила и
переназначила код, но задержанный scanner attempt может продолжить старую печать.
Наличие одной корректной связи в БД не предотвращает устаревшую этикетку.
Обратный порядок manual A → отмена → scanner B оставляет сходный риск старой
собранной HTML-ленты: она уже содержит C и не перечитывает привязку перед
`printTapeSections`. Этот обратный путь здесь **не воспроизводился**, это гипотеза
для следующей проверки, а не второй доказанный дефект.

## 4. Матрица действующих кнопок и пересечений

| Действие | Scope и пул | Состояния/транспорт | Пересечение/ограничение |
|---|---|---|---|
| Товарный WB scan + QR | одна выбранная незавершённая единица текущего supply | scan event, QR claim/receipt, затем pack | не равен ручному bulk print; повтор scan intent не выбирает соседа |
| Товарный WB scan + ЧЗ | один код tenant/seller/product pool | binding, `printed_codes`, native copies, pack | найден stale pool claim после отмены/переназначения |
| Explicit order-sticker + ЧЗ flag | ровно названный заказ, новый pool не выдаётся | ждёт принесённый CIS; flag pool не превращается в копию | отличен от product barcode; browser pool cases проверяют именно это |
| Перепечатывать ЧЗ | точный bound operator/pool code | atomic reprint claim, N копий одного CIS | не новая выдача N кодов; отдельные проверки replaced/cancelled проходят в SQLite suite |
| Inline «Перепечатать КИЗ» | конкретный `reprint_marking_ids` | ручная tape, canonical CIS | backend exact Ozon inline test прошёл; не печать первого кода наугад |
| QR строки | WB asset текущего заказа | preview/print batch, applied отдельно | не ЧЗ и не pack; Ozon WB QR не создаётся |
| Печать ЧЗ/ШК строки | заказ; Ozon label data по позициям | layout/copies, HTML tape; pool только для недостающих требуемых кодов | до отправки ленты binding уже может быть сохранён; cancel не равен rollback |
| Печать выбранного/всего | selected IDs либо fullTapeOrders одной поставки | tape backend; повтор использует существующие связи, добирает лишь недостающие | общий ручной координатор нескольких supplies ещё отсутствует |
| Проверить в WB | вся поставка, не checkbox selection | sync/readback всех её КИЗ | выбор строк не должен сужать это действие |
| Очистить ЧЗ | выбранные WB заказы, последовательно | delete, pool return по WMS-518, refresh | останавливается на первом отказе; уже успешные удаления сохраняются |
| Всё упаковано | все packingOrders поставки | pack-all-and-complete, возможно box placement | не только selected; printed и packed независимы, stock не списывает |
| Undo scan | последний обратимый шаг scan/history | отмена binding/pack/selection по шагу | не синоним удаления КИЗ или физического возврата товара; у Ozon нет WB history |
| Ozon scan/box | конкретная posting position | `order_product_ids`, собственные KIZ/status | WB scan-auto-print/pool матрица на Ozon автоматически не переносится |

В обычной поставке массовая панель присутствует. Общая WB-ветвь
`FfFbsSupplyWorkspace.tsx:5077` возвращает только `packingRows` и dialogs, поэтому
checkbox строк не даёт общей кнопки выбранной печати/очистки/проверки WB.
Это подтверждённое различие текущего кода и невыполненная часть предлагаемого
объединения, а не установленная этим аудитом историческая регрессия.
Ozon group-кнопка подписана «Печать всего (N)», но callback использует
`printPackingOrders`, то есть selected при наличии выбора: несоответствие
подписи и вычисленного scope видно в коде, отдельный UI-клик не выполнен.

Шесть допустимых flag-режимов: none, QR, pool, QR+pool, copy, QR+copy.
Pool+copy и QR+pool+copy нормализуются с приоритетом pool; N=1…10 означает
копии одного кода, не N единиц. Настройки, снятые до finish, исключают ещё не
отправленный тип этикетки; уже принятые job нельзя считать отменённой бумагой.

## 5. Минимальная следующая правка и границы NO-GO

Нужно закрыть именно актуальность печатного намерения, сохранив правило WMS-518:
на pool claim проверить под согласованными блокировками текущие order/marking/code
и их соответствие исходному scan; возвращать подтверждённый canonical payload
или запрет stale attempt. Frontend должен печатать подтверждённую текущую привязку,
а не доверять старому `printed_codes`. Отдельно требуется решить интервал
claim→dispatch и уже принятый/неизвестный print outcome: один recheck до claim
не доказывает отсутствие смены владельца после него. Нельзя решать это новым
общим запретом операторской упаковки или отменой законного возврата в пул.

Сохранить существующие exact-reprint atomic claims, tenant/supply/seller scope,
один CIS на N копий, replay ключей, QR→ЧЗ→pack и неизвестный print outcome.
Дополнить проверкой свежего и устаревшего pool payload, замены после claim,
manual→scan и scan→manual, двух операторов, partial failure/cancel, seller/warehouse
изоляции. После реализации нужен реальный PNG/QR replay найденного пересечения.

Не покрыты полностью: общий manual coordinator, все multiple-seller batch ошибки,
драйвер/бумага, live Ozon multi-position печать, весь operator journey, все
временные порядки замены/удаления и уже принятой очереди. Наличие одного найденного
дефекта не является доказательством отсутствия других. Проверка размеров в JSON
не доказывает применение mm установленным принтером и не доказывает его ошибку.
