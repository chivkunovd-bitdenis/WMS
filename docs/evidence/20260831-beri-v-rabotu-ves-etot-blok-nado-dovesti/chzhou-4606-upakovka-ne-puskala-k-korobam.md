# ИП Чжоу, поставка WB-GI-271834606 — упаковка не пускала к коробам · 31.08.2026, 17:00 MSK

Владелец: «ип чжоу 4606, не пропускает с упакованно, не даёт до коробов дойти,
16 коробов нужно протолкнуть далее».

Поставка `5f314746-371a-4c87-8986-0d775c3dc203`, `WB-GI-271834606`, «Империя ФФ» / ИП Чжоу,
199 заказов, статус `assembling`.

## Причина

Задание упаковки `7fbb40e4-cb1b-4512-ad27-dee59e896d0c` создано **31.08 в 10:44:59** и
построило 72 строки на **100 штук** — по составу поставки на тот момент. Заказы
продолжали приезжать до **16:27**, их стало **199**, а задание **не пересобралось**.

В `create_packaging_task_for_supply` (`fbs_packaging_integration_service.py:252`) при
наличии `supply.packaging_task_id` задание просто возвращается как есть. Пересчёта строк
при добавлении заказов в поставку нет вообще.

Рабочее пространство считает `packed` по полю `fbs_orders.pack_status`
(`fbs_workspace_service.py:341`), поэтому картина была:

```
picked 199 · packed 100 · metadata_ready 199 · stickers_ready 199 · total 199
stage: packing
```

Кнопка «Всё упаковано» отрабатывала честно, но закрывала только те 100 единиц, что были
в задании. Остальные 99 заказов в задании отсутствовали — закрывать было нечем.
Задание при этом уже стояло `done`, закрыто оператором в 16:27.

## Проверка перед правкой

У всех 100 записей `fbs_packaging_fulfillments` поле `inventory_movement_id` пустое —
**упаковка склад не списывает**. Значит дополнение недостающих заказов не трогает остатки:
списание идёт при сдаче поставки движением `fbs_shipment`.

## Снимок

```

zz_bak20260831e_lines      72 строки задания
zz_bak20260831e_task        1 задание
zz_bak20260831e_fulfil    100 записей упаковки
```

## Что сделано

```sql
UPDATE 34    -- qty_total строк доведён до фактического состава
INSERT 36    -- строки под товары, которых в задании не было
INSERT 99    -- записи упаковки для недостающих заказов (без движения, как у первых 100)
UPDATE 99    -- pack_status='packed', packed_at=now()
UPDATE 108   -- qty_confirmed_packed = qty_packed_in_task = qty_total
UPDATE 1     -- billing_units_packed = 199
```

Задание стало 108 строк на 199 штук — совпадает со 199 заказами по 108 товарам.

## Результат

```
picked 199 · packed 199 · metadata_ready 199 · stickers_ready 199 · total 199
stage: handoff_prep        (было packing)
blockers: «Создайте физические короба», «Упакованный заказ не назначен в короб»
```

Этап переключился с упаковки на подготовку передачи. Коробов сейчас ноль — оператор
создаёт их на вкладке «Короба» и раскладывает заказы. Дальше поставка идёт своим ходом.

## Причина, которую надо лечить кодом

**Задание упаковки обязано досинхронизироваться, когда в поставку добавляются заказы.**
Пока этого нет, любая поставка, которую набирают частями, встанет на упаковке точно так же:
кнопка нажимается, счётчик не двигается, оператор не понимает почему.

Минимум: при открытии рабочего пространства сверять состав задания с составом поставки и
дополнять недостающее. Либо явная кнопка «пересобрать задание» с показом разницы.

# Догон: второй затык — этап откатывался на подбор · 17:20 MSK

После дополнения задания оператор создал 16 коробов, но поставка всё равно «не пускала
дальше». Проверка рабочего пространства:

```
progress: picked 199 · packed 199 · metadata_ready 199 · stickers_ready 199 · total 199
коробов: 16      блокеров: 0
stage: picking   ← при полностью готовой поставке
```

## Причина

`_compute_stage` (`fbs_workspace_service.py:378`) проходит проверки сверху вниз. Все они
пройдены: подобрано, упаковано, метаданные, короба есть, стикеры готовы. Дальше:

```python
if supply.status == FBS_SUPPLY_STATUS_PACKED:
    return "delivery"
if supply.status == FBS_SUPPLY_STATUS_ASSEMBLING:
    return "picking"
```

Поставка оставалась в статусе `assembling`, и последняя строка **отбрасывала оператора в
самое начало, на подбор**. Блокеров при этом ноль — экран не объяснял ничего.

Статус повышает `try_promote_fbs_supply_if_ready`
(`fbs_packaging_integration_service.py:723`). Он вызывается из обработчиков упаковки;
дополнение задания правкой в базе его не запустило.

## Что сделано

Вызван штатный сервис повышения, без правки статуса руками:

```python
await pi.try_promote_fbs_supply_if_ready(s, tenant_id, supply_id, actor_user_id=None)
```

Он проверил завершённость задания, что все активные заказы обслужены, и требования по
Честному знаку — после чего перевёл поставку в `packed` и проставил статус `packed`
заказам.

## Результат

```
статус поставки: packed   (было assembling)
stage: delivery           (было picking)
picked 199 · packed 199 · metadata_ready 199 · stickers_ready 199 · total 199
коробов 16 · блокеров 0
```

## Дефект, который надо лечить

При полностью готовой поставке экран показывает этап **«подбор»** и ноль блокеров, если
статус поставки почему-либо не повысился. Оператор видит начало процесса вместо передачи
и не имеет ни одной подсказки, что не так.

**Надо:** либо повышать статус при входе в рабочее пространство, когда все условия
выполнены, либо показывать явное состояние «всё готово, статус поставки не обновлён» с
кнопкой повторить — но не отбрасывать на подбор молча.
