## Почему исправление закрывает дефект

В `marking_code_service.py:567` Python сначала выполняет `strip()`, затем
удаляет BOM, обычные пробелы, LF и CR, затем только краевые GS. SQL в
`_normalized_cis_sql` (строка 583) теперь повторяет этот порядок: начальный
`trim` содержит полный набор из 29 пробельных символов Python. Ранее набор
из шести символов не покрывал GS+TAB, NBSP и `0x1e`, и последующее Python-
сравнение уже не могло вернуть строку, которую SQL вообще не выбрал.

Начальный trim затрагивает только края. Внутренние TAB, NBSP и `0x1e`
остаются частью идентичности; внутренние обычные пробелы/CR/LF удаляются
ровно как раньше в Python. BOM удаляется после начального trim: если его
удаление открывает TAB/NBSP, второй общий strip не выполняется ни в одном
варианте. Последний trim удаляет только GS. Ограничения длины и наличие
буквенно-цифрового символа остаются в Python; SQL — отбор кандидатов, а не
самостоятельный валидатор допустимости КИЗа.

`find_marking_code_by_cis_identity` (604–678) сохраняет быстрый поиск по
исходному/нормализованному payload и вариантам GTIN. При отсутствии совпавшей
идентичности выполняется SQL fallback без зависимости от метаданных GTIN.
Каждый кандидат повторно сравнивается в Python; tenant указан в первом
поиске, fallback и финальном чтении выбранной строки. `for_update` и
приоритет статусов не изменены. Прежний сохранённый payload не переписывается.

`_existing_import_cis_codes` (1711–1759) использует тот же SQL fallback только
для неразрешённых идентичностей, снова внутри tenant и с Python-проверкой.
Все три публичных сервиса действительно достигают этого механизма:

| Путь | Проверка существования | Сохранение и атомарность |
|---|---|---|
| `import_marking_codes` | `_import_marking_codes_locked`, строка 1985, до создания пула для новых кодов | Общий `_try_insert_imported_code`, один commit импорта; rollback охватывает исключения |
| `auto_import_marking_codes` | Строка 2393, перед планированием назначений и вставками | Общий `_try_insert_imported_code`; пустые пулы удаляются; commit failure откатывает операцию |
| `assign_import_rows_to_product` | Строка 2669, перед назначением выбранных строк | Тот же helper; дубликаты пропускаются; commit failure откатывает операцию |

Общий helper (1488) хранит `cis_code` без замены нормализованным значением,
включает флаг только после успешной вставки и повторно проверяет товар/селлера.
SQL-уникальность `(tenant_id, cis_code)` остаётся защитой точного значения;
нормализованный повтор между импортами защищает существующий общий
транзакционный advisory lock по tenant, взятый до поиска дубликатов.
Эта защита не сводится к локальному mutex Python. Порядок Product.id,
исправленный до этого коммита, не изменён.

Соседние WB FBS (`fbs_marking_service.py:592`), приёмка
(`inbound_marking_service.py:225`), Ozon claim (`ozon_kiz_service.py:90`),
выбор позиции Ozon (`ozon_marking_position_service.py:103`) и проверка пары
(`marking_code_service.py:4873`) используют общий поиск. Проверки селлера,
товара и состояния после поиска остаются у вызывающих сервисов. Изменение
SQL не добавляет новую операцию списания, печати или обращения к площадке.
Полный операторский путь этих процессов заново не прогонялся.
