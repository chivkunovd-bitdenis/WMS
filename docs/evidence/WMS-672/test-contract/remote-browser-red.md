# WMS-672: реальный браузерный RED, передача разработчику

06.10.2026. Целевой продуктовый RED **доказан** по C5/R4 и C6/R5.
Полный контракт и приёмка остаются незавершёнными: таймеры C1/C2 на 300,
C4, C7/C8 требуют отдельного выяснения причины без ослабления ожиданий.

Проверен точный SHA `6e7a8cfad4e48c2446e6a9b1816e753e2516014e` на Linux
GitHub Actions runner Ubuntu 24.04, Node 24, Playwright 1.56.1 / Chromium.
[Фактический run 37431409929](https://github.com/chivkunovd-bitdenis/WMS/actions/runs/37431409929)
завершился с failure. Один job, последовательные контексты, 210.12 секунды
браузерного контракта, 11 тестов: **4 passed / 7 failed**, без skipped/cancelled.
Это синтетический HTTP и реальный экран/рендерер; внешняя сеть браузера
блокирована, системная печать перехвачена. Физической бумаги нет.

## Подтверждённый RED

* C5: на ошибке decode этикетки 150 из 300 передача не произошла, однако
  `mark-label-printed` был вызван **59 раз вместо 0**. Падение на строгом
  бизнес-утверждении `failed preparation must not mark existing boxes printed`,
  а не на fixture/setup. До проверки видимого сообщения и исправленного повтора
  этот тест не дошёл. Разработчик должен устранить ранние успешные отметки,
  сохранив исходные ожидания.
* C6: быстрое двойное подтверждение 200 этикеток создало **2 передачи вместо 1**.
  Падение на `same confirmation must not make a second tape`. До следующего
  утверждения о количестве отметок тест не дошёл. Нужна одна попытка на такое
  подтверждение, а не пользовательский запрет перепечатки.

Эти наблюдения согласуются с исходной постановкой: utility возвращает управление
до завершения decode/передачи, а экран пишет технические отметки независимо;
двойной callback начинает две подготовки. Это достаточное доказательство
целевых ошибок до реализации, но не доказательство остальных проверок.

## Положительные контроли и ограничения

C1/C2 для **приёмки 200 и возврата 200** прошли полностью: одна упорядоченная
лента, PDF ровно 200 страниц 58×40, текст каждой этикетки и CODE128 из растрового
PDF первой/средней/последней страницы. Прошли C3 (короткий/длинный код, специальный
текст, размер 60×80) и C10 (пустой/один короб, соседний диалог без автоматической
печати).

Обе серии 300, C4 и оба сценария потери ответа упали на ожидании передачи
`page.waitForFunction: Timeout 30000ms exceeded`. Их **не классифицируем как
доказанный бизнес-RED**. Для сценариев потери ответа есть дополнительный дефект
завершения оснастки: callback синтетической отметки ожидает передачу и остаётся
незавершённым при закрытии контекста. Истинные assertions восстановления/повтора
не достигнуты. Исправление этой оснастки относится к отдельному тестировщику;
в данном CI-поручении тесты, harness и ожидания не редактировались.
Замер C4 не завершён, `timing.json` отсутствует. WMS-659, грузоместа/палеты целиком,
права backend, браузерная приёмка C11 и физическая C12 данным job не проверялись.
