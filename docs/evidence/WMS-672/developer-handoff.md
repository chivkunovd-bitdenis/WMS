# WMS-672: передача реализации на удалённую проверку

06.10.2026. Это результат разработчика, не независимое ревью, приёмка,
полный CI, деплой или доказательство бумаги. Выпуск остаётся общим для всего
согласованного пакета; отдельно эту часть не выпускать.

## Изменение

`FfInboundRequestView` ожидает завершения decode всех изображений и вызова
передачи общей ленты до первого `mark-label-printed`. Синхронный ref исключает
вторую подготовку от быстрого двойного подтверждения. Ошибка подготовки
показывается в существующем Alert и снимает ожидание, без технических отметок.

Печатный helper получил необязательный callback перед передачей и awaitable
результат только для приёмки/возврата. Вызов без callback сохраняет `void`,
одноимённый одиночный helper и прежний контракт scan-to-print. HTML/CSS,
штрихкоды, подписи, размер 58×40, порядок и payload не изменены.

У браузерного helper исходный источник жил только в iframe. Для восстановления
он сохраняется вместе с исходной попыткой в существующей записи
`inboundDraftPersistence` (ключ API/tenant/user/document); новые таблицы,
складские объекты, режимы печати, очередь и отдельный persistence framework
не добавлены. Полный HTML записывается синхронно после decode и до `print()`;
если запись не удалась, передачи нет. В записи остаются ID попытки, исходные
технические отметки и незавершённые пути запросов. Подтверждённые пути снимаются
по одному, исходный HTML сохраняется, включая после `afterprint`.

После потери ответа повтор сначала GET-перечитывает исходный документ,
сравнивает технические отметки с исходными значениями и продолжает только
их сохранение. Новая лента в этом действии не отправляется. Если сама передача
неизвестна, существующее стандартное подтверждение требует проверки очереди
и бумаги; новая перепечатка требует следующего отдельного подтверждения.
`complete` означает завершение технических отметок и обновления карточки,
а не подтверждённую бумагу. При ошибке обновления карточки сохраняется прежняя
попытка для безопасного повтора без передачи.

## 06.10.2026: кандидат исправления native decode на 300

Это следующая передача разработчика. Полный CI до независимого ревью не
запускался. Продуктовый PASS для 300, C5/C7/C8 и приёмка не заявлены.
Точный SHA этого изменения определяется отдельным commit, содержащим только
этот handoff и `frontend/src/utils/printBarcodeLabel.ts`.

### Диагностика до изменения

Прочитаны AGENTS.md checkout и обновлённого origin/etalon, WMS-672, обе передачи
и опубликованный proof `f07207b6801b978db1b1c94406b5cbc6a82ea80f`.
Помощник до правки побайтно совпадал с продуктом
`163259d412d2ef5ba2d49b831cd5c7da284245d9` (SHA256
`59c2470dc109f39297486c7c265fdebf89db0831176590ab047c3819d6e672e8`).
Существующий remote RED сохранён до этого изменения; новый контракт не создавался.

Прочитаны реальные `events.json`, `page-0.state.json`, HTML и `probe.mjs`
скачанного artifact `11399591837`, runner `e49ca24c6`, run `37435750876`.
Событие сообщает именно `naturalWidth=836`, `naturalHeight=356`,
`srcLength=10242`, native EncodingError на `INB-000000000226`.
Во всех четырёх случаях 225 decode завершены, передача/отметки отсутствуют.
Первичны ошибка подготовки и cleanup; ожидание transfer заканчивается таймаутом
уже после них. В callback сохранения отметок выполнение не входило.

**Ограничение исходных артефактов:** PNG/data URL 226 не сохранён. В снятом HTML
нет data URL/iframe: product catch удалил его до диагностического снимка.
Проверку именно этих байтов и одиночный native decode в Chromium выполнить
по имеющимся файлам невозможно. Не объявлять их валидность установленной.

Неизменённый `renderBarcodeDataUrl` и настоящий JsBarcode локально вызваны для
226 с integer raster canvas (jsdom/PNG, без браузера). PNG parser с CRC/inflate
проверкой принимает результат 836×356; независимый ZXing CODE128 возвращает
точный `INB-000000000226`. Длина реконструированного data URL 2850, а не remote
10242: PNG-кодировщик иной, побайтного равенства не заявлено. Это проверка
генератора/содержимого отдельно от native decode исходного runner PNG.

Существующий helper вызывает все 300 `image.decode()` в одном проходе
`Promise.all`, без промежуточного кадра. Успешный decode временно удерживает
декодированный ресурс через отрисовку; один Promise.all сам по себе ресурсами
не владеет, проблема в одновременных native запросах. 225 растров RGBA дают
267854400 bytes (255.45 MiB); 226 дают 269044864 (256.58 MiB).
Точный лимит/внутренние locks данного Chromium не измерены; совпадение с 256 MiB
остаётся сильной гипотезой, а не доказательством установленного лимита.
Публичный исходник Chromium через CLI получить не удалось (URLError), поэтому
внешняя проверка конкретной реализации не заявлена.

До правки модель ресурса, занятого до кадра, на реальном helper воспроизвела
отказ при 226: начаты 300 запросов, нет промежуточного кадра, ноль передач и
сохранений. Это объясняет выбранное изменение расписания, но модель не заменяет
нативный результат удалённого браузера.

### Изменение и локальная проверка

Только awaitable-путь с `beforeTransfer` декодирует изображения параллельными
группами до 32. Между группами ждёт два кадра родительского окна, чтобы пройти
границу отрисовки; скрытый iframe для этого не используется. Если вкладка
приостанавливает кадры, task fallback через 100 ms снимает ожидание кадра и
отменяет оставшийся callback. Это расписание подготовки, не таймаут decode,
не повтор native запроса и не ослабление тестового таймаута. В фоне влияние
на native бюджет остаётся предметом удалённой проверки.

Все группы готовятся до прежних persistence callback и единственного `print()`.
Отказ группы прекращает подготовку с прежним cleanup; передача частичной ленты
не разрешается. Все этикетки остаются в одном исходном HTML/iframe; размер группы
не ограничивает число этикеток или печатную задачу. Legacy void-путь, используемый
scan-to-print, сохраняет прежний concurrent decode. Экран, восстановление C7/C8,
идентификатор попытки, отметки, рендерер PNG и HTML/CSS не менялись.

Локальные результаты:

### Передача ведущему и отдельному удалённому тестировщику

После публикации закрепить точный продуктовый SHA этого commit в принадлежащем
тестировщику runner. Приоритет — существующие неизменённые серии приёмки/возврата
300, PDF 300×58×40 и decode первой/средней/последней, полный C5 с corrected retry,
C6 single attempt и достигнутые C7/C8 после первой передачи. Перепроверить 200
и control scan-to-print. Не снижать deviceScaleFactor/разрешение, количество,
качество, утверждения или таймауты. Сохранить исходный PNG 226 до cleanup и
отдельно проверить его native decode в изоляции, чтобы проверить оставшуюся
альтернативу повреждённого источника. При отказе после кадров гипотеза ограничения
ресурсов требует дальнейшей диагностики; успешный pure model её не закрывает.

**C4 — открытое расхождение с оснасткой, не PASS:** frozen тест ставит hold и
до его снятия ждёт `decodeStarted === n`. Групповая подготовка начинает первые
32 и ждёт их завершения; на 200/300 этот точный тест остановится до снятия hold.
Тест и ожидания разработчиком не менялись и не ослаблялись. Ведущий должен передать
это отдельному тестировщику: требование R3 запрещает поштучные внешние ожидания,
но текущая оснастка дополнительно требует сразу всех n native decode. Это нельзя
молча выдать за пройденный контракт или скрыть исключением C4 из отчёта.
Новая логика расписания также требует отдельной постоянной проверки тестировщика:
перекрытие decode внутри группы, кадр между группами, отсутствие передачи при
отказе поздней группы, отсутствие зависания при остановленных кадрах и неизменный
legacy scan-to-print. Собственный локальный probe разработчика такой охраной
не считается; передача workflow и новой постоянной охраны остаётся у ведущего.

Далее — независимое ревью точного SHA и приёмка, затем полный CI. Кандидат
не выпускать отдельно от пакета. Mac Chrome/локальный браузер, агенты, навыки,
секреты/live API, принтер, merge и deploy не использовались.
