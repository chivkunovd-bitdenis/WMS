## До накатки

**1. Снять полный дамп боевой базы.** Отката миграций не будет: две ревизии
(`20260826_0111` и соседняя) намеренно ломают `downgrade` — история фактов
операций объявлена только-на-добавление. Единственный путь назад — восстановление
из дампа. Без свежего дампа не стартуем.

**2. Пересчитать отрицательные остатки.** На 29.08 их было 116 строк. После
списания фантомных возвратов число меняется. Проверка перед стартом:

```sql
select count(*) from inventory_balances
 where quantity < 0 or quantity_unpacked < 0 or quantity_packed < 0;
```

Само по себе это уже не блокер: три проверки «остаток ≥ 0» из миграции
`20260828_0130` убраны, накатка на таких строках больше не падает. Цифра нужна
для сверки после.

**3. Репетиция.** `scripts/deploy/probe-migrations.sh <ветка>` — снимает копию
боевой базы, гоняет на ней миграции с замером. Прогон 29.08: 27 миграций,
7 секунд, копия со 116 отрицательными остатками, финальная ревизия
`20260829_0241`.

`scripts/deploy/mankaev-fbs-rule-20260829.sql`. Раньше нельзя — колонок

## Проверка, что дефект возврата ушёл

```sql
-- должно быть 0: возвраты по заказам, чья поставка уже передана
select count(*)
  from fbs_shipment_reversal_ledger l
  join fbs_orders o    on o.id = l.fbs_order_id
  join fbs_supplies sp on sp.wb_supply_id = o.wb_supply_id
 where l.reversed_at > '<момент выкатки>'
   and sp.delivered_at is not null;
```

## Проверка, что публикация остатков не разъехалась

```sql
-- у кого включён обмен: до выкатки это ровно один продавец, ИП Манкаев Т.Т.
select s.name, b.wb_warehouse_id, b.stock_sync_enabled, b.last_sync_status, b.last_sync_at
  from fbs_warehouse_bindings b join sellers s on s.id = b.seller_id
 where b.stock_sync_enabled;
```

Если после выкатки включённых стало больше — это ошибка, разбираться до того,
как фоновая задача успеет опубликовать.
