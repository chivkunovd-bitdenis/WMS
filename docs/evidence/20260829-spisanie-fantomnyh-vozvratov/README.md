# Снятие с остатка возвратов, которых не было

**Дата:** 29 августа 2026
**Контур:** боевой (`sellerfocus.pro`, ветка `etalon`)
**Решение владельца:** снять, дано в переписке 29.08

---

## Что случилось

Когда Wildberries присылает статус отмены заказа, система **автоматически
прибавляет штуку обратно на склад**. Делает это функция
`reverse_fbs_shipment_if_needed` в `backend/app/services/fbs_cancellation_service.py`.

Она проверяет ровно две вещи: есть ли запись о списании и не возвращали ли уже.
**Приехала ли посылка физически — не проверяет.**

## Как вскрылось

Сверили две цифры:

| | |
|---|---:|
| Система насчитала возвратов | **283** |
| Склад (ФФ Империя Львов) видел коробок | **22** (9 накопленных + 13 приехавших 29.08) |

Разрыв больше чем в десять раз. Значит две с половиной сотни «возвратов» —
это прибавки в базе без товара на полке.

## К чему это привело

Остаток показывал пары, которых на складе нет. Кладовщик брал заказ в работу,
шёл искать и не находил. Отсюда жалобы «в системе есть, а на складе нет»
и затянутые сроки отгрузки.

**На приток заказов это не влияло.** Публикация остатков в кабинет у этих
продавцов выключена (`stock_sync_enabled = false`, `last_sync_at` пустой,
ноль строк публикации). Wildberries наш остаток не видит и продаёт по своему
числу.

---

## Что сняли

Формула: по каждому товару снимаем `min(насчитано возвратов, текущий остаток)`.

Минимум принципиален. Часть возвращённых пар **уже перепродана заново**: коробка
приехала, легла в кучу, уехала другому покупателю. Их снимать нельзя — товара
уже нет, остаток ушёл бы в минус.

| Продавец | Остаток до | Снято | Остаток после |
|---|---:|---:|---:|
| ИП Чжоу | 1742 | **94** | 1648 |
| Loviana | 759 | **54** | 705 |
| ООО Фэшн | 2683 | **2** | 2681 |
| **Итого** | | **150** | |

Двадцать восемь позиций стали нулевыми. **Ни одна не ушла в минус** — формула
не позволяет.

## Чего не делали

**ИП Агишеву не трогали.** У неё остаток отрицательный по другой причине —
списывали товар, который не приходовали. Формула дала бы прибавку вместо снятия.

**Автоматический приход при отмене не выключали.** Это правка кода, она уходит
отдельной задачей. Пока она не выкачена, фантомы будут набегать снова, и снятие
придётся повторить.

---

## Как найти эти движения

Все движения корректировки помечены отдельным типом:

```sql
select * from inventory_movements where movement_type = 'correction_phantom_return';
```

По ним же делается откат, если понадобится: те же строки с обратным знаком.

## Скрипт

`scripts/audit/spisat_fantomnye_vozvraty.py`

Пробный прогон — без аргументов, запись — с `--apply`. Внутри подробные
комментарии: почему минимум, почему отдельный тип движения, что не трогаем.

---

## Что осталось сделать

**Выключить автоматический приход при отмене.** Отдельная задача, фактура
подготовлена. Пока не сделано — фантомы копятся.

**Приходовать возвраты документом.** Механизм на бою есть: приёмка имеет тип
операции `return`, одна такая в базе уже проведена. Пользоваться им никто не
начал.

**Пересчитать склад.** Все три крупные приёмки приняты без единого скана —
`inbound_intake_boxes` пустая. Сколько реально привезли, не знает никто.
Единственная приёмка с пересчётом (Чжоу №000029, 113 коробов) показала
недостачу 91 штуку из 1665.

## Что проверили и что это доказало

Аудит всех положительных движений по трём продавцам:

| Источник прихода | Штук |
|---|---:|
| Приёмка (все привязаны к документу) | 5144 |
| Передача прав | 2794 |
| Возврат при отмене | 244 |
| Прочее | 29 |

**Товара из ниоткуда в системе нет.** Каждая штука имеет документ-основание.

Сверка заявленного и принятого по приёмкам:

| | Штук |
|---|---:|
| Заявил продавец | 6742 |
| Приняли мы | 6645 |
| **Разница** | **−97** |

**Система никогда не показывала больше, чем заявил продавец.** Наоборот,
на 97 штук меньше. Разрыв между учётом и полкой возник не в системе, а в
приёмке без пересчёта.
