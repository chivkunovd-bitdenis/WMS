# Возврат на остаток после передачи поставки WB — дефект сторожа

**Дата:** 29.08.2026
**Статус:** дефект найден, фикс описан, **на бой не выкачен** — ждёт команды владельца.
**Затронуто:** `backend/app/services/fbs_cancellation_service.py`

---

## Коротко

Когда WB отменяет заказ, WMS возвращает товар на остаток. Это верно только
если товар ещё лежит у нас. Если поставку уже передали WB и коробки уехали —
возвращать нечего, остаток становится завышенным.

Сторож, поставленный 29.08 в 16:58, должен был это отсекать. Он отсекает не
всё: проверяет статус **заказа**, а надо проверять факт передачи **поставки**.

## Почему сторож пропустил

Текущее условие в `reverse_fbs_shipment_if_needed`:

```python
supplier_status = (order.supplier_status or "").strip().lower()
if skip_if_supplier_complete and supplier_status == SUPPLIER_STATUS_COMPLETE:
    # не возвращаем товар на остаток
```

Проверяется поле `fbs_orders.supplier_status`. Оно приходит из WB и **меняется
после передачи**: у отменённых заказов WB ставит `cancel`, у части — оставляет
`confirm`. Как только значение перестаёт быть `complete`, условие ложно и
возврат проводится.

`fbs_supplies.delivered_at` таким свойством не обладает: он заполняется в момент
передачи и задним числом не снимается. Это и есть надёжный признак того, что
товар покинул склад.

---

## Правило, которое нужно (согласовано с владельцем 29.08)

> Если отгрузку ещё не провели, а отмена пришла — приходуем: товар всё равно
> никуда не повезут, он лежит у нас на полке.
> Если поставку уже передали WB — не приходуем: товара на складе нет.

## Фикс

В `backend/app/services/fbs_cancellation_service.py`, в
`reverse_fbs_shipment_if_needed`: вместо проверки статуса заказа проверять факт
передачи поставки, оставив проверку статуса как дополнительную.

```python
# Факт передачи поставки — единственный надёжный признак того, что товар
# физически покинул склад. `order.supplier_status` для этого не годится:
# WB после передачи меняет его на `cancel`/`confirm`, и проверка на
# `complete` перестаёт срабатывать (дефект 29.08.2026, см. этот док).
supply_delivered = False
if order.wb_supply_id:
    supply = (await session.execute(
        select(FbsSupply).where(
            FbsSupply.tenant_id == order.tenant_id,
            FbsSupply.wb_supply_id == order.wb_supply_id,
        )
    )).scalar_one_or_none()
    supply_delivered = supply is not None and supply.delivered_at is not None

supplier_status = (order.supplier_status or "").strip().lower()
already_handed_over = supply_delivered or supplier_status == SUPPLIER_STATUS_COMPLETE

if skip_if_supplier_complete and already_handed_over:
    logger.warning(
        "fbs_reversal_skipped_after_handover order=%s supply=%s delivered=%s status=%s",
        order.wb_order_id, order.wb_supply_id, supply_delivered, supplier_status,
    )
    ledger.reversed_at = datetime.now(UTC)   # отметка есть, движения нет
    return False
```

Связь заказа с поставкой — по тексту `wb_supply_id`, **не** по `supply_id`:
у отменённых заказов `fbs_orders.supply_id` пустой, заполнено только текстовое поле.

### Тесты (обязательны, без них не катим)

- `TC-NEW-001` — Given заказ списан и его поставка передана (`delivered_at`
  заполнен), а `supplier_status` пришёл как `cancel`, When приходит отмена,
  Then движения по складу нет, `reversed_at` проставлен, функция вернула `False`.
- `TC-NEW-002` — Given заказ списан, поставка НЕ передана (`delivered_at` пустой),
  When приходит отмена, Then товар возвращается на остаток (ожидаемое поведение,
  негативный контроль — сторож не должен блокировать этот случай).
- `TC-NEW-003` — Given у заказа нет `wb_supply_id` вовсе, When приходит отмена,
  Then возврат проводится (нет поставки — нечего было передавать).
