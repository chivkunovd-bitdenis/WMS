# WMS Feature Gate Protocol

Этот документ обязателен для любой WMS-задачи, где есть фича, рефакторинг,
изменение процесса, изменение UI/UX, складской сценарий, FBS/FBO/MP, приемка,
отгрузка, упаковка, каталог, остатки, сотрудники, доступы или печать.

Если задача попадает под этот документ, агент обязан прочитать его до любой
разработки. Нельзя заменять этот протокол общим планом, зелеными тестами,
описанием карточек или одним большим "оркестратор все посмотрел".

## Главный запрет

Запрещено начинать разработку фичи, пока по этой конкретной фиче нет явного
product OK.

Запрещено смешивать несколько фичей в один проход. Одна фича проходит один
изолированный цикл. Если фича большая, оркестратор сначала режет ее на
атомарные подфичи, и каждая подфича проходит этот же цикл отдельно.

Запрещено говорить "готово", "принято", "product approved", "browser QA passed"
или "release-ready", если соответствующий gate не был реально выполнен и
зафиксирован.

## Обязательная цепочка по каждой фиче

Каждая фича проходит строго в таком порядке:

1. Feature Intake
2. Business Analyst Agent
3. Product / UX Review Agent
4. Atomic Dev Agent
5. Code Review Agent
6. Browser Product QA Agent
7. Feature Integration Result

Переход к следующему шагу запрещен без явного результата предыдущего шага.

## Изоляция агентов

На каждую фичу должны быть отдельные роли:

- один BA agent;
- один Product / UX agent;
- один Atomic Dev agent;
- один Tester / Browser Product QA agent.

Оркестратор управляет очередью, но не подменяет эти роли своим общим выводом.
Если subagents недоступны, задача получает статус `BLOCKED_NO_ISOLATED_AGENTS`.
Оркестратор не имеет права подменять изолированных агентов собой и не имеет
права начинать разработку.

## Gate 1. Feature Intake

Оркестратор обязан создать карточку фичи:

```md
id:
title:
status:
ba_agent:
product_agent:
dev_agent:
qa_agent:
business_goal:
warehouse_user:
main_real_world_scenario:
screens_touched:
required_visible_data:
forbidden_ui_noise:
primary_actions:
secondary_actions:
empty_state:
error_state:
success_state:
business_assumptions:
product_verdict:
dev_result:
code_review_result:
browser_qa_result:
changed_files:
tests_run:
commit_or_patch_ref:
blocking_issues:
```

Если карточки нет, фича не существует как управляемая единица работы.

## Gate 2. Business Analyst Agent

BA agent обязан описать:

- что делаем;
- зачем это нужно бизнесу;
- кто пользователь;
- какую складскую работу он делает;
- какой экран открывает;
- что должен увидеть;
- какое главное действие выполняет;
- какой результат получает;
- какие данные обязательны;
- какие данные лишние;
- какие состояния нужны: пусто, ошибка, успех;
- каким способом реализуем процесс;
- почему именно так, а не отдельным экраном, вкладкой или сложным процессом.

Если данных не хватает, BA не спрашивает пользователя, а принимает разумное
складское допущение и явно фиксирует его.

Выход gate: `BA_READY` или `BA_REWORK`.

Разработка запрещена, если нет `BA_READY`.

## Gate 3. Product / UX Review Agent

Product / UX agent проверяет BA artifact до разработки. Он смотрит глазами
обычного сотрудника fulfillment/Wildberries/FBS, которому нужно быстро выполнить
складскую работу без объяснений.

Он обязан проверить:

- это похоже на реальный складской процесс;
- понятно, что делать дальше;
- основной сценарий выполняется минимальным числом кликов;
- экран не перегружен;
- нет лишних чипов, лейблов, бейджей;
- нет технического текста, подсказок для разработчиков и внутренних комментариев;
- нет дублирующих кнопок;
- нет лишних колонок;
- колонки, поля и кнопки имеют аккуратные рабочие размеры и не раздувают экран;
- длинные SKU, штрихкоды, названия, статусы и комментарии не ломают строки, не
  наезжают на соседние колонки и не делают кнопки нестабильными для клика;
- нужные колонки видны;
- действие не ломает приемку, отгрузку, сборку, сканирование, упаковку,
  маркировку или учет остатков;
- изменение не превращает WMS в Frankenstein UI из отдельных кусков.

Product / UX agent обязан дать явный verdict:

- `PRODUCT_APPROVED_FOR_DEV`;
- `PRODUCT_REWORK_REQUIRED`.

Если verdict не `PRODUCT_APPROVED_FOR_DEV`, разработчик не стартует. Фича
возвращается на BA/UX. Запрещено "параллельно начать кодить, пока продукт думает".

## Gate 4. Atomic Dev Agent

Atomic Dev Agent реализует только одну утвержденную фичу.

Правила:

- один dev agent = одна фича;
- не брать соседние фичи;
- не делать незапрошенный redesign;
- не менять глобальную архитектуру без необходимости;
- сохранять существующие WMS-паттерны;
- не добавлять технический текст в UI;
- не добавлять декоративный шум;
- не плодить чипы, лейблы, кнопки и колонки;
- держать размеры колонок, полей и кнопок компактными: никакие значения не
  должны раздувать таблицу, ломать переносы или перекрывать соседние действия;
- не трогать секреты, токены, secret panels, Railway variables и кабинеты ключей;
- по завершении перечислить измененные файлы и пользовательские сценарии.

Выход gate: `DEV_DONE` или `DEV_BLOCKED`.

## Gate 5. Code Review Agent

Code Review Agent проверяет только реализованную фичу и ее границы.

Он ищет:

- регрессии;
- сломанные сценарии;
- плохие состояния ошибок;
- лишнюю связанность;
- нарушение существующих паттернов;
- отсутствие нужных тестов;
- риск конфликтов с другими фичами;
- UI-мусор, если он попал в код.

Code review не заменяет product review и не заменяет browser QA.

Выход gate: `CODE_REVIEW_PASSED` или `CODE_REVIEW_FAILED`.

Если code review failed, фича возвращается в dev.

## Gate 6. Browser Product QA Agent

Browser Product QA Agent обязан открыть реальный UI в браузере и руками пройти
реальный складской сценарий. API, unit tests, build, screenshots без кликов и
локальные рассуждения не считаются заменой.

Он обязан проверить:

1. Реальный экран открывается.
2. Основной сценарий проходит руками.
3. Кнопки нажимаются.
4. Ввод, сканирование или выбор работают.
5. Успех виден пользователю.
6. Ошибка понятна пользователю.
7. Пустое состояние понятно.
8. UI не перегружен.
9. Нет технического мусора.
10. Нет лишних чипов, лейблов, столбцов.
11. Нет дублирующих кнопок.
12. Сотруднику fulfillment понятно следующее действие.
13. Колонки, поля и кнопки выглядят аккуратно и лаконично: длинные значения не
    распирают таблицу, не перекрывают действия и не делают клики нестабильными.

Главный вопрос QA:

> Передо мной конкретная складская работа. Я понимаю, что сейчас сделать, куда
> нажать, что отсканировать, где мой товар, где успех, где ошибка, и мне не
> мешает лишняя техническая муть?

Выход gate:

- `BROWSER_PRODUCT_QA_PASSED`;
- `BROWSER_PRODUCT_QA_FAILED`;
- `BROWSER_PRODUCT_QA_BLOCKED`.

Если staging, backend, миграции, авторизация или данные не дают пройти сценарий,
статус только `BROWSER_PRODUCT_QA_BLOCKED`. Нельзя записывать blocked как passed.

Если browser QA failed или blocked, фича не интегрируется как завершенная.

## Параллельность

Параллельно можно запускать только независимые фичи, у которых не пересекаются:

- экран;
- компонент;
- API route;
- сервис;
- модель данных;
- таблица БД;
- тестовый сценарий;
- печатный документ;
- складской процесс.

Если зоны пересекаются, оркестратор обязан назначить порядок. Два dev agents не
имеют права одновременно менять один экран, сервис, таблицу или компонент.

## Финальный integration review

После per-feature browser QA по всем фичам запускается общий reviewer. Он
проверяет все изменения вместе:

- нет UX-разнобоя между экранами;
- нет разных названий для одной сущности;
- нет конфликтующих кнопок;
- нет повторяющихся действий;
- не стало слишком много экранов;
- не появились лишние колонки, чипы, лейблы;
- не сломан общий FBS/FBO/MP/fulfillment процесс;
- нет ощущения, что каждую фичу делал отдельный человек без общей системы.

Если общий reviewer находит проблему, конкретные фичи возвращаются на доработку.

## Финальный browser regression

После общего reviewer обязателен общий браузерный прогон затронутых процессов:

- открыть ключевые экраны;
- пройти основные сценарии;
- проверить переходы между экранами;
- проверить, что фичи не мешают друг другу;
- проверить, что интерфейс остался простым;
- проверить, что сотруднику fulfillment понятно, что делать дальше;
- проверить отсутствие технических надписей, лишних чипов, лишних кнопок и
  лишних колонок.

Без финального browser regression итерация не завершена.

## Definition of Done

Фича считается done только если:

- есть карточка;
- есть BA_READY;
- есть PRODUCT_APPROVED_FOR_DEV до разработки;
- есть DEV_DONE;
- есть CODE_REVIEW_PASSED;
- есть BROWSER_PRODUCT_QA_PASSED;
- изменения сохранены в Git.

Итерация считается done только если:

- все фичи done;
- общий integration review passed;
- общий browser regression passed;
- изменения закоммичены;
- известен итоговый commit SHA;
- если нужно другим людям или CI, ветка запушена;
- если нужен staging, он собран именно из итогового SHA;
- если нужен deploy, явно проверено, какой SHA развернут.

Если какой-то gate не пройден, статус должен быть честным: `blocked`, `failed`
или `partial`. Запрещено называть такую работу готовой.
