# WMS-617: повторяемый набор для записи на staging

Реализация — `backend/app/cli/wms617_video_demo.py`. Модуль находится внутри
`app`, поэтому попадает в существующий Railway Docker image без изменения
рецепта сборки. Требования и вердикты приёмки остаются в
[WMS-617](../requirements/WMS-617.md); этот документ не заменяет приёмку.

## Граница безопасности

Команда принимает только `APP_ENV=staging`, точный tenant
`9c31f3f4-ce62-4c1f-891a-295b278f1e69` с именем `WMS Staging` и точный WB FBS base
`http://wb-emulator.railway.internal:8000`. Автор — существующий администратор
этого tenant, склад — существующий операционный склад этого tenant. Настройки
окружения команда не меняет. При несовпадении нужно исправить назначение запуска,
а не подменять окружение production флагом `APP_ENV`.

Команда не создаёт и не читает значения credentials, не создаёт пользователей,
не меняет права и не выполняет HTTP/provider-вызовы. Фоновые публикации остатков,
которые обычно планирует сервис движения, очищаются только в отдельной сессии
этого seed перед её единственным commit. Трансляция для новых товаров и привязок
отключена. Остальные WB/Ozon URL не используются.

Все UUID набора детерминированы через отдельное пространство WMS617. Существующие
`KURTKA-VIDEO-*`, `PIDZHAK-VIDEO-*`, `FBS-VIDEO-*`, `FBS-TEST-*`, `EMU-*` не изменяются;
их состояние раскрывается в `before.legacy_audit`/`after.legacy_audit`:
число SKU/селлеров/заказов/поставок, алиасы и основной ШК, физический остаток,
резерв и свободный остаток по складу, ячейки/тара, движения и ссылки на приходы,
статусы заказов/поставок, внешние ID и маршруты, инвентаризации с фактами,
общая сборка, начисления/счета/ставки и выбранные/невыбранные карточки.
Все чтения ограничены точным tenant и применимым складом; старые строки не меняются.

До добавления строк выбирается конкретный согласованный `candidate` из шести SKU
двух селлеров и связанных заказов/поставок. `excluded_product_ids` остаются в полном
аудите, но неполный посторонний VIDEO-товар не мешает использовать пригодные шесть.
Для кандидата вычисляется `local_readiness_checks`: полный локальный набор
даёт `decision=reuse_local_scope` и `created=false` без записи в БД. Если хотя бы
одного проверяемого элемента недостаёт, manifest содержит `decision=additive_scope`,
точный список `gaps` и причину: сохранить прежний набор и создать отдельный WMS617.
Такое решение относится к локальным данным. `provider_verification=unverified`
остаётся явным даже при reuse: внешние ID — ссылки WMS, не доказательство наличия
данных в эмуляторе; readiness внешней передачи этот аудит не утверждает.
Коды ЧЗ учитываются только для конкретных маркируемых SKU кандидата и их селлера.
Для каждого выбранного селлера независимо требуются профиль, ставка и начисление,
связанное с его проведённым приходом и его ставкой. Выставленный счёт должен иметь
источники минимум двух начислений того же селлера; произвольные три начисления у
одного селлера не покрывают отсутствие данных второго. Эти связи и числа видны
в `candidate.marking_by_product`, `billing_by_seller`, `invoice_ids`. Совпадение UUID с чужой записью прерывает
транзакцию. Все новые строки сохраняются одной транзакцией; поздняя ошибка
откатывает и документы, и остатки, и начисления. PostgreSQL-блокировка строки
tenant сериализует параллельные запуски этого seed.

Повторный `--apply` при наличии якорного документа не пишет ничего, не сбрасывает
primary barcode, сроки, упаковку, остатки или фактические количества. Он возвращает
актуальный audit. Удалённые после первого запуска строки автоматически не
восстанавливаются: `structural_complete=false` требует разбирательства, а не
сброса работы оператора. Сроки заказов относительны к первому запуску и затем
заморожены; audit показывает, какие уже просрочены.

## Состав

- Два новых селлера `WMS617 · Видео селлер 1/2`, синтетические реквизиты и ставка
  приёмки 500 копеек за штуку. Ни реквизиты, ни счёт не предназначены для оплаты.
- `WMS617-01…06`: обычный WB, WB с ЧЗ, WB второго селлера, два Ozon и связанный
  WB/Ozon товар. По два разных `ProductBarcode`, второй выбран основным. Данные
  параметров и карточки площадки заполнены; связанный товар имеет две привязки.
- Три проведённых синтетических прихода `WMS617-IN-1/2/3`, по 30 единиц каждого
  SKU. Семь движений через штатный inventory service с ссылкой на строку прихода
  и существующего автора. Первый товар размещён 20+10 в двух новых ячейках.
  Новые ячейки: `WMS617-01/02`, скан-коды `WMS617-CELL-1/2`; складской короб
  `WMS617-BOX-01` содержит 20 единиц `WMS617-01` в первой ячейке, ещё 10 лежат
  россыпью во второй ячейке. Склад существующий, новых складов нет.
- Восемь WB-заказов и четыре Ozon-заказа, один Ozon — на три единицы. Итого резерв
  14 единиц. Два WB и один Ozon оставлены новыми; остальные образуют обычную
  WB-поставку, две WB-поставки разных селлеров в общей сборке и Ozon-поставку.
  Два WB-маршрута: склад/СЦ и ПВЗ. Один новый WB-заказ намеренно просрочен.
- Две непроведённые инвентаризации по всем шести SKU: пустой факт и частично
  введённый факт первого товара. Ведомость показывает основной ШК и резервы.
- 20 синтетических кодов ЧЗ для `WMS617-02` в пуле; они годятся только для
  тестового контура, не являются реальными зарегистрированными кодами.
- WB и Ozon snapshots: выбранные карточки и по одной ещё не выбранной карточке
  `WMS617-07/08`. Три начисления связаны с тремя приходами; первые два включены
  в выставленный V2-счёт `WMS617-DEMO-001` на 750 рублей. У второго селлера
  отдельное начисление на 150 рублей.

## Неподтверждённые сценарии

Новые WB supply/order ID записаны в `wb_emulator_manifest`, но в БД эмулятора этот
seed не пишет. Новым селлерам не создаются credentials, поэтому вызовы WB от их
имени ещё не настроены. Нельзя показывать этот набор как успешную передачу,
синхронизацию доставки или получение настоящего marketplace-стикера. Отдельная
подготовка/проверка существующего тестового provider-контура нужна до таких
действий. Старые доставки перечислены в `legacy_delivery_unverified`; их наличие
не означает, что соответствующая поставка существует в эмуляторе.

Ozon подготовлен для локального чтения/подбора/упаковки; удалённые операции также
не подтверждены. Ничего не отправляется в настоящие WB/Ozon. Скрипт не создаёт
фиктивно отгруженную поставку ради наполнения вкладки: нет доказанного внешнего
состояния и связанного списания. Мобильный вход, физические сканы, принтер,
изоляцию на реальных тестовых учётках и браузерный маршрут проверяет ведущий с
аналитиком. Данные не реализуют отсутствующие WMS-494/498/499.

## Публикация и применение

Ведущий после ревью и проверки актуальной истории staging выполняет из чистого
checkout кандидата:

```sh
git fetch origin
git merge-base --is-ancestor origin/staging HEAD
bash scripts/railway-staging-deploy.sh
```

Затем необходимо подтвердить фактический SHA API. В shell **только staging API**,
где текущий каталог `/app` и уже установлены штатные переменные подключения:

```sh
python -m app.cli.wms617_video_demo --audit \
  --tenant-id 9c31f3f4-ce62-4c1f-891a-295b278f1e69 \
  --warehouse-id 307c0ccd-9a6b-41df-9180-f8ed68022237 \
  --actor-id be635fd2-de66-4892-9513-35d28686e686 \
  --manifest /tmp/wms617-before.json
python -m app.cli.wms617_video_demo --apply \
  --tenant-id 9c31f3f4-ce62-4c1f-891a-295b278f1e69 \
  --warehouse-id 307c0ccd-9a6b-41df-9180-f8ed68022237 \
  --actor-id be635fd2-de66-4892-9513-35d28686e686 \
  --manifest /tmp/wms617-apply.json
python -m app.cli.wms617_video_demo --audit \
  --tenant-id 9c31f3f4-ce62-4c1f-891a-295b278f1e69 \
  --warehouse-id 307c0ccd-9a6b-41df-9180-f8ed68022237 \
  --actor-id be635fd2-de66-4892-9513-35d28686e686 \
  --manifest /tmp/wms617-after.json
```

Каждый manifest создаётся эксклюзивно: существующий файл не перезаписывается.
Before/after содержит только разрешённые поля, без секретов. После запуска
перенести JSON из контейнера в постоянный Git-каталог доказательств WMS-617 и
закоммитить. Файлы `/tmp` сами по себе не являются сохранённым результатом.
Точные product/order/supply/count/assembly/invoice UUID и скан-коды находятся в
manifest. Для проверки повтора снова выполнить `--apply` с новым именем файла:
ожидается `created=false`, прежние ID/количества и сохранённая работа оператора.

## Локальные проверки

```sh
cd backend
.venv/bin/ruff check .
.venv/bin/mypy .
.venv/bin/pytest -n auto -q tests/test_wms617_video_demo.py
```

Также этот файл проверен на отдельной локальной PostgreSQL-базе `wms_test_wms617_seed`.
Проверки охватывают guards, атомарный rollback, повтор без DML, сохранение
операторских изменений, отсутствие изменения старых/чужих товаров, ссылки
движений на документы, чтение workspace четырёх поставок, скан обоих алиасов,
каталог обеих площадок, печатную ведомость с 14 резервами и чтение счёта/ставки.
Регрессия замечаний ревью: штатный `pick_scan` проходит ячейку → короб → второй
алиас товара и списывает физический остаток короба с 20 до 19; обе инвентаризации
ссылаются на тот же контейнер. Полный прежний VIDEO-набор выбирается для reuse
без INSERT/UPDATE/DELETE; неполный набор даёт additive_scope с gaps и сохраняется
неизменным.
