# WMS-399 · Дизайн-хендофф чата (для Codex)

Статус: `ПРОЕКТИРОВАНИЕ · 09.09.2026`. Дизайн и весь код прототипа —
Claude Opus, в рамках сессии, восстановленной координатором 09.09.2026.
Codex дальше собирает бэкенд и подключает эти экраны. Все правки в
исходниках прототипа — включая технические (совместимость с версиями
MUI/TS, устранение ошибок компиляции, мелкая уборка) — вносит тот же
Opus по замечаниям Codex; Codex не редактирует React-код прототипа
самостоятельно и не переверстывает дизайн. Codex прогоняет
`vite build`, `tsc -b --noEmit` и браузерную проверку и возвращает
Opus точные диагностики.

Требования — в `REQUIREMENTS_RU.md`. Здесь: как открыть прототип, как
он устроен, какие контракты нужно сохранить и где сознательные пробелы.

## 1. Как открыть прототип

Прототип живёт в `prototypes/wms399-chat/`. Он использует уже
установленный `node_modules` основного фронтенда через симлинк
`prototypes/wms399-chat/node_modules → WMS/frontend/node_modules`.
Никаких `npm install`, никаких новых зависимостей — только React 19,
MUI 9, TypeScript 6, Vite 8 (`plugin-react` 6).

Из корня рабочей копии:

```bash
cd prototypes/wms399-chat
node_modules/.bin/vite            # dev, слушает http://127.0.0.1:5199/
# или сборка + предпросмотр
node_modules/.bin/vite build
node_modules/.bin/vite preview
# и/или тайп-проверка (авторская конфигурация)
node_modules/.bin/tsc -b --noEmit
```

Порт `5199` зафиксирован в `vite.config.ts` (`strictPort: true`), чтобы
не конкурировать с боевыми и стейдж-приложениями. Приложение — SPA c
hash-роутингом; никакой серверной части у прототипа нет.

Реальные API прототип не вызывает. Все данные — синтетические, живут в
`src/data/seed.ts`. Загрузка вложений имитируется через
`URL.createObjectURL` для локальных `File` объектов, изображения из seed
приходят как inline SVG-`data:` URI. Ни сети, ни секретов не читаем.

## 2. Карта маршрутов и экранов

Роутинг — hash-based, чтобы прототип открывался как статический файл и
не требовал сервера. Реальные маршруты в основном фронте, естественно,
будут path-based; названия сегментов совпадают, менять их не надо.

| Hash | Экран | Файл-точка входа |
|------|-------|-------------------|
| `#/inbox` | Инбокс каналов текущей роли | `src/inbox/InboxScreen.tsx` |
| `#/c/<conversationId>` | Открытый канал (лента + композер + правая панель) | `src/conversation/ConversationScreen.tsx` |
| `#/c/<conversationId>?msg=<messageId>` | Тот же канал с прыжком/подсветкой сообщения | там же (`flashMessageId`) |
| `#/c/<conversationId>/t/<rootMessageId>` | Тред открыт в правой панели | `src/conversation/ThreadPanel.tsx` |
| `#/search` | Кросс-канальный поиск | `src/search/SearchScreen.tsx` |
| `#/notifications` | Центр уведомлений | `src/notifications/NotificationsScreen.tsx` |
| `#/prefs` | Настройки уведомлений | `src/notifications/PreferencesScreen.tsx` |

Плюс модальные и drawer-поверхности, которые не имеют собственного
маршрута (их состояние — в глобальном UI-стейте):

- Пикер документов (`DocumentPickerDialog`) — открывается из композера.
- Предпросмотр документа (`DocumentPreviewDrawer`) — открывается по кнопке
  «Открыть документ» из карточки/шапки канала.
- Ящик участников (`ParticipantsDrawer`) — из шапки канала.
- Лайтбокс изображений (`Lightbox`) — по клику на превью изображения.
- Меню демо-состояний (`DemoStateDrawer`) — по иконке молотка в топ-баре.

Из этих drawer-поверхностей достижимы **все обязательные состояния из
требований** (см. раздел 4 ниже) — руками через демо-меню и через
обычные UI-действия.

## 3. Дизайн-токены и палитра

Тема — `src/theme.ts`. Она специально повторяет базу существующего WMS
(`frontend/src/mui/theme.ts`), чтобы визуально не диссонировать с
порталом ФФ/селлера:

- Основной шрифт — `Inter` (подгружается из Google Fonts в `index.html`).
- Основные цвета:
  - `primary.main = #5b21b6` (фиолетовый бренд), `primary.dark = #4c1d95`, `primary.light = #7c3aed`.
  - `warning.main = #c2410c`, `warning.light = #fff7ed` — внутренние
    заметки и флаг «требует ответа».
  - `info.main = #0f766e`, `info.light = #ecfeff` — системные события.
  - Текст: `#0f172a` / `#475569`, фон приложения `#e8ecf4`, `Paper` `#ffffff`.
- Радиусы: `Paper` — 14, кнопки — 12; в приложении часто используется
  `borderRadius: 2` через `sx` для внутренних блоков.
- Пузыри сообщений:
  - Свои `shared` — фон `primary.main`, текст `primary.contrastText`,
    правое выравнивание.
  - Чужие `shared` — `background.paper`, `divider` рамка.
  - `internal` (внутренние заметки) — `#fff7ed` фон, оранжевая **пунктирная**
    рамка, шапка-плашка «Внутренняя заметка склада · селлер этого не увидит».
- Плашки статусов документов — в `src/common/StatusChip.tsx` с
  фиксированным набором цвет+фон на каждый статус (`draft`, `submitted`,
  `in_progress`, `confirmed`, `shipped`, `closed`, `discrepancy`).
- Аватары — `src/common/PersonaAvatar.tsx` и `src/common/SellerAvatar.tsx`,
  прямоугольные (`variant="rounded"`), инициалы по 2 буквы, фон из
  фиксированной палитры на актора/селлера.

`Row`/`Col` (`src/common/Row.tsx`) — тонкие обёртки над `Box display=flex`.
Причина: в MUI 9 `Stack` больше не принимает `alignItems`/`justifyContent`
как отдельные props (только через `sx`). `Row align="…" justify="…" spacing={…}`
даёт короткий читаемый API и совместим с MUI 9.

## 5. Контракты взаимодействия (что Codex обязан сохранить)

Перечень швов, которые Codex подключит к реальному API. Форматы данных
подобраны так, чтобы бэкенд мог отдавать их напрямую в редьюсер.

### 5.1. Полезные типы

Все — в `src/types.ts`. Ключевые:

- `Conversation` (`id`, `kind`, `sellerId?`, `warehouseId?`, `documentId?`,
  `title`, `subtitle?`, `pinned`, `archived`, `muted`, `participantIds`,
  `lastMessageId?`, `unreadIds`, `mentionIds`, `followupOpen`).
- `Message` (`id`, `conversationId`, `authorId`, `createdAt`, `editedAt?`,
  `deletedAt?`, `kind` = `text|system|document_card|deleted`,
  `visibility` = `internal|shared`, `text?`, `attachments?`, `reactions?`,
  `mentions?`, `replyToId?`, `threadRootId?`, `documentRef?`, `followup?`,
  `status` = `sending|sent|failed`, `readBy`, `clientMessageId?`,
  `systemPayload?`, `threadReplyCount?`).
- `Attachment` (`id`, `name`, `size`, `mime`, `kind` = `image|file`,
  `dataUri?`, `blobUrl?`, `uploadStatus` = `uploading|done|failed`,
  `uploadProgress`, `failReason?`, `width?`, `height?`).
- `NotificationEntry`, `NotificationPrefs`, `WmsDocument`, `DocLine`,
  `DocumentEvent`, `Role`, `Viewport`, `Actor`, `Seller`, `Warehouse`.

Все идентификаторы — строки, генерируются клиентом при отправке через
`clientMessageId`. Идемпотентность повторной отправки — по этому полю.

### 5.2. UI-действия и что они должны делать в бэкенде

| UI-действие | Что уже делает клиент | Что должен делать бэкенд |
|-------------|-----------------------|--------------------------|
| Открыть канал | `actions.openConversation(id, opts)` → `select_conversation`, `mark_read`, hash-navigate | `GET /chat/conversations/{id}`, `POST /chat/conversations/{id}/read` (батч по `messageIds`). |
| Отправить сообщение | `actions.sendMessage(convId, payload)` → добавляет `Message` со `status: 'sending'`, вложения проходят фейковый прогресс | `POST /chat/conversations/{id}/messages` с телом `text`, `visibility`, `attachments[]`, `mentions[]`, `reply_to_id?`, `thread_root_id?`, `document_ref?`, `client_message_id`. WS-event `message.created`. |
| Ответить в треде | Тот же путь, но с `threadRootId` | Тот же ресурс, тот же контракт. |
| Реакция | `dispatchData({ type: 'toggle_reaction', … })` | `POST /chat/messages/{id}/reactions` (toggle). WS-event `reaction.added/removed`. |
| Followup | `dispatchData({ type: 'toggle_followup', … })` | `POST /chat/messages/{id}/followup` (state `open`/`resolved`, `assignee_id?`). WS-event `followup.changed`. |
| Правка | `update_message` + `editedAt` | `PATCH /chat/messages/{id}`; бэкенд хранит историю правок. |
| Удаление | `delete_message` (soft) | `DELETE /chat/messages/{id}`; в ленте остаётся тумба. |
| Пин/мьют/архив канала | `dispatchData({ type: 'pin'|'mute'|'archive', … })` | `PATCH /chat/conversations/{id}` с соответствующим флагом. |
| Пикер документа | Открывает `Dialog`, читает `documentById` | `GET /chat/documents?seller_id=&kind=&q=` (или общий каталог документов через уже существующий доступ). |
| Открыть документ | `dispatch({ type: 'open_document', documentId })` — drawer с сообщением «перейдите в раздел» | Прототип **не** отдаёт управление реальному разделу; в интеграции — редирект в существующий экран приёмки/отгрузки/FBS/возврата. |
| Загрузка вложения | Клиент делает фейковый прогресс, при `forceUploadFail` — `failed` + retry | `POST /chat/attachments` (multipart), возвращает `id`, дальше `attach_to_message`; после `POST /chat/messages` — привязка. Антивирус — на бэкенде. |
| Скачать вложение | `<a href={dataUri ?? blobUrl}>` в лайтбоксе | `GET /chat/attachments/{id}/download` с проверкой прав получателя (см. §5.5). |
| Кросс-канальный поиск | Клиентский фильтр по seed | `GET /chat/search?q=&seller_id=&has_attachment=&has_document=` — той же формы результат `{message, conversation_title, before, after, match_start}`. |
| Центр уведомлений | Из `data.notifications`, `dispatchData({ type: 'notif_read'|'notif_read_all' })` | `GET /chat/notifications`, `POST /chat/notifications/{id}/read`, `POST /chat/notifications/read_all`. |
| Preferences | `dispatch({ type: 'set_prefs', … })`, локально | `PATCH /chat/notifications/preferences`. |

### 5.3. Реалтайм-транспорт

Прототип обходится без WS — реалтайм имитируется одной вкладкой на одной
машине. Контракт для бэкенда — как в требованиях: WS `/chat/ws` c
event-типами `message.*`, `reaction.*`, `followup.*`, `read_receipt.*`,
`conversation.*`, `attachment.status_changed`. Fallback long-poll — 3–5 сек.

Если WS упал — клиент обязан честно показывать «нет реального времени»
(в прототипе это баннер оффлайна; в интеграции — тонкая полоска в топ-баре).

### 5.4. Deep-link и якоря

Формат URL зафиксирован в `parseRoute` в `src/App.tsx`. Основной путь
для уведомлений/писем:

```
<origin><path>#/c/<conversationId>?msg=<messageId>
<origin><path>#/c/<conversationId>/t/<threadRootId>?msg=<messageId>
```

Клиент по этому URL сам выполнит `openConversation`, `mark_read` и
прокрутит/подсветит нужное сообщение. Уведомления и digest email должны
формировать именно эту схему, разве что hash → path-сегменты, если
основной фронт использует `BrowserRouter`.

### 5.5. Инварианты видимости и доступа (обязательны к сохранению)

Эти инварианты уже реализованы в прототипе через `visibleMessagesForActor`
и `conversationAccessible` в `src/state/selectors.ts`. Бэкенд обязан
дублировать их серверно — на клиента полагаться нельзя:

1. **Селлер не видит `visibility: 'internal'` ни в одном ответе API**:
   ни в `GET messages`, ни в `search`, ни в `notifications`, ни в
   `conversation.last_message`. Клиент не должен получать «отфильтруй
   сам»; для селлера этих сущностей просто не существует.
2. **Селлер не видит каналы других селлеров и внутренние каналы склада.**
   Селлеру `warehouse_internal` не отдаётся.
3. **Ссылки-якоря валидируются по правам получателя.** Прямой вход по
   ссылке на чужой канал или на internal-сообщение возвращает 403 и
   экран «Нет доступа» (в прототипе — состояние `permissionDenied`).
4. **Приглашения участников — только у админа ФФ.** Правило дизайна;
   бэкенд возвращает 403 остальным ролям.
5. **Чат ничего не двигает по складу.** Ни реакция, ни followup, ни
   прочтение, ни удаление сообщения не должны иметь побочных эффектов
   в модулях приёмки, отгрузки, FBS, упаковки, резерва и биллинга. См.
   третье главное правило `AGENTS.md`.
6. **Идемпотентность отправки** по `client_message_id` (уникально в
   пределах суток).

### 5.6. Что оставлено намеренно на потом

- Виртуализация ленты сообщений. Прототип рендерит всю ленту сразу;
  реальные каналы после месяца-двух работы получат хвосты в тысячи
  сообщений — виртуализацию (`react-virtual` или аналог) добавляет тот
  же Opus в отдельном заходе, без изменения визуальной композиции
  пузыря.
- WebSocket-транспорт (см. §5.3).
- Пагинация истории `?before=<messageId>`. Клиент готов принимать
  список сообщений одной страницей и мержить в `messagesByConversation`.
- Реальная антивирус-проверка вложений. В прототипе загрузка помечает
  все успешные вложения как `done` сразу же (или как `failed` по
  демо-флагу).
- Экспорт/аудит правок сообщений. Правки в прототипе хранятся только в
  `editedAt` (без истории). Бэкенд должен сохранять историю (для админа).

## 7. Клавиатура и доступность

Не потрачено времени на кастомные фокус-траки; используются штатные
`Tab`/`Shift+Tab` от MUI. Что уже сделано:

- Enter в композере — отправка, `Shift+Enter` — новая строка.
- Enter на строке инбокса — открыть канал.
- `Esc` — закрыть лайтбокс; `←`/`→` — переключение между изображениями
  вложения одного сообщения.
- `aria-label` на всех иконочных кнопках, `data-testid` на ключевых
  контейнерах (`chat-app`, `inbox`, `conversation-screen`, `composer`,
  `context-panel`, `participants-drawer`, `doc-preview-drawer`,
  `search-screen`, `notifications-screen`, `prefs-screen`).
- Immutable-safe контраст: пузыри `shared` — тёмный/светлый по фону
  собственного/чужого сообщения, `internal` — оранжевый на бежевом с
  явной плашкой (не только цветом).

Что осталось: полноценные skip-links, ARIA-live для нового сообщения в
открытой ленте, тактика фокуса при закрытии drawer'ов (сейчас MUI
возвращает фокус на элемент-триггер по умолчанию, чего в большинстве
кейсов достаточно). Аудит доступности отдельно с продуктом.

## 8. Известные ограничения прототипа

1. **Реального времени нет.** Все действия — только в одной вкладке.
   Второй пользователь на второй вкладке видит другой in-memory стейт.
2. **Виртуализации ленты нет.** С сотнями сообщений производительность
   упадёт.
3. **Пагинации истории нет.** Все сообщения загружаются сразу из seed.
4. **Настоящих push-уведомлений нет.** Есть только запрос
   `Notification.requestPermission()`, чтобы показать реалистичную
   ветку «разрешено / запрещено».
5. **Email digest не отправляется.** Просто UI-переключатель.
6. **Загрузка вложений — фейковый прогресс.** Реальные `File`
   обрабатываются через `URL.createObjectURL`, EXIF не чистится,
   антивирус не считается. Реальный контракт — на бэкенде.
7. **Аудит правок сообщений не сохраняется.** Только `editedAt`.
8. **Правки времени.** «Сегодня»/«Вчера» считаются от системного времени
   пользователя, а seed вшит в `2026-09-08`. Живая интеграция будет
   считать от `now()` относительно реального `createdAt`.
9. **Драфты — в памяти вкладки.** Перезагрузка страницы теряет их.
   При интеграции — вынести в `sessionStorage` или в бэкенд (по
   решению владельца).
10. **Роль «наблюдатель»** и полноценный аудит — вне прототипа.
11. **Проверки прав в UI — не защита.** Бэкенд обязан валидировать
    все инварианты §5.5 серверно; клиент опирается на них только для
    удобства (`visibleMessagesForActor`, `conversationAccessible`).
12. **Не проверен вручную в браузере автором дизайна.** Это макет и
    интерактивный чертёж; браузерный проход, `vite build` и
    `tsc -b --noEmit` выполняет Codex как проверяющий и возвращает
    замечания в ту же сессию Opus. Правки в React-исходниках вносит
    Opus, не Codex.

## 9. Открытые вопросы для владельца

Дублирую из `REQUIREMENTS_RU.md` §12, чтобы не потерялось:

1. Реальные лимиты вложений (25 МБ / 100 МБ / 10 файлов) — сейчас взяты
   с потолка.
2. Digest email — нужен ли в MVP.
3. Роль «наблюдатель» — включаем или откладываем.
4. Хранение вложений: общий бакет или per-tenant (влияет на биллинг).
5. Кому доступен аудит правок — только админ ФФ или ещё «супервайзер
   селлера».
6. Автосоздание канала при первом сообщении, а не при появлении
   документа — согласны ли операторы работать без пустых каналов.

Прототип демонстрируется без ответов на эти вопросы; финальный бэкенд
должен их зафиксировать.

## 10. Что не переделывается без владельца (и почему Codex не правит React-код сам)

Все правки в исходниках прототипа — включая устранение будущих ошибок
компиляции, миграции под новые версии MUI/TS и мелкую техническую
уборку — вносит Opus. Codex в этой задаче отвечает за проверки
(`vite build`, `tsc -b --noEmit`, ручной браузерный проход) и передаёт
диагностику обратно. Это разделение сознательное: точечные правки уже
трижды успевали смещать дизайн, а автор один.

Отдельно защищены от переделки без согласования с владельцем:


- Композицию канала (три колонки на десктопе, drill-down на мобильном).
- Различие `internal` vs `shared` (фон, рамка, плашка, скрытие для
  селлера).
- Отсутствие «личных сообщений» между сотрудниками — это сознательное
  решение (см. требования).
- Правило «приглашает только админ ФФ» — если оператору надо звать
  своих, это отдельная задача.
- Формат карточки документа и её кнопки «Открыть документ». Открывать
  документ внутри чата — плохой сценарий: приведёт к параллельному
  редактированию и ошибкам.
- Плашку «Демо · локальный макет» в топ-баре. Убирается при переносе в
  production сборку, но в прототипе она обязательна: слишком легко
  спутать демо с реальностью.

Все прочие правки — стилистические, шрифтовые, размерные — по-прежнему
вносит Opus, а не Codex. Если что-то из перечисленного окажется явно
неверным или неудобным на браузерном проходе, Codex фиксирует это как
замечание, а не переписывает исходники прототипа сам.
