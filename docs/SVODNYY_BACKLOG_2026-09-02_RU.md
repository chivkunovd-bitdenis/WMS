## Ozon: отдельно

Процесс **нерабочий**. Код есть — около 5 800 строк, шесть миграций, 83 зелёных
теста, экраны на фронте. Но наружу уходит ровно один настоящий запрос: проверка
пары ключей через `POST /v1/seller/info` (`ozon_client.py:95`). Всё остальное
ходит в `FakeMarketplaceTransport` — единственную реализацию транспортного
интерфейса во всём репозитории.

Отказ вшит намеренно в четырёх местах: `_run_blocked_ozon_fake`
(`api/fbs_orders.py:223`), `_blocked_ozon_provider`
(`fbs_autopoll_service.py:98`), `_blocked_ozon_unload_provider`
(`marketplace_unload_service.py:119`) и `ozon_live_handoff_blocked`
(`fbs_shipment_service.py:1505`). Есть тест, который **закрепляет** это падение.

Причина зафиксирована 25.08 в `tasks/ozon-integration-20260825/TASK.md:43-52`:
кабинет заблокирован самим Ozon, любой метод отвечает
`403 {"code":7, "message":"Company is blocked"}`. Ключи при этом валидные.
**Сегодня блокировку никто не перепроверял.**

Отдельная дыра помимо транспорта: привязку склада Ozon **создать нечем**.
Публикация остатков ищет привязки с `marketplace == "ozon"`
(`ozon_fbs_sync_service.py:129`), а сервис создания это поле не выставляет
вовсе, и в модели стоит `default="wb"`. Даже с рабочим транспортом остатки не
поедут, а заказы лягут как «склад не сопоставлен».

Ещё: QR поставки и этикетка заказа Ozon — base64 прозрачного пикселя 1×1
(`_FAKE_OZON_SUPPLY_QR`, `_FAKE_OZON_LABEL_PNG_BASE64`). Импорта товаров нет,
связь заводится руками через `PATCH /products/{id}/ozon-link`. Мобильный ТСД про

### Живое и не начатое

**38. Импорт каталога WB обрывается после первой сотни карточек** (D19). Цикл в
`wildberries_product_sync_service.py:66` выходит по условию
`len(total_cards) >= total_hint`, где `total_hint` — это `cursor.total` из ответа
WB, то есть число карточек **в текущем ответе**, а не всего. После первой
страницы условие срабатывает. Строка не менялась с создания файла. У любого
продавца с каталогом больше сотни товаров часть ассортимента физически
недоступна для заведения остатка.

**39. Фоновой синхронизации каталога товаров нет вообще** (D20). В расписании
Celery шесть задач: склады WB, низкий запас маркировки, автоопрос заказов,
полная сверка, статусы, сверка остатков. Каталога среди них нет — только ручной
запуск.

**40. Проверка «можно ли везти на ПВЗ» вырезана и закреплена тестом** (I14).
`fbs_supply_validator_service.py:295-296` — `pvz_allowed_count=len(orders),
pvz_blocked_count=0` захардкожено, поле `can_pvz` в валидаторе не читается
вообще, хотя приезжает от WB и хранится в модели. Тест
`test_fbs_supply_from_orders.py:427` — `test_tc05_preflight_pvz_ignores_legacy_can_pvz_gate`
— прямо утверждает, что заказ с `can_pvz=False` считается разрешённым к ПВЗ.
Обоснования, почему флаг признан устаревшим, в репозитории нет. **Это решение
владельца, а не баг для молчаливой починки:** либо флаг действительно не нужен,
либо оператор сегодня может отправить на пункт выдачи то, что туда нельзя.
